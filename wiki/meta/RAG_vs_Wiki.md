# RAG vs Wiki 模式

## 背景

这是两种截然不同的使用 LLM 管理知识的范式。[[agent/RAG/RAG]] 是当前主流的 LLM 知识增强方案；Wiki 模式（参见 [[meta/LLM_Wiki_方法论]]）是一种新兴的替代方案，强调知识的**持久化编译**而非实时检索。

## 对比表

| 方面 | RAG（检索增强生成） | Wiki 模式（持久化编译） |
|------|---------------------|----------------------|
| **核心隐喻** | 图书馆管理员（每次查找） | 程序员（编译一次，持续更新） |
| **知识处理时机** | 查询时实时检索 | 提前编译，持续更新 |
| **交叉引用** | 每次查询时重新发现 | 预先建立，自动维护 |
| **矛盾检测** | 依赖查询时偶然发现 | 系统性标记和追踪 |
| **知识累积** | 无累积，每次从零开始 | 持久化累积，复合增值 |
| **维护成本** | 无需维护 | LLM 自动维护（近零成本） |
| **深度综合** | 受限于检索窗口 | 可整合全部已读来源 |
| **基础设施** | 需要向量数据库、嵌入模型 | 仅需 Markdown 文件 + 索引 |
| **可解释性** | 检索过程不透明 | wiki 页面可直接阅读和审查 |
| **适用规模** | 大规模文档集（数百万文档） | 中等规模（~100 来源，数百页面） |

## 深入分析

### RAG 的核心局限

1. **无累积性**：每次查询都从原始文档开始检索，之前的所有分析和理解都不保留。一个需要综合 5 篇文档的微妙问题，每次都必须重新找到并拼接相关片段。
2. **无综合**：RAG 生成的答案消失在聊天历史中，不会反馈到知识库。用户问出的好问题、得到的好答案都白白浪费。
3. **检索精度瓶颈**：语义检索在需要跨文档综合的复杂问题上效果有限——它擅长找到"相关片段"，但不擅长"整合理解"。

### Wiki 模式的核心优势

1. **知识编译**：来源被"编译"进 wiki——提取关键信息、建立交叉引用、标记矛盾。后续查询直接读取编译产物，无需从原始文档重新检索。
2. **答案归档**：查询产生的有价值答案（对比、分析、新发现）可以归档回 wiki 作为新页面——探索的成果持续累积。
3. **维护近零**：LLM 承担所有维护工作——更新交叉引用、标记矛盾、保持一致性。人类放弃 wiki 是因为维护负担增长快于价值；LLM 不会厌倦。

### 互补而非替代

两者并非完全对立：
- **RAG 适合大规模检索**：当来源数量达到数千或数百万时，wiki 模式的人工策展成本不可承受
- **Wiki 适合深度积累**：当需要长期、深入地理解一个领域时，wiki 模式的累积性无可替代
- **可能的结合**：在 wiki 上层构建搜索（如 [[tools/qmd]]），实现"编译 + 检索"的混合方案

## 适用场景

| 场景 | 推荐方案 | 原因 |
|------|----------|------|
| 个人知识管理 | Wiki | 来源有限，需要深度综合 |
| 学术研究 | Wiki | 需要长期积累和跨来源整合 |
| 读书笔记 | Wiki | 内容固定，需要建立连接 |
| 企业文档问答 | RAG | 文档量大，需要广覆盖 |
| 客服知识库 | RAG | 需要快速检索大量 FAQ |
| 竞争分析 | Wiki | 需要持续跟踪和深度分析 |

## 演化脉络

```

       ↓

       ↓
RAG (2020s)            — LLM + 检索，但无累积性
       ↓
LLM Wiki (2026+)       — LLM 做维护，实现 Memex 的完整愿景
```
