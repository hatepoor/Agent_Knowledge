# 已知陷阱与边界

> 本页是**集中索引**：把散落在各页的坑按来源分类，便于速查；每条给「现象 → 根因 → 应对」。

## 核心结论

- 大部分坑集中在 **DOCX 解析**（坐标缺失、图片导出语义、装饰图过滤）与 **分块 / tokenizer**（默认联网加载模型）。
- 一个贯穿性的隐蔽问题是「**静默失效**」：PDF 专用选项用在 DOCX 上不报错、只是无效；这让很多「为什么我的配置没生效」的排查浪费大量时间。
- 每条都尽量链接到详解页，方便深入。结尾给出**上线前自查清单**（10 条），建议作为发布 RAG / 解析流水线的硬性门禁。

## 机制与原理

为什么 DOCX 与 PDF 的坑差异这么大？根源在于管线不同：

- DOCX / HTML / MD / CSV 等走 **`SimplePipeline` + 声明式后端**（如 `MsWordDocumentBackend`，基于 python-docx），**不含任何 ML 模型**，因此没有坐标、没有版面识别、没有图片描述能力。
- 只有 **PDF** 才有 ML 管线（`StandardPdfPipeline` / `NativePdfPipeline` / `VlmPipeline`），`PdfPipelineOptions` 里的图片、OCR、表格、VLM 选项只对它生效。

理解这一点，下面 90% 的 DOCX 陷阱都能一夜想通：**DOCX 不是「简化版 PDF」，它是另一套无模型的管线**。

## 实操

### DOCX 相关

**1. 没有页码、没有坐标**
- 现象：遍历 `DoclingDocument` 时，`PictureItem.prov` 是空列表，`prov` 里既没有页码也没有 bounding box。
- 根因：DOCX 是流式排版格式，本身**没有固定分页概念**（一页显示多少内容由渲染器/视图决定），docling 因此不提供定位坐标。
- 应对：用 `self_ref`、标题链、文档流序号做替代锚点；若业务确实需要页码/坐标，先把 DOCX 转 PDF 再解析。

**2. `generate_picture_images=True` 是误传**
- 现象：网上常见「给 DOCX 设 `generate_picture_images=True` 就能拿到图片」，实际无效。
- 根因：该参数只存在于 PDF 管线，`msword_backend.py` 全文零次出现，Word 后端根本不读它。
- 应对：DOCX 下直接调用 `pic.get_image(doc)` 必定返回 PIL 对象，无需也不该设这个开关。

**3. Markdown 里图片只剩占位符**
- 现象：`export_to_markdown()` / `save_as_markdown()` 导出的文本中，图片位置只有 `![]()` 之类的占位符，图片本体不在文件里。
- 根因：导出期参数 `image_mode` **默认 `ImageRefMode.PLACEHOLDER`**——这是导出层的开关，与解析无关。
- 应对：改为 `ImageRefMode.REFERENCED`（外链到图片文件）或 `ImageRefMode.EMBEDDED`（Base64 内嵌）；若只要 PIL 对象，直接走元素层 `pic.get_image(doc)`。

**4. 图注不会自动关联**
- 现象：`PictureItem.captions` 是空列表，`caption_text(doc)` 返回空串，图片和「图 1：xxx」对不上。
- 根因：Word backend 构造图片时传的是 `caption=None`，docling 不会去相邻段落推断图注。
- 应对：自己从图片相邻段落提取图注文本（做法见 [[rag/01_多源数据接入/图片提取与描述化|图片提取与描述化]]）。

**5. EMF / WMF 静默变 None**
- 现象：Office 里粘贴进来的图表常是 EMF / WMF 格式，解析后对应图片为 `None`。
- 根因：Pillow 读不了 EMF / WMF；docling 的兜底路径是把它们转 PDF 再渲染，**没装 LibreOffice 时兜底失败，该图直接为空**。
- 应对：确保环境装了 LibreOffice（用于 EMF/WMF → PDF 渲染）；或要求上游提供 PNG/JPEG 版的图片。

**6. 外部链接的图片被跳过**
- 现象：`doc.pictures` 里少了几张图，日志只有 warning，没有报错。
- 根因：Word backend 判断 `rel.is_external`，对外部链接的图片只发 warning 并返回 `None`，不内联下载。
- 应对：若需要这些图，预处理阶段把外部图片下载并改为内嵌；或确认源文档的「链接图片」本就不应入库。

**7. 装饰图被自动过滤（不是 bug）**
- 现象：一些小的分隔线、背景图标在遍历时「消失」了。
- 根因：面积 ≤ 25 平方像素、全透明、或纯白的图，会被归入 `ContentLayer.INVISIBLE`；而 `iterate_items()` 默认只遍历 `{ContentLayer.BODY}`。
- 应对：若确实需要这些装饰元素，显式传 `included_content_layers` 包含 `INVISIBLE` 再遍历。

**8. 同一位置多图被打包**
- 现象：遍历时某个 item 下还套着一组图，结构比预期深一层。
- 根因：同一位置的多个图片会被归入一个 `GroupLabel.PICTURE_AREA` 组。
- 应对：遍历时注意层级，遇到 `PICTURE_AREA` 组要递归展开其成员，避免漏数或误把组当单图。

### PDF 相关

**9. PDF 专用选项对 DOCX 静默无效（对照 DOCX 第 2 条）**
- 现象：把 `PdfPipelineOptions` 的 `do_picture_description`、`generate_picture_images` 用在 DOCX 转换上，配置「像生效了」但图片描述/渲染毫无变化。
- 根因：这些选项只在 PDF 的 ML 管线里被读取，DOCX 的 `SimplePipeline` 根本不碰 `PdfPipelineOptions`。
- 应对：选项与格式必须配对——图片描述/渲染只配在 `PdfPipelineOptions`（并经 `PdfFormatOption` 传入）；DOCX 要图片直接走 `pic.get_image(doc)`。

> PDF 自身的能力边界（版面/OCR/表格需模型、文本层可走 `NativePdfPipeline` 无模型）详见 [[docling/08_格式支持与依赖管理|格式支持与依赖管理]]。

### 分块相关

**10. `HybridChunker` 的 tokenizer 默认要联网**
- 现象：第一次分块卡很久甚至超时失败，报 HuggingFace 下载相关错误。
- 根因：默认 tokenizer 是 `sentence-transformers/all-MiniLM-L6-v2`，需访问 HuggingFace 拉模型权重。
- 应对：设 `HF_ENDPOINT=https://hf-mirror.com` 走镜像；或换 `OpenAITokenizer`（需 `docling-core[chunking-openai]`）；或自定义 `BaseTokenizer` 子类彻底离线。

**11. `HybridChunker(max_tokens=512)` 仍触发 HF 加载**
- 现象：明明只想本地跑、只设了 `max_tokens`，却还是去下载 MiniLM。
- 根因：`max_tokens` 只是预算参数，不替代 tokenizer；只要没显式传 `tokenizer=`，就走默认的联网 tokenizer。
- 应对：要完全避开 HF 加载，必须显式传 `tokenizer=`（如 `OpenAITokenizer` 或自定义实现）。

**12. `max_tokens` 是含标题链的总预算**
- 现象：每个 chunk 的 token 数明显小于你设的 `max_tokens`，像是被「偷偷砍了一刀」。
- 根因：源码里 `available_length = max_tokens - other_len`，`other_len` 是标题链与 caption 的 token 数，`max_tokens` 是「标题 + 正文 + 图注」的总预算而非纯正文预算。
- 应对：估算正文容量时主动给标题/图注留余量；若正文明显被截断，适当调大 `max_tokens`。

**13. 忘了装 `docling-core[chunking]`**
- 现象：代码写到 `from docling.datamodel.base import ...` 没问题，一调 `HybridChunker` 就抛 `ImportError`（semchunk 缺失）。
- 根因：semchunk 是 `feat-chunking` 引入的，缺失时**在运行时**才报 `ImportError`，不是导入期。
- 应对：分块场景安装时显式加 `docling-core[chunking]`（或 `docling-slim[feat-chunking]`），CI 里加一条 import `HybridChunker` 的健康检查提前暴露。

### 依赖相关

**14. 纯 DOCX 仍必须装 `docling-parse` 与 `pypdfium2`**
- 现象：只处理 `.docx`，装了 `docling-slim[format-docx]` + `convert-core`，一 `import DocumentConverter` 就 `ModuleNotFoundError`（先报 `docling_parse`，补齐后又报 `pypdfium2`，再补又报 `scipy`）。
- 根因：`DocumentConverter` 的导入链会连带触发 PDF 后端，所以 PDF 相关实现包即使不用也**必须存在**。
- 应对：按「`docling_parse → pypdfium2 → scipy`」顺序逐个补齐；或干脆按 [[docling/08_格式支持与依赖管理|格式支持与依赖管理]] 的决策表把最小组合一次性装齐。

**15. 装了 `[standard]` 但用不上模型**
- 现象：环境里 `torch`、`docling-ibm-models` 占了数百 MB，实际只解析 Office / HTML / Markdown。
- 根因：`standard` 组合默认带 torch 全家桶，但对声明式格式完全用不到 ML。
- 应对：纯 Office / HTML / Markdown 场景改用 `docling-slim[format-*]`，别碰 `standard` / `models-local`。

### 通用

**16. 把 PDF 专用选项用在 DOCX 上（静默无效）**
- 现象：见 PDF 第 9 条。强调：这是跨格式的通用坑，排查「配置不生效」时优先怀疑「选项与格式不匹配」。
- 应对：选项归属核对——`PdfPipelineOptions` 只进 `PdfFormatOption`；DOCX 走 `WordFormatOption`（其 `pipeline_cls = SimplePipeline`，无 ML 选项）。

**17. 换 embedding 模型后忘记重建索引**
- 现象：切换 embedding 模型 / 维度后检索质量骤降，或出现维度不匹配报错。
- 根因：向量空间随模型改变，旧索引对应的向量分布已作废，新查询向量与旧库不在同一空间。
- 应对：任何 embedding 模型升级都视为「索引全量重建」的触发条件，在流水线里把「模型版本」记入索引元数据并做一致性校验（见 [[rag/01_多源数据接入/Word解析|Word 解析]] 相关 RAG 实践）。

## 上线前自查清单

发布解析 / RAG 流水线前逐条确认：

1. **格式与 extras 匹配**：确认安装组合只含实际用到的格式 extras，DOCX / HTML / MD 场景未误装 `torch`。
2. **最小依赖齐备**：纯 DOCX 环境已装 `docling-parse` + `pypdfium2` + `scipy`，导入 `DocumentConverter` 不报 `ModuleNotFoundError`。
3. **表格未错位**：抽查 20–50 页含复杂表格的文档，确认合并单元格 / 跨页表未被截断或错位。
4. **图片都提取出来**：确认图片数符合预期，特别排查 EMF / WMF（需 LibreOffice）与外部链接图片（被跳过）两种情况。
5. **页眉页脚 / 装饰图已处理**：确认不需要的 `ContentLayer.INVISIBLE` 装饰元素已被过滤或按需保留。
6. **DOCX 定位锚点方案**：确认因 DOCX 无坐标，已用 `self_ref` / 标题链 / 文档流序号替代页码锚点（需页码则先转 PDF）。
7. **图片导出语义正确**：Markdown 导出已按需要设置 `ImageRefMode`（REFERENCED / EMBEDDED），而非默认 PLACEHOLDER。
8. **图注已补全**：确认 `captions` 为空时已从相邻段落自行提取图注。
9. **tokenizer 能离线工作**：分块用的 `HybridChunker` 已显式传 `tokenizer=`，或配好 `HF_ENDPOINT` 镜像，CI 可离线跑通。
10. **embedding 模型变更已重建索引**：确认当前索引的 embedding 模型版本与查询端一致，旧索引已废弃重建。
