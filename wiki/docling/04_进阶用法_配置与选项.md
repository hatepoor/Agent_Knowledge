> Docling 的「配置面」分两层：选哪个后端/管线（format_options），以及管线内部怎么跑（pipeline_options）。把层级搞混是最常见、且最隐蔽的坑。

## 核心结论

1. `DocumentConverter(format_options={...})` 的 `format_options` 是「按输入格式绑定后端+管线」的开关字典；真正的行为参数（`do_ocr`、`images_scale` 等）嵌在每种格式的 `FormatOption.pipeline_options` 里。
2. PDF 专用选项（OCR、表格结构、页面/图片渲染、图片描述）对 DOCX 等走 SimplePipeline 的格式**完全无效且静默**——因为那些格式根本不读 `PdfPipelineOptions`。
3. 想省资源：纯 Office 用细粒度 extras；想快：关掉 PDF 的 `generate_page_images` 与 `do_ocr`；想上 GPU：改 `accelerator_options.device`。

## 机制与原理

### 两类选项的分工

- **`format_options`（顶层）**：`dict[InputFormat, FormatOption]`。决定「这个格式用哪个 backend、哪个 pipeline」。例如 `{InputFormat.PDF: PdfFormatOption(pipeline_options=..., backend_options=...)}`。
- **`pipeline_options`（内嵌）**：挂在具体 `FormatOption` 里，描述「这条管线内部怎么处理」。对 PDF 是 `PdfPipelineOptions`，对原生 PDF 是 `NativePdfPipelineOptions`，对 VLM 场景是 `VlmPipelineOptions`，音视频还有各自管线选项。
- **`backend_options`**：同样内嵌于 `FormatOption`，控制底层解析器（如 PDF 的 `PdfBackendOptions.include_bitmap_images`）。

关键点：`DocumentConverter.__init__` 在 2.129.x 只接受 `allowed_formats` 与 `format_options` 两个参数，**没有**顶层 `pipeline_options`。所有管线级开关都要写进对应格式的 `FormatOption` 内部。

## 实操

### pipeline options 的层次

| 选项类 | 适用 | 是否含 ML 模型 | 关键能力 |
|---|---|---|---|
| `PdfPipelineOptions` | 普通 PDF | 是（layout/OCR/表格/图片描述） | 全功能 PDF 管线 |
| `NativePdfPipelineOptions` | 原生 PDF（docling-parse） | 否 | 纯解析、无模型，靠 `parser_threads` 并行 |
| `VlmPipelineOptions` | VLM 推理管线 | 是（视觉语言模型） | 文档理解/图片描述 |
| ASR 相关选项 | 音频/视频格式 | 是 | 语音转写 |

### 常用开关一览（多数只对 PDF 生效）

| 开关 | 所属类 | 含义 | 仅 PDF |
|---|---|---|---|
| `images_scale` | `PdfPipelineOptions` | 渲染分辨率，像素/点（影响 page/picture 图清晰度） | 是 |
| `generate_page_images` | `PdfPipelineOptions` | 把每页渲染图挂到 `page.image` | 是 |
| `generate_picture_images` | `PdfPipelineOptions` | 把 PDF 内嵌位图挂到 `PictureItem`（需 backend `include_bitmap_images=True`） | 是 |
| `do_ocr` | `PdfPipelineOptions` | 是否对扫描页/图片做 OCR | 是 |
| `do_table_structure` | `PdfPipelineOptions` | 是否识别表格结构（出 `TableItem.data`） | 是 |
| `do_picture_description` | `PdfPipelineOptions` | 是否用 VLM 生成图片文字描述 | 是 |
| `table_structure_options.mode` | `PdfPipelineOptions` | 表格解析模式（如 ACCURATE / FAST） | 是 |
| `parser_threads` | `NativePdfPipelineOptions`/`PdfPipelineOptions` | PDF 解析工作线程数，默认「CPU 线程数−1」 | 是 |

> DOCX 走 `SimplePipeline` + `MsWordDocumentBackend`，以上 PDF 专用开关一个都不读；DOCX 没有 OCR、没有页面渲染、没有表格结构识别（Word 自带结构）。

### 导出模式全解（ImageRefMode）

导出期用 `image_mode` 控制图片如何处理，三值对比：

| 模式 | 行为 | 何时用 |
|---|---|---|
| `PLACEHOLDER`（默认） | 图片位置只留 `<!-- image -->` 注释 | 只要正文文本、不在乎图 |
| `REFERENCED` | 图片落盘到 `artifacts_dir`，Markdown 写相对路径引用 | 需要图文分离、图片入库/单独处理 |
| `EMBEDDED` | 图片以 base64 内嵌进文档 | 单文件自包含、便于传输 |

`artifacts_dir` 与 `image_dir`：`REFERENCED` 时图片落在 `artifacts_dir`（默认与输出文件同目录的子目录），`image_dir` / `image_uri_prefix` 可进一步定制引用前缀。`save_as_markdown(..., image_mode=..., artifacts_dir=...)` 是图片落盘的入口。

### 批量转换

Python API 没有「目录批量」方法，通常两种做法：

```python
from pathlib import Path
from docling.document_converter import DocumentConverter

conv = DocumentConverter()
src_dir = Path("./corpus")
for p in sorted(src_dir.rglob("*")):
    if not p.is_file():
        continue
    try:
        result = conv.convert(str(p))
        out = Path("./out") / (p.stem + ".md")
        out.parent.mkdir(parents=True, exist_ok=True)
        result.document.save_as_markdown(str(out))
    except Exception as e:               # 失败隔离：单个文件出错不影响整批
        print(f"跳过 {p.name}: {e}")
```

**失败隔离是重点**：单个文件转换异常（损坏、不支持子格式）不应中断整批，所以每个文件独立 `try/except`，并可用 `result.status` 判断是否成功。等价地，CLI 的 `docling ./corpus --to md --output ./out` 已在内部实现批量与隔离。

### 并发与线程

两套并行参数不要混淆：
- **`parser_threads`**：PDF 解析器的工作线程数（无模型管线靠它并行），默认 CPU 线程数−1。
- **`accelerator_options.num_threads`**：模型推理的 CPU 线程数，默认 4（可用 `DOCLING_NUM_THREADS` 或 `OMP_NUM_THREADS` 覆盖）。

若用 `docling-serve` 部署做并发服务，进程级 worker 数需要另外留意（如 uvicorn worker 数）以避免 CPU 争用——**具体环境变量名与默认值（待核实）**，以 `docling-serve` 官方部署文档为准。

### 加速器配置

```python
from docling.datamodel.pipeline_options import PdfPipelineOptions
from docling.datamodel.accelerator_options import AcceleratorOptions

pipeline_options = PdfPipelineOptions(
    accelerator_options=AcceleratorOptions(device="cuda"),  # auto/cpu/cuda/cuda:N/mps/xpu
)
```

`AcceleratorDevice` 支持 `auto`（自动探测）、`cpu`、`cuda`、`cuda:N`（指定卡）、`mps`（Apple Silicon）、`xpu`（Intel GPU）。可用环境变量 `DOCLING_DEVICE` 全局设置；`num_threads` 默认 4；CUDA 还可开 `cuda_use_flash_attention2`（需 flash-attn）。

### 模型选择与远程推理

- **本地模型**（默认）：布局、OCR、表格、图片描述都在本地跑，数据不出机器，但需要 GPU/CPU 算力，且依赖 `models-local` 等 extras。
- **远程推理**：安装 `models-remote` extra，把重模型放到远端服务（如 `docling-serve`）调用，本地只做轻量解析。适合无 GPU 的边缘机或集中式推理。

取舍：本地换隐私与离线能力，远程换弹性算力；图片描述、VLM 理解类任务对远程更友好。

## 陷阱与边界

- **选项写错层级会静默无效**：把 `do_ocr` / `generate_page_images` 这类 `PdfPipelineOptions` 字段配给 DOCX，代码不会报错，但 DOCX 走 SimplePipeline 根本不读它们，等于没设。配置前先确认目标格式用的是哪条管线。
- **`generate_picture_images` 不是 DOCX 开关**：它只存在于 PDF 管线，DOCX 图片提取无需任何开关。
- **`parser_threads` 不等于模型并行**：有模型的 PDF 管线靠 `accelerator_options` 管推理，`parser_threads` 只管解析线程；原生无模型管线才只靠 `parser_threads`。
- **细粒度 extras 能省数百 MB**：纯 Office 场景用 `docling-slim[format-*]` + `convert-core`，别装 `[standard]`；但记得补 `docling-parse` 与 `pypdfium2`（导入链硬依赖）。
