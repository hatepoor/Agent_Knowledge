# 格式支持与依赖管理

> Docling 支持 34 种输入格式，但绝大多数场景只需要装其中一两个 extra——装错 extras 是最大的时间浪费源。

## 核心结论

- Docling 通过 `InputFormat` 枚举支持 **34 种输入格式**，覆盖 Office、OpenDocument、Web/文本、PDF、图像、表格、XML 系、专业存档、媒体与原生序列化等类别。
- 这些格式绝大多数走**声明式后端（`SimplePipeline`）**，**不含任何 ML 模型**；只有 PDF 才有 ML 管线（`StandardPdfPipeline` / `NativePdfPipeline` / `VlmPipeline`）。
- 自 **2.129.0** 起，官方拆分为**元包 `docling`**（wheel 仅约 5.2 kB）+ 实现包 **`docling-slim`**。默认 `pip install docling` 拉的是 `standard` 组合，会带入 `torch` 等数百 MB 依赖——对纯 Office / HTML / Markdown 场景纯属浪费。
- **最关键的事实**：处理 `.docx` / `.html` / `.md` / `.csv` 等声明式格式**不需要 `torch`**。很多教程与示例直接 `pip install docling` 一把梭，把本不必要的大模型依赖全装上了。

## 机制与原理

### 包形态：元包 + docling-slim

| 包 | 角色 | 体积 |
|---|---|---|
| `docling` | **元包**：本身几乎不含代码（约 5.2 kB），只负责把 extras 组合转嫁到实现包 | 极小 |
| `docling-slim` | **实现包**：真正的转换逻辑都在这里，可按需装 extras | 视 extras 而定 |

拆分的实践含义：

1. 你可以只装 `docling-slim[format-docx]`，而不碰任何 `torch` / `docling-ibm-models`。
2. 元包的真实含义由 extras 决定——`pip install docling` 等价于 `docling-slim[standard]`，而 `standard` 包含 `torch + docling-ibm-models + docling-parse + rapidocr` 等重依赖。
3. 升级时**包名与 extras 名会变**：`docling-slim` 是 2.129.0 之后才出现的形态，老版本只有单独的 `docling`。升级前务必先查 extras 是否改名（见「版本与升级注意」）。

### 34 种格式与对应后端

> 说明：**每条格式归属哪条管线已全部源码核实，见下方「管线映射」表**——这才是决定"要不要装模型"的关键。具体 backend 类名本库未逐个核实，故该列保留 `（待核实）`。

| 类别 | 格式 | 后端 / 管线 |
|---|---|---|
| Office | DOCX、DOC、RTF、PPTX、PPT、XLSX、XLS | DOCX/DOC/RTF 为 `MsWordDocumentBackend`（python-docx，SimplePipeline，无 ML）；PPT/XLS 系列 `（待核实）` |
| OpenDocument | ODT、ODS、ODP | 声明式后端，SimplePipeline，无 ML `（待核实）` |
| Web / 文本 | HTML、MHTML、MD、ASCIIDOC、LATEX、EPUB、EMAIL、BOXNOTE | 声明式后端，SimplePipeline，无 ML `（待核实）` |
| PDF | PDF | `StandardPdfPipeline` / `NativePdfPipeline` / `VlmPipeline`，含 ML `（已核实）` |
| 图像 | IMAGE | 图像后端 `（待核实）` |
| 表格数据 | CSV | 声明式后端，SimplePipeline，无 ML `（待核实）` |
| XML 系 | XML_USPTO、XML_JATS、XML_XBRL、XML_DOCLANG、DCLX | XML 专用后端 `（待核实）` |
| 专业 / 存档 | METS_GBS、EBCDIC、AFP、IWORK_PAGES | 专用后端 `（待核实）` |
| 媒体 | AUDIO、VIDEO、VTT | 媒体 / 转写后端，常配合 VLM `（待核实）` |
| 原生 | JSON_DOCLING | 可回读自身序列化结果，无 ML `（待核实）` |

核心判断：**凡是 PDF 之外的格式，基本都不需要 ML 模型**；需要模型的是 PDF 的版面/OCR/表格识别，以及图片描述（VLM）。

### 管线映射（28 个 FormatOption，源码核实）

`document_converter.py` 里每个 `FormatOption` 通过 `pipeline_cls` 字段绑定管线。**这条映射直接决定"要不要装模型"**——它比"支持哪些格式"更该先看：

| 管线 | 覆盖的 FormatOption | 是否含 ML 模型 |
|---|---|---|
| `SimplePipeline` | Word / Powerpoint / Excel / Odt / Ods / Odp / Markdown / AsciiDoc / HTML / CSV / BoxNote / PatentUspto / XMLJats / XMLDocLang / Dclx / XBRL / IWorkPages / Latex / Email / Epub / Ebcdic / Afp（共 22 个） | **否** |
| `StandardPdfPipeline` | Pdf / **Image** / MetsGbs | 是（layout + 表格 + OCR） |
| `NativePdfPipeline` | NativePdf | **否**（只读 PDF 原生文本层与位图） |
| `AsrPipeline` | Audio | 是（转写模型） |
| `VideoPipeline` | Video | 是 |

**三个反直觉点**：

1. **图像格式（IMAGE）走的是 `StandardPdfPipeline`**，不是无模型管线——因为图片解析需要 OCR 与 layout 模型。所以"处理图片"比"处理 Word"重得多，装依赖时要一并算进来。
2. **`NativePdfPipeline` 是无模型的 PDF 路径**（`NativePdfFormatOption`），只读 PDF 原生文本层、不做 layout 分析。适合"PDF 本身有文本层、且不需要表格重建"的场景——代价是省掉全部模型依赖。
3. **22 个 FormatOption 走 `SimplePipeline`**：Office / Web / 文本 / CSV / XML 全系都不需要 torch。这是"纯文档场景可以极轻量部署"的源码依据。

## 实操

### 按场景的安装决策表

> 这是本页最有价值的部分。先想清楚你要处理什么格式，再决定装哪些 extras，不要默认 `pip install docling`。

| 场景 | 安装命令 | 体积感受 |
|---|---|---|
| 只处理 Word | `docling-slim[format-docx] docling-slim[convert-core] docling-parse pypdfium2` | 小，无 torch（约 50 MB） |
| 处理 Word + PDF（要 OCR / 表格） | `docling`（即 `standard`） | 大，含 torch |
| Word + PDF（只要文本层） | 加 `docling-slim[format-pdf]` 与 `NativePdfFormatOption` | 中，无模型 |
| 要分块 | 追加 `docling-core[chunking]` | 中 |
| 要图片描述（PDF） | 追加 `docling-slim[models-vlm-inline]`，或用 API 方式 | 大（本地模型）或按调用付费（远程） |

> **实测最小依赖组合（纯 DOCX，约 50 MB、无 torch）**
> ```
> docling-slim[format-docx]    # 核心 + python-docx
> docling-slim[convert-core]   # numpy / pillow / rtree / scipy
> docling-parse                # 必须
> pypdfium2                    # 必须
> ```
> 注意：`from docling.document_converter import DocumentConverter` 的导入链会连带触发 PDF 后端，所以 `docling-parse` 与 `pypdfium2` 即使只处理 DOCX **也必须装**；缺一个就 `ModuleNotFoundError`。实测按 `docling_parse → pypdfium2 → scipy` 的顺序逐个补齐才通过。

### 验证已装版本与 extras

升级或排查环境前，先确认包名与版本：

```bash
pip show docling-slim      # 看版本，确认是 2.129.0+ 才有 docling-slim 形态
pip show docling           # 看元包，以及它依赖的实现包
```

若返回 `WARNING: Package(s) not found`，说明你处于老版本（单 `docling` 包）或装包路径不一致，extras 语法可能不同，需回到对应版本的文档。

## 陷阱与边界

- **装错 extras 是最大的时间浪费源**：纯 Office / HTML / Markdown 场景不需要 `torch`，若直接 `pip install docling`（= `standard`）会白装数百 MB 模型依赖。先按上面的决策表选 extras。
- **`docling-slim` 与 `docling-parse` / `pypdfium2` 的隐含耦合**：即使只处理 DOCX，导入链也会触发 PDF 后端，这两个包缺一不可，缺失即 `ModuleNotFoundError`（非安装期、而在导入/运行时才暴露）。
- **DOCX 场景不需要 torch**：这是很多介绍会忽略的一点。Word 后端 `MsWordDocumentBackend` 基于 python-docx，**不含任何 ML 模型**，装 `torch` 纯属多余。
- **版本漂移**：extras 与包名随版本变化（2.129.0 起才拆出 `docling-slim`）。升级前先 `pip show docling-slim` 看版本，并核对 extras 是否改名，避免 `pip install docling[xxx]` 直接报「unknown extra」。
- **PDF 专用选项对 DOCX 静默无效**：`PdfPipelineOptions` 里的 `do_picture_description`、`generate_picture_images` 等只对 PDF 管线生效；用在 DOCX 上不报错、但完全不起作用（详见 [[docling/09_已知陷阱与边界|已知陷阱与边界]]）。
