# 02 整体架构与核心组件

> Docling 的内核是一条单向流水线：文件 → Backend 解析成元素 → Pipeline 编排并增强 → 收敛为统一的 DoclingDocument → 交给 transforms 做导出 / 分块 / 抽取 / 可视化。理解这三层加下游 transforms，就理解了 Docling 的九成。

## 核心结论

- 架构分三层：**Backend 层**（格式 → 元素）、**Pipeline 层**（编排 + 增强）、**Datamodel 层**（统一表示），下游还有 **transforms 层**做序列化与消费。
- 关键对应：**DOCX / HTML / MD / CSV 等走无模型的 `SimplePipeline`；PDF 才有 ML 管线**（`StandardPdfPipeline` 含 layout/OCR/表格，`NativePdfPipeline` 无模型只读原生层，`VlmPipeline` 用视觉语言模型）。
- 一个输入格式如何被处理，由 `FormatOption` 决定——它把"用哪个 backend + 哪种 pipeline + 哪些选项"绑定在一起。
- 包形态（2.129.0 起）：元包 `docling`（wheel 仅 5.2 kB）引用实现包 `docling-slim`。

## 机制与原理

### 三层架构

| 层 | 职责 | 典型产物 |
| --- | --- | --- |
| Backend 层 | 按输入格式把原始文件解析成文档元素（文本、图片、表格等） | 元素流（含来源坐标） |
| Pipeline 层 | 编排解析步骤，对 PDF 类做 layout 检测 / OCR / 表格识别等增强 | 增强后的元素 |
| Datamodel 层 | 把元素收敛为统一的 `DoclingDocument` 表示 | 统一文档对象 |

### 完整数据流

```
文件 → DocumentConverter（按 InputFormat 选 FormatOption）
     → Backend（按格式解析，产出文档元素）
     → Pipeline（编排；PDF 类会做 layout/OCR/表格增强）
     → DoclingDocument（统一文档模型）
     → transforms（serializer / chunker / extractor / visualizer）
```

逐环节职责：

1. **DocumentConverter**：转换主入口（`document_converter.py`，约 33.8 KB）。根据文件类型匹配 `InputFormat` 枚举，再用对应的 `FormatOption` 决定后端与管线。
2. **Backend**：真正读文件的组件。按格式把字节解析成带坐标的文档元素。
3. **Pipeline**：决定要不要做 ML 增强。PDF 类在此触发 layout / OCR / 表格识别；声明式格式直接放行。
4. **DoclingDocument**：所有格式最终收敛成的统一模型，是下游唯一要对接的对象。
5. **transforms**：消费层——导出、分块、抽取、可视化。

### Backend 层详解

Backend 有三个基类（位于 `backend/abstract_backend.py`）：

| 基类 | 适用 | 说明 |
| --- | --- | --- |
| `AbstractDocumentBackend`（ABC） | 全部 | 所有 backend 的抽象基类 |
| `PaginatedDocumentBackend` | 分页型（PDF 类） | 按页处理，配合 ML 管线 |
| `DeclarativeDocumentBackend` | DOCX / HTML / MD 等 | 直接读 XML / 文本的声明式格式，无需模型 |

26 个 backend 文件按格式类别：

| 类别 | backend 文件 |
| --- | --- |
| 办公文档 | `msword_backend.py`（164 KB）、`mspowerpoint_backend.py`（62.8 KB）、`msexcel_backend.py`（74.6 KB）、`opendocument_backend.py`（69 KB）、`iwork_backend.py`、`csv_backend.py` |
| Web / 标记 | `html_backend.py`（200 KB，最大）、`md_backend.py`、`asciidoc_backend.py`、`latex_backend.py`、`epub_backend.py`、`boxnote_backend.py`、`email_backend.py` |
| PDF / 图像 | `pdf_backend.py`、`pypdfium2_backend.py`、`managed_pdfium_backend.py`、`docling_parse_backend.py`、`image_backend.py` |
| XML 系 | `xml_uspto`（专利，待核实文件名）、`xml_jats`（期刊）、`xml_xbrl`（财报，待核实文件名）、`dclx`（待核实文件名） |
| 专业 / 存档 | `afp_backend.py`、`ebcdic_backend.py`、`mets_gbs_backend.py` |
| 媒体 / 其他 | `webvtt_backend.py`、`noop_backend.py` |

> 注：XML 系与部分 backend 的精确文件名在源码核实列表里只给了前缀，这里以"待核实"标注，详见 [[docling/08_格式支持与依赖管理|格式支持与依赖管理]]。源码核实给出的 26 个 backend 文件清单见任务背景，未列全文件名的按前缀归入对应类别。

### Pipeline 层详解

Pipeline 三层基类：`BasePipeline`（ABC）→ `ConvertPipeline` → `PaginatedPipeline`。

| 管线 | 体积 | 模型 | 用途 |
| --- | --- | --- | --- |
| `SimplePipeline` | 2.4 KB | **无** | 声明式后端用（DOCX / HTML / MD / CSV 等） |
| `StandardPdfPipeline` | 50.8 KB | 有（layout / OCR / 表格） | PDF 主力，最重 |
| `NativePdfPipeline` | 16 KB | **无** | 只读 PDF 原生文本层与位图，速度快 |
| `VlmPipeline` | 30.3 KB | 视觉语言模型 | 把页面当图像交给 VLM |
| `ExtractionVlmPipeline` | 9.8 KB | VLM | 抽取类任务 |
| `AsrPipeline` + `asr_transcriber.py`（30 KB） | 2.9 KB | 有 | 音频转写 |
| `VideoPipeline` | 12.3 KB | 有 | 视频处理 |

**关键对应关系**：`SimplePipeline` 不含任何 ML 模型，负责 DOCX / HTML / MD 等声明式格式；只有 PDF 才进入 ML 管线（`StandardPdfPipeline` / `NativePdfPipeline` / `VlmPipeline`）。需要语音 / 视频时再分别走 `AsrPipeline` / `VideoPipeline`。

### FormatOption 机制

`document_converter.py` 里定义了 **28 个 FormatOption 类**，把"输入格式 → backend → pipeline → 选项"封装成一个对象。常用映射：

| FormatOption | 对应输入 |
| --- | --- |
| `WordFormatOption` | DOCX / DOC |
| `PdfFormatOption` / `NativePdfFormatOption` | PDF / 原生 PDF（`NativePdfFormatOption` 继承 `PdfFormatOption`） |
| `MarkdownFormatOption` | MD |
| `HTMLFormatOption` | HTML |
| `ExcelFormatOption` | XLSX / XLS |
| `ImageFormatOption` | 图像 |
| `AsciiDocFormatOption` | ASCIIDOC |
| `PatentUsptoFormatOption` / `XMLJatsFormatOption` / `XBRLFormatOption` | 对应 XML 系 |

用法示例：

```python
from docling.document_converter import (
    DocumentConverter, InputFormat, WordFormatOption,
)
from docling.pipeline.simple_pipeline import SimplePipeline
from docling.datamodel.pipeline_options import PipelineOptions

converter = DocumentConverter(
    format_options={
        InputFormat.DOCX: WordFormatOption(pipeline_options=PipelineOptions()),
    }
)
result = converter.convert("example.docx")
print(result.document.export_to_markdown())
```

> 注意：源码核实 `InputFormat` 枚举共 **34 种**，而 FormatOption 类为 **28 个**——并非一一对应，部分格式共用或复用同一 FormatOption（如 `NativePdfFormatOption` 继承 `PdfFormatOption`）。

### Datamodel 层详解

`datamodel/` 共 24 个模块，关键几个：

| 模块 | 体量 | 职责 |
| --- | --- | --- |
| `pipeline_options.py` | 91.7 KB | 所有管线选项的集中定义 |
| `stage_model_specs.py` | 71 KB | 各阶段模型规格 |
| `document.py` | 46.9 KB | `DoclingDocument` 主模型 |
| `backend_options.py` | 26.9 KB | backend 相关选项 |
| `base_models.py` | 22 KB | 含 `InputFormat` 枚举 |
| `accelerator_options.py` | — | 加速器：CPU / CUDA / MPS |
| `chart_extraction_options.py` | — | 图表抽取选项 |
| `picture_classification_options.py` | — | 图片分类选项 |

另有 `asr_model_specs.py` / `vlm_model_specs.py` / `layout_model_specs.py` / `vlm_engine_options.py` 等支撑语音 / 视觉 / 布局模型。

### transforms 层（下游能力）

位于 `docling_core/transforms/`，是消费统一文档的地方：

| 子层 | 作用 |
| --- | --- |
| `serializer/` | 导出器：base / common / doctags / html / doclang / azure |
| `chunker/` | 分块器族：hierarchical / hybrid / line / page，外加 code_chunking、chunk_expander、tokenizer 适配 |
| `deserializer/` | 反向解析（doclang），可回读序列化结果 |
| `visualizer/` | **可视化**：layout_visualizer / reading_order_visualizer / table_visualizer / key_value_visualizer——调试解析质量的利器 |
| `profiler/` | doc_profiler，文档画像 |

### 接口层

| 接口 | 说明 |
| --- | --- |
| `cli/`（6 个 py） | 命令行。官方示例：`docling report.pdf --to md --to json`、`docling ./corpus --to md --output ./out` |
| `service_client/`（7 个 py） | 调用 docling-serve HTTP 服务的客户端 |
| docling-serve | 可 Docker 起服务：`docker run -p 5001:5001 quay.io/docling-project/docling-serve` |

## 实操

想看一个文件走了哪条链路，最直观的办法是用 `visualizer/` 把 layout 与 reading order 画出来（详见 [[docling/06_后续处理_导出分块与抽取|后续处理]]）。排查"表格被拍平 / 顺序错乱"时，先看原生 `NativePdfPipeline` 是否有文本层；没有再上 `StandardPdfPipeline` 的 OCR + 表格模型。

包结构对照（docling 2.129.0 实测）：

| 子包 | py 文件数 | 说明 |
| --- | --- | --- |
| `backend/` | 26 | 各格式解析器 |
| `pipeline/` | 13 | 各管线 |
| `datamodel/` | 24 | 统一模型与选项 |
| `utils/` | 23 | 工具 |
| `cli/` | 6 | 命令行 |
| `service_client/` | 7 | 服务客户端 |
| `models/` `chunking/` `experimental/` | — | 模型 / 分块 / 实验 |

## 各组件职责总表

| 组件 | 职责 | 何时需要关心它 |
| --- | --- | --- |
| `DocumentConverter` | 入口，按格式选 FormatOption | 每次转换都用到 |
| FormatOption（28 个） | 绑定 backend + pipeline + 选项 | 要改某格式行为时 |
| Backend（26 个） | 按格式解析成元素 | 写自定义格式 / 排查解析问题时 |
| Pipeline（7 类） | 编排 + ML 增强 | 选 PDF 策略、控算力时 |
| `DoclingDocument` | 统一文档模型 | 写下游消费 / 抽取时 |
| `pipeline_options` | 管线参数 | 调 OCR / 表格 / 加速选项时 |
| transforms / serializer | 导出 | 要 Markdown / JSON 时 |
| transforms / chunker | 分块 | 做 RAG 切分时 |
| transforms / visualizer | 可视化 | 调试解析质量时 |
| CLI / docling-serve | 接口 | 不想写代码 / 要服务化时 |

## 陷阱与边界

- `docling`（元包，5.2 kB）与 `docling-slim`（实现）是 2.129.0 起的新结构，安装时别只 pip 了元包却期望所有 backend 都在——注意 extras 与 slim 的关系（见 [[docling/08_格式支持与依赖管理|格式支持与依赖管理]]）。
- "34 种 InputFormat"与"28 个 FormatOption"不是一一对应，别凭直觉假设每个格式都有一个独立 FormatOption。
- 把 PDF 一律当 ML 重任务是大坑：有原生文本层的 PDF 用 `NativePdfPipeline` 既快又准，能省掉整套路 layout/OCR。
- XML 系 backend 的精确文件名本轮未逐一核实，引用时以"待核实"标注为准。
