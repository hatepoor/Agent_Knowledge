> 从 3 行代码到图片落盘：Docling 的「最小可用」路径，以及每一步实际拿到了什么。

## 核心结论

1. `DocumentConverter().convert(path)` 一步就能把一份文档变成结构化的 `DoclingDocument`；这是全部后续处理的入口。
2. 导出（export / save_as）只是把内存里的文档树**序列化**成文本，**不是**解析环节。Markdown 里图片只剩 `<!-- image -->` 占位符，是导出期参数 `image_mode` 的默认行为，不代表解析时丢了图。
3. 纯 Office（DOCX/PPTX/XLSX）场景根本不需要 torch：用 `docling-slim` 的细粒度 extras 即可，不必安装 `[standard]` 元包的完整依赖。

## 机制与原理

`convert()` 的返回值类型是 `ConversionResult`，其中：

- `.document` 是 `DoclingDocument` —— 整篇文档的内存树（见 [[docling/05_DoclingDocument结构详解|DoclingDocument 结构]]）。
- 所有「导出」方法（`export_to_markdown` / `save_as_json` / `save_as_html` / `save_as_doctags`）都是在**已有文档树**上做序列化，与解析器、后端（backend）无关。
- 因此「解析期」与「导出期」是两件事：解析决定文档里有没有图、有没有坐标；导出决定图以占位符、引用还是 base64 形式出现在产物里。

这也解释了为什么「Markdown 里没有图」常被误判为 bug：其实图已经在 `DoclingDocument` 的 `PictureItem` 里，只是默认导出模式没有把它写出来。

## 实操

下面按「由简到繁」四级递进，每一级都是可运行代码。

### 第 1 级：3 行拿到文档

```python
from docling.document_converter import DocumentConverter

result = DocumentConverter().convert("report.pdf")
print(result.document.export_to_markdown())
```

这一步你拿到了：一个 `ConversionResult`，其 `.document` 是一棵 `DoclingDocument` 树；`export_to_markdown()` 默认以 `ImageRefMode.PLACEHOLDER` 输出——正文、标题、表格都在，但图片位置只留下 `<!-- image -->` 占位注释。PDF 还会带 `prov`（页码 + bbox），DOCX 则不带（见 [[docling/05_DoclingDocument结构详解|结构页]] 的 prov 说明）。

### 第 2 级：显式指定格式选项

```python
from docling.document_converter import DocumentConverter, WordFormatOption
from docling.datamodel.base_models import InputFormat

conv = DocumentConverter(
    format_options={
        InputFormat.DOCX: WordFormatOption(),
    }
)
result = conv.convert("paper.docx")
md = result.document.export_to_markdown()
```

何时需要它：
- **避免自动探测**：当你只处理某几种格式、想明确绑定后端时。
- **给特定格式配置专属管线**：例如 PDF 想关掉 OCR、调分辨率，就给 `InputFormat.PDF` 配一个 `PdfFormatOption(pipeline_options=...)`（见 [[docling/04_进阶用法_配置与选项|配置与选项]]）。
- DOCX 走的是 `SimplePipeline` + `MsWordDocumentBackend`（基于 python-docx），**不含任何 ML 模型**，所以 Word backend 构造图片时连 `generate_picture_images` 都不认——这个开关只属于 PDF 管线。

### 第 3 级：一次导出多种格式

```python
doc = result.document

doc.save_as_markdown("out.md")            # 人类可读的正文，适合检索/问答
doc.save_as_json("out.json")              # 完整结构化：文档树、prov、坐标都在
doc.save_as_html("out.html")              # 网页呈现
doc.save_as_doctags("out.doctags.txt")    # DocTags 序列，适合训练 / 喂给 VLM
```

用途差异：
- **Markdown**：最易消费，但默认丢图（占位符）；适合做 RAG 正文切分。
- **JSON**：信息的全集，任何字段（含图片引用、坐标、层级）都不丢；适合二次处理或长期归档。
- **HTML**：保留视觉结构，适合直接展示。
- **DocTags**：把版面、位置、内容编码成一串 token，是 Docling 自家训练/多模态场景的交换格式（旧名 `export_to_document_tokens` 已废弃，统一用 `export_to_doctags`）。

### 第 4 级：把图片真正落盘

```python
from pathlib import Path
from docling_core.types.doc.base import ImageRefMode

doc.save_as_markdown(
    "out.md",
    image_mode=ImageRefMode.REFERENCED,
    artifacts_dir=Path("out_artifacts"),
)
```

`REFERENCED` 模式下，`artifacts_dir` 里会生成实际图片文件，Markdown 中写入相对路径引用。对应的另外两种模式：
- `PLACEHOLDER`（默认）：只留 `<!-- image -->`。
- `EMBEDDED`：把图片以 base64 内嵌进 Markdown，单文件自包含但体积大。

**对比：直接从元素层取 PIL 对象**（绕过导出序列化，自己控制图片）：

```python
from docling_core.types.doc.items.picture import PictureItem

for item, _ in doc.iterate_items():
    if isinstance(item, PictureItem) and item.image is not None:
        pil = item.image.pil_image          # 直接拿到 PIL.Image
        pil.save(f"{item.self_ref.replace('/', '_')}.png")
```

`PictureItem.image` 是 `ImageRef`，其 `.pil_image` 属性会按 `uri` 懒加载并返回 PIL 对象；这比导出模式更灵活，适合你要对图做裁剪、OCR 或入库的场景。注意 DOCX 的图片 `prov` 为空，因此没有页码与坐标，只有图本身。

### CLI 用法

```bash
# 单文件，转成多种格式
docling report.pdf --to md --to json

# 目录批量转换，输出到指定目录
docling ./corpus --to md --output ./out

# 只转 DOCX（同样支持 --to 多值）
docling paper.docx --to md
```

CLI 与 Python API 共享同一套后端；`--to` 可重复指定，`--output` 指定批量落盘目录。

## 陷阱与边界

- **纯 Office 不必装 `[standard]`**：`pip install docling` 默认拉 `docling-slim[standard]`，会带 torch/torchvision（数百 MB）。只处理 Office 用 `docling-slim[format-docx,format-pptx,format-xlsx]` + `convert-core` 即可。但要注意：`from docling.document_converter import DocumentConverter` 的导入链会连带触发 PDF 后端，所以 `docling-parse` 与 `pypdfium2` **即使只处理 DOCX 也必须装**，缺一就 `ModuleNotFoundError`。
- **Markdown 里图片只有占位符是导出参数问题**，不是解析期丢图——想要图就显式传 `image_mode=ImageRefMode.REFERENCED/EMBEDDED`。
- **DOCX 没有页码与坐标**：`PictureItem.prov` 在 DOCX 下是空列表（Word 无固定分页概念），所以 `get_image(doc)`、`get_location_tokens()` 这类依赖 `prov` 的方法对 DOCX 图片无效。
- **DOCX 图片提取不需要任何开关**：网上流传的 `generate_picture_images=True` 只存在于 PDF 管线，`msword_backend.py` 全文零次出现该参数。
