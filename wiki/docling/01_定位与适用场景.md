# 01 定位与适用场景

> Docling 是 IBM Research 发起、现属 LF AI & Data 基金会的开源文档解析框架，官方定位语是"Turn complex documents into structured data your AI can use"——把复杂文档转成结构化数据供 AI 使用，而不是给人看的排版工具。

## 核心结论

- Docling 的核心价值是**统一文档模型 + 可完全离线 + 面向 AI 数据准备**三件事的交集。
- 它能解决传统"PDF 转文本"类工具最头疼的几类问题：表格结构被拍平、多栏阅读顺序错乱、公式/代码丢失、图片不可检索、页眉页脚污染、缺少溯源坐标。
- 它不是银弹：纯文本、结构简单、单一格式的场景，更轻的工具（如 MarkItDown）反而更合适；含 ML 模型的完整管线依赖较重。

## 机制与原理

### 它到底解决什么实际问题

下面每一条都是真实痛点 → Docling 的方案，不是空话：

| 痛点 | Docling 的方案 |
| --- | --- |
| 表格结构被拍平成一串文字，行列关系丢失 | 通过 PDF 管线的表格识别模型还原单元格、行列与合并关系，输出保留结构的表格（第三方测试表格准确率约 97.9%） |
| 多栏 / 复杂排版导致阅读顺序错乱 | layout 检测 + 阅读顺序（reading order）模型重新排列内容块，输出有序层级 |
| 公式、代码块在转换中丢失或乱码 | 保留公式与代码元素的语义类型，不把它们混进正文 |
| 图片信息进不了检索 | 图片作为带坐标的元素保留，可配合图片分类 / 描述进入多模态检索 |
| 页眉页脚、页码污染正文 | 页眉页脚被识别为独立元素类型，可在下游过滤 |
| 需要带坐标的溯源（证明某句来自第几页哪个框） | 每个元素携带 `prov` 来源信息，含页码与边界框坐标 |

### 三个关键词说明它的定位

1. **统一文档模型（DoclingDocument）**：一份输出喂所有下游。无论输入是 PDF、Word 还是 HTML，最终都收敛成同一个 `DoclingDocument`，导出 Markdown / JSON、做 chunking、抽取表格都只对接它。
2. **可完全离线**：MIT 许可，可自托管、可完全离线运行，数据不出本地——合规与隐私场景的关键。
3. **面向 AI 数据准备**：产物是带层级、坐标、阅读顺序的结构，专为 RAG / 微调 / 知识图谱服务，而非重排版给人看。

## 实操

判断一个场景要不要上 Docling，先问三件事：要不要表格保真？要不要离线？要不要多格式混杂？三项里命中两项，基本就值得投入。若只命中"纯文本且结构简单"，更轻的 MarkItDown / PyMuPDF4LLM 通常是更优解。

## 与替代品对比

下表按"输出格式 / 表格能力 / 部署 / 成本 / 许可 / 关键限制"对比 8 款常见工具（docling 自身数据来自源码核实，其余来自公开资料，个别项待核实）：

| 工具 | 输出格式 | 表格能力 | 部署 | 成本 | 许可 | 关键限制 |
| --- | --- | --- | --- | --- | --- | --- |
| **docling** | Markdown + 结构化 JSON | 最强（第三方测试约 97.9%） | 自托管 | 仅算力成本 | MIT | 依赖较重（含 ML 的 extras 拉 torch） |
| Unstructured | typed elements（非 Markdown） | 中等 | 自托管 / 云 | 开源免费，云按量 | MIT（待核实） | 元素流需额外整理成文档 |
| LlamaParse | Markdown / JSON | 75–90% | 云 API | 按 credit：3–45 credits/页；10 万页/月约 $375–$5,625 | 商业 | 依赖联网，数据出本地 |
| MarkItDown | 轻量 Markdown | 弱（无 layout 模型、无 OCR） | 自托管 | 免费 | MIT | PDF 弱，复杂排版丢失 |
| Marker | Markdown / JSON | 较强 | 自托管（建议 GPU） | 算力 | **GPL（商用需法务确认）** | CPU 上慢 |
| MinerU | Markdown / JSON | 强 | 自托管 | 算力 | 开源 | 仅 PDF，中文 / 学术文档突出 |
| PyMuPDF4LLM | Markdown | 60–70% | 自托管 | 免费极快 | 宽松 | 不做完整 layout 检测 |
| Azure DI / Textract | 结构化 JSON | 强 | 云 | 约 $1,000–$3,000 / 10 万页 | 商业 | 生态绑定 Azure / AWS |

> 说明：表格中成本与准确率数值来自公开第三方评测与官方定价页，随版本与汇率变动，落地前建议以当下官方口径复核。

## 适用 / 不适用场景

**适用：**

- 需要结构保真的 RAG 语料（表格、标题层级不能丢）
- 有离线 / 合规要求，数据不能出本地
- 多格式混杂（PDF + Word + HTML + 表格 + 图片一起进）
- 需要表格、图片进入检索，而非只喂纯文本
- 需要带坐标的溯源信息做可解释 / 可审计

**不适用：**

- 只要纯文本且结构简单——MarkItDown 更轻更快
- 超大 PDF 且无 GPU 预算——用 native PDF 管线或云服务更合适
- 只处理单一、简单格式，没必要引入完整框架
- 对许可极度敏感且不愿做法务确认——注意 Marker 的 GPL 风险（docling 本身是 MIT）

## 陷阱与边界

**一个诚实提示**：Docling 依赖确实较重，含 ML 模型的 extras 会拉入 torch 等大模型依赖，首次搭建生产级管线通常要 20–40 小时。但**很多介绍会忽略的一点**是：纯 Office / HTML / Markdown / CSV 场景根本不需要任何模型——它们走 `SimplePipeline`，只有 PDF 类才触发 layout / OCR / 表格的 ML 管线。选型时先把输入格式列清楚，很可能你只需要 `docling-slim` 的轻量部分，而不必拉满整套 ML 依赖。
