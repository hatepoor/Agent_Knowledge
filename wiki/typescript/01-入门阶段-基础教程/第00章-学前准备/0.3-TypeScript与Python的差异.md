# TypeScript 与 Python 的差异

> **什么时候该读**：你会 Python，零基础学 TS；或者已经在写 TS，想避免「把 Python 习惯照搬进 TS」的坑。

5. 把一段 Python 数据处理逻辑正确改写成 TypeScript

## 一、根本差异：一句话概括

| 维度 | TypeScript | Python |
|------|-----------|--------|
| 类型系统 | **静态强类型**——编译期检查 | 动态类型——运行期检查 |
| 执行方式 | 编译成 JS 后由宿主执行 | 解释器直接解释源码 |
| 工程化 | 强约束（`tsconfig.json` + 类型） | 灵活（`pyproject.toml` + 约定） |
| 适合 | 大型应用、库开发、团队协作 | 脚本、AI/数据、快速迭代 |

⭐ **一句话**：**Python 把错误留给运行期，TypeScript 把错误挡在编译期**——这一条差异决定了下面所有行为。

## 二、⭐ 逐项对照表

| 维度 | TypeScript | Python |
|------|-----------|--------|
| **类型系统** | 静态强类型：变量声明后类型固定（除非用 `any`/`unknown` 逃逸） | 动态类型：变量随时可指向不同类型的对象 |
| **类型标注必填性** | 局部变量**可以**省略（靠推断），但函数参数/返回值常写 | 注解**完全可选**，写不写都不影响运行 |
| **编译** | 编译到 JS（`.js`，可选 `.d.ts` 声明文件） | 无需编译，解释执行；`.pyc` 由解释器自动生成 |
| **类型检查时机** | **编译期**（`tsc` 跑一次就全知道了） | **运行期**（除非额外装 mypy / pyright） |
| **模块系统** | ESM 的 `import` / `export`（也有 CommonJS 的 `require` / `module.exports`） | `import` / `from ... import`（语言内建，无包配置） |
| **包管理** | `npm`（还有 pnpm / yarn / bun） | `pip`（还有 poetry / uv / conda） |
| **项目配置** | `tsconfig.json`（编译）+ `package.json`（依赖） | `pyproject.toml`（项目+依赖），或 `requirements.txt` |
| **依赖隔离** | `node_modules/` 目录，**自动隔离，无需激活** | 虚拟环境 venv，**需要 `activate`** |
| **运行时** | Node.js（服务端）/ 浏览器（前端）/ Deno、Bun | CPython / PyPy（解释器） |
| **异步模型** | `Promise` + `async/await`，单线程事件循环 | `asyncio` 协程 + `await`，受 GIL 限制 |
| **空值** | **两种**：`null`（显式置空）与 `undefined`（没有值） | **一种**：`None` |
| **字典 / 映射** | `Map<K, V>` 或 `Record<K, V>`；对象字面量键限 `string \| number \| symbol` | `dict`，键任意可哈希对象 |
| **数组访问越界** | 返回 `undefined`，**不报错** | 抛 `IndexError` |
| **类型兼容性** | **结构化**（长得一样就兼容） | **名义**（同一继承链才兼容），但鸭子类型可绕过 |

## 三、⭐ 类型标注 vs 类型注解：最容易误解的一点

这是 Python 用户迁移时**最大的认知偏差**。

### Python 的注解：运行时真实存在

```python
def add(a: int, b: int) -> int:
    return a + b

print(add.__annotations__)
# {'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

⭐ Python 的类型注解是**运行时对象的一部分**——它们被存进函数的 `__annotations__` 属性里。所以：

- 反射能读到（`__annotations__`）
- 框架能用它做**运行时校验**（FastAPI 靠这个自动校验请求体并生成文档）
- `dataclasses`、Pydantic 等库靠它构造校验器

### TS 的类型标注：运行时彻底消失

```ts
function add(a: number, b: number): number {
  return a + b;
}
```

编译产物：

```js
function add(a, b) {
    return a + b;
}
```

⭐ **运行时你能拿到的只有 `add.length === 2`（参数个数）**。参数是不是 `number`、返回值是不是 `number`——**完全无从得知**。

### 后果对比

| | Python 注解 | TS 类型标注 |
|---|---|---|
| 运行时可读 | ✅ | ❌ |
| 能做运行时校验 | ✅（框架直接用） | ❌（需另引 Zod 等库） |
| 影响运行时性能 | 极小（对象存在） | 零（完全不存在） |
| 校验时机 | 运行时 | 编译期 |

⚠️ **这解释了 LangChain.js 为什么用 Zod**——模型返回的 JSON 是外部输入，TS 类型在运行时已被擦除，**校验不了**，必须引入 Zod 这类运行时校验库。

## 四、⭐ 结构化类型 vs 名义类型

### TypeScript：结构化类型（structural typing）

TS 判断两个类型是否兼容，看的是**结构**（有哪些属性、属性什么类型），**不看名字**。

```ts
interface Point {
  x: number;
  y: number;
}

function draw(p: Point) {
  console.log(p.x, p.y);
}

// ✅ 合法：这个对象"长得像" Point
draw({ x: 1, y: 2 });

// ✅ 也合法：另一个类型，结构完全相同
interface Position { x: number; y: number; }
const pos: Position = { x: 3, y: 4 };
draw(pos);        // ✅ 不报类型错误
```

⚠️ **只要结构一样，就是同一个类型**——TS 不关心它叫什么、也不关心你有没有声明过 `Point`。

### Python：名义类型（nominal typing）

Python 判断兼容性看的是**身份**：`OtherPoint` 不是 `Point` 的子类，就不能传给 `draw`。

```python
class Point:
    def __init__(self, x: int, y: int):
        self.x, self.y = x, y

class Position:
    def __init__(self, x: int, y: int):
        self.x, self.y = x, y

def draw(p: Point) -> None:
    print(p.x, p.y)

draw(Position(3, 4))    # ❌ TypeError：Position 不是 Point
```

但 Python 有**鸭子类型（duck typing）**作缓冲：「如果它走起来像鸭子、叫起来像鸭子，那它就是鸭子」——运行时只检查「有没有 `x` 和 `y` 属性」，不检查类名。

### 对照与折中

| | TypeScript | Python |
|---|---|---|
| 默认兼容性判定 | 结构化 | 名义（子类） |
| 例外机制 | 无（结构就是唯一标准） | 鸭子类型（运行时检查属性） |
| 显式的结构化写法 | `interface`（默认就是） | `typing.Protocol`（结构化协议，需显式声明） |
| 显式的名义写法 | `class` + `private` 成员 | `class`（默认） |

⭐ **实用建议**：
- TS 里想「必须来自某个类」→ 用 `class` 加 `private` 字段（私有成员让结构化判定失效，从而强制名义关系）；
- Python 里想「只要有这个方法就行」→ 用 `typing.Protocol`。

```ts
class Counter {
  private count = 0;          // private 字段：外部对象无法"长得像"它
  increment() { this.count++; }
}
```

## 五、⚠️ 五个最容易照搬踩坑的点

### 1. ⚠️ TS 是编译型：不能像 Python 那样直接跑

```bash
python -c "print(1+1)"        # ✅ Python 可以
node -e "console.log(1+1)"    # ✅ JS 可以
node -e "const x: number = 1" # ❌ 不行！Node 不认识 TS 语法
```

TS **必须**先编译。临时想跑一个 `.ts` 文件，用 `npx tsx x.ts`（或 Deno/Bun 直接跑）。

⚠️ 而且注意：`npx tsx` **只转译不检查类型**。你的 `.ts` 里有类型错误它照样跑——**别把 `tsx` 当成「安全网」**。

### 2. ⚠️ `null` 和 `undefined` 是两种不同的空

Python 只有 `None`。TS 有两个：

| | 含义 | 典型来源 |
|---|---|---|
| **`undefined`** | 「**没有值**」 | 变量未初始化、属性不存在、函数无返回值、数组越界 |
| **`null`** | 「**显式置空**」 | 程序员主动赋值 `x = null` |

```ts
function find(id: string): string | undefined {
  // 找不到时返回 undefined（也可以返回 null，语义不同）
  return undefined;
}

let user: string | null | undefined = undefined;   // 还没拿到
user = null;                                        // 明确置空
```

⚠️ **这会影响你的类型标注**：⚠️ **想同时接受 `null` 和 `undefined`，就必须把两个都写进联合类型**——只写 `string | undefined` 时赋 `null` 会直接编译报错（`Type 'null' is not assignable to type 'string | undefined'`）。

而 `string | undefined` 和 `string | null` 在 `strict` 模式下是**不同的类型**。用 `=== null` 判空**漏掉** `undefined`；用 `=== undefined` 也漏掉 `null`。稳妥写法是两者都查，或用可选链 `?.` 和空值合并 `??`。

```ts
const len = user?.length ?? 0;   // user 为 null 或 undefined 都安全
```

### 3. ⚠️ 数组越界返回 `undefined`，不报错；`push` 才是 `append`

```python
nums = [1, 2, 3]
print(nums[5])       # ❌ IndexError：list index out of range
nums.append(4)      # 追加
```

```ts
const nums = [1, 2, 3];
console.log(nums[5]);   // ⚠️ 不报错！输出 undefined
nums.push(4);           // ✅ 对应 Python 的 append
```

⚠️ **两个坑叠在一起**：

1. TS 数组越界**静默返回 `undefined`**，不抛异常——比 Python 的 `IndexError` 更难发现；
2. ⚠️ **默认情况下编译器并不会提醒你这件事**：`strict: true` 只管 `null`/`undefined` 的显式标注，**不检查越界**。所以 `nums[0].toFixed(2)` 默认能通过编译，运行时却可能炸。

⭐ 想要编译器帮你防越界，需要额外开启 **`noUncheckedIndexedAccess`**（严格索引访问检查）：

```json
{ "compilerOptions": { "noUncheckedIndexedAccess": true } }
```

开启后 `nums[0]` 的类型变成 `number | undefined`，`nums[0].toFixed(2)` 立刻编译报错。这时才需要用可选链 `nums[0]?.toFixed(2)` 或空值合并 `nums[0] ?? 0` 来兜底。

⚠️ 另一个差别：**TS 数组是同质的**。`const nums: number[] = [1, 2, 3]` 之后 `nums.push("四")` 编译报错。Python 的 `list` 可以混装 `int` 和 `str` 不报错。

### 4. ⚠️ 对象是引用类型，浅拷贝陷阱完全一样

TS 和 Python 一样，**变量存的是引用**：

```ts
const a = { count: 1 };
const b = a;
b.count = 2;
console.log(a.count);   // 2！a 和 b 是同一个对象
```

⚠️ **浅拷贝（shallow copy）只复制一层**——这是两边共同的坑：

```ts
const original = { name: "张三", tags: ["a", "b"] };
const copied = { ...original };      // 展开运算符 = 浅拷贝

copied.tags.push("c");
console.log(original.tags);   // ⚠️ ['a','b','c']——嵌套数组被共享了！
```

Python 里对应 `copy.copy(original)`（或 `{**original}`）也有完全一样的问题。

⭐ **要真正隔离，嵌套层也要拷**：TS 用 `structuredClone(obj)`（浏览器与 Node 17+ 都内置）或逐层展开 `tags: [...original.tags]`；Python 用 `copy.deepcopy(original)`。

### 5. ⚠️ Python 的 `dict` 对应 TS 的 `Map`/`Record`，**不是**普通对象字面量

```python
scores = {}                    # 键可以是任何可哈希对象
scores[("a", 1)] = 100          # 元组做键，完全合法
```

```ts
// ⚠️ 对象字面量：键被限制为 string | number | symbol
const obj = { "a": 1 };
obj[("a", 1)] = 100;   // ❌ 编译报错：键的类型不对
```

TS 里有三种「键值映射」写法，**语义不同**：

| 写法 | 运行时结构 | 键类型 | 对应 Python |
|------|-----------|--------|------------|
| `{ a: 1 }`（对象字面量） | 普通对象 | `string \| number \| symbol` | 只能当「固定字段的结构体」用 |
| `new Map<string, number>()` | `Map` | **任意类型**（对象、数组都行） | ⭐ **`dict` 的真正对应** |
| `Record<string, number>` | 编译期是对象字面量 | `string \| number \| symbol` | `dict[str, int]` 的**类型标注** |

```ts
// ⭐ 任意类型的键 → 用 Map
const meta = new Map<object, string>();
meta.set({ id: 1 }, "第一");
console.log(meta.get({ id: 1 }));   // undefined——注意：按引用查找，不是按值

// ⭐ 字符串键的字典 → 用 Record 标注
type Score = Record<string, number>;
const scores: Score = { alice: 90, bob: 85 };
```

⚠️ **`Map` 是按引用查找的**，和 Python `dict` 用 `__hash__`/`__eq__` 的行为不同——`meta.get({id:1})` 拿不到刚才存进去的值，因为这是两个不同的对象。

⚠️ 另一个易混点：`Object.keys(obj)` 拿的是**字符串**键；`map.keys()` 拿的是**原键类型**。做类型转换时容易出错。

## 六、一段代码对照：把 Python 数据处理逻辑改写成 TS

**Python 版**（统计高分工单的标签出现次数，取前 3）：

```python
from collections import Counter

def top_tags(posts: list[dict], limit: int = 3) -> list[tuple[str, int]]:
    counts = Counter()
    for post in posts:
        if post["score"] >= 10:          # 只看高分帖
            counts.update(post["tags"])
    return counts.most_common(limit)

posts = [
    {"tags": ["ai", "llm"], "score": 20},
    {"tags": ["ai", "python"], "score": 5},      # 分数低，不计入
    {"tags": ["llm", "ai", "ai"], "score": 15},
]
print(top_tags(posts))
# [('ai', 3), ('llm', 2)]
```

**TypeScript 版**（逐行对应）：

```ts
type Post = {
  tags: string[];
  score: number;
};

function topTags(posts: Post[], limit = 3): [string, number][] {
  // ⚠️ 用 Map 而不是对象字面量：键任意、增删更安全（对应 Python 的 Counter）
  const counts = new Map<string, number>();

  for (const post of posts) {
    if (post.score >= 10) {
      for (const tag of post.tags) {
        // get 可能返回 undefined，用 ?? 兜底成 0 再 +1
        counts.set(tag, (counts.get(tag) ?? 0) + 1);
      }
    }
  }

  // Map 本身没有排序方法，先转成数组再排
  return [...counts.entries()]                 // entries() 返回 [键, 值] 的数组
    .sort((a, b) => b[1] - a[1])               // 按次数倒序
    .slice(0, limit);                          // 取前 limit 个
}

const posts: Post[] = [
  { tags: ["ai", "llm"], score: 20 },
  { tags: ["ai", "python"], score: 5 },        // 分数低，不计入
  { tags: ["llm", "ai", "ai"], score: 15 },
];

console.log(topTags(posts));
// [ [ 'ai', 3 ], [ 'llm', 2 ] ]
```

### 逐条差异说明

| Python | TypeScript | 说明 |
|--------|-----------|------|
| `list[dict]` | `Post[]` | TS 用 `interface`/`type` 定义结构，比 `dict` 更精确 |
| `post["score"]` | `post.score` | TS 用点号访问已知字段（`post["score"]` 也合法，但字段名写错时 TS 反而会帮你报错） |
| `Counter()` | `new Map<string, number>()` | `Counter` 是 Python 标准库特供，TS 没有对应物，用 `Map` 手动维护计数 |
| `counts.update(post["tags"])` | 内层 `for` + `counts.set(...)` | TS 标准库没有 `update`，得手写循环 |
| `counts.get(tag)` 返回 `0` | `counts.get(tag)` 返回 `number \| undefined` | ⚠️ TS 不会「自动」给你 0，必须 `?? 0` 兜底 |
| `list[tuple[str, int]]` | `[string, number][]` | TS 的**元组**（tuple）是固定长度、位置有类型的数组 |
| `counts.most_common(limit)` | `.sort(...).slice(0, limit)` | `Map` 无序，必须先 `entries()` 转数组再排 |
| 无需类型标注也能跑 | 参数/返回值类型**建议写** | `limit = 3` 的默认值让 TS 推断出 `number` |

⭐ **同样的语义，不同的外壳**：Python 用标准库的三行代码，TS 要手写计数循环——这就是「动态语言写起来快、静态语言写起来准」的典型体现。

## 七、陷阱

1. **⚠️ 以为 Python 注解和 TS 类型标注行为一样**——Python 注解运行时存在（可反射、可校验），TS 标注编译后彻底消失。**TS 永远不能替代运行时校验**；
2. **⚠️ 用 `=== null` 判空却漏掉 `undefined`**——TS 有两种空，判空要同时覆盖（或用 `??` / `?.`）；
3. **⚠️ 以为 `arr[0]` 一定是 `number`**——在 `strict` 下它是 `number | undefined`，直接 `.toFixed()` 会编译报错；
4. **⚠️ 把 Python 的 `dict` 写法直接搬过来**——`obj[key] = value` 在 TS 里键类型受限且不能动态增删键，用 `Map`；
5. **⚠️ 以为 `type: "module"` 之类的 ESM 配置能照搬 Python 的 import 风格**——TS 的模块有 `esModuleInterop`、`moduleResolution` 等一整套规则，细节见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/2-模块系统ESM与CommonJS|模块系统：ESM 与 CommonJS]]；
6. **⚠️ 以为 TS 是「Python 加了类型」**——TS 是**编译型**语言，Python 是解释型；一个要编译，一个直接跑，连错误暴露的时机都不同。

## 小结

- 根本差异：**静态强类型 + 编译期检查** vs 动态类型 + 运行期检查
- ⭐ **类型标注 vs 类型注解**：Python 注解运行时存在（`__annotations__`），TS 标注编译后**完全消失**
- ⭐ **结构化 vs 名义**：TS 的 `interface` 看结构（长得像就兼容），Python 的 `class` 看名义；Python 的 `typing.Protocol` 是显式的结构化折中
- 五个必踩坑：**编译型不能直接跑**、`null`/`undefined` 两种空、**数组越界返回 `undefined`**、浅拷贝陷阱、**`dict` 对应 `Map`/`Record` 而非对象字面量**
- 逐项对照：类型系统 / 编译 / 检查时机 / 模块 / 包管理 / 项目配置 / 运行时 / 异步 / 空值 / 键值映射
- 迁移心法：**语义不变，语法重写**——先想清楚类型，再套 TS 写法

## 练习

1. 写一个 Python 函数和一个 TS 函数，各自统计字符串列表中每个单词的出现次数并返回字典；对照两边的「计数容器」选型，说清为什么 TS 选 `Map`。
2. 在 TS 里分别用 `null` 和 `undefined` 给一个 `string | null | undefined` 变量赋值，用 `=== null` 和 `=== undefined` 分别判断，观察哪个漏掉了哪个；再改用 `??` 和 `?.` 写出安全的写法。
3. 验证类型擦除：写一个带参数类型标注的 TS 函数，编译后在 `.js` 里读 `fn.length` 和 `fn.toString()`，确认拿不到任何类型信息；再在 Python 里读 `fn.__annotations__`，对比两者。
4. 演示结构化 vs 名义：定义两个结构相同、名字不同的 TS `interface`，互相传参确认合法；在 Python 里做同样的事，观察 `TypeError`。
5. 把第六节的 Python 代码**先**按你的直觉翻译成 TS（不查对照表），然后逐条对照本篇的差异说明，找出你翻译错的地方。
6. 思考：为什么 LangChain.js 做结构化输出要用 Zod，而不是写一个 TS `interface` 就完事？
