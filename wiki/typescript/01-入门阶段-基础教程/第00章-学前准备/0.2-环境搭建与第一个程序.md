# 环境搭建与第一个程序

> **什么时候该读**：准备动手写第一行 TypeScript，需要把环境装好并跑通「写 → 编译 → 运行」三步。
> **阅读门槛**：零基础。会用命令行敲几条命令即可；Node.js 未装也没关系，本篇会一步步带你装。

## 学习目标

读完本篇，你应当能够：

1. 说清 Node.js 和 npm 分别是什么，并装好、验证版本
2. 在项目里安装 TypeScript 为**开发依赖**，用 `npx tsc --version` 确认
3. 手写一份 `tsconfig.json`，说清 `target` / `module` / `strict` / `outDir` / `rootDir` / `esModuleInterop` 各自管什么
4. 完整走通 `hello.ts` → `hello.js` → 运行结果
5. 在「编译后运行 / `tsx` / `ts-node`」三种方式里按场景正确选型
6. 避开本篇列出的四个常见环境事故

## 一、Node.js：跑 JS 的运行时

**Node.js** 是一个**运行时（runtime）**——把浏览器里的 V8 引擎搬到服务器上，再补上浏览器没有的能力：读写文件、监听网络端口、操作数据库等。

一句话定位：**Node.js 是「能执行 JavaScript 的程序」，不是「JavaScript 的一种方言」**。你在浏览器控制台里写的 JS，搬到 Node 里基本能跑。

| | 浏览器 | Node.js |
|---|---|---|
| 跑什么 | 网页里的 JS | 服务端 / 命令行里的 JS |
| 能不能读文件 | ❌ 出于安全被禁 | ✅ `fs` 模块 |
| 能不能监听端口 | ❌ | ✅ `http` 模块 |
| 入口 | `<script>` 标签 | `node x.js` 命令 |

⚠️ **TS 不能被 Node 直接执行**（上一节讲过：TS 需要先编译）。所以在写 TS 之前，**必须先装 Node**——它是整条链路的宿主。

### 安装与验证

去 [nodejs.org](https://nodejs.org) 下载 **LTS**（Long Term Support，长期支持版）安装包，一路下一步即可。

> ⚠️ 版本建议：**Node 20+ 是最低线**（LangChain.js v1 要求 20+），**22 / 24 LTS 是推荐**。别装 Current 版。

装完打开终端（Windows 用 PowerShell 或 Git Bash，macOS 用终端），验证：

```bash
node --version     # 例：v22.14.0
npm --version      # 例：10.9.2
```

⚠️ **两个命令都要能跑**。如果 `node` 提示「不是内部或外部命令」，说明 PATH 没配好——重装一次并勾选「添加到 PATH」。

### npm 是什么

**npm**（Node Package Manager）是 Node 生态的**包管理器**——负责下载、安装、管理第三方依赖包（library）。它随 Node 一起装好，不需要单独安装。

npm 的三个核心概念：

| 概念 | 含义 |
|------|------|
| **`package.json`** | 项目清单文件：记录项目名、依赖了哪些包、有哪些脚本 |
| **`node_modules/`** | 依赖包的实际存放目录（对应 Python 的虚拟环境 site-packages） |
| **包名@版本** | npm 上的一个包，比如 `typescript`、`react`、`@types/node` |

常用命令：

```bash
npm init -y                     # 生成 package.json 骨架（-y = 全部用默认值）
npm install express             # 装一个包到「生产依赖」
npm install -D typescript       # 装一个包到「开发依赖」
npm run build                   # 执行 package.json 里 scripts.build 定义的命令
```

⭐ **「依赖」vs「开发依赖」的区别**：生产依赖是程序运行时**必需**的（会被打进部署产物）；开发依赖是**只在开发编译时需要**的（部署后不需要）。TypeScript 属于后者——它产出的 `.js` 不需要 TypeScript 就能跑。

## 二、安装 TypeScript

### 建项目 + 装编译器

```bash
mkdir my-first-ts && cd my-first-ts
npm init -y
npm i -D typescript        # ⚠️ -D = --save-dev，装成开发依赖
```

安装后，`node_modules/.bin/` 下会出现一个叫 **`tsc`** 的可执行文件——`tsc` 就是 **TypeScript 编译器**（TypeScript Compiler）的命令行入口。

### ⚠️ 为什么必须是 `-D` 而不是全局安装

| 做法 | 命令 | 结果 |
|------|------|------|
| ✅ **本地开发依赖** | `npm i -D typescript` | 版本锁定在 `package.json`，团队和 CI 装出来的版本**完全一致** |
| ❌ **全局安装** | `npm i -g typescript` | 全机器共用一个版本，A 项目是 7.0、B 项目是 5.9，行为不一致，排查地狱 |

⭐ **铁律**：**永远用本地依赖 + `npx` 调用**，不要全局安装。

### 验证

```bash
npx tsc --version
```

⚠️ **`npx` 是什么**：`npx` 是 npm 自带的命令执行器，会**优先使用当前项目 `node_modules` 里的可执行文件**，找不到才去下载临时版本。所以 `npx tsc` 永远用的是项目锁定的那版 TS。

> 输出形如 `Version 7.0.0`。⚠️ 如果你看到的是 `5.x`，那说明装的是旧版——执行 `npm i -D typescript@latest` 更新。

## 三、⭐ `tsconfig.json` 最小配置

**`tsconfig.json`** 是 TypeScript 项目的配置文件，告诉编译器「怎么编译」。它必须叫这个名字、放在项目根目录，编译器才会自动找到它。

一个**能直接用**的最小版本：

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "outDir": "dist",
    "rootDir": "src",
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

### 逐字段解释

| 字段 | 含义 | 说明 |
|------|------|------|
| **`compilerOptions`** | 编译选项对象 | 所有编译行为配置都在里面 |
| **`target`** | 输出的 JS 语言版本 | 决定编译产物用哪个版本的语法。`ES2022` 覆盖 Node 20+ 与现代浏览器；越老的 target 兼容性越好、产物越大。⚠️ TS 6.0 的默认是 `es2025`，这里显式写 `ES2022` 是为了兼容面更广 |
| **`module`** | 输出的模块格式 | `NodeNext` = 跟随 `package.json` 里的 `"type"` 字段走。⚠️ TS 6.0 起默认值是 `esnext`，但 `esnext` 不适合直接跑在 Node 上，`NodeNext` 更安全 |
| **`moduleResolution`** | 模块解析规则 | 决定 `import` 一个路径时去哪找文件。现代项目跟 `module` 保持一致即可（`NodeNext` / `Bundler`） |
| **`strict`** | 严格模式总开关 | ⭐ **最关键的一个字段**。开启后，隐式 `any`、可能为 `undefined` 的值、可能为 `null` 的值都会报错 |
| **`outDir`** | 编译产物输出目录 | 生成的 `.js` 统一放这里，避免污染源码目录 |
| **`rootDir`** | 源码根目录 | 告诉编译器「源文件从哪开始」，`outDir` 下的目录结构由它推导 |
| **`esModuleInterop`** | ES 模块与 CommonJS 互操作 | 让 `import express from "express"` 这种写法在 Node 上正确工作 |
| **`skipLibCheck`** | 跳过第三方类型声明文件的检查 | 提速。⚠️ 只跳过**依赖库**的检查，**不跳过你自己代码的检查** |
| **`include`** | 要编译哪些文件 | 这里是数组，支持 glob 通配符，如 `["src/**/*"]` |

### ⚠️ `NodeNext` 依赖 `package.json` 的 `"type"` 字段

`module: "NodeNext"` 的意思是「**跟随 `package.json`**」——而 `package.json` 里那个 `"type"` 字段决定产物用哪种模块格式：

```json
// package.json
{
  "type": "commonjs"    // 默认值（npm init -y 生成的就是这个）→ 产物用 require/export
  // "type": "module"   // 改成这行 → 产物用 import/export
}
```

⚠️ **`npm init -y` 不会自动加 `"type": "module"`**，所以默认产物是 CommonJS（`require` / `module.exports`）。本篇的例子不用 import/export，两种格式跑起来都一样，所以先不用管。模块格式的完整规则见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/2-模块系统ESM与CommonJS|模块系统：ESM 与 CommonJS]]。

⚠️ **只写了 `module` 没写 `moduleResolution` 是不行的**——TS 6.0 之后两者必须配套（`NodeNext` 配 `NodeNext`、`ESNext` 配 `Bundler`），否则会报错。

### ⚠️ 关于 `strict`：为什么它必须开着

```ts
function greet(name: string) {
  console.log(name.toUpperCase());
}

let maybeName: string | undefined = undefined;
greet(maybeName);   // ⚠️ 若 strict 关闭：编译通过；运行时炸 TypeError
```

`strict: true` 时这行**直接编译报错**，告诉你「这里可能是 undefined」。这是 TS 存在的意义所在——**把线上事故提前到写代码的时候**。

⚠️ **新项目绝不要关 `strict`**。老项目实在关不掉时，也应该逐目录打开（`"strict": true` 可以配合 `// @ts-nocheck` 单文件豁免）。

### TS 6.0 的默认变化（⚠️ 别照抄老教程）

| 配置 | TS 6.0 起默认 | 影响 |
|------|--------------|------|
| `strict` | `true` | 不用再手写，但要知道它开了 |
| `module` | `esnext` | 直接用 `esnext` 跑 Node 上会有问题，推荐显式写 `NodeNext` |
| `target` | `es2025` | 新语法，兼容老浏览器时要手动调低 |
| `types` | `[]` | ⚠️ **不再自动引入 `@types/*`**。要用 Node 全局变量（`process`、`__dirname`）需显式写 `"types": ["node"]` |
| `noUncheckedSideEffectImports` | `true` | 只 import 不使用的副作用导入默认会被检查 |

⚠️ TS 6.0 已**废弃** `target: "es5"`、`moduleResolution: "node"`（node10）、AMD/UMD/SystemJS、`baseUrl` 作为查找根——**TS 7.0 会把它们变成硬错误**。

## 四、第一个 TypeScript 程序

### 目录结构

```text
my-first-ts/
├── package.json
├── tsconfig.json
├── node_modules/       ← npm 装的依赖（别手动改）
└── src/
    └── hello.ts        ← 源码放这里
```

### 代码

```ts
// src/hello.ts
function greet(name: string): string {
  return `你好，${name}！`;
}

const user: string = "张三";
const message: string = greet(user);

console.log(message);
```

### 编译 + 运行

```bash
# 1. 编译：读 tsconfig.json，把 src/ 下的 .ts 编译到 dist/
npx tsc

# 2. 运行：Node 执行编译产物
node dist/hello.js
```

输出：

```text
你好，张三！
```

### 看看编译产物长什么样

```bash
cat dist/hello.js
```

```js
"use strict";
Object.defineProperty(exports, "__esModule", { value: true });
function greet(name) {
    return `你好，${name}！`;
}
const user = "张三";
const message = greet(user);
console.log(message);
```

（前两行是 CommonJS 模式自动加的样板代码；用了 `"type": "module"` 就没有。**关键看后面——类型标注、返回值类型全部消失了。**）

⭐ 这就是上一节讲的「类型擦除」。

⚠️ **注意产物在 `dist/` 而不是 `src/`**：因为配了 `outDir: "dist"` 和 `rootDir: "src"`。如果没配，`.js` 会和 `.ts` 挤在同一个目录，甚至污染项目根目录。

### 单独编译一个文件

不想建工程时，可以直接指定文件（此时**忽略 `tsconfig.json`**）：

```bash
npx tsc hello.ts      # 产出 hello.js，和 hello.ts 并排
node hello.js
```

⚠️ 这种用法**不会**应用 `tsconfig.json` 里的 `strict` 等设置——所以生产项目别这么干，只适合临时试一下。

## 五、⭐ 三种运行 TS 的方式

这是新手最常问的问题。三种方式并存，选错的代价是**性能**或**心智负担**。

| 方式 | 命令 | 适用 | 原理 / 代价 |
|------|------|------|------------|
| **编译后运行** | `npx tsc && node dist/x.js` | **生产部署** | 最标准。产物是纯 JS，运行时零开销。⚠️ 改代码要重新编译 |
| **`tsx`** | `npx tsx src/x.ts` | ⭐ **本地开发首选** | 基于 **esbuild**（一个极快的 Rust 编写的转译工具）**按需转译，不做类型检查**，毫秒级启动 |
| **`ts-node`** | `npx ts-node src/x.ts` | 传统做法 | 通过 Node 的 loader 钩子逐文件转译，比 `tsx` 慢，且**与新版 Node 的 ESM 兼容性有坑** |

### 关键区别：类型检查

⭐ **只有 `tsc` 会做完整的类型检查**。

- `tsx` / `ts-node` **只转译不检查**——你的代码有类型错误，它照样跑
- 所以真实项目的流程是：**用 `tsc --noEmit` 单独做类型检查，用 `tsx` 跑代码**

```bash
npx tsc --noEmit          # 只检查类型，不产出文件（--noEmit = 不输出）
npx tsx src/hello.ts      # 直接跑
```

### 生产环境怎么配

```json
// package.json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "tsc",
    "start": "node dist/hello.js"
  }
}
```

```bash
npm run typecheck    # CI 里跑这一条挡住类型错误
npm run build        # 产出 dist/
npm start            # 生产启动
```

⚠️ **`npm start` 跑的是 `dist/hello.js`，不是 `src/hello.ts`**——生产环境里 Node 根本不认识 TS。

### 怎么装 `tsx`

```bash
npm i -D tsx              # 装成开发依赖
npx tsx src/hello.ts      # 直接用
```

⚠️ **`tsx` 也是开发依赖**。生产镜像里不需要它——因为生产跑的是编译好的 `.js`。

## 六、与 Python 的流程对照

Python 背景的读者可以这样映射：

| 环节 | Python | TypeScript |
|------|--------|-----------|
| 装运行时 | 装 CPython | 装 Node.js |
| 包管理器 | `pip` | `npm` |
| 依赖清单 | `requirements.txt` / `pyproject.toml` | `package.json` |
| 依赖隔离 | 虚拟环境 venv（要 `activate`） | `node_modules/`（**自动隔离，不用激活**） |
| 项目配置 | `pyproject.toml` / `setup.cfg` | `tsconfig.json` |
| 编译器 | 一般没有（`.pyc` 由解释器自动生成） | `tsc`（必需） |
| 跑单个文件 | `python x.py` | ⚠️ **不能直接跑**，需 `npx tsx x.ts` 或 `tsc` 后 `node x.js` |
| 类型检查 | 运行时才报（可选装 mypy/pyright） | 编译期就报（默认开启） |
| 发布到 PyPI | `python -m build` | `npm publish` |

⭐ **最大的体感差异**：Python 是「**写完直接跑**」，TS 是「**先编译再跑**」。多出的这一步就是类型安全的成本。

## 陷阱

1. **⚠️ 把 TypeScript 装成生产依赖**——用了 `npm i typescript` 而不是 `npm i -D typescript`。TypeScript 只在编译期用得上，装进生产依赖会让部署镜像白白变大，还可能被误当成运行时依赖。用 `package.json` 里的 `"devDependencies"` 检查一眼；
2. **⚠️ 全局安装 TypeScript**——`npm i -g typescript` 后到处能用 `tsc`，但版本不受项目控制，A 项目和 B 项目行为不一致，CI 上还会直接失败。只用 `npx tsc`；
3. **⚠️ `tsc` 提示「不是内部或外部命令」**——两种原因：① 没在项目里装（`npm i -D typescript`）；② 手动敲 `tsc` 而不是 `npx tsc`，导致 Node 找不到 `node_modules/.bin` 里的命令。**永远写 `npx tsc`**；
4. **⚠️ 输出目录污染项目根目录**——没配 `outDir` 时，`.js` 产物会和 `.ts` 源码混在一起，甚至落到根目录。后果：源码被覆盖、Git 里混进编译产物、VS Code 调试时找错文件。**必须配 `outDir` + `rootDir`**，并把 `dist/` 加进 `.gitignore`；
5. **⚠️ 忘了开 `strict` 或被老项目拖累不开 `strict`**——类型检查形同虚设，`undefined` 相关的线上事故照旧发生。新项目**一律 `strict: true`**；
6. **⚠️ 以为 `npx tsx` 会检查类型**——它只转译。类型错误要靠 `npx tsc --noEmit` 单独把关，否则错误会被推迟到线上。

## 小结

- **Node.js** 是跑 JS 的运行时；**npm** 是包管理器（随 Node 一起装）
- ⚠️ TypeScript 必须装成**本地开发依赖**：`npm i -D typescript`，调用写 `npx tsc`
- **`tsconfig.json`** 是必需的配置：`target`/`module`/`strict`/`outDir`/`rootDir`/`esModuleInterop` + `include`
- ⭐ **`strict: true` 不能关**——它是 TS 的价值所在
- 流程：`npx tsc` 编译到 `dist/` → `node dist/hello.js` 运行；产物是纯 JS，类型被擦除
- ⭐ 三种运行方式：编译后运行（生产）/ `tsx`（本地开发首选，esbuild 驱动，不做类型检查）/ `ts-node`（传统做法）
- CI 与本地都应跑 `npx tsc --noEmit` 单独做类型检查
- TS 6.0 默认 `strict: true`、`module: esnext`、`target: es2025`、`types: []`；7.0 已 GA

## 练习

1. 装好 Node（22/24 LTS），用 `node --version` 和 `npm --version` 验证；新建项目执行 `npm init -y` + `npm i -D typescript`，确认 `package.json` 里它出现在 `devDependencies` 而不是 `dependencies`。
2. 写一份 `tsconfig.json`（照第三节的最小配置），创建 `src/hello.ts`，跑通 `npx tsc` → `node dist/hello.js`，并 `cat dist/hello.js` 确认类型标注已消失。
3. 装 `tsx`（`npm i -D tsx`），用 `npx tsx src/hello.ts` 直接跑；然后在 `.ts` 里故意写一个类型错误（比如把字符串传给 `number` 参数），对比 `npx tsx`（照样跑）和 `npx tsc --noEmit`（报错）的差异。
4. 删掉 `tsconfig.json` 里的 `outDir`，重新编译，观察 `.js` 落在哪里；再把 `strict` 改成 `false`，观察第三节那个 `greet(maybeName)` 的报错如何消失。
5. 在 `package.json` 的 `scripts` 里配好 `typecheck` / `build` / `start` 三条脚本，然后用 `npm run` 依次跑通。
6. 对照第六节的表格，把你熟悉的 Python 流程逐项换成 TS 版本，说出「最大的体感差异」是什么。
