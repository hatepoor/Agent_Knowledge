# TypeScript 是什么与生态定位

> **什么时候该读**：你听说过 TypeScript，但不知道它跟 JavaScript 到底什么关系、为什么全世界都在用它。
> **阅读门槛**：零基础即可。本篇会从「JavaScript 是什么」讲起，不需要任何前置语言知识。

## 学习目标

读完本篇，你应当能够：

1. 说清 JavaScript 是什么、它跑在哪里
2. 亲手复现一个「运行时才炸」的类型错误，并解释它为什么恶心
3. 用一句话解释 TypeScript 是 JavaScript 的**超集**，以及「编译期类型擦除」意味着什么
4. 列出 TS 生态的四个支柱：`tsc`、`@types/*`、编辑器、框架
5. 说清本库中 LangChain.js / LangGraph.js 与 TS 的关系
6. 判断一个项目该用 TS 还是 JS 就够

## 一、JavaScript 是什么

**JavaScript**（常简称 JS）是一门编程语言。1995 年由 Netscape 浏览器公司发明，最初只为在网页里做交互效果（比如点按钮弹个框）。今天它已经跑在几乎所有地方：网页、后端服务器、手机 App、命令行脚本、桌面应用。

它的特点是**无处不在**：

- 浏览器原生支持 JS——所有现代浏览器（Chrome、Edge、Firefox、Safari）内置了 JS 引擎（**引擎**＝负责把 JS 源码翻译成机器码执行的内核，Chrome 的引擎叫 V8）
- 服务端有 **Node.js**（一个用 C++ 写、把 V8 引擎搬到服务器上的运行时程序）
- 手机、桌面、嵌入式设备都有各自的宿主实现

因此 JS 常被称为「**同构语言**」——同一套语言既能写前端也能写后端。

### JS 的类型系统：能跑，但经常跑错

JS 是**动态类型**语言：变量声明时不写类型，运行时才知道它是什么。

```js
// ⚠️ 这段代码语法完全合法，运行也不会立刻报错
let count = 10;
count = "十个";      // 合法——变量类型随时可以变
```

动态类型本身不是问题，问题是**类型错误要等到运行时才暴露**。下面三个例子都是真实会发生的：

### 场景一：调用不存在的方法（运行时崩溃）

```js
function calculateTotal(items) {
  // ⚠️ 手滑把 reduce 拼成了 reduc
  return items.reduc((sum, item) => sum + item.price, 0);
}

console.log(calculateTotal([{ price: 10 }, { price: 20 }]));
```

报错（运行时才出现）：

```text
TypeError: items.reduc is not a function
```

### 场景二：传错参数类型（运行时崩溃）

```js
function greet(name) {
  return "你好，" + name.toUpperCase();
}

greet(42);   // ⚠️ 42 是数字，没有 toUpperCase 方法
```

报错：

```text
TypeError: name.toUpperCase is not a function
```

### 场景三：静默算错（最危险，连报错都没有）

```js
function add(a, b) {
  return a + b;
}

console.log(add(1, "2"));   // ⚠️ 输出 "12"，不是 3
```

JS 的 `+` 遇到字符串就变成拼接。这行**不报任何错**，但账单金额错了。⭐ **静默错误比崩溃更可怕**——崩溃至少让你知道出事了。

⚠️ 这三个错误，在 TypeScript 里**全部在编译期就被拦下**，一行代码都跑不起来。

## 二、TypeScript 是什么：JavaScript 的超集

**TypeScript**（简称 TS）是微软在 2012 年推出的语言，由 **Anders Hejlsberg**（C# 与 Delphi 的作者）设计。它的定位一句话说清：

> **TypeScript 是 JavaScript 的超集（superset）——任何合法的 JS 代码都是合法的 TS 代码，反之不成立。**

「超集」意味着：**在已有 JS 代码里加一行类型标注，剩下的 JS 一行都不用改**。这让 TS 可以渐进式（incremental）引入，不用重写整个项目。

### TS 长什么样

```ts
// ✅ 完全合法的 JavaScript
function add(a, b) {
  return a + b;
}
```

```ts
// ✅ 完全合法的 TypeScript
function add(a: number, b: number): number {
  return a + b;
}
```

区别只有三处标注：参数 `a: number`、参数 `b: number`、返回值 `: number`。**这种「变量名后面加冒号再写类型」的写法叫作类型标注（type annotation）**。

### 编译：TS 变回 JS

TS 不是一门能被 CPU 直接执行的语言。它的执行流程是：

```text
hello.ts  ──[tsc 编译]──▶  hello.js  ──[Node/浏览器执行]──▶  输出结果
(带类型)                (纯 JavaScript，类型全部消失)
```

安装 TypeScript 后，编译命令是：

```bash
npx tsc hello.ts      # 产出 hello.js
node hello.js         # 执行编译产物
```

⚠️ **`.ts` 文件本身永远不会被浏览器或 Node 直接执行**——必须先编译成 `.js`。这一点是理解后面所有内容的关键。

## 三、⭐ TS 的「编译期」本质：类型在运行时被完全擦除

⭐ **这是整本教程最重要的一句话**：

> **TypeScript 的类型只存在于编译期。编译产物是纯 JavaScript，里面没有任何类型信息。**

这个机制叫 **类型擦除（type erasure）**——编译器在生成 JS 时，把所有类型标注、接口声明、类型别名**彻底删除**。

```ts
// 源码 hello.ts
interface User {
  name: string;
  age: number;
}

function describe(user: User): string {
  return `${user.name}  ${user.age} 岁`;
}
```

编译后得到的 `hello.js`（**注意里面什么都没有了**）：

```js
"use strict";
Object.defineProperty(exports, "__esModule", { value: true });
function describe(user) {
    return `${user.name}  ${user.age} 岁`;
}
```

（前两行是模块格式自动加的样板代码，可以先忽略。）

`interface User` 整个消失了，`user: User` 里的 `: User` 消失了，返回值类型也消失了。

### 三种语言放在一起对比

| 语言 | 类型信息在编译后 | 运行时能不能读到类型 |
|------|------------------|---------------------|
| **TypeScript** | ❌ 全部擦除 | ❌ 完全读不到 |
| Java | ✅ 保留在 `.class` 字节码里 | ✅ 反射能读到 `int`、`String` |
| Python | ✅ 注解保留在函数对象上 | ✅ `func.__annotations__` 能读到 |

Python 的注解运行时确实存在：

```python
def add(a: int, b: int) -> int:
    return a + b

print(add.__annotations__)   # {'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

TS 完全做不到这件事——`describe.length` 只能告诉你「这个函数有 1 个参数」，参数是不是 `User` 类型的，运行时无从得知。

⚠️ **这条性质的三个直接后果**（后面章节还会反复用到）：

1. **运行时不能靠类型做校验**——想做「外部输入是否符合预期类型」，必须引入额外工具（如 Zod），或自己手写 `typeof` 判断；
2. **类型不会影响运行时性能**——TS 和纯 JS 跑起来速度基本一样，类型检查只拖慢编译，不拖慢执行；
3. **`as` 断言（断言某个类型）在编译期也不产生任何检查**——它是纯粹的「我保证」，编译器只管语法不管对错。

## 四、TS 需要一个「宿主」来跑

TS 编译出的 JS **必须交给某个宿主程序执行**。常见宿主只有三类：

| 宿主 | 跑什么 | 典型场景 |
|------|--------|----------|
| **Node.js** | 服务端 / 命令行 | 后端 API、脚本、CLI 工具 |
| **浏览器** | 网页前端 | React / Vue / Svelte 页面 |
| **Deno / Bun** | 服务端，且**能直接跑 `.ts`** | 新一代运行时，省掉编译步骤 |

- **Node.js** 是服务器端的 JS 运行时（runtime＝「提供执行环境的程序」）。它把浏览器里的 V8 引擎搬到了服务器，并额外提供文件系统、网络等浏览器没有的能力。本库的 [[typescript/02-中段阶段-专题精讲/Node生态与异步/1-Node运行时与HTTP服务|Node 运行时与 HTTP 服务]] 专门讲这条线。
- **Deno** 和 **Bun** 是较新的运行时，原生内置了 TS 转译能力——写 `.ts` 文件直接 `deno run x.ts` / `bun run x.ts`，不需要 `tsc` 这一步。它们不改变「TS 编译成 JS」的本质，只是把编译步骤内置进了运行时。

⭐ **一句话记住**：TypeScript 负责「写」，Node 或浏览器负责「跑」，两者分工明确。

## 五、生态版图

TS 能流行，靠的不是语言本身，而是围绕它长出来的一整套工具。

| 支柱 | 说明 |
|------|------|
| **`tsc` 编译器** | TypeScript 自带的命令行编译器。`npx tsc` 既做**类型检查**（报告错误）也做**转译**（生成 `.js`）。用其他构建工具时也可以只用它的类型检查能力 |
| **`@types/*` 类型声明包** | 第三方库大多用 JS 写的，本身没有类型信息。`@types/xxx` 就是「这个库的说明书」，告诉编辑器每个函数收什么参数、返回什么。最大的来源是 **DefinitelyTyped** 社区仓库 |
| **编辑器支持** | VS Code 内置了 TypeScript 语言服务（language service：编辑器背后负责补全、跳转、重构的类型分析引擎），**装完 Node 和 TS 就有**，不需要额外插件。补全、跳转定义、批量重命名全部基于类型信息 |
| **框架支持** | React、Vue 3、Svelte、Next.js、NestJS、Fastify、Prisma、Vite……主流框架**全部 TS 化**（框架自身的类型定义用 TS 写，且官方文档以 TS 为默认示例） |

⭐ 最有说服力的一条：**几乎所有新出的 JavaScript 库，`.d.ts` 类型声明是标配**。哪怕库本体是 JS 写的，作者也会补一份类型声明——因为不给类型的库，在 TS 社区会被当成「半成品」。

## 六、⭐ 与本库其他主题的连接

这条线很重要：**TypeScript 不是一门孤立的语言，它是 LangChain.js / LangGraph.js 的一等公民。**

### 1. LangChain.js / LangGraph.js 是 TS 生态的一等公民

LangChain 的 JS 版本（包名 `langchain`）与 Python 版本**平起平坐**，不是「降级移植」：

- 官方文档以 JS/TS 为主要示例语言，类型定义完整；
- 本库 [[langchain/overview/LangChain概述|LangChain 概述]] 里的概念（模型、工具、Agent、流式输出）在 JS 侧一一对应；
- [[langgraph/overview/LangGraph概述|LangGraph 概述]] 里的 `StateGraph`（有状态图）同样有完整的 TS 实现（`@langchain/langgraph` 包）。

⚠️ 但要注意 **TS 版本不等于「零运行时类型」**：LangChain.js v1 做结构化输出（structured output）时用的是 **Zod**——一个**运行时**校验库。原因正是第三节那条：TS 类型在运行时被擦除，模型返回的 JSON 是不可信的外来数据，必须在运行时真校验。

### 2. Node.js 服务端

TS 最主流的落地场景之一就是服务端：Node + TS 写后端 API。入口在 [[typescript/02-中段阶段-专题精讲/Node生态与异步/1-Node运行时与HTTP服务]]。

### 3. Python 对照

本库读者如果已会 Python，迁移最快的路径是逐项对照：见 [[typescript/01-入门阶段-基础教程/第00章-学前准备/0.3-TypeScript与Python的差异|TypeScript 与 Python 的差异]]。

## 七、什么时候该用 TS，什么时候 JS 就够

| 场景 | 建议 | 理由 |
|------|------|------|
| 单个脚本、一次性任务 | **JS 够** | 类型收益抵不上搭环境的成本 |
| 十几行的小工具 | **JS 够** | 同上 |
| 中大型应用 | **用 TS** | 几百个文件后，没有类型基本改不动 |
| 团队协作（≥3 人） | **用 TS** | 编辑器的跳转/重构能力就是生产力 |
| 发布给别人的 npm 库 | **用 TS** | 必须提供 `.d.ts` 类型声明，否则使用者体验极差 |
| 已有 JS 老项目 | **渐进式引入** | 用 `allowJs` 让 TS 先「看着」老代码，改到哪儿给哪儿加标注 |
| 与 LangChain.js / LangGraph.js 配合 | **用 TS** | 生态默认语言，类型能帮你避开大量 API 误用 |

⭐ **判断标准很简单**：代码会**活过一周**并且**会被别人改**，就用 TS；一次性脚本就用 JS。

⚠️ 反过来的常见误区是「**TS 万能**」。TS 不解决：运行时性能问题（想更快该用 WASM 或换语言）、并发模型问题（Node 单线程的局限）、包体积问题（类型本身不进产物，但构建链会变重）。

## 八、版本基线

⚠️ **写这个教程时，TypeScript 最新稳定版已经不是 5.x 了**。认准这张表：

| 版本 | 状态 | 关键事实 |
|------|------|----------|
| **7.0** | ✅ 已 GA（2026-07-08） | 编译器换成 **Go 原生实现**（代号 `tsgo`），编译速度大幅提升。⚠️ **不提供 compiler API**——`typescript-eslint` 等直接调用 TS 内部 API 的工具需暂时留在 6.0 |
| **6.0** | ✅ 2026-03-23 发布，维护中 | **最后一个纯 JavaScript 实现版本**。默认 `strict: true`、`module: esnext`、`target: es2025` |
| **5.x** | 维护线 | 存量项目大量停留于此，新项目不建议从这里起步 |

> ⚠️ **别再写「TypeScript 5 是最新的」**——5.x 已是维护线，当前是 6.x / 7.x。

TS 6.0 还有一组影响体验的默认值变更，初学者必须知道：

- `strict: true` —— 类型检查默认就是严格模式（好事）
- `types: []` —— **不再自动引入 `@types/*`**。想用 Node 的 `process` 等全局变量，需要显式写 `"types": ["node"]`
- `noUncheckedSideEffectImports: true` —— 副作用导入（只 import 不取值）默认会被检查

这些变更的细节与配置写法在 [[typescript/02-中段阶段-专题精讲/工程化与工具链/1-编译流程与tsconfig|编译流程与 tsconfig]] 里展开。

## 陷阱

1. **⚠️ 以为 TS 是「带类型的 JS 运行时」**——TS 不是运行时，是一种**编译期语言**。产物是纯 JS，类型信息全部消失；
2. **⚠️ 以为 `tsc` 会自动运行你的代码**——`tsc` 只编译不执行。执行是 `node` 的事；
3. **⚠️ 以为装完 `typescript` 就能写 TS**——还要一个宿主（Node/浏览器）和一份 `tsconfig.json`（见下一篇）；
4. **⚠️ 以为 TS 能替代运行时校验**——外部数据（用户输入、模型返回的 JSON）必须用 Zod 之类的工具在运行时校验，TS 类型帮不上忙；
5. **⚠️ 把 `as` 当成安全检查**——`x as Foo` 只是「我向编译器保证」，编译器不验证、不报错、运行时更不管，写错了照样炸；
6. **⚠️ 用旧教程的「TypeScript 5 是最新」**——当前是 7.0 GA / 6.0 维护中，5.x 只是维护线。

## 小结

- **JavaScript** 是无处不在的动态类型语言；**类型错误只在运行时暴露**，甚至静默算错
- **TypeScript 是 JavaScript 的超集**：加类型标注，其余语法完全兼容，可渐进式引入
- ⭐ **TS 的本质是编译期语言**：编译产物是纯 JS，**类型被完全擦除**，运行时读不到任何类型信息
- TS 需要**宿主**执行：Node.js 跑服务端、浏览器跑前端、Deno/Bun 可直接跑 `.ts`
- 生态四支柱：`tsc` 编译器、`@types/*` 声明包、VS Code 内置语言服务、全 TS 化的框架
- LangChain.js / LangGraph.js 是 TS 生态一等公民，但结构化输出仍需 Zod 做运行时校验
- 选型：脚本用 JS，应用 / 团队 / 库用 TS
- 版本：7.0 已 GA（Go 原生编译器），6.0 是最后一个 JS 实现版，5.x 为维护线

## 练习

1. 在纸上或浏览器控制台里复现第一节的三个错误（拼错方法名、传错参数类型、`add(1, "2")`），记录各自的报错或错误输出。
2. 把上面三个例子改写成 TypeScript，写完后运行 `npx tsc`（或用在线的 TS Playground），确认**三个错误全部在编译期被报出**，并把报错信息抄下来。
3. 写一个 `interface User { name: string; age: number }`，编译成 JS 后打开产物文件，确认 `interface` 与类型标注已经全部消失——亲眼验证「类型擦除」。
4. 查一下你手头项目的 TS 版本（`npx tsc --version`），对照第八节的版本基线，判断它在哪个版本线上。
5. 思考并写下结论：既然类型在运行时被擦除，为什么 LangChain.js 做结构化输出时还要用 Zod？
