# 类型收窄与类型守卫

> **什么时候该读**：你从接口拿到的数据是 `unknown` / `any`，不知道是字符串还是对象；或者你写了 `switch` 但编译器在某个分支里还是让你强转；又或者你想让"处理失败"这件事变成**类型信息**而不是抛异常。
> **阅读门槛**：读完 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.3-泛型与类型约束]]。本篇的 `never`、穷尽检查依赖 2.2 讲的判别联合；`unknown` 的基础见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.1-类型推断与注解]]。

## 学习目标

读完本篇，你应当能够：

1. 说清**收窄（narrowing）**是什么，并列出 TS 的主要收窄触发点
2. ⭐ 写**用户自定义类型守卫** `function isString(x: unknown): x is string`，说清 `x is T` 签名的作用
3. ⭐ 写**断言函数** `function assertString(x: unknown): asserts x is string`（TypeScript 3.7+），并说清它与类型守卫的区别
4. ⭐ 用 `never` 类型做**穷尽检查**，写出 `const _exhaustive: never = x` 这个惯用法
5. 说明 `never` 的另一个用途（函数永不返回）
6. 解释 `?.`（可选链）与 `??`（空值合并）在收窄中的作用与局限
7. 避开三个经典陷阱：`typeof null === "object"`、`Array.isArray` 对 `any[]` 的收窄失效、收窄在闭包/回调中失效

## 一、什么是类型收窄

### 问题：一个值可能是多种类型

```ts
function printLength(x: string | number) {
  console.log(x.length);   // ⚠️ 报错：Property 'length' does not exist on type 'string | number'
}
```

**收窄（narrowing，也叫类型收窄 / type narrowing）** 是指 TypeScript 根据代码路径**推断出当前这个值具体是哪个类型**，从而允许你访问该类型独有的属性。

### 收窄是编译期的，不改运行时

```ts
function printLength(x: string | number) {
  if (typeof x === "string") {
    console.log(x.length);   // ✅ 编译通过
  }
}
```

编译后的 JavaScript 里，`typeof x === "string"` 这个判断**本来就有**（运行时行为完全没变）。TypeScript 只是**读懂**了这个判断，并用它来收窄类型。

⭐ **收窄不等于转换**。运行时那个值从来没有变过类型，变的只是"编译器认为它是什么"。

### 收窄依赖于"控制流分析"（control flow analysis）

TypeScript 会沿着代码的**执行路径**做分析：

```ts
function f(x: string | null) {
  // 这里 x 的类型是 string | null
  if (x === null) {
    return;                    // 这个分支里 x 是 null
  }
  console.log(x.length);        // ✅ 这个分支里 x 是 string（null 已被排除）
}
```

## 二、⭐ 收窄的触发点

TypeScript 有 8 类主要的收窄手段：

| 触发点 | 例子 | 收窄结果 |
|--------|------|---------|
| **`typeof`** | `typeof x === "string"` | 排除掉不可能是该 typeof 的成员 |
| **`instanceof`** | `x instanceof Error` | 收窄到该类及其子类 |
| **`in` 运算符** | `"name" in x` | 按"哪个成员有该属性"收窄 |
| **真值检查** | `if (x)` / `if (!x)` | 排除 `null`、`undefined`、`""`、`0`、`false`、`NaN` |
| **相等检查** | `x === null`、`x !== undefined` | 排除特定成员 |
| **显式类型标注** | `const y: string = x` | 从赋值处确定类型 |
| **`switch`** | `switch (x.kind)` | 按判别器收窄（2.2 第四节） |
| **类型守卫 / 断言函数** | `if (isString(x))` | 按你自己定义的规则收窄 |

### 逐个看

**1. `typeof`**

```ts
function f(x: string | number | boolean) {
  if (typeof x === "string") {
    x.toUpperCase();   // ✅ x: string
  } else if (typeof x === "number") {
    x.toFixed();       // ✅ x: number
  } else {
    x.valueOf();       // ✅ x: boolean
  }
}
```

⭐ `typeof` 的返回值只有这几个字符串：`"string"`、`"number"`、`"bigint"`、`"boolean"`、`"symbol"`、`"undefined"`、`"object"`、`"function"`。**没有 `"null"`**（这是第七节的一个坑）。

**2. `instanceof`**

```ts
function f(x: Error | string) {
  if (x instanceof Error) {
    x.message;   // ✅ x: Error
  } else {
    x.toUpperCase();   // ✅ x: string
  }
}
```

⭐ `instanceof` 检查的是**原型链**，所以子类实例也会匹配。

**3. `in`**

```ts
type Cat = { meow(): void };
type Dog = { bark(): void };

function speak(pet: Cat | Dog) {
  if ("meow" in pet) {
    pet.meow();   // ✅ x: Cat
  } else {
    pet.bark();   // ✅ x: Dog
  }
}
```

**4. 真值检查**

```ts
function f(x: string | null | undefined) {
  if (x) {
    x.toUpperCase();   // ✅ x: string（null 和 undefined 被排除）
  }
}
```

⚠️ 真值检查排除的不止 `null`/`undefined`——还包括 `""`、`0`、`false`、`NaN`。所以真值检查**不能用来区分 `0` 和 `undefined`**：

```ts
function g(x: number | undefined) {
  if (x) {
    // ⚠️ 这里 x 是 number，但排除了 0
  }
}
```

**5. 相等检查**

```ts
function f(x: string | null) {
  if (x === null) return;
  x.toUpperCase();   // ✅ x: string
}
```

**6. 显式类型标注**

```ts
declare const u: unknown;
const s: string = u as string;   // 用断言或收窄把类型"钉"下来
```

**7. `switch` + 判别器**

```ts
type State =
  | { kind: "idle" }
  | { kind: "loading"; progress: number };

function f(s: State) {
  switch (s.kind) {
    case "idle": break;
    case "loading":
      console.log(s.progress);   // ✅ s 被收窄
      break;
  }
}
```

**8. 自定义类型守卫 / 断言函数**——见第三、四节。

## 三、⭐ 用户自定义类型守卫

### 问题：内置收窄不够用

假设你要判断一个值是不是"用户对象"（有 `id` 和 `name`），这个判断没有现成的 `typeof` / `instanceof` 能表达。

### 用户自定义类型守卫（user-defined type guard）

**类型守卫（type guard）** 是一个返回 `boolean` 的函数，但它的**返回类型注解**里带一个特殊结构 `x is T`：

```ts
function isString(x: unknown): x is string {
  return typeof x === "string";
}
```

⭐ **`x is string` 这个签名是关键**：它告诉编译器"**如果这个函数返回 `true`，那么 `x` 在调用点就是 `string` 类型**"。

### 使用效果

```ts
function isString(x: unknown): x is string {
  return typeof x === "string";
}

declare const value: unknown;

if (isString(value)) {
  value.toUpperCase();   // ✅ value 在这里是 string
} else {
  // 这里 value 还是 unknown（守卫只会"变窄"，不会"放宽"）
}
```

### 更实用的例子：校验接口返回值

```ts
interface User {
  id: string;
  name: string;
}

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  return "id" in value && typeof value.id === "string"
      && "name" in value && typeof value.name === "string";
}

declare const res: unknown;

if (isUser(res)) {
  console.log(res.name);   // ✅ res: User
}
```

### ⚠️ 类型守卫的三条硬性要求

| 要求 | 说明 |
|------|------|
| **必须是函数** | 不能是箭头函数属性以外的任何形式 |
| **返回类型必须是 `boolean`** | 不能返回 `string \| boolean` 之类 |
| **返回类型注解必须写成 `x is T`** | 写成 `boolean` 就退化成普通函数，没有收窄能力 |

```ts
// ❌ 写成 boolean 就没有收窄能力
function isString2(x: unknown): boolean {
  return typeof x === "string";
}

declare const v: unknown;
if (isString2(v)) {
  v.toUpperCase();   // ⚠️ 报错：v 还是 unknown
}
```

### 类型守卫 vs 类型谓词函数的"双向"陷阱

类型守卫**只能变窄，不能放宽**：

```ts
function isNumber(x: number | string): x is number {
  return typeof x === "number";
}
// 这里参数类型是 number | string，守卫说是 number —— 合法（是子类型）
```

```ts
function isString3(x: string): x is string | number {
  return true;
}
// ⚠️ 报错：类型守卫的返回类型必须是参数类型的子类型
```

## 四、⭐ 断言函数 `asserts x is T`

### 与类型守卫的区别

| | 类型守卫 `x is T` | 断言函数 `asserts x is T` |
|---|-------------------|------------------------|
| 返回值 | `boolean` | **`void`**（不返回任何值） |
| 调用方式 | `if (isString(x)) { ... }` | `assertString(x);` —— **必须单独一条语句** |
| 生效范围 | 条件成立的那个分支内 | **调用语句之后的所有代码** |
| 失败时 | 返回 `false`，走 else | **应该抛异常**（断言失败 = 抛错） |
| 版本 | 一直都有 | **TypeScript 3.7+** |

### 写法

```ts
function assertString(x: unknown): asserts x is string {
  if (typeof x !== "string") {
    throw new Error("期望字符串，实际收到：" + typeof x);
  }
}
```

⚠️ **关键实现要求**：函数体**必须真的可能抛出异常**（或者调用一个会抛的函数）。

```ts
// ⚠️ 这个实现是错的：条件不满足时直接 return，
//    但调用方的代码仍然会按"x 一定是 string"继续执行 → 运行时炸
function assertString2(x: unknown): asserts x is string {
  if (typeof x !== "string") {
    return;   // ❌ 应该 throw
  }
}
```

⚠️ **注意**：TypeScript **不会**帮你检查这一点（实测 TS 5.8 / 7.0 均不报错）——编译器完全信任你的 `asserts` 签名。所以"必须抛错"是一条**纯靠自觉的约定**，写错了编译器不管、运行时才炸。

⭐ **对比 `never` 返回类型的函数**：那个是**编译器强制**的——

```ts
function assertNever(x: never): never { }
// ⚠️ 报错 TS2534：A function returning 'never' cannot have a reachable end point
```

因为 `never` 语义上要求"函数永远不返回"，编译器能直接检查出来；而 `asserts` 是"信任我"的约定，编译器无从判断。

### 使用效果

```ts
function assertString(x: unknown): asserts x is string {
  if (typeof x !== "string") throw new Error("not a string");
}

declare const value: unknown;

assertString(value);        // 单独一条语句，不能写进 if
console.log(value.toUpperCase());   // ✅ value 现在是 string
```

### 实战：把"校验失败"变成类型信息

```ts
interface User { id: string; name: string }

function parseUser(input: string): User {
  const data: unknown = JSON.parse(input);

  if (!isUser(data)) {
    throw new Error("用户数据格式错误");
  }
  return data;   // ✅ data 在这里已经是 User
}

function isUser(value: unknown): value is User {
  if (typeof value !== "object" || value === null) return false;
  const v = value as Record<string, unknown>;
  return typeof v.id === "string" && typeof v.name === "string";
}
```

### ⚠️ 断言函数的箭头函数写法

用箭头函数写断言函数时，**声明本身不报错，但调用时会报错**：

```ts
const assertString = (x: unknown): asserts x is string => {
  if (typeof x !== "string") throw new Error("not a string");
};

declare const v: unknown;
assertString(v);              // ⚠️ 报错 TS2775：Assertions require every name in the call target to be declared with an explicit type annotation
console.log(v.toUpperCase());  // ⚠️ 连带报错：v 还是 unknown，收窄没生效
```

⚠️ **原因**：TypeScript 要求"**断言函数的名字必须带显式类型注解**"——因为编译器要靠这个注解认出"这是个断言函数"。`const assertString = ...` 这种写法，编译器只能从变量的**初始化表达式**反推类型，而箭头函数的推断类型里丢失了 `asserts` 信息。

**正确写法：给变量本身写显式类型注解**：

```ts
const assertString: (x: unknown) => asserts x is string = (x) => {
  if (typeof x !== "string") throw new Error("not a string");
};

declare const v: unknown;
assertString(v);              // ✅ 不报错
console.log(v.toUpperCase());  // ✅ v 已收窄为 string
```

> 💡 **记忆点**：**`function` 声明的断言函数随便写；`const` 箭头函数必须显式标注变量的类型。**

> **版本说明**：`asserts x is T` 是 **TypeScript 3.7** 引入的。上面 TS2775 这条规则在 TS 3.7 与 5.x / 7.x 上表现一致。

## 五、⭐ `never` 类型与穷尽检查

### `never` 是什么

**`never` 是"底部类型"（bottom type）**——它表示"**这个值不可能存在**"。它是所有类型的**子类型**，也是**唯一没有任何类型是它的子类型**的类型。

```ts
function fail(): never {
  throw new Error("永远不会正常返回");
}
// ⚠️ fail 的返回类型是 never，因为它总是抛异常
```

### 用途一：函数永不返回

```ts
function throwError(msg: string): never {
  throw new Error(msg);
}

function process(input: string): string {
  if (!input) {
    throwError("输入为空");   // ✅ 因为 throwError 返回 never，
  }                            //    这个分支之后 input 一定是非空字符串
  return input.trim();
}
```

⭐ **为什么这有用**：`never` 类型的函数调用之后，编译器知道"控制流不会从这里继续"，所以能正确处理后面的收窄。

### 用途二：穷尽检查（exhaustive check）

⭐ **这是 `never` 最有价值的用法**，也是 TS 的标准惯用法。

```ts
type Status = "pending" | "success" | "error";

function assertNever(x: never): never {
  throw new Error("未处理的状态: " + x);
}

function handle(status: Status): string {
  switch (status) {
    case "pending": return "等待中";
    case "success": return "成功";
    case "error":   return "失败";
    default:
      // ⭐ 关键：编译器证明这里 status 只能是 never
      return assertNever(status);
  }
}
```

**⭐ 机制拆解**：

1. `switch` 的三个 `case` 覆盖了 `Status` 的**全部**可能值；
2. 于是 `default` 分支里的 `status` 的类型是 `never`（**不可能是别的东西**）；
3. `assertNever` 的参数类型是 `never`，所以 `status` 传进去**刚好合法**。

### ⭐ 它的真正价值：改代码时自动报错

假设以后 `Status` 加了一个新成员 `"cancelled"`：

```ts
type Status = "pending" | "success" | "error" | "cancelled";
```

**不用改 `handle` 函数**，编译立刻报错：

```text
错误：类型 '"cancelled"' 不能赋给类型 'never'。
```

⭐ **一句话**：穷尽检查把"**新增枚举值时容易漏掉分支**"这个运行时 bug，提前变成编译错误。这就是"让非法状态无法被表示"的实践。

### 完整的判别联合 + `never` 例子

```ts
type Result =
  | { kind: "success"; data: string }
  | { kind: "error"; code: number; message: string };

function assertNever(x: never): never {
  throw new Error("未处理的类型: " + JSON.stringify(x));
}

function render(result: Result): string {
  switch (result.kind) {
    case "success":
      return result.data;
    case "error":
      return `${result.code}: ${result.message}`;
    default:
      return assertNever(result);   // ✅ 穷尽性证明
  }
}
```

### `never` 的第三个用途：⚠️ 它**不能**用来表示"空函数"

```ts
function doNothing(): never {
  // ⚠️ 报错 TS2534：A function returning 'never' cannot have a reachable end point
  // 原因：这个函数能正常走到末尾 → 它**有可能返回** → 那它的返回类型就不该是 never
}
```

⚠️ `never` **不等于 `void`**：

| 类型 | 含义 |
|------|------|
| `void` | 「返回值没有意义」——调用者不关心返回什么 |
| `never` | 「**永远不会返回**」——函数总是抛异常或永不结束 |

```ts
function log(msg: string): void {
  console.log(msg);   // ✅ void：正常返回 undefined
}
```

⭐ **区别在于**：标 `void` 的函数**可以**正常走到末尾返回 `undefined`；标 `never` 的函数**必须**以抛异常或无限循环的方式结束，否则编译器报错。

## 六、`?.` 与 `??` 在收窄中的作用

### 可选链 `?.`

**可选链（optional chaining）** 在值为 `null` 或 `undefined` 时短路返回 `undefined`，不会抛"cannot read property of undefined"。

```ts
interface User {
  profile?: {
    avatar?: string;
  };
}

declare const user: User;

console.log(user.profile?.avatar);        // ✅ 不会报错
console.log(user.profile?.avatar?.length); // ✅ 链式也安全
```

### 空值合并 `??`

**空值合并（nullish coalescing）** 在左侧为 `null` 或 `undefined` 时返回右侧。

```ts
declare const config: { port?: number };

const port = config.port ?? 8080;   // port 为 null/undefined 时用 8080
```

⭐ **`??` 与 `||` 的关键区别**——`??` 只认 `null` 和 `undefined`，`||` 认**所有**"假值"（`0`、`""`、`false`、`NaN`）：

```ts
declare const maybeNum: number | undefined;
declare const maybeStr: string | undefined;

const a = maybeNum ?? 1;    // 0 时仍然得到 0 ← ?? 只对 null/undefined 生效
const b = maybeNum || 1;    // 0 时得到 1     ← || 对所有"假值"生效

const c = maybeStr ?? "x";  // "" 时仍然得到 "" ← 空字符串是有效值
const d = maybeStr || "x";  // "" 时得到 "x"
```

⭐ **实际影响**：用 `||` 写默认值时，`0`（比如「重试次数为 0」）、`""`（比如「用户名为空字符串」）这些**合法的业务值**会被悄悄替换掉——这是真实项目里非常常见的 bug。**默认值一律用 `??`。**

### 它们和收窄的关系

```ts
function f(x: string | null) {
  // ① 用 ?? 后，x 仍可能为 null，但可以安全地处理
  const name = x ?? "匿名";
  console.log(name.length);   // ✅ name 是 string

  // ② 用 ?. 后，结果类型会带上 undefined
  const len = x?.length;      // 类型：number | undefined
}
```

⭐ **它们是"值层面"的保护，不等于类型收窄**：

```ts
function f(x: string | undefined) {
  const len = x?.length;
  // ⚠️ len 的类型是 number | undefined，不是 number
  // ?. 只保证"不抛异常"，不保证"有值"
}
```

### ⚠️ `?.` 不会收窄变量的类型本身

这是本节的陷阱：

```ts
function f(x: string | undefined) {
  if (x) {
    // ✅ 这里 x 被收窄成 string
  }

  const len = x?.length;   // 类型：number | undefined
  // ⭐ 注意：x?.length 的存在**不会**让 x 本身变成 string
}
```

更直白的例子：

```ts
declare let maybe: string | undefined;

// ❌ 报错：string | undefined 不能赋给 string
const s: string = maybe;

// ❌ 报错：可选链的结果仍然带 undefined
const s2: string = maybe?.trim();
```

⭐ **结论**：`?.` 和 `??` 让你**写代码不炸**；要让**类型**变干净，还得靠 `if` + 真值检查收窄，或者类型守卫。

### `?.` 与 `??` 配合的常见模式

```ts
interface Account {
  address?: { city?: string };
}
declare const user: Account;
declare const a: string | undefined;
declare const b: string;
declare const c: string;

// 深取值 + 默认值
const city = user?.address?.city ?? "未知";

// 可选链 + 空值合并 的优先级
// ⚠️ ?? 不能和 || / && 混用（不写括号会报错）
const v = a ?? (b || c);   // ✅ 要加括号
```

## 七、⚠️ 三个经典陷阱

### 陷阱一：`typeof null === "object"`（历史 bug）

⭐ **这是 JavaScript 的历史遗留 bug**，从 1995 年就存在，且**永远不会被修复**（修了会破坏大量线上代码）。

```js
typeof null          // "object"  ← 不是 "null"！
typeof undefined     // "undefined"
typeof []            // "object"
typeof (() => {})    // "function"
```

**为什么**：早期 JS 用低两位标记值类型，`null` 的全零表示和对象指针撞了。

**对 TypeScript 的影响**：

```ts
function f(x: string | null) {
  if (typeof x === "object") {
    // ⚠️ 这里 x 的类型是 null（不是 string）
    // 因为 typeof null === "object"，TS 也认为这个分支里 x 可能是 null
  }
}
```

⭐ **TS 忠实地反映了运行时的真实行为**——它不会"自作聪明"地假设 `typeof x === "object"` 排除了 `null`。

**正确写法**：

```ts
function f(x: string | null | object) {
  if (x !== null && typeof x === "object") {
    // ✅ 现在 x 确实是对象
    Object.keys(x);
  }
}
```

### 陷阱二：`Array.isArray` 对 `any[]` 的收窄失效

```ts
function f(x: any[]) {
  if (Array.isArray(x)) {
    // ⚠️ x 仍然是 any[] —— 没有任何收窄
    // 因为 x 本来就是数组，守卫等于没检查
  }
}
```

**更常见的场景**——`Array.isArray` 把 `unknown` 收窄成 `any[]`：

```ts
function f(x: unknown) {
  if (Array.isArray(x)) {
    // ⚠️ x 的类型是 any[] —— 不是 unknown[]！
    // 元素类型是 any，等于放弃了检查
    x[0].foo.bar;   // 编译通过，但运行时可能炸
  }
}
```

⭐ **问题的本质**：`Array.isArray` 的类型定义是 `(arg: any) => arg is any[]`——它只能把类型收窄到 `any[]`，而 `any[]` 的元素类型是 `any`，**等于把检查又还回去了**。

**解法：写一个自己的守卫，用 `unknown[]`**：

```ts
function isArrayOf<T>(x: unknown): x is T[] {
  return Array.isArray(x);
}

// 或者更实用的：解析接口返回
function isStringArray(x: unknown): x is string[] {
  return Array.isArray(x) && x.every(item => typeof item === "string");
}

declare const res: unknown;
if (isStringArray(res)) {
  res[0].toUpperCase();   // ✅ res: string[]
}
```

⭐ **通用原则**：**任何以 `any` 作为收窄目标的守卫，都是在放弃检查**。收窄到 `unknown[]`、`Record<string, unknown>` 之类的类型才安全。

### 陷阱三：类型收窄在闭包 / 回调中可能失效

TypeScript 的收窄是**控制流分析**的结果——它沿着代码路径推导。**一旦跨进函数边界（闭包、回调），编译器必须假设这个变量在回调执行时可能已经被改掉了**。

```ts
function f(cond: boolean): void {
  let x: string | undefined;

  if (cond) {
    x = "hello";      // ⚠️ 只在条件成立时赋值
  }

  setTimeout(() => {
    console.log(x.length);   // ⚠️ 报错：x 可能是 undefined
  }, 1000);
}
```

**为什么**：编译器看到 `x` 有一条"从未被赋值"的路径，所以不敢假设回调执行时它一定是字符串。

⚠️ **注意 TS 5.4 起的一个改进**：如果变量在**最后一次赋值之后就不再被修改**，收窄可以保留到闭包里。所以下面这段**不报错**（实测 TS 5.8 / 7.0）：

```ts
function ok(): void {
  let x: string | undefined = "hello";   // 唯一的赋值，之后不再修改
  setTimeout(() => {
    console.log(x.length);   // ✅ TS 5.4+ 这里收窄被保留了
  }, 1000);
}
```

⭐ **所以真正的判断标准不是"用了闭包就一定失效"，而是"编译器能不能证明这个变量的值不会再变"**：

| 情况 | 收窄能否穿透闭包 |
|------|-----------------|
| 变量最后一次赋值后**不再被修改** | ✅ 能（TS 5.4+） |
| 变量**存在"可能没赋值"的路径** | ❌ 不能 |
| 变量**在回调内部还会被重新赋值** | ❌ 不能 |
| 用 `const` 做了快照 | ✅ 能（`const` 天然不可变） |

**三种解法**（无论 TS 版本，**用 `const` 快照都是最稳的写法**）：

**解法一：用 `const` 捕获**（`const` 的类型不可变，收窄能穿透闭包）：

```ts
function f(): void {
  let x: string | undefined = "hello";
  if (x) {
    const safe = x;          // const 快照，类型是 string
    setTimeout(() => {
      console.log(safe.length);   // ✅ 收窄被保留
    }, 1000);
  }
}
```

**解法二：用 `const` + 非空断言 `!`**：

```ts
function f(): void {
  let x: string | undefined = "hello";
  const safe = x!;           // 非空断言：告诉编译器"我确定不是 null/undefined"
  setTimeout(() => {
    console.log(safe.length);   // ✅
  }, 1000);
}
```

**解法三：把值作为参数传给回调**（最干净）：

```ts
function f(): void {
  let x: string | undefined = "hello";
  setTimeout((value: string | undefined) => {
    console.log(value?.length);   // ✅ 显式标注，行为完全确定
  }, 1000, x);
}
```

> **版本说明**：TypeScript 5.4 引入了"**闭包中的保留收窄**"（Preserved Narrowing in Closures Following Last Assignments）——如果变量在最后一次赋值之后不再被修改，收窄可以保留到闭包里。但只要存在"可能被改"的路径，收窄依旧会失效。这个改进不改变本节的核心结论：**跨函数边界的收窄不可靠**。

## 八、收窄与类型守卫的关系总结

| 手段 | 收窄方向 | 强度 |
|------|---------|------|
| `typeof` / `instanceof` / `in` | 宽 → 窄 | 内置、可靠 |
| 真值检查 | 宽 → 窄 | 可靠，但会排除 `0`/`""`/`false` |
| 类型守卫 `x is T` | 宽 → 窄（你定义规则） | 规则正确性靠你自己保证 |
| 断言函数 `asserts x is T` | 宽 → 窄（调用点之后） | 失败时抛错，类型一定正确 |
| `never` 穷尽检查 | 证明"没剩别的" | 编译期强制 |
| `?.` / `??` | **不收窄** | 只是运行时不抛异常 |

⭐ **一条实践建议**：

> **外部数据（接口返回、用户输入、`JSON.parse`）一律按 `unknown` 接住，然后用类型守卫或断言函数处理。**
> **内部数据（你确信来源和形状的）用联合类型 + `switch` + 判别器 + `never` 穷尽检查。**

## 陷阱

1. **⚠️ 忘了 `typeof null === "object"`**——这是 JS 的历史 bug，永远不会修；`typeof x === "object"` **不能**排除 `null`，必须额外写 `x !== null`；
2. **⚠️ 以为 `Array.isArray` 能把 `unknown` 收窄成安全类型**——它收窄到的是 `any[]`，元素类型是 `any`，等于放弃检查；自己写 `x is string[]` 这类守卫才安全；
3. **⚠️ 在闭包 / 回调里指望收窄还生效**——收窄**不保证**穿透函数边界（TS 5.4+ 只在"变量最后一次赋值后不再被修改"时才保留）；稳妥写法是 `const` 快照、显式参数标注，或 `!` 断言；
4. **⚠️ 把类型守卫写成返回 `boolean`**——那就没有收窄能力；必须写 `x is T`；
5. **⚠️ 断言函数不抛异常**——`asserts x is T` 的实现必须可能抛错，否则收窄是假的；⚠️ **编译器不会检查这一点**（实测 TS 5.8 / 7.0 都不报错），写错了只能靠 code review 拦；
6. **⚠️ 把 `asserts` 用在箭头函数上却没写变量类型注解**——`const f = (x: unknown): asserts x is string => {...}` 会报错；要写成 `const f: (x: unknown) => asserts x is string = (x) => {...}`；
7. **⚠️ 以为 `?.` 会把类型变干净**——`x?.length` 的类型是 `number | undefined`，`x` 本身也不会被收窄；`?.` 只保证"不抛异常"；
8. **⚠️ 用 `||` 代替 `??` 处理默认值**——`0 || 1` 得到 `1`、`"" || "x"` 得到 `"x"`，把合法的 `0` 和空字符串吃掉了；
9. **⚠️ 混用 `??` 和 `||` / `&&` 不加括号**——会报语法错误（`??` 与 `||`/`&&` 不能直接混用）；
10. **⚠️ 以为 `void` 和 `never` 一样**——`void` 是"返回值无意义"，`never` 是"永远不会返回"；穷尽检查必须用 `never`；
11. **⚠️ 忘了 `switch` 会漏分支**——不加 `default` + `never` 断言，新增联合成员时编译器不会提醒你。

## 小结

- ⭐ **收窄**是编译器根据控制流分析推断出更精确的类型；它是**编译期**的，运行时什么都没变
- ⭐ **收窄触发点**：`typeof`、`instanceof`、`in`、真值检查、相等检查、显式标注、`switch`、类型守卫/断言函数
- ⭐ **用户自定义类型守卫**：`(x: unknown) => x is T`，返回 `boolean`；`x is T` 签名是收窄的关键；只能变窄不能放宽
- ⭐ **断言函数**：`(x: unknown) => asserts x is T`，返回 `void`，实现里**必须抛错**（编译器不检查，靠自觉），调用语句之后全程收窄；TS 3.7+；用箭头函数写时**必须给变量加显式类型注解**，否则调用点报 TS2775
- ⭐ **`never`**：底部类型；用于"永不返回的函数"和**穷尽检查**；`default` 分支里 `const _exhaustive: never = x`（或 `assertNever(x)`）能在新增联合成员时立刻报错
- `?.` 只防运行时崩溃，`??` 只对 `null`/`undefined` 生效；**两者都不是类型收窄**
- ⚠️ 三个陷阱：`typeof null === "object"`、`Array.isArray` 收窄成 `any[]`、收窄不保证穿透闭包
- ⭐ **实践原则**：外部数据按 `unknown` 接住 + 类型守卫处理；内部数据用判别联合 + `switch` + `never` 穷尽检查
