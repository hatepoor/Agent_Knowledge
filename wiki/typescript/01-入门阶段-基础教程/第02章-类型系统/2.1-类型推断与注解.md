## 一、类型推断与类型注解：编译器替你干活

### 什么是类型推断

**类型（type）** 是「一个值具有哪些属性、能做哪些操作」的完整描述。**类型推断（type inference）** 是指编译器**不写你写**，从代码本身反推出这个值是什么类型：

```ts
let age = 18;             // age: number
const name = "张三";        // name: string（不是 "张三"！这是「拓宽」，见第三节）
const items = [1, 2, 3];   // items: number[]
```

### 什么是类型注解

**类型注解（type annotation）** 是你**手动写出来**的类型，语法是在变量名后加冒号：

```ts
let age: number = 18;
let name: string;
let items: number[] = [1, 2, 3];
```

注解是**编译期**的：它指导 `tsc` 做检查，编译成 JavaScript 时会被**完全擦除**（删掉）。所以类型注解**没有运行时开销**。

### 与 Python 的差异（重要）

| 维度 | TypeScript | Python |
|------|-----------|--------|
| 注解是否影响运行 | ❌ 完全被擦除 | ✅ `x: int = 1` 在运行期仍存在于 `__annotations__` |
| 不写注解会怎样 | 编译器**自动推断** | 运行期不管，静态检查工具（mypy/pyright）默认**不检查** |
| 类型错误的暴露时机 | **编译时**（`tsc` / IDE 立刻红） | 运行期（`TypeError` 才炸） |

⭐ **最关键的一条差异**：Python 里"没写类型 = 没人管"，TypeScript 里"没写类型 = 编译器替你猜"。所以 TS 的类型错误往往在你写完之前就报出来了。

### ⭐ 判断标准：什么时候写注解，什么时候让推断

这是本篇最实用的一条规则：

| 场景 | 做法 | 理由 |
|------|------|------|
| **导出的 API**（`export` 的函数、变量、类、接口的公共成员） | ✅ **显式写注解** | 导出类型会被写进 `.d.ts` 声明文件（见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/3-构建工具与包管理]]），一旦发布就是对外契约，不能靠"改一行代码就悄悄变了" |
| **函数内部的局部变量** | ✅ **让编译器推断** | 写多了是噪音；推断出的类型跟着值走，改代码时不用两头改 |
| **中间变量**（循环里、临时计算结果） | ✅ 让推断 | 同上 |
| **空数组 `const a = []`** | ⚠️ **必须写注解** | 推断不出元素类型，会退化成 `any[]`（这正是后面要讲的"污染"） |
| **递归函数的返回值** | ⚠️ 必须写注解 | 否则报错 TS7023/TS7024（"隐式 any，因为返回类型引用了自己"） |
| **函数的参数** | ✅ **必须写注解** | 参数没有初始值可推断；不写就是 `any`（`noImplicitAny` 下直接报错） |

⭐ **一句话规则**：**「对外的边界写注解，对内的过程让推断。」**

```ts
// ✅ 对外边界：注解
export function add(a: number, b: number): number {
  // ✅ 对内过程：推断
  const sum = a + b;
  return sum;
}

// ✅ 对外边界：注解
export const config: { retries: number } = { retries: 3 };

// ⚠️ 对内也写了注解——不必要，但也不算错
export function add2(a: number, b: number): number {
  const sum: number = a + b;   // 能用，但多此一举
  return sum;
}
```

## 二、上下文类型：编译器"引导"你的写法

### 什么是上下文类型

**上下文类型（contextual typing）** 是指：当一个表达式出现在**已经有类型的位置**上时，编译器用那个"目标类型"反过来指导这个表达式该怎么被推断。

最典型的场景是**函数参数**：

```ts
function handle(data: string[]) {
  // 在这个函数体内，data 的类型来自参数注解
}
```

但真正强大的是下面三种：

### 1. 数组字面量：元素类型由目标类型决定

```ts
// 推断：items 是 number[]
const items = [1, 2, 3];

// 上下文类型：目标类型是 string[]，所以元素被"引导"成 string
const names: string[] = ["a", "b"];
```

⚠️ 注意 `const names = ["a", "b"]` 的类型是 `string[]`，**不是** `("a" | "b")[]`。因为数组字面量在**可变**位置会「拓宽」（widening）成基础类型。唯一的例外是 `const` 声明的**字面量本身**：`const s = "a"` 类型是 `"a"`（因为 `const` 变量不可重新赋值，可以安全地保留更精确的类型）。

### 2. 回调参数：参数类型由回调签名决定

```ts
// map 的第二个参数是回调，回调里的 item 被"引导"成 number
const doubled = [1, 2, 3].map(item => item * 2);
//         ↑ 不需要写 (item: number)，上下文类型已经告诉编译器了
```

这也是为什么下面这行**不报错**：

```ts
const doubled = [1, 2, 3].map(item => item * 2);
```

而下面这行**报错**（`item` 是 `string | number`，不能做乘法）：

```ts
const mixed = [1, "a"];
const bad = mixed.map(item => item * 2);   // ⚠️ 运算符 "*" 不能用于 "string | number"
```

### 3. 对象字面量：属性类型由目标类型决定

```ts
interface User {
  name: string;
  age: number;
}

const user: User = {
  name: "张三",   // ✅ 上下文类型：string
  age: 18,        // ✅ 上下文类型：number
};
```

⚠️ 目标类型是接口时，对象字面量会触发**多余属性检查（excess property check）**：写了接口里没有的属性会直接报错。

```ts
interface User {
  name: string;
  age: number;
}

const user: User = {
  name: "张三",
  age: 18,
  nickname: "小张",   // ⚠️ 报错：对象字面量的未知属性 "nickname"
};
```

> **为什么会有多余属性检查**：对象字面量通常是一次性创建的，编译器额外严格一点可以拦住"打错字"这类错误。如果是先赋值给变量再传进去，就不检查了——这个放宽的行为是 TS 的历史遗留（结构化类型，见 [[typescript/01-入门阶段-基础教程/第01章-核心语法/1.4-类与接口]]）。

### ⭐ 上下文类型能救你，也能坑你

**救你**：

```ts
// 空数组有上下文类型，就不需要自己写
const nums: number[] = [];
```

**坑你**——当上下文类型是 `any` 时，上下文类型本身就会把表达式拉成 `any`：

```ts
declare const anything: any;
const arr = [anything];   // arr: any[] —— ⚠️ 上下文类型是 any，一切白搭
```

## 三、⭐ `any` 的危害：它会污染整条推断链

### `any` 是什么

**`any`** 是 TypeScript 里的"逃生舱"类型（escape hatch）。它表示：**这个类型放弃检查，随便什么都能放进去，随便什么都能取出来**。

```ts
let a: any = 42;
a = "hello";      // ✅ 允许
a.foo.bar.baz;    // ✅ 也允许 —— 完全不检查
```

### ⭐ 污染效应：一个 `any` 让下游全部退化

这是 `any` 最反直觉的地方：**`any` 不是"一个宽松的类型"，它是一种"传染性"的类型**。

```ts
declare const raw: any;      // 假设这里混进了一个 any

const step1 = raw.data;         // step1: any
const step2 = step1.title;      // step2: any —— ⚠️ 已经不是 string 了
const step3 = step2.length;     // step3: any
const step4 = step3 + 1;        // step4: any —— ⚠️ 字符串加数字也不再报错
```

⭐ **为什么**？因为在 TypeScript 的类型系统里，从 `any` 上取属性、调用方法、做运算，**结果一律是 `any`**。它会像链式反应一样顺着数据流一路传下去，直到你显式把它切断。

### 污染的常见源头

| 源头 | 说明 |
|------|------|
| `JSON.parse()` 的返回值 | 固定是 `any`（TS 不知道 JSON 里有什么） |
| 未标注的参数 | `noImplicitAny` 下会报错；关掉就是 `any` |
| 第三方库没有类型声明 | 隐式 `any`（见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/3-构建工具与包管理]]） |
| 显式写 `const x: any = ...` | 自己挖的坑 |

### ⭐ 切断污染的两种手段

**手段一：在边界处立刻收窄**（用类型守卫，详见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.4-类型收窄与类型守卫]]）：

```ts
declare const raw: any;

const parsed = JSON.parse(raw) as unknown;   // ✅ 先转成 unknown，阻断污染
// 然后用类型守卫逐个校验（见 2.4）
```

**手段二：把 `any` 换成 `unknown`**（下一节详述）。

### 与 Python 的差异

Python 里没有 `any` 这个概念。最接近的是 `typing.Any`：

```python
from typing import Any
def f(x: Any) -> Any:
    return x["whatever"]   # mypy 也不检查
```

⚠️ 但 Python 的 `Any` **不会像 TS 的 `any` 那样"污染"推断**——因为 Python 没有"从变量反推类型"这件事，每个变量都是自己声明的。TS 的 `any` 之所以危险，正是因为它**参与推断**。

## 四、⭐ `unknown` vs `any`：未知但安全

### 一句话区别

| | `any` | `unknown` |
|---|-------|-----------|
| 含义 | 「**放弃检查**，我什么都能干」 | 「「**还不知道**是什么，但你不许乱用」 |
| 可以赋值给它吗 | ✅ 任何值都行 | ✅ 任何值都行 |
| 它能赋值给别的吗 | ✅ 能赋给任何类型 | ❌ **只能赋给 `unknown` 或 `any`** |
| 能直接调方法/取属性吗 | ✅ 能 | ❌ **不能**，必须先收窄 |
| 会污染下游吗 | ✅ 会 | ❌ **不会**（收窄后下游拿到的是真实类型） |

### `unknown` 为什么"必须先收窄才能用"

因为 `unknown` 的含义是"类型信息尚未确定"。在你证明它是什么之前，编译器**拒绝**你把它当成 `string` 用：

```ts
declare const u: unknown;

console.log(u.length);      // ⚠️ 报错：Object is of type 'unknown'
const s: string = u;       // ⚠️ 报错：Type 'unknown' is not assignable to type 'string'
```

**收窄（narrowing）** 就是把 `unknown` 变成确定类型的手段。最常见的是 `typeof`：

```ts
declare const u: unknown;

if (typeof u === "string") {
  console.log(u.length);    // ✅ 在这个 if 块内，u 被收窄成 string
}
```

完整收窄机制见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.4-类型收窄与类型守卫]]。

### ⭐ `unknown` 的典型用法

**1. 处理外部输入的函数**——这是 `unknown` 最大的价值：

```ts
function parse(input: string): unknown {
  return JSON.parse(input);   // JSON.parse 返回 any，用 unknown 接住，切断污染
}

// 调用方必须自己收窄：
const result = parse('{"a":1}');
if (typeof result === "object" && result !== null) {
  // result 现在是 object
}
```

**2. 捕获异常**——`catch` 里的错误值类型默认是 `unknown`（`useUnknownInCatchVariables`，`strict` 家族的一员）：

```ts
declare function risky(): void;

try {
  risky();
} catch (err) {
  // err: unknown
  if (err instanceof Error) {
    console.log(err.message);   // ✅ 收窄后才安全
  }
}
```

**3. 泛型兜底**——当一个泛型参数约束不住时，用 `<T = unknown>`（详见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.3-泛型与类型约束]]）。

### ⭐ 一条实用的团队约定

> **「用 `unknown` 代替 `any`，除非你确信要放弃检查。」**

`any` 是"我不管了"，`unknown` 是"我先记着，等会儿确认"。前者会静默地让错误一路溜到最后才炸，后者会在你用错的地方立刻报错。

## 五、⭐ 类型断言 `as`：对编译器的承诺，不是运行时转换

### 什么是类型断言

**类型断言（type assertion）** 语法是 `值 as 目标类型`。它告诉编译器：**「我知道我在干什么，你别检查了。」**

```ts
declare const el: Element;
const input = el as HTMLInputElement;   // 我确信它是 input
input.value = "hello";                  // ✅ Element 没有 value，才需要断言
```

### ⚠️ 它不做任何运行时转换（最重要的一个认知）

**类型断言只在编译期存在。编译成 JavaScript 后，`as` 会被完全删除。**

```ts
const n = "42" as unknown as number;
console.log(n + 1);      // ⚠️ 运行时输出 "421"，不是 43！
```

因为运行时那个值**仍然是字符串**。断言只是让编译器"以为"它是数字。

### ⚠️ 写错了编译器不报错，运行时炸

这是 `as` 最危险的地方。**断言写错时，编译器通常不报错**（只在你断言的类型与原类型**完全无交集**时才报 TS2352），但运行时该炸还是炸：

```ts
declare const el: Element;
const input = el as HTMLInputElement;   // 编译通过

// 但如果 el 其实不是 input：
input.value = "hello";                  // ⚠️ 运行时 TypeError: Cannot set property 'value' of undefined
```

⭐ **判断标准**：`as` 只应在「**你比编译器更了解情况**」时使用。如果情况不清楚，说明你需要的是**收窄**（`typeof` / 类型守卫），不是断言。

### 什么时候用 `as` 是合理的

1. **从 DOM 查询拿元素**——`document.querySelector("input")` 返回 `Element | null`，你确信它存在；
2. **调用第三方库返回了宽泛类型**，你要收窄成具体类型；
3. **类型体操**——把 `unknown` 转成具体类型（`x as Foo`），但这**只是把检查责任转回给你自己**。

### ⭐ `as const`：让字面量不被拓宽

**`as const`** 是一个特殊的断言，把字面量**"冻结"成精确的类型**，同时加上 `readonly`（只读）修饰。

```ts
const s = "hello";                 // s: string
const s2 = "hello" as const;       // s2: "hello"  ← 保留字面量类型

const arr = [1, 2, 3];             // arr: number[]
const arr2 = [1, 2, 3] as const;   // arr2: readonly [1, 2, 3]  ← 元组 + 只读
```

对对象字面量同样有效：

```ts
const config = {
  mode: "dark",
  retries: 3,
} as const;
// 类型：{ readonly mode: "dark"; readonly retries: 3 }
```

⭐ **它解决的是什么问题**：普通推断会把 `"dark"` 拓宽成 `string`，把 `{mode, retries}` 拓宽成 `{mode: string; retries: number}`。当你需要**精确的字面量信息**（比如给 `satisfies` 用、或者当配置表的键）时，`as const` 是必需的。

## 六、⭐ `satisfies` 运算符（TypeScript 4.9+）

### 它解决什么问题

`as const` 保留了精确类型，但**没有校验**；`as` 做了校验（部分），但**拓宽了类型**。`satisfies` 两样都要。

**`satisfies` 的语义**：「**用右边这个类型检查我，但我自己的类型不被右边改变。**」

```ts
type Config = {
  name: string;
  retries: number;
};

const config = {
  name: "app",
  retries: 3,
  extra: true,        // ⚠️ 报错：对象字面量的未知属性 "extra"
} satisfies Config;
```

### ⭐ `as` vs `satisfies`：核心区别

用同一段代码对比：

```ts
type Config = {
  name: string;
  retries: number;
};

const source = {
  name: "app",
  retries: 3,
  extra: true,     // 多余属性
};

// 用 as 断言：断言「信不信由我」，类型被拓宽成 Config
const a = source as Config;
a.name;          // 类型：string
// ⚠️ 多余属性 extra 不会被报出来（as 只要求"两个类型有重叠"）
```

```ts
type Config = {
  name: string;
  retries: number;
};

// 用 satisfies：校验但不拓宽
const b = {
  name: "app",
  retries: 3,
  extra: true,     // ⚠️ 报错！多余的属性被发现了
} satisfies Config;

b.name;          // 类型：string（不是字面量 "app"，见下方说明）
```

| 对比项 | `as Config` | `satisfies Config` |
|--------|-------------|-------------------|
| 是否校验类型 | ⚠️ 弱校验（只检查"有重叠"） | ✅ **严格校验** |
| 是否检查多余属性 | ❌ 不检查 | ✅ **检查** |
| 结果变量的类型 | 被拓宽成 `Config` | **保持对象自身的推断类型**（键名、数量都不丢） |
| 拼错属性名 | ❌ 不报错 | ✅ **报错** |

⚠️ **一个必须说清的细节**：`satisfies` 保住的是**"对象的形状"**（有哪些键、键是什么），但**不改变"值的字面量类型"**：

```ts
type Config = { name: string; retries: number };

const b = { name: "app", retries: 3 } satisfies Config;
const n: "app" = b.name;   // ⚠️ 报错：b.name 的类型是 string，不是 "app"
```

因为普通对象字面量的属性值会按常规规则**拓宽**成 `string`——这和 `satisfies` 无关，是"字面量拓宽"规则本身。要**同时**拿到"严格校验"和"字面量类型 + 只读"，得把两者叠加：

```ts
type Config = { name: string; retries: number };

const c = { name: "app", retries: 3 } as const satisfies Config;
const n2: "app" = c.name;   // ✅ OK：字面量类型被保留
c.name = "other";           // ⚠️ 报错：as const 加了 readonly
```

⭐ **`as const satisfies T` 是"校验 + 冻结"的组合拳**，两者各管一件事，缺一不可。

### ⭐ 什么时候用 `satisfies` 而不是 `as`

⭐ **核心场景：你想同时做到"检查合法性"和"保留精确类型"。**

**场景一：配置表 / 主题表**——要保证每项都符合规范，同时还要保留每个项的**具体键名**：

```ts
type Theme = {
  name: string;
  colors: { bg: string; fg: string };
};

// 用 as：类型被拓宽成 Record<string, Theme>，丢失了 "light"/"dark" 这些具体键
const themes = {
  light: { name: "Light", colors: { bg: "#fff", fg: "#000" } },
  dark:  { name: "Dark",  colors: { bg: "#000", fg: "#fff" } },
} as Record<string, Theme>;
```

```ts
type Theme = {
  name: string;
  colors: { bg: string; fg: string };
};

// ⭐ 用 satisfies：校验通过，且保留了具体键
const themes = {
  light: { name: "Light", colors: { bg: "#fff", fg: "#000" } },
  dark:  { name: "Dark",  colors: { bg: "#000", fg: "#fff" } },
} satisfies Record<string, Theme>;

themes.light.colors.bg;   // ✅ 类型是 string（属性存在，能访问）
themes.dusk;               // ⚠️ 报错：拼写错误，键不存在
```

⭐ **注意 `as` 版本丢掉了什么**：`as Record<string, Theme>` 把类型拓宽成 `Record<string, Theme>`，于是 `themes` 变成"**任意字符串键**都合法"——`themes.dusk` 在 `as` 版本里**不报错**，因为 `Record<string, T>` 本来就允许任意键。而 `satisfies` 版本保留了 `"light" | "dark"` 这两个具体键，拼错立刻被拦下。

**场景二：路由表 / 事件映射**——保证每条记录形状正确，同时让 `keyof` 能推出精确的键集合：

```ts
type Handler = (payload: unknown) => void;

const handlers = {
  onClick: () => console.log("click"),
  onHover: () => console.log("hover"),
} satisfies Record<string, Handler>;

// keyof typeof handlers 得到 "onClick" | "onHover"（精确的两个键）
type HandlerName = keyof typeof handlers;
```

**场景三：既要字面量类型又要只读**——`as const` 和 `satisfies` 叠加使用：

```ts
const routes = {
  home: { path: "/", auth: false },
  admin: { path: "/admin", auth: true },
} as const satisfies Record<string, { path: string; auth: boolean }>;
// 结果：通过校验 + 精确字面量类型（path 是 "/admin" 而不是 string）+ readonly
```

> **版本说明**：`satisfies` 是 **TypeScript 4.9** 引入的运算符。当前维护线是 5.x，最新是 6.x/7.x，都支持。

## 七、声明合并

### 什么是声明合并

**声明合并（declaration merging）** 是指 TypeScript 会把**同名的多个声明**合并成一个。它最常用于**给已有类型"打补丁"**——扩展别人写的类型而不修改原文件。

### 三种常见形式

**1. 两个 `interface` 合并**（最常用）：

```ts
// 你的文件
interface AppConfig {
  myCustomProp: string;
}

// 另一个文件（比如某个第三方库的类型声明）
interface AppConfig {
  version: number;
}

// 合并后 AppConfig 同时拥有 myCustomProp 和 version
const cfg: AppConfig = { myCustomProp: "x", version: 1 };
```

**2. `interface` 与 `class` 合并**：

```ts
class Foo {
  bar = 1;
}

interface Foo {
  baz: string;    // 合并进 class Foo
}
```

**3. `namespace` 与其他声明合并**——常用于给函数加命名空间：

```ts
function build() { /* ... */ }

namespace build {
  export const version = "1.0";
}
```

### ⚠️ 声明合并的限制

| 限制 | 说明 |
|------|------|
| ❌ 同一个 `type` 别名不能合并 | `type A = {...}` 写两遍会报「重复标识符」——`type` 是**覆盖式**的，`interface` 是**合并式**的 |
| ❌ 合并的成员不能类型冲突 | 两个 `interface` 都声明 `id: string` 和 `id: number` → 报错 |
| ❌ 不适用于泛型参数 | `interface A<T>` 和 `interface A<U>` 合并会报错 |

⭐ **记住这一条就够了**：`interface` 可以合并，`type` 不行。要"打补丁"就用 `interface`。

---

## 八、`readonly` 数组

**`readonly`（只读）** 是 TypeScript 的编译期修饰符，标记属性或数组**不能被重新赋值**。

```ts
const nums: readonly number[] = [1, 2, 3];

nums[0] = 99;      // ⚠️ 报错：不能赋值给 "0"，因为它是只读的
nums.push(4);      // ⚠️ 报错：Property 'push' does not exist on type 'readonly number[]'
```

### 三种写法

| 写法 | 类型 | 说明 |
|------|------|------|
| `readonly number[]` | `readonly number[]` | ⭐ **推荐**，读起来像普通数组 |
| `ReadonlyArray<number>` | `readonly number[]` | 同样的类型，泛型风格写法 |
| `[1, 2, 3] as const` | `readonly [1, 2, 3]` | **元组**：长度和每个位置的类型都固定 |

### 元组 vs 数组

**元组（tuple）** 是长度固定、每个位置类型可以不同的数组：

```ts
const pair: [string, number] = ["age", 18];
pair[0];      // string
pair[1];      // number
pair[0] = "x"; // ✅ 可以
```

```ts
const fixed = ["a", 1] as const;
// 类型：readonly ["a", 1]
fixed[0].toUpperCase();   // ✅ 类型是 "a"，是 string
fixed[1].toFixed();       // ✅ 类型是 1，是 number
```

### `readonly` 是编译期的

⚠️ **`readonly` 挡不住运行时修改**。它只是不让编译器报错：

```ts
const nums: readonly number[] = [1, 2, 3];
nums.push(4);   // ⚠️ 编译报错
```

如果用 `as any` 绕过检查，运行时该改还是能改。它的作用是**表达意图**（"这个数组我打算当只读用"）+ **让编译器帮你守住**。

## 九、⚠️ `null` 与 `undefined` 在 strict 下的影响

### 两种模式

| 模式 | `null` / `undefined` 的待遇 |
|------|-----------------------------|
| `strictNullChecks: false`（旧默认） | `null` 和 `undefined` 可以赋给任何类型；`string` 这种类型**自动包含** `null` 和 `undefined` |
| `strictNullChecks: true`（**`strict` 家族成员，现在推荐默认开**） | `null` 和 `undefined` **只能**赋给 `null` / `undefined` / `unknown` / 包含它们的联合类型 |

```ts
// ⚠️ 在 strictNullChecks: true（现在的默认）下会报错：
//    Type 'null' is not assignable to type 'string'
// 只有在 strictNullChecks: false（旧模式）下才允许
let name: string = null;
```

⭐ **这张表是理解 strict 的关键**：旧模式下 `string` 实际上等于 `string | null | undefined`——所以你写 `string` 时，编译器**根本不会提醒你**这个值可能是 `null`。开了 `strictNullChecks` 之后，`string` 就真的是 `string`，`null` 必须显式写进联合类型里。**这正是 strict 提升安全性的核心机制。**

### strict 下 `null` / `undefined` 怎么影响推断

这是本节的核心。当 `strictNullChecks` 开启时：

```ts
let maybe = null;        // 推断：null
let maybe2 = undefined;  // 推断：undefined

// ⚠️ 报错：Type 'null' is not assignable to type 'string'
let name: string = null;

// ✅ 正确写法：显式写出"可能是 null"
let name2: string | null = null;
```

⭐ **`let x = null` 的"演化类型"（evolving type）**：不写注解时，TypeScript 会在**函数体内**根据后续赋值不断调整 `x` 的类型——这叫演化。写注解则等于把这个类型**钉死**：

```ts
function demo() {
  let x = null;          // 起始为 null
  x = "hello";           // ✅ 类型演化为 string
  x.length;              // ✅ 不报错（此时 x 就是 string）
  x = 42;                // ✅ 还能再演化成 number
}
```

```ts
function demo2() {
  let x: string | null = null;   // ⚠️ 显式注解 = 类型被钉死
  x = "hello";           // ✅ 合法
  x = 42;                // ⚠️ 报错：Type 'number' is not assignable to type 'string'
}
```

⭐ **两者真正的区别在"能赋什么值"，而不是"能不能收窄"**：

| | 无注解（演化） | 有注解（钉死） |
|---|---|---|
| `x = null` 后 `x = 42` | ✅ 允许，类型演化为 `number` | ⚠️ 报错（除非注解里含 `number`） |
| 赋完值后访问属性 | ✅ 已收窄，能访问 | ✅ **同样**已收窄（控制流分析对两者一视同仁） |
| 赋的值**之前**就用 | ⚠️ 报"可能为 null" | ⚠️ **同样**报"可能为 null" |

⭐ **一句话**：**注解的作用是"限定这个变量能装什么"，不是"禁止收窄"。** 两者在收窄上的表现完全一样；区别只在于**赋值兼容性**——注解是一道护栏，演化则随你写随你变。

> 💡 **实践建议**：业务代码里给"可能为 null"的变量**显式写 `string | null` 这样的注解**。因为演化类型在**函数体内**才生效，一旦你把这个变量传出去（返回值、对象属性、闭包），编译器拿到的就是你**最初声明时**的类型——演化只影响局部控制流，不影响对外暴露的类型。

### `strict` 家族与本篇的关系

`strict: true` 会**一次性打开**一组检查项，其中和本篇直接相关的两个：

| 选项 | 作用 |
|------|------|
| `strictNullChecks` | 让 `null`/`undefined` 严格参与类型计算（上面这一节） |
| `noImplicitAny` | 禁止隐式 `any`（参数不写类型、数组推断不出元素类型时报错） |

⭐ **`noImplicitAny` 是阻止 `any` 污染的第一道闸门**。它会在源头把"忘了写注解"变成编译错误，而不是让它悄悄变成 `any`。

> **版本说明**：TypeScript 6.0 起 `strict` 默认为 `true`（见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/1-编译流程与tsconfig]]）。这也意味着**你现在新写的项目默认就是 strict 模式**——本篇提到的 `null`/`undefined` 行为就是默认行为。

## 陷阱

1. **⚠️ 以为 `as` 会做运行时转换**——`as` 只在编译期存在，编译后被删除；`"42" as unknown as number` 在运行时依然是字符串，`n + 1` 得到 `"421"`；
2. **⚠️ 用 `as` 掩盖真实的类型不匹配**——断言写错时编译器**通常不报错**（只在你断言的类型与原类型完全无交集时才报 TS2352），但运行时照样炸；用 `as` 前先问自己「我比编译器更了解情况吗」；
3. **⚠️ 以为 `as` 和 `satisfies` 可以互换**——`as` **拓宽**类型且弱校验，`satisfies` **保留对象自身的形状**且严格校验；配置表、路由表这类场景优先用 `satisfies`；
4. **⚠️ 用 `any` 接住 `JSON.parse` 的结果**——`any` 会顺着数据流污染整条链，下游全部失去类型检查；改用 `unknown` 接住，再收窄；
5. **⚠️ 把 `unknown` 当 `any` 用**——`unknown` **必须先收窄**（`typeof`、`instanceof`、类型守卫）才能取属性、才能赋值给具体类型；直接 `u.length` 会报错；
6. **⚠️ 以为 `unknown` 太麻烦不如用 `any`**——`unknown` 报的错都是**真问题**，`any` 藏起来的是**真 bug**；只有"确定要放弃检查"（比如对接未知的第三方数据）才用 `any`；
7. **⚠️ 忘了 `const` 变量的字面量类型和 `let` 不同**——`const s = "a"` 是 `"a"`，`let s = "a"` 是 `string`；要精确类型请显式 `as const`；
8. **⚠️ 用 `as const` 代替 `satisfies` 去做校验**——`as const` **不检查任何东西**，它只是"冻结"类型；它俩经常搭配使用（`as const satisfies T`），但作用完全不同；
9. **⚠️ 用 `type` 做类型补丁**——`type` 是**覆盖式**的，重复声明会报「重复标识符」；要合并就用 `interface`；
10. **⚠️ 以为 `readonly` 能防住运行时修改**——`readonly` 是编译期的，用 `as any` 就能绕过；它的价值是表达意图 + 让编译器帮你守住，不是运行时保护；
11. **⚠️ 在 strict 项目里写 `let x = null` 然后指望它保持宽松**——显式注解（如 `let x: string | null = null`）会把类型钉死，后续必须处理 `null`；这正是 strict 的价值，不是麻烦。

## 小结

- ⭐ **判断标准**：**对外的边界（导出的 API、函数参数）写注解；对内的过程（局部变量、中间结果）让推断**
- **上下文类型**：目标类型反过来"引导"表达式——数组字面量、回调参数、对象字面量都受它影响；目标类型是 `any` 时，上下文类型反而会加剧污染
- ⭐ **`any` 会污染整条推断链**：从 `any` 上取属性、调用、做运算，结果一律是 `any`；`JSON.parse`、未标注参数、缺类型的第三方库是三大源头
- ⭐ **`unknown` vs `any`**：`unknown` = "还不知道，但你别乱用"，**必须先收窄**；`any` = "放弃检查"。团队约定：默认用 `unknown`
- ⭐ **`as` 是对编译器的承诺，不是运行时转换**：编译后被删除，写错编译能过、运行时炸；只在"你比编译器更了解情况"时用
- ⭐ **`satisfies`（TS 4.9+）= 校验但不拓宽**：既检查多余属性与拼写错误，又保留对象自身的推断形状（具体键名不丢）；配置表 / 路由表 / 主题表的标准解法；⚠️ 注意它**不保留字面量类型**——要同时拿到字面量 + 只读，需叠加 `as const satisfies T`
- **声明合并**：`interface` 可合并、`type` 不可；合并的前提是成员不冲突
- **`readonly` 数组**：三种写法 `readonly T[]` / `ReadonlyArray<T>` / `[...] as const`；编译期保护，非运行时
- ⭐ **strict 下 `null`/`undefined` 严格参与类型计算**：`strictNullChecks` 让 `null` 不能赋给 `string`；`noImplicitAny` 是阻止 `any` 污染的第一道闸门。TS 6.0 起 `strict` 默认开启

1. 写一个函数 `sumAll(values: unknown[]): number`，用 `typeof` 逐个判断并只累加真正是 `number` 的元素（数字字符串如 `"42"` 不计入）。体会 `unknown` 与 `any` 的差别：如果参数写成 `any[]`，你的判断还能被编译器检查到吗？
2. 下面这段代码会报错吗？为什么？请逐行说明编译器看到了什么类型：
   ```ts
   const a = "hi";
   const b = "hi" as const;
   const c = { k: "hi" };
   const d = { k: "hi" } as const;
   ```
3. 用 `satisfies` 写一个 `routes` 配置表，要求：每项形如 `{ path: string; auth: boolean }`，且必须包含 `home` 和 `admin` 两项；写完后用 `keyof typeof routes` 推出合法的路由名联合类型。
4. 故意写一个**错误的** `as` 断言（例如把 `string` 断言成 `number` 然后做算术），观察编译器**是否报错**、运行时**是否出错**，把这个现象和 `satisfies` 的行为对比记录下来。
