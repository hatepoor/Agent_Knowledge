# 泛型与类型体操

> **什么时候该读**：面试官问「泛型解决了什么问题」「条件类型怎么写」「infer 是什么」「映射类型和映射出来的对象什么关系」「什么是协变逆变」，答不上来就只能被归到「会写业务但不懂原理」那一档。
> **答题主线**：**泛型是"把类型当参数传"的编程手段，而类型体操是"用类型算类型"的编程语言**。二者是同一件事的两面——所有类型体操的原料都是泛型参数、条件类型、`infer` 和映射类型；理解的终点是知道**什么时候该停手**。

---

## Q1. 泛型解决什么问题？和 `any`、联合类型、函数重载相比强在哪？

**答：**

**泛型解决的是「我要写一份能处理多种类型、但每种类型下都保留精确类型信息」的代码。`any` 是放弃信息换通用，泛型是保留信息换通用。**

对比同一个需求——写一个返回属性值的工具函数：

```ts
// 1. any：通用，但信息全丢
function getAny(obj: any, key: string): any {
  return obj[key];
}
const v = getAny({ id: 1 }, 'id');   // v: any —— 后面写什么都行，也什么都不对

// 2. 联合类型：通用，但只能取公共属性
function getUnion(obj: { id: number } | { name: string }, key: 'id' | 'name') {
  return obj[key];   // 返回 number | string，且 key 和 obj 的对应关系丢了
}

// 3. 泛型：通用，且保留精确信息
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const v3 = get({ id: 1, name: 'a' }, 'id');   // v3: number ✅
```

**泛型 vs 重载**：

| 手段 | 缺点 |
|------|------|
| **重载** | 签名数量随类型增长，写到第 5 个就开始崩溃；实现体里还要处理"所有重载都不匹配"的情况 |
| **联合类型** | 丢失了"参数与结果之间的对应关系" |
| **`any`** | 完全丢失类型检查，且会传染 |
| **泛型** | 一次定义，任意类型，且**参数与结果保持对应** |

**泛型的本质是"在类型层面编程"**：TS 的类型系统本身是一门可计算的编程语言（可以理解为"类型层面的函数式语言"），泛型是给它的变量。

**关键收益**：`T[K]` 这类"**索引访问类型**"让类型可以**依赖另一个类型的形状**，这是 `any` 和联合类型都做不到的。

**实战中最常见的三个泛型场景**：

1. **工具函数**（`get`、`pick`、`map`）
2. **容器类**（`class Cache<T>`、`class Result<T, E>`）
3. **API 契约**（后端返回 `Result<UserDto>`，前端消费时自动拿到 `UserDto` 而不是 `unknown`）

**追问：泛型和 `unknown` 怎么选？**
→ 看**信息流方向**。数据从外部进来（不可信）用 `unknown`——先收窄再用；数据在你自己系统内部流转（类型已知）用泛型——精确传递。`unknown` 是"待解析"，泛型是"已声明的参数化契约"。

**追问：泛型在运行时真的存在吗？**
→ **不存在**。TS 泛型是**完全擦除**的——转译后 `function identity<T>(x: T): T { return x }` 变成 `function identity(x) { return x }`，`T` 一个字节都不剩。运行时如果写 `x instanceof List<string>` 会直接报错，因为 TS 不支持带类型参数的 `instanceof`。**Java 的泛型也是运行时擦除**（编译成 `Object` + 桥接方法 + 强制转换），所以两边行为一致。

## Q2. 泛型约束 `extends` 怎么用？只有 `extends` 一种约束形式吗？

**答：**

**`extends` 是泛型的约束关键字（constraint）。TS 只有这一种约束形式，但约束的对象可以是任意类型表达式——不限于类。**

```ts
// 基本形式：约束泛型参数的类型上界
function first<T extends { length: number }>(arr: T[]): T | undefined {
  return arr[0];
}
```

**约束的四种常见写法**：

```ts
// 1. 约束为对象类型（结构约束）
function get<T extends object>(x: T): T { return x; }

// 2. 约束为联合字面量（约束"键的取值范围"）
type Direction = 'north' | 'south' | 'east' | 'west';
function move(dir: Direction) {}

// 3. keyof 约束（约束"键必须来自另一个类型"）—— 最常用
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] { return obj[key]; }

// 4. 约束为构造函数（保留 new 能力）
function make<T extends new (...args: any[]) => object>(C: T): InstanceType<T> {
  return new C();
}
```

**`extends` 在泛型位置和在条件类型位置是同一关键字、不同含义**：

| 位置 | 含义 |
|------|------|
| `<T extends X>` | **约束**：T 必须是 X 的子类型 |
| `T extends X ? A : B` | **条件**：T 是不是 X 的子类型，是则 A 否则 B |

它们语法长得像，但一个在 `<>` 里、一个在 `?` 左边，别搞混。

**⚠️ 关键限制：约束的是"上界"，不是"精确类型"**。

```ts
function f<T extends string>(x: T): T { return x; }
const r = f('hello');   // r 的类型是 string，不是 'hello'
```

`extends` 表达的是"至少是"，不是"正好是"。想拿到精确字面量类型，靠**推断**（`const` 参数 / `as const`）或**条件类型收窄**，不靠约束。

**追问：泛型可以有多个约束吗？**
→ 可以，`extends` 可以写多个，用 `&` 连接，但**第一个必须是结构类型**（TS 4.7+ 放宽了此限制）：
```ts
function f<T extends string & { __brand: 'x' }>(x: T) {}
```

**追问：`extends` 约束和 `implements` 有什么区别？**
→ `implements` 是**类**实现接口的运行时/编译期契约（类必须真的有那些成员）；`extends`（泛型位置）是**类型层面的上界声明**，只是告诉编译器"T 的用法可以假定 T 有这些成员"，**没有任何运行时契约**。泛型 `extends` 一个类，不要求你真的继承它。

## Q3. `keyof` 和 `typeof` 在类型位置怎么用？有哪些坑？

**答：**

**`keyof T` 取键的联合，`typeof x` 取值的类型。两者都能把「运行时的值」搬进「类型世界」。**

### `keyof`：取出键名

```ts
interface Person {
  name: string;
  age: number;
}

type Keys = keyof Person;   // 'name' | 'age'
```

**三个必须知道的坑**：

**坑 1：`keyof` 数组得到的是 `number | 几个特殊方法名`，不是 `string`。**

```ts
type A = keyof string[];   // number | "length" | "toString" | ... | "pop" | ...
type B = keyof string;     // number | "length" | "toString" | ... （字符串的所有方法名）
```

因为数组**既能按下标访问，也能调用数组方法**。所以 `keyof` 数组 ≠ `number`。

**坑 2：`keyof` 会包含索引签名。**

```ts
interface Dict { [k: string]: number }
type K = keyof Dict;       // string | number
```

**坑 3：`keyof` 不递归。** `keyof` 只取**第一层**的键，不会深挖嵌套对象。

### `typeof`：在类型位置取值的类型

```ts
const conf = { host: 'localhost', port: 8080, debug: true };
type Conf = typeof conf;   // { host: string; port: number; debug: boolean }
```

注意：**`typeof` 出现在类型位置时，取的是值的类型；出现在值位置时，取的是 JS 的 `typeof` 运算符**。同一个词两套含义，面试常问。

**`typeof` + `keyof` 组合是最常见的"从值推类型"套路**：

```ts
const actions = {
  add: (n: number) => n + 1,
  remove: (n: number) => n - 1,
};
type ActionName = keyof typeof actions;   // 'add' | 'remove'
type ActionFn = (typeof actions)[ActionName];  // (n: number) => number
```

**`typeof` 保留的字面量信息**：

```ts
const level = 'debug';           // 类型是 string（变量声明会拓宽）
const level2 = 'debug' as const; // 类型是 'debug'
type L = typeof level2;          // 'debug'
```

**⚠️ `typeof` 的重要限制**：它只能作用于**值**（变量、函数、类、属性访问），**不能作用于类型**。要取类型的属性类型，用**索引访问类型** `T[K]`。

**追问：`keyof` 和 `Pick`/`Omit` 什么关系？**
→ `Pick<T, K>` = `{ [P in K]: T[P] }`，本质是「用 `keyof` 选键 + 映射类型拷贝」。`Omit<T, K>` = `Pick<T, Exclude<keyof T, K>>`。**内置工具类型几乎全是「映射类型 + 条件类型 + 索引访问」的组合**——学会这四个，工具类型不用背。

**追问：怎么把对象的所有 key 变成联合类型给 `switch` 用？**
→ `keyof typeof obj`。这是最直接的答案，但注意 `keyof` 出来的联合是 `string` 的话（索引签名场景）就没法做穷尽检查——**这也是为什么推荐用 `as const` 或显式 `satisfies` 保留字面量键**。

## Q4. 什么是索引访问类型 `T[K]`？为什么它是泛型体系的核心？

**答：**

**`T[K]` 表示「取 T 上键为 K 的那个属性的类型」。它是泛型体系的核心——因为它让类型可以依赖另一个类型的形状。**

```ts
interface Person { name: string; age: number }

type NameType = Person['name'];              // string
type ValueType = Person[keyof Person];       // string | number
```

**为什么它是核心**：类型体操里的绝大多数高级类型，最终都归结为「索引访问 + 条件判断」。

```ts
// 泛型版：K 变化时，返回类型跟着变
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
pluck({ id: 1, name: 'a' }, 'id');   // number，精确
```

对比非泛型版：你必须为每种 key 写重载，或者退化成联合类型丢失对应关系。

**三个实战用法**：

**1. 提取函数返回值类型**（工具函数基础）：

```ts
type ReturnTypeOf<T> = T extends (...args: any[]) => infer R ? R : never;
```

**2. 提取数组元素类型**：

```ts
type ElementOf<T> = T extends (infer E)[] ? E : never;
type E = ElementOf<string[]>;   // string
```

**3. 提取对象某个深层路径的类型**：

```ts
type PathValue<T, P extends string> =
  P extends `${infer Head}.${infer Rest}`
    ? Head extends keyof T ? PathValue<T[Head], Rest> : never
    : P extends keyof T ? T[P] : never;

type V = PathValue<{ user: { profile: { name: string } } }, 'user.profile.name'>;
// string
```

**⚠️ 关键限制：索引访问要求 K 确实是 T 的键**。

```ts
type Bad = Person['nope'];    // ❌ 编译报错：Property 'nope' does not exist on type 'Person'
```

这正是泛型要写 `K extends keyof T` 的原因——**把"键必须存在"这条规则编码进约束里**，而不是等到使用点才报错。

**追问：`T[K]` 和 `T extends Record<K, infer V> ? V : never` 有什么区别？**
→ 后者多了一层条件判断，用于处理 `T` 可能不是对象的情况。实践中 `T[K]` 配合 `K extends keyof T` 更简洁；但在**通用工具类型**里，为了兼容任意输入（可能传进来非对象），用条件类型兜底更稳。

**追问：索引访问能取方法吗？**
→ 能，取到的是方法的完整函数类型。比如 `Person['name']` 取属性，`SomeInterface['method']` 取方法签名（包含参数和返回值的完整信息）。这也是 `Parameters<T>` / `ReturnType<T>` 的实现基础。

## Q5. 条件类型是什么？什么是"分布式分发"？

**答：**

**条件类型 `T extends U ? X : Y` 就是类型层面的三元表达式。分布式分发（distributive）则是它对联合类型的一个副作用。**

```ts
type IfString<T> = T extends string ? 'is string' : 'not string';

type A = IfString<string>;        // 'is string'
type B = IfString<number>;        // 'not string'
type C = IfString<string | number>; // 'not string'（联合整体判断的结果）
```

### 分布式分发

当条件类型左侧是一个**裸类型参数（naked type parameter）**时，TS 会**把联合类型拆开，逐个判断，再把结果联合起来**：

```ts
type IfString<T> = T extends string ? 'yes' : 'no';
type D = IfString<string | number>;   // 'yes' | 'no'  ← 拆开分别判断再合并
```

**为什么会这样？** 因为**裸类型参数**意味着"这个类型可能是联合的每个成员"，语义上自然要逐个评估。

**⚠️ 陷阱：加 `[]` 会关闭分发**。

```ts
type IfString<T> = T extends string ? 'yes' : 'no';
type E = IfString<string | number>;         // 'yes' | 'no'（分发）
type F = IfString<[string | number]>;       // 'no'（[T] 包裹后不再是裸参数，不再分发）
```

**判断是否分发的实用技巧**：如果 `T` 是裸类型参数且可能为联合 → 会分发。

**分布发的实际价值**：这是 `Exclude`、`Extract`、`NonNullable`、`Omit` 的实现基础。

```ts
type Exclude<T, U> = T extends U ? never : T;   // 裸 T → 分发 → 逐个剔除
type Extract<T, U> = T extends U ? T : never;   // 裸 T → 分发 → 逐个保留
type NonNullable<T> = T & {};                  // 用 {} 技巧实现过滤 null/undefined
```

**分布式分发有时是坑**：当你想「联合整体判断」时，需要用 `[T] extends [U]` 的形式**关闭分发**：

```ts
type AllStrings<T> = [T] extends [string] ? true : false;
type G = AllStrings<string | number>;   // false（整体判断）
```

**追问：`Exclude<T, U>` 的原理能讲讲吗？**
→ 靠的就是分发：`Exclude<string | number, string>` 把联合拆成 `string` 和 `number`，对每个成员判断 `extends string ? never : 成员`——`string` 被剔除，`number` 保留，结果是 `number`。**如果去掉分发（写成 `[T] extends [U] ? never : T`），联合会整体保留或整体剔除，结果完全错误。**

**追问：条件类型里能用 `infer` 吗？**
→ 能，而且这正是 `infer` 的主场。`infer` 只能在条件类型的 `extends` 右侧出现，用来**从类型结构里"抓"出一部分**。见 Q7。

## Q6. 映射类型是什么？和对象字面量写法有什么区别？

**答：**

**映射类型是「用现有类型批量生成新类型」的语法：`{ [K in keyof T]: ... }`。**

```ts
interface Person { name: string; age: number; }

// 把每个属性变成可选
type PartialPerson = { [K in keyof Person]?: Person[K] };

// 把每个属性变成只读
type ReadonlyPerson = { [K in keyof Person]: readonly Person[K] };

// 把每个属性转成字符串
type StringifiedPerson = { [K in keyof Person]: string };
```

**核心结构拆解**：

```
{ [K in keyof T]: ... }        读作："对 T 的每个键 K，产出一个新属性"
      ↑    ↑
      |    └── keyof T：键的来源
      └─────── K：映射变量（不是普通变量）
```

**关键：`in` 左边是映射变量，右边是"键的集合"**，右边可以是 `keyof T`、字面量联合、或 `as` 重映射后的结果。

**四个必须掌握的高级特性**：

**1. 增删修饰符（homomorphic mapping）**：

```ts
type Getters<T> = { [K in keyof T as `get${Capitalize<K & string>}`]: () => T[K] };
type Setters<T> = { [K in keyof T as `set${Capitalize<K & string>}`]: (v: T[K]) => void };

type PersonApi = Getters<Person> & Setters<Person>;
// { getName: () => string; getAge: () => number; setName: (v: string) => void; ... }
```

**2. 键重映射（`as` 子句，TS 4.1+）**：

```ts
type Filter<T> = { [K in keyof T as K extends string ? `get${Capitalize<K>}` : never]: T[K] };
```

**3. 过滤（用 `never` 剔除键）**：

```ts
type PickByValue<T, V> = { [K in keyof T as T[K] extends V ? K : never]: T[K] };
// 挑出所有值为 boolean 的属性
```

**4. 修饰符增删（`+` / `-`，TS 2.8+）**：

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };   // 去掉只读
type Required2<T> = { +readonly [K in keyof T]-?: T[K] }; // 加只读、去掉可选
```

**⚠️ 关键陷阱：映射类型对数组和元组的行为特殊**。

```ts
type Boxed<T> = { [K in keyof T]: T[K] };
type B = Boxed<string[]>;   // string[] ✅ 不是 string[][]
// 因为对数组做同构映射时，TS 保留数组结构
```

**映射类型 vs 索引签名**（Q9 已提，这里强化）：

| | 映射类型 `{ [K in keyof T]: ... }` | 索引签名 `{ [k: string]: T }` |
|---|---|---|
| 键集合 | **有限、已知** | 无限、任意 |
| 每个键可以有不同类型 | ✅ | ❌ 全部同一个类型 |
| 多余属性检查 | ✅ 会报错 | ❌ 不报错 |

**内置工具类型就是映射类型的组合**，看懂这条，基本就掌握了全部工具类型：

```ts
type Partial<T> = { [K in keyof T]?: T[K] };
type Required<T> = { [K in keyof T]-?: T[K] };
type Readonly<T> = { readonly [K in keyof T]: T[K] };
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Record<K extends keyof any, T> = { [P in K]: T };
```

**追问：为什么 `Partial` 要写成 `[K in keyof T]?: T[K]` 而不是 `{ [K in keyof T]?: unknown }`？**
→ 因为要**保留原属性类型**。`T[K]` 是索引访问类型，把每个键对应的原类型搬过来；写成 `unknown` 就丢失类型信息了。同理 `Pick` 必须写 `T[P]` 而不是 `T[K]`——**映射的精髓就是"值位置跟着键位置走"**。

**追问：映射类型能映射函数吗？**
→ 可以，`{[K in keyof T]: T[K]}` 这种同构映射对函数类型会保留其调用签名。但**异构映射（改值类型）作用于函数类型会丢失调用签名**——这是 `Parameters` / `ReturnType` 要单独实现的原因。

## Q7. `infer` 是什么？它解决了什么问题？

**答：**

**`infer` 是"在类型结构里反向提取"的占位符——它让编译器告诉你「这个类型里那一部分是 X」，而你不用手写 X。**

```ts
// 需求：写一个取函数返回类型的工具
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
```

没有 `infer` 你几乎写不出来——因为 `R` 事先不知道，只能等编译器"告诉"你。

**`infer` 的三条硬规则**：

1. **只能出现在条件类型 `extends` 的右侧**；
2. **只能在 `infer X` 的位置被"抓取"**，不能像普通类型参数那样随意使用；
3. **一个 `infer` 可以抓一个，也可以抓多个**（抓多个时会把它们联合）：

```ts
type FirstAndLast<T extends any[]> =
  T extends [infer F, ...any[], infer L] ? [F, L] : never;

type FL = FirstAndLast<[1, 2, 3]>;   // [1, 3]
```

**四个高频实战用法**：

**1. 提取返回值**：

```ts
type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
type R = MyReturnType<() => string>;   // string
```

**2. 提取数组元素类型**（比 `T[number]` 更严谨，因为它能处理只读数组）：

```ts
type ElementOf<T> = T extends (infer E)[] ? E : never;
type E = ElementOf<readonly string[]>;   // string ✅
```

**3. 提取 Promise 的解包类型**：

```ts
type Awaited2<T> = T extends Promise<infer U> ? Awaited2<U> : T;
type A = Awaited2<Promise<Promise<number>>>;   // number（递归解包）
```

**4. 提取联合类型的"公共部分"和"全部分"**（`infer` 最高级的用法）：

```ts
type A = { id: number; name: string };
type B = { id: number; age: number };

// 公共 key：`keyof` 作用在联合上 = 各成员 key 的交集
type Common = keyof (A | B);        // 'id'

// 全部 key：keyof 分布式条件类型逐个成员求 keyof 再合并
type AllKeys<T> = T extends unknown ? keyof T : never;
type All = AllKeys<A | B>;          // 'id' | 'name' | 'age'

// 取出联合本身（而不是交集）——用 infer 保留整个 T
type AsUnion<T> = T extends infer U ? U : never;
type Whole = AsUnion<A | B>;        // A | B
```

**关键机制**：`T extends infer U ? U : never` 里，`U` 会**吸收整个 T**（含联合的每个成员），所以 `U` 就是原样；而 `T extends unknown ? keyof T : never` 因为 `T` 是**裸类型参数**，会**分布式**地逐个成员求 `keyof`，再把结果合并。

**⚠️ 常见误解**：`keyof (A | B)` 是**交集**（`keyof A & keyof B`），因为 `keyof` 作用在联合类型上取的是"所有成员都有的键"。想取"所有成员的键的并集"，必须靠分布式条件类型逐个拆开。

**⚠️ `infer` 的限制**：它只能推断**类型结构**，无法推断任意复杂的运行时逻辑。`infer` 也不是运行时推断——**全程零运行时**。

**追问：`infer` 和泛型参数 `T` 有什么区别？**
→ `T` 是**我声明**的类型参数，位置固定（函数签名处）；`infer` 是**编译器推导**出来的类型变量，只能出现在条件类型的 `extends` 右侧，作用是把匹配到的部分**绑定**到一个新名字上。两者常常配合：`<T>` 接收输入，`infer` 拆解输入。

**追问：`infer` 抓不到东西时会怎样？**
→ 条件类型直接走 `false` 分支（整个 `T extends ... ? A : B` 判为假）。所以 `infer` 抓不到通常表现为**结果变成了 `never`**——这是排查类型体操 bug 的第一现场。

## Q8. 模板字面量类型是什么？有什么用？

**答：**

**模板字面量类型把「字符串模板」提升到类型层面：`` `${Prefix}-${Suffix}` `` 是一种类型，可以做模式匹配。**

```ts
type EventName = `on${Capitalize<string>}`;
// 等价于 "on" + 任意首字母大写的字符串

type UserEvent = `user:${'created' | 'updated' | 'deleted'}`;
// "user:created" | "user:updated" | "user:deleted"
```

**核心能力：把「字符串模式」变成可用的类型，让编译器检查字符串格式。**

**四个实战场景**：

**1. 事件名 / 样式键的精确约束**：

```ts
type CSSVar = `--${string}`;              // 任意 CSS 自定义属性
type Theme = `theme-${'light' | 'dark'}`;

// 用在模板字面量类型上做模式匹配：
function getCSSVar(name: CSSVar): string { return `var(${name})`; }
getCSSVar('--main-color');   // ✅
getCSSVar('main-color');     // ❌ 编译报错
```

**2. 解析字符串（用 `infer` 拆）**：

```ts
type ParsePath<T extends string> =
  T extends `${infer Head}/${infer Rest}` ? [Head, ...ParsePath<Rest>] : [T];

type Segments = ParsePath<'a/b/c'>;   // ['a', 'b', 'c']
```

**3. 路由表**：

```ts
type Routes = {
  home: '/';
  user: `/user/${number}`;   // 模板字面量也能嵌 `${number}`
};

const nav: Routes['user'] = '/user/123';   // ✅
const bad: Routes['user'] = '/user/abc';   // ❌
```

**4. 事件名拼写防错**：

```ts
function on<K extends `on${string}`>(event: K, handler: (e: { type: K }) => void) {}
on('onClick', (e) => console.log(e.type));   // ✅ e.type 精确到 'onClick'
```

**⚠️ 模板字面量类型不会产生运行时校验**——它只是类型层面的约束，`'user/abc'` 这种非法值用 `as` 断言照样能塞进去。

**追问：模板字面量类型和正则类型（TS 4.9 的 `RegExp` 类型）是一回事吗？**
→ 不是。TS 4.9 引入的 **`RegExp` 类型**（`/^a+$/` 作为类型）支持在类型层面做正则匹配（`RegExpGroup` / `RegExpExecArray`），是"类型层正则"，能力更强但也更少见。模板字面量类型是更基础、更常用的机制。

**追问：`${string}` 和 `${number}` 有什么区别？**
→ 两者都是"某种模式的字符串"。`${number}` 只能匹配**能被解析为数字的字符串**（`"123"` ✅，`"12a"` ❌）。在模板字面量类型里，`${number}` 是**特殊语法**——它做的是"数字的字符串化"，而 `${string}` 是"任意字符串拼接"。这个区别在路由参数约束里很实用。

## Q9. 递归条件类型是什么？用来做什么？

**答：**

**递归条件类型 = 条件类型 + 引用自身，用来描述「无限深」的结构：嵌套对象、深度只读、深度可选、JSON 解析。**

```ts
type DeepReadonly<T> =
  T extends (infer U)[] ? readonly DeepReadonly<U>[] :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;
```

**核心结构**：

```
DeepReadonly<T>
  ├─ 是数组？   → 映射元素类型，元素递归
  ├─ 是对象？   → 映射每个属性，属性类型递归
  └─ 都不是？   → 原样返回（基本类型终止递归）
```

**必须有的"终止条件"**——否则 TypeScript 会报"类型实例化过深"（`Type instantiation is excessively deep and possibly infinite`）。上面 `T extends object` 的 else 分支（基本类型原样返回）就是终止点。**TS 4.1+ 递归类型有专门的优化，深度限制放宽了很多**，但仍要注意收敛。

**三个最有名的实战用法**：

**1. 深度可选（嵌套对象每一层都可省）**：

```ts
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};

type Cfg = { db: { host: string; port: number } };
const c: DeepPartial<Cfg> = { db: { host: 'x' } };   // ✅ port 可省
```

**2. JSON 解析结果类型**（把 JSON 字符串解析成类型）：

```ts
type JsonValue =
  | string | number | boolean | null
  | JsonValue[]
  | { [key: string]: JsonValue };

type ParseJson<S extends string> =
  S extends `"${infer Str}"` ? Str
  : S extends `${infer Num extends number}` ? Num
  : S extends 'true' ? true
  : S extends 'false' ? false
  : S extends 'null' ? null
  : S extends `[${infer Inner}]` ? ParseJson<Inner>[]
  : S extends `{${infer Inner}}` ? { [K in keyof ParseJson<Inner>]: ParseJson<Inner>[K] }
  : never;
```

**3. 深度键路径**（把嵌套对象的路径联合出来）：

```ts
type Paths<T> = T extends object
  ? { [K in keyof T & string]:
      | K
      | (T[K] extends object ? `${K}.${Paths<T[K]>}` : never)
    }[keyof T & string]
  : never;

type P = Paths<{ a: { b: { c: number } } }>;
// "a" | "a.b" | "a.b.c"
```

**追问：递归类型有什么实际限制？**
→ 1. **必须有终止条件**，否则触发 `Type instantiation is excessively deep`；2. **对联合类型分发**时要小心，`T[K] extends object` 遇到联合时，如果不想分发要写 `[T[K]] extends [object]`；3. **深度递归的类型在 VS Code 里 hover 会很慢**，类型体操写得越花，IDE 越卡。

**追问：手写递归类型 vs 直接写 `unknown` / `any`，实际项目怎么选？**
→ **业务代码里绝大多数时候直接用 `unknown` + 运行时 schema 校验（Zod）**。递归类型的价值主要在**库代码**和**开发者体验**——比如表单库的字段路径推导、配置 schema 的类型推导。**在业务里花两天写一个 `DeepPartial`，不如花两小时用 Zod 拿到运行时和类型双重安全。**

## Q10. 什么是协变、逆变、不变？为什么 TS 里函数参数是逆变的？

**答：**

**这三个词描述的是「类型 A 能不能赋给类型 B」的方向关系，取决于这个类型出现在什么位置。**

| 位置 | 关系 | 例子 |
|------|------|------|
| **返回值**（产出） | **协变**（covariant） | `Animal` → `Dog` 可以，因为返回 Animal 的地方能接受 Dog |
| **函数参数**（消费） | **逆变**（contravariant） | `Dog` → `Animal` 可以，因为要求能处理 Dog 的函数也能处理 Animal |
| **可变位置**（既能收又能产） | **不变**（invariant） | `Array<T>`、`Mutable<T>` |

**为什么参数是逆变的？** 直观解释：

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };

// 有一个能处理任何 Animal 的函数
function feedAll(f: (a: Animal) => void): void {
  console.log(f);
}

// 能处理 Dog 的函数可以传进去吗？可以！
// 因为 feedAll 只会喂 Animal，而 f 能处理 Dog ⊆ Animal，喂 Dog 时 f 应付得了。
feedAll((d: Dog) => { console.log(d.bark); });
```

**这就是"函数参数逆变"（contravariant）**——**约束越强（参数类型越具体）的函数，能用在要求越松的地方**。

**TS 的实际规则**：

| 配置 | 参数检查 | 说明 |
|------|---------|------|
| `strictFunctionTypes: true`（`strict` 家族默认包含，TS 3.5+） | **逆变** | 严格检查函数类型参数的 contravariance |
| `strictFunctionTypes: false` | **双变**（bivariant） | 宽松，容易漏类型错误 |

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };

// strict 下：Dog 不能赋给 Animal（因为参数逆变，方向反了）
declare const dogHandler: (d: Dog) => void;
const aHandler: (a: Animal) => void = dogHandler;   // ❌ strict 下报错
```

**⚠️ 方法（method）是个例外**：

```ts
interface Box {
  set(value: Animal): void;    // 方法语法 → 双变
}
interface Box2 {
  set: (value: Animal) => void; // 属性语法 → 严格逆变
}
```

**方法语法（`method() {}`）走双变，属性语法（`prop: () => void`）走严格逆变**。这是 TS 为了向后兼容保留的行为——写严格类型时优先用属性语法。

**不变（invariant）的典型**：`Array<T>` 是**不变**的，因为 `Animal[]` **不能**赋给 `Dog[]`——数组既能写入（消费）元素，又能读出（产出）元素，两个方向都被用到了。

```ts
declare const dogs: Dog[];
const animals: Animal[] = dogs;   // ✅ 读出来没问题
declare const dogs2: Dog[] = animals;   // ❌ 可能往里塞 Cat
```

**追问：实际开发中怎么用协变逆变指导设计？**
→ **核心原则：泛型在参数位置要"保守"，在返回值位置要"大方"。**
- `function pick<T>(items: T[]): T[]` —— T 在参数和返回值都出现 → 实际是不变；
- `function get<T>(items: T[]): T` —— T 只在返回值出现 → **协变**，可以安全地传更具体的类型；
- `function set<T>(items: T[], v: T)` —— T 出现在参数位置 → **逆变**，约束更强。

写 React 组件 props 时这条特别有用：**props 是逆变位置**（父传子），所以 props 里用 `T` 时要小心；**state 是协变位置**（子给父），相对宽松。

**追问：TS 6.0/7.0 对变型规则有变化吗？**
→ **没有。** 变型规则自 TS 3.5 引入 `strictFunctionTypes` 后基本稳定，TS 6.0（2026-03-23）和 TS 7.0（2026-07-08，Go 原生编译器）在这块没有语义变化。**类型系统的行为一致性在 TS 7 这类大版本迁移里是优先保证的。**
