# 工程化与工具链

> **什么时候该读**：面试官问「tsconfig 有哪些关键字段」「strict 开了哪些」「ESM 和 CJS 有什么区别」「`.d.ts` 怎么写」「构建工具怎么选」「TS 7 是什么」，答不上来会被认为「只会跑 `ts-node`，不懂工程链路」。
> **答题主线**：**一条编译链路贯穿全篇**——`tsconfig` 决定「查得严不严、输出成什么样」，模块解析决定「代码找得到不找得到」，构建工具决定「产物怎么来」，TS 6.0/7.0 决定「这条链路本身换了实现」。所有问题都能落回这四个环节。

---

## Q1. `tsconfig.json` 有哪些关键字段？`tsc` 到底做了哪几步？

**答：**

**`tsconfig.json` 是 TypeScript 项目的配置文件，`tsc` 读取它决定"查多严、输出什么、往哪找模块"。**

### `tsc` 的三个阶段

```
源码 .ts
  ↓ ① 解析（parse）
  ↓ ② 类型检查（check）  ← 报错都在这一步
  ↓ ③ 转译（emit）      ← 擦掉类型，产出 .js / .d.ts / .js.map
产物 .js
```

**关键认知：类型检查和转译是两步，可以分开。** `--noEmit` 只检查不产出；`--emitDeclarationOnly` 只产出 `.d.ts` 不产出 `.js`。这决定了后面构建工具选型的逻辑。

### 关键字段速查

| 字段 | 作用 | 面试要点 |
|------|------|---------|
| **`strict`** | 一组严格检查的总开关 | TS 6.0 起**默认 `true`** |
| **`target`** | 输出代码的语法目标 | 决定 emit 时的语法降级（async/await 降级等） |
| **`module`** | 输出模块格式 | TS 6.0 起**默认 `esnext`** |
| **`moduleResolution`** | 怎么找模块 | TS 6.0 废弃 `node`/`node10`，TS 7.0 变硬错误 |
| **`lib`** | 可用的标准库 API | 决定能不能用 `Promise`、`Array.prototype.at` |
| **`outDir` / `rootDir`** | 产物目录 / 源码根目录 | 配合 `include` 决定目录结构 |
| **`declaration`** | 是否产出 `.d.ts` | 库项目必开，TS 5.0+ 支持 `declaration: true` 配合 `rewriteRelativeImportExtensions` |
| **`declarationMap`** | `.d.ts` 附带源码映射 | 库项目建议开，跳转到源码 |
| **`sourceMap`** | JS 映射回 TS | 调试用 |
| **`include` / `exclude`** | 哪些文件参与编译 | `exclude` 默认排除 `node_modules`、`bower_components`、`jspm_packages` 和输出目录 |
| **`incremental`** | 增量编译 | 存 `.tsbuildinfo`，配合 `composite` 使用 |
| **`isolatedModules`** | 每个文件独立转译 | 转译器（esbuild/swc）要求开，Vite 项目必开 |
| **`verbatimModuleSyntax`** | 不改写 import/export 语法 | 与 `isolatedModules` 配合，避免类型导入被错误擦除 |
| **`skipLibCheck`** | 跳过 `.d.ts` 检查 | **默认开**，提速但会漏掉类型库之间的冲突 |
| **`noUncheckedIndexedAccess`** | 索引访问返回 `T \| undefined` | 建议开，防数组越界 bug |
| **`exactOptionalPropertyTypes`** | 可选属性不能显式赋 `undefined` | 建议开 |

**一条容易搞混的线**：`target` 决定**输出语法**，`lib` 决定**可用 API**。`target: es2022` 但 `lib` 没包含 `es2022`，`Array.prototype.at` 照样报类型错误——**因为 `lib` 才是类型环境的来源**。

**追问：`include` 和 `files` 有什么区别？**
→ `files` 是**精确的文件列表**（必须存在，缺一个就报错）；`include` 是**glob 模式**（支持 `*`、`?`、`**`）。实际项目几乎都用 `include` + `exclude`。另外 `include` 默认为 `**/*`（即包含所有文件），但 `exclude` 排除 `node_modules` 等。

**追问：`tsc` 能增量编译吗？怎么开？**
→ 能。开 `incremental: true`（或 `composite: true`，它会隐式开启），`tsc` 会把上次编译的哈希和类型信息存进 `.tsbuildinfo` 文件，下次只处理变化的文件。**但注意：增量编译只是"跳过没变的文件"，不等于"只做类型检查的部分"**——类型检查是全量语义分析，增量主要省在转译和部分检查上。

## Q2. `strict` 家族包含哪些选项？实际项目该怎么配？

**答：**

**`strict: true` 是一个打包开关，打开它等于同时打开一组严格检查。TS 6.0 起 `strict` 默认就是 `true`。**

### `strict` 家族全表

| 选项 | 作用 | 关掉的后果 |
|------|------|-----------|
| **`strictNullChecks`** | `null`/`undefined` 不能赋给非空类型 | ⚠️ **最关键的一个**，关掉等于放弃 null 安全 |
| **`noImplicitAny`** | 参数/变量没类型且推断不出时**报错**（而非隐式 `any`） | 拼写错误查不出来 |
| **`strictFunctionTypes`** | 函数参数**逆变**检查 | 函数类型赋值漏报（见上一篇 Q10） |
| **`strictBindCallApply`** | `bind`/`call`/`apply` 的参数严格检查 | 传错参数不报错 |
| **`strictPropertyInitialization`** | 类属性必须初始化 | `undefined` 逃逸到运行时 |
| **`noImplicitThis`** | `this` 上下文类型检查 | `this` 变成隐式 `any` |
| **`alwaysStrict`** | 输出 `"use strict"` | —— |
| **`useUnknownInCatchVariables`****（4.4+） | `catch` 里的变量是 `unknown` 而非 `any` | 异常处理失去类型保护 |

### 在 `strict` 之外，我建议**额外开**的三个

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,   // arr[0] 是 T | undefined
    "exactOptionalPropertyTypes": true, // 可选属性不能显式写 undefined
    "noImplicitOverride": true           // 子类覆写父类方法必须写 override
  }
}
```

**`noUncheckedIndexedAccess` 是被低估的一项**：开了之后 `arr[0]` 的类型是 `T | undefined`，逼你在代码里处理越界。**不写这个选项，`arr[0].foo` 在数组为空时就是运行时崩溃。**

### `strictNullChecks` 到底改了什么

```ts
// 开启 strictNullChecks
function f(x: string) {}
f(undefined);          // ❌ 报错
const s: string = null; // ❌ 报错

// 但 undefined 和 null 仍然可以赋给 any / unknown
```

**它带来的最大工作量是"初始化"问题**：

```ts
class User {
  name: string;              // ❌ strictPropertyInitialization 报错
  name!: string;             // ✅ 断言"我稍后一定会赋值"（⚠️ 有运行时风险）
  name?: string;             // ✅ 可选
}
```

**更好的做法是构造函数里 `readonly name: string`（参数属性）**，而不是用 `!` 逃逸。

### 关于 `skipLibCheck`

**默认是 `true`，通常建议保持开启**。它只跳过 `.d.ts` 文件的检查——**你自己的代码还是全查**。代价是类型库之间的冲突（比如两个 `@types` 声明了同一个全局名）查不出来。大型项目里如果开了它编译快很多。

**追问：`strict` 什么时候不适合开？**
→ 几乎没有"不适合"，只有"**成本**"问题。老项目全量开 `strict` 可能有几千个错误，**不要一次全开**。推荐策略：**新文件开、老文件豁免**——用 `// @ts-nocheck` 逐文件压制，或用 `strict` + 逐目录迁移。

**追问：`strictNullChecks` 是不是和 `any` 冲突？**
→ 不冲突，但 `any` 会**绕过**它。`any` 依然可以赋给 `string`，`strictNullChecks` 拦不住含 `any` 的表达式。这是 `any` 传染性的另一个体现。

## Q3. 模块解析策略（`moduleResolution`）有哪几种？怎么选？

**答：**

**`moduleResolution` 决定编译器「给一个模块说明符，它去哪里找文件」。TS 6.0 废弃了老的 `node`（即 `node10`），TS 7.0 会把它变成硬错误。**

### 各策略对照

| 策略 | 状态 | 特点 | 适用 |
|------|------|------|------|
| **`node10`**（别名 `node`） | ⚠️ **TS 6.0 废弃，TS 7.0 硬错误** | 老式算法：逐级向上找 `node_modules`，不管 `package.json` 的 `exports`/`type` | 只剩维护老项目 |
| **`node16`** | 现行 | 严格遵循 `package.json` 的 `exports`/`imports`，区分 ESM/CJS | 需要发布库、Node ESM 项目 |
| **`nodenext`** | 现行 | 基于 `node16`，随 Node 版本演进更新 | Node 后端项目的稳妥选择 |
| **`bundler`** | 现行（TS 5.0+） | 面向打包器：允许无扩展名导入、支持 `exports`、**不做 CJS/ESM 区分** | **前端 / Vite 项目首选** |
| **`classic`** | 老式 | TS 早期算法 | 几乎不用 |

### `node16` / `nodenext` vs `bundler` 的核心差异

`node16`/`nodenext` 会**区分 ESM 和 CJS**，并据此施加不同规则：

```jsonc
// package.json
{ "type": "module" }
```

- `.ts` 文件 → 按 ESM 处理，**顶层 `await` 允许**，相对导入**必须带扩展名**（`./foo.js`）；
- `.cts` 文件 → 按 CJS 处理。

```jsonc
{ "type": "commonjs" }
```

- `.ts` → 按 CJS 处理，**顶层 `await` 不允许**，导入语法宽松。

**`bundler` 则不做这个区分**——它假设"最终会被打包器处理"，所以允许 `./foo` 不带扩展名，允许混用 `import`/`require`。

**这也是 `verbatimModuleSyntax` 存在的原因**：它让 TS **不改写** `import`/`export` 语法，从而 `import type` 和值导入的区分在转译后依然清晰，交给打包器决定怎么处理。

### 选型结论（直接背）

| 场景 | 推荐 |
|------|------|
| **前端 / Vite / 打包器项目** | **`bundler`** |
| **Node 后端 ESM 项目** | **`nodenext`** |
| **要发布到 npm 的库** | **`node16`** 或 `nodenext`（要同时支持两种，用 `exports` 条件导出） |
| **老项目** | `node10` → **尽快迁到 `node16`/`bundler`**，TS 7.0 会直接报错 |

**追问：TS 6.0 废弃 `moduleResolution: node` 后，迁移路径是什么？**
→ 逐步换成 `node16`（后端/库）或 `bundler`（前端）。**这不一定是"报错"级别的改动**——老代码大部分能直接跑。但要注意 `node16`/`nodenext` 强制 ESM 下相对导入带扩展名，这一条会让一批文件需要改。

**追问：`baseUrl` 为什么也被废弃了？**
→ `baseUrl` 让编译器可以**凭空生成**模块路径（`import x from 'src/foo'` 凭空解析），这让编译结果**不可移植**——换个工具链（tsup/vite/esbuild）就解析不到。TS 6.0 废弃"把 `baseUrl` 当查找根"的用法，TS 7.0 变硬错误。**替代方案是 `paths`**（`paths` 只做别名映射，不影响产物，TS 5.0+ 可以配 `baseUrl: "."` 或完全省略）。

## Q4. ESM 和 CommonJS 有什么区别？在 TypeScript 里怎么落地？

**答：**

**ESM 是语言标准的模块系统（`import`/`export`，静态分析、编译期确定），CJS 是 Node 的运行时模块系统（`require`/`module.exports`，运行时解析）。**

### 核心差异

| 维度 | CommonJS | ESM |
|------|-----------|-----|
| **语法** | `require()` / `module.exports` | `import` / `export` |
| **加载时机** | **运行时**动态求值 | **编译期**静态分析确定 |
| **是否可静态分析** | ❌ 依赖执行顺序，条件 require 很难分析 | ✅ 依赖图可静态确定 |
| **顶层 `await`** | ❌ 不支持 | ✅ 支持 |
| **导出是动态的** | ✅ `exports.foo` 可以被改 | ❌ 导出绑定是**不可变**的（live binding） |
| **默认导入语义** | `module.exports` 整体 | `export default` 显式声明 |
| **循环依赖** | 部分可用（拿到半成品对象） | 会触发 TDZ（暂时性死区）错误 |
| **`__dirname` / `__filename`** | ✅ 有 | ❌ 没有（需 `import.meta.dirname` 等） |

**⚠️ 面试高频陷阱：`import x from './mod'` 在 CJS 里到底拿到什么？**

```js
// mod.js (CJS)
module.exports = { a: 1 };
```
```js
// main.js
import x from './mod.js';
console.log(x);   // { a: 1 }  ← 默认导入拿到的是 module.exports 整体
```
**CJS 模块被 ESM `import` 时，默认导入拿到 `module.exports` 整体**，而不是 `exports.default`。这导致很多"我明明写了 `export default` 为什么拿到 undefined"的困惑。

### TypeScript 里的落地方式

TS 的 `module` 字段（输出格式）和 `moduleResolution`（查找方式）是**两件事**：

| `module` | 输出 | 配套的 `moduleResolution` |
|---------|------|----------------------|
| `esnext` | 保留 `import`/`export` 原样 | `bundler` |
| `nodenext` | 按 `package.json` 的 `type` 决定输出 ESM 还是 CJS | `nodenext` |
| `node16` | 同上 | `node16` |
| `commonjs` | 转成 `require`/`exports` | `node10`（已废弃） |

**⚠️ TS 6.0 起 `module` 默认是 `esnext`**，这意味着新项目默认输出 ESM 语法——如果你的运行环境是老的 CJS，需要显式设置 `module: "commonjs"` 或在 `package.json` 里标 `"type": "module"`。

**文件扩展名约定**：

| 后缀 | 强制模块格式 |
|------|------------|
| `.mts` | 始终 ESM |
| `.cts` | 始终 CJS |
| `.ts` | 跟随 `package.json` 的 `type` 字段 |

**双包发布的做法**（库项目同时支持两种消费方）：

```json
{
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    }
  }
}
```

**实战中我更推荐的做法**：**别在应用项目里混用两套**。应用项目（尤其是后端）选一套定死——要么全 ESM（`"type": "module"`），要么全 CJS。混用的代价是运行时各种 `ERR_REQUIRE_ESM` / `__dirname is not defined` 报错。条件导出（`exports` 字段）留给**要发布给别人用的库**。

**追问：为什么 Node 从 12 到 22 一直在推 ESM？**
→ 因为 ESM 的**静态可分析性**是 Node 生态的关键能力：它让工具能做 tree-shaking（摇树优化）、自动引入 ESM 依赖（不用再 `import 'x'` 副作用导入）、更好的调试信息。**Node 22.12+ 起 `require(esm)` 默认开启**（能在 CJS 里 `require` 一个 ESM 模块），这大幅降低了迁移成本。

**追问：`import` 和 `require` 能混用吗？**
→ 技术上可以（TS 允许 `import x = require('y')` 这种 CJS 风格语法），但**不要混**。TS 5.x 起 `verbatimModuleSyntax` 会强制你显式区分 `import type` 和值导入，就是为了避免混用带来的坑。

## Q5. 声明文件 `.d.ts` 是什么？怎么写？`@types/*` 又是什么？

**答：**

**`.d.ts` 是「只有类型、没有实现」的声明文件。运行时它不存在，只给编译器看。**

### 三种使用场景

**1. 给自己的 JS 代码补类型**（`allowJs` + `checkJs`，或手写 `.d.ts`）：

```ts
// utils.d.ts
export declare function parse(input: string): Record<string, unknown>;
export declare const VERSION: string;
```

**2. 给没有类型的第三方库写声明**：

```ts
declare module 'legacy-lib' {
  export interface Options { timeout?: number }
  export function run(opts: Options): Promise<void>;
}
```

**3. 发布库时产出声明**：开 `declaration: true`，`tsc` 自动生成 `.d.ts`。

### `.d.ts` 的语法要点

```ts
// 变量声明
declare const version: string;
declare let counter: number;
declare var global: unknown;      // var 才有真正的全局作用域

// 函数声明
declare function greet(name: string, ...rest: boolean[]): void;

// 类声明
declare class Database {
  constructor(url: string);
  query(sql: string): Promise<unknown[]>;
  private secret: string;         // ⚠️ private 只在类型层面，不影响运行时
}

// 接口 / 类型别名
interface User { id: number }
type Result = { ok: true } | { ok: false; error: Error };

// 导入导出
export { User };
export type { Result };
import { User } from './types';

// 环境声明
declare const process: { env: Record<string, string | undefined> };

// 全局变量扩展（给已有全局加成员）
declare global {
  interface Window { myApp: App }
}
```

### `declare` 修饰符的含义

| 写法 | 含义 |
|------|------|
| `declare const x: T` | "**这个变量确实存在**，类型是 T"（不会生成任何 JS 代码） |
| `declare module 'x'` | 声明一个外部模块 |
| `declare global { }` | 在模块文件里扩展全局作用域 |

**⚠️ 最常见的错误：把 `declare` 用在了真实实现上**。

```ts
// ❌ 错误：文件里已经有实现了
declare function foo(): void;
function foo() {}   // 报错：Duplicate identifier
```

**`declare` 的意思是"我这里只有类型声明，没有实现"。**

### `@types/*` 是什么

**`@types/` 是 DefinitelyTyped 生态的包命名空间，专门放第三方库的**类型声明**（只有 `.d.ts`，没有运行时代码）。**

```bash
npm i -D @types/node        # Node 内置模块的类型
npm i -D @types/express     # express 的类型
```

**机制**：`tsc` 会**自动扫描 `node_modules/@types/` 下的所有包**，把它们当作全局环境的一部分引入。

**⚠️ TS 6.0 的重大变更：`types: []` 成为默认值**——**不再自动引入 `@types/*`**。

这带来的后果：

```jsonc
// 现在需要显式声明
{
  "compilerOptions": {
    "types": ["node"]     // 只引入 @types/node
  }
}
```

**为什么要改？** 因为自动全量引入是常见的性能瓶颈和冲突来源：装了个 `@types/jest` 就全局多出 `expect`、`describe`；装了个 `@types/mocha` 就和 jest 冲突。**显式声明更可控。**

**⚠️ 迁移期最常见的报错**：`Cannot find name 'process'`，或 `Cannot find name 'require'`。解决就是在 `types` 里补上 `"node"`。

**追问：有了 `@types/*`，为什么还要 `typesVersions` / `exports` 里的 `types` 条件？**
→ 因为 `@types/*` 只覆盖"没有自带类型"的库（大多数老库）。**现代库（express 5、zod、vite 等）自己就带 `.d.ts`**，直接 `import` 就有类型，不需要 `@types`。库的 `package.json` 里 `exports.types` 字段是告诉 TS "我的类型在哪个文件"，这在条件导出（ESM/CJS 双包）里必须配，否则 TS 会报"找不到类型声明"。

**追问：`.d.ts` 会被编译进产物吗？**
→ **不会**。`.d.ts` 本身不产生 JS，它只是类型信息。`tsc` 会把 `.ts` 编译成 `.js` + 同步产出一份 `.d.ts`。发布库时通常还会开 `declarationMap: true` 和 `sourceMap`，让使用者能跳转到你的源码。

## Q6. `tsc`、esbuild、Vite、tsup 怎么选？各自的定位是什么？

**答：**

**结论先说：现在的最佳实践是「esbuild/swc 负责转译（快），`tsc --noEmit` 负责类型检查（准）」，Vite 是开发服务器 + 构建编排，tsup 是库打包。**

### 定位对照

| 工具 | 类型检查 | 转译 | 打包 | 场景 |
|------|---------|------|------|------|
| **`tsc`** | ✅ 完整 | ✅ | ❌（只做模块转译，不打包） | 类型检查基准、发布纯 JS 库 |
| **esbuild** | ❌ **完全不做类型检查** | ✅ 极快 | ✅ | 底层转译引擎 |
| **swc** | ❌ | ✅ 快，Rust 实现 | ❌（需配 bundler） | Next.js 内部、配合 rspack |
| **Vite** | ❌（用 esbuild 转译） | ✅ | ✅（生产用 Rollup） | **前端应用开发** |
| **tsup** | ❌ | ✅（esbuild） | ✅ | **库打包**（esbuild 驱动，产出 dts） |
| **Rollup** | ❌ | ❌ | ✅ | 库打包（生态最全，插件多） |
| **tsdown** | ❌ | ✅ | ✅ | tsup 的新一代替代（ Rolldown 驱动） |
| **webpack** | ❌ | ✅（可用 babel/swc） | ✅ | 需要复杂定制的场景 |

### 为什么 esbuild 不做类型检查

**因为类型检查需要完整语义分析**——esbuild 是**单遍（single-pass）**解析器，只做语法级转换，没有符号表、没有类型信息。硬要做类型检查，esbuild 就不可能快。

**关键认知：type check 和 transpile 是两个正交的关注点。**

### 现代项目的标准分工

```
开发时：  vite dev     → esbuild 转译（秒级热更新） + tsserver/tsc 提供 IDE 类型提示
CI 时：   tsc --noEmit → 完整类型检查（作为质量门禁）
构建时：  vite build / tsup build → 转译 + 打包 + 生成 d.ts
```

**⚠️ 关键提醒**：**esbuild 只转译不做类型检查，意味着"运行时才发现类型错"**。所以 CI 里**必须有一步 `tsc --noEmit`**——很多团队只跑了 `vite build` 就上线，类型错误就漏过去了。

### tsup 的价值

tsup 是 esbuild 驱动的打包器，专为**库**设计：

- 自动产出 ESM（`.mjs`）+ CJS（`.cjs`）+ `.d.ts`；
- 默认 `dts: true`，用 rollup-plugin-dts 生成类型声明；
- 支持 `banner` / `footer` 注入（用于 CJS 的 `__esModule` 标记）；
- 支持 `external` 声明 peerDependencies 不打进产物。

```ts
// tsup.config.ts
import { defineConfig } from 'tsup';

export default defineConfig({
  entry: ['src/index.ts'],
  format: ['esm', 'cjs'],
  dts: true,
  sourcemap: true,
  clean: true,
});
```

**注意**：tsup 生成 `.d.ts` 用的是 **rollup-plugin-dts**（走的是 TypeScript API），这在 **TS 7.0 下会受影响**——TS 7.0 不提供 compiler API，基于 TS API 的工具要留在 6.0（等 7.1）。

### Rollup / tsup / tdown / webpack 怎么选

| 需求 | 选 |
|------|-----|
| 库打包，要极致简单 | **tsup** |
| 库打包，要最全的插件生态、最精细控制 | **Rollup** |
| 库打包，想要 Rollup 生态 + 更快的未来 | **tsdown**（Rolldown 驱动） |
| 应用打包，配置自由度高、生态最老牌 | **webpack** |
| 应用开发，热更新和 dev server | **Vite**（不用配） |

**我的判断**：**新库用 tsup，新应用用 Vite**，这两个组合覆盖 90% 的场景。

**追问：Vite 生产构建为什么用 Rollup 而不是 esbuild？**
→ 早期 Vite 用 esbuild 打包，收益不明显（瓶颈在 chunk 分割和 tree-shaking 的质量），后来换成 Rollup 拿到更好的产物质量和插件生态。**Vite 的核心价值是 dev server 的按需编译（deps pre-bundling + 原生 ESM），不是打包器本身。** 另外 Vite 6 起提供了 Rolldown（Rust 编写的打包器）作为可选替代，用 Vite 的 Rust 插件 API 可以拿到 esbuild 级的速度 + Rollup 级的兼容性。

**追问：`isolatedModules` 为什么是 Vite 项目的必选项？**
→ 因为 esbuild **只转译单个文件，不做跨文件分析**。如果一个文件里有 `export { SomeType }`（把类型当值导出），esbuild 不知道 `SomeType` 是类型，擦除后就会留下一个 `undefined` 导出。`isolatedModules: true` 让 tsc **主动报这类错误**，逼你写 `export type { SomeType }`。**这和 `verbatimModuleSyntax` 是配套的。**

## Q7. TypeScript 6.0 有哪些变化？哪些默认值改了？

**答：**

**TypeScript 6.0（2026-03-23 发布）是最后一个 JavaScript 实现版本**（5.x 已是维护线）。它本身是**为 TS 7.0 铺路的过渡版本**，所以在"废弃旧行为"这件事上比以往更激进。

### 默认值变更（重点）

| 字段 | 旧默认 | **TS 6.0 默认** | 影响 |
|------|-------|---------------|------|
| **`strict`** | `false` | **`true`** | 新项目自动是严格模式 |
| **`module`** | `commonjs`（取决于 `target`） | **`esnext`** | 新项目默认输出 ESM 语法 |
| **`target`** | `es5` | **`es2025`** | 默认不再降级到 ES5 |
| **`types`** | 自动引入全部 `@types/*` | **`[]`（空数组）** | ⚠️ **不再自动引入 `@types/*`** |
| **`noUncheckedSideEffectImports`** | `false` | **`true`** | 副作用导入（`import './polyfill'`）必须真实存在，否则报错 |

**逐条说清实际后果**：

**1. `strict: true`**
- 新项目默认就是严格模式，`strictNullChecks`、`noImplicitAny` 等全部开启。**升级老项目时会冒出一大批错误**——这是 6.0 升级最主要的痛点。

**2. `module: esnext`**
- 输出保留 `import`/`export` 原样。⚠️ **如果你的运行环境是 CJS 且没有在 `package.json` 里标 `"type": "module"`，产物会直接跑不起来**（`Cannot use import statement outside a module`）。**升级时务必检查 `package.json` 的 `type` 字段。**

**3. `target: es2025`**
- 默认不再把 async/await 降级成 generator+Promise 状态机。产物可读性和体积都更好。⚠️ **需要确认运行环境支持 ES2025**（Node 22+ 大部分支持；老浏览器/老 Node 需要显式降 `target`）。

**4. `types: []`**
- **这是最容易被低估的一条**。TS 不再自动扫描 `node_modules/@types/`。后果：
  - `process`、`require`、`__dirname` 全部报 `Cannot find name`；
  - 全局测试框架 API（`describe`、`it`）也不再自动可用；
  - **解法**：显式写 `"types": ["node"]`，或按需列出 `["node", "vitest/globals"]`。

**5. `noUncheckedSideEffectImports: true`**
- `import './setup.ts'` 这种纯副作用导入，如果文件不存在会报错。**Vite/Vitest 项目里写错路径会立刻暴露，而不是运行时莫名失败。**

### TS 6.0 废弃的项（TS 7.0 会变成硬错误）

| 被废弃 | 替代 |
|--------|------|
| `target: es5` | `target: es2015`+ 或更高 |
| `moduleResolution: node` / `node10` | `node16` / `nodenext` / `bundler` |
| AMD / UMD / SystemJS 模块格式 | ESM / CommonJS |
| `baseUrl` 作为模块查找根 | `paths`（别名映射） |

**⚠️ 重点：在 TS 6.0 里这些是"废弃警告"，在 TS 7.0 里会直接变成编译错误。** 所以 6.0 的正确用法是**当作迁移工具**：先升到 6.0，把警告全清掉，再上 7.0。

### TS 6.0 的其他重要变化

- **移除了一些过时的编译选项**（如 `charset`、`keyofStringsOnly`、`noImplicitUseStrict`、`suppressExcessPropertyErrors`、`suppressImplicitAnyIndexErrors`、`out`）；
- **`--build`（项目引用）模式增强**，增量编译更可靠；
- 性能提升（JS 实现的编译速度优化）。

**追问：升级到 TS 6.0 的推荐步骤？**
→ 1. 先在 **TS 5.x 最新版**上把 `strict` 相关问题清干净（手动开 `strict: true`，逐个修）；
2. 升到 6.0，看新增的废弃警告，**逐条清掉**（重点：`moduleResolution`、`baseUrl`、`target: es5`）；
3. 检查 `package.json` 的 `type` 字段和 `types` 数组；
4. 最后再上 TS 7.0。

**追问：为什么 TS 6.0 是个"过渡版本"？**
→ 因为 TS 7.0 是 **Go 原生编译器重写**，不再是渐进式演进。为了让 7.0 能做破坏性变更（比如把废弃项变硬错误），6.0 先把所有旧行为标记为废弃并给出警告，**给用户一个完整的迁移窗口**。这就是"6.0 是最后一个 JS 实现版本"的含义。

## Q8. TypeScript 7.0 是什么？Go 原生编译器带来了什么？有哪些限制？

**答：**

**TypeScript 7.0（2026-07-08 GA）是 TypeScript 编译器用 Go 重写的版本（原生编译器 `tsgo`），性能提升一个数量级，但有明确的限制。**

### 核心变化

| 维度 | TS 5.x / 6.0（JS 实现） | **TS 7.0（Go 原生）** |
|------|----------------------|----------------------|
| **实现语言** | TypeScript/JavaScript | **Go** |
| **编译速度** | 基准 | **快 10 倍左右**（大型项目从分钟级降到秒级） |
| **内存占用** | 高 | **显著降低** |
| **compiler API** | ✅ 提供（`ts.createProgram` 等） | ⚠️ **不提供** |
| **语言特性** | 全部 | **TS 6.0 的语言特性全部保留**（7.0 是编译器的重写，不是语言的破坏性变更） |

### ⚠️ 最重要的限制：不提供 compiler API

**这是 TS 7.0 影响最大的一条**，面试必须说清：

```ts
// 依赖 TS compiler API 的工具，在 TS 7.0 下会失效
import ts from 'typescript';

const program = ts.createProgram(['./src/index.ts'], {
  noEmit: true,
});
```

**直接受影响的工具**：

| 工具 | 影响 |
|------|------|
| **`typescript-eslint`** | ⚠️ **必须留在 TS 6.0**，等 TS 7.1 |
| **`ts-jest`** / `@swc/jest` 的类型检查部分 | 需要确认版本 |
| **`tsup` 的 `dts: true`**（用 rollup-plugin-dts → TS API） | 需要确认版本或改用其他方案 |
| **`ts-morph`** / `ts-simple-ast` | 需要更新 |
| **各类 AST 工具链**（`tsquery`、代码迁移脚本） | 需要更新 |

**面试这么答**：

> **TS 7.0 的取舍很清晰：拿"提供 compiler API"换"10 倍编译速度"。** 对**应用项目**（只跑 `tsc --noEmit` 做类型检查）这是纯收益；对**工具链作者**（需要读写 AST 的库）则需要等 7.1。
>
> **但两者不冲突**——因为 TS 6.0 和 7.0 可以共存于不同项目/不同依赖树。你甚至可以在 monorepo 里让应用用 7.0、工具链依赖 6.0。

### 为什么用 Go 重写

**主因是性能，其次是可维护性和并发模型**：

1. **大型仓库的类型检查是分钟级的**——monorepo 里动一个公共类型，影响几万文件，JS 实现的检查时间让人抓狂；
2. **Go 的并发原语**让多核并行分析变得自然；
3. **内存效率**大幅提升，能处理更大的程序。

### 迁移建议（实操层面）

| 步骤 | 动作 |
|------|------|
| 1 | 先升到 **TS 6.0**，把废弃警告全清掉（这是 7.0 的前置条件） |
| 2 | 在 CI 里跑一遍 `tsc --noEmit`，对比 6.0 和 7.0 的输出，**确认无新增错误** |
| 3 | 检查依赖树里有没有依赖 compiler API 的工具（`npm ls typescript`） |
| 4 | 应用项目直接上 7.0；工具链项目等 7.1 |

**⚠️ 特别注意 `skipLibCheck`**：TS 7.0 速度提升巨大，很多团队的第一反应是"那我是不是可以不开 `skipLibCheck` 了"。**建议先不开**——`skipLibCheck: false` 会暴露类型库之间的真实冲突，而这些冲突一旦出现很难排查。**先享受速度，再逐步处理类型库冲突。**

**追问：TS 7.0 会有哪些新语言特性？**
→ **7.0 的重点是编译器实现重写，不是语言特性**。新特性会先在 6.x 以 JS 实现落地（这样兼容性风险小），7.0 直接继承。**7.0 引入的新特性主要是"编辑器体验"层面的**——更快的诊断、更准确的类型推断提示。**语言层面的新特性应该关注 6.x 的 minor 版本更新。**

**追问：TypeScript 的未来会不会被 Go 生态的其他工具取代（比如 Go 写的类型检查器）？**
→ 短期内不会。TypeScript 的护城河是**整个 JS/TS 生态的类型定义**（`.d.ts` 有上百万个包）、**IDE 支持**、**工具链集成**——这些和编译器用什么语言写没关系。TS 7.0 用 Go 重写恰恰说明微软认为**这个类型系统值得投入，但需要更好的实现**。

## Q9. `tsc --watch`、增量编译、`--build`（项目引用）有什么区别？

**答：**

**这三个是"让类型检查更快"的三条不同路线：文件级监听、缓存复用、项目图构建。**

| 手段 | 机制 | 适合 | 局限 |
|------|------|------|------|
| **`--watch`** | 监听文件变化，改动时**重新检查受影响部分** | 开发时本地 | ⚠️ **每次都是"重跑整个程序"**，只是省掉了"没变的部分不做类型检查"，大型项目依然慢 |
| **`incremental: true`** | 把上次的**文件哈希 + 类型信息**存进 `.tsbuildinfo`，下次直接复用 | 单项目重复构建 | 跨项目共享不足 |
| **`--build`（项目引用）** | 把一个大项目拆成多个**子项目**，按依赖图**拓扑顺序**构建 | **monorepo** | 需要设计好项目划分 |

### 项目引用（Project References）详解

```jsonc
// 根 tsconfig.json
{
  "files": [],
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/utils" }
  ]
}
```

```jsonc
// packages/core/tsconfig.json
{
  "compilerOptions": {
    "composite": true,      // ⚠️ 项目引用必需：开启增量 + 声明产物
    "outDir": "./dist"
  },
  "include": ["src/**/*"]
}
```

**三个必要条件**：

1. 引用方要写 `references`，被引用方要开 `composite: true`；
2. **跨项目导入必须从被引用项目的 `outDir`（产物目录）导入**，不能直接引源码——因为产物目录里已经有 `.d.ts`，编译器能直接读；
3. 配合 `paths` 映射到产物路径，或者用 `tsc -b` 让 `tsc` 帮你把路径处理好。

**⚠️ 实践中最大的坑**：跨项目导入指向了**源码**而不是**产物**，导致引用方编译时找不到类型，或者两边都被编译两遍（性能反而更差）。

**`composite: true` 还会强制**：

- `declaration` 必须为 `true`（默认就会开）；
- `rootDir` 默认是当前目录；
- 不允许把 `include` 之外的文件 import 进来。

### 怎么选

| 场景 | 选 |
|------|-----|
| 本地开发改几个文件 | **`tsc --watch`**（最简单） |
| 单个项目重复构建 | **`incremental: true`** |
| **monorepo，多个包共享基础类型** | **`--build` + 项目引用** |
| CI | 用 `--build`（能按拓扑序并行构建不同包） |

**追问：Vite 项目需要配这些吗？**
→ **基本不需要**。Vite 走 esbuild 转译（不做类型检查），类型检查由 IDE 的 tsserver 负责增量检查 + CI 的 `tsc --noEmit` 负责。所以 Vite 项目通常只在 `tsconfig.json` 里配好 `moduleResolution: "bundler"`、`isolatedModules`、`verbatimModuleSyntax`，**不需要 `composite`/`references`**。

**追问：为什么 `--watch` 感觉还是很慢？**
→ 因为 TS 的类型检查是**全程序语义分析**——你改一个公共类型，编译器必须重新分析所有依赖它的文件。`--watch` 只跳过了"文件本身没变所以不看它"的优化，但**依赖关系变了就得重算**。这就是 TS 7.0 要解决的核心问题：**真正的增量是"只重算受影响子图"，而不是"跳过没变文件"**。

## Q10. 一个新项目的 `tsconfig.json` 你会怎么配？说一套完整的配置。

**答：**

**直接给一套能用的配置，然后解释每一行的理由——比背字段强。**

### 场景一：前端应用（Vite）

```jsonc
// tsconfig.json
{
  "compilerOptions": {
    // 类型检查
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,

    // 模块与解析
    "module": "esnext",            // TS 6.0+ 默认值，写出来是为了让团队一眼看到
    "moduleResolution": "bundler",  // Vite 用 bundler
    "verbatimModuleSyntax": true,   // 配合 isolatedModules，强制区分 type import
    "isolatedModules": true,        // ⚠️ esbuild 转译的硬性要求
    "resolveJsonModule": true,
    "allowImportingTsExtensions": true,  // 允许 import './x.ts'（Vite 场景）
    "noEmit": true,                 // ⚠️ Vite 不需要 tsc 产出

    // 目标环境
    "target": "es2022",             // TS 6.0 默认是 es2025，看浏览器支持情况定
    "lib": ["es2022", "dom", "dom.iterable"],

    // 辅助
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,

    // 路径别名（需要配 vite 的 resolve.alias 才能真正生效）
    "paths": { "@/*": ["./src/*"] }   // ⚠️ TS 5.0+ 起 paths 不再需要 baseUrl
  },
  "include": ["src", "vite.config.ts"]
}
```

### 场景二：Node 后端服务

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "module": "nodenext",           // 跟随 package.json 的 type
    "moduleResolution": "nodenext",
    "target": "es2022",
    "lib": ["es2023"],
    "types": ["node"],              // ⚠️ TS 6.0 起必须显式声明
    "outDir": "dist",
    "rootDir": "src",
    "sourceMap": true,
    "declaration": false,
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

### 场景三：发布的 npm 库

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "module": "esnext",
    "moduleResolution": "bundler",
    "target": "es2022",
    "lib": ["es2022"],
    "declaration": true,            // 必须：要发 .d.ts
    "declarationMap": true,         // 建议：让使用者能跳源码
    "sourceMap": true,
    "composite": true,              // 建议：支持 --build 增量
    "outDir": "dist",
    "rootDir": "src",
    "stripInternal": true,          // 剔除 @internal 标注的成员
    "types": []                     // 库不需要 Node 全局类型
  },
  "include": ["src"],
  "exclude": ["src/**/*.test.ts"]
}
```

### 几个配置取舍的判断

| 决定 | 我的理由 |
|------|---------|
| **必开 `strict`** | 已经是 TS 6.0+ 的默认，但**显式写出来**——因为它让意图明确，且防止将来关掉 |
| **必开 `noUncheckedIndexedAccess`** | 成本低，防的是"数组越界导致运行时崩溃"这类高频线上 bug |
| **必开 `isolatedModules` + `verbatimModuleSyntax`** | Vite/esbuild 生态的**硬性要求**，也是未来生态的默认方向 |
| **`noUnusedLocals` / `noUnusedParameters`** | ⚠️ **要配 `// eslint-disable` 的场景会变多**，可以先不开，靠 ESLint 管 |
| **`skipLibCheck: true`** | 保持默认。类型库冲突单独排查，不要用开它来掩盖问题 |
| **`baseUrl`** | ⚠️ TS 6.0 已废弃"把 `baseUrl` 当模块查找根"的用法。**TS 5.0+ 的 `paths` 已不需要 `baseUrl`**，直接写相对路径即可；运行时别名交给打包器配 |

### 通用铁律

1. **`tsconfig.json` 要提交到仓库**——它是项目契约；
2. **`tsc --noEmit` 必须是 CI 的必过项**——因为构建工具不做类型检查；
3. **类型检查和构建分开**——别指望 `vite build` 能查出类型错误；
4. **版本升级先升 6.0 清警告，再上 7.0**。

**追问：`paths` 在 `tsconfig` 里配了，为什么运行时还要在 Vite 里再配一遍 `resolve.alias`？**
→ 因为 **`paths` 只影响 TypeScript 编译器，不影响产物运行时**。TS 靠它解析模块，但转译出来的 JS 里还是 `import x from '@/foo'` 这个字面量，运行时需要 Vite/esbuild 自己去解析。两边都得配，**这也是 TS 官方一直在推 `bundler` 模式 + 打包器统一解析的原因**——让 `paths` 的行为和运行时尽量对齐。

**追问：`allowImportingTsExtensions` 是什么？**
→ TS 5.0+ 引入，允许 `import './foo.ts'` 这种**带 `.ts` 扩展名**的导入。它必须配 `noEmit: true` 或 `emitDeclarationOnly: true`（因为 TS 不允许在产出 JS 时保留 `.ts` 扩展名）。**在 Vite/Node ESM 项目里，显式写扩展名是推荐做法**——因为 Node 的 ESM 解析器**要求**显式扩展名，写 `.ts` 反而是最省心的方案（配合 `tsx` / `ts-node`，或 Node 22.18+ / 23.6+ 已默认开启的原生类型剥离）。
