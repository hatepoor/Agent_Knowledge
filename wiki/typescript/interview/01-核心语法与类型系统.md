# 核心语法与类型系统

> **什么时候该读**：面试官问「TypeScript 到底在做什么」「any 和 unknown 有什么区别」「as 和 satisfies 怎么选」「和 Java 有什么本质不同」，答不上来基本就被归到「只会写业务代码」那一档。
> **答题主线**：**TypeScript 的类型只活在编译期**。所有类型技巧（收窄、判别联合、never、readonly）本质都只做一件事——**在编译期把错误挡下来**。抓住这一条，后面每一题都是它的推论。

---

## Q1. TypeScript 到底是什么？它的类型在运行时还存在吗？

**答：**

**TypeScript 是 JavaScript 的超集 + 一套编译期类型系统。类型在编译后全部消失，运行时没有任何类型信息。**

这是所有 TS 面试题的根，必须先说清楚，否则后面全是错的。

| 阶段 | 发生了什么 | 类型信息还在吗 |
|------|-----------|---------------|
| **写代码** | 你写 `.ts` 文件 | 有 |
| **类型检查** | `tsc` 逐行推导、核对类型，报错 | 有，这一步的意义就在这里 |
| **转译（emit）** | 擦掉类型注解，产出 `.js` | **没了** |
| **运行** | Node 执行纯 JS | **没有** |

```ts
interface User {
  name: string;
  age: number;
}

const u: User = { name: 'Ada', age: 36 };
// 转译后：
// const u = { name: 'Ada', age: 36 };
```

所以：

1. **运行时没有 `instanceof User`**——`User` 是纯类型，编译后不存在；
2. **序列化不含类型**——`JSON.stringify` 出来的就是普通对象；
3. **`as` 断言只是骗编译器**，不产生任何运行时检查——它和 Python 的 `typing.cast` 一样，只影响静态分析，运行时该崩还是崩；
4. **类型信息只活在 `.d.ts` 里**——这正是声明文件存在的意义（见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/3-构建工具与包管理|构建工具与包管理]]）。

**一句话总结**：TS 是**编译期检查工具 + JS 超集语法**，不是一门"运行时还有类型"的新语言。

**追问：那 TS 的类型到底保护了什么？**
→ 保护的是**编译期能发现的错误**：打错字段名、把 `string` 传给了要 `number` 的参数、漏处理分支。**它保护不了运行时错误**——外部接口返回的数据结构 TS 管不了，所以边界上还得靠运行时校验（schema 校验 / `unknown` 收窄，见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.4-类型收窄与类型守卫|类型收窄与类型守卫]]）。

**追问：TypeScript 和 Java 比，本质差别在哪？**
→ 三点，面试就答这三条：
1. **都是编译型**：TS 编译到 JS，Java 编译到字节码，**类型检查都在运行时之前完成**；
2. **都是泛型擦除**：TS 运行时没有泛型（`new Box(1)` 里 `Box` 早没了），Java 运行时也擦除成 `Object` + 桥接方法；
3. **类型系统模型不同**：**Java 是名义类型**（nominal typing，看类名和继承关系）；**TS 是结构化类型**（structural typing，看形状）。

## Q2. `any` 和 `unknown` 有什么区别？为什么推荐 `unknown`？

**答：**

**`any` 是「类型系统的逃逸舱」，`unknown` 是「安全的未知」。新代码默认用 `unknown`。**

| 维度 | `any` | `unknown` |
|------|-------|-----------|
| 含义 | **任意类型**，编译器彻底放弃检查 | **任何类型的超集**，但用之前必须先收窄 |
| 赋值给别的类型 | ✅ 可以（`any` 可赋给任何类型） | ❌ 不行，必须先收窄成具体类型 |
| 别的类型赋给它 | ✅ 可以 | ✅ 可以 |
| 调它的方法 | ✅ 不报错（属性随便访问） | ❌ 报错，必须先收窄 |
| 传染性 | ⚠️ **传染**：一个表达式含 `any`，结果也是 `any` | 不传染，收窄后就是具体类型 |

```ts
// any：全放行
declare const a: any;
a.foo.bar.baz();          // ✅ 编译器一句都不报错，运行时可能 TypeError

// unknown：必须先收窄
declare const b: unknown;
b.foo.bar.baz();          // ❌ 编译报错：Object is of type 'unknown'
```

`unknown` 的正确用法是**当作「我还不知道这是什么」来写**，然后用类型守卫逐步缩小：

```ts
function parse(raw: string): unknown {
  return JSON.parse(raw);
}

const data = parse('{"a":1}');
// 直接用会报错，必须先收窄
if (typeof data === 'object' && data !== null && 'a' in data) {
  console.log(data.a);
}
```

**实战结论**：

- 写业务代码时**主动用 `any` 基本等于关掉类型检查**——它会沿着调用链传染，一处 `any` 整条链都瞎；
- 处理**外部不可信数据**（HTTP 响应、JSON、`process.env`、消息队列 payload）时，**入口类型标 `unknown`**，然后收窄到具体类型再往下走；
- `any` 只在两种情况下合理：① 从 JS 老代码迁移过来做过渡（用 `// eslint-disable` 标注）；② 确实要写"任意类型"的通用工具函数。

**追问：`any` 和 `unknown` 的赋值方向分别是什么？**
→ `any` **双向通行**（`any` → 任意类型、任意类型 → `any` 都行）；`unknown` **只能单向进入**（任意类型 → `unknown` 可以，`unknown` → 任意类型不行，除非先收窄）。这正是 `unknown` 安全的原因——它逼你先处理再使用。

**追问：`never` 和 `unknown` 分别站在类型体系的哪一端？**
→ `unknown` 是**顶类型**（top type，一切都是它的子类型）；`never` 是**底类型**（bottom type，它是所有类型的子类型，没有任何值能赋给它）。`any` 则是**在类型图谱里开的一个洞**，不属于这套层级。

## Q3. `as` 断言和 `satisfies` 运算符有什么区别？什么时候用哪个？

**答：**

**一句话：`as` 是「我不管，你说是就是」；`satisfies` 是「你帮我检查，但我保留它本来的类型」。**

| 维度 | `as`（类型断言） | `satisfies`（满足运算符，TS 4.9+） |
|------|----------------|-------------------------------|
| 是否检查 | ❌ **不检查**，编译器直接相信你 | ✅ **检查**，不满足就报错 |
| 结果类型 | 变成你断言的类型 | **保留表达式原本推断出的类型** |
| 用途 | 告诉编译器「这个值其实是这个类型」 | 校验配置对象，同时保留字面量信息 |
| 风险 | 高——可能把 A 断言成完全不相关的 B | 低——不满足直接编译失败 |

```ts
type Mode = 'strict' | 'loose';

// 用 as：mode 的类型是 'strict' | 'loose'（被拓宽了），而且 'xxx' 也编译得过
const a = { mode: 'loose', retries: 3 } as { mode: Mode; retries: number };
//    ^? { mode: Mode; retries: number }
a.mode = 'xxx';        // ❌ 报错，但 'xxx' 一开始就没报错

// 用 satisfies：校验通过，同时 mode 保留字面量类型 'loose'
const b = { mode: 'loose', retries: 3 } satisfies { mode: Mode; retries: number };
//    ^? { mode: 'loose'; retries: number }
```

**什么时候用哪个**：

| 场景 | 用哪个 |
|------|-------|
| 外部数据（`JSON.parse`、`res.json()`）拿到 `any`，你要告诉编译器它的真实形状 | `as` |
| 写配置对象、路由表、状态机，想**校验合法性**又**不想丢字面量类型** | `satisfies` |
| 枚举式数据要窄成联合类型 | `satisfies` |
| 从更宽的类型往更窄的方向"下压" | `as` |

```ts
// satisfies 的经典场景：路由表
const routes = {
  home: '/',
  user: '/user/:id',
} satisfies Record<string, `/${string}`>;
// routes.home 的类型是 '/'（字面量），不是 string
```

**再补一个 `as const`**：它把整个表达式**递归**变成只读字面量类型，是 `satisfies` 的搭档（`as const` + `satisfies` 是 TS 5.0+ 组合拳）。

```ts
const conf = { dir: 'out', level: 3 } as const;
// conf 的类型是 { readonly dir: "out"; readonly level: 3 }
```

**追问：`as` 断言有什么"安全"的写法吗？**
→ 有。TS 规定：**一次 `as` 只能做「类型之间足够重叠」的双向转换**，比如 `string` → `string | number` 合法，`string` → `number` 直接报错（`Conversion of type 'string' to type 'number' may be a mistake`）。所以 `as` 不能随手把字符串断言成数字——这也堵住了"断言当万能后门"的路。

**追问：`satisfies` 是什么时候引入的？**
→ **TypeScript 4.9**（2023 年 5 月）。设计目标是解决「既想校验又不想拓宽类型」这个长期痛点。

## Q4. 联合类型和字面量类型在实际业务里怎么用？什么是判别联合？

**答：**

**联合类型 + 字面量类型 + 一个判别字段 = 判别联合（discriminated union）。这是 TS 里最实用的建模手法**，比 `any` 强一百倍。

```ts
type Result<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

function render(r: Result<string>): string {
  switch (r.status) {
    case 'loading': return '加载中...';
    case 'success': return r.data;          // ✅ 这里 r.data 一定存在
    case 'error':   return r.error.message; // ✅ 这里 r.error 一定存在
  }
}
```

**关键在于 `status` 字段**：它是**判别属性（discriminant）**。编译器通过它收窄联合类型，切到哪个分支就只保留哪个成员——**这不是运行时检查，是编译期的类型流分析（control flow analysis）**。

| 建模方式 | 能表达什么 | 问题 |
|---------|-----------|------|
| `state: 'loading' \| 'success'` + 各自字段 | 状态和字段**独立**，可能拼出不存在的组合 | ❌ 非法状态可表示 |
| `{ status: 'success'; data: T } \| { status: 'error'; error: E }` | 状态和字段**绑定** | ✅ 非法状态无法表示 |

这就是所谓的 **"让非法状态不可表示"**（make illegal states unrepresentable）——TS 类型系统最实用的价值所在。

配套的两个技巧：

1. **字面量类型让 `switch` 能做穷尽检查**（配合 `never`，见 Q5）；
2. **`in` 操作符收窄**也能在没有判别字段时区分联合成员：

```ts
type Cat = { meow(): void };
type Dog = { bark(): void };
function speak(a: Cat | Dog) {
  if ('meow' in a) a.meow();   // ✅ a 被收窄成 Cat
  else a.bark();
}
```

**追问：为什么用 `type` 而不是 `interface` 来定义联合？**
→ 因为 `interface` **无法联合**（`interface A extends B | C` 语法非法，`type A = B | C` 才合法）。联合、交叉（`&`）、条件类型这些高级用法都只能靠 `type`。反过来，`interface` 支持**声明合并**、可以 `extends`，适合描述"对象的形状"；`type` 适合描述"类型的运算结果"。

**追问：`enum` 和字面量联合怎么选？**
→ **新代码优先用字面量联合**：`enum` 会生成真实运行时代码（体积开销、跨模块是 number 而非字符串，容易出 bug），且和字面量类型混用时还会互相干扰。`enum` 的合法场景只剩：需要与外部 C/JS 系统按数值交互、需要反向映射（`E.A → "A"`）、或纯数字常量集合。

## Q5. `never` 类型有什么用？

**答：**

**`never` 是「不可能出现的值」的类型。三个实际用途，按面试价值排序：**

### 1. 穷尽检查（最常用，价值最高）

```ts
type Shape = 'circle' | 'square';

function assertNever(x: never): never {
  throw new Error(`Unexpected value: ${x}`);
}

function area(s: Shape): number {
  switch (s) {
    case 'circle': return 1;
    case 'square': return 2;
    default:      return assertNever(s);
  }
}

// 将来给 Shape 加了 'triangle'，上面 area 立刻编译报错 —— 逼你去处理新分支
```

原理：`assertNever` 的参数类型是 `never`，意味着**传进来的必须是所有可能分支都排除后的剩余集合**。一旦联合类型新增成员，`s` 在 `default` 分支就不再是 `never`，参数类型检查失败。**编译器帮你抓漏。**

### 2. 标记「永不返回」的函数

```ts
function fail(message: string): never {
  throw new Error(message);
}

function parse(input: string): number {
  if (!input) fail('empty');   // ✅ 编译器知道这行之后 input 一定非空
  return Number(input);
}
```

`never` 返回值让编译器知道：**这条路径一定抛异常**，后面不用再考虑 `input` 为空的情况。

### 3. 空数组的正确类型

```ts
const arr: never[] = [];        // ✅ 正确：暂时没元素，未来 push 具体类型
const bad: string[] = [];       // ⚠️ 陷阱：推断了 never[]，push('a') 会报错
```

**追问：`never` 的类型地位是什么？**
→ **底类型（bottom type）**：它是**所有类型的子类型**。所以任何值都能赋给 `never`（但没有实际值满足），`never` 却不能赋给任何其他类型（除了 `unknown` 和 `any`）。这跟 `unknown`（顶类型）正好是一对。

**追问：函数返回类型写 `void` 和 `never` 有什么区别？**
→ `void` 表示「**返回值没意义**」（调用方别用返回值）；`never` 表示「**这个函数不会正常返回**」（一定抛异常或死循环）。`never` 是 `void` 的子类型。写 `void` 的函数实际上可能返回 `undefined`，写 `never` 的函数则**不可能返回任何值**。

## Q6. 可选链 `?.` 和空值合并 `??` 的区别？什么时候必须用？

**答：**

**`?.` 解决"中间可能是 null 就短路"，`??` 解决"null/undefined 才用兜底值"。关键区别：`??` 只对 `null`/`undefined` 生效，`||` 对所有 falsy 值生效。**

```ts
const port = config.port ?? 3000;   // ✅ 只有 null/undefined 才兜底
const count = config.count || 1;     // ⚠️ count=0 时也变成 1（陷阱）
```

| 表达式 | `null` | `undefined` | `0` | `''` | `false` | `NaN` |
|-------|-------|-------------|-----|------|---------|-------|
| `a ?? b` | → b | → b | → a | → a | → a | → a |
| `a \|\| b` | → b | → b | → b | → b | → b | → b |

**`?.` 的短路行为**：左侧一旦是 `null`/`undefined`，**整条表达式链直接返回 `undefined`，后面的代码根本不执行**（不是逐个判空）。

```ts
const name = user?.profile?.name;         // 中间任一环为 null → undefined
const len = user?.name.length;             // ⚠️ name 为 null 时不短路！因为 ?. 只保护紧邻的那一层
```

上面第二行是经典陷阱：`user?.` 只在 `user` 为 null 时短路；`user` 不为 null 但 `user.name` 为 undefined 时，`user?.name.length` 依然报错。正确写法是 `user?.name?.length`。

**三条硬规则**：

1. **`??` 不能和 `||`/`&&` 混用而不加括号**——ES2020 语法错误，TS 也会报错；
2. **`?.` 不能用在赋值左侧**：`a?.b = 1` 非法（可选链不能作为赋值目标）；
3. **`?.` 后面不能直接跟模板字符串里的可选调用**，但 `obj.method?.()` 这种可选调用是合法的（方法不存在时不报错，返回 `undefined`）。

**追问：`??` 和 `||` 到底该用哪个？**
→ **默认用 `??`**。`||` 只在你**明确**想让 `0`/`''`/`false` 也走兜底分支时才用。实践中 `||` 写 `port || 3000` 是高频 bug 源：配置里 `port: 0` 表示"随机端口"，结果被改成 3000。

**追问：可选链能不能替代 `try/catch`？**
→ 不能，两者解决完全不同的问题。可选链处理的是**"这条链上某个环节是空的"**；`try/catch` 处理的是"**某个操作抛异常**"。`user?.profile.name` 在 `profile` 为 null 时会短路返回 undefined，但如果 `profile` 是 `{ name: undefined }`，`?.` 不救你——**空值和"字段不存在"是两回事**。

## Q7. TypeScript 是结构化类型还是名义类型？和 Java 有什么本质不同？

**答：**

**TS 是结构化类型（structural typing）：看形状，不看名字。Java 是名义类型（nominal typing）：看身份，看继承关系。**

这是 TS 最容易被误解、也最能区分候选人的一题。

```ts
// TS：形状一样就兼容，与名字无关
interface Dog { bark(): void }
interface Cat { meow(): void }

function pet(animal: Dog) {}
const myCat: Cat = { meow() {} };
pet(myCat);        // ❌ 报错：缺 bark()，形状不匹配

// 但换个形状就完全兼容，哪怕完全不同的名字
function setFlag(flag: { enabled: boolean }) {}
setFlag({ enabled: true });   // ✅ 字面量对象结构匹配即可
```

**结论**：TS 里「接口名」只是**给人看的标签**，编译器只比对**属性和方法签名**。

Java 的对比：

| 维度 | TypeScript | Java |
|------|-----------|------|
| 类型模型 | **结构化**（形状匹配） | **名义**（名字 + 继承链） |
| 能否把不相关的类互相赋值 | ✅ 可以（只要形状一样） | ❌ 不行，必须有继承/接口关系 |
| 怎么表达"名义"需求 | 靠**品牌（brand）**手动模拟 | 原生支持 |
| 运行时类型 | ❌ 编译后不存在 | ✅ 字节码里有完整运行时类型信息 |

**TS 里怎么模拟名义类型？** 用 `unique symbol` 做品牌：

```ts
declare const userIdBrand: unique symbol;   // 只能通过 declare 声明，不能有真实值
type UserId = string & { readonly [userIdBrand]: true };

type OrderId = string & { readonly [userIdBrand]: true };  // 同一 brand，其实相等
// 若想区分，需要不同的 brand 常量

declare function createUserId(id: string): UserId;
declare function createOrderId(id: string): OrderId;

const uid = createUserId('1');
const oid = createOrderId('1');
// uid 和 oid 类型不兼容，字符串不能直接互传 —— 名义类型效果
```

**关键判断**：**TS 的结构化类型是"默认宽进"**，而 Java 的名义类型是"默认严进"。TS 的灵活是双刃剑——好处是适配 JS 生态（第三方对象只要形状对就能用），代价是**两个语义完全不同的对象会被误认为可互换**。

**追问：TS 的结构化类型会带来什么实际困扰？**
→ 典型是**"两个只有同名同形状字段但语义完全不同的对象被混用"**，比如 `UserId` 和 `AccountId` 都是 string。更麻烦的是 TS 报错信息只说"缺少属性"，不解释语义差异。解决办法就是用品牌类型给关键 ID 加一道"名义锁"，这是 TS 社区的标准实践。

**追问：Java 能不能做到结构化类型的效果？**
→ 不能直接做到。Java 可以用接口（interface）作为"结构契约"来近似，但一旦实现就必须 `implements` 显式声明，**不会因为你形状刚好匹配就自动兼容**。这本质上是两种设计哲学：Java 强调**显式契约**，TS 强调**隐式形状**。

## Q8. `readonly` 到底保证了什么？为什么它挡不住数组被改？

**答：**

**`readonly` 只冻结「属性本身不可重新赋值」，不冻结「属性指向的那个对象」。它是浅层的（shallow）。**

```ts
interface Config {
  readonly name: string;
  readonly tags: string[];
}

const c: Config = { name: 'app', tags: [] };
c.name = 'other';        // ❌ 编译报错：Cannot assign to 'name' because it is a read-only property
c.tags.push('a');        // ✅ 编译通过！readonly 不管数组内部
c.tags = ['x'];          // ❌ 报错（这才是 readonly 管的事）
```

原因很直白：`readonly` 只是给**这个属性槽位**加了个不可重写的标记，而 `tags` 指向的数组对象本身完全没变——你改的是数组**内容**，不是属性**指向**。

**三种深度方案**：

```ts
interface Config {
  readonly tags: readonly string[];              // 方案1：属性只读 + 数组元素只读
}

const c2 = { tags: ['a'] } as const;              // 方案2：as const 递归只读
// c2.tags 的类型是 readonly ["a"]

type DeepReadonly<T> =                        // 方案3：递归深度只读（要手写，TS 没有内置）
  T extends (infer U)[] ? readonly DeepReadonly<U>[] :
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;
```

**这个"浅层性"是高频面试陷阱**，因为很多人以为 `readonly` = 不可变。

**但也要说清另一面**：`readonly` 的**浅层性在实践中往往够用**，而且成本低。所以真实建议是：

- 表达"我不打算改这个引用"→ 用 `readonly`（如函数参数、配置对象）；
- 表达"这个东西真的深度不可变"→ 用 `as const` 或手写 `DeepReadonly`；
- **别指望 `readonly` 当运行时保护**——它编译后完全消失，外部 JS 照样能改（`readonly` 是**编译期**约束，不是运行时冻结）。

**追问：`readonly` 和 `Object.freeze` 有什么区别？**
→ `readonly` 是**编译期**的类型约束，运行时不存在，JS 代码或 `as any` 照样能改；`Object.freeze` 是**运行时**真正冻结对象（但只冻结一层，且冻结后 `Object.freeze` 也只是"软约定"——严格模式下写会抛错，非严格模式静默失败）。两者可以叠加：类型标 `readonly`，运行时再 `Object.freeze`。

**追问：`readonly` 数组上能用 `push` 吗？**
→ 不能。`readonly string[]` 的类型里根本没有 `push`/`pop`/`splice` 这些可变方法，只有 `map`/`filter`/`slice` 等不改变原数组的方法。要修改就用 `slice`/`concat`/`toSorted` 返回新数组，而不是绕过类型。

## Q9. 索引签名（index signature）是什么？什么时候用？和 `Record` 什么关系？

**答：**

**索引签名用来描述「一个对象的键名不确定，但我知道所有键对应的值是同一类型」。**

```ts
interface UserMap {
  [key: string]: number;    // 任意 string 键，值是 number
}

const scores: UserMap = { alice: 100, bob: 90 };   // ✅
scores.carol = 95;                                  // ✅
const wrong: UserMap = { alice: '100' };            // ❌ 值类型不匹配
```

**两条关键限制**：

1. **命名属性必须符合索引签名的值类型**——如果一个对象既有索引签名又有具名字段，具名字段的类型必须是索引签名值类型的子类型，否则报错；
2. **数值索引签名是字符串索引签名的子类型**——可以同时写 `string` 和 `number` 两个索引，但 `number` 的值类型必须是 `string` 那个的子类型。

```ts
interface Dict {
  [key: string]: string | number;
  [key: number]: number;      // ✅ number 是 string 的子类型
  name: string;               // ✅ string ⊆ string | number
}
```

**内置工具类型 `Record` 就是索引签名的语法糖**：

```ts
type Record<K extends keyof any, T> = { [P in K]: T };
// 等价于手写 { [key: string]: T }，但键名可以是字面量联合
type Status = 'active' | 'closed';
type StatusMap = Record<Status, number>;
// 展开成 { active: number; closed: number }
```

`Record<K, T>` 的优势是**键可以是有限集合**——手写索引签名写不出"只有这三个键"的效果。

**什么时候用索引签名**：

| 场景 | 用什么 |
|------|-------|
| 键名完全不确定（字典、缓存、`process.env`） | 索引签名 |
| 键名是有限字面量集合 | `Record<K, T>` 或映射类型 |
| 对象形状已知且固定 | **普通 interface**（有索引签名 = 任何多余属性都合法，等于放弃了一部分检查） |

**⚠️ 陷阱**：给 interface 加了索引签名后，**多写一个属性编译器不会报错**——这会让 typo 逃过检查。所以「键名不确定」才用索引签名。

**追问：`Record<string, T>` 和 `{ [k: string]: T }` 有什么区别？**
→ 结构上等价，但 `Record` 支持**有限键联合**（`Record<'a'|'b', T>`），也能直接配合 `Exclude`/`Pick`/`Partial` 等工具类型使用，可读性更好。**手写索引签名时优先考虑 `Record`。**

**追问：怎么让索引签名的值可空？**
→ 写成 `[key: string]: T | undefined`。但更严谨的做法是开启 **`noUncheckedIndexedAccess`**（TS 4.1+），开启后所有索引访问自动返回 `T | undefined`，**不需要手写 `| undefined`**——这是 TS 4.1 给"字典类数据"的标准解法。

## Q10. TypeScript 的类型系统相比 Java，弱在哪、强在哪？

**答：**

**TS 强在"表达力与工程效率"，弱在"运行时安全与逃逸口子"。这是 TS 面试最后一题的通配回答。**

| 维度 | TypeScript | Java |
|------|-----------|------|
| 编译模型 | 编译到 JS，Node/浏览器执行 | 编译到字节码，JVM 执行 |
| 泛型 | 运行时**擦除** | 运行时**擦除** |
| 类型检查时机 | **编译期**（`tsc` / IDE / CI） | **编译期**（`javac`） |
| 类型系统模型 | **结构化**（形状匹配） | **名义**（名字 + 继承） |
| 空安全 | `strictNullChecks`（TS 2.0）可开 | 无内建（需注解库/框架） |
| `any` 逃逸 | ⚠️ **有**，且沿调用链传染 | ⚠️ 有 `Object` / 原始类型，但受系统约束；泛型未检查操作会告警 |
| 运行时类型信息 | ❌ **完全没有** | ✅ 完整保留（反射、`instanceof`、`getClass()`） |
| 逃逸方式 | `as any`、JS 文件、`@ts-ignore` | `Object` + 强转 + 原始类型 |

**TS 的四个主要安全缺口**：

1. **`any` 传染**——一个 `any` 让整条表达式链失去检查（Q2）；
2. **`as` 断言**——可以断言成任何"看起来相关"的类型，编译器不再验证；
3. **结构化类型的隐式兼容**——形状相同的不同语义对象被混用（Q7）；
4. **运行时无类型**——外部数据、网络响应、JSON 进来就是脏的，TS 完全管不了。

**对应 Java 的对比**：Java 里 `List<String> l = new ArrayList<>();` 类型信息保留在字节码里，`l.get(0)` 有运行时检查；TS 里 `string[]` 转译后就是普通数组，`arr.get?.(0)` 是纯 JS 语义。

**我的结论**（面试时这么讲）：

> **TS 不是 Java 的替代品，是"在弱类型语言上加一层可选的编译期保险"**。它的价值 90% 来自 IDE 提示、重构安全、编译期挡错；代价是**你必须严格守住边界**（`unknown` 收窄、避免 `any`、开 `strict`）。
>
> Java 的类型安全是**运行时兜底**（编译过了运行时还能再挡一次）；TS 的类型安全是**编译期一次性的**（转译后 JS 没有任何防线）。所以 TS 项目必须补上运行时校验（Zod / JSON Schema）才算闭环。

**追问：那 TS 和 Python 比呢？**
→ Python 是**运行时**类型（`int`/`str` 是标签，不做检查，类型错误运行时才炸），TS 是**编译期**类型。Python 走 `typing` / `mypy` 可以获得类似 TS 的体验，但那是**额外工具链**，不是语言本身。详细逐项对照见 [[typescript/01-入门阶段-基础教程/第00章-学前准备/0.3-TypeScript与Python的差异|TypeScript 与 Python 的差异]]。

**追问：为什么 TS 敢做"擦除泛型"这种不安全的事？**
→ 因为 TS 的定位是**"渐进式类型化的 JavaScript"**：它必须 100% 兼容现有 JS 代码，任何运行时改动都会破坏兼容性。泛型擦除是这个约束下的必然结果——**放弃运行时校验，换取零运行时开销和完全兼容 JS**。Java 之所以能保留运行时泛型信息，是因为 JVM 提供了运行时类型系统。
