# 构建工具与包管理

> **什么时候该读**：你要把一个 TS 项目跑起来（`npx tsx src/index.ts`），或者要发一个自己的 npm 包；或者你发现 `npm install` 特别慢、`node_modules` 特别大、别人的依赖「明明没装却能 import」。
> **阅读门槛**：需要理解「`tsc` 只转译不打包」这件事（见第 1 篇 [[typescript/02-中段阶段-专题精讲/工程化与工具链/1-编译流程与tsconfig]] 第一节），以及 ESM / CJS 两套模块系统（见第 2 篇 [[typescript/02-中段阶段-专题精讲/工程化与工具链/2-模块系统ESM与CommonJS]]）。

## 学习目标

读完本篇，你应当能够：

1. 在 npm / pnpm / yarn / bun 之间做出选择，并说出各自的核心差异
2. 解释 `node_modules` 的**扁平化**结构带来了什么问题，pnpm 用**符号链接**怎么解决
3. 画出「编译器 / 转译器 / 打包器 / 开发服务器」的谱系，说清每个工具**做不做类型检查**
4. 用 `tsx` 直接跑 TS 文件，并说清它**为什么不检查类型**
5. 为一个没有类型标注的 JS 库写 `.d.ts` 声明文件，说清 `@types/*` 是什么
6. 把一个 TS 库发布到 npm：正确配置 `main` / `module` / `types` / `exports` / `files`，并避免 dual package 陷阱
7. 排查三个高频坑：import 路径缺 `.js`、`skipLibCheck` 掩盖冲突、`esModuleInterop` 没开

## 一、包管理器：npm / pnpm / yarn / bun

**包管理器**（package manager）就是帮你装依赖的工具：读 `package.json` 里的依赖声明，把包下载到本地、维护依赖树、生成 lockfile。

### 1.1 对比表

| 工具 | 定位 | 核心特点 | 依赖布局 |
|---|---|---|---|
| **npm** | Node 自带（随 Node.js 安装） | 最稳、文档最多、生态默认 | 扁平化 `node_modules` |
| **pnpm** | ⭐ 社区新宠 | ⭐ **硬链接省空间** + ⭐ **严格依赖隔离** | 符号链接 + 内容寻址 store |
| **yarn**（Berry，v2+） | 经典工具的新一代 | ⭐ **PnP**（Plug'n'Play）——不装 `node_modules`，零磁盘占用 | `.pnp.cjs` 虚拟映射 |
| **bun** | 新生代一体化工具 | ⭐ **极快**（安装/运行/打包都很快），自带 JS 运行时 | 扁平化 + 全局缓存 |

### 1.2 各自的招牌

**npm**：随 Node.js 一起装，命令是 `npm install`。生态里默认的选项，CI 镜像、教程、`.npmrc` 配置兼容性最好。

**pnpm**：⭐ 两个核心设计——

- **硬链接**：所有包从全局 **store**（内容寻址存储区，通常在用户目录）里**硬链接**到 `node_modules`。同一个包被 10 个项目依赖，磁盘上只存一份。
- **严格依赖隔离**：你在 `package.json` 里**没声明**的包，代码里**根本 import 不到**（报错形如 `Cannot find module 'xxx'`，或 pnpm 的 `ERR_PNPM_...` 类提示）。这叫**幽灵依赖**（phantom dependency）被消灭了。

**yarn Berry（v2+）**：⭐ **PnP** 是个激进的方案——**根本不创建 `node_modules` 目录**，而是用一个 `.pnp.cjs` 描述「哪个包依赖哪个包」，由运行时（Node 的 loader 钩子）按需解析。零磁盘占用、零安装时间，代价是：**所有工具都必须支持 PnP**，否则兼容性坑不少。

**bun**：⭐ 快是它的全部卖点——`bun install` 比 npm 快 10 倍以上，另有 `bun run`、`bun build`、`bun test`，还能当 Node 运行时（`bun run server.ts` 直接跑 TS）。

### 1.3 ⚠️ 不要混用

⚠️ **同一个项目里只能用一个包管理器。** 混用的具体后果：

| 混用方式 | 后果 |
|---|---|
| `npm install` 和 `pnpm install` 交替跑 | `node_modules` 结构被反复重建，pnpm 的符号链接布局被 npm 覆盖，依赖解析结果不稳定 |
| 提交了 `package-lock.json` 又提交 `pnpm-lock.yaml` | CI 上「用哪个锁文件」不确定，**装的依赖版本可能和本地不一致** |
| `yarn` 装完再用 `npm ci` | 同样问题 |

⭐ **规矩**：项目里**存在哪个 lockfile 就用哪个包管理器**，删掉不需要的那个。判断方法：看仓库根目录有没有 `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` / `bun.lockb`。

### 1.4 lockfile 是什么

**lockfile**（锁文件）是包管理器生成的、记录**每个依赖的确切版本和完整性哈希**的文件。

| 文件 | 属于 |
|---|---|
| `package-lock.json` | npm |
| `pnpm-lock.yaml` | pnpm |
| `yarn.lock` | yarn |
| `bun.lockb`（二进制）/ `bun.lock` | bun |

它的作用：保证**任何人、任何机器、任何时间**装出来的依赖树完全一致。⚠️ CI 里应该用 `npm ci`（而不是 `npm install`）——`ci` 严格按 lockfile 装，不改 lockfile，装不上就报错。

### 1.5 对照 Python

| | Node | Python |
|---|---|---|
| 包管理 | npm / pnpm / yarn / bun | pip / uv / poetry / pdm |
| 依赖声明 | `package.json` 的 `dependencies` | `pyproject.toml` 的 `[project].dependencies` |
| 锁定 | lockfile（npm/pnpm/yarn） | `requirements.txt` / `uv.lock` / `poetry.lock` |
| 隔离机制 | `node_modules` 目录 / pnpm 符号链接 / PnP | **虚拟环境**（venv / `.venv`） |

⭐ **最大的结构差异**：Python 用**虚拟环境**隔离不同项目的依赖（每个项目一个独立的 `site-packages`）；Node 早期用**目录**隔离（每个项目一个 `node_modules`）。而 npm 的扁平化让**同一个项目的所有依赖平铺在一个目录里**——这就引出了下一节的问题。

## 二、`node_modules` 扁平化 vs 嵌套，以及 pnpm 的方案

### 2.1 npm 的扁平化（flattening）

npm 3 之后不再把每个依赖装进自己的嵌套目录，而是**尽量平铺**到 `node_modules` 根下：

```text
node_modules/
├── express/          ← 你直接声明的
├── body-parser/      ← express 的依赖，被提升到根
├── cookie/           ← body-parser 的依赖，也被提升到根
└── ...               ← 冲突时才会出现嵌套
```

只有**同名冲突**时才会嵌套：

```text
node_modules/
├── express/
│   └── node_modules/
│       └── some-pkg/   ← 版本和根上的不同，只能嵌套
└── some-pkg/           ← 根上的版本
```

**为什么这么做？** 因为扁平化后目录层级浅，**Node 的模块查找快**（`require` 从当前目录逐级上溯 `node_modules`，扁平结构下大多一两跳就命中）。

### 2.2 ⚠️ 扁平化带来的两个问题

**问题一：幽灵依赖（phantom dependency）**

```ts
// package.json 里只声明了 express，没声明 body-parser
import bodyParser from "body-parser";  // ⚠️ 本地能跑！
```

因为 `body-parser` 被提升到了 `node_modules` 根目录，Node 照样能找到它。这就是**幽灵依赖**——**你用了没声明的依赖**。

⚠️ **为什么这是隐患？** 因为它只在「依赖树恰好长成那样」时成立。一旦：
- 依赖方升级了、把它挪进嵌套目录 → 你的代码**突然崩**；
- 你把 `body-parser` 加进 `dependencies` → 装了**两个版本**，行为不一致；
- 别人 clone 你的仓库（lockfile 不同）→ 装出不同的树。

**问题二：磁盘空间浪费**

同样的包被多个项目依赖时，每个项目都存一份完整副本。100 个项目、每个项目 200MB `node_modules` → 20GB。

### 2.3 ⭐ pnpm 的符号链接方案

pnpm 的做法是**内容寻址存储 + 硬链接 + 符号链接**：

```text
node_modules/
├── .pnpm/                      ← 虚拟 store：按 "包名@版本" 精确寻址，每个版本只存一份
│   ├── body-parser@1.20.2/
│   ├── express@4.19.2/
│   │   └── node_modules/
│   │       ├── body-parser -> ../../body-parser@1.20.2
│   │       └── express -> ../express@4.19.2/node_modules/express
│   └── ...
├── express -> .pnpm/express@4.19.2/node_modules/express     ← 顶层只放你声明的
└── body-parser -> .pnpm/body-parser@1.20.2/node_modules/body-parser
```

三个要点：

1. **顶层 `node_modules` 里只有你在 `package.json` 声明的包** → ⭐ **幽灵依赖直接消失**：想 import 一个没声明的包？报错，逼你补声明。
2. **每个包的 `node_modules` 里只有它自己声明的依赖** → 依赖隔离彻底。
3. **硬链接** → 所有项目的同一版本指向同一份磁盘数据 → ⭐ **省空间**。

```bash
pnpm add express        # 装依赖
pnpm add -D typescript  # 装开发依赖
pnpm remove lodash
pnpm install            # 按 lockfile 装全量
```

⭐ **pnpm 顺手还禁掉了幽灵依赖**，这是它相对 npm 最大的工程价值——很多团队的「依赖必须显式声明」规范，靠 pnpm 是**强制**的，靠 npm 只是**约定**的。

## 三、构建工具谱系

这一节是本篇的核心。先分清四个概念：

| 概念 | 干什么 | 代表 |
|---|---|---|
| **编译器**（compiler） | 类型检查 + 转译，产出 JS | `tsc` |
| **转译器**（transpiler） | 只转译，**不查类型** | `esbuild`、`swc`、`babel` |
| **打包器**（bundler） | 把多个模块打成一个或几个文件 | `rollup`、`webpack`、`vite`(build) |
| **开发服务器**（dev server） | 起本地服务、热更新、按需编译 | `vite`(dev) |

### 3.1 谱系表

| 工具 | 定位 | 特点 |
|---|---|---|
| `tsc` | 编译器 | 只转译不打包，类型检查权威 |
| `esbuild` | 单文件转译器 | 极快，**只转译不检查类型** |
| `vite` | 开发服务器 + 构建 | dev 用 esbuild、build 用 rollup，⭐ 前端主流 |
| `tsup` | 库打包 | 基于 esbuild，产物干净 |
| `webpack` | 传统打包 | 生态老、配置复杂 |

### 3.2 `tsc`：类型检查的权威

```bash
npx tsc --noEmit          # 只检查
npx tsc                   # 检查 + 转译（不打包）
```

- ⭐ **唯一能做权威类型检查的工具**。别的工具（esbuild、swc）为了速度**直接跳过**类型检查。
- ⚠️ **不打包**：`import "./utils"` 编译成 `import "./utils"`，产物里还是一个模块一个文件。
- 慢：大型项目全量 `tsc` 可能要几十秒。

### 3.3 `esbuild`：极快的转译器

**esbuild** 是用 Go 写的转译器，**快一个数量级**（比 tsc 快 10–50 倍）。

```bash
npx esbuild src/index.ts --bundle --outfile=dist/index.js --platform=node
```

- ⭐ **只转译，不检查类型**。类型写错了它照样给你产出能跑的 JS——**错误被静默吞掉**。
- ⚠️ 这是它最大的价值也是最大的坑：**用它当唯一的类型防线 = 放弃类型系统**。

### 3.4 `vite`：前端主流

**Vite** 是现在前端的事实标准工具，架构上是「两种模式」：

| 模式 | 用什么 | 行为 |
|---|---|---|
| **dev**（开发） | **esbuild** | 按需编译：启动快，改哪个文件只重编哪个（HMR，热替换） |
| **build**（生产构建） | **rollup** | 打包 + 压缩 + tree shaking（摇树），产出静态资源 |

```bash
npx vite            # 起开发服务器
npx vite build      # 生产构建
npx vite preview    # 本地预览构建产物
```

⚠️ **Vite 也不做类型检查**（dev 和 build 都不做）。所以标准做法是：

```bash
npx tsc --noEmit && npx vite build
```

**类型检查单独跑一遍，打包交给 Vite。**

### 3.5 `tsup`：库打包

**tsup** 是基于 esbuild 的**库打包工具**（给你要发布的 npm 包用），特点是**开箱即用、产物干净**：

```bash
npx tsup src/index.ts --format esm,cjs --dts
```

一条命令同时产出：

```text
dist/
├── index.js       # ESM 产物
├── index.cjs      # CJS 产物
└── index.d.ts     # 类型声明（--dts 让它调 tsc 生成）
```

⭐ **`--dts` 是关键**：tsup 借助 `rollup-plugin-dts`（或 `api-extractor`）生成声明文件，你不用额外跑一遍 `tsc`。

### 3.6 `webpack`：传统打包器

**webpack** 是老牌打包器，生态最大（loader / plugin 体系），但：

- ⚠️ **配置复杂**（webpack.config.js 动辄上百行）；
- 冷启动慢、增量构建也慢；
- 现在新项目基本不选了，**但存量项目里到处都是它**——学会读懂 webpack 配置仍然有用。

⚠️ **Vite 不是 webpack 的替代品在所有场景**：需要处理非常特殊的资源管线、或者团队里 webpack 插件生态是刚需时，webpack 仍合理。

### 3.7 选择建议

| 场景 | 选什么 |
|---|---|
| 前端应用 | ⭐ **Vite**（+ 单独 `tsc --noEmit`） |
| Node 后端服务 | `tsx` 跑开发 / `tsc` 或 `tsup` 出构建产物 |
| 发布 npm 库 | ⭐ **tsup**（或 `tsc` 双份 + 手写 `exports`） |
| 只想要类型检查 | `tsc --noEmit` |
| 极简脚本 | `bun run xxx.ts` |

## 四、`tsx`：直接跑 TS 文件

### 4.1 用法

```bash
npx tsx src/index.ts
```

或者在 `package.json` 里挂脚本：

```json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "start": "tsx src/index.ts"
  }
}
```

**`tsx`** 是一个 CLI 工具：底层用 **esbuild** 把你的 TS 文件在内存里转译成 JS，然后交给 Node 执行。

### 4.2 ⚠️ 它不检查类型

```ts
// src/broken.ts
const x: number = "hello";   // ⛔ 类型错误
console.log(x);
```

```bash
$ npx tsx src/broken.ts
hello        # ⚠️ 照跑不误！esbuild 不检查类型
```

⭐ **这是本节最该记住的一句话**：`tsx` **只转译，不检查类型**。

所以标准的工作流是**两件事分开做**：

```bash
# 开发时：tsx 跑得快，但类型检查交给编辑器
npx tsx src/index.ts

# 提交前 / CI 里：必须单独跑一遍类型检查
npx tsc --noEmit
```

⚠️ **只靠 `tsx` 开发 = 类型系统形同虚设**。编辑器（VS Code 的 TS 语言服务）会实时标红，但**编辑器不标红 ≠ 代码没错**——尤其是类型体操深、条件分支多的时候。

### 4.3 `tsx` vs `ts-node` vs Node 原生

| 方案 | 原理 | 类型检查 | 速度 |
|---|---|---|---|
| `tsx` | esbuild 转译 | ⛔ 否 | 快 |
| `ts-node` | 用 tsc 的 API 逐文件转译 | ✅ 可以开（但慢） | 慢 |
| `node --experimental-strip-types`（Node 22.6+） | Node 内置的**类型擦除**（不是转译） | ⛔ 否 | 最快 |

⭐ **Node 原生的类型擦除**（type stripping）：Node 22.6 起提供 `--experimental-strip-types`，Node 23.6+ 默认开启。它只做「把类型删掉」这一件事，**不支持**枚举、`namespace`、参数属性等需要**代码生成**的语法（因为它不改代码，只删类型）。优点是零依赖、启动最快。

### 4.4 `tsx watch`

```bash
npx tsx watch src/index.ts
```

文件一改就自动重启进程。等价于 `nodemon --exec tsx`，适合后端开发。

⚠️ 注意 `tsx watch` 是**整个进程重启**，不像 Vite 那样做热替换（热替换，HMR）——后端有连接状态，重启更安全。

## 五、声明文件 `.d.ts` 与 `@types/*`

### 5.1 为什么需要 `.d.ts`

**声明文件**（declaration file，`.d.ts`）只包含**类型信息**、不包含实现。作用是：**告诉 TypeScript「这个库长什么样」**。

两种来源：

1. **库作者自己写**（发布时用 `declaration: true` 自动生成，见第 1 篇第五节）；
2. **社区补写**（库作者没写时，别人补一份）。

### 5.2 `declare module "xxx"`：为整个包补声明

假设你用了某个没有类型的 JS 库 `legacy-utils`：

```ts
// src/types/legacy-utils.d.ts
declare module "legacy-utils" {
  export function parse(input: string): Record<string, unknown>;
  export function format(value: unknown): string;
  export const version: string;
}
```

放进项目里（记得让 `include` 覆盖到它），就能：

```ts
import { parse } from "legacy-utils";
const obj = parse("a=1");   // ✅ 类型是 Record<string, unknown>
```

⭐ `declare module "包名"` 的含义是：「**这个包我没读过源码，但我告诉你它导出什么**」。

### 5.3 `declare module "*.css"`：给非 TS 资源补声明

```ts
// src/types/assets.d.ts
declare module "*.css" {
  const content: { [className: string]: string };
  export default content;
}

declare module "*.svg" {
  const url: string;
  export default url;
}
```

⚠️ 没有这段声明，`import "./style.css"` 会报 `Cannot find module './style.css'`。

### 5.4 `@types/*`：DefinitelyTyped

**`@types/*`** 是「**类型声明包**」的命名空间约定。

**DefinitelyTyped** 是维护第三方库类型声明的开源社区。它的产出方式是：

```text
@types/express      ← express 的类型声明
@types/node         ← Node.js 的类型声明
@types/lodash       ← lodash 的类型声明
```

⭐ **`@types/<包名>` 对应 `<包名>`**：安装 `@types/express` 就是给 `express` 补类型。这些包**只含 `.d.ts`，不含任何运行时代码**（所以很轻）。

安装方式：

```bash
npm i -D @types/node @types/express
```

⚠️ **TS 6.0 起的坑**：`types` 默认为 `[]`，`@types/node` **不再自动引入**（见第 1 篇第六节）。症状是满屏 `Cannot find name 'process'`。解法是显式配 `"types": ["node"]`。

### 5.5 怎么判断一个包要不要装 `@types`

| 情况 | 要装 `@types/*` 吗 |
|---|---|
| 包是纯 JS，作者没写类型 | ✅ 要 |
| 包自带类型（`types` / `exports.types` 字段） | ❌ 不用 |
| 包是 `@scope/name` 形式 | ✅ 要装 `@types/scope__name`（**斜杠换成双下划线**） |

⚠️ **`@types` 命名规则的坑**：`@types/react-router` → 包名 `@react-router/dom`；`@types/babel__core` → 包名 `@babel/core`。规则是：**scope 里的 `@` 保留，斜杠换成 `__`**。

### 5.6 `skipLibCheck` 与类型冲突

```json
{
  "compilerOptions": {
    "skipLibCheck": true
  }
}
```

⚠️ **它的双刃性**：

- ✅ **好处**：不检查 `node_modules` 里 `.d.ts` 内部的自洽性，类型检查快 2–3 倍。
- ⚠️ **坏处**：**两个第三方库之间的类型冲突被你看不见**。

典型场景：`@types/express` 和 `@types/express-serve-static-core` 版本不匹配 → 它们内部声明打架 → 开 `skipLibCheck` 后那条报错消失了，但**用到冲突 API 时你依然会收到一条看不懂的报错**。

⭐ **判断方法**：遇到某条报错信息里出现一串 `.d.ts` 路径，先临时把 `skipLibCheck` 关掉跑一次，看看是不是第三方库内部冲突。如果是，解决办法是**对齐版本**（升级/降级到互相兼容的版本），而不是永久关掉 `skipLibCheck`。

## 六、发布一个 TS 库

这是本篇的落地环节。假设你写了个库 `my-utils`。

### 6.1 `package.json` 关键字段

```json
{
  "name": "my-utils",
  "version": "1.0.0",
  "description": "一些好用的工具函数",
  "type": "module",
  "main": "./dist/index.cjs",
  "module": "./dist/index.js",
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    },
    "./package.json": "./package.json"
  },
  "files": ["dist"],
  "sideEffects": false,
  "scripts": {
    "build": "tsup src/index.ts --format esm,cjs --dts --clean",
    "typecheck": "tsc --noEmit"
  }
}
```

| 字段 | 作用 | ⚠️ 注意 |
|---|---|---|
| `main` | 老式 CJS 入口 | 给老工具（老 Node、webpack 4）看 |
| `module` | 老式 ESM 入口 | 非标准约定，但 bundler 都认 |
| `types` | 类型声明入口 | 老式字段，TypeScript 会读 |
| `exports` | ⭐ 现代入口声明 | 优先于 `main`/`module`；同时是封装边界 |
| `files` | ⭐ 发布白名单 | 只有列出的路径进 npm 包 |
| `sideEffects` | 声明「本包无副作用」 | `false` 让 bundler 可以放心 tree shake |
| `type` | 决定 `.js` 按 ESM 还是 CJS 处理 | 见第 2 篇第三节 |

### 6.2 `files` 白名单

```json
{
  "files": ["dist"]
}
```

⚠️ **不写 `files` 会怎样？** npm 会按规则排除掉一些东西（`.gitignore` 里的、`.npmignore` 里的），但**剩下的全都发出去**——包括 `src/`、`tests/`、`tsconfig.json`、甚至你的 `.env`（如果有的话）。

⭐ **强烈建议显式写 `files`**：只发 `dist`（产物）。想额外让使用者能「点进源码」，就把 `src` 也加上：

```json
{
  "files": ["dist", "src"]
}
```

（配合第 1 篇的 `declarationMap: true`，使用者就能从 `.d.ts` 跳到源码。）

### 6.3 dual package 策略

**dual package**（双包）指**同时发布 ESM 和 CJS 两套产物**，让两种模块系统的用户都能用。

```bash
npx tsup src/index.ts --format esm,cjs --dts
```

产物：

```text
dist/
├── index.js      # ESM
├── index.cjs     # CJS
└── index.d.ts    # 类型声明
```

配合 `exports` 的条件导出（第 2 篇第 4.3 节）：

```json
{
  "exports": {
    ".": {
      "import": "./dist/index.js",
      "require": "./dist/index.cjs"
    }
  }
}
```

⚠️ **dual package 的风险就是第 2 篇讲的双包陷阱**：用户项目里如果同时存在 ESM 版和 CJS 版的两份副本，单例和 `instanceof` 会失效。

⭐ **规避三选一**：

1. **只发一种**（最省心）：纯 ESM（`"type": "module"`），或纯 CJS。老项目兼容用纯 CJS。
2. **发双份但让它们共享状态**：把状态放到一个两边都能访问的地方（globalThis）。
3. **明确接受风险**：确认你的库没有单例状态（不缓存、不用 `instanceof` 判定），双份也没问题。**纯函数库用 dual package 通常是安全的。**

### 6.4 发布前的检查清单

```
□ npm run typecheck 通过（tsc --noEmit）
□ npm run build 产物齐全：dist/index.js / index.cjs / index.d.ts
□ package.json 的 exports 路径与实际文件名完全一致（⛔ 大小写敏感）
□ 在一个空目录里 npm pack --dry-run 看要发出去哪些文件
□ types 字段 / exports.types 指向的 .d.ts 真实存在
```

```bash
npm pack --dry-run    # 预览将要发布的文件清单，不真正上传
npm publish           # 真正发布
```

## 七、常见坑

### 7.1 ⚠️ `tsc` 转译了，但 Node 运行时找不到模块

**症状**：

```text
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '/home/me/project/dist/utils'
```

**原因**：`tsc` **只转译、不改写 import 路径**。你写的是 `import { add } from "./utils"`，产物里还是 `"./utils"`——但 Node 的 ESM 要求完整扩展名。

**解法**：源码里统一写 `"./utils.js"`，TS 会自动映射到 `utils.ts`（第 2 篇第 7.3 节的后缀替换规则）。

⚠️ 另一个变体：写 `"./utils.ts"` —— **更糟**，运行时根本没有 `.ts` 文件。永远写 `.js`。

### 7.2 ⚠️ `skipLibCheck` 掩盖了第三方类型冲突

见第 5.6 节。**遇到看不懂的 `.d.ts` 相关报错，先关掉 `skipLibCheck` 复现一次。**

### 7.3 ⚠️ `esModuleInterop` 没开，默认导入报错

**症状**：

```text
error TS1259: Module '"./legacy.cjs"' can only be default-imported using the 'esModuleInterop' flag
```

**解法**：`tsconfig.json` 加 `"esModuleInterop": true`（**TypeScript 5.0 起该字段默认值就是 `true`**，所以新项目通常不用手写；只有显式关掉、或沿用很老的配置才会遇到这个报错）。

⚠️ **如果类型过了但运行时仍报错**，检查是不是只开了 `allowSyntheticDefaultImports` 而没开 `esModuleInterop`（前者只改类型，不改产物）。

### 7.4 其他高频坑速查

| 症状 | 原因 | 解法 |
|---|---|---|
| `Cannot find name 'process'` | TS 6.0 起 `types: []` | `"types": ["node"]` + 装 `@types/node` |
| `Cannot find module './x.css'` | 没有给非 TS 资源写声明 | `declare module "*.css"` |
| `Cannot find module 'foo'` 但明明装了 | TS 6.0 `types: []` 或没装 `@types/foo` | 显式配 `types` 或装 `@types` |
| 本地能跑、CI 挂 | lockfile 不一致 / `npm install` 而非 `npm ci` | CI 用 `npm ci` |
| 依赖在别人项目里 import 不到 | pnpm 严格隔离（幽灵依赖被禁） | 把依赖显式加进 `package.json` |
| 发布后使用者拿不到类型 | 没开 `declaration` 或 `types` 路径写错 | 开 `declaration`，核对 `types` 字段 |
| 生产构建报 `.d.ts` 冲突 | 第三方类型版本不匹配 | 对齐版本，而不是永久关 `skipLibCheck` |

## 八、陷阱

1. **⚠️ 用 `tsx` 当唯一防线**——`tsx` 基于 esbuild，**不检查类型**。类型错误会一路溜到运行时。必须配一份 `tsc --noEmit`。
2. **⚠️ 用 `esbuild` / `vite` 的构建当类型检查**——Vite 的 dev 和 build **都不做类型检查**。构建成功不代表类型正确。
3. **⚠️ 混用包管理器**——`node_modules` 结构被反复重建，lockfile 冲突。**一个项目一个包管理器，以 lockfile 为准。**
4. **⚠️ 依赖 pnpm 的严格隔离后，代码里 import 未声明的包报错**——这是**好事**（之前是幽灵依赖，随时会崩）。解法是补 `package.json` 声明，不是关掉隔离。
5. **⚠️ 源码里 import 路径不带 `.js`**——ESM 运行时 `ERR_MODULE_NOT_FOUND`。**永远写 `./x.js`**，哪怕源文件是 `.ts`。
6. **⚠️ 源码里 import 路径写 `.ts`**——运行时根本没有 `.ts` 文件。TS 编译期能过，运行时炸。
7. **⚠️ 用 `skipLibCheck: true` 掩盖第三方类型冲突**——冲突本身还在，只是那条报错被藏起来了，错误会在别处以更费解的形式冒出来。
8. **⚠️ 忘了 `esModuleInterop`**（或只开了 `allowSyntheticDefaultImports`）——默认导入报错，或类型过了运行时炸。
9. **⚠️ 发布时没写 `files`**——`src/`、`tests/`、甚至配置文件全被发出去。显式写白名单。
10. **⚠️ dual package 没评估双包陷阱**——用户项目里出现两份副本，单例失效、`instanceof` 为 `false`。纯函数库一般安全，有状态的库要想清楚。
11. **⚠️ `exports` 里的路径与实际文件名不一致（大小写）**——Linux 上直接 `ERR_PACKAGE_PATH_NOT_EXPORTED`，本地 Windows 上却正常。

## 小结

- 包管理器四选一：**npm**（默认）、**pnpm**（⭐ 硬链接省空间 + 严格依赖隔离）、**yarn Berry**（⭐ PnP 零 `node_modules`）、**bun**（⭐ 极快，自带运行时）。**不要混用**，以 lockfile 为准。
- npm 的**扁平化** `node_modules` 带来**幽灵依赖**和**磁盘浪费**；pnpm 用**内容寻址 store + 硬链接 + 符号链接**解决：顶层只有你声明的包，依赖彻底隔离。
- 工具谱系：**`tsc`**（唯一权威类型检查，不打包）、**`esbuild`**（极快转译，⭐ 不检查类型）、**`vite`**（前端主流，dev 用 esbuild / build 用 rollup，⭐ 也不检查类型）、**`tsup`**（库打包，基于 esbuild，`--dts` 出声明）、**`webpack`**（传统，配置复杂）。
- **`tsx`** 基于 esbuild 跑 TS：⚠️ **不检查类型**。工作流是「`tsx` 跑 + `tsc --noEmit` 查」。
- **`.d.ts`** 为无类型标注的库补类型：`declare module "包名"`、`declare module "*.css"`；**`@types/*`** 是 DefinitelyTyped 的类型包命名约定（⚠️ TS 6.0 起 `types: []` 不再自动引入）。
- 发库四件套：`main`/`module`/`types`/`exports` + **`files` 白名单** + dual package 策略 + 发布前 `npm pack --dry-run` 检查。
- 三大高频坑：**import 路径缺 `.js`**、**`skipLibCheck` 掩盖冲突**、**`esModuleInterop` 没开**。

## 练习

1. 分别用 npm 和 pnpm 装 `express`，对比两边 `node_modules` 的目录结构；在 pnpm 项目里故意 `import` 一个没声明的包，观察报错；再把它加进 `package.json` 解决。
2. 写一个只有两个函数的小库，用 `tsup --format esm,cjs --dts` 打包，写好 `exports` 条件导出，然后 `npm pack --dry-run` 看清单；在另一个空项目里分别用 `import` 和 `require` 引入它，确认走到了不同产物。
3. 写一个故意类型错误的 TS 文件（如 `const x: number = "hi"`），分别用 `npx tsx` 和 `npx tsc --noEmit` 跑，观察两者行为差异；解释为什么会有差异。
4. 建一个 `types/assets.d.ts`，声明 `*.svg` 的模块类型，让 `import logo from "./logo.svg"` 通过类型检查；再写一个 `declare module "legacy-lib"` 补声明。
5. 把 `skipLibCheck` 从 `true` 改成 `false` 跑一次类型检查，对比耗时和报错条数；找出一个第三方类型冲突并通过「对齐版本」解决（而不是永久关掉该选项）。
6. 搭一个 Vite + TS 的前端项目，故意写一个类型错误，验证 `vite build` **不会**报错，而 `tsc --noEmit` 会；然后把两者串成一条 `npm run build` 脚本。
7. 查一下 TypeScript 6.0 之后 `types` 字段的默认值变化，说明为什么「升级后满屏 `Cannot find name 'process'`」以及三种修法各自的适用场景。
