# 测试与错误处理

> **什么时候该读**：你要给项目加测试但不知道从哪下手；或者线上出了 bug，想知道「为什么没被测出来」；又或者你在用 `try/catch` 时发现 TS 报错说 `e` 是 `unknown`，不知道怎么用。
> **阅读门槛**：读完 [[typescript/02-中段阶段-专题精讲/Node生态与异步/2-Promise与异步流]]（会写 `async/await`、懂 Promise 链），以及 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.4-类型收窄与类型守卫]]（会写类型守卫）。测试里的异步断言全靠 `await`，不懂 Promise 会寸步难行。

## 一、⭐ 测试金字塔

### 1.1 三层结构

**测试（test）**：用代码验证代码的行为是否符合预期。

> **对照 Python**：Python 里对应 `pytest` 的 `test_*.py` 文件和 `assert` 语句。JS 世界的对应物是 Vitest / Jest。

**测试金字塔（test pyramid）** 是一个描述「不同粒度的测试各写多少」的经典模型：

```
                ▲
               ╱ ╲
              ╱ E2E ╲          端到端测试（E2E）
             ╱  少量  ╲         少而慢，覆盖关键用户路径
            ╱──────────╲
           ╱  集成测试   ╲      集成测试（Integration）
          ╱    中等数量    ╲    测「多个模块协作」，用真实依赖
         ╱──────────────────╲
        ╱     单元测试        ╲   单元测试（Unit）
       ╱       大量            ╲  最多、最快、覆盖细节
      ╱────────────────────────╲
```

⭐ **核心比例建议**（一个典型业务服务）：

| 层 | 数量占比 | 单个耗时 | 覆盖目标 | 失败时的诊断价值 |
|---|---------|---------|---------|----------------|
| **单元测试** | ~70% | 毫秒级 | 单个函数 / 类的**逻辑正确性**，含各种边界和异常分支 | 低（范围小但信息具体） |
| **集成测试** | ~20% | 秒级 | **模块协作**：路由 → 控制器 → 服务 → 数据库/外部 API 的整条链 | 中（能定位到集成点） |
| **端到端测试** | ~10% | 十秒~分钟级 | **真实用户路径**：起真服务、发真 HTTP 请求、点真前端 | 高（能确认"整件事真的能成"） |

### 1.2 每层的取舍

| 维度 | 单元测试 | 集成测试 | E2E 测试 |
|------|---------|---------|---------|
| **被测对象** | 一个纯函数 / 一个类 | 多个模块 + 真实或替身依赖 | 整个系统（起真进程） |
| **依赖怎么办** | 全部 mock 掉 | 用真数据库（Docker / 内存版）/ 外部服务用替身 | 全真 |
| **速度** | ⚡ 毫秒 | 🐢 秒 | 🐌 十秒起 |
| **稳定性** | 高（无 IO） | 中（依赖环境） | 低（网络、时间、随机数都可能抖） |
| **定位能力** | 精确（就知道这个函数错了） | 中等 | 差（只知道"这条路径挂了"） |
| **能不能独立跑** | 能，随手跑 | 需要起依赖 | 需要完整环境 |

⭐ **为什么是金字塔而不是冰淇淋（顶层很宽）**：越往上越慢、越脆、越难定位问题。所以**能用下层测的绝不用上层测**。

⭐ **但也别教条**：测试金字塔是 2009 年的经典模型，现代实践有调整——

- 很多团队发现 **E2E 少写、集成测试多写**（"冰山模型"）更实用，因为 E2E 既慢又脆；
- 也有人主张 **"宽金字塔"**（单元测试少写，靠类型系统和集成测试兜底）；
- **关键不是形状，是"每一层都够用"**。选型要看你项目的类型系统强度、团队规模、CI 时长预算。

### 1.3 什么该测什么不该测

| 该测 | 不该测 |
|------|-------|
| 业务规则、边界条件、异常分支 | 框架/库自己（那是别人的测试责任） |
| 你的类型系统**测不出来**的东西 | 私有实现细节（改了内部结构就挂的测试，是负担不是保障） |
| 曾经出过 bug 的地方（回归测试） | getter / setter 的转发这种没有逻辑的代码 |
| 契约：函数输入什么、输出什么 | "代码确实执行到这一行"这种实现细节 |

⭐ **一句话**：**测行为，不测实现。** 断言应该表达「用户能观察到的结果」，而不是「内部变量被赋成了什么」。

## 二、⭐ Vitest 为主，兼容 Jest

### 2.1 为什么选 Vitest

| | **Vitest 5** | **Jest** |
|---|---|---|
| 速度 | ⚡ 快（基于 Vite 的转换管线，不重复转译） | 较慢（每个文件独立转译 + 运行） |
| ESM 支持 | 原生 | 需要配置 |
| 配置 | `vitest.config.ts`，和 Vite 共用配置 | 独立的 `jest.config.js` |
| API | ⭐ 和 Jest **几乎完全一致** | 基准 |
| 生态 | 较新 | 更老更广 |
| TS 支持 | 直接支持 | 需要 `ts-jest` / SWC 之类 |

⭐ **迁移策略**：因为 API 一致，**大多数项目从 Jest 迁到 Vitest 只需改配置和少量 import**（`jest.fn()` → `vi.fn()`，`jest.mock` → `vi.mock`）。本篇用 Vitest，但概念完全通用。

⚠️ **版本基线（Vitest 5）**：**Vitest 5.0 于 2026-09-03 发布**，要求 **Node.js ≥ 22.12（或 24 / 26）**、**Vite ≥ 6.4**。Vitest 5 有两个**会让老测试突然变红**的默认行为变更：

| 变更 | 影响 | 应对 |
|------|------|------|
| **`clearMocks` 默认为 `true`** | 每个测试前自动清空 mock 调用历史；**跨测试统计调用次数的断言会归零** | 需要跨测试累积时显式设 `clearMocks: false` |
| **未 `await` 的异步断言直接失败** | `expect(p).resolves` / `expect(p).rejects` 忘了 `await` 会**报错**（不再静默通过） | 这其实是好事——把第 2.4 节那个坑变成了编译期外的运行时保护 |

```bash
npm i -D vitest @vitest/coverage-v8
```

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    environment: "node",           // 默认就是 node；测浏览器代码才用 jsdom
    globals: false,                // ⭐ 不把 describe/it/expect 注入全局，要显式 import（更清晰）
    coverage: {
      provider: "v8",              // 用 V8 的原生覆盖率信息，比插桩更快
      reporter: ["text", "html"],
      include: ["src/**/*.ts"],    // ⚠️ 别把测试文件本身算进覆盖率
    },
  },
});
```

### 2.2 三个核心函数

| 函数 | 作用 |
|------|------|
| **`describe(name, fn)`** | **分组**。把一组相关测试组织在一起，`name` 通常是「被测单元的名字」。可以嵌套 |
| **`it(name, fn)`** / **`test(name, fn)`** | **一个测试用例**。`it` 和 `test` 完全等价，`it` 更短所以常用 |
| **`expect(value)`** | **断言**。拿实际值跟期望值比对，匹配不上就抛错让测试失败 |

```ts
import { describe, it, expect } from "vitest";
import { add, divide } from "./math";

describe("add", () => {
  it("应该把两个正数相加", () => {
    expect(add(2, 3)).toBe(5);
  });

  it("应该处理负数", () => {
    expect(add(-2, 3)).toBe(1);
  });
});
```

> **对照 Python**：`describe` ≈ pytest 的 `class TestXxx` 或普通分组函数；`it` ≈ 一个 `def test_xxx()`；`expect(...).toBe(...)` ≈ 原生 `assert`。

### 2.3 ⭐ 常用断言的语义差异

**这是本节的重点**，选错断言会产生「假通过」或「无意义失败」。

| 断言 | 语义 | 典型用法 |
|------|------|---------|
| **`toBe(expected)`** | 用 **`Object.is`** 比较（严格的 `===`，外加区分 `+0`/`-0`、`NaN` 等） | 引用相等、原始值相等 |
| **`toEqual(expected)`** | **递归**比较结构和值，但**忽略 `undefined` 属性**；不检查类型 | 比较对象 / 数组内容 |
| **`toStrictEqual(expected)`** | 递归比较，**且**：检查 `undefined` 属性、检查稀疏数组、检查类实例的类型 | 需要"完全一样"时的严格比较 |
| **`toContain(item)`** | 数组 / 字符串 / 迭代器**包含**某项（字符串则查子串） | 检查数组含某元素 |
| `toBeTruthy()` / `toBeFalsy()` | 转成布尔后判断 | 判断存在性 |
| `toBeNull()` / `toBeUndefined()` / `toBeNaN()` | 精确判断 | 边界 |
| `toMatch(regexp)` | 字符串匹配正则 | 格式校验 |
| `toHaveLength(n)` | 长度 | 数组 / 字符串 |
| `toThrow()` | 函数**抛出**了异常 | 错误处理测试 |

#### `toBe` vs `toEqual` vs `toStrictEqual` ⭐

```ts
const a = { name: "Tom", age: 20 };
const b = { name: "Tom", age: 20 };

expect(a).toBe(b);             // ❌ 失败！两个不同的对象引用
expect(a).toEqual(b);          // ✅ 通过！结构和值相同
expect(a).toStrictEqual(b);    // ✅ 通过
```

⚠️ **`toEqual` 忽略 `undefined` 属性**：

```ts
expect({ a: 1, b: undefined }).toEqual({ a: 1 });            // ✅ 通过！
expect({ a: 1, b: undefined }).toStrictEqual({ a: 1 });      // ❌ 失败
```

⚠️ **`toEqual` 不检查类实例的类型**：

```ts
class Dog { bark() {} }
class Cat { meow() {} }

const dog = new Dog();
expect(dog).toEqual(new Cat());       // ✅ 通过！两者都没有 own property
expect(dog).toStrictEqual(new Cat()); // ❌ 失败：原型不同
```

⚠️ **`toBe` 在 `NaN` 上通过，但 `===` 不通过**：

```ts
expect(NaN).toBe(NaN);        // ✅ 通过（Object.is 把 NaN 视为相等）
expect(NaN).toBe(NaN);        // ✅ 同上
expect(0).toBe(-0);           // ❌ 失败（Object.is 区分 +0 / -0）
```

#### `toContain` 的三种含义

```ts
expect([1, 2, 3]).toContain(2);          // ✅ 数组包含元素
expect("hello world").toContain("world"); // ✅ 字符串包含子串
expect(new Set([1, 2])).toContain(2);      // ✅ 迭代器包含元素
expect({ a: 1 }).toContain("a");          // ❌ 失败：对象不是可包含的类型
```

⭐ **注意 `toContain` 是「包含」不是「等于」**——`expect([1,2,3]).toContain(1)` 通过，但**不能**用它判断数组相等。数组整体相等用 `toEqual`。

### 2.4 异步测试

```ts
it("应该异步返回用户", async () => {
  const user = await fetchUser("u1");
  expect(user.name).toBe("Tom");
});

// ⭐ 断言"应该抛错"——注意必须传函数，不能直接传调用结果
it("应该在用户不存在时抛错", () => {
  expect(() => findUser("nope")).toThrow("用户不存在");
  expect(() => findUser("nope")).toThrow(UserNotFoundError);  // 按错误类型断言
});

// 异步函数的抛错断言
it("应该异步抛错", async () => {
  await expect(fetchUser("nope")).rejects.toThrow(UserNotFoundError);
  await expect(fetchUser("ok")).resolves.toHaveProperty("id");
});
```

⚠️ **`toThrow` 必须包一层函数**：`expect(findUser("nope")).toThrow()` 会在 `expect` 求值时就把错误抛出来，测试会以「未捕获异常」的形式失败，而不是一条清晰的断言失败。**写成 `expect(() => findUser("nope"))`** 才是对的。

⚠️ **忘了 `await`**：`expect(promise).toThrow()` 这类写法永远不生效。异步断言一律 `await expect(...).rejects/resolves...`。

⭐ **Vitest 5 起这条变成硬保护**：未 `await` 的 `expect(p).resolves` / `expect(p).rejects` 断言**会直接让测试失败**，而不是静默通过。从 Vitest 4 升级后测试突然变红，先查是不是漏了 `await`。

⚠️ **Vitest 5 的 `toThrow("")` 语义变了**：空字符串现在匹配**任何**抛出的错误。要断言「错误信息为空」，得显式给匹配模式，而不是传空串。

## 三、⭐ mock 与 spy

### 3.1 三种测试替身

| 手段 | 是什么 | 用来干什么 |
|------|--------|-----------|
| **stub（桩）** | 返回预设值的假实现 | 替换掉「不重要的依赖」 |
| **spy（探针）** | **包住真实实现**，记录调用情况 | 断言"这个函数被调用了吗 / 传了什么参数" |
| **mock（模拟）** | 假实现 + 断言能力 | 替换掉「不好控制的依赖」（网络、时间、随机数） |

⭐ **一句话**：**spy 让你看见真实调用，mock 让你替换掉真实行为。**

### 3.2 `vi.fn()`：造一个假函数

```ts
import { vi, expect, it } from "vitest";

it("应该调用了发送函数", () => {
  const sendEmail = vi.fn();                       // ⭐ 一个什么也不做的假函数

  registerUser({ name: "Tom" }, sendEmail);        // 依赖注入：把假函数传进去

  expect(sendEmail).toHaveBeenCalledTimes(1);
  expect(sendEmail).toHaveBeenCalledWith(
    expect.objectContaining({ name: "Tom" })       // ⭐ 部分匹配
  );
});
```

⭐ **依赖注入（dependency injection，DI）**：把「要用什么」作为参数传进去，而不是在函数内部 `import`。这是**最推荐的可测试性手段**——不需要任何 mock 框架，天然可测。

```ts
// ⚠️ 难测：依赖被硬编码在内部
import { sendEmail } from "./mailer";
export async function registerUser(data: User): Promise<void> {
  await db.insert(data);
  await sendEmail(data);        // ⭐ 测试时没法换掉它
}

// ✅ 好测：依赖从参数进
export async function registerUser(
  data: User,
  deps: { db: Db; sendEmail: (u: User) => Promise<void> }
): Promise<void> {
  await deps.db.insert(data);
  await deps.sendEmail(data);
}
```

### 3.3 `vi.spyOn()`：包住真实方法

```ts
import { vi, expect, it } from "vitest";
import * as analytics from "./analytics";

it("注册成功时应该上报埋点", async () => {
  const spy = vi.spyOn(analytics, "track");       // ⭐ 保留真实实现，但记录调用

  await registerUser({ name: "Tom" });

  expect(spy).toHaveBeenCalledWith("user_registered");
  spy.mockRestore();                                // ⭐ 用完还原，否则污染其他测试
});
```

⚠️ **`vi.spyOn` 默认仍然调用真实实现**。想让它完全变成假的：

```ts
vi.spyOn(analytics, "track").mockImplementation(() => {});   // 只记录不执行
vi.spyOn(analytics, "track").mockResolvedValue(undefined);  // 返回 Promise
```

⭐ **`vi.mock("模块路径")`** 用于替换整个模块（模块级 mock），但它会**影响整个测试文件**，且在 ESM 下是静态提升的（hoisting）——必须写在文件顶层，且 Vitest 需要 `vi.mock` 工厂函数里用 `importOriginal` 才能保留原实现。**能用 DI 就别用模块 mock。**

### 3.4 ⚠️ 不要过度 mock

**过度 mock** 的症状：

| 症状 | 表现 |
|------|------|
| **测的是 mock 不是代码** | 测试里 mock 掉了 80% 的逻辑，断言的全是"我 mock 的东西被调用了"——这类测试**无论真实代码对错都通过** |
| **测实现细节** | 断言"内部调用了 `calculateTax` 方法"，结果重构时测试全挂，但用户行为毫无变化 |
| **测试通过，产品有 bug** | 集成时才炸——因为 mock 的行为和真实依赖不一致 |
| **mock 比被测代码还复杂** | 为了让 mock "像真的"，你写了几十行模拟逻辑 |

⭐ **判断标准**：**问自己「如果我把这个函数体换成 `return undefined`，这个测试还会通过吗？」** 如果会，那这个断言就是废话。

⭐ **实践建议**：

- **优先 mock「你自己控制不了的东西」**：网络、时间、随机数、第三方 SDK；
- **不要 mock「你自己写的代码」**——那样你测的是自己的 mock；
- **边界上用真依赖**：数据库用内存版（SQLite `:memory:`）、Redis 用 `ioredis-mock`、时间用 `vi.useFakeTimers()`；
- **一个测试只断言一件重要的事**——断言越多，失败时越难定位。

⚠️ **Vitest 5 的 `clearMocks` 默认是 `true`**：每个测试开始前自动清空所有 mock 的调用历史。这带来两个实际影响——

```ts
// ⚠️ 跨测试统计调用次数的写法，在 Vitest 5 下会拿到 0
it("第一次调用", () => {
  expect(sendEmail).toHaveBeenCalledTimes(1);
});
it("第二次调用", () => {
  expect(sendEmail).toHaveBeenCalledTimes(1);   // ⚠️ 期望 2，实际 1（历史被清了）
});
```

需要累积统计时，在配置里显式关掉：`test: { clearMocks: false }`，或改用 `vi.fn().mock.calls.length` 在单个测试内自己累加。

```ts
// ✅ 好：测行为，且用的是真实现
it("余额不足时不应该扣款", async () => {
  const db = createInMemoryDb();          // 真数据库（内存版）
  await db.insert({ id: "u1", balance: 10 });

  await expect(withdraw("u1", 100)).rejects.toThrow(InsufficientFundsError);
  expect(await db.getBalance("u1")).toBe(10);   // ⭐ 关键：余额没变
});
```

## 四、⭐ 错误处理分层

### 4.1 两类错误

| | **预期错误（expected error）** | **意外错误（unexpected error）** |
|---|---|---|
| **定义** | 业务上**可预期**会发生的情况 | 程序或环境的**异常** |
| **例子** | 密码错误、余额不足、找不到资源、参数不合法 | 数据库连不上、`TypeError`、内存溢出、第三方超时 |
| **谁应该处理** | 调用方**可能**能处理（用户重试、换个输入） | 一般**没人能处理**，需要兜底 + 告警 |
| **表达方式** | ⭐ **返回值**（`Result` 类型）或 **`throw`** | **`throw`** |

⭐ **核心原则**：**预期错误用返回值表达，意外错误用 `throw` 表达。**

### 4.2 ⭐ 不要用异常做流程控制

```ts
// ❌ 用异常表达"正常的业务分支"
function withdraw(amount: number): void {
  const balance = getBalance();
  if (balance < amount) {
    throw new Error("余额不足");        // ⚠️ 正常业务分支，不该用异常
  }
  deduct(amount);
}

// ✅ 用返回值表达
type WithdrawResult =
  | { ok: true; newBalance: number }
  | { ok: false; reason: "insufficient" | "frozen" };

function withdraw(amount: number): WithdrawResult {
  const account = getAccount();
  if (account.frozen) return { ok: false, reason: "frozen" };
  if (account.balance < amount) return { ok: false, reason: "insufficient" };
  deduct(amount);
  return { ok: true, newBalance: account.balance - amount };
}
```

⭐ **为什么不能滥用异常做流程控制**：

1. **异常是"绕过"常规控制流的**——读代码时 `try` 块里可能从任何一行抛出，静态分析难做；
2. **异常的类型在 TS 里默认是 `unknown`**（下一节讲），你**不能靠类型系统保证"这个 catch 出来的错误一定是 `InsufficientFundsError`"**；
3. **性能**：`throw` 的成本远高于返回（要构造栈帧）；
4. **误用为控制流会导致「该 catch 的没 catch，不该 catch 的 catch 了」**。

⭐ **但是——「预期错误用返回值」不是铁律**。区分标准是：

| 情况 | 建议 |
|------|------|
| 错误是**调用方正常业务的一部分**（如"库存不足"） | 用 `Result` 返回值，**调用方一定会处理** |
| 错误是**异常情况**（如"参数格式错了"、"数据库炸了"） | 用 `throw`，让上层统一兜底 |
| 错误是**调用方根本不该遇到的**（如内部断言失败） | 用 `throw` + 特殊标记（如 `Error` 的 `cause` 链） |

> **对照 Python**：Python 里通常用**异常**表达业务错误（`raise ValueError`），因为 Python 没有内置的 `Result` 类型，需要自己用 `dataclass` 或 `typing` 模拟。TS 里用 `Result` 更顺，因为 TS 的**判别联合**（discriminated union，见 [[typescript/01-入门阶段-基础教程/第02章-类型系统/2.2-联合类型与字面量类型]]）天然支持 `{ ok: true } | { ok: false }` 这种写法。

```python
# Python 的常见写法：用异常表达业务分支
def withdraw(amount: float) -> None:
    balance = get_balance()
    if balance < amount:
        raise ValueError("余额不足")      # ⚠️ 和 TS 里被诟病的写法一样
    deduct(amount)
```

```ts
// TS 的对应写法：用判别联合返回值表达业务分支
type WithdrawResult =
  | { ok: true; newBalance: number }
  | { ok: false; reason: "insufficient" | "frozen" };
```

### 4.3 错误要带上下文

```ts
// ❌ 信息太少，排查时只能靠猜
throw new Error("failed");

// ✅ 带上「哪个实体、哪个字段、哪个值」
throw new Error(`用户 ${userId} 创建失败：邮箱 ${email} 格式非法`);
```

⭐ **错误信息的三要素**：**什么操作失败了 + 涉及哪个实体 + 关键输入是什么**。注意别把密码、token 这类敏感信息写进错误信息（会进日志）。

## 五、⭐ 自定义 Error 类型

### 5.1 定义一个错误基类

```ts
/** 业务错误基类：可预期、调用方可能能处理 */
class AppError extends Error {
  /** 错误码：稳定的、可枚举的标识，不要用错误信息当标识 */
  readonly code: string;
  /** 是否可重试：给调用方（尤其是自动重试的上游）看的 */
  readonly retryable: boolean;
  /** 原始错误：用 ES2022 的 cause 保留根因 */
  override readonly cause?: unknown;

  constructor(
    message: string,
    options: { code: string; retryable?: boolean; cause?: unknown } = { code: "APP_ERROR" }
  ) {
    super(message, { cause: options.cause });     // ⭐ Node 16.9+ / ES2022 的 Error cause
    this.name = "AppError";                       // ⭐ 必须设 name
    this.code = options.code;
    this.retryable = options.retryable ?? false;
    // ⭐ ES5 target 下必须手动修复原型链（见 5.3）
    Object.setPrototypeOf(this, new.target.prototype);
  }
}
```

⭐ **为什么要设 `this.name`**：默认 `Error` 构造器把 `name` 设成 `"Error"`，不设的话所有自定义错误在日志里都显示成 `Error`，无法区分。

### 5.2 按语义派生具体错误

```ts
class ValidationError extends AppError {
  constructor(message: string, cause?: unknown) {
    super(message, { code: "VALIDATION_ERROR", cause });
    this.name = "ValidationError";
    Object.setPrototypeOf(this, new.target.prototype);
  }
}

class NotFoundError extends AppError {
  constructor(entity: string, id: string) {
    super(`${entity} 不存在: ${id}`, { code: "NOT_FOUND" });
    this.name = "NotFoundError";
    Object.setPrototypeOf(this, new.target.prototype);
  }
}

class UpstreamError extends AppError {
  constructor(service: string, cause: unknown) {
    super(`上游服务 ${service} 调用失败`, { code: "UPSTREAM_ERROR", retryable: true, cause });
    this.name = "UpstreamError";
    Object.setPrototypeOf(this, new.target.prototype);
  }
}
```

### 5.3 ⚠️ `instanceof` 在 ES5 target 下失效

```ts
const err = new ValidationError("邮箱格式非法");
console.log(err instanceof ValidationError);   // 期望 true
```

⚠️ **在 `target: "ES5"` 下，这行会返回 `false`。**

**为什么**：TS 把 `class` 编译成 ES5 时，用的是**函数 + 原型赋值**的旧写法：

```js
// ES5 编译产物（简化）
var ValidationError = /** @class */ (function (_super) {
    __extends(ValidationError, _super);
    function ValidationError(message) {
        var _this = _super.call(this, message) || this;
        _this.name = "ValidationError";
        return _this;
    }
    return ValidationError;
}(AppError));
```

⚠️ **问题在 `Error` 这个内置类型上**：`Error` 在 ES5 里是**内置函数**，内置函数的 `call(this, ...)` **不会**按 ES6 规范设置 `this` 的原型——它返回的是个**没有 `ValidationError.prototype` 的普通对象**。于是原型链断了，`instanceof` 判定失败。

⭐ **修法（两条，任选）**：

```ts
// 修法 A：在构造器里手动修原型链（最通用）
Object.setPrototypeOf(this, new.target.prototype);
```

```json
// 修法 B：把 target 提上去（推荐）
// tsconfig.json
{
  "compilerOptions": {
    "target": "es2022"    // ⭐ ES2015+ 用原生 class，instanceof 天然正确
  }
}
```

> **版本背景**：`target: "es5"` 在 **TypeScript 6.0 已废弃**，在 **TS 7.0 会变成硬错误**。所以**新项目根本不该用 ES5 target**——但如果你在维护老项目（或者用了某些还在输出 ES5 的老构建链），`Object.setPrototypeOf` 这行是必须写的。

⭐ **实践建议**：**两个都做**——写上 `Object.setPrototypeOf`（防御性，零成本），并把 `target` 提到 `es2022`（TS 6.0 起默认已是 `es2025`，见 [[typescript/02-中段阶段-专题精讲/工程化与工具链/1-编译流程与tsconfig]]）。

### 5.4 `name` 和 `code` 的分工

| 字段 | 用途 | 谁看 |
|------|------|------|
| `name` | 错误**类**的名字（`"ValidationError"`） | 人（读日志）、`err.name` 判断 |
| `code` | 稳定的**机器可读**错误码（`"VALIDATION_ERROR"`） | 代码（分支处理）、监控聚合 |
| `message` | 人类可读描述 | 人 |
| `cause` | 原始错误 | 排查根因 |

⭐ **不要用 `message` 做判断**：消息会随文案调整而变，代码会崩。**判断要用 `instanceof` 或 `code`。**

## 六、⭐ `unknown` 收窄错误

### 6.1 为什么会是 `unknown`

```ts
try {
  JSON.parse(raw);
} catch (e) {
  console.log(e.message);   // ⚠️ TS 报错：Object is of type 'unknown'
}
```

⭐ **原因**：**JS 允许 `throw` 任何东西**，不限于 `Error`：

```ts
throw "字符串错误";
throw { code: 123 };
throw null;
throw undefined;
```

所以 TS **无法**假设 catch 里的值是 `Error`——它只能知道「是个不知道的东西」。

> **版本背景**：这个行为由 `useUnknownInCatchVariables` 控制，它**在 `strict: true` 时默认为 `true`**（TS 4.4 起）。也就是说 **TS 5.x/6.x/7.x 开启 strict 就会是 `unknown`**。**TS 6.0 的默认 `strict: true` 意味着新项目一上手就是这个行为。**

> **对照 Python**：`except Exception as e` 已经保证了 `e` 是 `Exception` 的子类（除非你写 `except:` 裸捕获）。TS 相当于把 Python 的 `except:`（裸捕获）变成默认行为——这是**更安全**的选择。

### 6.2 三种收窄方式

#### 方式 A：`instanceof`（最常用）

```ts
try {
  await doWork();
} catch (e: unknown) {
  if (e instanceof AppError) {
    console.error(`[${e.code}] ${e.message}`, { cause: e.cause });
    if (e.retryable) scheduleRetry();
  } else if (e instanceof Error) {
    console.error("未知异常:", e.message);
  } else {
    // ⚠️ 非 Error 的抛出物：JSON 解析失败有时抛 SyntaxError（是 Error 子类），
    //    但 throw "字符串" 就落到这里
    console.error("非 Error 抛出物:", e);
  }
}
```

#### 方式 B：属性检查（duck typing）

当你不确定对方是不是 `Error` 子类，但确定它有 `code` 字段时：

```ts
function hasCode(e: unknown): e is { code: string; message: string } {
  return (
    typeof e === "object" && e !== null &&
    "code" in e && typeof (e as { code: unknown }).code === "string"
  );
}
```

#### 方式 C：类型谓词 + 复用

详见下一节。

### 6.3 通用收窄辅助函数

```ts
/** 把 unknown 收窄成 Error —— 复用型守卫 */
export function toError(e: unknown): Error {
  if (e instanceof Error) return e;
  if (typeof e === "string") return new Error(e);
  try {
    return new Error(JSON.stringify(e));
  } catch {
    return new Error(String(e));     // ⭐ JSON.stringify 遇到循环引用会自己抛
  }
}

// 用法
try {
  await doWork();
} catch (e: unknown) {
  logger.error(toError(e).message);
}
```

⭐ **这条主线要记住**：**`catch` 里的 `e` 是 `unknown` → 必须收窄 → 才能用。** 这不是 TS 在为难你，而是 JavaScript 真的允许 `throw "字符串"`——类型系统只是在如实反映现实。

## 七、断言函数（`asserts condition`）

### 7.1 复用第 2 章的类型守卫

**断言函数（assertion function）**：一个函数签名里带 `asserts` 的函数，**返回后 TS 就认为某个条件一定成立**，并且会把变量的类型收窄。

```ts
// 普通类型守卫：需要调用者写 if (isUser(x))
function isUser(v: unknown): v is { name: string; age: number } {
  return typeof v === "object" && v !== null && typeof (v as { name?: unknown }).name === "string";
}

// ⭐ 断言函数：调用后直接收窄，不需要 if
function assertIsUser(v: unknown): asserts v is { name: string; age: number } {
  if (!isUser(v)) {
    throw new ValidationError("用户数据格式非法");
  }
}

// 用法：不需要 if
const data: unknown = await response.json();
assertIsUser(data);            // ⭐ 从这里开始，data 就是 { name: string; age: number }
console.log(data.name.toUpperCase());   // ✅ 不报错了
```

> **对照 Python**：这对应 Python 的 `assert isinstance(data, User)`，之后类型检查器才知道 `data` 是 `User`。区别是：**Python 的 `assert` 语句可以被 `python -O` 优化掉**（生产环境不生效），**TS 的断言函数是编译期的，永远生效**，而且它是**函数调用**，会真的抛异常。

```python
# Python：assert 用于类型收窄（但可以被 -O 优化掉）
from typing import assert_never

def process(data: object) -> None:
    assert isinstance(data, User), "用户数据格式非法"   # ⚠️ python -O 下这行会消失
    print(data.name.upper())                            # mypy 知道 data 是 User
```

### 7.2 断言函数的三个约束

TS 对断言函数有严格要求，写错了会报错：

1. **必须显式标注返回类型** `asserts x is T`（不能靠推断）；
2. **被断言的变量必须是 `const` 或用 `let` 声明的普通标识符**——不能是属性访问（`asserts obj.x is T` ❌），因为属性可能中途被改；
3. **断言函数必须有显式返回类型标注**，且不能是箭头函数的表达式体简写（必须用 `{}` + 显式 `return` 或自然结束）。

```ts
// ❌ 错误示例
function assertIsUser(v: unknown) { ... }         // 缺返回类型标注
function assertProp(v: unknown): asserts v.x is string { ... }   // 不能断言属性
```

### 7.3 在错误处理里怎么用

```ts
function parseConfig(raw: string): Config {
  let parsed: unknown;
  try {
    parsed = JSON.parse(raw);
  } catch (e: unknown) {
    throw new ValidationError("配置文件不是合法 JSON", { cause: toError(e) });
  }
  assertIsConfig(parsed);        // ⭐ 不合法就抛 ValidationError
  return parsed;                 // ⭐ TS 知道 parsed 是 Config
}
```

⭐ **这就是 `unknown` 收窄主线的完整闭环**：`unknown` → 断言函数/类型守卫 → 可信类型；出错的路径统一转成 `AppError`，让上层用一套逻辑处理。

## 陷阱

1. **⚠️ 用 `toEqual` 断言"两个对象一样"，却用了 `toBe`**——`toBe` 比的是引用，两个字面量相同但不同引用的对象会失败；反过来用 `toEqual` 比 `NaN` 也会出问题；
2. **⚠️ 用 `toContain` 断言数组相等**——它只检查"包含"，`expect([1,2,3]).toContain(1)` 通过不代表数组就是 `[1,2,3]`；
3. **⚠️ 以为 `toEqual` 会检查 `undefined` 属性和类实例类型**——它**不**检查；要严格比较用 `toStrictEqual`；
4. **⚠️ `expect(() => fn()).toThrow()` 写成 `expect(fn()).toThrow()`**——错误在 `expect` 求值时就抛出来了，失败信息是一坨 stack 而不是清晰的断言失败；
5. **⚠️ 异步断言忘了 `await`**——`expect(promise).rejects.toThrow()` 不 await 就等于没断言；
6. **⚠️ 过度 mock**——把被测逻辑也 mock 掉，测试变成了"验证 mock 被调用了"，真实代码错了它照样通过；
7. **⚠️ `vi.spyOn` 忘了 `mockRestore()`**——污染同文件里后续的测试，出现莫名其妙的失败；⚠️ **Vitest 5 起 `clearMocks` 默认 `true`**，跨测试统计 mock 调用次数会拿到 0；
8. **⚠️ 断言实现细节而不是行为**——重构内部结构就全线飘红，测试变成负担；
9. **⚠️ 用异常做流程控制**——业务分支用 `throw` 会让类型系统失去保障、`catch` 里的 `unknown` 无法区分错误种类；
10. **⚠️ 自定义 Error 忘了设 `this.name`**——日志里所有错误都显示成 `Error`，无法分类；
11. **⚠️ ES5 target 下 `instanceof` 失效**——`err instanceof MyError` 恒为 `false`，分支永远进不去；修法：`Object.setPrototypeOf(this, new.target.prototype)` 或把 `target` 提到 `es2022`；
12. **⚠️ 忘了 `Object.setPrototypeOf`（在旧 target 下）**——`instanceof` 和 `err.name` 一起失灵；
13. **⚠️ 直接用 `e.message` 而不收窄 `unknown`**——strict 模式下 TS 会报错；如果为了绕过而写 `catch (e: any)`，等于把安全网拆了；
14. **⚠️ 错误信息不含上下文**——`throw new Error("failed")` 在生产日志里等于没写；
15. **⚠️ 错误信息里带敏感数据**——密码、token 写进 message 会进日志、进监控、进第三方错误平台；
16. **⚠️ 异步错误没被 `await` 捕获**——`try { doAsync(); } catch {}` 抓不到任何东西（错误发生在 `try` 块结束之后）；
17. **⚠️ 在 `finally` 里吞异常**——`finally { try { cleanup(); } catch {} }` 里若不处理，异常会覆盖掉 `try` 原本要抛出的错误；且 `finally` 里 `return` 会**吞掉**原异常（和第 2 篇的 `.finally` 同理）；
18. **⚠️ 用 `message` 做错误分支判断**——文案一改代码就崩；用 `instanceof` 或稳定的 `code`；
19. **⚠️ 覆盖率当成质量**——100% 行覆盖不代表逻辑正确；覆盖率只说明"这行被执行过"，不说明"结果对"；
20. **⚠️ 测试之间有顺序依赖**——上一个测试改了全局状态，下一个就挂；每个测试自己准备数据（`beforeEach`），不共享可变状态。

## 小结

- ⭐ **测试金字塔**：单元（多、快、细节）/ 集成（中、模块协作）/ E2E（少、慢、真实路径）；现代实践不一定是金字塔，关键是每层够用
- **测行为，不测实现**；断言要表达用户可观察的结果
- ⭐ **Vitest 5 为主**（2026-09-03 发布，需 Node ≥ 22.12 / Vite ≥ 6.4；快、原生 ESM、API 与 Jest 几乎一致，迁移成本低）；`describe` 分组 / `it` 用例 / `expect` 断言；⚠️ **Vitest 5 的 `clearMocks` 默认 `true`**、**未 `await` 的异步断言会直接失败**
- ⭐ **四个断言的区别**：`toBe` = 引用/值相等（`Object.is`）；`toEqual` = 递归比较但**忽略 `undefined` 属性、不查类类型**；`toStrictEqual` = 递归且**严格**；`toContain` = 包含（数组元素 / 字符串子串 / 迭代器元素）
- **mock 三兄弟**：stub 预设值、spy 包住真实实现并记录、mock 假实现 + 断言能力；⭐ **DI（依赖注入）是最推荐的可测试性手段**
- ⚠️ **不要过度 mock**：判据是「把函数体换成 `return undefined`，测试还过吗？」——过就说明断言没用
- ⭐ **错误分层**：**预期错误 → 返回值（`Result`）**；**意外错误 → `throw`**；**不要用异常做流程控制**
- ⭐ **自定义 Error**：`extends Error` + 设 `this.name` + 稳定 `code` + ES2022 `cause`；⚠️ **ES5 target 下 `instanceof` 会失效**，用 `Object.setPrototypeOf(this, new.target.prototype)` 修（`target: es5` 在 TS 6.0 已废弃、TS 7.0 变硬错误）
- ⭐ **`unknown` 收窄是 TS 错误处理主线**：strict 下 `catch (e)` 的 `e` 是 `unknown`（因为 JS 允许 `throw` 任何东西），必须 `instanceof` / 属性检查 / 类型谓词收窄后才能用
- **`asserts v is T` 断言函数**：调用后直接收窄，不需要 `if`；约束：必须显式标注返回类型、只能断言变量不能断言属性
- ⚠️ **错误信息要有上下文**（什么操作 + 哪个实体 + 关键输入），但**不能带敏感数据**

## 练习

1. 画一张测试金字塔图，写出你上一个项目里三层的实际数量，并估算改成建议比例后的 CI 时长变化。
2. 用 Vitest 写一个 `divide(a, b)` 的测试文件，至少覆盖：正常除法、除数为 0、小数、负数、边界值。**同一组断言，分别用 `toBe` / `toEqual` / `toStrictEqual` 各写一遍**，说清它们在这个例子里为什么结果相同。
3. 构造两个对象，让 `toEqual` 通过但 `toStrictEqual` 失败（提示：`undefined` 属性、`class` 实例）。写下你的例子和解释。
4. 写一个测试，验证 `expect(() => fn()).toThrow()` 和 `expect(fn()).toThrow()` 的**失败信息差异**（故意写错，看报错长什么样）。
5. 用 `vi.fn()` 实现一个假的 `sendEmail`，测试「注册用户成功后会发一封确认邮件」。然后改成用**依赖注入**的方式重写这个测试，对比两者的可读性。
6. 用 `vi.spyOn` 断言「下单成功会记录一条日志」，并演示忘记 `mockRestore()` 会导致后续测试失败的现象。
7. 设计一个「mock 过度」的反例：写一个测试，它 mock 掉了被测函数的大部分逻辑，然后证明这个测试在真实实现被破坏时**依然通过**。
8. 把一段用 `throw` 表达业务分支的代码改写成 `Result` 判别联合，并说明调用方代码会怎么变。
9. 实现 `AppError` + `ValidationError` + `NotFoundError`，写一个测试断言 `err instanceof ValidationError` 为 `true`。然后把 `tsconfig.json` 的 `target` 改成 `es5`，重新编译运行，观察测试是否还通过——解释原因并给出修法。
10. 在 `catch (e: unknown)` 里，分别用 `instanceof`、属性检查（duck typing）、`toError()` 辅助函数三种方式写一遍同样的错误处理，比较三者的适用范围。
11. 写一个 `assertIsConfig(v: unknown): asserts v is Config`，然后故意写一个"断言属性"的版本，看 TS 报什么错，并解释为什么 TS 不允许断言属性。
12. 写一个测试，故意在 `finally` 块里 `return` 一个值，观察它如何吞掉 `try` 块抛出的错误；对比 `.finally` 的行为。
