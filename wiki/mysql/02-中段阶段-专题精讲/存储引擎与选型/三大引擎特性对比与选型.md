# 三大引擎特性对比与选型

> **什么时候该读**：想系统搞清 InnoDB、MyISAM、MEMORY 三大引擎**各自有什么特性、逐项差在哪、什么时候该用哪个**；或者被面试问到「InnoDB 和 MyISAM 的区别」想要一份完整答案。

## 学习目标

读完本篇，你应当能够：

1. 逐一说出三大引擎的特性清单（而不是只背一句「InnoDB 支持事务」）
2. 用机制解释三个最容易考的区别：**锁粒度、崩溃行为、`COUNT(*)`**
3. 给一个具体场景时，快速判断该用哪个引擎（以及大多数时候为什么答案都是 InnoDB）
4. 说出三大引擎各自的「现代替代品」

## 一、三句话画像（先给结论）

| 引擎 | 一句话画像 |
|------|-----------|
| ⭐ **InnoDB** | 全能型事务引擎：行锁 + MVCC + 崩溃恢复，**MySQL 5.5（2010）起的默认引擎，生产唯一通用推荐** |
| **MyISAM** | 前默认引擎（2000 年代主力）：表锁、无事务、结构简单、只读快；⚠️ 今天只剩「遗留兼容 + 只读压缩归档」价值 |
| **MEMORY** | 内存表：数据全在 RAM，重启清空；⚠️ 官方已明说适用场景在萎缩，**今天没有推荐场景** |

⭐ **选型的现代答案很短：新表一律 InnoDB。** 但「为什么」和「例外是什么」必须搞清楚——这正是本篇余下部分的内容。

## 二、InnoDB：特性逐项拆

### 特性清单

| 特性 | 说明 | 版本 |
|------|------|------|
| **事务（ACID）** | 四个隔离级别，默认 **RR（可重复读）**；完整机制见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/为什么只有InnoDB支持事务]] | 长期 |
| **MVCC** | 多版本并发控制：读不阻塞写。每行带隐藏版本信息，读旧版本不用等写完 | 长期 |
| **行级锁** | 只锁被改的行，并发写不同行互不阻塞；RR 下还有间隙锁 / Next-Key Lock | 长期 |
| **外键** | `FOREIGN KEY` 真正生效的引擎 | 长期 |
| **崩溃恢复** | 断电重启后自动把数据恢复到一致状态（redo 重放 + undo 回滚），**不需要人工修表** | 长期 |
| **聚簇索引组织** | 数据本身按主键组织成 B+ 树（详见 [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]]） | 长期 |
| **Buffer Pool** | 数据页内存缓存，InnoDB 性能的核心（同上） | 长期 |
| **全文索引** | `FULLTEXT` | ⚠️ **5.6 起才支持**（此前是 MyISAM 独占） |
| **空间索引** | GIS 数据的 `SPATIAL INDEX` | 5.7+ |
| **自适应哈希索引（AHI）** | 对热点等值查询自动建内存哈希，加速查找 | 长期 |
| **Change Buffer** | 二级索引写入的缓冲优化（见专题概览第五节） | 长期 |
| **在线 DDL** | 大部分 DDL 不锁表（`ALGORITHM=INSTANT`/`INPLACE`） | 8.0 增强 |
| **行格式可压缩** | `ROW_FORMAT=COMPRESSED` | 长期 |

### 它为这些能力付出的代价

| 代价 | 说明 |
|------|------|
| **写入更重** | 每次修改要写 redo、维护 undo 版本链——「写放大」；但换来的是安全 |
| **结构复杂** | 表空间、双写缓冲、崩溃恢复流程——每个都要懂一点才能调优 |
| **`COUNT(*)` 不免费** | 因为 MVCC（不同事务看到的行数可能不同），InnoDB **没有**「全局精确行数」可存，无 WHERE 的 `COUNT(*)` 也要扫——见第六节 |

⭐ **一句话：InnoDB 的每个「慢一点」都是在为「不丢数据、并发高、崩溃自愈」付费。**

## 三、MyISAM：特性逐项拆

### 特性清单

| 特性 | 说明 |
|------|------|
| **表级锁** | 任何读写操作锁**整张表**。读锁之间共享；写锁独占——⭐ 这是它并发能力的死穴，见第六节 |
| **无事务** | 每条语句执行即生效，`ROLLBACK` 不回滚它（原因与证据见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/为什么只有InnoDB支持事务]]） |
| **无崩溃恢复** | 磁盘上只有 `.MYD`（数据）+ `.MYI`（索引）**两个文件，没有任何日志**；崩溃后靠「关闭标志位 + 修复（REPAIR）」，⭐ **修复可能丢数据** |
| **无外键** | ⚠️ `FOREIGN KEY` 语法**不报错但被静默丢弃**——完整性假象 |
| **键缓存（key cache）** | ⚠️ 只缓存**索引**（参数 `key_buffer_size`）；**数据不缓存**，靠操作系统页缓存——与 InnoDB Buffer Pool（数据+索引都缓存）的关键区别 |
| **非聚簇索引** | 索引叶子存的是「数据文件中的地址偏移」，不是行数据本身；查任何索引都要**按地址回数据文件取行** |
| **并发插入（concurrent insert）** | ⭐ 罕见优点：数据文件中间**没有空洞**时，`INSERT` 可与 `SELECT` 同时进行（新行追加到文件尾部，互不干扰） |
| **`myisampack` 只读压缩** | 压成只读表，体积显著缩小——⭐ 今天它仅存的实际价值 |
| **`COUNT(*)` 免费** | 无 WHERE 的 `COUNT(*)` 直接返回存储好的行数，O(1)——⭐ 经典面试点，见第六节 |
| **全文索引** | 最早支持 `FULLTEXT` 的引擎；但 InnoDB 5.6 起已补齐 |
| **`BLOB`/`TEXT` 可索引** | 该能力 InnoDB 5.6 起也有 |
| **⚠️ 无分区** | **MySQL 9.7 起 MyISAM 不再支持分区**（老版本建的分区 MyISAM 表在 9.7 中不可用） |

### 磁盘文件对比（一眼看懂结构差异）

```
MyISAM 表 t：                    InnoDB 表 t（innodb_file_per_table=ON）：
  t.frm   表结构（8.0 前有）        t.ibd   数据 + 索引 + 字典信息（一整个）
  t.MYD   数据
  t.MYI   索引
  （没有日志文件！）
```

⭐ **「没有日志文件」是理解 MyISAM 一切的钥匙**：没有 undo → 不能回滚；没有 redo → 崩溃不能恢复；这两样都没有 → 「事务」「崩溃安全」无从谈起。

## 四、MEMORY：特性逐项拆

### 特性清单

| 特性 | 说明 |
|------|------|
| **数据全在内存** | 崩溃 / 断电 / 重启即失。⭐ **表定义还在**（存在数据字典里），重启后表存在但**是空的** |
| **默认哈希索引** | 等值查找 O(1)；⚠️ **哈希不支持范围查询**（`>`、`<`、`ORDER BY`、`LIKE 'x%'` 都用不上），需要范围就显式建 `USING BTREE` |
| **固定长度行** | `VARCHAR(100)` 也按 100 字符占位（相当于按 `CHAR` 存）——存变长数据会**浪费大量内存** |
| **不支持 `BLOB`/`TEXT`** | 定位就是「小查找表」，存不了大字段 |
| **表级锁** | 写并发能力≈0；官方明说：繁忙负载下**不一定比 InnoDB 快** |
| **大小上限** | 受 `max_heap_table_size` 控制，**默认 16MB**——超了报错（表已满） |
| **无事务、无持久性** | 连「重启后还在」都不承诺，事务无从谈起 |

### 它的三个「现代替代品」

| 你想要 MEMORY 给的 | 现代替代 |
|---|---|
| 内存级临时计算（排序、分组中间结果） | 什么都不用做——MySQL **内部临时表** 8.0 起默认已用 **TempTable** 引擎，不是 MEMORY |
| 内存缓存热点数据 | **Redis**（见 [[redis/01-入门阶段-基础教程/第00章-学前准备/0.1-Redis是什么]]）；或干脆让 InnoDB 的 Buffer Pool 吃够内存 |
| 内存型 + 高可用 + 事务 | **NDB Cluster**（内存型且支持事务，但那是分布式集群形态，不是单机选项） |

⭐ **结论：MEMORY 在今天的 MySQL 里没有「必须用它」的场景。** 官方 9.7 手册也明确说它的 use cases are decreasing。

## 六、三个关键区别的机制拆解（面试高频）

### 区别一：表锁 vs 行锁，到底差在哪

同一时刻：会话 A 在**改第 1 行**，会话 B 想**改第 100 万行**。

```
MyISAM（表锁）：
  A: UPDATE t SET v=1 WHERE id=1;     → 锁住整张表
  B: UPDATE t SET v=1 WHERE id=1000000;
     → ⚠️ 阻塞，等 A 提交才轮到 B（哪怕两行毫无交集）

InnoDB（行锁）：
  A: UPDATE t SET v=1 WHERE id=1;     → 只锁 id=1 那行
  B: UPDATE t SET v=1 WHERE id=1000000;
     → ⭐ 直接执行，互不阻塞
```

⚠️ 三个连带后果：

1. **读写也互斥**：MyISAM 一个长 `SELECT` 会卡住所有 `UPDATE`/`INSERT`；InnoDB 的普通 `SELECT` 是 MVCC 快照读，**不锁任何东西**；
2. **「读快」是有条件的**：MyISAM 只在**纯只读 / 读多写极少**时占优；一旦有并发写，表锁立即成为瓶颈；
3. **锁是引擎层特性**：MySQL 的锁机制下放到了引擎层（见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]），所以「换引擎」会直接改变并发行为。

### 区别二：崩溃与重启后，三者各是什么状态

假设 INSERT 已提交、随后服务器断电：

| 引擎 | 重启后那行数据 | 靠什么 |
|------|--------------|--------|
| ⭐ InnoDB | **在**，且一致 | redo 重放（已提交的补回）+ undo 回滚（未提交的撤掉），全自动。机制见 [[mysql/03-进阶阶段-深度剖析/日志与复制内核/原理剖析-redo日志与WAL]] |
| MyISAM | **不确定** | 表有「是否正确关闭」标志位；配了 `myisam_recover_options` 时打开表自动修复，否则要人工 `REPAIR TABLE` / `myisamchk`。⭐ **修复 = 尽量能用，不保证不丢** |
| MEMORY | **没了** | 数据在 RAM 里，断电即失。表定义还在，内容为空 |

⭐ 这张表是「为什么生产库必须 InnoDB」的最直接答案：**生产环境的断电不是「会不会」，是「什么时候」。**

### 区别三：为什么 MyISAM 的 `COUNT(*)` 是 O(1)，InnoDB 不是

```sql
SELECT COUNT(*) FROM t;   -- MyISAM: 瞬间返回；InnoDB: 要数一遍
```

- **MyISAM**：行数就存在表元信息里（它没有 MVCC，任何时刻所有人看到的行数都一样）→ 直接读出来；
- **InnoDB**：⚠️ **有 MVCC**——同一个时刻，事务 X 可能看见 100 行，事务 Y 看见 105 行（Y 的快照更新）。**「全局行数」这个概念在 MVCC 下不存在唯一正确值**，所以 InnoDB 干脆不存，每次数（走最小的索引也要扫）。

两个补充，防止背了半句去答题：

1. MyISAM 的 O(1) **仅限无 WHERE**；`COUNT(*) WHERE status=1` 一样要走索引统计；
2. ⚠️ InnoDB 优化器会自动选**最小的索引**来数（降低扫描成本），但复杂度仍是 O(n)。

⭐ 深层原因（MVCC 如何让每行有多个版本）见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]]。

## 七、什么时候用哪个（选型决策）

### 决策表

| 你的场景 | 用什么 | 说明 |
|---------|--------|------|
| 业务表：要持久、要并发、可能参与事务 | ⭐ **InnoDB**（默认，不用想） | 覆盖 99% 的场景 |
| 需要全文搜索 | InnoDB（5.6+ 的 `FULLTEXT`） | 数据量大到 InnoDB 全文吃力时，交给搜索引擎（ES / Meilisearch），**不是换 MyISAM** |
| 只读压缩归档（历史数据，几乎不查） | ⚠️ 首选 **ARCHIVE** 引擎或 InnoDB `COMPRESSED` 行格式；`myisampack` 只在维护**已有的** MyISAM 压缩表时用 | MyISAM 压缩是历史方案 |
| 内部临时计算（排序/分组） | 不用选——**TempTable** 自动接管（8.0 起内部临时表默认引擎） | MEMORY 已退出这个位置 |
| 应用层缓存 | **Redis** | 不要用 MEMORY 表当缓存 |
| 内存型 + 高可用 + 事务 | **NDB Cluster** | 分布式形态，非单机 |
| 老库里已有的 MyISAM 表 | 评估后迁到 InnoDB | 全流程见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/引擎全景与迁移实操]] |

### 「MyISAM 还有什么用」——2026 年的诚实回答

| 曾经的理由 | 现状 |
|-----------|------|
| 读快 | ⚠️ 只在纯只读 + 无并发写下成立；InnoDB Buffer Pool 吃够内存后差距很小 |
| 表小、结构简单 | ✅ 属实，但「简单」换不来数据安全 |
| `myisampack` 压缩归档 | ⚠️ 仍可用，但 ARCHIVE / InnoDB 压缩行格式是更现代的选择 |
| 全文索引 | InnoDB 5.6 起已补齐 |
| `COUNT(*)` 快 | 仅无 WHERE；业务上很少为这个换引擎 |

⭐ **实际工作中的两类 MyISAM 表**：① 老系统遗留（迁）；② 极端只读压缩归档（可留，但要接受「无事务、崩溃可能丢、9.7 无分区」）。除此之外没有新场景。

### MEMORY 的使用红线

1. **⚠️ 不要当缓存**——重启清空 + 表级锁，两个特性都和「缓存」矛盾；
2. **⚠️ 不要存变长大字段**——定长占位，内存浪费严重；
3. **⚠️ 唯一勉强成立的用法**：进程生命周期内的临时查找表（重启就重建也没关系的小维表）。但这类需求临时表（InnoDB/TempTable）通常做得更好。

## 八、实操：三步确认与改变引擎

```sql
-- ① 看一张表现在是什么引擎
SHOW CREATE TABLE t\G          -- 看 ENGINE= 后面的值
SHOW TABLE STATUS LIKE 't'\G   -- Engine 列

-- ② 看实例支持哪些引擎（Transactions 列=引擎自己申报的事务能力）
SHOW ENGINES\G

-- ③ 改变引擎（⚠️ 是重建整张表，大表代价评估见迁移篇）
ALTER TABLE t ENGINE=InnoDB;
```

建表时显式指定（生产习惯，别依赖默认值）：

```sql
CREATE TABLE t (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  v VARCHAR(64) NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 九、陷阱

1. **⚠️ 背「InnoDB 支持事务，MyISAM 不支持」就以为自己懂区别了。** 面试和排错真正考的是**机制**：为什么（没有 undo/redo）、锁差在哪（表锁 vs 行锁）、崩溃后各怎样（恢复 vs 修复 vs 清空）。本篇第六节就是这三问的完整答案。
2. **⚠️ 以为「MyISAM 读永远比 InnoDB 快」。** 只在纯只读、无并发写时可能成立；有写就撞表锁。
3. **⚠️ 以为 MyISAM 上的 `FOREIGN KEY` 在保护数据。** 它被静默丢弃，约束从未生效——迁移 InnoDB 前先查孤儿数据（SQL 见迁移篇）。
4. **⚠️ 用 MEMORY 表当缓存或存会话。** 重启清空 + 默认 16MB 上限 + 表级锁；缓存用 Redis。
5. **⚠️ MEMORY 表建了哈希索引还做范围查询。** 默认哈希索引不支持 `>`/`<`/`ORDER BY`，要显式 `USING BTREE`。
6. **⚠️ 把「内部临时表用 MEMORY」当成 8.0 的行为。** 8.0 起内部临时表默认是 **TempTable**；用户自建的 `CREATE TEMPORARY TABLE` 默认 InnoDB。
7. **⚠️ 用 `myisampack` 的表当在线归档。** 压缩表是**只读**的，连 `INSERT` 都不行。
8. **⚠️ 新项目因为「查询快」选 MyISAM。** 2010 年（5.5）起官方就用默认值回答过这个问题了。

## 小结

- **InnoDB**：事务 + MVCC + 行锁 + 外键 + 崩溃恢复 + 聚簇索引 + Buffer Pool；代价是写入重、结构复杂、`COUNT(*)` 要扫——⭐ 生产唯一通用推荐
- **MyISAM**：表锁 + 无事务 + 无日志（只有 `.MYD`/`.MYI` 两个文件）→ 崩溃只能「修复」（可能丢数据）；优点：轻、只读快、`myisampack` 压缩、并发插入；⚠️ 9.7 起无分区——**只剩遗留兼容与只读压缩归档价值**
- **MEMORY**：全内存、重启清空、默认哈希索引、定长行、`max_heap_table_size` 上限（默认 16MB）——**今天没有推荐场景**，内部临时表已归 TempTable，缓存归 Redis
- 三大高频区别的机制：**表锁 vs 行锁**（并发写互不阻塞的前提）、**恢复 vs 修复 vs 清空**（断电后三种命运）、**`COUNT(*)` O(1) 的前提是无 MVCC**
- 选型速答：**新表一律 InnoDB**；例外都指向专用引擎（ARCHIVE / TempTable / Redis / NDB），而不是 MyISAM / MEMORY
