# 为什么只有 InnoDB 支持事务

> **什么时候该读**：学完 [[mysql/01-入门阶段-基础教程/第04章-事务与权限/4.1-事务与ACID]] 后想不通「事务这么重要，MySQL 为什么还留着不支持事务的引擎」；或者老库里发现了 `ENGINE=MyISAM` 的表，想知道该不该动它。

## 学习目标

读完本篇，你应当能够：

1. 说出事务需要哪四套机制，以及为什么「只加一半」不成立
2. 用机制解释 MyISAM 为什么没有事务（而不是背结论）
3. 解释 MEMORY 为什么没有事务（它连持久性都不承诺）
4. 说清 MySQL 与 PostgreSQL 在「事务归谁管」上的架构差异
5. 知道 NDB 这个反例说明了什么

## 一、一句话答案

**不是「InnoDB 实现了、别的引擎忘了实现」，而是三件事叠加的结果：**

1. **架构**：MySQL 把「事务」下放到了**存储引擎层**——要不要事务，是每个引擎自己决定的，Server 层不管；
2. **机制**：事务不是开关，而是 undo / redo / 行锁 / MVCC / 崩溃恢复**一整套互相咬合的设施**，没法只加一半；
3. **取舍**：这套设施的代价（写放大、内存、锁簿记、复杂度）正是 MyISAM 与 MEMORY 的设计目标要避开的东西——它们要的是「小、简单、快」。

⚠️ 还有一层历史原因：InnoDB 从来不是 MySQL 自己写的引擎，而是「外来的事务引擎」（见第七节）。

---

## 二、事务不是开关，是一整套地基

### ACID 每一条承诺，背后都压着一套机制

| ACID | 承诺 | 需要的机制 |
|------|------|-----------|
| **原子性（A）** | 要么全成，要么全撤 | **undo 日志**：记下修改前的旧值，用于回滚 |
| **隔离性（I）** | 并发事务互不干扰 | **行级锁 + MVCC**（快照读 + undo 版本链） |
| **持久性（D）** | 提交了就不丢 | **redo 日志**（WAL）：提交时 fsync，崩溃后重放 |
| **一致性（C）** | 状态只在合法值之间转移 | 前三条 + 约束检查 |

### 四套机制互相咬合

- **undo 一份日志两用**：既做回滚（A），又是 MVCC 的版本链（I）——见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]]；
- **崩溃恢复 = redo + undo 配合**：先重放 redo（把已提交的补回来），再回滚 undo（把未提交的撤掉）；
- **行锁与 MVCC 共同实现隔离级别**——见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

⚠️ **组合反例**（说明为什么不能只加一半）：

| 只有… | 结果 |
|------|------|
| 只有 undo，没有 redo | 能回滚，但**已提交的事务会因断电消失**（D 破了） |
| 只有 redo，没有 undo | 崩溃后**未提交的脏数据被当成事实重放**（A 破了） |
| 有锁没有 MVCC | 读会阻塞写，并发度暴跌（能工作，但代价巨大） |

⭐ **所以「给某个引擎加事务」，本质是「给它加一整层子系统」。**

### 官方把这件事写在明面上

```sql
mysql> SHOW ENGINES\G
 Engine: InnoDB   Support: DEFAULT
Transactions: YES   XA: YES   Savepoints: YES   ← 连 SAVEPOINT（保存点）都是引擎级能力
 Engine: MyISAM   Support: YES
Transactions: NO    XA: NO    Savepoints: NO
```

⭐ `SHOW ENGINES` 的 `Transactions` / `XA` / `Savepoints` 三列，就是「引擎自己申报的事务能力」。MyISAM 三列全为 `NO`——它连 `SAVEPOINT` 语法都不支持。

---

## 三、MyISAM：目标是「小、简单、读快」，事务正好是代价

### 官方定位

MySQL 9.7 手册对 MyISAM 的描述是：**表体积小（small footprint）**；表级锁限制了读写混合负载的表现，所以常用于**只读或读多写少的 Web 与数据仓库场景**。

### 机制上缺什么：具体到文件就能看清

- 每张 MyISAM 表在磁盘上**只有两个文件**：`.MYD`（数据）+ `.MYI`（索引）。**没有任何日志文件**——所以没有 undo 可回滚，也没有 redo 可重放。对照 InnoDB 的表空间 + redo + undo，差别一目了然；
- 崩溃处理（官方原文）：索引文件里存了一个「表是否被正确关闭」的标志位；只有配了 `myisam_recover_options`，服务器才会在打开表时自动检查、必要时修复；否则要用 `mysqlcheck` / `myisamchk` / `REPAIR TABLE` 人工处理。

⚠️ **注意用词的差别：「修复」不是「恢复」。**

| | 修复（REPAIR） | 恢复（InnoDB 崩溃恢复） |
|---|---|---|
| 目标 | 把表修得**能用** | 保证**已提交的一定在、未提交的一定不在** |
| 依据 | 原始数据 + 索引重建 | redo 重放 + undo 回滚 |
| 代价 | ⚠️ 可能丢数据 | 自动、无损 |

### 两条可以直接复现的证据（8.4 上实测）

⚠️ **证据一：同一个事务里回滚，MyISAM 不听话。**

```sql
CREATE TABLE t_innodb (id INT PRIMARY KEY, v VARCHAR(20)) ENGINE=InnoDB;
CREATE TABLE t_myisam (id INT PRIMARY KEY, v VARCHAR(20)) ENGINE=MyISAM;

START TRANSACTION;
INSERT INTO t_innodb VALUES (1, 'x');
INSERT INTO t_myisam VALUES (1, 'x');
ROLLBACK;

SELECT COUNT(*) FROM t_innodb;   -- 0   ✅ 回滚成功
SELECT COUNT(*) FROM t_myisam;   -- 1   ⚠️ 行永久留下
```

原因：MyISAM 没有可回滚的日志，**每条语句执行即生效**（相当于自动提交），外面包一层 `START TRANSACTION` 对它没有意义。

⚠️ **证据二：MyISAM 对 `FOREIGN KEY` 语法不报错、约束被静默丢弃。**

```sql
CREATE TABLE child_myisam (
  id INT PRIMARY KEY, parent_id INT,
  FOREIGN KEY (parent_id) REFERENCES parent_myisam(id)
) ENGINE=MyISAM;

SHOW CREATE TABLE child_myisam;
-- 结果里只剩一个普通索引 KEY `parent_id`，⚠️ FOREIGN KEY 约束消失了
```

这说明 MyISAM 连「约束检查」这条线都没走。

### 它换来了什么

| 换来 | 说明 |
|------|------|
| 体积小 | 没有日志、没有表空间开销（官方原话 small footprint） |
| 只读压缩 | `myisampack` 可压成只读压缩表，显著省空间 |
| 并发插入 | 数据文件中间无空洞时，`INSERT` 与 `SELECT` 可并行 |
| `BLOB`/`TEXT` 可索引 | 该能力 InnoDB 要到 5.6 之后才有 |
| 存储上限大 | 256TB |

⭐ 这些优点全部来自「不维护额外设施」。**「不支持事务」在某些场景下不是缺陷，是低成本。**

### 它的空间还在收缩

⚠️ **MySQL 9.7 起，MyISAM 已不再支持分区**；在老版本创建的分区 MyISAM 表**在 9.7 中无法使用**。官方手册也把它和 MEMORY、CSV 等一起归入第 18 章 **Alternative Storage Engines**（替代/特殊用途引擎），与 InnoDB（第 17 章）、NDB（第 25 章）分开成章。

## 四、MEMORY：它连「持久」都不承诺

### 官方定位（几乎就是答案）

MEMORY 的数据**脆弱**——崩溃、硬件故障、断电即失；**只应用于临时工作区，或从别的表拉出来的只读缓存**。服务器重启后表还在（定义存在数据字典里），但**数据清空**。

### 推理一步就够：持久性是事务的一半

- **D（持久性）被它主动放弃了**——一个明确不承诺「重启后还在」的引擎，谈事务安全没有意义；
- 没有持久性，A 和 I 也失去业务价值：临时中间结果出错重算一遍即可，不需要回滚；
- 这也解释了它为什么**不需要**日志、锁管理和版本链。

### 它的特性全部指向「内存中快」，且都与事务相斥

| 特性 | 说明 |
|------|------|
| 固定长度行存储 | `VARCHAR` 按 `CHAR` 存（补空格），省了变长处理但浪费空间 |
| 默认哈希索引 | 等值查找 O(1)，⚠️ 但不支持范围查询（要显式建 `BTREE`） |
| 表级锁 + 单线程执行 | ⚠️ 写并发几乎为零 |
| 不支持 `BLOB`/`TEXT` | 定位就是小查找表 |
| 大小上限 | 受 `max_heap_table_size` 控制，默认 16MB |
| 重启丢数据 | **D 直接放弃** |

### ⚠️ 反直觉：MEMORY 不一定比 InnoDB 快

官方原话（大意）：MEMORY 的性能受**单线程执行**和**更新时的表锁开销**限制，在繁忙服务器上的通用查询、或读写混合负载下，**不一定比 InnoDB 表快**。

⭐ 官方 9.7 已明确说它的 **use cases are decreasing**（适用场景在减少），并给出现代替代：

- 想把数据放内存、又要通用和持久 → **InnoDB 的 Buffer Pool**（见 [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]]）；
- 想内存级键值查找 + 高可用 → **NDB**；
- 只是想缓存 → 用 Redis（见 [[redis/01-入门阶段-基础教程/第00章-学前准备/0.1-Redis是什么]]）。

## 五、反例：NDB 证明「内存型 + 事务」可以并存

| 引擎 | 内存型 | 事务 | 锁粒度 | 持久化 |
|------|-------|------|--------|--------|
| MEMORY | ✅ | ❌ | 表 | ❌ 重启即失 |
| **NDB** | ✅ | ⭐ **✅** | 行 | ⭐ 可选磁盘持久化 |

官方在 MEMORY 章节里直接推荐 NDB 作为替代，并列出它额外提供的能力：**行级锁、多线程、可选磁盘持久化、支持变长类型（含 `BLOB`/`TEXT`）**。

⭐ 所以 MEMORY 没有事务是**定位选择**，不是技术做不到：内存型引擎完全可以有事务（NDB 就是），只是 MEMORY 选择了「更轻、更临时」。

---

## 六、最根本的原因：事务被下放到了「引擎层」

### MySQL 的两层结构

```
Server 层：SQL 解析 · 优化器 · 执行器 · binlog（复制 / 时点恢复用）
    │
    ▼
存储引擎层（插件式）：InnoDB ✅事务 │ MyISAM ❌ │ MEMORY ❌ │ …
```

### 官方特性表把界线划得很清楚

| 能力 | 归属 |
|------|------|
| `Transactions`（事务）、`MVCC`、`Locking granularity`（锁粒度） | ⭐ **引擎自己的特性** |
| `Backup / PITR`、`Replication`、`Encryption` | ⚠️ 标注 **Implemented in the server**（服务器层提供） |

⚠️ **服务器层能给你 binlog（复制、按时间点恢复）、备份、加密；唯独给不了回滚、隔离和崩溃恢复**——这三件事必须由引擎实现。

⭐ 这也解释了「为什么 MyISAM 的复制还能用」：binlog 在 Server 层、与引擎无关，它只是**把语句照搬给从库**，不是事务保证。

### 与 PostgreSQL 的对照

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| 事务 / WAL / MVCC 在哪一层 | ⚠️ **存储引擎层**（各引擎自选） | ⭐ **核心层**（所有表共享） |
| 存储实现 | 插件式引擎（InnoDB / MyISAM / …） | 表访问方法（heap 等）+ 索引结构 |
| 换存储方式的影响 | ⚠️ **可能失去事务** | ⭐ 事务承诺不变 |
| 后果 | 「选引擎」是一个**影响正确性**的决定 | 不存在这种选择 |

📌 PG 侧的存储结构见 [[postgresql/03-进阶阶段-深度剖析/存储引擎与页结构/原理剖析-堆表与页结构]]。

⭐ 另一处体现「引擎 + 服务器协作」的地方：InnoDB 与 Server 层 binlog 之间靠**两阶段提交（内部 XA）**对齐，这对应 `SHOW ENGINES` 里 InnoDB 的 `XA: YES` 与 `Savepoints: YES`。

### 为什么会有两套日志（顺便回答一个常见疑问）

MySQL 历史上同时有 binlog（Server 层，用于复制）和 redo（引擎层，用于恢复）两套日志，这**不是设计出来的，是历史演进的产物**——binlog 比 InnoDB 更早存在。完整推导见 [[mysql/03-进阶阶段-深度剖析/日志与复制内核/原理剖析-redo日志与WAL]]。

## 七、历史：为什么当年会这样

| 时间 | 事件 |
|------|------|
| 1995 – 2000 年代 | MySQL AB 自研的引擎（`ISAM` → `MyISAM`、`HEAP` → `MEMORY`）诞生于「读多写少、单机、够快就行」的年代，目标是**轻与快**，没有事务需求 |
| 2000 前后 | ⭐ **InnoDB 作为第三方引擎被集成进来**——芬兰 Innobase Oy（Heikki Tuuri）开发，**从第一天就是事务引擎**，身份是「可选项」 |
| 2005-10 | Oracle 收购 Innobase Oy |
| 2008 | Sun 收购 MySQL AB |
| 2010 | Oracle 收购 Sun（MySQL 归 Oracle 所有） |
| **2010（MySQL 5.5）** | ⭐ **InnoDB 正式取代 MyISAM 成为默认引擎**——官方对「事务安全 > 单纯读性能」的正式表态 |
| 2013（5.6） | InnoDB 获得全文索引（MyISAM 的独占能力消失） |
| 2015（5.7） | InnoDB 获得空间索引 |
| 2018（8.0） | 数据字典迁入 InnoDB（`mysql.ibd`）；移除查询缓存（MyISAM 曾是其最大受益者） |

⭐ **结论**：官方对「为什么不给 MyISAM 加事务」的答案是——**不加，直接换成 InnoDB**。给 MyISAM 补上 undo/redo/行锁/MVCC/崩溃恢复之后，得到的那个东西就是 InnoDB。

## 八、陷阱

1. **⚠️ 以为「MySQL 8.0 已经移除 MyISAM」。** 是谣言——9.7 手册里 MyISAM 仍在（`SHOW ENGINES` 显示 `Support: YES`）。准确表述是「退化为特殊用途引擎」。详见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/引擎全景与迁移实操]]。
2. **⚠️ 在事务里混用 InnoDB 和 MyISAM 表。** 回滚只回滚 InnoDB 那部分——「用了事务却不原子」的最隐蔽形态。详见下篇。
3. **⚠️ 用 MEMORY 换性能。** 官方说它不一定更快，且重启丢数据。
4. **⚠️ 以为 MyISAM 上的 `FOREIGN KEY` 生效了。** 它是被静默丢弃的，数据完整性可能早已破损（见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]]）。
5. **⚠️ 以为 MyISAM「读一定比 InnoDB 快」。** 只在纯只读、无并发写的场景下可能成立；有写入时表锁会先成为瓶颈。

## 小结

- 事务 = **undo（A）+ 行锁/MVCC（I）+ redo（D）+ 约束（C）** 四套机制，互相咬合，不能只加一半
- **MySQL 把事务下放到了引擎层**（PG 放在核心层）→ 所以「换引擎」可能改变正确性保证
- **MyISAM**：只有 `.MYD`/`.MYI` 两个文件、**无日志**；崩溃靠「关闭标志位 + 修复」（修复 ≠ 恢复）；`ROLLBACK` 不回滚、`FOREIGN KEY` 静默丢弃
- **MEMORY**：连持久性都不承诺（重启丢数据）；固定长度行、表级锁、无 `BLOB`/`TEXT`、默认 16MB；⚠️ 官方说不一定比 InnoDB 快
- **NDB 是反例**：内存型**且**支持事务 → 说明这是定位选择，不是技术不能
- 历史上：MyISAM 是 MySQL 自研的「轻快」引擎，InnoDB 是后引入的**第三方事务引擎**，2010 年（5.5）才成为默认
- 官方对「给 MyISAM 加事务」的答案是**换成 InnoDB**
