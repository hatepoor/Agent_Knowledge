# 引擎全景与迁移实操

> **什么时候该读**：接手老库要盘点用了哪些引擎；看到 `ENGINE=MyISAM` 不确定要不要动；或者单纯想知道 MySQL 到底有哪些引擎、各自什么定位。

## 学习目标

读完本篇，你应当能够：

1. 说出 MySQL 9.7 支持的全部引擎及一句话定位
2. 用 `SHOW ENGINES` / `information_schema` 盘点实例里的引擎
3. 安全地把 MyISAM 表迁移成 InnoDB
4. 分清「版本事实」与「网络谣言」
5. 避开混引擎事务的坑

## 一、引擎全景表（MySQL 9.7）

> 数据来源：MySQL 9.7 参考手册 Table 18.1「Storage Engines Feature Summary」+ `SHOW ENGINES` 输出（2026-10-14 核对）。

| 引擎 | 事务 | MVCC | 锁粒度 | 外键 | 全文索引 | 存储上限 | 一句话定位 |
|------|------|------|--------|------|---------|---------|-----------|
| ⭐ **InnoDB** | ✅ | ✅ | 行 | ✅ | ✅（5.6+） | 64TB | **默认引擎，生产唯一推荐** |
| MyISAM | ❌ | ❌ | 表 | ❌ | ✅ | 256TB | 只读/读多写少的遗留场景；⚠️ 9.7 起无分区 |
| MEMORY | ❌ | ❌ | 表 | ❌ | ❌ | RAM | 临时工作区/只读缓存；⚠️ 重启丢数据 |
| CSV | ❌ | ❌ | — | ❌ | ❌ | — | 逗号分隔文本表，**无索引**；导入导出中间态 |
| ARCHIVE | ❌ | ❌ | 行 | ❌ | ❌ | 无明确上限 | 压缩、**无索引**，只支持 `INSERT`/`SELECT`；冷归档 |
| BLACKHOLE | ❌ | ❌ | — | ❌ | ❌ | — | 接受写入但**不存数据**，查询恒为空；复制中继 |
| MERGE | ❌ | ❌ | — | ❌ | ❌ | — | 把多张同构的 **MyISAM** 表逻辑上合并成一张 |
| FEDERATED | ❌ | ❌ | — | ❌ | ❌ | — | 访问远端 MySQL 的表，本地只存定义；⚠️ 默认关闭 |
| EXAMPLE | ❌ | ❌ | — | ❌ | ❌ | — | 源码示例（存不了数据），仅供开发插件参考 |
| NDB（NDBCLUSTER） | ⭐ ✅ | ❌ | 行 | ✅ | ❌ | 384EB | 内存型分布式集群；⚠️ 只在 NDB Cluster 构建中提供 |

⚠️ 两个容易看错的地方：

- `SHOW ENGINES` 里还会看到 `PERFORMANCE_SCHEMA`——它是性能监控信息的承载结构，**不是给你建表用的引擎**，别当成选项；
- `MRG_MYISAM` 就是 MERGE 在 `SHOW ENGINES` 里的名字。

## 二、按定位分三组（背诵版）

| 组 | 引擎 | 什么时候会见到 |
|---|---|---|
| **生产默认** | InnoDB | 一切新表。默认值，不用想 |
| **特殊用途** | CSV / ARCHIVE / BLACKHOLE / MERGE / FEDERATED / EXAMPLE / MEMORY | 导入导出、归档、复制中继、临时工作区 |
| **集群** | NDB | 需要分布式高可用时（独立形态，不在单机 MySQL 里） |
| **兼容遗留** | MyISAM | 老库、从老备份恢复出来的表 |

⭐ 判断标准很简单：**只有 InnoDB 是「通用引擎」**，其余都是为某个具体场景存在的专用件。

## 三、⚠️ 版本事实（先破除谣言）

| 常见说法 | 事实 |
|---|---|
| ⚠️「MySQL 8.0 已彻底移除 MyISAM / 默认禁用」 | ❌ **不成立**。9.7 手册里 MyISAM、MEMORY 都有独立章节（第 18 章 *Alternative Storage Engines*），`SHOW ENGINES` 里 `Support: YES`。⚠️ 中文网络这类说法与官方手册矛盾，**不要引用** |
| 「InnoDB 是默认引擎」 | ✅ 但从 **MySQL 5.5（2010）** 起才是；之前默认是 MyISAM |
| 「MyISAM 还能用，和以前一样」 | ⚠️ 不完全。**9.7 起 MyISAM 不再支持分区**，老版本创建的分区 MyISAM 表在 9.7 中不可用 |
| 「MEMORY 在 8.0 还是临时表的默认引擎」 | ⚠️ 不是。8.0 起**内部临时表**默认用 **TempTable**（参数 `internal_tmp_mem_storage_engine`），取代了 MEMORY；用户自己 `CREATE TEMPORARY TABLE` 则默认 InnoDB |
| 「系统表还是 MyISAM」 | ⚠️ 8.0 起系统表与数据字典已迁入 InnoDB（`mysql.ibd`） |

⭐ **一句话**：MyISAM/MEMORY 都没有被移除，但定位已从「可选项」退化为「兼容遗留 + 特殊用途」。

## 四、实操一：盘点库里有哪些非 InnoDB 表

```sql
-- ① 看本实例支持哪些引擎、是否支持事务
SHOW ENGINES\G

-- ② 找出所有非 InnoDB 的用户表（老库排查的核心语句）
SELECT table_schema, table_name, engine, table_rows,
       ROUND(data_length/1024/1024, 1) AS data_mb
FROM information_schema.tables
WHERE table_schema NOT IN ('mysql','sys','information_schema','performance_schema')
  AND engine IS NOT NULL
  AND engine <> 'InnoDB'
ORDER BY data_length DESC;
```

⚠️ 两个注意点：

- 8.0 起 `information_schema` 是数据字典之上的**视图**，查询本身有成本，大实例上别频繁全表扫；
- `table_rows` 是**估算值**（InnoDB 尤其不准），要精确行数得 `COUNT(*)`。

## 五、实操二：把 MyISAM 迁移到 InnoDB

```sql
-- 核心语句就一条：重建表并换引擎
ALTER TABLE t ENGINE=InnoDB;
```

⚠️ **代价必须提前评估**：

| 项 | 说明 |
|---|---|
| 重建 | 这条语句是**复制整张表**，不是原地改个标记 |
| 空间 | 需要**约等于原表体积的额外空间**（新旧表并存） |
| 锁与耗时 | 会较长时间占用资源；大表要放到低峰期，或用在线工具 |
| 大表方案 | `pt-online-schema-change` 或 `gh-ost`（见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]） |

**迁移前检查清单**：

1. **有备份**（或确认可回滚）——见 [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]]；
2. 表的大小与行数（决定是否改用在线工具）；
3. 表上有没有**目标引擎不支持的特性**（MyISAM 特有的分区、行格式、`FULLTEXT` 的差异等）——⚠️ 不支持的会报错或丢失；
4. ⚠️ **心理预期**：MyISAM 上被静默忽略的 `FOREIGN KEY`，意味着**数据完整性可能早已破损**；转成 InnoDB 后新建约束会把这些脏数据暴露出来。**先查再转**：

```sql
-- 转换前先自查「孤儿数据」是否存在
SELECT COUNT(*) FROM child c
LEFT JOIN parent p ON p.id = c.parent_id
WHERE p.id IS NULL;
```

## 六、⚠️ 混引擎事务不原子（最容易踩的坑）

```sql
CREATE TABLE t_i (id INT PRIMARY KEY, v INT) ENGINE=InnoDB;
CREATE TABLE t_m (id INT PRIMARY KEY, v INT) ENGINE=MyISAM;

START TRANSACTION;
INSERT INTO t_i VALUES (1, 1);
INSERT INTO t_m VALUES (1, 1);   -- ⚠️ MyISAM：语句立即生效
ROLLBACK;

SELECT COUNT(*) FROM t_i;   -- 0  ✅ 回滚了
SELECT COUNT(*) FROM t_m;   -- 1  ⚠️ 永久留下
```

⭐ 原因见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/为什么只有InnoDB支持事务]]：MyISAM 没有 undo 日志，事务边界对它没有意义。

⚠️ 两个更隐蔽的后果：

1. **你以为的「原子操作」只保护了一半**——比如扣款成功、日志表（MyISAM）写了一半，回滚后仍然不一致；
2. **迁移到 InnoDB 不会自动修复历史脏数据**——它只让**今后**的事务变得可靠。

**处置原则**：凡是要参与事务的表，一律 InnoDB；确实不能转的（例如只读归档），就把它的操作**移出事务**，并在业务上明确接受「它不是原子的」。

## 七、选型速判

> ⚠️ 本表按「需求 → 引擎」速查；三大引擎（InnoDB / MyISAM / MEMORY）的**特性逐项对比与机制拆解**（锁粒度 / 崩溃行为 / `COUNT(*)`）见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/三大引擎特性对比与选型]]。

| 你的需求 | 用什么 |
|---|---|
| 任何需要事务 / 并发写 / 外键的场景 | ⭐ **InnoDB**（默认，不用想） |
| 临时一次性工作区 | InnoDB 临时表或内部 TempTable——⭐ **不要 MEMORY** |
| 只读归档、几乎不查、要省空间 | ARCHIVE（⚠️ 不能 `UPDATE`/`DELETE`，无索引） |
| 与外部系统交换 CSV | CSV（⚠️ 无索引，只做导入导出中间态） |
| 复制中继、丢弃写入 | BLACKHOLE |
| 需要内存级键值 + 高可用 | NDB Cluster（⚠️ 非单机部署形态） |
| 老库里的 MyISAM | 迁移到 InnoDB（见第五节） |

## 八、陷阱

1. **⚠️ 相信「MyISAM 已被移除」。** 官方手册与 `SHOW ENGINES` 都能证伪。
2. **⚠️ 用 MEMORY 当缓存换性能。** 官方：不一定更快，且重启丢数据 → 用 InnoDB Buffer Pool 或 Redis。
3. **⚠️ 在事务里混用引擎。** 回滚只有一半生效。
4. **⚠️ 直接对大表 `ALTER TABLE ... ENGINE=InnoDB`。** 复制全表 + 双倍空间，先评估、再用在线工具。
5. **⚠️ 用 ARCHIVE 存要查询的历史数据。** 它没有索引，查询只能全表解压扫描。
6. **⚠️ 迁移前不查孤儿数据。** MyISAM 上失效的外键会让脏数据在迁移后集中爆发。

## 小结

- 引擎全景：**InnoDB 是唯一通用引擎**，其余（CSV/ARCHIVE/BLACKHOLE/MERGE/FEDERATED/EXAMPLE/MEMORY）都是专用件；NDB 专注分布式集群
- 排查用 `SHOW ENGINES` + `information_schema.tables`（筛 `engine <> 'InnoDB'`）
- 迁移用 `ALTER TABLE t ENGINE=InnoDB`——⚠️ 它是**重建表**：要双倍空间，大表用 `pt-osc` / `gh-ost`
- ⚠️ **混引擎事务不原子**：MyISAM 的部分不会回滚
- ⚠️ 版本事实：MyISAM/MEMORY **未被移除**；9.7 起 MyISAM 无分区；内部临时表默认已是 TempTable
