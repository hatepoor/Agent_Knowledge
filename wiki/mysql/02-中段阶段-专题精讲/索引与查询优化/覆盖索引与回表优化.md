# 覆盖索引与回表优化

> **什么时候该读**：查询类型是 `ref`/`range`（说明索引生效了），但数据量大时仍觉得慢——很可能是回表次数太多。

## 学习目标

读完本篇，你应当能够：

1. 说清「回表」的过程及其代价
2. 识别并构造**覆盖索引**
3. 理解**索引下推（ICP）**如何减少回表
4. 权衡「覆盖索引」带来的存储与写入代价
5. 知道「回表次数」的诊断方法
6. 用最左匹配 + 覆盖索引组合优化典型查询

## 一、回表是什么

### 二级索引的查找过程

```sql
-- 索引：KEY idx_dept_salary (dept_id, salary)
SELECT name, email, created_at
FROM employees WHERE dept_id = 3 ORDER BY salary DESC LIMIT 20;
```

**执行过程**：

```
① 在 idx_dept_salary 二级索引里定位 dept_id=3 的区间
   → 索引叶子存的是 (dept_id, salary, 主键id)
   → 按 salary 有序，取前 20 个主键：101, 205, 308, ...
   ↓
② ⭐ 逐个回聚簇索引查完整行（20 次）
   → 20 次 B+ 树查找，每次可能读几个页
   ↓
③ 过滤 name/email/created_at，输出
```

⚠️ **第 ② 步就是「回表」**。它的问题是：**每个匹配行都要额外一次 B+ 树查找**。

### 代价有多大

| 匹配行数 | 回表次数 | 影响 |
|---------|---------|------|
| 10 | 10 次 | ⭐ 无感 |
| 1,000 | 1,000 次 | ⚠️ 开始变慢 |
| 100,000 | ⚠️ 100,000 次 | ❌ 严重 |

⚠️ **⚠️ 但不是所有场景都受影响**：`LIMIT 20` 时只回表 20 次，很快。⚠️ **真正的问题是「查很多行」的查询。**

## 二、覆盖索引 ⭐

### 定义

> **覆盖索引（covering index）**：索引里包含了查询需要的**全部列**，不需要回表。

### 判定：看 `Extra`

```sql
EXPLAIN SELECT dept_id, salary FROM employees WHERE dept_id = 3\G
```

| Extra | 含义 |
|-------|------|
| `Using index` | ⭐ **覆盖索引**，不回表 |
| `Using where` | ⚠️ 需要回表 |
| `Using index condition` | ICP 生效，⚠️ 仍需回表 |
| `Using index; Using where` | 部分覆盖 |

⭐ **`Using index` 就是「覆盖索引」的信号。**

### 构造覆盖索引

```sql
-- 查询：WHERE dept_id = 3 ORDER BY salary
-- 需要的列：dept_id（where）、salary（排序）、主键 id

-- ❌ 只有 (dept_id, salary)，缺 name/email → 要回表
KEY idx_dept_salary (dept_id, salary)

-- ✅ 加上要展示的列 → 覆盖索引
KEY idx_dept_salary_cover (dept_id, salary, name, email, created_at)
```

```sql
EXPLAIN SELECT name, email, created_at
FROM employees WHERE dept_id = 3 ORDER BY salary DESC LIMIT 20\G
-- Extra: Using index   ← ⭐ 不回表了
```

### ⚠️ 覆盖索引的三条限制

| 限制 | 说明 |
|------|------|
| **⚠️ 只对特定查询有效** | 换了查询要展示的列就不覆盖了 |
| ⚠️ **不能排序/范围之外的场景** | 覆盖索引本质是给「回表」用的优化，不是万能加速 |
| ⚠️ **索引变大，写入变慢** | 一行数据可能重复存在多个索引里 |

⚠️ **⚠️ 覆盖索引的代价必须权衡**：

```sql
-- 一个 100 字节的索引加上 5 个展示列 → 变成 300 字节
-- ⚠️ 磁盘占用 3 倍，写入慢 3 倍，buffer pool 占用 3 倍
```

⭐ **只在「读多写少」的高频查询上做覆盖索引。**

## 三、索引下推（ICP）⚠️

### 机制

⚠️ **没有 ICP 时**（MySQL 5.6 之前）：

```
二级索引定位 → 取出主键 → 回表读完整行 → 在服务器端判断 WHERE 条件
                                              ↑ 如果不满足就白回表了
```

⚠️ **有 ICP 时**（MySQL 5.6+）：

```
二级索引定位 → ⚡ 在存储引擎层就用索引里的列判断 WHERE 条件
              → 不满足的，不回表
              → 满足的，才回表
```

⭐ **ICP 把「过滤」提前到了「回表之前」，减少了无效回表。**

### 什么条件下 ICP 有效

⚠️ **索引里的列必须包含在 WHERE 条件里**：

```sql
KEY idx_created_status (created_at, status)

-- ✅ ICP 生效：status 在索引里
SELECT * FROM orders WHERE created_at > '2026-01-01' AND status = 'paid';
-- Extra: Using index condition
-- ⚠️ ⚠️ 但这个查询要 SELECT *，所以还是要回表（不是覆盖索引）

-- ⚠️ ICP 效果最好的情况：覆盖索引 + ICP
KEY idx_created_status_cover (created_at, status, user_id, amount)
SELECT user_id, amount FROM orders WHERE created_at > '2026-01-01' AND status = 'paid';
-- Extra: Using index; Using index condition    ← ⭐ 最优
```

### ⚠️ ICP 的限制

| 限制 | 说明 |
|------|------|
| **对二级索引有效，对聚簇索引无效** | ⚠️ 聚簇索引已经是整行了，没法再「提前过滤」 |
| ⚠️ 不能用于 MySQL 的 JOIN | JOIN 的 ICP 支持有限 |
| ⚠️ 不适用于 `range` 之外的某些情况 | |

📌 完整机制见 [[mysql/03-进阶阶段-深度剖析/优化器内核/原理剖析-优化器四阶段与成本模型]]。

## 四、`Using where` 的过滤成本

### 分清两种过滤

```sql
SELECT * FROM employees WHERE dept_id = 3 AND name = '张三';
```

| 过滤发生在哪 | 显示为 | 成本 |
|-------------|--------|------|
| **索引层**（用索引列判断） | 体现在 `type` 和 `key_len` | ⭐ 低 |
| **服务器层**（回表后判断） | ⚠️ `Using where` | ⚠️ 高（已经回表了） |

⭐ **`Using where` 本身不一定慢**，⚠️ **关键是它过滤了多少行、回表了多少次。**

### 危险组合

⚠️ **`Using where` + 高 `rows` + 回表**：

```sql
-- ⚠️ ⚠️ 最差组合：
-- 索引 (dept_id)，但 WHERE 里 name 的过滤要回表后才能做
SELECT name, salary FROM employees
WHERE dept_id = 3 AND salary > 20000;
-- type: ref, rows: 50000, Extra: Using where
-- → 回表 50000 次来判断 salary！😭
```

### 优化

```sql
-- ✅ 把 salary 放进索引（覆盖 + ICP）
KEY idx_dept_salary (dept_id, salary)
-- type: ref, Extra: Using index condition
-- → 在索引层判断 salary，回表次数大幅减少
```

⭐ **📌 优化口诀：把 WHERE 里用来过滤的列也放进索引，让过滤在索引层完成。**

## 五、排序时的覆盖索引

### 最优组合：等值 + 排序

```sql
-- 索引
KEY idx_user_status_created (user_id, status, created_at)

-- 查询：等值 + 排序
SELECT user_id, status, created_at, amount
FROM orders
WHERE user_id = 1 AND status = 'paid'
ORDER BY created_at DESC
LIMIT 20;
```

**执行**：

```
① 索引定位 (user_id=1, status='paid') 区间
② 该区间按 created_at 有序 → 直接倒着扫前 20 条   ⭐ 无 filesort
③ 需要的列都在索引里 → 不回表                    ⭐ Using index
-- Extra: Using index    ← ⭐⭐ 最优
```

⚠️ **⚠️ 但 `DESC` 排序需要 8.0+ 的降序索引**：

```sql
KEY idx_user_status_created (user_id, status, created_at DESC)
```

⚠️ 8.0 之前 `ORDER BY created_at DESC` 会 filesort。

### ⚠️ 排序列在索引中间会「断」

```sql
KEY idx_a_b_c (a, b, c)

-- ✅ 能用索引排序
WHERE a = 1 ORDER BY b, c

-- ❌ b 是范围查询，c 不能用于排序
WHERE a = 1 AND b > 2 ORDER BY c
-- ⚠️ 需要 filesort（可以用 ICP 过滤 c，但排序还是要额外做）
```

## 六、五个典型场景的优化

### 场景 1：列表页

```sql
-- 查询：某部门的员工列表，按创建时间倒序，展示列表页字段
SELECT id, name, email, created_at
FROM employees WHERE dept_id = ? AND deleted_at IS NULL
ORDER BY created_at DESC LIMIT 20;
```

```sql
-- ❌ 只有 (dept_id, created_at)
KEY idx_dept_created (dept_id, created_at)
-- ⚠️ 回表 20 次取 id/name/email

-- ✅ 覆盖索引
KEY idx_dept_created_cover (dept_id, created_at, id, name, email)
-- Extra: Using index   ⭐
```

⚠️ **⚠️ 但 `deleted_at IS NULL` 无法用索引**（见下一节）。⚠️ 更好的做法是把它放进索引：

```sql
KEY idx_dept_deleted_created (dept_id, deleted_at, created_at, id, name, email)
```

### 场景 2：关联查询

```sql
-- 查询：员工 + 部门名称
SELECT e.id, e.name, d.name AS dept_name
FROM employees e LEFT JOIN departments d ON e.dept_id = d.id
WHERE e.status = 1 LIMIT 100;
```

⚠️ **⚠️ `LEFT JOIN` 的右表只能被「驱动表已有的值」匹配**。所以左表覆盖索引能减少回表，右表只能靠主键定位（`eq_ref`，已经最优）。

```sql
-- ⭐ 优化点在左表：让左表覆盖，避免回表
KEY idx_status_cover (status, dept_id, id, name)
```

### 场景 3：聚合查询

```sql
SELECT dept_id, COUNT(*) FROM employees WHERE status = 1 GROUP BY dept_id;
```

```sql
-- ✅ 让 status 和 dept_id 都在索引里
KEY idx_status_dept (status, dept_id)
-- Extra: Using index   ⭐ 索引扫描就能完成聚合，不用回表
```

⚠️ **⚠️ 没有索引时是 `Using temporary; Using filesort`，大表上非常慢。**

### 场景 4：判断存在性

```sql
-- ⚠️ 只需要知道「有没有」，不需要任何列
SELECT 1 FROM orders WHERE user_id = 1 LIMIT 1;
```

⭐ **用 `LIMIT 1` 而不是 `COUNT(*)`**：

```sql
-- ❌ COUNT 要扫描所有匹配行
SELECT COUNT(*) FROM orders WHERE user_id = 1;

-- ✅ 找到一条就停（如果有合适索引）
SELECT 1 FROM orders WHERE user_id = 1 LIMIT 1;
```

⚠️ **⚠️ 但如果没有索引，`LIMIT 1` 也救不了**——还是要扫全表。

### 场景 5：范围查询 + 排序 ⚠️ 最难优化

```sql
SELECT * FROM orders
WHERE created_at >= '2026-01-01' AND status = 'paid'
ORDER BY amount DESC LIMIT 20;
```

⚠️ **这个查询天然难优化**：

```
需要：created_at 范围 + status 过滤 + amount 排序
      ↓
⚠️ 索引 (created_at, status) → 找不到 amount 的顺序
⚠️ 索引 (status, amount)     → 找不到 created_at 的范围
```

**三个方案**：

| 方案 | 说明 |
|------|------|
| **① 覆盖索引 + 接受 filesort** | `KEY (created_at, status, amount, ...)`，⚠️ 排序仍额外做 |
| ② 派生表 | 先用索引筛出小结果集，再排序 |
| ③ 应用层排序 | 查出一批（上限）再在应用层排 |

⭐ **实践中：先保证 WHERE 快（覆盖索引），排序慢一点可以接受。** 排序的数据量小（因为 WHERE 已经过滤了）。

## 七、诊断回表次数

### 方法 1：看 `rows`

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
-- rows: 50000   ← ⚠️ 意味着最多回表 50000 次
```

⚠️ **`rows` 是估算的匹配行数，接近回表次数。**

### 方法 2：`EXPLAIN ANALYZE`

```sql
EXPLAIN ANALYZE SELECT ...;
-- → Index lookup on employees using idx_dept (actual time=0.010..0.850 rows=50000 loops=1)
-- ⚠️ 单行耗时 0.85ms × 50000 = 42 秒
```

### 方法 3：`Handler_read_*`

```sql
FLUSH STATUS;
SELECT ...;
SHOW SESSION STATUS LIKE 'Handler_read%';
```

| 计数器 | 含义 |
|--------|------|
| `Handler_read_rnd_next` | ⚠️ **全表/全索引扫描的次数**。⚠️ **这个值大说明扫得多** |
| `Handler_read_rnd_next` | 顺序读行数 |
| `Handler_read_key` | ⭐ **按索引查找的次数** |
| `Handler_read_first` | 只读第一行（`LIMIT 1` 用） |
| `Handler_read_rnd` | 随机读（**回表的次数**） |

⚠️ **`Handler_read_rnd` 就是回表次数**（如果有 `Handler_read_rnd_next` 也很大，说明混合了全表扫描）。

📌 见 [[mysql/02-中段阶段-专题精讲/工具与可观测性/工具链总览]]。

### 方法 4：`performance_schema`

```sql
SELECT * FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 10;
-- ⚠️ 找「总耗时最长」的语句
```

## 八、索引设计的三个层次

⭐ **判断你的索引设计处于哪一层：**

| 层次 | 特征 | `Extra` | 优化空间 |
|------|------|---------|---------|
| **L0 无索引** | `type=ALL, key=NULL` | `Using where` | ⭐ 加索引 |
| **L1 索引用上了** | `type=ref, key=idx_x` | `Using where` | ⚠️ 减少回表 |
| **L2 索引下推** | `type=ref, key=idx_x` | `Using index condition` | ICP 生效 |
| **L3 覆盖索引** | `type=ref, key=idx_x` | ⭐ **`Using index`** | 已最优 |

⭐ **优化目标：从 L0 → L1 → L2 → L3。⚠️ 但不是所有查询都要到 L3**——索引变大是有代价的。

---

## 九、陷阱

1. **❌ 无脑做覆盖索引。** ⚠️ 索引变大、写入变慢。权衡读写比。
2. **❌ 覆盖索引只覆盖部分查询。** 换查询就不覆盖了。
3. **❌ 以为 ICP 能替代覆盖索引。** ⚠️ ICP 只减少回表次数，最后还是要回表取数据。
4. **❌ 覆盖索引的列不能太多。** ⚠️ 索引膨胀到比表还大就本末倒置了。
5. **❌ 用 `COUNT(*)` 判断存在性。** ⚠️ 用 `LIMIT 1`。
6. **❌ 只看 EXPLAIN 不看真实耗时。** 用 `EXPLAIN ANALYZE`。
7. **❌ 忽略 `Handler_read_rnd`。** 它就是回表次数。

---

## 小结

- **回表** = 二级索引找到主键后，再查聚簇索引取整行。⚠️ 每个匹配行一次
- ⭐ **覆盖索引** = 索引包含全部所需列，`Extra: Using index`，不回表
- ⚠️ **覆盖索引有代价**：只对特定查询有效、索引变大、写入变慢。⚠️ 只在读多写少的高频查询上做
- **ICP（索引下推）** = 把过滤提前到回表之前，`Using index condition`。⚠️ 对聚簇索引无效
- ⚠️ **危险组合**：`Using where` + 高 `rows` → 回表次数爆炸
- ⭐ **优化口诀：把 WHERE 里用来过滤的列也放进索引**
- 最优组合：等值列 + 排序列都在索引里 → `Using index` 且无 filesort
- 诊断回表次数：`rows` 估算 / `EXPLAIN ANALYZE` 真实耗时 / **`Handler_read_rnd`**
- 索引优化四个层次：无索引 → 索引用上 → ICP → 覆盖索引
