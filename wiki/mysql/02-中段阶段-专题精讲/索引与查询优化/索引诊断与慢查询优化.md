# 索引诊断与慢查询优化实战

> **什么时候该读**：要优化一个具体的慢查询；或者发现索引太多/无用想清理；或者优化器「不听话」不按你预期的走索引。

## 学习目标

读完本篇，你应当能够：

1. 用 `performance_schema` 找出最耗时的语句
2. 判断一个索引是否「无用」，并用**不可见索引**安全删除
3. 诊断「优化器估错行数」这个最难的优化问题
4. 用**直方图**解决数据倾斜导致的选错索引
5. 用 `optimizer_trace` 看优化器的完整决策过程
6. 走完一个完整的慢查询优化流程（含真实案例）

## 一、找慢查询：三个数据源

### 数据源 1：慢查询日志 ⭐

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.5;      -- ⚠️ 生产建议 0.5~1 秒
SET GLOBAL log_queries_not_using_indexes = 'ON';   -- ⚠️ 记录没走索引的（⚠️ 日志量大）
```

📌 详解见 [[mysql/02-中段阶段-专题精讲/工具与可观测性/工具链总览]]。

### 数据源 2：`performance_schema`（更精准）

```sql
-- 按总耗时排序，找出最耗时的 10 类语句
SELECT DIGEST_TEXT,
       COUNT_STAR,
       ROUND(SUM_TIMER_WAIT/1000000000000, 3) AS total_sec,
       ROUND(AVG_TIMER_WAIT/1000000000, 3) AS avg_ms,
       SUM_ROWS_EXAMINED,      -- ⭐ 扫了多少行
       SUM_ROWS_SENT,          -- ⭐ 返回了多少行
       ROUND(SUM_ROWS_EXAMINED / SUM_ROWS_SENT, 1) AS exam_per_sent   -- ⭐ 扫描/返回比
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

⭐ **`SUM_ROWS_EXAMINED / SUM_ROWS_SENT` 是最有价值的指标**：

| 比值 | 含义 |
|------|------|
| **1~10** | ⭐ 好。扫的行和返回的行接近 |
| **10~100** | ⚠️ 有浪费 |
| **> 100** | ❌ **⚠️ 严重浪费，优先优化** |

### 数据源 3：`sys` schema（可读性更好）

```sql
-- 最耗时的语句（人话版）
SELECT query, exec_count, total_latency, avg_latency, rows_sent_avg, rows_examined_avg
FROM sys.statement_analysis
ORDER BY total_latency DESC
LIMIT 10;

-- 找出扫描行数最多的（最有优化空间）
SELECT query, exec_count, total_latency, rows_sent_avg, rows_examined_avg
FROM sys.statements_with_full_table_scans
ORDER BY total_latency DESC
LIMIT 10;

-- 找出有临时表或排序的
SELECT * FROM sys.statements_with_sorting
ORDER BY total_latency DESC LIMIT 10;
```

⭐ **`sys.statements_with_full_table_scans` 是最实用的视图之一**——它直接列出全表扫描的语句。

## 二、索引是不是太多了

### 索引的代价回顾

| 代价 | 说明 |
|------|------|
| 写入变慢 | ⭐ 每次 INSERT/DELETE/UPDATE 要维护所有索引 |
| 空间 | 每个索引都是一棵独立 B+ 树 |
| DDL 更慢 | 建索引要扫表排序 |
| 优化器负担 | 候选索引太多时选错概率上升 |

### ⭐ 删除无用索引的正确流程

⚠️ **「这个索引看起来没用」不能靠猜。** 8.0 提供了安全的流程：

```
① 确认真的一直没用（查计数器，至少观察几天）
        ↓
② ALTER INDEX ... INVISIBLE（索引结构保留，优化器不用）
        ↓
③ 观察几天（如果有监控告警「索引未使用」，立刻能发现）
        ↓
④ 确认无人报错 → DROP INDEX
```

```sql
-- 步骤 1：查使用情况
SELECT OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, COUNT_STAR
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE INDEX_NAME IS NOT NULL AND COUNT_STAR = 0
ORDER BY OBJECT_SCHEMA, OBJECT_NAME;

-- ⚠️ 注意：Count_star=0 只表示「统计周期内没被用过」，不代表永远没用

-- 步骤 2：设为不可见
ALTER TABLE users ALTER INDEX idx_status INVISIBLE;

-- 步骤 3：观察（几天）

-- 步骤 4a：如果有问题，一键恢复
ALTER TABLE users ALTER INDEX idx_status VISIBLE;

-- 步骤 4b：确认没问题，删除
ALTER TABLE users DROP INDEX idx_status;
```

⚠️ **⚠️ 三个注意点**：

1. **`InnoDB` 的主键和唯一索引不能设为 invisible**（否则表没法用）。
2. **⚠️ 观察期要覆盖业务周期**（周一到周日都要覆盖，⚠️ 否则可能漏掉只在周末跑的批处理用到的索引）。
3. **⚠️ 索引可能服务 `JOIN` 的外键检查**——即使你的 `SELECT` 不用它，`INSERT` 时外键校验会用到。⚠️ 观察期要包含写入操作。

### 找出冗余索引

```sql
-- 用 sys 视图找可能冗余的索引
SELECT * FROM sys.schema_redundant_indexes\G
```

⚠️ **「可能冗余」不等于「一定可以删」**：⚠️ 单列索引 `(a)` 可能被某个复合索引覆盖不了。

## 三、⚠️ 优化器估错行数（最难的优化问题）

### 症状

```sql
-- EXPLAIN 说要扫 50 万行
EXPLAIN SELECT * FROM orders WHERE user_id = 5\G
-- type: ALL, key: NULL, rows: 500000

-- 实际只有 3 行
SELECT COUNT(*) FROM orders WHERE user_id = 5;   -- 3
```

⚠️ **后果**：优化器认为「走索引不如全表扫」（因为要扫 50 万 vs 3），**所以放弃了索引**。

### 为什么估算会错

优化器靠**统计信息**估算：

| 统计来源 | 说明 | 精度问题 |
|---------|------|---------|
| **InnoDB 基数估算** | 从 B+ 树取样本估算 | ⚠️ **基于随机采样，可能偏** |
| **直方图**（8.0+） | 列值的分布 | ⭐ 精准，但需要手动建 |
| `ANALYZE TABLE` | 更新统计信息 | 重建全部 |

### 解决步骤

#### 步骤 1：更新统计信息

```sql
ANALYZE TABLE orders;

-- 对比更新前后的基数估算
SELECT * FROM information_schema.TABLES WHERE TABLE_NAME = 'orders'\G
-- 看 TABLE_ROWS 和 AVG_ROW_LENGTH
```

⚠️ **`ANALYZE TABLE` 会锁表**（⚠️ 大表上是重操作）。⚠️ **不要为了「优化」在高峰期跑它。**

#### 步骤 2：建直方图（8.0+）⭐

⚠️ **直方图是解决数据倾斜的正解。**

```sql
-- 为倾斜的列建直方图
ANALYZE TABLE orders
  UPDATE HISTOGRAM ON user_id WITH 32 BUCKETS;

-- 查看已有的直方图
SELECT * FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME = 'shop';
```

| 参数 | 说明 |
|------|------|
| **桶数** | 建议是「不同值数量」的 1/10 左右，最大 1024 |
| **效果** | ⭐ 让优化器知道「user_id=5 只占 0.0001%」 |

⚠️ **直方图的限制**：

| 限制 | 说明 |
|------|------|
| ⚠️ **每个索引列只能有一个直方图** | 重建会替换旧的 |
| ⚠️ **只对单列有效**（多列联合分布不行） | |
| ⚠️ **`ANALYZE TABLE` 会重建所有直方图** | ⚠️ 只更新统计信息用 `NO_WRITE_TO_BINLOG` 选项 |
| ⚠️ 桶数不当会浪费空间 | 单列直方图最多 1024 个桶 |

⚠️ **⚠️ 最有效的组合**：**「倾斜的列建直方图 + 高频查询的列建索引」**。

#### 步骤 3：索引提示（Force Index）

⚠️ **最后手段。** ⚠️ 一旦用了，**数据分布变化后索引可能又「该不用了」**，所以要定期复查。

```sql
-- 强制指定
SELECT * FROM orders FORCE INDEX (idx_user) WHERE user_id = 5;

-- 建议/禁止（比 FORCE 温和）
SELECT * FROM orders USE INDEX (idx_user) WHERE user_id = 5;
SELECT * FROM orders IGNORE INDEX (idx_user) WHERE user_id = 5;
```

⚠️ **⚠️ 索引提示的代价**：

| 提示 | 含义 |
|------|------|
| `USE INDEX` | 建议优化器考虑这个 |
| ⚠️ **`FORCE INDEX`** | **强制使用，优化器不再有选择权** |
| `IGNORE INDEX` | 禁止使用这些 |

⚠️ **⚠️ `FORCE INDEX` 会让优化器无法选择更好的计划**。数据分布变化后它会「固化」成瓶颈。**能不用就不用。**

📌 优化器的完整决策过程见第三节。

## 四、`optimizer_trace`：看优化器在想什么

### 开启追踪

```sql
SET optimizer_trace = 'enabled=on';
SET optimizer_trace_max_mem_size = 1048576;    -- 默认 1MB，不够时会截断

-- 执行你要分析的查询（必须是 SELECT）
SELECT * FROM orders WHERE user_id = 5;

-- 看追踪结果
SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G

-- 关闭
SET optimizer_trace = 'enabled=off';
```

⚠️ **⚠️ `SET optimizer_trace = 'enabled=on'` 会影响当前会话的后续所有语句。** 分析完记得关掉，否则会一直记录（并占内存）。

### 读 trace 的三个关键部分

#### ① `considered_execution_plans`

```json
{
  "considered_execution_plans": [
    {
      "query_specification": {...},
      "plan": {"table": "orders", "access_type": "ALL", "rows_examined_per_scan": 500000},
      "cost": {...}
    },
    {
      "plan": {"access_type": "ref", "key": "idx_user", "rows_examined_per_scan": 3},
      "cost": {...}
    }
  ]
}
```

⭐ **对比两个计划的 `rows_examined_per_scan`**：

- ALL 计划：估 500000 行
- ref 计划：估 3 行

⚠️ **但优化器选了 ALL**——说明它算出的 cost 里，ALL 更便宜。⚠️ **问题在于它怎么算出这个 cost 的**。

#### ② `best_access_path`

```json
{
  "best_access_path": [
    {
      "table": "orders",
      "access_type": "ALL",
      "rows_examined_per_scan": 500000,
      "chosen": true,
      "cost": 100000.0,
      "reasoning": "chosen for best access"
    }
  ]
}
```

⭐ **`chosen: true` + `cost` 就是答案**。⚠️ 如果 cost 反直觉（比如 ALL 的 cost 明显更小），就去 `costing` 部分看它的算法输入。

#### ③ `grouping_operation` / `candidates_rejected`

```json
"candidates_rejected": [
  {"table": "orders", "access_type": "ref", "key": "idx_user",
   "reason": "chosen by heuristics"}
]
```

⚠️ **`candidates_rejected` 告诉你「哪些索引被考虑过但被否决了」**，⚠️ **但注意：优化器不一定看全所有索引**（它有自己的启发式筛选）。**没出现在这里的索引，可能根本没被考虑**——这就要回到索引设计层面解决。

### 诊断实例

**症状**：

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 5;
-- type: ALL, key: NULL
```

**trace 揭示**：

```
considered_execution_plans:
  - access_type: ref, key: idx_user, rows: 3,    cost: 4.5
  - access_type: ALL,           rows: 500000, cost: 98000.0

chosen: ALL（cost 98000 竟然更小）
```

⚠️ **问题在 cost 计算**：优化器算 ALL 的 cost 时用了「500000 行 × 单行成本」，但 ref 的 cost 里加了一个它认为很高的「索引跳跃」代价。

**解决**：建直方图让它知道 `user_id=5` 只占 0.0001%：

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON user_id WITH 32 BUCKETS;
ANALYZE TABLE orders;

EXPLAIN SELECT * FROM orders WHERE user_id = 5;
-- type: ref, key: idx_user   ← ✅
```

## 五、慢查询优化完整流程（实战）

### 流程图

```
① 发现慢查询（慢日志 / performance_schema / APM）
        ↓
② 找到执行计划（EXPLAIN）
        ↓
③ 定位问题类型
   ├── type=ALL + key=NULL
   │     ├── 索引没用上 → 检查函数/类型转换/OR
   │     ├── 优化器估错 → ANALYZE + 直方图
   │     └── 没有索引 → 加
   ├── type=ref 但 Extra 有 filesort
   │     └── 排序列没索引 → 加/改复合索引
   ├── Extra 有 temporary
   │     └── 改写查询（GROUP BY 和 ORDER BY 同列）
   ├── rows 与真实差很多
   │     └── 直方图 + ANALYZE
   └── type=ALL 但表很小
         └── 正常，不用优化
        ↓
④ 优化（加索引 / 改写 / 建直方图）
        ↓
⑤ 验证：EXPLAIN 对比 + EXPLAIN ANALYZE 实测
        ↓
⑥ 上线后监控（确保真的变快了）
```

---

### 案例 1：隐式类型转换

**现象**：慢日志里 `WHERE phone = ?` 占 40% 的耗时，`EXPLAIN` 显示 `type=ALL`。

```sql
-- 表定义
phone VARCHAR(20), KEY idx_phone (phone)

-- ❌ 应用代码传了 int
cur.execute("SELECT * FROM users WHERE phone = %s", (13800138000,))
```

```sql
-- 验证
EXPLAIN SELECT * FROM users WHERE phone = 13800138000\G
-- type: ALL, key: NULL     ← ⚠️

EXPLAIN SELECT * FROM users WHERE phone = '13800138000'\G
-- type: ref, key: idx_phone ← ✅
```

**根因**：`phone` 是 VARCHAR，和数字比较时 MySQL 会「把列转成数字」——⚠️ **而转换的是列，不是常量**，所以索引失效。

**修复**：
- 应用侧：把参数转成字符串
- 表侧（⚠️ 若 `phone` 语义是字符串）：应用侧修

📌 **📌 记忆锚点：索引失效的本质是「函数/运算作用在列上」。`VARCHAR` 列比数字 = 「隐式把列 CAST 成数字」。**

---

### 案例 2：数据倾斜

**现象**：`WHERE user_id = ? ORDER BY created_at DESC` 大部分查询很快，少数很慢。

```sql
-- 大 V 用户（user_id=8888）有 500 万订单
-- 普通用户只有 10~50 单
```

**诊断**：
```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 8888 ORDER BY created_at DESC LIMIT 20\G
-- rows: 3000000, Extra: Using filesort   ← ⚠️ 估错了，filesort 300 万行！
```

⚠️ **MySQL 对「非常倾斜」的数据分布估算很不可靠**。

**修复**：
```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON user_id WITH 64 BUCKETS;
ANALYZE TABLE orders;
```

⭐ **效果**：优化器知道 `user_id=8888` 虽然行多但占比大（可以走索引 + 范围扫描），而其他值走索引极快。

### 案例 3：`Using temporary` + `Using filesort`

**现象**：

```sql
SELECT dept_id, COUNT(*) FROM employees
WHERE status = 1
GROUP BY dept_id
ORDER BY name;
-- Extra: Using temporary; Using filesort  ← ⚠️ 最差组合
```

**为什么**：`GROUP BY dept_id` 用 `idx_dept` 排序，`ORDER BY name` 用 `idx_name` 排序。**两个不同索引只能选一个**，另一个需要额外排序。

**修复**：

```sql
-- 加联合索引，让两个操作都能用同一个索引
KEY idx_status_dept_name (status, dept_id, name)
```

⚠️ **⚠️ 更简单的方案：让 ORDER BY 和 GROUP BY 同列。**

---

### 案例 4：`WHERE col IS NULL` 用不上索引

⚠️ **`IS NULL` 在 B+ 树里也能用索引**（因为索引里 NULL 排在最前，是有序的）。⚠️ **但如果表里有大量 NULL（超过 70%），优化器会认为全表扫描更好。**

**修复**：

```sql
-- ⚠️ 方案 1：把 NULL 换成哨兵值（0 或 ''）
-- ⚠️ 方案 2：覆盖索引，让查询其他列顺便用上索引
KEY idx_dept_created_cover (dept_id, deleted_at, created_at, id, name)
--    ✅ 最优：deleted_at 参与索引，查询有其他索引列时能用上
```

---

### 案例 5：排序导致的全表扫描

⚠️ **⚠️ 这是一个很隐蔽的案例**：

```sql
-- 索引
KEY idx_status_created (status, created_at)

-- 查询
SELECT * FROM employees WHERE status = 1 AND created_at > '2026-01-01'
ORDER BY created_at DESC LIMIT 20;
```

⚠️ **`ORDER BY created_at DESC` + 索引里 `created_at` 是 ASC → 8.0 之前要反向扫描整个索引区间 → filesort**。

**修复（8.0+）：** 混合方向排序需要「真降序索引」：

```sql
KEY idx_status_created_desc (status, created_at DESC)
```

📌 降序索引见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引类型与选型]]。

---

### 案例 6：分页总数太慢

⚠️ **需求**：「共 12345 条，第 3 页」。

```sql
-- ❌ SQL_CALC_FOUND_ROWS：会扫全表
SELECT SQL_CALC_FOUND_ROWS * FROM orders WHERE status = 'paid' LIMIT 40, 20;
SELECT FOUND_ROWS();
```

**修复（三个方案）**：

| 方案 | 写法 | 优劣 |
|------|------|------|
| **① 覆盖索引 COUNT**（最快） | `SELECT COUNT(status) FROM orders WHERE status='paid';` | ✅ status 在索引里，扫索引比扫行快 |
| **② 窗口函数**（8.0+） | `SELECT *, COUNT(*) OVER() AS total ... LIMIT 40, 20;` | ✅ 一次往返 |
| **③ 缓存/估算** | `information_schema.TABLES.TABLE_ROWS` | ✅ 极快；⚠️ 不精确 |

⚠️ **⚠️ 最优：产品上改成「加载更多」不显示总数。** ⚠️ 如果一定要精确总数，用方案 ①（配合覆盖索引）。

📌 深分页的解法见 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.3-ORDER-BY排序与分页]]。

## 六、索引设计的长期实践

### 定期体检（建议每月）

```sql
-- ① 找出全表扫描的语句
SELECT * FROM sys.statements_with_full_table_scans
ORDER BY total_latency DESC LIMIT 20;

-- ② 找出没走索引的语句（⚠️ 需先开启 log_queries_not_using_indexes）
-- 查慢日志

-- ③ 找出可能冗余的索引
SELECT * FROM sys.schema_redundant_indexes\G

-- ④ 找出从未使用的索引
SELECT * FROM sys.schema_unused_indexes WHERE object_schema = 'shop'\G

-- ⑤ 找出没有索引的表
SELECT * FROM sys.schema_tables_with_missing_indexes\G
```

⭐ **`sys` schema 的这几个视图是最实用的索引体检工具。**

### 索引设计的原则回顾

| 原则 | 说明 |
|------|------|
| ⭐ **先看真实查询再设计索引** | 用 `performance_schema` 的数据，不要凭想象 |
| ⭐ **复合索引：等值列在前，范围/排序列在后** | 决定能用几列 |
| ⭐ **把 WHERE 里的过滤列也放进索引** | 减少回表 + ICP 生效 |
| ⚠️ **索引数量要克制** | 读写比决定 |
| ⚠️ **优先覆盖索引，读多写少** | 代价是空间和写入 |
| ⚠️ **数据倾斜用直方图** | 8.0+ 的正解 |
| ⚠️ **索引提示是最后手段** | 数据分布变了会固化 |

---

## 七、陷阱

1. **❌ 凭感觉加索引。** ⚠️ 用 `performance_schema` 的真实数据说话。
2. **❌ 索引没用就删。** ⚠️ 先 INVISIBLE，观察，覆盖一个完整业务周期。
3. **❌ 高峰期跑 `ANALYZE TABLE`。** ⚠️ 锁表。
4. **❌ 用 `FORCE INDEX` 一劳永逸。** ⚠️ 数据分布变了会固化。
5. **❌ 「优化器不听话」就一直加索引。** ⚠️ 先看 `optimizer_trace`，可能是统计信息问题。
6. **❌ 直方图建太多。** ⚠️ 每个索引列只能有一个，`ANALYZE TABLE` 会重建。
7. **❌ 用 `ORDER BY RAND()` 取随机。** ⚠️ 全表排序。

---

## 小结

- **三个数据源**：慢日志、`performance_schema.events_statements_summary_by_digest`（⭐ `SUM_ROWS_EXAMINED/SUM_ROWS_SENT` 比值最有价值）、`sys` schema（可读性最好）
- ⭐ **删索引的正确流程**：查计数器 → **INVISIBLE** → 观察 → DROP → 出问题 VISIBLE 恢复
- ⚠️ 观察期要覆盖完整业务周期（含周末批处理、含外键写入）
- ⭐ **优化器估错行数的解决**：`ANALYZE TABLE` → **直方图**（8.0+）→ 索引提示（最后手段）
- **`optimizer_trace`**：`considered_execution_plans`（对比各计划）→ `best_access_path`（谁赢了，为什么）→ `candidates_rejected`（哪些被否决）
- ⚠️ **`FORCE INDEX` 会让优化器失去选择权**，数据分布变化后会固化
- **六个实战案例**：隐式类型转换 / 数据倾斜 / Using temporary / IS NULL 用不上索引 / 排序方向 / 分页总数
