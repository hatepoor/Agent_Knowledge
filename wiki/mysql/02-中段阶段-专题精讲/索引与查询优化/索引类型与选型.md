# 索引类型与选型

> **什么时候该读**：查询慢，或者在设计表结构时决定要建哪些索引。

## 学习目标

读完本篇，你应当能够：

1. 说出 InnoDB 的四种索引类型及各自适用场景
2. 掌握**最左前缀原则**并判断一个查询能否用联合索引
3. 知道前缀索引、函数索引、不可见索引的用途
4. 为一个真实业务设计出合理的复合索引
5. 判断「索引是不是建太多了」

## 一、四种索引类型

| 类型 | 语法 | 用途 | 说明 |
|------|------|------|------|
| **B+ 树** | 默认 | ⭐ 95% 的场景 | 支持等值、范围、排序 |
| **哈希** | `USING HASH` | ⭐ **InnoDB 不支持用户建** | Memory 引擎才有 |
| **全文**（FULLTEXT） | `FULLTEXT KEY` | 文本搜索 | ⚠️ 中英分词效果都一般，大规模用 ES |
| **空间**（SPATIAL） | `SPATIAL KEY` | 地理数据 | 需要列是 `NOT NULL` |

### 为什么是 B+ 树

⭐ **B+ 树的设计目标是「减少磁盘 IO」，所以：**

| 特征 | 说明 |
|------|------|
| **非叶子节点只存键** | 一个节点能放更多键 → 树更矮 → IO 次数更少 |
| **叶子节点串成链表** | ⭐ **范围查询只需定位起点，然后顺序扫** |
| **聚簇索引只有一棵** | ⭐ InnoDB 的数据本身就按主键索引存放 |

📌 结构详解见 [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]]。

⚠️ **⚠️ 为什么不能用哈希索引做范围查询**：哈希把 `1~100` 映射成 8 个桶，存了 `1` 和 `100` 后，查 `1~100` 的范围无法通过哈希定位——哈希是无序的。

## 二、聚簇索引与二级索引 ★

### 两个概念

| 概念 | 说明 |
|------|------|
| **聚簇索引** | ⭐ **数据本身**按某个索引的顺序存放。InnoDB 里**只有一棵**，默认是主键 |
| **二级索引** | 索引叶子存的是「主键值」，需要回表才能拿到完整行 |

### 二级索引的查找过程

```
执行 SELECT name, salary FROM employees WHERE dept_id = 3;

① 在 idx_dept (dept_id) 二级索引里找到 dept_id=3 的所有记录
   → 拿到主键 id 列表：101, 205, 308
② ⭐ 逐个回聚簇索引查完整行（这叫「回表」）
③ 取 name 和 salary 列
```

⚠️ **⚠️ 回表是二级索引查询的主要开销**：每个匹配行都要再查一次聚簇索引。

📌 怎么避免回表见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

### 没有主键怎么办 ⚠️

⚠️ **InnoDB 会用一个隐藏的 6 字节 `DB_ROW_ID` 作为聚簇索引键**，顺序是「插入顺序」。⚠️ **如果没显式指定主键，删除再插入会让行「挪位置」，导致页分裂和空间碎片。**

⚠️ **⚠️ 隐式主键的顺序不可控**：两行 row_id 可能因为删除/重插而顺序颠倒。**所以永远显式指定主键。**

## 三、最左前缀原则 ★★

⚠️ **这是联合索引最重要、也最常考的概念。**

### 原理

```sql
KEY idx_a_b_c (a, b, c)     -- 相当于建了三个索引：a、(a,b)、(a,b,c)
```

### 能用上的查询

| 查询条件 | 用到索引的哪部分 | 能用吗 |
|---------|----------------|--------|
| `WHERE a = 1` | a | ✅ |
| `WHERE a = 1 AND b = 2` | a, b | ✅ |
| `WHERE a = 1 AND b = 2 AND c = 3` | a, b, c | ✅ |
| `WHERE a = 1 AND c = 3` | a（b 断了） | ⚠️ 部分 |
| `WHERE b = 2` | — | ❌ |
| `WHERE c = 3` | — | ❌ |
| `WHERE b = 2 AND c = 3` | — | ❌ |

### ⚠️ 「范围查询之后断了」

```sql
KEY idx_created_status (created_at, status)

-- ✅ 能用两个
WHERE created_at >= '2026-01-01' AND status = 'paid'

-- ⚠️ 只能用 created_at，status 用不上
WHERE created_at > '2026-01-01' AND status = 'paid'
-- ⚠️ 因为 created_at 是范围查询，它之后的列无法再用于「精确定位」
```

⚠️ **⚠️ 这是常见误解：「联合索引 `(a,b)` 能用于 `WHERE a>1 AND b=2`」——`b` 用不上，只能靠索引过滤（ICP）减少回表，不能用于定位。**

### ⚠️ 排序方向也遵循最左前缀

```sql
KEY idx_dept_hired (dept_id, hired_at)

-- ✅ 能用索引排序（避免 filesort）
WHERE dept_id = 1 ORDER BY hired_at

-- ❌ 不能（顺序反了）
WHERE dept_id = 1 ORDER BY hired_at, dept_id
```

## 四、复合索引的设计原则

### 原则一：把选择性高的列放前面

**选择性** = 该列不同值的数量 / 总行数。

```sql
SELECT COUNT(DISTINCT status) / COUNT(*) FROM orders;     -- status 选择性很低
SELECT COUNT(DISTINCT user_id) / COUNT(*) FROM orders;   -- user_id 选择性很高
```

⚠️ **⚠️ 但这个原则不能机械套用。** 对联合索引，列顺序的正确做法是：

> **把「等值查询的列」放前面，把「范围查询/排序的列」放后面。**

```sql
-- 常见场景：查某个用户的某个状态的订单，按时间倒序
KEY idx_user_status_created (user_id, status, created_at)
--      ⭐ 等值        ⭐ 等值    ⭐ 范围/排序

WHERE user_id = 1 AND status = 'paid' ORDER BY created_at DESC
-- ✅ 全部能用：a 等值 → b 等值 → c 范围且顺带排序
```

⚠️ **如果写成 `(status, user_id, created_at)`**，当 `status` 是范围查询时，后面的 `user_id` 就用不上了。

### 原则二：覆盖常用查询

⭐ **设计索引时，先列出最常见的 3~5 个查询，然后看能否用索引覆盖它们。**

```sql
-- 常用查询 1：列表页
SELECT id, name, email, created_at FROM users WHERE dept_id = ? ORDER BY created_at DESC LIMIT 20;

-- 常用查询 2：详情页
SELECT * FROM users WHERE id = ?;

-- 常用查询 3：登录
SELECT id FROM users WHERE email = ? AND status = 1;

-- 设计的索引
KEY idx_dept_created (dept_id, created_at),      -- 服务查询 1 ⭐ 覆盖
UNIQUE KEY uk_email (email)                      -- 服务查询 3
PRIMARY KEY (id)                                 -- 服务查询 2
```

⚠️ **注意：不是每个查询都要一个索引。** ⚠️ 索引过多会拖慢写入。

### 原则三：⚠️ 别为「可能用到」建索引

```sql
-- ❌ 过度设计
KEY idx_a (a), KEY idx_b (b), KEY idx_c (c), KEY idx_d (d),
KEY idx_e (e), KEY idx_f (f)
-- ⚠️ 每加一个索引，写入都要维护它
```

⭐ **判断标准**：跑一段真实的生产查询日志（`performance_schema` 或慢日志），看实际用到哪些。

📌 见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

## 五、三种特殊索引

### 前缀索引

⚠️ **`TEXT`/`BLOB` 不能直接建索引**，前缀索引是解决方案：

```sql
CREATE TABLE articles (
  title VARCHAR(200) NOT NULL,
  content TEXT,
  KEY idx_content (content(255))    -- 只索引前 255 个字符
);

-- ⚠️ 前缀长度怎么定？看这个值有多少种
SELECT COUNT(DISTINCT LEFT(content, 100)) FROM articles;
SELECT COUNT(DISTINCT LEFT(content, 255)) FROM articles;
-- ⭐ 找到「区分度已经够了」的最小长度
```

⚠️ **⚠️ 代价：前缀索引不能用于排序和覆盖索引**（因为它只有前缀）。

⚠️ **⚠️ 前缀长度受字符集限制**：`VARCHAR(255)` 在 utf8mb4 下最多 1020 字节，所以前缀索引长度 × 4 不能超过索引列长度。

### 函数索引（8.0.13+）

```sql
-- 给表达式建索引
CREATE TABLE users (
  email VARCHAR(255) NOT NULL,
  KEY idx_email_lower ((LOWER(email)))      -- ⭐ 双括号
);

-- 查询时表达式要「完全一致」才能用
SELECT * FROM users WHERE LOWER(email) = 'a@b.com';   -- ✅
SELECT * FROM users WHERE email = 'a@b.com';           -- ❌ 用不上
```

⚠️ **⚠️ 「完全一致」是个硬限制**：索引的表达式写法必须和查询一致（包括函数名大小写、括号）。

⚠️ **⚠️ 更常见的等价做法是生成列**（它能走普通索引，且跨版本可用）：

```sql
ALTER TABLE users ADD COLUMN email_lower VARCHAR(255)
  GENERATED ALWAYS AS (LOWER(email)) STORED;
CREATE INDEX idx_email_lower ON users (email_lower);
```

### 降序索引（8.0+）

```sql
CREATE INDEX idx_ord ON t (a ASC, b DESC);

-- 现在能用索引
SELECT * FROM t ORDER BY a ASC, b DESC;
-- ⚠️ 8.0 之前混合方向必须 filesort
```

⚠️ **⚠️ 8.0 的降序索引是「真降序」**：索引里按键值降序存储，不是反向扫描的技巧。所以 `ORDER BY a ASC, b DESC` 和 `ORDER BY a DESC, b ASC` 需要两个不同的索引。

### 不可见索引（8.0+）⭐

⚠️ **「这个索引看起来没用，要不要删掉」——这是个难题。** 不可见索引提供了一个安全做法：

```sql
-- 设为不可见：索引结构保留，但优化器不用它
ALTER TABLE users ALTER INDEX idx_status INVISIBLE;

-- ⭐ 观察几天，看有没有索引未使用的告警
-- 如果真没人用，再删除
ALTER TABLE users DROP INDEX idx_status;

-- ⭐ 如果发现有人在用，一键恢复（瞬间，不用重建）
ALTER TABLE users ALTER INDEX idx_status VISIBLE;
```

⭐ **这就是「在线删索引」的正确做法**：先 INVISIBLE，观察，确认后删除，出问题立刻 VISIBLE 恢复。

📌 详见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

## 六、索引的代价

⚠️ **索引不是免费的。每个索引都会：**

| 代价 | 说明 |
|------|------|
| **写入变慢** | ⭐ 每次 INSERT/DELETE 要维护所有索引 |
| **占用空间** | 索引和表一样要占磁盘（但通常比表小） |
| **优化器负担** | 索引太多，优化器选错的可能性上升 |
| **⚠️ DDL 更慢** | 建索引要扫表并排序 |

### 数量参考

| 表规模 | 索引数建议 |
|--------|-----------|
| 小表（<1 万行） | ⚠️ **1~2 个就够**，可能全表扫描反而快 |
| 中表（百万行） | 3~5 个 |
| 大表（千万行+） | ⚠️ **谨慎设计，每个索引都要有明确用途** |

⚠️ **⚠️ 小表上「索引反而慢」的原因**：索引是 B+ 树，读取要先定位树节点；而小表全表扫描可能一次 IO 就读完了。⚠️ 优化器会根据 `rows` 自动判断——`EXPLAIN` 里 `type = ALL`（全表扫描）对小表是正常的。

## 七、设计决策表

| 场景 | 索引设计 |
|------|---------|
| 主键 | ⭐ `BIGINT UNSIGNED` 单列（不要用 UUID） |
| 外键列 | ⭐ **手动建索引**（MySQL 不自动建） |
| 高频 WHERE 列 | 视选择性决定是否单列索引 |
| 高频 WHERE + 排序 | ⭐ 复合索引：等值列在前，范围/排序列在后 |
| 高频 WHERE + 函数 | 生成列 + 索引，或 8.0 函数索引 |
| 长文本搜索 | 前缀索引，或上 Elasticsearch |
| JOIN 关联列 | ⭐ **必须有索引**，且类型一致 |
| 状态/类型列 | ⚠️ **选择性低时别单独建索引**（`status=1` 占 99% 的行时用处不大） |
| 需要区分大小写 | `COLLATE utf8mb4_bin` |

## 八、陷阱

1. **❌ 联合索引的列顺序随手写。** 把等值列放前面，范围/排序列放后面。
2. **❌ 以为 `(a,b)` 能用于 `WHERE b=1`。** 最左前缀。
3. **❌ 以为范围查询后的列还能用。** `a>1 AND b=2` 里 b 用不上。
4. **❌ 索引列上用函数。** 用生成列或函数索引。
5. **❌ 外键列不建索引。** MySQL 不会自动建。
6. **❌ 建了用不到的索引。** 先 INVISIBLE 观察再删。
7. **❌ 给低选择性的状态列建单列索引。** 用不上。
8. **❌ 主键用随机 UUID。** 页面分裂严重。
9. **❌ 小表建一堆索引。** 反而慢。

---

## 小结

- 四种索引类型：B+ 树（默认）/ 哈希（InnoDB 不支持用户建）/ 全文 / 空间
- **聚簇索引只有一棵**（数据本身）；**二级索引的叶子存主键值**，查询要「回表」
- ⭐ **最左前缀原则**：(a,b,c) 相当于 a、(a,b)、(a,b,c)；⚠️ **范围查询之后的部分用不上**
- 复合索引设计：**等值列在前，范围/排序列在后**；覆盖最常用的 3~5 个查询
- **前缀索引**解决 TEXT 索引问题（⚠️ 不能排序、不能覆盖）
- **函数索引**（8.0.13+）⚠️ 要求查询表达式「完全一致」；生成列更通用
- ⭐ **不可见索引**（8.0+）是「在线删索引」的正确做法：INVISIBLE → 观察 → DROP → 出问题 VISIBLE 恢复
- ⚠️ **索引有代价**：写入变慢、占空间、优化器负担、DDL 更慢
- ⚠️ **小表上索引可能反而慢**（`type=ALL` 是正常的）
