# 备份恢复与安全加固

> **什么时候该读**：**上线前必读。** 「备份没演练过 = 没有备份。」

## 学习目标

读完本篇，你应当能够：

1. 区分逻辑备份与物理备份，说出各自适用场景
2. 掌握 `mysqldump` / `xtrabackup` / `mysqlbinlog` 的正确用法
3. 制定符合 **RPO / RTO** 目标的备份策略
4. **做一次真实的恢复演练**
5. 说出三个必须为 1 的参数和为什么
6. 完成生产环境的访问控制加固

## 一、备份的三个层次

| 层次 | 手段 | 恢复粒度 | 恢复时间（RTO） | 恢复点（RPO） |
|------|------|---------|---------------|---------------|
| **全量备份** | `mysqldump` / `xtrabackup` | 到备份时刻 | 慢（小时） | 到备份时刻 |
| **增量/binlog** | binlog + `mysqlbinlog` | 到任意时刻 | 中（分钟） | 任意时刻 |
| **主从复制** | 从库本身就是一份备份 | 近实时 | ⚠️ 秒级（但可能丢数据） | ⚠️ 异步：可能延迟几秒 |

⭐ **⚠️ 关键认知：只有全量备份是不够的。** 8.0.46 已经 EOL，如果你只在每月 1 号做全量备份，那么 8 月 13 日误删的数据，⚠️ **要恢复到 8 月 1 日的状态 = 丢掉 12 天数据**。

⭐ **必须配合 binlog。**

## 二、逻辑备份：`mysqldump`

### 基本用法

```bash
# ⭐ 单库（InnoDB）
mysqldump -u root -p --single-transaction shop > shop_20261013.sql

# ⭐ 多库
mysqldump -u root -p --single-transaction --databases shop shop2 > dbs.sql

# ⚠️ 备份所有库（⚠️ 谨慎，含 mysql 系统库）
mysqldump -u root -p --single-transaction --all-databases > all.sql

# 只备份结构
mysqldump -u root -p --no-data --single-transaction shop > schema.sql

# 只备份数据
mysqldump -u root -p --no-create-info --single-transaction shop > data.sql

# 表级
mysqldump -u root -p --single-transaction shop employees > employees.sql
```

### ⭐ `--single-transaction` 是核心参数

⚠️ **⚠️ 它让 `mysqldump` 用一个一致性快照导出 InnoDB 表，⚠️ 不锁表。**

| 有这个参数 | 没这个参数 |
|-----------|-----------|
| ⭐ 不锁表，业务不受影响 | ❌ 逐表加锁（`FLUSH TABLES WITH READ LOCK`），⚠️ 阻塞写入 |
| 数据一致 | ⚠️ 有可能出现「表 A 是 10 点的，表 B 是 11 点的」 |

⚠️ **⚠️ `--single-transaction` 只对 InnoDB 有效，对 MyISAM 无效**（MyISAM 会锁表）。

### 其他重要参数

| 参数 | 作用 |
|------|------|
| `--routines` | ⭐ 导出存储过程和函数 |
| `--triggers` | 导出触发器（⚠️ 8.0 默认开了） |
| `--events` | ⭐ 导出定时事件（⚠️ 容易漏） |
| `--single-transaction` | ⭐ 一致性快照，不锁表 |
| `--lock-tables=false` | 加了这个不用锁表 |
| `--hex-blob` | ⭐ 二进制数据用十六进制（防乱码） |
| `--default-character-set=utf8mb4` | ⭐ 字符集 |
| `--column-statistics=0` | ⚠️ MySQL 客户端备份 PostgreSQL 时需要 |
| `--set-gtid-purged=OFF` | ⚠️ 恢复时不想带 GTID 信息时用 |
| `--no-tablespaces` | ⚠️ 8.0 备份时避免 PROCESS 权限需求 |

⚠️ **⚠️ `--set-gtid-purged` 要注意**：默认会把备份文件的 GTID 记到「已执行集合」里。⚠️ **如果你是要恢复到主库并继续复制**，⚠️ **这个参数要加 `OFF`**，⚠️ 否则 GTID 冲突。

### 恢复

```bash
# 恢复到新库
mysql -u root -p -e "CREATE DATABASE shop_restore DEFAULT CHARSET utf8mb4;"
mysql -u root -p shop_restore < shop_20261013.sql

# ⚠️ 批量恢复时加 -- 避免参数解析问题
mysql -u root -p --default-character-set=utf8mb4 < shop_20261013.sql
```

⚠️ **⚠️ 恢复时的三个坑**：

| 坑 | 说明 |
|---|------|
| 字符集 | 恢复时 `sql_mode` 不严格，⚠️ 乱数据能塞进去 |
| ⚠️ 触发器/事件 | ⚠️ 恢复时触发器自动创建，⚠️ 可能产生意外的副作用 |
| ⚠️ 大文件 | ⚠️ 单个几 GB 的 SQL 文件恢复很慢，⚠️ 建议拆分成多个库/表分别恢复 |

⚠️ **⚠️ 恢复时关闭 `sql_mode` 会有风险**——⚠️ 宁可让恢复失败也不要写入损坏数据。

## 三、物理备份：`xtrabackup`

### 为什么需要物理备份

| 维度 | `mysqldump` | `xtrabackup` |
|------|------------|-------------|
| 备份方式 | 逻辑（SQL 语句） | 物理（数据文件） |
| 备份 100GB 数据库 | ⚠️ 几小时 | ⭐ 十几分钟 |
| 恢复时间 | ⚠️ 几小时 | ⭐ 十几分钟 |
| 恢复粒度 | ⭐ 表级 | ⛔ 只能整实例 |
| 跨版本恢复 | ⭐ 灵活 | ⚠️ 受限 |
| 能否在备库上备份 | ✅ | ⚠️ 要小心 |

⭐ **「逻辑备份适合迁移，物理备份适合快速恢复」。** 生产环境通常两个都要有。

### 基本流程

```bash
# ① 全量热备（不锁表，热复制数据文件）
xtrabackup --backup --target-dir=/backup/full \
  --user=root --password='xxx' --host=127.0.0.1

# ② 增量（基于上次全量或增量）
xtrabackup --backup --target-dir=/backup/inc1 \
  --incremental-basedir=/backup/full \
  --user=root --password='xxx'

# ③ 准备（⭐ 关键：生成 InnoDB 的 redo 应用，应用增量）
xtrabackup --prepare --target-dir=/backup/full
xtrabackup --prepare --target-dir=/backup/inc1 \
  --incremental-basedir=/backup/full

# ④ 恢复（⚠️ 目标目录必须为空）
xtrabackup --copy-back --target-dir=/backup/full --datadir=/var/lib/mysql
# 或者 mv（更快，⚠️ 要求同文件系统）
xtrabackup --move-back --target-dir=/backup/full
```

⚠️ **`--prepare` 是关键步骤**：⚠️ 它把「备份期间记录的 redo」应用到数据文件，⚠️ **不做的话恢复后数据库起不来**。

⚠️ **⚠️ `--copy-back` 需要目标目录为空**，⚠️ 且 ⚠️ **⚠️ 它会覆盖现有数据**——⚠️ **这是危险操作，恢复前务必确认路径。**

### 备份快照的一致性

⚠️ **`xtrabackup` 的物理复制不是原子快照**——⚠️ 不同文件复制的时间点不同。

⭐ **它靠「记录并应用 redo」来保证一致性**：

```
① 热复制数据文件（此时文件不一致）
② ⭐ 记录这期间的 redo 日志（位置从备份开始到结束）
③ 恢复时用 --prepare 应用这段 redo
    ↓
    恢复到「备份结束时刻」的一致状态
```

## 四、按时间点恢复（PITR）⭐

### 场景

```
8 月 1 日做了全量备份
8 月 13 日 10:00 误执行了 DELETE FROM orders
目标：恢复到 8 月 13 日 09:59
```

### 步骤

```bash
# ① 恢复全量备份到目标实例
mysql -u root -p -e "CREATE DATABASE shop_restore;"
mysql -u root -p shop_restore < full_backup.sql

# ② 找出误操作的 binlog 文件和位置
#    ⚠️ 从从库（或延迟从库）拿这个信息，因为它还保留着
mysql -e "SHOW BINLOG EVENTS IN 'binlog.000123' LIMIT 100;"

# ③ 找到误操作的位置（假设是 4567）

# ④ 生成「截止到误操作前」的 binlog 片段
mysqlbinlog \
  --start-position=154 \
  --stop-position=4567 \
  binlog.000123 binlog.000124 binlog.000125 \
  | mysql -u root -p shop_restore

# ④' 或者用时间点（更直观）
mysqlbinlog \
  --start-datetime="2026-08-13 09:00:00" \
  --stop-datetime="2026-08-13 09:59:59" \
  binlog.000123 binlog.000124 binlog.000125 \
  | mysql -u root -p shop_restore
```

### ⚠️ 三个关键点

| 点 | 说明 |
|---|------|
| ⚠️ **binlog 必须完整** | 从全量备份时刻到误操作时刻的 binlog 都要在 |
| ⚠️ **⚠️ binlog 格式必须是 ROW** | `STATEMENT` 无法定位到具体行，⚠️ 回放时可能执行了 DELETE 但不确定影响范围 |
| ⚠️ **⚠️ 需要 GTID 更准** | ⚠️ 用 GTID 可以精确定位到事务边界，避免「半个事务」 |

### GTID 模式下的 PITR

```sql
-- 1. 从全量恢复的实例上看 GTID 集合
SELECT * FROM information_schema.GTID_EXECUTED;

-- 2. 应用到误操作前的事务位置
mysqlbinlog --exclude-gtids='aaaaaaaa:1-456' binlog.* | mysql -u root -p shop_restore
```

⭐ **⚠️ GTID 的好处：能精确排除「误操作的那个事务」，⚠️ 而不是「从某位置到某位置」的模糊区间。**

## 五、备份策略

### RPO / RTO

| 术语 | 含义 | 问题 |
|------|------|------|
| **RPO**（恢复点目标） | 能容忍丢多少数据 | 「最多能接受丢 1 小时的数据？」 |
| **RTO**（恢复时间目标） | 能接受多久恢复 | 「最多能接受停机 1 小时？」 |

⚠️ **⚠️ RPO 和 RTO 直接决定了成本**——⚠️ RPO 越小，需要越频繁的备份/复制。

| 业务类型 | RPO | RTO | 方案 |
|---------|-----|-----|------|
| 论坛/日志类 | 24 小时 | 几小时 | 每日全量 |
| 电商订单 | ⚠️ **几分钟** | ⚠️ **几十分钟** | 全量 + binlog 实时 + 主从 |
| 金融/支付 | ⚠️ **接近 0** | ⚠️ **分钟级** | ⭐ MGR/半同步 + 全量 + binlog |
| 配置/字典数据 | 一周 | 一天 | 每周全量（从版本控制恢复更合适） |

### 推荐的组合

```
每日凌晨：全量物理备份（xtrabackup）
每小时：  增量物理备份（xtrabackup --incremental）
实时：    binlog 归档（每分钟或实时推送到对象存储/异地）
保留：    全量 7 天，增量 7 天，binlog 30 天
```

⚠️ **⚠️ binlog 保留期要能覆盖「最长可能的恢复时间窗」**——⚠️ 如果你可能需要恢复到 30 天前，⚠️ binlog 就要留 30 天。

### 三个必须为 1 的参数 ⭐

```sql
SHOW VARIABLES WHERE Variable_name IN (
  'innodb_flush_log_at_trx_commit',
  'sync_binlog',
  'log_bin'
);
```

| 参数 | 生产值 | 为什么 |
|------|-------|--------|
| ⭐ `innodb_flush_log_at_trx_commit` | **1** | ⚠️ 0 和 2 在断电时会丢 1 秒数据 |
| ⭐ `sync_binlog` | **1** | ⚠️ 0 和 N>1 在主库宕机时可能丢 binlog，⚠️ ⚠️ **这时从库永远补不上，数据永久丢失** |
| ⭐ `log_bin` | **ON** | ⚠️ 不开 binlog = ⚠️ **没有复制、没有 PITR、没有 CDC** |

⚠️ **⚠️ 性能代价**：⚠️ 两个参数都是 1 时，每次提交要两次 `fsync`，⚠️ 吞吐下降约 30%。

⚠️ **但这 30% 是「数据安全」的定价。** ⚠️ ⚠️ **金融/订单类系统不要为了性能调低这两个参数**——⚠️ 丢 1 秒数据可能是几千笔订单。

📌 详见 [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]]。

### 备份监控

⚠️ **⚠️ 备份最大的风险是「以为备份了，其实没成功」。** 必须监控：

```sql
-- 查 binlog 归档是否在推进
SHOW BINARY LOG STATUS;
SHOW BINARY LOGS;
```

⚠️ **必须监控的指标**：

| 指标 | 告警条件 |
|------|---------|
| 最后一次成功全量备份的时间 | > 26 小时 |
| 最后一次成功 binlog 归档的时间 | > 10 分钟 |
| binlog 文件大小 | 突然为 0（归档断了） |
| 备份文件大小 | 突然变小（备份不完整） |

⭐ **⚠️ 恢复演练的频率**：⚠️ **每季度至少一次**，⚠️ 在独立环境恢复并验证数据完整性。

## 六、恢复演练

⚠️ **⭐ 这是本篇最重要的一节。「没演练过的备份不是备份」。**

### 演练流程

```
① 在隔离环境准备一个实例（不同机器/容器）
        ↓
② 恢复最近的全量备份
        ↓
③ 应用 binlog 到指定时间点
        ↓
④ ⭐ 验证数据完整性（⚠️ 这一步最容易被跳过，也最重要）
        ↓
⑤ 记录恢复耗时（→ 真实的 RTO）
        ↓
⑥ 记录发现的问题（备��里缺了什么、binlog 断在哪）
```

### 验证数据完整性

```sql
-- ① 表数量对不对
SELECT COUNT(*) FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'shop';

-- ② 关键表行数
SELECT COUNT(*) FROM shop.orders;
SELECT COUNT(*) FROM shop.employees;

-- ③ ⚠️ 抽样核对（最关键）
SELECT * FROM shop.orders WHERE created_at = '2026-08-13 09:59:59' LIMIT 10;

-- ④ 校验和（有工具：mysqlcheck --check）
mysqlcheck -u root -p --check shop;

-- ⑤ 用应用层查询验证（⭐ 最真实的验证）
```

⚠️ **⚠️ 第 ④ 步「校验和」**：⚠️ `CHECKSUM TABLE` 可以对比，但它要求源和目标的数据完全一致，⚠️ **⚠️ 排除临时数据/时间戳的表**。

### 演练要记录什么

| 记录项 | 用途 |
|--------|------|
| ⭐ **实际恢复耗时** | ⚠️ 这是真实的 RTO，⚠️ 而不是文档里写的 |
| 遇到的问题 | 下一��备份要改进 |
| 缺失的 binlog | ⚠️ 说明保留期设置有问题 |
| 权限/配置问题 | ⚠️ 恢复环境要能访问对象存储等 |

## 七、安全加固

### 网络层

| 项 | 做法 |
|---|------|
| ⚠️ **不暴露公网** | 只监听内网，或用安全组限制 |
| ⚠️ **绑定内网地址** | `bind-address = 10.0.0.1`（⚠️ 不要 `0.0.0.0`） |
| ⚠️ **强制 TLS** | `require_secure_transport = ON` |
| ⚠️ **防火墙** | 只放行应用服务器的 IP |

⚠️ **⚠️ `bind-address` 默认是 `*`（所有网卡）。⚠️ 生产要显式设置成内网地址。**

```sql
-- 检查是否开了 TLS
SHOW VARIABLES LIKE 'have_ssl';
SHOW VARIABLES LIKE 'require_secure_transport';

-- 看当前连接是否用了 TLS
SELECT id, user, host, ssl_cipher FROM information_schema.PROCESSLIST
WHERE ssl_cipher IS NOT NULL;
```

⚠️ **`require_secure_transport = ON` 会阻止非 TLS 连接**——⚠️ 上线前先确认所有客户端都支持 TLS，⚠️ 否则会连不上。

### 账号层

⚠️ **⚠️ 最小权限原则**（详见 [[mysql/01-入门阶段-基础教程/第04章-事务与权限/4.2-角色权限与账号管理]]）：

```sql
-- ⭐ 应用账号：只给业务库的读写
CREATE USER 'app_rw'@'10.0.1.%' IDENTIFIED BY '强密码';
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'app_rw'@'10.0.1.%';

-- ⭐ 备份账号：只要只读
CREATE USER 'backup'@'localhost' IDENTIFIED BY '强密码';
GRANT SELECT, LOCK TABLES, SHOW VIEW, RELOAD, REPLICATION CLIENT
  ON *.* TO 'backup'@'localhost';
```

⚠️ **⚠️ 定期检查权限**：

```sql
-- 谁能干什么
SELECT * FROM information_schema.USER_PRIVILEGES;

-- ⚠️ 找出权限过大的账号
SELECT user, host FROM mysql.user
WHERE super_priv = 'Y' OR file_priv = 'Y';
```

### 数据层

| 项 | 做法 |
|---|------|
| ⚠️ **敏感字段加密** | 手机号、身份证用 `AES_ENCRYPT` ⚠️ 但密钥管理是难点 |
| ⚠️ **⚠️ 不要用数据库函数存密码** | 用 `caching_sha2_password` 或应用层 bcrypt/argon2 |
| ⚠️ **删除数据软删 + 归档** | 误删可恢复 |
| ⚠️ **定期检查异常账号** | `SELECT user, host, last_change_password FROM mysql.user;` |

⚠️ **⚠️ ⚠️ 最常见的数据泄露渠道不是 SQL 注入，是「应用账号权限太大」**——⚠️ 一次注入就能导出全库。

### 配置层

```ini
[mysqld]
# ⭐ 禁止 root 远程登录（⚠️ 默认就没有，但要确保）
# ⭐ 关闭不必要的默认账号
# ⚠️ 8.0 默认创建 mysql.sys / mysql.session / mysql.infoschema（只读系统账号）

# ⚠️ 本地磁盘读取（LOAD DATA / SELECT INTO OUTFILE）的管控
local_infile = OFF
secure_file_priv = /var/lib/mysql-files    # ⚠️ 限制文件读写目录
```

⚠️ **`secure_file_priv`**：⚠️ ⚠️ **MySQL 8.0 默认设为空（禁用 `LOAD DATA`/`SELECT INTO` 的文件操作）**。⚠️ ⚠️ **⚠️ 如果你的应用或备份流程需要这个功能，要显式设置目录**（⚠️ 不要设成 `/` 或空）。

```sql
SHOW VARIABLES LIKE 'secure_file_priv';
SHOW VARIABLES LIKE 'local_infile';
```

⚠️ **⚠️ 这些是重要的攻击面**：⚠️ `LOAD DATA INFILE` 可以读任意文件，⚠️ `SELECT INTO OUTFILE` 可以写 WebShell。

## 八、版本升级路径

⚠️ **MySQL 8.0 已于 2026-04-30 EOL**（见 [[mysql/README]]）。⚠️ **⚠️ 升级不能跳级**。

### 升级路径矩阵

| 当前版本 | 目标 | 路径 |
|---------|------|------|
| **5.7** | 8.4 LTS | ⚠️ 先 5.7 → 8.0 → 8.4 |
| **8.0** | 8.4 LTS | ⚠️ ⚠️ **不能直接到 9.7** |
| **8.4 LTS** | 9.7 LTS | ✅ 可以 |
| **8.4** | 26.x Innovation | ⚠️ ⚠️ **⚠️ 不能跳过兼容谱系** |

⚠️ **⚠️ 8.0 → 8.4 的关键破坏性变更**：

| 变更 | 说明 |
|------|------|
| `mysql_native_password` | ⚠️ **默认关闭**，需显式启用插件 |
| 一些参数被移除 | ⚠️ 启动参数名变了 |
| 部分默认值变化 | ⚠️ |
| 数据字典升级 | ⚠️ **不可逆**（⚠️ 降级不回去） |

⚠️ **⚠️ 8.0 → 8.4 之前的检查清单**：

```sql
-- 1. 有没有用被移除的特性
-- 2. 跑官方升级检查器（MySQL Shell）
-- 3. 检查 mysql_upgrade 是否需要跑

-- 用 MySQL Shell 的升级检查工具
-- mysqlsh -- util check-for-server-upgrade --host=... --user=root
```

⚠️ **⚠️ 升级前必做**：

| 项 | 说明 |
|---|------|
| ⚠️ **全量备份**（+ 已验证可恢复） | ⭐ 第一步 |
| ⚠️ **在测试环境完整演练一遍** | ⭐ 不在生产试错 |
| ⚠️ **记录当前配置** | `mysqld --verbose --help` |
| ⚠️ **检查应用兼容性** | ⭐ 驱动、ORM、连接池 |
| ⚠️ **准备回滚方案** | ⚠️ 保留旧版本的备份 |
| ⚠️ **低峰期操作** | ⚠️ 升级会重启 |

⚠️ **⚠️ ⚠️ 8.0 的数据字典不可逆**：⚠️ 一旦升级到 8.0，⚠️ **⚠️ 无法降级回 5.7**。⚠️ 升级前必须有**逻辑备份**（不只是物理备份），⚠️ 因为物理备份跨大版本可能不兼容。

### 升级后的验证

```sql
SELECT VERSION();                                  -- 版本对
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'; -- ⚠️ 参数没丢
SHOW GLOBAL STATUS LIKE 'Uptime';                   -- ⭐ 确认刚重启
```

⚠️ **⚠️ 升级后至少观察一周**：⚠️ 注意慢查询、错误日志、复制状态。

## 九、陷阱

1. **❌ 只做全量备份不做 binlog。** ⚠️ RPO 是「上次备份到现在」。
2. **❌ 备份文件没验证可恢复。** ⚠️ 备份的最常见失败是「从来没恢复过」。
3. **❌ `mysqldump` 不加 `--single-transaction`。** ⚠️ 锁表 + 数据不一致。
4. **❌ 生产把 `innodb_flush_log_at_trx_commit` 调到 0/2。** ⚠️ 断电丢 1 秒数据。
5. **❌ 生产把 `sync_binlog` 调到 0。** ⚠️ ⚠️ **主库宕机可能丢 binlog，从库永远补不上**。
6. **❌ 备份保留期不够长。** ⚠️ binlog 要能覆盖最长的恢复窗口。
7. **❌ 应用账号用 root 或权限过大。** ⚠️ 一次注入 = 全库泄露。
8. **❌ `bind-address` 不设成内网。** ⚠️ 数据库暴露在公网。
9. **❌ `secure_file_priv` 留空。** ⚠️ ⚠️ 文件读写攻击面。
10. **❌ 升级跳级。** ⚠️ 8.0 不能直接到 9.7。
11. **❌ 升级前不做逻辑备份。** ⚠️ 8.0 的数据字典不可逆，物理备份跨版本可能不兼容。
12. **❌ 恢复时不验证数据。** ⚠️ 只看「命令跑完了」不算恢复成功。

---

## 小结

- **备份三层**：全量 + binlog（增量）+ 主从复制（近实时）
- ⭐ **`mysqldump --single-transaction`** 是一致性快照、不锁表的关键（⚠️ 只对 InnoDB 有效）
- **`xtrabackup`** 是物理热备，⭐ 恢复快但只能整实例；⚠️ **`--prepare` 不能省**
- **PITR（按时间点恢复）** = 全量备份 + `mysqlbinlog --start/stop-position`
- ⭐ **三个必须为 1 的参数**：`innodb_flush_log_at_trx_commit`、`sync_binlog`、`log_bin`
- ⚠️ **RPO/RTO 直接决定成本**；⚠️ **binlog 保留期要覆盖最长恢复窗口**
- ⭐ **「备份没演练过 = 没有备份」**——每季度演练一次，记录**真实 RTO**
- 安全：⚠️ `bind-address` 设内网、⚠️ `secure_file_priv` 限制目录、⚠️ **最小权限**
- ⚠️ **版本升级不能跳级**（8.0 → 8.4 → 9.7）；⚠️ **8.0 的数据字典不可逆**，升级前必须有逻辑备份
