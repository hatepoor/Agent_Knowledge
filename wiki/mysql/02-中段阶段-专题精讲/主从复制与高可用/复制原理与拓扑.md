# 主从复制与高可用

> **什么时候该读**：要读从库分担压力；或者排查主从延迟；或者设计高可用方案。

1. 说清复制的完整链路（binlog → dump 线程 → relay log → 回放）

3. 掌握 GTID 的用法和它解决的问题
4. **诊断并治理主从延迟**（最重要）
5. 知道 MGR 和 InnoDB Cluster 是什么
6. 理解「延迟复制」在故障恢复中的作用

## 一、复制的完整链路

```
【主库】
  ① 写操作 → InnoDB 提交
  ② binlog thread 读取 binlog（binlog cache → binlog 文件）
  ③ ⚠️ ⚠️ 按 sync_binlog 策略刷盘
       ↓
  ④ Dump 线程（binlog dump thread）建立 TCP 连接，把 binlog 发出去
       ↓
【网络】
       ↓
【从库】
  ⑤ I/O 线程接收 → 写入 relay log（relay log 文件）
  ⑥ SQL 线程读 relay log → 应用到从库的数据文件
       ↓
  ⑦ ⚠️ relay log 写盘（按 slave_relay_log 策略）
```

⚠️ **「写入主库的 binlog」是复制的起点**——⚠️ **所以 binlog 丢失 = 复制断裂 = 无法按时间点恢复**。

### 关键线程

| 线程 | 在哪 | 作用 |
|------|------|------|
| `binlog dump` | 主库 | ⭐ 把 binlog 发给从库 |
| `I/O receiver` | 从库 | 接收 binlog 写 relay log |
| `SQL applier` | 从库 | ⚠️ **默认单线程**读 relay log 应用 |
| `purge` | 从库 | 清理 relay log |

⚠️ **⚠️ 从库回放默认单线程**——这是主从延迟的主因之一。

## 二、三种 binlog 格式

| 格式 | 记录什么 | 优点 | ⚠️ 缺点 |
|------|---------|------|---------|
| `STATEMENT` | SQL 语句 | 日志小 | ❌ **⚠️⚠️ 非确定性函数（`NOW()`、`UUID()`、`RAND()`）会导致主从不一致** |
| `ROW` | ⭐ **每一行的变化（before/after image）** | ✅ 数据一致 | 日志大 |
| `MIXED` | 自动切换 | 折中 | ⚠️ 行为不够可预测 |

### 为什么默认 `ROW` ⭐

⚠️ **⚠️ `STATEMENT` 格式的致命问题**：

```sql
-- 主库执行
INSERT INTO t (v) VALUES (RAND());
```

| 库 | 执行的时间点 | 结果 |
|---|------------|------|
| 主库 | T1 | 0.123456 |
| 从库 | ⚠️ **T2**（几毫秒后） | ⚠️ **0.654321** |

⚠️ **语句一样，但执行时刻不同 → 结果不同。** ⚠️ 这类不一致**极难排查**（数据看起来「莫名」变了）。

⚠️ **`ROW` 格式记录的是「实际发生了什么」，重放结果必然一致。** 这是数据一致性的根本保障。

### `ROW` 格式的三个参数

```ini
binlog_format = ROW
binlog_row_image = FULL        # 默认 FULL
binlog_row_metadata = MINIMAL  # 8.0 默认
```

| 参数 | 取值 | 说明 |
|------|------|------|
| `binlog_row_image` | `FULL` | ⚠️ 记录 before + after（**默认值，安全**） |
| | `MINIMAL` | ⚠️ 只记录「变化的列的 before」+ 全部 after。**日志小，但 ⚠️ 无法用于基于 binlog 的 CDC**（如 Canal/Debezium） |
| | `NONE` | ⛔ 不记录（⚠️ 基本不可用） |
| `binlog_row_metadata` | `MINIMAL` | 8.0 默认，⚠️ 不含列名，⚠️ CDC 场景要用 `FULL` |

⚠️ **⚠️ 如果你要用 Canal/Debezium 做 CDC，`binlog_row_image` 必须能提供完整行信息。** ⚠️ ⚠️ `MINIMAL` + ⚠️ ⚠️ 某些 CDC 工具会失败。

📌 见 [[redis/02-中段阶段-生产实践/09-缓存一致性-与数据库同步]]。

## 三、GTID

### 问题：传统 binlog 复制的痛点

```sql
-- 主库
SHOW MASTER STATUS;
-- File: binlog.000005   Position: 1234
```

⚠️ **从库配置这个位置就能同步。** ⚠️ **但如果主库做了 failover（新主库）**，⚠️ **⚠️ 新主库的 binlog 文件名和位置完全不同，配置要改。**

⚠️ **⚠️ 更麻烦的：漏掉一部分 binlog 后要手动指定文件 + 位置**，⚠️ 出错概率很高。

### GTID 的做法

```sql
-- 主库
SHOW MASTER STATUS;
-- Executed_Gtid_Set: 3e11fa47-71ca-11e1-9e33-c80aa9429562:1-23
```

⭐ **GTID（Global Transaction ID）= `UUID:序列号`**，每个事务在整个集群里都有唯一编号。

**从库配置只需要知道主库的 UUID**，⚠️ **自动从「已执行的事务」之后继续**，⚠️ **不需要管文件和位置。**

### GTID 的三个用法

#### 用法 1：只配置 UUID

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.1',
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'xxx',
  SOURCE_AUTO_POSITION = 1;      -- ⭐ 自动定位
```

#### 用法 2：跳过某些事务（修复数据用）

```sql
-- 在从库上把「误执行的 DELETE」排除掉
SET GTID_NEXT = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:123-456';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
```

⚠️ **这个操作很危险**，⚠️ 只在明确知道自己在做什么时用。

#### 用法 3：判断事务是否在某个库执行过

```sql
SELECT * FROM information_schema.GTID_EXECUTED\G
```

### 三个前提

⚠️ **⚠️ 用 GTID 必须开 `binlog_format=ROW`**：

```ini
[mysqld]
gtid_mode = ON
enforce_gtid_consistency = ON
binlog_format = ROW
```

⚠️ **这三个必须同时开**——⚠️ 只开 `gtid_mode` 会在 `STATEMENT` 格式时报错。

⚠️ **⚠️ 开启 GTID 是不可逆的**（8.0 里 `gtid_mode` 是只读参数，只能 ON 不能 OFF）。

## 四、⚠️ 主从延迟

### 现象

⚠️ **从库的数据落后于主库。**

⚠️ **影响**：

| 影响 | 说明 |
|------|------|
| **读到旧数据** | ⚠️ 用户提交后立刻查询却看不到 |
| **⚠️ ⚠️ 数据丢失** | ⚠️ **主库挂了，从库还没追上 → 最近的写入丢了** |
| 数据不一致 | 从库上做的修改会覆盖主库（⚠️ 单主模式下禁止） |

⚠️ **⚠️ 最严重的后果是数据丢失**：主库宕机时，未同步的 binlog 可能还在主库本地日志里（有丢失风险），也可能已经随主库一起没了。

### 三个诊断指标

```sql
SHOW REPLICA STATUS\G
```

⚠️ **⚠️ 8.0.22+ 是 `SHOW REPLICA STATUS`（`SHOW SLAVE STATUS` 已改名）**。

关键字段：

| 字段 | 含义 | ⚠️ 怎么看 |
|------|------|---------|
| `Seconds_Behind_Source` | ⚠️ **落后秒数** | ⚠️ **⚠️ 这个值可能骗人**（见下文） |
| `Replica_IO_Running` | I/O 线程状态 | ⚠️ 必须是 `Yes` |
| `Replica_SQL_Running` | SQL 线程状态 | ⚠️ 必须是 `Yes` |
| `Last_IO_Error` / `Last_SQL_Error` | 错误信息 | ⚠️ 报错时看这里 |
| `Read_Source_Log_Pos` / `Exec_Source_Log_Pos` | 已读/已执行位置 | ⚠️ 对比是否推进 |
| `Retrieved_Gtid_Set` / `Executed_Gtid_Set` | ⚠️ GTID 模式下的位置 | ⭐ **最准确的对比方式** |

### ⚠️ `Seconds_Behind_Source` 不可信

⚠️ **这是最需要警惕的一点。** 这个值是「**当前时间** - **最后执行的事件的时间戳**」，所以：

| 情况 | 显示值 | 实际延迟 |
|------|--------|---------|
| ⚠️ **网络断了** | **0** | ❌ 实际可能是几十秒 |
| ⚠️ **SQL 线程卡住** | **0** | ❌ 实际可能延迟很久 |
| ⚠️ **刚重连** | **0** | ❌ |
| ⚠️ **大事务执行中** | 递增 | 实际延迟更小 |

⚠️ **所以必须配合其他指标看**：

```sql
-- ⭐ 正确的延迟检测方法：连续采样，看「已执行 GTID」是否在推进
SELECT
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status
   WHERE VARIABLE_NAME = 'Slave_running_timestamps') AS last_event_time;
```

⭐ **推荐做法：监控「主从 GTID 集合的差」**（比如用 `pt-heartbeat` 在主从各建一个心跳表，对比时间差）。

```sql
-- pt-heartbeat 的表
SELECT * FROM heartbeat WHERE server_id = 'master';   -- 记为主库时间
SELECT * FROM heartbeat WHERE server_id = 'replica';  -- 记为从库时间
-- ⚠️ 两个时间差就是真实延迟
```

### 延迟的八个根因

| # | 根因 | 说明 | 排查 |
|---|------|------|------|
| 1 | ⚠️ **大事务** | ⭐ 头号原因。从库单线程回放，被大事务卡住 | 查 `performance_schema` 找长事务 |
| 2 | ⚠️ **从库单线程回放** | 主库有 10 个并发事务，从库串行 | ⭐ **开并行复制** |
| 3 | ⚠️ **DDL 卡住** | `ALTER TABLE` 会等所有大事务结束 | 看 `SHOW REPLICA STATUS` |
| 4 | ⚠️ **从库上有慢查询** | 占用资源 | 看慢日志 |
| 5 | ⚠️ **从库硬件差** | CPU/IO 不足 | 对比主从配置 |
| 6 | ⚠️ **无主键的表** | ⚠️ 回放时要全表扫描找行 | 查有无主键 |
| 7 | ⚠️ **表没有主键** | ⚠️ `ROW` 格式回放依赖主键定位 | ⚠️ **必须有主键** |
| 8 | ⚠️ **网络带宽** | binlog 传不过来 | 看 `Master_Sent_bytes` 增长 |

⚠️ **⚠️ 根因 6/7 特别隐蔽**：`ROW` 格式下，从库根据 binlog 里的 before image 找行。⚠️ **没有主键/唯一索引时，它要全表扫描**——⚠️ 主库插入很快，从库却慢上百倍。

### 治理措施

#### 措施 1：⚠️ 开并行复制（必做）⭐

```ini
[mysqld]  # 在从库上
slave_parallel_type = LOGICAL_CLOCK      # 5.7+
slave_parallel_workers = 8               # ⚠️ 建议 = CPU 核数
slave_parallel_type = 'COMMIT_ORDER'
```

⚠️ **⚠️ MySQL 8.0 的默认已经是 `LOGICAL_CLOCK`**（事务级并行），⚠️ 但 ⚠️ `slave_parallel_workers` 默认可能偏小。

⚠️ **⚠️ 5.6 及之前是「库级并行」**（按不同 schema 分组），⚠️ 只有一个库时没有并行效果。

```sql
SHOW VARIABLES LIKE 'slave_parallel%';
-- slave_parallel_type   = LOGICAL_CLOCK
-- slave_parallel_workers = 8
```

⚠️ **⚠️ 并行复制的代价**：⚠️ 可能产生更多冲突（多个事务改同一行），⚠️ 导致从库上的「死锁重试」增多。

#### 措施 2：禁止大事务

⚠️ 根治手段：⚠️ **应用侧分批提交**，⚠️ 主从都受益。详见 [[mysql/02-中段阶段-专题精讲/事务与并发控制/长事务与undo膨胀]]。

#### 措施 3：给表加主键

⚠️ **必做。** 检查无主键的表：

```sql
-- ⭐ 找出从库上无主键的表（⚠️ 这会显著拖慢复制）
SELECT table_schema, table_name
FROM information_schema.TABLES t
LEFT JOIN information_schema.TABLE_CONSTRAINTS c
  ON t.TABLE_SCHEMA = c.CONSTRAINT_SCHEMA
 AND t.TABLE_NAME = c.TABLE_NAME
 AND c.CONSTRAINT_TYPE = 'PRIMARY KEY'
WHERE t.TABLE_SCHEMA NOT IN ('mysql','information_schema','sys','performance_schema')
  AND c.CONSTRAINT_NAME IS NULL;
```

#### 措施 4：⏱ 延迟复制

⚭ **用延迟复制做「误删恢复」**：

```sql
-- 从库故意滞后 1 小时
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.1',
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = 'xxx',
  SOURCE_DELAY = 3600;      -- ⭐ 延迟 3600 秒
```

⚠️ **⚠️ 使用场景**：

```
10:00  主库发生误操作：DELETE FROM orders WHERE id > 10000;
10:01  发现问题

方法 A（用延迟从库）：
  ① 停止主库对业务的影响（或切到降级页）
  ② 用延迟从库（它还停在 09:00 的状态）
  ③ 从延迟从库导出误删前的数据
  ④ 恢复到主库

⚠️ 方法 B（没有延迟从库）：
  ① 用 binlog 定位误删的时间点
  ② 从全量备份 + binlog 重放到误删前一刻
  ③ ⚠️ 耗时几十分钟到几小时，且期间业务不可用
```

⭐ **延迟复制 + 全量备份 = 「点时间恢复」的可行方案。**

⚠️ **⚠️ 代价**：⚠️ 从库永远滞后 1 小时，⚠️ 读从库会读到 1 小时前的数据。⚠️ 且 ⚠️ **⚠️ 大事务会突破延迟限制**（MySQL 8.0.27+ 的 `replica_preserves_commit_order` 相关行为）。

#### 措施 5：GTID 跳过错误事务

⚠️ **⚠️ 危险操作**，只在明确知道自己在做什么时用。

```sql
-- 从库上：跳过误执行的 DELETE
STOP REPLICA SQL_THREAD;
SET GTID_NEXT = 'aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee:123-456';
BEGIN; COMMIT;
SET GTID_NEXT = 'AUTOMATIC';
START REPLICA SQL_THREAD;
```

## 五、MGR 与 InnoDB Cluster

### MGR（Group Replication）

⚠️ **MGR 是 MySQL 官方的高可用方案**，基于 Paxos 变体（组通信）。

**两种模式**：

| 模式 | 说明 | 特点 |
|------|------|------|
| **Single-Primary** | 一个主节点，多个从节点 | ⭐ 写只在主节点，读可分散（性能好） |
| **Multi-Primary** | 多个节点都可写 | ⚠️ 写冲突需要用户处理 |

| 特性 | 说明 |
|------|------|
| 自动故障切换 | 主节点挂了，从节点自动选举新的主 |
| 强一致性 | 基于 Paxos 保证事务一致 |
| ⭐ 分布式事务 | 8.0 支持，单主模式下性能好 |
| ⭐ 数据复制 | 无主架构，数据在所有节点 |

⚠️ **⚠️ MGR 的通信栈变化（重要）**：

| 版本 | 默认通信栈 |
|------|-----------|
| ≤ 9.7 | `XCOM` |
| **26.7+** | ⭐ **`MYSQL`**（MySQL Server 连接安全和认证） |

⚠️ **升级注意事项**：
- ⭐ **组内所有成员必须使用一致的通信栈**
- ⚠️ 改通信栈需要**协调运维步骤**（⚠️ 逐个升级会破坏组）
- ⚭� **`MYSQL` 通信栈的优势**：复用 MySQL 的认证和加密配置，运维更统一

### InnoDB Cluster

⚠️ **MGR + 两个配套工具的组合**：

```
MySQL Shell（AdminAPI）
   ↓ 配置拓扑、管理扩缩容、引导集群

MySQL Router
   ↓ ⭐ 代理层：应用连它，它自动路由
   ├── 写请求 → 主节点
   └── 读请求 → 从节点
```

| 组件 | 作用 |
|------|------|
| **MySQL Shell** | 命令行工具，AdminAPI 管理集群 |
| **MySQL Router** | ⭐ 代理，端口 6446（读写）/ 6447（只读） |

### 三种高可用方案对比

| 方案 | 复杂度 | 一致性 | 自动切换 | RTO | RPO | 成本 |
|------|-------|--------|---------|-----|-----|------|
| **主从复制**（手动） | 低 | ⚠️ 异步，可能丢数据 | ❌ 手动 | ⚠️ 分钟级 | ⚠️ 可能丢失 | 低 |
| **主从 + 半同步** | 中 | ⚠️ 至少一个从库确认 | ❌ 手动 | 分钟级 | ⚠️ 少量丢失 | 低 |
| ⭐ **MGR / InnoDB Cluster** | 高 | ✅ 强一致 | ✅ 自动 | ⚠️ 秒级 | ✅ 基本不丢 | 中 |
| 云托管（RDS/Aurora） | 低 | ✅ | ✅ 自动 | 秒级 | ✅ | ⚠️ 高 |

📌 更详细的原理见 [[mysql/02-中段阶段-专题精讲/主从复制与高可用/复制原理与拓扑]]。

## 六、搭建主从的完整步骤

⚠️ **⚠️ 以下步骤假设使用 GTID（推荐）。**

### 主库配置

```ini
[mysqld]
server_id = 1
log_bin = /var/log/mysql/binlog
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON
sync_binlog = 1                    -- ⚠️ 生产必须 1
innodb_flush_log_at_trx_commit = 1 -- ⚠️ 生产必须 1
```

### 从库配置

```ini
[mysqld]
server_id = 2
log_bin = /var/log/mysql/binlog     -- ⭐ 从库也要开 binlog（为将来升主准备）
relay_log = /var/log/mysql/relaylog
read_only = ON                      -- ⭐ 只读，防止误写
super_read_only = ON                -- ⭐ 8.0：连 SUPER 权限也不能写
gtid_mode = ON
enforce_gtid_consistency = ON
binlog_format = ROW
slave_parallel_type = LOGICAL_CLOCK
slave_parallel_workers = 8
```

### 复制账号

```sql
-- 在主库上执行
CREATE USER 'repl'@'10.0.0.%' IDENTIFIED BY '强密码';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl'@'10.0.0.%';
```

⚠️ **8.4+ 改了权限名**：

```sql
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl'@'%';
-- ⚠️ 8.4 起 REPLICATION SLAVE 被拆分/限制，需要看具体版本的授权要求
```

### 建立复制

```sql
-- 在从库上执行
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.1',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = '强密码',
  SOURCE_AUTO_POSITION = 1,        -- ⭐ GTID 自动定位
  SOURCE_CONNECT_RETRY = 60,
  SOURCE_RETRY_COUNT = 86400;      -- 无限重试

START REPLICA;
SHOW REPLICA STATUS\G
```

⚠️ **⚠️ 8.0.23+ 建议同时指定 TLS**：

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = '10.0.0.1',
  SOURCE_SSL = 1,
  SOURCE_SSL_CA = '/path/to/ca.pem',
  SOURCE_AUTO_POSITION = 1;
```

### 验证

```sql
SHOW REPLICA STATUS\G
-- 三个关键字段：
--   Replica_IO_Running: Yes
--   Replica_SQL_Running: Yes
--   Seconds_Behind_Source: 0（或很小）
```

⚠️ **`super_read_only = ON` 很重要**——⚠️ `read_only` 允许 SUPER 权限的用户写入，⚠️ `super_read_only` 连 SUPER 也不让写。

---

## 七、陷阱

1. **❌ 只看 `Seconds_Behind_Source`。** ⚠️ **它会骗人**（网络断开时显示 0）。用 GTID 集合差或 `pt-heartbeat`。
2. **❌ 从库不开 `slave_parallel_workers`。** ⚠️ 单线程回放是延迟主因。
3. **❌ 表没有主键。** ⚠️ `ROW` 格式回放要全表扫描，⚠️ 主库快从库慢上百倍。
4. **❌ `binlog_format = STATEMENT`。** ⚠️ 非确定性函数会导致主从不一致。
5. **❌ 用 `binlog_row_image = MINIMAL` 但要跑 CDC。** ⚠️ 工具会失败。
6. **❌ 从库不设 `read_only` / `super_read_only`。** ⚠️ 误写会导致数据不一致。
7. **❌ 在从库上跑慢查询或大批量操作。** ⚠️ 会造成严重延迟。
8. **❌ 用 `SHOW SLAVE STATUS`。** ⚠️ 8.0.22+ 是 `SHOW REPLICA STATUS`。
9. **❌ 主库不做 `sync_binlog = 1`。** ⚠️ 主库宕机会丢 binlog，⚠️ 从库就永久丢了那段数据。

---

## 小结

- 复制链路：⭐ **binlog → dump 线程 → relay log → SQL 线程回放**
- ⚠️ **从库回放默认单线程**——延迟的主因之一
- ⭐ **`binlog_format = ROW` 是数据一致性的根本保障**（`STATEMENT` + 非确定性函数 = 主从不一致）
- ⚠️ `binlog_row_image = MINIMAL` 会让 CDC 工具失败
- **GTID** 解决「主库 failover 后位置要改」的问题，⚠️ 需要 `ROW` 格式 + 不可逆
- ⚠️⚠️ **`Seconds_Behind_Source` 会骗人**——用 GTID 集合差或 `pt-heartbeat`
- **延迟的八个根因**：⭐ 大事务、单线程回放、DDL、从库慢查询、硬件、⚠️ **无主键表**、网络
- ⭐ **必做的三件事**：开并行复制、禁止大事务、⚠️ **给所有表加主键**
- **延迟复制**（`SOURCE_DELAY`）用于「误删恢复」，⚠️ 代价是从库永远滞后
- **MGR** 有两种模式，⚠️ **26.7 起默认通信栈从 XCOM 改为 MYSQL**（⚠️ 组内必须一致，⚠️ 升级需协调）
- **InnoDB Cluster = MGR + MySQL Shell + MySQL Router**
