## 一、InnoDB 为什么是默认

| 特性 | InnoDB | MyISAM |
|------|--------|--------|
| 事务 | ✅ | ❌ |
| 外键 | ✅ | ❌ |
| 锁粒度 | ⭐ **行锁** | 表锁 |
| MVCC | ✅ | ❌ |
| 崩溃恢复 | ✅ 自动 | ❌ 手动 |
| 索引组织 | ⭐ 聚簇索引 | 非聚簇 |

⚠️ **MyISAM 只在「只读超多、几乎不写」的遗留场景有价值。** 新项目一律用 InnoDB。

### 其他引擎

| 引擎 | 用途 | 注意 |
|------|------|------|
| `MEMORY` | 临时表、内存数据库 | ⚠️ 重启丢数据；⚠️ 支持的索引类型有限 |
| `CSV` | 导入导出中间态 | 无索引 |
| `ARCHIVE` | 归档压缩 | 只支持 `SELECT`，压缩后不能写 |
| `NDB Cluster` | 分布式集群 | ⚠️ 无全局锁（不同表可不同节点），但限制多 |

⭐ **`MEMORY` 的现代替代是 `TempTable`（内部临时表）+ InnoDB 普通表**——⚠️ 8.0 起**内部临时表**的默认引擎是 `TempTable`（参数 `internal_tmp_mem_storage_engine`，它替代了 MEMORY），**既不是 MEMORY 也不是 InnoDB**；只有用户自己 `CREATE TEMPORARY TABLE` 才默认 InnoDB。

📌 **引擎之间的取舍**（为什么只有 InnoDB 有事务、其他引擎各自放弃了什么）见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/为什么只有InnoDB支持事务]]；三大引擎（InnoDB / MyISAM / MEMORY）**特性逐项对比与选型**见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/三大引擎特性对比与选型]]；全引擎清单与老库迁移见 [[mysql/02-中段阶段-专题精讲/存储引擎与选型/引擎全景与迁移实操]]。

## 二、页（Page）：磁盘 IO 的基本单位

### 为什么要分页

⚠️ **磁盘 IO 以「块」为单位（通常 4KB），但如果每次只读 4KB，会浪费机械硬盘的寻道开销。** 所以数据库把所有数据组织成固定大小的页，**一次读一整页**。

| 引擎 | 页大小 | 可配置 |
|------|--------|--------|
| ⭐ **InnoDB** | **16KB**（默认） | ⚠️ 初始化时定，之后不能改 |
| MyISAM | 16KB | 固定 |

### 16KB 页的组成

```
┌────────────────────────────────────────────────┐
│ File Header      38 B   │ 文件头                │
├────────────────────────────────────────────────┤
│ Page Header      56 B   │ 页头（⭐ 关键）        │
├────────────────────────────────────────────────┤
│ Infimum + Supremum 26 B │ 虚拟的最小/最大记录    │
├────────────────────────────────────────────────┤
│ User Records     │ 实际存储的用户记录           │
│   (行数据)        │   按插入顺序，⚠️ 不有序     │
│                  │                             │
│                  │                             │
│                  │ ← 这是「无序」的关键          │
│                  │                             │
├────────────────────────────────────────────────┤
│ Free Space      │ 空闲空间（新行插这里）         │
├────────────────────────────────────────────────┤
│ Page Directory   │ 页目录（⭐ 槽数组）          │
├────────────────────────────────────────────────┤
│ File Trailer     8 B    │ 校验（防页断裂）        │
└────────────────────────────────────────────────┘
```

### Page Header 的关键字段

| 字段 | 作用 |
|------|------|
| `PAGE_N_DIR_SLOTS` | ⭐ **槽的数量**，页目录的索引项数 |
| `PAGE_HEAP_TOP` | 第一个记录的指针位置（堆顶） |
| `PAGE_N_HEAP` | ⭐ **记录数量**（⚠️ 含 infimum/supremum） |
| `PAGE_FREE` | 空闲空间链表头指针 |
| `PAGE_N_REC` | ⭐ 活跃记录数量（8.0 新增，用于快速判断） |

⭐ **`PAGE_N_HEAP` 和 `PAGE_N_REC` 的差值能告诉你「本页有多少是废弃的」**——⚠️ 这个差值大说明有膨胀。

### Page Directory（页目录）⭐

⚠️ **这是 InnoDB 最巧妙的设计之一。**

```
页里有很多记录，⚠️ 但记录是「插入顺序」不是「主键顺序」。
  ↓
所以不能二分查找——必须逐条比较（慢）
  ↓
解法：维护一个「槽」数组，每 4~8 条记录分一个槽。
槽里存的是该组第一条记录的「最小主键值」（因为组内有序）
  ↓
查询时先二分槽，再在组内（最多 8 条）顺序比较
  ↓
⭐ 页内查找变成「二分 + 少量顺序」，不再是全扫
```

📌 完整机制见 [[mysql/03-进阶阶段-深度剖析/00-剖析方法论]]。

## 三、聚簇索引：数据在 B+ 树的叶子上

### 叶子节点长什么样

```
┌────────────────────────────────────┐
│ 非叶子节点（索引层）                 │
│   [10 | 20] [30 | 40]              │  ← 只存键，不存数据
│   [50 | 60] [70 | 80]              │     ⭐ 键越多，节点越小，树越矮
└────────────────────────────────────┘
          ↓
┌────────────────────────────────────┐
│ 叶子节点（数据层）⭐                 │
│  页1: [5|row][10|row][20|row]      │  ← 每条记录 = 主键 + 完整行数据
│  页2: [30|row][40|row][50|row]     │
│  页3: [60|row][70|row][80|row]     │
│  页4: [90|row]  ← 双向链表         │  ← ⭐ 叶子间串成双向链表
└────────────────────────────────────┘
```

⭐ **三个关键特征**：

| 特征 | 意义 |
|------|------|
| **叶子存完整行** | ⭐ 聚簇索引查询不用「回表」 |
| **叶子间是链表** | ⭐ 范围查询只需定位起点，然后顺序扫 |
| **非叶子只存键** | ⭐ 相同内存能放更多键 → 树更矮 → IO 更少 |

### 行格式：记录的物理布局

| 行格式 | 版本 | 特点 |
|--------|------|------|
| `COMPACT` | 5.6 | 变长字段长度列表（逆序） |
| `REDUNDANT` | 5.0 | 老格式 |
| ⭐ **`DYNAMIC`** | **5.7+ 默认** | COMPACT 的改进，⭕ 变长字段可能存到「溢出页」 |
| `COMPRESSED` | 5.7+ | DYNAMIC + 压缩，⚠️ 性能开销 |

⚠️ **`DYNAMIC` 的「溢出页」行为值得知道**：

```
DYNAMIC 格式的行：
  ┌────────────────────────────────────┐
  │ 变长字段长度列表                     │
  │ NULL 值列表                         │
  │ 隐藏列（事务ID、DB_ROW_ID 等）       │
  │ 固定长度字段                         │
  │ ┌────────────┐ ┌────────────┐     │
  │ │ 变长字段1   │ │ 变长字段2   │  ← 都在本页
  │ └────────────┘ └────────────┘     │
  │ 溢出指针（如果有溢出）               │
  └────────────────────────────────────┘
```

⚠️ **DYNAMIC 格式下，变长字段在空间足够时存本页，不够时把「尾部」移到溢出页**，指针留在本页。⚠️ 这意味着**查大字段时要多读一页**。

📌 详见 [[mysql/03-进阶阶段-深度剖析/00-剖析方法论]]。

## 四、Buffer Pool ⭐

### 为什么需要

⚠️ **机械磁盘的 IO 慢（是内存的几十到几百倍）。** 但操作系统有「页缓存」，数据库不能完全依赖它——所以自己实现了一套。

```
① 查询要读某页
   ↓
② 数据在 Buffer Pool 吗？
   ├── ✅ 在 → ⭐ 直接读内存（微秒）
   └── ❌ 不在 → 从磁盘读（毫秒），然后放进 Buffer Pool
```

⭐ **`Buffer Pool` 是 InnoDB 最关键的内存结构。**

### 内存结构

```
Buffer Pool（默认物理内存的 50~70%）
├── 数据页        （最常用，占大头）
├── 索引页
├── 插入缓冲 / Change Buffer（写优化）
├── 自适应哈希索引（8.0 默认开）
└── 锁信息、事务信息等元数据
```

| 组成 | 作用 | 备注 |
|------|------|------|
| **数据页 / 索引页** | ⭐ 缓存读过的数据 | 主要部分 |
| **Change Buffer** | ⭐ **对非唯一二级索引的写入做缓冲** | ⚠️ 后台线程按条件刷盘 |
| **自适应哈希索引** | 自动为热点查询建哈希索引 | 8.0 默认开，⚠️ 高并发下可能造成性能抖动 |
| **⚠️ 空闲链表 / LRU 链表** | 淘汰策略 | 见下文 |

### LRU 淘汰策略 ⚠️

**标准的 LRU（Least Recently Used）的问题是**：

```
一次性扫表读 1000 万行：
  ① 每读一页都是「最近最少使用」→ 排在 LRU 尾部
  ② 但它用完就不要了
  ③ LRU 尾部本该是「冷数据」，被这次扫描填满了
  ④ ⚠️ 等真正需要「热数据」时，全被挤出去了 → 缓存命中率暴跌
```

⭐ **InnoDB 的解法：LRU 列表分两段**

```
┌──────────────────────────────────────────────┐
│ young 区（5/8，默认）：真正热的页              │
├──────────────────────────────────────────────┤
│ old 区（3/8，默认）：新读进来的页              │
└──────────────────────────────────────────────┘
```

**规则**：

| 页的年龄 | 行为 |
|---------|------|
| 在 `old` 区停留时间 < `innodb_old_blocks_time`（默认 1000ms） | ⭐ 移到 `young` 区 |
| 在 `old` 区停留时间 ≥ 阈值 | 留在 `old`，等待淘汰 |

⭐ **机制**：只有「在 old 区停留够久」的页才被认为是真正热的，会被提升到 young。而「一次性扫描」的页因为读完后很快就不再被访问，会被留在 old 区（不被提升），⚠️ 也不太可能被保留（因为 LRU 淘汰时优先淘汰 old 区尾部）。

```sql
SHOW VARIABLES LIKE 'innodb_old_blocks%';
-- innodb_old_blocks_pct    = 37   （old 区占 3/8）
-- innodb_old_blocks_time   = 1000 （停留多久算热）
```

### 三个必调参数

#### `innodb_buffer_pool_size` ⭐

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
```

| 场景 | 建议 |
|------|------|
| **专用数据库服务器** | 物理内存的 **70~80%** |
| ⚠️ **数据库和应用同机** | 物理内存的 **50~60%**（要给操作系统和应用留） |
| ⚠️ **建议下限** | 物理内存的 30%。⚠️ **低于这个值索引都装不下，必然慢** |

⚠️ **⚠️ 最大值**：⚠️ **64 位系统下 `innodb_buffer_pool_size` 上限是 16GB（8.0）**。⚠️ 超过要用 `innodb_buffer_pool_instances` 分多个实例，⚠️ **但实例数不能随意改**——⚠️ 8.0 里改它需要重建 buffer pool（会清空缓存）。

⚠️ **⚠️ 改这个参数要重启**，⚠️ 且重启后会「冷启动」（缓存全空，需要预热）。⚠️ **生产改这个参数要选低峰期 + 准备预热脚本。**

#### `innodb_buffer_pool_instances`（8.0+）

⚠️ 8.0 起默认 8 个实例。⚠️ **每个实例独立管理自己的 LRU 链表。**

| 参数 | 说明 |
|------|------|
| `innodb_old_blocks_pct` | old 区比例（默认 37） |
| `innodb_old_blocks_time` | 阈值毫秒（默认 1000） |

⚠️ **⚠️ `innodb_old_blocks_time` 调大**：更多页被当热的（缓存更多），⚠️ 但一次性扫描更容易污染缓存。**调大适合「数据量远小于内存」的场景。**

#### `innodb_buffer_pool_dump_at_shutdown` / `load_at_startup` ⭐

⚠️ **8.0 的冷启动问题**：MySQL 重启后 Buffer Pool 是空的，⚠️ 要磁盘 IO 才能重新预热，⚠️ 此时业务可能短暂变慢。

```sql
-- my.cnf
-- innodb_buffer_pool_dump_at_shutdown = ON   # 关闭时把热点页列表存到文件
-- innodb_buffer_pool_load_at_startup = ON    # 启动时加载
-- innodb_buffer_pool_dump_pct = 40           # 存最热的 40%
-- innodb_buffer_pool_load_now = ON           # ⚠️ 后台加载而不是启动时阻塞
```

⚠️ **⚠️ `innodb_buffer_pool_load_now = ON` 是关键**——⚠️ 否则 MySQL 启动时会等 buffer pool 加载完才接收连接，启动时间会长达几十分钟。

### Buffer Pool 的监控

```sql
-- 命中率（>99% 才算好）
SHOW ENGINE INNODB STATUS\G
-- Buffer pool hit rate 100.00 - 100 bits/1000

-- 或用 sys 视图
SELECT * FROM sys.innodb_buffer_stats_by_table\G

-- 监控配置
SELECT * FROM information_schema.INNODB_BUFFER_PAGE\G   -- ⚠️ 很慢，只在排查时用
```

| 命中率 | 判断 |
|--------|------|
| **> 99%** | ⭐ 好 |
| 95~99% | ⚠️ 考虑加内存或减小数据集 |
| < 95% | ❌ ❗ Buffer Pool 太小或查询模式有问题 |

⚠️ **⚠️ 冷启动后命中率会低，这是正常的。** 看「稳定运行后的稳态命中率」才有意义。

📌 Change Buffer 和刷盘机制见 [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]]。

## 五、Change Buffer：写入优化

### 机制

⚠️ **问题场景**：

```
INSERT INTO t (id, name, dept_id) VALUES (5, '张三', 3);
                                           ↑
                                    这是二级索引（非唯一）
```

⚠️ **如果 `dept_id` 有索引，这个 INSERT 需要：**

| 普通做法 | Change Buffer 做法 |
|---------|-------------------|
| 立刻在索引里找位置 → ⭐ **需要随机 IO** | 先把「要插入什么」记在 Change Buffer 里 → 顺序写 |
| ⛔ 随机 IO 慢 | ✅ 后台线程按条件合并刷盘 |

### 适用范围

| 场景 | 是否进 Change Buffer |
|------|-------------------|
| **⚠️ 非唯一二级索引的插入** | ✅ 会 |
| **聚簇索引** | ❌ 不会（必须立即有序） |
| **唯一索引** | ❌ 不会（⚠️ 唯一性检查需要立即读） |
| 页面已经在 Buffer Pool 里 | ❌ 不会（不需要随机 IO） |
| ⚠️ **「右部插入」（页空间足够放）** | ❠️ **不适用**——顺序追加不慢 |

⚠️ **⚠️ Change Buffer 不是万能的。** 如果工作集远小于 Buffer Pool（页都在内存里），Change Buffer **只会增加延迟**——数据写进去后要等后台线程刷。

### 监控与调优

```sql
SHOW VARIABLES LIKE 'innodb_change_buffering';
-- all      所有写入都缓冲（默认）
-- none     关闭
-- inserts  只缓冲插入
-- purges   只缓冲「删除后合并」

SHOW ENGINE INNODB STATUS\G
-- 关注 "insert buffer and adaptive hash index" 段落
-- 关注 "20% ... 1.23 inserts/s ... no ... 0.00 reads/s"
```

⚠️ **判断 Change Buffer 是否有效**：⚠️ 如果 pending reads 很高且 buffer pool 命中率也高，说明**工作集小但索引插入随机**——Change Buffer 在起作用。

⚠️ **⚠️ 生产建议：保持默认 `all`，不要改。** ⚠️ 只有在「Buffer Pool 小 + 大量非唯一索引写入」的场景才明确收益。

## 六、表空间与文件

### 8.0 的变化

```sql
SHOW VARIABLES LIKE 'innodb_file_per_table';    -- 默认 ON（8.0）
```

| 版本 | 表空间布局 |
|------|-----------|
| **5.7 及之前** | ⭐ 所有表的数据和索引都在 `ibdata1`（共享表空间），⚠️ **无法单独回收空间** |
| **8.0+** | ⭐ `innodb_file_per_table=ON` 时每表一个 `.ibd` 文件，⚠️ **⚠️ 但降级不能回收** |

⚠️ **⚠️ MySQL 8.0 最大的变化**：数据库的**表结构信息（数据字典）从 `.frm` 文件移到了 InnoDB 表空间**（`mysql.ibd`）。⚠️ 这是一个巨大的架构改进（让数据字典也能事务保护），⚠️ 但也意味着降级到 5.7 不可能（数据字典格式不兼容）。

### 数据目录结构

```
/var/lib/mysql/
├── ibdata1                    ← 共享表空间（8.0 里主要是 undo + 变更缓冲等）
├── mysql.ibd                  ← ⭐ 8.0：数据字典（表结构）
├── undo_001 / undo_002        ← 独立 undo 表空间（8.0 默认，⚠️ 可配置）
├── shop/
│   ├── employees.ibd          ← ⭐ 每表一个文件
│   └── departments.ibd
├── #innodb_redo/              ← ⚠️ redo 日志（⚠️ 不能删）
├── binlog.000001              ← ⚠️ binlog（⚠️ 不能删）
├── mysql/                     ← 系统库（账号、权限、变量）
├── sys/                       ← 性能视图
└── performance_schema/        ← 性能监控
```

### 三个危险的文件

⚠️ **绝对不能删/改的**：

| 文件 | 删了会怎样 |
|------|-----------|
| **`#innodb_redo/`** | ⚠️⚠️ **数据库无法启动** |
| **`binlog.*`** | ⚠️ **主从断链、CDC 断流**、不能按时间点恢复 |
| **`mysql.ibd`** | ⚠️⚠️ **丢失所有表结构和账号信息** |

⚠️ **⚠️ 不能直接 `cp /var/lib/mysql` 做备份**——不锁库的复制会得到不一致快照（部分页已写、部分未写）。

📌 正确的备份方式见 [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]]。

## 七、⚠️ 膨胀（bloat）

### 现象

⚠️ **DELETE 了很多行，但 `.ibd` 文件大小不变。**

```
DELETE FROM log WHERE created_at < '2025-01-01';   -- 删了 1000 万行
-- 但 log.ibd 仍然是 20GB
```

### 原因

⚠️ **InnoDB 的删除只是把记录标记为「已删除」，空间不还给操作系统。**

| 机制 | 说明 |
|------|------|
| 页内空间可复用 | ⭐ 删除后页内的空闲空间**能给新插入用** |
| ⛔ 但文件不缩小 | ⭐ **页内放不下新数据时，才需要重建页** |

⚠️ **关键区别**：

| 场景 | 表现 |
|------|------|
| **随机删除**（比如按主键） | ⚠️ 页内空间碎片化 → 空间利用率下降 |
| **顺序删除**（按主键范围，比如 `DELETE WHERE id < N`） | ✅ 前面的页整体空了，能被复用 |

### 治理

```sql
-- 重建表：整理碎片并回收空间（⚠️ 重操作）
OPTIMIZE TABLE log;      -- = REORGANIZE + ANALYZE

-- 只整理（不加索引统计）
ALTER TABLE log ENGINE = InnoDB;

-- 只更新统计
ANALYZE TABLE log;
```

⚠️ **⚠️ `OPTIMIZE TABLE` 对大表是重操作**（复制全表）。⚠️ 用 `pt-online-schema-change` 或 `gh-ost` 做无锁重建。

⚠️ **更好的预防手段：分区表 + DROP PARTITION**

```sql
ALTER TABLE log PARTITION BY RANGE (TO_DAYS(created_at)) (
  PARTITION p202501 VALUES LESS THAN (TO_DAYS('2025-02-01')),
  PARTITION p202502 VALUES LESS THAN (TO_DAYS('2025-03-01'))
);

-- 清理：⚠️ 秒级完成，⚠️ 不需要重建表，⚠️ 空间立刻还给操作系统
ALTER TABLE log DROP PARTITION p202501;
```

📌 分区表见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。

## 八、调优检查清单

| 项 | 检查命令 | 建议 |
|---|---------|------|
| `innodb_buffer_pool_size` | `SHOW VARIABLES LIKE 'innodb_buffer_pool_size'` | 专用机 70~80%，混合部署 50~60% |
| Buffer Pool 命中率 | `SHOW ENGINE INNODB STATUS\G` | > 99% |
| `innodb_flush_log_at_trx_commit` | `SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit'` | ⚠️ 生产 = 1 |
| `innodb_old_blocks_pct` | `SHOW VARIABLES LIKE 'innodb_old_blocks_pct'` | 默认 37，一般不改 |
| `innodb_file_per_table` | `SHOW VARIABLES LIKE 'innodb_file_per_table'` | 保持 ON |
| `innodb_flush_neighbors` | — | SSD 上考虑设为 0（⚠️ 见下） |
| 膨胀 | `.ibd` 文件大小 vs `information_schema` 的数据大小 | 明显膨胀则重建 |

⚠️ **`innodb_flush_neighbors`**：默认 1 表示刷脏页时「顺带刷相邻页」（对机械盘有利，靠连续 IO）。⚠️ **SSD 上建议设为 0**——⚠️ SSD 没有「相邻」的寻道优势，顺带刷会导致不必要的写放大。

## 九、陷阱

1. **❌ `innodb_buffer_pool_size` 设成物理内存的 95%。** ⚠️ 操作系统和其他进程会 OOM。
2. **❌ 改 `innodb_buffer_pool_size` 不考虑冷启动。** 重启后缓存全空。
3. **❌ 用 `innodb_old_blocks_time` 调大解决所有缓存问题。** 只在「工作集远小于内存」时有效。
4. **❌ 指望 `OPTIMIZE TABLE` 处理大表。** ⚠️ 那是复制全表，用 `pt-osc`。
5. **❌ 直接 `cp /var/lib/mysql` 备份。** ⚠️ 不一致快照。
6. **❌ DELETE 很多行后以为空间还回去了。** ⚠️ 页内能复用但文件不缩小。
7. **❌ SSD 上保持 `innodb_flush_neighbors=1`。** ⚠️ 无意义的写放大。
8. **❌ 用 MyISAM。**

## 小结

- InnoDB 是唯一推荐的引擎：**事务、外键、行锁、MVCC、崩溃恢复**
- **页是 16KB**，页内用**槽数组（Page Directory）**做二分查找
- ⭐ **聚簇索引的叶子存完整行**，叶子间是链表（支持范围查询）
- `DYNAMIC` 行格式下，变长字段可能溢出到溢出页
- ⭐ **`Buffer Pool` 是最关键的内存结构**，建议专用机 70~80%
- ⚠️ **LRU 的两段式设计**（young + old）解决了「一次性扫描污染缓存」的问题
- ⚠️ **`FOR UPDATE` 后 Buffer Pool 命中率 < 95% 是危险信号**
- **Change Buffer** 只对「非唯一二级索引 + 右部插入 + 页不在内存」有效；工作集小于内存时反而增加延迟
- 8.0 的数据字典进了 InnoDB（`mysql.ibd`），⚠️ 降级 5.7 不可能
- ⚠️ **`.ibd` 不缩小的解法**：`OPTIMIZE TABLE`（重）或 **分区表 + DROP PARTITION**（轻）
