## 一、工具全景

### MySQL 自带

| 工具 | 用途 | 什么时候用 |
|------|------|-----------|
| ⭐ `mysql` | 命令行客户端 | 日常 |
| ⭐ `mysqladmin` | 探活、关库、看状态 | 监控脚本 |
| ⭐ `mysqldump` | 逻辑备份 | 备份/迁移 |
| `mysqlbinlog` | ⭐ 读 binlog（做 PITR） | 恢复数据 |
| `mysqlcheck` | 检查/修复表 | 表损坏时 |
| `mysql_upgrade` | 系统表升级 | 版本升级后（⚠️ 8.0 已弃用） |
| ⭐ `mysqlsh`（MySQL Shell） | ⭐ 官方统一工具，含 AdminAPI | 管理集群、升级检查 |
| `mysql_tzinfo_to_sql` | 时区表导入 | 改时区时 |
| `innochecksum` | 检查表空间完整性 | 数据损坏排查 |

### Percona Toolkit（第三方，⚠️ 强烈推荐）

⭐ **`pt-*` 系列是 MySQL 运维的事实标准工具。**

| 工具 | 用途 |
|------|------|
| ⭐ `pt-query-digest` | ⭐ **慢日志聚合分析**，找 Top N 慢查询 |
| ⭐ `pt-online-schema-change` | ⭐ **在线改表**（不锁表） |
| ⭐ `pt-heartbeat` | ⭐ **心跳表测主从延迟** |
| `pt-archiver` | 归档大表数据 |
| `pt-table-checksum` | 主从数据校验 |
| `pt-slave-delay` | 人为设置从库延迟（⚠️ 演练用） |
| `pt-kill` | 杀掉指定用户/类型的查询 |

### 系统视图

| 库 | 用途 |
|----|------|
| ⭐ `performance_schema` | ⭐ **性能监控数据源**（等待事件、语句统计、锁、事务） |
| ⭐ `sys` | ⭐ **建在 performance_schema 上的可读视图**（⚠️ 用 SQL 而不是查 performance_schema） |
| `information_schema` | 元数据（表结构、索引、进程列表、权限） |
| `mysql` | 系统表（账号、变量、时区） |

⭐ **`sys` schema 是「应该优先用」的**：它把 performance_schema 的原始数据加工成人类能直接读懂的视图。

```sql
-- sys schema 有 100+ 个视图
SELECT * FROM sys.sys_views LIMIT 30;
```

## 二、`performance_schema`：原始监控数据

### 概览

```sql
SELECT * FROM performance_schema.setup_instruments
WHERE NAME LIKE 'statement%' AND ENABLED = 'YES';
```

⚠️ **`performance_schema` 默认开启但采集有限**——⚠️ 大量事件类型默认是 `DISABLED`：

```sql
-- 开启等待事件采集（⚠️ 有性能开销，生产要评估）
UPDATE performance_schema.setup_instruments
SET ENABLED = 'YES', TIMED = 'YES'
WHERE NAME LIKE 'wait/%' OR NAME LIKE 'statement/%';
```

⚠️ **⚠️ 开启全量采集有 5~10% 的性能开销**——⚠️ ⚠️ **生产要谨慎，先在测试环境评估。**

### 三个最实用的表

#### 表 1：`events_statements_summary_by_digest` ⭐⭐

⭐ **「哪个语句最耗资源」的答案全在这里。**

```sql
SELECT
  DIGEST,
  DIGEST_TEXT,
  COUNT_STAR,
  ROUND(SUM_TIMER_WAIT/1000000000000, 3) AS total_sec,
  ROUND(AVG_TIMER_WAIT/1000000000, 3) AS avg_ms,
  SUM_ROWS_EXAMINED,
  SUM_ROWS_SENT,
  ROUND(SUM_ROWS_EXAMINED / NULLIF(SUM_ROWS_SENT, 0), 1) AS exam_per_sent,
  SUM_NO_INDEX_USED,          -- ⭐ ⭐ 没走索引的次数
  SUM_CREATED_TMP_DISK_TABLES,-- ⭐ ⭐ 用了磁盘临时表
  SUM_SORT_MERGE_PASSES      -- ⭐ ⭐ filesort 的合并次数
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

⚠️ **三个最有价值的指标**：

| 指标 | 含义 | ⚠️ 告警条件 |
|------|------|-----------|
| ⭐ `SUM_ROWS_EXAMINED / SUM_ROWS_SENT` | 扫描/返回比 | ⚠️ **> 100 说明浪费** |
| ⭐ `SUM_NO_INDEX_USED` | 没走索引的次数 | ⚠️ **> 0 就该优化** |
| ⭐ `SUM_CREATED_TMP_DISK_TABLES` | 磁盘临时表次数 | ⚠️ **> 0 说明 `Using temporary` 落盘了** |
| `SUM_SORT_MERGE_PASSES` | filesort 合并次数 | ⚠️ > 0 说明排序量大 |

#### 表 2：`data_lock_waits`（8.0）⭐

```sql
-- 当前的锁等待
SELECT * FROM performance_schema.data_lock_waits\G

-- ⭐ 谁在等谁（简洁版）
SELECT
  r.trx_id AS waiting_trx,
  r.trx_query AS waiting_query,
  b.trx_id AS blocking_trx,
  b.trx_query AS blocking_query,
  TIMESTAMPDIFF(SECOND, b.trx_started, NOW()) AS blocking_duration
FROM performance_schema.data_lock_waits w
JOIN information_schema.INNODB_TRX b ON b.trx_id = w.blocking_engine_transaction_id
JOIN information_schema.INNODB_TRX r ON r.trx_id = w.requesting_engine_transaction_id;
```

⭐ **这是「查谁在阻塞我」的第一手段。**

⚠️ **MySQL 5.7 用 `information_schema.INNODB_LOCK_WAITS`**（⚠️ 字段和 8.0 不同）。

#### 表 3：`table_io_waits_summary_by_index_usage` ⭐

```sql
-- ⭐ 找出从未使用的索引（删索引的依据）
SELECT OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, COUNT_STAR, COUNT_READ, COUNT_WRITE
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE INDEX_NAME IS NOT NULL
  AND OBJECT_SCHEMA = 'shop'
  AND COUNT_STAR = 0
ORDER BY OBJECT_SCHEMA, OBJECT_NAME;
```

⚠️ **⚠️ ⚠️ `COUNT_STAR = 0` 只表示「从服务器启动以来没用过」**：⚠️ ⚠️ **⚠️ 如果服务器跑了很久没重启，这个结论可靠；⚠️ 如果刚重启，观察期太短，⚠️ ⚠️ 会误判很多有用的索引。**

📌 删索引的正确流程见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

### 其他有用的表

| 表 | 用途 |
|---|---|
| `events_waits_summary_global_by_event_name` | 等待事件统计（找瓶颈） |
| `events_statements_history` | 最近 N 条语句历史 |
| `setup_consumers` | 采集开关 |
| `variables_by_thread` | 各线程的变量值 |
| `memory_summary_global_by_event_name` | 内存分配 |

## 三、`sys` schema：优先用这个

### 十个最实用的视图

```sql
-- ① 最耗时的语句（人话版）
SELECT query, exec_count, total_latency, avg_latency,
       rows_sent_avg, rows_examined_avg
FROM sys.statement_analysis
ORDER BY total_latency DESC LIMIT 10;

-- ② ⭐ 全表扫描的语句
SELECT db, query, exec_count, total_latency, rows_examined_avg
FROM sys.statements_with_full_table_scans
ORDER BY total_latency DESC LIMIT 10;

-- ③ ⭐ 有排序的语句（找 filesort 问题）
SELECT query, total_latency, sort_merge_passes_avg, sort_rows_avg
FROM sys.statements_with_sorting
ORDER BY total_latency DESC LIMIT 10;

-- ④ ⭐ 临时表
SELECT query, total_latency, created_tmp_disk_tables_avg, created_tmp_tables_avg
FROM sys.statements_with_temp_tables
ORDER BY total_latency DESC LIMIT 10;

-- ⑤ ⭐ 可能冗余的索引
SELECT * FROM sys.schema_redundant_indexes\G

-- ⑥ ⭐ 从未使用的索引
SELECT * FROM sys.schema_unused_indexes WHERE object_schema = 'shop'\G

-- ⑦ 缺索引的表
SELECT * FROM sys.schema_tables_with_missing_indexes\G

-- ⑧ ⭐ 表的 Buffer Pool 占用
SELECT * FROM sys.innodb_buffer_stats_by_table\G

-- ⑨ ⭐ 锁等待
SELECT * FROM sys.schema_table_lock_waits\G

-- ⑩ 连接概览
SELECT * FROM sys.session WHERE command != 'Sleep' LIMIT 10;
```

### 视图命名规律

⭐ **看名字就知道是干什么的**：

| 前缀/后缀 | 含义 |
|-----------|------|
| `statements_with_*` | 有某种问题的语句 |
| `schema_*` | 元数据相关 |
| `innodb_*` | InnoDB 相关 |
| `user_*` | 用户相关 |
| `host_*` | 按主机分组 |
| `schema_table_*` | 表级 |

## 四、慢查询日志

### 配置

```sql
-- 运行时开启
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.5;          -- ⚠️ 生产建议 0.5~1 秒
SET GLOBAL log_queries_not_using_indexes = 'ON';   -- ⚠️ ⚠️ 日志量大
SET GLOBAL log_slow_extra = 'ON';           -- 8.0.14+，额外信息
```

```ini
[mysqld]
slow_query_log = ON
long_query_time = 0.5
slow_query_log_file = /var/log/mysql/slow.log
log_queries_not_using_indexes = OFF         # ⚠️ ⚠️ 默认 OFF，因为它太吵
min_examined_row_limit = 1000               # ⭐ 扫了少于 1000 行的不记
```

⚠️ **⚠️ `log_queries_not_using_indexes` 的问题**：⚠️ **很多「小表」查询本来就不该走索引**，⚠️ 开了之后日志爆炸。⭐ **用 `min_examined_row_limit` 过滤掉小表查询。**

### 日志内容

```sql
# Time: 2026-10-13T10:35:26.123456Z
# User@Host: app[app] @ [10.0.1.5]  Id: 12345
# Query_time: 3.502341  Lock_time: 0.000112
# Rows_sent: 20  Rows_examined: 1500000
SET timestamp=1792000000;
SELECT e.*, d.name FROM employees e LEFT JOIN departments d ON e.dept_id = d.id
WHERE e.status = 1 ORDER BY e.created_at DESC LIMIT 20;
```

| 字段 | 含义 | ⚠️ 怎么看 |
|------|------|---------|
| `Query_time` | 执行耗时 | ⚠️ **> 1 秒要关注** |
| `Lock_time` | ⭐ **锁等待时间** | ⚠️ **⚠️ 占比大说明是锁问题，不是查询慢** |
| `Rows_sent` | 返回行数 | |
| ⭐ `Rows_examined` | **扫描行数** | ⭐⭐ **和 `Rows_sent` 的比值是核心指标** |

⭐ **`Rows_examined / Rows_sent` 比值**：

| 比值 | 判断 |
|------|------|
| 1~10 | ✅ 好 |
| 10~100 | ⚠️ 有浪费 |
| ⚠️ **> 100** | ❌ **❗ 严重，优化它** |

⚠️ **`Lock_time` 占 `Query_time` 的 90%+ 时**：⚠️ 问题不是查询本身，是**锁竞争**。见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

### 用 `pt-query-digest` 分析

```bash
pt-query-digest /var/log/mysql/slow.log > report.txt

# 只看 Top 20
pt-query-digest --limit 20 /var/log/mysql/slow.log

# 看指纹聚合后的报告（⭐ 最有用）
pt-query-digest --type=fingerprint /var/log/mysql/slow.log
```

⭐ **`pt-query-digest` 的核心价值是把「参数不同的同类查询」聚合成一条**：

```
原始慢日志（1000 条）：
  SELECT * FROM orders WHERE user_id = 1
  SELECT * FROM orders WHERE user_id = 2
  SELECT * FROM orders WHERE user_id = 3
  ...

聚合后（1 条）：
  SELECT * FROM orders WHERE user_id = ?     ← 1000 次，总耗时 300 秒
```

📌 报告里要看：

| 指标 | 含义 |
|------|------|
| `Count` | 执行次数 |
| `Time` | 总耗时 |
| `Avg` | 平均耗时 |
| `95th` | P95 耗时 |
| ⭐ `Rows` | `Examined / Sent` |

### `long_query_time` 该设多少

| 建议值 | 理由 |
|--------|------|
| ⭐ **0.5 ~ 1 秒** | 生产推荐。⚠️ 太宽松会漏掉高频的慢查询 |
| 10 秒（默认） | ⚠️ 太宽松，⚠️ 只记录了最慢的，⚠️ 中间层的问题看不到 |
| 0.1 秒 | ⚠️ ⚠️ 太严格，日志量巨大，⚠️ 磁盘和 IO 压力 |

⭐ **折中做法**：⚠️ **APM 侧（应用层）捕获所有超过 100ms 的 SQL**，⚠️ 数据库侧只记录 > 1s 的。

## 五、`Handler_*` 计数器

### 是什么

⚠️ **`Handler_*` 是「存储引擎层的操作计数器」**——⭐ **它们能告诉你查询实际做了什么。**

```sql
FLUSH STATUS;              -- ⚠️ 会重置全局计数器
SELECT ...;                -- 执行你的查询
SHOW SESSION STATUS LIKE 'Handler_read%';
```

⚠️ **⚠️ 一定要用 `FLUSH STATUS`**，⚠️ 否则看到的是「服务器启动以来的累计值」，没有意义。

### 五个关键计数器

| 计数器 | 含义 | ⚠️ 诊断什么 |
|--------|------|-----------|
| ⭐ `Handler_read_rnd_next` | 顺序读次数（**全表扫描**） | ⚠️ **值大 = 全表扫描** |
| ⭐ `Handler_read_rnd` | 随机读次数 | ⭐ **≈ 回表次数** |
| ⭐ `Handler_read_key` | 按索引查找次数 | ✅ 好 |
| `Handler_read_first` | 只读第一行 | `LIMIT 1` |
| `Handler_read_prev` | 按键反向读 | 反向扫描索引 |

### 读法

| 计数器高 | 含义 |
|---------|------|
| ⚠️ `Handler_read_rnd_next` 很高 | ⭐ **全表扫描**（或全索引扫描） |
| ⚠️ `Handler_read_rnd` 很高 | ⭐ **回表次数多**（需要覆盖索引） |
| ⚠️ `Handler_read_rnd` + `Handler_read_next` 都高 | 混合——⚠️ 可能有多个不同的查询 |

⚠️ **⚠️ 注意**：`Handler_read_*` 统计的是「handler 层被调用的次数」，⚠️ **不是行数**。⚠️ 比如 `Handler_read_rnd_next` 的语义是「调用了 `rnd_next` 的次数」。

⭐ **📌 记忆锚点：`read_next` = 顺序扫 = 全表；`read_rnd` = 随机 = 回表；`read_key` = 索引查找 = 好。**

## 六、连接管理

### ⚠️ 一个连接一个线程

⚠️ **经典架构**：`max_connections` 个连接 = `max_connections` 个线程。

```sql
SHOW VARIABLES LIKE 'max_connections';        -- 默认 151
SHOW VARIABLES LIKE 'thread_cache_size';      -- 默认 0（禁用）
SHOW VARIABLES LIKE 'wait_timeout';           -- 默认 28800（8 小时）
SHOW VARIABLES LIKE 'thread_stack';           -- 默认 1M
```

### ⚠️ 为什么不能简单调大

| 问题 | 说明 |
|------|------|
| **内存** | 每个线程有栈内存（`thread_stack`，默认 1M 量级） |
| ⚠️ **上下文切换** | ⚠️ 线程数 > CPU 核数后，吞吐**下降** |
| **调度** | 1000 个线程在 8 核上切换，CPU 大部分时间在切换上下文 |

### 正确的做法

| 层 | 做法 |
|---|------|
| **数据库侧** | 配一个**合理的** `max_connections`（⚠️ 不要几千） |
| ⭐ **应用侧** | ⭐ **用连接池** |

### 8.0 的线程池

⚠️ **26.7 起，MySQL Thread Pool 进入社区版**：

```ini
thread_handling = pool-of-threads
thread_pool_max_threads = 16
thread_pool_min_threads = 4
```

⭐ **机制**：把「一连接一线程」改成「少数线程服务大量连接」。⚠️ **⚠️ 26.7 之前这个功能只在商业版**（⚠️ 这是 26.7 的一个重要变化）。

### 连接池配置

⚠️ **⚠️ `max_connections` 的一个重要考量**：⚠️ **所有连接池加起来可能超过它**。

```
应用实例 A：连接池 20
应用实例 B：连接池 20
...
共 10 个实例 → 200 个连接
    ↓
⚠️ 如果还有运维直连、监控、备份、复制...
    ↓
⚠️ 超过了 max_connections = 151 → ERROR 1040 Too many connections
```

⭐ **公式**：`max_connections >= (应用实例数 × 每实例池大小) × 1.5`（留 50% 余量给运维/监控）。

### 排查连接问题

```sql
-- ⭐ 当前连接（⚠️ 需要 PROCESS 权限看全部）
SELECT id, user, host, db, command, time, state, info
FROM information_schema.PROCESSLIST
ORDER BY time DESC;

-- 按用户/状态分组
SELECT user, command, COUNT(*) AS cnt, MAX(time) AS max_time
FROM information_schema.PROCESSLIST
GROUP BY user, command;

-- ⭐ 谁在等锁
SELECT * FROM sys.schema_table_lock_waits\G

-- 连接数超限时的处理
SHOW VARIABLES LIKE 'max_connections';
SET GLOBAL max_connections = 500;      -- ⚠️ 只影响新连接
```

⚠️ **⚠️ `SET GLOBAL max_connections` 只影响新连接**——⚠️ 已有的连接数不会减少。

⚠️ **`Too many connections` 时的应急**：

```sql
-- 找出最长的连接
SELECT id, user, host, time, state, info
FROM information_schema.PROCESSLIST
ORDER BY time DESC LIMIT 20;

-- 杀掉可疑的
KILL 12345;
```

📌 连接池的实践（SQLAlchemy / PyMySQL）见 [[sqlmodel/引擎与Session]]。

## 七、监控指标清单

⭐ **一个「够用」的 MySQL 监控应该覆盖这六类。**

### 1. 可用性

| 指标 | 来源 | 告警条件 |
|------|------|---------|
| ⭐ 服务存活 | `mysqladmin ping` / `SELECT 1` | 失败即告警 |
| 连接数 | `Threads_connected / max_connections` | ⚠️ > 80% |
| 主从状态 | `Replica_IO_Running` / `Replica_SQL_Running` | ⚠️ 不是 `Yes` |
| 主从延迟 | `pt-heartbeat` 时间差 | ⚠️ > 30 秒 |

### 2. 性能

| 指标 | 来源 | 告警条件 |
|------|------|---------|
| ⭐ QPS | `Questions` | 突变 |
| ⭐ 慢查询数 | 慢日志 / `SHOW GLOBAL STATUS` | ⚠️ 持续增长 |
| ⭐ Buffer Pool 命中率 | `SHOW ENGINE INNODB STATUS` | ⚠️ < 99% |
| ⭐ history list length | `trx_rseg_history_len` | ⚠️ > 100000 |

### 3. 事务与锁

| 指标 | 来源 | 告警条件 |
|------|------|---------|
| ⭐ 长事务数 | `INNODB_TRX`（> 30s） | ⚠️ > 0 |
| 锁等待 | `data_lock_waits` | ⚠️ > 0 |
| 死锁次数 | `Innodb_deadlocks` | 增长趋势 |

### 4. 存储

| 指标 | 来源 | 告警条件 |
|------|------|---------|
| 磁盘使用 | `information_schema.FILES` | ⚠️ > 80% |
| 表大小 | `information_schema.TABLES` | 突增 |
| ⚠️ 膨胀 | `.ibd` 大小 vs 数据量 | 明显差异 |

### 5. 复制

| 指标 | 来源 | 告警条件 |
|------|------|---------|
| ⭐ 延迟秒数 | `pt-heartbeat` | ⚠️ > 30 秒 |
| binlog 位点 | `SHOW REPLICA STATUS` | 停止推进 |
| ⚠️ GTID 差异 | `GTID_EXECUTED` 集合差 | 不收敛 |

### 6. 配置变更

| 指标 | 说明 |
|------|------|
| ⭐ 参数变更审计 | ⚠️ **`SET GLOBAL` 改了什么，谁改的** |

⚠️ **⚠️ 参数变更是「看不见的故障源」**：⚠️ 有人调了 `max_connections` 或 `innodb_flush_log_at_trx_commit`，⚠️ **性能突然变了但没人知道原因**。

```sql
-- 5.7 的审计（⚠️ 仅商业版）
SHOW GLOBAL AUDIT;

-- 8.0 用 performance_schema 的语句历史
SELECT * FROM performance_schema.events_statements_history_long
WHERE SQL_TEXT LIKE 'SET %' LIMIT 20;
```

### 一条实用的监控 SQL

```sql
-- 每分钟执行的健康检查
SELECT
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status
   WHERE VARIABLE_NAME = 'THREADS_CONNECTED') AS connections,
  (SELECT VARIABLE_VALUE FROM performance_schema.global_status
   WHERE VARIABLE_NAME = 'SLOW_QUERIES') AS slow_queries,
  (SELECT count FROM performance_schema.INNODB_METRICS
   WHERE name = 'trx_rseg_history_len') AS history_len,
  (SELECT count FROM information_schema.INNODB_TRX
   WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30) AS long_trx,
  (SELECT count FROM performance_schema.data_lock_waits) AS lock_waits,
  (SELECT ROUND(count / (SELECT @@innodb_buffer_pool_size / 16384), 4)
   FROM performance_schema.INNODB_METRICS WHERE name = 'buffer_pool_pages_free') ...
```

## 八、排查流程速查

⚠️ **「数据库很慢」的排查顺序：**

```
① 长事务？（⭐ 头号原因）
   SELECT ... FROM information_schema.INNODB_TRX
   WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 30;

        ↓ 无
② 锁等待？
   SELECT * FROM performance_schema.data_lock_waits\G

        ↓ 无
③ Buffer Pool 命中率低？
   SHOW ENGINE INNODB STATUS\G   -- 看 hit rate

        ↓ 正常
④ 磁盘 I/O 满？（iostat / iotop）
   ⚠️ 大查询、备份、批量写入

        ↓ 正常
⑤ CPU 满？
   ⚠️ 全表扫描、大 JOIN

        ↓ 正常
⑥ Top 慢查询
   FROM sys.statement_analysis ORDER BY total_latency DESC LIMIT 10
```

⭐ **⚠️ 这个顺序不能乱**——⚠️ **跳过长事务和锁，直接去看慢查询是浪费时间**（因为问题可能根本不在查询上）。

## 九、陷阱

1. **❌ 不开 `slow_query_log`。** ⚠️ 出问题时完全没有线索。
2. **❌ `long_query_time` 保持默认 10 秒。** ⚠️ 太宽松。
3. **❌ 开 `log_queries_not_using_indexes` 但不加 `min_examined_row_limit`。** ⚠️ 日志爆炸。
4. **❌ 用 `SHOW STATUS` 不 `FLUSH STATUS`。** ⚠️ 看到的是累计值，没有分析价值。
5. **❌ 用 `SHOW PROCESSLIST` 排查。** ⚠️ 它本身也要占连接，看不全。⚠️ 用 `information_schema.PROCESSLIST` 或 `sys.session`。
6. **❌ 把 `max_connections` 调到几千。** ⚠️ 线程爆炸反而更慢。用连接池。
7. **❌ 不监控 `history list length`。** ⚠️ 长事务的最灵敏指标。
8. **❌ 排查时跳过「长事务」直接看慢查询。** ⚠️ 可能白忙。
9. **❌ 不监控参数变更。** ⚠️ 「看不见的故障源」。
10. **❌ 以为 `EXPLAIN` 能告诉你真实耗时。** ⚠️ 那是估算，用 `EXPLAIN ANALYZE`。
11. **❌ 在高峰期跑 `ANALYZE TABLE`。** ⚠️ 锁表。

## 小段

- ⭐ **`sys` schema 优先于 `performance_schema`**——视图是加工过的可读版本
- **`events_statements_summary_by_digest`** 是「哪个语句最耗资源」的答案；⭐ 核心指标是 `SUM_ROWS_EXAMINED/SUM_ROWS_SENT` 比值和 `SUM_NO_INDEX_USED`
- **`data_lock_waits`** 是「查谁在阻塞我」的第一手段
- ⚠️ **`table_io_waits_summary_by_index_usage` 的 `COUNT_STAR=0` 可能是误判**（服务器刚重启时观察期太短）→ 用 INVISIBLE 索引观察
- 慢日志：⭐ **`Rows_examined / Rows_sent` > 100 = 严重浪费**；⚠️ **`Lock_time` 占大头 = 锁问题不是查询问题**
- `pt-query-digest` 把「参数不同的同类查询」聚合，是最有用的分析工具
- ⭐ **`Handler_read_*` 读法**：`read_next` = 全表扫，`read_rnd` = 回表，`read_key` = 走索引
- ⚠️ **`FLUSH STATUS` 后再查** `Handler_*`，否则看到的是累计值
- ⚠️ **`max_connections` 不要调太大**；公式：`实例数 × 池大小 × 1.5`
- **26.7 起 Thread Pool 进社区版**（⚠️ 之前只有商业版）
- **「数据库慢」的排查顺序**：⭐ 长事务 → 锁 → Buffer Pool → IO → CPU → 慢查询（⚠️ 不能跳步）
