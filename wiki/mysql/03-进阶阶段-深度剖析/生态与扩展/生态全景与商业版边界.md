## 一、插件体系

### 四个扩展点

| 扩展点 | 用途 | 示例 |
|--------|------|------|
| ⭐ **存储引擎** | 换数据存储实现 | InnoDB、MyISAM、MEMORY、⚠️ RocksDB |
| **认证插件** | 换认证方式 | `caching_sha2_password`、LDAP、Kerberos |
| **连接器/客户端插件** | 换通信方式 | MySQL X Protocol |
| **其他** | 分区、审计、优化器 hint | 各种 |

⚠️ **⚠️ 存储引擎插件是最重要的扩展点**——它让 InnoDB 能被「插进」一个原本只支持 MyISAM 的架构里（⭐ 历史原因，见 [[mysql/03-进阶阶段-深度剖析/日志与复制内核/原理剖析-redo日志与WAL]]）。

### ⚠️ 插件的限制

⚠️ **⚠️ 不是所有东西都能做成插件**：

| 能插件化 | 不能插件化 |
|---------|-----------|
| 存储引擎 | ⭐ **优化器内部**（⚠️ PG 的 `pg_hint_plan`/扩展也是有限的） |
| 认证 | SQL 解析器 |
| 分区 | 事务管理器 |
| 审计 | 内核线程调度 |

⚠️ **⚠️ 这就是为什么「换个数据库」总是有迁移成本**——⚠️ ⚠️ **两者的内核实现不一样，只能在「协议层」兼容，不能在「行为层」兼容。**

## 二、常用插件

### 官方插件

| 插件 | 版本 | 用途 |
|------|------|------|
| ⭐ **InnoDB** | 内置 | 默认引擎 |
| MyISAM | 内置 | 旧引擎 |
| MEMORY | 内置 | 内存表 |
| `mysql_native_password` | ⚠️ 8.4+ 默认禁用 | 老认证方式 |
| `group_replication` | 内置 | MGR |
| `daemon_example` | 官方示例 | ⚠️ **⚠️ 学插件开发的模板** |

⚠️ **`daemon_example` 是官方提供的「怎么写插件」的完整示例**——⚠️ 想研究插件实现先看它。

### 第三方（Percona Server）

| 功能 | 说明 |
|------|------|
| `audit_log` | 审计日志（⚠️ ⚠️ **Community 8.0.34+ 已部分内置**） |
| `group_replication` | 社区版已有 |
| Thread Pool | ⭐ **⚠️ 26.7 起进入官方 Community**（⚠️ 之前只在商业版） |
| `innodb_redo_log_capacity` | ⚠️ 官方 8.0.30+ 已内置 |
| 各种优化 | 缓冲池扩展、查询优化调整 |

⭐ **2026 年的一个重要变化**：⚠️ **⚠️ Percona 的多个功能被 Oracle 收编进 Community**（见下节）。

## 三、⭐ Community vs Enterprise 边界

### ⚠️ 先说结论：这是一个「移动的边界」

⚠️ **2026 年这个边界在往 Community 侧移动**，⚠️ **你查到的资料可能已经过时。**

### Enterprise 独有的功能（截至 2026-10）

| 功能 | 说明 | ⚠️ 能否绕过 |
|------|------|-----------|
| ⭐ **Enterprise Audit** | 审计日志（谁做了什么） | ⚠️ Community 8.0.34+ 有基础版 `audit_log` |
| **Enterprise Firewall** | 防火墙（自动识别异常 SQL） | ⛔ 不能 |
| **数据脱敏（Data Masking）** | 自动脱敏 PII | ⛔ 不能（需应用层做） |
| **额外的 Keyring 插件** | 更多密钥管理后端 | ⚠️ Community 有基础 keyring |
| **LDAP/Kerberos/WebAuthn/OIDC 认证** | 企业认证 | ⛔ 不能 |
| **Enterprise Backup** | 商业备份工具 | ⚠️ 用 `xtrabackup`（第三方，免费） |
| **MySQL Enterprise Monitor** | 监控平台 | ⚠️ 用 Prometheus + `mysqld_exporter` |
| ⭐ **`DISTANCE()` 向量函数** | 向量检索 | ⚠️ ⚠️ **⚠️ 仅 HeatWave / MySQL AI** |

### ⚠️ 已被收进 Community 的功能（2025-2026 的变化）

| 功能 | 进入 Community 的版本 | ⚠️ 意义 |
|------|-------------------|---------|
| ⭐ **Thread Pool** | **26.7.0**（2026-07） | ⚠️ 高并发场景的重要能力，现在免费了 |
| **超图优化器（Hypergraph）** | 9.7（默认关闭） | ⚠️ 多表 JOIN 的新优化器 |
| **JSON 对偶 DML** | 9.7 | |
| **Group Replication 主节点选举 / 遥测** | 9.7 | |
| **后量子 TLS（PQC）** | 26.7.0 | ⚠️ 抗量子攻击的密钥交换 |

⚠️ **⚠️ 社区对此有批评**（如 Vonng 的观点）：⭐ **「这些是长期可用的功能被'释放'了，不是新创新」**。⚠️ **⚠️ 这个批评有其道理**——⚠️ 这些功能在 Percona/其他分支里早就有了。

📌 版本详情见 [[mysql/README]] 的版本基线。

### ⚠️ 这对你的技术选型意味着什么

⚠️ **⚠️ 别因为「这是企业版功能」就自动排除它**——⚠️ **要先查它是不是已经进 Community 了。**

| 判断流程 | 做法 |
|---------|------|
| 1 | 查 [[mysql/README]] 的版本基线，确认你的目标版本 |
| 2 | 查官方文档确认功能归属（Community / Enterprise） |
| 3 | ⭐ **查开源分支**（Percona Server、MariaDB）是否有等价实现 |
| 4 | 评估「用应用层方案绕过」的代价 |

⭐ **📌 举例**：如果需要审计日志，选项有：
- Enterprise Audit（商业）
- ⭐ Community 8.0.34+ 的 `audit_log` 插件
- ⭐ **binlog + Canal/Debezium**（⚠️ 从数据变更反推审计）
- 应用层埋点

## 四、⚠️ 治理现状（了解即可）

⚠️ **2025-2026 的 MySQL 治理风波**（详见 [[mysql/README]]）：

| 日期 | 事件 |
|------|------|
| 2025-09 | Oracle 裁撤大部分 MySQL 工程团队 |
| 2026-02 | 社区峰会，约 200 人联署公开信要求基金会式治理 |
| 2026-05-27 | **OurSQL Foundation 成立**（Percona、PlanetScale、PingCAP、阿里等），⚠️ **Oracle 不是成员** |
| 2026-06-25 | Oracle 发布社区治理模型，设咨询性技术委员会（AWS、Google Cloud、Oracle） |

### ⭐ 对使用者的判断

| 方面 | 判断 |
|------|------|
| **短期风险** | ⭐ **低**。8.4 LTS 支持到 2032，9.7 LTS 到 2034 |
| **功能倒退风险** | ⭐ **低**。已发布的功能不会消失（⚠️ 商业版的可能有，但 Community 的不会） |
| **长期不确定性** | ⚠️ **存在**。⚠️ Oracle 的战略可能继续调整 |
| **应对** | ⭐ **锁定 LTS 版本**（8.4 或 9.7），⚠️ 避免用 Innovation 轨道 |

⚠️ **如果你是决策者**：⚠️ **⚠️ 可以关注开源分支**（Percona、MariaDB）作为备选，⚠️ 它们在 MySQL 生态不确定时的稳定性更好。

## 五、⭐ 国产数据库与 MySQL 兼容

### ⚠️ 「兼容 MySQL」有两层含义

| 层级 | 含义 | ⚠️ 兼容度 |
|------|------|---------|
| ⭐ **协议兼容** | 「能说 MySQL 的方言」 | ⚠️ **连接层兼容**，⚠️ 换过去可能有惊喜 |
| ⭐ **生态兼容** | ⚠️ **框架、ORM、工具都能用** | ⚠️ ⚠️ **这才是「兼容」的真正含义** |

⚠️ **⚠️ 大多数国产数据库做到的是「协议兼容 + 大部分语法兼容」，⚠️ 但 ⚠️ ⚠️ 「生态兼容」需要逐个验证。**

### ⚠️ 必须验证的兼容点

| 类别 | 具体要测的 |
|------|-----------|
| ⭐ **语法** | DDL/DML/事务/锁/函数/窗口函数/JSON |
| ⭐ **`SHOW` 命令** | ⚠️ ⚠️ **ORM 和工具重度依赖**（如 `SHOW COLUMNS` / `SHOW CREATE TABLE`） |
| ⚠️ **系统表** | ⚠️ ⚠️ **`information_schema` 的字段名和类型**——⚠️ ORM 的反射靠它 |
| ⚠️ **存储过程/触发器** | 语法差异 |
| ⚠️ **`AUTO_INCREMENT` 行为** | ⚠️ 空洞、并发行为 |
| ⚠️ **字符集/collation** | ⚠️ utf8mb4 支持度 |
| ⚠️ **索引类型** | ⚠️ FULLTEXT / SPATIAL 支持度 |
| ⚠️ **SQL 模式** | ⚠️ `sql_mode` 的实现 |
| ⚠️ **驱动** | ⚠️ PyMySQL / mysqlclient / JDBC 都能连吗 |
| ⚠️ **连接池** | ⚠️ `pool_pre_ping` 等特性 |

### 主要国产数据库

| 数据库 | 兼容情况 | 特点 | ⚠️ 注意 |
|--------|---------|------|---------|
| ⭐ **TiDB**（PingCAP） | MySQL 5.7/8.0 | 分布式（TiKV + TiFlash）、HTAP | ⚠️ ⚠️ **不兼容部分 MySQL 扩展**（如某些分区、触发器限制） |
| ⭐ **OceanBase**（蚂蚁） | MySQL 模式 | 分布式、金融级强 | ⚠️ Oracle 兼容模式 vs MySQL 模式二选一 |
| ⭐ **PolarDB**（阿里） | MySQL | 存算分离、共享存储 | ⚠️ 是「云原生改造的 MySQL」，兼容性最好 |
| **人大金仓**（Kingbase） | PG 语法 | 国产化替代 PG | ⚠️ ⚠️ **不是 MySQL 兼容** |
| **达梦**（DM） | Oracle 语法 | 金融/信创 | ⚠️ ⚠️ **不是 MySQL 兼容** |
| **GaussDB**（华为） | PG 语法 | 云原生 | ⚠️ **不是 MySQL 兼容** |
| **StarRocks / Doris** | MySQL 协议 | ⭐ **OLAP 专用** | �️ ⚠️ **不是 MySQL 替代，是数仓** |

### ⚠️ 三类国产数据库要分清

```
① MySQL 协议兼容型  → TiDB、OceanBase(MySQL模式)、PolarDB
                      ⚠️ 可以平滑替换 MySQL（⚠️ 但要测）

② PostgreSQL 兼容型  → Kingbase、GaussDB
                      ⚛� 和 MySQL 无关，要重新适配

③ 专用分析型        → StarRocks、Doris、ClickHouse
                      ⚛� 不是 OLTP 替代，是数仓/分析
```

⭐ **📌 关键判断：你的需求是「替换 MySQL 的 OLTP」，还是「新建数仓」？** ⚠️ **选错类别比选错产品严重得多。**

### 迁移前必做

```sql
-- 1. 语法兼容性检查
SELECT 'CREATE TABLE', COUNT(*) FROM information_schema.TABLES;
-- 逐个对比字段类型、默认值、字符集

-- 2. 检查不兼容的语法
-- ⭐ 用兼容性检测工具（如 Percona 的 pt-migration 思路）

-- 3. ⚠️ 实测：把应用连过去跑一遍完整业务
-- ⚠️ 包括：ORM 启动、事务、分页、批量操作、报表

-- 4. ⚠️ 性能基线对比
-- 同样数据量下对比查询延迟
```

⚠️ **⚠️ 迁移前必读对方的「兼容性说明」**——⚠️ 每家的「不兼容清单」比「兼容清单」更有价值。

## 六、云托管选项

⚠️ **如果不想自己运维 MySQL**，云托管是成熟选项：

| 云 | 选项 | 特点 |
|---|------|------|
| AWS | RDS for MySQL、Aurora MySQL | Aurora 兼容 MySQL，⚠️ **⚠️ 高可用/扩展更强，⚠️ 但部分参数受限** |
| Azure | Database for MySQL、Flexible Server | |
| Google Cloud | Cloud SQL、⭐ **⭐ AlloyDB**（PG 兼容，⚠️ 基于 PG） | |
| 阿里云 | RDS MySQL、⭐ **PolarDB** | |
| Oracle | ⭐ **HeatWave** | ⚠️ 含向量检索、ML 加速 |

⚠️ **⚠️ 云托管的常见限制**：

| 限制 | 说明 |
|------|------|
| ⚠️ 参数受限 | 有些 `innodb_*` 参数改不了 |
| ⚠️ 版本升级受控 | ⚠️ 你不能自己决定什么时候升 |
| ⚠️ 扩展能力有上限 | ⚠️ 存储/IOPS 达到上限要迁移方案 |
| ⚠️ 数据导出受限 | ⚠️ 有流量限制（⚠️ 做数据迁移时要注意） |
| ⚠️ ⚠️ **成本** | ⚠️ 长期托管成本可能超过自建 |

⚠️ **⚠️ 数据库版本支持情况要提前确认**：⚠️ **8.0 已于 2026-04-30 EOL**，⚠️ ⚠️ **各云的 MySQL 8.0 支持截止日可能比你想象的早**（⚠️ AWS 曾列出 2029-04-30，⚠️ 但 ⚠️ 不同服务不同）。

⚠️ **⚠️ MySQL 9.7 和 26.7 在 RDS 上可能只在「Preview 环境」**——⚠️ 生产用要先确认可用性。

## 七、陷阱

1. **❌ 以为「某个功能是企业版」就排除它。** ⚠️ **⚠️ 2026 年 Community 收编了很多功能**，先查最新版本归属。
2. **❌ 以为「兼容 MySQL 协议」等于「生态完全兼容」。** ⚠️ ⚠️ **`information_schema` 和 `SHOW` 命令的差异是最大的坑**。
3. **❌ 分不清国产数据库的三个类别。** ⚠️ **Kingbase 不是 MySQL 替代，是 PG 系**；⚠️ **Doris 不是 OLTP 替代，是数仓**。
4. **❌ 用 Innovation 轨道做生产。** ⚠️ 每季度必须升级，否则失去支持。
5. **❌ 以为选 LTS 就「零风险」。** ⚠️ ⚠️ **治理不确定性仍在**，⚠️ 必要时评估开源分支。
6. **❌ 迁移前不做实测。** ⚠️ ⚠️ **必须把应用完整跑一遍**，⚠️ 包括 ORM 反射、分页、批量。
7. **❌ 忽略云托管的参数限制。** ⚠️ 有些 `innodb_*` 改不了。
8. **❌ 不确认云厂商对目标版本的支持截止日。** ⚠️ 8.0 已 EOL，⚠️ 云上可能更早。

## 小结

- **插件四个扩展点**：⭐ **存储引擎**（最重要）、认证、连接器、其他。⚠️ ⚠️ **优化器内部不可插件化**
- ⭐ **Community / Enterprise 的边界在移动**——⚠️ **⚠️ Thread Pool（26.7）、超图优化器（9.7）、后量子 TLS（26.7）都已进 Community**
- ⚠️ **⚠️ 判断某个功能能不能用，要先查最新版本归属**，⚠️ 别信旧资料
- 仍在 Enterprise 的：Enterprise Firewall、Data Masking、LDAP/OIDC 认证、⭐ **`DISTANCE()` 向量函数（仅 HeatWave/MySQL AI）**
- **治理**：2026-05 OurSQL Foundation 成立（⚠️ Oracle 不是成员）。⭐ **应对：锁定 LTS 版本**
- ⚠️ **「兼容 MySQL」分两层**：⭐ **协议兼容** vs ⭐ **生态兼容**（⚠️ 真正的坑在 `information_schema` 和 `SHOW`）
- ⚠️ **国产数据库三类别**：MySQL 协议兼容型（TiDB/OceanBase/PolarDB）/ PG 兼容型（Kingbase/GaussDB）/ ⚠️ **OLAP 分析型（Doris/StarRocks）**
- ⚠️ **⚠️ 星恩数据库（StarRocks/Doris）不是 MySQL 的替代，是数仓**——⚠️ 选错类别比选错产品严重
