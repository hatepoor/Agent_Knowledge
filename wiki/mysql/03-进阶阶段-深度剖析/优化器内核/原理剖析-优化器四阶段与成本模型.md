## 一、⭐ 优化器的四个阶段

⚠️ **MySQL 优化器处理一条 SQL 的完整流程：**

```
SQL 语句
    ↓
┌──────────────────────────────────────────────┐
│ 阶段 1：解析 + 语法检查                          │
│  · 生成解析树                                   │
│  · 检查语法、语义、表是否存在                    │
│  ⛔ 失败 → ERROR 1064 / 1146                    │
└────────────────────┬─────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 阶段 2：预处理（Preprocessing）                 │
│  · 展开视图                                      │
│  · ⭐ 重写常量：WHERE 1=1 去掉                   │
│  · ⭐ 常量折叠：WHERE a + 1 = 3 → a = 2          │
│  · ⭐ 条件传播：WHERE a=1 AND a=2 → FALSE        │
│  · ⭐ 消除恒假条件 → 提前返回空集                  │
└────────────────────┬─────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 阶段 3：⭐ 逻辑改写（Logical Rewrite）          │
│  · 把 RIGHT JOIN 改成 LEFT JOIN                  │
│  · ⭐ 把子查询 JOIN 化（semi-join）              │
│  · ⭐ 谓词下推（predicate pushdown）             │
│  · 视图合并                                     │
│  · 等价变换（IN → semi-join）                    │
└────────────────────┬─────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 阶段 4：⭐ 物理优化 + 成本估算                   │
│  · 生成所有候选「访问路径」（全表扫/索引扫/…）    │
│  · ⭐ 用成本模型给每个路径打分                     │
│  · 选最便宜的                                   │
│  · ⭐ 决定 JOIN 的顺序（嵌套循环/哈希/归并）       │
└────────────────────┬─────────────────────────┘
                     ↓
               执行计划（EXPLAIN 看到的）
```

⭐ **📌 记忆锚点：解析 → 预处理 → 逻辑改写 → 物理优化。⚠️ 「优化」发生在后两个阶段。**

⚠️ **`EXPLAIN` 的输出是阶段 4 的结果**——⚠️ **看不到前三个阶段做了什么**，⚠️ 这就是为什么「我的子查询明明没走索引」的答案藏在 `optimizer_trace` 里。

## 二、阶段 2：预处理

### ⚠️ 三个重要变换

| 变换 | 输入 | 输出 |
|------|------|------|
| ⭐ **常量折叠** | `WHERE a + 1 = 3` | `WHERE a = 2` |
| ⭐ **条件传播** | `WHERE a = 1 AND a > 0` | `WHERE a = 1` |
| ⭐ **恒假消除** | `WHERE a = 1 AND a = 2` | ⚠️ **直接返回空集**（`Impossible WHERE`） |

```sql
-- ⚠️ 优化器在预处理时就算出这是空集了
EXPLAIN SELECT * FROM t WHERE 1=1 AND 2=2;
-- Extra: Impossible WHERE noticed after reading const tables
-- rows: 0
```

### ⭐ 恒假消除的优化价值

```sql
-- 如果 a 没有索引，且表有 1000 万行
SELECT * FROM t WHERE created_at = '2026-01-01' AND created_at = '2026-01-02';
-- ⭐ 预处理阶段就发现「同一天不可能同时是 1 号和 2 号」→ 直接返回空，⭕ 不扫表！
```

⚠️ **⚠️ 这是 MySQL 的一个「免费优化」**：⚠️ **⚠️ 但 PG 也会做这个**，所以迁移时不用担心。

📌 对照：[[postgresql/02-中段阶段-专题精讲/CTE与递归查询/递归查询与树形结构|CTE 与递归查询]]。

## 三、阶段 3：逻辑改写

### 改写 1：JOIN 方向统一

```sql
-- 优化器内部
SELECT * FROM a RIGHT JOIN b ON a.id = b.a_id;
-- ⭐ 被改写为（⭐ 表顺序调换）
SELECT * FROM b LEFT JOIN a ON a.id = b.a_id;
```

⚠️ **这是 `EXPLAIN` 里 `LEFT JOIN` 出现的原因之一**——⚠️ **即使你写的是 `RIGHT JOIN`，`EXPLAIN` 也可能显示 `LEFT JOIN`。**

### 改写 2：⭐⭐ 子查询 JOIN 化（semi-join）

⚠️ **这是 MySQL 5.6+ 的重要能力。**

```sql
-- 原始：IN 子查询
SELECT * FROM t1 WHERE id IN (SELECT id FROM t2);
```

⚠️ **朴素的执行方式**：⭐ **对 t1 的每一行，去跑一次 t2 的查询**（⚠️ 慢）。

⭐ **优化器改写为「半连接（semi-join）」**：

```sql
SELECT * FROM t1 WHERE EXISTS (SELECT 1 FROM t2 WHERE t2.id = t1.id);
-- ⭐ 变成一次 JOIN
```

⚠️ **四种 semi-join 策略**：

| 策略 | 说明 |
|------|------|
| `FirstMatch` | 一行行匹配，找到就停 |
| `LooseScan` | ⭐ 优化器**只扫一次 t2 的索引**，把结果缓存起来 |
| `Materialization` | 把子查询结果做成临时表 |
| `DuplicateWeedout` | 去重中间结果 |

⭐ **`optimizer_trace` 里能看到选了哪个策略**——⚠️ **⚠️ 但 8.0 里有「子查询转 JOIN」的开关**：

```sql
SET optimizer_switch = 'subquery_to_derived=on';
SET optimizer_switch = 'subquery_materialization=on';
```

⚠️ **⚠️ 「8.0 里优化器有子查询转 JOIN 能力，所以相关子查询不一定慢」是准确说法**——⚠️ ⚠️ **但仍要看实际执行计划**，别假设。

⚠️ **对照 PG**：⭐ **PG 的优化器更激进——会把相关子查询「拉平成 JOIN」**（pull-up），⚠️ 所以 PG 里「相关子查询一定慢」是彻底的误解。

### 改写 3：⭐ 谓词下推（predicate pushdown）

⚠️ **这是最容易被忽视的、但价值很大的改写。**

```sql
-- 原始：先 JOIN 再过滤
SELECT * FROM t1 JOIN t2 ON t1.id = t2.a_id
WHERE t2.status = 1;
```

⚠️ **⚠️ 朴素执行：**

```
① t1 全表扫描
② t2 全表扫描
③ JOIN（可能产生几亿行！）
④ 过滤 t2.status = 1
```

⭐ **谓词下推后**：

```
① t2 过滤 status=1（可能只剩 100 行）
② t1 扫描（如果只需要匹配这 100 个 id，可能走索引）
③ JOIN（只有 100 行参与）
```

⚠️ **⚠️ 这个改写在「外表行数 ≫ 内表过滤后行数」时收益巨大。**

⚠️ **⚠️ 但注意：⚠️ `LEFT JOIN` 的条件下推要小心**——⚠️ **「保留左表所有行」的语义不能被破坏**（见 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.4-JOIN连接查询]]）。

⚠️ **⚠️ 「条件下推」有两个不同的概念，容易混**：

| 概念 | 说明 |
|------|------|
| ⭐ **谓词下推（改写阶段）** | ⭐ 把 WHERE 条件推到 JOIN 之前，改变执行方式 |
| ⭐ **索引下推 ICP（执行阶段）** | ⭐ 把 WHERE 条件推到存储引擎层，减少回表 |

⚠️ **⚠️ 「推」到了不同的地方，但目标类似（都减少数据处理量）。**

## 四、⭐ 阶段 4：成本模型

### 成本 = IO 代价 + CPU 代价

```c
// ⚠️ MySQL 的成本公式（简化）
cost = io_cost + cpu_cost;

// IO 代价：按页读的次数
io_cost = page_reads * IO_PAGE_READ_COST;
// IO_PAGE_READ_COST 默认 1.0（8.0）

// CPU 代价：按比较次数
cpu_cost = (tuple_evaluations + other_operations) * CPU_TUPLE_COST;
```

### ⚠️ 关键：为什么「全表扫描有时更好」

```sql
-- 小表（500 行）无索引
SELECT * FROM small_t WHERE no_index_col = 1;
```

⚠️ **优化器的计算**：

```
全表扫描：
  读 500 行 = 5 个页（每页 100 行）
  io_cost = 5 × 1.0 = 5.0
  cpu_cost = 500 × 0.1 = 50
  总成本 ≈ 55

走索引（如果建了）：
  读 3~4 页（根+页+叶）
  io_cost = 4 × 1.0 = 4.0
  cpu_cost = 1 × 0.1 = 0.1
  总成本 ≈ 4.1
  ⚠️ 索引更便宜，优化器选索引
```

⚠️ **⚠️ 但如果条件是「匹配 90% 的行」**：

```
全表扫描：io 5 + cpu 50 = 55
索引扫描：读 4 页 + ⚠️ 回表 450 次 × 0.1 = 4 + 45 = 49
  ⚠️ 还是接近，且实际回表的随机 IO 比估算贵
  ⭐ 优化器可能判断全表扫更优 → ⛔ 放弃索引
```

⚠️ **⭐ 这解释了「为什么索引明明存在，优化器却不用」的第一个原因：低选择性的条件 + 回表代价。**

⚠️ **⚠️ `EXPLAIN` 里的 `rows` 和 `filtered` 就是成本模型的输入**——⚠️ **`filtered: 90%` 就是在说「这个条件过滤性差」。**

### ⚠️ 成本模型的硬编码常量

| 常量 | 默认 | 含义 |
|------|------|------|
| `io_block_read_cost` | 1.0（8.0） | ⭐ **读一个页的代价** |
| `memory_block_read_cost` | 0.1（8.0，⚠️ 老版本是 1.0） | ⭐ **⚠️ 8.0 把「内存页读」的代价降到 0.1** |
| `cpu_tuple_cost` | 0.1 | 比较一行数据的代价 |
| `disk_temptable_create_cost` | 20 | 建磁盘临时表 |
| `memory_temptable_create_cost` | 1 | 建内存临时表 |

⚠️ **⭐ 8.0 的一个重要变化**：`memory_block_read_cost` 从 1.0 降到 0.1。⚠️ **⭐ 这意味着 8.0 会更倾向于「多读几页但少做计算」的方案**，⚠️ 比如更倾向用覆盖索引（多读页但不回表）。

⚠️ **⚠️ SSD 上这些默认值可能不合适**——⚠️ 因为它假设「随机 IO 比顺序 IO 贵很多」，⚠️ SSD 上这个假设不成立。⚠️ 但 ⚠️ **MySQL 8.0.28+ 有 `innodb_read_io_threads` 等参数，⚠️ 但没有直接调「随机 IO 代价」的参数**（⚠️ PG 有 `random_page_cost`，⚠️ 这是 PG 的优势）。

## 五、⭐ 基数估算

### ⚠️ 为什么不准

⭐ **优化器靠「统计信息」估算「这个条件能匹配多少行」，⚠️ 但这个估算经常偏。**

**InnoDB 的统计信息来源**：

| 来源 | 说明 | ⚠️ 问题 |
|------|------|--------|
| **采样** | ⭐ 从索引随机抽约 20% 的页算基数 | ⚠️ **⚠️ 采样有随机性，数据倾斜时会偏** |
| `ANALYZE TABLE` | 重新采样 | ⚠️ **⚠️ 重建所有统计信息，⚠️ 大表上耗时长** |

```sql
-- 看当前的统计信息
SELECT * FROM mysql.innodb_table_stats WHERE table_name = 'orders'\G
-- 看 n_rows（估算行数）

SELECT * FROM mysql.innodb_index_stats
WHERE table_name = 'orders' AND stat_name = 'n_diff_pfx01'\G
-- 看索引前缀的去重值估算
```

### ⚠️ 倾斜导致的问题

```
orders 表：
  user_id=1    → 5,000,000 行（一个大客户）
  user_id=2~99 → 各 10 行

优化器估算（采样）：
  user_id=1    → 估 50 万
  user_id=2~99 → 估 50 万
  ⛔ 全都估高了！
```

⚠️ **后果**：

```
SELECT * FROM orders WHERE user_id = 2;
  ↓
优化器估 50 万行
  ↓
认为走索引要回表 50 万次（随机 IO 很贵）
  ↓
认为全表扫描更便宜
  ↓
⛔ 放弃索引，全表扫 1000 万行
  ↓
⚠️ 但实际只有 10 行！走索引只要几毫秒
```

### ⭐ 直方图（8.0+）

⚠️ **直方图让优化器知道「真实分布」。**

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON user_id WITH 64 BUCKETS;

-- 效果：
--   ⭐ 优化器知道 user_id=1 占 50%，user_id=2~99 各占 0.001%
--   ⭐ 对 user_id=2 的查询，选索引；对 user_id=1 的查询，可能全表扫（正确决策）
```

⚠️ **⭐ 直方图 vs `ANALYZE TABLE`**：

| | `ANALYZE TABLE` | 直方图 |
|---|-----------------|--------|
| 作用 | ⭐ 更新**所有**索引的基数 | ⭐ 补充**特定列**的分布 |
| ⭐ **重建已有直方图** | ⚠️ **是** | ⭐ **只建这一个** |
| 耗时 | ⚠️ 大表上几十分钟 | ⭐ 快 |

⚠️ **⚠️ `ANALYZE TABLE` 会重建所有直方图**——⚠️ 所以如果你精心建了直方图，⚠️ 跑一次 `ANALYZE TABLE` 会把它们「全部重建为默认状态」。⚠️ ⚠️ **所以要小心顺序。**

⚠️ **直方图的限制**：

| 限制 | 说明 |
|------|------|
| ⚠️ 每列最多一个 | 重建会替换旧的 |
| ⚠️ 只对单列有效 | ⚠️ **⚠️ 多列联合分布无法表示**（这是 PG 的 n_distinct 能做而 MySQL 不能的） |
| 桶数上限 1024 | 建议是「不同值数量」的 1/10 |

## 六、⭐ 索引下推（ICP）的实现位置

⚠️ **ICP 发生在「阶段 4 之后、执行时」——它不是一个优化阶段，而是执行期的优化。**

```
逻辑执行（Server 层）：
  读索引 → 拿到主键 → 回表 → 判断 WHERE → 返回

加了 ICP（存储引擎层）：
  读索引 → ⚡ 在引擎层判断 WHERE → 不满足的不回表 → 满足的回表
```

⚠️ **为什么 ICP 只对二级索引有效**：

| | ICP 能用吗 | 为什么 |
|---|----------|-------|
| ⭐ **二级索引** | ✅ | ⭐ 索引里有「其他列」可以判断 WHERE，返回数据才需要回表 |
| **聚簇索引** | ❌ | ⚠️ **聚簇索引已经是整行了**，⚠️ 拿到行就等于拿到了全部数据，⚠️ **没有「回表」这个动作，也就无从「提前过滤」** |

⚠️ **⚠️ ICP 的限制**：

| 限制 | 说明 |
|------|------|
| ⚠️ 不支持 JOIN | ⚠️ MySQL 的 ICP 对 JOIN 场景支持有限 |
| ⚠️ `OR` 条件处理受限 | |
| ⚠️ 函数包裹的列不行 | ⭐ 索引里存的是原值，无法预先计算函数结果 |

📌 详见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

## 七、⭐ 优化器的「启发式」

⚠️ **⚠️ 有些情况下优化器会「不做优化」或「做启发式判断」——⚠️ 这时 `optimizer_trace` 里会显示 `chosen: true` 但 `reasoning: "chosen by heuristics"`。**

### 场景 1：`OR` 条件的处理

```sql
SELECT * FROM t WHERE a = 1 OR b = 2;
```

⚠️ **⚠️ MySQL 早期版本对 `OR` 的处理很弱**——⚠️ 如果 `b` 没索引，⚠️ **整个查询退化成全表扫描**（因为无法「用两个索引合并」）。

⚠️ **⚠️ 索引合并（Index Merge）是「启发式」的，⚠️ 优化器不总是用它。** 可靠的做法是改写：

```sql
-- ✅ 改写成 UNION（优化器会分别用索引）
SELECT * FROM t WHERE a = 1
UNION
SELECT * FROM t WHERE b = 2;
-- ⚠️ 注意：UNION 会去重，要加 ALL 避免
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2;
```

⚠️ **⚠️ `EXPLAIN` 里看到 `Using union` 就是这个改写的结果。**

⚠️ **⚠️ `OR` 的解法优先级**：

| 优先级 | 方案 |
|-------|------|
| ⭐ 1 | **给所有 `OR` 的列都建索引**，让优化器能用 Index Merge |
| ⭐ 2 | **改写成 `UNION ALL`**（⚠️ 但语义上要确认「本来不会有重复」） |
| 3 | 强制索引（⚠️ 最后手段） |

### 场景 2：`ORDER BY` 与 `WHERE` 冲突

```sql
-- WHERE 用 idx_a，ORDER BY 用 idx_b
SELECT * FROM t WHERE a = 1 ORDER BY b;
```

⚠️ **优化器只能用一个索引**，⚠️ 要么用 `idx_a` 过滤但排序额外做（filesort），⚠️ 要么用 `idx_b` 排序但过滤不全扫描。⚠️ **它会算成本选一个。**

⭐ **解法**：⭐ **建联合索引 `(a, b)`**——⚠️ 这就是「复合索引：等值列在前，排序列在后」的设计依据。

### 场景 3：`MAX()` / `MIN()` 优化

```sql
SELECT MAX(id) FROM t;
-- Extra: Select tables optimized away
-- ⚠️ 优化器「发现」你只需要索引的最后一个值，⭕ 直接从根节点往下走，不扫数据
```

⚠️ **⚠️ 只在「WHERE 条件能用上索引」时生效**：

```sql
-- ✅ 能优化
SELECT MAX(id) FROM t WHERE a = 1;

-- ⛔ 不能优化（要扫所有匹配行才能比较）
SELECT MAX(v) FROM t WHERE a = 1;    -- v 没索引
```

## 八、⭐⭐ 实验清单

### 实验 1：⭐ 观察优化器的四个阶段

```sql
SET optimizer_trace = 'enabled=on';
SET optimizer_trace_max_mem_size = 1048576;

SELECT * FROM employees WHERE status = 1 AND dept_id = 3;

SELECT TRACE FROM information_schema.OPTIMIZER_TRACE\G
SET optimizer_trace = 'enabled=off';
```

⚠️ **⚠️ 看 trace 的三个部分**：

| 部分 | 看什么 |
|------|--------|
| ⭐ `considered_execution_plans` | 所有候选计划及其成本 |
| ⭐ `best_access_path` | ⭐ 谁赢了，理由是什么 |
| `candidates_rejected` | 哪些被否决了 |
| `grouping_operation` | JOIN 的分组和顺序 |

⭐ **⚠️ 重点找 `"chosen by heuristics"`**——⭐ **这说明优化器没做充分比较就「拍板」了**。

### 实验 2：验证谓词下推

```sql
-- 建两张表
CREATE TABLE small (id INT PRIMARY KEY, v INT);
CREATE TABLE big (id INT PRIMARY KEY, v INT);
-- big 插 100 万行，small 插 10 行

-- ⭐ 加上「小表过滤条件」
EXPLAIN FORMAT=TREE
SELECT * FROM big JOIN small ON big.id = small.id WHERE small.v = 1;
-- ⚠️ 对比：EXPLAIN FORMAT=TREE
SELECT * FROM big JOIN small ON big.id = small.id;
```

⭐ **观察第一版是不是更快。**

### 实验 3：验证基数估算不准

```sql
CREATE TABLE skew (user_id INT, v INT, KEY idx_user (user_id));
-- 插 100 万行 user_id=1，插 1000 行其他 user_id

EXPLAIN SELECT * FROM skew WHERE user_id = 999;
-- rows 估算值 ⚠️ 会偏高

-- 修复
ANALYZE TABLE skew UPDATE HISTOGRAM ON user_id WITH 16 BUCKETS;
ANALYZE TABLE skew;
EXPLAIN SELECT * FROM skew WHERE user_id = 999;
-- rows 估算值 ⭐ 变准了，且选了索引
```

### 实验 4：验证 OR 的处理

```sql
CREATE TABLE or_test (a INT, b INT, KEY idx_a (a), KEY idx_b (b));
-- a 有索引，b 没索引

EXPLAIN SELECT * FROM or_test WHERE a = 1 OR b = 2;
-- ⚠️ type=ALL（⛔ 放弃索引了）

-- 改写
EXPLAIN SELECT * FROM or_test WHERE a = 1
UNION ALL SELECT * FROM or_test WHERE b = 2;
-- ✅ 两个都能走索引（Using union）
```

⭐ **⚠️ 但注意：给 b 也建索引后，第一个查询可能也会用 Index Merge。** ⭐ **实验 2 和 4 的顺序很重要。**

## 九、陷阱

1. **❌ 以为 `EXPLAIN` 能看到优化器的全部行为。** ⚠️ **它只显示阶段 4 的结果**，⚠️ 要看全过程用 `optimizer_trace`。
2. **❌ 以为 `LEFT JOIN` 出现在 `EXPLAIN` 里就说明你写错了。** ⚠️ 优化器会把 `RIGHT JOIN` 改写成 `LEFT JOIN`。
3. **❌ 盲目 `ANALYZE TABLE`。** ⚠️ ⚠️ **它会重建所有直方图**——⚠️ 会覆盖你精心建的。
4. **❌ 以为数据倾斜只能靠直方图。** ⚠️ 直方图只对单列有效；⚠️ **⚠️ 多列倾斜只能靠「拆表/分片」**。
5. **❌ 依赖 `OR` 的 Index Merge。** ⚠️ ⚠️ **它是启发式的，优化器不保证用。** ⚠️ 可靠做法是改写或加索引。
6. **❌ 在 SSD 上还用默认成本参数。** ⚠️ ⚠️ **MySQL 没有「随机 IO 代价」参数**（⚠️ PG 有 `random_page_cost`），⚠️ 这是 MySQL 的短板。
7. **❌ 混淆「谓词下推」和「索引下推 ICP」。** ⚠️ **前者是优化阶段，后者是执行阶段。**
8. **❌ 以为「相关子查询一定慢」。** ⚠️ 8.0 有子查询转 JOIN 能力，要看实际计划。

## 小段

- ⭐ **优化器四阶段**：⭐ **解析 → 预处理（常量折叠/恒假消除）→ 逻辑改写（JOIN 化/谓词下推）→ 物理优化（成本模型选路径）**
- ⭐ **`EXPLAIN` 只显示阶段 4**，⚠️ **全过程要看 `optimizer_trace`**
- 阶段 2 的「恒假消除」是免费优化：⚠️ `WHERE a=1 AND a=2` 直接返回空，⛔ 不扫表
- ⭐ **逻辑改写的两个关键**：⭐ **子查询 JOIN 化（semi-join）** 和 ⭐ **谓词下推**
- ⚠️ **⚠️ 「谓词下推」（改写阶段）和「索引下推 ICP」（执行阶段）是两个不同的东西**
- **成本模型** = `io_cost + cpu_cost`；⚠️ **小表全表扫比走索引更便宜是正常决策**
- ⚠️ **8.0 把 `memory_block_read_cost` 从 1.0 降到 0.1**——⚠️ 更倾向覆盖索引
- ⚠️ **⚠️ MySQL 没有 `random_page_cost` 参数**（⚠️ PG 有）——⚠️ SSD 上无法调
- ⭐ **基数估算不准的原因**：InnoDB 靠采样；⚠️ **倾斜数据会严重偏**
- ⭐ **直方图（8.0+）** 补充单列分布；⚠️ **⚠️ `ANALYZE TABLE` 会重建所有直方图**
- ⚠️ **启发式行为**：`OR` 的 Index Merge 是启发式的，⚠️ 不保证；`chosen by heuristics` 是信号
- ⭐ **`OR` 的可靠解法**：给所有列建索引，或改写 `UNION ALL`
