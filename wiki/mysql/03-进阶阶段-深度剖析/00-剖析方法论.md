## 一、模块与依赖图

```
              ┌─────────────────────────┐
              │  ① 架构与存储内核         │
              │  连接层 → 服务层 → 引擎   │
              │  进程模型 / 页 / 表空间   │
              │  Buffer Pool / doublewrite│
              └───────────┬─────────────┘
                          │ 数据怎么存
              ┌───────────▼─────────────┐
              │  ② 事务与锁内核           │
              │  undo log / MVCC          │
              │  ReadView / 可见性        │
              │  锁体系 / 死锁            │
              └───────────┬─────────────┘
                          │ 并发怎么控制
        ┌─────────────────┼─────────────────┐
        │                 │                 │
┌───────▼────────┐ ┌─────▼──────┐ ┌────────▼────────┐
│ ③ 优化器内核    │ │ ④ 日志与   │ │ ⑤ 生态与扩展    │
│  成本模型       │ │   复制内核  │ │  插件 / 生态    │
│  统计信息       │ │  redo/WAL  │ │  国产数据库     │
│  索引下推       │ │  binlog    │ │  商业版边界     │
│  直方图        │ │  GTID      │ │                │
└────────────────┘ └────────────┘ └─────────────────┘
```

⭐ **推荐阅读顺序**：**① → ② → ④ → ③ → ⑤**

**为什么这个顺序**：

| 顺序 | 理由 |
|------|------|
| ① 先 | 「数据存在哪、怎么读」是最基础的 |
| ② 再 | 「怎么保证一致性」——依赖存储的基础 |
| ④ 第三 | ⚠️ redo/binlog 是「崩溃恢复」和「复制」的基础，⚠️ 而这两件事都依赖「怎么存」和「怎么锁」 |
| ③ 第四 | 优化器需要前三块都理解（它要知道代价怎么算） |
| ⑤ 最后 | 生态是「外围」，且有些内容依赖核心机制 |

## 三、读源码的正确方式

⚠️ **不要从 `main()` 开始读。** 那会看到几十万行的初始化代码然后放弃。

### 三种切入方式

| 方式 | 适用 | 方法 |
|------|------|------|
| **① 从一个具体问题开始** ⭐ | 理解机制 | 「RR 下的 MVCC 是怎么实现的」→ 找 `read_view` 相关代码 |
| **② 从一条 SQL 开始** | 理解全链路 | 「SELECT 的一生」→ 跟着一层层的 handler |
| **③ 从数据结构开始** | 理解存储 | 打开 `innodb_bufer.h` 看 `buf_block_t` |

⭐ **推荐 ①**：**带着问题读**。每个模块下面都列了「你应该能回答什么问题」。

### 必读的文件

| 模块 | 文件 | 内容 |
|------|------|------|
| 存储 | `storage/innobase/include/btr0cur.h` | B+ 树游标（页内查找） |
| 存储 | `storage/innobase/include/page0cur.h` | 页操作 |
| 存储 | `storage/innobase/include/buf0buf.h` | Buffer Pool |
| 事务 | `storage/innobase/include/trx0trx.h` | 事务结构 |
| 事务 | `storage/innobase/include/row0mysql.h` | 行版本 |
| 锁 | `storage/innobase/include/lock0lck.h` | 锁结构 |
| 优化器 | `sql/sql_optimizer.cc` | ⚠️ **优化器主逻辑**（很大） |
| 优化器 | `sql/opt_costmodel.cc` | 成本模型 |
| 日志 | `storage/innobase/include/log0log.h` | redo log |
| 日志 | `sql/binlog.cc` | binlog |

### 读源码的三条纪律

| 纪律 | 说明 |
|------|------|
| ⭐ **不要通读** | ⭐ **带着问题，只跟必要的调用链** |
| ⭐ **配实验验证** | ⚠️ **光看代码不如跑个实验**——每篇下面都有实验清单 |
| ⚠️ **版本会变** | MySQL 8.0 的代码结构和 5.7/5.6 差别很大；⚠️ 参考时注意版本 |

## 五、实验驱动

⭐ **⭐⭐ 这是本阶段最重要的一条：每个机制都要跑实验验证，不能只读文档。**

### 实验设计的三原则

| 原则 | 说明 |
|------|------|
| ⭐ **最小复现** | ⚠️ **不要在有生产数据的库上实验**。建一个干净的测试库 |
| ⭐ **单变量** | ⭐ **一次只改一个东西**，才能确定因果 |
| ⭐ **可重复** | ⚠️ 实验脚本要能反复跑（⚠️ 每次重置数据） |

### 观测工具

| 工具 | 用途 |
|------|------|
| `performance_schema` | ⭐ 观测锁、事务、语句 |
| `SHOW ENGINE INNODB STATUS` | ⭐ InnoDB 内部状态（锁、history list、checkpoint） |
| `SHOW ENGINE INNODB MUTEX` | 互斥量竞争 |
| `information_schema.INNODB_TRX` | 事务列表 |
| ⭐ `performance_schema.data_lock_waits` | ⭐ 锁等待（8.0） |
| `optimizer_trace` | ⭐ 优化器决策过程 |
| `EXPLAIN ANALYZE` | ⭐ 真实耗时（8.0.18+） |
| `pt-heartbeat` | 主从延迟 |

### 各模块的关键实验

**② 事务与锁内核**：

```sql
-- 实验 1：观察 undo 版本链
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 另一个连接看：
SELECT * FROM accounts WHERE id = 1;        -- 看到 100（快照读）
SHOW ENGINE INNODB STATUS\G                   -- 看 TRX 和 undo 状态
COMMIT;

-- 实验 2：间隙锁
BEGIN;
SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- 另一个连接：
INSERT INTO t (id) VALUES (15);              -- ⛔ 被间隙锁阻塞
```

**④ 日志与复制内核**：

```sql
-- 实验 1：观察 checkpoint
SHOW ENGINE INNODB STATUS\G                   -- LOG 段落
-- 观察 checkpoint LSN 和 buffer pool 修改页数的关系

-- 实验 2：观察刷盘策略的影响
SET GLOBAL innodb_flush_log_at_trx_commit = 0;
-- ⚠️ 对比提交延迟；⚠️ 然后测试崩溃丢数据（⚠️ 只在测试环境！）
```

⚠️ **⚠️ ⚠️ 任何会损坏数据的实验只在隔离的测试环境做**，⚠️ 且 ⚠️ **用 Docker 起一个临时实例，不要用重要数据。**

## 六、MySQL vs PostgreSQL：实现分歧

⚠️ **这一节是本阶段最值得反复看的**——⭐ **理解了两者的实现差异，就理解了为什么它们的语法/行为也不同。**

### 根本分歧：MVCC 实现

| 维度 | PostgreSQL | MySQL InnoDB |
|------|------------|--------------|
| 原理 | ⭐ **追加式** | ⭐ **undo 式** |
| 新版本 | 新行写在**表末尾** | 老版本信息写在 **undo log** |
| 回收 | ⭐ **`VACUUM`**（手动/自动） | ⭐ **purge 线程**（后台） |
| 空间回收 | 表不缩小，只是空间可复用 | 同 |
| 长期现象 | ⚠️ **表膨胀** | ⚠️ **undo 膨胀** |

```sql
-- PostgreSQL
UPDATE t SET v = 2 WHERE id = 1;
-- 表文件：[id=1,v=1][id=1,v=2]   ← 新行在末尾
-- VACUUM 回收

-- MySQL
UPDATE t SET v = 2 WHERE id = 1;
-- 表文件：[id=1,v=2]
-- undo:   [v=2 → v=1]           ← 老版本在 undo
-- purge 线程清理
```

📌 详见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]] 和 [[postgresql/03-进阶阶段-深度剖析/事务与MVCC内核/原理剖析-MVCC与快照隔离]]。

### 其他实现分歧

| 维度 | PostgreSQL | MySQL |
|------|-----------|-------|
| 锁粒度 | 关系级 + 行级（无间隙锁） | ⭐ **行级 + 间隙锁 + Next-Key** |
| 幻读防护 | RR 不防幻读（⚠️ 标准语义） | ⭐ **RR + 间隙锁** |
| WAL 实现 | 自己实现（XLog） | 自己实现（InnoDB redo） |
| 日志 → 复制 | ⭐ **WAL 直接喂给流复制** | ⚠️ **binlog 是独立的**（⚠️ 要把 redo 转成 binlog） |
| 外键索引 | ⭐ **自动建** | ⚠️ **不自动建** |
| 索引组织 | 堆表 + 索引（⚠️ 不聚簇） | ⭐ **聚簇索引**（数据按主键存） |
| JOIN 算法 | Hash Join / Merge Join / Nested Loop | Nested Loop / BKA（⚠️ 8.0.18+ 有 Hash Join） |

⚠️ **⚠️ 「为什么 MySQL 的 binlog 要单独一份而不是复用 redo？」** ⭐ **这是面试高频题。** 答案在 [[mysql/03-进阶阶段-深度剖析/日志与复制内核/原理剖析-redo日志与WAL]]：⭐ **redo 是物理日志（InnoDB 私有），binlog 是逻辑日志（Server 层，需要跨引擎兼容和可读性）**。

## 八、实验环境建议

⚠️ **强烈建议用 Docker 起一个隔离环境：**

```bash
docker run -d --name mysql-lab \
  -e MYSQL_ROOT_PASSWORD=Root@123456 \
  -p 127.0.0.1:3307:3306 \
  -v mysql_lab:/var/lib/mysql \
  -e TZ=Asia/Shanghai \
  mysql:9.7
```

⚠️ **关键点**：

| 项 | 说明 |
|---|------|
| ⭐ **端口用 3307** | ⚠️ 避开你本机可能有的 3306 |
| ⭐ **限定 127.0.0.1** | ⚠️ 别暴露到网络 |
| ⭐ **独立数据卷** | ⚠️ 随时 `docker rm -v` 重置 |

⚠️ **⚠️ ⚠️ 破坏性实验（改参数、模拟崩溃）只在容器里做**，⚠️ ⚠️ **绝对不要在有重要数据的库上试。**

⚠️ **⚠️ 想测崩溃恢复**：⚠️ **`docker kill --signal=KILL mysql-lab`**（⚠️ 模拟进程被杀），⚠️ 然后重启观察 InnoDB 的恢复过程（⚠️ 会比较慢，⚠️ 因为要应用 redo）。

## 九、陷阱

1. **❌ 从源码第一行开始读。** ⚠️ 一定会放弃。带问题读。
2. **❌ 只看文档不做实验。** ⚠️ 「看了就懂」是幻觉。
3. **❌ 在生产库上做实验。** ⚠️ ⚠️ 用 Docker 隔离环境。
4. **❌ 用 5.7 的资料理解 8.0 的行为。** ⚠️ 代码结构和行为都有大变化。
5. **❌ 忽略版本差异。** ⚠️ 8.0、8.4、9.7 之间也有差异（见 [[mysql/README]]）。
6. **❌ 学了不用。** ⚠️ 进阶知识在「遇到别人搞不定的性能问题时」才发挥价值。

## 小结

- **阅读顺序**：① 架构存储 → ② 事务锁 → ④ 日志复制 → ③ 优化器 → ⑤ 生态
- ⭐ **⭐⭐ 核心方法：带着问题读 + 配实验验证**——**只读不实验等于没学**
- ⚠️ **不要通读源码**，只看必要的调用链
- **观测工具**：`performance_schema` + `SHOW ENGINE INNODB STATUS` + `optimizer_trace` + `EXPLAIN ANALYZE`
- ⚠️ **破坏性实验只在 Docker 隔离环境做**，端口用 3307 避开本机实例
- ⭐ **MySQL vs PG 的根本分歧**：追加式 vs undo 式 MVCC；**聚簇 vs 堆表**；**间隙锁**；**binlog 独立于 redo**
- ⭐ **面试最常被问的两块**：事务与锁内核、日志与复制内核
- ⚠️ **⚠️ 高频面试题：「为什么 binlog 要独立于 redo」**
