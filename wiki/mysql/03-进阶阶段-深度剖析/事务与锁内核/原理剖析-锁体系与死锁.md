## 一、四种锁的层次

⚠️ **MySQL 的锁分成两大类：**

| 大类 | 锁 |
|------|-----|
| **按对象分** | 表级锁、行级锁 |
| ⭐ **按粒度细分（行锁）** | 记录锁（Record Lock）、**间隙锁（Gap Lock）**、**Next-Key Lock** |

### ⭐ Next-Key Lock 的设计（必须先懂这个）

⚠️ **这是理解所有行锁的关键。**

**B+ 树的索引是有序的**，所以 InnoDB 把「记录」和「记录之间的间隙」也纳入锁定范围。

```
索引值：  1    3    5    7    9
          ↑    ↑    ↑    ↑    ↑
        间隙1 间隙2 间隙3 间隙4 间隙5
       (0,1) (1,3) (3,5) (5,7) (7,9) (>9)
```

⭐ **三种行锁**：

| 锁 | 锁什么 | 例子（锁 `id=5`） |
|---|-------|-----------------|
| ⭐ **记录锁（Record Lock）** | ⭐ **只锁那一个存在的记录** | `id=5` 这行 |
| ⭐ **间隙锁（Gap Lock）** | ⭐ **只锁间隙（不含记录本身）** | `(3,5)` 和 `(5,7)` |
| ⭐ **Next-Key Lock** | ⭐ **记录锁 + 前面的间隙锁** | `id=5` + `(3,5)` |

⭐ **📌 记忆锚点：Next-Key = 左开右闭的区间 `(3, 5]`，即「间隙 (3,5) + 记录 5」。**

⚠️ **⚠️ 「左开右闭」的实现细节**：⚠️ **实际上是「记录 + 后面的间隙」**，⚠️ 因为锁的是「找到的记录，然后往右走到下一条记录之前」。

## 二、⭐ 间隙锁怎么防幻读

### 问题

```sql
-- RR 隔离级别下，事务 A
BEGIN;
SELECT COUNT(*) FROM t WHERE id > 10;    -- 假设返回 5 行
```

⚠️ **如果这时事务 B 插入 `id=11`：**

```
BEGIN;
INSERT INTO t (id) VALUES (11);   -- B 提交了
COMMIT;
```

```sql
-- A 继续
SELECT COUNT(*) FROM t WHERE id > 10;    -- ⚠️ 变成 6 行了！
```

⚠️ **⚠️ 但标准 SQL 定义：RR 只保证「同一行的读结果不变」，不保证「范围查询的行数不变」。** ⚠️ 所以这在标准 RR 下是**允许的**。

### MySQL 的做法

⚠️ **MySQL 的 RR 额外用间隙锁防幻读**：

```
事务 A 执行 SELECT ... WHERE id > 10 FOR UPDATE
    ↓
InnoDB 锁住 (10, +∞) 的所有间隙
    ↓
事务 B 想 INSERT id=11
    ↓
需要插入到间隙 (10, +∞) 里
    ↓
⛔ 被间隙锁挡住 → B 阻塞
```

⚠️ **⚠️ 关键点：⚠️ 快照读（普通 SELECT）不会加间隙锁。** 只有「**当前读**」（`FOR UPDATE` / `UPDATE` / `DELETE`）才会加。

### ⚠️ 这带来一个「幻读的定义分歧」

| | 快照读下的 RR | 当前读下的 RR |
|---|--------------|--------------|
| 范围查询后再查 | ⚠️ 读不到新插入的（快照读） | ⭐ **查得到新插入的**（当前读） |
| ⭐ 能防幻读吗 | ⭐ **「读」层面防住了**（快照固定） | ⭐ **「写」层面防住了**（间隙锁） |

⚠️ **⚠️ 结论：MySQL 的 RR 是「两个层面都防幻读」，⚠️ 但代价是间隙锁带来的锁竞争。**

⚠️ **⚠️ RC 下没有间隙锁**（⚠️ 除了一些特殊情况），⚠️ 所以 RC 允许幻读。

### ⚠️ 间隙锁的代价

⚠️ **间隙锁是「你不需要它也要锁」**：

```sql
-- ⭐ 只有 id=10 这一行
BEGIN;
SELECT * FROM t WHERE id = 10 FOR UPDATE;   -- ⭐ 锁住了 (0,10] 和 (10,+∞) 两个间隙！
```

⚠️ **⚠️ 现在整个表的插入都被阻塞了**——⚠️ 因为任何 `INSERT` 都要找间隙插入，⚠️ 而所有间隙都被锁了。

⭐ **所以间隙锁会导致「锁的范围比实际需要的大得多」。**

📌 对照 PostgreSQL：⭐ **PG 没有间隙锁**，⚠️ **PG 的 RR 确实允许幻读**。⚠️ **PG 的替代方案是「SSI（可串行化快照隔离）」**，⚠️ 是通过检测读写依赖来防幻读的，不加锁。⚠️ 这是 MySQL 和 PG 的重大实现差异。

## 三、意向锁

### 问题与解决

⚠️ **假设表有 1000 万行，事务 A 锁了第 500 行。** ⚠️ 现在事务 B 想「锁整张表」（`LOCK TABLES t WRITE`）：

| 做法 | 效率 |
|------|------|
| ⚠️ 检查每一行是否被锁 | ⚠️ **1000 万次检查** |
| ⭐ **查「有没有行锁」的标记** | ⭐ **一次判断** |

### 机制

⚠️ **表上有「意向锁」这个标记位**：

```
事务 A 锁住第 500 行
    ↓
自动在表上加「意向排他锁（IX）」
    ↓
事务 B 想锁表
    ↓
查表上的意向锁
    ↓
有 IX → ⛔ 阻塞（因为有行级排他锁）
```

| 意向锁 | 含义 |
|--------|------|
| **IS**（意向共享） | 「表内有行级共享锁（S）」 |
| **IX**（意向排他） | 「表内有行级排他锁（X）」 |
| **S** | 「要锁整表做共享」 |
| **X** | 「要锁整表做排他」 |

### ⭐ 兼容性矩阵（重要）

| | S | X | IS | IX |
|---|:-:|:-:|:-:|:-:|
| **S** | ✅ | ❌ | ✅ | ❌ |
| **X** | ❌ | ❌ | ❌ | ❌ |
| **IS** | ✅ | ❌ | ✅ | ✅ |
| **IX** | ❌ | ❌ | ✅ | ✅ |

⭐ **📌 关键：意向锁之间大多兼容（IX 和 IX 兼容），⚠️ 因为它们只表示「表内有行锁」，⚠️ 不真的冲突。⚠️ 只有「表级 S/X」才会被意向锁挡住。**

## 四、⚠️ MDL 锁（元数据锁）★

### 机制

⚠️ **每个表都有一个 MDL 锁**——⚠️ **⚠️ DDL 和 DML 之间的互斥就是通过它实现的。**

```
事务 A：SELECT * FROM t WHERE ...     -- ⚠️ 持有 MDL 读锁
事务 B：ALTER TABLE t ADD COLUMN ...   -- ⚠️ 需要 MDL 写锁 → ⛔ 等待
事务 C：SELECT * FROM t WHERE ...     -- ⚠️ 想要 MDL 读锁 → ⚠️⚠️ 也会被 B 挡住！
```

⚠️ **⚠️⚠️ 致命链条**：

```
① 事务 A 长时间未提交，持有 MDL 读锁
② 事务 B 执行 ALTER TABLE → 申请 MDL 写锁 → 排队
③ ⚠️⚠️ ⚠️ 后续所有对表 t 的普通查询也排队！
④ ⚠️⚠️ 整个表被「冻住」——因为都要拿 MDL 读锁，而 B 排在它们前面
⑤ ⚠️ 应用全面超时
```

⚠️ **⚠️ 这就是「DDL 卡住线上」的典型链条：⚠️ 「一个长事务 + 一个 DDL」= 整张表不可用。**

### MDL 的模式

| 模式 | 谁能拿 |
|------|--------|
| **读锁（SHARED_WRITE / SHARED_READ）** | `SELECT` / `INSERT` / `UPDATE` / `DELETE` |
| **写锁（EXCLUSIVE）** | ⭐ `ALTER` / `DROP` / `TRUNCATE` / `CREATE INDEX` |
| 意向写锁（INTENTION_EXCLUSIVE） | DDL 开始时先拿意向锁，让后续操作排队 |

⚠️ **⚠️ DDL 的两阶段**：⚠️ **先拿「意向写锁」（等现有读锁释放）→ 执行 DDL → 再拿「排他写锁」**。⚠️ ⚠️ **中间那段时间它会挡住新来的读请求**——⚠️ 这就是「DDL 期间查询全排队」的原因。

### 排查 MDL 等待

```sql
-- 8.0
SELECT * FROM performance_schema.metadata_locks WHERE LOCK_STATUS = 'PENDING'\G

-- 谁在等谁
SELECT 
  blocker.OBJECT_NAME, blocker.LOCK_TYPE, blocker.LOCK_STATUS,
  waiter.OBJECT_NAME, waiter.LOCK_TYPE, waiter.LOCK_STATUS
FROM performance_schema.metadata_locks blocker
JOIN performance_schema.metadata_locks waiter
  ON blocker.OBJECT_SCHEMA = waiter.OBJECT_SCHEMA
 AND ((blocker.OWNER_THREAD_ID = waiter.WAITING_THREAD_ID) 
   OR (blocker.WAITING_THREAD_ID = waiter.OWNER_THREAD_ID))
WHERE blocker.LOCK_STATUS = 'PENDING'
  AND waiter.LOCK_STATUS = 'GRANTED';
```

⚠️ **5.7 没有 `metadata_locks`**，用 `information_schema.INNODB_LOCKS` + `SHOW FULL PROCESSLIST` 交叉分析。

### 解决方案

| 方案 | 说明 |
|------|------|
| ⭐ **杀掉长事务** | ⭐ **第一手段**。长事务是根因 |
| 设 `lock_wait_timeout` | ⚠️ **DDL 的等待超时**（默认 31536000 秒 = ⚠️ **一年！**） |
| 设 `innodb_lock_wait_timeout` | 行锁等待超时（默认 50 秒） |

```sql
SHOW VARIABLES LIKE 'lock_wait_timeout';
-- ⚠️ 默认 31536000（一年）——意味着 DDL 会一直等下去！
-- ⭐ 生产建议设小一点，比如 60
SET GLOBAL lock_wait_timeout = 60;
```

⭐ **📌 记忆锚点：`lock_wait_timeout` 管 DDL（元数据），`innodb_lock_wait_timeout` 管 DML（行锁）。⚠️ 两者容易混。**

## 五、⚠️ 死锁

### 什么是死锁

```
事务 A                          事务 B
──────                          ──────
BEGIN;                          BEGIN;
SELECT * FROM t1 WHERE id=1      （加行锁 t1）
FOR UPDATE;                      
                                 SELECT * FROM t2 WHERE id=1
                                 FOR UPDATE;
SELECT * FROM t2 WHERE id=1      
FOR UPDATE;                       ⛔ 等待 t2（被 B 锁着）
                                 
⛔ 等待 t1（被 A 锁着）            
                                 
⚠️ 循环等待 → 死锁
```

### ⚠️ InnoDB 怎么处理

⚠️ **⚠️ InnoDB 有死锁检测机制**——⚠️ **它会自动回滚「代价较小」的那个事务**：

```
ERROR 1213 (40001): Deadlock found when trying to get lock;
try restarting transaction
```

⭐ **⚠️ 所以死锁不是「必须避免」，而是「必须能重试」：**

```python
import time, random
from pymysql.err import OperationalError

def execute_with_retry(conn, sql, params, max_retries=3):
    for attempt in range(max_retries):
        try:
            conn.begin()
            cur = conn.cursor()
            cur.execute(sql, params)
            conn.commit()
            return
        except OperationalError as e:
            conn.rollback()
            if e.args[0] == 1213:      # 死锁
                # ⭐ 退避 + 随机抖动，避免多个事务同时重试再次死锁
                sleep = random.uniform(0, 0.1 * (2 ** attempt))
                time.sleep(sleep)
                continue
            raise
    raise RuntimeError("重试耗尽")
```

⚠️ **⚠️ 重试必须加「退避 + 随机抖动」**——⚠️ 否则多个事务同时重试会立刻再次死锁。

### ⚠️ 死锁的四个成因

| 成因 | 例子 | 解决 |
|------|------|------|
| ⭐ **操作顺序不一致** | ⚠️ A：先 t1 后 t2；B：先 t2 后 t1 | ⭐ **所有事务按同一顺序访问表** |
| ⚠️ **大事务** | 大事务持有锁时间长 | 分批提交 |
| ⚠️ **索引缺失** | ⚠️ `UPDATE` 没走索引 → 锁全表 | 加索引 |
| ⚠️ **范围锁** | ⭐ 间隙锁扩大了锁定范围 | 用更精确的条件 |

⭐ **⭐ 第一条是根治方案：⚠️ 「⚠️ 按 ID 顺序更新」比「⚠️ 按任意顺序更新」安全得多。**

```python
# ❌ 危险：顺序不定
for item_id in ids:               # ⚠️ ids 顺序不确定
    update_stock(item_id)

# ✅ 安全：排序
for item_id in sorted(ids):       # ⭐ 所有事务顺序一致
    update_stock(item_id)
```


| 频率 | 判断 |
|------|------|
| ⭐ 偶发（几小时一次） | ✅ 正常，靠应用重试解决 |
| ⚠️ 每分钟多次 | ⚠️ 需要排查（操作顺序？索引？） |
| ❌ 持续死锁 | ❌ 有严重问题（大概率是索引缺失或顺序不一致） |

## 六、⭐ 实验清单

⚠️ **在隔离环境做。**

### 实验 1：验证 Next-Key Lock 的范围

```sql
CREATE TABLE t (id INT PRIMARY KEY, v INT);
INSERT INTO t VALUES (1,1),(5,5),(10,10);

-- 会话 A
BEGIN;
SELECT * FROM t WHERE id = 5 FOR UPDATE;   -- ⭐ 锁住 (1,5] 和 (5,10]

-- 会话 B
INSERT INTO t VALUES (3, 3);
-- ⛔ 被阻塞！（因为 3 在间隙 (1,5) 里）

-- 会话 B（另开连接，验证外侧可以）
INSERT INTO t VALUES (0, 0);
-- ✅ 不阻塞！（0 在 (-∞,1] 之外）
```

⭐ **这个实验能让你直观看到「为什么锁一行会阻塞邻近插入」。**

### 实验 2：验证快照读不加锁

```sql
-- 会话 A
BEGIN;
SELECT * FROM t WHERE id = 5;      -- ⭐ 快照读，不加锁

-- 会话 B（另一个连接）
UPDATE t SET v = 99 WHERE id = 5;
-- ✅ 不阻塞！快照读没加任何锁

-- 会话 B
SELECT * FROM t WHERE id = 5 FOR UPDATE;
-- ✅ 也不阻塞（快照读没锁住）
```

### 实验 3：验证 MDL 阻塞链条

```sql
-- 会话 A
BEGIN;
SELECT * FROM t WHERE id = 5;      -- 拿 MDL 读锁
-- 不提交

-- 会话 B
ALTER TABLE t ADD COLUMN c INT;
-- ⛔ 等待（要 MDL 写锁）

-- 会话 C（新开连接）
SELECT * FROM t WHERE id = 1;
-- ⚠️⚠️ 也被阻塞了！（因为 B 排在前面，⚠️ C 在等 MDL 读锁，⚠️ 但写锁排在它前面）
```

⭐ **⚠️ 这个实验能让你理解「DDL 卡住整张表」的机制。**

### 实验 4：造一个死锁

```sql
CREATE TABLE d1 (id INT PRIMARY KEY, v INT);
CREATE TABLE d2 (id INT PRIMARY KEY, v INT);
INSERT INTO d1 VALUES (1,1);
INSERT INTO d2 VALUES (1,1);

-- 会话 A                          -- 会话 B
BEGIN;                            BEGIN;
SELECT * FROM d1 WHERE id=1 
FOR UPDATE;                        SELECT * FROM d2 WHERE id=1
                                   FOR UPDATE;
-- 等 1 秒
SELECT * FROM d2 WHERE id=1         
FOR UPDATE;  ⛔ 等待               SELECT * FROM d1 WHERE id=1
                                  FOR UPDATE;  ⛔ 等待

-- ⚠️ 其中一个收到 ERROR 1213
SHOW ENGINE INNODB STATUS\G       -- ⭐ 看 LATEST DETECTED DEADLOCK
```

## 七、陷阱

1. **❌ 认为 RR 用「锁定读」防幻读。** ⚠️ **快照读不需要——快照本身就固定了。⚠️ 当前读靠间隙锁。**
2. **❌ 认为 PG 的 RR 也能防幻读。** ⚠️ **PG 的 RR 允许幻读**，它靠 SSI 检测。
3. **❌ 以为意向锁之间会冲突。** ⚠️ **IX 和 IX 兼容**（只表示「表内有行锁」）。
4. **⚠️ ⚠️ 在生产把 `lock_wait_timeout` 设成一年。** ⚠️ 默认值就是一年，⚠️ DDL 会一直等。**建议 60 秒。**
5. **⚠️ 混淆 `lock_wait_timeout` 和 `innodb_lock_wait_timeout`。** ⚠️ 前者管 DDL，后者管行锁。
6. **❌ 死锁当 bug 修。** ⭐ 偶发死锁靠应用重试；⚠️ 只有「持续死锁」才要排查。
7. **❌ 重试死锁时不加退避。** ⚠️ 多个事务同时重试立刻再死锁。
8. **❌ 不开 `innodb_print_all_deadlocks`。** ⚠️ 死锁记录被循环覆盖丢失。
9. **❌ 多线程/多协程更新时不排序。** ⚭� **按 ID 排序是最简单的死锁预防。**

## 小结

- ⭐ **三种行锁**：**记录锁**（锁存在的行）、**间隙锁**（锁间隙不含行）、**Next-Key**（记录 + 前面的间隙，`(3,5]`）
- ⭐ **RR 防幻读的两个层面**：⭐ **快照读靠「快照固定」；当前读靠「间隙锁」**。⚠️ **PG 只有前者**（⚠️ 所以 PG 的 RR 允许幻读）
- ⚠️ **间隙锁的代价**：「锁一行会阻塞邻近插入」，锁定范围比需要的大
- **意向锁（IS/IX）**：让「能不能锁表」变成 O(1) 判断。⭐ **IX 和 IX 兼容**
- ⭐ **MDL（元数据锁）**：DDL 需要写锁。⚠️⚠️ **「长事务 + DDL」= 整表冻结**——后续查询排在 DDL 后面
- ⚠️ **`lock_wait_timeout`（DDL）默认一年**，⚠️ 生产建议 60 秒；`innodb_lock_wait_timeout`（行锁）默认 50 秒
- ⭐ **死锁**：⚠️ InnoDB 自动检测并回滚代价小的；⚠️ **应用要重试 + 退避 + 随机抖动**
- ⭐ **死锁的根治**：⚠️ **所有事务按同一顺序访问表**（排序后遍历）
- ⚠️ **死锁排查**：`SHOW ENGINE INNODB STATUS\G` + ⭐ **生产必开 `innodb_print_all_deadlocks`**
- ⚠️ **偶发死锁是正常的**；⚠️ 持续死锁才要排查（多半是索引缺失或顺序不一致）
