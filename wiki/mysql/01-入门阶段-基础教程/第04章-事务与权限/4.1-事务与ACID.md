## 一、为什么需要事务

### 问题场景

```sql
-- 转账：从 A 扣 100，给 B 加 100
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

⚠️ **如果第二条语句失败了：**

```
A 的钱少了 100，但 B 没收到 → 100 元凭空消失
```

**事务保证**：这两条语句要么都成功，要么都不执行。

### 事务的定义

> **事务是一个或多个 SQL 语句组成的逻辑工作单元，这些语句要么全部执行成功，要么全部回滚。**

```sql
BEGIN;                          -- 或 START TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                         -- 都成功，提交
-- 如果中途任何一条报错，需要 ROLLBACK;
```

## 二、ACID 四个特性

| 特性 | 含义 | MySQL 怎么实现 |
|------|------|--------------|
| **A**tomicity 原子性 | 要么全做要么全不做 | ⭐ **undo log** |
| **C**onsistency 一致性 | 事务前后数据满足完整性约束 | ⭐ AID + 业务约束 |
| **I**solation 隔离性 | 并发事务互不干扰 | ⭐ **锁 + MVCC** |
| **D**urability 持久性 | 提交后数据不会丢 | ⭐ **redo log + 刷盘策略** |

### 原子性：undo log

```
你执行了 UPDATE
    ↓
InnoDB 先把「怎么撤销这次修改」写进 undo log
    ↓
如果 COMMIT：redo log 记录已提交，undo log 等待 purge 线程清理
如果 ROLLBACK：按 undo log 反向操作，把数据改回去
```

📌 详解见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]]。

⚠️ **⚠️ 关键推论**：`ROLLBACK` **不是「撤销」了，而是「执行了反向操作」**。这意味着：

| 现象 | 原因 |
|------|------|
| 回滚很慢 | ⭐ **要逐条执行反向的 UPDATE/DELETE**，数据量大时非常慢 |
| 自增 ID 回滚后仍有空洞 | ⚠️ **自增计数器不回滚**（因为它不是「数据状态」的一部分） |
| 回滚后 binlog 里还有记录 | ⚠️ 回滚的事务**不写 binlog**（除非开了 `binlog_rollback_on_timeout`） |

### 一致性

⚠️ **一致性是结果，不是机制。** 它是「AID 三者 + 业务约束」共同保证的。

```sql
-- 「转账总额不变」不是一个数据库能自动保证的约束
-- 它需要：原子性（要么都成）+ 业务代码保证计算正确
```

⚠️ **能自动保证的完整性**（由数据库负责）：

| 约束 | 保证什么 |
|------|---------|
| 主键唯一 | 不出现重复 ID |
| 非空约束 | 必填字段不为空 |
| 外键 | 引用完整性 |
| CHECK | 值域合法 |
| 唯一索引 | 不重复 |

⚠️ **不能自动保证的**：业务规则（如「转账前后总额相同」「订单金额 = 明细之和」）。**这些要靠触发器、应用逻辑或定时对账。**

### 隔离性：锁 + MVCC

- **写操作**：用**行锁**（`SELECT ... FOR UPDATE` 或 `UPDATE` 自动加锁）
- **读操作**：用 **MVCC**（读快照，不阻塞写）

📌 详见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]] 和 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

### 持久性：redo log + 刷盘策略

```sql
COMMIT;   -- 数据写到 redo log
```

⚠️ **redo log 什么时候真正落到磁盘？由 `innodb_flush_log_at_trx_commit` 决定：**

| 值 | 行为 | 安全性 |
|---|------|--------|
| `1`（**生产默认**） | 每次提交都写到操作系统缓存，并由 OS 刷盘 | ✅ 最安全 |
| `2` | 每次提交写到 OS 缓存，**每秒**由 MySQL 刷盘 | ⚠️ **MySQL 崩溃不丢，OS 崩溃丢 1 秒** |
| `0` | **每秒**由 MySQL 写并刷盘 | ❌ **MySQL 崩溃丢 1 秒** |

📌 见 [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]]。

### binlog 的持久性

```sql
-- sync_binlog 控制 binlog 的刷盘
-- 1（生产默认）= 每次提交都 fsync 到磁盘
-- 0 = 由 OS 决定何时刷
```

⚠️ **生产推荐组合**：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。⚠️ **代价是每次提交要两次 fsync，性能下降约 30%**——这是「数据安全 vs 性能」的明确取舍。

⚠️ **⚠️ 金融/订单类系统不要为了性能调低这两个参数。** 一个 `=2` 配置的数据库在断电时会丢掉一秒的数据，而这一秒里可能有上千笔订单。

## 三、四种隔离级别

### 三个并发问题

| 问题 | 定义 | 例子 |
|------|------|------|
| **脏读**（Dirty Read） | 读到别的事务**还没提交**的数据 | A 改了没提交，B 读到了，A 回滚了 → B 读到的是不存在的数据 |
| **不可重复读**（Non-repeatable Read） | 同事务内两次读**同一行**结果不同 | A 两次读 id=1，第一次 100，第二次 200（中间 B 改过） |
| **幻读**（Phantom Read） | 同事务内两次读**同一范围**，行数变了 | A 查 `salary > 100` 读到 10 行，中间 B 插了 1 个，读第二次变 11 行 |

### 四级隔离表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|------|-----------|------|------|
| `READ UNCOMMITTED`（RU） | ❌ 会 | ❌ 会 | ❌ 会 | ⭐ 几乎不用，实际等同于不加隔离 |
| `READ COMMITTED`（RC） | ✅ 防 | ❌ 会 | ❌ 会 | Oracle/PG/SQL Server 默认 |
| `REPEATABLE READ`（RR） | ✅ 防 | ✅ 防 | ⚠️ 基本防 | ⭐ **MySQL 默认** |
| `SERIALIZABLE` | ✅ 防 | ✅ 防 | ✅ 防 | ⭐ 并发性能极差，几乎不用 |

⚠️ **MySQL 的 RR 和标准 SQL 的 RR 不一样**——见下一节。

### 设置隔离级别

```sql
-- 会话级
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 全局（只影响新连接）
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 查看
SELECT @@transaction_isolation;          -- 会话级
SELECT @@global.transaction_isolation;   -- 全局级
```

### ⚠️⚠️ MySQL 的 RR 是什么水平

**这是本节最重要的一点。**

⚠️ **标准 SQL 定义 RR 是「同一事务内多次读同一行，结果相同」，并不保证不幻读。**

⚠️ **但 MySQL 的 RR 额外做了两件事来防幻读：**

| 机制 | 作用 |
|------|------|
| **快照读（一致性非锁定读）** | ⭐ `SELECT` 时用 MVCC 读历史快照，**完全不加锁**，整个事务看到的是同一份数据 |
| **当前读（一致性锁定读）** | ⭐ `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 读最新版本，**用间隙锁锁住范围阻止插入** |

**两个关键词的后果**：

```
快照读：读到的是事务开始时的快照 → 不会看到别人新提交的数据
当前读：读到最新数据 → 会被阻塞（有锁）
```

⚠️ **⚠️ 同一个事务里混用两种读，会导致「读到自己更新后看不到」的现象**：

```sql
BEGIN;
SELECT * FROM t WHERE id = 1;          -- 快照读：balance = 100
UPDATE t SET balance = 200 WHERE id = 1; -- 当前读：更新（并加了锁）
SELECT * FROM t WHERE id = 1;          -- ⚠️ 还是 100！（快照读，不变）
COMMIT;

-- ⚠️ 之后再开一个事务读，会看到 200
```

📌 这是 MySQL RR 的正确行为，不是 bug。但如果你的业务逻辑依赖「更新后立刻读到新值」，**必须用「当前读」**：

```sql
SELECT balance FROM t WHERE id = 1 FOR UPDATE;   -- ⭐ 当前读，能读到最新值
```

⚠️ **⚠️ 混用两种读而没意识到，是 MySQL 事务最隐蔽的 bug 之一。**

📌 详见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]]。

## 四、事务语句

### 基本用法

```sql
-- 方式 1（推荐）
START TRANSACTION;
UPDATE ...;
UPDATE ...;
COMMIT;    -- 或 ROLLBACK;

-- 方式 2：autocommit
SET autocommit = 0;
UPDATE ...;
UPDATE ...;
COMMIT;    -- 或 ROLLBACK;

-- ⚠️ 方式 3：不要用
START TRANSACTION;   -- 不带 BEGIN TRANSACTION 的会话会隐式提交
```

### ⚠️ DDL 会隐式提交

⚠️ **这是 MySQL 的一个大坑：**

```sql
BEGIN;
INSERT INTO t (v) VALUES (1);
CREATE TABLE new_t (id INT);      -- ⚠️ DDL！隐式 COMMIT
ROLLBACK;                          -- ⚠️ 回滚不了！INSERT 已经提交了
```

⚠️ **会隐式提交的语句**：

| 类型 | 语句 |
|------|------|
| **DDL** | `CREATE` / `ALTER` / `DROP` / `TRUNCATE` / `RENAME` |
| **权限** | `GRANT` / `REVOKE` |
| **事务控制** | `START TRANSACTION`（在已有事务时） |
| **锁** | `LOCK TABLES` / `UNLOCK TABLES` |
| **加载** | `LOAD DATA`（⚠️ 部分情况） |
| `SET autocommit` | 切换 autocommit |

⚠️ **所以：⚠️ 事务里不要放 DDL。** 需要「建表+插数据」的原子性，用外部编排（先建表，再事务插数据）。

### SAVEPOINT

```sql
BEGIN;
INSERT INTO a (v) VALUES (1);
SAVEPOINT sp1;                    -- 设一个中间点
INSERT INTO a (v) VALUES (2);
ROLLBACK TO sp1;                  -- 只撤销第二条，第一条还在
INSERT INTO a (v) VALUES (3);
COMMIT;
-- 最终：v=1 和 v=3
```

⚠️ `ROLLBACK TO sp1` **不会结束事务**，之后还能继续 `COMMIT` 或再 `ROLLBACK`。

⚠️ **⚠️ SAVEPOINT 会增加 undo log 和开销**，⚠️ 一个事务里设几十个 SAVEPOINT 会拖慢性能。只在必要时用。

### 回滚整个事务 vs 回滚到 SAVEPOINT

| 语句 | 效果 |
|------|------|
| `ROLLBACK;` | 撤销**整个**事务的所有修改，事务结束 |
| `ROLLBACK TO sp1;` | 撤销到 sp1，**事务继续** |

## 五、⚠️ 长事务的危害 ★

⚠️ **「长事务」指执行时间长的 InnoDB 事务**，包括「长时间不提交的事务」和「执行耗时长的 SQL」。**这是生产数据库最常见的问题之一。**

### 危害 1：undo log 膨胀

```
事务 A 开启后改了 1000 万行但没提交
    ↓
undo log 里有 1000 万条「反向操作」记录
    ↓
① 占满磁盘
② purge 线程被卡住（见危害 2）
③ 其他事务的 MVCC 读要遍历很长的版本链 → 变慢
```

### 危害 2：阻塞 purge 线程 ⚠️

⭐ **InnoDB 的 purge 线程负责清理「不再被任何事务需要的 undo log」。**

⚠️ **规则：只要有一个事务持有 ReadView，purge 就不能清理它之后版本的数据。**

```
事务 A 在 10:00 开启（ReadView = 10:00 的快照）
事务 B 从 10:00 到现在写了 1 亿行
    ↓
purge 想清理 B 的旧版本 → 但 A 的 ReadView 可能还要看 → ⛔ 停止
    ↓
⚠️ undo 表空间持续膨胀，最终磁盘满
```

⚠️ **这被称为 "history list length" 失控**，是「数据库越用越慢」的常见根因。

### 危害 3：锁等待与阻塞

```sql
-- 会话 1
BEGIN;
SELECT * FROM orders WHERE id = 1 FOR UPDATE;    -- 锁住 id=1
-- ⚠️ 忘记 COMMIT

-- 会话 2
UPDATE orders SET status='paid' WHERE id = 1;    -- ⛔ 一直等待
-- ⚠️ 其他所有要写这行的请求都排队
```

⚠️ **长事务持有的锁越多，并发能力越差。**

### 危害 4：主从延迟

⚠️ **⚠️ 重要**：⚠️ **一个大事务在从库重放时，从库无法并行应用其他事务**（单线程回放 binlog）。

⚠️ **⚠️ 你在从库上跑一个跑 10 分钟的批量 UPDATE，会导致从库延迟 10 分钟。**

📌 缓解手段见 [[mysql/02-中段阶段-专题精讲/主从复制与高可用/复制原理与拓扑]]。

### 排查长事务

```sql
-- ① 当前正在运行的事务
SELECT * FROM information_schema.INNODB_TRX\G

-- ② 找到运行超过 60 秒的事务
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec,
       trx_mysql_thread_id, trx_query
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY trx_started;
```

⚠️ **`trx_mysql_thread_id` 是连接 ID**，用它去 `SHOW PROCESSLIST` 找到是谁的连接。

```sql
-- ③ 哪些连接空闲但开着事务（最常见的长事务来源！）
SELECT t.trx_id, t.trx_started, p.id, p.time, p.state, p.command, p.info
FROM information_schema.INNODB_TRX t
JOIN information_schema.PROCESSLIST p ON p.id = t.trx_mysql_thread_id
ORDER BY t.trx_started;
```

⚠️ **最常见的长事务来源**：

| 来源 | 说明 |
|------|------|
| **⚠️ 忘了 COMMIT 的 SELECT 事务** | 代码里开了 BEGIN 但某条路径没提交 |
| **Python 默认不开 autocommit** | ⭐ `pymysql` 默认 `autocommit=False`，你必须显式 commit |
| 交互式客户端忘了 | 用 `mysql` 命令行时 |
| 存储过程里没提交 | |
| **应用连接池的 bug** | 连接借出后没还 |

📌 完整治理见 [[mysql/02-中段阶段-专题精讲/事务与并发控制/长事务与undo膨胀]]。

### 预防措施

| 措施 | 说明 |
|------|------|
| **⚠️ 应用侧超时不提交** | 每条语句设超时；连接空闲超时就断开 |
| 批量操作分批提交 | 每 1000 条 commit 一次 |
| 监控长事务数量和时长 | 超过阈值告警 |
| `innodb_lock_wait_timeout` 设小一点 | 默认 50 秒太长了，生产常设 5-10 秒 |

```sql
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
SET GLOBAL innodb_lock_wait_timeout = 5;    -- ⚠️ 只影响新连接
```

## 六、什么时候该用事务

### ✅ 该用

| 场景 | 为什么 |
|------|--------|
| 多表关联写入 | 保证一致性 |
| 转账/扣库存 | 必须原子 |
| 批量数据操作 | 部分失败要能整体回滚 |
| 需要保证「读到一致的数据」 | 用 RR 的快照读 |

### ❌ 不该用 / 要谨慎

| 场景 | 原因 |
|------|------|
| **单条 INSERT/UPDATE** | ⭐ **⚠️ 单条语句本身就是隐式事务，不需要显式 `BEGIN`** |
| 只读操作 | 单条 SELECT 是快照读，不需要显式事务 |
| 大批量 DELETE/UPDATE | ⚠️ 事务会很大，考虑分批 |
| 事务里包 DDL | ⚠️ 隐式提交，事务失效 |
| 事务里调外部接口 | ⚠️ 网络调用耗时长，事务被拉长 |

⚠️ **⚠️ Python 侧的重要提醒**：

```python
# PyMySQL 默认 autocommit=False
conn = pymysql.connect(...)      # ⚠️ 相当于永远处于「有未提交操作」状态

# 单条 INSERT 之后没有 commit
cur.execute("INSERT INTO ...")   # ⚠️ 数据在事务里，其他连接看不到！
conn.close()                     # ⚠️ 未提交的事务会被回滚，数据丢失
```

⚠️ **要么开 autocommit**：

```python
conn = pymysql.connect(..., autocommit=True)
```

⚠️ **要么显式管理事务**：

```python
conn = pymysql.connect(...)
try:
    conn.begin()
    cur.execute("INSERT INTO a ...")
    cur.execute("INSERT INTO b ...")
    conn.commit()      # ⭐ 成功提交
except Exception:
    conn.rollback()    # ⭐ 失败回滚
    raise
finally:
    conn.close()
```

📌 连接池场景见 [[sqlmodel/引擎与Session]]。

## 七、排查

```sql
-- 当前会话的事务状态
SELECT @@autocommit, @@transaction_isolation;

-- 正在运行的事务
SELECT * FROM information_schema.INNODB_TRX\G

-- 所有连接
SELECT id, user, host, db, command, time, state, info
FROM information_schema.PROCESSLIST
ORDER BY time DESC;

-- 等待的锁
SELECT * FROM performance_schema.data_lock_waits\G     -- 8.0
SELECT * FROM information_schema.INNODB_LOCK_WAITS;    -- 5.7

-- InnoDB 整体状态（含死锁历史）
SHOW ENGINE INNODB STATUS\G
```

⚠️ **⚠️ `SHOW PROCESSLIST` 需要 PROCESS 权限才能看到别人的连接**，否则只显示自己的。

## 八、陷阱

1. **❌ 不确认 `innodb_flush_log_at_trx_commit` 和 `sync_binlog`。** 生产必须都是 1。
2. **❌ 事务里放 DDL。** 隐式提交，事务失效。
3. **❌ 长事务不提交。** undo 膨胀、purge 卡住、锁阻塞、主从延迟。
4. **❌ Python 不 commit 就关连接。** 数据丢失。
5. **❌ 混用快照读和当前读而不自知。** 「更新后读不到新值」。
6. **❌ 单条语句也开显式事务。** 无意义的开销。
7. **❌ 批量操作不���批提交。** 事务巨大。
8. **❌ 事务里调外部接口。** 拉长事务时间。
9. **❌ 指望 RR 能防住所有幻读。** 快照读不是「锁定视图」。
10. **❌ `ROLLBACK` 之后自增 ID 会回退。** 不会。

---

## 小结

- ACID：**原子性靠 undo log**、隔离性靠**锁+MVCC**、持久性靠 **redo log + 刷盘策略**
- ⚠️ **`ROLLBACK` 是执行反向操作**，所以回滚慢；自增 ID 不回退
- 一致性是 AID 的结果；**业务规则数据库保证不了**（要靠代码或定时对账）
- 四种隔离级别：RU/RC/**RR（默认）**/Serializable。⚠️ **MySQL 的 RR 额外用间隙锁防幻读**，比标准 SQL 更强
- ⚠️ **MySQL RR 有「快照读」和「当前读」两种**：混用会导致「更新后读不到新值」
- ⚠️ **DDL 会隐式提交**，事务里不要放
- ⚠️ **长事务四大危害**：undo 膨胀、**阻塞 purge**、锁阻塞、主从延迟
- 排查：`information_schema.INNODB_TRX` 找长事务
- ⚠️ **Python `pymysql` 默认 `autocommit=False`**——单条 INSERT 不 commit 会在关连接时回滚
