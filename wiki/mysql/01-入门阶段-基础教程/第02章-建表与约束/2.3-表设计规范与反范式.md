# 表设计规范与反范式

## 学习目标

读完本篇，你应当能够：

1. 说出第一范式到第三范式在说什么
2. **判断什么时候该拆表、什么时候该冗余**
3. 避免「一张表塞三种事物」的设计错误
4. 在软删除、状态字段、审计字段上做出合理选择
5. 知道冗余的代价和「什么时候必须冗余」
6. 说出分库分表前必须做的设计准备

## 一、三种范式（够用了）

⚠️ **理论上到 BCNF、第五范式，实际工作中 1NF~3NF 已经覆盖 95% 的场景。** 知道前三个的意思即可。

### 第一范式（1NF）：列不可再分

```sql
-- ❌ 违反 1NF：一列里塞了多个值
CREATE TABLE users (
  id INT PRIMARY KEY,
  phones VARCHAR(100)          -- '13800138000,13900139000'
);

-- ✅ 符合 1NF：一列一个值
CREATE TABLE users (
  id INT PRIMARY KEY,
  phone VARCHAR(20)
);
```

⚠️ **MySQL 允许「伪 1NF」**（JSON 列里放数组），但**不要依赖它**——JSON 里的元素无法直接索引和约束。

### 第二范式（2NF）：非主键列依赖整个主键

⚠️ **2NF 只在复合主键时才有意义。**

```sql
-- 复合主键 (order_id, product_id)
CREATE TABLE order_items (
  order_id   BIGINT,
  product_id BIGINT,
  product_name VARCHAR(64),      -- ⚠️ 只依赖 product_id，不依赖 order_id
  unit_price  DECIMAL(10,2),     -- ⚠️ 只依赖 product_id
  quantity    INT,
  PRIMARY KEY (order_id, product_id)
);
```

⚠️ **`product_name` 违反了 2NF**：它只依赖复合主键的一部分（`product_id`）。后果是**改商品表时要同步改这里**，否则数据不一致。

```sql
-- ✅ 修正：拆表
CREATE TABLE order_items (
  order_id   BIGINT,
  product_id BIGINT,
  quantity   INT,
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE products (
  id BIGINT PRIMARY KEY,
  name VARCHAR(64),
  price DECIMAL(10,2)
);
```

### 第三范式（3NF）：非主键列不传递依赖主键

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  emp_id BIGINT,
  emp_dept_id BIGINT,      -- ⚠️ 依赖 emp_id，不直接依赖 order.id
  emp_dept_name VARCHAR(64) -- ⚠️ 传递依赖：id → emp_id → emp_dept_name
);
```

⚠️ **`emp_dept_name` 违反了 3NF**。后果：员工调到别的部门后，历史订单里的部门名是错的。

⭐ **判断标准很简单**：「这个字段的信息，能不能从本表的其他字段推出来？能 → 冗余 → 可能违反 3NF。」**

## 二、核心原则：一张表只描述一种事物 ⭐

⚠️ **这是本文最重要的一条，也是新手最容易犯的错。**

### 反例：一个表塞三种事物

```sql
-- ❌ 反面教材
CREATE TABLE everything (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,

  -- 用户的信息
  user_name VARCHAR(64),
  user_email VARCHAR(255),

  -- 订单的信息
  order_no VARCHAR(32),
  order_amount DECIMAL(10,2),
  order_status TINYINT,

  -- 商品的信息
  product_name VARCHAR(64),
  product_price DECIMAL(10,2),
  product_stock INT,

  ... 还有更多
);
```

**这个设计有六个致命问题**：

| 问题 | 后果 |
|------|------|
| **① 无法复用** | 同两个用户下十单，user_name 存了十遍 |
| **② 更新要改多处** | 改商品价格要更新所有相关订单行 |
| **③ 数据不一致** | 同一商品在不同订单里价格可能不同（虽然是快照语义，但容易出错） |
| **④ 一对一关系变成多行** | 每个订单都要重复一遍用户信息，浪费空间 |
| **⑤ 索引没法建** | 想给「用户表」建索引，但这里只是别人的冗余 |
| **⑥ 没有一张表是清晰的实体** | 没人能说清这表到底是什么 |

### 正确：拆成三张表

```sql
CREATE TABLE users (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255) NOT NULL,
  name VARCHAR(64) NOT NULL,
  UNIQUE KEY uk_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE products (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  stock INT NOT NULL DEFAULT 0,
  KEY idx_name (name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE orders (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  order_no VARCHAR(32) NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  total_amount DECIMAL(12,2) NOT NULL,
  status TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_created (user_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE order_items (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  order_id BIGINT UNSIGNED NOT NULL,
  product_id BIGINT UNSIGNED NOT NULL,
  -- ⚠️ 这里冗余了下单时的价格快照（正确的冗余）
  unit_price DECIMAL(10,2) NOT NULL,
  quantity INT NOT NULL,
  KEY idx_order (order_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 为什么要冗余 `unit_price`

⚠️ **这是一个「正确的冗余」，值得单独说。**

```sql
-- ❌ 只存 product_id，实时查商品表拿价格
-- 问题：商品调价后，历史订单的价格也变了
-- 「我三个月前下单时是 99 元，为什么现在订单显示 199 元？」

-- ✅ 存下单时的价格快照
unit_price DECIMAL(10,2) NOT NULL      -- 下单那一刻的价格
```

⭐ **判断标准：如果字段的含义是「事情发生时」的值，就必须快照，不能实时关联。**

类似场景：订单的收货地址、用户名、商品名、优惠券面额——**都要快照**。

## 三、什么时候该拆表

| 情况 | 该拆 |
|------|------|
| 字段的信息能被其他字段推导出来 | ✅ 拆（违反 3NF） |
| 同一个实体的信息在多行重复 | ✅ 拆 |
| 一个字段描述的是「另一类事物」 | ✅ 拆（本文核心原则） |
| 这类数据会被独立修改 | ✅ 拆 |
| 一对多关系 | ✅ 拆（子表） |

## 四、什么时候该冗余（不拆）

⚠️ **冗余不是原罪，有目的的冗余是优化手段。** 但要有意识。

### 可以冗余的情况

| 场景 | 冗余什么 | 为什么 |
|------|---------|--------|
| **快照语义** | 订单里的商品单价、用户名、地址 | 「事情发生时的值」 |
| **统计字段** | `order_count`、`total_spent` | 避免每次聚合全表 |
| **反规范化读性能** | 冗余几个会被频繁 JOIN 的字段 | 减少 JOIN 次数 |
| **避免 N+1 查询** | 列表页要显示的关联字段 | 一次查询 vs N 次 |

### 冗余的代价（必须知道）

| 代价 | 说明 |
|------|------|
| **更新不一致** | ⚠️ 冗余字段和源字段不同步 |
| **存储浪费** | 同样的信息存多份 |
| **同步成本** | 要写定时任务或触发器同步 |

⭐ **冗余的正确做法**：**在同一个事务里一起更新**，或者接受最终一致并有对账机制。⚠️ **最糟糕的做法是「靠人记得去更新」。**

### 统计字段的典型实现

```sql
CREATE TABLE users (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  email VARCHAR(255) NOT NULL,
  order_count INT NOT NULL DEFAULT 0,        -- ⭐ 冗余统计
  total_spent DECIMAL(12,2) NOT NULL DEFAULT 0,
  UNIQUE KEY uk_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**更新时机（关键）**：

```sql
-- ⚠️ 下单时更新（在同一个事务里）
BEGIN;
INSERT INTO orders (user_id, total_amount) VALUES (1, 99.00);
UPDATE users
   SET order_count = order_count + 1,
       total_spent = total_spent + 99.00
 WHERE id = 1;
COMMIT;
```

⚠️ **⚠️ 三个必须注意的点**：

1. **必须同一个事务**，否则会出现「订单建了但统计没加」
2. **⚠️ 订单取消/退款时要减回去**，忘了就是永久性数据错误
3. **⚠️ 历史数据迁移时要重算**，不能直接复制字段

⚠️ **如果统计准确性要求高，用「从订单表实时聚合」或「事件溯源 + 定时重算」，别硬维护。**

## 五、软删除 vs 状态字段

⚠️ **两种「标记已删除」的方式，选择错了会出事。**

| 方式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. `deleted_at` 软删除** | 加时间戳字段，非空表示删除 | ✅ 能知道什么时候删的 | ⚠️ 每个查询都要加 `WHERE deleted_at IS NULL` |
| **B. 状态字段** | `status` 枚举表示状态 | ✅ 状态语义更丰富 | ⚠️ 状态多了就乱 |
| **C. 真删** | `DELETE` | ✅ 最简单 | ❌ 数据不可恢复 |

### 软删除的三个必然后果

#### 后果 1：每个查询都要加过滤条件

```sql
-- ⚠️ 忘了这一句，你会看到已删除的数据
SELECT * FROM users WHERE deleted_at IS NULL;

-- ⚠️ 更隐蔽的坑：统计时忘了过滤
SELECT COUNT(*) FROM users;                    -- ❌ 含已删除
SELECT COUNT(*) FROM users WHERE deleted_at IS NULL;   -- ✅
SELECT COUNT(DISTINCT email) FROM users;      -- ⚠️ 含已删除的，统计重复！
```

⭐ **正解：用生成列 + 视图，或者干脆不用软删除。**

#### 后果 2：唯一索引冲突

见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]] 第六节的完整方案。

#### 后果 3：数据量膨胀且不回收

⚠️ **软删除的表只增不减。** 一年后 100 万行里可能有 30 万是已删除的，所有查询都在扫它们。

### 我的建议

| 场景 | 建议 |
|------|------|
| 金融/审计要求保留历史 | ✅ 软删除 + 归档 |
| 普通业务数据，误删要能找回 | ✅ 软删除 |
| 日志类数据 | ✅ 时间分区 + 自动删除（`PARTITION BY RANGE` + `DROP PARTITION`） |
| 临时数据（草稿、缓存） | ✅ 真删 |
| ⚠️ 简单 CRUD 业务 | ❌ **别用软删除**——维护成本大于收益 |

📌 分区表见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。

## 六、审计字段

### 四个标准字段

```sql
CREATE TABLE t (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  -- 业务字段...

  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  created_by BIGINT UNSIGNED NULL COMMENT '创建人ID',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                            ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  updated_by BIGINT UNSIGNED NULL COMMENT '更新人ID',
  deleted_at DATETIME NULL COMMENT '软删除时间',
  version     INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### `version` 乐观锁

⚠️ **这是防并发覆盖的重要手段**，尤其是配合「读-改-写」模式：

```sql
-- 1. 读
SELECT id, stock, version FROM products WHERE id = 1;
-- 假设读到 stock=10, version=3

-- 2. 改（带上 version 条件）
UPDATE products
   SET stock = 9, version = 4
 WHERE id = 1 AND version = 3;
-- ⚠️ 如果影响 0 行，说明有人先改了，要重试

-- 3. 应用层判断
-- affected_rows == 0 → 冲突，重试或报错
```

⚠️ **`version` 只在你显式传进去时才有效**。ORM 里通常叫 `optimistic_locking`。

📌 并发控制的完整对比见 [[mysql/01-入门阶段-基础教程/第04章-事务与权限/4.1-事务与ACID]]。

### 审计字段的取舍

| 字段 | 值得吗 | 说明 |
|------|-------|------|
| `created_at` / `updated_at` | ⭐ **必须有** | 排查问题、增量同步都要用 |
| `created_by` / `updated_by` | 视场景 | 需要追溯「谁改的」就要 |
| `version` | ⭐ 高并发场景必须 | 乐观锁 |
| `deleted_at` | ⚠️ 谨慎 | 见第五节 |

⚠️ **`created_by` 的现实问题**：谁来填？应用层传？还是从连接上下文（登录用户）取？⚠️ 很多项目建了但从来不填，最后是 NULL。**建之前先想清楚怎么填。**

## 七、为分库分表做的设计准备

⚠️ **如果你知道将来要分库分表（Sharding），现在就要做几件事**，否则将来改不动。

### 准备一：主键不能用自增

```sql
-- ❌ 分库后自增 ID 会冲突（每个库都从 1 开始）
id BIGINT UNSIGNED AUTO_INCREMENT

-- ✅ 用雪花算法或号段模式分配全局唯一 ID
id BIGINT UNSIGNED NOT NULL
```

📌 方案详见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.3-表设计规范与反范式]]。

### 准备二：把「所有查询都会用到的字段」放进同一个索引

⚠️ **分片键必须出现在查询条件里**，否则要广播到所有库。

```sql
-- ⚠️ 如果按 user_id 分片，所有查询都得带 user_id
-- 那就把 user_id 放在所有索引的最左列
KEY idx_user_status_created (user_id, status, created_at)
KEY idx_user_created (user_id, created_at)
```

⚠️ **「分片键在索引最左列」是硬约束**——这会限制你能不能用别的字段查。所以分片键的选择要谨慎（见下一节）。

### 准备三：避免全局唯一约束

⚠️ **分片后唯一索引只能保证「片内唯一」。** 全局唯一（比如 `uk_email`）需要额外的全局 ID 服务或发号器。

### 准备四：不用数据库特性（外键、跨表约束）

⚠️ 原因见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]]。

### 分片键怎么选

| 好的分片键 | 坏的分片键 |
|-----------|-----------|
| ✅ 查询条件里必有（如 `user_id`） | ❌ 查询时没有（如 `created_at`） |
| ✅ 数据分布均匀 | ❌ 分布倾斜（少数大客户） |
| ✅ 值稳定不变 | ❌ 会变（会引发数据迁移） |
| ✅ 基数大 | ❌ 基数小（分不了几片） |

⚠️ **「查询时必有」是最重要的标准。** 如果 30% 的查询不带分片键，就会变成「广播查询」——性能还不如不分片。

## 八、陷阱

1. **❌ 一张表塞多种事物。** 最严重的设计错误。
2. **❌ 把「实时关联的值」当历史值存。** 商品调价后历史订单就错了。
3. **❌ 冗余了但不同步更新。** 数据不一致的根源。
4. **❌ 统计字段忘了在退款时减回去。** 永久性数据错误。
5. **❌ 软删除后忘了在统计查询里过滤。** 数字虚高。
6. **❌ 软删除 + 唯一索引冲突。** 见约束那篇。
7. **❌ 建了 `created_by` 但从来填。** NULL 的审计字段等于没有。
8. **❌ 高并发场景不加乐观锁。** 后写的静默覆盖先写的。
9. **❌ 将来要分片却用自增主键。** 改造成本极高。
10. **❌ 分片键不在索引最左列。** 查询要广播。

## 小结

- 三范式够用：**1NF 列不可分 / 2NF 完全依赖整个主键 / 3NF 不传递依赖**
- ⭐ **核心原则：一张表只描述一种事物**
- ⭐ **「正确的冗余」判断标准**：字段的含义是「事情发生时」的值 → 必须快照（订单单价、收货地址、商品名）
- 冗余必须在**同一事务**里同步更新，退款/取消要减回去
- 软删除的三个后果：**每个查询都要过滤 / 唯一索引冲突 / 数据不回收**——维护成本常被低估
- 标准审计字段：`created_at` + `updated_at`（必须有）、`version`（高并发）、`created_by`（先想清楚怎么填）
- **将来要分片的话现在就要做**：主键非自增、分片键在所有索引最左列、无全局唯一约束、无外键
- 分片键第一标准是「**所有查询都带它**」
