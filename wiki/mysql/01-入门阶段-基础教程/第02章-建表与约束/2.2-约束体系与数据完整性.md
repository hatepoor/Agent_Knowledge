## 一、五类约束

| 约束 | 关键字 | 保证什么 | 靠什么实现 |
|------|--------|---------|-----------|
| **主键** | `PRIMARY KEY` | 唯一且非空 | 聚簇索引 |
| **唯一** | `UNIQUE` | 值不重复 | 唯一索引 |
| **外键** | `FOREIGN KEY` | 引用的值必须存在 | 子表索引 + 约束检查 |
| **检查** | `CHECK` | 值满足条件 | 表达式求值 |
| **非空** | `NOT NULL` | 不能为 NULL | 列标记 |

### 主键

```sql
ALTER TABLE employees ADD PRIMARY KEY (id);

-- 主键的三条性质
-- 1. 唯一
-- 2. 不为 NULL（⚠️ 即使声明 NULL 也会被隐式改成 NOT NULL）
-- 3. 一张表只能有一个主键
```

⚠️ **InnoDB 的主键就是聚簇索引**——数据本身按主键顺序物理存储。所以主键的选择会直接影响物理存储顺序，详见 [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]]。

⚠️ **⚠️ 主键要「短且有序」**：

| 主键类型 | 评价 |
|---------|------|
| `BIGINT AUTO_INCREMENT` 单列 | ⭐ **最优**。短（8字节）、有序（顺序插入不页分裂） |
| `VARCHAR(36)` UUID | ⚠️ 差。36 字节长，**随机分布导致页分裂严重** |
| `VARCHAR(36)` 有序 UUID | 可接受（MySQL 8.0 有 `UUID_TO_BIN` 函数） |
| 复合主键 | ⚠️ 索引变大，一级索引要存所有列 |

📌 分布式 ID 方案见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.3-表设计规范与反范式]]。

### 唯一约束

```sql
-- 单列
email VARCHAR(255) NOT NULL UNIQUE,

-- 联合唯一（⚠️ 语义是组合唯一，不是各自唯一）
UNIQUE KEY uk_dept_name (dept_id, name)
```

⚠️ **联合唯一的语义陷阱**：

```sql
-- uk_dept_name (dept_id, name)
INSERT INTO t (dept_id, name) VALUES (1, '张三');  -- ✅
INSERT INTO t (dept_id, name) VALUES (1, '李四');  -- ✅ 不同 name
INSERT INTO t (dept_id, name) VALUES (2, '张三');  -- ✅ 不同 dept_id
INSERT INTO t (dept_id, name) VALUES (1, '张三');  -- ❌ 组合重复
```

⚠️ **MySQL 不支持部分唯一索引**（PostgreSQL 支持 `UNIQUE (col) WHERE ...`）。⚠️ 这导致「条件唯一」的需求在 MySQL 里很别扭，见第六节的软删除方案。

⚠️ **NULL 与唯一约束**：`UNIQUE` 列可以有多个 NULL（因为 `NULL != NULL`）：

```sql
email VARCHAR(255) UNIQUE   -- 可以有多行的 email 是 NULL
```

### 检查约束

```sql
CREATE TABLE products (
  price  DECIMAL(10,2) NOT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  CONSTRAINT ck_price CHECK (price >= 0),
  CONSTRAINT ck_status CHECK (status IN (0,1,2))
);
```

⚠️ **⚠️ 8.0.15 之前 `CHECK` 是解析但不执行的**——语法通过，写入非法值也不报错。8.0.15+ 才真正强制执行。

```sql
-- 检查约束是否被强制
SELECT * FROM information_schema.CHECK_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA = 'shop';

-- 查看所有被 CHECK 约束的列
SELECT * FROM information_schema.CHECK_CONSTRAINT_USAGE;
```

⭐ **`CHECK` 是替代 `ENUM` 的好方案**（见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.1-数据类型全景]]）：加值不用改表结构，跨环境不会乱。

⚠️ **`CHECK` 不检查已有数据**：

```sql
-- 先加约束（已有 5 行数据是负数）
ALTER TABLE products ADD CONSTRAINT ck_price CHECK (price >= 0);
-- ❌ ERROR 3819: Check constraint 'ck_price' is violated
-- ⚠️ 必须先修数据再.constraints
```

## 二、外键：★ 最重要的取舍

### 外键的作用

```sql
CREATE TABLE orders (
  emp_id BIGINT UNSIGNED NOT NULL,
  CONSTRAINT fk_emp FOREIGN KEY (emp_id) REFERENCES employees(id)
);
```

**保证 `orders.emp_id` 的每个值，在 `employees` 里都有对应的行。**

⚠️ 没有外键时的失败场景：员工被删了，但订单还在，`orders.emp_id = 999` 指向一个不存在的员工——这就是**孤儿数据**。

### 外键的三个动作

```sql
CONSTRAINT fk_emp FOREIGN KEY (emp_id) REFERENCES employees(id)
  ON DELETE ???    -- 父行被删时怎么办
  ON UPDATE ???    -- 父行主键被改时怎么办
```

| 动作 | 含义 | 后果 |
|------|------|------|
| `RESTRICT`（默认） | 拒绝 | ⭐ **最安全**。有引用就不让删 |
| `CASCADE` | 级联 | ⚠️ 父删则子全删。**危险**：删部门连带删掉所有员工 |
| `SET NULL` | 置空 | ⚠️ 要求外键列可为 NULL，且**会丢失历史关联** |
| `NO ACTION` | 同 RESTRICT | |

⭐ **默认值 `RESTRICT` 是对的**，但很多人显式写出来是为了表达意图。

### 为什么很多生产系统故意不用外键 ⚠️

⚠️ **这是一个真实的工程分歧，没有标准答案。** 我把两方理由都列出来。

#### 用外键的理由

| 理由 | 说明 |
|------|------|
| **数据完整性由数据库保证** | 不依赖应用代码写对 |
| **防止应用 bug** | 应用漏了检查，数据库挡住 |
| **删改有明确语义** | `RESTRICT` 让「不能删有引用的行」变成硬约束 |
| **文档化** | 表结构本身说明了关联关系 |

#### 不用外键的理由

| 理由 | 说明 |
|------|------|
| **⚠️ 锁与性能** | ⭐ 每次插入/更新子表都要**检查父表**，加锁 |
| **⚠️ 级联删除的连锁风险** | 删一条数据触发一大串删除，且**你事先不知道会删多少** |
| **⚠️ 跨库不能有外键** | 分库分表（Sharding）后外键失效 |
| **并发死锁来源** | 两个事务各锁父表和子表，顺序不同就死锁 |
| **批量操作慢** | 批量导入 100 万行时每行都要验外键 |
| **DDL 受限** | ⚠️ **被引用的表不能随便 `TRUNCATE` 或改引擎** |

⚠️ **`TRUNCATE` 被外键挡住**是常见运维事故：

```sql
TRUNCATE TABLE departments;
-- ERROR 1701: Cannot truncate a table referenced in a foreign key constraint
-- ⚠️ 必须先 DROP FOREIGN KEY，或先删子表数据
```

### 我的建议

| 场景 | 建议 |
|------|------|
| **单体系统、数据量小、开发团队** | ✅ **用外键**。安全网价值大于性能损失 |
| **高并发写入、批量导入频繁** | ⚠️ 考虑不用，用应用层保证 |
| **分库分表** | ❌ 不用（技术上也不可能有） |
| **跨库** | ❌ 不用 |
| **微服务架构** | ❌ 不用（数据边界就是服务边界） |

⭐ **折中方案**：

```sql
-- 建表时不加外键，但用 CHECK-like 逻辑 + 应用层校验 + 定期巡检
-- 同时在表结构里用 COMMENT 记录关联关系
emp_id BIGINT UNSIGNED NOT NULL COMMENT '员工ID，关联 employees(id)，应用层保证'
```

⚠️ **不用外键就必须自己补上机制**：应用层校验 + 定期巡检孤儿数据：

```sql
-- 孤儿数据巡检（无外键时必做）
SELECT o.* FROM orders o
LEFT JOIN employees e ON o.emp_id = e.id
WHERE e.id IS NULL
LIMIT 100;
```

## 三、外键的性能代价

⚠️ **外键不是免费的**。

### 代价 1：多一次索引查找

```
INSERT INTO orders (emp_id, ...)
  ↓
① 在 orders.emp_id 的索引上插入记录
② ⭐ 拿 emp_id 去 employees 的主键/唯一索引查找
③ 找不到 → ERROR 1452
④ 找到了 → 继续
```

⚠️ **每次插入和更新外键列都要做第 ② 步。** 批量导入时这个开销是显著的。

### 代价 2：加锁

⚠️ **子表的写操作会锁住父表的相关行**（共享锁，取决于隔离级别和操作类型）。高并发下这会形成锁竞争。

### 代价 3：死锁来源

```
事务 A：先锁父表，再锁子表（删除父行 → 级联查子表）
事务 B：先锁子表，再锁父表（插入子行 → 查父表）
→ 循环等待 → 死锁
```

⚠️ **规范做法：所有涉及父子表的事务，操作顺序保持一致。**

📌 死锁排查见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

### 代价 4：⚠️ 外键列不会自动建索引

⚠️ **这是最容易被忽略的性能陷阱。**

```sql
CREATE TABLE orders (
  emp_id BIGINT UNSIGNED NOT NULL,
  CONSTRAINT fk_emp FOREIGN KEY (emp_id) REFERENCES employees(id)
);
-- ⚠️ MySQL 会自动为 emp_id 建索引吗？
-- ❌ 不会！MySQL 8.0 不会自动建（PostgreSQL 会）
```

⚠️ **后果**：查询 `WHERE emp_id = ?` 全表扫描。

⚠️ **⚠️ 对比：PostgreSQL 会自动为外键列建索引，MySQL 不会。** 这是从 PG 迁过来必踩的坑（见 [[mysql/01-入门阶段-基础教程/第00章-学前准备/0.3-MySQL与PostgreSQL的差异]]）。

```sql
-- 手动补
ALTER TABLE orders ADD KEY idx_emp (emp_id);
```

📌 验证：

```sql
SHOW INDEX FROM orders\G
-- 看有没有 emp_id 的索引
```

## 四、约束冲突的处理

### 三种插入策略

```sql
-- ① 冲突就更新（最常用）
INSERT INTO users (id, name, email) VALUES (1, '张三', 'a@b.com')
  AS new ON DUPLICATE KEY UPDATE
    name = new.name,
    updated_at = CURRENT_TIMESTAMP;

-- ② 冲突就忽略
INSERT IGNORE INTO users (id, name, email) VALUES (1, '张三', 'a@b.com');

-- ③ 冲突就替换（⚠️ 危险）
REPLACE INTO users (id, name, email) VALUES (1, '张三', 'a@b.com');
```

### ⚠️ `REPLACE` 的危险

⚠️ **`REPLACE` 不是「更新」，它是「删除 + 插入」。**

```sql
-- 假设 users 有这些列
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(64),
  email VARCHAR(255),
  bio TEXT,
  created_at DATETIME
);

-- 只想改 name
REPLACE INTO users (id, name) VALUES (1, '新名字');
-- ⚠️ email 变成默认值、bio 变成 NULL、created_at 变了！
```

**其他风险**：

| 风险 | 说明 |
|------|------|
| ⚠️ **未指定的列被重置** | 上面的例子 |
| ⚠️ **`AUTO_INCREMENT` 会跳号** | 删除时 ID 就被消耗了 |
| ⚭� **`ON DELETE CASCADE` 会被触发** | ⚠️ 删父行 → 级联删子行 → 不可预期 |
| ⚠️ **主从复制中断风险** | 某些配置下 `REPLACE` 在基于语句的复制中会出问题 |

⭐ **规范：用 `INSERT ... ON DUPLICATE KEY UPDATE`，不用 `REPLACE`。**

📌 详见 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.1-INSERT与REPLACE]]。

### `ON DUPLICATE KEY UPDATE` 的三段式写法

```sql
-- ① 只在插入时给默认值
INSERT INTO counters (id, cnt) VALUES (1, 1)
  ON DUPLICATE KEY UPDATE cnt = cnt + 1;

-- ② 冲突时用函数计算（比「读出来再算再写」快且原子）
INSERT INTO inventory (sku, qty) VALUES ('SKU001', 1)
  ON DUPLICATE KEY UPDATE qty = qty + 1;

-- ③ ⚠️ 只在值真的变化时才更新（避免无谓的更新时间和 binlog）
INSERT INTO users (id, name, updated_at) VALUES (1, '张三', NOW())
  AS new ON DUPLICATE KEY UPDATE
    name = new.name,
    updated_at = IF(name <> new.name, CURRENT_TIMESTAMP, updated_at);
```

⚠️ **第 ③ 条很重要**：无条件 `ON DUPLICATE KEY UPDATE` 会导致每次调用都产生一次 UPDATE，写 binlog、更新时间戳、触发器，甚至影响缓存失效。⚠️ **判断是否真变了再更新，能减少大量无谓写入。**

⚠️ **`VALUES(col)` 已在 8.0.20+ 弃用**，新写法：

```sql
INSERT INTO users (id, name) VALUES (1, '张三')
  AS new ON DUPLICATE KEY UPDATE name = new.name;
```

## 五、`CHECK` 与触发器的取舍

| 机制 | 优点 | 缺点 |
|------|------|------|
| **`CHECK`** | 简单、无性能开销、8.0.15+ 真正强制 | 只能检查单行的值，**不能跨行/跨表** |
| **触发器（TRIGGER）** | 跨行、跨表、复杂逻辑 | ⚠️ 隐式执行、⚠️ 难调试、⚠️ 影响复制、⚠️ 可能连锁 |

⚠️ **触发器的四个坑**：

| 坑 | 说明 |
|---|------|
| **隐式执行** | `UPDATE` 时不知道有触发器在跑，出问题难定位 |
| **⚠️ `TRUNCATE` 不触发** | 触发器只对 `DELETE` 生效 |
| **⚠️ 影响复制** | 基于语句的复制可能出错，要用 ROW 格式 |
| **连锁触发** | 触发器里改别的表，那张表又有触发器 → 可能死循环 |

⭐ **建议：能用 `CHECK` 就别用触发器；跨表逻辑放应用层。**

## 六、软删除与唯一约束的冲突 ⚠️

### 问题

需求：「用户名唯一，但软删除后可以被重新使用」

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(64) NOT NULL,
  deleted_at DATETIME NULL,
  UNIQUE KEY uk_username (username)          -- ⚠️ 删除后仍然占用
);
```

**结果**：`zhangsan` 软删除后，新用户仍然不能用这个用户名。

### 方案对比

| 方案 | 做法 | 优劣 |
|------|------|------|
| **A. 联合唯一 + 固定值** | `UNIQUE (username, deleted_at)`，未删除时 `deleted_at` 设成一个固定值（如 0） | ⚠️ 仍不行——`NULL` 不参与唯一性判断 |
| **B. 联合唯一 + 标记位** | 加 `is_deleted TINYINT`，`UNIQUE (username, is_deleted)` | ❌ **删除两次同名就冲突**（两行 `(zhangsan,1)`） |
| **C. 改用户名** | 删除时把 `username` 改成 `zhangsan__deleted__12345` | ✅ 简单有效；⚠️ 丢失原名 |
| **D. 应用层保证** | 数据库不加唯一约束，查重 + 插入放一个事务里 | ✅ 灵活；⚠️ 并发下要靠锁或唯一约束兜底 |
| **E. 部分索引** | PostgreSQL 支持 `UNIQUE (username) WHERE deleted_at IS NULL` | ⭐ **MySQL 不支持** |

⭐ **MySQL 场景的推荐做法**：

```sql
-- 用一个 deleted_flag 配合「不删除只标记」的方案
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(64) NOT NULL,
  deleted_at DATETIME NOT NULL DEFAULT '1970-01-01 00:00:00',  -- ⭐ 不用 NULL
  UNIQUE KEY uk_username (username, deleted_at)
);

-- 软删除：把 deleted_at 设为真实时间，天然避开唯一约束
UPDATE users SET deleted_at = NOW() WHERE id = 1;
-- 唯一键变成 ('zhangsan', '2026-10-13 10:00:00')

-- ⚠️ 同一个用户秒删两次会冲突（同一秒内删除两次）
-- 实际中可接受，或用更精确的时间
```

📌 软删除的整体设计见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.3-表设计规范与反范式]]。

## 七、陷阱

1. **❌ 以为外键列会自动建索引。** ⚠️ **MySQL 不会，PostgreSQL 会。** 必须手动加。
2. **❌ 盲目用 `ON DELETE CASCADE`。** 删一条可能连带删一大片，且事先不可知。
3. **❌ 用 `REPLACE` 当更新。** 它是「删除+插入」，未指定列被重置。
4. **❌ 依赖 `CHECK` 约束（8.0.15 以下）。** 解析但不执行。
5. **❌ 给已有数据的表加 `CHECK`。** 会因存量违规数据报错。
6. **❌ 用带 `NULL` 的列做唯一约束还指望「只能有一个 NULL」。** 允许多个 NULL。
7. **❌ 以为 MySQL 支持部分索引。** 不支持（PG 支持）。
8. **❌ 忘了 `TRUNCATE` 会被外键挡住。** 报 `ERROR 1701`。
9. **❌ `ON DUPLICATE KEY UPDATE` 无条件更新所有字段。** 产生无谓写入和 binlog。

## 小结

- 五类约束：主键 / 唯一 / 外键 / CHECK / NOT NULL
- **InnoDB 的主键就是聚簇索引**——主键要「短且有序」，`BIGINT AUTO_INCREMENT` 最优，UUID 最差
- **⚠️ 外键的核心取舍**：完整性保证 vs 锁开销、级联风险、分库分表失效
  - 单体小数据 → **用**
  - 高并发 / 分库分表 / 微服务 → **不用**（但要补巡检）
- **⚠️⚠️ 外键列不会自动建索引**（与 PG 相反），必须手动加
- **⚠️ `REPLACE` 是「删除+插入」不是「更新」**，用 `ON DUPLICATE KEY UPDATE`
- `ON DUPLICATE KEY UPDATE` 建议加「值真变了才更新」的判断，减少无谓 binlog
- `CHECK` 在 8.0.15+ 才真正执行，且**不检查已有数据**
- 软删除 + 唯一约束的冲突：用 `NOT NULL DEFAULT '1970-01-01'` 而不是 `NULL`
