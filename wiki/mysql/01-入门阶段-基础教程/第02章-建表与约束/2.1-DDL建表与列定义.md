## 一、生产级建表模板

⭐ **把这一段当模板背下来，所有表都这么写。**

```sql
CREATE TABLE employees (
  -- ========== 主键 ==========
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  
  -- ========== 业务字段 ==========
  dept_id  TINYINT UNSIGNED NOT NULL COMMENT '部门ID',
  name     VARCHAR(64)     NOT NULL COMMENT '姓名',
  email    VARCHAR(255)    NOT NULL COMMENT '邮箱',
  phone    VARCHAR(20)         NULL COMMENT '手机号',
  salary   DECIMAL(10,2)   NOT NULL DEFAULT 0.00 COMMENT '月薪',
  status   TINYINT         NOT NULL DEFAULT 1 COMMENT '状态：0离职 1在职',
  hired_at DATE            NOT NULL COMMENT '入职日期',
  deleted_at DATETIME          NULL COMMENT '软删除时间',
  
  -- ========== 时间戳 ==========
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                            ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  
  -- ========== 约束 ==========
  PRIMARY KEY (id),
  UNIQUE KEY uk_email (email),
  KEY idx_dept_hired (dept_id, hired_at),
  CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) REFERENCES departments(id)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='员工表';
```

### 模板里的每一条都有理由

| 写法 | 为什么 |
|------|--------|
| `BIGINT UNSIGNED` 主键 | 容量大，且与外键类型一致 |
| **字段和约束之间空一行分组** | 可读性 |
| 每个字段带 `COMMENT` | ⭐ 半年后你自己会感谢 |
| 表带 `COMMENT` | 同上 |
| `NOT NULL` 明确标注 | 不用依赖默认值推断 |
| `DEFAULT 0.00` 而不是 `DEFAULT 0` | ⭐ `DECIMAL` 的 0 和 0.00 在比较时不等价（视觉上） |
| `KEY idx_...` 命名有含义 | 排查慢查询时能看懂索引干什么的 |
| `ENGINE=InnoDB` 显式写 | 不依赖服务器默认值 |
| `COLLATE` 显式写 | 见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.6-字符集排序规则]] |

## 二、列定义的取舍

### `NOT NULL` vs `NULL`

⚠️ **一个关键点：「没写 NOT NULL」不等于「可以为 NULL」——取决于有没有默认值。**

| 写法 | 隐式默认值 | 能否省略 |
|------|-----------|---------|
| `name VARCHAR(64)` | **NULL** | ✅ 可以 |
| `name VARCHAR(64) NOT NULL` | 无 | ❌ 不可以（严格模式报错） |
| `name VARCHAR(64) DEFAULT ''` | `''` | ✅ 可以 |
| `name VARCHAR(64) NOT NULL DEFAULT ''` | `''` | ❌ 不可以 |
| `name VARCHAR(64) DEFAULT NULL` | NULL | ✅ 可以（显式） |

⚠️ **`VARCHAR` 和 `TEXT` 的默认值规则**：

```sql
-- ✅ 8.0.13+ 支持表达式默认值
CREATE TABLE t (name VARCHAR(64) DEFAULT '未知');
CREATE TABLE t (body TEXT DEFAULT (JSON_OBJECT()));   -- ⚠️ 表达式要加括号

-- ❌ 8.0.13 之前：TEXT/BLOB/JSON 不能有默认值
-- ❌ JSON 列至今不能有普通默认值
CREATE TABLE t (attrs JSON DEFAULT '{}');   -- 报错
```

### 默认值的三个陷阱

#### 陷阱 1：`TEXT` 不能有普通默认值

```sql
CREATE TABLE t (
  a VARCHAR(20) DEFAULT 'x',    -- ✅
  b TEXT DEFAULT 'x'            -- ❌ ERROR 1101
);
```

⚠️ **`TEXT` 想要默认值就用表达式括号**：`TEXT DEFAULT ('x')`。

#### 陷阱 2：默认值里用函数要加括号

```sql
-- ❌ 报错
CREATE TABLE t (a TIMESTAMP DEFAULT NOW());
-- ✅ 正确
CREATE TABLE t (a TIMESTAMP DEFAULT (NOW()));
```

#### 陷阱 3：默认值不是「写入时求值一次」

```sql
CREATE TABLE t (
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

⚠️ **这个默认值在每次 INSERT 时求值，不是建表时算一次存进去。** 所以它能正确记录每一行的创建时间。

### `UNSIGNED` 的取舍

| 好处 | 坏处 |
|------|------|
| 范围大一倍（0 ~ 2^64-1） | ⚠️ **无符号溢出不报错，静默变成巨大数** |
| 表达「天然非负」语义 | 计算中间值可能为负 |

⚠️ **无符号溢出的坑**：

```sql
CREATE TABLE t (n INT UNSIGNED);
INSERT INTO t VALUES (0);
SELECT n - 1 FROM t;   -- ⚠️ 结果是 18446744073709551615，不是 -1，不报错！
```

⭐ **规范建议**：主键/ID 用 `UNSIGNED`（语义上不可能为负），业务数值看情况——如果有减法运算（比如余额、库存），⚠️ **`UNSIGNED` 会让「减成负数」变成天文数字**，非常危险。

## 三、索引定义

### 索引命名规范

| 类型 | 命名 | 例 |
|------|------|-----|
| 主键 | `PRIMARY` | |
| 唯一索引 | `uk_`（unique key） | `uk_email` |
| 普通索引 | `idx_` | `idx_dept_hired` |
| 全文索引 | `ft_`（fulltext） | `ft_content` |
| 空间索引 | `sp_`（spatial） | `sp_geo` |

⭐ **命名不是形式主义**：排查慢查询时看 `SHOW INDEX` 能立刻知道这个索引是为哪个查询建的。

### 索引顺序的考量

```sql
KEY idx_dept_hired (dept_id, hired_at)
```

⚠️ **列顺序决定索引能用在哪**（最左前缀原则，详见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引类型与选型]]）：

| 查询条件 | 能用这个索引吗 |
|---------|--------------|
| `WHERE dept_id = 3` | ✅ 用了第一列 |
| `WHERE dept_id = 3 AND hired_at = '2026-01-01'` | ✅ 用了两列 |
| `WHERE hired_at = '2026-01-01'` | ❌ **跳过了第一列，用不上** |
| `WHERE dept_id = 3 ORDER BY hired_at` | ✅ 还能用于排序 |

### 冗余索引的判断

⚠️ **联合索引 `(a, b, c)` 能覆盖单独的 `(a)`，所以 `(a)` 是冗余的。**

```sql
KEY idx_a_b_c (a, b, c)    -- ✅ 有这个就够
KEY idx_a (a)              -- ❌ 冗余，白占空间和写入代价
```

⚠️ **但 `(a, b)` 不是 `(b, a)` 的替代**——顺序反了，用不上。

📌 冗余索引检测见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

## 四、`ALTER TABLE` 的代价 ⚠️

### 操作与锁表行为

⚠️ **MySQL 8.0 大部分 `ALTER` 支持「ALGORITHM=INPLACE, LOCK=NONE」**（不阻塞读写），但**不是全部**。这张表是排查线上 DDL 卡死的依据。

| 操作 | 算法 | 是否阻塞写 | 代价 |
|------|------|-----------|------|
| 加列（末尾，有默认值） | INPLACE | ❌ 否 | 低 |
| 加列（中间位置） | INPLACE | ❌ 否 | 中（要重排行） |
| 删列 | INPLACE | ❌ 否 | 中 |
| 改列类型（**扩大**） | INPLACE | ❌ 否 | ⚠️ **有损转换不能 INPLACE** |
| 改列类型（**缩小**） | INPLACE | ❌ 否 | ⚠️ 可能数据丢失 |
| 加索引 | INPLACE | ❌ 否 | 中（⚠️ 会占大量 IO） |
| 删索引 | INPLACE | ❌ 否 | 低 |
| 改字符集 | INPLACE | ❌ 否 | ⚠️ **重建整表，最高** |
| 改引擎 | COPY | ✅ **是** | ⚠️ 极高 |
| 改表名 | INPLACE | ❌ 否 | 低 |

⚠️ **「不阻塞写」不等于「不慢」**。`INPLACE` 期间会持续占用 IO 和 CPU，可能把线上服务拖慢——生产大表改表要在低峰期做，并监控。

### 显式指定算法

```sql
-- 检查 MySQL 认为哪种算法可行
EXPLAIN ALTER TABLE employees ADD COLUMN nickname VARCHAR(32) NULL;
-- 输出：inplace / copy

-- 显式指定，不可行就报错（避免意外降级到 COPY）
ALTER TABLE employees ADD COLUMN nickname VARCHAR(32) NULL,
  ALGORITHM=INPLACE, LOCK=NONE;
```

⚠️ **加上 `ALGORITHM=INPLACE, LOCK=NONE` 的好处**：MySQL 发现做不到时会直接报错，而不是悄悄用 COPY 锁表。

📌 **大表改表方案对比（`pt-osc` / `gh-ost` / MySQL 8.0 原生 INSTANT）见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。**

### 8.0 的 INSTANT 算法

⚠️ **8.0.12+ 加列支持 `ALGORITHM=INSTANT`，几乎瞬间完成。**

```sql
ALTER TABLE employees ADD COLUMN nickname VARCHAR(32) NULL, ALGORITHM=INSTANT;
```

⚠️ **限制**（8.0 时期）：只支持「加列」「加列末尾有默认值」「改列名」「加/删虚拟列」等有限操作；⚠️ **加列位置必须在最后**（有默认值的只能紧跟在 AUTO_INCREMENT 列后）。

### `pt-online-schema-change` 与 `gh-ost`

⚠️ **千万行以上的表，原生 `ALTER` 不管多「INPLACE」都很慢。** 这时用第三方工具：

| 工具 | 机制 | 特点 |
|------|------|------|
| **`pt-online-schema-change`** | 建影子表 → 触发器同步 → 原子改名 | 成熟稳定；⚠️ 有触发器开销和短暂锁 |
| **`gh-ost`** | 建影子表 → **binlog 同步** → 原子改名 | ⭐ 无触发器，对主库压力小；⚠️ 需要 binlog ROW 格式 |

📌 见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。

## 五、`CREATE` vs `ALTER` vs `RENAME`

```sql
-- 建表
CREATE TABLE t_new (...) ENGINE=InnoDB;      -- 用新结构建

-- 改表
ALTER TABLE t ADD COLUMN c INT, ALGORITHM=INSTANT;

-- 换引擎（⚠️ 极高代价，会阻塞写）
ALTER TABLE t ENGINE=MyISAM;

-- 改表名
RENAME TABLE t TO t_old, t_new TO t;         -- ⭐ 原子操作，多表互换推荐
```

⚠️ **`RENAME TABLE` 是原子的**，所以「建新表 → 导数据 → 改名」是零停机迁移表结构的标准套路：

```sql
-- 零停机换表结构
CREATE TABLE t_new LIKE t;
ALTER TABLE t_new ADD COLUMN c INT, ALGORITHM=INSTANT;
INSERT INTO t_new SELECT * FROM t;
RENAME TABLE t TO t_old, t_new TO t;    -- ⚠️ 原子，瞬间完成
DROP TABLE t_old;
```

⚠️ **⚠️ 但要注意**：切换瞬间，正在执行的查询会短暂阻塞（要获取 MDL 锁）；且**如果切换后代码不兼容新结构，会有问题**。

📌 MDL 锁的机制见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

## 六、生成列与函数索引

### 场景一：给表达式建索引

```sql
-- 需求：按 email 的小写查重
CREATE TABLE users (
  email VARCHAR(255) NOT NULL,
  email_lower VARCHAR(255)
    GENERATED ALWAYS AS (LOWER(email)) STORED,
  UNIQUE KEY uk_email_lower (email_lower)      -- ⭐ 给表达式建了索引
);

-- 现在可以走索引
SELECT * FROM users WHERE email_lower = 'a@b.com';
```

⚠️ **8.0.13+ 也可以用函数索引（更轻量，不占额外列空间）**：

```sql
CREATE TABLE users (
  email VARCHAR(255) NOT NULL,
  KEY idx_email_lower ((LOWER(email)))     -- ⭐ 双括号 = 函数索引
);
```

📌 见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引类型与选型]]。

### 场景二：间接索引 JSON

```sql
CREATE TABLE products (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  attrs JSON,
  color VARCHAR(20)
    GENERATED ALWAYS AS (attrs->>'$.color') STORED,   -- ⭐
  KEY idx_color (color)
);
```

⚠️ **原生 JSON 列不能建索引，这是唯一的绕过办法。**

### 场景三：冗余派生列

```sql
CREATE TABLE orders (
  unit_price DECIMAL(10,2) NOT NULL,
  quantity   INT NOT NULL,
  total      DECIMAL(12,2)
    GENERATED ALWAYS AS (unit_price * quantity) STORED
);
```

⚠️ **⚠️ 冗余列有维护代价**：如果业务规则变了（比如「满 100 减 10」），生成列的公式也要改（改公式 = 重建表）。

## 七、`CREATE TABLE ... AS SELECT` 的陷阱

```sql
-- ⚠️ 看起来方便，实际有坑
CREATE TABLE t_backup AS SELECT * FROM t;
```

| 坑 | 说明 |
|---|------|
| **不复制索引** | ⚠️ 备份表没有主键和索引 |
| **不复制默认值** | 只带值不带定义 |
| **不复制字符集/collation** | 继承数据库默认，可能不一致 |
| **不复制外键** | |
| **不复制生成列定义** | ⚠️ 生成列的值会变成普通列 |

⭐ **正确的做法**：

```sql
CREATE TABLE t_backup LIKE t;                    -- 只复制结构（含索引）
INSERT INTO t_backup SELECT * FROM t;            -- 导数据
```

⚠️ **`CREATE TABLE ... LIKE` 不复制外键约束**（MySQL 行为），但会复制索引、默认值、字符集、引擎。

## 八、陷阱

1. **❌ 省略 `ENGINE=InnoDB`。** 依赖服务器默认值不安全。
2. **❌ 省略 `CHARSET` / `COLLATE`。** 会因上层设置不一致而埋雷。
3. **❌ 字段不带 `COMMENT`。** 半年后没人知道字段什么意思。
4. **❌ 给 `TEXT` 设普通默认值。** 要用表达式括号。
5. **❌ JSON 列设默认值。** 不允许。
6. **❌ 用 `UNSIGNED` 存可能减成负数的值。** 溢出静默变天文数字。
7. **❌ 大表直接 `ALTER`。** 先 `EXPLAIN ALTER` 看算法，考虑 `pt-osc` / `gh-ost`。
8. **❌ 不加 `ALGORITHM=INPLACE, LOCK=NONE`。** MySQL 可能悄悄降级到 COPY 锁表。
9. **❌ 用 `CREATE TABLE ... AS SELECT` 做备份。** 丢索引、丢约束。用 `LIKE` + `INSERT`。
10. **❌ 建冗余的单列索引。** 联合索引已覆盖。
11. **❌ 字段名用保留字不加反引号。**

## 小段

- **生产建表模板**：`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='...'` + 每字段 `COMMENT`
- 「没写 NOT NULL」**不等于**「可为 NULL」——取决于有没有默认值
- `TEXT` 默认值要用 `TEXT DEFAULT ('x')`（8.0.13+）；JSON 列至今不能有普通默认值
- ⚠️ **`UNSIGNED` 的溢出坑**：`0 - 1` 在无符号列上得到天文数字，不报错
- 索引命名：`uk_` / `idx_` / `ft_` / `sp_`——**不是形式主义，是排查慢查询时的线索**
- ⚠️ **`ALTER` 一定要加 `ALGORITHM=INPLACE, LOCK=NONE`**，否则可能悄悄降级成 COPY 锁表
- 8.0.12+ 的 `INSTANT` 算法让「加列」几乎瞬间完成
- 零停机换表结构：`CREATE TABLE ... LIKE` → `INSERT` → **`RENAME TABLE`（原子）**
- ⚠️ **⚠️ `CREATE TABLE ... AS SELECT` 做备份会丢索引/默认值/生成列定义**，必须用 `LIKE` + `INSERT`
