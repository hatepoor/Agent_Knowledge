# MySQL 与 PostgreSQL 的差异

读完本篇，你应当能够：

1. 说出两者的**根本架构差异**（MVCC 实现方式）

3. 说出「照搬 PG 经验会踩的五个典型坑」
4. 知道自己该选哪个，以及判断依据
5. 迁移时知道哪些地方不能靠 sed 替换

## 一、先说根本差异：MVCC 实现方式

⚠️ **这是最本质的区别，也是理解其他所有行为差异的钥匙。**

| 维度 | PostgreSQL | MySQL InnoDB |
|------|------------|--------------|
| **MVCC 方式** | **追加式（append-only）** | **undo log 式** |
| **新版本放哪** | 新行直接写在表末尾的**新页**上 | 旧版本信息写在 **undo log** 里 |
| **老数据怎么清** | VACUUM 回收不再需要的行 | purge 线程顺着 undo 链清理 |
| **长事务后果** | 表膨胀，VACUUM 跑不动 | undo 表膨胀，purge 卡住 |

**用类比理解：**

```
PostgreSQL（追加式）：
  表文件：[版本A][版本B][版本C][版本D]  ← 新版本都在后面
  更新一行 → 在末尾追加新版本
  VACUUM → 把没人要的老版本标记为可复用空间

MySQL（undo 式）：
  表文件：[版本D]                     ← 表里只有最新版本
  undo log：[版本D→C→B→A 的还原信息]  ← 老版本在 undo 里
  读老版本 → 顺着 undo 链往回找
```

**这个差异导致的行为区别**：

| 场景 | PostgreSQL | MySQL |
|------|-----------|-------|
| 一次热更新产生 100 万行变更 | 表膨胀 100 万行 | 表不变大，但 undo log 涨 100 万条 |
| 「空间回收」 | ⚠️ 必须 `VACUUM` | purge 线程自动做，但长事务会卡住它 |
| 「表持续变大」 | 常见现象 | 正常情况下不会 |

📌 深入对照见 [[postgresql/03-进阶阶段-深度剖析/事务与MVCC内核/原理剖析-MVCC与快照隔离]] 与 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-undo日志与MVCC]]。

## 二、语法对照速查

⭐ **这张表是本篇最实用的部分。** 速查版见 [[mysql/速查索引]] 第六节。

### 自增主键

```sql
-- MySQL
CREATE TABLE users (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  PRIMARY KEY (id)
);

-- PostgreSQL
CREATE TABLE users (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);
-- 或用序列（PG 特有）
CREATE TABLE users (
  id BIGSERIAL PRIMARY KEY
);
```

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| 关键字 | `AUTO_INCREMENT` | `IDENTITY` / `SERIAL` / `SERIAL4` / `SERIAL8` |
| 独立序列对象 | ❌ 没有 | ✅ 有 `SEQUENCE`，可被多表共享 |
| 重启后 ID 连续性 | `innodb_autoinc_lock_mode=1`（连续）时重启会回退 | 序列默认**不连续**（缓存预分配） |

⚠️ **PG 的序列默认即使事务回滚也不回收 ID**，所以 PG 的 ID 会有「空洞」，这是特性不是 bug。MySQL 的 `AUTO_INCREMENT` 在传统模式（`innodb_autoinc_lock_mode=2`，MySQL 8.0 默认）下也有空洞——因为并发插入时会「先分配后使用」。

⚠️ **InnoDB 的自增锁**：8.0 之前并发插入自增列会有争用（`innodb_autoinc_lock_mode` 默认 0 = 表级自增锁），8.0 默认改成 2（交叉模式），性能大幅改善。这是「用 MySQL 就该用 8.0」的一个典型理由。

### 分页

```sql
-- MySQL：跳过 10 行，取 5 行
SELECT * FROM users LIMIT 10, 5;

-- PostgreSQL：取 5 行，跳过 10 行
SELECT * FROM users LIMIT 5 OFFSET 10;
```

⚠️ **这是最容易搞混的地方。** MySQL 的 `LIMIT n, m` 里，**n 在前表示跳过的行数**。很多人以为 `LIMIT 10, 5` 是「取 10 行跳过 5 行」——错。

### 标识符引用

```sql
-- MySQL：反引号
SELECT `order`, `group` FROM `select`;

-- PostgreSQL：双引号
SELECT "order", "group" FROM "select";
```

⚠️ **PG 里双引号是标识符，单引号是字符串——MySQL 完全相反**（默认模式下）。这是从 MySQL 迁到 PG 最容易出事的点。

### 真 UTF-8 与字符集

```sql
-- MySQL：必须显式指定 utf8mb4
CREATE DATABASE app DEFAULT CHARACTER SET utf8mb4;
-- ⚠️ MySQL 的 utf8 实际是 utf8mb3（最多 3 字节），存不了 emoji（4 字节）

-- PostgreSQL：默认就是 UTF-8
CREATE DATABASE app;    -- 不需要指定
```

| 库 | 默认字符集 | 坑 |
|----|-----------|-----|
| MySQL | 取决于系统版本，**老版本默认 latin1** | 一定要显式 `utf8mb4` |
| PostgreSQL | `UTF8`（真 UTF-8） | 无 |

⭐ **MySQL 存量库里可能还有 latin1 或 utf8mb3 的表**，这是迁移到 PG 时的常见编码问题。

### JSON 类型

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| 类型 | `JSON` 一个类型 | `json`（文本存储）+ `jsonb`（二进制）**两个** |
| 性能 | 二进制存储，查询快 | `jsonb` 更快且支持索引；`json` 保留原始格式便于展示 |
| 操作符 | `->` `->>` 函数 | `->` `->>` `#>` 运算符 |
| 提取函数 | `JSON_EXTRACT(doc, '$.a')` | `doc->'a'` / `doc->>'a'` |
| 展开成行 | `JSON_TABLE()`（8.0.4+） | `jsonb_array_elements()` / `jsonb_to_recordset()` |

⚠️ **MySQL 的 `->>` 不带引号、`->` 带引号**（和 PG 一致）。但 MySQL 没有 `#>`, `#>>` 这类路径运算符。

### 日期时间

| 需求 | MySQL | PostgreSQL |
|------|-------|-----------|
| 当前时间 | `NOW()` / `CURRENT_TIMESTAMP` | `NOW()` / `CURRENT_TIMESTAMP`（基本一致） |
| 日期相减得天数 | `DATEDIFF(d1, d2)` | `d1 - d2` 直接得 interval |
| 格式化 | `DATE_FORMAT(d, '%Y-%m-%d')` | `TO_CHAR(d, 'YYYY-MM-DD')` |
| 截取到秒/毫秒 | `DATE_FORMAT(d, '%H:%i:%s')` | `date_trunc('day', d)` |
| 加时间间隔 | `d + INTERVAL '1 day'` | 同（两边语法接近） |
| 时间戳 | `UNIX_TIMESTAMP(d)` / `FROM_UNIXTIME(ts)` | `EXTRACT(EPOCH FROM d)` |

⚠️ **`DATE_FORMAT` 和 `TO_CHAR` 的格式符完全不同**（`%Y` vs `YYYY`），不能照搬。

### 类型对照

| 语义 | MySQL | PostgreSQL | 注意 |
|------|-------|-----------|------|
| 布尔 | `TINYINT(1)` 或 `BOOLEAN` | 原生 `BOOLEAN` | MySQL 的 `BOOLEAN` 是 `TINYINT(1)` 的别名 |
| 整数 | `INT` / `BIGINT` | `INTEGER` / `BIGINT` | |
| 浮点 | `FLOAT` / `DOUBLE` | `REAL` / `DOUBLE PRECISION` | |
| 精确小数 | `DECIMAL(p,s)` | `NUMERIC(p,s)` | 同 |
| 长文本 | `LONGTEXT`（最大 4GB） | `TEXT` | ⚠️ PG 的 `TEXT` 就是无限长，不需分类型 |
| 二进制 | `VARBINARY(n)` / `BLOB` | `BYTEA` | |
| 数组 | ❌ **无原生数组** | `type[]` | PG 独有 |
| 枚举 | `ENUM('a','b')` | 用 `CREATE TYPE ... AS ENUM` 或 CHECK | PG 需要单独建类型 |
| UUID | `CHAR(36)` 或 `BINARY(16)` | `UUID` 类型 | PG 有原生类型 |
| 范围 | ❌ 无 | `int4range` 等原生 | |
| 网络地址 | `INET_ATON()` 函数 | `INET` 类型 | PG 独有 |
| 时区时间戳 | `TIMESTAMP`（⚠️ 不带时区） | `TIMESTAMPTZ`（带时区） | ⚠️ 见下 |

⚠️ **时区语义是重大差异**：

| | MySQL | PostgreSQL |
|---|--------|-----------|
| `TIMESTAMP` | ⚠️ **不存时区**，`SET time_zone` 只影响转换时的解释 | — |
| 带时区类型 | `TIMESTAMP` 配合连接时区，实际行为类似 | `TIMESTAMPTZ`（推荐），内部存 UTC 瞬时 |
| 建议 | 生产统一设置 `time_zone`，明确存的是哪个时区 | 用 `TIMESTAMPTZ` |

📌 详见 [[postgresql/01-入门阶段-基础教程/第02章-数据类型/2.3-日期时间类型]]。

### 大小写敏感

| 库 | 表名 | 标识符 |
|----|------|--------|
| MySQL | Linux 敏感 / Windows 不敏感（⚠️ 跨平台不一致） | — |
| PostgreSQL | **永远不敏感**（自动转小写） | 敏感，要用双引号保留大小写 |

⚠️ **MySQL 的跨平台不一致是最坑的**：本地 Windows 上 `Users` 和 `users` 都能用，部署到 Linux 上其中一个就报表不存在。

⭐ **规范建议（MySQL）**：所有表名列名统一小写 + 下划线，避免全部问题。

## 三、行为差异（不只是语法）

⚠️ **语法能查文档对照，行为差异只能靠踩坑。这里是最容易翻车的部分。**

| 维度 | MySQL | PostgreSQL |
|------|-------|-----------|
| **GROUP BY 严格性** | 宽松（可关 `ONLY_FULL_GROUP_BY`），SELECT 非聚合列可选任意值 | **严格**，SELECT 的非聚合列必须在 GROUP BY 里 |
| **NULL 排序** | `NULL` 排在**最前** | `NULL` 默认排在**最后**（`NULLS LAST`） |
| **字符串比较** | 默认**不区分大小写**（取决于 collation） | **区分大小写** |
| **LIKE 大小写** | 默认不敏感 | 敏感，需要 `ILIKE` |
| **类型转换宽松度** | 非常宽松（⚠️ 这是优势也是陷阱） | 严格 |
| **除零** | 返回 NULL（除非开了 `ERROR_FOR_DIVISION_BY_ZERO`） | **报错** |
| **隐式索引创建** | 对外键列**不会**自动建索引 | **会**自动建索引 |
| **NOT IN 与 NULL** | ⚠️ 遇到 NULL 全返回 NULL | 同（两个库都有这个陷阱） |
| **空字符串与 NULL** | ⚠️ **两者不等**，Oracle 兼容模式才当 NULL | 严格区分 |

⭐ **「NULL 排序位置」这个差异极容易埋 bug**：

```sql
-- 需求：取最近 10 条
SELECT * FROM users ORDER BY created_at DESC LIMIT 10;
```
如果 `created_at` 有 NULL 值，两个库返回的「最近」记录不同——MySQL 的 NULL 会排在最前（`DESC` 时），所以你可能拿到一批 NULL 时间的记录。**正确写法**：

```sql
SELECT * FROM users WHERE created_at IS NOT NULL ORDER BY created_at DESC LIMIT 10;
-- 或者显式指定
SELECT * FROM users ORDER BY created_at DESC NULLS LAST LIMIT 10;   -- PG 语法，MySQL 8.0 不支持 NULLS LAST
```

### Oracle 兼容模式

MySQL 有 `sql_mode` 可以切换到 Oracle 兼容行为（`NO_UNSIGNED_SUBTRACTION`、`ONLY_FULL_GROUP_BY` 等）。⚠️ **老项目为了兼容 Oracle 会开启这些**，新项目**不要开**——直接按 MySQL 原生行为开发更清爽。

## 四、照搬 PG 经验会踩的五个坑

按踩坑频率排序。

### 坑 1：`LIMIT n, m` 语义搞反

```sql
-- PG 写法：取 5 行，跳过 10 行
LIMIT 5 OFFSET 10

-- 直译到 MySQL 会写成：
LIMIT 5, 10      -- ❌ 这是「跳过 5，取 10」！
LIMIT 10, 5      -- ✅ 这才是「跳过 10，取 5」
```

### 坑 2：字符串用双引号

```sql
-- PG 正确
WHERE name = '张三'

-- 从 PG 迁移时手滑写成（MySQL 默认模式下也能跑，但在 PG 里会当标识符）
WHERE name = "张三"    -- ❌
```

⚠️ 更隐蔽的情况：`"users"` 在 PG 里是表名，在 MySQL 里是字符串 `'users'`。**一行代码两库含义完全不同。**

### 坑 3：以为 `utf8` 就是 UTF-8

```sql
-- MySQL
CREATE TABLE t (name VARCHAR(50) CHARACTER SET utf8);   -- ❌ utf8mb3
INSERT INTO t VALUES ('😀');   -- 报错：Incorrect string value
```

⭐ 这是 MySQL 独有的坑。**任何时候都写 `utf8mb4`。**

### 坑 4：忘了 PG 默认更严格

| 场景 | PG 会怎样 | MySQL 会怎样 |
|------|----------|--------------|
| `SELECT a, COUNT(*) FROM t GROUP BY b` | ❌ 报错（a 不在 GROUP BY 里） | ⚠️ 能跑，a 取任意值 |
| `1/0` | ❌ 报错 | 返回 NULL |
| `NULL + 1` | ❌ 报错 | 返回 NULL |
| 外键列 | 自动建索引 | 不建索引 |

⚠️ **从 PG 迁到 MySQL 时，代码会「突然能跑」——这些原本被 PG 挡住的错误写法会静默产生错误结果。** 这是最危险的一类迁移问题。

### 坑 5：函数名与行为差异

| 语义 | MySQL | PostgreSQL |
|------|-------|-----------|
| 截取字符串 | `SUBSTR(s, 2, 3)` | `SUBSTRING(s FROM 2 FOR 3)` 或 `SUBSTR(s, 2, 3)` |
| 找子串 | `LOCATE(sub, s)` | `POSITION(sub IN s)` |
| 字符串转数字 | `CAST('123' AS UNSIGNED)` | `CAST('123' AS INTEGER)` 或 `'123'::int` |
| 数组聚合 | `GROUP_CONCAT()` | `string_agg(x, ',')` |
| 分组 | `GROUP BY` | `GROUP BY` + `GROUPING SETS/ROLLUP/CUBE` |
| 开窗 | `ROW_NUMBER() OVER (ORDER BY x)` | 同 |

⚠️ **PG 有 `string_agg` 这个概念，MySQL 用 `GROUP_CONCAT` 实现，但后者有 1024 字节默认截断的坑。**

完整函数清单见 [[mysql/函数手册]]。

## 五、怎么选

| 场景 | 推荐 | 理由 |
|------|------|------|
| LAMP / 传统 Web 后端 | **MySQL** | 生态成熟、运维资料多 |
| 需要复杂查询、报表、分析 | PostgreSQL | 类型系统强、索引更丰富 |
| 需要 JSON 深度操作 | 看场景 | PG 有 `jsonb` + GIN 索引；MySQL 8.0 够用 |
| 需要数组类型 | PostgreSQL | MySQL 无原生数组 |
| 全文检索 | 都不理想 | 都建议上 Elasticsearch（见 [[rag/05_查询转换与改写/查询改写与扩展]]） |
| 国产化替代 / 信创 | **MySQL 及其国产衍生** | 达梦/人大金仓/TiDB/OceanBase 多兼容 MySQL |
| Node.js / Java 生态 | 都行 | 生态都有成熟驱动 |
| 云托管选择多 | PostgreSQL | AWS RDS/Aurora、Azure、阿里云对 PG 支持更激进 |
| 已有技术栈 | 跟随现有 | ⭐ 迁移成本通常大于收益 |

⭐ **最重要的一条：跟随你团队已有的技术栈。** 数据库迁移不是「换个更好的」，是要重写 ORM 层、SQL 语法、数据类型映射、运维工具链。除非有明显收益，否则不值得。

## 六、迁移时不能靠 sed 替换的东西

⚠️ **如果你真要做迁移，下面这些必须人工处理：**

| 项 | 为什么 |
|----|--------|
| **标识符引号** | 双引号 ↔ 反引号，含义还相反 |
| **字符串引号** | PG 单引号 ↔ MySQL 单引号（看似一致，但 `"` 语义不同） |
| **分页语法** | `LIMIT m OFFSET n` ↔ `LIMIT n, m`，顺序不同 |
| **类型映射** | `SERIAL` → `AUTO_INCREMENT`；`TIMESTAMPTZ` → `TIMESTAMP` + 时区设置 |
| **JSON 操作** | `jsonb` → `JSON`，运算符换成函数 |
| **数组字段** | ❌ **MySQL 无对应**，需要拆成子表或用 JSON 存数组 |
| **`GROUP BY` 严格性** | MySQL 宽松会掩盖 PG 下的错误逻辑，**建议先在 MySQL 打开 `ONLY_FULL_GROUP_BY` 跑一遍** |
| **隐式转换** | MySQL 会隐式转换类型，PG 报错。**迁移前把隐式转换显式化** |
| **NULL 排序** | 需要显式加 `WHERE x IS NOT NULL` 或写 CASE |
| **函数名** | 逐个对照 |

⭐ **迁移建议**：先用工具做初版转换（如 `pgloader` 能从 PG 导到 MySQL），但**必须人工 review 所有 SQL**，重点检查上面这十项。

## 七、陷阱

1. **❌ 以为语法相近就能照搬。** 行为差异比语法差异危险得多。
2. **❌ 忘了 `LIMIT n, m` 顺序相反。**
3. **❌ 在 MySQL 里用 `utf8`。** 必须是 `utf8mb4`。
4. **❌ 用双引号包字符串。** 一行代码两库含义不同。
5. **❌ 因为「MySQL 宽松」而放松代码检查。** 原本 PG 挡住的错误会静默产生脏数据。
6. **❌ 以为 MySQL 有数组类型。** 没有，只能用 JSON 或拆子表。
7. **❌ 忽略 NULL 排序差异。** 「取最近 N 条」的结果可能不同。
8. **❌ 只对比语法不对比行为。** 行为差异才是上线后的事故来源。

## 小段

- **根本差异**：PG 追加式 MVCC（新行在表末尾）vs MySQL undo 式（老版本在 undo log）
- `AUTO_INCREMENT` vs `IDENTITY`/`SERIAL`；MySQL 无独立序列
- `LIMIT n, m`（跳过 n 取 m）vs `LIMIT m OFFSET n`——**顺序相反**
- 反引号（MySQL）vs 双引号（PG）；字符串都是单引号
- MySQL 必须 `utf8mb4`；`utf8` 是 utf8mb3，存不了 emoji
- PG 有 `json` + `jsonb`、数组、`bytea`、`inet` 原生类型；MySQL 有 `JSON`、无数组
- **行为差异更危险**：GROUP BY 严格性、NULL 排序、大小写、除零、隐式转换
- **迁移不能靠 sed**：十类必须人工处理，其中数组字段无对应、宽松性掩盖错误最危险
- **选型第一原则：跟随已有技术栈**
