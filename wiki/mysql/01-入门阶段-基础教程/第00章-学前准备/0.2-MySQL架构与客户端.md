## 一、mysqld 的三层架构

MySQL 服务器进程 `mysqld` 内部是分层的。这个分层决定了很多「为什么会出现这个现象」。

```
       客户端 A        客户端 B        客户端 C
          │               │               │
          └───────────────┴───────────────┘
                          │
        ┌─────────────────▼──────────────────┐
        │ ① 连接层（Connection Layer）          │
        │  · 协议解析（经典协议 3306 / X 协议）   │
        │  · 认证与授权                          │
        │  · 连接管理：一个连接 = 一个线程       │
        │  · 连接池（可选，8.0+ 内置）           │
        └─────────────────┬──────────────────┘
                          │
        ┌─────────────────▼──────────────────┐
        │ ② 服务层（Server Layer）              │
        │  · SQL 解析器 → 语法树                │
        │  · 查询优化器 → 执行计划 ★核心        │
        │  · 执行器：调存储引擎、拿结果          │
        │  · 内置函数（日期/字符串/JSON…）       │
        │  · 优化器缓存、触发器、视图            │
        └─────────────────┬──────────────────┘
                          │
        ┌─────────────────▼──────────────────┐
        │ ③ 存储引擎层（Storage Engine）        │
        │  · InnoDB（默认，事务引擎）             │
        │  · MyISAM（旧，无事务）                │
        │  · MEMORY / CSV / Archive 等          │
        │  · 各引擎自己的索引与存储实现 ★        │
        └─────────────────┬──────────────────┘
                          │
                    ┌─────▼─────┐
                    │ 磁盘文件   │
                    └───────────┘
```

### ① 连接层

| 职责 | 说明 |
|------|------|
| **协议解析** | 把网络上来的字节流解析成 SQL 语句 |
| **认证授权** | 验证用户名密码，确认这个连接能访问哪些库 |
| **连接管理** | ⚠️ **经典架构下一个连接对应一个线程**，连接多了线程就多 |
| **端口监听** | 经典协议 3306，X 协议 33060 |

⚠️ **「一个连接一个线程」是理解 MySQL 性能问题的关键。** 1000 个连接 = 1000 个线程，每个线程有独立栈内存。`max_connections` 调太大不是好事——线程数超过了 CPU 能并发的上限，只会增加上下文切换。

> 💡 8.0 引入了**线程池（Thread Pool）插件**，2026 年的 26.7 起进入社区版。它把「一连接一线程」改成「少数线程服务大量连接」，大幅降低上下文切换。这是高并发场景的重要优化手段。

### ② 服务层 ★ 最核心的一层

这一层做四件事，每件都值得记住：

| 步骤 | 做什么 | 关键概念 |
|------|--------|---------|
| **解析** | 文本 SQL → 语法树 | 语法错误在这一步报 |
| **优化** | 语法树 → 执行计划 | ⭐ **MySQL 最核心的组件** |
| **执行** | 按计划调存储引擎 | 存储引擎在这里被调用 |
| **返回** | 汇总结果给客户端 | 边查边返回（流式） |

⚠️ **优化器为什么重要**：你写的 `WHERE` 只是描述了「要什么」，优化器负责决定「怎么拿最快」。它要考虑的变量包括：有哪些索引、每个索引的选择性多高、表的行数是多少、统计信息新不新、内存够不够……

**优化器也会猜错**，猜错就会选到慢计划。诊断手段见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

### ③ 存储引擎层

⭐ **这是 MySQL 最有特色的设计：存储引擎是可插拔的。**

| 含义 | 说明 |
|------|------|
| SQL 层不关心数据怎么存 | 服务层只发「给我 id=5 这行」，InnoDB 怎么找到它它说了算 |
| 各引擎能力不同 | InnoDB 支持事务，MyISAM 不支持；同一个 SQL 在不同引擎下行为可能不同 |
| 表可以指定引擎 | `CREATE TABLE t (...) ENGINE=MyISAM;` |
| 一个实例可以有多个引擎 | 每张表可以选不同引擎 |

**各引擎对比：**

| 引擎 | 事务 | 行锁 | 外键 | MVCC | 建议 |
|------|------|------|------|------|
| **InnoDB** | ✅ | ✅ | ✅ | ✅ | ⭐ **默认，唯一推荐** |
| MyISAM | ❌ | ❌（表锁） | ❌ | ❌ | 只在读极多的老场景用 |
| MEMORY | ❌ | ❌（表锁） | ❌ | ❌ | 临时表，重启丢数据 |
| CSV | ❌ | ❌ | ❌ | ❌ | 导入导出中间态 |
| Archive | ❌ | ✅ | ❌ | ❌ | 归档压缩 |

⚠️ **InnoDB 是默认引擎，且从 MySQL 5.5 起就是默认。** 本知识库所有内容默认讨论 InnoDB。切到 MyISAM 会失去事务、外键、行锁——除非你在维护遗留系统，否则不要。

📌 **为什么 MyISAM / MEMORY 没有事务**（机制 + 架构原因 + 历史），以及其他引擎各自的定位与老库迁移实操：[[mysql/02-中段阶段-专题精讲/存储引擎与选型/为什么只有InnoDB支持事务]] · [[mysql/02-中段阶段-专题精讲/存储引擎与选型/引擎全景与迁移实操]]

## 二、两个端口与两个协议

| 端口 | 协议 | 用途 |
|------|------|------|
| **3306** | 经典协议（文本） | ⚠️ 绝大多数客户端用这个 |
| **33060** | X Protocol（二进制） | 8.0 引入，MySQL Shell 用；部分连接池（如 MySQL Connector/Python 的 `mysqlx`）也支持 |
| 33061 | Group Replication | 8.0.22+ 的常规 GR 端口 |

⚠️ **「X 协议」的价值在于二进制编码，比经典协议的文本解析快**。但生态支持度远不如经典协议——**绝大多数场景用 3306 就够了**。

⚠️ **连接串里指定协议**：MySQL Connector/Python 里 `mysql://` 用经典协议，`mysqlx://` 用 X 协议。这个区别在 [[sqlmodel/引擎与Session]] 里有对应说明。

## 三、三种启动方式

| 方式 | 命令 | 说明 |
|------|------|------|
| **systemd**（Linux 推荐） | `sudo systemctl start mysql` | ⭐ 生产标准方式，能设开机自启、自动重启 |
| **直接启动** | `mysqld --defaults-file=/etc/my.cnf` | 前台运行，日志直接输出到终端，调试用 |
| **包装脚本** | `mysqld_safe --defaults-file=/etc/my.cnf` | ⚠️ 老方式，崩溃后自动重启；**不推荐新部署** |

⚠️ **`mysqld_safe` 是历史遗留方案。** 它会作为父进程监控 `mysqld`，崩溃时拉起来。但它本身不管理日志、不处理依赖关系。**现在应该用 systemd 或容器编排**（Kubernetes Operator 也有）。

> 相关：[[docker/01-入门阶段-基础教程/00-章节目录]] —— 容器里通常直接跑 `mysqld`，让 Docker 的重启策略兜底。

## 四、配置文件与参数

### 配置文件在哪

| 系统 | 路径 |
|------|------|
| Linux | `/etc/my.cnf`、`/etc/mysql/my.cnf`、`~/.my.cnf` |
| Windows | `C:\ProgramData\MySQL\MySQL Server 8.4\my.ini` |

⚠️ **可能有多个文件，加载顺序是「后加载的覆盖先加载的」**。排查「我改了配置怎么没用」时，第一步是确认改的是哪个文件：

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';   -- 看实际生效值
```

### 参数分两类（这个区分很重要）

| 类型 | 特点 | 举例 |
|------|------|-----|
| **动态变量（dynamic）** | ⭐ **可以在运行时改**，新连接立即生效 | `max_connections`、`innodb_buffer_pool_size` |
| **静态变量（static）** | 只能改配置文件 + 重启 | `innodb_data_file_path`、`datadir` |

```sql
-- 动态：运行时改，会话级或全局级
SET GLOBAL max_connections = 500;          -- 全局，新连接生效，已有连接不变
SET SESSION sql_mode = 'STRICT_TRANS_TABLES';  -- 只影响当前连接

-- 静态：改完要重启
-- SET GLOBAL datadir='/data';   ← 会报错：变量是只读的
```

⚠️ **`SET GLOBAL` 只影响新连接，已有的连接不变。** 这是新手调参数后「为什么没用」的最常见原因。

### 三个必须知道的参数

| 参数 | 说明 | 详见 |
|------|------|------|
| `innodb_buffer_pool_size` | ⚠️ **最重要的参数**，InnoDB 缓存池，建议物理内存的 50-70% | [[mysql/02-中段阶段-专题精讲/InnoDB存储引擎/专题概览]] |
| `innodb_flush_log_at_trx_commit` | 提交时刷 redo 策略，**1=安全 0=可能丢数据** | [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]] |
| `sql_mode` | ⚠️ SQL 严格模式 | 见下节 |

完整参数表见 [[mysql/速查索引]] 第八节。

## 五、sql_mode：生产必开

⚠️ **这一节单独拎出来，因为它直接关系到数据是否会悄悄出错。**

`sql_mode` 控制 MySQL 对「不合规」SQL 的处理态度。

```sql
SHOW VARIABLES LIKE 'sql_mode';
```

### 非严格模式下的危险行为

```sql
-- 表定义：name VARCHAR(5) NOT NULL
INSERT INTO users (name, age) VALUES ('张三丰超长名字', 'abc');
```

| 模式 | 结果 |
|------|------|
| 非严格 | ⚠️ `张三丰超长名字` 被**静默截断**成 `张三丰超`，`'abc'` 被转成 `0`，**不报错** |
| 严格 | ❌ 直接报错，插入失败 |

⚠️ **静默截断是生产事故的常见来源**：你以为存了完整名字，实际只存了前 5 个字符，等到用户投诉时数据已经错了一万条。

### 生产推荐的 sql_mode

```sql
SET GLOBAL sql_mode = 'STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION';
```

| 值 | 作用 |
|---|------|
| `STRICT_TRANS_TABLES` | ⭐ 核心：数据不合法时报错而不是截断 |
| `NO_ZERO_IN_DATE` / `NO_ZERO_DATE` | 禁止 `'0000-00-00'` 这类非法日期 |
| `ERROR_FOR_DIVISION_BY_ZERO` | 除零报错而不是返回 NULL |
| `NO_ENGINE_SUBSTITUTION` | 表指定的引擎不可用时直接报错，不偷偷换成 InnoDB |

⭐ **PostgreSQL 没有对应开关**——它默认就是严格模式。这是 PG 和 MySQL 的一个重要行为差异，迁移时要注意。

## 六、连接管理

| 项 | 说明 |
|----|------|
| 一个连接 = 一个线程 | ⚠️ 经典架构，连接多则线程多 |
| `max_connections` | 默认 151，太小会「Too many connections」 |
| `wait_timeout` | 空闲连接超时时间，默认 28800 秒（8 小时） |
| `thread_cache_size` | 线程缓存，建议 100-200，减小建连开销 |
| 8.0 线程池 | 26.7 起进社区版，解决高并发上下文切换 |

⚠️ **`max_connections` 不是越大越好。** 每个线程有栈内存（默认 `thread_stack` 1MB 量级），1000 个连接就是几个 GB 的虚拟内存（虽然不是全部驻留）。且线程数超过 CPU 核数后，吞吐会**下降**。

**正确的思路**：数据库侧设一个合理的 `max_connections`，连接管理交给**连接池**（应用侧）。详见 [[mysql/02-中段阶段-专题精讲/工具与可观测性/工具链总览]]。

## 七、陷阱

1. **❌ 以为「装了 MySQL」就等于有服务端。** 可能只装了客户端。判断标准是能否连上。
2. **❌ `SET GLOBAL` 后觉得没生效。** 它只影响新连接，已有连接不变。
3. **❌ 改错配置文件。** 可能有多个文件，用 `SHOW VARIABLES` 确认实际生效值。
4. **❌ 生产不开 `STRICT_TRANS_TABLES`。** 静默截断会造成大批脏数据。
5. **❌ 把 `max_connections` 调到几千。** 线程爆炸反而更慢。应该用连接池。
6. **❌ 用 `mysqld_safe` 做新的生产部署。** 用 systemd。
7. **❌ 以为 SQL 层知道数据怎么存。** 存储引擎是插件，各表可能用不同引擎。
8. **❌ 切到 MyISAM。** 没有事务和外键。

## 小结

- `mysqld` 三层：连接层（协议+认证+一连接一线程）/ 服务层（⭐优化器）/ 存储引擎层（插件化）
- **服务层的优化器是核心**，但会猜错
- **存储引擎插件化**是 MySQL 特色，表可以各选引擎；InnoDB 是唯一推荐
- 端口：3306 经典协议、33060 X 协议
- 启动：Linux 用 systemd，`mysqld_safe` 是遗留方案
- 参数分动态/静态，**`SET GLOBAL` 只影响新连接**
- **`sql_mode` 生产必开 `STRICT_TRANS_TABLES`**，否则静默截断
