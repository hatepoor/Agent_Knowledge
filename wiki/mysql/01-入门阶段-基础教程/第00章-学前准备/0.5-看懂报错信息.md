# 看懂报错信息

## 学习目标

读完本篇，你应当能够：

1. 读懂 MySQL 报错的三段结构（错误信息 + SQLSTATE + 错误码）
2. 用「错误码前缀 + SQLSTATE 类别」快速定位问题
3. 逐条排查 12 类最常见报错
4. 知道「报错不是失败」的情况（如 `SHOW WARNINGS`）
5. 建立一条固定的排错路径，而不是随机试

## 一、报错的三个部分

MySQL 报错通常长这样：

```
ERROR 1064 (42000) at line 1: You have an error in your SQL syntax;
check the manual that corresponds to your MySQL server version for the
right syntax to use near 'FROM users'
```

拆成三段：

| 部分 | 值 | 作用 |
|------|-----|------|
| **错误码** | `1064` | ⭐ 唯一编号，查文档/搜错误码用这个 |
| **SQLSTATE** | `42000` | 五位标准错误码，**跨数据库通用**（写异常处理用这个） |
| **错误信息** | 一句话描述 + 位置 | 人读 |

### 两种错误码的区别

⚠️ **这是个关键概念，不同用途要用不同的：**

| 用途 | 该看哪个 | 原因 |
|------|---------|------|
| **查 MySQL 文档 / 搜索引擎** | 错误码（`1064`） | MySQL 特有信息更详细 |
| **写跨库兼容的异常处理** | SQLSTATE（`42000`） | 标准，不同数据库能统一处理 |

### SQLSTATE 前缀分类

| 前缀 | 类别 | 含义 | 该找谁 |
|------|------|------|-------|
| `42...` | **语法错误或访问权限问题** | `42000` 语法、`42001` 无权限、`42S02` 表不存在 | 你自己 |
| `23...` | **完整性约束** | `23000` 通用、`23001` 重复键、`23006` 外键 | 数据问题 |
| `22...` | **数据类型问题** | `22001` 超出范围、`22007` 日期非法、`22012` 除零 | 数据问题 |
| `08...` | **连接问题** | `08004` 服务器拒绝、`08001` 连不上 | 网络/服务 |
| `40...` | **事务问题** | `40001` 死锁、`40001` 序列化失败 | 重试 |
| `HY...` | **通用错误** | `HY000` 泛用、`HY025` 非法密码 | 看信息文本 |
| `0A...` | **不支持** | `0A000` 功能未启用 | 查特性 |
| `3D...` | **目录错误** | 库/表不存在 | |

📐 **记忆锚点**：`42` 语法权限、`23` 约束、`22` 类型、`08` 连接、`40` 事务。**看到开头两位就知道该往哪查。**

## 二、固定排错路径

⚠️ **新手最常见的问题是没路径地乱试。按这四步走，能解决 90% 的问题。**

```
① 读错误码 → 2xx? 4xx? 2xx 是语法/权限，4xx 是数据/连接
    ↓
② 定位到「哪一层」
    ├─ 连不上         → 服务/网络层
    ├─ 语法报错       → SQL 文本层（对照第③步）
    ├─ 找不到表/列    → 名字问题（大小写？字符集？）
    └─ 类型/约束报错  → 数据层（查现存数据）
    ↓
③ 语法报错就逐字对照 ← 这类占一半以上
    关键字全大写 → 检查分号 → 检查引号 → 检查保留字
    ↓
④ 用信息视图查现场
    SHOW WARNINGS;        看上一条语句的警告
    SHOW CREATE TABLE t;  看真实表结构
    SHOW VARIABLES LIKE '%x%';  查系统变量
```

⭐ **第 ④ 步是最容易被跳过、但效率最高的一步。** 你以为的表结构和实际表结构经常不一样（大小写、字符集、列名拼写）。

## 三、12 类常见报错逐条排查

### 类别 1：连接类（`08...`）

#### `ERROR 2003 (HY000): Can't connect to MySQL server on 'localhost'`

| 可能原因 | 排查 |
|---------|------|
| 服务没启动 | `docker ps` 或 `systemctl status mysql` |
| 端口不对 | `SHOW VARIABLES LIKE 'port'` 或看配置 |
| 防火墙拦截 | 检查云服务器安全组、Windows 防火墙 |
| socket 路径不对 | 客户端默认走 socket，参数写 host 才走 TCP |

⚠️ **最常见的是「服务真的没起」**。Docker 场景下检查 `docker ps -a` 看容器是不是退出了。

#### `ERROR 1045 (28000): Access denied for user 'root'@'localhost'`

| 可能原因 | 排查 |
|---------|------|
| 密码错 | 确认大小写（MySQL 密码大小写敏感） |
| host 不匹配 | ⚠️ **`'root'@'localhost'` 和 `'root'@'127.0.0.1'` 是两个不同的账号** |
| 认证方式不匹配 | 8.0 的 `caching_sha2_password` vs 老的 `mysql_native_password` |

```sql
SELECT user, host, plugin FROM mysql.user;   -- 看账号和认证方式
```

⚠️ **host 部分极易踩坑**：账号 `'app'@'localhost'` 只允许本地 socket 连接，`'app'@'127.0.0.1'` 只允许 TCP 从本机连接，**两者不通用**。

#### `ERROR 1040 (42000): Too many connections`

| 项 | 说明 |
|---|------|
| 原因 | 连接数超过 `max_connections`（默认 151） |
| 排查 | `SHOW PROCESSLIST;` 看谁占着连接 |
| 解决 | ⚠️ **查大连接用 `information_schema.PROCESSLIST` 而不是 `SHOW PROCESSLIST`**——后者本身也要占一个连接 |

⚠️ **连接泄漏是根本原因**：应用侧没关连接、连接池配置错、事务忘记 commit 导致连接不归还。

📌 见 [[mysql/02-中段阶段-专题精讲/工具与可观测性/工具链总览]]。

### 类别 2：语法类（`42S02`）

#### `ERROR 1064 (42000): You have an error in your SQL syntax`

⭐ **这是最常见的报错，占日常问题的一半以上。** 逐项对照：

| 检查项 | 常见错误 |
|--------|---------|
| 分号 | 漏了结尾分号 |
| 引号配对 | 单引号没闭合、字符串里有单引号没转义 |
| 保留字 | 表名/列名是 `order`、`group`、`key`、`desc`、`range` |
| 逗号 | 字段列表末尾多逗号，或少了逗号 |
| 括号 | 子查询或函数括号不配对 |
| 关键字拼写 | `SELECT` 写成 `SELCT`、`WHERE` 写成 `WHER` |
| 大小写混用 | 表名在 Linux 上大小写敏感 |

⚠️ **`order`、`group`、`key`、`desc`、`range`、`table`、`select`、`from`、`default`、`status`、`condition` 都是保留字。** 用了必须加反引号：

```sql
SELECT `order`, `key`, `status` FROM `logs`;
```

📌 完整保留字清单见 [[mysql/术语与关键字手册]]。

#### `ERROR 1064` 的一个特殊原因：`--` 注释

```sql
-- 这行注释后面要有空格！
SELECT 1 -- 这是注释
```
⚠️ **`--` 后面必须跟空格或换行**，否则会被当成减号操作符。同样 `#` 才是 MySQL 的另一种注释写法。

### 类别 3：找不到对象（`42S02`）

#### `ERROR 1146 (42S02): Table 'app.user' doesn't exist`

| 可能原因 | 排查 |
|---------|------|
| 表名拼错 | `SHOW TABLES;` |
| 大小写 | ⚠️ **Linux 上 `User` ≠ `user`** |
| 库选错了 | `SELECT DATABASE();` |
| 用了 schema 语法 | MySQL 里 schema = database，`app.users` 会解析成 `app`.`users` |

```sql
SHOW DATABASES;
USE app;
SHOW TABLES;
SELECT DATABASE();     -- 确认当前库
```

⚠️ **「表不存在」的第一检查项永远是 `SELECT DATABASE();`** 忘切库是最常见的原因。

#### `ERROR 1054 (42S22): Unknown column 'xxx' in 'field list'`

```sql
SHOW CREATE TABLE users\G    -- ⭐ 看真实结构
SHOW COLUMNS FROM users;
```

⚠️ **`SHOW CREATE TABLE` 比 `DESC users` 更全**——它能看到索引、外键、引擎、字符集这些 `DESC` 不显示的信息。加 `\G` 让它竖排显示。

### 类别 4：数据类型（`22...`）

#### `ERROR 1264 (22003): Out of range value for column 'age' at row 1`

| 可能原因 | 说明 |
|---------|------|
| 超出类型范围 | `TINYINT` 存 200、超范围 |
| 零日期 | ⚠️ `'0000-00-00'` 在严格模式下禁止 |
| 隐式转换失败 | `VARCHAR` 列塞纯数字能转，反之不行 |

```sql
-- 看列定义
SHOW CREATE TABLE users\G

-- 看现存数据有没有已经越界的
SELECT id, age FROM users WHERE age < 0 OR age > 127;
```

⚠️ **如果严格模式没开，这个报错会变成静默截断**——问题更隐蔽。见 [[mysql/01-入门阶段-基础教程/第00章-学前准备/0.2-MySQL架构与客户端]]。

#### `ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' for column 'name'`

⚠️ **这是 emoji 存不进去**，原因几乎一定是字符集不是 utf8mb4。

```sql
SHOW CREATE TABLE users\G
-- 看是不是 CHARACTER SET utf8mb3 或 latin1

-- 修表
ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- 同时要改列定义（如果当时是用 CHARACTER SET 指定的）
ALTER TABLE users MODIFY name VARCHAR(255) CHARACTER SET utf8mb4;
```

📌 详见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.1-数据类型全景]]。

#### `ERROR 1292 (22007): Incorrect datetime value: '2026-13-45'`

| 可能原因 | 说明 |
|---------|------|
| 月份/日期非法 | 13 月、2 月 30 日 |
| 格式不对 | `DATE_FORMAT` 的格式符和 `STR_TO_DATE` 不匹配 |
| 时区 | ⚠️ `TIMESTAMP` 列受 `time_zone` 影响 |

```sql
SELECT NOW(), @@time_zone, @@global.time_zone;
SELECT STR_TO_DATE('2026/01/15', '%Y/%m/%d');   -- 格式符要对上
```

⚠️ **`DATE_FORMAT` 的分钟是 `%i` 不是 `%M`**（`%M` 是英文月名）。这个坑见 [[mysql/函数手册]]。

### 类别 5：完整性约束（`23...`）

#### `ERROR 1062 (23000): Duplicate entry 'a@b.com' for key 'users.uk_email'`

| 可能原因 | 说明 |
|---------|------|
| 唯一索引冲突 | ⚠️ **注意：主键冲突也是这个错误码** |
| 插入时列顺序错 | 值和列不对应 |

```sql
-- 看是哪个索引冲突
SHOW INDEX FROM users\G
-- 或
SELECT CONSTRAINT_NAME, COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA='app' AND TABLE_NAME='users';
```

解决：

```sql
-- 方案 A：冲突则更新
INSERT INTO users (id, name, email) VALUES (1,'张三','a@b.com')
  AS new ON DUPLICATE KEY UPDATE name = new.name;

-- 方案 B：冲突则忽略
INSERT IGNORE INTO users (id, name, email) VALUES (1,'张三','a@b.com');

-- 方案 C：先查再决定（需要事务保护）
```

⚠️ **主键冲突和唯一索引冲突是同一个错误码**，看报错里的 key 名区分：`PRIMARY` 是主键，其他是唯一索引。

#### `ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails`

⚠️ **外键约束失败 = 你插入/更新的值在被引用的表里不存在。**

```sql
SELECT * FROM departments WHERE id = 999;   -- 确认部门真的不存在
SELECT CONSTRAINT_NAME, COLUMN_NAME, REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA='app' AND REFERENCED_TABLE_NAME IS NOT NULL;
```

⚠️ **删除时报同一个错（`1451`）= 有子表在引用它。** 解决顺序：先删子表记录，或把外键设为 `ON DELETE CASCADE`。

📌 外键的生产实践（⚠️ 很多团队故意不用外键）见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]]。

#### `ERROR 1172 (42000): BLOB/TEXT column 'xxx' can't be used in key specification without a key length`

⚠️ **`TEXT`/`BLOB` 类型不能直接建索引**（因为没有长度上限）。两个解法：

```sql
-- 方案 A：指定前缀长度
CREATE INDEX idx_content ON articles (content(255));

-- 方案 B：改用 varchar（更常用）
ALTER TABLE articles MODIFY content VARCHAR(2000);
```

📌 见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引类型与选型]]。

### 类别 6：权限类（`42001`）

#### `ERROR 1142 (42000): SELECT command denied to user 'app'@'127.0.0.1' for table 'users'`

```sql
SHOW GRANTS FOR CURRENT_USER();   -- 看自己有什么权限
GRANT SELECT, INSERT ON app.users TO 'app'@'127.0.0.1';
FLUSH PRIVILEGES;   -- 8.0 通常不需要，但显式执行无害
```

⚠️ **`GRANT` 之后 `FLUSH PRIVILEGES` 在 8.0 里通常不必要**（8.0 会自动生效），但老习惯写上无害。

### 类别 7：事务与死锁（`40001`）

#### `ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction`

**这不是 bug，是设计。** InnoDB 检测到循环等待，主动回滚一个事务。

```sql
-- 看当前事务和锁
SELECT * FROM information_schema.INNODB_TRX;
SHOW ENGINE INNODB STATUS\G     -- ⭐ LATEST DETECTED DEADLOCK 段落
```

客户端策略：**捕获 1213 或 40001 后退避重试整个事务**。⚠️ 不是重试单条语句，是重试整个事务。

📌 死锁成因与排查见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]。

### 类别 8：磁盘与资源

#### `ERROR 1114 (HY000): The table 'users' is full`

⚠️ **表空间满了。** 三种情况：

| 情况 | 判断 | 解决 |
|------|------|------|
| 磁盘满 | `df -h` | 扩磁盘或删数据 |
| 表空间上限 | MyISAM 常见（单表文件上限） | 改 InnoDB |
| InnoDB 数据文件满 | 看 `ibdata1` 大小 | 扩 `innodb_data_file_path` 或加数据文件 |

#### `ERROR 1041 (HY000): Out of memory`

内存不足。检查 `innodb_buffer_pool_size` 是否设得太大（⚠️ 超过物理内存的 70% 会出问题）。

### 类别 9：安全类

#### `ERROR 2064 (42000): You have an error in your SQL syntax`（安全版）

⚠️ **注意：`2064` 可能是 SQL 注入防护触发的。** 典型场景：拼接字符串时用户输入了 `' OR '1'='1`，导致语法错误或更糟的结果。

```sql
-- ❌ 危险
query = f"SELECT * FROM users WHERE name = '{user_input}'"

-- ✅ 安全：用参数化查询
cur.execute("SELECT * FROM users WHERE name = %s", (user_input,))
```

📌 见 [[mysql/02-中段阶段-专题精讲/备份恢复与安全/备份体系与恢复演练]]。

## 四、不是错误的情况

⚠️ **有些「问题」其实不是错误，是警告或提示。**

### `SHOW WARNINGS`

```sql
INSERT INTO users (id, name) VALUES (1, '张三');
SHOW WARNINGS;
-- ⚠️ 可能返回 Warning 1265 Data truncated
```

⭐ **在非严格模式下，很多本该报错的情况会变成警告。** 你的数据已经被截断了，但你没注意到。

📌 **养成习惯：批量导入数据后跑一次 `SHOW WARNINGS`。**

### `0 rows affected`

`UPDATE` 影响了 0 行**不一定是错误**，可能是：
- WHERE 条件没匹配到（数据本来就那样）
- 值本来就一样

⚠️ 但在「更新后校验」的逻辑里，0 行往往意味着异常——比如你按 ID 更新但 ID 拼错了。要区分就得先查存在性。

### `NULL` 参与运算

```sql
SELECT 1 + NULL;        -- 返回 NULL，不是 1
SELECT NULL = NULL;     -- 返回 NULL，不是 true
SELECT NULL <= NULL;    -- ⚠️ 返回 NULL，表示「未知」，不是 false
```

⚠️ **这是 SQL 三值逻辑**：`TRUE` / `FALSE` / **`UNKNOWN`**。`WHERE` 只保留 `TRUE` 的行，所以 `WHERE col = NULL` 永远查不到任何行——**必须写 `WHERE col IS NULL`**。

📌 详见 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.2-WHERE条件与函数]]。

## 五、快速对照表

| 错误码 | 一句话含义 | 第一反应 |
|--------|-----------|---------|
| `1045` | Access denied | 密码或 host 部分 |
| `1040` | Too many connections | 查 `information_schema.PROCESSLIST` 找泄漏 |
| `1062` | Duplicate entry | 唯一索引冲突，看 key 名 |
| `1064` | 语法错误 | ⭐ 逐字对照 SQL |
| `1146` | 表不存在 | `SELECT DATABASE()` 确认切库了 |
| `1054` | 列不存在 | `SHOW CREATE TABLE` |
| `1264` | 数值超范围 | 看列定义，可能没开严格模式 |
| `1366` | 字符串编码错 | ⭐ 改 utf8mb4 |
| `1292` | 日期/时间非法 | 格式符对不对 |
| `1452` | 外键失败（加/改） | 被引用的值不存在 |
| `1451` | 外键失败（删） | 有子表在引用 |
| `1213` | 死锁 | ⚠️ **这是设计，退避重试** |
| `1172` | TEXT 不能建索引 | 用前缀长度或改 varchar |
| `1114` | 表空间满 | 查磁盘 |

## 六、陷阱

1. **❌ 不看错误码，只读错误信息。** 错误码才是精准检索的钥匙。
2. **❌ 随机试 SQL。** 按「三层定位」走，别乱改。
3. **❌ 以为「表不存在」是表被删了。** **九成是没切库**。
4. **❌ Linux 上表名大小写随便写。** 本地 Windows 能跑，部署就崩。
5. **❌ 把死锁当 bug 修。** 它是并发系统的正常保护，客户端重试即可。
6. **❌ 批量导入后不看 `SHOW WARNINGS`。** 数据可能已被静默截断。
7. **❌ 在 `WHERE` 里写 `= NULL`。** 永远查不到，要用 `IS NULL`。
8. **❌ 拼接 SQL 字符串。** 用参数化查询。

## 小结

- 报错三段：**错误码**（查文档用）/ **SQLSTATE**（跨库异常处理用）/ 错误信息
- SQLSTATE 前缀速记：`42` 语法权限 `23` 约束 `22` 类型 `08` 连接 `40` 事务
- **固定排错路径**：读错误码 → 定位层 → 逐字对照 SQL → 用 `SHOW CREATE TABLE` / `SHOW WARNINGS` 查现场
- 最高频的三个：`1064` 语法（查分号/引号/保留字）、`1146` 表不存在（**先查切库**）、`1366` 编码（改 utf8mb4）
- **`1213` 死锁不是 bug**，是保护机制，客户端退避重试
- ⚠️ **非严格模式下，很多错误变成警告**，批量操作后跑 `SHOW WARNINGS`
