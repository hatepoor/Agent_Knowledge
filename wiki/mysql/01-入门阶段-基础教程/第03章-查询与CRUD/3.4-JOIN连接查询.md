# JOIN 连接查询

## 学习目标

读完本篇，你应当能够：

1. 区分五种 JOIN 的语义，并画出结果集
2. ⚠ **避免隐式 JOIN 导致的行数膨胀**
3. 知道 `LEFT JOIN` 的过滤条件该写在 `ON` 还是 `WHERE`
4. 掌握子查询、EXISTS、派生表的取舍
5. 避免 JOIN 的三个性能坑（笛卡尔积、无索引、大表 JOIN）
6. 写出带聚合的分组统计

## 一、五种 JOIN

### 用这两张表理解

```
departments（部门表）          employees（员工表）
┌────┬────────┐               ┌────┬─────┬────────┐
│ id │ name   │               │ id │dept│ name   │
├────┼────────┤               ├────┼─────┼────────┤
│  1 │ 技术部  │               │  1 │  1  │ 张三   │
│  2 │ 市场部  │               │  2 │  1  │ 李四   │
│  3 │ 空部门  │               │  3 │  2  │ 王五   │
└────┴────────┘               │  4 │ 99  │ 孤儿   │  ← dept=99 不存在
                              └────┴─────┴────────┘
```

### INNER JOIN（默认）

**只保留两边都匹配上的行**

```sql
SELECT e.name, d.name FROM employees e
INNER JOIN departments d ON e.dept_id = d.id;
```

| name | d.name |
|------|--------|
| 张三 | 技术部 |
| 李四 | 技术部 |
| 王五 | 市场部 |

⚠️ **被过滤掉了**：空部门（3，无员工）、孤儿员工（dept=99）

### LEFT JOIN（左外连接）

**保留左表全部，右表匹配不上的补 NULL**

```sql
SELECT e.name, d.name FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id;
```

| name | d.name |
|------|--------|
| 张三 | 技术部 |
| 李四 | 技术部 |
| 王五 | 市场部 |
| **孤儿** | **NULL** |

⚠️ **被过滤掉了**：空部门（3，因为它在右表，左表没有对应员工）

### RIGHT JOIN

**保留右表全部。** ⚠️ **实践中几乎不用**，因为 `A RIGHT JOIN B` 等价于 `B LEFT JOIN A`（交换顺序即可），用 LEFT 更直观。

```sql
SELECT e.name, d.name FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id;
```

会包含空部门（name 为 NULL）。

### FULL OUTER JOIN

⚠️ **⚠️ MySQL 不支持 `FULL OUTER JOIN`！** 需要手写：

```sql
-- MySQL 模拟 FULL OUTER JOIN
SELECT e.name, d.name FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
UNION ALL
SELECT e.name, d.name FROM employees e
RIGHT JOIN departments d ON e.dept_id = d.id
WHERE e.id IS NULL;    -- 只取右表独有的
```

### CROSS JOIN（笛卡尔积）

**每行 × 每行**

```sql
SELECT e.name, d.name FROM employees e CROSS JOIN departments d;
-- 4 员工 × 3 部门 = 12 行
```

⚠️ **这是最容易出事的写法**——⚠️ **忘记写 `ON` 条件的 `FROM a JOIN b` 等价于 `CROSS JOIN`**：

```sql
-- ⚠️ 忘记 ON → 笛卡尔积 1200 万行！
SELECT * FROM employees e JOIN departments d;
-- ⚠️ MySQL 会直接报 ERROR 1064（语法错）吗？
-- ❌ 不会！MySQL 允许 JOIN 不带 ON（等价 CROSS JOIN）
```

⭐ **这是生产事故的经典原因**：一条错误的 JOIN 可能产生百万级结果集，把库拖垮。

## 二、`ON` vs `WHERE` ⚠️★

⚠️ **这是 JOIN 里最容易出错的地方。**

### 关键差异

| 写法 | 执行顺序 | 对 `LEFT JOIN` 的影响 |
|------|---------|---------------------|
| `ON` 条件 | ⭐ **JOIN 阶段**（生成结果集时） | ⚠️ **匹配不上就补 NULL** |
| `WHERE` 条件 | **WHERE 阶段**（结果集生成后） | ⚠️ **把 NULL 行过滤掉，`LEFT JOIN` 退化成 `INNER JOIN`** |

### 经典陷阱

```sql
-- 需求：列出所有员工，包括未分配部门的
SELECT e.name, d.name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id
WHERE d.name = '技术部';        -- ⚠️ ⚠️ ⚠️
```

**结果：只有技术部的员工。**

**为什么？**

```
① LEFT JOIN 生成结果集：孤儿员工的 d.name 是 NULL
② WHERE d.name = '技术部'：NULL = '技术部' → UNKNOWN → ❌ 被过滤
③ LEFT JOIN 退化成了 INNER JOIN
```

**正确写法：条件放 `ON` 里**

```sql
SELECT e.name, d.name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.id AND d.name = '技术部';
-- 结果：孤儿员工保留，d.name 为 NULL
```

### 什么时候该用 `WHERE`

⚠️ **`WHERE` 不是不能用**，取决于需求：

```sql
-- ✅ 场景：统计各部门人数（只关心有员工的部门）
SELECT d.name, COUNT(e.id)
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
WHERE d.active = 1           -- ⭐ 过滤右表本身的属性 → 用 WHERE
GROUP BY d.id;
```

**判断标准**：

| 过滤条件针对 | 放哪 |
|-------------|------|
| **右表的属性**（要保留左表所有行，只是想匹配特定右表行） | `ON` |
| **整体的行**（不想要 NULL 行 / 过滤左表自己的属性） | `WHERE` |

## 三、隐式 JOIN 的行数膨胀 ⚠️

### 问题

```sql
-- 需求：查询每个部门的名称和员工数
SELECT d.name, COUNT(*) AS cnt
FROM departments d, employees e      -- ⚠️ 隐式 JOIN
WHERE d.id = e.dept_id
GROUP BY d.name;
```

⚠️ **看起来对，但 `COUNT(*)` 是错的**：

```sql
-- ✅ 正确：COUNT(右表列) 而不是 COUNT(*)
SELECT d.name, COUNT(e.id) AS cnt
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
GROUP BY d.id, d.name;
```

| 写法 | 空部门的 `cnt` |
|------|--------------|
| ⚠️ `COUNT(*)` | **1**（因为有一行 d.* 是 NULL） |
| ✅ `COUNT(e.id)` | **0**（`COUNT(列)` 忽略 NULL） |

⚠️ **⚠️ 这是「COUNT(*) vs COUNT(列)」在 JOIN 场景下的具体体现。** 空部门的结果：

| 写法 | 结果 |
|------|------|
| ⚠️ `COUNT(*)` | 技术部=2, 市场部=1, 空部门=**1** ← 错 |
| ✅ `COUNT(e.id)` | 技术部=2, 市场部=1, 空部门=**0** ← 对 |

### 一对多 JOIN 的重复

```sql
-- 部门 JOIN 员工 JOIN 订单
SELECT d.name, COUNT(o.id)
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
LEFT JOIN orders o ON o.emp_id = e.id
GROUP BY d.id;
```

⚠️ **一个员工有 10 单，会让该员工的行变成 10 行**——员工数被重复计数。

**正确做法：分开统计或用子查询**

```sql
SELECT d.name,
       (SELECT COUNT(*) FROM employees e WHERE e.dept_id = d.id) AS emp_cnt,
       (SELECT COUNT(*) FROM orders o JOIN employees e ON e.id = o.emp_id
         WHERE e.dept_id = d.id) AS order_cnt
FROM departments d;
```

⚠️ **多表 JOIN 的聚合极易出错。** 每个 `COUNT` 都要问自己「这个值会不会因为 JOIN 而重复」。

⭐ **更安全的做法：先各自聚合到子表，再 JOIN**：

```sql
SELECT d.name, ec.emp_cnt, COALESCE(oc.order_cnt, 0)
FROM departments d
LEFT JOIN (SELECT dept_id, COUNT(*) emp_cnt FROM employees GROUP BY dept_id) ec
       ON ec.dept_id = d.id
LEFT JOIN (SELECT e.dept_id, COUNT(*) order_cnt
           FROM orders o JOIN employees e ON e.id = o.emp_id
           GROUP BY e.dept_id) oc
       ON oc.dept_id = d.id;
```

📌 这就是「反范式冗余统计字段」要解决的问题——见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.3-表设计规范与反范式]]。

## 四、JOIN 的三个性能坑

### 坑 1：⚠️ 缺少索引

```sql
-- ⚠️ JOIN 列没有索引 → 全表扫描笛卡尔积
SELECT * FROM employees e JOIN orders o ON o.emp_id = e.id;
```

⚠️ **JOIN 的性能完全取决于关联列有没有索引。**

```sql
-- 检查
SHOW INDEX FROM orders\G
-- 必须有 idx_emp (emp_id)
```

⚠️ **⚠️ 外键列不会自动建索引**（见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]]）。

### 坑 2：⚠️ 关联列类型不一致

```sql
-- ⚠️ 类型不一致 → 隐式类型转换 → 索引失效
CREATE TABLE a (id BIGINT);          -- 大
CREATE TABLE b (id INT);            -- 小
SELECT * FROM a JOIN b ON a.id = b.id;   -- ⚠️ b.id 被转成 BIGINT，b 的索引用不上
```

**规则**：JOIN 关联的两列**类型和字符集必须完全一致**。

| 检查项 | 要求 |
|--------|------|
| 整数类型 | `INT` ↔ `INT`，`BIGINT` ↔ `BIGINT` |
| 有无符号 | `UNSIGNED` ↔ `UNSIGNED` |
| 字符集 | `utf8mb4` ↔ `utf8mb4` |
| collation | ⭐ **必须一致**，见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.6-字符集排序规则]] |

⚠️ **字符集/collation 不一致是 JOIN 索引失效的头号原因。**

### 坑 3：⚠️ 过滤条件位置错误导致优化器选错驱动表

```sql
-- ⚠️ LEFT JOIN 的右表条件写在 WHERE，且 LEFT JOIN 退化
SELECT * FROM a LEFT JOIN b ON a.id = b.a_id WHERE b.active = 1;
-- ⚠️ 优化器可能把 b 当驱动表做 INNER JOIN
```

⚠️ **正确写法**（条件放 `ON`）：

```sql
SELECT * FROM a LEFT JOIN b ON a.id = b.a_id AND b.active = 1;
```

📌 完整诊断用 [[mysql/02-中段阶段-专题精讲/索引与查询优化/EXPLAIN解读]]。

### 排查 JOIN 慢的三步

```sql
-- ① 看执行计划：type 是 ALL 吗？
EXPLAIN SELECT * FROM a LEFT JOIN b ON a.id = b.a_id\G

-- ② 分别看两边的行数
SELECT COUNT(*) FROM a;
SELECT COUNT(*) FROM b;

-- ③ 检查关联列的索引和类型
SHOW INDEX FROM b\G
SHOW CREATE TABLE b\G
```

## 五、子查询 vs JOIN

### 三种写法

```sql
-- ① 标量子查询（返回单值）
SELECT name, (SELECT COUNT(*) FROM orders o WHERE o.emp_id = e.id) AS cnt
FROM employees e;

-- ② 表子查询（返回表）
SELECT * FROM employees WHERE dept_id IN (SELECT id FROM departments WHERE active = 1);

-- ③ EXISTS（返回布尔）
SELECT * FROM employees e
WHERE EXISTS (SELECT 1 FROM departments d WHERE d.id = e.dept_id AND d.active = 1);
```

### 对比

| 写法 | 语义 | 性能 | 可读性 |
|------|------|------|--------|
| `JOIN` | 两表都有数据 | ⭐ **通常最快**（优化器能重排） | ⭐ |
| `IN (子查询)` | 子查询结果在左列中 | 中 | 好 |
| `EXISTS` | ⭐ **只关心「有没有」** | ⭐ **相关子查询快** | 好 |
| `= (标量子查询)` | 单值 | 中（每行执行一次） | 一般 |

### ⚠️ `IN` vs `NOT IN` 的 NULL 陷阱

```sql
-- ⚠️ 极度危险
SELECT * FROM employees e
WHERE e.dept_id NOT IN (SELECT id FROM departments WHERE active = 0);
```

⚠️ **如果子查询结果里有任何 NULL，整个查询返回空集**：

```
子查询返回：{3, NULL}
WHERE dept_id NOT IN (3, NULL)
  = dept_id != 3 AND dept_id != NULL
  = TRUE AND UNKNOWN
  = UNKNOWN    ← 永远不满足 → 结果为空
```

**正确写法：**

```sql
-- ① 用 NOT EXISTS
SELECT * FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM departments d
                  WHERE d.id = e.dept_id AND d.active = 0);

-- ② 或在子查询里过滤 NULL
WHERE dept_id NOT IN (SELECT id FROM departments WHERE active = 0 AND id IS NOT NULL)
```

⭐ **`NOT EXISTS` 天然没有这个问题**，这是它相对 `NOT IN` 的核心优势。

### `EXISTS` 的短路特性

```sql
-- EXISTS 找到第一条就停止
SELECT * FROM departments d
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.emp_id = d.id);
```

⚠️ **`EXISTS` 里不需要写 `SELECT *`**——只需要判断「有没有」，选什么列不影响（甚至 `SELECT 1` 更快，因为 MySQL 可能优化成常量）。

### 相关子查询 vs 派生表

```sql
-- 相关子查询（每行执行一次子查询）
SELECT * FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.id);
-- ⚠️ 外层 N 行 → 子查询执行 N 次

-- 派生表（先算一次子查询）
SELECT * FROM (SELECT dept_id, COUNT(*) cnt FROM employees GROUP BY dept_id) t;
-- ✅ 8.0 里优化器常能把相关子查询转成 JOIN

-- ✅ 8.0+ 可以用这个更直接的写法
SELECT * FROM departments d
LEFT JOIN (SELECT dept_id, COUNT(*) cnt FROM employees GROUP BY dept_id) t
       ON t.dept_id = d.id;
```

⚠️ **MySQL 8.0 的优化器有「子查询转 JOIN」的能力**，所以「相关子查询一定慢」是过时说法。⚠️ **但仍要看实际执行计划**，别假设。

## 六、经典查询模式

### 模式 1：每个部门的员工数（含零员工的部门）

```sql
SELECT d.id, d.name, COUNT(e.id) AS emp_cnt
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
GROUP BY d.id, d.name
ORDER BY emp_cnt DESC;
```

⚠️ **必须 `COUNT(e.id)` 而不是 `COUNT(*)`**（见第三节）。

### 模式 2：取每组前 N 条

```sql
-- 8.0+ 窗口函数（推荐）
SELECT * FROM (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM employees e
) t WHERE rn <= 3;
```

⚠️ **分组列和排序列要一致**。

📌 完整的排名、同比、环比见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

### 模式 3：连续登录 N 天的用户

```sql
SELECT user_id, COUNT(DISTINCT login_date) AS days
FROM (
  SELECT user_id, DATE(created_at) AS login_date
  FROM logins
  WHERE created_at >= '2026-01-01'
) t
GROUP BY user_id
HAVING days >= 3;
```

⚠️ **`DATE()` 作用在列上会索引失效**——如果量大，考虑加生成列：

```sql
ALTER TABLE logins ADD COLUMN login_date DATE
  GENERATED ALWAYS AS (DATE(created_at)) STORED;
CREATE INDEX idx_login_date ON logins (login_date);
```

### 模式 4：找出「没有订单的员工」

```sql
-- ✅ 推荐
SELECT e.* FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.emp_id = e.id);

-- ❌ 危险（子查询有 NULL 就返回空）
SELECT e.* FROM employees e
WHERE e.id NOT IN (SELECT emp_id FROM orders);

-- ✅ 也可以
SELECT e.* FROM employees e
LEFT JOIN orders o ON o.emp_id = e.id
WHERE o.id IS NULL;      -- ⭐ 用「右表主键为 NULL」判断「没匹配上」
```

⚠️ **`WHERE o.id IS NULL` 是 LEFT JOIN 的经典用法**（⚠️ 不能用 `o.emp_id IS NULL`，因为 `emp_id` 本身可能为 NULL）。

### 模式 5：占比计算

```sql
SELECT d.name,
       COUNT(e.id) AS emp_cnt,
       ROUND(COUNT(e.id) * 100.0 / SUM(COUNT(e.id)) OVER (), 2) AS pct
FROM departments d
LEFT JOIN employees e ON e.dept_id = d.id
GROUP BY d.id, d.name;
```

⚠️ **⚠️ `SUM(...) OVER ()` 的结果不能直接用在 `WHERE`**（窗口函数在 WHERE 之后才计算）：

```sql
-- ❌ 报错
WHERE pct > 10    -- ❌ Unknown column 'pct'

-- ✅ 用子查询包一层
SELECT * FROM ( ... ) t WHERE pct > 10;
```

## 七、自连接

⚠️ **同一张表 JOIN 自己**，常用于「上下级」「关注关系」。

```sql
-- 查每个员工和他的直属上级
SELECT e.name AS emp, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
```

⚠️ **`LEFT JOIN` 是必须的**——CEO 没有上级（`manager_id IS NULL`），用 `JOIN` 会漏掉他。

### 层级查询（MySQL 8.0+ 用递归 CTE）

```sql
WITH RECURSIVE dept_tree AS (
  -- 锚点：顶层部门（parent_id IS NULL）
  SELECT id, name, parent_id, 0 AS level
  FROM departments WHERE parent_id IS NULL

  UNION ALL

  -- 递归：下一层
  SELECT d.id, d.name, d.parent_id, t.level + 1
  FROM departments d
  JOIN dept_tree t ON d.parent_id = t.id
)
SELECT * FROM dept_tree ORDER BY level, name;
```

⚠️ **⚠️ 必须设置 `cte_max_recursion_depth` 防止无限递归**：

```sql
SET cte_max_recursion_depth = 1000;    -- 默认 1000
```

📌 树形结构的其他方案见 [[postgresql/02-中段阶段-专题精讲/CTE与递归查询/递归查询与树形结构]]（PG 版有更详细的对比）。

## 八、陷阱

1. **❌ 忘记写 `ON` 条件。** 变成笛卡尔积，可能拖垮数据库。
2. **❌ `LEFT JOIN` 的过滤条件写在 `WHERE` 里过滤右表列。** 退化成 `INNER JOIN`。
3. **❌ 用 `COUNT(*)` 统计右表行数。** 应该 `COUNT(右表.列)`。
4. **❌ 一对多 JOIN 后直接聚合。** 计数会被重复。
5. **❌ 关联列类型/字符集不一致。** 索引失效。
6. **❌ 用 `NOT IN (子查询)` 且子查询可能有 NULL。** 返回空集。用 `NOT EXISTS`。
7. **❌ `WHERE o.emp_id IS NULL` 判断「没匹配」。** 应用右表主键判断。
8. **❌ 在 `WHERE` 里用窗口函数结果。** 窗口函数在 WHERE 之后计算。
9. **❌ 关联列没有索引。** 全表扫描。

## 小结

- 五种 JOIN：`INNER` / `LEFT` / `RIGHT` / `FULL`（⚠️ **MySQL 不支持**，用 `UNION ALL` 模拟）/ `CROSS`
- ⚠️ **`ON` 在 JOIN 阶段、`WHERE` 在之后**；`LEFT JOIN` 的右表条件放 `WHERE` 会退化成 `INNER JOIN`
- ⚠️ **统计右表行数用 `COUNT(右表.列)` 而非 `COUNT(*)`**
- 一对多 JOIN 后聚合会重复计数 → 先各自聚合到子表再 JOIN
- 三个性能坑：**关联列无索引 / 类型不一致（含 collation）/ 条件位置错误**
- `NOT IN (子查询)` 有 NULL 陷阱（返回空集），**用 `NOT EXISTS`**
- 找「没有关联的行」：`NOT EXISTS` 或 `LEFT JOIN ... WHERE 右表主键 IS NULL`
- MySQL **没有** `FULL OUTER JOIN`
