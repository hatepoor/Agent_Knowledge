## 一、NULL 的三值逻辑 ★★

⚠️ **这是 SQL 最反直觉、也最容易出错的机制。** 单独一节讲透。

### 三个逻辑值

| 值 | 含义 |
|---|---|
| `TRUE` | 条件成立 |
| `FALSE` | 条件不成立 |
| **`UNKNOWN`** | ⭐ **NULL 参与比较的结果** |

### 为什么 NULL 是特殊的

```sql
-- 建表时允许为空
CREATE TABLE t (
  id INT,
  nickname VARCHAR(20) NULL
);

INSERT INTO t VALUES (1, NULL), (2, '张三');
```

**比较运算的真值表**：

| 表达式 | 结果 | 说明 |
|--------|------|------|
| `NULL = NULL` | ⚠️ **`NULL`**（不是 `TRUE`） | 两个 NULL 不「相等」 |
| `NULL <> NULL` | ⚠️ **`NULL`** | 也不「不等」 |
| `NULL = '张三'` | ⚠️ **`NULL`** | |
| `1 + NULL` | ⚠️ **`NULL`** | 任何值参与运算都是 NULL |
| `NULL IS NULL` | ⭐ **`TRUE`** | ⭐ 这才是正确的判断方式 |

**核心机制**：因为 NULL 表示「**未知**」，而「未知 == 未知」这个问题本身是未知的，所以返回 `NULL` 而不是 `TRUE`。

### ⚠️ 为什么 `= NULL` 永远查不到

```sql
-- ❌ 永远返回 0 行
SELECT * FROM t WHERE nickname = NULL;

-- ❌ 也永远返回 0 行（NULL 不是 TRUE）
SELECT * FROM t WHERE nickname <> NULL;

-- ✅ 正确
SELECT * FROM t WHERE nickname IS NULL;       -- 查 NULL 的
SELECT * FROM t WHERE nickname IS NOT NULL;   -- 查非 NULL 的
```

**机制**：`WHERE` 只保留结果为 `TRUE` 的行。`nickname = NULL` 的结果是 `UNKNOWN`，**不是 `TRUE`，所以被过滤掉了**。

### 三值逻辑真值表（重要）

**`AND` 的规则**：

| A | B | `A AND B` |
|---|---|----------|
| TRUE | TRUE | TRUE |
| TRUE | FALSE | FALSE |
| TRUE | **UNKNOWN** | **UNKNOWN** |
| FALSE | TRUE | FALSE |
| FALSE | FALSE | FALSE |
| FALSE | **UNKNOWN** | ⭐ **FALSE** |

⭐ **关键**：**只要有一个 `FALSE`，结果就是 `FALSE`**（不管另一边是什么）。这是「短路」语义。

**`OR` 的规则**：

| A | B | `A OR B` |
|---|---|----------|
| TRUE | TRUE | TRUE |
| TRUE | FALSE | TRUE |
| TRUE | **UNKNOWN** | ⭐ **TRUE** |
| FALSE | TRUE | TRUE |
| FALSE | FALSE | FALSE |
| FALSE | **UNKNOWN** | **UNKNOWN** |

⭐ **关键**：**只要有一个 `TRUE`，结果就是 `TRUE`**。

### 这张表解释了什么

```sql
-- 情况 1：查「有昵称的」
SELECT * FROM t WHERE nickname <> '张三';
-- id=1（nickname 是 NULL）：NULL <> '张三' → UNKNOWN → ❌ 过滤掉了
-- ⚠️ 但你的本意可能是「除了张三的都要」，那 id=1 也该出来！
```

⚠️ **这是一个真实的设计陷阱**：「查询所有非张三的用户」在有 NULL 的数据上会漏人。

**正确的写法**：

```sql
SELECT * FROM t WHERE nickname <> '张三' OR nickname IS NULL;
-- 或者用更直白的写法
SELECT * FROM t WHERE IFNULL(nickname, '') <> '张三';
```

### `NOT` 的 UNKNOWN 问题

```sql
SELECT * FROM t WHERE NOT (nickname = '张三');
-- id=1：NOT(UNKNOWN) → UNKNOWN → ❌ 过滤掉
-- ⚠️ NOT 和 NULL 组合，结果永远是 NULL，不是 TRUE
```

⭐ **规则**：`WHERE` 里出现 `NOT` 时要格外小心，因为任何 `UNKNOWN` 经过 `NOT` 还是 `UNKNOWN`，永远不会被选中。

### 实际的解决方案：`COALESCE`

```sql
-- 把 NULL 当成某个默认值再比较
SELECT * FROM t WHERE COALESCE(nickname, '') <> '张三';
SELECT * FROM t WHERE COALESCE(score, 0) > 60;
```

⚠️ **但注意**：`COALESCE` 会让列变成**表达式**，⚠️ **索引可能失效**（见第四节）。

## 二、逻辑运算符与优先级

### 优先级表（从高到低）

| 优先级 | 运算符 | 说明 |
|-------|--------|------|
| 1 | `()` | ⭐ **括号最高** |
| 2 | `NOT` | |
| 3 | `*` `/` `%` | 算术 |
| 4 | `+` `-` | 算术 |
| 5 | `=` `<=>` `>=` `>` `<=` `<` `<>` `!=` `IS` `LIKE` `IN` `BETWEEN` | 比较 |
| 6 | `AND` | |
| 7 | `OR` | ⚠️ **最低** |
| 8 | `:=` | 赋值 |

### ⚠️ `AND` 高于 `OR` 是高频错误

```sql
-- ❌ 你的本意：(1)或(2)
SELECT * FROM users WHERE dept_id = 1 OR dept_id = 2 AND status = 1;
-- ⚠️ 实际是：dept_id=1 或 (dept_id=2 且 status=1)

-- ✅ 加括号明确意图
SELECT * FROM users WHERE (dept_id = 1 OR dept_id = 2) AND status = 1;
```

### 推荐的查询写法：用 `IN` 代替 `OR`

```sql
-- ❌ 冗长
SELECT * FROM users WHERE dept_id = 1 OR dept_id = 2 OR dept_id = 3;

-- ✅ 更清晰
SELECT * FROM users WHERE dept_id IN (1, 2, 3);
```

⚠️ **`IN` 和 `OR` 性能几乎一样**（优化器会转换），但 `IN` 可读性更好。

⚠️ **`IN` 的 NULL 陷阱**（PostgreSQL 用户尤其要注意）：

```sql
-- ⚠️ 如果列表里有 NULL，且列中也有 NULL
SELECT * FROM users WHERE dept_id IN (1, 2, NULL);
-- ⚠️ 结果可能是空集！因为 dept_id=NULL 的行匹配失败
```

⭐ **永远不要在 `IN` 列表里放 `NULL`。**

## 三、日期条件

### 三种写法

```sql
-- ① 时间戳范围（最可靠）
SELECT * FROM orders WHERE created_at >= '2026-01-01 00:00:00'
                            AND created_at <  '2026-02-01 00:00:00';

-- ② 用函数（有索引失效风险，见下节）
SELECT * FROM orders WHERE DATE(created_at) = '2026-01-15';

-- ③ 用 EXTRACT
SELECT * FROM orders WHERE YEAR(created_at) = 2026 AND MONTH(created_at) = 1;
```

### ⭐ 为什么推荐「左闭右开」

```sql
-- ✅ 推荐
WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'

-- ❌ 不推荐（边界重复）
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
-- ⚠️ 如果有 '2026-01-31 23:59:59' 这条数据，会被漏掉！
```

**原因**：`BETWEEN` 是**闭区间**，包含两端。如果日期列是 `DATE` 类型没问题，但如果是 `DATETIME`，`BETWEEN '2026-01-01' AND '2026-01-31'` 实际是 `<= '2026-01-31 00:00:00'`，当天的其他时间都被漏掉。

📐 **记忆锚点：时间范围永远用「>= 起点 AND < 终点」。**

### 「最近 N 天」的写法

```sql
-- ✅ 正确
WHERE created_at >= NOW() - INTERVAL 7 DAY

-- ⚠️ 危险：DATE() 包裹会让索引失效
WHERE DATE(created_at) >= DATE_SUB(NOW(), INTERVAL 7 DAY)

-- ⚠️ 更危险：函数作用在列上
WHERE created_at >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)
-- ⚠️ CURDATE() 是函数调用，整个表达式不再是「列的简单比较」，索引可能失效
```

## 四、函数与索引失效 ⚠️★

### 什么是索引失效

```
没有索引时：扫描 100 万行 → 返回结果
有索引时：  索引查找 → 返回 10 行

如果 SQL 里对列做了函数/运算，MySQL 无法用索引「定位」，
只能扫描全部行再逐行计算——索引等于白建。
```

### 索引失效的场景

| 写法 | 索引 | ✅ 改法 |
|------|------|--------|
| `WHERE DATE(created_at) = '2026-01-15'` | ❌ | `WHERE created_at >= '2026-01-15' AND created_at < '2026-01-16'` |
| `WHERE YEAR(created_at) = 2026` | ❌ | `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| `WHERE salary * 1.1 > 3000` | ❌ | `WHERE salary > 3000 / 1.1` ⭐ **把运算移到常量侧** |
| `WHERE name LIKE '%张三'` | ❌ | `LIKE '张三%'`（前缀匹配能用索引） |
| `WHERE name LIKE '%张三%'` | ❌ | 全文索引，或生成列 |
| `WHERE id = '123'` | ⚠️ | `WHERE id = 123`（⚠️ 字符串和数字比较会隐式转换） |
| `WHERE col1 = col2`（都是列） | ❌ | 建复合索引或改写 |
| `WHERE COALESCE(nickname,'') = '张三'` | ❌ | ⭐ 生成列 + 索引 |

### ⭐ 核心原则

> **索引失效的本质：优化器无法把「表达式」和「索引中的原始值」对应起来。**
>
> **规律：函数和运算应该作用在「常量」上，而不是作用在「列」上。**

```sql
-- ❌ 函数在列上
WHERE DATE(created_at) = '2026-01-15'
-- ✅ 函数在常量上（右侧是常量，不影响列）
WHERE created_at = '2026-01-15 00:00:00'

-- ❌ 运算在列上
WHERE salary * 1.1 > 3000
-- ✅ 运算在常量侧
WHERE salary > 2727.27
```

### 索引下推（ICP）能救一部分

⚠️ **8.0 的索引下推（Index Condition Pushdown）** 能在存储引擎层提前过滤，减少回表，但**它不能改变「无法用索引定位」这个事实**——扫描照样要扫全表。

📌 详见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

### `LIKE` 的三种模式

| 模式 | 能用索引 | 说明 |
|------|---------|------|
| `LIKE '张三%'` | ✅ | 前缀匹配 |
| `LIKE '%张三'` | ❌ | 后缀匹配 |
| `LIKE '%张三%'` | ❌ | 任意位置匹配 |
| `LIKE '张_三'` | ❌ | `_` 通配 |

⭐ **`LIKE 'xxx%'` 之所以能用索引**，是因为 B+ 树的键是**有序的**，可以直接定位到前缀区间。而 `%xxx` 的顺序在索引里是散的。

⚠️ **`LIKE` 不区分大小写**（取决于 collation）：

```sql
WHERE name LIKE 'zhang%'    -- ✅ 能匹配 'Zhang'
WHERE name LIKE 'zhang%' COLLATE utf8mb4_bin   -- 区分大小写
```

⚠️ **`LIKE` 的转义**：

```sql
-- 查含 % 的字符串（用户搜索功能常见坑）
WHERE comment LIKE '%\%%' ESCAPE '\\'
-- 或者用 INSTR(comment, '%') > 0
```

## 五、常用函数及坑

### 字符串函数

```sql
CONCAT('a', 'b')                    -- 'ab'
CONCAT('a', NULL)                   -- ⚠️ NULL！
CONCAT_WS(',', 'a', NULL, 'b')      -- 'a,b'  ⭐ 跳过 NULL
IFNULL(x, 0)                        -- x 为 NULL 返回 0
COALESCE(a, b, c)                   -- 第一个非 NULL
LENGTH('中文')                      -- ⚠️ 6（字节）
CHAR_LENGTH('中文')                 -- ⭐ 2（字符）
SUBSTRING('abcdef', 2, 3)           -- 'bcd'（从 1 开始）
TRIM('  a  ')                       -- 'a'
REPLACE(s, from, to)
LPAD('7', 3, '0')                   -- '007'
LOCATE('cd', 'abcdef')              -- 3（位置从 1 开始）
```

⚠️ **三个高频坑**：

| 坑 | 说明 |
|---|---|
| ⚠️ `CONCAT` 遇 NULL 返回 NULL | 用 `CONCAT_WS` 或 `IFNULL` |
| ⚠️ `LENGTH` 是字节数 | 中文/emoji 场景用 `CHAR_LENGTH` |
| ⚠️ 位置从 **1** 开始 | `SUBSTRING(s, 0, 3)` 返回空串不是前 3 个 |

### 数值函数

```sql
ROUND(3.14159, 2)      -- 3.14
CEIL(3.1)              -- 4
FLOOR(3.9)             -- 3
TRUNCATE(3.99, 1)      -- 3.9（截断不四舍五入）
ABS(-5)                -- 5
MOD(10, 3)             -- 1
GREATEST(3, 7, 2)      -- 7
LEAST(3, 7, 2)         -- 2
```

⚠️ **`ROUND` vs `TRUNCATE`**：`ROUND` 四舍五入，`TRUNCATE` 直接截断。**金额场景通常用 `DECIMAL` 而不是这两个函数。**

### 日期函数

```sql
NOW()                                    -- 当前时间
CURDATE()                                -- 当前日期
DATE_ADD(NOW(), INTERVAL 7 DAY)
DATE_SUB(NOW(), INTERVAL 30 DAY)
DATEDIFF('2026-10-13', '2026-10-01')     -- 12（⚠️ 只算天）
TIMESTAMPDIFF(HOUR, a, b)                -- ⭐ 精确到任意单位
DATE_FORMAT(NOW(), '%Y-%m-%d')           -- ⚠️ 分钟是 %i 不是 %M
YEAR(d), MONTH(d), DAY(d)
LAST_DAY('2026-02-05')                   -- 2026-02-28
UNIX_TIMESTAMP(d) / FROM_UNIXTIME(ts)
```

⚠️ **`DAYOFWEEK` 的 1 是周日**：

```sql
DAYOFWEEK('2026-10-13')   -- 3（周二，⚠️ 从周日开始数）
WEEKDAY('2026-10-13')     -- 1（周二，从周一开始数）

-- 业务要「周一到周五」
WHERE DAYOFWEEK(d) IN (2,3,4,5,6)          -- 用 DAYOFWEEK
WHERE WEEKDAY(d) BETWEEN 0 AND 4           -- 用 WEEKDAY 更直观
```

⚠️ **⚠️ 日期函数作用在列上会索引失效**，见第四节。

### 聚合函数

```sql
COUNT(*)                    -- 总行数
COUNT(col)                  -- ⚠️ 非 NULL 的数量
COUNT(DISTINCT col)         -- 去重数量
SUM(col) / AVG(col)         -- ⚠️ 自动忽略 NULL
MIN(col) / MAX(col)
GROUP_CONCAT(col SEPARATOR ',')   -- ⚠️ 默认截断 1024 字节！
```

⚠️ **四个坑**：

#### 坑 1：`COUNT(col)` 不统计 NULL

```sql
-- 需求：统计用户数
SELECT COUNT(name) FROM users;    -- ❌ 少了 nickname 为 NULL 的用户
SELECT COUNT(*) FROM users;       -- ✅
SELECT COUNT(name, email) FROM users;   -- ⚠️ 多参数时等价于 COUNT(*)，只判断是否全 NULL
```

#### 坑 2：`GROUP_CONCAT` 的 1024 字节截断

```sql
SELECT GROUP_CONCAT(name) FROM users;
-- ⚠️ 结果被静默截断到 1024 字节，不报错！
```

```sql
-- 解决
SET SESSION group_concat_max_len = 1024000;
-- 或 my.cnf [mysqld] group_concat_max_len = 1024000
```

⚠️ **这是最隐蔽的 bug 之一**——数据量大时你会发现「少了很多人」，但没有任何报错。

#### 坑 3：`SUM` 忽略 NULL 但 `COUNT` 不忽略

```sql
-- 需求：计算平均分（有 3 个 NULL 成绩）
SELECT AVG(score) FROM students;        -- 只按 2 个有效值算
SELECT SUM(score)/COUNT(*) FROM students;  -- ⚠️ 除以 3，结果偏小
SELECT AVG(IFNULL(score, 0)) FROM students;  -- 明确是否把 NULL 当 0
```

⭐ **必须想清楚：NULL 是「没有成绩」还是「0 分」？业务语义不同，算法不同。**

#### 坑 4：`GROUP BY` 与 `ONLY_FULL_GROUP_BY`

⚠️ **MySQL 5.7.5 起默认开启严格模式**，此时 SELECT 里的非聚合列必须出现在 GROUP BY 中：

```sql
-- ⚠️ 严格模式下报错
SELECT dept_id, name, COUNT(*) FROM employees GROUP BY dept_id;

-- ✅ 两种改法
SELECT dept_id, name, COUNT(*) FROM employees GROUP BY dept_id, name;
SELECT dept_id, MAX(name) AS name, COUNT(*) FROM employees GROUP BY dept_id;
```

📌 详见 [[mysql/01-入门阶段-基础教程/第00章-学前准备/0.3-MySQL与PostgreSQL的差异]] 的行为差异表。

## 六、条件函数

```sql
IF(score >= 60, '及格', '不及格')                  -- MySQL 特有
CASE
  WHEN score >= 90 THEN 'A'
  WHEN score >= 80 THEN 'B'
  WHEN score >= 60 THEN 'C'
  ELSE 'F'
END
CASE dept_id                                   -- 简单映射
  WHEN 1 THEN '技术部'
  WHEN 2 THEN '市场部'
END
IFNULL(v, default)                              -- MySQL 特有
COALESCE(a, b, c)                               -- 标准 SQL
NULLIF(a, b)                                    -- a=b 时返回 NULL
```

⚠️ **`CASE` 是标准 SQL**，`IF`/`IFNULL` 是 MySQL 特有。⚠️ **跨库兼容的代码应该用 `CASE`/`COALESCE`。**

### 实战：`CASE` 做条件聚合

```sql
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN status = 1 THEN 1 ELSE 0 END) AS active,
  SUM(CASE WHEN status = 0 THEN 1 ELSE 0 END) AS inactive,
  SUM(CASE WHEN salary > 20000 THEN 1 ELSE 0 END) AS high_salary
FROM employees;
```

📌 更完整的条件聚合见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

## 七、`IS` 的用法

| 写法 | 含义 |
|------|------|
| `col IS NULL` | 判断是否为 NULL |
| `col IS NOT NULL` | 判断是否非 NULL |
| `col IS TRUE` / `IS FALSE` | 判断布尔值 |
| `a <=> b` | ⭐ **NULL 安全等于**：NULL = NULL 返回 TRUE |
| `a = b` | 普通等于，NULL 参与返回 UNKNOWN |

```sql
-- ⭐ 找「姓名相同或者都是 NULL」的行
WHERE name <=> NULL
WHERE a <=> b
```

⚠️ **`<=>` 用得少但很实用**，在需要「把 NULL 当普通值比较」的场景是唯一正确解。

## 八、陷阱

1. **❌ 用 `= NULL` 或 `<> NULL`。** 永远返回 0 行，要用 `IS NULL`。
2. **❌ `WHERE` 里出现 `NOT` 却不考虑 UNKNOWN。** UNKNOWN 永远不会被选中。
3. **❌ `IN (1, 2, NULL)`。** NULL 会导致结果异常。
4. **❌ 忘了 `AND` 优先级高于 `OR`。** 加括号。
5. **❌ 对列用函数/运算。** 索引失效。
6. **❌ `WHERE DATE(col) = ...`。** 改成范围比较。
7. **❌ `BETWEEN` 用在 `DATETIME` 上。** 用「>= 且 <」。
8. **❌ `COUNT(col)` 当总行数。** NULL 不计入。
9. **❌ 忘记调 `group_concat_max_len`。** 静默截断。
10. **❌ `AVG` 时不考虑 NULL 的业务语义。** 结果可能不是你想要的。
11. **❌ `LENGTH` 当字符数。** 中文/emoji 场景用 `CHAR_LENGTH`。
12. **❌ `CONCAT` 时忘记 NULL 的影响。**

## 小结

- ⭐ **三值逻辑**：`TRUE`/`FALSE`/**`UNKNOWN`**；NULL 参与比较结果是 UNKNOWN，而 WHERE 只选 TRUE
- `= NULL` / `<> NULL` **永远返回 0 行**；正确写法是 `IS NULL` / `IS NOT NULL`
- 真值表关键点：`AND` 中有 `FALSE` 就是 `FALSE`；`OR` 中有 `TRUE` 就是 `TRUE`
- `NOT` + UNKNOWN 永远是 UNKNOWN → 用 `COALESCE` 或 `OR ... IS NULL`
- ⚠️ **`AND` 优先级高于 `OR`**，多个 `OR` 条件要加括号
- `IN` 列表里绝不放 NULL
- ⭐ **索引失效的本质：函数/运算作用在「列」上。规律是把它们移到「常量」侧**
- `LIKE 'x%'` 能用索引，`LIKE '%x'` 不能
- 常见坑：`CONCAT` 遇 NULL、`LENGTH` 是字节数、`COUNT(col)` 忽略 NULL、`GROUP_CONCAT` 默认截断 1024 字节、`DAYOFWEEK` 1=周日、日期分钟格式符 `%i`
