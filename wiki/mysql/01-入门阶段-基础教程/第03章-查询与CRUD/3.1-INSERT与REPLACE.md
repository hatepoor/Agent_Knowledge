# INSERT 与 REPLACE

## 学习目标

读完本篇，你应当能够：

1. 掌握三种插入冲突处理策略的语法和差异
2. **说清 `REPLACE` 为什么危险**，并知道什么时候绝对不能用
3. 批量插入的正确写法及其性能收益
4. 用 `ON DUPLICATE KEY UPDATE` 做原子计数（比读改写好）
5. 知道 `LAST_INSERT_ID()` 的用法和坑
6. 理解「影响行数」的含义

## 一、基础插入

```sql
-- 单行
INSERT INTO users (name, email) VALUES ('张三', 'a@b.com');

-- 多行（⚠️ 比多次单行插入快得多）
INSERT INTO users (name, email) VALUES
  ('李四', 'b@c.com'),
  ('王五', 'd@e.com'),
  ('赵六', 'f@g.com');

-- 不指定列（⚠️ 危险，字段顺序变更时会出错）
INSERT INTO users VALUES ('张三', 'a@b.com', ...);
```

⚠️ **始终显式指定列名。** `INSERT INTO users VALUES (...)` 依赖表当前的列顺序，一旦有人加了列就全错位。

### 插入查询结果

```sql
-- 从一张表复制到另一张
INSERT INTO users_backup (name, email) SELECT name, email FROM users WHERE created_at < '2025-01-01';
```

⚠️ **`INSERT ... SELECT` 会加锁**，大数据量时影响线上业务，用 `pt-online-schema-change` 类的工具或分批。

## 二、三种冲突处理策略 ⚠️

⚠️ **核心问题：插入的主键或唯一键已存在时怎么办？**

### 策略一：`ON DUPLICATE KEY UPDATE`（推荐）

```sql
INSERT INTO users (id, name, email) VALUES (1, '张三', 'a@b.com')
  AS new
  ON DUPLICATE KEY UPDATE
    name = new.name,
    updated_at = CURRENT_TIMESTAMP;
```

⚠️ **8.0.20+ 的新写法**：在 `VALUES` 后加 `AS new`，用 `new.列名` 引用新值。

```sql
-- ⚠️ 旧写法（8.0.20 起弃用，但还能用）
INSERT INTO users (id, name, email) VALUES (1, '张三', 'a@b.com')
  ON DUPLICATE KEY UPDATE name = VALUES(name);
```

| 版本 | 写法 |
|------|------|
| 8.0.20 之前 | `ON DUPLICATE KEY UPDATE col = VALUES(col)` |
| **8.0.20+** | `VALUES (...) AS new ON DUPLICATE KEY UPDATE col = new.col` |

⚠️ **为什么推荐新写法**：旧写法 `VALUES(col)` 在解析时有歧义（和关键字 `VALUES` 冲突），MySQL 官方已标记弃用，未来会移除。

### 策略二：`INSERT IGNORE`

```sql
INSERT IGNORE INTO users (id, name, email) VALUES (1, '张三', 'a@b.com');
```

⚠️ **「IGNORE」不只忽略主键冲突**：

| 情况 | 行为 |
|------|------|
| 主键/唯一键冲突 | ⚠️ **跳过这一行**（警告） |
| 字段超长 | ⚠️ **截断后插入**（非严格模式） |
| NOT NULL 列为 NULL | ⚠️ **转成默认值** |
| 类型转换失败 | ⚠️ **转成 0 或空串** |

⚠️ **⚠️ 这就是 `INSERT IGNORE` 的危险：它会「尽力插入」而不是「失败」。** 在严格模式下有些情况仍会报错，但整体行为不可预测。

⭐ **只在一种场景用它：批量导入时「能导入多少算多少」，并且之后 `SHOW WARNINGS` 检查。**

### 策略三：`REPLACE`（⚠️ 最危险）

```sql
REPLACE INTO users (id, name, email) VALUES (1, '张三', 'a@b.com');
```

⚠️ **`REPLACE` 的真实语义是「删除冲突行 + 插入新行」，不是「更新」。**

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  name VARCHAR(64),
  email VARCHAR(255),
  bio TEXT,
  level INT DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 只改 name
REPLACE INTO users (id, name) VALUES (1, '新名字');
-- ⚠️ 结果：
--   name = '新名字'    ✅ 想要的
--   email = NULL       ❌ 未指定 → 默认值
--   bio = NULL         ❌ 未指定 → NULL
--   level = 0          ❌ 未指定 → 默认值
--   created_at = 重置   ❌ 变了
```

### `REPLACE` 的六个风险

| 风险 | 说明 |
|------|------|
| **⚠️ 未指定的列被重置** | 最常见的数据丢失 |
| **⚠️ 自增 ID 跳号** | 删除时消耗了 ID |
| **⚠️ 触发 `ON DELETE CASCADE`** | 删父行会级联删子行 |
| **⚠️ 触发器行为异常** | 只触发 `INSERT` 触发器，不触发 `DELETE` 和 `UPDATE` |
| **⚠️ 复制问题** | 基于语句的复制下可能不一致 |
| **⚠️ 冗余字段全丢** | 所有没写的列都归默认值 |

⚠️ **`REPLACE` 唯一可以接受的场景**：「整行替换」且你**确实**要清空未指定列。绝大多数情况下应该用 `ON DUPLICATE KEY UPDATE`。

### 三种策略对比

| 场景 | 用哪个 |
|------|--------|
| 幂等写入（重复就更新） | ⭐ `ON DUPLICATE KEY UPDATE` |
| 原子计数（`cnt = cnt + 1`） | ⭐ `ON DUPLICATE KEY UPDATE` |
| 批量导入，尽力而为 | `INSERT IGNORE`（+ 查 WARNINGS） |
| **整行替换**（明确要清空其他列） | `REPLACE`（少用） |
| **只更新部分列** | ⭐ **永远不要用 `REPLACE`** |

## 三、`ON DUPLICATE KEY UPDATE` 的三个高价值用法

### 用法 1：原子计数 ⭐

```sql
-- 累加访问次数
INSERT INTO page_views (page_id, views) VALUES (1, 1)
  ON DUPLICATE KEY UPDATE views = views + 1;
```

⚠️ **为什么不能「先 SELECT 再 UPDATE」**：

```python
# ❌ 有竞态条件
count = SELECT views FROM page_views WHERE page_id = 1
UPDATE page_views SET views = count + 1 WHERE page_id = 1
# ⚠️ 两个请求同时来，都读到 100，都写成 101 —— 丢了一次
```

⚠️ **⚠️ 逗号表达式的求值顺序陷阱**：

```sql
-- ❌ 危险
ON DUPLICATE KEY UPDATE views = views + 1, views = views + 1;
-- ⚠️ 第二个赋值用的是第一个赋值后的值，结果是 +2，但这依赖未定义行为

-- ✅ 明确用绝对增量（库存扣减同理）
ON DUPLICATE KEY UPDATE stock = stock - 1;
```

⚠️ **绝不要写 `col = col + 1, col = col + 1`**——同一个字段多次赋值，MySQL 从左到右求值，所以第二个 `col` 拿到的是更新后的值。结果数值上等于 +2，但**这不是文档保证的行为**，且可读性极差。

### 用法 2：条件更新（防止覆盖）

```sql
INSERT INTO stock (sku, qty) VALUES ('SKU001', 10)
  AS new ON DUPLICATE KEY UPDATE
    qty = IF(qty < 0, qty, new.qty);       -- 只在 qty 为负（异常态）时才更新
```

### 用法 3：避免无谓写入 ⭐

```sql
INSERT INTO users (id, name, updated_at) VALUES (1, '张三', NOW())
  AS new ON DUPLICATE KEY UPDATE
    name = new.name,
    -- ⚠️ 关键：只有 name 真变了才更新时间戳
    updated_at = IF(name <> new.name, CURRENT_TIMESTAMP, updated_at);
```

⚠️ **为什么重要**：无条件更新会导致每次调用都：
- 写一行到 binlog（主从延迟来源）
- 更新时间戳（让「最近修改」的语义失真）
- 触发缓存失效 / ES 同步
- 占用 undo log

📌 这个技巧在数据同步场景极其重要，见 [[redis/02-中段阶段-生产实践/09-缓存一致性-与数据库同步]]。

## 四、批量插入

### 三种写法与性能

```sql
-- ❌ 最慢：10000 次网络往返 + 10000 个事务
INSERT INTO t (a) VALUES (1);
INSERT INTO t (a) VALUES (2);
...

-- ⚠️ 好一些：1 次往返，但 1 个大事务
INSERT INTO t (a) VALUES (1),(2),(3),...;

-- ✅ 最好：分批，每批一个事务
INSERT INTO t (a) VALUES (1),(2),(3),(4),(5);   -- 500 行一批
INSERT INTO t (a) VALUES (6),(7),(8),(9),(10);
...
```

⚠️ **批量插入的关键是「批量大小」和「事务数量」的权衡**：

| 批大小 | 事务数 | redo log | 失败重做量 | 评价 |
|--------|-------|---------|-----------|------|
| 10 | 1000 | 小 | 少 | 网络往返多，慢 |
| 500~2000 | 适当 | 适中 | 适中 | ⭐ **推荐** |
| 10000 | 1 | 巨大 | ⚠️ 全部重做 | 主库压力大，易主从延迟 |

⚠️ **大批量插入会产生巨大的 redo log 和 binlog**，导致主从延迟。生产环境批量导入要：
1. 分批提交
2. 关闭或延迟 binlog（如果有从库）
3. 用 `LOAD DATA INFILE`（见下）

### `LOAD DATA INFILE`

⭐ **大批量导入的正规武器**，比 `INSERT` 快一到两个数量级。

```sql
LOAD DATA INFILE '/path/to/data.csv'
INTO TABLE employees
  CHARACTER SET utf8mb4
  FIELDS TERMINATED BY ',' ENCLOSED BY '"'
  LINES TERMINATED BY '\n'
  IGNORE 1 LINES
  (name, email, salary, hired_at)
  SET created_at = NOW(), updated_at = NOW();
```

⚠️ **关键点**：

| 要点 | 说明 |
|------|------|
| ⚠️ **文件必须在服务器上** | 不是客户端本地路径。要用 `LOCAL INFILE` 从客户端传（需服务端 `local_infile=1`） |
| ⚠️ **字符集要显式指定** | 不指定中文可能乱码 |
| ⚠️ **列名列表要对齐** | 不指定的列用默认值 |
| ⚠️ **错误日志** | 加 `... INTO OUTFILE '/tmp/errors.txt'` 看失败的行 |

⚠️ **`LOAD DATA` 会按行锁表还是表锁？** 8.0 的 InnoDB 在 `innodb_file_per_table` 下通常用行锁，但大批量时仍建议在低峰期执行。

## 五、`LAST_INSERT_ID()`

```sql
INSERT INTO users (name, email) VALUES ('张三', 'a@b.com');
SELECT LAST_INSERT_ID();      -- 返回刚生成的自增 ID
```

⚠️ **`LAST_INSERT_ID()` 的两个特性**：

| 特性 | 说明 |
|------|------|
| **是连接级的** | 每个连接各自维护，不是全局的 |
| **在同连接内一直有效** | 后续别的插入会覆盖它 |

```python
# ✅ 正确用法：在同一个连接里取
conn = pymysql.connect(...)
cur = conn.cursor()
cur.execute("INSERT INTO users (name) VALUES ('张三')")
new_id = cur.lastrowid        # ⭐ 驱动直接给了，不用再查
cur.execute("INSERT INTO logs (user_id) VALUES (%s)", (new_id,))
```

⚠️ **别在插入和取 ID 之间做别的插入**——那会覆盖 `LAST_INSERT_ID()`：

```python
cur.execute("INSERT INTO users (name) VALUES ('张三')")
cur.execute("INSERT INTO audit (action) VALUES ('x')")   # ❌ 覆盖了 lastrowid
id = cur.lastrowid            # ❌ 拿到的是 audit 表的 ID（如果没有自增则返回 0）
```

### `LAST_INSERT_ID(expr)` 的额外用途

```sql
INSERT INTO t (a, b) VALUES (10, 20);
SET @id = LAST_INSERT_ID();      -- 记下自动生成的 ID

INSERT INTO t (a, b) VALUES (@id, 30);   -- 用它当外键
```

⭐ **这是在一条 SQL 里传递自增 ID 的标准技巧**（因为 MySQL 不支持在 VALUES 里引用上一次的自增值）。

## 六、影响行数的含义 ⚠️

### `ROW_COUNT()`

```sql
-- INSERT 新增一行
INSERT INTO users (name) VALUES ('张三');
SELECT ROW_COUNT();    -- 1

-- UPDATE 改了值
UPDATE users SET name = '李四' WHERE id = 1;
SELECT ROW_COUNT();    -- 1

-- ⚠️ UPDATE 改成一样的值
UPDATE users SET name = '李四' WHERE id = 1;
SELECT ROW_COUNT();    -- 0  ← 值没变
```

⚠️ **`ROW_COUNT()` 返回 0 不一定是失败**，可能是「值本来就一样」。

⚠️ **⚠️ 但要小心这个默认行为**：

```ini
[mysqld]
mysql affected_rows = on      # 默认
# client_found_rows = on      # ⚠️ 如果打开这个，UPDATE 无变化也返回 1
```

⚠️ **`client_found_rows`**：部分驱动（如 MySQL Connector/J 的某些配置、Go 的 `interpolateParams`）会打开它，让 UPDATE 无变化时返回 1 而不是 0。⚠️ **依赖影响行数做乐观锁时，必须确认这个配置。**

### `FOUND_ROWS()` 与 `SQL_CALC_FOUND_ROWS`

```sql
-- ⚠️ 为了拿「符合条件的总行数」，把结果全查出来
SELECT SQL_CALC_FOUND_ROWS * FROM users WHERE status = 1 LIMIT 10;
SELECT FOUND_ROWS();    -- 总数

-- 更好的做法（8.0+ 窗口函数）
SELECT COUNT(*) OVER () AS total FROM users WHERE status = 1 LIMIT 10;
```

⚠️ **`SQL_CALC_FOUND_ROWS` 会扫全表**。数据量大时用窗口函数或两次查询。

📌 分页总数的正确做法见 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.3-ORDER-BY排序与分页]]。

## 七、`INSERT ... SELECT` 与锁

```sql
INSERT INTO orders_backup (order_no, amount)
SELECT order_no, amount FROM orders WHERE created_at < '2025-01-01';
```

⚠️ **`INSERT ... SELECT` 的锁行为**：

| 隔离级别 | 行为 |
|---------|------|
| `REPEATABLE READ`（默认） | ⭐ **共享锁（S）** 读源表，允许并发读但阻塞写 |
| `READ COMMITTED` | 加间隙锁，间隙被锁住，其他事务不能插 |

⚠️ **⚠️ 大表 `INSERT ... SELECT` 会长时间持有锁，影响线上业务。** 缓解方案：

```sql
-- 分批：先查 ID 范围，再逐批插入
INSERT INTO orders_backup (order_no, amount)
SELECT order_no, amount FROM orders WHERE id BETWEEN 1 AND 10000;
INSERT INTO orders_backup (order_no, amount)
SELECT order_no, amount FROM orders WHERE id BETWEEN 10001 AND 20000;
```

📌 在线 DDL 方案见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。

## 八、陷阱

1. **❌ 用 `REPLACE` 当更新。** 它是删除+插入，会丢数据。
2. **❌ `INSERT INTO t VALUES (...)` 不指定列名。** 列顺序变更就错位。
3. **❌ 在 `ON DUPLICATE KEY UPDATE` 里写 `col = col + 1, col = col + 1`。** 行为不可靠。
4. **❌ 用「先 SELECT 再 UPDATE」做计数。** 有竞态，要用 `ON DUPLICATE KEY UPDATE`。
5. **❌ 在插入和取 `LAST_INSERT_ID()` 之间做别的插入。** 会被覆盖。
6. **❌ 批量插入不分批。** 巨大的 redo/binlog 造成主从延迟。
7. **❌ `LOAD DATA INFILE` 不指定 `CHARACTER SET`。** 中文乱码。
8. **❌ 依赖 `ROW_COUNT()` 判断「更新成功」却不检查 `client_found_rows`。**
9. **❌ 大表 `INSERT ... SELECT` 不分批。** 长时间持锁。
10. **❌ 在 8.0.20+ 还用 `VALUES(col)` 写法。** 已弃用。

## 小结

- 三种冲突策略：`ON DUPLICATE KEY UPDATE`（**首选**）/ `INSERT IGNORE`（尽力插入）/ `REPLACE`（**删除+插入，危险**）
- **⚠️ `REPLACE` 的六个风险**：未指定列被重置、自增跳号、触发级联删除、触发器行为异常、复制问题、冗余字段丢失
- **8.0.20+ 用 `AS new ON DUPLICATE KEY UPDATE col = new.col`**，旧的 `VALUES(col)` 已弃用
- **原子计数**必须用 `ON DUPLICATE KEY UPDATE col = col + 1`（读改写有竞态）
- 「值真变了才更新」的 `IF(旧值 <> 新值, ...)` 能显著减少 binlog 和缓存失效
- 批量插入：**500~2000 行一批**；大批量用 `LOAD DATA INFILE`（记得字符集）
- ⚠️ 插入与取 `LAST_INSERT_ID()` 之间不能有别的插入；可用 `LAST_INSERT_ID(expr)` 在一条 SQL 里传递 ID
