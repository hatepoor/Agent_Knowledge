## 一、基础排序

### 单列与多列

```sql
-- 升序（默认 ASC）/ 降序（DESC）
SELECT * FROM employees ORDER BY salary;

-- 多列：先按部门排，同部门内按薪资从高到低
SELECT * FROM employees
ORDER BY dept_id ASC, salary DESC;
```

⭐ **多列排序靠「字典序」**：逐列比较，前一列相同时才看后一列。所以**排序列的顺序很重要**。

### `NULL` 的排序位置 ⚠️★

⚠️ **这是本篇最重要的坑。**

| 排序方向 | MySQL 中 NULL 的位置 | PostgreSQL 中 NULL 的位置 |
|---------|--------------------|------------------------|
| `ORDER BY col ASC` | ⚠️ **排在最前** | 排在最后 |
| `ORDER BY col DESC` | ⚠️ **排在最后** | 排在最前 |

⚠️ **两个数据库的行为完全相反！**

### 这会导致什么 bug

```sql
-- 需求：取最近修改的 10 条记录
SELECT * FROM docs ORDER BY updated_at DESC LIMIT 10;
```

⚠️ **如果有记录的 `updated_at` 是 NULL（刚创建还没更新），MySQL 的 `DESC` 会把它们排在最后**——这倒是符合直觉。

但换成升序就出问题了：

```sql
-- 需求：取最早创建的 10 条
SELECT * FROM docs ORDER BY created_at ASC LIMIT 10;
-- ⚠️ MySQL 里 NULL 排在最前 → 拿到的是一堆 NULL 的记录！
```

### 三种修正写法

```sql
-- ① 显式过滤（最简单，如果不需要 NULL）
SELECT * FROM docs WHERE created_at IS NOT NULL ORDER BY created_at ASC LIMIT 10;

-- ② 用 CASE 明确指定 NULL 位置（MySQL 不支持 NULLS LAST 语法）
SELECT * FROM docs
ORDER BY created_at IS NULL, created_at ASC
LIMIT 10;

-- ③ 8.0 没有 NULLS LAST，需要用 CASE
SELECT * FROM docs
ORDER BY CASE WHEN created_at IS NULL THEN 1 ELSE 0 END, created_at
LIMIT 10;
```

⚠️ **⚠️ MySQL 不支持 `ORDER BY x NULLS LAST` 语法**（PostgreSQL 支持）。这是从 PG 迁移时的高频错误。

⚠️ **⚠️ 注意：`CASE` 和 `IS NULL` 表达式会让索引失效**（见下文）。⚠️ 如果排序列大量为 NULL 且性能敏感，考虑在表设计时用 `NOT NULL DEFAULT '1970-01-01'`。

### 多列 NULL 排序

```sql
-- 让 NULL 永远排在最后（无论升降序）
ORDER BY (col IS NULL), col DESC
--  (col IS NULL) 返回 0 或 1，false 排前 → NULL 自动最后
```

## 二、`ORDER BY` 与索引

### 什么时候能用索引

⭐ **规则：`ORDER BY` 的列顺序必须和索引的列顺序一致（最左前缀），且排序方向一致。**

```sql
-- 索引
KEY idx_dept_salary (dept_id, salary)

-- ✅ 能用索引排序
SELECT * FROM employees WHERE dept_id = 1 ORDER BY salary DESC;
SELECT * FROM employees ORDER BY dept_id, salary;        -- 无 WHERE 也可以
SELECT * FROM employees WHERE dept_id > 0 ORDER BY dept_id, salary;

-- ❌ 不能用（列顺序不符）
SELECT * FROM employees WHERE dept_id = 1 ORDER BY salary, dept_id;
-- ❌ 不能用（跳跃）
SELECT * FROM employees WHERE dept_id = 1 ORDER BY salary;
-- ⚠️ dept_id 是等值条件时，salary 能用（这是"索引跳跃"，MySQL 支持）
-- ❌ 不能用（混合方向）
SELECT * FROM employees ORDER BY dept_id ASC, salary DESC;
-- ⚠️ dept_id 无 WHERE 时，混合方向需要 8.0+ 的降序索引支持
```

### 8.0 的降序索引

```sql
-- 8.0+ 支持真正的降序索引
CREATE INDEX idx_ord ON t (a ASC, b DESC);

-- 现在这个查询能用索引
SELECT * FROM t ORDER BY a ASC, b DESC;
-- 在 8.0 之前：MySQL 会反向扫描整个索引，
--             如果 a 的方向也不匹配就彻底不行
```

⚠️ **8.0 之前混合方向排序只能 filesort。**

### `filesort` 是什么

⚠️ **`Using filesort` 不表示「在磁盘排序」！** 它表示「**不能用索引顺序，需要额外排序**」——可能在内存里排（数据量小时），也可能在磁盘（数据量大时）。

```sql
EXPLAIN SELECT * FROM employees ORDER BY age\G
-- Extra: Using filesort
-- ⚠️ age 列没有索引
```

⚠️ **判断是否真的慢**：看 `rows` 和 `sort_merge_passes`。⚠️ **⚠️ `Using temporary` + `Using filesort` 同时出现才是危险信号**（分组 + 排序都要额外开表）。

📌 完整的执行计划分析见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/EXPLAIN解读]]。

### CASE 自定义排序

⚠️ **需求：按状态排序，且状态有业务优先级（不是字母顺序）**

```sql
-- 需求：待付款 > 待发货 > 已完成 > 已取消
SELECT * FROM orders
ORDER BY CASE status
  WHEN 'pending'  THEN 1
  WHEN 'paid'     THEN 2
  WHEN 'shipped'  THEN 3
  WHEN 'cancelled' THEN 4
  ELSE 5
END;
```

⚠️ **`CASE` 表达式必然导致 filesort**（无法用索引）。数据量大时的替代方案：

```sql
-- 方案 2：表里加一个 priority 列，排序后再同步
-- 优点：能建索引
ORDER BY priority, id;
```

## 三、`LIMIT` 的准确语义 ⚠️

### `LIMIT n, m` 不是「取 n 行跳过 m 行」

```sql
-- 语法：LIMIT [偏移量, ]行数
-- LIMIT n, m  ⭐ 跳过前 n 行，取 m 行

LIMIT 10, 5      -- ⭐ 跳过 10 行，取 5 行（第 11~15 条）
LIMIT 5          -- 取前 5 行（等价于 LIMIT 0, 5）
```

⚠️ **⚠️ 这是与 PostgreSQL 顺序相反的地方**：

```sql
-- PostgreSQL：LIMIT m OFFSET n（行数在前）
LIMIT 5 OFFSET 10        -- 取 5 行，跳过 10 行

-- MySQL：LIMIT n, m（偏移在前）
LIMIT 10, 5              -- 跳过 10 行，取 5 行
-- ⭐ 两者等价！
```

⚠️ **从 PG 迁移时，⚠️ `LIMIT 5 OFFSET 10` 直接翻译成 `LIMIT 5, 10` 是错的**（那会变成「跳过 5 取 10」）。

### 两条等价写法

```sql
-- 写法 1
LIMIT 10, 5

-- 写法 2（更清晰，和 PG 一致）
LIMIT 5 OFFSET 10
```

⭐ **推荐用写法 2**——它和 PostgreSQL 语法一致，减少迁移出错的机会。

📌 完整差异见 [[mysql/01-入门阶段-专题基础/00-章节目录#MySQL↔PostgreSQL语法差异速查|速查索引]]。

## 四、深分页问题 ★★

### 问题

```sql
-- 取第 1000001 到 1000020 条
SELECT * FROM articles ORDER BY id LIMIT 1000000, 20;
```

**这个查询做了什么**：

```
① 扫描/定位到第 1000001 行          ← 核心开销
② 丢掉前 1000000 行
③ 取接下来的 20 行
```

⚠️ **MySQL 必须先处理掉前面的一百万行**，即使你只要 20 行。数据量越大越慢：

| 偏移量 | 耗时量级 |
|--------|---------|
| 1,000 | 毫秒 |
| 100,000 | 百毫秒 |
| 1,000,000 | ⚠️ 秒级 |
| 10,000,000 | ⚠️ 十秒级 |

### ⭐ 键集分页（游标分页）

**核心思想：不要「跳过 N 行」，而是「记住上一页最后一行在哪」。**

```sql
-- 第 1 页
SELECT * FROM articles ORDER BY id LIMIT 20;
-- 假设最后一行的 id = 20

-- 第 2 页：WHERE id > 20
SELECT * FROM articles WHERE id > 20 ORDER BY id LIMIT 20;
-- 假设最后一行的 id = 40

-- 第 3 页
SELECT * FROM articles WHERE id > 40 ORDER BY id LIMIT 20;
```

**为什么快**：

| 方案 | 扫描量 |
|------|--------|
| `LIMIT 1000000, 20` | 扫描 1000020 行 |
| `WHERE id > 1000000 LIMIT 20` | ⭐ **扫描 20 行**（索引直接定位） |

⚠️ **无论第几页，耗时都是恒定的。**

### 键集分页的三种变体

#### 变体 1：单列游标

```sql
SELECT * FROM articles WHERE id > %s ORDER BY id LIMIT 20;
```

⚠️ **只能用于「向前翻页」，不能跳到第 N 页。**

#### 变体 2：复合排序游标

⚠️ **排序列不唯一时，必须把所有排序列都带上。**

```sql
-- 排序：ORDER BY created_at DESC, id DESC
-- 游标：上一页最后一行的 (created_at, id)
SELECT *
FROM articles
WHERE (created_at, id) < (%s, %s)          -- ⭐ 行值比较
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

⚠️ **⚠️ 必须加 `id` 作为「打破平局」的列。** 否则 `created_at` 相同的多行会被漏掉或重复：

```sql
-- ❌ 有 bug
SELECT * FROM articles WHERE created_at < %s ORDER BY created_at DESC LIMIT 20;
-- ⚠️ 假设有 5 行 created_at 完全相同，这 5 行里只有一部分能被查到

-- ✅ 加 id 打破平局
WHERE (created_at, id) < (%s, %s)
ORDER BY created_at DESC, id DESC
```

⚠️ **行值比较 `(a, b) < (x, y)` 是标准 SQL**，MySQL 和 PG 都支持。

⚠️ **⚠️ 用 OR 写的等价版本无法用索引**：

```sql
-- ❌ 等价但慢（无法用索引）
WHERE created_at < %s OR (created_at = %s AND id < %s)

-- ✅ 用行值比较（能用索引）
WHERE (created_at, id) < (%s, %s)
```

#### 变体 3：反向翻页

```sql
-- 在第 100 页，用户点了「上一页」
-- ⭐ 先 LIMIT 1, 1 取「上一页的第一条」
SELECT * FROM articles ORDER BY id DESC LIMIT 1, 1;
-- 拿到 id = X

-- 然后取 X 之后的 N 条，再反转显示
SELECT * FROM articles WHERE id >= %s ORDER BY id LIMIT 21;
```

⚠️ **前后翻页的实现**，比键集分页更复杂但体验更好。

### 键集分页的三个限制

| 限制 | 说明 |
|------|------|
| **不能跳页** | 用户没法直接点「第 500 页」 |
| **游标要编码给前端** | 上一页的游标值要传给前端 |
| **不适合需要总数的场景** | 「共 12345 条，第 3 页」——总数还是要单独查 |

### 混合分页方案

⚠️ **实际产品常用的折中**：

```python
# 快速跳页用偏移（因为前几页很快）
if page <= 10:
    sql = "SELECT * FROM t ORDER BY id LIMIT %s, 20"
# 继续翻页用键集（因为深页很慢）
else:
    sql = "SELECT * FROM t WHERE id > %s ORDER BY id LIMIT 20"
```

## 五、带总数的分页

### 需求

「共 12345 条，第 3 页」

### 方案一：两次查询（推荐）

```sql
-- 第一次：查总数（有缓存时更快）
SELECT COUNT(*) FROM articles WHERE status = 'published';

-- 第二次：查当页数据
SELECT * FROM articles WHERE status = 'published' ORDER BY id LIMIT 40, 20;
```

⚠️ **总数查询可能很慢**（`COUNT(*)` 在大表上要扫）。优化手段：
- 加缓存（总数变化不频繁时）
- 用近似总数（`information_schema.TABLES` 的统计信息，`⚠️ 不精确但快`）
- 前端改成「加载更多」不显示总数

### 方案二：`SQL_CALC_FOUND_ROWS`（⚠️ 有坑）

```sql
SELECT SQL_CALC_FOUND_ROWS * FROM articles WHERE status = 'published' LIMIT 40, 20;
SELECT FOUND_ROWS();    -- 总数
```

⚠️ **两个问题**：
1. **它会扫全表**（为了算总数），和 `LIMIT` 的优化冲突
2. ⚠️ **有 BUG**：⚠️ 如果查询里有 `ORDER BY` 或 `GROUP BY`，或使用 InnoDB 的间隙锁，`FOUND_ROWS()` 的结果可能不准确

⭐ **不建议用。**

### 方案三：窗口函数（8.0+，最优雅）

```sql
SELECT *,
       COUNT(*) OVER () AS total_count    -- ⭐ 一次查询拿到总数
FROM articles
WHERE status = 'published'
ORDER BY id
LIMIT 40, 20;
```

⚠️ **限制**：`COUNT(*) OVER ()` 的窗口是「查询开始到结束的所有行」，所以它**也会扫描全部行**——和方案一性能接近，但没有两次往返。

### 方案四：覆盖索引拿总数（最快）

```sql
-- 用一个「只含索引列」的查询，数索引条目（比扫行快）
SELECT COUNT(id) FROM articles WHERE status = 'published';
```

⚠️ **⚠️ 只有当 `status` 在索引里时才能这么优化。** InnoDB 的二级索引比聚簇索引小，扫描更快。

📌 优化手段汇总见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]。

## 六、排序的常见场景

### 按「最近更新」

```sql
-- ⚠️ 需要索引 (updated_at, id)
SELECT * FROM docs ORDER BY updated_at DESC, id DESC LIMIT 20;
```

⚠️ **`updated_at` 必须建索引**，否则每次都要全表排序。⚠️ 而且 ⚠️ **`updated_at` 大量重复**（同一秒多次更新），所以要加 `id` 打破平局。

### 按「热度」排序

```sql
-- 如果「热度」是一个统计字段
SELECT * FROM articles ORDER BY view_count DESC LIMIT 20;
-- ⚠️ view_count 应该和 id 组成联合索引 (view_count, id)

-- 如果「热度」要实时算（互动量/时间衰减）
SELECT * FROM articles
ORDER BY (view_count * 1.0 / POW(HOUR(NOW() - created_at) + 2, 1.5)) DESC
LIMIT 20;
-- ⚠️ 这种复杂表达式必然 filesort，且计算成本高
-- ✅ 生产做法：用定时任务把分数算好存起来
```

### 按「分组内排名」

```sql
-- 每个部门薪资前 3 名（窗口函数，8.0+）
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn
  FROM employees
) t
WHERE rn <= 3;
```

📌 完整的排名/同比环比实战见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/覆盖索引与回表优化]]。

## 七、陷阱

1. **❌ 忘了 MySQL 的 NULL 排序位置和 PG 相反。** `DESC` 时 NULL 在最后，`ASC` 时在**最前**。
2. **❌ 用 `ORDER BY x NULLS LAST`。** MySQL 不支持这个语法。
3. **❌ 把 `LIMIT 5 OFFSET 10` 翻译成 `LIMIT 5, 10`。** ⚠️ 语义完全相反。
4. **❌ 深分页用 `LIMIT 1000000, 20`。** 用键集分页。
5. **❌ 键集分页只用单个排序列。** ⚠️ 排序不唯一时会漏行/重复，必须加打破平局的列。
6. **❌ 用 OR 代替行值比较。** `WHERE (a,b) < (x,y)` 才能用索引。
7. **❌ `ORDER BY` 的列没有索引。** 每次全表 filesort。
8. **❌ 以为 `Using filesort` 就是在磁盘排序。** 它只表示「不能用索引顺序」。
9. **❌ 用 `SQL_CALC_FOUND_ROWS` 拿总数。** 会扫全表且结果可能不准。
10. **❌ 排序方向与索引方向不一致。** 8.0 前无法用索引。

## 小段

- ⚠️ **NULL 排序位置：MySQL `ASC` 时在最前、`DESC` 时在最后（与 PG 相反）**，用 `ORDER BY (col IS NULL), col` 强制 NULL 最后
- MySQL **不支持** `NULLS LAST` 语法
- `ORDER BY a, b` 按字典序，前列相同时才看后列；8.0+ 支持真正的降序索引
- **`Using filesort` ≠ 磁盘排序**，只表示「不能用索引顺序」；⚠️ `Using temporary` + `Using filesort` 同时出现才危险
- ⚠️ **`LIMIT n, m` 是「跳过 n 行取 m 行」**，与 PG 的 `LIMIT m OFFSET n` 顺序相反（推荐用 `LIMIT m OFFSET n` 保持一致）
- ⭐ **深分页的本质是要处理掉前 N 行**；**键集分页 `WHERE id > 游标` 扫描量恒定**
- 键集分页**必须加打破平局的列**，用行值比较 `(a,b) < (x,y)`（比 OR 写法能用索引）
- 拿总数：两次查询 / 窗口函数 `COUNT(*) OVER ()` / 覆盖索引，⚠️ 不要用 `SQL_CALC_FOUND_ROWS`
