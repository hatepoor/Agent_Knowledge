## 一、`JSON` 类型

### 定义

> **`JSON` 类型以二进制格式存储 JSON 文档**，MySQL 会校验合法性并优化存取。

```sql
CREATE TABLE products (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64) NOT NULL,
  attrs JSON NULL
);

INSERT INTO products (name, attrs) VALUES
  ('手机', '{"color":"black","storage":256}'),
  ('耳机', '{"color":"white"}');
```

### ⚠️ 三个主要限制

#### 限制 1：不能建普通索引

⚠️ **这是最大的限制。**

```sql
-- ❌ 不行
CREATE INDEX idx_attrs ON products (attrs);
CREATE INDEX idx_attrs ON products (attrs(100));   -- 前缀索引也不支持
```

⭐ **解法：生成列间接索引**（见第五节）。

#### 限制 2：不能有默认值

```sql
-- ❌ 报错
CREATE TABLE t (attrs JSON DEFAULT '{}');
-- ERROR 1101
```

⭐ **解法**：设 `NULL`，在应用层处理；或用表达式 `DEFAULT (JSON_OBJECT())`。

#### 限制 3：⚠️ 不能完全替代关联表

见第四节「JSON vs 关联表」。

## 二、查询 JSON

### 两种操作符 ⭐

```sql
-- attrs->>'$.color'  → 取值并去引号（⭐ 最常用）
SELECT attrs->>'$.color' FROM products;
-- black

-- attrs->'$.color'   → 取值但保留引号
SELECT attrs->'$.color' FROM products;
-- "black"
```

⚠️ **`->` 和 `->>` 的区别只有引号。**

### 等价的函数写法

```sql
-- 这两个等价
SELECT attrs->>'$.color' FROM products;
SELECT JSON_UNQUOTE(JSON_EXTRACT(attrs, '$.color')) FROM products;

-- 这两个等价
SELECT attrs->'$.color' FROM products;
SELECT JSON_EXTRACT(attrs, '$.color') FROM products;
```

⭐ **`JSON_EXTRACT` 返回的字符串带引号，所以基本都要包一层 `JSON_UNQUOTE`——这就是 `->>` 存在的原因。**

### 条件查询

```sql
-- 注意：JSON 值要加引号
SELECT * FROM products WHERE attrs->>'$.color' = 'black';

-- 数组包含
SELECT * FROM products WHERE JSON_CONTAINS(attrs, '256', '$.storage');

-- 数组/对象长度
SELECT id, JSON_LENGTH(attrs, '$.tags') FROM products;
```

### 常用 JSON 函数

| 函数 | 作用 |
|------|------|
| `JSON_EXTRACT(doc, path)` | 按路径取值（带引号） |
| `JSON_UNQUOTE(v)` | 去引号 |
| `JSON_SET(doc, path, val)` | 设置值 |
| `JSON_INSERT(doc, path, val)` | 仅当路径不存在时插入 |
| `JSON_ARRAY(...)` | 构造数组 |
| `JSON_OBJECT(k, v, ...)` | 构造对象 |
| `JSON_LENGTH(doc, path)` | 数组长度或对象键数 |
| `JSON_CONTAINS(doc, val, path)` | 是否包含 |
| `JSON_MERGE_PATCH(d1, d2)` | 合并（8.0.3+） |
| ⭐ `JSON_TABLE(...)` | ⭐ 把 JSON 展开成行 |
| `JSON_VALID(s)` | 是否合法 JSON |

## 三、`JSON_TABLE`：把数组展开成行 ⭐

### 场景

```sql
CREATE TABLE products (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(64),
  tags JSON
);

INSERT INTO products VALUES
  (1, '手机', '["electronics","hot","sale"]'),
  (2, '耳机', '["electronics"]');
```

### 展开

```sql
SELECT p.id, p.name, t.tag
FROM products p
JOIN JSON_TABLE(
  p.tags,                                    -- 源数组
  '$[*]' COLUMNS (tag VARCHAR(50) PATH '$') -- 每个元素取成 tag 列
) AS t;
```

**结果**：

```
id | name | tag
1  | 手机  | electronics
1  | 手机  | hot
1  | 手机  | sale
2  | 耳机  | electronics
```

### ⚠️ 三个限制

| 限制 | 说明 |
|------|------|
| ⚠️ **每次查询都要展开** | 无法索引，每次都算 |
| ⚠️ **数据量大时开销大** | 10 万行 × 5 个标签 = 50 万次展开 |
| ⚠️ **不能有外键** | 一致性要靠应用 |

⭐ **所以 `JSON_TABLE` 适合「临时查询/导出」，不适合高频查询。**

## 四、JSON vs 关联表 ⭐

### 决策树

```
这个多值字段需要：
├── 按它 JOIN 别的表？        → 是 → 关联表
├── 按它高频查询/筛选？        → 是 → 关联表
├── 按它排序/统计？            → 是 → 关联表
├── 需要外键保证一致？         → 是 → 关联表
└── 只是存下来偶尔整体读？    → 否 → ⭐ JSON 可以
```

### 三方对比

| 维度 | JSON | 关联表 |
|------|------|--------|
| 能建索引 | ❌（要生成列） | ⭐ ✅ |
| 能加外键 | ❌ | ⭐ ✅ |
| 读取方便 | ⭐ ✅ | 要 JOIN |
| 一致性保证 | ⚠️ 靠应用 | ⭐ 数据库保证 |
| 结构灵活 | ⭐ ✅ | ❌ 要改表 |

### ⚠️ 订单明细这类数据绝对不能用 JSON

```
订单明细需要：
  · 按商品统计销量        → 要 JOIN 商品表
  · 单条明细退款          → 要操作独立行
  · 明细金额参与对账      → 要 SUM
  · 外键保证商品存在      → 要外键

⭐ 全都需要独立行 → 必须拆关联表
```

📌 详见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.3-表设计规范与反范式]]。

## 五、生成列：给表达式建索引 ⭐

### 两种类型

| 类型 | 是否存数据 | 能否建索引 |
|------|----------|----------|
| `VIRTUAL` | ❌ 只存计算公式 | ✅ |
| ⭐ `STORED` | ✅ 存结果 | ✅ |

```sql
CREATE TABLE t (
  first_name VARCHAR(32),
  last_name  VARCHAR(32),
  -- VIRTUAL：读时计算，不占存储
  full_name VARCHAR(65) GENERATED ALWAYS AS (CONCAT(first_name,' ',last_name)) VIRTUAL,
  -- STORED：写时计算并存储，读得快
  name_upper VARCHAR(65) GENERATED ALWAYS AS (UPPER(first_name)) STORED,
  INDEX idx_full (full_name),
  INDEX idx_upper (name_upper)
);
```

### 三个用途

| 用途 | 说明 |
|------|------|
| ⭐ **给表达式建索引** | 最主要的用途 |
| ⭐ **间接索引 JSON** | 见下 |
| 派生列冗余 | 存一个由其他列算出来的值 |

### ⭐ 间接索引 JSON

```sql
ALTER TABLE products ADD COLUMN color VARCHAR(20)
  GENERATED ALWAYS AS (attrs->>'$.color') STORED;
CREATE INDEX idx_color ON products (color);

-- 现在能走索引了
SELECT * FROM products WHERE color = 'black';
```

⚠️ **⚠️ 生成列只能索引 JSON 的「固定路径」**——`attrs->>'$[*]'`（所有元素）**无法索引**。

### ⚠️ 生成列的限制

| 限制 | 说明 |
|------|------|
| 只能引用本行的列 | 不能引用其他表 |
| 不能用子查询 | |
| ⚠️ **不能用非确定性函数** | ⭐ `NOW()`、`RAND()` 不行 |
| 不能引用自增列 | |
| `STORED` 列不能有 `DEFAULT` | |
| 改基列会重建表 | ⚠️ 大表上是重操作 |

⚠️ **⚠️ `NOW()` 不能用在生成列里**——所以「自动更新时间」要用 `ON UPDATE CURRENT_TIMESTAMP`（真实列），不是生成列。

## 六、`ENUM` 与 `SET`

### 定义

```sql
CREATE TABLE orders (
  status ENUM('pending','paid','shipped','cancelled') NOT NULL DEFAULT 'pending',
  tags SET('vip','urgent','gift') NULL
);
```

| | `ENUM` | `SET` |
|---|---|---|
| 能选几个 | ⭐ **只能一个** | ⭐ **多个组合** |
| 存储 | 内部是整数（1,2,3…） | 位图 |
| 最多 | 65,535 个值 | 64 个成员 |

### ⚠️ `ENUM` 的三个问题

| 问题 | 说明 |
|------|------|
| ⚠️ **① 加值要改表结构** | `ENUM('a','b')` 加 `'c'` 要 `ALTER TABLE`，大表上很贵 |
| ⚠️ **② 跨环境值序可能不一致** | ⚠️⚠️ **A 环境是 `('pending','paid')`，B 环境是 `('paid','pending')`，导出的数据含义相反** |
| ⚠️ **③ 看不到实际值** | 查表看到的是数字 `1`，要看原文得对着代码 |

### ⭐ 替代方案

```sql
-- 用 VARCHAR + CHECK 约束
CREATE TABLE orders (
  status VARCHAR(16) NOT NULL DEFAULT 'pending',
  CONSTRAINT ck_status CHECK (status IN ('pending','paid','shipped','cancelled'))
);
```

| 优点 | 说明 |
|------|------|
| ✅ 加值不用改表结构 | 改 CHECK 约束即可（且可在线） |
| ✅ 跨环境一致 | 存的是字符串本身 |
| ✅ 可读 | 查出来就是 `'pending'` |

⚠️ **⚠️ `CHECK` 约束在 8.0.15 之前是「解析但不执行」**，8.0.15+ 才真正强制。⚠️ **且 `CHECK` 不检查已有数据**——加约束前要先修存量违规数据。

📌 详见 [[mysql/01-入门阶段-基础教程/第02章-建表与约束/2.2-约束体系与数据完整性]]。

## 七、`BOOLEAN` 与二进制类型

### `BOOLEAN` 是什么

⚠️ **MySQL 没有真正的布尔类型。**

```sql
CREATE TABLE t (is_active BOOLEAN);
-- ⚠️ BOOLEAN 是 TINYINT(1) 的别名

INSERT INTO t VALUES (2);      -- ⚠️ 能存进去！不是 0/1 也行
INSERT INTO t VALUES (-1);     -- ⚠️ 也能
```

**要严格限制**：

```sql
is_active TINYINT(1) NOT NULL DEFAULT 1
-- 或用 CHECK
CONSTRAINT ck_active CHECK (is_active IN (0,1))
```

⚠️ **对照 PostgreSQL**：PG 有原生 `BOOLEAN`，只接受 `TRUE`/`FALSE`/`NULL`。这是 PG 更严谨的地方。

### 二进制类型

| 类型 | 对应 | ⚠️ 坑 |
|------|------|-------|
| `BINARY(n)` | 定长二进制 | ⚠️ **补 `\0`**（和 CHAR 补空格一样） |
| `VARBINARY(n)` | 变长二进制 | ⭐ 推荐 |
| `TINYBLOB`/`BLOB`/... | 二进制 TEXT | 不能建普通索引 |

⭐ **实践：避开 `BINARY`，用 `VARBINARY`。**

⚠️ **不建议在数据库里存文件本体**——文件放对象存储，数据库存 URL + 元数据。理由：大文件拖慢备份、占满 Buffer Pool、传输慢。

## 八、空间类型（了解即可）

| 类型 | 用途 |
|------|------|
| `GEOMETRY` | 通用几何 |
| `POINT` | 点 |
| `LINESTRING` | 线 |
| `POLYGON` | 多边形 |
| `MULTIPOINT` 等 | 多元素组合 |

常用函数：`ST_Distance`（距离）、`ST_Contains`（包含）、`ST_Intersects`（相交）、`ST_GeomFromText`。

⚠️ **MySQL 的空间类型不是 PostGIS**：没有拓扑支持、没有空间索引的高级操作、没有坐标系转换（PostGIS 有 `geometry`/`geography` 双类型）。**复杂 GIS 请用 PostgreSQL + PostGIS。**

## 九、陷阱

1. **❌ 给 JSON 列建普通索引。** 用生成列。
2. **❌ JSON 列设默认值。** 不允许。
3. **❌ 把订单明细塞进 JSON。** 需要 JOIN 和单条操作时必须拆表。
4. **❌ 用 `ENUM`。** 三个问题，用 `VARCHAR` + `CHECK`。
5. **❌ 以为 `BOOLEAN` 限制 0/1。** 它是 `TINYINT(1)` 别名，能存任何值。
6. **❌ 用生成列存 `NOW()`。** 非确定性函数不允许。
7. **❌ 用 `BINARY`。** 补 `\0`，用 `VARBINARY`。
8. **❌ 往数据库存文件本体。** 用对象存储 + URL。

## 小结

- **`JSON` 三个限制**：不能建普通索引（用生成列）、不能有默认值、⚠️ **不能替代关联表**
- `->>` 取值去引号（最常用）、`->` 保留引号；等价于 `JSON_UNQUOTE(JSON_EXTRACT(...))`
- ⭐ **`JSON_TABLE`** 把 JSON 数组展开成行，适合临时查询，不适合高频
- ⭐ **JSON vs 关联表决策树**：会 JOIN/查询/统计/要外键 → 关联表；只是偶尔整体读 → JSON
- ⭐ **生成列**：`VIRTUAL`（不存数据）vs `STORED`（存结果），都能建索引；⚠️ **不能用 `NOW()`**
- ⚠️ **`ENUM` 三个问题**（加值改表/跨环境值序可能反/不可读），用 `VARCHAR` + `CHECK` 替代
- ⚠️ **`BOOLEAN` 是 `TINYINT(1)` 别名**，不限制 0/1
