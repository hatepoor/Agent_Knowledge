## 一、正确的初始化顺序 ⚠️

⚠️ **顺序错了要返工。按这四步走。**

### 步骤 1：服务器级配置

```ini
[mysqld]
character-set-server     = utf8mb4
collation-server         = utf8mb4_0900_ai_ci
default-time-zone        = '+00:00'
sql_mode = STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

```sql
-- 运行期验证
SHOW VARIABLES LIKE 'character_set_server';
SHOW VARIABLES LIKE 'collation_server';
```

⚠️ **这四行是「生产数据库」的最低配置。** 特别是 `sql_mode`——不开严格模式，类型溢出会被静默截断（见 00 篇）。

### 步骤 2：建库时指定

```sql
CREATE DATABASE shop
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

⚠️ **不要省略 COLLATE。** 不写会继承服务器值，但显式写出来更清晰、更不怕上层变化。

### 步骤 3：建表时指定（配模板）

```sql
CREATE TABLE employees (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  dept_id TINYINT UNSIGNED COMMENT '部门ID',
  name VARCHAR(64) NOT NULL COMMENT '姓名',
  email VARCHAR(255) NOT NULL COMMENT '邮箱',
  phone VARCHAR(20) NULL COMMENT '手机号',
  salary DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '月薪',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0离职 1在职',
  hired_at DATE NOT NULL COMMENT '入职日期',
  deleted_at DATETIME NULL COMMENT '软删除时间',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                            ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

  PRIMARY KEY (id),
  UNIQUE KEY uk_email (email),
  KEY idx_dept_hired (dept_id, hired_at),
  CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) REFERENCES departments(id)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE=InnoDB
  DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_0900_ai_ci
  COMMENT='员工表';
```

### 这个模板里的每一个选择都有来源

| 写法 | 来自哪篇 |
|------|---------|
| `id BIGINT UNSIGNED` | 1.2 数值类型 |
| `salary DECIMAL(10,2)` | 1.2（金额必须 DECIMAL） |
| `phone VARCHAR(20)` | 1.3（手机号是字符串） |
| `hired_at DATE` | 1.4（只要日期） |
| `created_at DATETIME` | 1.4（避开 TIMESTAMP 2038） |
| `updated_at ... ON UPDATE` | 1.4（自动更新时间） |
| `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci` | 1.6 |
| 每个字段带 `COMMENT` | 团队规范 |

⭐ **把这个模板存成团队的建表规范**，每张表都这么写，从根上避免不一致。

### 步骤 4：连接层指定

```python
pymysql.connect(..., charset='utf8mb4', collation='utf8mb4_0900_ai_ci')
```

```sql
-- 客户端内
SET NAMES utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

## 二、验证清单

⚠️ **建完之后跑这四条，确认各层一致。**

```sql
-- 1. 服务器层
SHOW VARIABLES WHERE Variable_name IN ('character_set_server','collation_server');

-- 2. 数据库层
SELECT DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA WHERE SCHEMA_NAME = 'shop';

-- 3. 表层：查有没有不一致
SELECT TABLE_NAME, TABLE_COLLATION
FROM information_schema.TABLES
WHERE TABLE_SCHEMA='shop' AND TABLE_COLLATION != 'utf8mb4_0900_ai_ci';

-- 4. 列层：查有没有非 utf8mb4 或非统一 collation
SELECT TABLE_NAME, COLUMN_NAME, CHARACTER_SET_NAME, COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA='shop'
  AND CHARACTER_SET_NAME IS NOT NULL
  AND COLLATION_NAME != 'utf8mb4_0900_ai_ci';
```

⭐ **第 4 条要特别注意**：`utf8mb4_bin` 的列（用户名/密码/token）会出现在这个结果里——**那是故意的，不是错误**。排查时要排除它们。

## 三、诊断已有库的问题

### ⭐ 症状一：中文变问号

```sql
SELECT * FROM users WHERE name = '张三';   -- 查不到
-- 但数据里明明是「张三」
```

**根因排查**：

```sql
-- 1. 数据实际存成什么了
SELECT name, HEX(name) FROM users LIMIT 5;
-- ⚠️ 如果 HEX 出来是问号（3F），说明写入时就已经坏了，字符集改不回来

-- 2. 各层字符集
SHOW VARIABLES LIKE 'character_set%';
SHOW CREATE TABLE users\G
```

### ⭐⭐ `HEX()` 能区分「存坏了」和「显示错了」

| HEX 结果 | 含义 | 能修吗 |
|---------|------|--------|
| `E5BCA0E4B889` | ⭐ 数据是对的，只是显示层字符集不对 | ✅ 改字符集配置即可 |
| `3F3F3F` | ⚠️ 写入时就变成问号了 | ❌ **数据已损坏，只能从备份恢复** |

⭐ **这是排查编码问题最关键的一步**——先判断能不能修，再动手。

### 症状二：emoji 存不进去

```sql
INSERT INTO users (name) VALUES ('😀');
-- ERROR 1366: Incorrect string value
```

**修法**：

```sql
-- 1. 改表（会重建表）
ALTER TABLE users CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 2. ⚠️ 检查是否有列级显式设置（这行不会被 CONVERT TO 改掉）
SELECT COLUMN_NAME, CHARACTER_SET_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA='shop' AND CHARACTER_SET_NAME IS NOT NULL
  AND CHARACTER_SET_NAME != 'utf8mb4';
-- 逐个改列
ALTER TABLE users MODIFY name VARCHAR(64) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
```

⚠️ **`CONVERT TO` 只改表级和未显式指定的列。** 如果建表时写了 `name VARCHAR(64) CHARACTER SET utf8`,这列不会被自动改。

### 症状三：JOIN 特别慢

```sql
-- 检查各表/列的 collation 是否一致
SELECT TABLE_NAME, TABLE_COLLATION FROM information_schema.TABLES
WHERE TABLE_SCHEMA='shop';

-- 查实际执行计划
EXPLAIN SELECT * FROM t_a JOIN t_b ON t_a.name = t_b.name;
-- ⚠️ 如果两边的 type 都是 ALL，说明索引失效了
```

📌 完整的索引诊断见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/EXPLAIN解读]]。

## 四、⚠️ 大表改字符集的代价

⚠️ **`ALTER TABLE ... CONVERT TO` 会重建整张表**：

| 表行数 | 影响 |
|--------|------|
| < 10 万 | 几秒，直接改 |
| 10 万 ~ 1000 万 | 几分钟到几十分钟，⚠️ 需要在线 DDL 工具 |
| > 1000 万 | ⭐ 必须用 `pt-online-schema-change` 或 `gh-ost` |

📌 见 [[mysql/02-中段阶段-专题精讲/大表与在线DDL/在线DDL方案对比]]。

## 五、建表规范自查清单

⚠️ **每次建表前过一遍：**

- [ ] 引擎是 `InnoDB`（显式写了）
- [ ] `DEFAULT CHARSET=utf8mb4`
- [ ] `COLLATE=utf8mb4_0900_ai_ci`
- [ ] 表有 `COMMENT`
- [ ] 主键是 `BIGINT UNSIGNED AUTO_INCREMENT`
- [ ] 金额列是 `DECIMAL(p,2)` 不是 `FLOAT`/`DOUBLE`
- [ ] 手机号/UUID/IP 是字符串不是数字
- [ ] 时间列是 `DATETIME` 不是 `TIMESTAMP`（除非要时区语义）
- [ ] 用户名/密码/token 列是 `COLLATE utf8mb4_bin`
- [ ] 每个字段都有 `COMMENT`
- [ ] 有 `created_at` / `updated_at`
- [ ] 需要索引的列不是 `TEXT`
- [ ] 状态列用 `VARCHAR` + `CHECK` 而不是 `ENUM`

---

## 六、陷阱

1. **❌ 不写 `ENGINE=InnoDB`。** 依赖服务器默认值不安全。
2. **❌ 省略 `CHARSET` / `COLLATE`。** 会因上层设置不一致而埋雷。
3. **❌ 字段不带 `COMMENT`。** 半年后没人知道字段什么意思。
4. **❌ 用 `HEX()` 判断不清就乱改。** 数据已损坏时改字符集也救不回来。
5. **❌ 在大表上直接 `CONVERT TO`。** 用在线 DDL 工具。
6. **❌ 验证时把 `utf8mb4_bin` 的列当错误。** 那是故意设的。
7. **❌ 跳过「建表规范自查清单」。** 十三条里漏一条都是隐患。

## 小结

- ⭐ **初始化四步**：服务器配置（含 `sql_mode`）→ 建库指定 → 建表指定（配模板）→ 连接层指定
- **建表模板**：`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='...'` + 每字段 `COMMENT`
- 用四条 SQL 验证各层一致（⚠️ 排除故意设的 `utf8mb4_bin` 列）
- ⭐ **`HEX()` 是排查编码的关键**：`3F`（问号）= 数据已损，改配置救不回
- 大表改字符集必须用在线 DDL 工具
- **建表前过 13 条自查清单**
