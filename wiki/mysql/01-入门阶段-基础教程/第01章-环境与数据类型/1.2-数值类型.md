## 一、整数：五兄弟

### 定义

> **整数类型存「没有小数部分的数」。** MySQL 提供五种，区别只在**占多少字节**和**能表示多大范围**。

### 五兄弟对照

| 类型 | 字节 | 有符号范围 | 无符号范围 | 典型用途 |
|------|-----:|-----------|-----------|---------|
| `TINYINT` | 1 | -128 ~ 127 | 0 ~ 255 | 状态、类型、性别 |
| `SMALLINT` | 2 | -32,768 ~ 32,767 | 0 ~ 65,535 | 年份、小计数 |
| `MEDIUMINT` | 3 | -8,388,608 ~ 8,388,607 | 0 ~ 16,777,215 | ⚠️ 较少用 |
| `INT` | 4 | ±21.47 亿 | 0 ~ 42.95 亿 | 普通 ID、计数 |
| `BIGINT` | 8 | ±922 亿亿 | 0 ~ 1844 亿亿 | ⭐ **主键、大 ID** |

⭐ **选型就看「最大可能值」**：

```
最大可能值 < 255                    → TINYINT
最大可能值 < 6.5 万                 → SMALLINT
最大可能值 < 4294967295（约42.9亿）  → INT
以上                                  → BIGINT
```

### ⚠️ 为什么主键用 `BIGINT UNSIGNED` 而不是 `INT`

**理由一：增长上限**

```
INT UNSIGNED 上限约 42.9 亿，看起来够多。但：
  - 自增 ID 单调递增，且⚠️ 回滚也消耗 ID
  - 如果用全局分布式 ID（如雪花算法），42.9 亿很快就到顶
  - 换类型 = 改表结构，大表上极贵
```

**理由二：⚠️ 主外键类型必须一致**

```sql
-- ❌ 类型不一致
CREATE TABLE a (id INT UNSIGNED);
CREATE TABLE b (a_id INT);           -- ⚠️ 少了 UNSIGNED

SELECT * FROM a JOIN b ON a.id = b.a_id;
-- ⚠️ b.a_id 被隐式转换成无符号 → 索引可能失效
```

⭐ **规范：主键和外键用完全相同的类型**，一律 `BIGINT UNSIGNED`。

### ⚠️ `UNSIGNED` 的致命坑

**好处**：范围大一倍，语义上「不可能为负」。

**⚠️ 坑：无符号溢出不报错，静默变成天文数字**

```sql
CREATE TABLE t (n INT UNSIGNED);
INSERT INTO t VALUES (0);

SELECT n - 1 FROM t;
-- ⚠️ 结果：4294967295，不是 -1，也不报错！
```

**机制**：无符号整数下溢时，会「绕回」到最大值。

⭐ **结论**：
- **ID / 主键** → 用 `UNSIGNED`（天然非负，且不会做减法）
- **⚠️ 余额、库存、任何可能减成负数的值** → **不要用 `UNSIGNED`**，否则「减成负数」会变成天文数字，极难排查

## 二、浮点：`FLOAT` 与 `DOUBLE`

### 定义

> **浮点类型存「近似值」**，用二进制科学计数法表示，因此**无法精确表示大多数十进制小数**。

### 两种浮点

| 类型 | 字节 | 有效数字 | 范围 |
|------|-----:|---------:|------|
| `FLOAT`（单精度） | 4 | ⚠️ **约 7 位** | 约 ±3.4×10³⁸ |
| `DOUBLE`（双精度） | 8 | ⚠️ **约 15 位** | 约 ±1.8×10³⁰⁸ |

### ⚠️⚠️ 为什么浮点会丢精度

**实测**：

```sql
CREATE TABLE t (f FLOAT, d DOUBLE, dec DECIMAL(10,2));
INSERT INTO t VALUES (0.1, 0.1, 0.1);

SELECT f = 0.1, d = 0.1, dec = 0.1 FROM t;
```

| 列 | `= 0.1` | 实际存储 |
|----|:------:|---------|
| `FLOAT` | ❌ FALSE | 0.100000001490116... |
| `DOUBLE` | ❌ FALSE | 0.100000000000000005551... |
| `DECIMAL` | ✅ TRUE | 0.1（精确） |

**根因**：`0.1` 转成二进制是**无限循环小数**（`0.0001100110011...`），浮点只能存前若干位，所以存的是「最接近 0.1 的二进制数」，不是 0.1 本身。

⭐ **类比**：就像 `1/3 = 0.333333...` 用十进制只能存 `0.333333`，永远差一点。

## 三、`DECIMAL`：精确小数 ⭐

### 定义

> **`DECIMAL(p,s)` 用十进制方式精确存储，不做二进制转换，因此没有精度损失。**

### 两个参数

| 参数 | 含义 | 限制 |
|------|------|------|
| `p` | **精度**：总位数（含小数点） | 最大 65 |
| `s` | **标度**：小数位数 | 最大 30 |

```sql
salary DECIMAL(10,2)     -- 共 10 位，其中 2 位小数 → 最大 99,999,999.99
rate   DECIMAL(20,8)     -- 共 20 位，8 位小数 → 汇率
qty    DECIMAL(10,3)     -- 数量，3 位小数
```

### ⚠️ 金额为什么必须用 `DECIMAL`

```sql
-- ❌ 绝对不要
CREATE TABLE orders (amount DOUBLE);

-- 场景：对账
SELECT SUM(amount) FROM orders WHERE user_id = 1;
-- ⚠️ 可能得到 100.00000000000001 而不是 100
-- ⚠️ 用 = 比较时对不上，用 ORDER BY 时顺序可能错
```

**后果**：
- 对账差一分钱，查半天
- `WHERE amount = 0.3` 查不到实际是 0.3 的行
- 累计误差随行数放大

⭐ **规范：所有金额、需要精确对账的数值，一律 `DECIMAL`。**

### 常用金额类型

| 业务 | 类型 | 能表示 |
|------|------|--------|
| 电商订单 | `DECIMAL(10,2)` | 最大 99,999,999.99 |
| 支付金额 | `DECIMAL(16,2)` | 更大 |
| 汇率 | `DECIMAL(20,8)` | 8 位小数 |
| 数量 | `DECIMAL(10,3)` | 3 位小数 |

## 四、三种数值类型的选型

| 需求 | 选 | 理由 |
|------|-----|------|
| 计数、ID、状态 | 整数（按量级） | 精确、省空间 |
| ⭐ **金额、对账** | ⭐ **`DECIMAL(p,s)`** | 精确 |
| 科学计算、统计 | `DOUBLE` | 近似可接受 |
| 传感器数据、图形 | `FLOAT` | 精度要求低、省空间 |

⚠️ **「要不要精确」是唯一的分界线。** 涉及钱 → `DECIMAL`，其他看量级。

## 五、`AUTO_INCREMENT` 自增

### 三个必须知道的行为

| 行为 | 说明 |
|------|------|
| **① 必须是索引** | `AUTO_INCREMENT` 列必须建索引（通常是主键） |
| **② 每表一个计数器** | ⚠️ **每张表独立**，表 A 到 100 不影响表 B 从 1 开始 |
| **③ 失败也消耗 ID** | ⚠️ 插入失败（重复键）时，消耗掉的 ID **不回收** |

### 实测「失败也消耗 ID」

```sql
CREATE TABLE t (id INT AUTO_INCREMENT PRIMARY KEY, v INT);
INSERT INTO t (v) VALUES (1),(2),(3);       -- id = 1,2,3

-- 造一个重复键冲突
INSERT INTO t (id, v) VALUES (3, 99);       -- ❌ 报错 Duplicate entry

INSERT INTO t (v) VALUES (4);               -- id = ⚠️ 5，不是 4！
SELECT * FROM t;
```

⚠️ **这就是「自增 ID 有空洞」的原因之一。** 空洞是正常的，不要试图「修复」。

### `TRUNCATE` 会重置计数器

```sql
DELETE FROM t;                -- 清空，⚠️ 计数器不重置
INSERT INTO t (v) VALUES (1); -- id 继续往后

TRUNCATE TABLE t;             -- ⚠️ 重置计数器（且不可回滚）
INSERT INTO t (v) VALUES (1); -- id = 1
```

⚠️ **`TRUNCATE` vs `DELETE`**：`TRUNCATE` 更快且重置自增，但**不可回滚、不触发 DELETE 触发器、不支持 WHERE**。

### 8.0 的自增锁改进

| 参数 | 8.0 之前默认 | 8.0 默认 |
|------|------------|---------|
| `innodb_autoinc_lock_mode` | `0`（表级锁） | ⭐ **`2`（交叉模式）** |

**影响**：`0` 模式下并发插入自增列会争用同一把表锁；`2` 模式大幅改善并发性能。⭐ **这是「该用 8.0」的具体理由之一。**

## 六、陷阱

1. **❌ 主键用 `INT`。** 用 `BIGINT UNSIGNED`，且主外键类型一致。
2. **❌ 用 `UNSIGNED` 存余额/库存。** ⚠️ 减成负数会静默变天文数字。
3. **❌ 金额用 `FLOAT`/`DOUBLE`。** 对账必出问题，用 `DECIMAL`。
4. **❌ 以为 `ROUND()` 能救浮点。** `ROUND(0.1+0.2, 2)` 看着是 0.30，但 `WHERE amount = ROUND(x,2)` 比较仍可能出问题。
5. **❌ 假设自增 ID 严格连续。** 回滚和失败都消耗 ID。
6. **❌ 用 `DELETE` 期望重置自增。** 只有 `TRUNCATE` 重置。
7. **❌ 用整数存手机号。** 丢前导 0。

---

## 小结

- 整数五兄弟按「最大可能值」选；⭐ **主键一律 `BIGINT UNSIGNED`，主外键类型必须一致**
- ⚠️ **`UNSIGNED` 的坑：下溢不报错，静默变天文数字**——余额/库存不要用
- **浮点存的是「近似值」**——`0.1` 在 `FLOAT`/`DOUBLE` 里都不等于 0.1
- ⭐ **金额必须 `DECIMAL(p,s)`**：p 总位数、s 小数位
- `AUTO_INCREMENT`：每表独立计数器、⚠️ **失败也消耗 ID**、只有 `TRUNCATE` 重置
- 8.0 把 `innodb_autoinc_lock_mode` 默认从 0 改成 2，改善并发
