## 一、五种字符串类型

### 定义

> **字符串类型存「文字」。** 区别在**定长还是变长**、**能存多长**、**能不能建索引**。

| 类型 | 最大长度 | 定长/变长 | 能建普通索引 |
|------|---------|----------|------------|
| `CHAR(n)` | n ≤ 255 | ⭐ **定长** | ✅ |
| `VARCHAR(n)` | n ≤ 65,535 **字节** | ⭐ **变长** | ✅ |
| `TINYTEXT` | 255 字节 | 变长 | ❌ |
| `TEXT` | 65,535 字节 | 变长 | ❌ |
| `MEDIUMTEXT` | 16,777,215 字节 | 变长 | ❌ |
| `LONGTEXT` | 4,294,967,295 字节 | 变长 | ❌ |

⚠️ **`CHAR`/`VARCHAR` 的 n 是「字符数」，但总字节数不能超 65,535。**

---

## 二、`CHAR` vs `VARCHAR` ⭐

### 定长 vs 变长的物理差异

```sql
CREATE TABLE t1 (name CHAR(10));
CREATE TABLE t2 (name VARCHAR(10));

INSERT INTO t1 VALUES ('ab');
INSERT INTO t2 VALUES ('ab');
```

| | `CHAR(10)` | `VARCHAR(10)` |
|---|---|---|
| 实际占用 | ⭐ **固定 10 字节** | ⭐ **2 字节 + 1~2 字节长度前缀** |
| 存 `'ab'` | `'ab        '`（补空格） | `'ab'` |
| 存 `'张三丰 extra'` | ⚠️ 截断成 10 字节 | ⚠️ 截断 |

### ⚠️ `CHAR` 的补空格陷阱

```sql
SELECT name FROM t1;
-- 返回 'ab'（MySQL 读取时默认去掉尾部空格）

-- 但长度可能骗人
SELECT LENGTH(name) FROM t1;      -- ⚠️ 10（补了空格）
SELECT CHAR_LENGTH(name) FROM t1; -- 2
```

⚠️ **更隐蔽的**：`PAD_CHAR_TO_FULL_LENGTH` 开启时，返回的字符串**带尾部空格**，应用层做 `== 'ab'` 比较可能失败。

### 选型

| 选 `CHAR` | 选 `VARCHAR` |
|----------|-------------|
| **长度固定且很短** | ⭐ **绝大多数情况** |
| 例：性别（`CHAR(1)`）、状态码、UUID（`CHAR(36)`） | 例：姓名、邮箱、标题、URL |

⭐ **判断标准一句话：长度会不会变？会变就 `VARCHAR`。**

## 三、`VARCHAR(n)` 的 n 到底是什么 ⚠️

### 是「字符数」，不是「字节数」

```sql
CREATE TABLE t (name VARCHAR(10));
```

| 存什么 | 占用字节 | 能存几个 |
|--------|---------|---------|
| 纯 ASCII（`abc`） | 1 字节/字符 | 10 个 |
| 中文（utf8mb4） | 3 字节/字符 | 10 个（30 字节） |
| emoji（utf8mb4） | 4 字节/字符 | 10 个（40 字节） |

⭐ **所以 `VARCHAR(10)` 在 utf8mb4 下最多占 40 字节。**

### ⚠️ 65,535 字节的硬限

```sql
-- ❌ 报错
CREATE TABLE t (name VARCHAR(65535));
-- ERROR 1074: Column length too big for column 'name' (max = 21845)

-- 原因：65535 字符 × 3 字节（中文）= 196605 字节 > 65535 字节上限
```

⭐ **`VARCHAR` 的实际上限取决于字符集**：

| 字符集 | 最大字符数 |
|--------|-----------|
| `latin1`（1 字节） | 65,535 |
| `utf8mb4`（最多 4 字节） | ⚠️ 约 16,383（纯 ASCII 时）~ 更少 |

**需要更长怎么办？** → 用 `TEXT`。

## 四、`TEXT` 家族与它的三个限制 ⚠️

### 什么时候用 `TEXT`

| 用 `VARCHAR` | 用 `TEXT` |
|-------------|----------|
| 需要索引 | 不需要索引 |
| 需要排序/比较 | 只做展示或全文检索 |
| 长度已知且 ≤ 几百 | 长度不定（用户输入、文章正文） |

### ⚠️ 三个限制

#### 限制 1：不能有普通默认值

```sql
-- ❌ 报错
CREATE TABLE t (a VARCHAR(20) DEFAULT 'x',   -- ✅ VARCHAR 可以
                b TEXT DEFAULT 'x');          -- ❌ TEXT 不行
-- ERROR 1101: BLOB/TEXT column 'b' can't have a default value
```

⭐ **解法**：用表达式默认值（8.0.13+）

```sql
b TEXT DEFAULT ('x')      -- ⭐ 加括号，当作表达式
```

#### 限制 2：不能建普通索引

```sql
CREATE TABLE articles (content TEXT);
CREATE INDEX idx_content ON articles (content);
-- ❌ ERROR 1172: BLOB/TEXT column 'content' can't be used in key specification
```

⭐ **两种解法**：

```sql
-- 方案 A：前缀索引（只索引前 N 个字符）
CREATE INDEX idx_content ON articles (content(255));

-- 方案 B：改用 VARCHAR（更常用）
ALTER TABLE articles MODIFY content VARCHAR(2000);
```

📌 前缀长度的选择见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引类型与选型]]。

#### 限制 3：⚠️ 某些场景不能用

`TEXT` 列不能用于：
- `GROUP BY` 的某些优化（默认会物化临时表）
- 部分函数参数
- 作为唯一索引的一部分

## 五、⭐ `utf8` vs `utf8mb4`

⚠️ **这是 MySQL 最经典的坑。**

### 三个字符集

| 名称 | 真实含义 | 每字符最大字节 | 能存 emoji |
|------|---------|--------------|-----------|
| `latin1` | 西欧语言 | 1 | ❌ |
| ⚠️ **`utf8`** | ⚠️ **实际是 `utf8mb3`** | **3** | ❌ |
| ⭐ **`utf8mb4`** | ⭐ 真正的 UTF-8 | **4** | ✅ |

### 为什么 emoji 存不进去

```sql
CREATE TABLE t (name VARCHAR(20) CHARACTER SET utf8);
INSERT INTO t VALUES ('😀');
-- ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' for column 'name'
```

**拆解**：

| 字符 | Unicode | UTF-8 编码 | 字节数 |
|------|---------|-----------|-------:|
| 😀 | U+1F600 | `F0 9F 98 80` | ⚠️ **4** |
| 中 | U+4E2D | `E4 B8 AD` | 3 |
| A | U+0041 | `41` | 1 |

⚠️ **emoji 需要 4 字节，而 `utf8`（真名 `utf8mb3`）最多只支持 3 字节——所以存不进去。**

### ⭐ 结论

**任何时候都写 `utf8mb4`，不要写 `utf8`。**

```sql
-- 服务器级
SET GLOBAL character_set_server = 'utf8mb4';

-- 库级
CREATE DATABASE app DEFAULT CHARACTER SET utf8mb4;

-- 表级
CREATE TABLE t (...) DEFAULT CHARSET=utf8mb4;

-- 列级（如果表级没设）
name VARCHAR(64) CHARACTER SET utf8mb4

-- 连接级（Python）
pymysql.connect(..., charset='utf8mb4')
```

📌 **五层级的完整规则 + collation 见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.6-字符集排序规则]]。**

## 六、常用字段选型表

| 字段 | 推荐类型 | 理由 |
|------|---------|------|
| 主键 ID | `BIGINT UNSIGNED` | 见 1.2 |
| ⚠️ **手机号** | ⭐ `VARCHAR(20)` | ❌ **不是整数**：可能前导 0、可能带 `+86`、要字符串拼接 |
| 邮箱 | `VARCHAR(255)` + UNIQUE | RFC 上限 |
| 用户名 | `VARCHAR(64)` + ⚠️ `COLLATE utf8mb4_bin` | 区分大小写 |
| 密码哈希 | `VARCHAR(255)` | bcrypt/argon2 输出约 60 字符 |
| 姓名 | `VARCHAR(64)` | |
| 标题 | `VARCHAR(255)` | 便于索引 |
| URL | `VARCHAR(500)` 或 `TEXT` | |
| 文章正文 | `TEXT` / `LONGTEXT` | 不建索引 |
| UUID | `CHAR(36)` | 定长；⚠️ 有序 UUID 用 `BINARY(16)` 更省 |
| IP 地址 | `VARBINARY(16)` 或 `VARCHAR(45)` | IPv6 最长 45 字符 |
| 性别 | `CHAR(1)` 或 `TINYINT` | 定长短 |

## 七、陷阱

1. **❌ 用 `utf8` 而不是 `utf8mb4`。** 存不了 emoji。
2. **❌ 用整数存手机号。** 丢前导 0，不能字符串拼接。
3. **❌ 给 `TEXT` 设普通默认值。** 要用 `TEXT DEFAULT ('x')`。
4. **❌ 给 `TEXT` 建普通索引。** 用前缀索引或改 `VARCHAR`。
5. **❌ `VARCHAR(65535)`。** 超字节上限，会报错。
6. **❌ 用 `CHAR` 存变长数据。** 浪费空间且补空格。
7. **❌ 用 `LENGTH()` 当字符数。** 它是字节数，中文场景用 `CHAR_LENGTH()`。
8. **❌ 用户名/密码/token 用默认 collation。** 要用 `utf8mb4_bin`。

---

## 小结

- `CHAR` 定长（补空格）、`VARCHAR` 变长、`TEXT` 家族不能建普通索引
- ⭐ **`VARCHAR(n)` 的 n 是字符数**，但总字节数 ≤ 65,535（utf8mb4 下上限远小于 65535 字符）
- **选型一句话：长度会变就 `VARCHAR`，不定长且不索引就 `TEXT`**
- ⚠️ **`TEXT` 三限制**：不能普通默认值（用 `DEFAULT ('x')`）、不能建普通索引、部分场景不可用
- ⭐⭐ **`utf8` 是假 UTF-8（utf8mb3，最多 3 字节），emoji 要 4 字节——一律用 `utf8mb4`**
- 手机号、UUID、IP 都是**字符串**不是数字
