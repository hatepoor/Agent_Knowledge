# 数据类型全景

## 一、四大分类

MySQL 的所有类型可以归成四类。⚠️ **这个分类框架比背单个类型更重要。**

| 分类 | 包括 | 回答的问题 |
|------|------|-----------|
| ⭐ **① 数值类型** | 整数（5 种）、浮点（2 种）、精确小数（DECIMAL） | 「能表示多大的数、多精确」 |
| ⭐ **② 字符串类型** | CHAR、VARCHAR、TEXT 四兄弟、BINARY/VARBINARY | 「能存多长的文字」 |
| ⭐ **③ 日期时间类型** | DATE、TIME、DATETIME、TIMESTAMP、YEAR | 「表示哪个时刻或哪段时长」 |
| ⭐ **④ 特殊类型** | JSON、ENUM、SET、BOOLEAN、空间类型 | 「结构化的其他需求」 |

⭐ **记忆锚点：数值管「多大」、字符串管「多长」、日期管「何时」、特殊管「其他」。**

## 二、⭐ 存储范围总表

⚠️ **这张表是全章最该记住的东西。** 不需要全背，但要知道**去哪查**、以及**常用类型的量级**。

### 数值类型

| 类型 | 字节 | 有符号范围 | 无符号范围 |
|------|-----:|-----------|-----------|
| `TINYINT` | 1 | -128 ~ 127 | 0 ~ 255 |
| `SMALLINT` | 2 | -32,768 ~ 32,767 | 0 ~ 65,535 |
| `MEDIUMINT` | 3 | -8,388,608 ~ 8,388,607 | 0 ~ 16,777,215 |
| `INT` | 4 | -2,147,483,648 ~ 2,147,483,647 | 0 ~ 4,294,967,295 |
| `BIGINT` | 8 | -9,223,372,036,854,775,808 ~ 9,223,372,036,854,775,807 | 0 ~ 18,446,744,073,709,551,615 |
| `FLOAT` | 4 | 约 ±3.4×10³⁸（7 位有效数字） | — |
| `DOUBLE` | 8 | 约 ±1.8×10³⁰⁸（15 位有效数字） | — |
| `DECIMAL(p,s)` | 变长 | p 最大 65，s 最大 30 | — |

### 字符串类型

| 类型 | 最大长度 | 说明 |
|------|---------|------|
| `CHAR(n)` | n ≤ 255 | 定长 |
| `VARCHAR(n)` | n ≤ 65,535 **字节** | 变长 |
| `TINYTEXT` | 255 字节 | |
| `TEXT` | 65,535 字节（≈64KB） | |
| `MEDIUMTEXT` | 16,777,215 字节（≈16MB） | |
| `LONGTEXT` | 4,294,967,295 字节（≈4GB） | |
| `BINARY(n)` / `VARBINARY(n)` | n ≤ 255 / 65,535 | 二进制版 CHAR/VARCHAR |
| `TINYBLOB` / `BLOB` / `MEDIUMBLOB` / `LONGBLOB` | 同 TEXT 四兄弟 | 二进制版 |

### 日期时间类型

| 类型 | 字节 | 范围 |
|------|-----:|------|
| `DATE` | 3 | 1000-01-01 ~ 9999-12-31 |
| `TIME` | 3 | -838:59:59 ~ 838:59:59 |
| `DATETIME` | 5 | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 |
| `TIMESTAMP` | 4 | 1970-01-01 00:00:01 ~ **2038-01-19 03:14:07**（UTC） |
| `YEAR` | 1 | 1901 ~ 2155 |

### 特殊类型

| 类型 | 限制 |
|------|------|
| `JSON` | 内部像 LONGTEXT |
| `ENUM('a','b',...)` | 最多 65,535 个不同值 |
| `SET('a','b',...)` | 最多 64 个成员 |
| `BOOLEAN` | 实际是 `TINYINT(1)` 的别名 |
| `GEOMETRY` / `POINT` / `LINESTRING` / `POLYGON` | 空间数据 |

⭐ **几个最该记住的量级感**：

| 记忆点 | 数值 |
|--------|------|
| `INT UNSIGNED` 上限 | 约 **42.9 亿** |
| `BIGINT` 上限 | 约 **1844 亿亿** |
| `TIMESTAMP` 天花板 | **2038-01-19** |
| `TEXT` 上限 | **64KB** |
| `VARCHAR(n)` 的 n 是**字符数**，但受 65,535 **字节**硬限 | |

## 三、怎么查一个列的类型

⚠️ **不要靠猜，也不要靠 `DESC`（信息不全）。三种方法按信息量排序：**

### 方法 1：`SHOW CREATE TABLE`（⭐ 最全）

```sql
SHOW CREATE TABLE employees\G
```

输出包含：**列类型、字符集、collation、默认值、是否可空、索引、外键、引擎、表注释**。

⭐ **加 `\G` 竖排显示**，否则一行挤成一团没法读。

### 方法 2：`information_schema.COLUMNS`（可批量查）

```sql
SELECT COLUMN_NAME, COLUMN_TYPE, IS_NULLABLE, COLUMN_DEFAULT,
       CHARACTER_SET_NAME, COLLATION_NAME, COLUMN_COMMENT
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'employees';
```

| 字段 | 给你什么 |
|------|---------|
| `COLUMN_TYPE` | ⭐ 完整类型（如 `varchar(64)`） |
| `IS_NULLABLE` | 是否可空 |
| `COLUMN_DEFAULT` | 默认值 |
| `COLUMN_COMMENT` | ⭐ 列注释 |

⭐ **这个方法的价值是「可批量」**——比如「找出所有 `VARCHAR` 但没写注释的列」：

```sql
SELECT TABLE_NAME, COLUMN_NAME, COLUMN_TYPE
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'shop'
  AND DATA_TYPE = 'varchar'
  AND (COLUMN_COMMENT IS NULL OR COLUMN_COMMENT = '');
```

### 方法 3：`DESC`（最省事但信息少）

```sql
DESC employees;
```

⚠️ **只给字段名/类型/可空/键/默认值**，没有字符集、collation、注释。快速看一眼可以，排查问题必须用方法 1 或 2。

## 四、类型转换：什么时候会发生

⚠️ **这是新手最容易栽的地方——「我明明存的是数字，怎么变成字符串了」。**

### MySQL 会在三种情况下自动转换

| 情况 | 示例 | 结果 |
|------|------|------|
| ⭐ **① 插入时目标列类型不同** | `TINYINT` 列插入 `'123'` | 转成 123（能转就转） |
| ⭐ **② 比较时两边类型不同** | `VARCHAR` 列 `WHERE phone = 13800138000` | ⚠️ **列被转成数字，索引失效** |
| ③ 运算时 | `'1' + 1` | 2（字符串转数字） |

### ⚠️ 最危险的是第 ② 种：隐式转换让索引失效

```sql
-- 表定义
phone VARCHAR(20), KEY idx_phone (phone)

-- ❌ 传了数字
SELECT * FROM users WHERE phone = 13800138000;
-- EXPLAIN: type=ALL, key=NULL   ← ⚠️ 索引失效！

-- ✅ 传字符串
SELECT * FROM users WHERE phone = '13800138000';
-- EXPLAIN: type=ref, key=idx_phone
```

**机制**：`VARCHAR` 列和数字比较时，MySQL 选择「把**列**转成数字」（而不是把常量转成字符串）。⚠️ **列一旦被函数/转换包裹，索引就用不上了。**

📌 详见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/EXPLAIN解读]]。

### ⚠️ 转不了的时候会怎样

| 输入 | 目标类型 | 严格模式 | 非严格模式 |
|------|---------|---------|-----------|
| `'abc'` | `INT` | ❌ 报错 | ⚠️ 变成 0 |
| `'123abc'` | `INT` | ❌ 报错 | ⚠️ 变成 123（前缀能转就转） |
| `200` | `TINYINT` | ❌ 报错 | ⚠️ 变成 127 |

⭐ **结论：转不转、转成什么，完全取决于 `sql_mode`。这就是为什么 00 篇反复强调严格模式。**

## 五、选型五问 ⭐

⚠️ **遇到一个新字段，按这五问走，不用背类型表也能选对。**

```
① 它是「数字」「文字」「时刻」还是「其他结构」？
   → 定大类
        ↓
② 如果是数字：需要小数吗？
   ├─ 不需要 → 整数（按量级选 TINYINT/SMALLINT/INT/BIGINT）
   └─ 需要 → 是「金额/要精确对账」还是「科学计算」？
              ├─ 精确 → DECIMAL(p,s)
              └─ 近似 → FLOAT / DOUBLE
        ↓
③ 如果是文字：长度固定吗？需要索引吗？
   ├─ 定长且短 → CHAR
   ├─ 变长 → VARCHAR
   └─ 很长/不定长 → TEXT
        ↓
④ 如果是时刻：要时区吗？会超过 2038 吗？
   ├─ 要时区语义 → TIMESTAMP（但注意 2038）
   └─ 不要 → DATETIME
        ↓
⑤ 需要区分大小写吗？（用户名/密码/token/邮箱）
   ├─ 是 → COLLATE utf8mb4_bin
   └─ 否 → 默认 collation
```

⭐ **第 ⑤ 问最容易被漏，但后果最严重**——详见 [[mysql/01-入门阶段-基础教程/第01章-环境与数据类型/1.6-字符集排序规则]]。

## 六、一个完整的选型示例

```
需求：电商系统的「订单表」

字段：订单号、用户ID、商品ID、数量、单价、订单状态、创建时间、备注

① 订单号    → 文字，长度固定但可能含字母 → VARCHAR(32) + UNIQUE
              ⚠️ 不用整数：订单号可能含字母，且不想让人看出「共有多少单」
② 用户ID    → 数字，无小数，量大 → BIGINT UNSIGNED + 索引
③ 商品ID    → 同上 → BIGINT UNSIGNED + 索引
④ 数量      → 数字，无小数，小 → INT UNSIGNED（或 SMALLINT）
⑤ 单价      → ⭐ 金额，要精确 → DECIMAL(10,2)   ❌ 绝不用 FLOAT
⑥ 订单状态  → 枚举，取值少 → TINYINT + CHECK，或 VARCHAR + CHECK
              ⚠️ 不用 ENUM（加值要改表）
⑦ 创建时间  → DATETIME（避开 TIMESTAMP 的 2038）+ 索引
⑧ 备注      → 可能很长 → TEXT 或 VARCHAR(500)，不建索引
```

⭐ **注意⑤和⑦的两个「❌」**——这两个是最常见的错误选型。

---

## 七、本篇陷阱

1. **❌ 用 `DESC` 排查类型问题。** 信息不全，用 `SHOW CREATE TABLE\G`。
2. **❌ 以为「插入成功」就是类型对。** 非严格模式下 `'abc'` 进 `INT` 列会变成 0。
3. **❌ 给 `VARCHAR` 列传数字做等值查询。** ⚠️ **索引失效**，必须加引号。
4. **❌ 金额用 `FLOAT`/`DOUBLE`。** 见 1.2。
5. **❌ 忘记「区分大小写」这个维度。** 用户名/密码/token 必须 `utf8mb4_bin`。
6. **❌ 用整数存手机号。** 丢前导 0，且不能字符串拼接。

## 小结

- **四大分类**：数值（多大）/ 字符串（多长）/ 日期时间（何时）/ 特殊（其他）
- ⭐ **存储范围总表**要记住量级：`INT UNSIGNED` ≈ 42.9 亿、`TIMESTAMP` 到 2038、`TEXT` 64KB
- 查类型用 `SHOW CREATE TABLE\G`（最全）或 `information_schema.COLUMNS`（可批量）
- ⚠️ **隐式类型转换是索引失效的隐蔽原因**——`VARCHAR` 列等值查询必须传字符串
- ⭐ **选型五问**：定大类 → 要不要小数 → 定长还是变长 → 时区和 2038 → 区分大小写
- **转换行为完全由 `sql_mode` 决定**——这就是严格模式重要的原因
