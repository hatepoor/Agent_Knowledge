## 一、两个概念的区别

⚠️ **这一节必须先分清，否则后面全是混乱。**

| 概念 | 回答的问题 | 例子 |
|------|-----------|------|
| **字符集（character set）** | ⭐ **能存哪些字符？每个字符几个字节？** | `utf8mb4`、`latin1` |
| **排序规则（collation）** | ⭐ **怎么比较和排序这些字符？** | `utf8mb4_0900_ai_ci` |

⭐ **类比**：字符集是「字典里有哪些字」，collation 是「按什么顺序查这些字」（拼音？笔画？）。

### collation 名的三段式结构 ⭐

```
utf8mb4_0900_ai_ci
   │      │   │ └── ci = case insensitive（不区分大小写）
   │      │   └──── ai = accent insensitive（不区分重音）
   │      └──────── 0900 = Unicode 9.0 算法
   └─────────────── 字符集
```

⭐ **同一字符集下有几十种 collation，差异全在「比较和排序的规则」。**

---

## 二、MySQL 8.0 的两个默认

| collation | 全称含义 | 特点 |
|-----------|---------|------|
| ⭐ **`utf8mb4_0900_ai_ci`** | Unicode 9.0，accent/case 不敏感 | ⭐ **MySQL 8.0 默认** |
| `utf8mb4_general_ci` | 通用规则，较宽松 | MySQL 5.7 默认，**8.0 里是遗留** |
| `utf8mb4_bin` | 二进制精确比较 | ⭐ **区分大小写和重音** |

⚠️ **8.0 默认从 `general_ci` 改成了 `0900_ai_ci`**，带来两个实际差异：

1. **`general_ci` 的排序规则不严格符合 Unicode**：某些字符的比较结果「不对」
2. **`0900_ai_ci` 用 Unicode 9.0 算法**：多语言排序更正确

## 三、排序规则如何影响索引 ⚠️★

⚠️ **这是本篇最重要的机制，也是生产事故的常见来源。**

### 问题：collation 不一致，索引完全失效

```sql
CREATE TABLE t_a (
  name VARCHAR(50) COLLATE utf8mb4_general_ci
) ENGINE=InnoDB;

CREATE TABLE t_b (
  name VARCHAR(50) COLLATE utf8mb4_0900_ai_ci
) ENGINE=InnoDB;

-- 两表 JOIN，走索引
SELECT * FROM t_a JOIN t_b ON t_a.name = t_b.name;
-- ✅ 快，走索引

-- ⚠️ 改成显式指定不同 collation
SELECT * FROM t_a JOIN t_b ON t_a.name = t_b.name
  COLLATE utf8mb4_general_ci;
-- ❌ 极慢！索引全部失效
```

### ⭐ 为什么会失效（机制链条）

```
① 两列的 collation 不一致
        ↓
② 无法直接比较「原始字节」（排序规则不同，字节大小不等于排序位置）
        ↓
③ 优化器必须对每一行做「转换后再比较」
        ↓
④ 转换后的结果无法用原索引查找
        ↓
⑤ 退化成全表扫描 O(n×m)
```

⚠️ **MySQL 的显式 `COLLATE` 优先级高于列定义**，所以你手写的那个 collation 覆盖了列上的设置，两边变成「一个 general 一个 0900」，索引必废。

### 索引自身也受影响

```sql
CREATE TABLE users (
  name VARCHAR(50) COLLATE utf8mb4_general_ci,
  email VARCHAR(255) COLLATE utf8mb4_0900_ai_ci,   -- ⚠️ 不一致
  INDEX idx_name (name),
  INDEX idx_email (email)
);

-- 单列查询各自都能走索引
SELECT * FROM users WHERE name = 'ABC';        -- ✅ 走 idx_name
SELECT * FROM users WHERE email = 'a@b.com';   -- ✅ 走 idx_email

-- ⚠️ 但同一张表里两种 collation，复杂查询（OR、UNION、子查询）无法合并索引
```

⭐ **规范要求：一张表内所有列用同一个 collation，最好全库统一。**

## 四、大小写敏感的影响 ⚠️

```sql
-- MySQL 默认（ci = case insensitive）
SELECT * FROM users WHERE name = 'zhangsan';
SELECT * FROM users WHERE name = 'ZhangSan';   -- ⚠️ 查得到，同一行！

-- 需要区分大小写
SELECT * FROM users WHERE name = 'zhangsan' COLLATE utf8mb4_bin;
-- 或者建列时用 COLLATE utf8mb4_bin
```

### ⚠️ 常见事故

⚠️ **密码、token、邮箱这类字段用了默认的 `ci`，导致「大小写不同的两个值被判为相同」。**

```
场景：用户名 zhangsan 已注册
  ↓
有人注册 ZhangSan
  ↓
⚠️ UNIQUE 索引不报错（因为 ci 认为两者相同，会报 Duplicate）
  ↓
但登录时输入 ZhangSan，能登上 zhangsan 的账号！
```

### ⭐ 必须用 `utf8mb4_bin` 的字段

| 字段 | 为什么 |
|------|-------|
| ⭐ **用户名** | 大小写不同应是不同账号 |
| ⭐ **密码 / 密码哈希** | 必须精确匹配 |
| ⭐ **Token / API Key** | 精确匹配 |
| ⭐ **邮箱** | ⚠️ 邮箱本地部分理论区分大小写（实际多数服务不区分，看业务） |
| 手机号 | 纯数字，无所谓（但建议统一） |

## 五、五个层级

⚠️ **字符集设置有五个层级，上层被下层继承，一旦下层显式设置就隔离了上层。**

| 层级 | 设置方式 | 影响范围 |
|------|---------|---------|
| **服务器** | `character-set-server` / `collation-server` | 所有库 |
| **数据库** | `CREATE DATABASE ... DEFAULT CHARSET x COLLATE y` | 库内所有表 |
| **表** | `CREATE TABLE ... DEFAULT CHARSET x COLLATE y` | 表内所有列 |
| **列** | `name VARCHAR(50) CHARACTER SET x COLLATE y` | 单列 |
| **连接** | 客户端 `charset` 参数 | ⚠️ **连接层还有自己的设定** |

### ⚠️ 第五层的特殊性

⚠️ **连接字符集和列字符集不一致时也会出问题**：

```sql
SET NAMES utf8mb4;                  -- 连接设为 utf8mb4
CREATE TABLE t (name VARCHAR(50));   -- 继承服务器默认 utf8mb4_0900_ai_ci
```

如果服务器默认是 `latin1`，而你 `SET NAMES utf8mb4`，那么：
- 客户端发的是 utf8mb4 字节
- MySQL 以为是 latin1 解码 → **乱码**

**Python 里这个参数叫 `charset`**：

```python
pymysql.connect(..., charset='utf8mb4')
```

⚠️ **不指定会怎样？** 取决于 PyMySQL 的默认值（通常会根据服务端配置推断），但**显式指定最保险**。

## 六、团队规范模板

⭐ **把这张表贴进团队的数据库规范文档。**

| 项 | 规范 | 原因 |
|---|------|------|
| 字符集 | 一律 `utf8mb4` | 支持 emoji 和全部 Unicode |
| collation | 一律 `utf8mb4_0900_ai_ci` | ⭐ 统一，否则 JOIN 索引失效 |
| ⭐ 用户名/密码/token | `COLLATE utf8mb4_bin` | ⭐ 区分大小写 |
| 表/列名 | 小写 + 下划线（`user_orders`） | ⭐ 避开 Linux 大小写敏感问题 |
| 引擎 | 一律 `InnoDB` | 事务、外键、行锁 |
| 每张表 | 带 `COMMENT` | 可维护性 |
| 每列 | 尽量带 `COMMENT` | |
| 金额 | `DECIMAL(p,2)` | 精确 |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | |
| 时间 | `DATETIME`（不用 `TIMESTAMP`） | 避开 2038 |
| 时区 | 统一 `+00:00` 或 `+08:00` | |
| `sql_mode` | 含 `STRICT_TRANS_TABLES` | 避免静默截断 |

## 七、陷阱

1. **❌ 表 A 用 `general_ci`、表 B 用 `0900_ai_ci`。** JOIN 时索引完全失效。
2. **❌ 同一张表里不同列用不同 collation。** 复杂查询无法合并索引。
3. **❌ 用户名/密码/token 用默认的 `ci` collation。** 大小写不同的值会被判为相同。
4. **❌ 只改服务器层不管表层。** 已有表不会自动变。
5. **❌ 依赖 `SET NAMES` 而不配客户端 `charset`。** 可能出现乱码。
6. **❌ 以为 `utf8mb4` 就万事大吉。** ⚠️ collation 选错一样出问题。

---

## 小结

- **字符集**管「存什么」，**collation** 管「怎么排序和比较」
- collation 名三段：`utf8mb4_0900_ai_ci` = 字符集 + Unicode 9.0 + 不区分重音 + 不区分大小写
- 8.0 默认 `utf8mb4_0900_ai_ci`（5.7 是 `general_ci`）
- ⚠️ **collation 不一致会导致 JOIN 索引完全失效**（退化成 O(n×m) 全表扫描）——因为无法直接比较字节，必须逐行转换
- ⭐ **用户名/密码/token 必须 `utf8mb4_bin`**
- 五个层级：服务器 → 库 → 表 → 列 → 连接，**下层显式设置会隔离上层**
