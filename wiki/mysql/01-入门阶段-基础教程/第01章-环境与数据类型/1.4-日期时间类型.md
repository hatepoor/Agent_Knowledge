## 一、五种类型

### 定义

> **日期时间类型表示「哪个时刻」或「哪段时长」。** 区别在**精度**、**范围**、**是否带时区语义**。

| 类型 | 格式 | 字节 | 范围 |
|------|------|-----:|------|
| `DATE` | `2026-10-13` | 3 | 1000-01-01 ~ 9999-12-31 |
| `TIME` | `13:45:02` | 3 | -838:59:59 ~ 838:59:59 |
| `DATETIME` | `2026-10-13 13:45:02` | 5 | 1000-01-01 00:00:00 ~ 9999-12-31 23:59:59 |
| `TIMESTAMP` | `2026-10-13 13:45:02` | 4 | 1970-01-01 00:00:01 ~ **2038-01-19 03:14:07** |
| `YEAR` | `2026` | 1 | 1901 ~ 2155 |

### 选型

| 需求 | 选 |
|------|-----|
| 生日、账期、纪念日（只有日期） | `DATE` |
| ⭐ **业务时间（创建/更新时间）** | ⭐ **`DATETIME`** |
| 需要时区语义 | `TIMESTAMP`（⚠️ 注意 2038） |
| ⚠️ **时长**（跑了多久） | ⚠️ **`TIME`** |
| 只要年份 | `YEAR` |

## 二、⚠️ `TIME` 存的是「时长」，不是「时刻」

⚠️ **这是最容易误解的一点。**

```sql
-- TIME 的设计意图是「时长」
CREATE TABLE tasks (duration TIME);

INSERT INTO tasks VALUES ('100:00:00');   -- ✅ 「跑了 100 小时」

-- 如果你想存「凌晨 1 点」这个时刻
INSERT INTO tasks VALUES ('01:00:00');    -- ⚠️ 语法上可以，但语义是「1 小时的时长」
```

**判断方法**：`TIME` 的范围是 `-838:59:59 ~ 838:59:59`——⚠️ **能超过 24 小时，说明它不是「一天中的时刻」。**

⭐ **「一天中的时刻」怎么存？** 用 `TIME` 也能凑合（它不带日期），但要清楚语义。⭐ **更好的做法是用 `DATETIME` 存完整时间戳，展示时只取时间部分。**

## 三、⭐ `DATETIME` vs `TIMESTAMP`（时区）

⚠️ **这是本篇最重要的区别。**

### 核心差异

| | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 存什么 | ⭐ **你给的字面值** | ⭐ **转成 UTC 后存** |
| 读出来 | 原样返回（**不转换**） | 按当前 `time_zone` 转回本地 |
| 2038 限制 | ❌ 无 | ⚠️ **有** |
| 时区语义 | ⚠️ 不带 | ✅ 带 |

### 实测

```sql
SET time_zone = '+00:00';
SELECT NOW();    -- 2026-10-13 05:35:00（UTC）

SET time_zone = '+08:00';
SELECT NOW();    -- 2026-10-13 13:35:00（东八区）
-- ⚠️ 同一个时刻，不同连接时区下 NOW() 返回不同数字
```

### 这导致什么实际差异

```
场景：一条记录的创建时间是「北京时间 2026-10-13 13:35」

用 DATETIME：
  · 无论连接的 time_zone 是什么，读出来都是 2026-10-13 13:35:00
  · ⚠️ 但如果写入时连接的 time_zone 不同，存的值就不同
  · ⚠️ 部署到 UTC 服务器后，同样的代码存出来的时间差 8 小时

用 TIMESTAMP：
  · 内部存 UTC，读取时按连接的 time_zone 转换
  · ✅ 换服务器时区不影响语义
  · ⚠️ 但 2038 年后溢出
```

### ⭐ 生产建议

| 方案 | 做法 | 优劣 |
|------|------|------|
| **A. 全链路 UTC** ⭐ | 服务器、连接、业务代码统一 UTC，展示层转本地 | ✅ 无歧义、跨时区友好；⚠️ 展示要转换 |
| **B. 统一东八区** | 所有层设 `+08:00` | ✅ 国内业务简单；⚠️ 出海要改 |
| **C. 不设** | 默认 `SYSTEM` | ❌ 依赖机器配置 |

⚠️ **⚠️ 绝对不要用方案 C。** `time_zone` 默认是 `SYSTEM`（跟随操作系统）——⚠️ **开发机是东八区、生产机是 UTC 时，同一份代码存出来的时间含义不同。**

### 配置

```sql
-- my.cnf
[mysqld]
default-time-zone = '+00:00'      -- 或 '+08:00'

-- 运行期
SET GLOBAL time_zone = '+00:00';

-- 查看
SELECT @@global.time_zone, @@session.time_zone;
```

⭐ **推荐组合**：**`DATETIME` 类型 + 显式设置 `time_zone`**。
理由：避开 `TIMESTAMP` 的 2038 问题，同时通过显式 `time_zone` 消除歧义。

## 四、`ON UPDATE CURRENT_TIMESTAMP`

```sql
CREATE TABLE t (
  id INT PRIMARY KEY AUTO_INCREMENT,
  data VARCHAR(100),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                            ON UPDATE CURRENT_TIMESTAMP
);
```

| 字段 | 行为 |
|------|------|
| `created_at` | 插入时自动设为当前时间 |
| `updated_at` | ⭐ **该行任意列被更新时，自动刷新** |

### ⚠️ 两个限制

**限制 1：值没变则不更新**

```sql
UPDATE t SET data = 'x' WHERE id = 1;   -- data 本来就是 'x'
-- ⚠️ updated_at 不变（MySQL 检测到值没实际变化）
```

**限制 2：⚠️ 它不是「绝对可靠的最后修改时间」**

| 情况 | 会触发吗 |
|------|---------|
| `UPDATE` | ✅ |
| `LOAD DATA` 导入 | ⚠️ 部分情况不触发 |
| `REPLACE` | ⚠️ 行为不同（等价于删+插） |
| 直接改数据文件 | ❌ 不触发 |

⭐ **要「绝对准确」的审计时间，用 binlog 或专门的审计表。**

## 五、日期函数速查

⚠️ **完整版见 [[mysql/函数手册]] 与 [[mysql/01-入门阶段-基础教程/第03章-查询与CRUD/3.5-常用函数详解]]。** 这里只列最常用和最容易错的。

### 提取部分

```sql
YEAR(d), MONTH(d), DAY(d)          -- 年月日
HOUR(t), MINUTE(t), SECOND(t)      -- 时分秒
DAYOFWEEK('2026-10-13')            -- ⚠️ 3（周二，⚠️ 1=周日）
WEEKDAY('2026-10-13')              -- ⭐ 1（周二，0=周一）
LAST_DAY('2026-02-05')             -- 2026-02-28
```

⚠️⚠️ **`DAYOFWEEK` 的 1 是周日，不是周一。** 业务上的「周一」要用 `WEEKDAY` 或 `DAYOFWEEK(d) IN (2,3,4,5,6)`。

### 计算

```sql
DATE_ADD(NOW(), INTERVAL 7 DAY)
DATE_SUB(NOW(), INTERVAL 30 DAY)
DATEDIFF('2026-10-13', '2026-10-01')            -- ⚠️ 12（只算天）
TIMESTAMPDIFF(HOUR, a, b)                       -- ⭐ 精确到任意单位
```

⚠️ **`DATEDIFF` 只算天，会抹掉时分秒**：

```sql
DATEDIFF('2026-10-02 01:00:00', '2026-10-01 23:00:00')   -- ⚠️ 1（实际只差 2 小时）
TIMESTAMPDIFF(HOUR, '2026-10-02 01:00:00', '2026-10-01 23:00:00')  -- ⭐ 2
```

### ⚠️⚠️ `DATE_FORMAT` 的格式符

```sql
DATE_FORMAT(NOW(), '%Y-%m-%d %H:%i:%s')
-- 2026-10-13 13:35:00
```

| 格式符 | 含义 | ⚠️ 常见错认 |
|--------|------|-----------|
| `%Y` / `%y` | 四位年 / 两位年 | |
| `%m` / `%c` | 两位月 / 不补零月 | |
| `%d` | 两位日 | |
| `%H` / `%h` | 24 小时 / 12 小时 | |
| ⚠️ **`%i`** | ⚠️ **分钟** | ⚠️⚠️ **很多人以为 `%M`** |
| ⚠️ **`%M`** | ⚠️ **英文月名**（October） | |
| `%S` / `%s` | 秒 | |

⚠️⚠️ **MySQL 的分钟是 `%i` 不是 `%M`。** `%M` 是英文月名。⭐ **对照 PostgreSQL**：PG 用 `TO_CHAR(ts, 'YYYY-MM-DD HH24:MI:SS')`，格式符完全不同（`YYYY` 才是年，`MI` 才是分钟）——**跨库迁移时这里必错**。

📌 详见 [[mysql/01-入门阶段-基础教程/第00章-学前准备/0.3-MySQL与PostgreSQL的差异]]。

## 六、陷阱

1. **❌ 用 `TIMESTAMP` 存到 2038 年之后。** 新表用 `DATETIME`。
2. **❌ 依赖 `time_zone = SYSTEM`。** 换服务器时区含义就变，必须显式设置。
3. **❌ 用 `TIME` 存「一天中的时刻」。** 它设计意图是时长（范围超 24 小时）。
4. **❌ `DAYOFWEEK` 当作「周几=1 表示周一」。** 它 1=周日。
5. **❌ `DATE_FORMAT` 用 `%M` 取分钟。** 是 `%i`。
6. **❌ `DATEDIFF` 用来算小时差。** 抹掉时分秒，用 `TIMESTAMPDIFF`。
7. **❌ 用 `NOW()` 做生成列的默认值。** 非确定性函数不允许。
8. **❌ 以为 `ON UPDATE CURRENT_TIMESTAMP` 是绝对可靠的审计时间。**

## 小结

- 五种类型：`DATE`（日期）/ `TIME`（**时长**）/ `DATETIME`（业务时间）/ `TIMESTAMP`（带时区，⚠️ 2038）/ `YEAR`
- ⚠️ **`TIME` 的范围超 24 小时，说明它存的是「时长」不是「时刻」**
- ⭐ **`DATETIME` 存字面值不转换，`TIMESTAMP` 转 UTC 存并按连接时区转换**
- ⭐ **生产推荐：`DATETIME` + 显式 `time_zone`**（避开 2038 + 消除歧义）
- ⚠️ **绝不能依赖 `time_zone = SYSTEM`**
- 日期函数三个坑：**`DAYOFWEEK` 1=周日**、**`DATE_FORMAT` 分钟是 `%i`**、**`DATEDIFF` 只算天**
- `ON UPDATE CURRENT_TIMESTAMP` 有「值没变不更新」和「不是绝对可靠」两个限制
