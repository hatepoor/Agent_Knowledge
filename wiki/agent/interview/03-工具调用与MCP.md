# 工具调用与 MCP

> **适用场景**：Agent 岗核心题。工具层出问题，模型再强也没用。
> **主线**：**Function Calling 是「模型表达调用意图」，MCP 是「工具怎么接进来」**，两者不在一个层次。

---

## Q1. Function Calling 的原理是什么？是模型真的执行了函数吗？

**答：**

**不是。模型只输出「调用意图」，真正执行的是你的应用代码。**

完整链路：

```
① 应用把工具定义（name / description / parameters schema）随请求传给模型
② 模型判断需要调用，返回结构化 tool_calls：
   [{"id": "call_1", "name": "get_weather", "arguments": {"city": "北京"}}]
③ 应用解析 tool_calls，执行本地函数/HTTP 请求
④ 应用把结果作为 tool 消息回传：
   {"role": "tool", "tool_call_id": "call_1", "content": "晴，26℃"}
⑤ 模型基于结果继续生成，或继续调用其他工具
```

关键点：

| 点 | 说明 |
|----|------|
| **模型不接触真实系统** | 它只生成 JSON，权限、鉴权、执行都在应用侧 |
| **schema 是契约** | 模型按 schema 生成参数，应用必须再校验一次 |
| **多轮** | 一次响应可以包含多个 tool_calls，也可以连续多轮 |
| **不是所有模型都原生支持** | 不支持时用提示词解析 JSON，但可靠性差很多 |

**追问：模型怎么「知道」该调哪个工具？**
→ 靠工具名、描述、参数 schema 和当前上下文做语义匹配。**所以工具描述写得清不清楚，直接决定选择准确率**——这是工程问题，不是模型问题。

## Q2. 工具描述和参数 schema 怎么写，才能让模型选对？

**答：**

工具定义是**给模型看的 API 文档**，不是给人看的注释。

| 要素 | 差的做法 | 好的做法 |
|------|---------|---------|
| **name** | `tool1`、`do_stuff` | `get_order_status`（动宾、无歧义） |
| **description** | 「查询订单」 | 「按订单号查询物流状态；**仅在用户提供订单号时使用**；不用于退款」 |
| **参数描述** | `order_id: string` | `order_id: 订单号，形如 A123456，不是用户 ID` |
| **枚举** | 自由字符串 | `status: enum["pending","shipped","done"]` |
| **必填** | 全部 required | 只把真正必需的标 required |
| **示例** | 无 | 在 description 里给一个调用示例 |

**三条经验**：

1. **写清「什么时候不要用」**，比写「什么时候用」更能减少误选；
2. **参数名用业务语言**，别用 `arg1`、`data`；
3. **相似工具要合并或明确区分**（`search_docs` vs `search_web` 要在描述里说清边界）。

**追问：工具描述能写多长？**
→ 有成本，但**准确性优先**。一个工具描述多 50 字，换来误选率下降，通常划算。真正要控制的是**工具数量**，不是单个描述长度。

## Q3. 工具太多（几十个）怎么办？

**答：**

工具数量超过 **10~20 个**后，选择准确率通常明显下降。四种治理手段：

| 手段 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **分组 + 路由** | 先判断领域，再只给该领域的工具 | 准确率高 | 多一次决策 |
| **工具检索** | 按用户问题检索最相关的 K 个工具 | 可扩展到几百个 | 检索可能漏 |
| **合并粗粒度工具** | 把 5 个细工具合成 1 个带 `action` 参数的工具 | 减少选择空间 | 单工具内部逻辑变复杂 |
| **子 Agent 隔离** | 每个子 Agent 只带自己领域的工具 | 职责清晰、可并行 | 编排成本高 |

**推荐组合**：**领域路由 + 工具检索 + 子 Agent 隔离**。先按业务域分流，域内再用检索缩小候选，复杂域直接交给专属子 Agent。

**追问：为什么不能靠「让模型自己记住所有工具」？**
→ 工具描述全塞进上下文会**占用大量 token、互相干扰**，而且模型对长列表的注意力会衰减。**工具选择本质是检索问题，不是记忆问题。**

## Q4. 并行工具调用怎么用？有什么坑？

**答：**

模型可以在一次响应里返回多个 `tool_calls`，应用**并发执行**后一起回传：

```python
results = await asyncio.gather(*[run(tc) for tc in resp.tool_calls])
```

适合：**互不依赖的查询**（同时查天气、汇率、库存）。

坑：

| 坑 | 说明 |
|----|------|
| **有依赖时不能并行** | 第二步需要第一步的返回值，模型却一次全发出 |
| **副作用顺序** | 转账、扣库存这类操作，顺序不能乱 |
| **错误隔离** | 一个失败不应让整批结果丢失；每个 tool_call 单独返回错误 |
| **结果顺序** | 回传时要按 `tool_call_id` 对应，不能靠数组顺序猜 |
| **限流** | 一次 20 个并发请求可能打爆下游 |

**追问：怎么判断该不该并行？**
→ 看**数据依赖**和**副作用**。只读、无依赖 → 并行；有依赖或写操作 → 串行，或在工具描述里明确「必须先调用 X」。

## Q5. 工具调用失败了，怎么让 Agent 正确处理？

**答：**

**错误要「可被模型理解」，而不是「可被程序员调试」。**

| 错误类型 | 回传给模型的内容 |
|---------|-----------------|
| **参数错误** | 哪个字段错了、期望什么格式、给一个正确示例 |
| **业务错误**（订单不存在） | 明确的业务语义，不要抛堆栈 |
| **临时故障**（超时/429） | 「暂时不可用，可稍后重试」+ 重试建议 |
| **权限错误** | 「无权限访问 X」，不要让模型反复试 |

错误处理四原则：

1. **不要吞异常**：吞掉后模型会以为成功，继续基于错误前提推理；
2. **区分可重试/不可重试**：可重试的由应用层退避重试，不要都丢给模型；
3. **错误信息要短且具体**：一长串堆栈会污染上下文；
4. **保留 `tool_call_id`**：否则模型对不上是哪次调用失败。

**追问：工具失败后让模型自己重试，合适吗？**
→ 只适合**参数类错误**（模型能改）。网络超时、权限问题让模型重试，只会浪费轮次。**重试策略应该在应用层，不在提示词里。**

## Q6. 模型编造工具参数（幻觉参数）怎么办？

**答：**

三层防御，从「约束」到「兜底」：

| 层 | 做法 |
|----|------|
| **schema 约束** | 枚举、格式（date/uuid）、必填、`additionalProperties: false` |
| **服务端校验** | 执行前再校验一次；不合法直接返回结构化错误，让模型修正 |
| **业务兜底** | 关键操作前做存在性/权限/额度校验；高危操作加人工确认 |

常见幻觉：

- 编造不存在的 `order_id`；
- 把用户昵称当 ID；
- 日期格式错误；
- 传了 schema 里没有的字段。

**追问：为什么 schema 约束不能完全解决？**
→ 因为 schema 只保证**结构合法**，不保证**语义正确**。`order_id="A123"` 格式没问题，但可能根本不存在。**语义校验必须在工具实现里做。**

## Q7. MCP 是什么？它和 Function Calling 是什么关系？

**答：**

**MCP（Model Context Protocol）是「模型应用 ↔ 外部工具/数据源」的标准化接入协议。**

一句话对比：

| 层 | 解决什么 | 类比 |
|----|---------|------|
| **Function Calling** | 模型怎么**表达**「我要调什么」 | 点菜的菜单格式 |
| **MCP** | 工具怎么**接进**应用、怎么被发现和调用 | 厨房的标准化接口 |

MCP 的核心能力（Server 侧暴露三类）：

| 能力 | 作用 |
|------|------|
| **Tools** | 可执行的动作（查库、发请求） |
| **Resources** | 可读取的数据（文件、记录） |
| **Prompts** | 预置的提示模板 |

协议层：**JSON-RPC 2.0**；传输方式常见 **stdio（本地进程）** 和 **HTTP（远程服务）**。

**关系**：MCP 让工具接入标准化，**Function Calling 仍是模型调用这些工具的方式**。两者互补，不是替代。

**追问：MCP 最大的价值是什么？**
→ **解耦**。工具提供方按协议实现一次，所有支持 MCP 的客户端都能用；不用为每个框架写一套适配。**它解决的是「N 个模型 × M 个工具」的集成爆炸。**

## Q8. MCP 的传输方式和安全边界要注意什么？

**答：**

| 传输 | 适用 | 风险 |
|------|------|------|
| **stdio** | 本地进程（文件系统、本地 CLI） | Server 以**你的权限**运行，能读本地文件、执行命令 |
| **HTTP/SSE** | 远程服务、多客户端共享 | 认证、越权、中间人、工具投毒 |

安全要点：

| 风险 | 说明 | 对策 |
|------|------|------|
| **不可信 Server** | 第三方 MCP 可能返回恶意内容或诱导调用 | 只接可信来源；审工具描述 |
| **工具投毒** | 工具描述里藏指令，劫持模型行为 | 把工具描述当不可信输入；做审查 |
| **权限过大** | stdio Server 继承本地权限 | 最小权限、沙箱、只读挂载 |
| **远程认证缺失** | HTTP Server 裸奔 | OAuth/Token、mTLS、网关鉴权 |
| **数据外带** | 工具把敏感数据发到外部 | 出站白名单、审计日志 |

**追问：MCP 能解决 Prompt 注入吗？**
→ 不能。**MCP 只标准化接入，不负责内容可信**。工具返回的文本仍可能包含注入指令，必须在应用层做隔离和校验。

## Q9. 设计一个好用的工具，有哪些工程原则？

**答：**

七条，按重要性排：

| 原则 | 说明 |
|------|------|
| **① 单一职责** | 一个工具只做一件事；不要 `do_everything(action=...)` 塞十个功能 |
| **② 幂等** | 重试不产生重复副作用；写操作带幂等键 |
| **③ 返回结构化 + 摘要** | 给模型「结论 + 关键字段」，原始大对象放外面 |
| **④ 错误语义化** | 错误信息让模型能判断「该重试还是换方法」 |
| **⑤ 参数少而明确** | 参数越多，模型填错概率越高 |
| **⑥ 命名可读** | `search_orders` 优于 `so`；动宾结构 |
| **⑦ 限制返回大小** | 截断/分页，避免一次塞爆上下文 |

**追问：工具返回应该给「原始数据」还是「给模型看的摘要」？**
→ **两者都要，但进上下文的是摘要**。原始数据落文件/DB，摘要里带引用 id，需要细节时再让模型调另一个工具取。**这是控制上下文最有效的手段之一。**
