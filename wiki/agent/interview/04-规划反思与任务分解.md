# 规划、反思与任务分解

> **适用场景**：中高级 Agent 岗。面试官想确认你会不会「把复杂任务拆开」，而不是只会写 ReAct。
> **主线**：**规划解决「先做什么」，反思解决「做错了怎么改」，两者都不能替代外部验证。**

---

## Q1. 什么时候需要规划？什么时候不需要？

**答：**

**规划不是默认动作。**它适合「步骤多、有依赖、需要全局视角」的任务。

| 需要规划 | 不需要规划 |
|---------|-----------|
| 任务有多个阶段，顺序重要 | 单步就能完成 |
| 子任务之间有依赖 | 子任务彼此独立、可并行 |
| 需要先分配预算/资源 | 一次调用就能拿到结果 |
| 长任务，容易迷路 | 短任务，轮次少 |

**判断标准**：**如果「先做哪一步」会显著影响结果或成本，就值得规划；否则边做边看（ReAct）更轻。**

**追问：规划会不会让 Agent 变慢？**
→ 会多一次模型调用，但可能**减少后续试错轮次**。长任务通常净收益为正；短任务则纯亏。**要看「规划省下的轮次」是否大于「规划本身的成本」。**

## Q2. Plan-and-Execute 是怎么工作的？

**答：**

三个角色：

```
Planner（规划）→ Executor（逐步执行）→ Replanner（按需调整）
```

| 阶段 | 做什么 |
|------|--------|
| **Plan** | 把目标拆成有序步骤，每步有明确的输入/产出 |
| **Execute** | 按步骤执行，每步可以是 ReAct、工具调用或子 Agent |
| **Replan** | 某步失败/前提变化时，修改剩余计划 |

```python
plan = planner.invoke(goal)          # ["查资料", "对比", "写报告"]
for step in plan:
    result = executor.invoke(step)
    if not result.ok:
        plan = replanner.invoke(goal, plan, done, result.error)
```

**和 ReAct 的区别**：ReAct 每步都重新决定下一步；Plan-and-Execute **先锁定全局结构**，只在必要时调整。

**追问：Replan 什么时候触发？**
→ 三类：① 某步连续失败；② 执行结果推翻了计划的前提假设；③ 预算/时间不够，需要缩减范围。**没有重规划机制的计划系统，本质上是一次性脚本。**

## Q3. 任务分解的粒度怎么定？

**答：**

好的子任务满足四个条件：

| 条件 | 说明 |
|------|------|
| **可独立验证** | 有明确的完成标准（测试通过、字段齐全、文档生成） |
| **单步可完成** | 一个子任务不需要再拆就能执行 |
| **上下文自足** | 执行它所需的信息都在输入里，不用回头翻全局 |
| **产出可交接** | 输出是结构化的，下一步能直接用 |

**过粗**：一个子任务还是「写完整报告」，等于没拆。
**过细**：拆成「打开文件」「读第一行」，协调成本超过执行成本。

**经验**：**按「可交付物」拆，不按「动作」拆。**「产出竞品对比表」是子任务；「调用搜索工具」不是。

**追问：拆完之后发现漏了一步怎么办？**
→ 正常。规划不可能一次完美，**要允许在执行中追加/合并子任务**，并把变更记录到状态里，避免后续步骤基于旧计划。

## Q4. Reflection 是什么？怎么实现？

**答：**

**Reflection 是让模型对自己的输出做审查，再根据审查结果改进。**

两种形态：

| 形态 | 做法 |
|------|------|
| **单轮自审** | 生成 → 让模型按检查清单评审 → 修改 |
| **多轮迭代** | 生成 → 评审 → 修改 → 再评审，直到通过或达到轮次上限 |

检查清单比「你觉得哪里不好」有效得多：

```
□ 是否回答了用户的原问题？
□ 关键结论是否有依据？
□ 是否遗漏了约束条件？
□ 格式是否符合要求？
```

**追问：Reflection 什么时候有效？**
→ 当**有明确的评判标准**时（代码能跑测试、报告有检查项、SQL 能执行）。如果标准模糊（「写得好不好」），反思容易变成自我表扬或无关痛痒的修改。

## Q5. Reflection 和 Reflexion 的区别是什么？

**答：**

| 维度 | Reflection | Reflexion |
|------|-----------|-----------|
| 范围 | **单次生成内**的审查与修改 | **跨尝试**的经验复用 |
| 记忆 | 不需要长期记忆 | 把反思写入记忆，下次重试时带上 |
| 触发 | 生成后立即 | 一次尝试失败后 |
| 关键 | 评判标准 | 失败判定 + 记忆写入 |

```
Reflection：写 → 审 → 改（同一次任务内）
Reflexion：做 → 失败 → 总结原因 → 存起来 → 下次带着做
```

**追问：为什么 Reflexion 需要「失败判定」？**
→ 因为不知道失败，就不会触发反思。**没有验证器的 Reflexion，等于让模型自己说「我失败了」，不可靠。**

## Q6. 模型能可靠地评估自己的输出吗？怎么提高可靠性？

**答：**

**不可靠，而且有系统性偏差**：

| 偏差 | 表现 |
|------|------|
| **自利偏差** | 倾向给自己的答案打高分 |
| **一致性偏差** | 倾向认为自己的推理是对的 |
| **标准漂移** | 同一输出，不同轮次评分不同 |

提高可靠性的四种手段：

| 手段 | 做法 |
|------|------|
| **外部验证器** | 单元测试、SQL 执行、JSON schema 校验、规则检查 |
| **换模型评审** | 用另一个模型/另一次独立调用评审，减少自我偏袒 |
| **结构化评分** | 按维度打分（正确性/完整性/格式），而不是整体「好不好」 |
| **人工抽检** | 定期抽样校准自动评审的准确率 |

**一句话**：**能用程序验证的，不要用模型评审；必须用模型评审的，要校准。**

**追问：LLM-as-judge 靠谱吗？**
→ 在**有明确评分标准 + 参考答案**的任务上比较靠谱；开放式创作、主观偏好类任务偏差大。**它是评估工具，不是真理。**

## Q7. 长任务怎么防止「目标漂移」？

**答：**

五道防线：

| 防线 | 做法 |
|------|------|
| **目标置顶** | 原始目标放在 system 或固定位置，每轮都可见 |
| **阶段检查点** | 每个阶段结束复述「目标是什么、现在到哪了」 |
| **结构化状态** | 目标、已完成、待办、约束写在状态里，不靠模型记忆 |
| **定期对齐** | 每 K 轮做一次「是否偏离目标」的自检 |
| **外部验收** | 最终结果按原始需求逐条核对 |

**根因**：上下文越长，早期目标在注意力中的权重越低；模型会被最近的工具结果牵着走。

**追问：为什么「把目标再贴一遍」有效？**
→ 因为它把目标从「很久以前的历史」变成「当前可见的约束」。**这不是模型能力问题，是上下文工程问题。**

## Q8. Tree of Thoughts（ToT）适合什么场景？为什么生产上很少见？

**答：**

ToT 的核心是**多路径生成 + 评估 + 回溯**：

```
        问题
       /  |  \
     思路A 思路B 思路C
      |     |     |
    评估   评估   评估
      \     |     /
       选最优/回溯
```

适合：

- 搜索空间不大但需要权衡的推理任务（谜题、规划、数学）；
- 一步错会导致全盘错的场景；
- 有可靠评估函数（能判断中间状态好坏）。

生产上少见的原因：

| 原因 | 说明 |
|------|------|
| **成本高** | 每条路径都要多次模型调用 |
| **延迟高** | 串行展开 + 评估 |
| **评估难** | 中间状态好坏往往没有可靠判据 |
| **收益不稳定** | 很多任务用一次规划 + 反思就够 |

**追问：ToT 的思想能不能用在工程上？**
→ 能，但通常降级为「**少量候选 + 外部评估**」：生成 2~3 个方案，用规则/测试选一个。**不需要真的建一棵树，保留「多路径 + 评估」的内核即可。**
