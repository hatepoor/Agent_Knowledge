# 记忆与上下文工程

> **适用场景**：做过「有记忆的 Agent」必问。答「存到向量库」会被继续追问到崩。
> **主线**：**记忆不是「存得越多越好」，是「在正确的时机，把正确的信息放进上下文」。**

---

## Q1. 短期记忆和长期记忆有什么区别？

**答：**

| 维度 | 短期记忆 | 长期记忆 |
|------|---------|---------|
| **范围** | 当前会话/任务 | 跨会话、跨任务 |
| **存什么** | 对话历史、工具结果、任务进度 | 用户偏好、事实、历史结论、经验 |
| **存哪** | 上下文窗口 + 会话状态 | 数据库 / 向量库 / KV Store |
| **生命周期** | 会话结束即失效（或归档） | 长期保留，可更新、可遗忘 |
| **访问方式** | 每轮直接带入 | 按需检索后注入 |
| **主要问题** | 窗口不够、越跑越长 | 写入质量、检索精度、冲突、隐私 |

**一句话**：**短期记忆解决「这一轮别忘了」，长期记忆解决「下次还记得」。**

**追问：短期记忆一定要放上下文里吗？**
→ 不一定。可以把完整历史存外部，上下文只放「最近 N 轮 + 任务状态摘要」。**上下文是工作台，不是仓库。**

---

## Q2. 上下文窗口不够用，有哪些管理策略？

**答：**

六种策略，通常组合使用：

| 策略 | 做法 | 适合 |
|------|------|------|
| **滑动窗口** | 只保留最近 N 轮 | 对话型，近期信息最重要 |
| **摘要压缩** | 旧历史压成一段摘要 | 长对话、长任务 |
| **结构化状态** | 目标/进度/约束存字段，不靠历史 | 任务型 Agent |
| **检索注入** | 只把相关片段放进上下文 | 知识密集、文档多 |
| **工具结果截断** | 工具只返回摘要 + 引用 | 检索/SQL 结果大 |
| **分层保留** | 系统约束永久、近期完整、远期摘要 | 通用 |

**推荐组合**：

```
系统提示（永久）
+ 任务状态（结构化，每轮更新）
+ 最近 3~5 轮完整对话
+ 相关检索片段（按当前问题）
+ 远期历史摘要
```

**追问：为什么要单独保留「任务状态」？**
→ 因为摘要是**有损**的，容易把「约束条件」压没。把目标、已完成、待办、硬约束写成结构化字段，**不依赖模型从历史里回忆**，是防目标漂移最有效的手段。

---

## Q3. 摘要压缩怎么做？信息丢了怎么办？

**答：**

三种做法：

| 做法 | 说明 |
|------|------|
| **滚动摘要** | 每 N 轮把最旧的一段压成摘要，保留最近完整轮次 |
| **分段摘要** | 按主题/阶段分别摘要，检索时按需取 |
| **结构化摘要** | 按固定字段提取：目标、结论、约束、未决问题、关键实体 |

推荐**结构化摘要**，因为它比自由文本更稳定：

```markdown
## 任务目标
## 已确认事实
## 关键约束
## 已尝试且失败的方法
## 待办
```

**防丢信息的三个手段**：

1. **摘要 + 原始引用**：摘要里保留 `doc_id` / `message_id`，需要细节时再取；
2. **关键实体单独存**：订单号、人名、金额不进摘要，进结构化字段；
3. **压缩后自检**：让模型回答「原始目标是什么、有哪些硬约束」，答不上就说明压丢了。

**追问：摘要用大模型还是小模型？**
→ 成本敏感用小模型，但**涉及约束/数字的摘要建议用强模型**。摘要错误会一路污染后续推理，省这点钱不划算。

## Q4. 长期记忆怎么做「写入、检索、更新、遗忘」？

**答：**

四个环节都要设计，缺一个就会烂：

| 环节 | 关键问题 | 做法 |
|------|---------|------|
| **写入** | 什么值得记？ | 只记「稳定事实/偏好/结论」，不记寒暄和临时状态；写入前做去重 |
| **检索** | 什么时候取？取多少？ | 语义检索 + 元数据过滤；按当前任务取 Top-K，不是全量注入 |
| **更新** | 新旧冲突怎么办？ | 同实体新事实覆盖旧事实，保留版本/时间戳 |
| **遗忘** | 什么时候删？ | TTL、低频衰减、用户主动删除、合规要求 |

**写入是最容易做错的一环**：

- 什么都记 → 噪声多、检索不准、成本高；
- 只记模型总结 → 丢失原始语义；
- 不记来源 → 后面无法判断可信度。

**建议的记忆条目结构**：

```json
{
  "content": "用户偏好简洁回答，不需要客套",
  "type": "preference",
  "source": "conversation:abc#turn-7",
  "confidence": 0.9,
  "created_at": "...",
  "updated_at": "..."
}
```

**追问：为什么一定要能「遗忘」？**
→ 三个原因：① 记忆会过期（用户换工作、换偏好）；② 错误记忆会一直污染；③ 合规要求「用户可删除」。**没有删除能力的记忆系统，不是资产，是负债。**

## Q5. Agent 记忆和 RAG 有什么区别？

**答：**

技术上高度重叠（都涉及切分、embedding、向量检索），但**语义和使用方式不同**：

| 维度 | Agent 记忆 | RAG |
|------|-----------|-----|
| **内容** | 关于**用户/交互**的信息 | 关于**外部知识**的文档 |
| **来源** | Agent 自己产生/提取 | 预先准备的语料 |
| **写入** | 运行时动态写 | 离线/准实时入库 |
| **检索时机** | 每轮判断要不要取 | 每个问题都取 |
| **更新** | 频繁、按实体覆盖 | 按文档版本更新 |
| **错误后果** | 记错用户偏好，持续影响体验 | 召回错文档，单次答错 |

**一句话**：**RAG 是「查资料」，记忆是「记住你」。**

**追问：能不能用同一套向量库？**
→ 可以，工程上常见。但要**分 namespace/collection**，并且**用不同的检索策略**：记忆更依赖元数据（用户、时间、类型），RAG 更依赖语义相似度和重排。

## Q6. 用户画像应该怎么存？

**答：**

**结构化字段 + 向量记忆结合**，不要全塞向量库。

| 内容 | 存法 | 原因 |
|------|------|------|
| 稳定属性（职业、语言、时区） | 结构化表/KV | 精确读取，不需要语义检索 |
| 偏好（回答长度、语气） | 结构化字段 | 每次都要用，必须稳定 |
| 历史事件（「上次说在准备面试」） | 向量记忆 + 时间戳 | 按语义检索 |
| 推断结论（「偏好技术细节」） | 带置信度的记忆条目 | 可能错，要能修正 |

**更新策略**：

- 显式信息（用户直接说）→ 高置信度，直接写；
- 隐式推断（从行为猜）→ 低置信度，多次验证后再提升；
- 冲突 → 以时间更新、置信度更高的为准。

**追问：画像要不要每次全量注入上下文？**
→ 不要。只注入**与当前任务相关的部分**（比如写代码时不需要「喜欢简短回复」之外的偏好）。全量注入既浪费 token，也容易让模型过度迎合。

## Q7. 多租户场景下，记忆怎么隔离？

**答：**

四层隔离，从逻辑到物理：

| 层 | 做法 | 强度 |
|----|------|------|
| **逻辑隔离** | 所有查询强制带 `tenant_id` 过滤 | 弱，靠代码纪律 |
| **命名空间** | 按租户分 namespace/collection | 中 |
| **行级安全（RLS）** | 数据库策略强制隔离 | 强 |
| **物理隔离** | 独立库/独立实例 | 最强，成本最高 |

**必须做的三件事**：

1. **租户 id 不能由模型生成**，只能来自认证上下文；
2. **检索接口统一封装**，禁止业务代码裸查（否则总会有人忘加过滤）；
3. **写入时校验归属**，防止把 A 的数据写到 B 的命名空间。

**追问：只在应用层加 `WHERE tenant_id = ?` 够吗？**
→ 不够。一次漏写就是数据泄露。**生产上建议 RLS 兜底**，应用层过滤只是第一道。

## Q8. 新旧记忆冲突了，怎么处理？

**答：**

按「冲突类型」分别处理：

| 冲突 | 例子 | 策略 |
|------|------|------|
| **事实更新** | 用户换工作了 | 新事实覆盖旧事实，保留历史版本 |
| **偏好变化** | 以前喜欢详细，现在要简洁 | 以最近一次明确表达为准 |
| **推断 vs 明确** | 推断「喜欢 Python」，用户说「现在用 Go」 | 明确表达优先 |
| **来源冲突** | 两个文档说法不同 | 按来源可信度/时间排序，必要时都保留并标注 |

工程手段：

- **时间戳 + 版本号**：检索时优先新版本；
- **置信度**：低置信度不覆盖高置信度，除非多次验证；
- **软删除**：旧记忆标记失效，不物理删除（便于回溯）；
- **人工确认**：关键冲突（如医疗、财务信息）让用户确认。

**追问：为什么不直接「后来者覆盖」？**
→ 因为后来的可能是**模型推断错误**，不是用户真实变化。**覆盖规则要区分「用户明确说」和「模型猜」。**

## Q9. 上下文里各部分内容的优先级怎么排？

**答：**

按「违反代价」排序，越靠前越不能丢：

| 优先级 | 内容 | 说明 |
|--------|------|------|
| **1** | 系统约束/安全规则 | 不可协商，永远保留 |
| **2** | 当前任务目标与硬约束 | 防止跑偏 |
| **3** | 最近几轮对话 | 保持连贯 |
| **4** | 与当前问题相关的检索/记忆 | 按需注入 |
| **5** | 远期历史摘要 | 背景信息 |
| **6** | 工具原始结果 | 尽量截断，只留摘要 |

**冲突时的取舍**：**先保约束，再保目标，再保连贯，最后才是信息量。**

**追问：为什么工具结果排最后？**
→ 因为它**体积最大、时效性最强、最容易重新获取**。丢了可以再查；约束和目标丢了，整轮就废了。
