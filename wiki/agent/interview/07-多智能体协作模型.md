# 多智能体协作模型

> **适用场景**：简历写了「多智能体系统」必问。
> **边界说明**：本篇讲**协作模型与工程取舍**；`StateGraph`、`Send`、`Command`、子图实现见 [[langgraph/interview/07-多智能体与子图]]。
> **主线**：多 Agent 的本质是**控制权在多个决策单元之间转移**，不是「多调几次模型」。

---

## Q1. 为什么需要多 Agent？单 Agent 不够吗？

**答：**

**单 Agent 能做好就不要拆。**拆分的合理理由只有四类：

| 理由 | 说明 |
|------|------|
| **职责与工具集差异大** | 客服只需要订单工具，运维只需要部署工具；混在一起工具描述互相干扰 |
| **上下文隔离** | 每个 Agent 只带自己领域的知识，避免长上下文互相污染 |
| **权限边界** | 高危操作由独立 Agent 执行，便于审批和审计 |
| **并行** | 多个子任务可以同时跑 |

**不该拆的情况**：

- 只是 Prompt 太长；
- 只是想让回答「更专业」；
- 只是想让架构看起来先进。

**追问：拆多 Agent 的代价是什么？**
→ ① 延迟增加（每次交接至少多一次模型调用）；② 信息损耗（交接时上下文被裁剪）；③ 调试困难（链路跨多个 Agent）；④ 成本成倍增加。**这些代价必须由「职责隔离带来的收益」覆盖。**

---

## Q2. 多 Agent 有哪几种协作拓扑？

**答：**

四种基本形态：

| 拓扑 | 结构 | 决策方式 | 适合 | 风险 |
|------|------|---------|------|------|
| **Supervisor（主管）** | 星型，中心调度 | 主管决定下一步 | 任务边界清晰、需要统一验收 | 主管成为瓶颈/单点 |
| **Swarm（交接）** | 网状，Agent 直接转交 | 当前 Agent 决定交给谁 | 对话式分流、链式协作 | 互相踢皮球 |
| **Hierarchical（层级）** | 树形，主管套主管 | 分层决策 | 专家多、可自然分组 | 层级越深越慢 |
| **Network（网络）** | 全连接 | 任意 Agent 可调任意 | 探索型、Agent 少 | 不可预测、难审计 |

**选择顺序**：

```
专家 ≤ 5 个、边界清晰     → Supervisor
需要对话式转接            → Swarm（加防循环）
专家 > 5 个、能分组       → Hierarchical
探索型、Agent ≤ 4 个      → Network（谨慎）
```

**追问：生产上为什么 Supervisor 最常见？**
→ 因为它**可预测、可审计**：所有路由经过同一个决策点，出问题能定位到「主管为什么选错」。**可审计性在生产环境通常比灵活性更重要。**

## Q3. 多 Agent 的角色应该怎么划分？

**答：**

按「**职责 + 工具 + 权限 + 领域**」四要素划分，确保**唯一归属**：

| 要素 | 要求 | 反例 |
|------|------|------|
| **职责** | 一件事只有一个 Agent 负责 | 两个 Agent 都能处理退款 |
| **工具** | 工具集尽量不重叠 | 所有 Agent 都挂了数据库工具 |
| **权限** | 高危权限只给必要 Agent | 每个 Agent 都能删数据 |
| **领域** | 有明确的输入类型边界 | 「通用助手」处理所有事 |

**判断标准**：给一个请求，能**唯一确定**该由谁处理，不需要协商。

**追问：角色划分错了会有什么表现？**
→ 三个信号：① 请求在两个 Agent 之间来回转；② 两个 Agent 给出矛盾结论；③ 某个 Agent 的工具调用总是失败（因为它拿到了不属于自己的任务）。**出现这些信号，先改角色边界，不要先改 Prompt。**

## Q4. Agent 之间怎么通信？共享状态还是消息传递？

**答：**

两种模型：

| 模型 | 机制 | 优点 | 缺点 |
|------|------|------|------|
| **共享状态（黑板）** | 所有 Agent 读写同一份状态 | 实现简单、信息不丢 | 上下文膨胀、互相污染、并发写冲突 |
| **消息传递** | Agent 之间发结构化消息 | 隔离好、可审计 | 需要设计消息契约、可能丢上下文 |

**推荐：混合模式**

```
共享：任务级信息（目标、进度、验收标准、当前负责人）
消息：交接时的任务卡（目标、输入、约束、上下文引用）
```

**任务卡示例**：

```json
{
  "task": "实现分页接口",
  "inputs": {"spec": "doc:api-spec#3.2"},
  "constraints": ["不改数据库 schema", "兼容旧客户端"],
  "acceptance": ["单测通过", "返回结构符合 spec"],
  "deadline": "2026-10-19T18:00:00+08:00"
}
```

**追问：为什么不把所有历史都共享？**
→ 每个 Agent 都要为别人的历史付 token；无关信息会干扰判断；一个 Agent 的错误结论会污染所有下游。**共享「结论和引用」，不共享「原始过程」。**

## Q5. 交接（handoff）时，上下文应该传什么？

**答：**

传「**接手方完成任务所需的最小充分集**」，四样东西：

| 内容 | 说明 |
|------|------|
| **目标** | 要做什么、验收标准是什么 |
| **已确认事实** | 前面查到的、确定的结论 |
| **约束** | 不能做什么、必须遵守什么 |
| **引用** | 大内容的 id/路径，按需再取 |

**不该传的**：

- 上一个 Agent 的完整思考过程；
- 无关的工具原始返回；
- 已被推翻的假设（要明确标注「已排除」）。

**追问：怎么判断「最小充分」？**
→ 问三个问题：① 没有它，接手方能完成任务吗？② 有它，会不会误导？③ 需要细节时，能不能按引用取到？**三个都过，才放进交接包。**

## Q6. 多 Agent 之间出现冲突、重复工作或互相等待，怎么解决？

**答：**

| 问题 | 表现 | 解决 |
|------|------|------|
| **重复工作** | 两个 Agent 做了同一件事 | 任务去重（按任务 id/幂等键）+ 唯一归属 |
| **结论冲突** | A 说可以退款，B 说不行 | 设仲裁者（主管/规则引擎），或按权限高者优先 |
| **资源竞争** | 同时改同一条记录 | 锁/租约（lease）+ 串行化 |
| **互相等待** | A 等 B 的输出，B 等 A 的 | 依赖图检测 + 超时 + 降级 |
| **踢皮球** | 无限转交 | 最大交接次数 + 禁止回传 + 人工兜底 |

**通用原则**：**任何跨 Agent 的等待都要有超时，任何转交都要有次数上限。**

**追问：为什么「让主管仲裁」不总是可行？**
→ 主管也可能判断错，而且会增加一次调用。**能用规则/权限解决的冲突，不要交给模型仲裁**；模型仲裁只用于「规则覆盖不到」的语义冲突。

## Q7. A2A 协议是什么？它和 MCP 有什么区别？

**答：**

**A2A（Agent2Agent Protocol）是让不同来源的 Agent 互相发现、委派任务、交换结果的开放协议。**

| 维度 | MCP | A2A |
|------|-----|-----|
| **连接对象** | Agent ↔ **工具/数据源** | Agent ↔ **Agent** |
| **核心对象** | Tools / Resources / Prompts | Agent Card / Task / Artifact |
| **解决的问题** | 工具接入标准化 | 跨框架/跨组织的 Agent 协作 |
| **典型场景** | 接数据库、文件系统、API | 跨团队/跨厂商的 Agent 委派 |

**一句话记法**：**MCP 让 Agent 拿到工具，A2A 让 Agent 找到同行。**

版本口径（2026-10）：A2A 当前稳定规范为 **v1.0.x**，由 Linux Foundation 下的 AAIF 治理；传输以 **JSON-RPC 2.0 over HTTPS** 为主，也支持 gRPC / REST 绑定。

**追问：什么时候真的需要 A2A？**
→ 当 Agent **跨组织/跨框架**时。同一个应用内的多 Agent，用本地编排（共享状态/消息）就够了；A2A 的价值在「边界之外」。**内部协作上 A2A，通常是过度设计。**

## Q8. 多 Agent 的成本为什么容易失控？

**答：**

因为成本不是线性叠加，而是**相乘**：

```
总成本 ≈ Agent 数量 × 每个 Agent 的上下文 × 交接轮次
```

| 放大源 | 说明 |
|--------|------|
| **每个 Agent 都有独立 system prompt** | 即使很短，也要每轮付 |
| **交接重复传输** | 同一份背景在多个 Agent 之间传 |
| **主管每轮都要决策** | 一次任务可能 N 次主管调用 |
| **失败重试** | 子 Agent 失败，整条链重跑 |
| **并行扇出** | 一次派 20 个任务，成本 ×20 |

**控制手段**：

1. 给每个 Agent 设 **token/轮次预算**；
2. 交接只传任务卡，不传全量历史；
3. 主管用**小模型**做路由；
4. 扇出前先估算成本，超过阈值转批处理；
5. 监控「单任务成本」而不是「总成本」。

**追问：怎么向老板解释多 Agent 贵？**
→ 用「**单任务成本 × 任务量**」算总账，并对比「单 Agent + 人工兜底」的方案。**如果多 Agent 只提升了 5% 的成功率，却让成本翻倍，通常不划算。**

## Q9. 什么情况下不该用多 Agent？

**答：**

五个「不该」：

| 场景 | 原因 |
|------|------|
| **职责无法清晰划分** | 一定会互相推诿 |
| **任务本身很简单** | 拆分只增加延迟和成本 |
| **对延迟极敏感** | 每次交接都是串行开销 |
| **没有评估手段** | 无法判断多 Agent 是否真的更好 |
| **团队没有排障能力** | 跨 Agent 链路出问题很难定位 |

**判断口诀**：**「一个 Agent 加几个工具能不能解决？」能，就先别拆。**

**追问：那什么时候值得拆？**
→ 当出现以下信号之一：① 工具多到选择准确率明显下降；② 上下文长到目标开始漂移；③ 权限需要硬隔离；④ 子任务可以真正并行。**拆分是为了解决具体问题，不是为了架构好看。**
