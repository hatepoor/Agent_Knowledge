# Agent 基础与能力边界

> **适用场景**：Agent 岗开场必问。这一篇决定面试官把你归到「搭过 Demo」还是「做过系统」。
> **主线**：**Agent = 模型 + 工具 + 循环 + 状态**，四样缺一不可；但「能不能用」取决于任务是否真的需要自主决策。

---

## Q1. 什么是 AI Agent？它和 Chatbot 的本质区别是什么？

**答：**

**Agent 是让模型在运行时自主决定「下一步做什么」，并通过工具与外部环境交互、直到完成目标的系统。**

和 Chatbot 的本质区别不在「会不会多轮对话」，而在**控制权在哪**：

| 维度 | Chatbot | Agent |
|------|---------|-------|
| 控制流 | 人决定问什么，模型只回答 | **模型决定调用什么工具、循环几次** |
| 输出 | 一段文本 | 文本 + **动作**（查库、发请求、写文件） |
| 状态 | 对话历史 | 对话历史 + **任务状态、工具结果、中间产物** |
| 终止 | 人停止提问 | **模型判断目标达成**，或预算耗尽 |
| 失败方式 | 答错 | 答错、**乱调工具、死循环、跑偏** |

一句话：**Chatbot 是「你问我答」，Agent 是「你给目标，我自己想办法」。**

**追问：多轮对话的 Chatbot 算 Agent 吗？**
→ 不算。如果没有「模型自主选择动作」这一环，多轮只是上下文更长。**判断标准是：控制流是否由模型在运行时决定。**

## Q2. 一个 Agent 系统由哪几部分组成？

**答：**

四层，少一层都会在某个场景塌掉：

| 层 | 作用 | 典型实现 |
|----|------|---------|
| **模型（大脑）** | 理解目标、推理、决定下一步 | LLM / 推理模型 |
| **工具（手脚）** | 与外部世界交互 | Function Calling、MCP、HTTP API |
| **循环（控制流）** | 把「想→做→看」串起来，直到终止 | ReAct、Plan-and-Execute、图编排 |
| **状态（记忆）** | 保存对话、任务进度、中间结果 | 上下文、Checkpointer、Store |

外围还有三层工程能力：

- **可观测**：trace、日志、指标；
- **安全**：权限、沙箱、审批；
- **评估**：任务成功率、轨迹质量、成本。

**追问：这四层里哪层最容易被低估？**
→ **状态**。很多人只关注「模型聪明不聪明、工具多不多」，但生产事故大多出在状态：上下文爆了、恢复后重复执行、多轮之间任务目标丢了。**状态设计是 Agent 工程的核心难点。**

## Q3. Agent 的「自主性」怎么分级？

**答：**

工程上常用五级分法（不是官方标准，但便于沟通）：

| 级别 | 形态 | 谁决定控制流 | 例子 |
|------|------|-------------|------|
| **L0** | 单次调用 | 人 | 分类、摘要 |
| **L1** | 固定流程（Workflow） | 代码 | 检索→生成→校验 |
| **L2** | 模型选工具，但流程固定 | 代码 + 模型局部决策 | 意图识别后走固定分支 |
| **L3** | 模型决定循环（ReAct） | **模型** | 通用工具 Agent |
| **L4** | 模型自主规划、拆任务、多 Agent 协作 | **模型** | 长任务、研究型 Agent |

**关键判断**：级别越高，**能力上限越高，可控性越差**。

生产上大多数系统停在 **L2~L3**：

- L2 用「模型做分类、代码做流程」，稳定、可测；
- L3 用「模型做循环」，灵活，但要加预算和终止条件；
- L4 只在任务边界清晰、有强评估和人工兜底时才用。

**追问：级别越高是不是越先进？**
→ 不是。**能解决问题的最低级别就是最好的级别。**用 L4 做「查天气」，是过度设计；用 L0 做「排查线上故障」，是能力不足。

## Q4. Agent 和 Workflow 怎么选？

**答：**

这是 Anthropic《Building Effective Agents》里的核心区分：

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制流 | **预先定义**的代码路径 | 模型**运行时**决定 |
| 可预测性 | 高 | 低 |
| 调试 | 容易 | 难（路径不定） |
| 灵活性 | 低（没预设的路径走不了） | 高 |
| 成本 | 可控 | 随轮次增长 |
| 适合 | 步骤固定、可枚举 | 步骤不确定、需要探索 |

**决策顺序**（很重要，面试官爱听）：

```
1. 能用单次调用解决吗？        → 直接调模型
2. 能拆成固定流程吗？          → Workflow（提示链/路由/并行）
3. 只有「下一步不确定」时       → Agent
```

**一句话**：**先用最简单的方案，只有在「必须让模型决定控制流」时才上 Agent。**

**追问：为什么很多团队一上来就做 Agent？**
→ 因为 Demo 效果惊艳。但上线后会发现：80% 的请求其实是固定流程，用 Agent 反而更慢、更贵、更难测。**成熟的团队会把 Agent 收缩到真正需要自主决策的那 20%。**

## Q5. Agent 和 RAG 是什么关系？

**答：**

**RAG 是「检索增强生成」，是一种能力；Agent 是「自主决策循环」，是一种架构。**两者是正交的，可以组合。

| 组合 | 形态 | 例子 |
|------|------|------|
| 纯 RAG | 检索 → 拼接 → 生成，一次完成 | 知识库问答 |
| 纯 Agent | 工具循环，不一定要检索 | 代码执行、运维操作 |
| **Agentic RAG** | Agent 自己决定「要不要检索、检索什么、检索几次」 | 复杂研究型问答 |

Agentic RAG 的典型行为：

- 判断问题是否需要查库（不需要就直接答）；
- 把大问题拆成多个子查询；
- 对检索结果不满意时**改写查询重试**；
- 交叉验证多个来源后再回答。

**追问：Agentic RAG 一定比普通 RAG 好吗？**
→ 不一定。它更灵活，但**更慢、更贵、更不可控**。简单事实问答用普通 RAG；需要多跳推理、多源对比时才上 Agentic RAG。**判断标准是「检索策略是否需要根据中间结果变化」。**

## Q6. 什么场景不应该用 Agent？

**答：**

五类典型「不该用」：

| 场景 | 原因 | 更合适的做法 |
|------|------|-------------|
| **步骤完全固定** | 不需要自主决策 | Workflow / 提示链 |
| **对延迟极敏感**（如在线搜索） | 多轮循环延迟不可接受 | 单次调用 + 缓存 |
| **结果要求强确定**（如计费、对账） | 模型决策不可复现 | 规则引擎 + 模型只做辅助 |
| **错误代价极高且不可逆**（如直接转账） | 不能让模型自主执行 | 人工审批 / 只读 Agent |
| **没有可靠评估手段** | 无法判断改得好不好 | 先建评估，再上 Agent |

**共同点**：这些场景要么**不需要自主性**，要么**承担不起自主性的代价**。

**追问：那 Agent 适合什么？**
→ 三个特征同时满足：**步骤不确定、工具可安全调用、结果可验证**。比如：多源信息调研、代码修复（有测试验证）、客服工单分派（有人工兜底）。

## Q7. Agent 最常见的失败模式有哪些？

**答：**

按发生频率排：

| 失败模式 | 表现 | 根因 |
|---------|------|------|
| **死循环** | 反复调同一个工具、反复改写同一查询 | 没有终止条件 / 工具一直返回无用结果 |
| **目标漂移** | 做着做着忘了原始任务 | 上下文太长，早期目标被淹没 |
| **工具误用** | 选错工具、参数编造 | 工具描述不清 / 工具太多 |
| **上下文爆炸** | 越跑越慢、越跑越贵 | 历史只增不减 |
| **错误累积** | 前面错一步，后面全错 | 没有校验/回滚 |
| **过早终止** | 信息不够就下结论 | 模型自信 / 停止条件太松 |
| **权限越界** | 调用了不该调的工具 | 工具权限没做最小化 |

**追问：这七种里哪一种最难排查？**
→ **目标漂移**。它不报错、不循环，输出看起来也合理，只是「答的不是最初的问题」。排查要靠 trace 对比「第一轮的目标」和「最后一轮的动作」。

## Q8. Agent 的成本和延迟主要来自哪里？

**答：**

**成本 ≈ 轮次 × 每轮 token**，延迟 ≈ 轮次 × 每轮耗时。

| 来源 | 说明 | 优化方向 |
|------|------|---------|
| **轮次多** | 每轮都是一次完整模型调用 | 减少不必要的反思/确认轮 |
| **上下文重复** | 每轮都带全量历史 | 裁剪、摘要、只带相关片段 |
| **工具结果太大** | 检索返回整篇文档 | 工具侧做字段裁剪/摘要 |
| **重试** | 失败重试放大成本 | 幂等 + 退避 + 熔断 |
| **模型选型** | 全流程用大模型 | 路由/简单步骤用小模型 |

**一个常被忽略的点**：**延迟是串行的**。ReAct 5 轮，每轮 2 秒模型 + 1 秒工具，就是 15 秒。**并行工具调用**和**流式输出**是改善体验的关键，不是锦上添花。

**追问：怎么定位成本花在哪？**
→ 按「轮次 / 节点 / 模型」三个维度打点，记录输入输出 token。**大多数成本问题不是单价高，而是「历史太长」或「轮次太多」。**

## Q9. 选 Agent 框架时，你看重什么？

**答：**

按优先级：

| 优先级 | 考量 | 说明 |
|--------|------|------|
| **1** | **是否需要持久化/中断恢复** | 需要 → 选带 Checkpointer 的（如 LangGraph）；不需要 → 轻量库即可 |
| **2** | **控制粒度** | 要自定义路由/并行/多 Agent → 低层框架；标准 ReAct → 高层封装 |
| **3** | **可观测性** | 能否接入 trace、回放、评估 |
| **4** | **团队熟悉度** | 团队不会调的问题，框架再好也白搭 |
| **5** | **生态与锁定风险** | 工具/模型是否可替换，避免绑死一家 |

**我的判断顺序**：**先看「有没有状态恢复需求」，再看「控制流复杂度」，最后才看功能列表。**

**追问：为什么不直接选功能最多的？**
→ 功能多意味着抽象多、调试难。**Agent 的复杂度已经很高，框架应该减少而不是增加认知负担。**很多团队最终会从高层框架下沉到低层编排，就是因为「出问题时看不懂」。
