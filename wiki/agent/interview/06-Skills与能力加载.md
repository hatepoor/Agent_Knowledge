# Skills 与能力加载

> **适用场景**：简历写了「Skills 系统」必问。面试官想确认：你是真做了「渐进加载」，还是把 Prompt 换了个名字。
> **主线**：**Skills 是「按需加载的 SOP」，不是「更长的 Prompt」。**

---

## Q1. Skills 是什么？它解决什么问题？

**答：**

**Skills 是把「某类事情应该怎么做」封装成可复用、可按需加载的能力模块**，通常以 Markdown（`SKILL.md`）形式存在，可以附带模板、示例、脚本。

它解决三个问题：

| 问题 | 没有 Skills | 有 Skills |
|------|------------|-----------|
| **知识复用** | 每次在 Prompt 里重复写流程 | 写一次，自动匹配 |
| **上下文浪费** | 所有规范全量塞进系统提示 | 只加载当前任务需要的 |
| **一致性** | 每次输出质量取决于当次 Prompt | 固定 SOP，输出稳定 |

**和 Tool 的区别**：Tool 是「能做什么动作」，Skill 是「这类事应该按什么步骤做」。**Tool 给手脚，Skill 给作业指导书。**

**追问：Skills 和「把 Prompt 存成模板」有什么区别？**
→ 关键在**渐进加载**和**自动触发**。模板需要人主动选、全量注入；Skills 先只暴露 `name + description`，命中后才加载正文。**这是 token 经济性的差异，不只是组织形式。**

---

## Q2. Skills 和 Prompt 的区别是什么？

**答：**

| 维度 | Prompt | Skills |
|------|--------|--------|
| **生命周期** | 单次请求 | 长期存在、可版本管理 |
| **加载方式** | 每次全量注入 | **元数据常驻，正文按需** |
| **内容** | 指令 + 上下文 | SOP + 模板 + 示例 + 脚本 |
| **复用** | 复制粘贴 | 自动匹配 / 显式调用 |
| **维护** | 改一次发一次 | 改文件即生效 |
| **一致性** | 依赖当次写法 | 固定流程，输出稳定 |

**一句话**：**Prompt 是「这次怎么做」，Skill 是「这类事以后都这么做」。**

**追问：Skill 里能不能放 Prompt？**
→ 能，而且通常会放。Skill 是容器，里面可以有指令、示例、模板。**区别在加载机制和复用边界，不在内容形态。**

---

## Q3. Skills、MCP、Tools、RAG 四者怎么区分？

**答：**

| 概念 | 解决什么 | 形态 | 类比 |
|------|---------|------|------|
| **Tools** | 能执行什么动作 | 函数/API | 手脚 |
| **MCP** | 工具怎么标准化接入 | 协议 | 标准接口 |
| **Skills** | 这类事按什么步骤做 | Markdown SOP | 作业指导书 |
| **RAG** | 事实/知识从哪查 | 检索 | 参考书 |

**组合关系**：

```
Skill（流程）→ 调用 Tool（动作）→ Tool 可能通过 MCP 接入
             → 需要事实时走 RAG
```

**面试常见追问**：「Skills 能不能替代 MCP？」
→ 不能。**Skills 管「怎么做」，MCP 管「怎么接」。**一个 Skill 可以调用多个 MCP 工具；一个 MCP 工具也可以被多个 Skill 使用。

**追问：那 Skills 能不能替代 RAG？**
→ 也不能。RAG 提供**事实**，Skills 提供**流程**。用 Skill 存知识库内容，会变成「全量加载」，失去检索的意义。

---

## Q4. 「渐进加载」具体分几层？

**答：**

三层，按「需要多少加载多少」：

| 层 | 加载什么 | 何时加载 | 体积 |
|----|---------|---------|------|
| **L1 元数据** | `name` + `description` | **常驻**，启动时就注入 | 几十 token |
| **L2 正文** | `SKILL.md` 的步骤/规范 | 命中该 Skill 时 | 几百~几千 token |
| **L3 附件** | 模板、示例、脚本、参考文档 | 正文里明确需要时 | 按需，可能很大 |

```
用户请求
  ↓
L1：用 description 匹配（便宜）
  ↓ 命中
L2：加载正文，按步骤执行
  ↓ 需要模板/脚本
L3：再读具体文件
```

**价值**：假设有 50 个 Skill，全量加载要几万 token；渐进加载在大多数请求里只花几百 token。

**追问：L1 的 description 有多重要？**
→ **决定命中率**。写得太窄，该触发时不触发；写得太宽，什么请求都命中。**description 要写「做什么 + 什么时候用 + 什么时候不用」。**

## Q5. 一个 `SKILL.md` 应该怎么写？

**答：**

结构建议：

```markdown
---
name: api-design-review
description: 审查 REST API 设计。当用户要求评审接口、检查 RESTful 规范时使用；
             不用于生成新接口文档。
---

# API 设计评审

## 使用场景
- 用户给出接口定义，要求评审
- 需要检查命名、状态码、分页、错误格式

## 步骤
1. 读取接口定义（OpenAPI/文档）
2. 按检查清单逐项核对
3. 输出「问题 + 原因 + 修改建议」表格

## 检查清单
- [ ] 资源命名用复数名词
- [ ] 状态码语义正确
- [ ] 错误响应结构统一

## 示例
（给一个输入/输出示例）

## 注意事项
- 不要直接改用户的接口定义，只给建议
```

五个要点：

| 要点 | 说明 |
|------|------|
| **description 精准** | 包含触发条件和排除条件 |
| **步骤可执行** | 不要写「仔细分析」，要写「读什么、查什么、输出什么」 |
| **有检查清单** | 比散文式说明更稳定 |
| **有示例** | 输入/输出各一个，减少歧义 |
| **有边界** | 明确「不做什么」 |

**追问：Skill 正文写多长合适？**
→ **够用就好，但要完整**。正文太长会挤占上下文；太短则模型自由发挥。经验是**一页以内**，细节放 L3 附件。

## Q6. Skill 是怎么被触发/选中的？

**答：**

三种触发方式：

| 方式 | 机制 | 适用 |
|------|------|------|
| **自动匹配** | 模型根据 `description` 判断是否加载 | 通用、无需用户知道 Skill 存在 |
| **显式调用** | 用户输入 `/skill-name` 或指定 | 专业流程、需要确定性 |
| **路由模型** | 先用一个小模型分类，再加载对应 Skill | Skill 很多、需要控制成本 |

**自动匹配的可靠性取决于三件事**：

1. `description` 的区分度；
2. Skill 数量（太多会互相干扰）；
3. 是否有「无匹配」的兜底路径。

**追问：多个 Skill 同时命中怎么办？**
→ 三种策略：① 只加载置信度最高的一个；② 加载多个但限制总 token；③ 先加载「元 Skill」做二次路由。**不要无脑全加载，会互相冲突。**

---

## Q7. Skills 需要版本管理、权限和测试吗？

**答：**

需要，而且这是「Demo Skill」和「生产 Skill」的分界线。

| 维度 | 做法 |
|------|------|
| **版本管理** | Git 管理；`version` 字段；变更记录；支持回滚 |
| **权限** | `allowed-tools` 限制可调用的工具；脚本在沙箱执行；敏感操作需审批 |
| **测试** | 固定输入集回归；检查「是否触发」「步骤是否走对」「输出格式」 |
| **灰度** | 新版本先小流量；对比成功率/成本 |
| **审计** | 记录「哪个 Skill 被加载、执行了哪些工具」 |

**最容易忽略的是测试**：

- 只测「能跑通」，不测「该触发时有没有触发」；
- 只测正常输入，不测「不该触发」的负样本；
- 改了 description 不回归，导致原来能命中的现在不命中。

**追问：Skill 里的脚本要不要签名/校验？**
→ 生产环境建议要。**Skill 能执行代码，等于把你的权限交给一份 Markdown**；来源不可信的 Skill 和不可信代码同级。

---

## Q8. Skills 在生产中最常见的坑有哪些？

**答：**

| 坑 | 表现 | 根因 | 对策 |
|----|------|------|------|
| **误触发** | 无关请求也加载 Skill | description 太宽 | 加排除条件、负样本测试 |
| **不触发** | 该用的场景没加载 | description 太窄/术语不匹配 | 用用户语言写描述 |
| **正文太长** | 上下文被挤爆 | 把参考文档塞进 SKILL.md | 拆到 L3 附件 |
| **Skill 冲突** | 两个 Skill 给出矛盾步骤 | 职责重叠 | 明确边界、路由 |
| **版本漂移** | 线上行为和文档不一致 | 改了文件没发版 | 版本号 + 发布流程 |
| **权限过大** | Skill 调用了不该调的 tool | 没配 `allowed-tools` | 最小权限 + 沙箱 |
| **不可观测** | 出问题不知道加载了哪个 Skill | 没打点 | trace 记录 Skill 名与版本 |

**追问：如果只能改一处来提升 Skills 系统稳定性，改哪里？**
→ **改 description 的边界**。大多数问题不是「Skill 内容不好」，而是「该用的没用、不该用的用了」。**触发准确率是 Skills 系统的生命线。**
