# Agent 评估与可观测性

> **适用场景**：中高级岗、主管面。会不会评估，是「能上线」和「只能演示」的分界线。
> **主线**：**Agent 评估不能只看最终答案，必须看「怎么走到答案的」。**

---

## Q1. Agent 评估和普通 LLM 评估有什么区别？

**答：**

| 维度 | 普通 LLM 评估 | Agent 评估 |
|------|--------------|-----------|
| **输出** | 一段文本 | 文本 + **动作序列 + 环境状态变化** |
| **路径** | 一次生成 | 多步、**路径不唯一** |
| **正确性** | 答案对不对 | 答案对 + **过程是否合理/安全** |
| **环境依赖** | 无 | 工具有副作用、会失败、会变 |
| **非确定性** | 采样随机 | 采样 + 路由 + 工具返回，**方差更大** |
| **失败归因** | 模型能力 | 模型/工具/上下文/编排/环境，**五类** |

**核心难点**：**结果对不代表过程对**。Agent 可能「蒙对」——调用了错误的工具、绕了一大圈，最后答案碰巧正确。生产上这种「侥幸成功」不可接受。

**追问：那能不能只评最终结果？**
→ 不够。结果评估告诉你「行不行」，过程评估告诉你「为什么行/不行、成本多少、有没有风险」。**要做优化，必须看过程。**

---

## Q2. Agent 应该评哪些指标？

**答：**

分三层：

**① 结果层**

| 指标 | 说明 |
|------|------|
| **任务成功率** | 最终状态/答案是否满足验收标准 |
| **一次成功率** | 不需要人工干预/重试的比例 |
| **部分完成率** | 长任务中完成的子目标比例 |

**② 过程层**

| 指标 | 说明 |
|------|------|
| **工具选择准确率** | 是否选了正确的工具 |
| **参数正确率** | 参数是否合法、语义正确 |
| **步骤数** | 相对最优路径多了几步（冗余度） |
| **无效调用率** | 重复调用、空结果调用占比 |
| **恢复成功率** | 工具失败后能否换策略 |

**③ 工程层**

| 指标 | 说明 |
|------|------|
| **单任务成本** | token + 工具费用 |
| **P95 延迟** | 端到端耗时 |
| **人工介入率** | 需要审批/转人工的比例 |
| **异常终止率** | 超轮次、超时、崩溃的比例 |

**追问：如果只能看三个指标，选哪三个？**
→ **任务成功率 + 单任务成本 + P95 延迟**。这三个决定了「能不能用、用不用得起、用户等不等得了」。过程指标用于定位问题，不用于对外汇报。

## Q3. 什么是轨迹评估（trajectory evaluation）？

**答：**

**评估 Agent 的执行路径，而不只是最终结果。**

一条轨迹包含：

```
用户请求
→ 第 1 轮：模型决策 + 工具调用 + 工具返回
→ 第 2 轮：...
→ 最终答案 / 最终状态
```

评估维度：

| 维度 | 问题 |
|------|------|
| **工具选择** | 选的工具对吗？有没有更合适的？ |
| **参数质量** | 参数是否最小必要、有没有编造？ |
| **顺序合理性** | 有没有可以先做却拖到后面的步骤？ |
| **冗余度** | 有没有重复调用、无效循环？ |
| **安全性** | 有没有越权、高危操作、数据外带？ |
| **可解释性** | 每一步的理由是否成立？ |

**怎么评**：

1. **规则断言**：必须调用 A、不能调用 B、参数必须来自用户输入；
2. **参考轨迹对比**：与人工标注的最优路径比步骤；
3. **LLM 评审**：给轨迹 + 评分标准，让模型判断合理性（需校准）。

**追问：轨迹不唯一，怎么定「对」？**
→ 不追求「唯一最优路径」，而是定**约束**：必须包含哪些步骤、禁止哪些动作、步数上限、成本上限。**满足约束的轨迹都算合格。**

## Q4. LLM-as-judge 怎么用于 Agent 评估？

**答：**

三种用法：

| 用法 | 做法 | 适合 |
|------|------|------|
| **单条打分** | 给轨迹/答案 + 评分标准，输出分数 | 批量评估 |
| **成对比较** | 给 A/B 两版输出，判断哪个更好 | 版本对比、A/B |
| **检查清单** | 逐项回答「是否满足」 | 可解释性要求高的场景 |

**提高可靠性的五个手段**：

1. **评分标准具体**：不要「好不好」，要「是否包含 X、是否违反 Y」；
2. **给参考答案/参考轨迹**；
3. **换模型评审**，避免自评偏差；
4. **位置随机化**（成对比较时避免偏爱第一个）；
5. **人工抽检校准**，算评审与人工的一致率。

**追问：LLM-as-judge 最大的风险是什么？**
→ **把评审模型的偏好当成标准**。比如评审偏爱长答案，系统就会优化「更长」而不是「更对」。**评审标准必须来自业务，不是来自评审模型。**

## Q5. Golden Set（黄金集）怎么建？

**答：**

四个来源，按价值排序：

| 来源 | 说明 |
|------|------|
| **真实线上请求采样** | 最有代表性，覆盖真实分布 |
| **失败案例** | 每个线上事故/差评都进集合 |
| **边界与对抗样本** | 空输入、超长输入、歧义、注入 |
| **人工构造的典型任务** | 覆盖核心场景，保证基线 |

**分层设计**：

| 层 | 目的 |
|----|------|
| **冒烟集**（20~50 条） | 每次提交都跑，快速发现问题 |
| **回归集**（200~500 条） | 发版前跑，覆盖主要场景 |
| **深度集**（按需） | 专项评估（长任务、多 Agent、安全） |

每条样本至少包含：**输入、期望结果/验收标准、允许的工具集、成本/延迟上限**。

**追问：Golden Set 要不要定期更新？**
→ 要。业务在变、模型在变、工具在变，**一年前的黄金集可能已经不代表当前分布**。建议每季度回顾，把新出现的失败案例补进去。

## Q6. Agent 的回归测试怎么做？

**答：**

难点是**非确定性**：同样输入，路径和输出可能不同。四种做法：

| 做法 | 说明 |
|------|------|
| **固定环境** | 工具 mock 成固定返回；模型温度设 0（仍不能保证完全确定） |
| **断言「状态」而不是「文本」** | 检查最终数据库状态、文件内容、返回值结构 |
| **断言「约束」而不是「路径」** | 必须调用 A、不能调用 B、步数 ≤ N |
| **多次运行看统计** | 同一 case 跑 5 次，成功率 ≥ 4/5 才算过 |

**分层测试**：

```
单元：单个工具/节点（纯函数，易测）
集成：固定工具的完整链路（mock 模型或 mock 工具）
端到端：真实模型 + 预发环境（少量冒烟）
回放：拿线上 trace 重放（验证修复）
```

**追问：模型升级后怎么快速判断有没有退化？**
→ 跑**同一套回归集**，对比成功率、平均步数、成本、延迟四个指标。**不要只看「感觉变好了」。**

## Q7. 一条 Agent trace 里应该看什么？

**答：**

按「输入 → 决策 → 动作 → 结果」看：

| 层 | 看什么 | 异常信号 |
|----|--------|---------|
| **请求** | 用户原始输入、会话历史 | 输入被截断/转义错误 |
| **模型决策** | 每轮的 thought/tool_calls | 工具选错、参数编造、过早终止 |
| **工具调用** | 工具名、参数、耗时、返回大小 | 重复调用、空返回、超大返回 |
| **状态变化** | 每步后关键字段 | 字段没更新、被覆盖 |
| **错误** | 异常、重试、降级 | 吞异常、无限重试 |
| **汇总** | 总轮次、总 token、总耗时 | 轮次异常多、成本超预算 |

**关键能力**：**按 `thread_id` / `trace_id` 串起完整链路**，能还原「第几轮开始跑偏」。

**追问：trace 里最容易被忽略的是什么？**
→ **工具返回的原始内容**。很多人只看「调用了什么工具」，不看「工具返回了什么」。**大量跑偏的根因是工具返回了空/错/格式变了，而模型基于错误信息继续推理。**

## Q8. 线上 Agent 出问题，怎么归因？

**答：**

五类归因，按概率排：

| 类型 | 典型现象 | 排查 |
|------|---------|------|
| **工具问题** | 返回空/报错/结构变 | 看工具日志、返回体、下游健康 |
| **上下文问题** | 前期对、后期跑偏 | 看 token 曲线、关键信息是否被挤掉 |
| **模型决策** | 选错工具、参数错、提前停 | 看该轮输入输出、温度、模型版本 |
| **编排问题** | 路由错、死循环、状态覆盖 | 看路由分支、状态变更、轮次上限 |
| **环境问题** | 超时、限流、网络抖动 | 看依赖服务指标、错误码分布 |

**排查顺序**：

```
① 先排除环境/工具（外部因素，最容易验证）
② 再看上下文（token 是否爆炸、关键信息是否丢失）
③ 再看模型决策（换模型/降温度能否复现）
④ 最后看编排（路由、状态、终止条件）
```

**追问：为什么要「先排除外部因素」？**
→ 因为模型问题最难改、成本最高。**很多看似「模型变笨」的问题，实际是工具返回格式变了或下游超时。**先验证外部，能避免无效的 Prompt 调优。
