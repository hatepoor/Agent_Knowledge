# ReAct 与推理循环

> **适用场景**：Agent 岗必问，且一定会追问「怎么防止死循环」。
> **主线**：ReAct 的本质是**把推理和行动交织**；它的所有工程问题，都来自「循环没有边界」。

---

## Q1. 什么是 ReAct？它的核心循环是什么？

**答：**

ReAct = **Reasoning + Acting**，由 Yao 等人在 2022 年提出。核心是让模型**边想边做**：

```
Thought（想）→ Action（做）→ Observation（看）→ Thought → ...
                                                    ↓
                                                最终答案
```

| 阶段 | 做什么 | 例子 |
|------|--------|------|
| **Thought** | 分析当前状态、决定下一步 | 「需要先查订单状态」 |
| **Action** | 选择工具并给参数 | `get_order(order_id="A123")` |
| **Observation** | 读取工具返回 | 「已发货，预计明天到」 |
| **Repeat** | 根据新信息继续决策 | 「信息够了，可以回答」 |

**为什么有效**：模型不需要一次想完全程，可以**根据外部反馈动态调整**。这让它适合「步骤不确定」的任务。

**追问：ReAct 一定要用文本标签写 `Thought:` 吗？**
→ 不一定。标签是**提示词层面**的实现方式；现在很多模型通过原生工具调用（tool_calls）完成 Action，Thought 可以是隐藏的推理或简短的 `reasoning` 字段。**关键是「推理→行动→观察」的循环，不是标签格式。**

---

## Q2. ReAct 和 CoT（思维链）有什么区别？

**答：**

| 维度 | CoT | ReAct |
|------|-----|-------|
| 是否与外部交互 | ❌ 纯内部推理 | ✅ 调工具、读结果 |
| 信息来源 | 模型参数里的知识 | 模型知识 + **实时外部信息** |
| 适合 | 数学、逻辑、需要多步推导 | 需要查数据、执行操作的任务 |
| 错误纠正 | 只能自我怀疑 | **可以被 Observation 打脸** |
| 成本 | 一次生成 | 多轮调用 |

**一句话**：**CoT 是「闭卷推理」，ReAct 是「开卷 + 可以动手」。**

**追问：能不能组合？**
→ 能，而且常见：每一轮的 Thought 内部就是用 CoT 做推理。**ReAct 不排斥 CoT，它是在 CoT 外面加了「行动」这一层。**

## Q3. ReAct 循环怎么判断「该停了」？

**答：**

三层终止条件，缺一不可：

| 层 | 条件 | 说明 |
|----|------|------|
| **模型层** | 不再产生 tool_calls，直接输出最终答案 | 最常见，但不可靠 |
| **业务层** | 显式「提交/完成」工具；或关键字段已齐全 | 比「模型自己觉得够了」可靠 |
| **预算层** | 最大轮次、最大 token、最大耗时 | 安全网，必须有 |

```python
MAX_STEPS = 12

for step in range(MAX_STEPS):
    resp = llm.invoke(messages)
    if not resp.tool_calls:
        return resp.content          # 模型层终止
    run_tools(resp.tool_calls)
else:
    return fallback_answer(messages)  # 预算层兜底
```

⚠️ **不要把「预算层」当主终止条件**。它是异常兜底，正常任务应该在模型层或业务层结束。

**追问：模型提前说「完成了」但其实没完成，怎么办？**
→ 加**验收条件**：不是看模型说没说完成，而是检查「必要字段/必要动作是否都做了」。这是 Agent 里最容易被忽略的一层。

## Q4. ReAct 为什么会死循环？怎么治？

**答：**

死循环的本质是：**模型在同一个状态上重复做同一个动作，且没有机制强行打断。**

常见成因：

| 成因 | 表现 |
|------|------|
| 工具一直返回空/错误 | 模型反复重试同一查询 |
| 工具描述不清 | 模型一直在试不同参数 |
| 目标本身无法完成 | 模型不肯承认失败 |
| 没有轮次上限 | 无限循环 |
| 上下文太长，忘了已经试过 | 重复相同动作 |

治理手段（从软到硬）：

1. **重复检测**：同一工具 + 同一参数连续出现 N 次 → 注入提示「你已经试过，请换策略」；
2. **强制反思**：每 K 轮要求模型总结「已尝试什么、为什么失败、下一步换什么」；
3. **终止工具**：提供 `finish` / `give_up` 工具，让模型有「合法退出」的路径；
4. **预算上限**：最大轮次/时长/token，超出返回兜底结果；
5. **降级**：转人工、返回部分结果、说明卡在哪。

**追问：为什么「让模型自己意识到在循环」不可靠？**
→ 因为它的上下文里**没有显式的「已尝试列表」**，只有一堆相似的历史。**要靠工程手段把「重复」变成可见信号**，不能指望模型自觉。

## Q5. ReAct 的上下文为什么会越跑越大？怎么控制？

**答：**

每一轮都会追加：模型输出（含 Thought）+ 工具调用 + 工具结果。**轮次线性增长，token 超线性增长**（因为每轮都要重发全部历史）。

| 膨胀源 | 占比通常最大 |
|--------|-------------|
| 工具返回（检索文档、网页、SQL 结果） | ⭐ 最大 |
| 历史 Thought | 中 |
| 重复的系统提示 | 固定但每轮都付 |

控制手段：

| 手段 | 做法 |
|------|------|
| **工具侧截断** | 工具只返回必要字段，长文本摘要后再返回 |
| **Observation 压缩** | 旧轮次的工具结果替换成一句话摘要 |
| **滑动窗口** | 只保留最近 N 轮完整内容 |
| **分层摘要** | 早期历史压成「任务进展摘要」 |
| **外部存储** | 大结果存文件/DB，上下文只留引用 id |

**追问：压缩会不会丢关键信息？**
→ 会。所以压缩要**保「结论和约束」，丢「原始数据」**。比如保留「订单 A123 已发货」，丢掉完整物流 JSON。**判断标准：后续轮次还需不需要原始细节。**

## Q6. ReAct 和 Plan-and-Execute 怎么选？

**答：**

| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| 决策时机 | **边做边想** | **先想完再做** |
| 适合 | 步骤不确定、需要探索 | 步骤可预判、任务较长 |
| 优点 | 灵活、能根据反馈调整 | 全局视角、不容易跑偏 |
| 缺点 | 容易迷路、上下文膨胀 | 计划可能过时、需要重规划 |
| 成本 | 每步一次模型调用 | 规划一次 + 每步执行 |

**选择标准**：

- **任务步骤在开始时无法确定** → ReAct；
- **任务有清晰的阶段**（调研→分析→写作）→ Plan-and-Execute；
- **两者结合**：先 Plan 出粗粒度阶段，每个阶段内部用 ReAct 执行，阶段间可重规划。

**追问：Plan-and-Execute 的最大风险是什么？**
→ **计划与执行脱节**。计划基于开始时的不完整信息，执行中发现前提变了却不回头改计划。**必须设计「重规划触发条件」**（如连续两步失败、关键假设被推翻）。

## Q7. ReAct 和 Reflexion 的区别是什么？

**答：**

| 维度 | ReAct | Reflexion |
|------|-------|-----------|
| 记忆范围 | **单次任务内** | **跨尝试** |
| 失败后 | 继续在当前上下文里试 | 把失败原因写成「反思」存起来，下次带着它重试 |
| 核心机制 | 观察驱动下一步 | **反思驱动策略改进** |
| 适合 | 大多数工具型任务 | 可重试、有明确成败判定的任务 |

**Reflexion 的典型流程**：

```
尝试 1 → 失败 → 生成反思（为什么失败、下次怎么改）
      → 尝试 2（带上反思）→ 成功/继续反思
```

**追问：Reflexion 一定有效吗？**
→ 不一定。它依赖两个前提：① **能判断失败**（有验证器/测试）；② **反思是具体的**（「下次先检查参数类型」而不是「我要更仔细」）。没有验证器的任务，反思容易变成空话。

## Q8. Thought 是必须的吗？推理模型普及后 ReAct 有什么变化？

**答：**

**Thought 的作用是「让决策可解释、可调试」，不是「让模型会推理」。**

变化：

| 阶段 | 形态 |
|------|------|
| 早期 | 靠提示词强制输出 `Thought:`，模型才会「想一步」 |
| 现在 | 模型原生支持工具调用，内部已有推理；外部 Thought 可省略或简化 |
| 推理模型 | 内置长思考，ReAct 更像「思考→调用→再思考」，外部只需要记录**决策理由** |

**建议保留的东西**：

- **简短的决策理由**（为什么选这个工具），用于 trace 和排查；
- **关键假设**（「我假设 A123 是订单号」），用于发现误解。

⚠️ **不要为了「像 ReAct」而强制模型输出大段 Thought**：费 token、可能泄露内部推理、对结果没帮助。

**追问：那面试里还要讲 Thought 吗？**
→ 要，但要讲**它的工程价值**（可观测、可干预），而不是把它当成「让模型变聪明的咒语」。

## Q9. 线上一个 ReAct Agent 跑偏了，你怎么调试？

**答：**

按「先定位轮次，再判断归因」走：

```
① 拿 trace：按 request_id / thread_id 拉完整轮次
② 找拐点：从哪一轮开始偏离目标？
③ 分三类归因：
   ├─ 模型决策错：选错工具 / 参数编造 / 过早终止
   ├─ 工具返回错：空结果 / 报错 / 返回结构变了
   └─ 上下文问题：关键信息被挤掉 / 历史太长导致忽略目标
④ 复现：固定输入、降低温度、回放同一轮
⑤ 修复：改提示 / 改工具描述 / 加校验 / 加终止条件
⑥ 防复发：把该 case 加进回归集
```

**关键判断**：

| 现象 | 大概率原因 |
|------|-----------|
| 同一工具反复调 | 工具返回不满足模型预期，或描述有歧义 |
| 参数总是错 | schema 描述不清 / 缺少示例 |
| 前面答对后面跑偏 | 上下文太长，目标被淹没 |
| 突然停止 | 模型误判完成，缺验收条件 |

**追问：为什么强调「加进回归集」？**
→ 因为 Agent 的修改很容易「修好一个、弄坏另一个」。**没有回归集的调优，本质上是在赌博。**
