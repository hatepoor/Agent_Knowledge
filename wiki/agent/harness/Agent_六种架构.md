# Agent 六种架构

## 定义

Agent 架构是指 Agent 系统中各组件的组织方式，决定了能力边界、可靠性、灵活性和适用场景。从最简单的单循环到多 Agent 协作，六种架构覆盖了从高度自主到高度可控的完整光谱。

## 核心循环

所有架构共享同一个基础循环：**感知 → 推理 → 行动**。不同架构的区别在于如何组织和扩展这个循环——是让它自由运转，还是在中间插入规划、反思、检索或编排环节。

## 六种架构详解

### 1. 单 Agent 循环（Single Agent Loop）

入门首选，实现简单。直接体现 [[agent/planning/ReAct]] 模式：每步"先想再做"，感知-推理-行动自然循环。

- **优点**：最简单、易调试、适合边界清晰的任务
- **缺点**：上下文窗口易撑满、复杂任务易偏航、无法并行
- **适用场景**：修 bug、写函数、回答具体问题，建议 15 步以内完成

### 2. 规划 + 执行（Plan & Execute）

将"想清楚"和"去做"分离为两个阶段。先生成完整计划，再逐步执行。

两种变体：
- **静态规划**：一次性生成全部计划，线性执行
- **动态规划**：每步执行后重新评估，必要时调整后续计划

- **优点**：可人工审查计划、推理与执行职责分离、对长任务友好
- **缺点**：初始计划可能不准、两阶段增加延迟
- **典型实现**：Claude Code Plan Mode

### 3. 多 Agent 协作（Multi-Agent）

Orchestrator 负责任务拆解和调度，多个 Subagent 各司其职、并行工作。

两种协作模式：
- **Subagent（短暂隔离）**：为单一子任务生成独立 Agent，完成后销毁，各自拥有独立上下文，互不干扰
- **Agent Teams（长期协作）**：多个 Agent 持久存在，通过消息传递持续协作

- **优点**：天然并行、可专门化角色、独立上下文减少干扰
- **缺点**：协调复杂度高、Token 成本高
- **典型实现**：[[agent/orchestration/AutoGen]]、CrewAI

### 4. 反思与自我修正（Reflection）

Agent 输出结果后，由 Critic 评估质量；不达标则修正重来，直到满意或达到最大迭代次数。

两种方式：
- **自我反思**：同一个模型自己审视自己的输出
- **独立 Critic 模型**：用另一个模型（或同一模型的不同提示）专门负责评估

- **优点**：显著提升输出质量，尤其在代码生成、文本润色场景
- **缺点**：多次迭代增加延迟和成本，必须设置最大迭代次数防止无限循环
- **典型应用**：写测试 → 运行 → 失败 → 修复 → 再运行

### 5. RAG + Agent（检索增强型智能体）

Agent 主动决定**何时检索**、**检索什么**，可以多次查询外部知识库。与普通 [[agent/RAG/RAG]] 的被动一次性检索形成关键区别。

- **优点**：突破上下文限制、减少幻觉、知识可实时更新
- **缺点**：检索质量直接影响效果、索引维护有成本
- **关键特征**：Agent 是主动的检索决策者，而非被动接受检索结果

### 6. 工作流编排（Workflow / DAG）

Agent 行为固化为有向无环图（DAG），节点间流转关系预定义。每个节点可以是 LLM 调用、工具调用或条件分支。

**纯 Agent vs DAG 对比**：

| 维度 | 纯 Agent | DAG |
|------|---------|-----|
| 自主性 | 高 | 低 |
| 可预测性 | 低 | 高 |
| 灵活性 | 高 | 中 |
| 可审计性 | 弱 | 强 |
| 失败重试 | 整体重来 | 节点级重试 |

- **优点**：可预测、可审计、可重试、支持并行
- **缺点**：灵活性受限，无法处理未预见的路径
- **典型实现**：LangGraph

## 横向对比

| 架构 | 自主性 | 可预测性 | 并行能力 | 适合复杂度 | 学习成本 |
|------|-------|---------|---------|-----------|---------|
| 单 Agent 循环 | 高 | 低 | 无 | 低 | 低 |
| 规划 + 执行 | 中 | 中 | 无 | 中 | 中 |
| 多 Agent 协作 | 高 | 低 | 强 | 高 | 高 |
| 反思修正 | 中 | 中 | 无 | 中 | 中 |
| RAG + Agent | 高 | 低 | 可选 | 中高 | 中 |
| 工作流编排 | 低 | 高 | 强 | 高 | 高 |

## 常见组合模式

实际项目中，六种架构常常组合使用：

- **工作流编排 + 多 Agent**：顶层用 DAG 编排流程，每个节点内部用多 Agent 协作
- **多 Agent + RAG**：多个 Subagent 分别检索不同知识库，Orchestrator 汇总结果
- **规划执行 + 反思**：计划生成后由 Critic 审查，不合格则重新规划

## 常见误区

### 误区 1：架构越复杂越好
架构复杂度应匹配任务复杂度。能用单 Agent 循环解决的问题，不必引入多 Agent 协作。**用能满足需求的最简架构。**

### 误区 2：反思一定提升质量
反思的效果取决于模型的自我评估能力。如果模型无法准确识别自身错误，反思只是浪费 Token。需要实测验证。

### 误区 3：DAG 不需要 Agent
DAG 和 Agent 是互补关系。DAG 提供确定性骨架，Agent 提供灵活性节点。很多生产系统是"DAG 编排 + Agent 节点"的混合体。

### 误区 4：上下文窗口大了就不需要 RAG
更大的上下文窗口降低了 RAG 的必要性，但没有消除。精准检索在海量知识库场景下仍然不可替代——把整个文档塞进上下文既昂贵又有噪声。
