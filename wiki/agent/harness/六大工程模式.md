# 六大工程模式

> 来源：阿里云开发者《给野马套上缰绳：Agent Harness 工程实践》
> 这六大模式是 Harness Engineering 的"设计模式手册"——每一条都已经被多家团队在生产环境验证过。

## 模式1：双阶段架构（Initializer + Executor）

- **解决问题**：跨会话延续、不依赖单次 Context Window
- **做法**：Initializer Agent 理解任务 → 制定计划 → 写入 plan.md → 退出；Executor Agent 读取 plan.md → 按步执行 → 跨 Context Window 接力
- **关键细节**：两个 Agent 不共享 Context Window，只通过 Workspace 里的 plan.md 接力。

## 模式2：工具签名即文档（Tool-Signature-as-Doc）

- **解决问题**：Agent 选错工具
- **做法**：工具名是动词短语，参数 schema 每个字段都带 description，返回值结构稳定
- **启示**：LangChain 在 Terminal Bench 实验里专门提到：仅仅改善工具描述与返回结构，就能带来可观的准确率提升。

## 模式3：Sub-Agent 隔离（Context-Isolated Sub-Agent）

- **解决问题**：上下文污染 & 工具选择空间爆炸
- **做法**：每个 Sub-Agent 有独立 Context Window；每个 Sub-Agent 只看到自己需要的工具；主 Agent 只接收 Sub-Agent 的结构化输出
- **启示**：Complex 任务交给 Sub-Agent，但关键是"隔离"而不是"拆"。

## 模式4：上下游反压（Upstream-Downstream Backpressure）

- **解决问题**：无限循环、错误无法自我修复
- **做法**：上游给确定性设置 + 一致上下文；下游测试 / 类型检查 / Lint / CI 拒绝无效工作；错误信号回传 → 上游调整
- **关键细节**：Linter 的错误信息本身就是上下文工程。它不只说"违反规则 X"，而是解释"为什么这个规则存在、正确做法是什么"——这样 Agent 读到错误后就能自我修正。

## 模式5：智能体审智能体（Agent-Audits-Agent）

- **解决问题**：自我合理化、偏见无法被同一 Context 识别
- **做法**：Reviewer Sub-Agent 只看 git diff + docs/rules/*.md；角色设定为"怀疑态度的 Senior Reviewer"
- **启示**：失效的从来不是"换一个模型再评估"，而是"用同样的 Context 再评估一次"——后者只会复现同一个偏见。

## 模式6：熵管理与文档园丁#

- **解决问题**：代码库与文档随时间腐化
- **做法**：部署一个后台 Agent 做"文档园丁"，定期扫描过期文档、检测架构漂移、提交清理 PR；持续小额偿还技术债
- **启示**：把"垃圾回收"做成定时任务，而不是项目结束的善后。
