# 提示词工程（Prompt Engineering）

## 定义
提示词工程是关于如何构造和精炼提示词（Prompt）的艺术和科学，目的是最大化 AI 模型的性能，让它产出更符合需求的高质量输出。简单来说，就是**与 AI 高效沟通的技巧**。

## 基本原则
- **明确具体**：避免模糊表达，给精确的指令
- **提供上下文**：告诉模型身份、背景和目标
- **指定格式**：明确输出格式要求（JSON、bullet points等）
- **分步思考**：引导模型逐步推理（Chain-of-Thought）

## 核心技巧

### 1. 角色设定
让模型扮演特定角色来激活专业知识。如："你是一位经验丰富的 Python 编程导师"

### 2. 清晰指令
降低歧义，越精确越好。对比：
- 差：写点关于狗的东西
- 好：用生动活泼的语言，为6-8岁儿童写一段100字左右的关于金毛寻回犬性格特点的简短介绍

### 3. 零样本与少样本（Zero-shot & Few-shot）

**Zero-shot（零样本）**：直接给模型任务描述，不提供任何示例，让模型凭预训练学到的通用能力完成。适合任务定义清晰、不易出歧义的场景。

```
将以下句子翻译为法语：今天天气很好
```

**Few-shot（少样本）**：在提示词中提供几个输入→输出的示例，让模型"照着学"，自动推断你期望的格式、风格和逻辑。示例比描述更高效——花 200 字描述"保持口语化风格"，不如直接给 2 个示例来得精确。

```
将英文产品评论翻译为中文，保持口语化风格：

英文: "This phone is amazing, battery lasts forever!"
中文: "这手机太棒了，电池能用好久！"

英文: "Terrible quality, broke after one week."
中文: "质量太差了，用一周就坏了。"

英文: "Good value for the price, highly recommend."
中文:
```

**选型建议**：

| 维度 | Zero-shot | Few-shot |
|------|-----------|----------|
| 适用场景 | 任务定义明确、通用能力足够 | 需要特定格式/风格/领域适配 |
| Token 消耗 | 低 | 中（示例占用上下文） |
| 输出可控性 | 较低（依赖模型理解） | 较高（示例锚定行为） |
| 调试难度 | 难（不知道模型怎么理解任务） | 易（可以逐个调整示例） |
| 典型示例数 | 0 | 3-5 个（太少学不到模式，太多浪费 token） |

**最佳实践**：
- 示例要**覆盖边界情况**，不要全给简单案例
- 示例之间用明确分隔符分开（如 `---` 或空行）
- 如果 5 个示例还不够，考虑任务是否该拆分为多步（→ [[agent/prompt/提示词工程|提示词链]]）
- 示例的顺序会影响输出（位置偏差），重要示例放在开头和结尾

### 4. 思维链（Chain-of-Thought）
引导模型展现中间推理过程。如："请一步一步分析这个问题，先列出已知条件，再推导中间步骤，最后给出结论"

### 5. XML 标签隔离
用标签分隔数据与指令，防止注入和混淆

### 6. 提示词链（Prompt Chaining）
多个Prompt串联完成复杂任务，每步输出作为下一步输入

### 7. 元提示（Meta-Prompt）
让AI自己优化提示词

### 8. 防幻觉设计
在提示词中加入约束减少编造：如"如果不确定请说不知道"、"请引用来源"

## 进阶概念
| 概念 | 说明 |
| --- | --- |
| Chain-of-Thought (CoT) | 引导中间推理过程 |
| ReAct | 推理+行动交替进行 |
| Role Prompting | 角色扮演引导 |
| Structured Output | 强制按JSON/XML格式输出 |
| Self-Consistency | 生成多个推理结果后投票选择 |
| Tree-of-Thoughts | 同时探索多条推理路径 |

## 新手一问一答（实战指南）

> 本节用问答形式串起全文，适合初学者快速上手。每条都标注对应上方哪个技巧，方便回查。

### 心智模型：提示词 = 给 LLM 的"任务说明书"

你写提示词，本质上是在写一份给新员工的**任务说明书**——它没看过你的项目、不知道你的偏好、不会读你的言外之意。**你说得多明确，它就做多准。**

---

### Q1：写提示词的基本原则是什么？

四条，缺一不可：

| 原则 | 一句话 | 反面（小白常踩） |
|------|--------|------------------|
| **明确具体** | 告诉它"做什么、做多少、做到什么程度" | "写点关于狗的"→ 它不知道写多长、什么风格、给谁看 |
| **提供上下文** | 给身份、背景、目标 | 不告诉它"你是谁"，它用通用口吻回答专业问题 |
| **指定格式** | 明确输出结构（JSON / 表格 / 要点） | 不指定格式，它返回一大段散文，你还得二次处理 |
| **分步思考** | 引导它先推理再结论 | 直接问"答案是什么"，复杂推理容易出错 |

对比示例：

```
❌ 差：写点关于狗的东西
✅ 好：用生动活泼的语言，为6-8岁儿童写一段100字左右的关于金毛寻回犬性格特点的简短介绍
```

### Q2：怎么让模型扮演专业角色？（角色设定）

开头给模型一个身份，激活它的"专业知识域"。

```
你是一位有10年经验的Python编程导师，擅长用通俗类比解释复杂概念。
请向初学者解释什么是装饰器，要求：
1. 先用一个生活类比
2. 再给一个最简单的代码示例
3. 最后总结3个要点
```

**为什么有效**：模型预训练数据里"资深Python导师"的内容质量普遍高于"随便一个人回答"。角色 = 激活高质量知识子集。

> 对应 → [[#1. 角色设定|§角色设定]]

### Q3：Zero-shot 和 Few-shot 是什么？什么时候用？

- **Zero-shot（零样本）**：只给任务描述，不给示例。适合任务定义清晰、模型本来就会的场景。
- **Few-shot（少样本）**：给几个"输入 → 输出"的示例，让模型"照着学"。适合需要特定格式/风格/领域适配的场景。

```
# Few-shot 示例
将英文产品评论翻译为中文，保持口语化风格：

英文: "This phone is amazing!"
中文: "这手机太棒了！"

英文: "Terrible quality."
中文: "质量太差了。"

英文: "Good value for the price."
中文: ← 模型补全这里
```

**选型决策**：

| 维度 | Zero-shot | Few-shot |
|------|-----------|----------|
| 适用 | 任务明确、通用能力够 | 需要特定格式/风格 |
| Token 消耗 | 低 | 中（示例占上下文） |
| 输出可控性 | 低 | 高（示例锚定行为） |
| 典型示例数 | 0 | 3-5 个 |

**注意**：示例要覆盖边界情况，不要全给简单案例；示例顺序会影响输出（位置偏差）。

> 对应 → [[#3. 零样本与少样本（Zero-shot \& Few-shot）|§零样本与少样本]]

### Q4：什么是思维链（CoT）？怎么用？

**思维链**：让模型把推理过程写出来，而不是直接给答案。对数学、逻辑、多步推理任务特别有效。

```
❌ 直接问：25个苹果，分给3个人每人几个，剩几个？

✅ CoT：请一步一步分析：
1. 先列出已知条件
2. 再做除法运算
3. 最后给出结论
```

**进阶变体**：
- **Self-Consistency**：生成多个推理链，投票选最一致答案
- **Tree-of-Thoughts**：同时探索多条推理路径，选最优
- **ReAct**：推理 + 行动交替进行（思考一步 → 调工具 → 再思考）

> 对应 → [[#4. 思维链（Chain-of-Thought）|§思维链]] · [[agent/patterns/ReAct|ReAct 模式]]

### Q5：怎么防止模型胡编（幻觉）？

在提示词里加**硬约束**：

```
规则：
1. 如果不确定，回答"我不知道"，不要编造
2. 所有事实性陈述必须标注来源
3. 如果上下文里没有相关信息，明确说"提供的材料中没有相关内容"
4. 不要假设未提及的事实
```

**原理**：模型默认行为是"生成流畅的回答"，不加约束时它宁可编也不会说"不知道"。约束改变了它的默认策略。

> 对应 → [[#8. 防幻觉设计|§防幻觉设计]]

### Q6：怎么让输出格式可控？（结构化输出）

明确告诉模型要什么格式，甚至给模板：

```
请按以下JSON格式输出：
{
  "summary": "一句话总结",
  "keywords": ["关键词1", "关键词2"],
  "sentiment": "positive/negative/neutral"
}
```

更可靠的方式是用 **`with_structured_output()`**（LangChain）或**函数调用 / 工具调用**，把 Pydantic schema 绑定到 LLM——模型输出直接变成结构化对象，不是自由文本。

> 对应 → [[langchain/modules/langchain_prompts/Prompt高级技巧|Prompt 高级技巧]] · LangChain `with_structured_output` API

### Q7：复杂任务怎么处理？（提示词链）

**提示词链（Prompt Chaining）**——把一个大任务拆成多个小 Prompt 串联，每步输出喂给下一步。

```
步骤1：提取关键信息 → 步骤2：分类 → 步骤3：生成回复
```

**为什么不要一个大 Prompt 全包**：
- 一个 Prompt 塞太多步骤，模型注意力被稀释，每步都做不好
- 拆开后每步可独立调试、独立评估
- 某步失败可以重试，不用全链重来

> 对应 → [[#6. 提示词链（Prompt Chaining）|§提示词链]]

### Q8：怎么用 XML 标签隔离不同部分？

用标签把**指令、上下文、数据**分开，防止混淆和注入：

```xml
<指令>
从以下文档中提取所有日期和事件，输出为表格
</指令>

<上下文>
你是一个信息提取助手，只提取明确出现的信息，不推断。
</上下文>

<文档>
2026年3月，产品v1.0发布。2026年6月，用户突破10万。
</文档>
```

> 对应 → [[#5. XML 标签隔离|§XML 标签隔离]]

### Q9：提示词写完怎么调试和优化？

**迭代流程**（和 RAG 的评估思路一样）：

1. **写一版** → 2. **跑测试集**（准备 10-20 条输入 + 期望输出）→ 3. **看失败案例** → 4. **改提示词** → 回到 2

关键：**不要靠感觉调，要靠测试集量化**。记录每次修改前后的通过率，才知道改动是好是坏。

> 关联 → [[rag/12_评估与监控/评估体系与RAGAS|RAG 评估监控]] 的离线测试集思路，同样适用于提示词调优
