# Chroma 核心原理

## 架构概览

Chroma 的架构分为三层：

```
应用层（Python API）
    ↓
向量索引层（HNSW）── 负责相似度搜索
    ↓
元数据存储层（SQLite/DuckDB）── 负责文档文本、元数据、ID 的存储
```

当你在 `collection.add()` 中添加一条数据时，Chroma 做了两件事：把向量插入 HNSW 索引图，把文档文本和元数据写入 SQLite。查询时，先在 HNSW 索引中找到最相似的向量 ID，再从 SQLite 中取出对应的文档和元数据返回。

## HNSW 索引

HNSW（Hierarchical Navigable Small World）是 Chroma 的核心索引算法，也是当前最主流的向量索引方案。

### 基本原理

HNSW 的核心思想是构建一个**多层图结构**，类似跳表（Skip List）：

```
第 3 层（最稀疏）：  A -------- D -------- H
第 2 层：          A --- C --- D --- F --- H
第 1 层：          A - B - C - D - E - F - G - H
第 0 层（最稠密）：  所有节点都在这层，密集连接
```

**查询过程**：从最顶层开始，在当前层找到最近的邻居，然后下降到下一层继续搜索，逐层细化，直到第 0 层得到最终的最近邻结果。

这就像找人问路：先问城市级别的大方向，再问区级别的，最后问街道级别的。

### 关键参数

```python
collection = client.create_collection(
    name="docs",
    metadata={
        "hnsw:space": "cosine",       # 距离度量：cosine / l2 / ip
        "hnsw:M": 16,                  # 每个节点的最大连接数（默认 16）
        "hnsw:construction_ef": 100,   # 构建索引时的搜索宽度（默认 100）
        "hnsw:search_ef": 10,          # 查询时的搜索宽度（默认 10）
    }
)
```

| 参数 | 默认值 | 影响 | 调优建议 |
|------|--------|------|----------|
| `hnsw:space` | cosine | 距离度量方式 | 文本用 cosine，图像用 l2 |
| `hnsw:M` | 16 | 图中每个节点的连接数。越大精度越高，但内存和构建时间增加 | 一般 16-64，高精度场景可调到 32-48 |
| `hnsw:construction_ef` | 100 | 构建索引时搜索的候选数量。越大索引质量越高，但构建越慢 | 50-500，数据量大时适当调高 |
| `hnsw:search_ef` | 10 | 查询时搜索的候选数量。越大结果越准，但查询越慢 | 10-100，对精度要求高时调高 |

### HNSW vs 其他索引

| 索引 | 查询速度 | 精度 | 内存 | Chroma 使用 |
|------|----------|------|------|-------------|
| Flat（暴力搜索） | O(n) 最慢 | 100% | 最低 | 不使用 |
| IVF（倒排文件） | 快 | 高 | 中 | 不使用 |
| HNSW | 最快 | 很高 | 高 | **默认使用** |
| PQ（乘积量化） | 快 | 中 | 最低 | 不使用 |

Chroma 选择 HNSW 是因为它在中小规模数据上速度和精度的综合表现最好。

## 存储后端

### SQLite（默认）

Chroma 默认使用 SQLite 存储元数据和文档文本：

```python
# 持久化客户端 —— 底层是 SQLite
client = chromadb.PersistentClient(path="./chroma_data")
```

SQLite 的特点：
- **单文件**：所有数据存在一个 `.sqlite3` 文件中
- **无并发写入**：SQLite 写锁是文件级的，不支持并发写入
- **适合规模**：几十万条文档，单文件几百 MB

文件结构（在 `path` 目录下）：

```
chroma_data/
├── chroma.sqlite3        # 元数据和文档文本
├── {uuid}/               # HNSW 索引文件
│   ├── header.bin
│   ├── data_level0.bin   # 第 0 层图数据
│   └── length.bin
└── ...
```

### DuckDB

Chroma 内部早期使用 DuckDB 做向量计算，现在 HNSW 索引独立实现，DuckDB 角色弱化。用户通常不需要关心这个细节。

## Embedding 流程

当你调用 `collection.add(documents=["..."])` 时：

```
原始文本 "Python 是解释型语言"
    ↓
Embedding 函数（默认 all-MiniLM-L6-v2）
    ↓
384 维浮点向量 [0.023, -0.115, 0.087, ...]
    ↓
HNSW 索引层：将向量插入图结构
    ↓
SQLite 存储层：保存 ID、原文、元数据
```

`collection.query(query_texts=["..."])` 时：

```
查询文本 "什么是 Python？"
    ↓
同一个 Embedding 函数
    ↓
384 维查询向量
    ↓
HNSW 索引：在图中搜索最近的 k 个向量
    ↓
取出对应 ID → 从 SQLite 获取文档文本和元数据
    ↓
返回 documents + metadatas + distances + ids
```

关键：**add 和 query 必须使用同一个 Embedding 函数**，否则向量空间不一致，检索结果无意义。

## Collection 的内部结构

每个 Collection 在 SQLite 中对应三张核心表：

```sql
-- 1. 元数据表：存每条文档的 metadata
-- collection_id, key, string_value, int_value, float_value

-- 2. 文档表：存原文和 embedding 的引用
-- id, collection_id, document (原文文本)

-- 3. embedding 表：存向量数据（实际在 HNSW 文件中）
-- id, collection_id, embedding (二进制)
```

## 距离计算

Chroma 返回的 `distances` 值含义：

```python
# cosine 距离 = 1 - cosine_similarity
# 所以 0 表示完全相同，2 表示完全相反
# 越小越相似

results = collection.query(query_texts=["query"], n_results=3)
# distances: [[0.12, 0.35, 0.78]]
# 0.12 → 非常相似
# 0.78 → 不太相似
```

| 距离类型 | 范围 | 越小含义 |
|----------|------|----------|
| cosine（默认） | [0, 2] | 越相似 |
| l2 | [0, ∞) | 越相似 |
| ip | (-∞, ∞) | 越大越相似（注意方向相反） |

## 性能特点

| 操作 | 时间复杂度 | 说明 |
|------|------------|------|
| add（单条） | O(log n) | HNSW 插入 |
| add（批量） | O(k log n) | k 条数据 |
| query | O(log n) | HNSW 搜索 |
| delete | O(1) | 标记删除（惰性） |
| count | O(1) | 直接读取计数 |

**惰性删除**：Chroma 的 delete 不会立即从 HNSW 索引中移除节点，而是标记为删除。后续查询时会跳过被标记的节点。定期重建索引可以回收空间。

## 限制

| 限制 | 说明 | 应对方式 |
|------|------|----------|
| 无分布式 | 不能跨机器分片 | 数据量大时换 Qdrant/Milvus |
| 写锁 | SQLite 不支持并发写入 | 单线程写入，或使用 Client-Server 模式 |
| 内存 | HNSW 索引全在内存 | 几十万条以上需要评估内存 |
| 无多模态 | 不支持原生图文混合检索 | 用 Weaviate 或 Milvus |
| 无事务 | 不支持 ACID 事务 | 写入前备份，或使用 Client-Server 模式 |
