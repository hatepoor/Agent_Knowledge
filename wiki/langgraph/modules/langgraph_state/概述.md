# 状态管理概述

## 什么是状态（State）

在 LangGraph 中，**状态（State）** 是整个图执行过程中共享和传递的核心数据结构。每一个节点（Node）在执行时都会读取当前状态，执行自己的逻辑，然后返回对状态的更新。图引擎负责将这些更新合并到状态中，并传递给下一个节点。

可以把状态想象成一条流水线上的"工件"——每个工位（节点）都会对工件进行加工，然后把它传给下一个工位。

```
输入 → [节点A] → 更新状态 → [节点B] → 更新状态 → [条件边] → [节点C][[ → 最终状态 → 输出
```

## 核心概念

### 1. 状态是共享的

- 所有节点共享同一个状态对象
- 每个节点可以读取状态中的任意字段
- 每个节点只返回它要修改的字段（部分更新）

### 2. 状态通过 Reducer 合并

节点返回的不是完整的新状态，而是**部分更新**。LangGraph 使用 **Reducer（归约函数）** 来决定如何将节点的输出合并到现有状态中。

- 默认行为：直接覆盖（overwrite）
- 自定义行为：追加、合并、去重等

详见 → [[langgraph/modules/langgraph_state/Reducer|Reducer 归约函数]]

### 3. 状态定义方式

LangGraph 支持多种状态定义方式：

| 方式 | 特点 | 适用场景 |
|------|------|----------|
| `TypedDict` | 简单、轻量 | 大多数场景（推荐） |
| `Pydantic BaseModel` | 自带验证、序列化 | 需要严格类型校验 |
| `MessagesState` | 内置消息列表 | 聊天/对话场景 |

详见 → [[langgraph/modules/langgraph_state/状态定义|状态定义详解]]

## 状态完整流转示意图

下面是一个 RAG（检索增强生成）场景中状态的完整流转过程：

```
初始状态                    retrieve 节点后              generate 节点后
┌──────────────────┐       ┌──────────────────┐       ┌──────────────────┐
│ query: "什么是AI"│       │ query: "什么是AI"│       │ query: "什么是AI"│
│ context: (未定义) │  ──→  │ context: "AI是..."│  ──→  │ context: "AI是..."│
│ answer: (未定义)  │       │ answer: (未定义)  │       │ answer: "AI指..."│
│ retry_count: 0   │       │ retry_count: 0   │       │ retry_count: 0   │
└──────────────────┘       └──────────────────┘       └──────────────────┘
     ↑ 初始输入                  ↑ 只更新了 context          ↑ 只更新了 answer
```

### 用代码实现上述流转

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# 定义状态结构
class RAGState(TypedDict):
    query: str          # 用户查询
    context: str        # 检索到的上下文
    answer: str         # 生成的回答
    retry_count: int    # 重试次数
    messages: Annotated[list, add_messages]  # 消息列表（使用 Reducer）

# 节点 A：检索上下文
def retrieve(state: RAGState) -> dict:
    """根据查询检索相关上下文"""
    query = state["query"]
    print(f"[retrieve] 正在检索: {query}")
    # 实际项目中会调用向量数据库
    context = f"关于 '{query}' 的检索结果：AI 是人工智能的缩写..."
    return {"context": context}  # 只更新 context 字段

# 节点 B：生成回答
def generate(state: RAGState) -> dict:
    """基于检索结果生成回答"""
    query = state["query"]
    context = state["context"]
    print(f"[generate] 基于上下文生成回答")
    # 实际项目中会调用 LLM
    answer = f"根据检索结果，{context}"
    return {"answer": answer}  # 只更新 answer 字段

# 节点 C：质量检查
def quality_check(state: RAGState) -> dict:
    """检查回答质量，决定是否重试"""
    answer = state["answer"]
    retry_count = state["retry_count"]
    # 简单的质量检查逻辑
    if len(answer) < 10 and retry_count < 3:
        return {"retry_count": retry_count + 1}  # 增加重试计数
    return {"retry_count": retry_count}

# 构建图
builder = StateGraph(RAGState)
builder.add_node("retrieve", retrieve)
builder.add_node("generate", generate)
builder.add_node("quality_check", quality_check)

builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "generate")
builder.add_edge("generate", "quality_check")

# 条件边：如果回答质量不够且重试次数未满，回到 generate
def should_retry(state: RAGState) -> str:
    if len(state["answer"]) < 10 and state["retry_count"] < 3:
        return "retry"
    return "finish"

builder.add_conditional_edges("quality_check", should_retry, {
    "retry": "generate",
    "finish": END
})

graph = builder.compile()

# 执行
result = graph.invoke({
    "query": "什么是 AI",
    "context": "",
    "answer": "",
    "retry_count": 0,
    "messages": []
})
print(f"最终回答: {result['answer']}")
```

## 状态生命周期

状态从创建到持久化，经历以下生命周期：

### 1. 定义阶段（Definition）

在图构建之前，你需要定义状态的结构：

```python
from typing import TypedDict, Annotated, Optional
from langgraph.graph.message import add_messages

class MyState(TypedDict):
    # 必需字段
    messages: Annotated[list, add_messages]
    # 可选字段
    context: Optional[str]
    # 带默认值的字段（注意：TypedDict 不强制默认值，但可以在初始化时提供）
    retry_count: int
```

### 2. 初始化阶段（Initialization）

当调用 `graph.invoke()` 或 `graph.stream()` 时，传入的初始输入成为状态的初始值：

```python
# 初始化状态 — 未提供的字段会被设为 None
initial_state = {
    "messages": [("user", "你好")],
    "retry_count": 0
}
# context 字段未提供，值为 None
```

### 3. 更新阶段（Update）

每个节点执行后返回一个**部分更新字典**，图引擎使用 Reducer 将其合并到当前状态：

```python
# 节点返回部分更新
def my_node(state: MyState) -> dict:
    return {"context": "新的上下文"}  # 只更新 context

# 图引擎内部执行的操作：
# 1. 获取节点返回的更新: {"context": "新的上下文"}
# 2. 对每个字段应用 Reducer:
#    - context 没有自定义 Reducer → 直接覆盖
#    - messages 使用了 add_messages → 追加并去重
# 3. 生成新的完整状态
```

### 4. 检查点阶段（Checkpoint）

如果配置了 Checkpointer，每个节点执行后都会保存完整状态快照：

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# 每次节点执行后，状态自动保存到内存
result = graph.invoke(
    {"messages": [("user", "你好")], "retry_count": 0},
    config={"configurable": {"thread_id": "conv-001"}}
)

# 可以随时获取保存的状态
state = graph.get_state({"configurable": {"thread_id": "conv-001"}})
print(state.values)  # 完整状态快照
```

### 5. 恢复阶段（Restore）

可以从检查点恢复状态，实现多轮对话或故障恢复：

```python
# 多轮对话 — 自动恢复之前的状态
config = {"configurable": {"thread_id": "conv-001"}}

# 第一轮
graph.invoke({"messages": [("user", "我叫小明")], "retry_count": 0}, config=config)

# 第二轮 — 状态自动恢复，LLM 能"记住"之前的对话
graph.invoke({"messages": [("user", "我叫什么？")][[, "retry_count": 0}, config=config)
```

## 状态更新模式

LangGraph 提供了多种状态更新模式：

- **覆盖模式**：新值直接替换旧值（默认）
- **追加模式**：通过 Reducer 将新值追加到列表
- **部分更新**：只返回需要变更的字段
- **删除模式**：通过 `RemoveMessage` 删除特定元素

详见 → [[langgraph/modules/langgraph_state/状态更新模式|状态更新模式]]

### 覆盖 vs 追加：代码对比

```python
from typing import TypedDict, Annotated
from langgraph.graph.message import add_messages

class StateA(TypedDict):
    # 没有 Reducer → 覆盖模式
    items: list

class StateB(TypedDict):
    # 使用 add_messages Reducer → 追加模式
    messages: Annotated[list, add_messages]

# 覆盖模式示例
def node_a(state: StateA) -> dict:
    return {"items": ["new_item"]}  # items 被完全替换为 ["new_item"]

# 追加模式示例
def node_b(state: StateB) -> dict:
    return {"messages": [("assistant", "你好")]}  # 消息被追加到列表末尾
```

## State vs Config：何时使用哪个

LangGraph 中有两种传递数据的方式：**State** 和 **Config**。理解何时使用哪个非常重要。

### State（状态）

适合存放**在图执行过程中会被读取、修改、传递的数据**：

```python
class MyState(TypedDict):
    messages: Annotated[list, add_messages]  # 对话历史
    context: str        # 检索到的上下文
    answer: str         # 生成的回答
    retry_count: int    # 执行过程中会变化的计数器
```

### Config（配置）

适合存放**不影响图逻辑、但需要传递给节点的运行时参数**：

```python
# 通过 config 传递
config = {
    "configurable": {
        "thread_id": "conv-001",     # 对话标识（用于持久化）
        "user_id": "user-456",       # 用户标识
        "model_name": "gpt-4o",      # 运行时参数
        "temperature": 0.7           # 运行时参数
    }
}

# 在节点中访问 config
def my_node(state: MyState, config: dict) -> dict:
    model_name = config["configurable"]["model_name"]
    temperature = config["configurable"]["temperature"]
    # 使用这些参数...
```

### 对比表

| 维度 | State | Config |
|------|-------|--------|
| 用途 | 图执行的核心数据 | 运行时参数和元数据 |
| 是否被 Reducer 处理 | 是 | 否 |
| 是否被 Checkpointer 持久化 | 是 | 否（thread_id 除外） |
| 节点是否可以修改 | 是 | 否 |
| 典型内容 | 消息、上下文、结果 | thread_id、user_id、模型参数 |
| 访问方式 | `state["field"]` | `config["configurable"]["key"]` |

### 经验法则

- **如果数据在图的节点之间需要传递和被修改** → 用 State
- **如果数据只是给节点使用的参数，不需要被图引擎追踪** → 用 Config
- **如果数据需要跨多轮对话持久化** → thread_id 放 Config，对话内容放 State

## 常见陷阱

### 1. 可变状态陷阱

Python 中的列表和字典是可变对象，直接修改会导致意外行为：

```python
# ❌ 错误：直接修改状态中的列表
def bad_node(state: MyState) -> dict:
    state["messages"].append(("assistant", "你好"))  # 直接修改了原始状态！
    return {}  # 没有返回更新，但状态已被修改

# ✅ 正确：返回新的值让 Reducer 处理
def good_node(state: MyState) -> dict:
    return {"messages": [("assistant", "你好")]}  # 通过 Reducer 安全更新
```

### 2. Reducer 不匹配

状态定义中的 Reducer 和节点返回的格式必须匹配：

```python
class State(TypedDict):
    # messages 使用了 add_messages Reducer
    messages: Annotated[list, add_messages]
    # count 没有 Reducer → 覆盖模式
    count: int

# ❌ 错误：返回了 Reducer 无法处理的格式
def wrong_node(state: State) -> dict:
    return {"messages": "不是列表"}  # add_messages 期望列表格式

# ✅ 正确：返回与 Reducer 兼容的格式
def right_node(state: State) -> dict:
    return {"messages": [("assistant", "正确的格式")]}
```

### 3. 遗漏必需字段

初始化时遗漏字段会导致 `KeyError`：

```python
class MyState(TypedDict):
    query: str
    context: str
    answer: str

# ❌ 运行时在 generate 节点中访问 state["context"] 会报 KeyError
# 因为初始化时没有提供 context
result = graph.invoke({"query": "问题"})

# ✅ 提供所有必需字段的初始值
result = graph.invoke({
    "query": "问题",
    "context": "",
    "answer": ""
})

# ✅ 或者使用 Optional 类型
from typing import Optional

class SafeState(TypedDict):
    query: str
    context: Optional[str]  # 允许为 None
    answer: Optional[str]
```

### 4. 在节点中读取尚未写入的字段

```python
# 节点执行顺序：A → B → C
# 如果 B 节点尝试读取 A 节点才会写入的字段，但 A 还没执行：

def node_b(state: MyState) -> dict:
    # 如果 context 还没有值，使用默认值
    context = state.get("context", "默认上下文")  # ✅ 安全
    # context = state["context"]  # ❌ 可能 KeyError
    return {"result": process(context)}
```

### 5. 状态过大导致性能问题

```python
# ❌ 在状态中存储大量数据
class BloatedState(TypedDict):
    messages: Annotated[list, add_messages]
    all_documents: list      # 存储了 1000 个完整文档
    all_embeddings: list     # 存储了所有向量

# ✅ 只存储必要的引用
class LeanState(TypedDict):
    messages: Annotated[list, add_messages]
    doc_ids: list            # 只存储文档 ID
    context: str             # 只存储最终筛选的上下文
```

## 大状态的性能考量

当状态变得很大时（如长对话历史、大量检索文档），需要注意性能：

### 1. Checkpointer 存储开销

每个节点执行后，Checkpointer 会保存**完整状态快照**。如果状态很大，存储开销会快速增长：

```python
# 假设状态包含 100 条消息，每条消息平均 500 token
# 图有 5 个节点 → 每轮对话产生 5 个快照
# 每个快照 ≈ 50,000 token → 每轮对话 ≈ 250,000 token 的存储量

# 优化方案：定期裁剪消息历史
def trim_messages(state: MyState) -> dict:
    messages = state["messages"]
    if len(messages) > 20:
        # 只保留最近 20 条消息
        return {"messages": messages[-20:][[}
    return {}
```

### 2. 网络传输开销

使用 Checkpointer 时，状态需要在应用和存储之间传输。大状态会增加延迟：

```python
# 使用 PostgreSQL checkpointer 时，大状态会增加数据库 I/O
from langgraph.checkpoint.postgres import PostgresSaver

# 优化：保持状态精简，只存储必要数据
```

### 3. 内存占用

`MemorySaver` 将所有状态保存在内存中，大状态会导致内存溢出：

```python
from langgraph.checkpoint.memory import MemorySaver

# MemorySaver 适合开发和测试
# 生产环境建议使用 PostgresSaver 或 SqliteSaver
checkpointer = MemorySaver()  # 所有对话状态都在内存中！
```

### 性能优化建议

| 策略 | 说明 |
|------|------|
| 精简状态字段 | 只存储必要数据，不存储中间计算结果 |
| 定期裁剪消息 | 长对话中只保留最近 N 条消息 |
| 使用引用而非完整数据 | 存储文档 ID 而非完整文档 |
| 选择合适的 Checkpointer | 生产环境使用 PostgresSaver |
| 避免深层嵌套 | 扁平结构比嵌套结构序列化更快 |

## 与持久化的关系

状态管理是持久化（Checkpointing）的基础。Checkpointer 会在每个节点执行后保存完整状态快照，使得：

- 多轮对话可以恢复历史状态
- 可以在任意步骤进行"时间旅行"
- 可以在失败后从上次检查点恢复

详见 → [[langgraph/modules/langgraph_checkpoint/概述|持久化概述]]
