# LangGraph 核心概念与运行模型

> **适用场景**：一面/二面的基础题。这一篇答不好，后面的持久化、多智能体会被直接判定为「只会调 API」。
> **答题基调**：先给一句话定义，再讲「为什么这样设计」，最后给一个自己踩过的坑。

---

## Q1. LangGraph 是什么？它解决了什么问题？

**答：**

一句话：**LangGraph 是一个用于构建「有状态、可循环、可持久化」Agent 工作流的低层编排框架。**它把工作流建模成一张图：节点是执行单元，边是控制流，共享状态在节点之间流转。

它主要解决四类问题：

| 问题 | 线性 Chain 的困境 | LangGraph 的做法 |
|------|------------------|-----------------|
| **循环** | Chain 是 DAG，表达不了「调工具→再思考」的反复 | 条件边构成环，原生支持循环 |
| **状态** | 每步之间靠参数手动传递 | 声明式 State，节点只返回增量 |
| **恢复** | 进程崩了就从零开始 | Checkpointer 按步骤存快照，可续跑 |
| **人工介入** | 只能阻塞等输入 | `interrupt()` 暂停，之后用同一 `thread_id` 恢复 |

**定位要说清**：LangGraph 不负责模型调用、Prompt、工具实现——那些仍来自 LangChain 组件或供应商 SDK。**它只管「什么时候执行谁、状态怎么流」。**

**追问：它和「工作流引擎」像吗？**
→ 像，但它是**面向 LLM 应用**的：状态里装的是消息、工具调用、检索结果；原生支持 token 流式输出和「模型决定下一步」的非确定性路由。传统工作流引擎假设流程是预先确定的。

## Q2. LangGraph 和 LangChain 是什么关系？什么时候用哪个？

**答：**

**两者是分层关系，不是替代关系。**

```
┌──────────────────────────────────┐
│ 应用 / Agent                      │
├──────────────────────────────────┤
│ LangGraph：编排层                  │  控制流、状态、持久化、中断
├──────────────────────────────────┤
│ LangChain：组件层                  │  模型、消息、工具、Retriever、Prompt
└──────────────────────────────────┘
```

关键事实：**LangChain 1.x 的 `create_agent` 底层就是编译成 LangGraph 图来跑的。**所以「用 LangChain 就不用 LangGraph」是误解——你只是没直接碰那层。

选型判断：

| 场景 | 选择 |
|------|------|
| 单次模型调用、线性 RAG 管道 | LangChain（LCEL）足够 |
| 需要反复调工具（ReAct 循环） | LangGraph，或直接用 `create_agent` |
| 需要人工审批、断点恢复、时间旅行 | **必须 LangGraph**（`create_agent` 也能挂 checkpointer，但控制粒度粗） |
| 多 Agent 精细编排 | LangGraph |
| 快速验证一个想法 | 先用 `create_agent`，复杂了再下沉到手写图 |

⚠️ **版本提醒**：1.0 起 `langgraph.prebuilt` 命名空间已弃用，`create_react_agent` 这类预置组件推荐从 `langchain.agents` 导入。面试举例时说一句「我按 1.x 的导入路径讲」，能避免被追问版本差异。

**追问：既然 `create_agent` 底层是图，为什么还要手写？**
→ 三个理由：**控制粒度**（自定义路由、并行扇出）、**状态结构**（业务字段不只是 messages）、**中间件表达不了的逻辑**（跨节点的补偿、审批）。`create_agent` 是「80% 场景的默认答案」，手写图是「剩下 20% 的出口」。

## Q3. 为什么不用 while 循环自己写 Agent？LangGraph 的价值到底在哪？

**答：**

**原型阶段自己写循环完全够用**，三十行就能跑通 ReAct。LangGraph 的价值在「要上生产」之后才显现：

| 维度 | 自己写 while | LangGraph |
|------|-------------|-----------|
| 状态管理 | 手写字典，靠约定 | 声明式 State + reducer |
| 断点恢复 | 自己序列化，极易漏字段 | Checkpointer 按步骤自动存 |
| 并发扇出 | 自己开线程/协程 + 聚合 | `Send` + superstep 统一调度 |
| 人工介入 | 阻塞在 `input()` | `interrupt()` 暂停，进程可退出 |
| 流式输出 | 自己拆 token 和步骤事件 | `stream_mode` 多路复用 |
| 可观测 | 打日志 | 状态可查、可回放、可时间旅行 |
| 可视化 | 无 | 图结构可渲染 |

**一句话结论**：**流程简单、无恢复需求时，裸循环更轻；一旦需要「中断后还能接着跑」，图框架的抽象就开始回本。**

**追问：LangGraph 有什么代价？**
→ ① 学习曲线（State/reducer/Channel 概念多）；② 抽象泄漏（出问题要懂 Pregel 执行模型）；③ 简单场景会过度设计。**不要为了用框架而用框架。**

## Q4. 用 LangGraph 构建一张图的完整流程是什么？`compile()` 到底做了什么？

**答：**

标准五步：

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]

def call_model(state: State) -> dict:
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(State)          # 1. 绑定状态 schema
builder.add_node("model", call_model) # 2. 注册节点
builder.add_edge(START, "model")      # 3. 连边（含入口）
builder.add_edge("model", END)        #    连出口
graph = builder.compile()             # 4. 编译成可执行图
graph.invoke({"messages": [...]})     # 5. 调用
```

`compile()` 不是「打包」，它做了四件事：

1. **结构校验**：必须有入口；边只能指向已注册的节点；检查不可达节点。
2. **把普通函数包装成 Pregel 节点**：绑定它要读哪些 channel、写哪些 channel。
3. **解析 State schema**：为每个字段建立 channel，绑定 reducer。
4. **注入运行时能力**：绑定 checkpointer / store，生成 `invoke`、`stream`、`update_state`、`get_state` 等接口。

**编译后图是只读的**：要改结构必须重新 build。这也是为什么生产上通常把「构图」封装成一个工厂函数。

**追问：`compile()` 能查出所有错误吗？**
→ 不能。结构错误（孤立节点、入口缺失）编译期能查；**路由返回值不在映射表里、并行写同一字段没配 reducer、状态 schema 不匹配**，往往要运行到那一步才暴露。

## Q5. 什么是 superstep？为什么需要同步屏障？

**答：**

LangGraph 的执行模型借自 **Pregel / BSP（整体同步并行）**：

```
superstep 1:  A 执行
              ↓ 同步屏障：统一提交 A 的写入
superstep 2:  B、C 并行执行（都被 A 激活）
              ↓ 同步屏障：统一提交 B、C 的写入，按 reducer 合并
superstep 3:  D 执行
```

规则：**每一轮把所有「被激活」的节点并行跑完，统一提交本轮的状态更新，再决定下一轮激活谁。**

**同步屏障的作用**：让同一 superstep 内的节点看到**同一份轮次开始时的状态快照**，不会读到别人写了一半的数据。这保证了并行执行的可复现性。

⚠️ **注意一个细节**：屏障保证「同轮不互相看见」，但**不保证写入顺序**。所以并行写同一字段时，reducer 必须满足**交换律和结合律**（如加法、集合并集），否则结果仍不确定。

**追问：superstep 和线程是什么关系？**
→ 没有必然关系。superstep 是**逻辑轮次**，同轮节点可以串行、多线程或异步执行。判断并行只看「是否在同一轮被激活」，不看物理线程数。

**追问：这和 LangChain 的 `AgentExecutor` 有什么区别？**
→ `AgentExecutor` 本质是单条 `while` 循环，一次只有一条执行路径；LangGraph 的一轮可以有多条分支同时跑，再统一汇合。

## Q6. Channel 是什么？它和 State 的字段是什么关系？

**答：**

**State 是给开发者看的「类型声明」，Channel 是运行时真正存值的地方。**State 里每个字段，编译后对应一个 Channel。

Channel 负责两件事：

| 职责 | 说明 |
|------|------|
| **存当前值** | 该字段在这一轮结束后的值 |
| **定义更新语义** | 收到一个写入时，怎么和旧值合并 |

常见的更新语义：

- **LastValue**：后写覆盖先写（默认行为）
- **Topic / 追加型**：把新值追加到列表（消息历史就是这类）
- **BinaryOperatorAggregate**：用你提供的二元函数聚合，也就是自定义 reducer

所以那句「reducer 决定怎么合并」的底层含义是：**reducer 就是 Channel 的更新函数。**

**追问：为什么要单独抽象 Channel，直接存字典不行吗？**
→ 因为并行写入需要「合并规则」和「版本管理」。字典只能覆盖，无法表达「两条分支的消息都要保留」。Channel 把「存什么」和「怎么合」解耦，才撑得起扇出/扇入。

## Q7. 节点函数的返回值是怎么合并进 State 的？

**答：**

三个规则，必须记准：

1. **返回 dict = 增量更新（partial update）**。只更新 dict 里出现的 key，没出现的保持原值。
2. **返回 `None` = 不更新**。适合只做副作用（记日志、发请求）的节点。
3. **不要返回「完整的 State 期望整体替换」**。是否替换由该字段的 reducer 决定，不由「你返回了多少 key」决定。

```python
def node(state: State) -> dict:
    return {"answer": "42"}      # 只改 answer，其他字段不动
```

⚠️ **一个高频坑：原地修改 state**。

```python
state["messages"].append(msg)    # ❌ 绕过了 reducer，并行时会丢消息
return {"messages": [msg]}       # ✅ 交给 reducer 合并
```

节点拿到的是状态的**只读视图**（运行时通常会做保护）。原地改可变对象，等于绕过了 Channel 的合并逻辑——单条路径看不出问题，一扇出就丢数据。

**追问：节点可以返回不是 State 里定义的 key 吗？**
→ 不行。写入未声明的字段会报 `InvalidUpdateError`。要加字段，先改 State schema。

## Q8. 构图时最容易犯哪些错误？哪些编译期能发现，哪些只能运行时暴露？

**答：**

| 错误 | 发现时机 | 后果 |
|------|---------|------|
| 没有从 `START` 连边 | 编译期 | 图无法启动 |
| 边指向不存在的节点 | 编译期 | 编译报错 |
| 节点名重复 | 编译期 | 后者覆盖前者 |
| 条件边返回值不在映射表里 | **运行时** | 路由失败，抛异常 |
| 并行节点写同一字段但没配 reducer | **运行时** | `InvalidUpdateError`：LastValue 每个 superstep 只允许一个写入 |
| 循环没有退出条件 | **运行时** | `GraphRecursionError` |
| 子图与父图 state schema 不兼容 | **运行时** | 字段读不到或写入被拒 |
| 在节点里原地改 state | **运行时** | 并行时数据丢失，最难查 |

**最危险的反而是不报错的那两类**：条件边写错映射、在节点里原地改 state——流程照跑，结果不对，排查成本极高。所以并行写入的字段必须显式配 reducer，这是我在项目里踩过的坑。

**追问：怎么给循环加保护？**
→ 两道：① 业务层显式判断（达到最大轮次就路由到 `END`）；② 运行时兜底 `recursion_limit`，超出抛 `GraphRecursionError`。**前者是正常退出，后者是安全网，不能拿安全网当退出条件。**

## Q9. LangGraph 和 CrewAI、AutoGen 有什么区别？该怎么选？

**答：**

| 维度 | LangGraph | CrewAI | AutoGen |
|------|-----------|--------|---------|
| 抽象层级 | **低层**：显式定义图 | 高层：角色 + 任务 | 高层：对话驱动 |
| 控制力 | 强，每步可指定 | 中，靠角色分工 | 较弱，靠对话涌现 |
| 状态与恢复 | 原生 Checkpointer | 有限 | 有限 |
| 可审计性 | 高，执行路径可回放 | 中 | 低（对话式难复现） |
| 上手成本 | 高 | 低 | 中 |
| 适合 | 生产级、要审批/恢复/精细编排 | 快速搭角色协作原型 | 研究型多 Agent 对话 |

**选型结论**：

- 要**上线、要审计、要断点恢复**（金融、运维、企业流程）→ LangGraph；
- 要**两天出个 Demo**、角色分工清晰 → CrewAI；
- 要**研究多 Agent 对话行为** → AutoGen。

**追问：LangGraph 是不是一定更好？**
→ 不是。它的代价是抽象多、代码量大。**如果需求是线性的、不需要恢复，用 LangGraph 属于过度设计。**技术选型看约束，不看热度。
