# 控制流与动态编排

> **适用场景**：从「会画直线图」进阶到「会写真实 Agent」的分界线。
> **主线**：普通边管顺序，条件边管分支，`Send` 管扇出，`Command` 管「更新 + 跳转」一体。

---

## Q1. 普通边、条件边、入口和出口，分别怎么用？

**答：**

| 元素 | API | 作用 |
|------|-----|------|
| **普通边** | `add_edge("a", "b")` | 固定流转：a 执行完必到 b |
| **条件边** | `add_conditional_edges("a", router, {...})` | 由 `router(state)` 的返回值决定下一站 |
| **入口** | `add_edge(START, "a")` | 声明图从哪开始，**必须有** |
| **出口** | `add_edge("z", END)` | 声明正常结束 |
| **条件入口** | `add_conditional_edges(START, router)` | 按输入直接分流到不同子流程 |

```python
def router(state: State) -> str:
    return "tools" if state["messages"][-1].tool_calls else "answer"

builder.add_conditional_edges("model", router, {
    "tools": "tools",
    "answer": END,
})
```

⚠️ **`END` 也是路由目标之一**，不要忘了在映射表里给它留位置。

**追问：条件边能返回多个节点吗？**
→ 能。`router` 返回 `list[str]` 时，这几个节点会在**同一个 superstep 并行执行**。这是静态扇出：分支数量在代码里写死。

---

## Q2. `add_conditional_edges` 的第三个参数（路径映射）为什么建议显式写？

**答：**

第三个参数 `path_map` 建立「**router 返回值 → 节点名**」的映射：

```python
builder.add_conditional_edges("classify", router, {
    "billing": "billing_agent",
    "tech": "tech_agent",
    "other": "fallback_agent",
})
```

显式写有三个好处：

1. **拼写错误在编译期暴露**。不写映射时，返回值直接被当成节点名，写错要到运行时才报。
2. **解耦路由值和节点名**。router 返回业务语义（`"billing"`），节点名可以随便改。
3. **可读性**。看图的人一眼知道有哪些分支。

⚠️ **不写映射时**，router 的返回值必须**精确等于**已注册的节点名，否则运行时抛路由错误。

**追问：router 返回了映射表里没有的值会怎样？**
→ 运行时失败。这是「编译期查不出、运行时才炸」的典型。防御手段：router 末尾永远有 `return "fallback"`，映射表里永远有 fallback 分支。

## Q3. `Send` 是什么？它和条件边返回列表有什么区别？

**答：**

`Send` 是**运行时动态扇出**：在节点里根据数据决定「要起多少个任务、每个任务吃什么输入」。

```python
from langgraph.types import Send

def dispatch(state: State) -> list[Send]:
    return [Send("process_doc", {"doc": d}) for d in state["docs"]]

builder.add_conditional_edges("dispatch", dispatch, ["process_doc"])
```

| 维度 | 条件边返回 list | `Send` |
|------|----------------|--------|
| 分支数量 | 代码里写死 | **运行时才知道**（由数据长度决定） |
| 每个分支的输入 | 共享同一份 State | **每个 Send 可以带独立输入** |
| 典型场景 | 固定几条并行路径 | map-reduce：N 个文档/N 个子任务 |
| 结果汇总 | 各分支写回同一 State，靠 reducer 合并 | 同上，通常配 `Annotated[list, operator.add]` |

**一句话**：条件边是「选路」，`Send` 是「派活」。

**追问：`Send` 的输入和主图 State 是什么关系？**
→ `Send(node, arg)` 的 `arg` 会作为目标节点的**输入状态**。如果目标节点的 schema 是主图 State 的超集/子集，框架会按字段兼容处理。**最常见做法**是给被派发的节点定义一个只含必要字段的小 schema，避免每个分支都携带全量状态。

## Q4. `Command` 是什么？它和普通返回值、`Send` 有什么区别？

**答：**

`Command` 把「**更新状态**」和「**决定下一站**」合并成一次返回：

```python
from langgraph.types import Command

def review(state: State) -> Command:
    if state["score"] > 0.8:
        return Command(goto="publish", update={"status": "approved"})
    return Command(goto="revise", update={"status": "rejected"})
```

| 能力 | 普通返回值 | 条件边 | `Command` |
|------|-----------|--------|-----------|
| 更新状态 | ✅ | ❌（只读） | ✅ |
| 决定下一站 | ❌（走固定边） | ✅ | ✅ |
| 跨图跳转 | ❌ | ❌ | ✅ `graph=Command.PARENT` |
| 适合 | 单纯算数据 | 纯路由 | **路由依赖刚算出的结果** |

**最大价值在 handoff**：多 Agent 场景里，一个 Agent 说「我处理不了，转给 billing」，同时把交接信息写进状态——这就是 `Command(goto=..., update=..., graph=Command.PARENT)`。

**追问：`Command` 和 `Send` 能一起用吗？**
→ 可以。`Command(goto=[Send(...), Send(...)], update={...})` 能同时做「更新 + 动态扇出」。但可读性会下降，复杂编排建议拆成两步。

**追问：`Command` 会不会让图变得不可分析？**
→ 会。路由逻辑藏在节点函数里，静态看图看不出边。**代价是灵活性换可读性**，团队要约定：`Command` 只用于 handoff 这类「必须原子完成」的场景。

## Q5. 怎么在 LangGraph 里实现循环？退出条件怎么设计？

**答：**

循环 = **条件边回指上游节点**：

```python
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", should_continue, {
    "tools": "tools",
    "done": END,
})
builder.add_edge("tools", "agent")     # ← 回到 agent，形成环
```

退出条件要**分层设计**：

| 层级 | 手段 | 作用 |
|------|------|------|
| **业务层（主）** | 模型不再产生 tool_calls、任务完成标记、置信度达标 | 正常退出 |
| **预算层** | 最大轮次、最大 token、最大耗时 | 防止成本失控 |
| **运行时兜底** | `recursion_limit`（可配置） | 最后的安全网，超出抛 `GraphRecursionError` |

```python
config = {"recursion_limit": 50}
```

⚠️ **不要把 `recursion_limit` 当业务退出条件**。它抛的是异常，不是正常返回，上层拿到的是失败而不是「达到上限的结果」。

**追问：循环里状态会无限增长吗？**
→ 会。每轮都往 `messages` 追加，checkpoint 越写越大。必须在循环里做裁剪或摘要，否则长任务会先被存储拖垮，而不是被逻辑拖垮。

## Q6. 多个并行分支怎么合流（fan-in）？会不会重复执行？

**答：**

把多条边指向同一个节点即可：

```
        ┌─→ B ─┐
A ──────┤      ├─→ D
        └─→ C ─┘
```

```python
builder.add_edge("a", "b")
builder.add_edge("a", "c")
builder.add_edge("b", "d")
builder.add_edge("c", "d")
```

**语义**：D 会在 B、C **都完成后**执行一次（隐式 join）。框架按 superstep 计算「D 的所有入边是否都已在本轮或之前完成」。

⚠️ **两个坑**：

1. **D 只执行一次，不是两次**。如果你需要「每条分支各处理一次」，用 `Send` 而不是普通边。
2. **B、C 写同一个字段必须配 reducer**，否则同一 superstep 多写入会抛 `InvalidUpdateError`。

**追问：如果 B 走了条件分支没到 D，D 会永远等吗？**
→ 不会。join 的判断基于「本轮实际完成的分支」，不是「所有可能的入边」。没被激活的分支不参与等待。

## Q7. 子图怎么用？共享状态还是独立状态？

**答：**

子图就是一个**编译后的图，当成节点注册**：

```python
sub = StateGraph(SubState)
sub.add_node("step", step_fn)
sub.add_edge(START, "step")
sub.add_edge("step", END)

builder.add_node("subtask", sub.compile())
```

状态关系有两种模式：

| 模式 | 做法 | 适用 |
|------|------|------|
| **共享 schema** | 父子用同一 State（或子集） | 子图只是「把一段流程封装起来」 |
| **独立 schema** | 子图自己的 State，父图节点做入参/出参转换 | 子图可复用、对外隔离 |

```python
def call_sub(state: ParentState) -> dict:
    result = sub.invoke({"query": state["question"]})
    return {"answer": result["answer"]}
```

**追问：子图里能中断吗？恢复时从哪继续？**
→ 能。中断会冒泡到父图，`get_state` 能看到子图的暂停点。恢复时用同一个 `thread_id`，父图会重新进入子图并从断点续跑。**这也是子图状态要可序列化的原因。**

**追问：子图能单独加 checkpointer 吗？**
→ 一般不需要，继承父图的即可。单独加会让「父图一个 thread、子图另一个 thread」对不上，恢复时容易错位。

## Q8. 要并行处理 1000 个文档，`Send` 直接发 1000 个任务合适吗？

**答：**

**不合适。**`Send` 只负责「表达并行意图」，不负责「限流」。一轮内发 1000 个任务，框架会尝试同时激活 1000 个节点，后果是：

- 模型 API 被打爆（429）；
- 内存/连接数飙升；
- 单个失败会让整轮重试成本极高。

生产做法是**分批 + 限流 + 幂等**：

| 手段 | 做法 |
|------|------|
| **分批** | 每轮只 `Send` 一个批次（如 20 个），批内并行、批间串行 |
| **信号量** | 节点内部用 `asyncio.Semaphore` 限制真实并发 |
| **队列** | 大任务落到消息队列，图只负责编排，Worker 消费 |
| **幂等** | 每个任务带唯一 id，失败重试不重复写 |
| **失败隔离** | 单任务异常不要炸整批，记录后继续 |

**追问：批间串行会不会太慢？**
→ 会慢，但可控。**吞吐的上限由下游决定，不由图决定。**先测下游的 QPS 上限，再定批大小，比「一把梭」然后全线 429 更工程化。

## Q9. 路由函数里能不能调用 LLM？应该注意什么？

**答：**

**能，但要清楚代价。**

路由函数在 superstep 的调度阶段执行，必须是**快速、确定性**的：

| 做法 | 问题 |
|------|------|
| 在 router 里直接调 LLM 分类 | 每轮都多一次模型调用，延迟和成本翻倍；结果不确定，同一状态可能路由到不同分支 |
| 在 router 里查数据库 | 阻塞调度；异常会导致整图失败 |
| 在 router 里做副作用（写库、发消息） | 路由可能被重放/重试，副作用会重复执行 |

**推荐模式**：**先用一个节点做分类，把结果写进 State，router 只读 State 做纯函数判断。**

```python
def classify(state) -> dict:
    return {"intent": llm_classify(state["question"])}   # 节点里调模型

def route(state) -> str:
    return {"billing": "billing", "tech": "tech"}[state["intent"]]  # 纯函数
```

**追问：router 会被重复执行吗？**
→ 会。恢复、重试、时间旅行都可能让它再跑一次。**所以 router 必须是纯函数**，这是最容易忽略的约束。
