## 一、标准答法（30 秒版）

> LangGraph 是**基于状态机的 Agent 编排框架**。核心是三件：**StateGraph**（定义节点和边）、**State**（跨节点流转的数据）、**Checkpointer**（持久化状态以支持恢复）。

**接着必须展开的**（否则显得只会背概念）：

| 点 | 内容 |
|---|---|
| ① 为什么不用裸循环 | ⭐ **自己写 while 循环，中断/恢复/并发/可视化全要自己实现** |
| ② 执行模型 | ⭐ **Pregel 式的 superstep**：每轮所有就绪节点并行执行，然后同步 |
| ③ 和 LangChain 的关系 | ⭐ `create_agent` 底层就是编译成 LangGraph 来跑的 |

## 二、核心概念（⭐ 这是深挖区）

### State：数据怎么流转

```python
from typing import Annotated, TypedDict
from langgraph.graph import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # ⭐ reducer 决定怎么合并
```

⭐ **三个必答点**：

| 点 | 内容 |
|---|---|
| **reducer** | ⭐ **决定「新值怎么合并到旧值」**。`add_messages` 是追加+去重；不写 reducer 就是覆盖 |
| **为什么需要 reducer** | ⭐ **并行节点同时写同一个字段，没有合并规则就会互相覆盖** |
| **Channel** | 底层概念：每个状态字段是一个 Channel，有各自的 reducer |

⚠️ **追问：「不用 reducer 会怎样？」**
→ ⭐ **扇出场景下后写的覆盖先写的**——这是 LangGraph 最经典的 bug。

### superstep：执行模型

```
superstep 1: 节点 A 执行
              ↓ 同步点（barrier）
superstep 2: 节点 B、C 并行执行（都被 A 激活）
              ↓ 同步点
superstep 3: 节点 D 执行
```

⭐ **关键**：**同一 superstep 内的节点并行，superstep 之间有同步屏障。**

⚠️ **追问：「为什么要同步屏障？」**
→ ⭐ **保证状态一致性**——所有节点看到的是同一轮开始时的状态，避免读到「半个更新」的状态。

### 三种边

| 边 | 作用 |
|---|---|
| **普通边** | `A → B`，固定流转 |
| ⭐ **条件边** | `A → (B 或 C)`，由函数返回值决定 |
| ⭐ **`Send`** | 动态扇出：一个节点触发 N 个并行任务 |

⚠️ **追问：`Send` 和普通扇出有什么区别？**
→ ⭐ **`Send` 是「动态」的**——N 在运行时才知道（如「给每个文档起一个处理节点」）。静态扇出在构图时就固定了。

## 三、Checkpointer（⭐ 高频深挖）

### 它解决什么问题

| 场景 | 没有 Checkpointer | 有 Checkpointer |
|------|------------------|----------------|
| 多轮对话 | ❌ 每轮是新图 | ✅ 按 `thread_id` 恢复 |
| 人工介入（HITL） | ❌ 只能阻塞 | ⭐ **`interrupt()` 暂停，恢复时续跑** |
| 崩溃恢复 | ❌ 全丢 | ✅ 从最后一个 checkpoint 继续 |
| 时间旅行 | ❌ 无 | ⭐ **可以回到任意历史状态** |

⚠️ **追问：`interrupt()` 的原理？**
→ ⭐ **把当前状态持久化后抛出/暂停，进程可以退出；恢复时用同一个 `thread_id` 重新 invoke，从 checkpoint 继续。**

📌 [[langchain/memory/Checkpointer存储后端]] · [[langgraph/modules/langgraph_human_in_loop/interrupt机制]]

### 后端的选型（你项目里两个都用了）

| 后端 | 适用 |
|------|------|
| `InMemorySaver` | ⚠️ **仅开发/测试**，重启即丢 |
| ⭐ `SqliteSaver` | 单机、轻量、本地应用 |
| ⭐ `PostgresSaver` | ⭐ **生产**，支持多进程共享 |

⚠️ **追问：为什么生产用 PG 不用 SQLite？**
→ ⭐ **多进程/多实例要共享状态**。SQLite 是文件锁，并发写会冲突；PG 支持真正的并发。

## 四、你项目里的用法（⭐ 这是加分项）

按 memory 记录，你的多智能体系统用了：**StateGraph + Send 动态扇出 + SqliteSaver/PostgresSaver + SummarizationMiddleware**。

**建议这样讲**（⚠️ 具体细节请按实际调整）：

```
「我的系统是一个终端交互的多智能体编排。用 StateGraph 定义编排节点和
专家节点，专家节点内部是各自的 ReAct 循环。

两个关键设计：
① 用 Send 做动态扇出——编排节点决定派给哪几个专家，运行时才确定数量，
   比静态扇出灵活。
② 用 PostgresSaver 做状态持久化——支持中断恢复和多轮对话的 thread_id
   隔离。开发期用 SqliteSaver，生产切 PG。

踩过的坑：一开始没给 messages 字段配 add_messages reducer，扇出时
后写的节点覆盖了先写的。后来所有并行写入的字段都显式配了 reducer。」
```

⭐ **最后那句「踩过的坑」是整段回答的价值所在**——它证明你真的写过，不是看文档看来的。

## 五、LangGraph vs 自己写循环（必答题）

⚠️ **这题答不好，前面全白搭。**

| 维度 | 自己写 while 循环 | LangGraph |
|------|----------------|-----------|
| 状态管理 | 手写 | 声明式（State + reducer） |
| 中断恢复 | ❌ 自己实现 | ✅ Checkpointer |
| 并发/扇出 | ❌ 自己实现 | ✅ Send + superstep |
| 人工介入 | ❌ 阻塞式 | ✅ interrupt/resume |
| 可视化 | ❌ 无 | ✅ 图结构可渲染 |
| 流式 | ❌ 自己实现 | ✅ `astream` |
| 调试 | 打日志 | ✅ 状态可检查、可时间旅行 |

⭐ **一句话结论**：**原型可以自己写循环；要上生产（要恢复、要并发、要人工介入），必须用图框架。**

## 六、高频追问速查

| 追问 | 答法要点 |
|------|---------|
| LangGraph 和 LangChain 什么关系？ | ⭐ **`create_agent` 底层编译成 LangGraph**；LangGraph 是编排层 |
| superstep 是什么？ | 一轮并行执行 + 同步屏障 |
| reducer 是干什么的？ | ⭐ **定义并行写入时怎么合并**，防覆盖 |
| `Send` 和静态扇出的区别？ | ⭐ Send 是运行时动态决定数量 |
| Checkpointer 为什么需要？ | 恢复/多轮/HITL/时间旅行 |
| `interrupt()` 后进程能退出吗？ | ⭐ **能**，状态已持久化，恢复时同 thread_id 续跑 |
| 为什么生产用 PG 不用 SQLite？ | 多进程共享状态，SQLite 文件锁冲突 |
| 状态很大怎么办？ | ⭐ 大字段外置到 Store，State 只存引用 |
| 流式有几种模式？ | `values`（全量状态）/ `messages`（增量消息）/ `custom`（自定义） |
| 怎么调试跑偏的图？ | ⭐ 检查中间状态 + `get_state_history` 时间旅行 |
