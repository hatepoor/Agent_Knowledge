# 流式输出与可观测性

> **适用场景**：做过 Chat 产品必问。答「用 `stream` 就能流式」不够，要能说清**流的是什么粒度**。
> **主线**：`stream_mode` 决定「切片的单位」，`astream_events` 决定「事件的粒度」。

---

## Q1. `stream_mode` 有哪些模式？分别输出什么？

**答：**

常用五种：

| 模式 | 每个 chunk 是什么 | 典型用途 |
|------|------------------|---------|
| **`values`** | 每一步结束后的**完整 State** | 调试、需要全量快照的前端 |
| **`updates`** | 每一步**哪个节点写了什么**（增量） | 展示「正在做什么」、进度条 |
| **`messages`** | LLM 的 **token 级增量** + 元数据 | 打字机效果 |
| **`custom`** | 节点里手动 `writer()` 发出的任意数据 | 业务进度、中间结果 |
| **`debug`** | 框架级详细事件（任务开始/结束等） | 本地排查 |

```python
for chunk in graph.stream(inputs, stream_mode="updates"):
    print(chunk)          # {"node_name": {...写入的字段...}}

for mode, chunk in graph.stream(inputs, stream_mode=["updates", "messages"]):
    ...
```

⚠️ **多模式时返回 `(mode, chunk)` 元组**，单模式时直接返回 chunk。这个差异很容易在切换时写错。

**追问：`values` 和 `updates` 怎么选？**
→ 前端只需要「最新完整状态」→ `values`；需要知道「哪一步产生了什么」→ `updates`。`values` 的数据量随 State 增大而增大，长对话里别用它推 token。

## Q2. `messages` 模式输出的到底是什么？怎么区分不同节点的模型调用？

**答：**

`messages` 模式输出的是 **`(message_chunk, metadata)` 二元组**：

```python
for chunk, metadata in graph.stream(inputs, stream_mode="messages"):
    print(metadata["langgraph_node"], chunk.content)
```

| 字段 | 含义 |
|------|------|
| `chunk` | `AIMessageChunk`，含 `content`（文本片段）、`tool_call_chunks`（工具调用增量） |
| `metadata["langgraph_node"]` | 这个 token 来自哪个节点 |
| `metadata["langgraph_step"]` | 第几个 superstep |
| `metadata["tags"]` / `checkpoint_ns` | 追踪与子图定位 |

**注意**：`messages` 模式流的是**模型输出**，不是「所有消息」。用户输入不会从这里出来；要展示完整对话，得自己维护。

**追问：工具调用的参数也是流式的吗？**
→ 是。`tool_call_chunks` 会分片到达（函数名先到、参数 JSON 分片追加）。要展示「正在调用什么工具」，需要把分片拼起来再解析，不能每片都 `json.loads`。

**追问：`messages` 模式和 `astream_events` 的 `on_chat_model_stream` 有什么区别？**
→ 前者是**图层面的约定输出**，简单直接；后者是**回调事件**，能拿到模型开始/结束、工具开始/结束等完整生命周期，适合做复杂 UI。**只要打字机效果用 `messages`，要做事件驱动的 UI 用 `astream_events`。**

## Q3. 怎么把流式结果推给前端？SSE 要注意什么？

**答：**

典型链路：**LangGraph `astream` → FastAPI `StreamingResponse`（SSE）→ 前端 `EventSource` / fetch stream**。

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json

app = FastAPI()

@app.post("/chat")
async def chat(req: ChatRequest):
    async def gen():
        async for chunk, meta in graph.astream(
            {"messages": [("user", req.text)]},
            {"configurable": {"thread_id": req.thread_id}},
            stream_mode="messages",
        ):
            if chunk.content:
                yield f"data: {json.dumps({'text': chunk.content})}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(gen(), media_type="text/event-stream")
```

工程注意点：

| 点 | 说明 |
|----|------|
| **格式** | SSE 每条以 `data: ` 开头、`\n\n` 结尾；别漏空行 |
| **心跳** | 长任务中间要发注释行（`: ping`）防代理断连 |
| **背压** | 下游消费慢时要有队列/丢弃策略，不能让内存无限涨 |
| **错误帧** | 流中出错要发一个结构化 error 事件，不能直接断连让前端猜 |
| **结束标记** | 显式 `[DONE]`，前端才知道是正常结束 |
| **Nginx** | 关闭 `proxy_buffering`，否则 token 会被攒着一起发 |
| **断线重连** | SSE 自带重连会重发请求，需要客户端带 `last_event_id` 或业务去重 |

**追问：为什么不用 WebSocket？**
→ 单向推送 SSE 足够，协议简单、自带重连、走 HTTP 基础设施（网关/鉴权/日志都现成）。**需要双向实时交互（语音、协同）再上 WebSocket。**

## Q4. `astream_events` 是什么？和 `stream` 有什么区别？

**答：**

`astream_events` 基于 **LangChain 回调系统**，把执行过程拆成细粒度事件：

```python
async for event in graph.astream_events(inputs, config, version="v2"):
    if event["event"] == "on_chat_model_stream":
        print(event["data"]["chunk"].content)
```

常见事件：

| 事件 | 触发 |
|------|------|
| `on_chain_start` / `on_chain_end` | 图、子图、节点开始/结束 |
| `on_chat_model_start` / `on_chat_model_stream` / `on_chat_model_end` | 模型调用生命周期 |
| `on_tool_start` / `on_tool_end` / `on_tool_error` | 工具调用 |
| `on_retriever_start` / `on_retriever_end` | 检索 |
| `on_custom_event` | 自定义事件 |

| 维度 | `stream` | `astream_events` |
|------|----------|------------------|
| 抽象层级 | 图的状态/消息 | 组件级生命周期 |
| 数据 | 状态增量、token | 事件名 + data + run_id + 父子关系 |
| 适合 | 简单打字机、进度 | 复杂 UI（显示「正在检索」「正在调工具」）、自定义埋点 |
| 开销 | 低 | 较高（事件多） |

**追问：`version="v2"` 是什么？**
→ 事件 schema 的版本。新版 schema 统一了字段结构。**升级时注意事件字段可能变**，前端解析逻辑要跟着改。

## Q5. 怎么在节点里发自定义进度？`custom` 模式怎么用？

**答：**

用 `get_stream_writer()` 拿到写入器：

```python
from langgraph.config import get_stream_writer

def process(state: State) -> dict:
    writer = get_stream_writer()
    for i, doc in enumerate(state["docs"]):
        writer({"progress": f"{i+1}/{len(state['docs'])}", "stage": "parsing"})
        parse(doc)
    return {"done": True}
```

消费端：

```python
for chunk in graph.stream(inputs, stream_mode="custom"):
    print(chunk)     # {"progress": "3/10", "stage": "parsing"}
```

适用场景：

- 长耗时节点内部的进度（解析 100 个文档）；
- 业务阶段提示（「正在检索知识库」）；
- 想把中间结果推给前端，但不想污染 State。

**追问：`custom` 和 `updates` 的区别？**
→ `updates` 是**节点结束后**的正式状态写入，事务性、会进 checkpoint；`custom` 是**节点执行过程中**的旁路消息，不进状态。**进度类信息用 custom，业务结果用 updates。**

## Q6. 子图的流式输出怎么拿到？怎么区分是哪个子图？

**答：**

需要显式开启子图流式（不同版本参数名略有差异，常见为 `subgraphs=True`）：

```python
for namespace, chunk in graph.stream(inputs, stream_mode="updates", subgraphs=True):
    print(namespace, chunk)
```

`namespace` 是一个元组，标识层级路径（父图 → 子图 → 更深子图）。可以用它做：

- 前端按节点路径展示「正在哪个子流程」；
- 过滤只关心某个子图的事件；
- 日志里还原调用树。

**追问：不开子图流式会怎样？**
→ 子图内部的中间步骤**不会单独输出**，只在子图整体结束时作为一个节点更新出现。表现为「点了半天没反应，最后一次性出来」——长流程里体验很差。

## Q7. 流式和中断能一起用吗？恢复后还能继续流吗？

**答：**

能，但要理解**流的生命周期**：

1. `astream` 跑到 `interrupt()` → 流**结束**（不是挂起）；
2. 调用方拿到中断载荷，展示审批 UI；
3. 审批后**新开一个 `astream`**，传 `Command(resume=...)` → 从断点继续流。

```python
# 第一次
async for chunk in graph.astream(inputs, config, stream_mode="messages"):
    ...

# 恢复（新的流）
async for chunk in graph.astream(Command(resume=decision), config, stream_mode="messages"):
    ...
```

**注意**：两次流之间没有共享的连接，前端要自己把「前半段输出」和「后半段输出」拼起来。

**追问：流到一半网络断了怎么办？**
→ 图和 checkpoint 不受影响（状态已落盘），但**已经推给前端的 token 不会重发**。重连后应该：① 用 `get_state` 拿当前完整状态渲染；② 再决定是继续流还是从头重放。**不要盲目重跑，会重复执行副作用。**

## Q8. 生产环境怎么观测 LangGraph 应用？看哪些指标？

**答：**

三层观测：

| 层 | 工具 | 看什么 |
|----|------|--------|
| **追踪（Trace）** | LangSmith / Langfuse / OpenTelemetry | 每次调用的完整链路：节点耗时、模型输入输出、工具调用、token 数 |
| **指标（Metrics）** | Prometheus + Grafana | QPS、P95/P99 延迟、错误率、token 消耗、工具成功率 |
| **日志（Logs）** | 结构化日志 | `thread_id`、`checkpoint_id`、节点名、异常栈 |

**LangGraph 特有的观测点**：

| 指标 | 意义 |
|------|------|
| 每个 superstep 的耗时 | 定位是模型慢还是工具慢 |
| 循环轮次分布 | 发现「停不下来」的会话 |
| checkpoint 写入延迟 | PG 是否成为瓶颈 |
| 中断停留时长 | 审批流程是否卡住 |
| 恢复次数 | 是否存在重复恢复/异常重试 |
| State 大小 | 是否该瘦身 |

**追问：线上一个会话答偏了，怎么排查？**
→ 拿 `thread_id` → `get_state_history` 拉时间线 → 找到第一次跑偏的 superstep → 看当时的 State（模型输入、工具返回）→ 必要时从该点分叉重放。**这是图框架相比裸循环最大的运维优势：可回放。**

**追问：LangSmith 是必须的吗？**
→ 不是。可以用 Langfuse 或 OpenTelemetry 自建。但**必须有一种能按 `thread_id` 还原链路的工具**，否则线上问题只能靠猜。
