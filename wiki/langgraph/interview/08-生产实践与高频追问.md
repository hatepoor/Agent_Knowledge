# 生产实践与高频追问

> **适用场景**：三面/主管面。这一篇不考 API，考的是「你有没有为线上负过责」。
> **答题基调**：每个答案都落到「约束 → 取舍 → 具体做法」，不要只给结论。

---

## Q1. 一个 LangGraph 应用怎么部署到生产？典型架构是什么？

**答：**

典型链路：

```
客户端 → 网关（鉴权/限流）→ FastAPI → LangGraph（编译好的图）
                                      ├─ PostgresSaver（状态）
                                      ├─ Redis（缓存/会话热数据）
                                      ├─ 模型供应商
                                      └─ LangSmith / OTel（追踪）
```

关键设计：

| 组件 | 做法 |
|------|------|
| **图实例** | 应用启动时**编译一次**，全局复用；不要每请求 build |
| **Checkpointer** | 启动时初始化连接池 + `setup()`，随应用生命周期存活 |
| **API 层** | 只做「参数校验、鉴权、thread_id 归属校验、流式转发」 |
| **Worker** | 长任务（批量解析、离线评估）与在线请求分离，避免互相拖垮 |
| **可观测** | 每个请求带 `thread_id` / `trace_id`，日志结构化 |
| **扩缩容** | 服务无状态（状态在 PG），可水平扩容；注意连接池总连接数 ≤ PG 上限 |

**追问：为什么图要编译一次？**
→ `compile()` 会解析 schema、构建 Pregel 执行计划，有固定开销。每次请求编译既浪费 CPU，也让连接池/checkpointer 难以复用。**图是「配置」，不是「请求对象」。**

## Q2. 编译后的图能多请求并发复用吗？线程安全吗？

**答：**

**能复用，图本身是只读的。**但要区分三样东西：

| 对象 | 是否共享 | 注意 |
|------|---------|------|
| **CompiledGraph** | ✅ 全局共享 | 编译后结构不可变，可并发调用 |
| **Checkpointer / 连接池** | ✅ 共享 | 必须用线程安全/异步安全的连接池 |
| **单次执行的 State** | ❌ 每次独立 | 由 `config` 里的 `thread_id` 隔离，不在图对象上 |

实践建议：

- **同步服务**（多线程）：图共享没问题，但每个线程要有自己的 DB 连接（用 pool）；
- **异步服务**（FastAPI + asyncio）：用 `AsyncPostgresSaver`，不要在协程里调同步阻塞的 DB 方法；
- **不要在节点函数里存实例变量**当请求上下文，那是全局状态，会串号。

**追问：同一个 `thread_id` 被两个请求同时调用会怎样？**
→ 会竞争同一条状态时间线，产生交错写入甚至冲突。**同一 thread 必须串行**：用分布式锁（Redis `SETNX` + 过期）或按 thread_id 做队列分区。这是多副本部署必须处理的问题。

## Q3. 超时和重试怎么做？哪些能重试，哪些不能？

**答：**

分三层设置，且**只重试幂等操作**：

| 层 | 手段 | 说明 |
|----|------|------|
| **模型调用** | SDK 自带重试 + 指数退避 | 只重试 429/5xx/超时；4xx 参数错误重试没意义 |
| **工具调用** | 自己包一层 | 查询类可重试；**写操作必须有幂等键**才可重试 |
| **节点/整图** | `asyncio.wait_for` / 任务超时 | 防止单个节点拖死整个请求；新版也提供节点级超时配置 |

```python
import asyncio

async def call_with_timeout(coro, seconds=30):
    try:
        return await asyncio.wait_for(coro, timeout=seconds)
    except asyncio.TimeoutError:
        return {"error": "timeout"}     # 交给路由决定降级还是终止
```

⚠️ **重试的三个陷阱**：

1. **重复副作用**：发邮件、扣款、创建工单，重试会执行两次 → 幂等键 + 唯一约束；
2. **重试风暴**：下游已经过载，所有请求一起重试会压垮它 → 退避 + 抖动 + 熔断；
3. **重试放大成本**：一次失败重试 3 次，token 成本 ×4 → 设总预算上限。

**追问：重试放在节点里还是框架层？**
→ **优先放在最贴近故障的地方**（模型 SDK / 工具客户端），语义最清楚。节点级重试适合「整个节点可安全重放」的场景，且必须保证节点幂等。

## Q4. 怎么控制一个 Agent 的 token 成本？

**答：**

六个杠杆，按性价比排序：

| 杠杆 | 做法 | 效果 |
|------|------|------|
| **① 裁剪历史** | 滑动窗口 + 摘要，别把全量 messages 每次带上 | 最直接，通常省一半以上 |
| **② 路由用小模型** | 分类/路由/简单工具选择用便宜模型 | 高频调用降本明显 |
| **③ 工具结果瘦身** | 检索只返回必要字段，别把整篇文档塞进上下文 | 减少无效 token |
| **④ 缓存** | 相同问题/相同检索结果缓存（注意失效策略） | 重复请求降本 |
| **⑤ 预算上限** | 单请求最大 token / 最大轮次，超限终止 | 防单点爆炸 |
| **⑥ 提前终止** | 结果满足条件就停，不要「再确认一遍」 | 减少无意义轮次 |

**追问：怎么知道成本花在哪？**
→ 按 `thread_id` / 节点 / 模型三个维度打点：输入 token、输出 token、调用次数。**大多数成本问题不是单价高，而是「上下文太长」或「循环太多」。**

## Q5. LangGraph 升级版本要注意什么？

**答：**

| 风险 | 说明 | 应对 |
|------|------|------|
| **导入路径变化** | 1.0 起 `langgraph.prebuilt` 弃用，预置组件迁到 `langchain.agents` | 锁版本 + 读 changelog + 全局搜旧导入 |
| **中断 API 变化** | 旧版异常式中断 → `interrupt()` + `Command(resume=)` | 升级前先改中断相关代码并补测试 |
| **状态 schema 兼容** | 老 checkpoint 可能缺新字段 | 新字段给默认值，先兼容再清理 |
| **checkpoint 表结构** | 新版本可能需要加表/加列 | 预发执行 `setup()`，确认幂等 |
| **流式 schema 变化** | 事件字段/返回结构可能调整 | 前端解析层做版本适配 |

**升级流程建议**：

1. 锁定依赖版本（`requirements.txt` / `uv.lock`），禁止浮动版本上生产；
2. 预发环境用**真实 thread 回放**（`get_state_history` + 恢复），验证兼容；
3. 灰度：先切 5% 流量，观察错误率和延迟；
4. 保留回滚方案（旧镜像 + 数据库向后兼容）。

**追问：能直接跳大版本吗？**
→ 不建议。跨大版本要逐个小版本读 breaking changes，尤其是中断、checkpoint、流式这三块。**升级的成本主要在「状态兼容」和「前端协议」，不在代码本身。**

## Q6. 一张图怎么写测试？

**答：**

四层测试，从便宜到贵：

| 层 | 测什么 | 怎么写 |
|----|--------|--------|
| **① 节点单测** | 输入 State → 输出增量 | 节点是纯函数，直接调用断言；外部依赖打桩 |
| **② 路由单测** | 每个分支是否走对 | 构造 State，断言 router 返回值 |
| **③ 图集成** | 整条链路 | `InMemorySaver` + 假模型，跑完整 `invoke` |
| **④ 回放测试** | 真实历史是否还能跑 | 拿线上 `thread_id` 的 checkpoint，在预发重放 |

重点覆盖：

- **中断/恢复**：暂停后恢复，状态是否正确、副作用是否重复；
- **并行扇出**：reducer 合并结果是否符合预期；
- **异常分支**：工具报错、模型超时、路由 fallback；
- **循环终止**：达到上限是否正常收口。

```python
def test_router_billing():
    assert route({"intent": "billing"}) == "billing_agent"

def test_interrupt_resume():
    graph = build_graph(InMemorySaver())
    graph.invoke({"amount": 100}, {"configurable": {"thread_id": "t"}})
    out = graph.invoke(Command(resume={"approved": True}),
                       {"configurable": {"thread_id": "t"}})
    assert out["approved"] is True
```

**追问：模型输出不稳定，测试怎么写？**
→ **不要断言模型的自然语言**。要么打桩返回固定结构，要么断言「结构 + 关键字段 + 路由结果」。端到端测试只做冒烟，不做逐字比对。

## Q7. 什么时候用 `create_agent`，什么时候手写图？

**答：**

**默认用 `create_agent`，遇到它的表达边界再下沉。**

| 场景 | 选择 |
|------|------|
| 标准 ReAct：模型 + 工具 + 循环 | `create_agent` |
| 需要中间件（摘要、限流、人审、PII） | `create_agent` + middleware |
| 需要多阶段固定流程（检索→校验→生成→审核） | 手写图 |
| 需要并行扇出/合流 | 手写图（`Send`） |
| 需要多 Agent 精细路由 | 手写图或 Supervisor 图 |
| 需要自定义 State（业务字段） | 手写图（`create_agent` 的 State 以 messages 为中心） |

**判断口诀**：**「一条循环 + 一组工具」用 `create_agent`；「多段流程 + 分支/并行/审批」用手写图。**

**追问：手写图是不是显得更高级？**
→ 不是。**用框架的高层封装解决它擅长的问题，才是工程判断。**手写图带来的维护成本是真实的，只有在需要控制力时才付这个成本。

## Q8. 线上最常见的 LangGraph 事故有哪些？

**答：**

| 事故 | 现象 | 根因 | 处置 |
|------|------|------|------|
| **状态膨胀** | 越用越慢，PG 写入飙升 | 消息只增不减、大对象进 State | 裁剪/摘要 + 大对象外置 |
| **死循环** | 单请求跑几分钟、token 爆表 | 缺业务退出条件，只靠 recursion_limit | 加轮次/预算闸门 |
| **重复副作用** | 用户收到多封邮件 | 恢复重跑 + 无幂等 | 副作用后置 + 幂等键 |
| **同 thread 并发** | 状态错乱、回答串台 | 两个请求同时写一个 thread | 分布式锁/串行队列 |
| **checkpoint 丢失** | 重启后待办消失 | 用了内存后端 | 生产 PG + 备份 |
| **连接池耗尽** | 请求排队、超时 | 每请求新建连接/池太小 | 共享池 + 上限保护 |
| **模型超时拖垮** | 整个请求卡死 | 无超时/无降级 | 超时 + fallback 模型 |
| **权限越界** | A 用户读到 B 的会话 | thread_id 直接透传 | 归属校验 + 不可猜测 id |

**追问：如果只能加一个监控告警，加哪个？**
→ **单请求的 superstep 数与 token 消耗**。这两个指标同时异常，基本能覆盖死循环、上下文膨胀、路由失效三类高频事故。

## Q9. 「你项目里最大的技术难点是什么？」——用 LangGraph 项目怎么答？

**答：**

用 **STAR + 一个机制细节 + 一个踩坑**，控制在 90 秒：

```
S（背景）：终端多智能体系统，需要支持多轮对话、专家动态分派、人工审批。
T（任务）：既要并行处理多个子任务，又要保证中断后能恢复、状态不串。
A（行动）：
  ① 用 StateGraph 定义编排节点 + 专家节点，专家内部是各自的 ReAct 循环；
  ② 用 Send 做动态扇出——派给几个专家是运行时决定的，不是写死的；
  ③ 用 PostgresSaver 按 thread_id 持久化，配合 interrupt() 做高危操作审批；
  ④ 给并行写入的字段全部显式配 reducer。
R（结果）：支持断点恢复和多轮隔离；【待补充：具体指标】。
坑：一开始 messages 没配 add_messages，扇出时同一 superstep 多写入直接报
   InvalidUpdateError；后来所有并行字段都显式声明了 reducer，并补了扇出场景的测试。
```

⚠️ **量化数据不要编**。没有实测就讲「支持了什么能力」，不要报「提升了 40%」。

**追问：为什么不用 `create_agent` 一把梭？**
→ 「因为需要动态扇出和自定义状态字段，`create_agent` 的 messages 中心模型表达不了。标准 ReAct 部分仍然复用了它的思路，只在编排层下沉。」**这个回答体现了「知道边界」，比「手写更牛」可信。**

**追问：如果重做一次，你会改什么？**
→ 给一个真实改进：**「先把状态 schema 和 reducer 设计定稿，再写节点」**。状态设计错了，后面所有节点都要返工——这是图框架和传统脚本最大的差别。
