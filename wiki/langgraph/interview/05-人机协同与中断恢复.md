# 人机协同与中断恢复

> **适用场景**：只要岗位涉及「Agent 上线」，这题必问。金融、运维、内容审核类业务甚至是必考。
> **主线**：`interrupt()` 不是「阻塞等待」，而是「**存档后退出，之后从存档点续跑**」。

---

## Q1. `interrupt()` 是什么？它的执行原理是什么？

**答：**

`interrupt()` 是 LangGraph 原生的**人机协同原语**：在节点内部调用，把当前值抛给调用方并**暂停整个图**，等人工处理完后恢复。

```python
from langgraph.types import interrupt

def approval_node(state: State) -> dict:
    decision = interrupt({"question": "是否执行退款？", "amount": state["amount"]})
    return {"approved": decision["approved"]}
```

原理分四步：

1. 节点执行到 `interrupt()`，框架**抛出内部中断信号**（本质是框架内部异常；业务代码若用宽泛的 `except Exception` 包住，会把中断吞掉，必须避免）；
2. 当前 superstep 的状态被写入 **checkpoint**，记录「停在哪个节点、下一步是谁」；
3. `invoke` 返回，调用方拿到中断载荷（`result["__interrupt__"]` 或 `state.interrupts`）；
4. 恢复时传 `Command(resume=值)`，**节点从头重新执行**，这次 `interrupt()` 直接返回 resume 值，继续往下走。

⚠️ **两个前置条件**：必须挂 **Checkpointer**，必须传 **`thread_id`**。缺一个就报错——因为没有存档点，中断后无法恢复。

**追问：中断期间进程能退出吗？**
→ **能**。这正是它和 `input()` 的本质区别：状态已经落盘，进程可以重启、可以换机器，之后用同一 `thread_id` 恢复。适合「审批要等一天」的场景。

## Q2. `interrupt()` 和 `interrupt_before` / `interrupt_after` 有什么区别？

**答：**

| 方式 | 触发点 | 配置时机 | 能否传载荷 | 适用 |
|------|--------|---------|-----------|------|
| **`interrupt()`** | 节点**内部**任意位置 | 写在代码里 | ✅ 可传结构化数据 | 需要把中间结果交给人工看 |
| **`interrupt_before`** | 指定节点**执行前** | 编译时静态声明 | ❌ 只能看到当前 State | 高危操作执行前审批 |
| **`interrupt_after`** | 指定节点**执行后** | 编译时静态声明 | ❌ | 执行后复核、人工检查输出 |

```python
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["execute_refund"],   # 静态断点
)
```

**核心区别**：

- `interrupt()` 是**动态的**：可以在节点里根据条件决定要不要停，还能把「要审批什么」一起送出去；
- `interrupt_before/after` 是**静态的**：图结构确定后就固定了，适合「这个节点永远要人看一眼」。

恢复方式也不同：静态断点用 `graph.invoke(None, config)` 继续；`interrupt()` 用 `Command(resume=...)` 带回数据。

**追问：能同时用吗？**
→ 能，但没必要。混用会让「这次停到底是哪种中断」变得难判断。**统一用 `interrupt()` 更可控。**

## Q3. 中断后怎么恢复？恢复时传什么？

**答：**

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "refund-42"}}

# 第一次：跑到 interrupt 暂停
graph.invoke({"amount": 500}, config)

# 人工审批后恢复
graph.invoke(Command(resume={"approved": True, "reviewer": "张三"}), config)
```

关键点：

| 点 | 说明 |
|----|------|
| **传 `Command(resume=...)`** | 不是传新的业务输入。传普通 dict 会被当成「新输入」，不是恢复 |
| **同一个 `thread_id`** | 换 id 就找不到存档点，等于新开一条会话 |
| **传 `None` 也能续跑** | `invoke(None, config)` 用于静态断点；`interrupt()` 场景应传 `Command(resume=...)` |
| **恢复是幂等入口** | 前端要防重复提交，否则会重复恢复 |

**追问：`Command(resume=...)` 的值去哪了？**
→ 它成为 `interrupt()` 的**返回值**。所以节点里写 `decision = interrupt(...)`，恢复后 `decision` 就是 `{"approved": True, ...}`。

**追问：恢复时能同时更新状态吗？**
→ 能。`Command(resume=..., update={...})` 可以一边带回人工结果，一边改其他字段。但**不要用它替代正常的状态更新逻辑**，容易让状态来源变乱。

## Q4. 为什么恢复时节点会「从头重跑」？这会带来什么问题？

**答：**

因为 LangGraph 的恢复粒度是 **superstep**，不是「函数内的某一行」。框架只能定位到「这个节点没跑完」，不能定位到「停在第 37 行」。所以恢复时**整个节点函数重新执行**，`interrupt()` 这次直接返回 resume 值。

**带来的问题：`interrupt()` 之前的副作用会重复执行。**

```python
def bad_node(state):
    send_email(state["user"])        # ❌ 每次恢复都再发一次
    ok = interrupt("确认发送？")
    return {"sent": ok}
```

| 错误做法 | 后果 |
|---------|------|
| `interrupt()` 前发消息/扣款/写库 | 恢复时重复执行，用户收到两封邮件、扣两次款 |
| 用随机数/时间戳生成业务 id | 重跑后 id 变了，下游对不上 |
| 在 `interrupt()` 前调模型 | 重复计费 |

**正确做法**：

1. **把副作用移到 `interrupt()` 之后**，人工确认了再执行；
2. 必须在前面的，用**幂等键**（业务单号 + 唯一约束）去重；
3. 生成 id 的逻辑要**确定性**（由状态推导），不要用随机数。

**追问：这是不是框架的缺陷？**
→ 不是，是**有意的设计**。要精确到行级恢复，就得把函数拆成极细的节点，代价更大。框架选择了「节点级重跑 + 要求幂等」，这是分布式工作流的通用取舍。

## Q5. 人工要在暂停期间修改状态，怎么做？

**答：**

用 `update_state` 在恢复前改：

```python
graph.update_state(
    config,
    {"amount": 300, "note": "人工核减"},
    as_node="approval",
)
graph.invoke(Command(resume={"approved": True}), config)
```

`as_node` 决定「这次更新记在哪个节点名下」，影响下一轮激活判断：

| 写法 | 效果 |
|------|------|
| `as_node="approval"` | 视为 approval 节点的写入，后续按它的出边继续 |
| 不写 | 框架尝试推断，容易推错 |
| `as_node` 指向不存在的节点 | 报错 |

**常见用途**：

- 审批人改了金额/收件人；
- 外部系统回填了单号；
- 修正模型产出的错误参数，再让它继续执行。

**追问：改了状态后，原来的 `interrupt()` 还会返回旧值吗？**
→ 不会。恢复时传的 `Command(resume=...)` 才是 `interrupt()` 的返回值；`update_state` 改的是 State 字段。两者是不同通道，**别混着用**。

## Q6. 多级审批（初审 + 复审）怎么设计？

**答：**

两种模式：

**① 多个中断节点串行**

```python
builder.add_node("first_review", first_review)   # interrupt 一次
builder.add_node("second_review", second_review) # 再 interrupt 一次
builder.add_edge("first_review", "second_review")
```

清晰、易调试，适合固定两级。

**② 一个节点 + 循环 + 状态里的审批层级**

```python
class State(TypedDict):
    approval_level: int
    approvals: list

def review(state):
    decision = interrupt({"level": state["approval_level"]})
    return {
        "approvals": [decision],
        "approval_level": state["approval_level"] + 1,
    }

def next_step(state) -> str:
    return "review" if state["approval_level"] < 2 else "execute"
```

灵活，适合级数不固定或按金额动态决定级数。

| 模式 | 优点 | 缺点 |
|------|------|------|
| 多节点 | 流程可视化清晰 | 级数写死，改动要改图 |
| 循环 | 级数动态 | 图上看不出有几级，排查靠状态 |

**追问：并行会签（多人同时审批）怎么做？**
→ 用 `Send` 扇出多个审批任务，每个任务一个 `interrupt()`，汇总节点按 reducer 收集结果，再判断「全部通过 / 任一否决」。注意每个分支要带自己的审批人 id，否则恢复时分不清是谁。

## Q7. 中断一直没人处理怎么办？超时和取消怎么实现？

**答：**

LangGraph **没有内置的审批超时**，要自己在业务层做。

| 需求 | 做法 |
|------|------|
| **查待办** | `graph.get_state(config)`，`state.next` 非空 = 停在某处等恢复 |
| **超时提醒** | 定时任务扫「停在审批节点超过 N 分钟」的 thread，发通知 |
| **超时自动处理** | 定时任务写入 `Command(resume={"approved": False, "reason": "timeout"})`，走拒绝分支 |
| **取消** | 标记会话取消 + 清理/归档 checkpoint；不要直接删中间快照 |
| **人工撤回** | 从更早的 checkpoint 分叉，重新走流程 |

⚠️ **超时策略要写进业务规则**：是「超时视为拒绝」还是「超时升级到上级」，不能由技术侧默认。

**追问：能强杀一个正在跑的图吗？**
→ 同步调用只能靠超时中断；异步任务可以取消 task。但**强杀不会自动清理状态**，需要显式标记「已取消」，否则会留下永远停在中间的 thread。

## Q8. 生产环境做 HITL，最容易踩哪些坑？

**答：**

| 坑 | 现象 | 根因 | 解法 |
|----|------|------|------|
| **没挂 checkpointer** | 一调 `interrupt()` 就报错 | 没有存档点 | 编译时挂上，且用持久化后端 |
| **`thread_id` 变了** | 恢复后像是新会话 | 每次请求重新生成 id | id 由业务主键推导，全链路透传 |
| **恢复时传了新输入** | 图重新开始跑 | 没传 `Command(resume=...)` | 恢复入口单独一个 API |
| **副作用重复** | 重复发邮件/扣款 | 节点从头重跑 | 副作用后置 + 幂等键 |
| **`interrupt` 被 try/except 吞掉** | 不暂停，直接往下跑 | 用了宽泛的 `except Exception` | 不要包住 `interrupt()`；中断信号不是业务异常 |
| **重复恢复** | 同一审批被执行两次 | 前端重复点击/消息重投 | 恢复接口加幂等锁（按 thread_id + checkpoint_id） |
| **内存后端上生产** | 重启后待办全丢 | 用了 `InMemorySaver` | 生产必须 PG |
| **审批信息不全** | 人工看不到上下文，只能盲批 | `interrupt()` 只传了「要不要批准」 | 把关键字段、风险提示一起传出去 |

**追问：怎么防止「审批人和操作人串号」？**
→ 恢复接口必须校验：当前登录人是否在该 thread 的审批人列表里。`thread_id` 不是授权凭证，**授权要单独做**。
