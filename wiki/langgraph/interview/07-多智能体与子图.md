# 多智能体与子图

> **适用场景**：简历写了「多智能体系统」必问。面试官真正想确认的是：**你是真的拆了职责，还是把一个大 Prompt 拆成几个名字。**
> **主线**：多 Agent 的本质是**控制权在多个决策单元之间转移**，不是「多调几次模型」。

---

## Q1. 为什么需要多 Agent？单 Agent 不够吗？

**答：**

多 Agent 不是默认选项，**单 Agent 能做好就不要拆**。拆分的合理理由只有四类：

| 理由 | 说明 |
|------|------|
| **职责与工具集差异大** | 客服 Agent 只需要订单工具，运维 Agent 只需要部署工具；混在一起工具描述互相干扰，选择准确率下降 |
| **上下文隔离** | 每个 Agent 只带自己领域的知识，避免长上下文互相污染、token 成本失控 |
| **权限边界** | 高危操作（退款、删库）必须由独立 Agent 执行，便于加审批和审计 |
| **并行** | 多个子任务可以同时跑（多文档分析、多源检索） |

**不该拆的情况**：

- 只是 Prompt 太长 → 用分段提示或子流程，不需要多 Agent；
- 只是想让「回答更专业」→ 加检索或换模型，不需要多 Agent；
- 团队想显得架构先进 → 这是反模式。

**追问：拆多 Agent 的代价是什么？**
→ ① **延迟**：每次转交至少多一次模型调用；② **信息损耗**：handoff 时上下文被裁剪，接手方可能缺关键信息；③ **调试难度**：一条链路跨多个 Agent，出错定位成本高；④ **成本**：token 消耗成倍增加。

## Q2. Supervisor（主管）模式怎么实现？

**答：**

一个**中心调度节点**决定「下一步交给谁」，专家执行完回到主管：

```
            ┌──────────────┐
   ┌───────►│  Supervisor  │◄───────┐
   │        └──────┬───────┘        │
   │       ┌───────┼────────┐       │
   ▼       ▼       ▼        ▼       │
 research  coder  writer  ...  ─────┘
```

两种写法：

**① 条件边（显式，图上看得到）**

```python
def route(state) -> str:
    return state["next_agent"]        # research / coder / FINISH

builder.add_conditional_edges("supervisor", route, {
    "research": "research",
    "coder": "coder",
    "FINISH": END,
})
builder.add_edge("research", "supervisor")
builder.add_edge("coder", "supervisor")
```

**② `Command`（把决策和交接合一）**

```python
def supervisor(state) -> Command:
    decision = llm.with_structured_output(Route).invoke(state["messages"])
    return Command(goto=decision.next, update={"next": decision.next})
```

| 写法 | 优点 | 缺点 |
|------|------|------|
| 条件边 | 结构可视、易测 | 路由逻辑和节点分离 |
| `Command` | 决策与跳转原子化，适合 handoff | 图上看不出边，可读性下降 |

**追问：主管自己要不要有工具？**
→ 通常**不给**。主管只做路由，给了工具它会忍不住自己干活，导致职责混乱。**主管的职责是「分派 + 验收」，不是「执行」。**

## Q3. Swarm / handoff 模式是什么？和 Supervisor 有什么区别？

**答：**

**Swarm 是去中心化的交接**：Agent 之间直接转交控制权，没有中心调度。

```python
from langgraph.types import Command

def sales_agent(state) -> Command:
    if needs_technical_support(state):
        return Command(
            goto="tech_agent",
            update={"handoff_reason": "需要技术支持"},
            graph=Command.PARENT,      # 跳到父图里的另一个节点
        )
    return Command(goto=END, update={"reply": "..."})
```

| 维度 | Supervisor | Swarm |
|------|-----------|-------|
| 控制结构 | 中心化，星型 | 去中心化，网状 |
| 决策者 | 主管统一决定 | 当前 Agent 自己决定交给谁 |
| 跳转次数 | 每次都要回主管（2 跳） | 直接转交（1 跳） |
| 可预测性 | 高，路径集中 | 低，路径发散 |
| 适合 | 任务边界清晰、需要统一验收 | 对话式转接（客服分流）、链式协作 |

**追问：Swarm 最大的风险是什么？**
→ **互相踢皮球**。A 觉得该 B 处理，B 觉得该 A 处理，无限循环。必须加：最大交接次数、禁止回传标记、兜底人工。

## Q4. 层级（Hierarchical）模式怎么组织？

**答：**

**Supervisor 套 Supervisor**：顶层主管管几个「团队主管」，团队主管管自己的专家。

```
Top Supervisor
├── Research Team Supervisor
│   ├── Web Searcher
│   └── Doc Analyst
└── Engineering Team Supervisor
    ├── Coder
    └── Reviewer
```

实现方式：**把每个团队做成子图**，顶层把子图当节点。

```python
research_team = build_research_graph().compile()
builder.add_node("research_team", research_team)
builder.add_conditional_edges("top_supervisor", route, {
    "research_team": "research_team",
    "engineering_team": "engineering_team",
})
```

| 优点 | 缺点 |
|------|------|
| 每层只关心自己的子目标，上下文更小 | 层级越深，延迟和 token 成本越高 |
| 团队可独立开发/测试/复用 | 跨层信息传递容易丢 |
| 权限和预算可按团队隔离 | 调试要跨多个图看 |

**追问：什么时候该用层级，而不是扁平 Supervisor？**
→ 当专家数量超过 **5~7 个**、且能自然分组时。扁平主管的选择空间太大会降低路由准确率；分组后每层只做 3~5 选 1，准确率和可维护性都更好。

## Q5. 网络（Network）模式是什么？适合什么场景？

**答：**

**任意 Agent 之间都可以互相调用**，没有固定拓扑：

```
   A ◄────► B
   ▲  ╲  ╱  ▲
   │   ╳    │
   ▼  ╱  ╲  ▼
   C ◄────► D
```

实现上就是每个 Agent 都能通过 `Command(goto=...)` 跳到任意其他 Agent。

| 特点 | 说明 |
|------|------|
| 灵活性 | 最高，路径由运行时决定 |
| 可预测性 | 最低，同一输入可能走完全不同路径 |
| 调试 | 最难，需要完整的 trace 才能还原 |
| 适合 | 探索型任务、研究型协作、Agent 数量少（3~4 个） |

**追问：为什么生产很少用纯 Network？**
→ 因为**不可审计**。金融、医疗这类场景要求「同样的输入走同样的审批路径」，网络模式做不到。生产上通常用 Supervisor 做骨架，只在局部允许 handoff。

## Q6. Agent 之间的上下文怎么传？全量共享还是裁剪？

**答：**

三种策略，按隔离程度递增：

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **全量共享** | 所有 Agent 读写同一个 `messages` | 实现最简单，信息不丢 | 上下文爆炸、互相污染、成本高 |
| **任务摘要传递** | handoff 时只传「任务 + 关键结论」 | 上下文干净、成本可控 | 摘要会丢细节，接手方可能缺信息 |
| **独立 State + 显式契约** | 每个 Agent 自己的 State，父图做转换 | 隔离最好、可复用 | 设计成本高，跨 Agent 追踪难 |

生产推荐：**默认「任务摘要 + 必要原始数据引用」**。

```python
return Command(
    goto="coder",
    update={
        "task": "实现分页接口",
        "context_refs": ["doc:api-spec#3.2"],   # 大内容存外部，只传引用
        "constraints": ["不改数据库 schema"],
    },
)
```

**追问：为什么不全量共享 messages？**
→ 三个后果：① 每个 Agent 都要为别人的历史付 token；② 无关信息会干扰判断（检索 Agent 的原始文档对写代码没用）；③ 一旦某个 Agent 写入了错误结论，会污染后续所有 Agent。

## Q7. 怎么防止多个 Agent 之间无限委派、来回踢皮球？

**答：**

四道闸门，从业务到运行时：

| 闸门 | 做法 |
|------|------|
| **① 转移白名单** | 每个 Agent 只能转给固定的几个下游，不能任意跳 |
| **② 访问计数** | State 里记 `visited` / `hop_count`，超过阈值强制收口到人工或 `END` |
| **③ 禁止回传** | 记录「上一个 Agent」，不允许立刻原路退回（防 A→B→A→B） |
| **④ 预算控制** | 最大轮次、最大 token、最大耗时，任一超限即终止 |

```python
def guard(state) -> str:
    if state["hop_count"] > 6:
        return "human_escalation"
    if state["last_agent"] == state["next_agent"]:
        return "supervisor"        # 打回主管重新决策
    return state["next_agent"]
```

⚠️ **不要只靠 `recursion_limit`**。它能防死循环，但抛的是异常，用户拿到的是失败；业务闸门能给出「已转人工」的正常结果。

**追问：怎么发现线上正在踢皮球？**
→ 监控 handoff 次数分布。正常任务 1~3 次，出现大量 6 次以上的 thread，就是路由逻辑有问题（通常是两个 Agent 的职责边界没划清）。

## Q8. 子图和「多 Agent」是什么关系？是一回事吗？

**答：**

**不是一回事，但经常一起用。**

| 概念 | 本质 | 解决的问题 |
|------|------|-----------|
| **子图** | 结构封装机制：把一张图注册成节点 | 复用、分层、隔离状态 |
| **多 Agent** | 协作拓扑：多个决策单元转移控制权 | 职责分工、权限隔离、并行 |

关系：

- 子图**可以**用来实现多 Agent（每个 Agent 一张子图）；
- 子图**也可以**只是「把一段固定流程封装起来」，跟多 Agent 无关；
- 多 Agent **也可以**不用子图，全在一张扁平图里用 `Command` 跳转。

**判断标准**：如果子图内部有自己的**决策循环**（自己调模型、自己选工具），它是一个 Agent；如果只是固定几步数据处理，它只是一个子流程。

**追问：子图和多 Agent 一起用时，状态怎么设计？**
→ 父图存「任务级」信息（目标、验收标准、当前负责人），子图存「执行级」信息（中间结果、工具返回）。**跨边界只传必要字段**，不要把父图全量状态灌进子图。

## Q9. 多 Agent 系统最常见的失败模式有哪些？

**答：**

| 失败模式 | 表现 | 根因 | 对策 |
|---------|------|------|------|
| **职责重叠** | 两个 Agent 都能处理同一请求，互相推 | 边界没定义清楚 | 用「输入类型 + 工具集」明确唯一归属 |
| **上下文丢失** | 接手方反复问已经说过的信息 | handoff 裁剪过头 | 传结构化任务卡，而不是一句话 |
| **踢皮球** | 无限转交 | 无访问计数/白名单 | 四道闸门 |
| **主管失效** | 主管总是选同一个 Agent | 路由 Prompt 太弱/选项太多 | 结构化输出 + 减少候选 + few-shot |
| **成本失控** | 单请求几十次模型调用 | 每个 Agent 都带全量历史 | 上下文隔离 + 预算上限 |
| **错误放大** | 上游结论错了，下游全部基于它执行 | 没有验收环节 | 关键节点加校验/人工复核 |
| **不可复现** | 同样输入结果差异大 | 网络模式 + 高温度 | 固定路由 + 降温度 + 记录 trace |

**追问：如果只能改一处来提升多 Agent 稳定性，改哪里？**
→ **收窄每个 Agent 的职责和工具集**。大部分多 Agent 问题不是编排框架的问题，而是「一个 Agent 干了太多事」。职责清晰后，路由准确率和输出稳定性都会明显改善。
