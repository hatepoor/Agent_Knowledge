# Skills 渐进加载

> **什么时候该读**：⭐ 这是你**简历上最独特的亮点**——大多数候选人只有 MCP 和工具调用，没有 Skills 系统。
> 完整机制在 [[agent/skills/Skills]]。

## 面试定位

⚠️ **Skills 是相对新的概念**（Deep Agents / Claude Skills 一脉）。能讲清它，直接体现「你在跟进前沿且做过生产实践」。

**这题的价值**：它同时考察 ① 上下文工程理解；② 架构设计能力；③ 工程落地能力。

---

## 一、标准答法（30 秒版）

> Skills 是「**按需加载的知识/能力包**」：每个 Skill 是一个带元信息的 Markdown 文档（`SKILL.md`），Agent 先只看**名称和摘要**，判断需要哪个后再加载完整内容。

**必须展开的核心**（否则只是复述）：

| 点 | 内容 |
|---|---|
| ① 解决什么问题 | ⭐ **上下文窗口有限**。100 个工具的完整定义会撑爆 prompt |
| ② 怎么渐进 | ⭐ **三层：列表（名字+摘要）→ 选中后加载全文 → 执行时按需引用资源** |
| ③ 和工具的区别 | ⭐ **工具是「能做」，Skills 是「知道怎么做」** |

---

## 二、⭐ 三层加载模型（这是精华）

```
第 1 层：列表
  ┌────────────────────────────────────────┐
  │ skills:                                  │
  │  - code-review: 代码审查规范与清单        │  ← 只有名字 + 一句话摘要
  │  - sql-optimize: SQL 优化方法论          │     （几十 token）
  │  - rag-eval: RAG 评估流程               │
  └────────────────────────────────────────┘
                    ↓ 模型判断「需要 rag-eval」
第 2 层：加载全文
  ┌────────────────────────────────────────┐
  │ SKILL.md 完整内容（几千 token）           │
  │  - 适用场景                              │
  │  - 执行步骤                              │
  │  - 注意事项                              │
  │  - 关联资源引用                          │
  └────────────────────────────────────────┘
                    ↓ 执行中需要具体资源
第 3 层：按需引用
  ┌────────────────────────────────────────┐
  │ scripts/checklist.md                     │
  │ references/metrics.md                   │
  └────────────────────────────────────────┘
```

⭐ **关键数字感**：第 1 层可能只花几百 token 就能让模型「知道有哪些能力可用」；如果不用渐进加载，把 20 个 Skill 全文塞进去要几万 token。

⚠️ **追问：「这和 RAG 检索有什么区别？」**
→ ⭐ **Skills 是「人写好、结构化、可信的」，RAG 是「检索出来的、可能噪声大的」。** Skills 的本质是**上下文工程**，不是检索。
→ ⭐ 也可以答：Skills 的「第 1 层」类似 RAG 的检索（按需召回），但第 2/3 层是**确定性加载**，不是相似度匹配。

⚠️ **追问：「和 MCP 什么关系？」**
→ ⭐ **互补，不替代**：
| | MCP | Skills |
|---|---|---|
| 提供 | **能力**（能调什么） | **知识**（该怎么做） |
| 形式 | 工具/资源/提示词 | Markdown 文档 |
| 加载 | 全量注册工具 schema | ⭐ **渐进加载** |
| 典型 | 查数据库、调 API | 代码审查规范、SOP |

## 三、你项目里的实践（⭐ 重点讲这段）

按 memory 记录，你已建成**生产级 Agent Skills 系统**，采用 `list_skills` / `load_skill` 渐进加载模式（与 Deep Agents 的 `SKILL.md` 加载方式一致），并支持 skills/MCP/RAG/长短记忆接入。

**建议这样讲**（⚠️ 具体实现请按实际调整）：

```
「我的 Agent 系统有个 Skills 子系统，解决的是「能力太多但上下文有限」
的问题。

架构：
① 每个 Skill 是一个目录，里面有 SKILL.md（含 frontmatter：name、
   description、适用场景）和可选的 scripts/、references/。
② Agent 有两个元工具：list_skills 只返回 name + description（几十
   token），load_skill 按名字加载完整 SKILL.md。
③ 模型先 list，判断需要哪个，再 load——这就是渐进加载。

为什么不用 MCP 做这件事：MCP 的工具定义是静态 schema，加载即全量。
而 Skills 的内容是「方法论」，可能几千字，且不是每次都需要。

效果：Agent 能挂 20+ 个 Skill 而上下文不爆炸。如果要全量加载，
prompt 会多出几万 token，既慢又贵，还会稀释注意力。」
```

⭐ **最后那句「稀释注意力」是加分点**——它说明你理解「上下文不是越多越好」。

## 四、设计上的三个关键决策（会被追问）

### 决策 1：Skill 的粒度

| 粒度 | 问题 |
|------|------|
| 太粗 | 加载后大部分内容用不上，浪费 token |
| 太细 | 列表本身变长，模型选不准 |
| ⭐ **合适** | ⭐ **一个 Skill 解决一类任务**，且 `description` 能明确区分边界 |

⚠️ **实践建议**：`description` 里写清「**什么时候不该用**」——这对模型的选择准确率提升最明显。

### 决策 2：什么时候该用 Skills 而不是工具

| 用 Skills | 用工具 |
|-----------|--------|
| 内容是多步方法论 | 单次确定性调用 |
| 需要模型「读懂再决定」 | 参数明确、直接执行 |
| 更新频繁（改文档即可） | 要改代码 |
| ⭐ **「知道怎么做」** | ⭐ **「能做」** |

### 决策 3：Skill 之间怎么组合

⚠️ **追问「一个任务需要多个 Skill 怎么办？」**

| 方案 | 优劣 |
|------|------|
| 全部加载 | ⭐ 简单但上下文膨胀 |
| 模型自己逐个 load | 灵活但可能漏 |
| ⭐ **Skill 里显式声明依赖** | ⭐ 加载 A 时提示「还需要 B」 |

## 五、高频追问速查

| 追问 | 答法要点 |
|------|---------|
| Skills 解决什么问题？ | ⭐ **上下文有限 + 能力数量多** 的矛盾 |
| 渐进加载的三层？ | 列表（摘要）→ 全文 → 按需资源 |
| 和 RAG 的区别？ | ⭐ **Skills 是确定性的人写知识，RAG 是相似度检索** |
| 和 MCP 的关系？ | ⭐ 互补：MCP 给能力，Skills 给知识 |
| Skill 粒度怎么定？ | ⭐ 一个 Skill 一类任务；description 写清边界 |
| 什么时候用 Skills 不用工具？ | ⭐ 「知道怎么做」vs「能做」 |
| 多个 Skill 怎么组合？ | 显式声明依赖，或模型逐个 load |
| 怎么评估 Skill 被选对了？ | ⭐ 记录「list → load → 是否真的用到」的转化率 |
| 全文加载一次多少钱？ | ⭐ 取决于 SKILL.md 大小；这正是渐进加载要省的 |
