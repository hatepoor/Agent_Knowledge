# Agent 专项高频追问与答法

> **什么时候该读**：⭐ **面试前最后一天只看这一篇。** 前面四篇是「知识点」，这篇是「弹药库」。

## 使用方式

⚠️ **每条的格式是「问题 → 及格答案 → 加分答案」。** 目标是答到「加分」那层。

**评分标准**：
- **及格**：说清了定义
- **良好**：说清了「为什么」和权衡
- ⭐ **加分**：说清了「我项目里怎么做的 + 踩过什么坑」

---

## 一、原理类

### Q：Agent 和普通 LLM 调用的本质区别？

**及格**：Agent 能调工具、能多轮。
**加分**：⭐ **普通调用是「一次映射」，Agent 是「感知-决策-行动-观察的闭环」。** 关键是：① 有环境反馈（工具结果）；② 有状态（跨轮记忆）；③ 有终止条件（不是固定轮数）。

### Q：为什么模型不能自己执行工具？

**及格**：模型只会生成文本。
**加分**：⭐ **这是安全边界。** 模型输出必须由框架校验后才执行——否则模型幻觉出一个「删除数据库」的调用就危险了。生产里还要加**权限校验 + 人工审批**（敏感操作）。

### Q：Function Calling 和 ReAct 的关系？

**及格**：FC 是底层机制，ReAct 是上层范式。
**加分**：⭐ **FC 解决「怎么让模型结构化地请求工具」，ReAct 解决「什么时候请求、请求了之后怎么办」。** FC 是单轮的，ReAct 是多轮闭环。

### Q：上下文窗口满了怎么办？

**及格**：压缩历史。
**加分**：⭐ **四层手段，按优先级：**
1. ⭐ **外置**：关键信息放 Store，不靠上下文传递
2. ⭐ **摘要**：SummarizationMiddleware 压缩早期历史
3. ⭐ **裁剪**：只保留最近 N 轮 + 系统提示
4. **分片**：超长任务拆成多个子会话

⚠️ **追问「摘要丢细节怎么办？」** → 关键信息外置，不指望摘要。

### Q：怎么评估一个 Agent 好不好？

**及格**：看任务完成率。
**加分**：⭐ **五个维度：**
| 维度 | 指标 |
|------|------|
| 效果 | 任务完成率、答案正确率 |
| 效率 | 平均步数、token 消耗 |
| 稳健 | 工具失败恢复率、超时率 |
| 安全 | 危险操作拦截率、越权率 |
| 体验 | 首字延迟、总时长 |

⚠️ **「只看最终答案」是常见误区**——步数效率和经济性同样重要。

## 二、工程类（⭐ 你的强项）

### Q：多智能体怎么分工？

**及格**：Supervisor 模式，一个编排 Agent 派活。
**加分**：⭐ **三种模式 + 选型：**
| 模式 | 适用 |
|------|------|
| ⭐ **Supervisor** | 中心化调度，任务可明确拆分 |
| **Network** | 对等协作，需要协商 |
| **Hierarchical** | 层级管理，大规模 |

**接着说你的实践**：用 StateGraph 做编排节点 + 专家节点，专家内部各自 ReAct。

📌 [[agent/patterns/MultiAgent协作]]

### Q：多智能体一定要用框架吗？自己写行不行？

**及格**：可以，但要自己实现状态管理和恢复。
**加分**：⭐ **原型可以；生产不行。** 理由是四个「生产必需」：中断恢复、并发扇出、人工介入、可观测。这四个自己写成本极高。

### Q：Agent 跑偏了怎么办？

**加分答案（四层）：**
1. **预防**：强 system prompt（写清边界和禁止事项）+ `recursion_limit`
2. **检测**：⭐ **相同 tool_call 连续 N 次 → 主动中断**（这是无限循环的最强信号）
3. **兜底**：工具返回可读错误，让模型自己纠偏，而不是抛异常
4. **兜底再兜底**：人工介入点（HITL）

### Q：流式有什么用？怎么实现？

**加分答案：**
- **用户体验**：实时看到思考过程，长任务不焦虑
- **工程价值**：⭐ **长任务不超时**（HTTP 网关通常 30s~60s 超时）
- 三种模式：`values`（全量状态）/ `messages`（增量消息，⭐ 最常用）/ `custom`（自定义）

📌 [[langchain/streaming/流式传输]]

### Q：怎么做人工介入（HITL）？

**加分答案**：⭐ **LangGraph 的 `interrupt()` + `Command(resume=...)`。**
```
① 敏感操作前 interrupt() → 状态持久化，进程可退出
② 人工审批（Web UI / IM）
③ 用同 thread_id + Command(resume=决策) 恢复
```
⚠️ **关键**：中断后**进程可以退出**——这是和「阻塞等待」的本质区别。

📌 [[langgraph/modules/langgraph_human_in_loop/interrupt机制]]

### Q：模型选型怎么考虑？

**加分答案（四个维度）：**
| 维度 | 考虑 |
|------|------|
| 能力 | 工具调用准确率、长上下文、指令遵循 |
| 成本 | 输入/输出单价、缓存命中率 |
| 延迟 | 首 token、总时长 |
| 可用性 | 限流、SLA、降级方案 |

**实践**：⭐ **主模型 + 备用模型**（`ModelFallbackMiddleware`），或按任务难度路由（简单任务用小模型省钱）。

## 三、场景设计题（⭐ 最拉差距）

### Q：「设计一个能查数据库的 Agent」

**答题骨架（⭐ 六步，按顺序说）：**

1. **澄清需求**：⭐ **先问**——查什么库、谁能用、要不要写操作、并发多大
2. **安全边界**：只读账号（最小权限）；⚠️ **禁止 DDL/DML**；SQL 白名单或参数化
3. **工具设计**：不是「执行任意 SQL」，而是**语义化工具**（`get_user_orders(user_id)`）——⭐ **收窄能力面**
4. **Schema 感知**：把表结构注入上下文（或提供 `describe_table` 工具）
5. **结果处理**：大结果集要分页/截断，别把一万行塞进上下文
6. **可观测**：记录每条 SQL + 耗时 + 返回行数

⚠️ **最常见的错误答案**：直接给一个 `execute_sql(sql)` 工具。⭐ **那是把数据库暴露给 LLM。**

### Q：「Agent 调用一直很慢，怎么排查？」

**答题骨架（按顺序）：**
1. **定位是哪一段慢**：模型调用？工具执行？序列化？
2. **模型侧**：prompt 长度（上下文膨胀）、模型选型、是否可流式
3. **工具侧**：工具内部 IO、N+1 查询、缺索引
4. **框架侧**：⭐ **是否每轮都重建连接/重新拉 Schema**
5. **优化**：缓存（LLM 响应缓存、Schema 缓存）、并行工具调用、减少轮数

### Q：「怎么防止 Agent 被提示词注入？」

**加分答案：**
- ⭐ **权限最小化**：注入成功也做不了坏事（只读账号、无敏感工具）
- ⭐ **输出校验**：Agent 的输出/行动要过策略检查
- **隔离**：不可信内容（网页、用户输入）与指令分离
- ⚠️ **根本难点**：LLM 分不清「指令」和「数据」，所以**不能只靠 prompt 防**

## 四、反问环节（⭐ 你也该提问）

⚠️ **面试结尾「你有什么问题」是加分项，不要问薪资福利。**

| 好问题 | 为什么好 |
|--------|---------|
| 「团队目前 Agent 落地最大的瓶颈是什么？」 | 体现你在想真问题 |
| 「Agent 的评估体系是怎么建的？」 | 体现你知道评估难 |
| 「 Skills / MCP 这块有在用吗？」 | 体现你关注前沿且可切入你的亮点 |
| 「这个岗位是偏平台基建还是业务落地？」 | 体现你在想匹配度 |
