# 分块与检索策略

> **什么时候该读**：RAG 岗面试**最容易被深挖的一题**。答「按 512 切」= 没调过参数。
> 完整机制在 [[rag/03_智能分块/文档分块策略]]。

## 面试定位

⚠️ **分块是 RAG 里「最影响效果又最容易被想当然」的环节。** 这题能区分「看过 demo」和「调过系统」。

---

## 一、分块：三种策略 + 选型

### 三种主流策略

| 策略 | 做法 | 优点 | ⚠️ 缺点 |
|------|------|------|---------|
| **固定长度** | 按 token/字符数切 + overlap | 简单、可控 | ⚠️ **切断语义**（一句话切两半） |
| **结构感知** | 按标题/段落/列表边界切 | ⭐ **保留语义完整** | 依赖文档结构质量 |
| **语义分块** | 按 embedding 相似度突变点切 | ⭐ 语义最完整 | 计算成本高 |

### ⭐ 选型决策（这是加分点）

```
文档结构清晰（有标题层级）？
  ├─ 是 → ⭐ 结构感知分块
  └─ 否 → 文档量大吗？
            ├─ 是（>10万篇）→ 固定长度（成本可控）
            └─ 否 → 语义分块（效果优先）
```

### 块大小怎么定（必被追问）

**标准答案**：⭐ **没有普适最优值，但有推理过程：**

| 因素 | 影响 |
|------|------|
| **Embedding 模型上限** | 通常 512 token，超了要截断 |
| **语义完整性** | 块要能独立表达一个意思 |
| **检索精度** | 块越大，召回越准但噪声越多 |
| **上下文预算** | top-k 个块 + prompt 要塞进窗口 |

⭐ **常用起点：512 token、overlap 50~100（10~20%）。**

⚠️ **追问「overlap 有什么用？」**
→ ⭐ **缓解「语义被切断」**——一个观点跨块时，overlap 让它至少在一块里完整。代价是索引体积增大（overlap 20% ≈ 体积 +20%）。

⚠️ **追问「怎么验证块切得好不好？」**
→ ⭐ **抽 20~50 个块人工看**：是否语义完整、是否混入噪声（页眉页脚）、是否切断表格。

## 二、四种特殊内容（⭐ 拉差距的地方）

⚠️ **「我按 512 切」之外，能说出特殊内容的处理才是真做过。**

| 内容 | 问题 | 处理 |
|------|------|------|
| ⭐ **表格** | 按行切会把表头和数据切开，语义全毁 | ⭐ **整块保留不切** + 表头前置 |
| ⭐ **代码** | 按字符切会切断函数 | ⭐ **按 AST/语法边界切** |
| ⭐ **列表** | 切断列表丢层级 | 尽量整块，或带上下文标题 |
| ⭐ **图片** | 纯文本流直接丢 | ⭐ **提取 + 视觉模型描述化** |

### 表格处理（⭐ 你项目里的重点）

**「摘要 + 原表」双轨**：
```
① 表格上方生成一段文字摘要（「下表列出了 2024 年各季度销售额，Q1 最高」）
② 表格本身整块保留
③ 检索时摘要参与匹配，命中后返回完整表格
```
⭐ **为什么**：表格的向量表示效果差（数字密集、无语义），摘要让它能被检索到。

## 三、检索：从单路到混合

### 三种检索方式

| 方式 | 原理 | 强 | 弱 |
|------|------|-----|-----|
| ⭐ **稠密（向量）** | query/doc 分别 embedding，算余弦相似度 | ⭐ **语义泛化**（「怎么退款」能匹配「退货流程」） | ⚠️ **精确匹配弱**（SKU、型号、专有名词） |
| ⭐ **稀疏（BM25）** | 词频 + 逆文档频率 | ⭐ **精确匹配强** | 无语义（同义词召回不了） |
| **混合** | 两路结果融合 | ⭐ 互补 | 复杂度高 |

### 融合：RRF（必答）

**公式**：
```
RRF(d) = Σ  1 / (k + rank_i(d))
         i
```
- `rank_i(d)`：文档 d 在第 i 路检索里的排名
- `k`：常数（通常 60）

⭐ **为什么用 RRF 而不是加权平均**：⚠️ **不同检索的分数不可比**（向量的余弦相似度和 BM25 的分数量纲不同），但**排名可比**。RRF 只用排名，不用调权重。

## 四、查询侧优化（⭐ 加分项）

⚠️ **大多数人只优化索引侧，查询侧是区分点：**

| 技术 | 作用 |
|------|------|
| ⭐ **查询改写** | 把口语化问题改成检索友好的形式 |
| **查询扩展** | 同义词、相关词（提升召回） |
| ⭐ **HyDE** | 让模型先「虚构一个答案」，用这个答案去检索（假设性问题有效） |
| **多查询** | 生成 N 个角度的查询，分别检索后融合 |
| **路由** | 判断该查哪个知识库/该不该查 |

⚠️ **追问「HyDE 为什么有效？」**
→ ⭐ **问题的向量和答案的向量分布不同**（「怎么退款」vs「退款需在 7 天内申请」）。用一个虚构答案检索，相当于「用答案的语言去找答案」。

## 五、上下文构建（⭐ 最容易被忽略）

⚠️ **检索到 top-k 不等于直接把它们拼进 prompt：**

| 问题 | 处理 |
|------|------|
| 顺序 | ⭐ 重要的放前面/后面（中间易被忽略，「lost in the middle」） |
| 冗余 | 去重、合并相邻块 |
| 超长 | 截断或二次摘要 |
| ⭐ 溯源 | 每个块带来源元数据，生成时要引用 |

⚠️ **追问「lost in the middle 是什么？」**
→ ⭐ **LLM 对长上下文中间部分的内容利用不充分**。所以 top-1 别放中间，或控制上下文长度。

## 六、高频追问速查

| 追问 | 答法要点 |
|------|---------|
| 块大小怎么定？ | ⭐ 512 起点，按语义完整性和上下文预算权衡 |
| overlap 的作用？ | ⭐ 缓解语义切断，代价是体积 +20% |
| 三种分块怎么选？ | 结构清晰→结构感知；量大→固定；量小效果优先→语义 |
| 表格怎么处理？ | ⭐ 整块不切 + 表头前置 + 摘要双轨 |
| 为什么混合检索？ | ⭐ 向量弱在精确匹配，BM25 弱在语义 |
| RRF 为什么比加权好？ | ⭐ 分数不可比但排名可比，且不用调权重 |
| HyDE 为什么有效？ | ⭐ 问题和答案的向量分布不同 |
| 检索到就完事了吗？ | ⭐ 不是，还有顺序、去重、截断、溯源 |
| lost in the middle？ | ⭐ LLM 对长上下文中间部分利用不充分 |
| 怎么验证分块质量？ | ⭐ 抽样人工看：语义完整、无噪声、表格没切断 |
