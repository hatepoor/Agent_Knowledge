# RAG 全流程问答

> **什么时候该读**：RAG 岗面试第一题。答「检索+生成」是及格线以下。
> 完整机制在 [[rag/00_导览与基础/RAG基础与演进全景]]。

## 面试定位

⚠️ **这题考察：① 懂不懂全流程（不只是「向量检索」）；② 知不知道每层的坑；③ 有没有做过评估。**

---

## 一、标准答法（30 秒版）

> RAG 是「**检索增强生成**」：用户提问时先从知识库检索相关内容，拼进 prompt 让模型基于**检索到的内容**回答，而不是只靠模型参数里的知识。

**必须展开的三点**：

| 点 | 内容 |
|---|---|
| ① 解决什么问题 | ⭐ **模型的知识截止、幻觉、无法访问私有数据** |
| ② 核心流程 | ⭐ **解析 → 清洗 → 分块 → 索引 → 检索 → 重排 → 生成** |
| ③ 关键认知 | ⭐ **「垃圾进，垃圾出」——检索质量决定上限，生成只是下限** |

---

## 二、七步流程（⭐ 这是骨架，必须能画出来）

```
① 文档解析     docling 解析 PDF/DOCX/HTML → 结构化元素
       ↓
② 数据清洗     Unicode 规范化、去噪（页眉页脚）、去重、脱敏
       ↓
③ 智能分块     固定/结构感知/语义/父子分块 + overlap
       ↓
④ 索引构建     Embedding → 向量索引（+ 可选 BM25 稀疏索引）
       ↓
⑤ 查询处理     查询改写/扩展/HyDE/多查询
       ↓
⑥ 混合检索     稠密（向量）+ 稀疏（BM25）→ RRF 融合
       ↓
⑦ 重排 + 生成   Cross-Encoder 精排 → 拼上下文 → LLM 生成 → 溯源引用
```

⭐ **每步说一个「你踩过的坑」**，整段回答就有血有肉了。

📌 各步详解：[[rag/README]] · [[docling/README]] · [[rag/03_智能分块/文档分块策略]]

## 三、每层的高频追问

### 追问 1：为什么要分块？不分行不行？

**加分答案**：⭐ 三个原因
1. **上下文窗口有限**：一篇 10 万字的文档塞不进去
2. **Embedding 有长度上限**：且长文本的向量会「稀释」主题
3. ⭐ **检索粒度**：块太大 → 检索到但包含大量无关内容；块太小 → 语义不完整

⚠️ **接着必被问**：「块大小怎么定？」→ 见 [[interview/03-RAG专项/分块与检索策略]]

### 追问 2：为什么需要混合检索？纯向量不行吗？

**加分答案**：⭐ **向量检索弱在「精确匹配」**——
- 用户搜「iPhone 15 Pro Max 256G」，向量检索可能召回「手机选购指南」（语义近但不含这个 SKU）
- ⭐ **BM25 擅长词精确匹配，向量擅长语义泛化**。两者互补
- 融合方式：**RRF（Reciprocal Rank Fusion）**，不用调权重

📌 [[rag/06_混合检索/混合检索]]

### 追问 3：重排（Rerank）是必要的吗？

**加分答案**：⭐ **召回 50~100 条后，用 Cross-Encoder 精排到 top 5。**
- **为什么**：向量检索是「双塔」（query 和 doc 分别编码，无法精细交互）；Cross-Encoder 把 query+doc 拼一起过模型，精度高但慢
- ⭐ **「先粗后排」是标准范式**——用速度换精度

### 追问 4：怎么评估 RAG 好不好？

**加分答案**：⭐ **两个层面，不能只用一个：**

| 层面 | 指标 | 工具 |
|------|------|------|
| ⭐ **检索质量** | Recall@K、Precision@K、MRR、NDCG | ragas 的 `context_recall` / `context_precision` |
| ⭐ **生成质量** | 忠实度（faithfulness）、答案相关性、有根据性 | ragas 的 `faithfulness` / `answer_relevancy` |

⚠️ **「只看最终答案准不准」是常见误区**——⚠️ **如果检索就没召回对的内容，生成再好也没用。必须分层评估。**

📌 [[rag/12_评估与监控/评估体系与RAGAS]]

### 追问 5：RAG 有什么局限性？

⭐ **这题能体现你是否真做过：**

| 局限 | 说明 |
|------|------|
| **多跳推理** | 需要综合多个文档的推理，单轮检索不够 |
| **全局性问题** | 「这份文档主要讲了什么」——不是检索能答的 |
| **时效性** | 索引不更新就答旧知识 |
| **表格/图片** | ⚠️ 纯文本切块会丢结构，需要专门处理 |
| **长文档连贯性** | 分块切断上下文，答案可能前后矛盾 |

## 四、你项目里的实践（⭐ 按 memory 记录组织）

你的 RAG 系统用了：**docling 解析 + chunking 策略 + ragas 评估 + PG 向量库**。

**建议这样讲**（⚠️ 具体参数请按实际调整）：

```
「我做的 RAG 重点是解析和评估两头，因为这两头最容易被忽略但最影响效果。

解析侧：用 docling 处理 PDF/DOCX。关键痛点是 DOCX 里的图片和表格——
纯文本抽取会把表格打成乱码、图片直接丢。docling 的元素层能保留
表格结构，图片可以单独提取后走视觉描述。

分块侧：按文档结构做结构感知分块，而不是定长切。表格整块保留不切，
避免切断表头。

评估侧：用 ragas 建了检索和生成两层的评估。发现过一个典型问题——
context_recall 高但 faithfulness 低，说明检索到了但模型没用上，
根因是拼进 prompt 的上下文太长、关键内容被稀释了。后来做了重排 +
上下文裁剪。」
```

⭐ **「发现过 context_recall 高但 faithfulness 低」这种具体案例，比任何理论都有说服力。**

⚠️ **如果实际没遇到这个问题，不要编**——换成你真实遇到过的问题。

## 五、高频追问速查

| 追问 | 答法要点 |
|------|---------|
| RAG 解决什么问题？ | ⭐ 知识截止、幻觉、私有数据 |
| 完整流程几步？ | ⭐ 解析→清洗→分块→索引→检索→重排→生成 |
| 块大小怎么定？ | 512 是常用起点，按「语义完整性」和「检索精度」权衡 |
| 纯向量为什么不够？ | ⭐ 弱在精确匹配，要混合 BM25 |
| 重排必要吗？ | ⭐ 召回 50~100 后精排到 top 5，速度换精度 |
| 怎么评估？ | ⭐ 检索层（recall/precision）+ 生成层（faithfulness）分层评 |
| RAG 的局限？ | 多跳推理、全局性问题、时效性、表格图片、长文档连贯 |
| Embedding 模型怎么选？ | 多语言场景选中英文均衡的；注意维度（影响存储）和上下文长度 |
| chunk overlap 有什么用？ | ⭐ 缓解「语义被切断」，但增大索引体积 |
| 怎么处理表格？ | ⭐ 整块保留 + 表头前置 + 摘要+原表双轨 |
