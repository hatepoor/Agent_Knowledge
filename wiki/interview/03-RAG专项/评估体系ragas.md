# 评估体系 ragas

> **什么时候该读**：⭐ RAG 岗面试**最能体现工程成熟度的一题**。大多数人答不出评估怎么做。
> 完整机制在 [[rag/12_评估与监控/评估体系与RAGAS]]。

## 面试定位

⚠️ **「你做过 RAG 评估吗」这个问题，会的人不到三成。** 答好直接体现：你不是跑了个 demo，是真的在优化效果。

---

## 一、标准答法（30 秒版）

> RAG 评估必须**分两层**：**检索层**看「该检索到的是否检索到了」，**生成层**看「基于检索内容答得对不对、有没有编」。我用 ragas 做了这两层的自动化评估。

**必须展开的**：

| 点 | 内容 |
|---|---|
| ① 为什么分层 | ⭐ **检索没召回 → 生成再好也没用；检索对了 → 生成可能不用或瞎编** |
| ② 怎么评 | ⭐ **无参考（LLM-as-Judge）为主**，不依赖人工标注 |
| ③ 关键实践 | ⭐ **建 Golden Set（问题+标准答案+应检索的文档）** |

---

## 二、两层指标体系（⭐ 必须背下来）

### 检索层

| 指标 | 衡量什么 | 低说明什么 |
|------|---------|-----------|
| ⭐ **`context_recall`** | 应检索的文档是否被检索到 | 分块/检索策略有问题 |
| ⭐ **`context_precision`** | 检索到的文档有多少是相关的 | 检索精度差，prompt 被稀释 |
| `context_relevancy` | 检索内容与问题的相关度 | 同上 |

### 生成层

| 指标 | 衡量什么 | 低说明什么 |
|------|---------|-----------|
| ⭐ **`faithfulness`** | 答案是否忠于检索内容（不编） | ⚠️ **幻觉** |
| ⭐ **`answer_relevancy`** | 答案是否切题 | 跑题/啰嗦 |
| `answer_correctness` | 与标准答案的一致度 | 需要标注答案 |

⚠️ **必答的组合判断**（⭐ 这是工程经验）：

| context_recall | faithfulness | 诊断 |
|:---:|:---:|---|
| 高 | 高 | ✅ 健康 |
| 高 | ⚠️ **低** | ⭐ **检索到了但模型没用上** → prompt 太长/关键内容被稀释/需要重排 |
| ⚠️ **低** | 高 | ⭐ **没检索到但模型答对了** → 靠模型自身知识，检索系统没贡献 |
| 低 | 低 | ❌ 检索和生成都有问题 |

⭐ **「高 recall 低 faithfulness」是最有价值的诊断**——它精确定位问题在「上下文构建」而不在检索。

---

## 三、ragas 的工作方式（会被追问原理）

### 核心思路：LLM-as-Judge

```
① 准备：问题 + 检索到的 contexts + 生成的 answer
       ↓
② 用另一个 LLM（judge）按指标定义打分
       ↓
③ 聚合输出 0~1 的分
```

⚠️ **追问：「LLM 打分可靠吗？」**
→ ⭐ **有噪声，但比没有好。** 三个缓解：① 固定 judge 模型和 prompt；② 多样本取平均；③ **关键指标抽样人工校验**（校准 judge 的偏差）。

### 数据准备：Golden Set

```
问题        应检索到的文档（可选）    标准答案（可选）
─────────────────────────────────────────────────
「怎么退款？」 doc_023, doc_087        7 天内可申请，原路退回
```

⭐ **这是评估的地基。** 没有 Golden Set 就没有基线，改了分块参数也说不清是变好还是变坏。

⚠️ **Golden Set 从哪来**：① 真实用户问题（最好）；② 让领域专家写；③ ⚠️ **用 LLM 从文档反向生成问题**（快但可能有偏差，要人工筛）。

## 四、你项目里的实践（⭐ 按 memory 记录组织）

你的 RAG 用 ragas 评估检索质量。

**建议这样讲**（⚠️ 具体数值请按实际调整，不要编）：

```
「我用 ragas 建了离线的分层评估。

流程：
① 先建 Golden Set——从真实使用场景里挑问题，标出应该检索到的文档。
② 一次改动跑一轮评估，对比 context_recall / context_precision /
   faithfulness 三个核心指标。
③ 只看单一指标会误判，所以我看组合。比如如果 recall 高但
   faithfulness 低，问题不在检索而在上下文构建。

最有价值的一次发现：【此处填你真实遇到过的问题和根因】。

另外，离线评估之外还上了在线监控——检索为空率、用户点「没有帮助」
的比例，这些是离线覆盖不到的真实信号。」
```

⚠️ **再次强调**：方括号处必须填**你真实遇到的**。没有就删掉那句，不要编。

## 五、评估的三个常见误区（⭐ 加分）

| 误区 | 为什么错 |
|------|---------|
| ❌ **只看答案准不准** | ⭐ **不分层就定位不了问题**——是检索的错还是生成的错？ |
| ❌ **没有基线** | ⭐ **改了半天不知道是变好还是变坏**。必须有 Golden Set |
| ❌ **只做离线评估** | ⭐ **离线覆盖不了真实分布**。要加在线信号（检索空结果率、用户反馈） |

## 六、高频追问速查

| 追问 | 答法要点 |
|------|---------|
| 为什么评估要分两层？ | ⭐ **检索错和生成错要分开定位** |
| `faithfulness` 低说明什么？ | ⭐ **幻觉**——答案里有检索内容不支持的部分 |
| recall 高但 faithfulness 低？ | ⭐ **检索到了没用上** → 上下文构建问题 |
| recall 低但答案对？ | ⭐ **靠模型自身知识**，检索系统没贡献 |
| Golden Set 从哪来？ | 真实问题 > 专家写 > LLM 反向生成（要人工筛） |
| LLM 打分可靠吗？ | ⭐ 有噪声；固定 judge + 多样本平均 + 关键指标人工校准 |
| 离线评估的局限？ | ⭐ 覆盖不了真实分布，要配在线信号 |
| 怎么定位一次效果回退？ | ⭐ 对比两层指标 + 看是哪个指标掉的 |
