# 项目三：个人知识库

> ⚠️ **本页是「讲项目的骨架」。** 所有 `【待补充】` 必须由你填真实数据。
>
> ⭐ **这个项目最容易被低估。** 它其实同时是「LLM 应用 + 知识管理 + 工具链建设」三个能力的证明。

---

## 一、简历描述

### 一句话版

> 基于 LLM Wiki 方法论的个人知识库系统，三层架构（raw/wiki/schema）+ 自动化质量校验，沉淀 672 页跨 16 个技术主题。

### 三句话版

> 按「LLM 增量式构建持久化 wiki」方法论维护的个人知识库，采用 raw（不可变来源）/ wiki（LLM 生成维护）/ schema（操作规范）三层架构。
> 覆盖 Python、LangChain、LangGraph、PostgreSQL、MySQL、Redis、Docker、RAG 等 16 个技术主题共 672 页，全部带 YAML frontmatter 与 Obsidian 双链。
> 自建三项自动化校验（断链 / 函数覆盖率 / 名词覆盖率）脚本，把「有没有用了没讲的东西」从人工抽样变成全量核查。

### 详细版（面试开场用）

> 「我维护一个个人知识库，但它不只是笔记——**核心是一套『人机协作的知识生产规范』。**
>
> 架构分三层：`raw/` 放不可变的来源文档，`wiki/` 是我让 LLM 生成和维护的结构化页面，`schema` 定义 LLM 该怎么操作这套库的规范。
>
> 我认为最有价值的是**质量校验自动化**。比如『断链校验』——遍历所有页面提取双链，比对目标是否存在；『名词覆盖率校验』——把正文里出现的专有名词和索引页做全量比对，揪出「用了但没讲」的概念。
>
> 这套机制让我能在**不人工审每句话**的前提下，保证知识库的一致性和可追溯性。」

---

## 二、⭐ STAR 重构

### S（Situation）背景

```
「学的东西多而散：Python、LangChain、LangGraph、PG、MySQL、Redis、
Docker、RAG… 每个都学一点，但过段时间就忘，而且同一个概念在不同
教程里说法不一，不知道该信谁。

更实际的问题是：写过的东西再过三个月看，经常发现『这里用了某个
术语但从没解释过』——零基础回头看根本看不懂。」
```

### T（Task）任务

```
「要一个能长期积累、且质量不随规模下降的知识系统。
两个硬要求：① 结构化到能被检索和引用；② 质量可自动校验——
不然页数一多，人工审不过来。」
```

### A（Action）方案 ⭐ 三个设计决策

**决策 1：三层架构**

```
raw/     —— 不可变的来源文档（文章、教程）。只读不改，是事实来源
wiki/    —— LLM 生成和维护的结构化页面。完全由 LLM 写，我负责策展
schema   —— 定义 LLM 该怎么操作这套库的规范（页面类型、frontmatter、
           链接格式、操作日志）

这样分工的理由：来源和派生内容分离，避免「改了派生内容就丢了
原始依据」。」
```

📌 [[meta/知识库三层架构]] · [[meta/LLM_Wiki_方法论]]

**决策 2：写作基线（⭐ 这是最核心的方法论）**

```
「踩过三次坑之后定下的硬规则：

① 零前置假设——任何关键字/名词首次出现必须在本页解释，
   不假设读者有基础；
② 入门层必须有零基础入口，明确声明『不要求任何前置知识』；
③ 每篇写到『机制/实操/陷阱』三层，宁可写透一个点；
④ 每篇配索引兜底——专有名词、函数、语法各一本总索引。
」
```

⭐ **「三次返工换来四条规则」这个故事本身就有说服力**——它证明规范不是纸上写的，是踩出来的。

**决策 3：三项自动化校验**

```
① 断链校验：遍历 md，提取 wikilink，比对目标文件是否存在。
   难点是误报——表格里的转义符、行内代码里的示例链接、
   代码块里的数学写法都会被误判，要逐类处理。
② 名词覆盖率校验：提取正文的专有名词，和术语索引页全量比对，
   揪出「用了但没讲」的。
③ 函数覆盖率校验：同思路，对函数手册比对。
```

⭐ **这个设计的价值主张**：**把「质量」从「人工抽样」变成「全量可核查」。** 这是这套系统区别于普通笔记的核心。

## 四、⭐ 预判追问

### Q1：为什么不用 Notion / 语雀 / 现成工具？

**答**：⭐ 「三个原因：① **要 Obsidian 的双链和图谱**——知识之间的关联比单篇内容更重要；② **要 Git 版本管理**——能看「这个结论是什么时候、基于什么改的」；③ ⚠️ **最关键的：要能被程序化校验。** 现成工具是「给人看的」，我要的是「能被 LLM 自动维护 + 自动检查的」。纯 Markdown 是唯一同时满足这三者的。」

### Q2：让 LLM 写知识库，质量怎么保证？

**答**：⭐ 「两层：① **schema 层**——把踩过的坑固化成硬规则（零基础假设、每篇配索引、篇数必须核实不能凭记忆填）；② **校验层**——写完自动跑断链/名词/函数覆盖率，不合格就打回。⚠️ **关键是规范要「可自动校验」**——不能校验的规范等于没有。」

### Q3：断链校验有什么难的？

**答**：⭐ 「难在误报。我遇到过的四类：① 表格单元格里 Obsidian 用 `\|` 转义别名分隔符，得先还原；② 行内代码里的 `[[链接]]` 是语法示例，Obsidian 不解析，得剥除；③ 三反引号代码块要整块剥除；④ **短链接 `[[页面名]]` 要按全库 basename 解析**——我第一版脚本漏了这个，把 13 个真实存在的链接误报成断链，差点以为库烂了。」

⭐ **这个回答极好**——它有具体的技术细节、有踩坑、有修正。**「差点以为库烂了」这种真实感是编不出来的。**

### Q4：672 页怎么维护？不乱吗？

**答**：⭐ 「靠索引层。每主题 4~5 本索引（README 导航 / 学习路线图 / 术语手册 / 函数手册 / 速查索引），正文只讲机制。查东西先查索引再进正文，不用遍历。而且每篇都有明确的『前置知识』和『看不懂该退回哪里』，不会在超纲的页面上硬啃。」

### Q5：这个项目对你有什么实际价值？

**答**：⭐ 「【按实际答】。对我来说最大的价值是**它本身就是我学习方法论的实验场**——我用它验证了『LLM 增量式维护 wiki』这套模式是否成立。结论是成立，但前提是**规范必须可自动校验**。」

### Q6：为什么坚持「零基础写作」？

**答**：⭐ 「因为我自己的学习路径就是这样：先建心智模型，再逐步深入。如果一上来就堆术语表，看着像学了，其实理解是悬空的。⚠️ **代价是篇幅变长**——但宁可写透一个点，不要罗列十个点。」

## 五、⭐ 这个项目的差异化定位

⚠️ **不要说「这是我的笔记库」——那会被当成个人杂物。**

```
「这个项目的本质不是『记笔记』，是**一套人机协作的知识生产流水线**。

我设计的不是内容，是『LLM 怎么在有约束的前提下持续产出高质量
结构化内容』这件事。三层架构、写作基线、自动化校验，都是围绕
这个目标。

如果要往深了说，它和 RAG 是同一个问题的两种解法：
RAG 是『检索时找相关内容』，Wiki 是『事先就把知识组织好』。
我在这个项目里验证的是后者。」
```

⭐ **最后那句「和 RAG 是同一个问题的两种解法」是杀手锏**——它把第三个项目和你最强的第二个项目串起来了，体现你有系统性的思考。

## 六、⭐ 常见自杀式回答

| ❌ 别说 | 为什么 |
|--------|--------|
| 「这是我的个人笔记」 | 直接把自己降格成「记笔记的」 |
| 「用 Obsidian 记了很多笔记」 | 工具不是项目 |
| 「让 AI 帮我写了很多文档」 | ⚠️ 显得你在偷懒，而不是在设计流水线 |
| 「有 600 多篇呢」 | 数量不是价值，**规范和质量才是** |
