# 项目一：终端多智能体系统

> ⚠️ **本页是「讲项目的骨架」，不是「项目文档」。** 目的：让你在 3 分钟和 10 分钟两个版本都能讲，且接得住追问。
>
> ⚠️⚠️ **所有 `【待补充】` 必须由你填真实数据。我不会编造。**

---

## 一、简历描述（三个版本）

### 一句话版（30 字内）

> 基于 LangChain/LangGraph 的终端交互多智能体系统，支持 Skills 渐进加载、MCP 工具接入与长短记忆。

### 三句话版（简历正文用）

> 基于 LangGraph 构建的多智能体编排系统，编排节点负责任务分解与派发，专家节点内部运行独立 ReAct 循环。
> 自研 Skills 渐进加载机制（`list_skills` / `load_skill`），使 Agent 可挂载 20+ 能力包而不撑爆上下文。
> 集成 MCP 工具、RAG 检索、Checkpointer/Store 长短记忆，支持中断恢复与多轮会话隔离。

### 详细版（面试开场用）

> 「我做过一个终端交互的多智能体系统。核心痛点是：**能力越来越多，但上下文窗口有限，而且长任务需要能中断恢复。**
>
> 架构上是 LangGraph 的 StateGraph：一个编排节点负责理解用户意图、决定派给哪些专家；专家节点内部是各自的 ReAct 循环，可以调自己的工具。
>
> 三个我比较有心得的设计：
> ① **Skills 渐进加载**——用 list_skills/load_skill 两个元工具，让模型先看能力清单再按需加载，避免全量塞 prompt；
> ② **长短记忆分层**——短期用 PostgresSaver 存会话状态，超限时 SummarizationMiddleware 压缩；长期偏好外置到 Store，不依赖摘要保留；
> ③ **可观测**——每轮 Thought/Action/Observation 都结构化记录，跑偏时能定位到具体哪一步。」

## 二、⭐ STAR 重构（按这个顺序讲）

⚠️ **不要按「我先做了 A，又做了 B」的时间顺序讲——那是流水账。按 STAR 讲才有说服力。**

### S（Situation）背景

```
「Agent 的能力需求在涨：工具越加越多，Skills 也从几个涨到二十几个。
直接全量注册的后果是 prompt 里有几万 token 的工具定义和 Skill 全文，
既慢又贵，而且模型注意力被稀释，选错工具的情况变多。」
```

⭐ **关键：把「问题」说具体。** 「能力多」不是问题，「prompt 几万 token 导致选错工具」才是问题。

### T（Task）任务

```
「要设计一个机制，让 Agent 能挂几十个能力，但每次只把需要的加载进上下文。
同时长任务要能中断恢复——终端场景下用户可能中途离开。」
```

### A（Action）方案 ⭐ 重点，讲 2~3 个设计决策

**决策 1：Skills 渐进加载**

```
「每个 Skill 是一个目录：SKILL.md（含 frontmatter 的 name/description/
适用场景）+ 可选的 scripts/ 和 references/。

Agent 侧只有两个元工具：
  list_skills()  → 只返回 name + description（几十 token）
  load_skill(name) → 返回该 Skill 的完整 SKILL.md

模型先 list 看有哪些能力，判断需要哪个再 load。这就是渐进加载。
```

**决策 2：长短记忆分层**

```
「三层：
  短期：Checkpointer（PostgresSaver）存会话状态和图状态，按 thread_id 隔离
  压缩：SummarizationMiddleware 在超阈值时摘要化早期历史
  长期：Store 存跨会话的用户偏好，按 (用户ID, 类型) 命名空间隔离

关键认知：摘要会丢细节，所以『必须记住的』显式写进 Store，
不指望压缩时留下。」
```

**决策 3：可观测性**

```
「每轮循环记录 Thought / Action / Observation 到结构化日志。
排查『Agent 答错了』时能直接定位到是哪一步开始错的——
是工具选错了，还是工具返回了模型不理解的内容。」
```

### R（Result）结果 ⚠️ 必须填真实数据

```
【待补充】 Skill 数量：从 X 个到 Y 个
【待补充】 prompt token 变化：全量约 X token → 渐进加载后约 Y token
【待补充】 工具选择准确率：X% → Y%（如有测量）
【待补充】 长任务中断恢复：支持 / 实际发生过几次
```

⚠️ **如果没有量化数据，就用定性描述**：
```
「最直观的变化是 Agent 能挂的 Skill 数量从个位数涨到二十几个，
而单轮 prompt 没有明显变长。另外长任务中途离开再回来能接着跑，
不用重新开始。」
```

## 四、⭐ 预判追问（按被问概率排序）

### Q1：为什么不把所有工具都注册进去？

**答**：⭐ 「两个原因：① **上下文成本**——几十个工具的 JSON Schema 就有几万 token，每轮都付这个钱；② **注意力稀释**——工具太多模型选不准，我实测过工具数量上去后选错率变高。渐进加载把『选择』和『加载』分成两步，成本就降下来了。」

### Q2：Skills 和 MCP 工具的区别？

**答**：⭐ 「**MCP 给的是『能力』——能调什么；Skills 给的是『知识』——该怎么做。** 比如 MCP 提供一个 `query_db` 工具，Skills 提供『SQL 优化方法论』。两者互补，我在系统里都接了。」

### Q3：SummarizationMiddleware 压缩丢了关键信息怎么办？

**答**：⭐ 「所以我不依赖摘要保留关键信息。**必须记住的（用户偏好、任务目标）显式写进 Store**，摘要只负责让对话能继续下去。这是有意识的分工——摘要不是记忆，是压缩。」

### Q4：多智能体之间怎么通信？

**答**：⭐ 「进程内是 LangGraph 的状态流转（State + reducer），不是网络调用。编排节点把任务写进状态，专家节点读状态、写回结果。⚠️ **如果专家要跨进程/跨团队，那才需要 A2A 这类协议**——我评估过，当前规模不需要。」

### Q5：怎么防止 Agent 跑偏/无限循环？

**答**：⭐ 「四层：① `recursion_limit` 硬限制；② 检测连续相同 tool_call 主动中断；③ 工具返回可读错误让模型自己纠偏，而不是抛异常；④ 敏感操作加人工介入点。」

### Q6：这个系统上线了吗？有多少用户？

⚠️ **如实答。** 没上线就说「个人项目/内测中，主要价值在架构验证」。**不要编用户数。**

### Q7：如果重做一次，你会改什么？

⭐ **这题是「是否有反思能力」的试金石。** 示例（按实际改）：
```
「两个点：
① Skills 的粒度一开始定得太细，导致 list 返回的清单本身就很长，
   模型选择困难。后来合并成「一个 Skill 一类任务」。
② 评估做得太晚——应该先建 Golden Set 再优化，不然改完不知道
   有没有变好。」
```

### Q8：上下文一直涨的问题怎么发现的？

**答**：⭐ 「跑长任务时发现轮数一多就超限或者成本飙升。看了下每轮 Observation 都追加进 messages，只增不减。所以上了 SummarizationMiddleware + 关键信息外置。」

## 五、⭐ 常见自杀式回答（避免）

| ❌ 别说 | 为什么 |
|--------|--------|
| 「我用 LangChain 做了一个 Agent」 | 太泛，等于没说 |
| 「支持很多工具」 | 没有信息量，要说**几个、什么类型、怎么选的** |
| 「用了 RAG 提升了效果」 | ⚠️ **没有量化 = 没有提升**。要么给数据，要么给定性观察 |
| 「按网上的教程做的」 | 即使部分是，也要讲**你改了什么、为什么改** |
| 「多智能体之间用消息队列通信」 | ⚠️ 进程内用消息队列是过度设计，会被追问「为什么不直接函数调用」 |

## 六、讲项目的三个技巧

### 技巧 1：先讲「问题」再讲「方案」

⚠️ **面试官不关心你用了什么框架，关心你解决了什么问题。** 每句话以「因为…所以…」开头。

### 技巧 2：主动埋「可追问的点」

⭐ **故意留一个你准备好的深挖点**，等面试官来问。比如「Skills 渐进加载」——他问你就赢。

### 技巧 3：不会的大方说不会

```
「这个我没做过，但我猜可能是…（给推理）」
```
⭐ **比硬编好得多。** 硬编被戳穿一次，前面全白讲。
