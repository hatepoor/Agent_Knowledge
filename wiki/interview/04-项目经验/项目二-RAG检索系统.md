# 项目二：RAG 检索系统

> ⚠️ **本页是「讲项目的骨架」。** 所有 `【待补充】` 必须由你填真实数据。
>
> ⭐ **这个项目的最佳讲法：主打「解析」和「评估」两头**——这两头最容易被忽略，且你有 docling + ragas 的真实实践。

---

## 一、简历描述

### 一句话版

> 基于 docling + ragas 的文档解析与检索增强系统，重点解决 DOCX 表格/图片解析与 RAG 效果分层评估。

### 三句话版

> 面向多格式文档的 RAG 检索系统，用 docling 做元素级解析，解决 DOCX 中表格结构丢失与图片信息缺失问题。
> 分块采用结构感知策略，表格整块保留并配摘要双轨，代码按语法边界切分。
> 建立基于 ragas 的分层评估体系（检索层 recall/precision + 生成层 faithfulness），用 Golden Set 做回归基线。

### 详细版（面试开场用）

> 「我做的 RAG 系统，重点不在『搭起来』，而在两个容易被忽略的头尾：**解析**和**评估**。
>
> 解析侧：用 docling 处理 PDF/DOCX/HTML。核心痛点是 DOCX 的表格——纯文本抽取会把表格打成乱码，图片直接丢。docling 的元素层能保留表格结构，图片单独提取后走视觉描述。
>
> 评估侧：用 ragas 建了检索和生成两层评估。**只看最终答案会漏掉一半问题**——比如检索没召回对的内容，生成再好也没用。分层评估能精确定位是哪一层的问题。」

---

## 二、⭐ STAR 重构

### S（Situation）背景

```
「文档来源杂：PDF、DOCX、HTML 都有。DOCX 是最麻烦的——
表格被纯文本抽取打成乱码，图片信息直接丢失，而业务上这些表格
和图片里的信息恰恰是关键的。」
```

### T（Task）任务

```
「两个目标：① 解析要保住表格结构和图片信息；
② 要有办法量化『效果有没有变好』——不然调分块参数就是瞎猜。」
```

### A（Action）方案 ⭐ 讲 2~3 个

**决策 1：docling 元素级解析**

```
「用 docling 而不是纯文本抽取。它把文档解析成元素树（标题/段落/
表格/图片），表格能保留结构，图片可以按元素提取。

提取出来的图片走视觉模型描述化——不是简单存个路径，
而是生成一段描述文字参与检索。」
```

📌 [[docling/README]] · [[rag/01_多源数据接入/图片提取与描述化]]

**决策 2：结构感知分块 + 特殊内容处理**

```
「不定长切。按文档的标题层级做结构感知分块，标题链前置让每个块
自带上下文。

四种特殊内容分别处理：
  表格 → 整块不切 + 表头前置 + 「摘要+原表」双轨
  代码 → 按语法边界切，不切断函数
  列表 → 尽量整块，保留层级
  图片 → 提取后视觉描述化
」
```

⭐ **「表格摘要双轨」是亮点**：表格的向量表示效果差（数字密集无语义），配一段文字摘要才能被检索到。

📌 [[rag/03_智能分块/特殊内容分块]]

**决策 3：ragas 分层评估**

```
「建 Golden Set（问题 + 应检索的文档），每次改动跑一轮评估。

看两个核心组合：
  context_recall —— 该检索到的是否检索到了
  faithfulness   —— 答案是否忠于检索内容

最有价值的诊断是『recall 高但 faithfulness 低』——说明检索到了
但模型没用上，问题在上下文构建而不在检索。」
```

📌 [[rag/12_评估与监控/评估体系与RAGAS]]

### R（Result）⚠️ 必须填真实数据

```
【待补充】 文档处理量：X 篇 / X 万页
【待补充】 表格识别准确率：X%（如有测量）
【待补充】 context_recall：X% → Y%
【待补充】 faithfulness：X% → Y%
【待补充】 通过评估发现并修复的问题数：X 个
```

⚠️ **没有数据就定性**：
```
「最直接的改善是 DOCX 表格从『乱码不可用』变成『结构完整可检索』。
评估体系的价值是让后续每次调优都有依据，不用凭感觉。」
```

## 三、技术栈清单

| 层 | 技术 |
|----|------|
| 解析 | docling |
| 分块 | 结构感知 + 特殊内容策略 |
| Embedding | 【待补充：模型名】 |
| 向量库 | PostgreSQL + pgvector |
| 检索 | 混合（向量 + BM25）+ 重排 |
| 评估 | ragas |
| 框架 | LangChain |

⚠️ **追问「为什么用 PG + pgvector 而不是专用向量库？」**
→ 按实际答。常见理由：① 已有 PG 基础设施，少维护一个组件；② 数据量不大（百万级以下）PG 够用；③ 能用 SQL 做元数据过滤和 JOIN。

## 四、⭐ 预判追问

### Q1：为什么用 docling 不用 PyPDF2/unstructured？

**答**：⭐ 「PyPDF2 只抽文本，表格和图片全丢。unstructured 也行但 docling 的**元素层模型**更清晰——它把文档解析成结构化的元素树，我能按元素类型分别处理（表格整块、图片提取、标题链前置）。这对后续分块质量影响很大。」

### Q2：表格「摘要+原表」双轨具体怎么做？

**答**：⭐ 「表格上方生成一段文字摘要（『下表列出了 2024 各季度销售额，Q1 最高』），表格本身整块保留。检索时摘要参与匹配——因为**表格的向量表示效果差**（数字密集、无语义）；命中摘要后返回完整表格给模型。」

### Q3：图片怎么处理？

**答**：⭐ 「docling 按元素提取图片，然后走视觉模型生成描述文字。描述文字参与检索和上下文，原图可以按需展示。⚠️ **不是所有图片都值得描述**——装饰性图片的描述是噪声，我按尺寸和位置做了过滤。」

### Q4：chunk 大小定的多少？为什么？

**答**：⭐ 「【按实际答】。起点是 512 token、overlap 10~20%。定这个值的推理：① embedding 模型上限；② 语义完整性——块要能独立表达一个意思；③ 上下文预算——top-k 个块加 prompt 要塞进窗口。⚠️ **我抽了样本人工看过块的质量**，不是拍脑袋定的。」

### Q5：recall 低怎么排查？

**答**：⭐ 「五步：① 是完全没召回还是部分召回；② top-k 是否太小；③ 分块是否切断语义/表格是否被打散；④ 是否缺精确匹配（SKU/型号加 BM25）；⑤ query 是否被正确理解（查询改写）。」

### Q6：faithfulness 低说明什么？

**答**：⭐ 「**幻觉——答案里有检索内容不支持的部分。** 但如果 recall 同时高，问题通常在上下文构建：拼进 prompt 的内容太长、关键内容被稀释。解法是重排 + 裁剪，只留最相关的。」

### Q7：评估的 Golden Set 怎么来的？

**答**：⭐ 「【按实际答】。优先级是：真实用户问题 > 领域专家写 > LLM 从文档反向生成。⚠️ 最后一种要人工筛，因为 LLM 生成的问题可能偏离真实分布。」

### Q8：RAG 有什么没解决的问题？

⭐ **这题体现你是否真做过。** 示例：
```
「两个：① 多跳推理——需要综合多个文档才能答的问题，单轮检索不够，
   后来考虑上 Agentic RAG；② 全局性问题——『这份文档主要讲了什么』
   这类不是检索能答的，要走摘要路线。」
```

## 五、⭐ 常见自杀式回答

| ❌ 别说 | 为什么 |
|--------|--------|
| 「用 LangChain 几行就搭起来了」 | 显得没深度，把项目说成了 demo |
| 「分块用 512」 | 没有推理过程，会被追问问倒 |
| 「效果提升了很多」 | ⚠️ 没有数据 = 没有提升 |
| 「用了向量数据库所以很快」 | ⚠️ 向量库不背性能锅，要看索引和检索策略 |
| 「评估就是看答案对不对」 | ⚠️ **恰恰证明没做过评估** |

⭐ **面试时主动强调，这是你和「跑过 demo 的人」的区别：**

```
「很多人做 RAG 停留在『能跑通』。我花时间最多的是两头：

① 解析——因为垃圾进垃圾出，DOCX 表格图片处理不好，后面全白搭；

中间的分块检索反而是相对标准的。」
```
