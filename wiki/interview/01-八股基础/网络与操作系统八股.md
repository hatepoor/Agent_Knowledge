# 网络与操作系统八股

> **什么时候该读**：面试前速成网络与 OS 部分。
> ⚠️ 这部分知识库内无专页，**本页自带完整答案**（不像前两篇大量外链）。

---

## 一、HTTP 与 HTTPS

### Q：HTTP 和 HTTPS 的区别？

**一句话**：HTTPS = HTTP + **TLS**。TLS 在传输层之上提供加密、身份验证、完整性保护。

**展开骨架**：
| 点 | 内容 |
|---|---|
| 默认端口 | HTTP 80 / HTTPS **443** |
| 握手 | ⭐ TLS 握手额外 1~2 个 RTT（1.3 优化到 1-RTT，0-RTT 有重放风险） |
| 证书 | 由 CA 签发，验证服务器身份 |
| 加密 | 非对称加密协商密钥 + 对称加密传数据 |

### Q：HTTPS 的握手过程？

**一句话**（TLS 1.2，四步）：
```
① ClientHello      客户端发支持的 TLS 版本、加密套件、随机数
② ServerHello      服务端选套件、发证书、发随机数
③ 密钥协商         客户端验证证书 → 生成预主密钥 → 用服务端公钥加密发送
④ Finished         双方各自推导出会话密钥，之后对称加密通信
```

⚠️ **追问：为什么用非对称 + 对称混合？**
→ 非对称加密慢但能安全协商密钥；对称加密快。⚠️ **全程只用非对称会太慢。**

### Q：HTTP 1.1 / 2 / 3 的区别？

| 版本 | 关键变化 |
|------|---------|
| 1.1 | Keep-Alive 长连接、管道化 |
| **2** | ⭐ **多路复用**（单连接并发多请求）、头部压缩 HPACK、服务端推送 |
| **3** | ⭐ **基于 QUIC（UDP）**，解决 TCP 队头阻塞；连接迁移 |

**追问：HTTP/2 的多路复用解决了什么问题？**
→ HTTP/1.1 的队头阻塞（一个慢请求阻塞后续请求）。⚠️ **但 HTTP/2 在 TCP 层仍有队头阻塞，这是 HTTP/3 换 QUIC 的原因。**

### Q：GET 和 POST 的区别？

**一句话**：语义上 GET 是**获取**（安全、幂等、可缓存），POST 是**提交**（不安全、不幂等）。

⚠️ **高频错误答案**：「GET 参数在 URL、POST 在 body」——这是实现细节不是规范区别。**「GET 有长度限制」也是误解**（是浏览器/服务器实现限制，不是协议规定）。

### Q：常见的状态码？

| 码 | 含义 |
|---|---|
| 200 / 204 | 成功 / 成功无内容 |
| 301 / 302 | 永久重定向 / 临时重定向 |
| 304 | ⭐ **未修改**（协商缓存命中） |
| 400 / 401 / 403 | 请求错误 / **未认证** / **无权限** |
| 404 / 405 | 不存在 / 方法不允许 |
| 429 | ⭐ **限流** |
| 500 / 502 / 503 / 504 | 服务端错误 / 网关错误 / 过载 / 网关超时 |

⚠️ **追问：401 和 403 的区别？**
→ ⭐ **401 = 「你是谁」（未认证）；403 = 「我知道你是谁但你不配」（已认证但无权限）。**

## 二、TCP 与 UDP

### Q：TCP 的三次握手？

```
① SYN      客户端发 SYN（seq=x）
② SYN-ACK  服务端回 SYN-ACK（seq=y, ack=x+1）
③ ACK      客户端回 ACK（ack=y+1）
```

**追问：为什么是三次不是两次？**
→ ⭐ **防止历史重复连接初始化**（旧 SYN 延迟到达），并确认双方的收发能力都正常。

### Q：四次挥手？

```
① FIN      客户端请求关闭
② ACK      服务端确认
③ FIN      服务端也请求关闭
④ ACK      客户端确认，进入 TIME_WAIT
```

**追问：为什么有 TIME_WAIT？**
→ ⭐ ① 确保最后一个 ACK 能被对方收到（否则要重传）；② **让旧连接的报文在网络中消散**，避免影响新连接。

### Q：TCP 怎么保证可靠传输？

| 机制 | 作用 |
|------|------|
| 序号 + 确认应答 | 保证有序、不丢 |
| 超时重传 | 丢包重发 |
| 流量控制（滑动窗口） | ⭐ **接收方**告诉发送方能收多少，防淹没 |
| 拥塞控制（慢启动/拥塞避免/快重传/快恢复） | ⭐ **网络**层面的自适应 |

⚠️ **追问：流量控制和拥塞控制的区别？**
→ ⭐ **流量控制防「接收方被淹没」，拥塞控制防「网络被压垮」。** 这是高频题。

### Q：TCP 和 UDP 的区别？

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（重传、有序） | ⚠️ 不可靠，可能丢/乱序 |
| 速度 | 慢（握手+确认） | 快 |
| 头部 | 20 字节 | 8 字节 |
| 适用 | 文件、网页、支付 | ⭐ **视频、语音、游戏、DNS** |

## 三、操作系统

### Q：进程和线程的区别？

| | 进程 | 线程 |
|---|---|---|
| 资源 | ⭐ **独立地址空间** | ⭐ **共享进程资源** |
| 创建开销 | 大 | 小 |
| 通信 | IPC（管道/消息队列/共享内存） | ⭐ 直接读写共享变量（要同步） |
| 崩溃影响 | 不影响其他进程 | ⚠️ **整个进程崩溃** |

⚠️ **追问：为什么线程切换比进程快？**
→ 线程切换不用切页表（地址空间不变），缓存局部性更好。

### Q：进程间通信（IPC）有哪些？

| 方式 | 特点 |
|------|------|
| 管道 / 命名管道 | 单向、父子进程 |
| **消息队列** | 有格式、异步 |
| ⭐ **共享内存** | 最快，但要自己同步 |
| 信号量 | 同步原语 |
| Socket | ⭐ 可跨机器 |
| 信号 | 异步通知 |

### Q：什么是死锁？四个必要条件？

**一句话**：两个以上进程互相等待对方持有的资源。

⭐ **四个必要条件（缺一不可）：**
1. **互斥**：资源一次只能被一个进程持有
2. **占有并等待**：持有资源的同时等待别的资源
3. **不可抢占**：资源不能被强制夺走
4. **循环等待**：存在等待环

⚠️ **追问：怎么预防？**
→ ⭐ **破坏「占有并等待」**（一次性申请所有资源）或 **破坏「循环等待」**（按固定顺序申请）。⚠️ 后者是数据库死锁治理的同一思路。

📌 对应 MySQL 的死锁治理见 [[mysql/03-进阶阶段-深度剖析/事务与锁内核/原理剖析-锁体系与死锁]]

### Q：用户态和内核态？

**一句话**：内核态可执行所有指令、访问所有内存；用户态受限。**系统调用是用户态到内核态的入口。**

⚠️ **追问：为什么要有这个区分？**
→ 隔离与保护——防止用户程序直接操作硬件/破坏内核。

### Q：IO 模型有哪些？

| 模型 | 说明 |
|------|------|
| 阻塞 IO | 调用后一直等 |
| 非阻塞 IO | 立即返回，轮询 |
| **IO 多路复用** | ⭐ `select`/`poll`/`epoll`，单线程监听多连接 |
| 信号驱动 IO | IO 就绪时发信号 |
| 异步 IO | 内核完成后通知 |

⭐ **追问：`select` 和 `epoll` 的区别？**
→ `select` 有**连接数上限**（1024）且每次都要遍历全部 fd；`epoll` **只返回就绪的 fd**，且用事件注册避免重复遍历。⚠️ **这是 Redis/Nginx 高性能的核心。**

### Q：虚拟内存和分页？

**一句话**：虚拟地址经页表映射到物理地址；进程看到的是独立的连续地址空间，实际物理页可离散。

⚠️ **追问：为什么需要虚拟内存？**
→ ① 隔离保护；② 让每个进程有独立的地址空间；③ ⭐ **用磁盘换页扩展可用内存**（swap）。

### Q：什么是零拷贝？

**一句话**：减少数据在内核态与用户态之间的**重复拷贝**。典型如 `sendfile`（直接从页缓存发给网卡）。

⚠️ **追问：Kafka 为什么快？零拷贝是原因之一吗？**
→ ⭐ **是**——Kafka 用 `sendfile` 把日志直接从页缓存发到网卡，避免四次拷贝。
