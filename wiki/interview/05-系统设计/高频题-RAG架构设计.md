# 高频题：设计一个企业知识库 RAG

> **什么时候该读**：RAG 岗系统设计题最高频。
> 框架见 [[interview/05-系统设计/系统设计方法论]]，本页套用六步框架。

---

## 一、按六步框架走一遍

### ① 澄清需求（⭐ 先问）

| 问题 | 影响 |
|------|------|
| ⭐ **文档类型和规模？** | 决定解析器和索引方案 |
| ⭐ **用户量 / 查询量？** | 决定检索性能和缓存 |
| ⭐ **要不要权限隔离？** | ⭐ **企业场景必须问，否则是安全事故** |
| 知识更新频率？ | 决定增量索引 |
| ⭐ **幻觉容忍度？** | 决定要不要引用、要不要「拒答」机制 |
| 多轮追问还是单轮？ | 决定上下文管理 |

**结论示例**：
```
「我按：10 万篇文档（PDF/DOCX/HTML 混合）、日查询 1 万次、
需按部门权限隔离、知识每周增量更新来设计。」
```

### ② 规模估算

```
「10 万篇 × 平均 20 页 → 2000 万页
每页 ≈ 500 token → 总分块约 1000 万个（按 512 token/块）

存储：
  分块文本 ≈ 1000万 × 2KB = 20GB
  向量（1024 维 float32）≈ 1000万 × 4KB = 40GB
  ⭐ 合计约 60GB，单库 + pgvector 能扛，但要有归档策略

查询：日 1 万次，QPS ≈ 0.1（低并发）
  ⚠️ 瓶颈不在 QPS，在单次查询的延迟和检索质量」
```

### ③ 数据模型

```
Document(id, title, source, owner_dept, status, created_at, updated_at)
Chunk(id, document_id, seq, content, embedding, metadata)
  -- metadata：页码、标题链、权限标签、内容类型（text/table/image）
QueryLog(id, user_id, query, rewritten_query, retrieved_ids, answer, latency)
```

⭐ **`metadata` 里的「权限标签」和「标题链」是关键**——前者管安全，后者管上下文质量。

### ④ 高层架构

```
写入链路（离线）：
  文档上传 → 对象存储 → 解析（docling）→ 清洗 → 分块
           → Embedding → 写入 pgvector + BM25 索引

读取链路（在线）：
  查询 → 查询改写 → 权限过滤注入 → 混合检索（向量 + BM25）
        → RRF 融合 → Cross-Encoder 重排 → 上下文构建 → LLM 生成
        → 引用编号校验 → 返回 + 溯源

  ⚠️ 关键：权限过滤在检索层做，不是检索后过滤
```

⭐ **「权限过滤在检索层」这句话一定要说**——这是企业 RAG 和 demo RAG 的分水岭。

### ⑤ 深入关键点（⭐ 讲这三个）

**深入 1：权限隔离怎么实现**

```
「两个方案：
  方案 A：检索后过滤——先检索再按权限删
    ⚠️ 问题：top-k 被删后可能不足，且浪费检索算力
  方案 B（⭐ 选这个）：检索前注入——把权限标签作为过滤条件
    传给向量检索和 BM25
    优点：精准且高效

实现上：每个 chunk 带 owner_dept 标签，查询时用当前用户
可见的部门集合做 metadata filter。
⚠️ 注意：标签要在写入时打，且用户部门变更要能同步。」
```

**深入 2：知识更新怎么做**

```
「增量流程：
  文档变更 → 重新解析该文档 → 删除旧 chunk → 写入新 chunk

⚠️ 两个坑：
① 删除和写入要原子（用文档ID做维度，先写新的再删旧的，
   或事务保证）
② 如果换了 embedding 模型，必须全量重建——旧向量和新向量
   空间不兼容，混用等于随机」
```

**深入 3：检索质量怎么保证**

```
「分层评估：
  检索层：context_recall / context_precision
  生成层：faithfulness / answer_relevancy

离线用 Golden Set 回归，在线监控『检索空结果率』和用户反馈。

⚠️ 企业场景还要防一种情况：用户问了知识库没有的问题。
这时要允许模型说『知识库未收录』，而不是硬编一个答案。」
```

### ⑥ trade-off

| 决策 | 我的选择 | 代价 | 什么时候改 |
|------|---------|------|-----------|
| 向量库 | PG + pgvector | ⚠️ 亿级后性能下降 | 超 5000 万块上专用向量库 |
| 权限过滤 | 检索前注入 | ⚠️ 索引要带标签，写入复杂 | — |
| 分块 | 结构感知 | ⚠️ 依赖文档结构质量 | 文档杂乱时混定长 |
| 更新 | 增量 | ⚠️ 一致性要处理 | — |
| 拒答机制 | 允许说不知道 | ⚠️ 用户可能觉得「不智能」 | — |

## 二、⭐ 三个可能的追问

### 追问 1：pgvector 什么时候不够用？

**答**：⭐ 「量级上，千万级以下 PG 够用；过了之后要考虑：① 专用向量库（Milvus/Qdrant）；② 分片；③ ⚠️ 更要紧的是**先看是不是检索策略问题**——很多时候慢是因为没建对索引或 top-k 太大，不是向量库的锅。」

📌 [[tools/向量数据库/概述]]

### 追问 2：用户问了个知识库没有的问题，怎么处理？

**答**：⭐ 「三层：① prompt 明确允许说『未收录』；② ⭐ **检索结果为空或相关度低于阈值时，走单独的 prompt**（『知识库没有，是否要…』）而不是硬答；③ 记录这类 query——它可能是知识库的缺口，反向推动内容补充。」

### 追问 3：多轮追问怎么处理上下文？

**答**：⭐ 「两种：① 把上一轮的 query+answer 作为上下文拼进新 query（简单）；② ⭐ **查询改写**——把「那它的价格呢」改写成独立完整的问题（「XX 产品的价格」），因为原始短 query 单独检索效果差。实践中② 效果明显更好。」

📌 [[rag/05_查询转换与改写/查询改写与扩展]]

## 三、⭐ 常见扣分点

| ❌ 行为 | 改进 |
|--------|------|
| 不问权限隔离 | ⭐ **企业场景第一问** |
| 检索后过滤权限 | 改成检索前注入 |
| 不提评估 | 补分层评估 + Golden Set |
| 分块只说 512 | 说清推理 + 特殊内容处理 |
| 忽略 embedding 更换的代价 | 提「必须全量重建」 |
| 不说怎么处理「知识库没有」 | 补拒答机制 |
