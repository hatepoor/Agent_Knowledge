# 系统设计方法论

> **什么时候该读**：系统设计题不是「画架构图」，是「在约束下做权衡」。答不好方法论，画得再漂亮也没用。
>
> ⚠️ **本页是全模块的地基**，后面三篇高频题都基于这个框架。

## 面试定位

⚠️ **系统设计题考察的不是「知不知道某个技术」，是「能不能在信息不全的情况下做出合理决策并说清理由」。**

**最常见的失败**：听到题目就画架构图，画完发现漏了关键约束。

---

## 一、⭐ 六步框架（必须按顺序）

```
① 澄清需求（3~5 分钟）     ← ⭐ 最重要，也最容易被跳过
② 估算规模（2 分钟）        ← 决定技术选型的量级
③ 定义接口 / 数据模型        ← 把模糊需求变具体
④ 高层架构（先粗后细）       ← 先画主干，再逐个深入
⑤ 瓶颈与权衡                ← ⭐ 主动说出 trade-off
⑥ 扩展与运维                ← 监控、降级、限流
```

⚠️ **第 ① 步是区分度的来源。** 主动问出关键约束的人，和上来就画图的人，评委分数差一档。

---

## 二、第 ① 步：澄清需求的提问清单

⭐ **按题目类型选 3~5 个问。问对问题比答对问题更能体现水平。**

### 通用问题

| 问题 | 为什么问 |
|------|---------|
| ⭐ **用户量 / QPS 量级？** | 决定单机还是分布式 |
| ⭐ **读多还是写多？比例？** | 决定缓存策略、索引、分片 |
| ⭐ **一致性要求？强一致还是最终一致？** | 决定同步/异步、分布式事务 |
| ⭐ **延迟要求？P99 多少？** | 决定能否用重计算 |
| 数据量？年增长？ | 决定存储和归档策略 |
| 可用性要求？几个 9？ | 决定多副本、多活 |

### 针对 Agent/RAG 的特有问题

| 问题 | 为什么问 |
|------|---------|
| ⭐ **文档规模？多少篇、多大？** | 决定解析策略、索引方案 |
| ⭐ **检索精度要求？** | 决定要不要重排、混合检索 |
| ⭐ **知识更新频率？** | 决定增量索引还是全量重建 |
| 要不要权限隔离？ | ⭐ **企业场景必须有**，否则是安全事故 |
| 多轮对话还是单轮？ | 决定上下文管理策略 |
| ⭐ **幻觉容忍度？** | 决定要不要引用、要不要拒答机制 |

### ⚠️ 不要问的

| 别问 | 为什么 |
|------|--------|
| 「用什么语言？」 | ⚠️ 技术选型该你建议，不是问面试官 |
| 「数据库用 MySQL 还是 PG？」 | 同上。**该你给出选择和理由** |
| 「预算多少？」 | 脱离技术判断 |

---

## 三、第 ② 步：规模估算（⭐ 速查表）

⚠️ **不用精确，要量级对。** 面试官看的是「你有没有数量级意识」。

### 常用数字

| 项 | 速记 |
|---|---|
| 1 天秒数 | 86,400 ≈ 10⁵ |
| 1 字符 | 1 字节（ASCII）/ 3 字节（中文 utf8） |
| 1 token | ≈ 4 字符（英文）/ ≈ 1.5 汉字 |
| 1 篇文档（10 页） | ≈ 5 万字符 ≈ 1 万 token |
| 1 个 512 维 float 向量 | 2 KB |
| 1 张图片 | 100 KB ~ 2 MB |

### 估算模板

```
「假设日活 10 万，每人平均 5 次请求 → 日请求 500 万
 峰值按 3 倍算 → QPS ≈ 500万 × 3 / 86400 ≈ 170 QPS
 这个量级单机 + 读写分离能扛，但要有缓存和限流。

存储：每人每天产生 1 条记录 × 1KB → 日增 100MB → 年增 36GB
 这个量级单库 5 年内不用分片，但要考虑归档。」
```

⭐ **「5 年内不用分片，但要考虑归档」这种结论，比「要分库分表」更能体现判断力。**

---

## 四、第 ③ 步：接口与数据模型

⚠️ **别跳过这步直接画架构。** 数据模型往往是设计的核心。

```
「核心实体：
  User(id, name, ...)
  Document(id, owner_id, title, status, created_at)
  Chunk(id, document_id, content, embedding, metadata)
  QueryLog(id, user_id, query, response, latency, created_at)

关键关系：Document 1→N Chunk。
⚠️ 这里有个设计决策：embedding 存在 Chunk 行里还是单独的表？
  —— 存行里简单，但会让表很宽；拆开便于单独优化向量检索。
  我选存行里，因为量级还没到需要拆的程度。」
```

⭐ **说出「为什么这么选」比选什么更重要。**

---

## 五、第 ④ 步：高层架构（先粗后细）

### 先画主干（3~5 个框）

```
客户端 → 网关 → 服务层 → 存储层
                  ↓
              异步任务（解析/索引）
```

⚠️ **不要一上来画 15 个框。** 先立主干，再逐个深入面试官感兴趣的部分。

### 逐层深入的顺序

| 层 | 深入点 |
|----|--------|
| 网关 | 鉴权、限流、路由 |
| 服务 | 缓存、连接池、异步化 |
| ⭐ **存储** | 索引、分片、归档（⭐ 通常是重点） |
| 异步 | 队列、重试、幂等 |

---

## 六、第 ⑤ 步：主动说 trade-off ⭐ 这是加分核心

⚠️ **面试官不一定问，但你要主动说。** 这是「工程师」和「架构师」的区别。

### trade-off 表达模板

```
「这里有两个选择：
  方案 A：X
  优点：…
  代价：…
  方案 B：Y
  优点：…
  代价：…

我选 A，因为当前量级下 B 的代价（运维复杂度）大于收益。
如果 QPS 再涨 10 倍，我会重新评估。」
```

⭐ **「如果再涨 10 倍我会重新评估」这句话一定要说**——它体现你知道**没有放之四海皆准的架构，只有适合当前约束的架构**。

### 常见权衡维度

| 维度 | 对立面 |
|------|--------|
| 一致性 | 可用性（CAP） |
| 延迟 | 吞吐 |
| 成本 | 性能 |
| 简单 | 灵活 |
| ⭐ **读优化** | ⭐ **写优化** |

---

## 七、第 ⑥ 步：别漏了运维

⚠️ **很多人画完架构就停了，显得没上过生产。**

| 项 | 内容 |
|----|------|
| **监控** | QPS、延迟（P50/P99）、错误率、饱和度 |
| **限流** | 入口限流、按用户限流、按接口限流 |
| **降级** | 核心功能保、非核心关（如关闭推荐） |
| ⭐ **告警** | 什么情况叫人？什么情况自愈？ |
| **发布** | 灰度、回滚 |

---

## 八、⭐ 三个常见扣分点

| 扣分行为 | 改进 |
|---------|------|
| ❌ 上来就画图 | ⭐ **先问约束** |
| ❌ 只讲「用什么」不讲「为什么」 | ⭐ 每个选择配一句 trade-off |
| ❌ 追求「最先进」的方案 | ⭐ **追求「适合当前约束」的方案** |
| ❌ 忽略运维 | 补监控/限流/降级 |
| ❌ 面试官一质疑就全盘推翻 | ⭐ **坚持有理由的部分，修正没想清楚的部分** |

---

## 九、自测

- [ ] 能背出六步框架
- [ ] 通用问题清单能说出 4 个
- [ ] 规模估算：日请求 500 万的 QPS 是多少？（答案 ≈ 170）
- [ ] 能用模板说一段 trade-off
- [ ] 知道「如果再涨 10 倍」这句话为什么要说
