# 高频题：高并发后端设计

> **什么时候该读**：⭐ Agent 岗也会问后端题——因为 Agent 系统本身是高并发 IO 密集服务。
> 框架见 [[interview/05-系统设计/系统设计方法论]]。

## 面试定位

⚠️ **你的 Agent 项目就是高并发场景**（大量模型调用 + IO 等待），所以这题和你的经验直接相关，不要当成「不相关的后端题」。

---

## 一、按六步框架走一遍

### ① 澄清需求

| 问题 | 影响 |
|------|------|
| ⭐ **QPS 量级？峰值多少？** | 决定单机/集群/分布式 |
| ⭐ **读多还是写多？** | 决定缓存和索引策略 |
| 一致性要求？ | 强一致 vs 最终一致 |
| 延迟要求？P99？ | 决定同步/异步 |
| 可用性要求？ | 决定副本和降级 |

**结论示例**：
```
「按日活 100 万、峰值 QPS 1 万、读写比 9:1、最终一致可接受、
P99 < 200ms 来设计。」
```

### ② 规模估算

```
「峰值 QPS 1 万：
  假设 8 核机器单机可扛 2000 QPS（含 DB 调用）→ 需要 5 台
  考虑冗余和峰值系数 → 8~10 台

  日请求 8640 万，日增数据（写 10%）≈ 864 万条 × 1KB ≈ 8.6GB/日
  ⚠️ 这个写入量必须考虑分片和归档，单库撑不久」
```

⭐ **「8~10 台」这种具体结论比「需要集群」有信息量得多。**

### ③ 高层架构

```
客户端 → CDN（静态资源）
   ↓
DNS / 负载均衡（L4）
   ↓
API 网关集群（L7）—— 鉴权、限流、路由、灰度
   ↓
无状态服务集群 ← 配置中心
   ↓
Redis 集群（缓存 + 限流计数器 + 分布式锁）
   ↓
数据库（主从 + 读写分离）
   ↓
消息队列（异步任务：发通知、写日志、数据同步）
```

### ④ 逐层深入（⭐ 讲四个点）

**深入 1：缓存**

```
「Redis 做多级缓存：
  ① 热点数据缓存（Cache-Aside：读先缓存后库，写先库后删缓存）
  ② 会话/Token 缓存
  ③ 计算结果缓存

⚠️ 三个问题及解法：
  穿透（查不存在）→ 布隆过滤器 + 缓存空值
  击穿（热点 key 过期）→ 互斥锁 / 逻辑过期
  雪崩（大量同时过期）→ TTL 加随机值」
```

📌 [[redis/02-中段阶段-生产实践/03-缓存三大问题与缓存模式]]

**深入 2：数据库**

```
「读写分离：写主库，读从库。
⚠️ 主从延迟会导致「写完立刻读不到」——解法：
  ① 写完后的第一次读走主库（读己之写）
  ② 或业务上容忍秒级延迟

索引：为高频查询建联合索引，等值列在前、范围列在后。
⚠️ 索引不是越多越好，每个都增加写代价。」
```

📌 [[mysql/02-中段阶段-专题精讲/主从复制与高可用/复制原理与拓扑]]

**深入 3：异步化**

```
「非核心链路异步化：发通知、写审计日志、数据同步走消息队列。
好处：削峰 + 降延迟 + 故障隔离。
⚠️ 代价：要保证幂等和最终一致，且增加了排查难度。」
```

**深入 4：限流与降级**

```
「限流三层：
  ① 入口限流（网关层，按 IP/用户）
  ② 接口限流（按 QPS 配额）
  ③ 依赖限流（防止打垮下游）

降级：核心功能保（下单、支付），非核心关（推荐、排行）。
⚠️ 降级开关要能动态生效，不能发版才生效。」
```

### ⑤ trade-off

| 决策 | 我的选择 | 代价 | 什么时候改 |
|------|---------|------|-----------|
| 一致性 | 最终一致 | ⚠️ 短暂不一致 | 涉及资金改强一致 |
| 缓存 | Cache-Aside | ⚠️ 有延迟窗口 | — |
| 读写分离 | 主从 + 代理 | ⚠️ 延迟 + 复杂度 | QPS < 500 可单库 |
| 异步 | 消息队列 | ⚠️ 幂等和排查成本 | 简单场景可同步 |
| 分片 | 暂不分 | ⚠️ 单库上限 | 日增 > 50GB 或单表 > 亿 |

## 二、⭐ 高频追问

### Q：缓存和数据库怎么保证一致？

**答**：⭐ 「Cache-Aside：读先缓存后库；写先更新库再删缓存（不是更新缓存）。
⚠️ **为什么删而不是更新缓存**：① 更新缓存可能算错（并发）；② 懒加载，删了下次读再建。
⚠️ **为什么先写库后删缓存**：先删缓存会有「旧数据被重新读入缓存」的窗口。」

### Q：分布式锁怎么实现？

**答**：⭐ 「Redis：`SET key val NX PX ttl` + **唯一 token** + Lua 脚本保证「比对后删除」原子。
⚠️ 三个要点：① 必须有过期时间（防死锁）；② 删除前要校验 token（防删别人的锁）；③ ⚠️ ** Redlock 有争议，生产要评估**——单节点 Redis 挂了下锁信息就丢了。」

📌 [[redis/02-中段阶段-生产实践/06-分布式锁]]

### Q：接口幂等怎么保证？

**答**：⭐ 「三层：① **唯一业务键**（如订单号）+ 数据库唯一索引兜底；② **Token 机制**（下单前领 token，用后作废）；③ 状态机（只允许「待支付→已支付」，不允许重复流转）。
⚠️ 关键：**幂等要服务端保证，不能信客户端**。」

### Q：怎么防止超卖？

**答**：⭐ 「三种，按可靠性排：
  ① ⭐ **数据库扣减 + 唯一索引/乐观锁**（`UPDATE stock SET n=n-1 WHERE n>0`，看影响行数）——最可靠
  ② Redis 预扣（快，但要和 DB 对账）
  ③ 消息队列串行化（慢，不推荐单独用）

⚠️ 纯 Redis 扣减有丢数据风险，必须和 DB 最终一致。」

### Q：慢查询怎么排查？

**答**：⭐ 「① 慢日志 + `pt-query-digest` 找 Top N；② `EXPLAIN` 看执行计划（type 是否 ALL、Extra 是否有 filesort/temporary）；③ ⚠️ **先排除长事务**——它是「数据库越用越慢」的头号根因；④ 针对性优化（加索引/改写/覆盖索引）。」

## 三、⭐ 和你的 Agent 项目的关联（加分）

⚠️ **主动把后端口题拉到你熟悉的领域：**

```
「这套后端能力我在 Agent 项目里也用了——
比如 LLM 响应缓存用 Redis 做（相同 query 直接返回，省成本和延迟）；
连接池配了 pool_pre_ping 防止拿到已断开的连接；
模型调用有降级（主模型失败切备用）。
可以说 Agent 系统本质上就是一个高并发 IO 密集服务，
只不过『下游』从数据库换成了 LLM API。」
```

⭐ **最后这句是杀手锏**——它把「后端题」和「你的主战场」连起来了。
