# 高频题：设计一个多智能体系统

> **什么时候该读**：Agent 岗系统设计题**最高频**。
> 框架见 [[interview/05-系统设计/系统设计方法论]]，本页套用六步框架。

---

## 一、按六步框架走一遍

### ① 澄清需求（⭐ 先问，别画图）

**该问的（选 4~5 个）：**

| 问题 | 影响 |
|------|------|
| ⭐ **智能体数量级？几个还是几十个？** | 决定要不要动态注册/发现 |
| ⭐ **是同团队还是跨组织？** | ⭐ **决定要不要 A2A**（跨组织才需要） |
| ⭐ **任务是长跑还是短交互？** | 决定要不要中断恢复/流式 |
| **并发用户量？** | 决定连接池、模型限流策略 |
| **工具是内部还是外部？** | 决定 MCP 接入方式 |
| **敏感操作要审批吗？** | 决定要不要 HITL |

⚠️ **「同团队还是跨组织」是关键分水岭**——答错方向，后面全错。

**结论示例**：
```
「我按同团队、5~10 个专家 Agent、长任务、需中断恢复来设计。
如果是跨组织，我会引入 A2A 做边界通信，但同团队用 LangGraph
的进程内编排更合适。」
```

### ② 规模估算

```
「假设 1 万日活，每人 10 次会话，每会话平均 5 轮 →
  日请求 50 万，QPS ≈ 50万/86400 ≈ 6（低并发）
  ⚠️ 但 LLM 调用是瓶颈：每轮 1~3 次模型调用 →
  日模型调用 ≈ 250 万次
  ⭐ 这个量级的瓶颈不在数据库，在模型调用的成本和延迟。」
```

⭐ **「瓶颈在模型调用不在数据库」这个判断很重要**——它决定后面优化方向。

### ③ 数据模型

```
Session(thread_id, user_id, created_at)         -- 会话
Message(session_id, role, content, created_at)  -- 消息
Task(task_id, session_id, agent, status, ...)   -- 任务（跨 Agent 派发）
Skill(name, description, version)               -- Skill 元信息
ToolCallLog(...)                                -- ⭐ 可观测性必备
```

### ④ 高层架构

```
                    ┌─────────────────────┐
                    │   终端 / Web UI      │
                    └──────────┬──────────┘
                               │ WebSocket / SSE
                    ┌──────────▼──────────┐
                    │  API 网关            │  ← 鉴权、限流、流式
                    └──────────┬──────────┘
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
   ┌──────▼──────┐     ┌──────▼──────┐      ┌──────▼──────┐
   │ 编排 Agent   │     │ Checkpointer │      │   Store     │
   │ (Supervisor)│     │ (会话状态)    │      │ (长期记忆)   │
   └──────┬──────┘     └──────────────┘      └─────────────┘
          │ Send 动态扇出
   ┌──────┼──────┐
   │      │      │
┌──▼──┐┌──▼──┐┌──▼──┐
│专家A ││专家B ││专家C │   ← 各自内部 ReAct 循环
└──┬──┘└──┬──┘└──┬──┘
   │      │      │
   └──────┴──────┘
          │
   ┌──────▼──────┐
   │ MCP Server  │  ← 工具
   └─────────────┘
```

### ⑤ 深入关键点（⭐ 主动讲这三个）

**深入 1：编排怎么派活**

```
「编排 Agent 决定派给哪些专家，用 LangGraph 的 Send 做动态扇出——
运行时才确定数量，比静态扇出灵活。

专家之间不直接通信，都通过编排节点中转——避免 N×N 的通信复杂度。」
```

**深入 2：上下文管理（⭐ 最容易被问）**

```
「三层：
  短期：Checkpointer 按 thread_id 存会话状态
  压缩：SummarizationMiddleware 超限时摘要化
  长期：Store 存用户偏好，⭐ 不依赖摘要保留

关键认知：摘要会丢细节，所以必须记住的显式外置。」
```

**深入 3：可观测性**

```
「每轮记录 Thought/Action/Observation 到结构化日志。
跑偏时能定位到具体哪一步——是选错工具，还是工具返回了模型
不理解的内容。

另外要检测『连续相同 tool_call』——这是无限循环的最强信号。」
```

### ⑥ trade-off（⭐ 必说）

| 决策 | 我的选择 | 代价 | 什么时候改 |
|------|---------|------|-----------|
| 编排 | Supervisor 中心化 | ⚠️ 编排节点是瓶颈 | 专家数 > 20 考虑 Network |
| 通信 | 进程内状态流转 | ⚠️ 不能跨进程 | 跨团队时上 A2A |
| 状态 | PostgresSaver | ⚠️ 多一次 IO | 单机可换 SqliteSaver |
| 上下文 | 摘要压缩 | ⚠️ 丢细节 | 关键信息外置 Store |

## 二、⭐ 三个可能的追问方向

### 追问 1：专家 Agent 挂了怎么办？

**答**：⭐ 「三层：① 工具/模型调用有重试和降级（`ModelFallbackMiddleware`）；② 单个专家失败不让整个会话崩，编排节点可以跳过或换方案；③ 任务状态持久化，恢复后重试。」

### 追问 2：模型调用成本怎么控？

**答**：⭐ 「四层：① **LLM 响应缓存**（相同/相似 query 直接返回，Redis 实现）；② **按难度路由**（简单任务用小模型）；③ **控制轮数**（`recursion_limit` + 相同调用检测）；④ **上下文精简**（渐进加载 + 摘要，别每轮都付几万 token）。」

📌 [[redis/02-中段阶段-生产实践/03-缓存三大问题与缓存模式]]

### 追问 3：怎么保证不泄露别人的会话？

**答**：⭐ 「thread_id 加租户/用户前缀，检索时强制带前缀。⚠️ 光靠 thread_id 不够——**要防 ID 被猜测**，用不可猜测的随机 ID，并且授权检查放在服务端不是客户端。」

## 三、⭐ 如果题目是「跨组织」

⚠️ **这是加试题，答好直接上一档。**

```
「跨组织的话，架构要多一层：

  我方编排 Agent ──A2A──> 对方 Agent（黑盒）
                      ↑
                 读对方的 Agent Card（/.well-known/agent-card.json）
                 拿到技能清单、接口、鉴权方式

关键差异：
① 不能直接函数调用，要走 HTTP + 任务状态机
② 对方是黑盒——看不到内部实现，只能按契约对接
③ 鉴权要处理跨组织的 OAuth/mTLS
④ ⚠️ 要处理『对方拒绝受理』（rejected）和『中途反问』
   （input-required）——这两个是本地编排没有的状态

而且接入方要把远端 Agent 包成本地工具（agent-as-tool），
不要包成 MCP server——那会丢失有状态多轮的语义。」
```
