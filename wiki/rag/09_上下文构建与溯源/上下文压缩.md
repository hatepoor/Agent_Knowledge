# 上下文压缩（Contextual Compression）

> 检索链路第 9 步后半段（Post-Retrieval）。分层脚手架：粗召回放开 k 追求 Recall，过滤与压缩把噪声砍掉保住 Precision——"检索回 50 块、只喂给 LLM 5 块干净的"。门槛过滤见 [[rag/07_元数据过滤/元数据过滤]]。

## 概述

LangChain 官方博客的思路："让初始检索专注召回（加大返回文档数），由压缩器（compressors）负责精确度。"压缩区别于过滤（整块丢弃）与重排（只变顺序）：**压缩在块内保留相关语句、去掉噪声**，是"检索回 50 块 → 喂给 LLM 5 块干净"这条生产管线中承上启下的一环。

> API 级详解见 [[langchain/modules/langchain_retrievers/ContextualCompressionRetriever|ContextualCompressionRetriever]]。

## 一、什么是"压缩"

| 操作 | 输出变化 | 判定依据 | 成本 |
|------|----------|----------|------|
| 过滤 | 块数 ↓，内容不变 | 相似度阈值 / LLM 判定 / 元数据规则 | 低~中 |
| **压缩** | 块内容变短，只留相关语句 | LLM 逐块提取 | 高（每块一次 LLM 调用） |
| 重排 | 顺序变化 + 截断 | Cross-Encoder / LLM listwise | 中 |

核心组件：
- **`LLMChainExtractor`**：LLM 从每块中**只提取与查询相关的语句**，输出压缩后的文本——同时完成过滤与压缩；对长块、噪声密集块收益最大。
- **`LLMChainFilter`**：布尔判定不改内容（属过滤）。
- 三者可组合成 `DocumentCompressorPipeline`，也可与普通文档转换器（如 TextSplitter）串联。

## 二、标准管线：粗召回 → 便宜过滤 → 贵压缩

```python
# pip install -qU langchain-community langchain-openai langchain-chroma
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import (
    DocumentCompressorPipeline, EmbeddingsFilter, LLMChainExtractor,
)
from langchain_community.document_transformers import EmbeddingsRedundantFilter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI

# 管线：去冗余 → 相似度过滤（便宜） → LLM 逐块提取（贵而精）
pipeline = DocumentCompressorPipeline(transformers=[
    EmbeddingsRedundantFilter(embeddings=OpenAIEmbeddings()),     # 1) 语义去重
    EmbeddingsFilter(embeddings=OpenAIEmbeddings(),
                     similarity_threshold=0.75),                  # 2) 便宜的门槛过滤
    LLMChainExtractor.from_llm(
        ChatOpenAI(model="gpt-4o-mini", temperature=0)),          # 3) 块内压缩提取
])
compression_retriever = ContextualCompressionRetriever(
    base_compressor=pipeline,
    base_retriever=vectorstore.as_retriever(search_kwargs={"k": 50}),  # 粗召回给足
)
clean_docs = compression_retriever.invoke("A100 的显存带宽是多少")  # 输出少量干净块
```

> 设计原则：**便宜的过滤器放前面、贵的放后面**——LLM 压缩只处理已经过两轮筛减的少量候选，成本可控。

## 三、常见问题

**Q1：所有块都被过滤/压缩后为空怎么办？**
必须有兜底：① 降低阈值重试；② 返回未过滤的原始 Top-k 并在 prompt 声明"证据置信度低"；③ 触发查询改写重检索（[[rag/14_范式与前沿/Agentic_RAG|Agentic RAG 的 rewrite 节点]]）。静默返回空集是最差体验。

**Q2：LLMChainExtractor 会不会把块改写得失去引用价值？**
会——提取后的文本是"改写产物"，严格溯源场景应保留原始块与提取块的映射（原始块仍存 metadata），或在引用校验（[[rag/10_LLM生成/生成校验与防幻觉|生成校验]]）时对原文核验。

**Q3：过滤/压缩/重排都上会不会过度？**
会徒增成本。用评估集逐级消融（保留/去掉每一步看指标 Delta），每一步都必须有正贡献 + 满足延迟预算。

## 四、最佳实践

1. **召回优先、过滤保精**：粗召回 k 放大到 50–100，让过滤/压缩去抠精度——这是官方博客给出的核心分工。
2. **过滤压缩链按成本排序**：去冗余 → EmbeddingsFilter → （可选）LLM 压缩 → 重排；每步单独开关做消融。
3. **记录过滤漏斗**：50 → 32 → 8 → 5 的每级留存率是调参最直观的观测指标（[[rag/12_评估与监控/在线监控与可观测性|可观测性]]）。
