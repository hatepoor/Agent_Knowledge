# 检索索引类型与混合索引构建

> RAG 流程第 4 步。在选好向量库（[[rag/04_混合索引构建/向量数据库选型指南|向量数据库选型]]）与 Embedding（[[rag/04_混合索引构建/Embedding与向量检索]]）之后，决定"用哪种 ANN 索引结构、以及要不要词项索引起齐"来把分块落库索引。"混合索引构建"= 稠密（向量）+ 稀疏（词项）索引在入库侧同时建好，检索侧才能做 [[rag/06_混合检索/混合检索|混合检索]]。

## 一、向量索引结构：ANN 三兄弟

| 结构 | 原理 | 召回/速度 | 内存 | 适用 |
|------|------|-----------|------|------|
| **Flat（暴力扫描）** | 全量精确计算 | 召回最高、最慢 | 高 | 小规模(<几十万)或对精度敏感 |
| **IVF（倒排+聚类）** | 先聚类再在候选簇搜索 | 折中 | 中 | 中等规模 |
| **HNSW（分层小世界）** | 多层图近邻跳转 | 速度/召回均衡、主流 | 较高 | 大规模、低延迟默认选 |
| **DiskANN / 图变体** | 磁盘映射图 | 海量可扩展 | 低 | 亿级、成本敏感 |

> HNSW 是 2025–2026 生产默认；IVF 用于内存/成本敏感；召回要求极严则分层 HNSW，必要时的重排（[[rag/08_交叉编码器重排/重排序与交叉编码器|Cross-Encoder]]）弥补 ANN 损失。

### ANN 关键参数
- **ef_search / ef_construction（HNSW）**：搜索/建图时候选广度，越大召回越高、越慢。
- **nprobe（IVF）**：探测簇数，越大召回越接近全量。
- **M**：边数，影响图连接密度与内存。
> 原则：**先在 Flat 上建立"理想召回基线"，再逐档调 ANN 逼近**，用清晰的 Recall@k 而非直觉设参。官方文档：Qdrant indexing https://qdrant.tech/documentation/concepts/indexing/ · Milvus index https://milvus.io/docs/index.md · pgvector Indexes https://github.com/pgvector/pgvector#indexes

## 二、混合索引：稠密 + 稀疏同库就位

要让 [[rag/06_混合检索/混合检索|混合检索]] 不靠两套系统拼接，需要入库侧**同时建两类索引**：

| 方式 | 实现 | 典型库 |
|------|------|--------|
| 稀疏索引（BM25/FTS） | 词项倒排 + 打分 | Elasticsearch / OpenSearch / pgvector + PG fulltext |
| 稠密索引（向量 ANN) | HNSW/IVF | 见上 |
| 双通道混合 | sparse+dense 并存、融合查询 | Qdrant sparse-dense · Weaviate hybrid · Milvus hybrid |

> 关键：**embedding 模型升级 = 全量重建稠密索引**（向量语义空间变了，旧向量不可混用）；稀疏索引一般只需增量维护。这是高频事故源，见 [[rag/04_混合索引构建/索引与部署流水线|索引与部署流水线]] 的迁移章节。

## 三、混合索引构建的最佳实践

1. **索引即 schema，先设计再入库**：同库混合时，明确哪字段向量化、哪字段建词项、哪字段入元数据过滤（[[rag/07_元数据过滤/元数据过滤]]）。
2. **难度预算倒排**：召回要求高 + 数据量大 → HNSW + 精排补偿；规模小 → Flat 最诚实。
3. **索引参数版本化**：把维度、索引类型、ef/M 等连同 embedding 版本一起写进索引元数据，配合部署流水线做对账。
4. **入库与查询用同一套向量化 API**，避免离线/在线 embedding 不一致（会静默劣化检索）。
