# 向量数据库选型指南

## 概述

向量数据库是 RAG 的"记忆体"：存向量、做 ANN、带元数据过滤、管生命周期。选型不是"谁强用谁"，而是**在运维成本、功能完备度、与既有数据栈的亲和度之间做权衡**。本文给出一致对比框架与决策流程，并附各库官方出处。

> 相关 API 级用法见 [[langchain/modules/langchain_retrievers/VectorStoreRetriever|VectorStoreRetriever]] 与 [[langchain/modules/langchain_retrievers/自定义Retriever|自定义 Retriever]]。

## 零、结论先给（选型收敛）

市场上一堆向量库，但绝大多数项目只需在下面 4 个里挑一个，**不用在 9 个库里逐个比**：

| 你的处境 | 首选 | 何时才需要换/补 |
|---------|------|----------------|
| 原型、笔记、个人工具 | **Chroma**（嵌入式零运维） | 数据量上来、要长期生产才迁 Qdrant |
| 已重度使用 PostgreSQL | **pgvector**（与业务同事务） | 文本检索依赖强→改看 Elasticsearch |
| 自建生产独立向量库 · 通用/中文 | **Qdrant**（强过滤+量化，单机性能高） | 大多数新项目以此默认 |
| 生产 · 十亿级或原生多租户 | **Milvus**（分布式/分区）/ **Weaviate**（原生 multi-tenancy） | 明确是这两类诉求才上 |

> 一句话：**原型用 Chroma，已有 PG 用 pgvector，自建生产默认 Qdrant，只有"超大/强多租户"才上 Milvus 或 Weaviate。** 其余（FAISS / Pinecone / Redis / OpenSearch……）仅在下方任一条能稳定满足你时作为替换，不必都备齐。

## 一、先分清四类方案

| 类别 | 代表 | 本质 | 适合 |
|------|------|------|------|
| 独立向量数据库 | Milvus/Zilliz Cloud、Qdrant、Weaviate、Pinecone | 专为向量设计，功能全 | 生产主库、大规模、多租户、高可用 |
| 嵌入式/轻量 | Chroma、LanceDB、FAISS（库非库） | 进程内/单文件，零运维 | 原型、桌面、小规模 |
| 传统库扩展 | pgvector/PostgreSQL、OpenSearch、Redis | 借既有存储加向量能力 | 已有该数据库、数据需强一致/事务 |
| 云托管/平台内嵌 | 各云向量服务、LangChain 生态 | 免运维 | 快速上云 |

## 二、关键维度对比框架

| 维度 | 关注点 | 为什么重要 |
|------|--------|-----------|
| 索引类型 | HNSW/IVF/量化/多租户原生索引 | 决定召回-延迟-内存三角与租户隔离方式 |
| 过滤能力 | 元数据/标量过滤是否走索引、是否支持表达式 | 混合过滤（filter+vector）性能差异可达数量级 |
| 混合检索 | 是否内置 BM25/稀疏检索、RRF | 少一套 Elastic 组件；否则需自行拼装（02 层方案） |
| 多租户 | 原生 multi-tenancy vs 手动 tenant 过滤 | 影响隔离强度与运维，见 [[rag/13_工程横切/多租户与大并发|多租户与大并发]] |
| 部署形态 | 独立服务/嵌入式/托管 | 运维成本与数据边界 |
| 一致性/事务 | 与业务库同事务？ | 文档-索引强一致需求 |
| 生态 | LangChain/LlamaIndex 集成、备份、监控 | 工程效率 |

### 主流库快照（2025–2026 概览，参数以官方文档为准）

| 库 | 开源 | 核心特点 | 最适配场景 | 官方文档 |
|----|------|----------|-----------|----------|
| **Milvus** | 是(Apache-2.0) | 云原生分布式、分区/Partition 隔离、GPU 加速、十亿级 | 大规模生产、多租户隔离 | https://milvus.io/docs |
| **Qdrant** | 是(Apache-2.0) | Rust、payload 过滤强、量化支持好、单机性能高 | 中大规模生产、复杂过滤 | https://qdrant.tech/documentation/ |
| **Weaviate** | 是(BSD-3) | **原生多租户**（1.21+）、模块化向量化、GraphQL | 多租户 SaaS | https://weaviate.io/developers/weaviate |
| **Chroma** | 是(Apache-2.0) | 嵌入式、`where` 过滤、开箱即用 | 原型/个人项目 | https://docs.trychroma.com/ |
| **pgvector** | 是 | PostgreSQL 扩展、事务一致、SQL 生态 | 已有 PG、需要强一致 | https://github.com/pgvector/pgvector |
| **FAISS** | 是(MIT) | 检索算法库（非数据库）、极快 | 自建检索层/特征服务 | https://github.com/facebookresearch/faiss |
| **Elasticsearch/OpenSearch** | 是 | BM25 与向量一体、kNN、RRF 内置 | 已有 ES 的文本检索升级 | https://www.elastic.co/guide/ |
| **Pinecone** | 否(托管) | Serverless、命名空间、免运维 | 不想运维 | https://docs.pinecone.io/ |
| **Redis** | 是(RSAL) | 内存级、兼做语义缓存 | 已有 Redis、低延迟 | https://redis.io/solutions/vectordb/ |

## 三、决策流程

```
规模/团队/数据栈问题
 ├─ 已重度使用某数据库(Postgres/ES/Redis) 且数据强一致优先 → 先试其向量能力(pgvector/ES kNN/Redis)
 ├─ 原型/小数据 → Chroma 或 LanceDB（零成本起步）
 └─ 生产级、独立向量库 →
      ├─ 需要强多租户原生隔离 → Weaviate multi-tenancy
      ├─ 十亿级/分布式/多分区 → Milvus
      ├─ 强过滤+量化+单机够用 → Qdrant
      └─ 云上免运维 → Pinecone / 云厂商托管
最终校验：用真实数据+真实查询跑 Recall@k 与 P95 延迟基准，别只看宣传指标
```

## 四、LangChain 最小可运行示例（pgvector 与 Chroma 对照）

```python
# 例 1：pgvector（已有 Postgres 时最省事的路径）
# pip install -qU langchain-postgres psycopg[binary]
from langchain_postgres import PGVector

conn = "postgresql+psycopg://user:pass@localhost:5432/ragdb"
db = PGVector.from_texts(
    ["Postgres 里也能做向量检索", "pgvector 支持 HNSW 与 IVFFlat"],
    embeddings, connection=conn, collection_name="docs",
)
hits = db.similarity_search("向量检索怎么做", k=2)
```

```python
# 例 2：带元数据过滤（生产必会——用 tenant/date 等标量剪枝候选集）
# pip install -qU langchain-community qdrant-client
from langchain_qdrant import QdrantVectorStore
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")
store = QdrantVectorStore(client=client, collection_name="docs", embedding=embeddings)
store.add_texts(
    ["产品 A 使用手册", "产品 B 常见问题"],
    metadatas=[{"product": "A", "lang": "zh"}, {"product": "B", "lang": "zh"}],
)
# filter 走 Qdrant payload 索引，先按 product 剪枝再做向量搜索
docs = store.similarity_search("怎么升级", k=5, filter=models.Filter(
    must=[models.FieldCondition(key="product", match=models.MatchValue(value="A"))]
))
```

## 五、常见问题

**Q1：能用 FAISS 直接上生产吗？**
FAISS 是算法库不是数据库：无持久化/ACID/权限/多写多读治理，需自建存储与并发控制。小数据高可控场景可接受，规模化后通常迁移独立向量库或 pgvector。

**Q2：向量库和业务库要不要同一份？**
看一致性要求：文档删除后索引残留会造成"幽灵召回"。强一致场景选 pgvector（同事务）或"双写+补偿删除"；独立向量库要设计删除/更新同步机制（05 层 [[rag/04_混合索引构建/索引与部署流水线|索引与部署流水线]]）。

**Q3：怎么对比两个向量库的真实差距？**
同一批真实文档+同一 Embedding，跑同一组查询集，比 Recall@10、P95 延迟、内存占用与成本单价。榜单分数与你的领域数据无关。

**Q4：多租户数据会不会串？**
取决于隔离模式：原生多租户（Weaviate）、集合/分区隔离（Milvus partition、Qdrant collection per tenant、Pinecone namespace）还是 tenant_id 过滤共享集合。安全设计见 [[rag/13_工程横切/多租户与大并发|多租户与大并发]]。

## 六、最佳实践

1. **元数据过滤必须走索引**：无索引的标量过滤=全量扫描，会把 ANN 优势吃光。
2. **按查询模式建分区/集合**：如按租户、按文档类型、按日期归档分区，显著提升隔离与清理效率。
3. **固定 Embedding 维度与模型版本**：升级模型=重建集合；维度变更需迁移计划。
4. **量化兜底而非默认**：先用原精度 HNSW 测基线，再评估量化对领域 Recall@k 的影响。
5. **做好备份与恢复演练**：向量库与原始文档都要可重建——索引永远可以从 raw 文档重放，备份 raw 是最后防线。
