# 多语言与中英混排检索

## 概述

中英混排语料（英文技术文档 + 中文笔记、中英对照材料）对 RAG 的每个环节都有额外约束。本文给出分类框架与逐环节设计。

> 基础组件见 [[rag/04_混合索引构建/Embedding与向量检索|Embedding与向量检索]]；稀疏侧分词见 [[rag/06_混合检索/BM25算法详解|BM25算法详解]] 与 [[rag/06_混合检索/倒排索引|倒排索引]]。

## 一、先分类：三种形态，卡点不同

把"中英混排"当成一个问题会导致方案错配，它实际是三类：

| 形态 | 表现 | 卡在哪 |
|------|------|--------|
| **A. 文档内混排** | 同一 chunk 中英交错，如"`create_agent` 是 LangChain v2 的入口函数" | 分词与向量质量 |
| **B. 文档集混排** | 一部分文档全英文（官方 docs），一部分全中文（自己的笔记） | 查询语言与文档语言不匹配 → 跨语言检索 |
| **C. 查询侧混排** | 用户问："LangGraph 的 Send 机制怎么用？" | 中英分词器都要生效 |

真实场景通常是 **A+B+C 同时存在**。

## 二、核心判断：不要按语言分库

有一个值得放在最前面的结论：

> **多语言 RAG 本质上不是数据库问题，而是表示学习阶段的 embedding 对齐问题。**

现代多语言 embedding（BGE-M3、Qwen3-Embedding、multilingual-e5）在对比学习训练阶段已把中英语义投影到同一向量空间。只要模型选对，**中文 query 可以直接命中英文原文**，不需要翻译层或语言路由。

| 方案 | 做法 | 适用 | 代价 |
|------|------|------|------|
| **统一向量空间**（默认） | 所有语言用同一多语言 embedding，共用一个索引 | 绝大多数场景 | 依赖 embedding 的跨语言对齐质量 |
| 分语言索引 + 语言路由 | 按语言分库，查询时按检测语言路由 | **同一内容存在多语言版本**；或受监管场景需强制语言一致 | 维护成本翻倍，跨语言查询需额外路由逻辑 |

**一个常见误区**：中英对照的文档**不要当重复内容去重**。它们应视为独立文档各存一份，靠 embedding 的跨语言对齐让两者都能被召回——这反而是提升召回的免费加成。

## 三、Embedding 选型（核实于 2026-09）

| 模型 | 维度 | 显存/大小 | 许可 | 适配场景 |
|------|------|-----------|------|----------|
| **BGE-M3** | 1024 | 1.2GB | MIT | **中英混排首选**。单次前向同时产出 dense + sparse + multi-vector，8192 token，混合检索免第二套分词管线 |
| **Qwen3-Embedding-4B** | 2560 | ≈2.5GB | Apache 2.0 | 精度甜点，32K 上下文，MTEB 多语言第一梯队，输出已 L2 归一化 |
| Qwen3-Embedding-8B | 4096 | 4.68GB | Apache 2.0 | 最强，需 A100 级显卡 |
| multilingual-e5-large | 768 | — | MIT | 跨语言对齐扎实，但**必须**加 `query:` / `passage:` 前缀 |
| bge-large-zh-v1.5 | 1024 | — | — | 纯中文短文本，轻量 |
| OpenAI text-embedding-3-large | 3072 | API | — | 免运维，支持 MRL 截断省存储 |

> 截至目前没有 Qwen3.5 / Qwen3.6 的 embedding 模型，Qwen3-Embedding 仍是当前代，不是被取代的旧版。

**关键坑**：**BGE-M3 的 dense 输出未做 L2 归一化**，必须手动归一化，否则相似度失真（有实测因此低估效果约 8%）。Qwen3-Embedding 已自动归一化，**不要重复处理**。

## 四、预处理：四件必做的事

中英混排的预处理比单语言麻烦，核心原则是"**检测 → 规范化 → 双路分词**"：

| 动作 | 为什么必须做 |
|------|--------------|
| **Unicode NFC 归一化** | 同一汉字可能有多种 Unicode 编码形式，不归一化会出现字面相同却匹配不上 |
| **全角转半角** | 中文排版习惯产生全角逗号、括号、冒号，会污染分词与 term 匹配 |
| **chunk 级语言检测** | 混排文档**内部语言会切换**，按文档粒度打标签是错的。工具用 `lingua`（准确率优于 fastText / CLD3），置信度低的标 `und` 走字符级兜底 |
| **存两份文本** | `text_orig` 用于生成与引用溯源，`text_norm` 用于检索匹配 |

```python
import re, unicodedata
from lingua import Language, LanguageDetectorBuilder

# 全角 → 半角（含全角空格）
_FW = str.maketrans({
    **{chr(0xFF01 + i): chr(0x21 + i) for i in range(94)},
    "\u3000": " ",
})

def normalize(text: str) -> str:
    text = unicodedata.normalize("NFC", text)   # 1. NFC 规范化
    text = text.translate(_FW)                  # 2. 全角转半角
    return re.sub(r"[ \t]+", " ", text)         # 3. 压缩横向空白，不动换行

def lang_tag(chunk: str) -> str:
    """在 chunk 粒度打语言标签，而不是文档粒度"""
    has_zh = bool(re.search(r"[\u4e00-\u9fff]", chunk))
    has_en = bool(re.search(r"[A-Za-z]{3,}", chunk))
    if has_zh and has_en:
        return "mixed"          # 中英混排，单独标记便于后续分析
    if has_zh:
        return "zh"
    if has_en:
        return "en"
    return "und"                # 代码块/公式，字符级兜底
```

> 切分层面还需注意：**separators 要同时包含中英标点**（`。`、`！`、`？`、`. `）。但**切分边界与分词边界是两件独立的事**——切分用标题/段落/句末标点，分词用 jieba，不要混为一谈。详见 [[rag/03_智能分块/混合索引的分块策略|混合索引的分块策略]]。

## 五、稀疏路：中文必须分词

这是形态 A/C 的关键。中文没有空格词边界，而倒排索引的 key 是"词项"——不分词，整句会变成一个 token，**BM25 在中文上完全失效**。

```python
import jieba

def tokens_for_bm25(text: str) -> list[str]:
    # 检索建库用搜索引擎模式：长词二次切分，召回更高
    return list(jieba.cut_for_search(text))

# 领域术语必须注册，否则会被切碎（create_agent → create / _ / agent）
for term in ["LangGraph", "StateGraph", "create_agent", "Send", "Checkpointer"]:
    jieba.add_word(term, freq=10000)
```

**两条铁律**：
1. **索引阶段与查询阶段必须用同一分词器 + 同一份词典**，否则 token 空间不一致，结果无意义
2. **jieba 只服务稀疏路**。稠密路的 tokenize 由 embedding 模型自带的 tokenizer 负责（BGE-M3 用 XLM-RoBERTa 的 SentencePiece），**两者完全无关、互不共享**

> 若直接用 BGE-M3 的 sparse 输出（lexical weights），可以完全绕开 jieba。

## 六、评估：必须按语言组合分片

中英混排会让 RAGAS 的分数产生系统性偏差，见 [[rag/12_评估与监控/评估体系与RAGAS|评估体系与RAGAS]]：

- **Response Relevancy 依赖 embedding**：中文 query + 英文 answer 时，反向生成问题的相似度计算受 embedding 跨语言能力影响，分数**不可与单语言场景直接比较**
- **CP / CR 的裁判是 LLM**：中英混排上下文会引入语言切换，裁判判断稳定性下降
- **必须按语言组合分片统计**：`中文问→中文答`、`中文问→英文答`、`英文问→英文答` 分别算

整体均值会掩盖跨语言这一侧的短板——而跨语言恰恰是最需要监控的指标。

## 七、上线前必须验证的一件事

**测 embedding 的跨语言召回能力。** 准备 10–20 组"中文 query → 英文文档"的配对，计算 Recall@10。这是整套方案成立的前提假设，**不能靠厂商宣传判断**。

若表现不佳，两条应对路径：

| 路径 | 做法 | 评价 |
|------|------|------|
| **双语索引**（推荐） | 英文文档入库时由 LLM 生成中文摘要，摘要与原文一起索引。中文 query 命中摘要，生成时用英文原文 | 不破坏统一向量空间，成本可控 |
| 混用模型 | 英文文档换另一个 embedding 模型 | 破坏统一空间，需两套索引 + 跨空间分数融合，复杂度陡增，仅在摘要方案不够用时考虑 |

## 八、常见坑清单

1. **中英共用同一个 analyzer** —— 中文必须走 jieba / IK，英文走 standard。后果最严重且最易犯
2. **忘记 L2 归一化 BGE-M3 的 dense 向量** —— 相似度全部失真，且无报错、症状隐蔽
3. **按文档粒度打语言标签** —— 混排文档内部语言会切换，必须按 chunk
4. **把中英对照文档当重复内容去重** —— 应各存一份
5. **跨语言检索沿用单语言的 top-k** —— 初始召回噪声更高，稠密召回建议开到 50，不要只用 10
6. **评估不分语言切片** —— 整体均值掩盖跨语言短板
7. **未验证 embedding 的跨语言能力就上线** —— 前提假设未验证
8. **全角字符未归一化** —— 中文排版标点污染 term 匹配
