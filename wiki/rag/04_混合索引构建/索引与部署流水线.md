# 索引与部署流水线

## 概述

检索质量的天花板在索引侧：**脏文档、过期文档、不一致的索引**会让检索环节的一切调优归零。生产级 RAG 需要把"文档 → 索引"做成一条可观测、可重放、可回滚的**数据流水线（pipeline）**，并与在线服务解耦。本文给出索引流水线的完整生命周期、Embedding 模型升级的迁移方案与发布/回滚策略。

> 配套：架构总览见 [[rag/13_工程横切/生产级RAG系统架构|生产级 RAG 系统架构]]；分块与元数据设计见 [[rag/03_智能分块/文档分块策略|文档分块策略]]。

## 一、索引流水线的五个阶段

```
采集/触发 ─► 解析与清洗 ─► 分块与元数据 ─► 向量化 ─► 写入与校验
(事件/定时/手动)  (PDF/Word/HTML/扫描件)  (结构感知+去重)  (Embedding 批量)  (索引+对账)
     ▲                                                        │
     └────────────── 失败重试 / 告警 / 补偿 ──────────────────┘
```

| 阶段 | 关键动作 | 常见坑 |
|------|----------|--------|
| 采集 | 来源接入（网盘/DB/上传/爬虫），事件驱动触发 | 重复采集、增量漏采 |
| 解析清洗 | OCR（扫描件）、表格/版式还原、去页眉页脚、去重（hash） | OCR 错字直接污染语义 |
| 分块 | 结构感知分块 + 元数据（来源/层级/版本/权限标签） | 块切断语义、元数据缺权限字段 |
| 向量化 | 批量 Embedding + 幂等（同 hash 不重算） | 模型版本漂移 |
| 写入校验 | 增量 upsert、删除同步、块数与文档对账 | 幽灵块（文档删了索引还在） |

## 二、可重放与对账（数据面纪律）

1. **raw 文档是唯一事实源**：对象存储按内容寻址保存（文档 hash 命名），向量库/元数据库都视为"可从 raw 重放的派生数据"。
2. **索引任务幂等**：以 `(文档 hash, chunker 版本, embedding 版本)` 为任务键，重复触发不产生重复块。
3. **对账任务**：周期性比对"raw 文档数 vs 索引块归属"；发现孤儿块（无对应 raw）与缺失块（raw 有而索引无）即告警并补偿。
4. **删除闭环**：文档更新/删除事件 → 索引增量更新；软删保留审计、硬删清块——与 [[rag/11_安全审核与日志/安全与合规|合规删除权]] 打通。

## 三、Embedding 模型升级与索引迁移（高频事故源）

Embedding 升级 = 索引 schema 变更：新模型向量空间不同，旧索引不可用。推荐**影子索引 + 双写**策略：

```text
① 新集合(模型 v2) 与旧集合(模型 v1) 并行
② 全量/增量把文档灌入新集合（影子构建，不影响线上）
③ 对账 + 用 golden set 跑 v1 vs v2 检索质量对比（Recall@k）
④ v2 质量达标 → 切查询流量到 v2（灰度：5%→50%→100%）
⑤ 旧集合保留 N 天作回滚窗口，期满清理
```

关键规则：
- 查询侧 Embedding 与索引侧**必须同版本**，一次升级必须"索引先建好、查询再切换"，顺序错了=静默全量检索失效。
- 每个集合记录元数据：`embedding_model、维度、chunker 版本、数据集 hash、构建时间`——可观测与回放的地基。

## 四、发布与部署策略

| 变更类型 | 发布策略 | 回滚手段 |
|----------|----------|----------|
| 索引内容更新 | 增量流水线 + 对账 | 重建该批文档块（幂等） |
| Embedding/分块变更 | 影子索引双写 + 灰度切流 | 切回 v1 集合 |
| Prompt/模型变更 | 流量百分比灰度 | feature flag 即时回切 |
| 检索器/重排变更 | A/B 对比（同流量分流） | 开关回退 |
| 全链路 | 蓝绿/金丝雀部署，观测对比（[[rag/12_评估与监控/在线监控与可观测性|SLO 看板]]） | 回滚上一发布版本 |

发布前哨卡（CI）：格式校验（frontmatter/配置）、离线评估回归（RAGAS，质量不降才放行）、安全注入用例（[[rag/11_安全审核与日志/安全与合规|安全回归]]）。

## 五、常见问题

**Q1：增量索引怎么保证不错不漏？**
用文档级"更新时间戳 + 内容 hash"双因子判断变更；事件总线驱动（上传/编辑触发），定时全量扫描兜底（如每日对账）。绝不用"删库重建"当常规手段。

**Q2：扫描件/图片类文档怎么进索引？**
先 OCR（质量校验：置信度、版面还原），再做表格结构化，最后分块。OCR 错误率直接影响检索——建议 OCR 后人工抽检 + 关键字段二次校验。

**Q3：单次全量重建要几小时，能优化吗？**
拆流水线并行（按文档域分片）、批量 Embedding API、只重建变更分片；常态化"影子索引"使重建对线上零影响。重索引频率与文档变更频率匹配即可，不必每次全量。

**Q4：索引出错（如脏数据进库）怎么快速止血？**
分片隔离：按文档域/租户分集合分区，出问题只重建该片；配合对账告警在"污染扩散前"发现。备好"一键回滚到上一索引快照"。

## 六、最佳实践

1. **索引流水线当"数据产品"运营**：监控项含成功率、对账偏差、增量延迟；每类文档源有独立的健康度。
2. **一切可重放**：从 raw 到索引的任何一步坏了都能重跑；流水线代码与 raw 一起版本化。
3. **变更的最小单元是"集合+版本"**：先影子构建、再灰度切流、留回滚窗口——把索引升级做成标准操作而不是事故。
4. 文档治理（去重/过期/权限标注）是持续任务而非一次性清洗，配合 [[rag/12_评估与监控/评估体系与RAGAS|评估体系]] 形成"索引质量-检索质量"联动看板。
