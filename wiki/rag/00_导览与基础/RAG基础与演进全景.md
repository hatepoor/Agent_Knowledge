# RAG 基础与演进全景

## 概述

RAG（Retrieval-Augmented Generation，检索增强生成）在生成前先从外部知识源**检索**相关证据，再将证据注入提示词，让 LLM **基于证据生成**。它不是某个库，而是一类可组合的**架构模式**：2024–2026 年的演进主线是从"线性三段流水线"走向"模块化、Agent 化"。

> 概念层速览见 [[agent/RAG/RAG核心概念与演进|agent/RAG 核心概念与演进]]（Agent 视角）；本文从系统学习主线重讲其原理边界与全景坐标系。

## RAG 解决什么问题、不解决什么

| 能力 | RAG 的作用 | 边界与误区 |
|------|-----------|-----------|
| 幻觉 | 提供事实锚点，可显著降低（非消除）幻觉 | 检索质量差时"坏上下文"照样带偏生成 |
| 时效性 | 知识库实时更新，不受训练 cutoff 限制 | 文档未更新=答案未更新 |
| 私域知识 | 把私有文档接进 LLM | 权限与敏感数据是**新增**的安全面 |
| 推理/全局综合 | 弱——逐块检索缺乏全局视角 | 全局问题建议 [[rag/14_范式与前沿/GraphRAG与知识图谱|GraphRAG]] 或长上下文方案 |

**RAG 的本质**是"内存外置"：把模型的参数记忆换成可控、可更新、可审计的检索空间。因此评估 RAG 的收益要看三件事：召回是否够、证据是否真、引用是否对得上——这正是 04 层评估体系的由来。

## 三代演进坐标系

Gao et al. 2024 综述（arXiv:2312.10997）把 RAG 划分为三个阶段，是目前引用最广的分类法：

### 1. Naive RAG（朴素 RAG）
线性流水线 `Index(切块+向量化) → Retrieve(Top-K) → Generate(拼接生成)`。
**痛点**：分块粒度一刀切、相似度检索召回碎片化、无查询改写、无重排，检索质量与上下文纯度都不可控。

### 2. Advanced RAG（高级 RAG）
把流水线拆成三段可独立优化的阶段：

| 阶段 | 典型手段 | 本目录对应页面 |
|------|----------|----------------|
| Pre-Retrieval（检索前） | 文档清洗、分块策略、元数据、查询改写/扩展 | [[rag/03_智能分块/文档分块策略|分块]] · [[rag/05_查询转换与改写/查询改写与扩展|查询增强]] |
| Retrieval（检索中） | 混合检索（稀疏+稠密）、领域 Embedding 微调、重排 | [[rag/04_混合索引构建/Embedding与向量检索|Embedding]] · [[rag/06_混合检索/混合检索|混合检索]] |
| Post-Retrieval（检索后） | 重排 Top-N、上下文压缩、去噪 | [[rag/06_混合检索/混合检索|重排序]] · [[rag/05_查询转换与改写/查询改写与扩展|上下文构建]] |

### 3. Modular RAG（模块化 RAG，当前主流工程范式）
检索、记忆、路由、预测、任务适配被拆成**可插拔模块**，同一问题可走多路径（如"先路由：直接答 / 查库 / 联网"）。其自然延伸就是 Agentic RAG：由 LLM 作为控制器动态编排这些模块，见 [[rag/14_范式与前沿/Agentic_RAG|Agentic RAG]]。

## 一条 RAG 请求的完整数据流

```
User Query
   │  (1) 查询理解/改写          ← 是否多跳？是否需查最新？术语是否对齐知识库？
   ▼
[Router 路由] ──直接答──► LLM（无需外部知识）
   │ 需要检索
   ▼
(2) 检索：Query 向量化 ──► 向量库 ANN 搜索 Top-K
   │              └──► 稀疏检索（BM25）─► 混合融合（RRF）─► 重排（Cross-Encoder）
   ▼
(3) 上下文构建：Top-N 证据 + 元数据 → 去重/压缩 → 组装 Prompt
   ▼
(4) 生成：LLM 基于证据作答（要求引用出处）
   ▼
(5) 校验/观测：引用是否被证据支持？耗时/成本/质量指标上报
```

每个环节都有独立的质量放大器与成本放大器——这是为什么"RAG 调优"本质上是**分环节定位瓶颈**，而不是整体玄学调参。

## 工程上 RAG 的四个性能瓶颈区间（经验法则）

| 瓶颈 | 典型症状 | 首选排查方向 |
|------|----------|--------------|
| 召回不足 | 答非所问、漏关键点 | 分块粒度、混合检索、查询改写、Embedding 与领域匹配度 |
| 上下文被污染 | 答案有矛盾/引用无关 | 重排、上下文压缩、元数据过滤 |
| 生成不稳 | 同样的证据答法漂移 | Prompt 约束、引用格式、temperature 下调 |
| 全链路慢/贵 | P95 超标、账单高 | 语义缓存、重排窗口、Token 预算、小模型路由 |

## 常见问题

**Q1：RAG 和 Fine-tuning 怎么选？**
RAG 适合"知识快速变化、需要溯源、私有文档量大"；微调适合"固化风格/领域格式/行为"。两者互补：常以 RAG 提供事实、微调提供行为（"检索到的答案用产品语气回答"）。详见 [[meta/RAG_vs_Wiki|RAG vs Wiki]] 讨论的同类取舍。

**Q2：RAG 是不是已经被长上下文取代了？**
没有。2025–2026 的主流结论是**长上下文与 RAG 互补而非互斥**：长上下文解决"单篇超长文档深读"，RAG 解决"海量文档中找到对的片段"。两者混合（长上下文 + 精筛）是生产常见形态，见 [[rag/14_范式与前沿/多模态与长上下文RAG|多模态与长上下文RAG]]。

**Q3：为什么我"加了 RAG 反而更差"？**
通常是检索环节带回无关或冲突上下文。第一步不是换模型，而是做检索质量诊断：人工看 Top-K 命中是否相关；用 [[rag/12_评估与监控/评估体系与RAGAS|RAGAS]] 的 Context Precision/Recall 定位是召回还是重排问题。

## 最佳实践

1. **先定评价指标再动结构**：任何 RAG 改动都应有离线指标（Recall@k、Faithfulness）背书。
2. **把 RAG 当作可观测系统**：每轮请求记录"检索了什么、重排后剩什么、引用了哪块"，可观测是调优的前提（[[rag/12_评估与监控/在线监控与可观测性|生产可观测性]]）。
3. **从 Naive 起步、按证据升级**：先跑通最小闭环并量化基线，再逐项加混合检索/重排/查询改写，每次只改一个变量。
4. **知识库治理先行**：脏文档、重复文档、过期文档是 RAG 质量上限的天花板，索引侧治理优先于检索侧炫技。
