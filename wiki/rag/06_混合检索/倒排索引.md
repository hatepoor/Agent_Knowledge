# 倒排索引

## 定义

**倒排索引（Inverted Index）是"词项 → 包含该词项的文档列表"的映射结构。** 它是全文检索与 BM25 打分的底层物理数据结构——不是算法，而是存储结构。

> 本文讲**索引结构本身**。基于它打分的算法见 [[rag/06_混合检索/BM25算法详解|BM25算法详解]]；与向量索引的协同见 [[rag/06_混合检索/混合检索|混合检索]]；稠密侧的对应结构见 [[rag/04_混合索引构建/检索索引类型与混合索引|索引类型与混合索引（ANN）]]。

## 一、为什么叫"倒排"：与正排索引对比

| 维度 | 正排索引 Forward Index | 倒排索引 Inverted Index |
|------|------------------------|-------------------------|
| 映射方向 | 文档 ID → 该文档包含的词项列表 | 词项 → 包含该词项的文档 ID 列表 |
| 回答"哪些文档含 X" | 必须遍历所有文档逐个检查 → **O(N)** | 以 X 为 key 查一次 → **接近 O(1)** |
| 回答"某文档含哪些词" | 直接读 → O(1) | 需要重建 → O(N) |
| 典型载体 | MySQL 行记录、JSON 文档、Python dict | Lucene / Elasticsearch / OpenSearch 的核心资产 |

"倒排"之名即来自**映射方向的反转**：文档被存储时的自然顺序是"先有文档、再数它有什么词"（正排）；检索需要的是反向查询，于是把映射倒过来存一份。

> 检索要回答的正是前者，所以全文检索必须用倒排。这也是为什么 ES 的索引文件比原始文档大——它付出了额外存储，换取查询从 O(N) 降到接近 O(1)。

## 二、结构组成：词典 + 倒排列表

倒排索引由两大部分构成：

1. **词典（Term Dictionary / Lexicon）**：所有出现过的词项构成的有序集合，提供"某词是否存在、它的列表在哪"的查找能力
2. **倒排列表（Posting List）**：每个词项对应一个列表，记录该词出现在哪些文档，及附加统计信息

### 倒排列表里存什么（posting 的字段）

这是最容易被忽略、但决定 BM25 能否工作的部分。一条 posting 通常包含：

| 字段 | 含义 | 用途 |
|------|------|------|
| `doc_id` | 文档编号 | **必须**，标识命中 |
| `tf`（term frequency） | 该词在本文档中的出现次数 | **BM25 打分的输入**（词频饱和函数的自变量） |
| `positions` | 词在文档中的位置列表 | 支持短语查询（"Send 机制"要求两词相邻） |
| 字段标记 | 命中发生在标题还是正文 | 字段加权（标题命中给更高分） |

示例：

```
词项 "RAG"
  → Doc1: tf=3, positions=[2, 45, 102]
  → Doc2: tf=1, positions=[8]
  → Doc3: tf=2, positions=[15, 77]
```

**关键推论**：BM25 公式里需要的三个量，全部来自倒排索引——
- `tf`（词频）→ 直接从 posting 取
- `df`（文档频率）→ 就是 posting list 的**长度**
- `|d|`（文档长度）→ 文档级元数据

所以倒排索引不只负责"找到候选文档"，还负责**提供打分所需的全部统计量**。删除 `tf` 字段，BM25 就无法计算。

## 三、查询是怎么执行的

以查询 `"Send 机制怎么用"` 为例（中文场景，衔接 [[rag/06_混合检索/BM25算法详解|jieba 分词]]）：

```
query: "Send 机制怎么用"
   ↓ 分词（jieba / IK Analyzer）
tokens: [Send, 机制, 怎么, 用]
   ↓ 查词典定位各词的 posting list
Send → [D1, D3]      机制 → [D1]      怎么 → []      用 → [D5, D9]
   ↓ 过滤停用词（"怎么"通常被滤掉）+ 求交集
候选文档: [D1]
   ↓ 按 BM25 打分（用 tf、df、文档长度）
排序输出: D1
```

三个值得注意的点：

1. **求交是性能热点**。多个词的 posting list 需要找共同文档，最坏情况是逐个比对。工程上用**跳表（skip list）**加速——在列表上每隔一段建立跳跃指针，能快速跳过不可能匹配的区间。这是"多词 AND 查询"能保持毫秒级的原因。
2. **零命中词直接短路**（如上面的"怎么"），省掉后续计算。
3. **排序发生在求交之后**，且只对候选集打分，不是全库扫描。

## 四、工程实现的两个难点

### 难点 1：词典太大 → 用 FST 压缩

词项数量可达百万级，直接存字符串词典内存吃不消。Lucene 的做法是 **FST（Finite State Transducer，有限状态转换器）**：把词典压缩成有向无环图，**共享公共前缀与后缀**，内存占用可降到原词典的几十分之一，同时仍支持前缀查找。

> FST 也是"自动补全"能高效工作的原因——它天然支持按前缀遍历。

### 难点 2：倒排列表太长 → 用增量编码压缩

高频词（如中文的"的"、英文的"the"）在千万级语料中可能出现上亿次，posting list 会非常长。两个标准手段：

- **增量编码（delta encoding）**：posting list 中 `doc_id` 是递增有序的，所以不存绝对值，只存与前一条的**差值**。差值通常很小，占用字节数极少。
- **变长整数编码（VByte / VarInt）**：小数值用 1 字节，大数值才扩展到 2–4 字节，进一步压缩。
- **Roaring Bitmap**：位图方案，适合极长的列表，且支持快速的位运算求交。

> 这一层是搜索引擎的"内功"：不做压缩，索引文件会大到无法放进内存，检索延迟直接崩掉。

## 五、与向量索引的对比

RAG 的混合检索之所以要跑两路，根源在两种索引的**能力差异**：

| 维度 | 倒排索引（稀疏） | 向量索引（稠密，见 [[rag/04_混合索引构建/ANN近似最近邻搜索|ANN]]） |
|------|------------------|------------------------------|
| 匹配方式 | 词项**精确匹配** | 语义**相似度**（近似最近邻） |
| 强项 | 标识符、术语、编号、低频精确词 | 同义改写、跨语言、模糊表述 |
| 弱项 | 词汇鸿沟（换个说法就查不到） | 精确匹配不敏感（`Send` 与 `Sending` 可能混淆） |
| 中文前置 | **必须分词**（jieba / IK） | 无（模型自带 tokenizer） |
| 增量维护 | 容易（新文档追加，但 IDF 会变） | 较难（HNSW 图结构插入代价高） |
| 打分依据 | 词频统计（TF/IDF） | 向量距离（余弦/内积） |

**两者强项互补，所以走两路再融合**（[[rag/06_混合检索/混合检索|RRF 融合]]），而不是二选一。

## 六、中文场景的特殊约束

**中文没有空格作为词边界，而倒排索引的 key 是"词项"。** 这意味着：

- 直接按空格切分 → 整句变成一个"词项" → 倒排索引形同虚设 → **BM25 在中文上完全失效**
- 必须先用分词器（jieba / IK Analyzer）切词，再建索引；**索引与查询必须用同一分词器、同一份自定义词典**，否则 token 空间不一致，检索结果无意义

这直接决定了架构选择：

| 检索路径 | 谁负责 tokenize |
|----------|-----------------|
| 稀疏（倒排索引 / BM25） | jieba 或 ES 的 IK Analyzer |
| 稠密（向量） | embedding 模型自带的 tokenizer（如 BGE-M3 的 SentencePiece） |

**两者完全独立，互不共享。** 详见 [[rag/06_混合检索/BM25算法详解|BM25算法详解]] 的分词章节。

## 七、常见问题

**Q1：倒排索引和向量索引能放在同一个库里吗？**
能。Qdrant、Milvus、Weaviate 都支持同一集合内并存稀疏与稠密向量，ES 则用 `dense_vector` 字段加向量检索。这属于入库侧设计，见 [[rag/04_混合索引构建/检索索引类型与混合索引|索引类型与混合索引]]。

**Q2：文档更新后倒排索引要重建吗？**
不用全量重建，但**IDF 会变**（依赖全局的 N 与 df），所以分数需重算。`rank_bm25` 这类内存实现是"整体重算"，不支持增量；ES 天然支持增量写入并维护统计。高频更新场景建议上 ES 而非内存 BM25。

**Q3：为什么我的 BM25 对某些查询完全无结果？**
最常见两个原因：① 中文未分词；② 查询词未登录词典且被切碎（如 `create_agent` 被切成 `create` / `_` / `agent`）。解法是维护自定义词典。

**Q4：posting list 里存 `positions` 会不会太占空间？**
会显著增加索引体积。所以很多实现提供"是否存储位置"的开关——不需要短语查询时可关掉，节省 30%–50% 空间。
