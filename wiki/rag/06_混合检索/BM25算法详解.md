# BM25 算法详解

> 检索链路第 6 步。本文专讲 BM25 **算法原理**（公式拆解 + 手算例子）；工程封装见 [[langchain/modules/langchain_retrievers/BM25Retriever|BM25Retriever]]；与向量检索融合策略见 [[rag/06_混合检索/混合检索|混合检索]]。

## 概述

BM25（Best Matching 25）是**基于词频统计的稀疏检索打分算法**，由 Robertson 于 1990 年代在 Okapi 系统中提出。它通过倒排索引实现高效检索，用**饱和词频**和**文档长度归一化**两个关键改进修正了 TF-IDF 的缺陷。在 RAG 中作为**词法检索通道**与向量检索互补使用。

---

## 一、从 TF-IDF 到 BM25

### TF-IDF 回顾

TF-IDF 由两个零件组成：

- **TF（词频）**：词 `t` 在文档 `d` 中出现次数。出现越多 → 越相关。
- **IDF（逆文档频率）**：词 `t` 在多少篇文档出现过。出现越少 → 区分度越高。

$$\text{IDF}(t) = \log\left(\frac{N}{df(t)}\right)$$

- `N` = 文档总数
- `df(t)` = 包含词 `t` 的文档数

比如"的"出现在几乎所有文档 → df 大 → IDF 接近 0 → 权重几乎为零。"BM25"只在少数文档出现 → df 小 → IDF 大 → 权重高。

### TF-IDF 的三个问题（BM25 要修的）

| 问题 | 现象 | TF-IDF 的缺陷 |
|------|------|----------------|
| TF 无上限 | 词出现 100 次比 1 次分数高 100 倍 | 高频词主导排序，长文档刷分 |
| 长文档天然占便宜 | 长文档词多，TF 自然高 | 不公平 |
| IDF 不够平滑 | 某词只出现在 1 篇文档时 IDF 极大 | 极端值导致排序不稳定 |

---

## 二、BM25 完整公式

$$\text{score}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t, d) \cdot (k_1 + 1)}{f(t, d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}$$

看着吓人，拆成 **4 个零件** 就清楚了。

### 零件 1：IDF（平滑版）

$$\text{IDF}(t) = \log\left(\frac{N - df(t) + 0.5}{df(t) + 0.5} + 1\right)$$

和经典 IDF 的区别：分子分母各加了 `0.5` 做拉普拉斯平滑——防止某词只出现在 1 篇文档时 IDF 爆炸。加了 `+1` 保证 IDF 恒为非负。

**直觉理解**：这个词有多"稀有"。越稀有 → IDF 越大 → 命中后加分越多。

### 零件 2：TF 饱和函数（核心改进）

$$\frac{f(t, d) \cdot (k_1 + 1)}{f(t, d) + k_1}$$

`f(t, d)` 是词 `t` 在文档 `d` 中的出现次数。

**关键特性：饱和增长**——TF 越大，分数增长越慢，最终趋近上限 `k₁ + 1`。

| TF（出现次数） | 分数（k₁=1.5） | 相对于上限 2.5 |
|----------------|----------------|-----------------|
| 0 | 0 | 0% |
| 1 | 1.0 | 40% |
| 3 | 1.67 | 67% |
| 10 | 2.17 | 87% |
| 100 | 2.47 | 99% |

**对比 TF-IDF**：TF-IDF 里 TF 线性增长（出现 100 次是 1 次的 100 倍），BM25 让它"涨到一定程度就不涨了"——因为一个词出现 3 次 vs 10 次，对相关性的贡献差别不大。

**`k₁` 的作用**：控制饱和速度。

| k₁ 值 | 效果 | 适用场景 |
|--------|------|----------|
| 0 | 完全忽略词频（只看有没有） | 矿物/法律文档，关键词出现即算 |
| 1.2~2.0 | 正常饱和（默认 1.5） | 大多数场景 |
| ∞ | 退化为线性 TF（= TF-IDF） | 不推荐 |

### 零件 3：文档长度归一化

$$\left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)$$

- `|d|` = 当前文档长度（词数）
- `avgdl` = 全体文档平均长度

**作用**：这篇文档比平均长度长多少，就给 TF 部分打多少折扣。

| 文档长度 | 归一化因子（b=0.75） | 效果 |
|----------|----------------------|------|
| `|d| = avgdl` | 1.0 | 正常长度，无惩罚 |
| `|d| = 2×avgdl` | 1.75 | 长文档，TF 被稀释，打折 |
| `|d| = 0.5×avgdl` | 0.625 | 短文档，浓缩，加分 |

**为什么需要**：长文档天然词多、TF 自然高，如果不归一化，长文档永远排在前面。归一化让"短而精"的文档也有机会。

**`b` 的作用**：控制惩罚力度。

| b 值 | 效果 |
|------|------|
| 0 | 完全不惩罚长度（所有文档一视同仁） |
| 0.75（默认） | 适度惩罚 |
| 1 | 最强惩罚（长度影响最大化） |

### 零件 4：求和 Σ

对查询 `q` 里的**每个词** `t` 分别算上面三零件的乘积，然后**加起来**。

也就是说：一篇文档的 BM25 分数 = 查询里每个词各自贡献的分值之和。查询里多个词都命中了同一篇文档 → 分数叠加 → 排名更靠前。

## 三、手算例子

假设有 4 篇文档：

| 文档 | 内容 | 长度 |
|------|------|------|
| D1 | "RAG 检索 增强 生成" | 4 词 |
| D2 | "RAG 是 检索 增强 生成 的 框架" | 7 词 |
| D3 | "向量 检索 是 语义 搜索" | 5 词 |
| D4 | "RAG 和 向量 检索 可以 结合" | 6 词 |

查询 `q = "RAG 检索"`，参数 k₁=1.5, b=0.75。

### 全局统计量

- N = 4（4 篇文档）
- avgdl = (4+7+5+6)/4 = 5.5

### 词频统计

| 词 | D1 | D2 | D3 | D4 | df(t) |
|----|----|----|----|----|--------|
| RAG | 1 | 1 | 0 | 1 | 3 |
| 检索 | 1 | 1 | 1 | 1 | 4 |

### 算 IDF

```
IDF("RAG") = log((4 - 3 + 0.5) / (3 + 0.5) + 1)
           = log(1.5/3.5 + 1) = log(1.429) ≈ 0.357

IDF("检索") = log((4 - 4 + 0.5) / (4 + 0.5) + 1)
            = log(0.5/4.5 + 1) = log(1.111) ≈ 0.105
```

"检索"出现在所有文档 → IDF 低（区分度低）；"RAG"出现在 3 篇 → IDF 高一些。

### 算 D1 的分数

D1 长度=4，RAG 出现 1 次，检索出现 1 次：

```
TF饱和(RAG, D1) = 1 × (1.5+1) / (1 + 1.5) = 2.5/2.5 = 1.0
长度归一(D1) = 1 - 0.75 + 0.75 × (4/5.5) = 0.25 + 0.545 = 0.795

RAG 贡献 = 0.357 × 1.0 / 0.795 ≈ 0.449

TF饱和(检索, D1) = 1 × 2.5 / (1 + 1.5) = 1.0
检索 贡献 = 0.105 × 1.0 / 0.795 ≈ 0.132

score(D1) = 0.449 + 0.132 ≈ 0.581
```

### 算 D2 的分数

D2 长度=7，两个词各出现 1 次：

```
长度归一(D2) = 0.25 + 0.75 × (7/5.5) = 0.25 + 0.955 = 1.205

RAG 贡献 = 0.357 × 1.0 / 1.205 ≈ 0.296
检索 贡献 = 0.105 × 1.0 / 1.205 ≈ 0.087

score(D2) = 0.296 + 0.087 ≈ 0.383
```

D2 比 D1 长 → 归一化因子更大 → 同样的 TF 被打折 → 分数更低。

### 完整排序结果

| 文档 | 长度 | RAG 命中 | 检索命中 | 分数 | 排名 |
|------|------|----------|----------|------|------|
| D1 | 4 | ✓ | ✓ | **0.581** | 1 |
| D4 | 6 | ✓ | ✓ | ~0.45 | 2 |
| D2 | 7 | ✓ | ✓ | **0.383** | 3 |
| D3 | 5 | ✗ | ✓ | ~0.13 | 4 |

D3 只命中了"检索"（且"检索"的 IDF 很低），没命中"RAG"，所以分数最低。D1 最短且两个词都命中，排第一。

## 四、参数调优速查

| 参数 | 默认 | 调大效果 | 调小效果 | 建议 |
|------|------|----------|----------|------|
| k₁ | 1.5 | 更重视词频差异 | 更忽略词频（只看有没有） | 0.5~2.0，默认即可 |
| b | 0.75 | 更惩罚长文档 | 更不惩罚长度 | 0.5~0.8，默认即可 |

**大多数场景不需要调**，这两个默认值是 Robertson 经验校准的近最优值。

---

## 五、底层依赖：倒排索引

BM25 的计算效率来自**倒排索引**——它不是去扫每篇文档，而是维护一张"词 → 出现在哪些文档"的表：

```
"RAG"   → [D1:1, D2:1, D4:1]       ← 直接知道哪些文档包含"RAG"
"检索"  → [D1:1, D2:1, D3:1, D4:1]
```

查询时只需查表 → 取交集 → 算分数 → 排序。复杂度是 O(命中文档数)，不是 O(全库)，所以即使千万级文档也能毫秒返回。

## 六、在 RAG 中怎么使用

### 在管线里的位置

```
文档入库                           查询时
┌─────────┐    ┌──────────┐       ┌─────────┐
│ 文档分块 │ →  │ 向量化入库 │       │ 用户查询 │
└─────────┘    └──────────┘       └────┬────┘
      ↓              ↓                  │
┌──────────────┐  ┌──────────┐         │
│ BM25 倒排索引 │  │ 向量索引   │ ←─────┘
│ （另建一份）  │  │ （主索引） │
└──────┬───────┘  └─────┬────┘
       │                 │
       ▼                 ▼
  BM25 Top-K        向量 Top-K
       │                 │
       └────────┬────────┘
                ▼
          RRF 融合排序  ← [[rag/06_混合检索/混合检索|混合检索]]
                │
                ▼
          喂给 LLM 生成回答
```

关键点：**BM25 不替代向量检索，而是和它并行跑，各召回一批，再融合**。单独用 BM25 有词汇鸿沟问题（"成本"搜不到"费用"），单独用向量有精确词失配问题（"A100-80G"搜不准）。

### 完整代码：从零搭建混合检索

```python
# pip install rank-bm25 langchain langchain-community langchain-chroma langchain-openai jieba

from langchain_core.documents import Document
from langchain_community.retrievers import BM25Retriever
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain.retrievers import EnsembleRetriever
import jieba

# ---- 1. 文档入库 ----
docs = [
    Document(page_content="LangChain 是 LLM 应用开发框架", metadata={"source": "intro.md"}),
    Document(page_content="BM25 是基于词频统计的关键词检索算法", metadata={"source": "bm25.md"}),
    Document(page_content="向量检索通过 embedding 语义相似度匹配文档", metadata={"source": "vector.md"}),
    Document(page_content="RAG 通过检索增强生成，减少幻觉", metadata={"source": "rag.md"}),
]

# ★ 中文必须预处理分词，否则 BM25 按空格切 → 中文整句变一个词
def preprocess(text: str) -> str:
    return " ".join(jieba.cut(text))

docs_for_bm25 = [
    Document(page_content=preprocess(d.page_content), metadata=d.metadata)
    for d in docs
]

# 路1：BM25 索引（倒排索引，纯 CPU，无 API Key）
bm25 = BM25Retriever.from_documents(docs_for_bm25)
bm25.k = 5

# 路2：向量索引（用原始未分词文本做 embedding）
vectorstore = Chroma.from_documents(docs, OpenAIEmbeddings())
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# ---- 2. 混合检索 ----
ensemble = EnsembleRetriever(
    retrievers=[bm25, vector_retriever],
    weights=[0.4, 0.6],  # 术语型语料 → BM25 权重上调
)

# ---- 3. 查询 ----
query = "RAG 怎么减少幻觉"
query_bm25 = preprocess(query)  # 查询也要分词
results = ensemble.invoke(query)
for r in results:
    print(f"[{r.metadata['source']}] {r.page_content}")

# ---- 4. 接 LLM 生成 ----
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="gpt-4o")
prompt = ChatPromptTemplate.from_template("""
基于以下检索到的上下文回答问题。如果上下文中没有相关信息，回答"我不知道"。

上下文：
{context}

问题：{question}
""")

context = "\n\n".join(r.page_content for r in results)
chain = prompt | llm | StrOutputParser()
answer = chain.invoke({"context": context, "question": query})
print(answer)
```

### 5 个关键配置

| 配置项 | 默认值 | 怎么调 | 影响 |
|--------|--------|--------|------|
| `k`（每路召回数） | 4 | 起步设 5~10 | 太小漏召回，太大噪声多 |
| `k1`（TF 饱和） | 1.5 | 通常不改 | 控制词频增长速度 |
| `b`（长度惩罚） | 0.75 | 通常不改 | 控制长文档惩罚力度 |
| `weights`（两路权重） | 0.5/0.5 | 术语型→BM25↑；语义型→向量↑ | 谁主导召回 |
| **中文分词器** | 空格（=不分词） | **必须换 jieba** | 不分词 → 中文 BM25 完全失效 |

**最容易被坑的一点**：`rank_bm25` 默认按空格分词。中文文档如果直接喂进去，整句话会被当成一个词 → 倒排索引形同虚设。**必须用 jieba 预处理**，入库和查询都要分词。

### 什么时候该用 BM25（场景判断）

| 你的语料/查询特点 | BM25 权重 | 理由 |
|-------------------|-----------|------|
| 代码、API 名、变量名 | ↑ 上调到 0.5+ | 精确词匹配是刚需 |
| 产品型号、ID、编号 | ↑ 上调 | 向量检索对这些不敏感 |
| 政策条款、合同条文 | ↑ 上调 | 措辞精确，不能靠语义模糊 |
| 自然语言问答（"怎么部署"） | ↓ 下调到 0.3 | 向量检索更强 |
| 跨语言查询 | 几乎无效 | BM25 不懂跨语言同义 |
| 混合语料（既有术语又有自然语言） | 0.4 左右 | 两路互补，标准配置 |

### 生产环境的 3 个注意事项

**1. 文档更新后要重建 BM25 索引**
BM25 的 IDF 依赖全局统计（N、df），文档增删后 IDF 会变。`from_documents` 会重新计算，不是增量更新。如果文档频繁变动，考虑：
- 定时全量重建（简单可靠）
- 用 Elasticsearch（原生支持增量 + BM25）

**2. BM25 不支持元数据过滤**
如果需要"只在 topic=retrieval 的文档里搜"，BM25 做不到。两种方案：
- 分库建多个 BM25 实例（按 topic 隔离）
- 用支持 BM25 + 过滤的库（Elasticsearch、Qdrant）

**3. 中文分词器要和业务匹配**
jieba 通用场景够用，但如果有大量专业术语，需要加载自定义词典：
```python
jieba.load_userdict("my_dict.txt")
# my_dict.txt 每行一个词：LangChain\nBM25\n交叉编码器\n
```
