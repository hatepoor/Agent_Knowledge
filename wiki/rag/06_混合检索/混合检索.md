# 混合检索（Hybrid Search）

> 检索链路第 6 步。本文讲**融合策略**（两路互补 + RRF + 权重调参）；BM25 算法公式拆解与手算例子见 [[rag/06_混合检索/BM25算法详解|BM25算法详解]]；让 Embedding 重建同索引见 [[rag/04_混合索引构建/Embedding与向量检索]]；多路召回后再做精排见 [[rag/08_交叉编码器重排/重排序与交叉编码器]]。

## 概述

单一检索通道必然有盲区：**稠密向量检索**擅长语义同义但会漏精确术语/编号/代码；**稀疏检索（BM25）**精确匹配强但理解不了同义改写。混合检索 = 多路召回 + 融合排序（RRF），是生产 RAG 提升 Recall 最有效的单项手段。

> API 级用法详见 [[langchain/modules/langchain_retrievers/EnsembleRetriever|EnsembleRetriever]]（RRF 公式与权重调参）。

## 一、两条检索通道的互补性

| 通道 | 原理 | 强项 | 盲区 |
|------|------|------|------|
| 稠密检索（向量） | Embedding 语义相似 | 同义改写、语义相关、跨语言 | 精确数字/型号/代码符号、稀有专名（低频 token 被池化稀释） |
| 稀疏检索（BM25/SPLADE） | 词项统计匹配 | 术语/编号/代码精确命中、专名 | 同义不同词、概念性表述 |

> 经验：代码、规格、政策条款、产品型号类语料里 BM25 常常是"隐藏 MVP"；纯语义语料里向量主导。**不要凭感觉选，量化对比单路 vs 混合的 Recall@k**。

## 二、混合检索的两种主流实现

> **默认：用应用层 LangChain EnsembleRetriever 起步**（不绑定底层库、可插拔调权，先把链路跑通）；**只有在你本就在用支持原生混合的库（ES / OpenSearch / Qdrant / Milvus 新版）时才切原生**，少一套组件。两者取其一即可，别并行维护。

### 1. 应用层拼接（LangChain 路线）
BM25 + 向量库各自召回 → **RRF 融合**：

$$RRF(d) = \sum_{r \in \text{rankings}} \frac{1}{k + \text{rank}_r(d)}$$

k 常用 **60**（Anthropic/Elastic 实践值；k 越小越强调榜首）。RRF 无需分数归一化，天然把不同尺度的检索结果压到同一排序语境。

```python
# pip install -qU rank-bm25 langchain-community chromadb
from langchain.retrievers import EnsembleRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_chroma import Chroma

bm25 = BM25Retriever.from_texts(texts, k=10)
vector = Chroma.from_texts(texts, embeddings).as_retriever(search_kwargs={"k": 10})

ensemble = EnsembleRetriever(
    retrievers=[bm25, vector],
    weights=[0.4, 0.6],     # 按语料特性调：术语型语料加重 BM25
)
hits = ensemble.invoke("A100 的显存是多少")   # 内部：两路 Top-K → RRF(k=60) → 融合 Top-N
```

### 2. 数据库原生混合（Elasticsearch/OpenSearch/Qdrant/Milvus 新版本）
ES 内置 BM25 + dense_vector + `rrf` 检索器、Qdrant 提供 sparse+dense 混合（`Query API` 的 prefetch + fusion）——少一套组件，推荐在"本来就选型了该库"时使用。官方文档：ES https://www.elastic.co/guide/en/elasticsearch/reference/current/rank-vectors.html · Qdrant https://qdrant.tech/documentation/concepts/hybrid-queries/

## 三、什么时候需要"混合+重排"两件套

| 场景 | 建议 |
|------|------|
| 术语/编号/代码/型号多 | 必上混合检索（BM25 权重上调） |
| 自然语言问答为主 | 向量 + 可选轻量混合；重排收益大 |
| 长文档、跨章节 | 混合 + 重排 + 父子分块组合拳 |
| 对延迟极敏感 | 混合检索可留，重排窗口缩到 top_n=3 或用小模型 |

> 反向提醒：**先量化单路基线**再决定要不要混合。若单路 Recall@10 已 >0.9 且查询模式单一，混合的边际收益可能配不上组件复杂度。

## 四、常见问题

**Q1：RRF 和加权分数融合（score fusion）哪个好？**
RRF 对分数尺度鲁棒、无需调归一化，是默认选择；加权和需要各通道分数可比较（如都归一化到 0–1），收益场景有限。EnsembleRetriever 默认 RRF。

**Q2：两路结果大量重叠怎么办？**
正常。RRF 对"多路同时命中"天然加权（排名叠加），这正是它增强稳定命中的机制。

**Q3：多路召回让延迟翻倍，能接受吗？**
能优化：向量与 BM25 并行请求；对高频查询做语义缓存（[[rag/13_工程横切/性能与成本优化|性能与成本优化]]）。

## 五、最佳实践

1. **管线顺序固定**：粗召回（大 k、混合）→ RRF 融合 → [[rag/08_交叉编码器重排/重排序与交叉编码器|Cross-Encoder 精排]] → 上下文压缩。每步可单独开关做消融。
2. **把检索参数写进观测**：记录 k、weights、融合分数分布，可观测性是调优前提。
3. **中文语料务必验 BM25 分词**：BM25 对中文按字/词索引差异大（jieba/ik 分词 vs 字符 n-gram），直接影响术语命中。
4. **重排结果保留分数与来源元数据**，供生成环节做引用与置信过滤。
