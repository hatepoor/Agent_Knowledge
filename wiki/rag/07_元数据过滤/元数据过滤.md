# 元数据过滤（Metadata Filter）

> 检索链路第 7 步。把"检索条件"从纯文本扩展到结构化字段（日期/类目/权限/租户），在向量搜索前/后用标量条件剪枝候选集；也可作检索结果的门槛过滤。结构化的条件解析见 [[rag/05_查询转换与改写/查询结构化与槽位映射]]。

## 概述

元数据过滤分两种时机：
- **索引侧硬过滤**（检索时）：日期、权限、租户等硬条件**不依赖模型**，又便宜又可靠——先按元数据剪枝，再做向量搜索。**权限过滤是安全要求**（见 [[rag/11_安全审核与日志/安全与合规]] 与 [[rag/13_工程横切/多租户与大并发]]）。
- **检索后门槛过滤**（Post-Retrieval）：对候选块做"要不要"的判定——相似度阈值 / LLM 相关性判定 / 元数据规则，把噪声砍掉保住 Precision。

## 一、结构化的过滤条件（Self-Query 落地）

LLM 把自然语言转成"向量 + 元数据过滤条件"，让 query 与 filter 并行执行：

```python
# 完整语法见 [[langchain/modules/langchain_retrievers/SelfQueryRetriever|SelfQueryRetriever]]
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain.chains.query_constructor.base import AttributeInfo

fields = [
    AttributeInfo(name="product", description="产品线名称", type="string"),
    AttributeInfo(name="date", description="文档发布日期", type="string"),
]
sq = SelfQueryRetriever.from_llm(
    llm=llm, vectorstore=vectorstore,
    document_contents="产品手册片段",
    metadata_field_info=fields,
)
sq.invoke("A 产品线 2026 年之后的升级说明")
# → 解析出 filter={product:"A", date:{$gte:...}} + query 向量
```

> 生产关键：**过滤条件应由服务端从鉴权上下文注入**（租户/角色），不由 LLM 自由生成权限相关字段——否则是越权漏洞。实现见 [[rag/13_工程横切/多租户与大并发|多租户与大并发]] 的 shared+filter 范式。

## 二、Post-Retrieval 门槛过滤（整块丢弃）

| 组件 | 判定依据 | 成本 | 特点 |
|------|----------|------|------|
| `EmbeddingsFilter` | 对候选块与查询再算一次向量相似度，低于阈值丢弃 | 低（零 LLM、毫秒级） | 过滤默认首选；"双塔粗排的第二次机会" |
| `LLMChainFilter` | LLM 逐块判定"相关/不相关"（布尔） | 中（每块一次调用） | 能懂语义否定与条件，比阈值准 |
| LlamaIndex `SimilarityPostprocessor` 等 | 分数阈值 / 关键词 / 日期 | 低~中 | 生态不同，思路一致 |

```python
# 阈值门槛过滤实例（context 层面的文档压缩器）
from langchain.retrievers.document_compressors import EmbeddingsFilter, DocumentCompressorPipeline
from langchain_community.document_transformers import EmbeddingsRedundantFilter
# 管线：去冗余 → 相似度过滤（便宜）
pipeline = DocumentCompressorPipeline(transformers=[
    EmbeddingsRedundantFilter(embeddings=embeddings),   # 1) 语义去重
    EmbeddingsFilter(embeddings=embeddings, similarity_threshold=0.75),  # 2) 门槛过滤
])
```

## 三、与过滤/重排/压缩的区别

| 操作 | 输出变化 | 判定依据 | 成本 |
|------|----------|----------|------|
| **过滤**（整块丢弃） | 块数 ↓，内容不变 | 相似度阈值 / LLM 相关判定 / **元数据规则** | 低~中 |
| **压缩**（块内提取） | 块内容变短，只留相关语句 | LLM 逐块提取 | 高 | 
| **重排**（只变顺序） | 顺序变化 + 截断 | Cross-Encoder / LLM listwise | 中 |

三者可组成管道 `DocumentCompressorPipeline`；过滤最便宜放前面，[[rag/09_上下文构建与溯源/上下文压缩|压缩]] 最贵放最后。

## 四、常见问题

**Q1：EmbeddingsFilter 的阈值怎么定？**
采样真实查询与命中块的相似度分布，取"明显相关块"的下界（常在 0.70–0.85，随模型不同差异大）；阈值过高会把"间接相关但必要"的块滤掉，宁可先松后紧（叠加重排兜底）。

**Q2：过滤和重排先做哪个？**
先过滤后重排：过滤便宜且缩小重排候选集；重排（[[rag/08_交叉编码器重排/重排序与交叉编码器|Cross-Encoder]]）一次见全体候选做全局比较，放最后产出最终 Top-N。都上时务必用评估集消融。

**Q3：过滤条件依赖的元数据不干净怎么办？**
先做索引侧元数据治理（[[rag/04_混合索引构建/索引与部署流水线]]）——字段缺失/脏值会让过滤静默漏召回。

## 五、最佳实践

1. **元数据硬过滤永远最先做**：日期、权限、租户等硬条件不依赖模型，又便宜又可靠。
2. **权限过滤下推检索层**：服务端注入租户过滤，不交给 LLM 生成的 filter（安全底线）。
3. **记录过滤漏斗**：50 → 32 → 8 → 5 的每级留存率是调参最直观的观测指标（[[rag/12_评估与监控/在线监控与可观测性|可观测性]]）。
