# 生产级 RAG 系统架构

## 概述

从 Demo 到生产，RAG 系统要回答的不再是"检索准不准"，而是**分层、解耦、可扩展、可观测、可治理**。本文给出生产级 RAG 的参考架构：按"数据面 / 索引面 / 检索面 / 生成面 / 治理面"分层，每层可独立演进与扩容，并标注每层的典型组件与故障模式。

> 对应实践：离线评估闭环见 [[rag/12_评估与监控/评估体系与RAGAS|RAG 评估体系与 RAGAS]]，成本与多租户见本层后续页面。

## 一、参考架构总览

```
┌────────────────────────── 接入面 ──────────────────────────┐
│  业务 API / 对话 UI  │  身份与权限网关(鉴权/限流/审计)      │
└───────────────┬────────────────────────────────────────────┘
                ▼
┌────────────────────────── 编排面 ──────────────────────────┐
│  RAG Orchestrator（路由/查询改写/多轮状态/Agent 编排）      │
│  可选：LangGraph / create_agent / 自研编排                  │
└───────┬───────────────────────────────┬────────────────────┘
        ▼                               ▼
┌── 检索面 ──────────────┐      ┌── 生成面 ──────────────────┐
│ 混合检索(BM25+向量)      │      │ LLM 网关(多模型路由/重试)   │
│ RRF 融合 → Cross-Encoder │      │ 引用组装/上下文压缩         │
│ 重排 → 语义缓存(Redis)   │      │ 输出校验(引用/合规过滤)     │
│         │               │      │                           │
│   向量库(主)+搜索(辅)    │      │   在线 LLM / 本地部署 LLM   │
└─────────┬───────────────┘      └────────────┬──────────────┘
          │                                  │
┌─────────▼──────────────────────────────────▼───────────────┐
│                数据面 / 索引面（离线为主）                    │
│ raw 文档存储(S3/对象存储) → 解析/清洗 → 分块 → Embedding     │
│ → 向量库索引 + 元数据(Postgres/ES) → 版本化/一致性保障        │
└─────────────────────────────────────────────────────────────┘
┌────────────────── 治理面（贯穿全层）────────────────────────┐
│ 可观测(LangSmith/OTel) · 评估回归(CI) · 安全合规(RBAC/审计)  │
│ 多租户隔离 · 成本账单 · 配置/索引版本管理                     │
└─────────────────────────────────────────────────────────────┘
```

## 二、各层职责与关键设计

| 层 | 组件 | 关键设计决策 | 典型故障 |
|----|------|--------------|----------|
| 接入面 | API 网关、鉴权 | 限流、租户识别（传给检索做数据隔离） | 鉴权泄漏、突发流量打爆检索 |
| 编排面 | 路由/改写/多轮 | 缓存优先 → 简单直答 → 检索；Agent 化要设步数上限 | 死循环、改写劣化 |
| 检索面 | 混合检索+重排 | 检索与生成解耦为独立服务；k/top_n 配置化 | 召回漂移、重排延迟超时 |
| 生成面 | LLM 网关 | 模型路由（大小模型分级）、超时/重试/熔断 | 上游 LLM 抖动拖垮全站 |
| 数据/索引面 | 流水线 | 增量索引、失败重试、Embedding 版本管理 | 脏数据进库、双写不一致 |
| 治理面 | 观测/评估/合规 | 指标 SLO、失败回流、RBAC+审计 | 指标盲区导致静默劣化 |

## 三、分层解耦的三条硬原则

1. **检索服务与生成服务独立部署**：检索是"确定性快路径"（可缓存、可预热），生成是"慢路径"，两者扩缩容节奏完全不同；耦合部署时检索抖动直接拉高全链路 P95。
2. **索引与代码同版本管理**：Embedding 模型版本、分块器版本、索引数据集 hash 都进配置库；发布记录里写明"本次改动配套哪个索引版本"，否则线上无法回放（[[rag/12_评估与监控/在线监控与可观测性|可观测性]] 的前提）。
3. **所有跨层调用走显式接口**（检索 RPC/HTTP、缓存 key、trace id 透传），禁止层间直接共享内部对象——为灰度、替换、多租户隔离留出边界。

## 四、流量与容量设计要点

- **热点缓存**：语义缓存（相似度阈值命中）承接重复/近似查询，削峰同时降本（[[rag/13_工程横切/性能与成本优化|性能与成本优化]]）。
- **读写分离**：检索走只读副本；索引更新走写路径并异步同步副本，避免重建索引阻塞在线查询。
- **优雅降级**：向量库故障 → 降级到 BM25/ES 单路；LLM 故障 → 返回缓存/候选答案；保证"检索挂了不白屏，生成挂了能兜底"。
- **容量公式**：QPS × (检索延迟预算) 决定检索副本数；token/s 决定生成并发与队列；内存 = 向量库索引常驻内存，超限走 DiskANN/分片。

## 五、常见问题

**Q1：先 monolith 后拆服务可以吗？**
可以，但建议从一开始就把"检索/生成/索引"三个模块在代码边界上分开（同仓不同包），服务化只是把边界变成进程边界——否则后期拆分成本极高。

**Q2：编排层要不要上 Agent？**
默认路由+流水线起步；当"要不要检索/检索几轮/跨源综合"成为高频需求再 Agent 化（03 层）。编排面做成可插拔：同一条检索/生成链路既可被固定流程驱动，也可被 Agent 驱动。

**Q3：数据面用什么存 raw 文档？**
对象存储（S3/MinIO 等）+ 内容寻址（文档 hash 去重）。raw 是"最后防线"：向量库、元数据库都可以从 raw 重放重建，raw 的备份与版本管理优先级最高。

**Q4：怎么避免"索引和文档不同步"幽灵数据？**
设计文档生命周期事件（新增/更新/删除 → 触发索引任务），删除要走"软删 + 索引补偿"而非只在业务库删；定期对账（文档数 vs 索引块数、抽样比对最新版本）。

## 六、最佳实践

1. **先定义 SLO 再搭架构**：可用性、P95 延迟、检索 miss 率、引用正确率、单请求成本，五条基线驱动所有容量与降级设计。
2. **索引管道与在线服务共用同一份 schema**（字段定义、Embedding 配置），杜绝"两边各改各的"。
3. **灰度与回滚**：索引双版本（新索引构建完切流量，旧索引保留可回退）；Prompt/模型按流量百分比灰度并对比观测指标。
4. 生产变更清单：评估回归通过 → 灰度 → 观测对比 → 全量 → 回填 golden set。见 [[rag/04_混合索引构建/索引与部署流水线|索引与部署流水线]]。
