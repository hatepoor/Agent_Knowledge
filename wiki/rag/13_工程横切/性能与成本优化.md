# 性能与成本优化

## 概述

RAG 的每一层都有"性能-成本"旋钮：检索层省的是算力与存储，生成层省的是 token，工程层省的是重复计算。优化铁律：**先量化基线（延迟分解 + 成本账单按组件拆分），再动手**；任何优化都要用 [[rag/12_评估与监控/评估体系与RAGAS|评估指标]] 守住质量底线。本文给出从高 ROI 到低 ROI 的优化清单。

## 一、成本构成模型（先算清钱花在哪）

| 成本项 | 驱动因素 | 占比经验 | 主要杠杆 |
|--------|----------|----------|----------|
| LLM 生成 token | 上下文长度×请求量 | 最高（常 >60%） | 语义缓存、上下文裁剪、模型路由、小模型 |
| Embedding API | 索引总量+重索引频率 | 中（一次性+增量） | 批量、本地开源模型、降维 |
| 向量库基础设施 | 内存/副本/分片 | 中 | 量化、分区、副本策略 |
| 检索推理（重排） | 候选窗口×请求量 | 低-中 | 缩小 top_n、小重排模型、缓存 |

> 账单拆分建议：按 `模型 × 场景（检索/生成/重排/评估）× 租户` 打标签计量——成本优化没有标签就无从下手。

## 二、高 ROI 优化清单（按投入产出排序）

### 1. 语义缓存（通常第一位）
把"语义重复"的查询命中缓存答案，跳过整条 LLM 链路：

```python
# pip install -qU langchain-openai redis
import redis
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.caches import RedisSemanticCache   # 语义缓存：相似度>阈值即命中

cache = RedisSemanticCache(
    embedding=OpenAIEmbeddings(model="text-embedding-3-small"),
    redis=redis.Redis(host="localhost", port=6379),
    score_threshold=0.92,        # 阈值经验区间 0.90–0.95：越高越保守
)
llm = ChatOpenAI(model="gpt-4o", temperature=0, cache=cache)
```

- 生产报告常见量级：命中率 25%–40% 时 LLM 调用成本下降约 1/3~1/2（取决于查询重复度）。
- **缓存答案必须带证据与来源**：命中的是"旧检索结果+旧引用"，知识库更新后要按文档版本失效缓存（TTL/事件失效）。
- 只缓存 temperature=0 的确定性问题；检索/重排结果也可分层缓存。

### 2. 上下文瘦身（Token 即金钱）
- 检索返回 Top-N 的 token 总量设硬预算（如 ≤3k），超出按相关性截断或压缩。
- 重排后只留 top 3–5；去重、删导航噪声（[[rag/05_查询转换与改写/查询改写与扩展|上下文构建]] 军规）。
- 历史消息摘要化（memory 中间件），防多轮对话上下文无限膨胀。

### 3. 模型路由（分级用模型）
| 场景 | 建议 | 效果 |
|------|------|------|
| 简单 FAQ / 命中缓存的生成 | 小模型（如 mini 档/本地 7B） | token 单价低一个数量级 |
| 检索质量评分/改写 | 中档模型 + 结构化输出 | 平衡质量与成本 |
| 复杂综合/Agent 决策 | 旗舰模型 | 只花在刀刃上 |

### 4. 检索面优化
- **候选窗口校准**：粗召回 k 不是越大越好——50 通常够，过了只是喂重排。
- 重排 top_n=3–5、缓存重排结果（同一 query 的 top-N 短期复用）。
- Embedding 用批量 API 或本地开源模型（省索引成本）；维度过高可用 Matryoshka 降维至质量不掉档的最小维度。

### 5. 索引成本治理
- 增量索引替代全量重建；文档 hash 去重防重复 Embedding。
- 冷热分层：不常用文档降级到磁盘索引/独立集合。
- 量化评估：先用原精度建基线，再对比量化后 Recall@k 损失决定是否启用。

## 三、延迟优化（面向 P95）

| 环节 | 手段 |
|------|------|
| 检索 | 向量与 BM25 并行；过滤器走索引；向量库放同可用区/同机房 |
| 重排 | 小候选集+小模型；必要时异步/降级（top_n=1 直取第一） |
| 生成 | 流式输出提升首 token 体验（TTFT）；LLM 网关超时/重试上限；对慢模型设置 fallback |
| 全链路 | 语义缓存削峰；热点索引只读副本；连接池与并发控制 |

注意：**优化 P50 是自嗨，生产盯 P95/P99**——队列积压与上游抖动都在尾部。

## 四、常见问题

**Q1：缓存导致答案过期怎么办？**
缓存 key 绑定文档版本：知识库更新事件 → 使相关租户/文档域的缓存失效（按 metadata 域做缓存 tag）。宁可命中率低一些，不可给过期答案。

**Q2：小模型路由怎么保证质量不掉？**
路由前先离线评测：把 golden set 用候选小模型跑一遍，质量达标的场景才允许路由；线上对路由决策抽样复核（[[rag/12_评估与监控/在线监控与可观测性|可观测性]] 按场景看质量）。

**Q3：重排太慢拖垮 P95，能砍吗？**
能分级：对"缓存命中率高的高频查询"用规则排序直返；仅对复杂查询启用重排。砍之前先量化重排对 Recall 的贡献——若 top_k 检索已很准，重排收益低可降级。

**Q4：成本优化与质量提升冲突怎么取舍？**
原则：**质量下限由 SLO 守，成本上限由预算守**。每次优化同时记录质量指标变化；质量跌破阈值即回滚该优化项。用"单位成本下的质量"（如分数/元）做跨方案比较。

## 五、最佳实践

1. **先量化再优化**：延迟用 P95 分解链路各环节；成本按组件打标签，两周一个周期观测趋势。
2. **每个优化项一个开关**（feature flag），可独立灰度/回滚，且配套评估回归。
3. **缓存答案带上证据链**（引用来源、生成时的文档版本），否则"快了但不可信"。
4. 把成本与质量同时写进发布报告：一次发布只允许"同质量更便宜"或"同成本更高质量"。
