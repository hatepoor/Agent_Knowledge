# 多租户与大并发

## 概述

SaaS 化的 RAG（每个企业客户 = 一个租户）面临两个核心问题：**隔离**（A 租户绝不能检索到 B 租户的文档）与**公平性**（大租户不能拖垮小租户、单租户流量洪峰不能打挂集群）。隔离是安全底线（与 [[rag/11_安全审核与日志/安全与合规|安全与合规]] 联动），并发是容量工程。本文给出三种隔离模式、选型矩阵与限流/扩容要点。

## 一、三种隔离模式

| 模式 | 做法 | 隔离强度 | 成本 | 适用 |
|------|------|----------|------|------|
| **store-per-tenant**（物理隔离） | 每租户独立集合/数据库/实例 | 最强（故障与噪声也隔离） | 最高（海量小租户时管理爆炸） | 大客户、强合规、数据不可混合 |
| **shared + 过滤**（逻辑隔离） | 共享集合，每块带 `tenant_id`，检索时强制过滤 | 中（依赖实现正确性） | 最低（共享基础设施） | 中小租户规模化默认选择 |
| **共享 + 分区**（中间态） | 共享集群但按租户分区/分片（Milvus partition、Qdrant 多集合、Pinecone namespace、Weaviate 原生多租户） | 中-强 | 中 | 租户量级差异大的折中 |

> **实现纪律**：租户过滤必须由**服务端强制注入**，而非信任客户端传参——从请求里取租户身份（网关解析 token），拼进检索 filter，客户端无法覆盖。否则"传别人的 tenant_id 就查到别人的数据"是必现漏洞。

## 二、shared+filter 的正确实现（主流默认）

```python
# 服务端从鉴权上下文取租户，注入检索过滤（示例：Qdrant payload 过滤）
def search_for_tenant(query: str, tenant_id: str, k: int = 5):
    # tenant_id 来自网关解析的 token，绝非客户端请求体字段
    return vectorstore.similarity_search(
        query,
        k=k,
        filter=models.Filter(
            must=[models.FieldCondition(
                key="tenant_id",
                match=models.MatchValue(value=tenant_id),   # 走 payload 索引，不拖慢 ANN
            )]
        ),
    )
```

要点：
- `tenant_id` 字段**建索引**（否则过滤=全扫描）；插入时由服务端写入，不接受文档自带。
- 检索、重排、缓存**全部带租户维度**：语义缓存的 key 必须含 tenant_id（否则 A 的缓存答案会发给 B——缓存是最容易漏的隔离点）。
- 评估与观测按租户聚合：质量/成本/延迟分租户看板，才能发现"某个租户知识库脏了"这类单点劣化。

## 三、选型建议

| 条件 | 推荐 |
|------|------|
| 租户数少（<几十）且数据量大/合规严 | store-per-tenant（物理库或独立集合+独立凭据） |
| 租户多（数百~数万）中小数据量 | shared + tenant_id 过滤（首选）；集合级分区（namespace/partition）做中大型租户 |
| 平台级多租户、想省运维 | Weaviate 原生多租户 / Pinecone namespace 等托管抽象 |
| 已有 Postgres | pgvector + 行级安全（RLS）：`USING (tenant_id = current_setting('app.tenant'))`，数据库层兜底防漏 |

## 四、大并发与公平性

1. **租户级限流/配额**：按租户设 QPS 与 token 预算；超限返回 429 而非拖死集群（网关层实现）。
2. **共享池 + 租户权重**：检索副本共享但给大租户保留最小吞吐（weighted fair queue），避免"一个租户刷爆全部检索线程"。
3. **热点防护**：多租户场景的流量极不均（头部租户 >> 长尾）。方案：头部租户独立集合/副本 + 语义缓存优先服务热点租户 + 长尾共享池。
4. **容量核算按"最大租户 × 峰值"而非平均值**设计检索副本；向量库内存随租户数据增长规划冷热分层。
5. **爆炸半径控制**：索引重建、Embedding 模型升级对租户分批灰度（先小租户后大租户），失败可回滚到旧索引。

## 五、常见问题

**Q1：shared+filter 会不会因过滤把 ANN 性能拖垮？**
会，如果 tenant_id 过滤没走索引（在向量搜索前做标量剪枝）。所有向量库都支持带索引的 filter（Qdrant payload index、Milvus 标量字段索引、ES filter + kNN）；建对索引后，命中过滤的搜索仍接近纯 ANN 性能。

**Q2：租户删除/退出时数据怎么清干净？**
级联清理：文档对象 → 向量块 → 语义缓存 → 评估 trace。向量库删除按 tenant_id 批量删块；缓存 key 带租户前缀批量失效；保留审计记录（合规删除与取证删除要区分）。

**Q3：一个租户内部还要不要分权限（部门/角色）？**
要，隔离模型是两层的：租户层（上文模式）+ 租户内 RBAC（文档级权限）。实现：metadata 里同时带 `tenant_id` 与 `doc_acl`（角色/部门标签），检索 filter 二者并查；复杂 ACL 可考虑检索后精排层再做一次权限过滤。

**Q4：多租户下怎么保证"我的改动不影响别人"？**
① 索引/Prompt/模型按租户组灰度；② 变更前后对比各租户组质量指标（评估集按租户分组）；③ 全链路 trace 带租户标签，故障能定位到"哪个租户的哪次请求"。

## 六、最佳实践

1. **隔离在检索层强制，信任在网关层终结**：服务端注入租户上下文，客户端永不直接碰向量库。
2. **先设计租户模型再选向量库**：租户数×数据量×合规决定隔离模式；选型回头参考 [[rag/04_混合索引构建/向量数据库选型指南|向量数据库选型]]。
3. **缓存、评估、观测三处同步租户化**——漏一处就是事故（缓存串答案、指标算错、日志泄租户数据）。
4. 定期做"跨租户越权检索"攻击测试（安全回归 CI 的一部分）。
