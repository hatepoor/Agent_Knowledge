# 固定长度分块与递归字符分块

> 递归字符分块是 2026 年最稳的默认基线——它用「分隔符优先级」模拟了人眼找断句的方式，而固定分块只是它最退化的一级。

## 核心结论

- **固定长度分块**是唯一以「长度」为唯一依据的方法：按字符数或 token 数等量切割。它最简单、最快、完全可重现，但会在任意位置下刀，可能切断句子和语义单元。它适合做对照基线，或处理本就无结构的均匀流（如日志行）。
- **递归字符分块**是固定分块的升级：按**分隔符优先级**逐级降级切分，尽量在自然边界断开，而非在字符中间腰斩。
- 二者关系：**固定分块是递归分块的特例**——递归分块只有一级分隔符（空字符串 `""`，即字符级）时，就退化成固定分块。
- 中文开发者要特别注意：**不能照搬英文的字符数经验值**。中文「字符」与「token」的比例和英文差异巨大，直接按英文字符阈值切，结果要么块过大、要么把中文词切散。

## 机制与原理

### 固定长度：唯一依据是长度

给定 `chunk_size`，从文本头逐段取固定长度，不关心里面是什么内容。例如 `chunk_size=500` 字符，第 1 块取 [0,500)，第 2 块取 [500,1000)……直到切完。overlap 就是相邻块重叠的前一段尾部字符。

优点：实现一行代码、零依赖、可重现。缺点：一个块可能从「……价格由市场决」切到「定。」——句子被劈成两半，embedding 拿到的语义是残缺的。

### 按字符 vs 按 token：中文的坑

| 口径 | 实现 | 问题 |
|---|---|---|
| 按字符 | `text[i:i+size]`，无需任何模型 | 不等于模型真实计费/窗口单位；中文尤其不准 |
| 按 token | 调用 tokenizer 数 token | 更贴近模型，但需引入 tokenizer 依赖 |

**为什么中文不能照搬英文字符经验值**：英文一个词约 5~6 字母，512 token ≈ 2000+ 字符；中文常见 1 字 ≈ 1~2 token（以你用的智谱 embedding-3 为例，CJK 大致 1~2 字符/token（待核实具体比率）），512 token 只对应约 500~1000 字符。如果照搬英文「chunk_size=2000 字符」的标准，中文实际会塞进约 2~4 倍 token，**直接撑爆 embedding 模型窗口**。结论：中文分块一律以 token 为口径，用真实 tokenizer 校准字符数。

### 递归分块：分隔符优先级逐级降级

递归分块不盲目按长度下刀，而是维护一份**分隔符优先级列表**，按「最像段落边界 → 最不像」的顺序尝试：

1. 先用最高优先级分隔符（如 `\n## `、`\n\n`）把文本切开；
2. 若某一段仍超过 `chunk_size`，就**降级**到下一级分隔符（如 `\n`、`。`）继续切；
3. 一路降到最低级（空字符串 `""`，即字符级）兜底，保证任何超长文本都能被切成合规块。

这就是「递归」二字的来历：对切出的每一段，若还超长，就对它**递归地**用更低级分隔符再切。

### 分隔符列表的设计（关键）

中英混排文档必须**同时覆盖中英文标点**，否则中文会一路退到空格甚至字符级，把词切散。一个可用的列表：

```
["\n## ", "\n### ", "\n\n", "\n", "。", "！", "？", ". ", " ", ""]
```

逐项解释：

| 分隔符 | 作用 |
|---|---|
| `\n## ` / `\n### ` | 最优先：Markdown 二级/三级标题，整节语义最整 |
| `\n\n` | 段落边界，绝大多数正文的自然断点 |
| `\n` | 换行，退一步的软断点 |
| `。` / `！` / `？` | 中文句末标点，保证不切在句子中间 |
| `. ` | 英文句末（注意句号后带空格，避免误切 `Mr.Smith` 之类） |
| ` ` | 空格，词/单词边界兜底 |
| `""` | 空字符串=字符级，最后兜底，保证一定能切完 |

**`keep_separator` 的含义**：切完后是**保留**还是**丢弃**分隔符。设为 `True` 时，分隔符会被拼回块尾，保持文本可读性（尤其 `\n\n` 被保留后，块开头不会丢失段落感）；设为 `False` 则丢弃。中文场景建议 `keep_separator=True`，因为把 `。` 丢掉会让块结尾变成「……所以我们要优化它」缺句号，读起来怪、也可能影响边界判断。

### 一个具体的降级示例

假设 `chunk_size=50`，有这段文本：

```
第一章 背景\n\n本项目研究中文分块。早期的系统按字符切。这导致了语义断裂。我们改用递归分块来修复。
```

降级过程：

1. 先按 `\n\n` 切 → 得 [`第一章 背景`, `本项目研究……来修复。`]，第二段仍超 50 字符；
2. 对超长的第二段按 `\n` 切 → 无 `\n`，失败；
3. 降到 `。` → 切成 [`本项目研究中文分块。`, `早期的系统按字符切。`, `这导致了语义断裂。`, `我们改用递归分块来修复。`]，前几段仍超 50；
4. 再降到 ` `（空格，本例无空格）→ 失败；
5. 最后降到 `""` 字符级 → 把每个超长句按 50 字符硬切兜底。

可见递归分块「尽力在自然边界断，断不了才字符级兜底」，而固定分块从头到尾只有第 5 步。

## 实操

```python
# pip install -qU langchain-text-splitters
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 中英混排：分隔符同时覆盖中英文标点
separators = ["\n## ", "\n### ", "\n\n", "\n", "。", "！", "？", ". ", " ", ""]

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,        # 按 token 理解；若按字符需先校准中文比例
    chunk_overlap=80,      # 约 15.6%，落在 10~20% 有效区间
    separators=separators,
    keep_separator=True,   # 保留分隔符，保持块可读性
    # length_function=len, # 默认按字符；中文建议换成 tokenizer 计 token
)

chunks = splitter.split_text(long_doc)
print(f"切成 {len(chunks)} 块，首块长度 {len(chunks[0])}")
```

> 注意 `length_function`：上面 `chunk_size=512` 是按 token 设的，但若 `length_function` 仍是默认 `len`（字符数），则实际是按 512 **字符**切。中文务必把 `length_function` 换成你的 tokenizer（如智谱兼容的 tiktoken 风格或自行计数），否则数值语义错位。

## 陷阱与边界

1. **中文标点缺失 → 切在词中间**：分隔符列表漏了中文句号 `。`，长段落就会一路退到空格甚至 `""`，中文词被劈开（如「机器学习」切成「机器」「学习」），embedding 语义受损。**检查清单**：列表必须含 `。！？`。
2. **overlap 设太大 → 块重复挤占名额**：overlap 超过 30% 会反噬——索引膨胀、摄入变慢、检索返回近似重复的块，挤掉真正相关的块。守住 10~20%。
3. **字符数当 token 数 → 块超模型窗口**：见上文，中文按英文字符阈值会塞爆 embedding 窗口。
4. **`keep_separator=False` 丢边界**：标题/段落的换行被丢，块开头丢失上下文锚点，且下游结构感知无法从块里还原层级。
5. **固定分块当生产默认**：除非是对照实验，否则不要拿固定分块做正式索引——它切断语义的代价在混合检索（尤其是 BM25 稀疏侧）上会被放大。
