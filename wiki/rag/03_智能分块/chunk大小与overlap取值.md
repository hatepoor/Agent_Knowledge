> chunk 大小与 overlap 是分块环节最基础、也最容易被「拍脑袋」定死的两个旋钮：它们决定了每个检索单元能装多少语义、以及相邻单元之间留多少缓冲。

## 核心结论

- **递归字符分块 @ 512 token + 10~20% overlap** 是当前最稳妥的基准默认值，实测检索准确率约 **69%**。在没有评估集做精调之前，直接用它不会犯大错。
- **overlap 是双刃剑**：在 10~20% 区间内它是稠密召回的保护措施，超过 30% 就开始反噬——索引膨胀、摄入变慢，还会让近似重复的块挤占候选名额。
- **混合索引下 overlap 必须更保守**：纯向量方案里 overlap 是好事，但你的下游是「稠密 embedding + jieba/BM25 稀疏」的混合检索，overlap 对稀疏侧是污染源。混合场景下建议 **10~15%**。
- 一个反直觉的硬事实：**BGE-M3 支持 8192 token，不代表你应该切 8192 的块**。模型支持的长上下文是给「文档级 embedding」用的，不是给 chunk 用的。
- 永远用**评估集 + 真实长度分布**定参数，不要照搬英文社区以字符数为单位的经验值——中文信息密度更高，你又是中英混排。

## 机制与原理

### 为什么 512 token 是默认值

512 token 这个默认值之所以站得住，是因为它同时满足两个相互拉扯的约束：

1. **大到能承载一个完整概念及其直接语境**。一个技术概念（比如「什么是交叉熵」）通常需要一两段话才能把定义、适用场景、公式说清楚，512 token 刚好够放下这样一坨自洽的内容。
2. **小到不会被周围噪声淹没**。如果一个块塞进 2000 token，里面可能混了三个不相关的主题，embedding 模型会把它们「平均」成一个向量，检索时这个块既匹配 A 也匹配 B，但哪个都匹配不精确。

同时，512 token 落在一**所有主流 embedding 模型输入限制之内**（智谱 embedding-3、BGE-M3、OpenAI text-embedding-3 都远超这个量级），所以不必担心截断。它不是一个理论上「最优」的数，而是一个「在准确率、噪声、兼容性三角里最不坏」的折中。

### overlap 的双刃剑性质

overlap 指的是相邻两块之间重复的那部分文本。它的存在是为了解决一个具体问题：**答案恰好跨在切分边界上时，如果不重叠，任何一块都拿不到完整答案**。

| 维度 | 收益 | 成本 |
|---|---|---|
| 召回 | 保证跨边界的答案至少在一个块里完整出现；提升稠密召回最多约 **14.5%** | — |
| 索引 | — | 重复文本 → 索引体积变大、摄入更慢 |
| 候选质量 | — | 返回近似重复的块，**挤占 top-k 名额**，稀释真正相关的块 |

有效区间是 **10~20%**。注意「超过 30% 反噬」是实测结论：重叠太多时，索引里充斥着彼此只差几十个字的块，检索器在融合阶段反而更难把真正相关的块顶上来。

生产系统里还有一个去重补充手段：在摄入阶段丢弃与已有块 embedding 余弦相似度 **> 0.98** 的块，相当于在 overlap 之上再加一道「语义级去重」闸门，进一步抑制近似重复块。

### 混合索引下 overlap 必须更小（重点）

这一点对你的场景尤其关键，需要展开讲清楚。你的下游是**混合检索**：稠密侧用智谱 embedding-3（未来可能换 BGE-M3），稀疏侧用 jieba + BM25。这两种检索对 overlap 的态度是**相反**的。

- **稠密侧（embedding）**：overlap 是保护措施。重复一点文本对向量没坏处，反而让它更稳定。
- **稀疏侧（BM25）**：overlap 是**污染源**。同一段文字在多个块里重复出现，会触发三个连锁问题：

  1. **词频被重复计入**。BM25 按词频打分，同一段话在两个块里各出现一次，那个块的该词 TF 被抬高，分数被无意义地夸大。
  2. **重复块同时挤进候选**。融合阶段（RRF / 加权求和）给每个检索器的 top-k 名额，两个内容几乎一样的块各占一个稠密/稀疏名额，真正不同的相关块反而被挤出去。
  3. **文档频率虚高，拉低 IDF**。如果同一段落被切成多块且都在同一文档里重复，该词的 DF 偏高，IDF 权重被压低，等于削弱了这个词作为区分信号的敏感性。

  稀疏检索对重复文本远比稠密检索敏感，因为它直接拿词频说话。所以混合索引下，overlap 不能沿用纯向量的 10~20% 甚至 30%，要更保守：**10~15%** 是更稳的区间。

### 一个反直觉点：模型支持 8192 token ≠ 该切 8192

BGE-M3 的上下文窗口是 8192 token，这是一个常被误解的数字。要分清两件事：

- **模型支持的上限**：模型能把多长的文本一次性编码进一个向量。8192 是上限。
- **语义编码的有效长度**：把一个定长向量塞进过长文本时，模型只能做「全局平均式」的池化，多个主题被压进同一个向量，语义被平均掉，**检索精度反而下降**。

长上下文能力是给「文档级 embedding / 整篇相似度」这类场景用的，不是鼓励你把 chunk 切到 8192。chunk 的有效长度通常远小于模型上限。这也是为什么 512 这种量级在实践中比 8192 好用。

### 中文与代码混排的修正

英文社区的分块经验很多以「字符数」为单位（例如 1000 characters）。搬到你的中文知识库要打两个折扣：

- **中文信息密度高于英文**。同样 1000 字符，中文承载的语义量明显大于英文。按字符数切，中文块其实比英文块「装得更多」，容易超载。
- **代码块是另一种语言**。代码按标点/缩进组织语义，和 prose 完全不同。

所以**按 token 数配分块比按字符数稳**，而且必须实测你自己的长度分布——中英混排 + 代码，真实分布和英文纯文本样本不会一样。

## 实操

### 如何实测自己的最优值

不要凭直觉定参数。给你一套可操作的方法，直接落到你「数千 chunk、混合检索」的规模：

1. **统计真实 chunk 长度分布**。切完一遍后看 P50 / P95 / 最大长度。配置的理论值（512）往往和真实分布不符——比如你的代码块普遍到 1500 token，512 就会把函数切两半。
2. **在参数网格上跑 Recall@10**。选一个网格，例如：

   ```
   候选 chunk 大小: 256 / 384 / 512 / 768
   候选 overlap   : 10% / 15% / 20%（混合检索建议只测到 15%）
   组合 = 12 组
   ```

   用**同一批 query**（不要换问题）逐组跑，看每组的 Recall@10。
3. **用评估集定参数，不用直觉**。建一个几十到上百条的 query + 标准答案集合，每次改参数都回归一遍。这是唯一能把「69% 基准」往上推的办法。

示例：用你已有的检索入口，对每组参数输出 `Recall@10 = 命中相关块数 / 10`，挑最高的那组作为新的默认。

### 给你的具体默认值建议

| 你的约束 | 建议起点 |
|---|---|
| 纯稠密（仅 embedding） | 512 token + 15% overlap |
| 混合检索（稠密 + BM25，你的场景） | 512 token + 10~15% overlap，优先试 10% |
| 含大量代码块 | 先按上面统计 P95，代码块单独走 AST 切（见 [[rag/03_智能分块/特殊内容分块\|特殊内容分块]]） |

## 陷阱与边界

- **把「模型窗口上限」当 chunk 大小**：BGE-M3 8192 不是让你切 8192，见上文反直觉点。
- **中文照搬英文的字符数经验值**：中文信息密度更高，按字符数切会超载；改用 token 数并实测分布。
- **overlap 沿用纯向量时代的 30%**：在混合检索下这是污染源，压到 10~15%。
- **不统计真实长度分布**：理论 512 和实际 P95 可能差几倍，尤其是代码块。先统计再定。
- **把 overlap 当万能药**：overlap 救的是「跨边界截断」，救不了「块内主题混杂」——后者要靠更小/更语义化的切分解决。
- **忽略去重**：开了大 overlap 又不做相似度去重（>0.98 丢弃），候选名额会被近似重复块稀释。
