> 分块工具的选择，收益主要在「速度」和「依赖精简」；切分质量本身的差别不大——因为质量的瓶颈在策略选择，不在实现速度。这是本页的核心判断。

## 核心结论

- **LangChain `langchain-text-splitters`** 生态最成熟、零额外依赖，作为默认选择足够；它的瓶颈在「策略选得对不对」，不在「切得快不快」。
- **Chonkie**：Rust 核心，比 LangChain 快约 5–10 倍，API 现代，chunk 对象自带 `token_count` / `start_index` / `end_index`（索引偏移内置，溯源方便）。
- **semchunk**：纯 Python，仅两个依赖（dill + tqdm），MIT，**不需要 embedding 模型**——用统计句子边界做低成本切分。
- **LlamaIndex NodeParser**：父子分块与句子窗口是**内置组件**（`HierarchicalNodeParser` / `SentenceWindowNodeParser`）；代码分块用 `CodeSplitter`（tree-sitter，比 LangChain `from_language()` 精确）。
- **docling `HybridChunker`**：结合文档结构树 + tokenizer，产出块自带标题路径与页码元数据；**注意 DOCX 场景下没有页码**（实测 prov 为空）。
- **实际判断**：若已在用 LangChain，换分块库的收益主要是速度与依赖精简；只有当吞吐量成为问题（百万级文档全量重建）时，换 Rust 实现才有明显收益。

## 机制与原理

### 为什么「切分质量」和「用哪个库」关系不大

所有分块库最终都是在做同一件事：把文本按某种边界切成块。差异主要在**实现语言（Python vs Rust）**和**API 设计**，而**不是切分策略本身**。递归字符切分的逻辑（换行 > 句号 > 空格）无论 LangChain 还是 Chonkie 实现，结果几乎一样。

真正决定检索效果的，是更高层的策略选择：

- chunk 多大、overlap 多少（见 [[rag/03_智能分块/chunk大小与overlap取值\|chunk 大小与 overlap 取值]]）
- 代码/表格/公式分别怎么切（见 [[rag/03_智能分块/特殊内容分块\|特殊内容分块]]）
- 要不要上下文增强（见 [[rag/03_智能分块/上下文增强分块\|上下文增强分块]]）

所以「换分块库」通常换不来质量提升，只能换来**吞吐量和依赖体积**的改善。这一点要记牢，避免为了「更好效果」而盲目换库。

### 各库定位速览

| 库 | 核心语言 | 关键卖点 | 适用取舍 |
|---|---|---|---|
| LangChain text-splitters | Python | 生态成熟、零额外依赖、组件全 | 默认够用，速度一般 |
| Chonkie | Rust | 快 5–10×、现代 API、chunk 带偏移 | 追求速度/溯源 |
| semchunk | 纯 Python | 仅 2 依赖、MIT、无需 embedding | 精简依赖、低成本 |
| LlamaIndex NodeParser | Python | 父子/句子窗口内置、CodeSplitter 精确 | 要高级检索结构 |
| semantic-text-splitter | Rust | TextSplitter/MarkdownSplitter、自定义 tokenizer | 安装有摩擦 |
| docling HybridChunker | Python+Rust | 结构树+tokenizer、元数据最全 | 要全元数据、配 docling 解析 |

## 实操

### 1. LangChain `langchain-text-splitters`

最常被默认采用的方案。组件清单：

- `RecursiveCharacterTextSplitter`：按分隔符优先级递归切，最常用。
- `CharacterTextSplitter`：单一分隔符切（如只按换行）。
- `TokenTextSplitter`：按 token 数切（配 tokenizer，避免按字符数的偏差）。
- `MarkdownHeaderTextSplitter`：按 Markdown 标题层级切，并保留标题元数据。
- `HTMLHeaderTextSplitter`：HTML 同理。
- `RecursiveJsonSplitter`：按 JSON 结构递归切。
- `SemanticChunker`：在 `langchain_experimental` 里，按语义相似度切（需 embedding）。
- `from_language()`：二十多种语言的预置分隔符（代码分块省事版）。

一句话评：**作为默认选择足够，切分质量瓶颈在策略选择而不在实现速度**。如果已经在用 LangChain 生态，没有强理由去换。

### 2. Chonkie

Rust 核心的独立分块库，主打速度与现代化 API。API 示例：

```python
import chonkie

# TokenChunker：按 token 切，chunk 自带偏移信息
chunker = chonkie.TokenChunker(
    tokenizer="gpt2",   # 或任意支持的分词器
    chunk_size=512,
    chunk_overlap=64,
)
chunks = chunker.chunk(text)
for c in chunks:
    print(c.token_count, c.start_index, c.end_index)  # 内置溯源偏移
```

它提供 `TokenChunker` / `RecursiveChunker` / `SemanticChunker`。相比 LangChain 的两个实质优势：

- **快约 5–10 倍**（Rust 核心）。
- **chunk 对象自带 `token_count` / `start_index` / `end_index`**——索引偏移内置，检索到块后能直接定位回原文位置，溯源定位不用自己再算。

适合你已经有一定规模、想提速、又想要内置偏移溯源的场景。

### 3. semchunk

纯 Python，仅两个依赖（dill + tqdm），MIT 许可。最大特点是**不需要 embedding 模型**——它用统计句子边界（如句子长度、标点概率）做低成本切分，而不是靠语义相似度。

适合：想精简依赖、不想为了切分而加载一个 embedding 模型、又接受「句子边界级」而非「语义级」切分的场景。

### 4. LlamaIndex NodeParser

LlamaIndex 把分块叫 **NodeParser**，粒度控制更细。它的杀手锏是**高级检索结构是内置的**：

- `HierarchicalNodeParser`：父子分块（parent-child），大块检索、小块喂 LLM。
- `SentenceWindowNodeParser`：句子窗口（检索命中句 + 周围窗口一起喂）。

而在 LangChain 里，父子分块/句子窗口需要你自己用 Retriever 组装，不是开箱组件。

代码分块用 **`CodeSplitter`**，基于 **tree-sitter**，比 LangChain 的 `from_language()` 精确（真正按语法树切，而非按预置分隔符近似切）。

如果你要做父子分块或句子窗口检索（这两类在 RAG 里对长文档很常用），LlamaIndex 是更省事的选择。

### 5. semantic-text-splitter

Rust 编译（安装时有摩擦，需要本地编译或预编译 wheel）。提供 `TextSplitter` 与 `MarkdownSplitter`，支持自定义 tokenizer。语义切分能力和 Chonkie 的 `SemanticChunker` 类似，但生态与易装性不如 Chonkie。除非你已经用 Rust 工具链，否则 Chonkie 通常是更顺的选择。

### 6. docling `HybridChunker`

与 docling 解析器配套的切分器，优势是**元数据来自解析阶段、信息最全**：

- 结合**文档结构树**（标题层级、段落、表格等元素）+ **tokenizer** 切分。
- 产出的块自带**标题路径**（这个块属于「第 2 章 > 2.1 节」）与**页码**元数据（PDF 有页码）。

对处理「中英混排 Word 文档」的你来说，docling 能先把 DOCX 解析成带类型的元素流，再交给 `HybridChunker`，元数据最全。

**重要实测结论**：DOCX 场景下**没有页码**——DOCX 的 `prov`（provenance）是空的，只有 PDF 才有页码。所以别指望用 DOCX 拿到页码元数据，它只会是空字段。这与 [[rag/03_智能分块/特殊内容分块\|特殊内容分块]] 里「元素级分流」那节呼应。

### 选型建议表

| 场景 | 建议 |
|---|---|
| 通用默认 | LangChain（生态成熟、零依赖） |
| 追求速度、更现代 API | Chonkie |
| 想精简依赖 | semchunk |
| 代码分块 | LlamaIndex `CodeSplitter`（tree-sitter）或 LangChain `from_language()` |
| 父子 / 句子窗口 | LlamaIndex 内置 NodeParser |
| 要最全的元数据 | docling `HybridChunker` |

## 陷阱与边界

- **以为换库能换质量**：切分质量瓶颈在策略，不在实现库。换库主要换速度与依赖（见上文核心判断）。
- **盲目上 Rust 库却装不上**：semantic-text-splitter 需本地编译，环境没 Rust 工具链会卡住；优先 Chonkie。
- **DOCX 期待页码**：docling 的页码元数据在 DOCX 下为空（prov 实测为空），别依赖它做溯源。
- **LlamaIndex 父子分块不去 LangChain 硬凑**：如果要父子/句子窗口，直接用 LlamaIndex 内置，别在 LangChain 里手搓 Retriever 组装。
- **semchunk 当语义切分用**：它只做句子边界级切分，不含 embedding 语义，别和 `SemanticChunker` 混为一谈。
- **只切不分类型**：无论选哪个库，代码/表格/公式仍要按 [[rag/03_智能分块/特殊内容分块\|特殊内容分块]] 分别处理，库不替你做元素级分流。
