> 正文是线性序列、表格是二维结构、代码是有语法的树、公式是符号表达式——用同一种「按字符/按标点」策略处理混合文档，必然在某一类内容上失手。

## 核心结论

- **不同内容类型的信息组织方式根本不同**，所以不存在「一种分块策略通吃」这回事。混合文档必须**按内容类型分别处理**。
- **代码绝不能按 token 或标点切**：会把函数切成两半，语法不完整、无法执行。正确做法是用 AST / tree-sitter 按函数、类、方法边界切。
- **表格整块不切分**：表一旦被切断，行列对应关系就废了，LLM 会自信地给出基于「半个表」的错误答案。
- **公式与列表保持完整**：公式里的逗号、括号是语法的一部分；列表项不要切半。
- 落脚点是**元素级分流**：正文按段落/标题切、表格整块摘出、代码按函数边界、图片转文字描述——这是处理中英混排 Word 文档（含表格与图片）的唯一正确做法。

## 机制与原理

### 为什么「一种策略通吃」必然失败

递归字符分块器本质上是把一个字符串按分隔符优先级切开（换行 > 句号 > 空格……）。它对「线性散文」有效，是因为散文的语义确实沿字符序列线性排列。但下面几类内容是另一套组织逻辑：

| 内容类型 | 信息组织方式 | 错误切分的后果 |
|---|---|---|
| 正文 | 线性序列 | 跨边界的答案丢失（overlap 能救） |
| 表格 | 二维结构（行×列） | 行列对应断裂，数据作废 |
| 代码 | 有语法的树（AST） | 函数被切断，无法执行/编译 |
| 公式 | 符号表达式 | 括号/逗号被当标点切断，语义全毁 |
| 列表 | 项级结构 | 列表项被切半，条目含义残缺 |

也就是说，**切分单元必须对齐内容的「自然边界」**，而不是对齐字符流。下面分类型讲怎么做。

### 代码分块

代码块的语义边界是语法结构，不是标点。一个函数 `def foo(): ...` 内部的换行、逗号、冒号都是语法的一部分，按 `RecursiveCharacterTextSplitter` 默认分隔符切，极大概率在某个函数中间断开——结果是上半截 `def foo():` 和下半截函数体被分进两个块，任何一个都无法独立编译或回答「foo 做什么」。

**正确做法：用 AST 解析，按函数/类/方法边界切。**

- Python 内置 `ast` 模块即可拿到函数、类的节点和它们在源码里的起止行，按节点边界切就保证每块是一个完整可编译单元。
- 多语言场景用 **tree-sitter**，它支持几十种语言、能给出精确语法树，比纯正则稳健得多。

**每个代码块要带上下文元数据**，否则语义是断裂的：

- 所属文件名 / 模块路径
- 所属类名（方法块要知道自己挂在哪个类下）
- 依赖的导入语句（函数体用到的符号可能来自文件顶部的 `import`）

没有这些，单独检索出一个 `def preprocess():` 块，读者不知道它属于哪个模块、依赖什么，可用性大打折扣。

**更省事的替代**：如果你不想自己写 AST 逻辑，LangChain 的 `RecursiveCharacterTextSplitter.from_language()` 预置了各语言的分隔符。以 Python 为例，它的分隔符优先级是：

```python
# LangChain from_language 为 Python 预置的分隔符（优先在类/函数边界断开）
separators = [
    "\nclass ", "\ndef ", "\n\tdef ",   # 类与方法边界优先
    "\n\n", "\n", " ", ""              # 退化：段落、行、词、字符
]
splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=512,
    chunk_overlap=64,
)
```

它覆盖 Python / JS / TS / Go / Rust / Java / C++ 等二十多种语言，代价是**不如真正 AST 精确**——它是在「类/函数分隔符」附近切，但切出来的块未必是完整语法单元（比如一个超长函数内部仍可能被二次切分）。对精确性要求高的场景，还是上 tree-sitter。

### 表格分块

表格是二维结构，行与列之间有强绑定。一旦被「按行截断」或「按字符截断」，读者拿到的是「一半的行 + 一半的列」，而 LLM 不知道自己拿的是残表，会自信地基于残缺数据作答——这是表格类幻觉的主要来源。

**核心动作：整块不切分，且必须先摘出来。**

1. **从正文流里摘出表格**，换成占位符（如 `[[TABLE_1]]`），让递归切分器根本碰不到它。表格作为独立单元单独存储。
2. **表题/表头前置关联**。表题（caption）通常在表格上方，解析时要专门把它和表格绑定，否则检索到表格却不知道它讲什么。
3. **检索文本与生成文本分离**——这是处理表格的关键技巧：
   - **检索用摘要**：给表格写一段自然语言摘要（「表 1 列出了各模型在 MMLU 上的准确率」），用摘要去匹配 query，因为自然语言比二维矩阵更容易被 embedding/BM25 命中。
   - **生成用原始表格**：真正喂给 LLM 的是原始结构化表格（或 Markdown 表格），保证数据精确。

这样既解决了「表难被检索到」（摘要好匹配），又解决了「表被切断」（整块不切），还解决了「数据失真」（生成用原始表）。

### 公式与数学内容

公式里的逗号、括号、上下标是语法的一部分，不是自然语言标点。按标点切会把 `∑_{i=1}^{n} (x_i - μ)²` 这种表达式从中间断开，破坏符号结构。

**做法：整体保留一个公式作为一个不可分割单元**，要么整块作为公式块，要么在切分时给公式段（如 `$$...$$` 或行内 `$...$`）加保护，不让字符切分器越过它的边界。

### 列表

列表项之间语义独立。一个 `1. 安装依赖 2. 配置环境变量 3. 启动服务` 的列表，如果切分器在第 2 项中间断开，下半截「配置环境变量」会失去「这是第 2 步」的上下文。

**做法：保持列表项完整性**，在列表项边界切，不要把单个列表项切成两半。多数现代分块器（LangChain `MarkdownHeaderTextSplitter`、Chonkie 等）对 Markdown 列表有原生支持，需要时显式开启。

## 实操

针对你的「中英混排 Word 文档（含表格与图片）」场景，推荐的管线是这样的：

1. **先用解析器做元素级分流**。docling 或类似工具能把 DOCX 解析成带类型的元素流（paragraph / table / code / picture / heading），这一步就把内容类型标好了——这是后续分别处理的前提。
2. **按类型分别切**：
   - 正文段落 → 递归字符分块（512 + 10~15% overlap，见 [[rag/03_智能分块/chunk大小与overlap取值\|chunk 大小与 overlap 取值]]）
   - 表格 → 整块摘出，存为独立节点 + 自然语言摘要
   - 代码 → `from_language()` 或 tree-sitter 按函数边界
   - 图片 → 转文字描述（caption / OCR / 多模态描述）后再当正文块
   - 公式 → 整体保留
   - 列表 → 按项边界
3. **块带类型元数据**。每个块打 `content_type` 标签，方便检索阶段按类型过滤或加权（例如代码块命中时给更高权重）。

> 关于解析阶段的元数据：用 docling 的 `HybridChunker` 时，产出的块会自带标题路径等元数据；但**实测 DOCX 场景下没有页码**——DOCX 的 `prov`（provenance）是空的，只有 PDF 才有页码。这点在 [[rag/03_智能分块/分块工具选型\|分块工具选型]] 里有展开。

## 陷阱与边界

- **表格跟着正文被递归切分器切断**：不先摘出表格，是混合文档最常见的失手。务必先占位、后处理。
- **代码块被切断导致无法执行**：按 token/标点切代码必出问题，上 AST / tree-sitter / `from_language()`。
- **公式被切散**：把公式里的括号逗号当标点切断，符号结构报废。整体保留。
- **列表项被切半**：失去「第几步」语境。保持列表项完整。
- **以为摘要可替代原始表**：摘要只用于检索匹配，生成时仍要原始表格，否则数据失真。
- **图片直接喂块**：图片要先转文字描述才能进 embedding，否则检索不到也读不懂。
