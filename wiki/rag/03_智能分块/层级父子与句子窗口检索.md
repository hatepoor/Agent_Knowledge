# 句子窗口与自动合并检索

## 概述

句子窗口检索（Sentence-Window Retrieval）与自动合并检索（Auto-Merging Retrieval）是 LlamaIndex 提出并命名的两种**层级化检索模式**，共同思想是：**用小块做检索（精确命中），用大块喂给 LLM（上下文完整）**。区别在于"从小块放大到大块"的策略：前者按固定邻接窗口扩展，后者按父子树形结构动态合并。它们是 [[rag/03_智能分块/文档分块策略|文档分块策略]] 中"父子分块"思想的两个工程化变体。

## 一、两种模式对比

| 维度 | 句子窗口（SWR） | 自动合并（AMR） |
|------|-----------------|-----------------|
| 检索单元 | 单句（1–3 句） | 层级树的叶子块（如 128 token） |
| 上下文扩展策略 | 命中句 ±k 句的固定窗口 | 同一父块的子块命中占比超阈值 → 整体替换为父块 |
| 结构假设 | 线性文本、句邻接即相关 | 文档有章节层级（章→节→段） |
| 最适配 | 信息密集的散文（论文、报告正文） | 层级结构长文档（手册、教材、法规） |
| 关键参数 | `window_size`（±2~3 常见） | `simple_ratio_thresh`（0.3–0.4 常见） |

> AMR 与 LangChain 的 [[rag/03_智能分块/文档分块策略|ParentDocumentRetriever]] 是同一思想的两种实现：LangChain 版本"检索子块、返回父块"是静态映射；AMR 增加了**动态阈值判断**——只有当足够多的兄弟子块同时命中时才升级到父块，避免"只命中一个子块却拖回整个大父块"的上下文膨胀。

## 二、LlamaIndex 代码示例

### 句子窗口检索

```python
# pip install -qU llama-index
from llama_index.core.node_parser import SentenceWindowNodeParser
from llama_index.core.postprocessor import MetadataReplacementPostProcessor
from llama_index.core import VectorStoreIndex

# 1) 每句单独成节点，并把前后窗口存进 metadata
node_parser = SentenceWindowNodeParser.from_defaults(
    window_size=3,                          # 命中句前后各 3 句
    window_metadata_key="window",
    original_text_metadata_key="original_text",
)
nodes = node_parser.get_nodes_from_documents(documents)

# 2) 只对"句节点"建向量索引
index = VectorStoreIndex(nodes)

# 3) 查询时把命中的短句替换为完整窗口再交给 LLM
query_engine = index.as_query_engine(
    similarity_top_k=6,
    node_postprocessors=[MetadataReplacementPostProcessor(target_metadata_key="window")],
)
```

### 自动合并检索

```python
from llama_index.core.node_parser import HierarchicalNodeParser, get_leaf_nodes
from llama_index.core.retrievers import AutoMergingRetriever
from llama_index.core.storage.docstore import SimpleDocumentStore
from llama_index.core import StorageContext

# 1) 三级层级解析：2048 → 512 → 128 token
node_parser = HierarchicalNodeParser.from_defaults(chunk_sizes=[2048, 512, 128])
nodes = node_parser.get_nodes_from_documents(documents)
leaf_nodes = get_leaf_nodes(nodes)

# 2) 全层级节点入 docstore（供合并时取父块），叶子节点入向量索引
storage_context = StorageContext.from_defaults()
storage_context.docstore.add_documents(nodes)
index = VectorStoreIndex(leaf_nodes, storage_context=storage_context)

# 3) 叶子命中占比 ≥30% 的父块触发合并
retriever = AutoMergingRetriever(
    index.as_retriever(similarity_top_k=12),   # 多召回叶子
    storage_context=storage_context,
    simple_ratio_thresh=0.3,
)
```

## 三、怎么选（含与父子分块的关系）

| 场景 | 建议 |
|------|------|
| 文档无明显层级、句间连贯性强 | SWR（窗口即语义邻域） |
| 章节层级清晰（标题结构、法规条款） | AMR / LangChain ParentDocumentRetriever |
| 命中常集中在同一节的多处 | AMR 收益最大（合并成完整小节） |
| 命中零散分布于全文 | SWR 更稳（合并条件难触发，AMR 退化成普通检索） |
| 不确定 | 先跑 [[rag/12_评估与监控/评估体系与RAGAS|评估基线]]，两种模式用 TruLens RAG Triad（Context Relevance / Groundedness / Answer Relevance）横向对比再定 |

## 四、常见问题

**Q1：window_size 调多大？**
从 ±2 开始，按答案所需上下文跨度调；窗口过大趋近于直接检索大块（丧失小块检索精度优势），过小则 LLM 缺上下文。有实验表明 SWR 在密集文档上优于固定分块基线，但窗口是首要敏感参数。

**Q2：ratio_thresh 设 0.5 好还是 0.3 好？**
阈值高 → 少合并、上下文小而精；阈值低 → 常合并、上下文大而全但更贵。经验起点 0.3–0.4；必须配合"喂给 LLM 的总 token 预算"约束（[[rag/13_工程横切/性能与成本优化|成本优化]]），防止合并后父块叠加超预算。

**Q3：SWR/AMR 和重排什么关系？**
正交且互补：SWR/AMR 决定"返回哪块、放多大"，重排决定"候选谁排前面"。常见组合：粗召回 → 重排 → 对 Top 候选做窗口扩展/合并 → 上下文组装。

**Q4：这两种模式能用 LangChain 实现吗？**
能。SWR ≈ 按句切块 + 返回时拼接邻句（自定义 Retriever 或句子窗口式 parent 映射）；AMR ≈ ParentDocumentRetriever 加上"命中兄弟块数阈值"判断。LangChain 官方 how-to 提供 ParentDocumentRetriever 全套（见 [[rag/03_智能分块/文档分块策略|分块策略页]] 引用）。

## 五、最佳实践

1. **块层级设计从真实文档结构出发**：AMR 的 `chunk_sizes` 应贴合文档本身的标题层级（章/节/段），机械的 2048/512/128 只对均匀长文有效。
2. **把"合并率/窗口命中率"作为观测指标**：合并率长期≈0 说明层级或阈值不匹配语料；窗口命中句占比异常低说明 Embedding 与句粒度不匹配。
3. **评估时用同一评估集横向对比**：直接检索 vs SWR vs AMR，看 RAG Triad 三项分数与成本（token/延迟），用数据选型而非直觉。
4. 与 [[rag/09_上下文构建与溯源/上下文压缩|过滤压缩管线]] 叠加时注意顺序：先合并成上下文单元，再做块内压缩，避免对将被合并的碎片重复压缩。
