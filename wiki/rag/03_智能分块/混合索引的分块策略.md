# 混合索引的分块策略

## 概述

通用分块方法见 [[rag/03_智能分块/文档分块策略|文档分块策略]]。本文回答一个**特有问题**：当同时建**稠密（向量）**与**稀疏（倒排/BM25）**两套索引时，切分该怎么设计？

核心结论一句话：**用一套 chunk 边界，但为两路准备两套文本表示。**

> 前提背景：[[rag/06_混合检索/混合检索|混合检索]] 的两路召回靠 RRF 融合，而融合建立在"两路返回的是同一个单元"这一假设上。本文所有约束都由此推导而来。

## 一、为什么必须共享 chunk 边界

这是最容易做错、且做错后极难排查的一点。

**绝不能给稠密与稀疏各切一套 chunk**，原因有三：

| 原因 | 说明 |
|------|------|
| **RRF 融合的前提** | 融合依赖两路候选的**同一 ID**。若稠密返回 `child_042`、稀疏返回 `parent_007`，无法判断两者是否同一段内容，融合退化成简单拼接，排名失去意义 |
| 工程复杂度 | 两套 chunk 需要维护两套 ID 映射表，且每次改参数都要同步 |
| 可调试性 | 两条路结果对不上，无法判断"是检索错了还是切分错位了" |

正确的职责划分：

| 层面 | 是否共享 | 说明 |
|------|----------|------|
| **chunk 边界** | 共享 | 两路索引的切片位置完全一致 |
| **chunk_id** | 共享 | 融合与回溯的唯一依据 |
| **metadata** | 共享 | 标题路径、文档 ID、语言标签、块类型 |
| **文本表示** | **不共享** | 稠密路用原文，稀疏路用分词后的词项序列 |

## 二、推荐方案：父子块结构

单一粒度的 chunk 无法同时满足两种索引的诉求，用父子块解耦：

```
原始文档
  ↓ 按标题层级 / 语义边界切分
父块 Parent（≈1500 字符）—— 生成时送入 LLM
  ↓ 在父块内部再切
子块 Child（≈400 字符）—— 建立索引
  ↓ 两路共用 child_id
稠密：原文 → embedding      稀疏：jieba 分词 → 倒排索引
  ↓ 检索 → 在子块粒度 RRF 融合 → 回溯父块 → 送入生成
```

具体流程与父子块的价值见 [[rag/03_智能分块/层级父子与句子窗口检索|层级父子与句子窗口检索]]；本文补充的是**混合索引下的额外约束**。

## 三、参数怎么定：两种索引的偏好冲突

稠密与稀疏对 chunk 的偏好**部分冲突**，参数取折中：

| 参数 | 稠密的偏好 | BM25 的偏好 | 混合场景建议 |
|------|-----------|-------------|--------------|
| **chunk 大小** | 256–512 token，语义聚焦 | 300–800 字符，tf 才有统计意义 | **400–600 字符**（中文约 200–300 字） |
| **边界依据** | 语义完整 | 词项共现窗口 | 语义边界优先（标题 > 段落 > 句号） |
| **overlap** | 10–25%，防语义切断 | **越少越好** | **10–15%**，比纯向量方案更保守 |
| **最小长度** | 无硬约束 | 太短则 tf/df 统计无意义 | 不小于 100 字符 |
| **最大长度** | 不超过模型**有效**窗口 | 长文档被长度归一化惩罚 | 不超过模型窗口的 1/4 |

**关于"最大长度"的反直觉点**：模型支持的长上下文（如 8192 token）**不是** chunk 大小的目标值。一个 1024 维向量要编码很长的文本，语义会被平均掉，多个主题混在一个向量里会导致检索精度下降。长上下文能力是给"整文档 embedding"场景用的，不是给 chunk 用的。

## 四、overlap 在混合索引下是把双刃剑（关键差异）

这是与纯向量方案**最重要的差别**，也是最容易忽略的一处：

| 视角 | overlap 的作用 |
|------|----------------|
| **对稠密侧** | **保护措施**。确保被切断的语义在相邻 chunk 中仍完整，所以纯向量方案常建议开到 20%–30% |
| **对稀疏侧** | **污染源**。同一段文字在多个 chunk 重复出现，导致三个问题 |

稀疏侧的具体危害：

1. **tf 被重复计入** → 同一词在多个 chunk 中"出现多次"，BM25 分数被无意义抬高
2. **候选名额被挤占** → 内容重复的几个 chunk 会同时进入候选集，占用 RRF 的有限名额
3. **df 虚高** → 该词在全局看来更"常见"，IDF 权重反而被拉低（对真正需要它的查询是削弱）

> **结论**：**混合索引下的 overlap 必须比纯向量方案更小**，10%–15% 是稳妥区间。若沿用纯向量时代的 30% overlap，稀疏路会明显劣化，且症状隐蔽（分数分布整体偏移，无报错），很难定位到切分参数上。

## 五、性价比最高的一招：把标题路径写进 chunk

结构化文档中，一个 chunk 脱离标题后往往完全不知道在讲什么。解法是把**标题链前置**到 chunk 文本：

```
LangGraph 状态管理 > Reducer 机制 > Send 的用法

Send 用于在节点内动态派发多个任务...
```

收益是**双向**的：

- **稠密侧**：获得语义锚点。孤立的"Send 用于动态派发任务"语义模糊，带上 `LangGraph > Reducer` 后向量落点准确得多
- **稀疏侧**：标题中的词项成为可匹配 token。用户搜 `Reducer` 时能直接命中，否则该词只存在于标题、不在任何正文 chunk 里

**边界**：只拼接**当前块所在的标题层级链**，不要把整棵标题树整体塞入。引入无关的上层词项会稀释 BM25 的 tf，也会让向量语义变散。

> 这一招是 Contextual Retrieval（Anthropic）的轻量版——后者用 LLM 生成更丰富的上下文前缀，效果更好但成本更高。见 [[rag/03_智能分块/文档分块策略|文档分块策略]] 的 2025–2026 改进章节。

## 六、表格与图片：作为独立"伪段落"入索引

从 Word/PDF 解析出的表格与图片，不走文本分块流程，而是各自成为独立的可检索单元：

| 内容类型 | 检索文本（`text_for_index`） | 生成文本（`text_for_llm`） | 是否切分 |
|----------|------------------------------|----------------------------|----------|
| 正文段落 | 标题链 + 子块原文 | 子块原文 | 是（父子块） |
| **表格** | 表名 + **自然语言摘要** + Markdown 表 | **原始 Markdown 表格** | **不切分**（整表一块） |
| **图片** | 图注 + **视觉模型生成的描述** | 描述（或按需回传原图） | 不切分 |

设计要点：**检索文本与生成文本分离**。表格用摘要检索（自然语言，用户口语化提问能命中），用原表生成（数据精确、行列关系完整）。原理与明细见 [[rag/01_多源数据接入/文档解析_PDF_Word_图片与表格|文档解析]]。

## 七、代码：父子块构建

```python
from langchain_text_splitters import (
    MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter,
)

# 第一层：按标题层级切父块，保留标题 metadata
header_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "h1"), ("##", "h2"), ("###", "h3")],
    strip_headers=False,      # 标题本身是可检索内容，不要剥离
)

# 第二层：在父块内部切子块
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=450,
    chunk_overlap=60,         # ≈13%：混合索引下不能开到 20%+
    separators=["\n```\n", "\n\n", "\n", "。", "！", "？", ". ", " "],
    keep_separator=True,      # 中英标点都要作为切分边界
)

def build_parent_child(raw_md: str, doc_id: str):
    parents, children = [], []

    for p_idx, parent in enumerate(header_splitter.split_text(raw_md)):
        # 拼出当前块的标题层级链，只取存在的层级
        path = " > ".join(
            parent.metadata[h] for h in ("h1", "h2", "h3")
            if parent.metadata.get(h)
        )
        parent_id = f"{doc_id}#p{p_idx}"
        parents.append({"id": parent_id, "text": parent.page_content, "title_path": path})

        for c_idx, piece in enumerate(child_splitter.split_text(parent.page_content)):
            children.append({
                "id": f"{parent_id}c{c_idx}",     # 子块 ID —— 两路索引共用
                "parent_id": parent_id,           # 回溯父块的指针
                "text_for_index": f"{path}\n\n{piece}" if path else piece,
                "text_for_llm": piece,
                "doc_id": doc_id,
            })
    return parents, children
```

建两路索引时 ID 用同一批，只有文本表示不同：

```python
children = build_parent_child(raw_md, doc_id)[1]

# 稠密路：带标题链的原文 → embedding
dense_upsert([
    {"id": c["id"], "vector": embed(c["text_for_index"]), "payload": c}
    for c in children
])

# 稀疏路：分词后的词项序列 → 倒排索引
sparse_upsert([
    {"id": c["id"], "tokens": list(jieba.cut_for_search(c["text_for_index"]))}
    for c in children
])
```

检索时在子块粒度融合，再回溯父块送 LLM：

```python
def hybrid_search(query: str, top_k: int = 5):
    dense_ids  = dense_search(embed(query), limit=50)            # 返回 child_id
    sparse_ids = sparse_search(list(jieba.cut_for_search(query)), limit=50)

    fused = rrf_fuse([dense_ids, sparse_ids])[:20]

    # 子块 → 父块去重：命中的多个子块常属于同一父块，必须去重
    parent_ids = list(dict.fromkeys(
        child_to_parent_map[cid] for cid in fused
    ))[:top_k]

    return [parent_store[pid] for pid in parent_ids]
```

**父块去重这一步很关键**：命中的 5 个子块很可能来自同一个父块，不去重会导致上下文被同一段内容重复占满，浪费 token 预算。

## 八、上线前检查清单

1. 两路索引是否共用**同一批 chunk_id**？（否则 RRF 融合失效）
2. overlap 是否控制在 15% 以内？
3. 代码块与表格是否完整未被切断？
4. chunk 是否携带了标题路径？
5. 是否统计过实际 chunk 长度分布（P50 / P95）？——配置的理论值与真实分布常不符，中文与代码混排的文档尤其明显
6. 稀疏路的 analyzer 是否用了中文分词器（jieba / IK），而非空格切分？
7. 索引与查询是否使用同一分词器 + 同一份自定义词典？
8. 检索后是否对父块做了去重？

## 九、常见问题

**Q1：能不能干脆只建一套 chunk，纯向量检索？**
可以，但会丢掉标识符精确匹配的能力（函数名、型号、编号）。是否值得上混合索引，取决于语料中"精确词"的占比——技术文档、代码库、合同条款占比较高，收益明显。

**Q2：父块要不要也入索引？**
通常不需要。父块只作为"返回单元"存在，不参与召回。若某些查询确实需要更大范围的语义匹配，可让父块也入向量库，但这会让候选粒度混杂，融合逻辑变复杂，需谨慎评估。

**Q3：overlap 调小会不会伤到稠密侧？**
会有一点。但用父子块可以弥补——即使子块边界切断了语义，回溯到的父块仍提供完整上下文。这正是父子块与"小 overlap"能配合使用的原因。
