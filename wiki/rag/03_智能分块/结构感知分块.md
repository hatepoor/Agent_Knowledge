# 结构感知分块

> 结构感知是性价比最高的一份质量方案——结构信息是现成的，不需要模型推理，成本为零，却能把块天然对齐到章节。

## 核心结论

- 在 2026 年的分块工具箱里，**结构感知是「性价比最高」的高质量方案**：文档里的标题、章节、代码节点本身就是免费的边界信号，你不用付任何 embedding 或 LLM 调用，就能把块切得「不跨章节、语义自洽」。
- 它的依据来自文档格式自带的标记：Markdown 的 `#` 层级、HTML 的 `<h1>`~`<h6>`、Word 的段落样式（`style.name` 以 `Heading` 开头）、LaTeX 的 `\section{}`、以及代码的 AST 节点。
- 它和父子分块是**同一件事的两种说法**：第一刀切出的 section 是父块，第二刀切出的 chunk 是子块。所以「两阶段切分」与「父子分块」本质是同一个结构。
- 关键成功要素有三条：**两阶段顺序不能反**、**第二刀用 `split_documents` 而非 `split_text`**、**标题链前置**。下面逐条展开。

## 机制与原理

### 依据：四种格式的结构标记

| 格式 | 结构标记 | 如何读取 |
|---|---|---|
| Markdown | `#` / `##` / `###` | 正则按 `#` 数量判层级 |
| HTML | `<h1>`~`<h6>` | 解析 DOM 的标题节点 |
| Word（python-docx） | 段落 `style.name` 以 `Heading` 开头 | `p.style.name.startswith("Heading")` |
| LaTeX | `\section{}` / `\subsection{}` | 正则提取 |
| 代码 | 函数/类/AST 节点 | 语言解析器（如 `tree-sitter`） |

对你的场景（中英混排 Word 文档，有表格与图片）而言，最重要的一条是 **Word 标题样式**——作者用「标题 1/2/3」排出来的层级，比正文里的标点可靠得多，应当优先作为切分依据。

### 必须两阶段，且顺序不能反

结构感知不是「一步切到位」，而是**两刀**：

1. **第一刀：结构感知**——按标题层级切出「父块」（section），保证每个父块**不跨章节**；
2. **第二刀：递归**——在每个父块内部再用递归分块切，保证每个子块**不超长**。

**顺序绝不能颠倒。** 原因：

- 结构边界是**硬边界**——章节与章节之间是不该跨越的语义分界；
- 递归只能在自然边界「尽量」断开，是**软边界**。

如果先递归，章节边界早就被切碎了，后续你想「按结构重组」就得做「把碎片拼回章节」的复杂工作，metadata 也早已丢失。原则就一句：**从粗到细，从硬边界到软边界**。先拿硬边界框住大块，再在块内用软边界细切，永远不会丢失结构信息。

### 关键 API 细节：`split_documents` vs `split_text`

这是最容易犯的错，也是结构感知能否生效的分水岭：

- **第二刀必须用 `split_documents(sections)`**（传入第一刀产出的 `Document` 对象列表）；
- **不能用 `split_text(md_text)`**（传入原始字符串）。

区别在于：`split_documents` 会**继承 metadata**——第一刀从标题里提取出的 `section` / `subsection` / 标题文本，会被自动带进切出的每个子块；而 `split_text` 只收到一段纯文本，第一刀辛辛苦苦提取的标题信息**全部丢失**，等于白切。

```python
# 错误：第二刀用 split_text，metadata 全丢
md_text = md_splitter.split_text(raw)        # 返回 str，标题信息没了
chunks = recursive.split_text(md_text)       # 纯文本再切，无层级元数据

# 正确：第二刀用 split_documents，metadata 继承
sections = md_splitter.split_text(raw)       # 实为 Document 列表（带 metadata）
chunks = recursive.split_documents(sections)  # 每个 chunk 继承 section 元数据
```

### `strip_headers=False`：保留标题文本本身

默认 `MarkdownHeaderTextSplitter` 会把标题从正文里剥掉只留 metadata。但标题是**高信息量的可检索内容**——用户搜「参数建议」时，往往只有标题里出现了「参数」二字能命中。所以设 `strip_headers=False`，让标题文本留在 chunk 里一起被 embed / 索引。

### 标题链前置：把层级路径拼到 chunk 前面

把「当前 chunk 所在的标题层级链」拼到 chunk 文本前面，例如：

```
# 安装 > ## 配置 > ### 参数建议
Send 用于动态派发任务，建议 batch_size 设为 32……
```

收益是双向的：

- **稠密侧（embedding-3）**：孤立的「Send 用于动态派发任务」语义模糊，向量落点飘；带上章节路径后，模型能锚定「这是安装-配置-参数建议下的内容」，向量落点准确得多。
- **稀疏侧（jieba / BM25）**：标题中的词项（安装、配置、参数建议）成为可匹配的 token，恰好命中用户用标题词发起的查询。

**边界**：只拼**当前所在的层级链**，不要把整棵标题树（祖先章节的全部标题、甚至文档根标题）塞进去。引入无关上层词项会稀释 BM25 的词频权重，也让稠密向量语义变散，反而伤害检索。

## 实操

```python
# pip install -qU langchain-text-splitters
from langchain_text_splitters import (
    MarkdownHeaderTextSplitter,
    RecursiveCharacterTextSplitter,
)

# 第一刀：结构感知（按标题层级，保留标题文本）
headers = [
    ("#", "h1"),
    ("##", "h2"),
    ("###", "h3"),
]
md_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers,
    strip_headers=False,   # 标题文本保留在 chunk 里，提升可检索性
)
sections = md_splitter.split_text(markdown_doc)  # 返回 Document 列表

# 第二刀：递归（在父块内部细切，继承 metadata）
recursive = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=80,
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],
    keep_separator=True,
)
chunks = recursive.split_documents(sections)  # 关键：split_documents

# 验证 metadata 确实继承了标题链
for c in chunks[:3]:
    print(c.metadata, "->", c.page_content[:40])
```

Word 文档同理：先用 `python-docx` 遍历段落，遇到 `style.name.startswith("Heading")` 就开新 section，把层级与标题写入 metadata，再对每段正文用 `split_documents` 细切。表格/图片作为特殊元素单独分流（见 [[rag/03_智能分块/特殊内容分块]]）。

## 陷阱与边界

1. **标题层级配得太细 → 长尾标题被当正文**：如果你把 `####` 甚至 `#####` 也列进 `headers_to_split_on`，那些极少出现的小标题会变成「只有一行标题」的碎 section。只配到文档实际用到的层级（通常 `#`~`###`）。
2. **标题下无正文 → 空块**：某个标题后面紧跟下一个标题、中间没有正文，会切出「只有一行标题」的空块。需后处理：空块要么并入相邻 section，要么丢弃。
3. **Python 注释 `# 这是注释` 被误判**：在代码文件里，Markdown 风格的 `#` 是注释而非标题。对代码务必走 AST 分块，别用 Markdown 结构切分器。
4. **表格跨标题边界被切断**：结构切分器按文本流切，表格可能正好跨越章节标题，被拦腰截断。表格应作为整体元素单独保留（特殊内容分块）。
5. **两阶段不会跨章节合并小块**：如果文档标题很密（几乎每段一个小标题），第一刀切出大量极短 section，第二刀在 section 内部「切不出东西」，于是产生大量几十 token 的碎块。解决：在同一 section 内做后处理合并——把相邻的、都过短的子块拼起来，直到接近 `chunk_size`。这是结构感知最常见的「碎块瘟疫」，务必在摄入管线里加一步合并。
