> 块被从全文切下来后，最大的痛点是「脱离上下文语义不完整」。本页讲解决这个问题的两条模型/工程路线：Late Chunking 与 Contextual Retrieval。

## 核心结论

- 要解决的**根本问题**：块脱离全文后语义残缺。例如「它支持动态扇出」单独成块，读者不知道「它」指什么——这种指代与背景缺失会直接拉低检索与生成的准确率。
- **Late Chunking（Jina AI，2024）**：先整篇嵌入、再按块边界池化。每个块向量**自带全文语境**，代价是需要支持长上下文的 embedding 模型。
- **Contextual Retrieval（Anthropic，2024）**：切分后用 LLM 给每块生成「上下文前缀」再嵌入。实测**检索失败率相对下降 49%，叠加重排后下降 67%**，代价是每块一次 LLM 调用。
- 第三条路是工程手段「标题链前置」（零成本、效果有限），在 [[rag/03_智能分块/结构感知分块\|结构感知分块]] 的标题链前置里讲。
- 成本效果排序：**标题链前置（近零）< Late Chunking（需换模型）< Contextual Retrieval（每块一次 LLM）**。殊途同归，都在补「块缺的上下文」。

## 机制与原理

### 根问题：块为什么语义不全

分块天然在做「局部化」：把一个长文档切成小单元，是为了让每个单元的 embedding 聚焦、检索时更精准（见 [[rag/03_智能分块/chunk大小与overlap取值\|chunk 大小与 overlap 取值]] 里「块内主题混杂」那段）。但局部化的代价是**单元失去了全文背景**。

典型症状：

- 指代缺失：「它」「该方法」「上文提到」单独成块时无法解析。
- 背景缺失：「阈值设为 0.85」不知道是在讲什么任务的阈值。
- 范围缺失：「以下三种情况」后面被切走了，块自己不完整。

这个问题有三条解法，分属不同成本档：

1. **标题链前置**（工程，零成本）——补结构信息，见结构感知页。
2. **Late Chunking**（改嵌入机制）——本页讲。
3. **Contextual Retrieval**（改文本内容）——本页讲。

### Late Chunking（先嵌后切，Jina AI 2024）

**做法**：不要先切再各自嵌入。而是：

1. **整篇文档做一次长上下文嵌入**，模型输出每个 token 的向量（而非一个文档级向量）。
2. **按块边界对 token 向量做池化**（通常是 mean pooling），得到每个块的向量。

关键在第一步：因为编码是在「看过整篇文档」的前提下做的，所以**每个块向量都携带了全文语境**——它知道「它」指的是前文哪个对象，知道「阈值 0.85」属于哪个任务。这是它和「先切后嵌」的本质区别：先切后嵌时，每块只在自己的小窗口里编码，天然看不到窗外。

**代价：需要支持长上下文的 embedding 模型**。Late Chunking 的前提是嵌入模型能吃下整篇文档后再吐出逐 token 向量。已知支持的有：

- **BGE-M3**（8192 token 上下文，长上下文 embedding 场景适用）——你未来若换 BGE-M3，这条路可行。
- **jina-embeddings-v3** 等支持长上下文的模型。

**对你的直接意义**：你当前用智谱 embedding-3。Late Chunking 是否可用，取决于 embedding-3 的上下文上限是否够大、且是否支持逐 token 输出向量——**这一点需要实测确认（待核实）**。在换 BGE-M3 之前，不要假设 Late Chunking 开箱即用。

### Contextual Retrieval（切后加前缀再嵌，Anthropic 2024）

**做法**：

1. 正常切分得到一块块原文。
2. 用 LLM 为**每一块**生成一段「上下文前缀」——说明「这块在全文里讲什么、它和前后文的关系」。
3. 把「前缀 + 原文」拼在一起再嵌入，存入索引。

注意它改的是**文本内容**（往块里塞上下文），不是改嵌入机制。块向量本身还是普通 embedding，但向量编码的文本已经不再是「孤零零的一块」，而是「带背景的一块」。

**实测效果**（Anthropic 公开数据）：

- 检索失败率相对下降 **49%**。
- 叠加重排（reranking）后，下降 **67%**。

这是个相当可观的提升，尤其适合你这种「文档内部指代多、块容易失语境」的知识库。

**代价：每块一次 LLM 调用**。即便用 prompt caching 把全文缓存起来摊薄成本，对「数千 chunk」规模仍是可观的开销——但要算清账：这是一次性摄入成本，索引建好后查询不再花钱，而它换来的是持续的检索质量提升。

### 两条路线对比

| 维度 | Late Chunking | Contextual Retrieval |
|---|---|---|
| 提出方 / 年份 | Jina AI / 2024 | Anthropic / 2024 |
| 改的是什么 | **嵌入机制**（先嵌后切、池化） | **文本内容**（加上下文前缀再嵌） |
| 核心依赖 | 支持长上下文的 embedding 模型 | 一个能写前缀的 LLM |
| 块向量是否带全文语境 | 是（编码时看过整篇） | 是（前缀由 LLM 基于全文生成） |
| 主要成本 | 需换/用长上下文 embedding 模型 | 每块一次 LLM 调用 |
| 是否改索引内容 | 否（向量更聪明） | 是（文本被加长） |

有意思的是：一个改嵌入机制、一个改文本内容，**殊途同归**——最终都让块向量「懂」了自己在全文中的位置。选哪条，本质是看你手里的牌：有长上下文 embedding 模型就走 Late Chunking；有 LLM 预算就走 Contextual Retrieval。

### 第三条路（一笔带过）

工程手段「标题链前置」：把「文档标题 > 章节 > 小节」这样的标题链拼到每个块前面。它**零成本**（不用模型），但只补了结构信息，补不了章节内的指代（「它」指什么仍然不知道）。效果是三条路里最有限的，但在 [[rag/03_智能分块/结构感知分块\|结构感知分块]] 里详细讲，因为它和「按标题切分」是配套的。

## 实操

### Contextual Retrieval 的成本控制

如果你决定走 Contextual 路线，几个摊薄成本的做法：

1. **prompt caching**：把整篇文档作为 system/user 的缓存部分传入，只对每个块发一次增量请求（「请为下面这块生成上下文前缀」）。这样全文只编码一次，成本主要来自增量生成。
2. **只对长块生成前缀**：短块（比如 < 100 token）本身语境通常够用，跳过不生成；只给「有价值的长块」加前缀，省掉一大笔调用。
3. **批量生成**：把同文档的多个块放在一个请求里批量产出前缀，减少往返开销。

### 效果验证

无论走哪条路，都回到评估集验证（方法见 [[rag/03_智能分块/chunk大小与overlap取值\|chunk 大小与 overlap 取值]] 的「实测最优值」）：

- 在「加上下文」前后分别跑同一批 query 的 Recall@10。
- Contextual 路线可对照 Anthropic 的 49% / 67% 结论，看你的数据是否吻合。

### 换模型时的联动

- 若未来从智谱 embedding-3 换到 **BGE-M3**：Late Chunking 的可行性随之打开（BGE-M3 支持长上下文），可与 Contextual 做 A/B 对比，挑效果/成本更优者。
- 注意 embedding 模型一换，**所有块向量都要重算**——上下文增强策略也要一并重跑，不要新旧混用。

## 陷阱与边界

- **Late Chunking 需模型真支持长上下文**：伪支持（标称长上下文但实际截断）会让块向量只看到半篇，反而比先切后嵌更差。换模型前务必验证。
- **Contextual 前缀生成失败要降级**：某块前缀生成失败（超时/报错）时，应**回退为「不加前缀」照常嵌入**，而不是丢块——丢块比「块缺上下文」更糟。
- **前缀版本变更后必须重跑**：前缀的 prompt 改过、或 LLM 版本升级后，旧块是新风格、新块是旧风格，索引里块风格不一致会扰检索。任何前缀逻辑变更都要全量重嵌。
- **以为上下文增强能替代好的切分**：增强是「补丁」，基础切分（大小、特殊内容处理）仍是地基。先切好，再增强。
- **忽略重嵌成本**：换 embedding 模型或改前缀逻辑 = 全量重算，纳入运维预算。
