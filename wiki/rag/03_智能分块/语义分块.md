# 语义分块

> 语义分块用「相邻句子的语义距离突变」来下刀——逻辑优雅，但 2026 年的实测给了它一个清醒的定位：它是补位选手，不是默认选项。

## 核心结论

- 语义分块的机制：把文本按句子切分 → 给每个句子做 embedding → 算相邻句子的余弦距离 → 在距离的**突变点**（超过阈值）下刀。逻辑是「语义连续的地方距离小，话题切换处距离骤增」。
- **但它是最被滥用的方法**：索引开销比递归分块**慢约 14 倍**（每个句子一次 embedding），而准确率增益**往往小到测不出来**。
- 只有当**内容话题突变且不均匀、且无结构可用**时才真正值得；一旦文档「已统一且有结构」，递归或结构感知分块能**免费**捕获同样的边界——你不该用昂贵的 embedding 去「猜」一份文档明明已经白纸黑字写着的边界。
- 正确用法是**组合**：先按结构（零成本）切，只在结构缺失的长段落内部才启用语义判断，把 14 倍成本摊薄到很小一部分内容上。

## 机制与原理

### 完整流程

1. **句子切分**：用标点把文本切成句子单元（中文按 `。！？`，英文按 `. ! ?`）。
2. **逐句 embedding**：对每个句子调用 embedding 模型，得到句向量。
3. **算相邻距离**：计算相邻句子向量的余弦距离（或余弦相似度的补数），得到一条「距离序列」。
4. **找突变点下刀**：距离序列里某个位置突然跳高（当前句与上一句语义不连续），就在那里切开。

直觉：同一段落内句子彼此相关 → 距离小；从「实验方法」切到「政策建议」 → 距离骤增 → 这就是该切的边界。

### 朴素实现的性能陷阱（重要）

最直白的写法是「for 循环里逐句调 embed API」——这有两个致命问题：

- **极慢**：每个句子一次网络往返，几千句就是几千次请求；
- **易限流**：请求量暴涨会触发 embedding 服务（包括智谱 embedding-3）的 QPS / 速率限制，直接报错或退避。

正确做法：**批量化**——把句子攒成一批，一次请求返回整批向量；或改用**本地 embedding 模型**（如 `bge-small-zh` 本地推理），彻底绕开 API 限流。批大小按服务上限调（如 32~128 句/批）。

### 成本数据（已核实）

| 指标 | 数值 | 说明 |
|---|---|---|
| 索引开销 | 比递归分块**慢约 14 倍** | 每个句子一次 embedding，递归只需对最终块 embed |
| 准确率增益 | **往往小到测不出来** | 在已有结构的文档上，提升不显著 |

参照基准：递归分块 @ 512 token + 10~20% overlap 已达约 69% 检索准确率。语义分块要「值回」14 倍成本，必须在特定场景里体现出可测量的增益——而这恰恰很少发生。

### 阈值怎么定

绝对阈值**不可跨模型迁移**：不同 embedding 模型的相似度分布差异极大（有的模型句子间距离普遍 0.2，有的普遍 0.6），在一个模型上「距离 > 0.5 切」在另一个模型上可能一刀切到底或切得稀碎。

建议用**相对方法**：

- 按**分位点**截断：把距离排个序，取前 10%（或某个分位）作为「突变」，低于该分位不切；
- 或找**最大距离差**：在距离序列里找相邻差距最大的若干处作为候选断点，按想要的块数截断。

这样无论换成哪个 embedding 模型，切分逻辑都相对稳定。

## 何时真正值得

语义分块只在该场景发光：**内容话题突变且不均匀，同时没有结构标记可用**。典型例子：

- **研究报告**在方法论 / 结果 / 政策含义之间反复跳转，且没用小标题分隔；
- **多来源拼接的法规文本**，段落来源混杂、话题跳跃；
- **话题跳跃的客服通话记录**，用户一句投诉、一句闲聊、一句技术细节来回切。

这些场景下，符号级的分隔符（句号、换行）根本捕捉不到「话题已换」，只有语义距离能标出真正的边界。

## 何时不值得（关键判断）

**内容已统一且有结构时，递归或结构感知分块能免费捕获同样的边界。**

举个例子：一份用 Word 标题样式排好的技术文档，章节边界清清楚楚写在 `Heading 2` / `Heading 3` 里。你此时上语义分块，等于花 14 倍成本去「猜」一份文档明明已经告诉你的边界。结构感知分块（零成本）切出来的块，边界准确率反而更高——因为它用的是**确定的结构事实**，而非**embedding 估计的概率**。

一句话：**有结构先用结构，没结构再谈语义。**

## 与结构感知的组合策略

把语义分块从「全局默认」降级为「局部补刀」，是 2026 年最务实的落地法：

```
文档 → 结构感知切分（零成本）
       └─ 对每个「结构内、但仍过长、且无内部标点层级」的段落
             → 仅在这一段内部启用语义分块
```

这样，14 倍成本只花在「结构缺失的长段落」这一小部分内容上，整体索引速度几乎不受影响，却能在真正需要语义边界的地方拿到增益。

## 实操（批量 embedding 的骨架）

```python
# 伪代码骨架：批量 embedding 避免逐句限流
sentences = split_into_sentences(long_paragraph)      # 按中英文标点切句
BATCH = 64
embeds = []
for i in range(0, len(sentences), BATCH):
    batch = sentences[i:i+BATCH]
    embeds += embed_api(batch)                        # 一次请求多句，规避限流

# 算相邻余弦距离
import numpy as np
dists = [1 - cosine(embeds[i], embeds[i+1]) for i in range(len(embeds)-1)]
# 相对阈值：取距离前 10% 分位作为突变点
thr = np.quantile(dists, 0.90)
cuts = [i for i, d in enumerate(dists) if d > thr]
# 按 cuts 拼装 chunk
```

> 落地前先确认：你的文档是否真有结构？有结构请直接走 [[rag/03_智能分块/结构感知分块]]，把语义分块留给上面的「组合策略」里的局部补刀。

## 陷阱与边界

1. **逐句调用导致限流**：见性能陷阱，务必批量化或本地模型。
2. **阈值跨模型迁移失效**：绝对阈值换模型即废，用分位/最大差等相对方法。
3. **对已有结构的文档盲目启用**：花 14 倍成本重做结构感知已免费做好的事。
4. **分出的块长度不均**：语义边界随话题密度走，有的块几十字、有的上千字，反而恶化检索（过短缺语境、过长稀释向量）。必要时对过短块做合并、过长块兜底递归切。
5. **句子切分器本身的误差**：中英混排、缩写（`Dr.`）、省略号会误判句边界，先在切句层校准，否则后续距离全错。
