# 文本规范化（Text Normalization）

> 文本规范化是让"看起来一样"的文本"真的在比特层面也一样"的底层工程——它不增删语义，只统一字面，却是后续分块、embedding 与 BM25 都能正确匹配的前提。

## 核心结论

RAG 检索的本质是"比对"：稠密向量比语义相似度，BM25 比词项是否出现。两套比对都假设**相同的字就是相同的字**。但真实语料里，同一个汉字、同一个字母、同一个标点，常常以多种 Unicode 编码形式存在。如果不先做归一，就会出现最气人的现象：**字面完全相同、肉眼无法分辨，检索却匹配不上**——因为底层码位不同。

规范化的收益不显山露水，但不做的代价实实在在：重复 index、召回漏检、相似度计算被噪声拉低。它应该放在清洗管线最靠前，且**在去重、噪声检测、分块之前**完成，因为后面所有环节都依赖"字面一致"这个前提。

## 机制与原理

### 1. Unicode 规范化（NFC / NFD / NFKC / NFKD）

Unicode 里很多"一个可见字符"可以有多种编码方式，典型分两类：

- **组合字符（Composed vs Decomposed）**：以「é」为例。它可以是一个码位 `U+00E9`（LATIN SMALL LETTER E WITH ACUTE，预组合形式），也可以是两个码位 `U+0065`（e）+ `U+0301`（COMBINING ACUTE ACCENT，组合附加符）。两者显示完全一样，但字节不同。
- **兼容等价（Compatibility）**：全角字母 `Ａ`（U+FF21）和半角 `A`（U+0041）、罗马数字 Ⅱ 和 II、上标 ² 和数字 2，在"兼容意义"上相等，但码位不同。

四种标准形式：

| 形式 | 含义 | 做了什么 | 典型用途 |
|------|------|----------|----------|
| NFC | 标准组合 | 能组合的尽量合为一个码位 | **默认推荐**，最接近"人写的字" |
| NFD | 标准分解 | 拆成基字符 + 组合符 | 某些语言处理、排序 |
| NFKC | 兼容组合 | 先兼容映射再组合 | 归一全角/上标/罗马数字 |
| NFKD | 兼容分解 | 先兼容映射再分解 | 清洗噪声字形 |

为什么必须做：同一份文档里，可能一段来自 Word 复制（NFC），一段来自网页粘贴（NFD），肉眼一致却在 `==` 比较、`hash`、词项统计时判为不同。对中文而言，带声调的拼音、注音、某些异体字都可能出现组合/分解差异；对拉丁字母，重音字符、德文 ä ö ü 是重灾区。

### 2. 全角转半角

中文排版习惯会引入大量全角字符：全角逗号 `，`（U+FF0C）、全角括号 `（）`（U+FF08/FF09）、全角冒号 `：`（U+FF1A）、全角空格（U+3000，IDEOGRAPHIC SPACE）。这些对人和模型看起来"差不多"，但对分词器（jieba）和 BM25 的 term 匹配是**完全不同的 token**——全角逗号和半角逗号会被当成两个不同标点，全角字母和半角字母是两个不同词项。

映射思路是区间整体平移：全角 ASCII 可视字符集中在 `U+FF01`–`U+FF5E`，对应的半角是 `U+0021`–`U+007E`，差一个固定偏移 `0xFEE0`。再加两个特例：全角空格 `U+3000` → 普通空格 `U+0020`，全角居中句号 `U+30FB` 等个别符号按需处理。

### 3. 顺序问题（极易踩坑）

正确顺序：**先 Unicode 规范化 → 再全角转半角 → 再空白压缩**。

- 必须先 NFC/NFKC，**再**全角转半角：因为 NFKC 会把全角字母 `Ａ` 直接规范成半角 `A` 本身；如果你先手动转半角、后 NFKC，某些边界字形（如全角数字、全角片假名）可能没被覆盖到，而 NFKC 能一次性处理更全。反过来若顺序颠倒，部分全角字形在 NFKC 之前已被你改掉不影响，但**真正危险的是先做空白/换行处理再 Unicode 归一**——组合符可能被误当普通字符处理。
- 更隐蔽的错序：先压缩空白再做全半角。全角空格 `U+3000` 若没先转成普通空格，你的"压缩连续空格"正则（`[ \t]+`）根本不会匹配它，导致全角空格残留。所以**空格归一依赖全角转半角先完成**。

### 4. 空白处理

要清理的不可见/冗余空白：

| 类型 | 码位 | 说明 |
|------|------|------|
| NBSP 不间断空格 | U+00A0 | 网页/Word 常见，视觉同空格但非 ASCII 空格 |
| 零宽空格 | U+200B | 完全不可见，会插入到 token 中间破坏匹配 |
| BOM | U+FEFF | 文件头标记，残留会干扰首字符比较 |
| 行尾空白 | — | 拖尾空格 |
| 连续空格 / 空行 | — | 排版冗余 |

关键约束：**压缩横向空白（连续空格）时绝对不要动换行**。换行是后续切分（按段、按标题）的重要边界信号——你把一个空行压没了，下游可能把两段不同语义的文本并成一块，破坏了结构感知分块。正确做法是只压 ` `、`\t`、NBSP、全角空格这类的横向空白，空行单独用「连续空行 → 单个空行」处理，且不进一步吞掉。

### 5. 换行统一

文档常混用 `\r\n`（Windows CRLF）、`\r`（老 Mac）、`\n`（Unix LF）。尤其你的素材是 Windows 环境下的 Word 文档，转出来很可能带 `\r\n`，而处理脚本、正则、分词器往往按 `\n` 假设。统一成 `\n` 是第一步；第二步才是空行压缩。

### 6. 编码检测与乱码修复

来源可能是 GBK、UTF-8、带 BOM 的 UTF-8 混杂。检测用 `chardet`（老）或 `charset-normalizer`（新，对中文更稳）。常见乱码：UTF-8 字节被按 GBK 解码，会产生「锟斤拷」（源自 UTF-8 的 U+FFFD 替换字符被反复错误编码）这类特征串，是强信号。

修复边界要清醒：**有些乱码不可逆**。一旦字节被错误解码又重新编码，原始信息已丢，只能标记/丢弃，不能"还原"。所以原则是"在读取入口就正确解码"，而不是事后救火。

### 7. 存两份文本的工程取舍

归一化会改变字面（NFKC 改掉全角、上标、兼容字形；全半角改变符号）。如果只存一份归一后的文本，会出现一个一致性问题：**引用溯源时，用户看到的"原文"和库里存的"归一文本"对不上**，尤其涉及代码、公式、专有名词时。

推荐策略——存两份：

- `text_orig`：保留原始字面，用于**生成引用、溯源展示、人工复核**，不动它。
- `text_norm`：归一后的文本，用于**检索匹配、embedding、BM25**。

两者通过同一文档 ID 关联。代价是多一份存储，收益是"检索用的干净文本"和"给人看的原文"各司其职，互不污染。

## 实操

```python
import unicodedata
import re

# 全角(FF01-FF5E) -> 半角(21-7E)，差值 0xFEE0
FULL_TO_HALF = {c: chr(ord(c) - 0xFEE0)
                for c in range(0xFF01, 0xFF5E + 1)}
FULL_TO_HALF[0x3000] = ' '  # 全角空格

def to_half_width(text: str) -> str:
    return ''.join(FULL_TO_HALF.get(ord(ch), ch) for ch in text)

def normalize_text(text: str) -> str:
    text = text.replace('\ufeff', '')          # 去 BOM
    text = unicodedata.normalize('NFC', text)  # 先 Unicode 归一
    text = to_half_width(text)                 # 再全半角
    text = text.replace('\r\n', '\n').replace('\r', '\n')  # 换行统一
    text = text.replace('\u00a0', ' ').replace('\u200b', '')  # NBSP / 零宽
    text = re.sub(r'[ \t]+', ' ', text)        # 横向空白压缩(不动换行)
    text = re.sub(r'\n{3,}', '\n\n', text)     # 空行压到最多两行
    return text.strip()
```

编码检测示例（`charset-normalizer` 优于 `chardet`，对 CJK 更可靠）：

```python
from charset_normalizer import from_bytes
best = from_bytes(raw_bytes).best()
encoding = best.encoding          # 推断编码
text = best.output()              # 解码为文本
if '�' in text:                   # 含替换字符 => 可能仍有乱码
    ...                           # 标记待人工核查(待核实)
```

## 陷阱与边界

- **过度规范化破坏代码块与数学符号**：NFKC 会把上标数字（`x²`→`x2`）、全角符号、某些上下标改掉，影响代码或公式的字面正确性。建议对 ` ``` ` 围栏代码块、LaTeX `$...$` 区域**跳过** NFKC，只做基础清洗。
- **对已有索引执行规范化变更后忘记重建索引**：改了归一规则（比如从 NFC 换成 NFKC、补了全半角），但旧向量库还是用旧规则建的——新旧文档字面不一致，检索对不上。任何归一规则变更都视为**破坏性变更，必须全量重建索引**。
- **零宽字符被忽略**：`U+200B`、`U+200D`（零宽连字）、`U+FEFF` 肉眼不可见，却会插进词中间（如 `手​机` 变成两个 token），务必在归一阶段清除。
- **只归一正文不归一查询**：用户查询若未走同一套归一，而库里文本归一了，照样匹配不上。归一管线要同时作用于**索引侧与查询侧**（见 [[rag/05_查询转换与改写/查询结构化与槽位映射|查询改写]] 的一致性要求）。
