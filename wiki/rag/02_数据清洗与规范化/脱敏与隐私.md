# 脱敏与隐私（PII Masking & Privacy）

> 脱敏不是"清洗阶段跑一次正则"那么简单。真正的坑在**全链路**——索引、缓存、日志、监控里只要还有一处原文，脱敏就等于没做。

## 核心结论

个人敏感信息（PII）一旦进向量库，会被 embedding 编码进向量、被检索召回、被 LLM 读进上下文、被记进日志——它会在整条 RAG 链路上"复制扩散"。所以脱敏的第一原则是**全链路一致性**：只要有一处残留原文，前功尽弃。

工程折中：**入库前脱敏 + 原文单独加密存储**。这样既保证检索/生成侧不接触明文，又在需要溯源/合规调阅时能从加密库取回原文。纯"检索时脱敏"风险高（明文曾落库），纯"入库前脱敏不留原文"则丢失溯源能力。

## 机制与原理

### PII 类型清单（中文场景）

| 类型 | 结构特征（识别要点） | 风险 |
|------|----------------------|------|
| 手机号 | `1[3-9]` 开头，共 11 位 | 高，可直连个人 |
| 身份证号 | 18 位（17 位数字 + 校验位，末位可为 X）；或 15 位旧版 | 极高，唯一标识 |
| 银行卡号 | 16–19 位、有 Luhn 校验特征 | 高 |
| 邮箱 | `本地部分@域名` 结构 | 中 |
| 详细地址 | 省/市/区/路/号 序列，含门牌 | 中高 |
| 车牌 | 省份简称 + 字母 + 5–6 位字母数字 | 中 |
| IP 地址 | IPv4/IPv6 结构 | 中（可定位网络） |
| 人名 | 无固定格式，需 NER | 中 |
| 企业统一社会信用代码 | 18 位，含登记管理部门/行政区划码 | 中（企业身份） |

> 不必写完整正则，关键是掌握结构特征：号码类有固定长度与开头规律，适合正则；人名、地址无固定形态，必须靠 NER。

### 正则 + NER 的组合

- **正则擅长结构化字段**：手机号、身份证、银行卡、邮箱、车牌——格式固定，规则写清就能高精度识别。
- **NER 擅长非结构化字段**：人名、详细地址、机构名——没有固定形态，靠序列标注模型识别。
- **必须组合**：纯正则会漏掉人名/地址（无格式），纯 NER 会漏掉号码（模型对长数字串不稳定、易把号码当普通数字）。两者结果取并集，覆盖才完整。中文 NER 可选 `LAC` / `HanLP` / `bert-base-chinese` 类模型。

### 脱敏策略三选一

| 策略 | 做法 | 对下游检索的影响 |
|------|------|------------------|
| 遮蔽 | 保留格式，如 `138****1234` | **破坏原始字面匹配**——检索"13812341234"查不到，BM25 词项已变 |
| 替换 | 换成统一占位符，如 `[手机号]` | **引入统一伪词项**——所有手机号都变同一个 token，语义上"无差别"，可能污染相似度 |
| 删除 | 直接移除 | 语义断裂，但最干净；缺失上下文可能影响回答 |

这个取舍常被忽略：**遮蔽**让"按原号码检索"失效；**替换**把千差万别的真实值都变成同一个占位符，会在 embedding/BM25 里制造大量"相同 token"，反而扭曲分布。选哪种取决于"检索时是否还需要拿原值做匹配"——通常建议替换成带类型信息的占位符（如 `[手机号]`），兼顾可读与可控，并接受其对字面匹配的代价。

### 全链路一致性（最重要的实践）

脱敏不能只在清洗阶段做一次。需要同时处理的位置：

- **索引**：入库的 chunk 文本必须已脱敏（最基本）。
- **向量库**：embedding 不应编码明文——源头文本脱敏后自然满足。
- **缓存**：检索结果缓存、对话上下文缓存里若存了含 PII 的回答，照样泄露。
- **日志**：清洗日志、检索日志、LLM 调用日志常把 query/上下文原文写下，是重灾区。
- **监控指标**：把"含 PII 的请求"当特征统计，也可能留存原文。

做法：建立"明文边界"清单，凡越界处一律不落明文，或落的是已脱敏/加密态。配合 [[rag/11_安全审核与日志/安全与合规|安全与合规]] 与 [[rag/11_安全审核与日志/审核与审计日志|审核与审计日志]] 做统一管控。

### 脱敏的时机选择

| 时机 | 做法 | 取舍 |
|------|------|------|
| 入库前脱敏 | 清洗阶段就脱敏，向量库/检索/生成都不见明文 | 安全，但丢失原文信息 |
| 检索时脱敏 | 原文入库，召回后在返回前脱敏 | 保留信息，但明文曾落库，风险高 |
| 推荐折中 | **入库前脱敏 + 原文单独加密存储** | 检索侧安全；需溯源时从加密库解密取回 |

建议走折中：日常检索/生成只见脱敏文本；需要合规调阅或人工复核时，凭授权从加密原文库取回。加密映射表/密钥必须独立保管，**绝不能和脱敏后的知识库放一起**（见陷阱）。

### 审计要求

脱敏操作要留痕：谁、何时、对哪些字段、用哪种策略。这不仅是合规要求，也是事后能回答"这条 PII 去哪了/为什么召回里没有"的依据。审计日志本身也要脱敏（不能把被审计的明文又写进日志）。与 [[rag/11_安全审核与日志/审核与审计日志|审核与审计日志]] 共用一套留痕规范。

## 实操

```python
import re

PII_PATTERNS = {
    '手机号': r'(?<![\d])1[3-9]\d{9}(?![\d])',
    '身份证': r'(?<![\d])\d{17}[\dXx](?![\d])',
    '邮箱':   r'[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}',
    '银行卡': r'(?<![\d])\d{16,19}(?![\d])',
}

def mask_text(text: str) -> str:
    # 1) 结构化字段:正则遮蔽(保留前3后4)
    text = re.sub(PII_PATTERNS['手机号'],
                  lambda m: m.group()[:3] + '****' + m.group()[-4:], text)
    text = re.sub(PII_PATTERNS['邮箱'], '[邮箱]', text)
    # 2) 非结构化字段:NER 结果用 [类型] 替换(示意)
    # text = apply_ner_mask(text)   # LAC/HanLP 等
    return text

# 入库前脱敏;原文另存加密库(略)
clean = mask_text(chunk_text)
```

## 陷阱与边界

- **只脱敏一次**：只在清洗阶段脱敏，但索引/缓存/日志里还有原文 → 等于没脱敏。必须全链路一致性（见上文）。
- **脱敏后忘记录入索引**：脱敏改了文本，但向量/BM25 索引若还指向旧文本或未重建，检索结果会不一致。任何脱敏规则变更都要**重建索引**。
- **用可逆映射但映射表未加密**：为了溯源把"明文↔占位符"的映射表存下来，却没加密、和知识库放一起——攻击者拿到表就能反解全部 PII。映射表必须独立加密存储、独立授权。
- **遮蔽破坏字面匹配不自知**：用 `138****1234` 后，用户拿完整号码检索会失败，却没人意识到。若业务需要按原值检索，应改用"检索时动态匹配"或保留可逆加密而非遮蔽。
- **NER 误报污染正文**：NER 把普通词当人名/地址替换，会破坏正常语义。建议 NER 结果做人工抽样核对，并与正则结果交叉验证后再落库。
