# GraphRAG 与知识图谱

## 概述

向量 RAG 的固有短板是**只见片段、不见全局**：它擅长"查某块事实"，做不好"跨文档的关系推理、全局归纳（全局有哪些主题、整体趋势是什么）"。GraphRAG（微软，2024-2026 代表实现）在向量之上叠加**知识图谱**：索引时用 LLM 抽取实体与关系构建图，查询时沿图做社区级推理，回答全局性问题显著优于朴素 RAG（论文报告综合性与多样性任务上胜率约 70%–80%）。

> 定位澄清：GraphRAG 不是替代向量 RAG，而是补"全局/关系类问题"的另一种索引-检索范式。成本远高于向量 RAG（LLM 抽取贵），上之前先判断问题类型。

## 一、向量 RAG vs GraphRAG 的适用边界

| 问题类型 | 例子 | 向量 RAG | GraphRAG |
|----------|------|----------|----------|
| 事实查询（单点） | "A 公司的年假政策？" | ✅ 快而准 | 杀鸡用牛刀 |
| 关系查询（跨文档多跳） | "哪些供应商同时供货 A 和 B？" | ❌ 依赖恰好命中 | ✅ 图遍历天然胜任 |
| 全局归纳（语料级） | "这份财报季整体最突出的风险是什么？" | ❌ 碎片化 | ✅ 社区摘要+map-reduce |
| 时效性/高频更新 | 新闻问答 | ✅ 增量索引容易 | ⚠️ 图抽取重建成本高 |

## 二、GraphRAG 核心机制（微软方案）

```
索引阶段（离线、贵）：
  Document → LLM 实体/关系抽取 → 知识图谱(节点=实体, 边=关系)
          → Leiden 社区检测(层次化社区)
          → 为每个社区生成 LLM 摘要(community summary)
查询阶段：
  Local Query：定位相关实体 → 沿图取邻居与社区摘要 → 组装上下文生成
  Global Query（全局归纳）：按社区摘要做 map → reduce 多次 LLM 综合
  DRIFT（2025）：结合局部遍历与全局搜索的自适应检索
```

- **社区检测用 Leiden 而非 Louvain**：层次更稳、可复现（论文要点）。
- 开源：`microsoft/graphrag`（MIT 许可），提供完整索引/查询 CLI 与 Python API；另有 **LightRAG、Nano-GraphRAG** 等轻量变体降低抽取成本。
- 与向量 RAG 可融合：图谱实体链接到原文块，形成"图谱召回 + 向量召回"混合路由（复杂问题走图、简单问题走向量）。

## 三、何时值得上 GraphRAG（决策清单）

✅ 该上：语料内部实体/关系密集（研报、法规、产品矩阵、供应链）；高频问"关系/对比/全局归纳"类问题；可接受索引成本。

❌ 不上：纯"单点事实问答"、低更新延迟要求低、语料互不关联（一堆无关文档建图无意义）、预算敏感。

> 成本提示：图抽取是 LLM 密集任务，千万级 token 语料建图成本可能高达数千到数万美元级（按 2025 市场价量级粗估），务必先做小样本试算 ROI。

## 四、最小认知示例（流程而非完整代码）

```python
# 微软 GraphRAG 提供 CLI/API 完成"索引→查询"全流程（此处示意关键配置与查询）
# 1) 索引（离线，一次性）：解析文档 → 实体/关系抽取 → 社区摘要
#    graphrag index --root . --config settings.yaml
# 2) 全局查询（语料级归纳）
#    graphrag query --method global "这份语料里最突出的共同主题是什么？"
# 3) 本地查询（实体为中心的事实/关系问答）
#    graphrag query --method local "XX 公司与哪些实体存在合作关系？"
```

> 深入实现（图谱存储、提示词模板、增量更新）以官方文档为准：https://microsoft.github.io/graphrag/。若要自研轻量版，核心是"抽取质量"与"社区摘要质量"两道 LLM 关卡——建议先用开源实现跑通再考虑定制。

## 五、常见问题

**Q1：知识图谱 vs 向量库，是不是二选一？**
不是。生产上更常见"向量为主 + 图谱兜底复杂问题"或"图增强检索"（用图扩展查询实体、用社区摘要补充上下文）。选型问句是"用户问题里有跨实体关系/全局归纳需求吗"。

**Q2：GraphRAG 抽取的实体不干净怎么办？**
抽取是质量瓶颈。缓解：领域实体词典/受控 schema 约束抽取；抽取结果人工抽检；实体对齐（同一实体多种写法）用 embedding 相似度+LLM 判重。质量不行时"图是脏的"，查询再聪明也没用。

**Q3：文档频繁更新，图怎么维护？**
增量更新是难点（新增文档可能与旧实体连边、也可能改社区结构）。实践：低频全量重建 + 高频增量追加；评估社区稳定性；必要时"新文档先进向量 RAG，图定期重建"。

**Q4：GraphRAG 能用在小语料吗？**
小语料（<几百篇）图收益有限，常见结论是向量 RAG 已够；语料大、关系密才划算。先量化：拿 50 个全局性问题对比向量 vs GraphRAG 的答案质量再决定。

## 六、最佳实践

1. **问题分类先行**：把高频问题分成"事实/关系/全局"三类，对应向量 RAG / 图查询 / 社区摘要——别用一套引擎答所有题。
2. **图质量与成本双看板**：监控抽取的实体/边数量、社区数、单文档抽取成本；异常膨胀常是抽取失控信号。
3. **评估用全局性问题集**：普通 RAGAS 的单跳指标测不出图的价值；建"跨文档综合"题型（[[rag/12_评估与监控/评估体系与RAGAS|评估体系]] 自定义指标）。
4. 图与向量双引擎时，路由与结果合并要可观测（记录走了哪条路），复盘才有依据。
