# HTML 与网页解析

> 网页和 Word/PDF 最大的不同：它**不是为阅读设计的文档，而是为浏览器渲染设计的程序产物**。正文之外塞满了导航栏、侧边栏、页脚、广告、Cookie 提示——解析的本质是「从噪声里把正文捞出来」，捞不干净比捞不全更伤检索。

## 核心结论

- **网页正文占比常低于 30%**（具体比例随站点而异，待核实），噪声（导航、广告、相关阅读）才是主体，解析重点是去噪不是抽取。
- **两种正文抽取思路**：启发式密度算法（readability 类，快、通用、偶有误判）vs 专用解析器/渲染（准、但需要浏览器、重）。
- **动态页面必须 headless 浏览器**（Playwright 等）渲染后再抽，代价是慢、重、要维护浏览器版本。
- **结构化数据（JSON-LD / Open Graph / meta）是现成的元数据金矿**——作者、发布日期、标题直接拿来，对时效性过滤极有价值。
- **反爬对抗、版权风险、高频更新的内容，不值得自建抓取**——优先用官方 API 或现成导出。

## 机制与原理

### 1. 网页与静态文档的结构差异

| 维度 | 静态文档（PDF/Word） | 网页 |
|------|----------------------|------|
| 主体 | 正文为主 | 正文 + 大量模板噪声 |
| 噪声来源 | 页眉页脚 | 导航栏、侧边栏、页脚、广告、Cookie 弹窗、相关阅读 |
| 结构 | 固定版式 | DOM 树，可嵌套任意深 |
| 内容获取 | 直读 | 可能需 JS 渲染 |

对 RAG 而言，网页解析的成败不在「能不能读出字」，而在「能不能把字和噪声分开」。

### 2. 正文抽取的两种思路

**A. 启发式密度算法（readability 类）**

代表：Mozilla Readability、trafilatura、newspaper3k。原理是统计 DOM 节点的**文本密度 / 链接密度 / 标点密度**，把「密集、少链接、多标点」的区块判为正文。

- 优点：快、无需浏览器、通用性强、对主流新闻/博客效果好。
- 缺点：对非常规版式（论坛、文档站、SPA）偶有误判，会把代码块、评论区当正文或反之。

**B. 专用解析器 / 渲染式**

把页面用真实浏览器渲染，结合视觉布局（如「页面中央大块文字」）判断正文，或先转 PDF/图片再走文档解析管线。

- 优点：准确率最高，能处理复杂版式。
- 缺点：需要 headless 浏览器，资源重、速度慢、要维护浏览器版本。

| 思路 | 速度 | 准确率 | 依赖 | 适用 |
|------|------|--------|------|------|
| 启发式密度 | 快 | 良好（常规页） | 轻 | 批量、常规文章 |
| 渲染式 | 慢 | 高（复杂页） | 重（浏览器） | 版式怪、SPA、需要像素级判断 |

### 3. 动态渲染：headless 浏览器

当正文由 JavaScript 异步加载（SPA、无限滚动、登录后才显示），纯 HTTP 抓取拿到的只是空壳 HTML。此时需 Playwright / Puppeteer 启动真实浏览器，等 JS 渲染完成再抽取。

代价：

- **慢**：每页多了浏览器启动 + 渲染时间（秒级）。
- **重**：要装浏览器二进制，定期升级，容器里更麻烦。
- **需维护**：浏览器版本、反爬策略会变，脚本要跟着改。

> 个人知识库规模（数千 chunk 级）下，除非确实在抓动态站，否则优先启发式方案，避免把简单任务搞成爬虫工程。

### 4. 结构化数据：现成的元数据来源

网页 `<head>` 里常带机器可读的结构化数据，比从正文猜元数据可靠得多：

| 来源 | 提供什么 | RAG 用途 |
|------|----------|----------|
| **JSON-LD** | author、datePublished、headline、publisher | 作者/发布日期过滤、时效性 |
| **Open Graph** | og:title、og:description、og:image | 标题/摘要/封面 |
| **meta 标签** | `<meta name="author">`、`<meta name="description">` | 补充元数据 |

```python
from bs4 import BeautifulSoup
import json
html = open("page.html", encoding="utf-8").read()
soup = BeautifulSoup(html, "html.parser")
# 1) 抓 JSON-LD
ld = soup.find("script", type="application/ld+json")
meta = json.loads(ld.string) if ld else {}
# 2) 抓 Open Graph / 普通 meta
og = {t.get("property"): t.get("content")
      for t in soup.find_all("meta") if t.get("property","").startswith("og:")}
# 3) 抓常规 meta
author = soup.find("meta", attrs={"name": "author"})
```

这些字段对「只要 2024 年后的文档」「排除某作者」这类**元数据过滤**非常有用，见 [[rag/07_元数据过滤/元数据过滤|元数据过滤]]。

### 5. 噪声剔除的具体做法

两种常用信号：

- **按 DOM 结构剔除**：直接移除 `<nav>`、`<header>`、`<footer>`、`<aside>`、class/id 含 `ad`/`sidebar`/`cookie`/`related` 的节点。简单有效，但依赖站点一致性。
- **按文本重复率剔除**：模板文字（导航项、版权声明）在**同一站点多页间高度重复**。先抓 N 页，统计跨页高频重复的片段，建「噪声词表」过滤。这对「同一文档站成百上千页」的批量接入特别有效。

> 去噪后建议再跑一遍「正文纯度」检查：随机抽 5 页人工看是否还混着广告/相关阅读链接。

### 6. 何时不值得自建抓取

以下情况，自建爬虫的维护成本会超过收益：

- **反爬对抗强**：需要代理池、验证码、登录态维护——工作量指数上升，且随时被封。
- **版权风险高**：抓取并入库受版权保护内容，个人知识库也需谨慎，优先确认授权或走官方导出。
- **内容更新频繁**：今天抓的明天就过期，需持续增量维护，复杂度远超一次性摄入。

替代方案：官方 API / RSS / Obsidian Web Clipper / 让来源方提供导出文件，再走本环节的文档解析管线。

## 实操

一个轻量网页接入流程（启发式优先）：

```python
import requests
from trafilatura import extract  # 启发式正文抽取
url = "https://example.com/post"
html = requests.get(url, timeout=10).text
article = extract(html, include_comments=False)
if not article:                  # 启发式失败，再考虑渲染式
    article = render_with_playwright(url)
# 元数据从 JSON-LD / OG 补，而非从正文猜
```

## 陷阱与边界

1. **把导航/广告当正文**：未去噪直接入索引，污染检索、拉低相关性。→ DOM 结构 + 跨页重复率双管齐下。
2. **动态页抓到空壳**：SPA 只拿到 `<div id="root">` 空节点。→ 检测正文为空时切换到 headless 渲染。
3. **误伤正文**：过度按 class 名删节点，把正文容器（恰好叫 `content`）也删了。→ 优先用成熟库的正文算法，别手写粗暴规则。
4. **元数据缺失导致无法时效过滤**：只存正文不存发布日期，后期无法「只要新文档」。→ 从 JSON-LD/OG 抓取日期。
5. **版权与合规**：批量抓取受保护内容带来法律风险。→ 确认授权或走官方导出。
