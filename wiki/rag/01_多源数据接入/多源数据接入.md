# 多源数据接入（Data Ingestion）

> RAG 流程第 1 步。本页是**接入环节的总览与入口**——回答「数据怎么进来、进来时该带上什么、后续能不能增量维护」。具体的格式解析细节见 [[rag/01_多源数据接入/文档解析_PDF_Word_图片与表格|解析总览]]。

## 核心结论：这是唯一一处「源头污染」

接入环节做错的事，下游任何环节都救不回来。原因是链路是单向的：

```
解析质量 ≈ 切分质量 ≈ 检索质量 ≈ 生成质量
```

切分只能在解析结果上工作，检索只能在切分结果上工作。**下游所有的调参、重排、提示词优化都只是在挽救，无法上游修复。** 一个被拍平的表格，无论用什么 embedding、怎么调 top-k，都不可能还原出丢失的行列关系。

因此接入阶段的投入回报率高于后续任何环节——这也解释了为什么本环节被拆成 8 个专题页。

## 一、数据源分类与接入方式

| 数据源 | 典型接入方式 | 关键注意点 |
|---|---|---|
| 本地文件（PDF/Word/PPT） | 目录扫描 + 专用解析器 | 格式解析是主要工作量，见 [[rag/01_多源数据接入/文档解析_PDF_Word_图片与表格\|解析总览]] |
| 网页 / 在线文档 | 抓取 + 正文抽取 | 导航/广告/页脚噪声，见 [[rag/01_多源数据接入/HTML与网页解析]] |
| 数据库 | 查询适配器 + 增量键 | 按更新时间游标分批，避免全表扫描 |
| API / 云存储 | 平台 SDK | 鉴权、限流、增量游标 |
| 音视频 | 转写后入链 | 转写质量直接决定下游上限 |
| 结构化导出（CSV/JSON） | 拍平为统一 schema | 字段命名统一、空值显式处理 |

> LangChain Document Loaders — https://python.langchain.com/docs/concepts/document_loaders/
> LlamaIndex Readers — https://docs.llamaindex.ai/en/stable/understanding/loading/loading/

**一个容易混淆的层次区分**：LangChain 的 `DocumentLoader` 是**抽象接口**，真正的解析工作在底层引擎（docling / unstructured / LlamaParse）。选型决策发生在引擎那一层，不在 loader 那一层——`DoclingLoader` 只是包装。详见解析总览页。

## 二、接入阶段必须完成的四件事

### 1. 取到 —— 保留结构，而不是只取到文字

「取到」的合格标准不是「拿到了文本」，而是**拿到了带结构的文本**：标题层级、表格行列、图片位置、列表边界。

这个区别决定了下游能否做结构感知切分。如果接入阶段只吐出一串纯文本，切分阶段就只能按长度硬切——**策略空间在接入阶段就已经被定死了**。

### 2. 认清 —— 打元数据，且必须在此刻打

元数据要在元素产生的那一刻写上，而不是切分之后回头补。原因是**切分后块已脱离原文**：你只知道块的内容，无法再回答「它来自第几页、属于哪个章节」。

字段清单与 DOCX 无页码的应对方案见 [[rag/01_多源数据接入/元数据与溯源锚点]]。

### 3. 成批与增量 —— 支持全量重建，也支持单篇更新

两个能力都要有：
- **全量重建**：改了切分策略或换了 embedding 模型时必须能重跑（换 embedding 会让旧索引全部作废）
- **增量更新**：日常只加几篇文档时，不该触发全量重算

支撑这两者的是内容指纹与变更检测设计，见 [[rag/01_多源数据接入/增量接入与去重]]。

### 4. 可重放 —— 同样输入必须产出同样结果

接入管线要幂等。否则出问题时无法复现，也就无法定位。配套要求是把清洗规则、解析器版本、提示词版本都记入索引元数据。

## 四、六个常见坑

1. **只取文本不取结构** —— 下游无法做结构感知切分，且无法为 chunk 补标题链
2. **元数据事后补** —— 切分后位置信息已永久丢失
3. **页眉页脚未剔除** —— 症状隐蔽：每页重复的词会让 IDF 权重跌到接近 0，同时抬高所有 chunk 的分数基线，真实相关的块反而凸显不出来
4. **表格被拍平** —— 行列关系丢失后，LLM 会基于错位的数字自信地答错，这是最难排查的一类故障
5. **用文件字节 hash 做去重** —— 同一文档重新保存一次字节就变了，会被误判为新文档
6. **换 embedding 后忘记重建索引** —— 向量空间改变，旧索引全部作废；这是高频事故

## 五、最佳实践

1. **接入即打元数据**，把来源、权限、时间下沉到元素层，为后续过滤与溯源买单
2. **先试文本层，再考虑重模型** —— 数字文档的文本层比任何 OCR 或视觉识别都更准确，且成本为零
3. **抽样验证不能省**：用 20–50 页真实文档肉眼检查有无丢字、表格是否错位、图片是否提取、标题层级是否正确。解析问题在上线后极难定位，几十分钟的抽样能省掉几天的无效排查
4. **低信任来源单独标记**，供 [[rag/11_安全审核与日志/安全与合规|安全环节]] 区分处理
5. **接入管线版本化**：解析器版本、清洗规则版本、提示词版本都写进索引元数据，便于定位「哪次改动导致效果下降」
