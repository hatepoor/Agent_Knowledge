# 图片提取与描述化

> 表格能转成 Markdown 进正文流，图片是二进制、Markdown 装不下，所以**图片必须回到元素层取，且若不生成文字描述就完全不可检索**——给视觉模型的不该只是图，而是「图 + 图注 + 章节路径 + 前后段落」四件套。

## 核心结论

- **图片和表格不能照搬同一套处理**：表格能转 Markdown 进正文流、原表即使不摘要也能被 BM25 部分匹配；图片若不生成描述，则**完全不可检索**——描述化是必需品，不是增强项。
- **图像本体在元素层直接可取**（`pic.get_image(doc)` → PIL），但**图注和上下文都不在元素层**：图注 DOCX 下为空、得从相邻段落提取，上下文（标题链、前后段落）得遍历时自己维护。
- **一句话总结：图在元素层，图注和上下文要自己凑。**
- **定位靠「保序 + 锚定 + 探测」**：一次遍历把图片本身也塞进有序序列，找到图片索引后向前后各探一格拿图注与上文。
- **描述质量取决于你喂了多少上下文**：只丢图得到「这是一张柱状图」的废话；喂足四件套才能得到带数值、自包含、能被中文 query 命中的描述。
- **视觉模型失败时别丢块**：降级保留「图注 + 标题链 + 原图路径」，比描述质量差严重得多的是让「原文这里有一张图」彻底消失。

## 机制与原理

### 1. 为什么图片与表格的处理方式不能照搬

两者在 RAG 里有结构性差异：

| 维度 | 表格 | 图片 |
|---|---|---|
| 能否转 Markdown | 能（纯文本行列） | 不能（二进制） |
| 进哪种数据流 | 正文流（导出时就在 Markdown 里） | 元素层（导出后只剩占位符） |
| 不处理时的可检索性 | 原表单元格文字**仍能被 BM25 部分匹配** | **若不生成描述则完全不可检索** |

结论：

- **表格可以从 Markdown 里抽**，图片必须回到元素层取——这是两条不同的取数路径，不要混为一谈。
- 更深一层的差异在于「不描述也还活着」 vs 「不描述就死了」：**图片描述是必需品，不是增强项**。你的语料是中文 + 英文混排的 Word 文档，图一旦没有文字描述，稠密 embedding 和 jieba/BM25 都无从索引它（未来换 BGE-M3 也一样）。

### 2. 图片处理链路的三样输入，来源各不相同

这是整件事的核心知识点。图片要变成可检索的 chunk，需要四类信息，而它们的来源完全不同：

| 输入 | 来自哪里 |
|---|---|
| **图像本体** | 元素层直接可取：`pic.get_image(doc)` → PIL 对象 |
| **图注（caption）** | 字段存在，但 DOCX 下为空，**需自己从相邻段落提取** |
| **上下文：标题链** | 完全不在元素层，遍历时维护标题栈推导 |
| **上下文：前后段落** | 完全不在元素层，从文档流取相邻元素 |

> **一句话总结：图在元素层，图注和上下文要自己凑。** 任何「我直接遍历图片元素就有了一切」的假设都是错的——图注和上下文是两套独立的采集逻辑。

### 3. 定位机制：保序 + 锚定 + 探测

要让「图」和「它的图注 / 上下文」精确配对，靠的不是正则全文扫，而是基于一次有序遍历的**位置配对**。

**保序** —— 一次遍历把所有元素按文档顺序存成有序序列。`docling` 的 `iterate_items()` 本身就是按阅读顺序产出元素。**关键：序列里必须包含图片元素本身**，不能只存文本——否则图片与正文的位置关系就断了，后面无法锚定。

**锚定** —— 找到图片在序列中的索引。

**探测** —— 以图片为锚点，向前后各探一格。

实测样例（一个 8 元素的序列）：

```
[0] 标题
[1] 正文
[2] 标题
[3] 引导句：「我们压测了三种方案的吞吐量，结果如图 1 所示。」
[4] 图片            ← 锚点
[5] 图注：「图 1 三种方案的吞吐量对比」
[6] 标题
[7] 正文
```

**图注识别规则（正反两面都要写）**：

- **正向**（命中才是题注）：以「图 3」「图 3-1」「图 3：」「Figure 3」「Fig. 3」开头；且**短**（一般一行，几十字内）。
- **反向**（排除，这些不是题注）：
  - 篇幅长 / 多句号 → 不是；
  - 以「如」「见」「参见」「详见」开头 → 这是正文里的**引用**不是题注；
  - 超过 **120 字**直接排除。
- **要双向探测**：先探**下一格**（中文文档题注多在图下），再探**上一格**（部分排版题注在图上方）。

实测效果（对应上面 8 元素样例）：

- 下一格 `图 1 三种方案的吞吐量对比` 以「图 1」开头、短 → **被正确识别为题注**。
- 上一格 `……结果如图 1 所示。` 虽含「图 1」但不以「图 N」开头、且是引用句式 → **被正确排除**。

**这说明反向规则是有效的**——如果只做「含图 N 就当题注」，上面那句引导句就会被误判为题注，污染描述。

**上文取三层（由近到远）**：

1. **标题链**——遍历时累积的「当前章节路径」；
2. **引导句**——在图前段落里搜「图 N」对齐编号的那句话；
3. **紧邻前一段**——图片正上方的相邻段落。

建议只取 1–2 段，取多了会污染描述。**引导句是三层里最有价值的**：它是作者专门为这张图写的那句话，同时给出「这张图在讲什么」以及上下文语境，是描述生成最该纳入的上下文。

### 4. 图片过滤：哪些值得描述

docling 已经自动过滤了一类（面积极小、全透明、纯白 → `ContentLayer.INVISIBLE`，见 [[rag/01_多源数据接入/Word解析|Word 解析]]）。但它**过滤不掉的**是：大尺寸装饰图（logo、整页背景、美化配图）。

判断规则（按优先级）：

1. **被正文引用**（出现「图 N」「如下图」等）→ 最高优先，必描述；
2. **带图注** → 次优先；
3. **面积与宽高比**（大图、接近内容区尺寸的图更可能是信息图）。

**最省事的组合策略：只处理「带图注」或「被正文引用」的图。** 既避开装饰图噪声，又不会漏掉真正承载信息的图。

## 实操

下面这段（非完整脚本）演示了**保序序列 + 双向探测 + chunk 组装**的核心逻辑——把遍历结果存成含图片元素的序列，再以图片为锚点取图注与上文：

```python
seq = []                      # 保序序列，必须包含图片元素本身
title_stack = []
for item, _ in doc.iterate_items():
    if item.label == DocItemLabel.SECTION_HEADER:
        title_stack.append(item.text)
    seq.append(item)

for i, item in enumerate(seq):
    if item.label != DocItemLabel.PICTURE:
        continue
    # 双向探测：先下一格（题注多在图下），再上一格（部分在图上方）
    cap = ""
    if i + 1 < len(seq) and _is_caption(seq[i + 1].text):   # 正向规则
        cap = seq[i + 1].text
    elif i - 1 >= 0 and _is_caption(seq[i - 1].text):
        cap = seq[i - 1].text
    # 上文三层：标题链 + 引导句（搜"图 N"）+ 紧邻前一段
    guide = _find_guide(seq, i)            # 在图前段落搜"图 N"对齐
    ctx = title_stack + ([guide] if guide else [])
    chunk = {
        "kind": "image",
        "self_ref": item.self_ref,
        "title_path": "/".join(title_stack),
        "caption": cap,
        "image": item.get_image(doc),      # 元素层 PIL 对象
        "context": ctx,
    }
    # 后续：把 chunk 交给视觉模型生成 description（见下文）
```

> `_is_caption` 实现前面的正向/反向规则（「图 N」开头且 ≤120 字、非「如/见/参见」引用句式）；`_find_guide` 在图片之前的段落里找含「图 N」且编号对齐的那句引导句。

## 描述生成：关键是给足上下文

### 输入四件套

喂给视觉模型的不该只有图，而是：

1. **图**（PIL 对象，来自元素层）；
2. **图注**（自己提取的 `caption`）；
3. **章节路径**（`title_path`，标题链）；
4. **前后段落**（尤其引导句）。

只丢图会得到「这是一张柱状图」这种废话；喂足四件套才能让模型理解这张图在文档里到底在讲什么。

### 对输出的三条硬要求

- **数值必须完整**：性能对比图里的数字常是全文唯一来源，漏了就永久检索不到（智谱 embedding-3 / 未来的 BGE-M3 都索引不到没写进文本的数值）。
- **描述必须自包含**：不能出现「如图」「该流程」「上图」这类指代，因为它会被单独检索出来，脱离原语境后这些词毫无意义。
- **架构图要说明节点与连线关系**：不能只说「一个架构图」，要讲清节点是什么、连线表示什么关系。

### 语言策略

描述用**文档主语言**（中文场景用中文，利于中文 query 命中 jieba/BM25）；但**英文术语与标识符保留原文**（如 `PictureItem`、`embedding-3`、`dense/sparse` 不翻译）。

### FIGURE_PROMPT 模板（结构化）

```
请描述这张图，输出结构化结果：
1. 图表类型（柱状图/折线图/流程图/架构图…）
2. 标题与坐标轴含义（X 轴、Y 轴分别表示什么）
3. 关键数值（完整列出，不要省略任何一个数字与单位）
4. 结论与趋势（如图为对比，说明谁高谁低、差距多少）
5. 若为架构图：说明各节点是什么、连线表示什么关系
6. 约束：不要臆测图中没有的信息；不要使用「如图」「该图」等指代
```

## 存到 chunk 里有什么（字段清单）

| 类别 | 字段 | 说明 |
|---|---|---|
| 标识 | `id` / `doc_id` / `kind="image"` | 与文本块、表格块共用同一套 ID 体系 |
| 定位 | `title_path` / `self_ref` | 注意 DOCX 无 page/bbox（见 [[rag/01_多源数据接入/Word解析\|Word 解析]]） |
| 内容 | `caption` / `description` / `image_path` | 三件套 |
| 检索 | `text_for_index` / `text_for_llm` | 见下 |
| 工程 | `image_hash` / `desc_model` / `prompt_version` | 去重、缓存、换模型后哪些块要重跑 |

**两个文本字段的关系**：

- `text_for_index` = 标题链 + 图注 + 描述（+ 引导句）。索引侧多带上下文是为了提升召回——用户问「三种方案吞吐量对比」时能命中标题链与图注里的同义表述。
- `text_for_llm` = 图注 + 描述。

**与表格的关键不同**：表格的 `text_for_llm` 必须是**原表**（摘要不含精确数值，丢了数就错了）；而图片的**描述文本本身就精确**，所以 `text_for_index` 与 `text_for_llm` 两边基本重合——这正是图片「不描述就死、描述了就活」的体现。

## 生成阶段的两种回传策略

- **默认：只回传描述文本**。最省钱，不要求生成模型（如最终回答用的 LLM）支持视觉输入；图片的语义已经压进 `text_for_llm` / `text_for_index` 里参与检索与生成。
- **按需：把原图作为多模态输入一并给出**。当问题明显指向图内细节（具体数值、趋势、节点关系）时，检索到该图片块后，把 `image_path` 对应的原图连同问题一起喂给支持视觉的模型，拿到更精确的回答。

## 工程要点

- **图片按内容 hash 去重**：同一张架构图常跨文档重复出现，不做去重就是重复付费（重复跑视觉模型）。用 `image_hash` 在入库前去重。
- **描述结果按「图片 hash + 提示词版本」缓存**：改了 `FIGURE_PROMPT`（`prompt_version` 变了）要能重跑对应块；没改就命中缓存，省成本。
- **视觉模型失败时不要丢弃这个块**：降级保留「图注 + 标题链 + 原图路径」——直接丢块会让「原文这里有一张图」彻底消失，比描述质量差严重得多。至少保证检索时能知道「此处有图」并回退到原图多模态路径。

## 陷阱与边界

1. **图号会在不同范围重置**：有的文档全文连续编号（图 1~50），有的**每章重置**（每章都从图 1 开始）。用「图 N」匹配引导句时必须**结合章节路径**一起判定，否则会串到别的章节的同号图上——这个错误很隐蔽，描述会错配到完全不相干的图。
2. **描述里出现指代词**：「如图」「上述流程」「该图」这类词一旦写进 `description`，因为它会被单独检索出来、脱离原语境，这些指代就失效了。提示词里要硬性禁止。
3. **以为图注会自动带**：DOCX 下 `PictureItem.captions` 恒空，`caption_text(doc)` 返空串；不自己提取就会丢图注上下文。
4. **以为从 Markdown 能抽到图**：默认 `image_mode=PLACEHOLDER`，Markdown 里只有占位符；图片必须回元素层取。
5. **只丢图给视觉模型**：得到废话描述，检索价值极低；必须凑齐四件套。
6. **EMF/WMF 图静默变 `None`**：Office 图表粘贴进来是 EMF/WMF，无 LibreOffice 时 docling 兜底失败、得到 `None`（详见 [[rag/01_多源数据接入/Word解析\|Word 解析]]），描述阶段会拿不到图。
