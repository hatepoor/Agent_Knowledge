# 表格提取与处理

> 一句话定位：表格是 RAG 管线里最容易被"切坏、索坏、答错"的内容类型——它必须被当作独立对象在切分前摘出，并用"摘要 + 原表"双轨同时进索引。

## 核心结论

表格是 RAG 最容易失手的地方，根本原因是**信息组织方式与检索方式的冲突**：用户用自然语言提问，而表格里全是结构化数据。两者之间的语义鸿沟，比"正文段落 vs 自然语言提问"之间的鸿沟大得多。

举一个具体例子。假设有一张表：

| 模型 | 上下文窗口 | 参数量 | 厂商 |
|------|-----------|--------|------|
| Model-A | 8192 | 7B | 甲 |
| Model-B | 32768 | 13B | 乙 |
| Model-C | 128000 | 70B | 丙 |

用户问："哪个模型支持 8192 上下文？"

- **BM25 / jieba 稀疏路**几乎匹配不到。用户问"支持""上下文"，表里却是"模型""上下文窗口""8192"——词项（term）完全对不上，"支持"在表里根本没出现。稀疏检索依赖字面词项重叠，这种提问天然吃亏。
- **稠密 embedding 路**（本库用智谱 embedding-3）对表格结构建模也很弱。被 Markdown 语法包裹的文本，模型很难稳定地把"8192 属于 Model-A 的上下文窗口这一列"编码进向量，召回的往往只是整张表附近的内容，而非精确行。

结论先行：**表格不能当普通文本处理**。它必须被当作一种与段落、图片并列的独立内容类型（content_type = table），在切分之前就从正文流里摘出来单独处置。后续的"摘要 + 原表双轨索引"都是建立在这个前提之上的。

相关环节请参阅 [[rag/01_多源数据接入/图片提取与描述化|图片提取与描述化]]（同样是独立内容类型、同样需要生成文本进索引）以及 [[rag/01_多源数据接入/元数据与溯源锚点|元数据与溯源锚点]]（表格块也需要自己的定位元数据）。

## 机制与原理

### 为什么表格必须整块不切分

递归字符切分器按段落、句子、词的边界把长文切成固定大小的块。这套逻辑对自然语言有效，但对表格是**毁灭性**的：它会沿着行或列把表格从中间切断。

一旦被切断，行列对应关系就废了。LLM 拿到的可能是"表格上半 3 行 + 下半 2 列"的残缺上下文，却会**自信地**给出错误答案，不会提示"表格不完整"。

所以正确做法是：在切分之前就把表格从正文流里**摘出来**，作为不可分割的整体单元。表格"不可切分"的优先级应高于段落"尽量填满 token 窗口"。

### 两种摘出实现方式

| 方式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| ① 正则匹配 Markdown 表格语法 | 用正则识别 `\|.*\|` 行与分隔行 `\|---+\|` | 实现简单、零依赖 | 脆弱：嵌套表、变体语法、单元格内换行容易漏判或误判 |
| ② 遍历元素树按类型判断 | 解析器产出结构化文档树（如 `DoclingDocument`），按元素类型 `table` 直接提取 | 准确、稳健，推荐 | 依赖解析器产出结构化对象，需要先接好解析器 |

**强烈推荐方式②**。原因很简单：方式与文档的语义结构对齐，而不是与某种文本的表面格式对齐。当你的素材是 Word 文档时，docling 这类解析器产出的 `DoclingDocument` 里，表格就是一个带 `TableItem` 语义的元素，直接取即可，不必去猜"这一段文本长得像不像表格"。

### 表头表名要前置

Word / PDF 里的表题（caption）通常在表格**上方**，例如"表 3：主流模型对比"。但很多解析器默认只抽取单元格网格，把表题丢弃或放到不相关位置。结果是一个"孤立的表格块"，没有任何上下文锚点——检索时它既匹配不到"模型对比"这类提问，也无法告诉读者它讲的是什么。

正确做法是在解析阶段把表题与表格**显式关联**，拼成：

```
表 3：主流模型对比

| 模型 | 上下文窗口 | 参数量 | 厂商 |
|------|-----------|--------|------|
| Model-A | 8192 | 7B | 甲 |
...
```

这样表名就成了表格块的语义锚点，能显著提升稠密路对该块的召回。

### 核心手法：摘要 + 原表双轨

这是本页最关键的设计。一张表要同时承载两种匹配职责，单一表示做不到：

- **自然语言摘要**负责匹配"用户用自然语言问表格在讲什么"，稠密路能很好召回它。
- **原表（原始 Markdown）**负责匹配"具体数值与列名"，BM25 / jieba 能在 `8192`、`上下文窗口` 上精确命中。

只保留摘要会漏掉精确数值；只保留原表会漏掉自然语言提问的召回。**两者都要进索引**。

摘要的写法有硬性要求：**必须自包含，不得使用"该表""如表所示""见上表"这类指代**。因为摘要块进入索引后是独立被召回的，读者（和 LLM）看不到"那张表"。好的摘要应直接说出主题、各列含义和关键单元格的具体数值，例如：

> 表 3 对比三款模型规格：Model-A（甲厂）上下文窗口 8192、参数量 7B；Model-B（乙厂）上下文窗口 32768、参数量 13B；Model-C（丙厂）上下文窗口 128000、参数量 70B。

注意最后一句里没有任何指代词，读者即使没看过原表也能理解。

### 统一的 chunk 双文本字段设计

本库对图片、表格、正文采用一致的 chunk 设计：每个 chunk 携带两个文本字段，分别服务检索与生成。

| 字段 | 表格场景的取值 | 用途 |
|------|---------------|------|
| `text_for_index` | 表名/表号 + 摘要 + 原表 | 同时喂给稠密 embedding 与稀疏 BM25，承担召回职责 |
| `text_for_llm` | 原始 Markdown 表（数据精确、行列完整） | 作为检索命中后回填给 LLM 的上下文，保证数值精确 |

**这里与图片的关键差异必须点明**：图片没有"原始文本"，其 `text_for_llm` 是 VLM 生成的描述；但表格的 `text_for_llm` **必须是原表本身**。因为摘要不含精确数值，把摘要喂给 LLM 去回答"8192 是哪个模型"会丢精度。表格的"生成文本"走的是原表，摘要只服务于索引侧的召回。

代码侧一个简化的摘出与打包片段（docling 路径，约 20 行）：

```python
from docling.document import DoclingDocument

def extract_tables(doc: DoclingDocument):
    chunks = []
    for el in doc.iterate_items():
        if el.self_ref.startswith("#/tables/"):
            caption = el.caption_text if el.caption_text else el.name
            md = el.export_to_markdown()          # 原始 Markdown 表
            summary = llm_summarize(caption, md)   # 自包含自然语言摘要
            text_for_index = f"{caption}\n\n{summary}\n\n{md}"
            chunks.append({
                "content_type": "table",
                "text_for_index": text_for_index,
                "text_for_llm": md,               # 生成侧用原表，保精度
                "meta": {"self_ref": el.self_ref},
            })
    return chunks
```

### 各解析器的表格能力对比

不同解析器对表格的处理能力差异极大，选型时这是硬指标：

| 解析器 | 表格机制 | 准确率 / 表现 | 备注 |
|--------|----------|--------------|------|
| docling | TableFormer 模型重建行列与多级表头 | 第三方测试表格准确率约 97.9%（待核实） | 能处理合并单元格、多级表头，推荐 |
| PyMuPDF4LLM | 基于 PyMuPDF 的表格提取 | 约 60–70%（待核实） | 简单表格可用，复杂表格易错 |
| LlamaParse | 云端 LLM 驱动解析 | 约 75–90%（待核实） | 需联网与 API，按页计费 |
| 普通文本抽取器 | 无表格结构理解 | 把表格拍平成"单元格汤" | 仅适合纯文本，表格场景不可用 |

> 注：上表准确率数字来自第三方评测，本库未独立复现，标注（待核实）。实际选型应结合你自己的样本做少量人工校验。

docling 的 TableFormer 之所以强，是因为它把表格还原成带行列坐标和表头层级的语义结构，而不是简单按视觉位置排布。多级表头（一个表头单元格跨多列、跨多行）也能重建。

### 合并单元格与跨页表格

- **合并单元格**：docling 能解析合并单元格的语义，但导出为 Markdown 时会**拉伸成规则网格**（把合并区域重复填充），这在某些场景会和原意有细微偏差。建议对新接入的文档**人工校验少量样本**，确认关键表没有语义错位。
- **跨页 / 多层表头复杂表**：与其执着于 Markdown 还原，不如**出图后用视觉模型（VLM）直接看**。对一张结构混乱的复杂表，VLM 读取图片后给出的理解和答案，往往比 Markdown 还原更准、更快。这正好与 [[rag/01_多源数据接入/图片提取与描述化|图片提取与描述化]] 的视觉路径互补。

### Markdown 表格符号会污染 BM25

`|`、`---`、`:`、以及单元格内的 `-` 分隔，都会成为 BM25 / jieba 分词后的**噪声词项**，稀释有信息量词项的 IDF 权重。

因此建稀疏索引前应**剔除这些符号**再分词。注意：剔除只发生在索引侧 `text_for_index`——`text_for_llm` 仍保留完整 Markdown，保证 LLM 看到精确表格。

## 实操

1. **接入阶段**：用 docling 解析 Word / PDF，拿到 `DoclingDocument`，遍历元素树，按 `self_ref` 前缀（如 `#/tables/`）筛选表格元素。不要用正则兜底作为主要手段。
2. **关联表题**：解析时把 `caption_text` 或 `name` 取出来，拼到表格正文之前，形成"表名/表号 + 表"的结构。
3. **生成摘要**：调用 LLM 把表格转成自包含摘要，prompt 中硬性要求"不得出现'该表''如上'等指代，必须写出关键数值"。
4. **打包 chunk**：`text_for_index = 表名 + 摘要 + 原表`，`text_for_llm = 原表`。两个字段进同一条记录。
5. **清洗符号**：`text_for_index` 在建索引前去掉 `|`、`---`、`:` 等，再送 jieba / BM25。
6. **校验**：对合并单元格表、跨页表抽样人工核对，复杂表可转图走 VLM。

一个去符号再建稀疏索引的小片段（约 12 行）：

```python
import re

def clean_for_sparse(text: str) -> str:
    # 去掉 Markdown 表格分隔行与竖线，保留单元格文字
    text = re.sub(r"^\s*\|?\s*:?-+:?\s*\|?\s*$", " ", text, flags=re.M)
    text = text.replace("|", " ")
    return re.sub(r"\s+", " ", text).strip()

# 建索引时
sparse_text = clean_for_sparse(chunk["text_for_index"])
bm25.add(sparse_text)
dense_vec = embed(chunk["text_for_index"])   # 稠密路保留原结构
```

## 陷阱与边界

1. **表格被切分器切断**：没在切分前摘出，递归切分沿行列把表切断，LLM 基于残缺表自信答错。这是最致命的一条。
2. **只索引摘要不索引原表**：自然语言召回到了，但具体数值匹配不到，问"8192 是哪个模型"答不上。
3. **只索引原表不索引摘要**：精确数值能命中，但"对比一下各模型规格"这类自然语言提问召回不到。
4. **摘要过于笼统**：写成了"该表列出了模型参数"，没写具体数值和列含义，等于没提供锚点。
5. **表头未前置**：表格块孤立无上下文，既不召回也不可读。
6. **Markdown 符号污染稀疏索引**：`|`、`---` 成噪声词项，稀释有效词项权重，拉低 BM25 质量。
7. **合并单元格语义错位**：拉伸成规则表后未人工校验，关键表数值对不上原意。
8. **把表格当图片处理**：误用图片路径（VLM 描述）去替代原表，丢失精确数值。
