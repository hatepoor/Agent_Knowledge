# 增量接入与去重

> 一句话定位：个人知识库不必每次全量重建——用"三级内容指纹"做变更检测，只重算真正变化的部分，同时让索引保持幂等、可回滚、可删除。

## 核心结论

个人知识库的典型写入模式是"偶尔新增几份文档，偶尔修订一份"，而不是"每天全量刷新"。但全量重建的成本随文档量**线性上升**：每加一份文档，重建就要把全部文档重新解析、重新切块、重新算 embedding、重新建索引。对个人库而言，这种"改一个错别字也要重跑全篇"的性价比极低。

因此要做**增量接入**：只处理变化的部分。而增量的前提是**可靠的变更检测**，变更检测的前提是**稳定的内容指纹（hash）**。本页把指纹设计、变更粒度、幂等回滚、删除处理串起来，构成接入环节的"收口"逻辑，向上承接 [[rag/01_多源数据接入/元数据与溯源锚点|元数据与溯源锚点]]（指纹字段就挂在元数据上），向下衔接 [[rag/04_混合索引构建/索引与部署流水线|索引与部署流水线]]（版本化与回滚）。

一条贯穿全页的原则：**同一个输入，无论跑多少次，产出必须一致**（幂等）。否则你无法判断"索引变了"到底是内容变了，还是跑批随机性导致的。

## 机制与原理

### 为什么要做增量

全量重建的问题在个人库里被放大：

- **embedding 调用是主要成本**：本库用智谱 embedding-3，每次全量都要为所有块重新请求接口，文档上到几百份时单次重建就可能花掉可观的额度与时间。
- **VLM 调用不可忽略**：图片描述（见 [[rag/01_多源数据接入/图片提取与描述化|图片提取与描述化]]）依赖视觉模型，重跑全量是纯浪费。
- **个人库的变更频率低**：一周可能只新增一两份、修订零次，却要为"没变的那 99%"反复付费。

增量让"只动变化部分"成为可能，把成本从 O(总量) 降到 O(变化量)。

### 内容指纹的设计：三级 hash 共用"去重 + 变更检测"一个键体系

核心认知：**不同目的要用不同的 hash**，混用会出 bug。至少区分三级：

| 级别 | 计算对象 | 识别什么 | 用途 |
|------|----------|----------|------|
| 文件字节 hash | 原始文件二进制 | 文件本身有没有被替换 | 判断"是不是同一个文件实体" |
| 正文 hash（`content_hash`） | 规范化后的正文文本 | 内容变没变 | 文档级去重、文档级变更检测 |
| chunk hash | 单个 chunk 的规范化文本 | 某个块变没变 | 块级重算、复用 embedding / 图片描述 |

为什么正文 hash 不能对原始字节算？因为**同一份文档重新保存一次，字节就会变**（修改时间、元数据、压缩方式都可能动），字节 hash 会误判为"全新文档"。而正文 hash 对"清洗后的纯文本"算，重新保存不改内容就不会变。

为什么还需要 chunk hash？因为文档级检测只能告诉你"整篇变了"，但一个文档里可能只有第 3 段被改。chunk hash 让你**只重算变化的那几个块**，复用其余块的 embedding 与 VLM 描述——这对省调用至关重要。

三级 hash 的分工（约 16 行）：

```python
import hashlib

def norm_text(s: str) -> str:
    return re.sub(r"\s+", " ", s).strip()   # 规范化：去多余空白

def file_hash(path):     return hashlib.md5(open(path,"rb").read()).hexdigest()
def content_hash(text):  return hashlib.md5(norm_text(text).encode()).hexdigest()
def chunk_hash(chunk):   return hashlib.md5(norm_text(chunk["text_for_index"]).encode()).hexdigest()
```

### 变更检测的三种粒度

| 粒度 | 做法 | 代价 |
|------|------|------|
| 文档级 | 用正文 hash 比对，变了就整篇重跑（重新解析、切块、embedding） | 最简单；但改一个错别字也要重跑全篇 |
| 块级 | 按 chunk hash 比对，只重算 hash 变化的块，复用在位块的向量 | 省 embedding 与 VLM 调用；需维护"块 → 向量"映射 |
| 字段级 | 只重算受影响的元数据字段（如重新分页后的 `page`） | 最省；但实现复杂，需追踪字段级依赖 |

对个人知识库，推荐组合是 **文档级检测 + 块级重算**：

- 先用文档级 `content_hash` 快速判断"这篇动没动"——没动直接跳过，零成本；
- 动了之后，用块级 `chunk_hash` 逐块比对，只重算变化的块，复用其余块的 embedding 与图片描述。

这样既避开了"改一字重跑全篇"的浪费，又不必一上来就实现复杂的字段级依赖追踪。

### 幂等与可重放

"幂等"指同一份输入无论跑几次，产出完全一致。要满足它需注意：

- **清洗规则固定**：不要因运行环境不同而产生不同规范化结果（如依赖 locale 的大小写转换）。
- **日期不写入正文**：不要在解析出的文本里塞 `2026-09-19` 这种运行期日期，否则同内容两次跑出不同 hash，破坏幂等。日期只放元数据（`updated_at`），且来源是文档本身的修改时间而非"今天"。
- **随机种子固定**：VLM / LLM 摘要若带随机性，要固定 seed 或干脆要求确定性输出。

幂等的价值在于配合 [[rag/04_混合索引构建/索引与部署流水线|索引与部署流水线]] 的**版本化**：每次重建生成一个带版本号的索引快照，新版本验证无误后再切换；出问题能**回滚**到上一个版本。同时记录每批次的"来源清单 + 条数"，便于对账（"这次应该处理了 3 份新增、1 份修订"）。

### 删除的处理

文档被删除时，索引里它对应的块也必须删，否则会留下指向不存在来源的"孤儿块"，检索时召回无解引用。但**删除比新增危险**——误删不可逆、且难以及时发现。

建议：

- **软删除标记**：先给文档打 `deleted=true`，保留一段时间再物理清理，留出反悔窗口。
- **定期清理**：后台任务扫描软删除超过保留期的块，再真正移除。
- **审计日志**：任何删除操作都记录"谁、何时、删了哪个 `doc_id`、影响了多少块"，便于追溯与恢复。

### BM25 的"全量耦合"特性（最重要的一条展开）

这是增量后最容易被忽略、也最致命的点，单列展开。

**向量检索不依赖全局统计量**：稠密向量是逐块独立算的，插入一个新块只需在向量库里加一个节点，历史块的向量和它们彼此的相似度**完全不受影响**。所以向量索引做增量几乎零副作用。

**BM25 依赖全局统计量，具有"全量耦合"特性**：BM25 的分数公式里包含 IDF（逆文档频率），而 IDF 是**跨所有文档统计**出来的——`df`（某词项出现的文档数）和`总文档数 N` 都是全局量。此外 BM25 还依赖`avgdl`（所有文档的平均长度）。

这意味着：**每新增或删除一份文档，全局的 `df`、`N`、`avgdl` 都会变，于是历史文档里每一个包含这些词项的块的 BM25 分数都要重算。** 不是"只重算新文档的分数"，而是"所有文档的分数都变了"。

举例：你新增一份文档，里面频繁出现"上下文窗口"这个词。那么全局 `df("上下文窗口")` 上升 → IDF 下降 → **所有**之前文档里含"上下文窗口"的块的该词项得分都被拉低，哪怕它们内容一字未改。如果增量后只给新文档重算 BM25 而保留旧分数，检索排序就会悄悄失真。

因此增量后的硬性动作：**重建（或整体重算）BM25 索引的全局统计量**。多数 BM25 实现（如 `rank_bm25` 的 `BM25Okapi` 在 `corpus` 上整体 fit）本身就需要全量语料来构建——这恰恰说明它的"全量耦合"本质。务实做法是在增量批次后，用"全量文档流 + 剔除孤儿块"重新 fit 一次 BM25，成本远低于全量重建 embedding，但必须做。

对照表：

| 检索路 | 是否依赖全局统计量 | 增量副作用 | 增量动作 |
|--------|------------------|-----------|----------|
| 向量检索（embedding-3） | 否，逐块独立 | 无 | 直接插节点 |
| BM25 / jieba 稀疏 | 是（IDF、N、avgdl） | 历史文档分数全变 | 重算全局统计量（重 fit） |

## 实操

1. **入库前算指纹**：每份文档解析后立刻算 `file_hash` 与 `content_hash`，挂到元数据（见 [[rag/01_多源数据接入/元数据与溯源锚点|元数据与溯源锚点]]）。
2. **文档级快筛**：比对 `content_hash` 与已入库集合，未变的整篇跳过。
3. **块级比对**：变化的文档，逐块比 `chunk_hash`，只重算变化块，复用在位块的向量与描述。
4. **软删除 + 审计**：删除走标记态，记录审计日志，定期清理。
5. **BM25 重 fit**：每批增量后，用全量（剔除孤儿块）重新构建 BM25 全局统计量。
6. **版本化切换**：新索引带版本号，验证后切换，旧版本保留以便回滚。

一个增量主循环骨架（约 22 行）：

```python
def incremental_ingest(paths, store, bm25):
    for p in paths:
        fh, ch = file_hash(p), content_hash(read_text(p))
        if ch in store.doc_hashes:        # 文档级：内容没变
            continue
        chunks = parse_and_chunk(p)        # 解析 + 切块
        for c in chunks:
            kh = chunk_hash(c)
            if kh in store.chunk_hashes:   # 块级：复用旧向量
                store.reuse(kh)
            else:
                c["vector"] = embed(c["text_for_index"])
                store.add(c)
        store.doc_hashes[ch] = fh
    bm25.refit(store.all_texts())          # 重算全局统计量
    store.publish_version()                 # 版本化切换
```

## 陷阱与边界

1. **用文件字节 hash 做变更检测**：重新保存就判定为"变了"，触发无意义全量重跑。应改用正文 hash。
2. **只按路径判重**：同一文件放两个目录就重复入库。应结合 `content_hash` 去重。
3. **删除后留孤儿块**：索引里残留指向已删文档的块，检索召回无解引用。
4. **增量后没更新全局统计量**：这是 BM25 专属大坑——新增/删除文档改变 `df`、`N`、`avgdl`，所有历史文档 BM25 分数都要重算，否则排序失真；向量检索无此问题。
5. **把运行期日期写进正文**：破坏幂等，同内容两次跑出不同 hash。
6. **硬删除无审计**：误删不可逆且无从追溯。
7. **文档级变更却块级不复用**：变了就整篇重算，浪费 embedding / VLM 调用。
