# 元数据与溯源锚点

> 一句话定位：元数据是"加载时打标、随文档对象穿透切分"的结构化信息，它的核心价值是在内容脱离原文之后，仍能回答"它来自第几页、属于哪个章节、是什么类型"。

## 核心结论

最重要的一句话：**元数据必须在解析（加载）阶段就打上，而不是切分之后才补。** 一旦文本被切成块，块就已经脱离原文语境，你手里只有一个字符串——此时你无法再知道"它来自第几页、属于哪个章节、原本是不是表格"。位置信息一旦在解析阶段丢失，就是**永久丢失**，后续任何环节都补不回来。

这正是 `Document`（LangChain）或 `DoclingDocument`（docling）这类对象存在的意义：它们不只是"一段文本"，而是**承载文本之外的结构化信息**的容器。这些元数据要能穿透切分（chunking）阶段，一路传到下游的索引、检索、生成环节。如果你在解析时把信息丢进纯字符串里，切分器只会忠实地把字符串切断，把元数据一起切碎。

实践原则：在解析器产出结构化文档对象后，**第一件事**就是把溯源字段提取并挂到每个将生成的 chunk 上，而不是等切完再想"我还能拿到什么"。

本页与 [[rag/01_多源数据接入/表格提取与处理|表格提取与处理]] 紧密配合：表格块需要 `content_type=table` 和 `self_ref` 来定位；也承接 [[rag/01_多源数据接入/增量接入与去重|增量接入与去重]] 的去重字段。

## 机制与原理

### 完整字段清单（四类）

元数据按用途分为四类，建议统一命名，避免下游各取所需导致字段漂移：

| 类别 | 字段 | 用途 |
|------|------|------|
| 标识 | `source` / `doc_id` / `content_hash` | 溯源（定位原始文件）、去重（识别重复入库）、增量更新（判断内容变没变） |
| 定位 | `page` / `bbox` / `title_path` / `self_ref` / 文档流序号 | 引用定位（回答"出自第几页"）、标题链拼接（提供章节锚点） |
| 内容属性 | `lang` / `content_type`（text/table/figure） / `char_count` | 语言分片统计（中文 vs 英文分别评估）、按类型分流（表格走双轨、图片走 VLM）、质量过滤（过短块丢弃） |
| 治理 | `created_at` / `updated_at` / `trust_level` / `acl` | 时效性过滤（只召回近 N 天）、低信任来源标记（标注（待核实）来源）、权限过滤（按读者 ACL 收口） |

- `source`：原始文件路径或 URL，溯源的最粗粒度锚点。
- `doc_id`：文档级稳定 ID（建议由文件路径规范化得到，而非随机），去重与增量都依赖它。
- `content_hash`：正文的规范化 hash，见 [[rag/01_多源数据接入/增量接入与去重|增量接入与去重]] 的三级 hash 设计。
- `page` / `bbox`：页码与包围盒坐标，PDF 场景可用；DOCX 场景为空（见下一节）。
- `title_path`：从文档根到当前块所经历标题的链，如 `第一章 > 第二节 > 子标题`，回报最高（详下）。
- `self_ref`：解析器内部的元素引用，如 `#/pictures/0`，是 DOCX 下最可靠的定位锚点。
- `content_type`：区分 text / table / figure，驱动下游分流逻辑。

### 一个关键差异：DOCX 没有页码（实测结论）

这是本库在 Windows + Word 素材场景下踩到的真实坑，单列一节强调。

- docling 解析 **DOCX** 后，元素的位置信息（`prov`）是**空列表**——因为 DOCX 是流式文档格式，**没有固定分页概念**。一页在哪里结束，由打开它时的渲染器（Word、WPS、打印驱动）决定，文档本身不存页码。
- 这意味着"第 N 页"这类溯源在 DOCX 场景**做不到**。你无法诚实地告诉用户"这句话出自第 3 页"。
- 可用的替代锚点：
  - `self_ref`（如 `#/pictures/0` / `#/tables/2`）：解析器内部的稳定元素引用，最可靠；
  - **标题链**：在遍历元素树时维护一个标题栈，记录"当前块属于哪个章节"；
  - **文档流序号**：块在正文流中的出现顺序，如第 12 个块。

对比 **PDF**：PDF 的 `prov` 里带有 `page_no` 与 `bbox`，可以做**坐标级溯源**——"这句话出自第 3 页、坐标 (120, 340)"。

实践建议：

- 如果产品必须支持"第几页"定位，要么在解析前把 DOCX 转成 PDF（用 libreoffice / Word 另存），要么**接受降级**为"章节 + 段落序号"的定位表述。
- 在元数据 schema 里，`page` 对 DOCX 文档应允许为空并显式标注，避免下游过滤时因空值静默匹配失败（见陷阱）。

### `title_path` 的三个用途（回报最高的字段）

在所有元数据里，`title_path` 是投入产出比最高的一个，因为它同时服务召回、过滤、合并三件事：

1. **拼接进 chunk 文本作为语义锚点**：把 `第一章 > 第二节` 拼到块前面，相当于给每个块补了一段"它属于哪"的上下文，能显著提升稠密路对该块的召回——尤其对短块效果明显。
2. **作为元数据过滤条件**：检索时按章节范围收口，例如"只在『模型对比』这一章内找"。这比全文检索更可控，也能解释"为什么召回了这条"。
3. **作为块合并时的边界判断依据**：如果两个相邻块 `title_path` 相同，说明它们同属一个父章节，可以安全合并以还原上下文；一旦 `title_path` 变了，就说明跨了章节，应停止合并。

构建 `title_path` 的典型做法（约 18 行）：

```python
def build_title_paths(doc):
    stack = []          # 标题栈，维护章节层级
    results = []
    for el in doc.iterate_items():
        lvl = getattr(el, "level", None)
        if el.category == "heading" and lvl:
            # 维护栈深度：遇到更浅的标题就弹出深层
            while stack and stack[-1][0] >= lvl:
                stack.pop()
            stack.append((lvl, el.text))
        else:
            results.append({
                "text": el.text,
                "title_path": " > ".join(t for _, t in stack),
                "self_ref": el.self_ref,
            })
    return results
```

### 元数据如何驱动下游

元数据不是"存着好看"，它直接驱动多个下游环节（用 wikilink 串起来）：

- **过滤**：[[rag/07_元数据过滤/元数据过滤]] —— 按时间（`updated_at`）、权限（`acl`）、类型（`content_type`）在检索时收口。
- **溯源**：[[rag/09_上下文构建与溯源/溯源与引用]] —— 生成答案时，用 `source` / `self_ref` / `title_path` 回链到原文位置，给出可核查的引用。
- **评估分片**：[[rag/12_评估与监控/离线评估集]] —— 按 `lang` 组合（中英混排）、按 `source` 分片统计召回与准确率，定位哪些来源质量差。

### text 与 metadata 的分工（LangChain Document 视角）

LangChain 的 `Document` 对象天然分 `page_content` 与 `metadata` 两半，正好对应本库设计：

- `page_content`：喂给 embedding 与 LLM 的文本（即前文 `text_for_index` / `text_for_llm` 的取值来源）。
- `metadata`：本页讨论的所有定位与治理字段。

关键纪律：**定位信息只放在 `metadata`，不烧进 `page_content`**。原因：定位信息会变（如重新分页后 `page` 变了），但正文不应因此重算 embedding。把定位留在 metadata，正文稳定，增量更新时才能只动 metadata 不动向量。

## 实操

1. **解析即打标**：docling 产出 `DoclingDocument` 后，立刻遍历元素树，把 `source`、`doc_id`、`self_ref`、`content_type`、`char_count` 挂到每个待生成块。
2. **维护标题栈**：遍历时维护 `title_path`，拼进块文本与 metadata。
3. **DOCX 降级**：检测到源是 DOCX 时，`page` 字段置空并标注，定位改用 `self_ref` + `title_path`；若必须页码，先转 PDF。
4. **统一时间格式**：`created_at` / `updated_at` 一律用 ISO 8601（`2026-09-19`），避免"`2026/9/19`""`09-19-2026`"混用导致过滤失效。
5. **空值策略**：对可能为空字段（DOCX 的 `page`）显式写 `null` 并约定过滤时的处理分支，不要留空字符串。

一个从 docling 元素提取元数据的片段（约 14 行）：

```python
def attach_meta(el, source, doc_id):
    prov = el.prov[0] if el.prov else None
    return {
        "source": source,
        "doc_id": doc_id,
        "self_ref": el.self_ref,
        "content_type": el.category,            # text/table/figure
        "page": prov.page_no if prov else None,  # DOCX 下为 None
        "bbox": prov.bbox if prov else None,
        "char_count": len(el.text or ""),
        "title_path": current_title_path,
    }
```

## 陷阱与边界

1. **分块后才想起来打标**：块已脱离原文，拿不到页码与章节，溯源信息永久丢失。
2. **字段命名不统一**：上游写 `page_no`、下游读 `page`，过滤静默落空。应在 schema 层统一。
3. **时间格式不一致**：`2026/9/19` 与 `2026-09-19` 混用，按时间窗口过滤时漏召回。
4. **空值未处理**：DOCX 的 `page` 为空字符串而非 `null`，下游 `page > 0` 比较时类型错误或静默匹配不上。
5. **把定位信息烧进正文**：重分页后正文变化，导致 embedding 被迫重算，浪费增量更新的收益。
6. **误以为 DOCX 有页码**：展示"出自第 3 页"会给出虚假溯源，应在 DOCX 场景降级为章节定位。
7. **`content_type` 缺失**：表格与正文混在一起走同一索引逻辑，失去双轨索引的机会。
