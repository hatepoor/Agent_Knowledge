# 文档解析：RAG 解析层总览

> 解析是 RAG 质量的第一道天花板。链路是 `解析 → 切分 → 检索 → 生成`：下游环节只能挽救、不能修复上游丢失的信息。一个被拍平的表格、一段被漏掉的正文，在检索和生成阶段再怎么调参都救不回来。

## 核心结论

- **解析不是「把文件读成文本」那么简单**，而是把文档里的结构（标题层级、表格行列、图片语义、页码坐标）尽量无损地搬到知识库。结构即信息，拍平结构等于主动丢弃信息。
- **先试文本层，再上视觉层**：数字文档（Word、原生 PDF、HTML）自带文本层，直接读结构最快最准；只有扫描件、图片型 PDF、复杂版式才需要 OCR 或视觉模型。
- **表格是真正的分水岭**，也是幻觉的主要来源。各家在干净单栏文本上表现都合格，差距全在合并单元格、多级表头、密集数值网格上。
- **用自己的文档实测，比看任何评测都重要**——尤其用你最难解析的那几张表。

## 第一决策：文本层 vs 视觉层

判断文档是「数字版」还是「扫描版」，决定走哪条解析路线：

| 路线 | 原理 | 代表工具 | 适用 |
|------|------|----------|------|
| **文本层解析** | 直接读取文件内的文本/结构数据 | PyMuPDF、PDFPlumber、python-docx、BeautifulSoup | 有文本层的数字版 PDF、可直读的 .docx、HTML |
| **视觉层解析** | 把页面当图像，OCR / 模型还原结构 | PaddleOCR、MinerU、Marker、VLM | 扫描件、图片型 PDF、复杂版式、图表 |

**决策原则**：能走文本层就走文本层——它快、精确、保留原始结构坐标。只有文本层拿不到或质量差（扫描件、乱码、多栏串行）时，再上视觉层。不要一上来就堆重模型，那是成本与时间的最大浪费。

> 如何判断有没有文本层？见 [[rag/01_多源数据接入/PDF解析|PDF 解析]] 中的「数字版 vs 扫描版分流」。一句话：抽取字符数与字符密度，密度过低就是扫描件。

## 解析器横向对比表（8 款）

| 工具 | 输出格式 | 表格能力 | 部署方式 | 成本 | 许可 | 关键限制 |
|------|----------|----------|----------|------|------|----------|
| **docling**（IBM） | Markdown + 结构化 JSON | 最强（第三方测试约 97.9%） | 自托管 | 仅算力成本 | MIT | 依赖较重，生产级管线约需 20–40 小时搭建 |
| **Unstructured** | typed elements（非 Markdown） | 75–100%（波动大） | 自托管 / 云 | $0 自托管 / 约 $0.015 每页云 | MIT / Apache（待核实） | 50+ 格式覆盖但 `[all-docs]` 安装耗时长；输出是元素流，需额外整理 |
| **LlamaParse**（LlamaIndex） | Markdown / JSON | 75–90% | 云 API | 按 credit（3–45 credits/页）；10 万页/月约 $375–$5,625 | 商业 | 规模化成本陡增 |
| **MarkItDown**（微软） | 轻量 Markdown | 基础 | 本地 | $0 | MIT | 无 layout 模型、无 OCR，PDF 处理弱 |
| **Marker** | Markdown / JSON | 良好 | 自托管（建议 GPU） | 仅算力成本 | **GPL** | 商用需法务确认；CPU 上很慢 |
| **MinerU** | Markdown | 良好 | 自托管 | 仅算力成本 | 社区开源（待核实） | 仅支持 PDF；中文与学术文档表现突出 |
| **PyMuPDF4LLM** | 极快 Markdown | 60–70% | 本地 | $0 | GNU AGPL / 商业版（待核实） | 不做完整 layout 检测，直读 PDF 原生结构 |
| **Azure DI / AWS Textract** | JSON（非 Markdown） | 良好 | 云 | 约 $1,000–$3,000 / 10 万页 | 商业 | 生态绑定；输出需再转 Markdown |

> 表格能力数字来自第三方测试与编辑评分，非统一条件下的实验室结果；成本按 2026 年官方定价折算。**务必用自己的文档实测后再下结论。**

## 按场景选型

| 场景 | 首选 | 理由 / 备选 |
|------|------|-------------|
| **Word + 图表 + 中英混排** | **docling** | 见下方专条说明 |
| 数字版 PDF 纯文本 | PyMuPDF | 表格多时换 PDFPlumber |
| PDF 扫描件转带结构文本 | MinerU / Marker | 纯 OCR 只出无布局文字 |
| 格式极杂（邮件/HTML/图片混） | Unstructured | 50+ 格式覆盖，但依赖重 |
| 预算充足、要极致表格精度 | LlamaParse | 先用样本对比 docling 再定 |
| 已绑定云厂商 | Textract / Azure DI | 注意输出是 JSON，需后处理 |
| 最简单 Markdown 导出 | MarkItDown | 无 OCR，PDF 弱 |

**「Word + 图表 + 中英混排」为什么选 docling**（你的主要素材场景）：

1. **表格是分水岭，而 docling 表格能力最强**——TableFormer 能重建合并单元格与多级表头，这正是中英混排报告里最难的格式。
2. **MIT 许可，自托管免费，无 GPL 风险**——对比 Marker 的 GPL 商用隐患，对个人知识库长期维护更省心。
3. **一次拿到 Markdown + 结构化 JSON**——Markdown 可直接入混合检索，结构化 JSON 保留表格与坐标，省去「先解析再补结构」的二次工程。

> 你的素材以「中英混排 Word + 表格 + 图片」为主、PDF 是次要来源，因此本环节的重点在 [[rag/01_多源数据接入/Word解析|Word 解析]] 与 [[rag/01_多源数据接入/表格提取与处理|表格提取与处理]]，而非 PDF。

## 一个必须建立的认知：表格是分水岭

各家解析器在干净单栏文本上表现都「合格」，真正的差距全部集中在：

- **合并单元格**（跨行/跨列的表头）
- **多级表头**（"2024 年 / 上半年 / 销售额"这种嵌套）
- **密集数值网格**（成百上千个单元格的财务/实验表）

表格一旦被扁平化为「一行行文字」，列与行的对应关系（"A 列是产品，B 列是价格"）就永久丢失。更危险的是：LLM 会**自信地**基于错误的数字作答——它不会意识到表格已经被破坏。这是 RAG 故障里最难排查的一类：答案看起来很顺、引用「似乎」有依据，但数字从根上就错了。

因此表格处理是独立专题，见 [[rag/01_多源数据接入/表格提取与处理|表格提取与处理]]。

## 三分钟自测法

不要先去读评测报告。从你自己的语料里**挑最难的三张表**（合并单元格最多 / 跨页 / 最依赖列头语义的），逐工具跑一遍，**人工**看输出：

1. 表头层级对不对？合并单元格有没有被拆散？
2. 行列对齐有没有错？数字有没有串行？
3. 多级表头有没有被正确识别为层级？

这一步的性价比远高于任何 benchmark——再漂亮的评测数字，也比不上「你的真实文档跑出来对不对」。
