# 生产可观测性

## 概述

离线评估回答"这版改得好不好"，可观测性回答"线上现在好不好、哪里坏了"。RAG 是可观测性要求极高的系统：**检索了什么、重排后剩什么、生成了什么、引用是否对得上**——每一环都需要留痕，才能定位"答案变差"究竟是分块、索引、检索还是生成的问题。本文给出 RAG 专属的观测对象、LangSmith 落地方式与反馈闭环。

> 指标口径与离线评估衔接见 [[rag/12_评估与监控/评估体系与RAGAS|RAG 评估体系与 RAGAS]]；成本观测见 [[rag/13_工程横切/性能与成本优化|性能与成本优化]]。

## 一、RAG 专属观测对象（三层埋点）

| 层 | 必采字段 | 回答的问题 |
|----|----------|-----------|
| 检索层 | query（改写前后）、检索器类型、k、Top-K 块 id/来源/分数、重排后 Top-N | 召回够吗？排序对吗？命中分布是否漂移 |
| 生成层 | 注入的上下文块清单、Prompt token 数、答案、引用的编号 | 上下文干净吗？引用是否对得上证据 |
| 系统层 | 各阶段耗时、token 用量、成本、缓存命中、失败/超时 | 快不快、贵不贵、稳不稳 |

配套指标：**检索零命中率**（retrieval miss rate）、**平均相似度分布**（整体检索置信是否下滑，可能是索引/Embedding 出问题）、引用正确率（抽检）。

## 二、LangSmith 落地

LangSmith 提供 tracing（链式追踪）+ 在线评估 + 数据回流，与 LangChain/LangGraph 无缝：

```python
# 1) 打开追踪：所有 chain/agent 自动上报（需环境变量 LANGCHAIN_API_KEY）
from langchain.agents import create_agent
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_PROJECT"] = "rag-prod"      # 按环境/模块分项目

# 2) 自定义观测：在关键节点打标（检索评分、是否触发 rewrite、引用校验结果）
from langchain.callbacks import tracing_v2_enabled
with tracing_v2_enabled("rag-prod"):
    # 手动埋点：把检索命中列表、重排分数等结构化字段写入 run
    pass
```

生产化要点：
- **按项目/标签切分**：`env=prod/staging`、`tenant=xxx`，便于横向对比租户质量。
- **失败与低分自动标记**：接入反馈 API（👍/👎、检索 miss、引用失败），把"线上问题"沉淀为可评估数据。
- **在线评估**：对线上流量抽样子集跑 RAGAS 指标（成本可控的采样 + 批处理），与离线回归形成双轨。
- **回放（playback）**：把线上失败 case 一键拉回本地复现，修完补进 golden set。

## 三、反馈闭环（持续变好的飞轮）

```
线上请求 → 追踪/埋点 → 质量信号(用户反馈/自动判分/检索 miss)
    → 失败 case 回流 golden set → 离线评估回归 → 修复(分块/检索/Prompt)
    → 灰度上线 → 线上对比(旧 vs 新) → 再回流…
```

- 关键：**线上采样要带环境变量可复现**（索引版本、模型版本、参数快照），否则案例无法回放。
- 建立 SLO 看板：可用性、P95 延迟、检索 miss 率、引用正确率抽检、单请求成本。告警阈值与 04 层经验区间对齐（如 Faithfulness 采样均值跌破 0.90 触发人工复核）。

## 四、常见问题

**Q1：只用日志不行吗，为什么要专门的 trace 平台？**
RAG 链路是"多步、带上下文、需跨步关联"，普通日志难把"这次用了哪些块、引用了哪个编号"串成一条可回放记录。LangSmith/OpenTelemetry（GenAI 语义约定）这类 trace 工具的价值在关联与回放。

**Q2：采样还是全量追踪？**
全量 trace 存储成本高；推荐：全量轻量埋点（耗时/token/结果）+ 抽样深 trace（含上下文明细，如 10%–20%）。反馈或异常触发时对该会话临时全量。

**Q3：多租户环境怎么观测不串数据？**
trace 里带 tenant 标签 + 平台级权限隔离；指标按租户聚合，质量差异可视化（配合 [[rag/13_工程横切/多租户与大并发|多租户与大并发]]）。

**Q4：可观测性建设投入产出怎么衡量？**
直接产出：故障定位时间从"小时级"到"分钟级"；间接产出：失败案例回流形成评估资产，是 RAG 迭代的最强燃料。建议第一个版本只做"埋点 + 失败回流"，别一上来追求完整看板。

## 五、最佳实践

1. **先埋检索与引用，再补全量**：RAG 特有故障（召回差/引用错）的数据在检索层与引用校验，比通用 LLM 观测更关键。
2. **引用校验在线化**：用轻量规则（引用的编号是否存在于注入块清单）+ 抽检 LLM 判分，幻觉泄漏可被及时发现。
3. **观测配置版本化**：埋点 schema 变更要向后兼容，避免历史数据不可比。
4. 把"可回放失败案例数"当 RAG 平台健康度指标之一——案例库枯竭 = 系统可能在退化而无人知晓。
