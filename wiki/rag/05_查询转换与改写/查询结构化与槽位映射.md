# 查询结构化与槽位映射

## 概述

槽位映射（slot mapping）源自任务型对话 NLU 的 slot filling 思想：把一句自然语言拆成**语义查询串 + 一组结构化槽位（字段=操作符=值）**。在 RAG 中对应 LangChain 官方所称的 **Query Construction**——把用户问题翻译成目标数据源的查询语法。官方博客的核心论点：**"很多查询的答案不仅藏在语义相似度里，更藏在数据固有的结构里"**——例如"1980 年的 aliens 电影"，`aliens` 应走向量检索，`year == 1980` 必须走精确过滤；让结构化过滤条件**在检索前剪枝候选块**，可显著提升答案质量。

> 元数据过滤的 Retriever 实现见 [[langchain/modules/langchain_retrievers/SelfQueryRetriever|SelfQueryRetriever]]；查询改写类增强见 [[rag/05_查询转换与改写/查询改写与扩展|查询增强与上下文构建]]。

## 一、三条翻译路线（按数据源）

| 路线 | 数据源 | 输出 | 典型工具 |
|------|--------|------|----------|
| **Text-to-Metadata-Filter** | 向量库（非结构化文档 + 结构化元数据） | `query + filter(field, comparator, value)` | SelfQueryRetriever / 自建 Pydantic 链 |
| **Text-to-SQL** | 关系库（结构化数据） | SQL 语句（可再混合语义检索，如 PGVector） | LangChain SQL 链 |
| **Text-to-Cypher** | 图数据库 | Cypher 查询 | GraphRAG/图查询链 |

三者统一模式：**Pydantic schema 定义槽位 → LLM with_structured_output 填槽 → 解析校验 → 翻译为存储层过滤语法**。

## 二、标准实现：Pydantic 填槽

```python
# pip install -qU langchain-openai
from datetime import date
from typing import Literal, Union
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

class Filter(BaseModel):
    """简洁槽位模式：字段-比较符-值（三段式）"""
    field: Literal["publish_date", "length_sec", "view_count", "author"]
    comparison: Literal["eq", "lt", "lte", "gt", "gte"]
    value: Union[int, date] = Field(description="publish_date 必须为 ISO-8601 日期")

class TutorialSearch(BaseModel):
    """检索教程视频库的槽位 schema"""
    content_search: str = Field(description="对视频转写文本的语义检索词")
    title_search: str = Field(description="针对标题的关键词检索词（精简）")
    filters: list[Filter] = Field(default_factory=list,
        description="多个过滤条件取逻辑与；时间区间须拆成 gte/lte 两个槽位")

system = """你是把用户问题转换为数据库查询的专家。遇到不认识的缩写或词，
不要试图改写，原样保留。今天是 {today}。"""
prompt = ChatPromptTemplate.from_messages([
    ("system", system), ("human", "{question}"),
])
query_analyzer = prompt | ChatOpenAI(model="gpt-4o", temperature=0) \
                        .with_structured_output(TutorialSearch)

slots = query_analyzer.invoke({
    "question": "5 分钟以内、讲 multi-modal agent 的视频",
    "today": date.today().isoformat(),
})
# → content_search="multi-modal agent", filters=[Filter(field="length_sec",
#    comparison="lt", value=300)]
```

官方示例输出（LangChain Query Construction 博客）：`"Taylor Swift 或 Katy Perry 的、3 分钟以内的 dance pop 情歌"` 会被解析为
`{"query": "teenager love", "filter": "and(or(eq(\"artist\",\"Taylor Swift\"), eq(\"artist\",\"Katy Perry\")), lt(\"length\",180), eq(\"genre\",\"pop\"))"}`——语义串与槽位过滤器彻底分离，支持 AND/OR/嵌套。

## 三、槽位工程的关键设计

| 设计点 | 做法 | 为什么 |
|--------|------|--------|
| **Schema 粒度** | 字段少用 verbose schema（每槽位独立字段）；字段多用 succinct schema（Filter 三段式列表） | verbose 更受控但塞不下几十个字段，官方明确给出两档取舍 |
| **枚举约束** | `Literal` 锁定字段名/比较符 | 防止 LLM 发明不存在的字段——最常见的静默失败 |
| **Few-shot** | 给 2–3 组「问题→槽位」样例 | 日期区间、时间词解析的准确率主要靠它 |
| **时间标准化** | 注入当前日期；区间拆成 gte/lte 双槽位 | "最近一个季度""上季度"没有锚点就无法解析 |
| **填槽校验** | Pydantic 校验失败 → 重试一次 → 失败降级为纯向量检索 | 填槽是增强不是依赖，坏了不能瘫 |
| **安全槽位** | `tenant_id`/权限槽位由**服务端强制覆盖**，绝不信任 LLM 填的值 | LLM 填错租户 = 越权检索（[[rag/13_工程横切/多租户与大并发|多租户安全]]） |

## 四、常见问题

**Q1：LLM 把槽位填错了（如日期解析错）怎么办？**
三层防御：Literal 枚举 + Pydantic 类型校验拦住格式错误；few-shot + 当前日期注入降低语义错误；对关键槽位（时间、金额）用确定性解析器（正则/日期库）预提取，LLM 只兜底复杂表述。

**Q2：槽位过滤太严导致 0 命中？**
与分块过滤的兜底同理：先放宽槽位（去掉非硬性条件）重试一次；再不行退化为纯语义检索并在答案中声明"按条件未找到，以下为语义近似结果"。0 命中必须可解释。

**Q3：什么时候该上 Text-to-SQL？**
查询本质是聚合/排序/跨表（"上季度华东区销售额 Top10 客户"）时，向量检索天然不适配。生产建议：SQL 由受控模板 + 槽位拼装，或至少加 SQL 校验与只读账户，别让 LLM 自由生成 DDL/DML（安全见 [[rag/11_安全审核与日志/安全与合规|安全与合规]]）。

**Q4：SelfQueryRetriever 和自己写 Pydantic 链怎么选？**
SelfQueryRetriever 开箱即用、与主流向量库过滤语法对接好，适合标准元数据过滤；自建链适合需要复杂槽位（多实体、区间、业务规则）或要把槽位路由到多种存储的场景——两者共享同一套"schema→structured output"原理。

## 五、最佳实践

1. **先给元数据建索引与字典**：槽位映射的上限由元数据质量决定——字段枚举值标准化（如统一的部门/产品命名）先于任何 LLM 优化。
2. **把"语义串+槽位"整体当一条查询记录**：观测两者，才能回答"是没检索到还是被过滤掉了"（[[rag/12_评估与监控/在线监控与可观测性|可观测性]]）。
3. **评估槽位准确率单列指标**：构造「问题→期望槽位」标注集，报槽位 F1——这是 query analyzer 的独立回归项。
4. 槽位映射与 [[rag/09_上下文构建与溯源/上下文压缩|检索后过滤]] 是一对：前者在检索前剪枝（快），后者在检索后精修（准），生产常双管齐下。
