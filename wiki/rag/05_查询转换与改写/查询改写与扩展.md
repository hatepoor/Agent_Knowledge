# 查询改写与扩展（Query Rewrite & Expansion）

> 检索链路第 5 步（Pre-Retrieval 查询理解）。自述式检索见 [[rag/05_查询转换与改写/查询结构化与槽位映射]]；把检索条件转成元数据过滤见 [[rag/07_元数据过滤/元数据过滤]]。

## 概述

检索质量 = f(查询质量, 索引质量)。用户原始问题通常是**口语化、含指代、多意图、缺领域术语**的——直接用原文去检索等于"带着模糊的钥匙开锁"。查询增强（Query Enhancement）在检索前把查询改造成更易命中的形态。

## 一、查询增强/改写的六种手段

| 手段 | 做法 | 典型收益 | 代价 |
|------|------|----------|------|
| 查询改写（Rewrite） | LLM 把口语/含指代问题改写成检索友好句式 | 中高 | 1 次 LLM 调用延迟 |
| 多查询扩展（Multi-Query） | LLM 生成 3–5 个同义/子问题变体分别检索后去重合并 | 高（覆盖率↑） | 检索次数 ×3–5，成本/延迟↑ |
| HyDE（假设性文档） | 先生成"如果存在答案，文档会怎么写"的假想段落再检索 | 高（特定领域） | 依赖 LLM 生成质量，慢 |
| 子问题分解（Decomposition） | 多跳问题拆成可分别检索的子问题 | 多跳问答必需 | 编排复杂度↑ |
| Self-Query（结构化过滤） | LLM 把自然语言转成"向量 + 元数据过滤条件" | 精确剪枝 | 需元数据 schema 与受控生成 |
| 指代消解 | 多轮对话中把"它/这个方案"补全为完整实体 | 对话式 RAG 必需 | 需会话状态 |

> 注：HyDE 与 Multi-Query 二选一优先 Multi-Query——HyDE 在答案形态与文档差异大时反而引入噪声。Self-Query 产出的过滤条件接线到 [[rag/07_元数据过滤/元数据过滤]]。**所有改写手段都要用 [[rag/12_评估与监控/评估体系与RAGAS|评估指标]] 验证净收益**（改写本身有 LLM 成本与幻觉风险）。

## 二、代码示例

```python
# 1) Multi-Query：一次提问，多路召回，去重合并
# pip install -qU langchain-community
from langchain.retrievers import MultiQueryRetriever

base = vectorstore.as_retriever(search_kwargs={"k": 5})
multi = MultiQueryRetriever.from_llm(retriever=base, llm=llm, include_original=True)
hits = multi.invoke("Transformer 相比 RNN 好在哪？")   # 自动生成 3 个变体查询并集合并
```

```python
# 2) Self-Query：自然语言 → 元数据过滤（需 AttributeInfo 声明可过滤字段）
# 完整语法见 [[langchain/modules/langchain_retrievers/SelfQueryRetriever|SelfQueryRetriever]]
from langchain.retrievers.self_query.base import SelfQueryRetriever
from langchain.chains.query_constructor.base import AttributeInfo

fields = [
    AttributeInfo(name="product", description="产品线名称", type="string"),
    AttributeInfo(name="date", description="文档发布日期", type="string"),
]
sq = SelfQueryRetriever.from_llm(
    llm=llm, vectorstore=vectorstore,
    document_contents="产品手册片段",
    metadata_field_info=fields,
)
sq.invoke("A 产品线 2026 年之后的升级说明")   # 解析出 filter={product:"A", date:{$gte:...}} + query 向量
```

## 三、常见问题

**Q1：查询改写会不会把好问题改坏？**
会，且难提前预知。缓解：① 只对"检索后评分低/无命中"的查询触发改写（条件路由，见 [[rag/14_范式与前沿/Agentic_RAG|Agentic RAG 的 rewrite 节点]]）；② A/B 对比改写前后 Recall@k；③ 保留原文兜底（include_original=True）。

**Q2：Multi-Query 每轮多 3–5 次检索，生产能扛住吗？**
延迟敏感场景建议"只对复杂/低置信查询启用"，或把改写做成离线候选缓存。成本收益要量化：覆盖率提升 vs 检索与 token 成本。

**Q3：多轮对话里查询和检索怎么协同？**
检索用"指代消解后的当前问题"，生成带"历史摘要"。历史越长越要压缩/摘录，防上下文稀释（可配合 langchain 的 memory 中间件）。

## 四、最佳实践

1. **查询增强是"条件触发"而非全量开启**：默认直查，路由到增强最省成本——Agentic 化见 [[rag/14_范式与前沿/Agentic_RAG|Agentic_RAG]]。
2. **Self-Query 的前提是元数据干净**：字段缺失/脏值会让结构化过滤静默漏召回——先做索引侧元数据治理（[[rag/04_混合索引构建/索引与部署流水线]]）。
3. **改写策略改动归还 golden queries 回归**（[[rag/12_评估与监控/离线评估集|离线评估]]）。
