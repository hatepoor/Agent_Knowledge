# 容器安全加固 · 专题概览

## 专题定位

本专题解决的问题是：**容器到底隔离得多好，以及怎么把它加固到能承载不可信负载。**

**何时该翻这个专题**

- 容器要运行**不可信代码**（用户提交的代码、第三方脚本、AI Agent 生成的代码）
- 要接生产环境，需要过安全评审
- 需要回答"容器被攻破后能造成多大破坏"
- 需要隔离同一台机器上的多个租户
- 基础镜像被扫出 CVE

> ⚠️ **本专题的立场**：**容器不是安全边界。** 它默认提供的隔离**足以防止误操作，但不足以抵御有攻击意图的恶意代码**。所有加固措施的目的都是**提高攻击成本**，而不是"保证不可逃逸"。理解这一点，才能正确选择技术方案。

---

## 一、核心认知：容器隔离的真实强度

### 1.1 容器与虚拟机的安全差异

| 维度 | 容器 | 虚拟机 |
|------|------|--------|
| 隔离边界 | **共享宿主内核**，靠 namespace + cgroup | **独立内核**，靠硬件虚拟化 |
| 逃逸难度 | ⚠️ **较低**：一个内核漏洞即可逃逸 | 较高：需突破 hypervisor |
| 默认权限 | ⚠️ 容器内是 **root**（映射到宿主 root） | 独立内核内 root 影响有限 |
| 攻击面 | 宿主内核全部系统调用 | 精简的虚拟化接口 |

**结论**：

| 场景 | 容器够用吗 |
|------|-----------|
| 隔离自己的不同服务 | ✅ 够用，且是主流做法 |
| 运行队友写的代码 | ⚠️ 加固后可用 |
| 运行**用户提交/互联网下载**的代码 | ❌ **需要额外隔离层**（gVisor、Kata、microVM、或虚拟机） |
| 多租户 SaaS 的代码执行 | ❌ 同上，且应配合专门的沙箱方案 |

### 1.2 三类攻击面

```
① 镜像层        恶意/有漏洞的镜像 → 容器内被攻陷
② 运行时层      容器配置不当 → 权限过大、可逃逸
③ 宿主机层      Docker 本身、socket、内核 → 直接拿下宿主
```

**加固的本质是：让攻击者即使拿下容器，也拿不到宿主。**

## 二、加固措施全景（按层次）

| 层次 | 措施 | 关键参数 |
|------|------|----------|
| **镜像** | 最小基础镜像、非 root、扫漏洞、固定 digest、无密钥 | `FROM ...-slim/alpine/distroless`、`USER` |
| **运行时** | 只读根文件系统、削减能力、禁提权 | `--read-only`、`--cap-drop`、`--security-opt` |
| **内核** | seccomp、AppArmor/SELinux、用户命名空间 | `--security-opt seccomp=`、`--userns` |
| **资源** | 限制 CPU/内存/进程数（防 DoS） | `-m`、`--cpus`、`--pids-limit` |
| **网络** | 禁网或白名单、不暴露端口、隔离网络 | `--network none`、`internal: true` |
| **宿主机** | 保护 socket、用 rootless、专用节点 | `docker` 组管理、rootless 模式 |
| **审计** | 日志、事件流、不可变审计 | `logging`、`docker events` |

## 三、镜像层加固

### 3.1 最小化基础镜像

| 做法 | 收益 |
|------|------|
| 用 `-slim` / `-alpine` / `distroless` | 减少**攻击面**（少装一个包就少一份漏洞） |
| 多阶段构建 | **构建工具不进运行镜像**（攻击者拿不到编译器） |
| 移除 shell | `distroless` / `scratch` 里没有 shell，攻击者难以执行后续命令 |
| 不装 `curl` / `wget` / `nc` | ⚠️ **这几样是攻击者最常用的"下载下一阶段载荷"工具** |

**权衡**：移除 shell 也让你无法 `docker exec` 排查。**建议保留一个调试用 target**（见 [[docker/02-中段阶段-专题精讲/镜像优化与瘦身/专题概览]]）。

### 3.2 非 root 运行（基础且必做）

```dockerfile
RUN useradd -m -u 10001 appuser && chown -R appuser /app
USER 10001                # 用数字 UID 更明确
```

| 要点 | 说明 |
|------|------|
| 默认容器内是 **root（UID 0）** | 而 Docker 默认**不做用户映射**，容器里的 root 在宿主上（名义上）也是 root |
| **用数字 UID** | 用户名在不同系统映射可能不同；K8s 的 `runAsNonRoot` 也要求能判断非零 |
| 只读文件系统 + 非 root 才是完整组合 | 单独任一项都不够 |

### 3.3 镜像漏洞扫描

```bash
# Docker Scout（Docker Desktop 集成）
docker scout cves myapp:1.0
docker scout recommendations myapp:1.0

# 或用 Trivy（开源，CI 里常用）
trivy image myapp:1.0
```

| 要点 | 说明 |
|------|------|
| **扫描要进 CI** | 每次构建都扫，而不是出事才扫 |
| 设严重等级阈值 | 如"存在 CRITICAL 则构建失败" |
| 定期重构镜像 | 基础镜像的安全更新需要**重新构建**才能获得（旧镜像不会自动打补丁） |

### 3.4 固定镜像 digest

```dockerfile
FROM python:3.12-slim@sha256:abc123...
```

| 收益 | 代价 |
|------|------|
| ✅ **完全可复现**，tag 被覆盖也不受影响 | 每次安全更新需手工改 digest |
| ✅ 防止供应链攻击中的 tag 篡改 | 需配合自动化更新工具（如 Renovate） |

### 3.5 密钥不进镜像

| ❌ 错误做法 | 为什么危险 |
|------------|-----------|
| `ENV SECRET=xxx` | `docker inspect` 直接可见 |
| `ARG SECRET` + `RUN` 使用 | **`docker history --no-trunc` 可见明文** |
| `COPY .env /app/` | 镜像层里永久保留（即使后来删除） |
| 把私钥 `COPY` 进去再删 | 层里还在 |

| ✅ 正确做法 | 说明 |
|------------|------|
| 运行时环境变量 / `--env-file` | 简单，但 `inspect` 可见（需配合权限控制） |
| **挂载文件 / Docker secret** | 更安全，不进入镜像层 |
| **BuildKit `--mount=type=secret`** | **唯一安全的构建期密钥方案** |

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=pipconf,target=/root/.pip/pip.conf \
    pip install -r requirements.txt
```

```bash
docker build --secret id=pipconf,src=./pip.conf -t myapp .
```

## 四、运行时加固（收益最高的一层）

### 4.1 只读根文件系统

```bash
docker run --read-only \
  --tmpfs /tmp \
  --tmpfs /run \
  -v appdata:/var/lib/app \
  myapp:1.0
```

| 要点 | 说明 |
|------|------|
| `--read-only` | 根文件系统只读，**攻击者无法写入任何持久化文件**（如 webshell、挖矿程序） |
| **必须显式提供可写点** | 用 `--tmpfs` 给临时目录，用 `-v` 给数据目录。否则应用可能因无法写文件而失败 |
| 常见需要可写的路径 | `/tmp`、`/run`、`/var/cache`、应用数据目录 |

> **这是"性价比最高"的一条加固措施**：一条参数就能阻断"写入恶意文件"这一大类攻击链。代价是**需要先确认应用要写哪些路径**（用 `docker diff` 观察）。

### 4.2 削减 Linux 能力（capabilities）

**背景**：Linux 把 root 的特权拆成了几十个 **capability**（能力）。Docker 默认只给容器约 14 个（不是全部）。

> ⚠️ **常见误解**：以为"容器默认没有任何特权"。实际上 **Docker 默认给容器这些能力**：
> `CHOWN`、`DAC_OVERRIDE`、`FSETID`、`FOWNER`、`MKNOD`、`NET_RAW`、`SETGID`、`SETUID`、`SETFCAP`、`SETPCAP`、`NET_BIND_SERVICE`、`SYS_CHROOT`、`KILL`、`AUDIT_WRITE`

**正确的做法是白名单**：

```bash
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE myapp:1.0
```

| 参数 | 作用 |
|------|------|
| `--cap-drop=ALL` | 先全部丢掉 |
| `--cap-add=<需要的能力>` | **只加回确实需要的** |

**几个敏感能力的含义**（这些一旦给了，风险很高）：

| capability | 给了意味着什么 |
|-----------|----------------|
| `SYS_ADMIN` | ⚠️ **几乎等于 root**，可挂载文件系统、操作命名空间。**绝对不要给** |
| `NET_ADMIN` | 可改网络配置、iptables |
| `SYS_PTRACE` | 可调试/注入其他进程（**跨容器逃逸的常见路径**） |
| `SYS_MODULE` | 可加载内核模块 → **直接拿下宿主内核** |
| `DAC_READ_SEARCH` | 可绕过文件读权限 |
| `NET_RAW` | 可构造原始包（**SYN 扫描、ARP 欺骗**） |

```bash
# 查容器实际拥有的能力
docker exec <容器> capsh --print        # 需要 libcap-bin
docker inspect <容器> --format '{{json .HostConfig.CapAdd}} {{json .HostConfig.CapDrop}}'
```

### 4.3 禁止提权：`no-new-privileges`

```bash
docker run --security-opt no-new-privileges:true myapp:1.0
```

| 作用 | 说明 |
|------|------|
| 阻止进程通过 `setuid` 二进制或文件能力**获得新特权** | 例如容器里有个 `setuid root` 的程序，攻击者也无法借它提权 |
| 副作用 | 某些需要 setuid 的程序（如 `sudo`、部分 `ping`）会失效 |

> **这条几乎无成本、收益明确，建议默认开启。** 配合 `--cap-drop=ALL` 形成纵深防御。

### 4.4 `--privileged`：绝对禁用

```bash
docker run --privileged myapp:1.0      # ❌ 生产严禁
```

| `--privileged` 做了什么 | 后果 |
|------------------------|------|
| 给容器**全部** capability | 包含 `SYS_ADMIN` / `SYS_MODULE` |
| 关闭 seccomp / AppArmor 限制 | 内核接口全开放 |
| 挂载宿主设备 | 可直接操作磁盘 |

> **`--privileged` 的容器约等于"宿主机上的 root shell"**。它只应出现在"确实需要操作硬件/内核"的特殊场景（如运行 Docker-in-Docker、加载内核模块的运维工具），且必须在隔离的专用机器上。
>
> **同样的风险也适用于**：`--pid=host`、`--ipc=host`、`--network=host`（三者都削弱隔离）、`-v /var/run/docker.sock:/var/run/docker.sock`（**等于把宿主控制权交出去**）、`-v /:/host`（直接暴露宿主根目录）。

### 4.5 seccomp 与 AppArmor

| 机制 | 作用 | Docker 默认 |
|------|------|-------------|
| **seccomp** | 过滤系统调用：禁止容器调用危险 syscall | ✅ **默认启用**一个白名单 profile（禁用约 40+ 个危险 syscall） |
| **AppArmor**（Ubuntu/Debian） | 限制程序能访问的资源（路径、网络） | ✅ 默认启用 `docker-default` 策略 |
| **SELinux**（RHEL/CentOS） | 强制访问控制 | 按发行版配置 |

```bash
# 使用自定义 seccomp profile
docker run --security-opt seccomp=my-profile.json myapp:1.0

# 查看当前容器用的 seccomp 配置
docker inspect <容器> --format '{{json .HostConfig.SecurityOpt}}'
```

> **注意**：`--privileged` 会**关闭** seccomp 与 AppArmor。这也是它危险的原因之一。
>
> **自定义 seccomp profile 的常见痛点**：一些新语言运行时（如较新的 Go、Node、JIT）会调用默认 profile 未放行的 syscall，导致"不加固能跑、加固后崩"。**排查方式是 `dmesg | grep -i seccomp`**，然后按需白名单化。

### 4.6 用户命名空间（userns-remap）

| 机制 | 效果 |
|------|------|
| 默认行为 | 容器内 UID 1000 = 宿主上 UID 1000 |
| **启用 userns-remap** | 容器内 UID 1000 映射到宿主上一个**高位、无特权**的 UID（如 100000+） |

| 收益 | 代价 |
|------|------|
| ✅ 即使容器内是 root，**在宿主上也没有特权** | ⚠️ 卷的属主管理变复杂（宿主上看到的是映射后的 UID） |
| ✅ 大幅提高逃逸难度 | 需要重建现有容器；部分镜像/卷需调整 |

```json
// /etc/docker/daemon.json
{
  "userns-remap": "default"
}
```

> **权衡说明**：userns-remap 是**很强的加固**（把"容器内 root"降级为"宿主上的普通用户"），但会让卷权限调试变复杂——因为宿主上看到的文件属主是映射 UID。**在已有大量卷的生产环境启用需要评估迁移成本。**

### 4.7 rootless 模式

让 **Docker 守护进程本身**以非 root 用户运行。

| 收益 | 说明 |
|------|------|
| ✅ 即使整个 Docker 被攻破，也不是宿主 root | 根本性提升 |
| ✅ 减少 `docker` 组的特权面 | 组成员不再等于 root |

| 限制 | 说明 |
|------|------|
| 不支持部分功能 | 如 `--privileged`、部分网络驱动 |
| 端口 < 1024 需额外配置 | 需 `setcap` 或反向代理 |
| 性能略有差异 | 网络路径不同 |

## 五、网络与资源加固

### 5.1 网络最小化

| 措施 | 参数 | 效果 |
|------|------|------|
| **完全禁网** | `--network none` | ✅ 阻断数据外泄与反弹 shell（**沙箱必备**） |
| **内部网络** | Compose `internal: true` | 该网络无法访问互联网 |
| **不暴露端口** | 用 `expose` 而非 `ports` | 减少可达入口 |
| **只绑本机** | `-p 127.0.0.1:8080:80` | 避免对整个局域网暴露 |

### 5.2 资源限制（防 DoS）

```bash
docker run -m 512m --cpus=1 --pids-limit=100 myapp:1.0
```

| 限制项 | 防什么 |
|--------|--------|
| `-m` | 内存耗尽（避免拖垮宿主） |
| `--cpus` | CPU 霸占 |
| `--pids-limit` | **fork 炸弹** |
| `--ulimit nofile` | 文件句柄耗尽 |

> **在沙箱场景里，资源限制不只是"运维优化"，而是"安全必需"**：不可信代码可能故意挖矿或耗尽资源。详见 [[docker/沙箱/沙箱安全加固]]。

## 六、宿主机层：最容易忽视的部分

### 6.1 Docker socket 是最高权限入口

| 事实 | 说明 |
|------|------|
| `/var/run/docker.sock` 可控制整个 Docker | 能起特权容器 = **等于宿主 root** |
| **`docker` 组成员 = 特权用户** | 加入组前要评估 |
| **把 socket 挂进容器极其危险** | 该容器可控制宿主上的所有容器 |

```bash
# ❌ 高危：等于把宿主控制权交给这个容器
docker run -v /var/run/docker.sock:/var/run/docker.sock myapp

# 如果确实需要（如 CI 里的构建容器），考虑：
#   - Docker socket 代理（如 tecnativa/docker-socket-proxy），只放行必要 API
#   - rootless Docker
#   - Kaniko / BuildKit 等无需 socket 的构建方案
```

### 6.2 隔离专用节点

| 做法 | 说明 |
|------|------|
| 不可信负载跑在**专用机器/专用节点** | 与核心服务物理隔离 |
| 用更强的隔离运行时 | **gVisor**（用户态内核）、**Kata Containers**（轻量 VM）、**Firecracker**（microVM） |
| 云沙箱服务 | E2B、Modal 等（见 [[agent/harness/Agent沙箱与安全隔离]]） |

## 七、加固检查清单

**可直接用于评审：**

### 镜像层

- [ ] 基础镜像为 `-slim` / `-alpine` / `distroless`
- [ ] 用多阶段构建，构建工具不在运行镜像里
- [ ] `USER` 指定非 root（优选数字 UID）
- [ ] 镜像里无 shell 类工具（或已评估必要性）
- [ ] 无任何密钥（`ENV` / `ARG` / `COPY` 都检查）
- [ ] 已做漏洞扫描，无 CRITICAL/HIGH
- [ ] 固定 tag 或 digest

### 运行时

- [ ] `--read-only` + 显式 `--tmpfs` / `-v` 提供可写点
- [ ] `--cap-drop=ALL` + 按需 `--cap-add`
- [ ] `--security-opt no-new-privileges:true`
- [ ] **未使用** `--privileged`、`--pid=host`、`--ipc=host`
- [ ] **未挂载** `docker.sock`、宿主根目录
- [ ] seccomp / AppArmor 未被禁用

### 网络

- [ ] 仅必要端口暴露，且只绑 `127.0.0.1`（若仅本机需要）
- [ ] 数据层网络设 `internal: true`
- [ ] 不可信负载用 `--network none` 或白名单代理

### 资源

- [ ] 设置了 `-m`、`--cpus`、`--pids-limit`
- [ ] 内存限制配了次数上限的重启策略（避免重启风暴）

### 宿主与审计

- [ ] `docker` 组成员经过审查
- [ ] 容器日志已收集（便于事后审计）
- [ ] 有镜像更新与重建机制（基础镜像的安全补丁需重建才能获得）
- [ ] 不可信负载有额外的隔离层（专用节点 / gVisor / microVM）

## 八、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 认为"容器是安全边界" | 高估隔离强度，出事才醒悟 | 明确容器隔离的局限 |
| 容器内跑 root | 逃逸后权限最大化 | `USER` 非 root + userns-remap |
| `--privileged` 图方便 | 等于交出宿主 | 用 `--cap-add` 精确授权 |
| `--cap-drop=ALL` 但不加需要的 | 应用启动失败 | 用 `capsh --print` 或日志确认缺失能力 |
| `--read-only` 但没给可写点 | 应用崩溃 | 用 `docker diff` 找出需要写的路径 |
| 自定义 seccomp 后应用崩 | syscall 被拒 | `dmesg \| grep seccomp` 排查，按需白名单 |
| 密钥放 `ARG` | `docker history` 可见 | 用 `--mount=type=secret` |
| 镜像扫过就放心 | 旧镜像不会自动获得新补丁 | **定期重建镜像** |
| 挂载 docker.sock 进容器 | 容器可控制宿主 | 用 socket 代理或 rootless |
| userns-remap 直接在生产开 | 卷属主全变，服务异常 | 先在测试环境评估 |
| 只加固容器不管宿主 | 宿主被直接攻击 | 宿主也要打补丁、最小化服务 |

## 小结

| 要点 | 内容 |
|------|------|
| 核心认知 | **容器不是安全边界**。默认隔离防误操作够用，防恶意代码不够 |
| 三类攻击面 | 镜像层（漏洞）、运行时层（配置）、宿主机层（socket/内核） |
| 最高性价比措施 | **非 root 用户**、**`--read-only`**、**`--cap-drop=ALL`**、**`no-new-privileges`**、**资源限制** |
| 默认就有防护 | seccomp 白名单与 AppArmor 默认启用，`--privileged` 会关掉它们 |
| 绝对禁用 | `--privileged`、`--pid=host`、`-v /var/run/docker.sock`、`-v /:/host` |
| 密钥 | `ARG`/`ENV` 都会泄漏进镜像；构建期用 `--mount=type=secret` |
| 宿主层 | `docker` 组 = 特权；考虑 rootless 与 userns-remap |
| 不可信代码 | 需要额外隔离层（专用节点 / gVisor / Kata / microVM） |
