# 数据持久化与备份 · 专题概览

## 专题定位

本专题解决的问题是：**容器里的数据怎么存得不丢、备得下来、迁得走。**

容器的设计前提是"**无状态、可随时替换**"，但现实里总有状态要保存。**这个矛盾就是本专题的全部内容。**

**何时该翻这个专题**

- 要上生产，需要明确"数据放在哪、怎么备份"
- 要换机器/迁移环境，需要把数据搬走
- 数据库要升级版本（如 PG 17 → 18），需要迁移方案
- 曾经误删过容器导致数据丢失
- 需要设计容灾与恢复流程

> ⚠️ **前置提醒**：卷、绑定挂载、tmpfs 的**基础用法**在 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.1-数据卷与绑定挂载]]。本专题讲的是**基于它们的备份与迁移设计**，不重复基础语法。

---

## 一、容器存储的五个层次

先建立全局概念，再谈策略。

| 层次 | 生命周期 | 性能 | 适用 | 备份难度 |
|------|----------|------|------|----------|
| **容器可写层** | 随容器销毁 | 较差（写时复制） | ❌ **不应存任何需要保留的东西** | —— |
| **tmpfs** | 随容器销毁 | 最快（内存） | 临时文件、敏感数据 | 不适用 |
| **具名卷（volume）** | **独立于容器** | 好 | ✅ **生产数据默认选择** | 中（需容器中转） |
| **绑定挂载（bind mount）** | 宿主机目录的生命周期 | 好（Windows/macOS 可能慢） | 开发、配置文件 | **易**（宿主机直接可见） |
| **外部存储**（NFS / 云盘 / CSI） | 独立于主机 | 取决网络 | 多主机共享、K8s | 取决后端 |

### 选择决策

```
数据需要跨主机共享吗？
├── 需要 → 外部存储（NFS / 云块存储 / CSI 驱动）
└── 不需要
    ├── 需要直接在宿主机访问/编辑吗？（配置、开发）
    │   ├── 是 → 绑定挂载
    │   └── 否 → ✅ 具名卷（推荐：Docker 管属主、可移植、有元数据）
    └── 是临时数据吗？ → tmpfs
```

> **关键建议**：**生产环境优先用"具名卷 + 定期备份"，而不是"绑定挂载"**。原因：具名卷由 Docker 管理属主（避免 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.1-数据卷与绑定挂载]] 里的 UID 权限坑），且不与宿主机的目录结构耦合。

## 二、备份的三要素

一个"能用的备份"必须同时满足三点。缺任何一点，备份等于没有。

| 要素 | 含义 | 缺失的后果 |
|------|------|-----------|
| **① 一致性** | 备份是某个时刻的完整、可用状态 | 数据库打包到一半的状态 → 恢复后起不来或数据损坏 |
| **② 可恢复性** | 有明确的、验证过的恢复步骤 | 出事了才发现不知道怎么恢复 |
| **③ 可验证性** | 能定期确认备份是好的 | "以为有备份"但文件是空的/损坏的 |

> **最危险的认知是"我有备份"**。**正确的表述是"我在 X 时间点做过一次恢复演练，恢复耗时 Y 分钟"**。

## 三、两类备份方式

| | **逻辑备份** | **物理备份** |
|---|---|---|
| 做法 | 用数据库工具导出 SQL/命令（`pg_dump`、`mysqldump`、`redis-cli --rdb`） | 直接复制数据文件（打包卷目录） |
| 一致性 | ✅ 天然一致（工具保证） | ⚠️ 需先停服务或确保一致性 |
| 体积 | 通常更小（文本 + 压缩） | 与数据目录等大 |
| 恢复速度 | 慢（要重新执行） | **快**（直接放回去） |
| 跨版本恢复 | ✅ **可跨大版本**（如 PG 16 → 18） | ❌ 通常只能在同版本 |
| 部分恢复 | ✅ 可只恢复某张表 | ❌ 只能整体 |
| 适用 | ✅ **常规备份、迁移、升级** | 大库快速恢复、同版本回滚 |

> **实践结论**：**两者都要做**。逻辑备份保证"能跨版本恢复"，物理备份保证"能快速恢复"。这是生产环境的通行做法。

## 四、卷的备份与恢复

### 4.1 通用方法：临时容器 + tar

```bash
# 备份
docker run --rm \
  -v pgdata:/data \
  -v "$PWD:/backup" \
  alpine \
  tar czf /backup/pgdata-$(date +%Y%m%d-%H%M%S).tar.gz -C /data .

# 恢复
docker volume create pgdata-restored
docker run --rm \
  -v pgdata-restored:/data \
  -v "$PWD:/backup" \
  alpine \
  sh -c "tar xzf /backup/pgdata-20260922-120000.tar.gz -C /data"
```

| 为什么用容器中转 | 说明 |
|------------------|------|
| Windows / macOS 上访问不到 `/var/lib/docker/volumes` | Docker 跑在虚拟机里 |
| ❌ **不该直接操作 Docker 内部目录** | Docker 不感知外部改动，可能状态不一致 |
| 镜像用 `alpine` 最小 | `tar` 是标准工具，自带 |

### 4.2 一致性处理（关键）

**⚠️ 数据库运行中直接 tar 打包，极可能得到不一致的快照。**

| 方案 | 做法 | 代价 |
|------|------|------|
| **方案 A：停服务再打包** | `docker stop <容器>` → tar → `docker start` | 有停机窗口 |
| **方案 B：数据库自身的一致性快照** | PG 用 `pg_basebackup` / `pg_start_backup`；MySQL 用 `FLUSH TABLES WITH READ LOCK` | 需了解具体数据库 |
| **方案 C：用逻辑备份代替** ✅ | `pg_dump` / `mysqldump` 天然一致 | 恢复慢 |
| **方案 D：文件系统快照** | 底层存储支持快照（LVM、ZFS、云盘快照） | 需要存储层支持 |

> **推荐组合**：**方案 C（逻辑备份）做常规 + 方案 A（短暂停机）做定期物理备份**。

### 4.3 备份脚本示例

```bash
#!/usr/bin/env bash
set -euo pipefail

BACKUP_DIR="/backup/pg"
STAMP="$(date +%Y%m%d-%H%M%S)"
CONTAINER="my-postgres"
DB_USER="app"
DB_NAME="appdb"
RETAIN_DAYS=7

mkdir -p "$BACKUP_DIR"

# ① 逻辑备份（一致，可跨版本）
docker exec "$CONTAINER" pg_dump -U "$DB_USER" -d "$DB_NAME" -Fc \
  > "$BACKUP_DIR/logical-$STAMP.dump"

# ② 校验备份非空（避免生成空文件却以为成功）
if [ ! -s "$BACKUP_DIR/logical-$STAMP.dump" ]; then
  echo "ERROR: backup is empty!" >&2
  exit 1
fi

# ③ 清理过期备份
find "$BACKUP_DIR" -name "logical-*.dump" -mtime +"$RETAIN_DAYS" -delete

echo "OK: $BACKUP_DIR/logical-$STAMP.dump ($(du -h "$BACKUP_DIR/logical-$STAMP.dump" | cut -f1))"
```

| 脚本要点 | 为什么 |
|----------|--------|
| `set -euo pipefail` | 任一步失败立即中止，避免产生"半截备份" |
| `-Fc` 自定义格式 | 支持并行恢复与选择性恢复（优于纯文本 SQL） |
| **校验文件非空** | ✅ 这是最容易被忽略、也最关键的一步 |
| 保留策略 | 避免备份把磁盘占满（反而造成故障） |

### 4.4 恢复演练（必做）

```bash
# ① 起一个临时数据库容器
docker run -d --name pg-restore-test \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=test -e POSTGRES_DB=appdb \
  postgres:18

# ② 等它就绪
until docker exec pg-restore-test pg_isready -U app -d appdb; do sleep 1; done

# ③ 恢复
docker exec -i pg-restore-test pg_restore -U app -d appdb --clean --if-exists \
  < /backup/pg/logical-20260922-120000.dump

# ④ 验证数据（关键：不只验证"命令成功"，要验证"数据对"）
docker exec pg-restore-test psql -U app -d appdb -c "SELECT count(*) FROM 关键表;"

# ⑤ 清理
docker rm -f pg-restore-test
```

> **`pg_restore` 到已存在的库时需要 `--clean --if-exists`** 才能真正覆盖。**只验证"命令没报错"是不够的，必须查数据条数或校验和。**

## 五、各数据库的备份命令速查

| 数据库 | 逻辑备份 | 恢复 | 备注 |
|--------|----------|------|------|
| **PostgreSQL** | `pg_dump -Fc -U user -d db > x.dump` | `pg_restore -U user -d db x.dump` | `-Fc` 自定义格式；`--clean --if-exists` |
| PostgreSQL（全库） | `pg_dumpall -U postgres > all.sql` | `psql -U postgres -f all.sql` | 含角色与权限 |
| **MySQL / MariaDB** | `mysqldump --single-transaction -u root -p db > x.sql` | `mysql -u root -p db < x.sql` | `--single-transaction` 保证 InnoDB 一致性 |
| **Redis** | `redis-cli SAVE`（生成 `dump.rdb`）或 `BGSAVE`（后台） | 把 `dump.rdb` 放回数据目录 | 或用 `redis-cli --rdb x.rdb` 远程拉取 |
| **MongoDB** | `mongodump --uri=... --archive=x.archive` | `mongorestore --archive=x.archive` | —— |
| **SQLite** | 直接复制文件（但**须先确保无写入**） | 放回文件 | 或用 `.backup` 命令 |

**PostgreSQL 在容器里的完整示例：**

```bash
# 备份（注意 -Fc）
docker exec my-postgres pg_dump -U app -d appdb -Fc > appdb.dump

# 确认备份可用（列出内容而不恢复）
docker exec -i my-postgres pg_restore -l < appdb.dump

# 恢复到新库
docker exec my-postgres psql -U app -c "CREATE DATABASE appdb_restored;"
docker exec -i my-postgres pg_restore -U app -d appdb_restored < appdb.dump
```

> **`pg_restore -l` 是"只看目录不恢复"**，可以在不产生任何改动的情况下验证备份文件是否可读。**这是低成本验证备份的有效手段。**

## 六、迁移场景

### 6.1 换机器（同版本）

**方案：物理备份 + 卷搬运**

```bash
# 源机器
docker stop my-postgres
docker run --rm -v pgdata:/data -v "$PWD:/backup" alpine \
  tar czf /backup/pgdata.tgz -C /data .
# 把 pgdata.tgz 传走（scp / 网盘）

# 目标机器
docker volume create pgdata
docker run --rm -v pgdata:/data -v "$PWD:/backup" alpine \
  sh -c "tar xzf /backup/pgdata.tgz -C /data"
```

**或：逻辑备份（更稳，推荐）**

```bash
# 源机器
docker exec my-postgres pg_dump -U app -d appdb -Fc > appdb.dump

# 目标机器（新建容器后）
docker exec -i my-postgres-new pg_restore -U app -d appdb --clean --if-exists < appdb.dump
```

### 6.2 大版本升级（如 PG 17 → 18）

| 方式 | 说明 | 推荐度 |
|------|------|--------|
| **逻辑备份 + 恢复** | `pg_dump` → 新版本容器 → `pg_restore` | ✅ **最简单可靠**，适合中小库 |
| `pg_upgrade` | 官方升级工具，需同时在两个版本的数据目录上运行 | 适合大库、停机窗口小 |
| **物理复制数据目录** | ❌ **不可跨大版本** | 禁止 |

> ⚠️ **"直接把旧版本的数据目录挂给新版本容器"是常见错误**：PostgreSQL 的大版本之间数据文件格式不兼容，会直接拒绝启动并报 "database files are incompatible with server"。**必须用 `pg_dump`/`pg_upgrade` 或先完成升级再迁移。**

### 6.3 迁移检查清单

| 检查项 | 说明 |
|--------|------|
| 目标机器上卷已创建 | 否则 Docker 会创建空卷 |
| 目录权限正确 | 数据库用户 UID 匹配（具名卷通常自动处理） |
| 环境变量一致 | 用户名、库名、编码、时区 |
| **字符集与排序规则** | 跨平台迁移时容易出问题 |
| 扩展已安装 | 如 `pgvector`、`pg_trgm`，需在目标库先装 |
| 恢复后验证数据条数与关键查询 | 不只验证"能启动" |
| 应用连接串已更新 | 主机名/端口/密码 |

## 七、跨主机共享存储

当容器需要跨主机访问同一份数据（或需要"容器飘到哪台机器数据都跟得上"）时：

| 方案 | 说明 | 适用 |
|------|------|------|
| **卷驱动 + NFS** | `docker volume create -d local -o type=nfs -o o=addr=... -o device=:/path nfsvol` | 简单共享，性能一般 |
| **云块存储驱动** | 云厂商提供的 Docker 卷插件 | 云环境 |
| **CSI（Container Storage Interface）** | K8s 的标准接口 | ✅ K8s 环境 |
| **分布式文件系统** | Ceph、GlusterFS、JuiceFS | 大规模 |

> ⚠️ **NFS 上的数据库是常见反模式**：NFS 的锁与一致性语义对数据库不友好，可能导致数据损坏。**数据库数据目录不要放 NFS**，除非厂商明确支持。

## 八、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 数据只放容器可写层 | 容器重建即丢 | 必须挂卷 |
| 数据库运行中直接 tar 卷 | 备份不一致，恢复后损坏 | 用 `pg_dump` 等工具，或先停机 |
| 只备份不演练 | 出事时才发现恢复不了 | **定期恢复演练** |
| 不校验备份文件非空 | "有备份"实际是空文件 | 脚本里加非空校验 |
| 备份不设保留策略 | 备份把磁盘占满，反而造成故障 | `find -mtime +N -delete` |
| 跨大版本直接复制数据目录 | 数据库拒绝启动 | 用 `pg_dump` / `pg_upgrade` |
| 数据库数据目录放 NFS | 锁与一致性风险 | 用块存储 |
| 只验证"恢复命令成功" | 数据可能不完整 | 查条数/校验和 |
| 忘了卷里还有 WAL 等辅助文件 | 物理备份不完整 | 物理备份打包整个数据目录 |
| 生产用绑定挂载且 UID 不匹配 | 权限报错 | 具名卷或显式 `chown` |

## 小结

| 要点 | 内容 |
|------|------|
| 存储层次 | 可写层（不用）、tmpfs（临时）、**具名卷（生产默认）**、绑定挂载（开发/配置）、外部存储（跨主机） |
| 备份三要素 | **一致性**、**可恢复性**、**可验证性**（缺一等于没有备份） |
| 两类备份 | 逻辑备份（一致、可跨版本、慢）与物理备份（快、不可跨版本）。**两者都要做** |
| 卷备份 | 临时容器 + `tar`；容器运行时打包有风险，需先停机或用快照 |
| 恢复演练 | 必须做，且要**验证数据**而不只是"命令成功" |
| 升级迁移 | 跨大版本用 `pg_dump`/`pg_upgrade`，**不能直接复制数据目录** |
| 常见反模式 | 数据库数据目录放 NFS；备份不设保留策略；不校验备份非空 |
