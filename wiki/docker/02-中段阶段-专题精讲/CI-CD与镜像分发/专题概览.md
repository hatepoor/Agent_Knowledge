# CI/CD 与镜像分发 · 专题概览

## 专题定位

本专题解决的问题是：**镜像怎么从代码自动变成可部署的产物，以及怎么可靠地分发出去。**

**何时该翻这个专题**

- 手工 `docker build` + `docker push` 太频繁，想自动化
- 不知道该用什么样的镜像 tag 策略
- 需要支持多 CPU 架构（amd64 + arm64）
- 部署要能回滚
- 要建私有仓库（不想依赖公共仓库）
- 需要通过安全合规要求（镜像签名、SBOM）

---

## 一、镜像的完整生命周期

```
① 代码提交
    ↓
② 构建（docker build / buildx）
    ↓
③ 扫描（漏洞、lint）
    ↓
④ 标记（tag：版本号 + 可变标签）
    ↓
⑤ 推送（push 到仓库）
    ↓
⑥ 分发（各环境拉取）
    ↓
⑦ 部署（滚动 / 蓝绿）
    ↓
⑧ 验证与回滚
```

**本专题覆盖 ②~⑧**。核心原则：

> **镜像是一次构建、多处部署的不可变产物。** 同一个镜像从测试环境一路推到生产，**中间不允许重新构建**（否则"测试过的"和"上线的"不是同一个东西）。

## 二、Tag 策略（最容易被忽视的关键设计）

### 2.1 三层标签设计

一个健壮的策略同时使用**三类标签**：

| 类型 | 示例 | 可变性 | 用途 |
|------|------|--------|------|
| **不可变版本标签** | `myapp:1.4.2`、`myapp:v2.0.1` | ❌ 永不复用 | ✅ **部署与回滚的锚点** |
| **Git 关联标签** | `myapp:git-a1b2c3d` | ❌ 不可变 | 溯源：这个镜像对应哪次提交 |
| **可移动环境标签** | `myapp:staging`、`myapp:prod` | ✅ 会移动 | 便于"部署最新通过测试的版本" |
| 追加标签 | `myapp:1.4`、`myapp:1` | 移动 | 便于"用主版本号"（**生产不建议**） |

### 2.2 推荐的打标流程

```bash
IMAGE="registry.example.com/myapp"
VERSION="1.4.2"
GIT_SHA="a1b2c3d"

docker build -t "$IMAGE:$VERSION" -t "$IMAGE:git-$GIT_SHA" .
docker push "$IMAGE:$VERSION"
docker push "$IMAGE:git-$GIT_SHA"

# 只有测试通过后才移动环境标签
docker tag "$IMAGE:$VERSION" "$IMAGE:staging"
docker push "$IMAGE:staging"
```

| 要点 | 说明 |
|------|------|
| **永远不用 `latest` 部署** | 不可复现，无法确定线上跑的是哪个版本 |
| **版本标签不可复用** | 即使构建失败，那个 tag 也不能给下一次用（否则"1.4.2"指向了两个东西） |
| **用 digest 做最终锚定** | 部署时可指定 `myapp@sha256:...`，完全消除 tag 被移动的风险 |

### 2.3 版本号从哪来

| 方式 | 说明 |
|------|------|
| **Git tag 驱动** | `git tag v1.4.2` → CI 读出 tag → 作为镜像版本 |
| **Git SHA** | 每次提交一个唯一标签（适合高频发布） |
| **语义化版本 + 构建号** | `1.4.2-build.37` |
| **日期版本** | `2026.09.22-a1b2c3d` |

```bash
# 在 CI 脚本里取版本
VERSION=$(git describe --tags --always --dirty)
# 若用 tag 驱动发布
VERSION=${GITHUB_REF_NAME#v}          # 从 refs/tags/v1.4.2 去掉 v
```

## 三、多平台构建

### 3.1 为什么需要

| 场景 | 说明 |
|------|------|
| Apple 芯片开发、Linux amd64 部署 | 构建机是 arm64，生产是 amd64 |
| 混合架构集群 | 部分节点是 arm64 |
| 边缘设备 | 常为 arm 架构 |

**不做多平台会遇到什么**：在 Mac 上构建的镜像推到 amd64 服务器上，运行时出现 `exec format error`（见 [[docker/01-入门阶段-基础教程/第00章-学前准备/0.4-看懂报错信息]]）。

### 3.2 `buildx` 用法

```bash
# ① 创建并使用一个多平台 builder
docker buildx create --name multiplatform --use --bootstrap

# ② 构建并直接推送（多平台构建通常必须推送，因为本地无法加载多架构镜像）
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t registry.example.com/myapp:1.4.2 \
  --push \
  .

# ③ 查看镜像支持的平台
docker buildx imagetools inspect registry.example.com/myapp:1.4.2
```

| 要点 | 说明 |
|------|------|
| `--push` 而非 `--load` | ⚠️ **多平台构建无法 `--load` 到本地**（本地镜像库只存单一架构） |
| `--platform` 可与 Dockerfile 的 `FROM --platform=$TARGETPLATFORM` 配合 | 让基础镜像也选对架构 |
| **构建速度** | 多平台会串行或用多个 builder 实例，明显更慢 |

### 3.3 Dockerfile 里的多平台处理

```dockerfile
# 声明参数（BuildKit 自动注入）
ARG TARGETPLATFORM
ARG BUILDPLATFORM

FROM --platform=$BUILDPLATFORM golang:1.23 AS builder
ARG TARGETOS
ARG TARGETARCH
WORKDIR /src
COPY . .
# 交叉编译：构建机架构 ≠ 目标架构
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build -o /app/server .

FROM alpine:3.21
COPY --from=builder /app/server /usr/local/bin/server
ENTRYPOINT ["server"]
```

| 技巧 | 说明 |
|------|------|
| `FROM --platform=$BUILDPLATFORM` | **构建阶段用构建机的架构**（避免 QEMU 模拟，快很多） |
| `GOARCH=$TARGETARCH` | 交叉编译出目标架构的二进制 |
| 需要模拟时（如 Python 的 C 扩展） | BuildKit 会用 QEMU，**速度明显变慢** |

> **一条实用建议**：**优先用"交叉编译"而不是"模拟执行"**。Go/Rust 等支持交叉编译的语言可以 `FROM --platform=$BUILDPLATFORM` 加速；Python/Node 这类需要运行构建脚本的语言则无法避免 QEMU 模拟，**多平台构建会慢数倍**。

## 四、CI 中的构建缓存

**没有缓存复用的 CI 构建是最浪费时间的环节之一**（每次重装依赖）。

### 4.1 两种缓存策略

| 策略 | 机制 | 优缺点 |
|------|------|--------|
| **仓库内缓存**（`--cache-from` / `--cache-to`） | 把构建缓存作为镜像层推到仓库的独立 tag | ✅ 简单；⚠️ 缓存导出/导入耗时 |
| **CI 平台缓存** | 用 CI 自己的缓存卷（如 Actions 的 `cache`） | ✅ 快；⚠️ 依赖平台，跨 runner 可能失效 |

### 4.2 `buildx` 的缓存导出/导入

```bash
docker buildx build \
  --platform linux/amd64 \
  --cache-from type=registry,ref=registry.example.com/myapp:buildcache \
  --cache-to   type=registry,ref=registry.example.com/myapp:buildcache,mode=max \
  -t registry.example.com/myapp:1.4.2 \
  --push \
  .
```

| 参数 | 说明 |
|------|------|
| `--cache-from` | 从仓库拉取缓存 |
| `--cache-to` | 把缓存推回仓库 |
| **`mode=max`** | 缓存**所有中间阶段**（多阶段构建时必要）。默认 `mode=min` 只缓存最终阶段用到的层 |

> ⚠️ **忘了 `mode=max`** 是多阶段构建缓存的经典坑：构建阶段（builder）的层不会被缓存，导致每次都要重新编译。

### 4.3 GitHub Actions 完整示例

```yaml
name: build-and-push

on:
  push:
    branches: [main]
    tags: ["v*"]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
      id-token: write          # 用于签名

    steps:
      - uses: actions/checkout@v4

      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (tags & labels)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=semver,pattern={{version}}
            type=sha,prefix=git-
            type=ref,event=branch

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          provenance: true
          sbom: true

      - name: Scan for vulnerabilities
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}@${{ steps.build.outputs.digest }}
          severity: "CRITICAL,HIGH"
          exit-code: "1"          # 发现严重漏洞则失败
```

| 步骤 | 作用 |
|------|------|
| `setup-buildx-action` | 提供 buildx（多平台与缓存能力） |
| `metadata-action` | **自动生成标准 tags 与 labels**（不用手写脚本） |
| `cache-from/to: type=gha` | 用 GitHub Actions 的缓存后端 |
| `provenance` / `sbom` | 生成**来源证明**与**软件物料清单**（供应链安全） |
| Trivy + `exit-code: 1` | **把漏洞扫描变成门禁** |

### 4.4 GitLab CI 示例

```yaml
stages: [build, scan, deploy]

variables:
  IMAGE: $CI_REGISTRY_IMAGE

build:
  stage: build
  image: docker:27
  services: [docker:27-dind]
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin $CI_REGISTRY
  script:
    - docker buildx create --use --name ci || true
    - |
      docker buildx build \
        --platform linux/amd64,linux/arm64 \
        --cache-from type=registry,ref=$IMAGE:buildcache \
        --cache-to   type=registry,ref=$IMAGE:buildcache,mode=max \
        -t $IMAGE:$CI_COMMIT_SHORT_SHA \
        -t $IMAGE:staging \
        --push .

scan:
  stage: scan
  image: aquasec/trivy:latest
  script:
    - trivy image --exit-code 1 --severity CRITICAL,HIGH "$IMAGE:$CI_COMMIT_SHORT_SHA"

deploy:
  stage: deploy
  script:
    - ./deploy.sh "$IMAGE:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

## 五、私有仓库与分发

### 5.1 仓库选型

| 方案 | 说明 | 适用 |
|------|------|------|
| **Harbor** | CNCF 开源，含 RBAC、漏洞扫描、镜像复制、保留策略 | ✅ **自建首选** |
| **云厂商 CR** | 阿里云 ACR、腾讯云 TCR、AWS ECR、GCR | ✅ 云环境 |
| **`registry:2`** | Docker 官方最简仓库 | 本地测试 |
| **GitHub/GitLab 内置** | GHCR、GitLab Registry | 与代码托管同平台时方便 |

### 5.2 本地起一个最简仓库（用于测试）

```yaml
services:
  registry:
    image: registry:2
    ports:
      - "127.0.0.1:5000:5000"
    environment:
      REGISTRY_STORAGE_DELETE_ENABLED: "true"      # 允许删除镜像
    volumes:
      - registry-data:/var/lib/registry
    restart: unless-stopped

volumes:
  registry-data:
```

```bash
docker tag myapp:1.4.2 localhost:5000/myapp:1.4.2
docker push localhost:5000/myapp:1.4.2
docker pull localhost:5000/myapp:1.4.2
```

| 要点 | 说明 |
|------|------|
| **镜像名前必须带仓库主机名** | 推送前先 `docker tag` 成 `主机:端口/名字` 格式（见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.1-镜像的获取与管理]]） |
| **本地仓库默认不加密、不认证** | 只用于测试；生产必须上 Harbor 或云 CR |
| 需要给 Docker 配 insecure-registries | 用 HTTP 时要在 `daemon.json` 里声明 |

### 5.3 部署时的分发策略

| 策略 | 说明 |
|------|------|
| **按需拉取**（默认） | 部署时各机器自己 `pull` |
| **预拉取** | 发布前先把镜像拉到目标机器，减少切换窗口 |
| **离线导入** | `save` → 传输 → `load`（无网络环境） |
| **P2P 分发** | 大规模集群时（dragonfly 等） |

## 六、供应链安全

**镜像从构建到部署中间有多个可被篡改的环节。** 现代实践要求三件事：

| 机制 | 作用 | 工具 |
|------|------|------|
| **SBOM（软件物料清单）** | 列出镜像里所有组件与版本 | `docker buildx --sbom`、Syft |
| **Provenance（来源证明）** | 证明"这个镜像由哪次构建、从哪个提交产生" | `buildx --provenance` |
| **签名** | 证明镜像未被篡改、来源可信 | **Cosign**（sigstore）、Notation |

```bash
# 生成 SBOM 与 provenance（buildx 一键）
docker buildx build --sbom=true --provenance=true -t myapp:1.4.2 --push .

# 用 cosign 签名（密钥模式）
cosign sign --key cosign.key registry.example.com/myapp:1.4.2
# 或用无密钥模式（基于 OIDC 身份）
cosign sign registry.example.com/myapp:1.4.2

# 部署前验证签名
cosign verify --key cosign.pub registry.example.com/myapp:1.4.2
```

| 补充措施 | 说明 |
|----------|------|
| **固定基础镜像 digest** | 防止基础镜像被换掉（供应链攻击常见手法） |
| **依赖锁定** | `requirements.txt` 用 hash 锁定、`package-lock.json` |
| **扫描进 CI** | 门禁化，不是可选项 |
| **最小化基础镜像** | 组件越少，漏洞面越小（见 [[docker/02-中段阶段-专题精讲/镜像优化与瘦身/专题概览]]） |

## 七、部署与回滚

### 7.1 三种部署策略

| 策略 | 做法 | 停机 | 回滚难度 | 适用 |
|------|------|------|----------|------|
| **重建（recreate）** | `docker compose up -d` 重建容器 | ⚠️ 有短暂停机 | 易（换回旧 tag） | 单机、可接受秒级停机 |
| **滚动更新（rolling）** | 逐批替换副本 | ✅ 无 | 中 | 多副本 |
| **蓝绿（blue-green）** | 起一套新的，验证后切流量 | ✅ 无 | **易（切回）** | 需要快速回滚 |
| **金丝雀（canary）** | 小比例流量到新版本，观察后放量 | ✅ 无 | 易 | 风险敏感的变更 |

### 7.2 Compose 下的滚动更新

Compose 支持有限的滚动更新（需配 `deploy` 相关字段，且行为随版本演进）：

```yaml
services:
  app:
    image: registry.example.com/myapp:1.4.2
    deploy:
      replicas: 3
      update_config:
        order: start-first          # 先起新的再停旧的
        parallelism: 1
        delay: 10s
      rollback_config:
        order: stop-first
```

```bash
docker compose up -d --no-deps app
```

> ⚠️ **Compose 的滚动更新能力有限**：它没有完善的健康门控与自动回滚。**如果滚动更新是硬需求，这是考虑 K8s 的合理信号。**

### 7.3 蓝绿部署（Compose 下的实用做法）

**思路**：用两套服务 + 一个反向代理（或只切镜像 tag）。

```yaml
services:
  proxy:
    image: nginx:1.27-alpine
    ports: ["80:80"]
    volumes: ["./nginx.conf:/etc/nginx/nginx.conf:ro"]

  app-blue:
    image: registry.example.com/myapp:1.4.1
    expose: ["8000"]

  app-green:
    image: registry.example.com/myapp:1.4.2
    expose: ["8000"]
    profiles: ["green"]          # 默认不启动
```

```bash
# ① 起绿组
docker compose --profile green up -d app-green
# ② 验证绿组（直接从 proxy 容器内 curl，不切流量）
docker compose exec proxy curl -s http://app-green:8000/health
# ③ 改 nginx.conf 把上游指向 app-green，reload
docker compose exec proxy nginx -s reload
# ④ 观察一段时间，确认无异常
# ⑤ 下线蓝组
docker compose stop app-blue
```

### 7.4 回滚

```bash
# 最快回滚：把镜像 tag 换回上一个版本并重建
sed -i 's/myapp:1.4.2/myapp:1.4.1/' compose.yaml
docker compose up -d app

# 更严格的做法：部署时记录 digest，回滚用 digest
docker compose exec app cat /proc/1/environ | tr '\0' '\n' | grep IMAGE
```

| 回滚要点 | 说明 |
|----------|------|
| **回滚必须能在分钟级完成** | 所以**旧镜像不能被删**（保留策略要留出回滚窗口） |
| **数据库变更要向前兼容** | 否则回滚应用时数据库结构已经不兼容 |
| 记录"部署了什么" | 用 digest 记录，而不是 tag |

> ⚠️ **回滚最容易被忽略的障碍是数据库迁移**：如果 1.4.2 加了一个字段并让应用依赖它，回滚到 1.4.1 时数据库里已经有这个字段（通常没问题）；但**如果 1.4.2 删了字段，回滚就会失败**。
>
> **实践原则：数据库变更要"向前兼容 + 分两步发布"**（先加字段并双写，下个版本再删旧字段）。

## 八、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|----------|------|----------|
| 用 `latest` 部署 | 无法确定线上版本，无法精确回滚 | 用不可变版本标签或 digest |
| 版本标签复用 | 同一个 tag 指向两个不同的镜像 | 失败就换新版本号 |
| 每个环境各构建一次 | "测试过的"和"上线的"不是同一个镜像 | **一次构建、多次部署** |
| 多平台构建忘 `--push` | 报错或只产出单平台 | 多平台必须 `--push` |
| CI 缓存忘 `mode=max` | 多阶段构建每次都重编译 | `--cache-to ...,mode=max` |
| 私有仓库推送前没 `tag` | 推到了错误的仓库或失败 | tag 成 `主机:端口/名字` 格式 |
| 扫描不设 `exit-code` | 有严重漏洞也照样发布 | 门禁化（`exit-code: 1`） |
| 基础镜像不固定 digest | 供应链攻击可行 | 固定 digest + 自动化更新 |
| 回滚时发现镜像被清理了 | 无法回滚 | 保留策略留出回滚窗口（如保留近 10 个版本） |
| 数据库变更不兼容回滚 | 回滚应用后服务异常 | 分两步发布，保证向前兼容 |
| 用 Compose 做滚动更新指望自动回滚 | 做不到 | 承认边界，或上 K8s |
| CI 的 registry 凭据硬编码 | 泄露 | 用 CI 的 secret 机制 |

## 小结

| 要点 | 内容 |
|------|------|
| 核心原则 | **一次构建、多处部署**；镜像不可变；不用 `latest` |
| Tag 策略 | 不可变版本标签（部署锚点）+ Git SHA（溯源）+ 可移动环境标签（便捷）；最严格用 digest |
| 多平台 | `buildx --platform ... --push`；**多平台无法 `--load`**；优先交叉编译而非 QEMU 模拟 |
| 缓存 | `--cache-from` / `--cache-to`，**多阶段必须 `mode=max`** |
| 私有仓库 | 自建首选 **Harbor**；`registry:2` 仅用于测试 |
| 供应链 | SBOM + provenance + **签名（Cosign）** + 固定基础镜像 digest + 扫描门禁 |
| 部署策略 | 重建（简单）、滚动（多副本）、**蓝绿（易回滚）**、金丝雀 |
| 回滚 | 必须分钟级；**保留旧镜像**；**数据库变更要向前兼容** |
