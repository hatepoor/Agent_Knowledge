# 镜像优化与瘦身 · 专题概览

## 专题定位

本专题解决的问题是：**镜像太大、构建太慢、拉取太久。**

这三件事看起来是三个问题，实际同源：**镜像的层结构**。理解层，就能同时解决三者。

**何时该翻这个专题**

- 镜像体积超过预期（比如一个 Python 应用打到 1 GB 以上）
- 部署时拉取镜像耗时明显（带宽受限或环境多）
- 每次构建都要几分钟，开发迭代很慢
- 磁盘上镜像层占了大量空间
- 基础镜像有已知 CVE，需要换成更小的发行版

---

## 一、先量化：大在哪里

**优化之前必须先测量。** 凭感觉"应该能瘦"通常会改错方向。

### 1.1 `docker history`：逐层看体积

```bash
docker history myapp:1.0
docker history myapp:1.0 --no-trunc --format "table {{.Size}}\t{{.CreatedBy}}" | head -20
```

| 观察 | 结论 |
|------|------|
| 某一层特别大 | 那一层对应的指令是优化主目标 |
| `RUN apt-get install` 层大 | 装了不必要的包，或缺 `--no-install-recommends` |
| `RUN pip install` 层大 | 缺 `--no-cache-dir`，或装了编译工具 |
| 基础镜像自己的层就很大（几百 MB） | ⚠️ **换基础镜像是第一优先级** |

> ⚠️ **`SIZE` 是"层大小"而非"净增量"**。一个 `RUN rm -rf /data` 的层可能显示 `0B`，但被删的数据仍在**上一层**里。所以看到"某层很小"不代表那部分没占空间。

### 1.2 `dive`：交互式分析（推荐）

```bash
# 安装后用
dive myapp:1.0
```

`dive` 提供两个视图：

| 视图 | 作用 |
|------|------|
| **层视图** | 每层的大小与指令，左侧显示 |
| **文件树视图** | 每层具体增删了哪些文件，右侧显示 |

**它最有价值的输出是"浪费的层"**：`dive` 会用一个百分比估算 **镜像效率**（多少空间是真正被需要的）。效率低于 90% 说明有明显浪费。

| 典型信号 | 含义 |
|----------|------|
| 某层里出现 `/usr/share/doc`、`/usr/share/man` | 文档没清理 |
| 出现包管理器缓存（`/var/cache/apt`、`~/.cache/pip`） | 缓存进了镜像 |
| 出现编译工具（`gcc`、`make`） | 应该用多阶段构建剥离 |
| 出现 `.git`、测试文件 | `.dockerignore` 缺失 |

### 1.3 体积与构建时间的两个指标

| 指标 | 怎么量 |
|------|--------|
| 镜像体积 | `docker images myapp` |
| 构建时间 | `time docker build --no-cache -t t .` |

**建议把这两个数字记下来作为基线**，否则优化效果无法验证。

## 二、六个优化手段（按收益排序）

### 手段 1：换基础镜像（收益最大）

**通常是单步收益最大的一招。**

| 基础镜像 | 体积量级 | 说明 |
|----------|----------|------|
| `debian:12` | ~120 MB | 完整 Debian |
| `python:3.12` | ~1 GB | Debian + Python + 编译器 + 文档 |
| `python:3.12-slim` | ~150 MB | 精简 Debian + Python，**无编译器** |
| `python:3.12-alpine` | ~50 MB | Alpine + Python，**无 bash、用 musl** |
| `gcr.io/distroless/python3` | ~50 MB | **无 shell、无包管理器** |
| `scratch` | 0 | 完全空，需放静态二进制 |

| 选型决策 | 建议 |
|----------|------|
| 默认选择 | `-slim`（体积与兼容性平衡最好） |
| 需要极小体积且能承受兼容问题 | `-alpine`（注意 `musl` 与 `glibc` 差异，某些二进制不兼容） |
| 安全要求高、能接受无法调试 | `distroless` |
| 静态编译的语言（Go/Rust） | 构建阶段 + `scratch` 或 `distroless` |

> **权衡提醒**：`alpine` 不是"无脑更优"。它的 `musl libc` 与主流 `glibc` 有差异，某些预编译的 Python wheel、JVM 特性、glibc 相关的二进制会有问题。**"能跑通"优先于"体积最小"。**
>
> `distroless` / `scratch` 的代价是**没有 shell**，出问题时 `docker exec` 进不去。**建议保留一个基于 alpine 的调试目标**，用 `--target` 构建：
> ```bash
> docker build --target debug -t myapp:debug .
> ```

### 手段 2：多阶段构建

把"构建工具"与"运行产物"分开，构建阶段的一切都不进最终镜像。

```dockerfile
FROM golang:1.23 AS builder
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app/server .

FROM alpine:3.21
COPY --from=builder /app/server /usr/local/bin/server
ENTRYPOINT ["server"]
```

| 收益 | 说明 |
|------|------|
| 体积 | 几百 MB → 几十 MB（视语言） |
| **安全** | 镜像里没有编译器（攻击者可利用的工具少了一大类） |
| 构建缓存 | 构建阶段的缓存可复用于开发环境 |

语法详见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.3-多阶段构建与最佳实践]]。

### 手段 3：合并 RUN，同层清理

**原理**：层是只读的，"删除"只是在新层做标记，底层数据仍在。

```dockerfile
# ❌ 无效：删除发生在不同层
RUN apt-get update && apt-get install -y build-essential
RUN apt-get purge -y build-essential

# ✅ 有效：装与删在同一层
RUN apt-get update && \
    apt-get install -y --no-install-recommends build-essential && \
    make && make install && \
    apt-get purge -y --auto-remove build-essential && \
    rm -rf /var/lib/apt/lists/*
```

**必加的三个"清理"动作：**

| 包管理器 | 清理命令 | 常见体积 |
|----------|----------|----------|
| apt | `rm -rf /var/lib/apt/lists/*` | 几十 MB |
| pip | `pip install --no-cache-dir` | 几十 MB |
| npm | `npm ci --omit=dev` + `npm cache clean --force` | 上百 MB |
| apk | `apk add --no-cache` | 小但值得 |
| yum/dnf | `yum clean all` | 几十 MB |

> **`--no-install-recommends`（apt）值得单独强调**：不加它，装 `curl` 可能连带装上几十个"推荐包"。实测经常能省 30-50%。

### 手段 4：`.dockerignore`

不做会导致上下文膨胀与缓存频繁失效。

```
.git
.env
.env.*
__pycache__
*.pyc
.venv
node_modules
*.log
data/
tests/
docs/
```

见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.2-构建过程与分层缓存]]。

### 手段 5：削减依赖本身

| 做法 | 收益 |
|------|------|
| 生产环境只装运行期依赖 | `npm ci --omit=dev`、Python 拆分 `requirements.txt` / `requirements-dev.txt` |
| 用静态编译产物 | Go/Rust 可产出不依赖系统库的二进制 |
| 换更轻的替代库 | 如 `psycopg[binary]` 而非从源码编译 `psycopg` |
| 移除开发工具 | 镜像里不需要 `vim`、`curl`、`git`（除非确实需要） |

> ⚠️ **一个常见反例**：为了"方便排查"而在生产镜像里装 `curl`、`vim`、`tcpdump`。这会显著增大体积**并扩大攻击面**。**正确做法是"排查时临时起一个带工具的容器"**，而不是把它们装进生产镜像：
> ```bash
> docker run --rm -it --network container:<目标容器> nicolaka/netshoot
> ```

### 手段 6：层压缩与 squash

| 手段 | 做法 | 收益/代价 |
|------|------|-----------|
| **启用 zstd 压缩** | 在 `daemon.json` 里设 `"features": {"containerd-snapshotter": true}` 并配置压缩 | 拉取更快、磁盘更小；需较新版本支持 |
| **`--squash`** | `docker build --squash` 把所有层压成一层 | 体积减小；⚠️ **丢失层缓存与共享能力**，后续构建变慢 |
| **`docker-slim`** | 第三方工具，通过分析运行时行为自动裁剪 | 效果好但需验证；对动态语言有风险 |

> **关于 `--squash` 的权衡**：它牺牲了"层共享"这个 Docker 的核心优势。10 个基于同一基础镜像的 squash 镜像会各占一份基础层。**只在"体积比构建速度更重要"时使用。**

## 三、构建速度优化

体积之外，构建速度直接影响开发体验。

| 手段 | 做法 | 效果 |
|------|------|------|
| **依赖清单先复制** | `COPY requirements.txt` → `RUN install` → `COPY . .` | 改代码不重装依赖（收益最大） |
| **BuildKit 缓存挂载** | `RUN --mount=type=cache,target=/root/.cache/pip pip install -r req.txt` | 依赖增量安装，跨构建复用 |
| **并行构建** | BuildKit 自动并行独立分支 | 多阶段构建时明显 |
| **`--target` 构建调试阶段** | 只构建需要的阶段 | 迭代时更快 |
| **多平台构建用 buildx** | `docker buildx build --platform linux/amd64,linux/arm64` | 一次产出多架构（见 [[docker/02-中段阶段-专题精讲/CI-CD与镜像分发/专题概览]]） |

**缓存挂载示例（Python）：**

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
COPY . .
```

**apt 的缓存挂载（注意加锁）：**

```dockerfile
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends curl
```

> **`sharing=locked` 为什么必要**：apt 的缓存目录在多构建并发时会冲突。加锁避免竞态失败。这是 CI 环境里常见的坑。

## 四、拉取速度优化

体积小了，拉取自然快。此外还有：

| 手段 | 说明 | 注意 |
|------|------|------|
| **就近仓库** | 用地域接近的镜像仓库（私有 Harbor、云厂商 CR） | 生产应自建，避免依赖公共加速器 |
| **镜像预热** | 在部署前先把镜像拉到目标机器 | 减少发布时的等待窗口 |
| **只传增量层** | 层可共享，只有变化的层需要传输 | 所以"减小层数"很重要 |
| **P2P 分发** | 如 dragonfly、kraken | 大规模集群时才值得 |
| **固定基础镜像 digest** | 避免不同机器拉到不同版本导致层不一致 | 见 [[docker/02-中段阶段-专题精讲/CI-CD与镜像分发/专题概览]] |

## 五、实战：把 Python 镜像从 1.1 GB 压到 150 MB

**起点（常见的新手写法）：**

```dockerfile
FROM python:3.12
COPY . .
RUN pip install -r requirements.txt
CMD ["python","app.py"]
```

| 步骤 | 改动 | 体积 |
|------|------|------|
| 0 | 起点 | ~1.1 GB |
| 1 | `FROM python:3.12-slim` | ~420 MB |
| 2 | 加 `.dockerignore`（排除 `.git`、`.venv`、`__pycache__`） | ~350 MB |
| 3 | 依赖清单先复制；`pip install --no-cache-dir` | ~280 MB |
| 4 | 需要编译的包改用多阶段构建（构建阶段装 `build-essential`、`libpq-dev`，运行阶段只装 `libpq5`） | ~170 MB |
| 5 | 加缓存挂载 `--mount=type=cache,target=/root/.cache/pip` | ~170 MB（但构建时间显著缩短） |
| 6 | 切非 root 用户、加 `HEALTHCHECK`（不改变体积，提升安全与可观测性） | ~170 MB |

**关键收益来源排序**（按本案例）：换 slim > 多阶段剥离编译工具 > 清理缓存与上下文 > 其他。

> **注意最后一步没有减体积**：优化不等于"只盯着体积"。**安全与可观测性同样属于"镜像质量"**，只是不体现在 MB 上。

## 六、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 凭感觉优化，不先 `dive`/`history` | 改错目标，收益很小 | **先测量** |
| 用 `alpine` 求最小 | `musl` 兼容问题，某些包装不上或运行异常 | 优先 `slim`；用 alpine 要验证功能 |
| 用 `distroless` 后无法排查 | 出故障时 `exec` 进不去 | 保留一个 alpine 的调试 target |
| `RUN install` 与 `RUN remove` 分开 | 体积不变 | 同层清理 |
| 用 `--squash` 解决一切 | 丢失层共享与缓存 | 只在必要时用 |
| 为了排查把 `curl`/`vim` 装进生产镜像 | 体积增大 + 攻击面扩大 | 临时起 netshoot 容器 |
| 只优化体积，不动构建顺序 | 开发迭代依然慢 | 依赖清单先复制 + 缓存挂载 |
| 在多平台构建中假设层可共享 | 不同架构的层不通用 | 分别构建、分别缓存 |
| 依赖公共镜像加速器做生产分发 | 可用性与可信度风险 | 自建私有仓库 |

## 小结

| 要点 | 内容 |
|------|------|
| 先测量 | `docker history` 找"最大层"，`dive` 找"浪费的文件" |
| 收益排序 | 换基础镜像 > 多阶段构建 > 同层清理 > `.dockerignore` > 削减依赖 > 压缩 |
| 同层原则 | "装"与"删"必须在同一条 `RUN` 里 |
| 必加清理 | apt 清 `/var/lib/apt/lists/*`、pip 用 `--no-cache-dir`、npm 用 `--omit=dev` |
| 速度优化 | 依赖清单先复制 + BuildKit 缓存挂载（apt 记得 `sharing=locked`） |
| 安全代价 | 更小的基础镜像同时减少攻击面；但 `distroless`/`scratch` 会失去调试能力 |
| 不要跑偏 | 优化不只看 MB——非 root 用户、健康检查同样属于镜像质量 |
