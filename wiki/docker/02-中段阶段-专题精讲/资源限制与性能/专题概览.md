# 资源限制与性能 · 专题概览

## 专题定位

本专题解决的问题是：**限制为什么没生效、容器为什么变慢、限制值该设多少。**

入门阶段的 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.1-资源限制]] 回答了"**怎么设限制**"。本专题回答"**限制是怎么实现的、为什么行为与直觉不符、如何诊断与定容**"。

**何时该翻这个专题**

- 设了限制但容器仍吃满宿主机
- 容器没被杀但明显变慢（怀疑限流）
- 容器"莫名其妙"被 OOM 杀掉
- 需要为服务确定合理的内存/CPU 限额（容量规划）
- 同一台机器上多个服务互相干扰

---

## 一、底层原理：cgroup

**Docker 的资源限制不是 Docker 自己实现的**，而是把参数写进 Linux 内核的 **cgroup（control group，控制组）**。

### 1.1 cgroup 的职责与不是它的职责

| 机制 | 负责 | 不负责 |
|------|------|--------|
| **namespace** | **隔离**：进程能"看到"什么 | 不限制用量 |
| **cgroup** | **限制**：进程能"用"多少 | 不隔离可见性 |

> **两者是正交的**：namespace 让容器看不见别的容器，cgroup 让容器用不超配额。**说"容器靠 cgroup 隔离"是不准确的。**

### 1.2 cgroup v1 与 v2

| | cgroup v1 | cgroup v2 |
|---|---|---|
| 层级结构 | **每种资源一棵独立的树**（memory、cpu、blkio 各一棵） | **统一的一棵树** |
| 内存硬限制文件 | `/sys/fs/cgroup/memory/memory.limit_in_bytes` | `/sys/fs/cgroup/memory.max` |
| 内存软限制 | `memory.soft_limit_in_bytes` | `memory.high` |
| 现代系统默认 | 旧系统 | ✅ **现代发行版与 Docker 默认** |

```bash
docker info | grep -i cgroup
# Cgroup Version: 2
```

**为什么要知道版本**：写监控脚本、读 cgroup 文件、排查限制问题时要选对路径。

### 1.3 关键 cgroup 文件（cgroup v2）

| 文件 | 含义 | 对应参数 |
|------|------|----------|
| `memory.max` | 内存硬上限 | `-m` |
| `memory.high` | 内存软上限（超过会被限速回收，不杀进程） | `--memory-reservation` |
| `memory.current` | 当前用量（**含 page cache**） | —— |
| `memory.swap.max` | swap 上限 | `--memory-swap` |
| `memory.events` | OOM 事件计数（含 `oom_kill`） | —— |
| `cpu.max` | CPU 带宽（`quota period`） | `--cpus` |
| `cpu.stat` | **限流统计**（`nr_throttled`、`throttled_usec`） | —— |
| `cpuset.cpus` | 绑定的 CPU 核 | `--cpuset-cpus` |
| `pids.max` / `pids.current` | 进程数限额与当前值 | `--pids-limit` |

```bash
# 直接读容器内的 cgroup 文件（绕过所有抽象）
docker exec <容器> cat /sys/fs/cgroup/memory.max
docker exec <容器> cat /sys/fs/cgroup/cpu.max
docker exec <容器> cat /sys/fs/cgroup/cpu.stat
```

## 二、内存：比直觉复杂

### 2.1 哪些内存算进配额

**关键事实**：容器的内存用量**不只是应用自己 malloc 的内存**，还包括：

| 组成 | 说明 | 是否计入 `-m` |
|------|------|---------------|
| 进程匿名内存（堆、栈） | 应用实际分配的内存 | ✅ 计入 |
| **Page cache** | 进程读写文件产生的缓存 | ✅ **计入**（易被误解的元凶） |
| 内核对象（socket 缓冲、内核栈） | —— | ✅ 计入 |
| 共享内存（`/dev/shm`） | 默认 64 MB | ✅ 计入 |
| **tmpfs 挂载的内容** | 内存文件系统 | ✅ **计入** |

> ⚠️ **"容器内存超了但我程序只用了 100 MB" 的典型原因**：
> - 程序大量读写文件 → **page cache 涨到限额** → 触发回收
> - `/dev/shm` 或 `tmpfs` 里写了大量数据
> - 应用是多线程/多进程，RSS 分散

**查看细分：**

```bash
docker exec <容器> cat /sys/fs/cgroup/memory.stat
# anon        ← 匿名内存（真正"堆"）
# file        ← page cache
# shmem       ← tmpfs / shm
```

| 字段 | 含义 | 归因 |
|------|------|------|
| `anon` 大 | 应用分配的多 | 查内存泄漏 |
| `file` 大 | 文件缓存 | 通常无害（可被回收），但会挤占配额 |
| `shmem` 大 | tmpfs/shm 用量 | 查 `/dev/shm` 与 `--tmpfs` |

### 2.2 page cache 的可回收性（为什么有时候不会被杀）

| 情况 | 行为 |
|------|------|
| page cache 占满配额 | 内核**优先回收** cache（丢弃缓存页），不杀进程 |
| 回收后仍不足（anon 内存也接近上限） | **才触发 OOM Killer** |
| 这解释了什么 | "容器内存显示 100% 但没被杀"——因为都是可回收的 cache |

> **`docker stats` 的 `MEM USAGE` 包含 page cache**，所以它可能显示得比"应用实际占用"高。判断是否真危险要看 `anon` 的值。

### 2.3 OOM 的行为与诊断

```bash
# 判据
docker inspect <容器> --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
docker exec <容器> cat /sys/fs/cgroup/memory.events
# oom      3        ← 触发 OOM 的次数
# oom_kill 2        ← 实际杀掉进程的次数

# 宿主侧的内核日志
dmesg | grep -i "oom\|Killed process"
journalctl -k | grep -i oom
```

| 现象 | 含义 |
|------|------|
| `OOMKilled: true` + 退出码 137 | 确认内存超限被杀 |
| `memory.events` 里 `oom_kill` 增长 | 反复被杀，说明限制过小或内存泄漏 |
| 容器没被杀但宿主 OOM | 说明**容器没设限制**，吃掉了宿主内存 |

### 2.4 `--memory-swap` 的性能代价（重要）

回顾入门阶段的结论：**不设 `--memory-swap` 时，swap 额度默认等于 `-m`**。

本专题补充**性能视角**：

| 场景 | 表现 | 原因 |
|------|------|------|
| 容器用 swap | ⚠️ **CPU 飙升、延迟急剧上升，但不被杀** | 频繁换页（swap in/out） |
| 典型症状 | `docker stats` 显示内存接近上限、CPU 高、服务响应慢 | —— |

> **"容器变慢但没死"的第一怀疑对象就是 swap。** 解决方式：
> ```bash
> docker run -m 512m --memory-swap 512m myapp    # 禁用 swap
> ```
> 或者把限制调大到一个合理值。**数据库类服务强烈建议禁用 swap**（换页会破坏其性能假设）。

## 三、CPU：为什么"限制"的表现不像限制

### 3.1 CFS 调度与配额机制

Docker 用 Linux 的 **CFS（完全公平调度器）** 实现 CPU 限制，机制是"配额/周期"：

```
--cpus=1.5  →  cpu.max = "150000 100000"
                 ↑配额    ↑周期(微秒)
             每 100ms 周期内最多用 150ms 的 CPU 时间
```

| 术语 | 含义 |
|------|------|
| **quota（配额）** | 一个周期内允许使用的 CPU 时间 |
| **period（周期）** | 默认 100ms |
| **throttling（限流）** | 周期内配额用完后，**该周期剩余时间被强制停止**运行 |

### 3.2 限流的真实体验

**关键认知**：CPU 限制**不是"平滑地降速"，而是"跑满配额后暂停，等下个周期"**。

| 后果 | 说明 |
|------|------|
| **延迟尖刺** | 请求可能"卡住"几十毫秒直到下个周期，表现为 P99 延迟异常 |
| 平均值看起来正常 | 因为长期平均确实在配额内 |
| 多线程应用受影响更大 | 线程被一起节流 |

> **这解释了一个常见困惑**："CPU 限制设了 2 核，但服务延迟比不限制时高很多。" —— 因为**不限制时它可以突发用满多核**，限制后遇到突发流量就被节流。

### 3.3 诊断限流（关键技能）

```bash
# 看限流统计
docker exec <容器> cat /sys/fs/cgroup/cpu.stat
# nr_periods      1000        ← 总周期数
# nr_throttled    250         ← 被限流的周期数  ⚠️ 关注这个
# throttled_usec  15000000    ← 被限流的总微秒数

# 宿主侧：从 cgroup 目录读（不需要进容器）
```

| 判据 | 结论 |
|------|------|
| `nr_throttled` / `nr_periods` > 10% | ⚠️ **应用在频繁被限流，限制设小了** |
| `throttled_usec` 持续增长 | 同上 |
| `nr_throttled` 为 0 | 限制未构成瓶颈 |

**在 Prometheus 环境里的通用指标**：

```
container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total
# 这个比值 > 0.1 通常意味着需要调大 CPU 限额
```

### 3.4 `--cpus` / `--cpu-shares` / `--cpuset-cpus` 的语义对比

| 参数 | 机制 | 是硬限制吗 | 何时用 |
|------|------|-----------|--------|
| `--cpus=1.5` | CFS 配额 | ✅ 是 | **限制峰值**（推荐） |
| `--cpu-shares=512` | 相对权重（默认 1024） | ❌ **不是**。无竞争时可占满 | 调优先级 |
| `--cpuset-cpus="0,1"` | 绑核（cpuset） | ✅ 是（物理隔离） | 减少干扰与上下文切换 |

```bash
# 验证 --cpu-shares 不是限制：宿主空闲时启动 CPU 密集容器
docker run -d --name s1 --cpu-shares=100 progrium/stress --cpu 4
docker stats s1       # CPU % 会接近 400%，说明没有被限制
```

> **`--cpu-shares` 的正确理解**：它只在"多个容器同时争抢同一批 CPU"时起作用。**它分配的是"竞争时的份额"，不是"绝对上限"。**

## 四、为什么"限制没生效"

这是最常见的疑问，原因通常是以下几类。

| 原因 | 判据 | 处理 |
|------|------|------|
| **改的是 `run` 命令，但容器是旧的** | `docker inspect` 的 `HostConfig.Memory` 是旧值 | **删除容器重建**（限制是创建时确定的） |
| **用 Compose 改了配置但只 `restart`** | 同上 | 用 `docker compose up -d` |
| **在容器内看到的是宿主总量** | `free` 显示宿主内存 | 用 `docker stats` 或读 cgroup 文件 |
| **Docker Desktop 环境限制** | 你在宿主 `top` 里看到的是虚拟机内的进程 | 在 Docker Desktop 的 VM 里验证 |
| **`--cpu-shares` 被当成限制** | 无竞争时仍占满 CPU | 改用 `--cpus` |
| **`deploy.resources` 被当成无效** | 以为 Compose 不支持 | Compose 下 `deploy.resources.limits` **是生效的** |
| **IO 限制在 Docker Desktop 上不生效** | `--device-*-bps` 无效 | 需在 Linux 上 |
| **`-m` 有效但容器用 swap 撑过去** | 内存超限但没被杀 | 显式设 `--memory-swap` |

**验证三连（每次改完限制都跑一遍）：**

```bash
# ① 配置是否写上了
docker inspect <容器> --format 'Mem={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}} Pids={{.HostConfig.PidsLimit}}'

# ② 运行时是否被约束
docker stats --no-stream <容器>

# ③ 内核层是否真的生效
docker exec <容器> cat /sys/fs/cgroup/memory.max
docker exec <容器> cat /sys/fs/cgroup/cpu.max
```

## 五、容量规划：限制值该设多少

### 5.1 原则

| 原则 | 说明 |
|------|------|
| **基于观测，不要拍脑袋** | 先不设硬限制跑一段时间，看真实峰值，再定限额 |
| **硬限制留出余量** | 峰值 × 1.3~1.5 |
| **总和不要超过宿主机容量** | 因为**限制是上限，不是预留**。所有容器同时达到上限会互相挤 |
| **区分"上限"与"预留"** | `limits` 是上限；`reservations` 才是预留（用于调度） |

### 5.2 观测方法

```bash
# 持续采样（推荐跑一段时间）
docker stats --no-stream --format \
  "table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.MemPerc}}\t{{.PIDs}}" \
  > stats-sample.txt

# 或用 Prometheus + cAdvisor 采集 container_memory_working_set_bytes
#   working_set = 用量 - 可回收 cache，比 MEM USAGE 更贴近"真实压力"
```

| 指标 | 用途 |
|------|------|
| `container_memory_working_set_bytes` | **判断内存压力的正确指标**（排除可回收 cache） |
| `container_memory_working_set_bytes` / `limits` | 内存压力比，> 80% 需要关注 |
| `container_cpu_cfs_throttled_periods_total` 比率 | CPU 限流严重度 |
| PIDs 数的峰值 | 定 `--pids-limit` |

### 5.3 限制与调度的关系（多容器同机）

**关键事实**：**限制值不是预留，多个容器可以"同时声称"超过宿主机容量的限额。**

```
宿主机 8 核 16 GB
├── app1:  --cpus=4 -m 8g     ← 限额
├── app2:  --cpus=4 -m 8g     ← 限额
└── 总额限 = 8 核 16 GB  ← 恰好等于宿主，安全
```

若总额限**远超**宿主：

```
├── app1:  --cpus=8 -m 16g
├── app2:  --cpus=8 -m 16g
└── app3:  --cpus=8 -m 16g    ← 三者同时达到上限 → 互相争抢 + 宿主 swap 抖动
```

| 策略 | 做法 |
|------|------|
| **保守** | 所有容器限额之和 ≤ 宿主容量 |
| **超卖**（常见） | 限额之和 > 宿主，依赖"实际不同时达峰"。⚠️ 需要监控与告警 |
| **预留** | 用 `deploy.resources.reservations` 或 K8s 的 requests |

> **实践建议**：**单机 Docker 场景用保守策略**（限额之和不超过宿主容量），因为 Docker 没有成熟的调度器帮你处理超卖后的争抢。**超卖是 K8s 的强项，不是单机 Compose 的。**

## 六、性能诊断工具箱

| 想知道什么 | 命令 |
|-----------|------|
| 实时资源占用 | `docker stats` |
| 内存细分（anon/file/shmem） | `docker exec <容器> cat /sys/fs/cgroup/memory.stat` |
| 是否被 OOM | `docker exec <容器> cat /sys/fs/cgroup/memory.events` |
| CPU 限流情况 | `docker exec <容器> cat /sys/fs/cgroup/cpu.stat` |
| 生效的限额 | `docker inspect <容器> --format '{{json .HostConfig}}'` |
| 容器内进程 | `docker top <容器>` |
| 容器内进程的实时资源 | `docker exec <容器> top` |
| 宿主整体压力 | `top` / `vmstat 1` / `iostat -x 1`（Linux） |
| 宿主 IO 等待 | `iostat -x` 看 `%iowait`（高说明磁盘是瓶颈） |
| 宿主的 OOM 记录 | `dmesg \| grep -i oom` |

### 一个典型的诊断流程

```
服务变慢
├── docker stats → CPU 高吗？
│   ├── CPU 接近限额 → 查 cpu.stat 的 nr_throttled
│   │   ├── 限流严重 → 调大 --cpus
│   │   └── 未限流    → 是应用本身在算（优化代码 / 增副本）
│   └── CPU 不高但慢 → 查内存与 IO
│       ├── 内存接近上限 → 查 memory.stat 的 anon/file
│       │   ├── anon   大 → 内存泄漏或配额过小
│       │   └── file   大 → page cache（通常无害，但挤占配额）
│       └── 宿主 %iowait 高 → 磁盘是瓶颈（查宿主机）
└── docker stats → 内存接近上限 + CPU 高 → 怀疑在用 swap
    └── docker inspect 确认 --memory-swap 是否未设
```

## 七、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 改限制后不重建容器 | 限制不生效 | 删容器重建 / `up -d` |
| 用容器内 `free` 验证限制 | 看到宿主总量，误判 | `docker stats` 或 cgroup 文件 |
| 只设 `-m` 不设 `--memory-swap` | 用 swap 撑到 2 倍，变慢但不被杀 | 显式设 `--memory-swap` = `-m` 禁 swap |
| `--cpu-shares` 当限制 | 限制"不生效" | 用 `--cpus` |
| 看到 `MEM USAGE` 接近上限就紧张 | 可能都是可回收 cache | 看 `memory.stat` 的 `anon` |
| CPU 限额设成"平均用量" | 突发被限流，P99 延迟恶化 | 按峰值 × 1.3 设，并监控 `nr_throttled` |
| 所有容器限额之和远超宿主 | 争抢 + swap 抖动 | 单机用保守策略 |
| 假设 IO 限制在 Docker Desktop 生效 | 不生效 | 在 Linux 验证 |
| 用 `--restart always` + 内存泄漏 | 无限重启风暴 | `on-failure:N` |
| 不监控 `working_set` | 用被 cache 污染的指标做容量规划 | 用 `working_set` 或 `anon` |

## 小结

| 要点 | 内容 |
|------|------|
| 底层 | 全部落到 **cgroup**（v2 是统一层级）。namespace 管隔离，cgroup 管限额 |
| 内存配额包含 | 匿名内存 + **page cache** + 内核对象 + tmpfs/shm |
| 内存诊断 | `memory.stat` 看 `anon`（真实占用）vs `file`（可回收 cache）；`memory.events` 看 OOM |
| swap 代价 | 用 swap 会**变慢但不被杀**。数据库应禁用 swap |
| CPU 机制 | CFS 配额/周期。限流表现为**延迟尖刺**而非平滑降速 |
| CPU 诊断 | `cpu.stat` 的 **`nr_throttled / nr_periods`**，> 10% 说明限额过小 |
| 三类参数区别 | `--cpus`（硬限制）、`--cpu-shares`（相对权重，**不是限制**）、`--cpuset-cpus`（绑核） |
| 限制没生效 | 首选原因是"容器没重建"；其次是"用 `--cpu-shares` 当限制" |
| 容量规划 | 基于 `working_set` 观测，按峰值 × 1.3；**单机不超卖** |
