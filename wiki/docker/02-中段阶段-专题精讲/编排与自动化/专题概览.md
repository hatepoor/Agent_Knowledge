# 编排与自动化 · 专题概览

## 专题定位

本专题解决的问题是：**把重复的 Docker 操作变成可复用、可自动化的东西。**

两条路线：

| 路线 | 工具 | 适合 |
|------|------|------|
| **声明式编排** | Compose 进阶能力（profiles / watch / include / 多文件） | 服务编排、环境管理 |
| **程序化控制** | Docker SDK（如 Python `docker`） | 批量操作、动态创建容器、集成到应用里 |

**何时该翻这个专题**

- 手工敲 Docker 命令太多，想封装
- 需要"按需启动一组服务"（如只启动调试工具）
- 开发时希望改代码自动重载
- 需要在程序里动态创建/销毁容器（**AI Agent 沙箱就是这个场景**）
- 想把 Docker 操作接入脚本或 CI
- 配置越来越大，需要拆分组织

## 一、Compose 进阶能力

### 1.1 `profiles`：按需启动服务

**回顾**（详见 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.3-环境变量与多环境配置]]）：`profiles` 让服务默认不启动。

**进阶用法：用 profile 组织"环境组合"**

```yaml
services:
  # 基础服务（无 profile，总是启动）
  app:
    image: myapp:1.0
  db:
    image: postgres:18

  # ── 开发工具组 ──
  adminer:
    image: adminer:latest
    profiles: ["tools"]
  mailhog:
    image: mailhog/mailhog:latest
    profiles: ["tools"]

  # ── 可观测性组 ──
  prometheus:
    image: prom/prometheus:v2.55.0
    profiles: ["observability"]
  grafana:
    image: grafana/grafana:11.3.0
    profiles: ["observability"]

  # ── 压测组 ──
  k6:
    image: grafana/k6:latest
    profiles: ["loadtest"]
```

```bash
docker compose up -d                                  # 只起 app + db
docker compose --profile tools up -d                  # 加开发工具
docker compose --profile tools --profile observability up -d
docker compose --profile "*" up -d                    # 全部
```

| 要点 | 说明 |
|------|------|
| **profile 让"一套配置支持多种组合"** | 避免维护多份几乎相同的文件 |
| 被 `depends_on` 引用的 profile 服务**会被自动启用** | 即使没显式指定 |
| 未激活 profile 的服务在 `ps` 里也看不到 | 加 `--profile` 才显示 |

> **`profiles` 与多文件合并的区别**：`profiles` 解决"**要不要这个服务**"，多文件合并解决"**同一个服务的配置怎么变**"。两者互补。

### 1.2 YAML 锚点：消除重复配置

**问题**：多个服务有相同的日志配置、资源限制、重启策略，复制粘贴容易漏改。

```yaml
# 用 x- 前缀定义可复用的片段（Compose 会忽略 x- 开头的顶层字段）
x-common: &common
  restart: unless-stopped
  logging:
    driver: local
    options:
      max-size: "10m"
      max-file: "3"

x-resources-small: &res-small
  deploy:
    resources:
      limits:
        cpus: "0.5"
        memory: 256M

services:
  app:
    image: myapp:1.0
    <<: *common                    # ← 合并公共配置
    <<: *res-small
    ports: ["8000:8000"]

  worker:
    image: myapp:1.0
    command: ["python","worker.py"]
    <<: *common
    <<: *res-small
```

| 要点 | 说明 |
|------|------|
| `x-` 前缀 | Compose 规定：`x-` 开头的顶层字段被忽略，专门用于放复用片段 |
| `&anchor` / `*alias` / `<<:` | 标准 YAML 的锚点、引用、合并语法 |
| ⚠️ **`<<:` 只做浅合并** | 嵌套的映射（如 `logging.options`）会被**整体替换**，不是逐键合并 |

> ⚠️ **浅合并陷阱的实例**：两个锚点都有 `logging` 字段时，后者会**整体覆盖**前者的 `logging`，而不是合并 `options`。排查方式是 `docker compose config` 看最终结果。

### 1.3 `include`：拆分大型配置

```yaml
# compose.yaml —— 主文件
name: myproject

include:
  - path: ./compose/db.yaml
  - path: ./compose/app.yaml
    env_file: ./compose/.env.app        # include 也可指定环境变量
  - path: ./compose/monitoring.yaml
    profiles: ["observability"]         # include 也支持 profile
```

| 好处 | 说明 |
|------|------|
| **按职责拆分文件** | 数据库、应用、监控各自一份，职责清晰 |
| **团队协作** | 不同人负责不同文件，减少冲突 |
| **可跨项目复用** | 把通用部分（如监控栈）抽成独立文件供多个项目 include |

> **`include` 与 `-f` 多文件的区别**：`-f` 是"在命令行组合文件"（调用方决定），`include` 是"**在文件里声明依赖**"（被复用方可自带依赖）。**做可复用模块时用 `include`。**

### 1.4 `depends_on` 的进阶语义

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy
        restart: true              # ← db 重启时，app 也重启
      migrate:
        condition: service_completed_successfully    # ← 等它成功跑完
```

| `condition` 取值 | 含义 |
|------------------|------|
| `service_started` | 容器启动了（**默认，最弱**） |
| `service_healthy` | 健康检查通过 |
| `service_completed_successfully` | **退出码为 0**（用于初始化/迁移任务） |

**`service_completed_successfully` 的典型用法**——数据库迁移：

```yaml
services:
  migrate:
    image: myapp:1.0
    command: ["alembic","upgrade","head"]
    depends_on:
      db:
        condition: service_healthy
    restart: "no"                    # 迁移任务不该重启

  app:
    image: myapp:1.0
    depends_on:
      migrate:
        condition: service_completed_successfully    # ✅ 迁移成功后才启动
      db:
        condition: service_healthy
```

> **这是生产环境的标准模式**：**迁移必须成功完成，应用才能启动**。若只写 `depends_on: [migrate]`，应用会在迁移进行中就启动，可能访问到中间状态的表结构。

### 1.5 `develop.watch`：开发热重载

```yaml
services:
  app:
    build: .
    develop:
      watch:
        # 源码变化 → 同步进容器（应用自带热重载时最有效）
        - action: sync
          path: ./src
          target: /app/src
        # 依赖清单变化 → 重建镜像
        - action: rebuild
          path: ./requirements.txt
        # 排除不该同步的
        - action: sync+restart
          path: ./config
          target: /app/config
    command: ["uvicorn","app:app","--host","0.0.0.0","--reload"]
```

```bash
docker compose watch
```

| action | 行为 | 何时用 |
|--------|------|--------|
| `sync` | 把文件同步进容器 | 应用支持热重载（uvicorn `--reload`、nodemon） |
| `sync+restart` | 同步后重启容器 | 配置变更需要重启才生效 |
| `rebuild` | 重新构建镜像并重建容器 | 依赖变化（`requirements.txt`、`package.json`） |

> **`watch` 是"绑定挂载 + 热重载"的更好替代**：绑定挂载在 Windows/macOS 上可能有性能与权限问题，`watch` 通过同步机制规避了一部分。**但它要求应用自身支持热重载。**

### 1.6 Makefile：封装常用命令

即使有 Compose，命令组合依然会长。用 Makefile 封装：

```makefile
.PHONY: up down logs shell test backup

COMPOSE := docker compose

up:                ## 启动全部服务
	$(COMPOSE) up -d --build

down:              ## 停止并清理（保留卷）
	$(COMPOSE) down

logs:              ## 跟踪日志
	$(COMPOSE) logs -f --tail=100

shell:             ## 进应用容器
	$(COMPOSE) exec app sh

test:              ## 跑测试
	$(COMPOSE) run --rm app pytest -q

backup:            ## 备份数据库
	$(COMPOSE) exec -T db pg_dump -U $${DB_USER} -d $${DB_NAME} -Fc > backup-$$(date +%F).dump

restart-fresh:     ## 完全重建（⚠️ 会删卷）
	$(COMPOSE) down -v && $(COMPOSE) up -d --build
```

| 收益 | 说明 |
|------|------|
| 新人只需看 `make help` | 不用记一长串命令 |
| **把危险命令显式命名** | `restart-fresh` 名字里就带着"会删数据"的警示 |
| 便于接入 CI | CI 直接调 `make test` |

## 二、程序化控制：Docker SDK

### 2.1 什么时候需要 SDK

| 用 CLI 就够 | 需要 SDK |
|-------------|----------|
| 单次执行的操作 | **需要循环处理很多容器/镜像** |
| 人来看结果的场景 | **结果要作为数据结构传给程序** |
| 简单脚本 | **需要动态创建/销毁容器**（如沙箱） |
| —— | 需要根据容器状态做条件分支 |

**判断标准**：**需要解析输出、需要条件逻辑、需要动态生命周期管理时，用 SDK。**

### 2.2 Python SDK 基础（`docker` 包）

```bash
pip install docker
```

```python
import docker

client = docker.from_env()      # 自动从环境变量/默认 socket 读取连接信息

# ── 镜像 ──
client.images.pull("python", tag="3.12-slim")
for img in client.images.list():
    print(img.tags, img.short_id)

# ── 容器 ──
container = client.containers.run(
    "python:3.12-slim",
    command=["python", "-c", "print('hello')"],
    detach=True,
    remove=False,               # 保留以便查看退出码
    mem_limit="256m",
    network_mode="none",
    read_only=True,
)
result = container.wait()       # 阻塞直到退出，返回 {"StatusCode": n}
print("exit code:", result["StatusCode"])
print(container.logs().decode())
container.remove()

# ── 列出与过滤 ──
for c in client.containers.list(all=True, filters={"label": "app=myapp"}):
    print(c.name, c.status)

# ── 执行命令 ──
exit_code, output = container.exec_run(["ls", "-la", "/app"])
print(exit_code, output.decode())
```

### 2.3 两种调用方式：高层 vs 低层 API

| 方式 | 写法 | 特点 |
|------|------|------|
| **高层 API** | `client.containers.run(...)`、`client.images.build(...)` | 参数友好，**返回值是对象**，可直接 `c.logs()` |
| **低层 API** | `client.api.create_container(...)`、`client.api.exec_create(...)` | 直接映射 Docker HTTP API，**返回值是字典**，更接近原始接口 |

| 选择 | 建议 |
|------|------|
| 一般操作 | ✅ 高层 API（`client.containers.*`、`client.images.*`） |
| 需要 API 的全部参数或精细控制 | 低层 API（`client.api.*`） |

```python
# 低层 API 示例：更接近 Docker 原始接口
resp = client.api.create_container(
    image="python:3.12-slim",
    command=["python","-c","print(1)"],
    host_config=client.api.create_host_config(
        mem_limit="256m",
        network_mode="none",
        read_only=True,
        pids_limit=100,
        cap_drop=["ALL"],
        security_opt=["no-new-privileges:true"],
    ),
)
client.api.start(resp["Id"])
print(client.api.wait(resp["Id"]))          # {'StatusCode': 0}
client.api.remove_container(resp["Id"], force=True)
```

> **低层 API 的价值**：当你要用一些高层 API 未封装的参数（如精细的 `HostConfig`、`Ulimit`、`SeccompProfile`）时，低层 API 更直接。**沙箱实现里常用这种方式**（见 [[docker/沙箱/Docker_Sandbox核心类]]）。

### 2.4 一个真实场景：动态沙箱执行器

**这是"用 SDK 而非 CLI"最典型的理由**——Agent 需要在运行时按需创建、执行、销毁容器。

```python
import docker
from dataclasses import dataclass

@dataclass
class SandboxConfig:
    image: str = "python:3.12-slim"
    memory: str = "256m"
    cpus: float = 1.0
    timeout: int = 30
    network_disabled: bool = True
    read_only: bool = True

class Sandbox:
    def __init__(self, config: SandboxConfig | None = None):
        self.cfg = config or SandboxConfig()
        self.client = docker.from_env()

    def execute(self, code: str) -> dict:
        container = self.client.containers.run(
            self.cfg.image,
            command=["python", "-c", code],
            detach=True,
            # ── 安全与资源限制 ──
            mem_limit=self.cfg.memory,
            memswap_limit=self.cfg.memory,        # 禁 swap（见资源限制专题）
            nano_cpus=int(self.cfg.cpus * 1e9),
            pids_limit=100,
            network_disabled=self.cfg.network_disabled,
            read_only=self.cfg.read_only,
            tmpfs={"/tmp": "size=64m"},
            cap_drop=["ALL"],
            security_opt=["no-new-privileges:true"],
            user="1000:1000",                     # 非 root
            # ── 清理策略 ──
            labels={"purpose": "sandbox"},
        )
        try:
            result = container.wait(timeout=self.cfg.timeout)
            return {
                "exit_code": result["StatusCode"],
                "stdout": container.logs(stdout=True, stderr=False).decode(),
                "stderr": container.logs(stdout=False, stderr=True).decode(),
            }
        except Exception as e:                    # 超时等
            container.kill()
            return {"exit_code": -1, "error": str(e)}
        finally:
            container.remove(force=True)          # ★ 必须清理，否则容器堆积

    def cleanup_orphans(self):
        """清理上次异常退出留下的沙箱容器"""
        for c in self.client.containers.list(
            all=True, filters={"label": "purpose=sandbox"}
        ):
            c.remove(force=True)
```

| 设计要点 | 为什么 |
|----------|--------|
| `memswap_limit == mem_limit` | **禁用 swap**，避免"变慢但不被杀" |
| `read_only=True` + `tmpfs` | 只读根文件系统 + 提供可写临时区 |
| `cap_drop=["ALL"]` | 削减能力 |
| `network_disabled=True` | 阻断数据外泄 |
| `user="1000:1000"` | 非 root |
| **`finally: remove(force=True)`** | ⚠️ **最关键的一行**。不加会积累大量停止的容器，最终吃满磁盘 |
| `cleanup_orphans()` | 应对"进程被杀导致 finally 未执行"的情况 |
| `labels` | 便于按标签批量清理与统计 |

> **这个例子的完整版本（含容器池、挂载 skills、结果结构化）见 [[docker/沙箱/Docker_Sandbox核心类]] 与 [[docker/沙箱/沙箱实战手册]]。**

## 三、Compose 的能力边界

**知道边界，才不会用错工具。**

| Compose 能做 | Compose **不能**做 |
|--------------|-------------------|
| 单机多容器编排 | ❌ **跨多台主机**调度 |
| 依赖顺序与健康检查 | ❌ **自动扩缩容**（按负载） |
| 资源限制 | ❌ **自动重调度**（节点挂了自动迁移） |
| 滚动更新（有限支持） | ❌ 服务发现与负载均衡（需自己加 proxy） |
| 环境与配置管理 | ❌ 密钥集中管理 |

### 什么时候该考虑 Kubernetes

**出现以下任一需求时，Compose 就不够了：**

| 信号 | 说明 |
|------|------|
| 需要**跨多台机器**部署 | Compose 只管单机 |
| 需要**按负载自动扩缩** | 需要 HPA 之类的机制 |
| 需要**节点故障自愈** | 需要调度器 |
| 需要**零停机滚动更新** | 需要更完善的发布策略 |
| **多团队**共享集群 | 需要命名空间与配额 |

> **不要过早引入 K8s**。**单机够用就用 Compose**——它的复杂度低一个数量级，运维成本也低。**只有当"单机 + Compose"确实成为瓶颈时再迁移。**

## 四、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 `depends_on` 简单形式等迁移完成 | 应用在表结构变更中就启动 | 用 `condition: service_completed_successfully` |
| YAML 锚点浅合并覆盖了嵌套配置 | 配置静默丢失 | 用 `docker compose config` 验证 |
| `profiles` 服务没加 `--profile` | 服务没起来 | 加参数；或用 `profiles: ["*"]` |
| 用 Compose 做跨主机 | 做不到 | 上 K8s 或其他编排 |
| SDK 里忘了 `container.remove()` | **容器与卷堆积，磁盘耗尽** | `finally` 中清理 + 定期清理孤儿容器 |
| SDK 用 `detach=False` 且没超时 | 程序永久阻塞 | 用 `detach=True` + `wait(timeout=)` |
| 忘了设 `memswap_limit` | 沙箱用 swap 变慢 | 与 `mem_limit` 设成同值 |
| 每次执行都 `pull` 镜像 | 慢且浪费 | 启动时检查本地是否有，或预热 |
| 用 `docker compose restart` 应用配置变更 | 不生效 | 用 `up -d` |
| 把危险命令写进默认可执行的 target | 误操作删数据 | 命名带上警示（如 `restart-fresh`）+ 加二次确认 |

## 小结

| 要点 | 内容 |
|------|------|
| Compose 进阶 | `profiles`（按需启动服务）、锚点 `x-`（消除重复）、`include`（拆分与复用）、`develop.watch`（热重载） |
| `depends_on` 的三档 | `service_started`（弱）< `service_healthy` < **`service_completed_successfully`（迁移任务的标准模式）** |
| 封装 | Makefile 封装命令组合，危险操作在命名上警示 |
| SDK 的价值 | 需要**循环、条件逻辑、动态生命周期**时用 SDK，而不是解析 CLI 输出 |
| Python SDK | 高层 `client.containers.run()` 友好；低层 `client.api.*` 可直接用全部参数（沙箱常用） |
| **SDK 最重要的纪律** | **`finally` 里必须 `remove(force=True)`**，否则容器堆积吃满磁盘 |
| Compose 边界 | 单机够用；需要跨主机/自动扩缩/自愈时才上 K8s |
