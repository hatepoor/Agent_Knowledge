# 日志与监控 · 专题概览

## 专题定位

本专题解决的问题是：**容器里的日志去哪了、怎么收集，以及上线后如何知道服务是否健康。**

**何时该翻这个专题**

- 容器日志把宿主机磁盘写满（最紧急）
- 容器删除后日志就没了，无法追溯历史
- 需要跨多个容器/多台机器查日志
- 要上生产，需要可观测性（指标 + 日志）
- 需要告警：服务挂了要能第一时间知道
- 健康检查通过但服务实际不可用

> ⚠️ **日志的基础机制**（`docker logs`、日志文件位置、无限增长问题）在 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.3-进入容器与查看日志]] 与 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.2-磁盘占用与日志清理]]。本专题讲**收集体系与监控设计**。

## 一、先理解容器的日志模型

### 1.1 设计意图：日志即标准输出

容器的日志模型有一条核心原则：

> **应用应该把日志写到 stdout / stderr，由容器运行时统一接管。**

这是"12-Factor App"的日志原则：**应用不关心日志去哪，只负责产生。**

| 传统做法 | 容器做法 |
|----------|----------|
| 应用写 `/var/log/app.log` | 应用写 stdout |
| 日志轮转靠 logrotate | 运行时负责（驱动 + `max-size`） |
| 采集靠日志 agent 读文件 | 采集靠日志驱动直接转发 |

### 1.2 写文件的日志为什么是问题

| 问题 | 说明 |
|------|------|
| `docker logs` 看不到 | 只显示 stdout/stderr |
| 容器删除即丢失 | 文件在可写层里 |
| 采集器要额外挂载路径 | 破坏"容器自包含" |
| 多副本时分散在各容器 | 难以聚合 |

**两种应对**：

| 方案 | 说明 | 评价 |
|------|------|------|
| **改造应用写到 stdout** | 最简单、最符合容器理念 | ✅ **推荐** |
| 把日志目录挂到卷 + 用 agent 采集 | 兼容旧应用 | ⚠️ 折中方案 |

> **实践建议**：**新写的应用一律输出到 stdout；遗留应用不要为了容器化而重写日志逻辑，用卷 + 采集器过渡。**

## 二、日志驱动（driver）与选择

| 驱动 | 行为 | `docker logs` 可用 | 适用 |
|------|------|-------------------|------|
| `json-file` | 写本地 JSON 文件（**默认**） | ✅ | 单机、开发 |
| `local` | 类似 json-file 但**默认带轮转**、二进制更省空间 | ✅（受限） | ✅ **单机推荐** |
| `journald` | 交给 systemd journal | ✅ | Linux + 已有 journal |
| `syslog` | 发到 syslog | ❌ | 已有 syslog 体系 |
| `fluentd` / `fluent-bit` | 发到 Fluentd/Fluent Bit | ❌ | ✅ **集中日志常用** |
| `gelf` | Graylog 格式 | ❌ | 用 Graylog 时 |
| `awslogs` / `gcplogs` | 发到云日志 | ❌ | 云环境 |
| `none` | 丢弃 | ❌ | 明确不需要日志时 |

### 关于 `local` 驱动的推荐

**如果你不想上集中日志系统，用 `local` 驱动就比 `json-file` 好**——它默认带轮转，不需要额外配置 `max-size`。

```json
// /etc/docker/daemon.json
{
  "log-driver": "local",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

### 关于放弃 `docker logs` 的代价

**选择 `fluentd`/`syslog` 等驱动后，`docker logs` 会失效**（因为没有本地文件）。这是很重要的权衡：

| 场景 | 建议 |
|------|------|
| 开发环境 | `json-file` 或 `local`（需要 `docker logs` 排错） |
| 生产环境 | 转发到集中平台（排错去平台查，不用 `docker logs`） |
| 过渡期 | 用 `fluent-bit` 同时保留本地小缓冲 |

> **若生产改用转发型驱动，务必保留"最近少量日志"的能力**，否则线上排错时会非常被动。做法之一是给关键服务配双写（部分驱动支持），或在采集平台保留近期日志的快速查询窗口。

## 三、集中式日志：架构与栈选择

### 3.1 三段式架构

```
① 采集              ② 传输/缓冲           ③ 存储与查询
容器 stdout    →    Fluent Bit      →    Loki / Elasticsearch
日志驱动转发         Promtail               ↑
                    缓冲与批处理        可视化：Grafana / Kibana
```

### 3.2 三套主流栈对比

| 栈 | 组成 | 资源占用 | 查询能力 | 适用 |
|----|------|----------|----------|------|
| **PLG** | Promtail + Loki + Grafana | ✅ **低** | 标签为主，全文较弱 | ✅ **推荐入门与中小规模** |
| **EFK/ELK** | Fluentd/Fluent Bit + Elasticsearch + Kibana | ⚠️ 高（ES 吃内存） | ✅ **全文检索强** | 日志量大、需要复杂检索 |
| **Graylog** | GELF + MongoDB + ES | 中高 | 强 | 已有 Graylog |

> **选型建议**：**从 PLG 开始**。Loki 的索引策略（只索引标签，不索引全文）让它资源占用远低于 ES，对个人项目与中小团队足够。**日志量上到每天几十 GB 再考虑 ES。**

### 3.3 可直接运行的最小日志栈

```yaml
name: logging

services:
  loki:
    image: grafana/loki:3.2.0
    command: -config.file=/etc/loki/local-config.yaml
    volumes:
      - loki-data:/loki
    ports:
      - "127.0.0.1:3100:3100"
    restart: unless-stopped
    networks: [monitoring]

  promtail:
    image: grafana/promtail:3.2.0
    volumes:
      # 读取宿主上所有容器的日志文件
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./promtail-config.yaml:/etc/promtail/config.yaml:ro
    command: -config.file=/etc/promtail/config.yaml
    restart: unless-stopped
    networks: [monitoring]

  grafana:
    image: grafana/grafana:11.3.0
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD:?必须设置}
      GF_USERS_ALLOW_SIGN_UP: "false"
    volumes:
      - grafana-data:/var/lib/grafana
    ports:
      - "127.0.0.1:3000:3000"
    restart: unless-stopped
    networks: [monitoring]

volumes:
  loki-data:
  grafana-data:

networks:
  monitoring:
```

**`promtail-config.yaml`（最小配置）：**

```yaml
server:
  http_listen_port: 9080

positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: docker
    static_configs:
      - targets: [localhost]
        labels:
          job: docker
          __path__: /var/lib/docker/containers/*/*-json.log
    pipeline_stages:
      # 把 docker 的 JSON 包装拆开，取出日志正文
      - json:
          expressions:
            output: log
            stream: stream
      - labels:
          stream:
      - output:
          source: output
```

| 要点 | 说明 |
|------|------|
| **挂载 `/var/lib/docker/containers` 只读** | `:ro`。Promtail 只读日志，不该有写权限 |
| **挂载 `docker.sock` 只读** | 用于自动发现容器并打标签。⚠️ 挂 socket 有安全含义（见 [[docker/02-中段阶段-专题精讲/容器安全加固/专题概览]]）——生产可改用静态路径发现 |
| **`pipeline_stages` 拆 JSON** | Docker 把日志包成 `{"log":"...","stream":"stdout"}`，需拆开 |
| **Grafana 密码用 `${:?}`** | 缺失即报错，避免用默认密码上线 |
| **只绑 `127.0.0.1`** | 监控界面不该对公网开放 |

> ⚠️ **日志系统的存储同样会增长**，需要为 Loki 配置保留期（`limits_config.retention_period`）与定期清理。**否则你为了排查磁盘而建的日志系统，自己会成为磁盘问题。**

## 四、监控：三层指标

### 4.1 三层模型

| 层次 | 指标示例 | 采集方式 | 回答什么 |
|------|----------|----------|----------|
| **容器层** | CPU、内存、网络、磁盘 IO、重启次数 | cAdvisor | 容器是否健康 |
| **应用层** | 请求量、延迟分布、错误率、队列长度 | 应用暴露 `/metrics` | 服务是否正常 |
| **业务层** | 订单数、支付成功率、活跃用户 | 业务代码埋点 | 业务是否正常 |

> **只看容器层是不够的**：容器 CPU/内存都正常，但业务可能已经全错了。**三层都要有，但优先级是"业务 > 应用 > 容器"**。

### 4.2 容器层：cAdvisor + Prometheus

```yaml
services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.49.1
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker:/var/lib/docker:ro
      - /dev/disk:/dev/disk:ro
    ports:
      - "127.0.0.1:8081:8080"
    privileged: true          # ⚠️ cAdvisor 需要读取宿主 cgroup 信息
    restart: unless-stopped

  prometheus:
    image: prom/prometheus:v2.55.0
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
      - prom-data:/prometheus
    ports:
      - "127.0.0.1:9090:9090"
    restart: unless-stopped

volumes:
  prom-data:
```

**`prometheus.yml`：**

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: cadvisor
    static_configs:
      - targets: ["cadvisor:8080"]

  - job_name: myapp
    static_configs:
      - targets: ["app:8000"]        # 应用暴露 /metrics 的地址
```

> ⚠️ **cAdvisor 需要 `privileged` 或大量挂载**，这本身与安全加固冲突。**折中方案**：cAdvisor 只在专用监控节点运行，或改用宿主的 node_exporter + cgroup 直接采集。

### 4.3 应用层：暴露 `/metrics`

**Python（FastAPI + prometheus-client）：**

```python
from fastapi import FastAPI
from prometheus_client import Counter, Histogram, make_asgi_app

app = FastAPI()

REQUEST_COUNT = Counter("app_requests_total", "请求总数", ["method", "endpoint", "status"])
REQUEST_LATENCY = Histogram("app_request_latency_seconds", "请求延迟", ["endpoint"])

@app.get("/metrics")
def metrics():
    return make_asgi_app()

@app.get("/health")
def health():
    return {"status": "ok"}
```

| 要点 | 说明 |
|------|------|
| **`/metrics` 与 `/health` 分开** | `/metrics` 给监控系统，`/health` 给编排/负载均衡 |
| **用 Histogram 而非平均值** | 平均值掩盖长尾，**P99 才是用户感受** |
| **标签要有边界** | 不要把用户 ID 当标签（导致指标基数爆炸） |

### 4.4 关键指标（少而精）

| 类型 | 指标 | 为什么重要 |
|------|------|-----------|
| **延迟** | P50 / P95 / **P99** | 平均值骗人，长尾决定体验 |
| **流量** | 每秒请求数（QPS） | 判断负载 |
| **错误** | 5xx 比例、异常计数 | 直接反映故障 |
| **饱和度** | 内存 `working_set` / limit、CPU 限流比率、队列长度 | 预测即将出问题 |
| 容器特有 | **重启次数**、**OOM 次数**、**健康状态** | 容器化的独有信号 |

> **容器场景必须额外监控的三个指标**：
> - `container_restart_count` —— 反复重启说明有隐藏崩溃
> - `container_oom_events_total` —— 内存限制过小或泄漏
> - `container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total` —— **CPU 限流比率**（> 0.1 说明限额过小，见 [[docker/02-中段阶段-专题精讲/资源限制与性能/专题概览]]）

## 五、健康检查：三种检查的区别

这是很容易混的一组概念。

| 类型 | 回答的问题 | 失败时该做什么 | Docker 对应 |
|------|-----------|----------------|-------------|
| **liveness（存活）** | 进程还活着吗？ | **重启容器** | `HEALTHCHECK` / K8s `livenessProbe` |
| **readiness（就绪）** | 能接收流量吗？ | **从负载均衡摘除**，不重启 | Compose `depends_on: service_healthy` / K8s `readinessProbe` |
| **startup（启动）** | 启动完成了吗？ | 给启动更多时间 | K8s `startupProbe`；Docker 用 `start_period` |

### 关键区别与常见错误

| 错误 | 后果 |
|------|------|
| **liveness 检查依赖了外部服务**（如数据库） | 数据库抖动 → 所有应用容器被判为"不健康" → **被批量重启** → 雪崩 |
| readiness 只检查"端口开着" | 服务还没加载完数据就接流量 → 请求失败 |
| `start_period` 设太短 | 慢启动服务（数据库、JVM）被判不健康 |
| **健康检查写得比业务还重** | 检查本身消耗大量资源（如每次都查全表） |

```yaml
# ✅ 好的 liveness：只检查自身
healthcheck:
  test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
  interval: 30s
  timeout: 5s
  retries: 3
  start_period: 40s

# ✅ 好的 readiness：检查依赖是否就绪（在 Compose 里由 depends_on + condition 表达）
```

> **一条重要原则**：**liveness 检查绝不能依赖外部系统。** 只应检查"进程自身的健康"（能否响应 HTTP、文件描述符是否正常）。依赖检查属于 readiness 的范畴。
>
> **Docker 只有一种 `HEALTHCHECK`**，它同时被 `depends_on: service_healthy` 用作就绪判据。这意味着**在 Compose 里要谨慎设计它的内容**——包含依赖检查能让启动顺序正确，但**不要用 `--restart` 与严格健康检查组合出"雪崩重启"**。

## 六、告警设计

| 原则 | 说明 |
|------|------|
| **基于症状，不基于原因** | 告"错误率 > 1%"（症状），而不是告"CPU 高"（原因，可能无害） |
| **每条告警必须可行动** | 收到后不知道该做什么的告警是噪音 |
| **用持续时间过滤抖动** | "5xx 比例 > 1% 持续 5 分钟"而不是瞬时值 |
| **分级** | P1（立即处理）vs P2（工作时间处理） |
| **告警要有 Runbook** | 写明"先看什么、再做什么" |

**推荐的起步告警（4 条）：**

| 告警 | 条件 |
|------|------|
| 服务不可达 | `/health` 连续失败 3 次 |
| 错误率高 | 5xx 比例 > 1% 持续 5 分钟 |
| 容器反复重启 | `restart_count` 5 分钟内增长 > 2 |
| 资源接近上限 | 内存 `working_set` / limit > 90% 持续 10 分钟 |

> **不要一上线就配几十条告警**。告警疲劳（alert fatigue）会让真正的故障被忽略。**从 4 条开始，逐步补充。**

## 七、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 不配日志轮转 | 磁盘被日志写满 | 用 `local` 驱动或配 `max-size` |
| 应用只写文件不写 stdout | `docker logs` 看不到、容器删了就丢 | 改造为写 stdout |
| 改用 `fluentd` 后依赖 `docker logs` | 线上排错时发现没有本地日志 | 保留近期缓冲或明确改变排错流程 |
| 日志系统自身无保留期 | 日志库自己把磁盘占满 | 配 `retention_period` 与清理 |
| 挂 `docker.sock` 给采集器 | 安全风险 | 只读挂载，或用静态路径发现 |
| 只监控容器 CPU/内存 | 业务全错但指标"健康" | 补应用层与业务层指标 |
| 用平均延迟 | 长尾问题被掩盖 | 用 P95/P99 |
| 健康检查依赖数据库 | 数据库抖动导致应用批量重启 | liveness 只查自身 |
| 指标标签用高基数（用户 ID） | 监控系统内存爆炸 | 标签要有边界 |
| 监控界面暴露到公网 | 信息泄露 | 只绑 `127.0.0.1`，前置认证 |
| 告警配得太多 | 告警疲劳，真故障被忽略 | 从少数可行动告警开始 |

## 小结

| 要点 | 内容 |
|------|------|
| 容器日志模型 | 应用写 **stdout/stderr**，运行时接管。写文件的日志是容器化的障碍 |
| 驱动选择 | 开发用 `json-file`/`local`；生产转发到集中平台（但要接受 `docker logs` 失效） |
| `local` 驱动 | 默认带轮转，是单机比 `json-file` 更好的选择 |
| 集中日志栈 | **PLG（Promtail + Loki + Grafana）** 资源占用低，推荐入门 |
| 监控三层 | 容器层（cAdvisor）、应用层（`/metrics`）、业务层（埋点）。优先级：业务 > 应用 > 容器 |
| 容器特有指标 | **重启次数、OOM 次数、CPU 限流比率** |
| 健康检查 | liveness 只查自身（失败则重启）；readiness 才查依赖（失败则摘流量） |
| 告警 | 基于症状、必须可行动、用持续时间过滤抖动、从 4 条起步 |
