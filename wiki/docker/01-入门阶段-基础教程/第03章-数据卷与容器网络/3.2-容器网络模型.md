# 容器网络模型

## 学习目标

读完本篇，你应当能够：

1. 说清容器网络要解决的三类通信问题，并分别给出方案
2. 准确区分 `bridge` / `host` / `none` 三种默认网络模式，并为场景选对
3. **解释"为什么两个容器默认不能用容器名互相访问"**，并用自定义网络解决它
4. 说清容器如何访问宿主机上的服务
5. 用 `docker network` 命令诊断"容器之间连不上"的问题

## 一、容器网络要解决的三类问题

初学者常把"网络问题"当成一个问题，其实它包含三类，方案完全不同：

```
① 外部 → 容器     外面的人怎么访问容器里的服务？   → 端口映射（见 3.3）
② 容器 → 容器     两个容器怎么互相通信？          → 自定义网络 + 服务名
③ 容器 → 外部     容器里的程序怎么上网/访问宿主？  → 网络模式 + DNS
```

**本篇重点讲 ② 和 ③**，①（端口映射）在 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.3-端口映射与访问]] 详述。

## 二、三种默认网络模式

每个容器启动时都会接入某个网络。Docker 预置了三个：

```bash
docker network ls
# NETWORK ID     NAME      DRIVER    SCOPE
# 1a2b3c4d       bridge    bridge    local     ← 默认，容器不加 --network 就用它
# 5e6f7a8b       host      host      local
# 9c0d1e2f       none      null      local
```

### 2.1 `bridge`（网桥模式）—— 默认

| 特点 | 说明 |
|------|------|
| 每个容器获得一个**独立 IP**（通常 `172.17.0.0/16` 段） | 容器之间可通 |
| 有**独立的网络栈**（自己的网卡、自己的端口空间） | 所以容器里监听 80 端口，不会占用宿主的 80 |
| 与外部通信需**端口映射**（`-p`） | 见 3.3 |
| 有**内置 DNS**（但默认 bridge 上**不可用容器名解析**，见下节） | 关键坑点 |

### 2.2 `host`（主机模式）

```bash
docker run -d --network host nginx
```

| 特点 | 说明 |
|------|------|
| 容器**直接使用宿主机的网络栈** | ❌ 不隔离网络 |
| 容器里监听 80 = 宿主上监听 80 | **`-p` 变得无意义且会报错** |
| 性能最好（无 NAT 转换开销） | 适合对网络性能敏感的场景 |
| ⚠️ **端口会冲突** | 两个容器都想监听 80 就会有一个起不来 |
| ⚠️ **平台限制** | **Windows / macOS 上效果受限**（因为中间有虚拟机），Linux 上才完整可用 |

| 何时用 | 说明 |
|--------|------|
| 需要极致网络性能 | 如高频交易、压测工具 |
| 容器需要看到宿主的真实网络接口 | 如网络监控工具 |
| 单纯想省掉端口映射 | 一般**不推荐**，牺牲了隔离与灵活性 |

### 2.3 `none`（无网络）

```bash
docker run -d --network none alpine sleep 300
```

| 特点 | 说明 |
|------|------|
| 容器**完全没有网络**（只有一个 `lo` 回环接口） | 完全隔离 |
| 用途 | ① 纯计算任务 ② **安全沙箱**：执行不可信代码时禁用网络 |

> **沙箱场景的关键一招**：`--network none` 是防止代码外泄数据最简单有效的手段。见 [[docker/沙箱/沙箱安全加固]]。

### 2.4 三种模式对比

| 维度 | `bridge` | `host` | `none` |
|------|----------|--------|--------|
| 网络隔离 | ✅ 有 | ❌ 无 | ✅ 完全 |
| `-p` 端口映射 | 需要且有 | 无效 | 无意义 |
| 端口冲突风险 | 低 | **高** | —— |
| 性能 | 有 NAT 开销 | **最好** | —— |
| 容器名解析 | 自定义网络下可用 | 不适用 | —— |
| 适用 | **绝大多数场景** | 性能敏感 / 需真实网络 | **安全沙箱** |

## 三、核心问题：为什么容器之间不能用容器名互访

这是 Docker 网络最容易让初学者困惑的一点。

### 3.1 现象

```bash
docker run -d --name app myapp:1.0        # 用默认 bridge
docker run -d --name db postgres:18

docker exec app ping db
# ping: bad address 'db'   ← 解析失败！
```

但用 IP 却能通：

```bash
docker inspect db --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'
# 172.17.0.3

docker exec app ping 172.17.0.3
# 通！
```

### 3.2 原因

| 原因 | 说明 |
|------|------|
| **默认 `bridge` 网络不提供 DNS 名称解析** | Docker 的内置 DNS 只在**用户自定义网络**上启用 |
| 更根本的原因 | 默认 bridge 是"所有容器的公共大杂院"，Docker 无法在其中建立可靠的名字映射 |
| 用 IP 能通 | 因为它们在同一个网段，二层三层都通 |

### 3.3 解决方案：创建自定义网络（必须掌握）

```bash
# ① 创建一个自定义网络
docker network create mynet

# ② 把容器接入它
docker run -d --name app --network mynet myapp:1.0
docker run -d --name db  --network mynet postgres:18

# ③ 现在可以用名字访问了
docker exec app ping db        # ✅ 通
```

**自定义网络带来的三个额外好处：**

| 好处 | 说明 |
|------|------|
| ✅ **内置 DNS，可用容器名/服务名解析** | 这是最重要的 |
| ✅ **网络隔离** | 不在同一个自定义网络里的容器互相看不见（默认 bridge 上所有容器都能互相看到） |
| ✅ **网络别名** | `--network-alias` 可以给容器起多个可用名 |

> **这就是 Compose 自动帮你做的事**：`docker compose up` 会创建一个名为 `<项目名>_default` 的自定义网络，把所有服务接进去。所以 **Compose 里可以直接用服务名当主机名**（`DB_HOST=db`）。这是 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.2-用Compose编排多容器服务]] 的核心机制之一。

### 3.4 网络管理命令

```bash
docker network create mynet                    # 创建
docker network ls                              # 列出
docker network inspect mynet                   # 查看网络内有哪些容器、各自 IP
docker network connect mynet <容器>             # 把运行中的容器接入
docker network disconnect mynet <容器>          # 断开
docker network rm mynet                        # 删除（有容器连着会失败）
docker network prune                           # 清理未使用的网络
```

**`docker network inspect` 是排查"容器互访失败"的第一入口**：

```bash
docker network inspect mynet --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
```

输出会列出网络内所有容器的名字与 IP。**如果某个容器不在列表里，说明它没接入这个网络**——这就是问题所在。

## 四、容器如何访问宿主机上的服务

这是一个高频需求：容器里的应用要连宿主上跑着的服务（比如宿主上有一个没进容器的 Redis）。

### 三种方式

| 方式 | 写法 | 适用平台 | 说明 |
|------|------|----------|------|
| **`host.docker.internal`** ✅ | `host.docker.internal:6379` | Windows / macOS **原生支持**；Linux 需 `--add-host=host.docker.internal:host-gateway` | **推荐**，语义清晰 |
| 宿主在 bridge 上的网关 IP | `172.17.0.1:6379`（默认 bridge 的网关） | Linux | 需要先确认网关地址 |
| 用 `--network host` | 直接用 `127.0.0.1:6379` | Linux | 但会失去网络隔离 |

```bash
# Linux 上启用 host.docker.internal
docker run --add-host=host.docker.internal:host-gateway myapp:1.0

# 查默认 bridge 的网关
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Gateway}}{{end}}'
# 172.17.0.1
```

> ⚠️ **容器里的 `localhost` 永远指容器自己**。这是初学者最常犯的错误：在容器里写 `localhost:5432` 想连宿主上的数据库，结果连的是容器自己的 5432。

## 五、网络驱动概览（知道有这些即可）

除了 `bridge`，Docker 还提供其他网络驱动。**入门阶段不必掌握，但要知道它们存在**：

| 驱动 | 用途 | 备注 |
|------|------|------|
| `bridge` | 单机容器通信（默认） | 本篇重点 |
| `host` | 用宿主网络栈 | —— |
| `none` | 无网络 | —— |
| `overlay` | **跨多台机器**的容器通信 | 需要 Swarm 或 K8s 等编排 |
| `macvlan` / `ipvlan` | 让容器获得局域网的"真实 IP" | 需要网络管理员配合 |
| `container:<容器名>` | 复用另一个容器的网络栈 | 特殊场景 |

### 底层机制（一句话，中段会展开）

Docker 的网络在 Linux 上是通过这些内核能力实现的：

| 机制 | 作用 |
|------|------|
| **veth pair** | 一对虚拟网卡，一端在容器内、一端在宿主机上，像一根"虚拟网线" |
| **bridge（网桥）** | 类似于虚拟交换机，把多根虚拟网线连起来 |
| **iptables / nftables** | 做 NAT（地址转换）与端口转发，实现端口映射与出网 |
| **Docker 内置 DNS** | 在自定义网络上提供容器名解析 |

> 这些机制的完整原理（含 `docker0` 网桥、NAT 规则、DNS 实现）属于中段内容，见 [[docker/02-中段阶段-专题精讲/网络进阶与多容器互联/专题概览]]。

## 六、排查"容器之间连不上"的固定流程

```bash
# 第 1 步：确认两个容器是否在同一个自定义网络
docker network inspect <网络名> --format '{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'
#   缺陷：某个容器不在这里 → 它没接入该网络

# 第 2 步：从 A 容器内部测试名称解析
docker exec app nslookup db
docker exec app ping db

# 第 3 步：测试端口连通性（不只是能否解析，还要看端口通不通）
docker exec app sh -c "nc -zv db 5432 || echo 'port unreachable'"
#   注意：镜像里可能没有 nc/curl，见下

# 第 4 步：确认目标服务确实在监听
docker exec db sh -c "netstat -tlnp || ss -tlnp"

# 第 5 步：看双方日志
docker logs --tail 50 app
docker logs --tail 50 db
```

> ⚠️ **排查工具缺失是常见障碍**：`slim` / `alpine` 镜像里通常**没有** `ping`、`nc`、`curl`、`nslookup`。三种应对：
> 1. 临时起一个带工具的同网络容器：`docker run --rm --network mynet nicolaka/netshoot`
> 2. 用容器里已有的工具（Python 的 `socket` 模块也行）
> 3. 用 `docker exec -u root` + 临时安装（不推荐，会污染容器）

**用 Python 测试连通性（几乎总有 Python 或可换用其他语言）：**

```bash
docker exec app python -c "
import socket
s = socket.socket(); s.settimeout(3)
try:
    s.connect(('db', 5432)); print('connected OK')
except Exception as e:
    print('failed:', e)
"
```

## 七、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 在默认 bridge 上用容器名访问 | 解析失败 | 创建**自定义网络** |
| 在容器里用 `localhost` 访问别的容器 | 连到容器自己 | 用**服务名**（自定义网络内） |
| 在容器里用 `localhost` 访问宿主服务 | 连到容器自己 | 用 `host.docker.internal`（Linux 需加 `--add-host`） |
| 用 `--network host` 后又加 `-p` | 报错/无效 | `host` 模式不需要端口映射 |
| 两个 `host` 模式容器都要同一端口 | 一个起不来 | 改用 bridge + 端口映射 |
| 假设 slim/alpine 镜像有 `ping`/`curl` | 排查时命令不存在 | 备一个 `netshoot` 类工具容器 |
| 忘了 Compose 会自动建网络 | 手工建了重复的 | Compose 下直接用服务名 |

## 小结

| 要点 | 内容 |
|------|------|
| 三类通信问题 | 外部→容器（端口映射）、容器→容器（自定义网络）、容器→外部（DNS/网关） |
| 三种默认模式 | `bridge`（默认，有隔离，需 `-p`）、`host`（无隔离，性能好，Windows/macOS 受限）、`none`（无网络，用于沙箱） |
| 核心坑点 | **默认 bridge 不支持容器名解析**，必须建**自定义网络** |
| 自定义网络的三好处 | 内置 DNS、网络隔离、支持别名 |
| 容器访问宿主 | `host.docker.internal`（Linux 需 `--add-host=host.docker.internal:host-gateway`） |
| 永远记住 | 容器里的 `localhost` = 容器自己 |
| 底层机制 | veth pair + bridge + iptables/NAT + 内置 DNS（中段展开） |

## 练习

1. **复现并修复名称解析问题**：
   ```bash
   docker run -d --name db1 -e POSTGRES_PASSWORD=x postgres:18
   docker run -d --name app1 alpine sleep 300
   docker exec app1 nslookup db1          # 观察失败
   ```
   然后创建自定义网络，把两个容器接入，再试一次。
2. **验证网络隔离**：创建两个自定义网络 `net1` 和 `net2`，各放一个容器。验证 `net1` 里的容器解析不到 `net2` 里的容器。
3. **对比三种模式**：
   ```bash
   docker run -d --name b1 -p 8081:80 nginx
   docker run -d --name h1 --network host nginx      # Linux 上试
   docker run -d --name n1 --network none alpine sleep 300
   docker exec n1 sh -c "ip addr"                    # 看有几个接口
   ```
4. **容器访问宿主服务**：
   ```bash
   # 先在宿主上起一个服务（用 Python 起个临时 HTTP 服务）
   python -m http.server 9000
   # 再从容器内访问
   docker run --rm --add-host=host.docker.internal:host-gateway alpine \
     sh -c "wget -qO- http://host.docker.internal:9000 || echo 'failed'"
   ```
5. **诊断练习**：`docker network inspect bridge` 与 `docker network inspect mynet` 的输出有何不同？哪个能提供容器名解析？
