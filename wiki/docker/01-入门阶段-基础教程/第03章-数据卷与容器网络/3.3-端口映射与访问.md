# 端口映射与访问

## 学习目标

读完本篇，你应当能够：

1. 准确写出端口映射的方向，并解释"写反了会怎样"
2. 使用端口的四种绑定形式，包括**只绑本机**这种更安全的形式
3. 独立排查"端口被占用"与"服务起来了但访问不到"两类问题
4. 说清 Windows / macOS 上端口访问行为与 Linux 的差异
5. 说出 `EXPOSE` 与 `-p` 的真实关系

## 一、为什么需要端口映射

由上一节可知：默认 `bridge` 模式下，容器有**独立的网络栈**。容器里的程序监听 80 端口，指的是**容器的** 80 端口。

宿主机上并没有一个叫 80 的端口在监听你的服务。所以外部的请求无法直接进来。

**端口映射就是建立一条"宿主端口 → 容器端口"的转发规则。**

```
外部请求
   ↓
宿主机:8080   ──[由 Docker 建立的转发规则]──→   容器:80
（真正监听的端口）                              （服务实际监听的端口）
```

## 二、方向：左边宿主，右边容器

**这是全篇最重要的一句话：**

```bash
docker run -p <宿主端口>:<容器端口> <镜像>
#           ↑ 外面访问用这个    ↑ 服务在容器里监听这个
```

### 写反了会怎样

```bash
# 服务在容器里监听 80，你想从宿主的 8080 访问
docker run -p 8080:80 nginx      # ✅ 正确：访问 localhost:8080
docker run -p 80:8080 nginx      # ❌ 错误：把宿主的 80 转发到容器的 8080
                                 #    而容器的 8080 上根本没人监听
```

**错误写法的表现**：命令能正常执行，容器状态也是 `Up`，但访问 `localhost:80` 会得到**连接被拒绝或 502**。因为转发目标端口是空的。

> **为什么"容器 Up"却"访问不到"**：端口映射**不会**检查容器内是否真有服务在监听那个端口。它只是建立转发规则。所以"容器在跑"与"端口能访问"是两件独立的事。

**记忆法**：

| 记忆点 | 说明 |
|--------|------|
| **"从外到内"** | 按数据流动方向写：外部（左）→ 容器（右） |
| **冒号右边等于 `EXPOSE` 的值** | 容器内端口就是 Dockerfile 里 `EXPOSE` 声明的那个 |

## 三、四种绑定形式

| 写法 | 含义 | 谁能访问 |
|------|------|----------|
| `-p 8080:80` | 宿主所有网卡的 8080 → 容器 80 | ⚠️ **任何能连到你机器的人都行**（含同局域网、公网） |
| `-p 127.0.0.1:8080:80` | **只绑回环地址** | ✅ 仅本机可以访问 |
| `-p 8080:80/udp` | 指定协议为 UDP（默认 TCP） | 按需 |
| `-p 127.0.0.1:8080:80/udp` | 组合 | —— |
| `-p 80` | **随机映射**宿主端口到容器 80 | 端口由系统分配，用 `docker port` 查 |
| `-P`（大写） | 把镜像 `EXPOSE` 的**所有**端口随机映射 | 批量测试时用 |

### 安全建议：本地开发加 `127.0.0.1`

```bash
# ❌ 不推荐（本机开发时）
docker run -p 5432:5432 postgres:18
# 后果：局域网里任何人都能连你的数据库。如果还用了弱密码，等于敞开大门

# ✅ 推荐
docker run -p 127.0.0.1:5432:5432 postgres:18
# 后果：只有本机能连
```

> ⚠️ **这个细节容易被忽略但风险实在**：`-p 5432:5432` 的默认行为是绑定 `0.0.0.0`，即所有网卡。在咖啡厅的公共 WiFi 下，你的数据库可能对同网段所有人可见。**本地开发一律加 `127.0.0.1:` 前缀。**
>
> 云端服务器上更要注意：除了加 `127.0.0.1`，还要检查云服务商的**安全组/防火墙**是否放行了该端口。

## 四、查看与管理端口映射

### 4.1 `docker ps` 的 PORTS 列

```bash
docker ps
# CONTAINER ID   NAME    ...   PORTS                    STATUS
# a1b2c3d4e5f6   web     ...   0.0.0.0:8080->80/tcp     Up 5 minutes
```

| 显示 | 含义 |
|------|------|
| `0.0.0.0:8080->80/tcp` | **所有网卡**的 8080 → 容器 80 |
| `127.0.0.1:8080->80/tcp` | 只绑了回环 |
| `80/tcp`（无箭头） | **只声明未映射**（来自 `EXPOSE`），外部访问不到 |

### 4.2 `docker port`

```bash
docker port web
# 80/tcp -> 0.0.0.0:8080
```

### 4.3 `docker inspect`

```bash
docker inspect web --format '{{json .NetworkSettings.Ports}}'
# {"80/tcp":[{"HostIp":"0.0.0.0","HostPort":"8080"}]}
```

### 4.4 端口映射不可修改

```bash
docker run -p 8080:80 --name web nginx
# 想改成 8081 → 只能删除重建
docker rm -f web
docker run -p 8081:80 --name web nginx
```

> 回顾 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]]：端口映射是**创建时**确定的，`docker start` 无法变更。

## 五、`EXPOSE` 与 `-p` 的真实关系（常见误解澄清）

| | `EXPOSE`（Dockerfile 中） | `-p`（`docker run` 中） |
|---|---|---|
| **性质** | **声明**（文档性质） | **动作**（真正建立转发规则） |
| 是否真的开放端口 | ❌ **不会** | ✅ 会 |
| 唯一实际作用 | ① 告诉使用者该镜像提供哪个端口 ② 配合 `-P` 选择随机映射哪些端口 | 建立映射 |

**结论**：

> **镜像写了 `EXPOSE 8000` 但 `docker run` 不加 `-p`，外部一样访问不到。**

这是初学者最常见的困惑之一。`EXPOSE` 是"说明书上写着这个设备有个 8000 口"，`-p` 才是"真的把线接上去"。

## 六、排查"端口访问不到"

按这个顺序走，每一步都在排除一个可能性：

```bash
# 第 1 步：容器在运行吗？
docker ps
#   STATUS 是 Up 吗？不是就先解决启动问题

# 第 2 步：端口映射的宿主端口是多少？
docker port <容器名>
#   确认你访问的端口号与这里一致

# 第 3 步：宿主的那个端口真的被监听了吗？
#   Linux/macOS:
lsof -i :8080
#   Windows:
netstat -ano | findstr :8080
#   应该能看到 docker-proxy 或 dockerd 在监听

# 第 4 步：从容器内部访问服务本身，确认服务是活的
docker exec <容器> sh -c "wget -qO- http://localhost:80 || echo failed"
#   如果这一步就失败 → 问题在容器内的服务，不在端口映射

# 第 5 步：确认容器内监听的端口与你映射的一致
docker exec <容器> sh -c "netstat -tlnp || ss -tlnp"
#   如果服务监听的是 127.0.0.1:80（而不是 0.0.0.0:80），
#   那么从容器外部（含宿主）无法访问 —— 见下方陷阱

# 第 6 步：看容器日志
docker logs --tail 50 <容器>
```

### 一个必须知道的陷阱：服务绑定在 `127.0.0.1`

| 服务监听地址 | 容器内可访问 | **从宿主机/其他容器可访问** |
|--------------|-------------|---------------------------|
| `0.0.0.0:8000` | ✅ | ✅ |
| `127.0.0.1:8000` | ✅ | ❌ **不行** |

**这是"端口映射配对了但访问不到"的第二大原因**（第一大是方向写反）。

很多开发框架默认只绑回环地址。必须显式改成 `0.0.0.0`：

```bash
# Flask
flask run --host=0.0.0.0 --port=8000

# uvicorn
uvicorn app:app --host 0.0.0.0 --port 8000

# Django
python manage.py runserver 0.0.0.0:8000
```

> **为什么必须是 `0.0.0.0`**：`0.0.0.0` 表示"监听本机所有网络接口"，包括容器那根通往宿主机的虚拟网卡。`127.0.0.1` 只监听回环接口，而宿主机的请求是从**另一个接口**进来的，所以被拒。
>
> 这条同样适用于 Dockerfile 里的启动命令——**这是容器化 Web 应用最容易漏的一步。**

## 七、端口被占用怎么办

```bash
docker run -p 8080:80 nginx
# docker: Error response from daemon: driver failed programming external
# connectivity ... bind: address already in use
```

### 找出占用者

| 平台 | 命令 |
|------|------|
| Linux / macOS | `lsof -i :8080` 或 `sudo ss -tlnp \| grep 8080` |
| Windows | `netstat -ano \| findstr :8080`，再用 `tasklist /FI "PID eq <PID>"` 查进程名 |

### 三种处理

| 处理 | 说明 |
|------|------|
| **换端口**（最常用） | `-p 8081:80`，改一下就行 |
| 找出并停掉占用者 | 如果是另一个容器：`docker ps \| grep 8080` |
| 确认是僵尸容器 | 有时容器停了但转发规则残留，`docker restart docker`（Linux）或重启 Docker Desktop 可清 |

> ⚠️ **注意"占用者通常是另一个容器"**：初学者常去查宿主进程，其实往往是之前测试留下的一个容器还在跑。**先 `docker ps` 看一遍。**

## 八、Windows / macOS 上的行为差异

因为 Docker 实际跑在一个轻量 Linux 虚拟机里（回忆 [[docker/01-入门阶段-基础教程/第00章-学前准备/0.2-Docker的组成与运行架构]]），端口访问行为与纯 Linux 有差异：

| 场景 | Linux | Windows / macOS |
|------|-------|-----------------|
| 访问 `localhost:<宿主端口>` | ✅ | ✅（Docker Desktop 做了转发） |
| 访问 `<宿主局域网IP>:<宿主端口>` | ✅ 通常可以 | ⚠️ **可能不通**（尤其 macOS 某些版本） |
| 用 `--network host` | ✅ 完整生效 | ⚠️ 效果受限，不等价 |
| 绑定挂载的权限行为 | 严格按 UID | 较宽松（文件共享层做了映射） |
| 容器访问宿主 | `172.17.0.1` 或 `host-gateway` | `host.docker.internal`（原生支持） |

> **实践建议**：**在你的开发生命周期中，至少有一次在 Linux 上验证**。因为生产环境绝大多数是 Linux，而 Windows 上的"能跑"可能掩盖了权限、端口绑定、大小写敏感等问题。

## 九、底层：端口映射是怎么实现的（一句话）

在 Linux 上，Docker 通过两套机制实现端口映射：

| 机制 | 说明 |
|------|------|
| **iptables/nftables 的 DNAT 规则** | 把发往宿主某端口的包改写到容器 IP 的对应端口，由内核处理 |
| **`docker-proxy` 用户态进程** | 某些场景下（如绑定 `127.0.0.1` 或需要避免 DNAT 局限时）由 Docker 的一个进程负责转发 |

| 现象 | 原因 |
|------|------|
| `lsof -i :8080` 看到 `docker-proxy` | 说明走的是用户态转发 |
| 只看到 DNAT 规则，没有进程 | 说明纯内核转发，性能更好 |

> 完整原理（DNAT/SNAT 规则链、veth、`docker0` 网桥）见 [[docker/02-中段阶段-专题精讲/网络进阶与多容器互联/专题概览]]。

## 十、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| `-p` 方向写反 | 容器 Up 但访问不到 | **左宿主、右容器** |
| 忘了 `-p` | 访问不到 | 加上 `-p`；`EXPOSE` 不顶用 |
| 服务绑 `127.0.0.1` | 容器外访问不到 | 启动命令改 `0.0.0.0` |
| 本地开发绑 `0.0.0.0` | 局域网可访问，有风险 | 加 `127.0.0.1:` 前缀 |
| 端口被旧容器占着 | `address already in use` | 先 `docker ps` 查 |
| 想改端口用 `docker start` | 无效 | 删容器重建 |
| 在 macOS 上用宿主局域网 IP 访问 | 可能不通 | 用 `localhost` |
| 只在本机验证就上生产 | Linux 上暴露问题 | 目标平台验证一次 |

## 小结

| 要点 | 内容 |
|------|------|
| 方向 | `-p <宿主端口>:<容器端口>`，**左宿主右容器** |
| 四种形式 | 全接口 / `127.0.0.1:` 只本机（**本地开发推荐**）/ `/udp` 指定协议 / 只写一个端口 = 随机宿主端口 |
| `EXPOSE` vs `-p` | `EXPOSE` 只是声明，`-p` 才真正开放 |
| 排查顺序 | `ps` → `port` → 宿主监听 → 容器内自测 → 监听地址是否 `0.0.0.0` → `logs` |
| 两大隐形原因 | ① 方向写反 ② 服务绑在 `127.0.0.1` |
| 不可修改 | 端口映射是创建时确定的，改需重建容器 |
| 平台差异 | Windows/macOS 用 `localhost` 可以，宿主局域网 IP 可能不通；生产是 Linux，需在 Linux 验证 |

## 练习

1. **验证方向**：分别用 `-p 8080:80` 和 `-p 80:8080` 启动 nginx，用浏览器/`curl` 测试哪个能访问。解释失败的那个为什么容器却显示 `Up`。
2. **验证 `EXPOSE` 不顶用**：`docker run -d --name n1 nginx`（不加 `-p`）。用 `docker port n1` 看输出，然后尝试访问 `localhost:80`，解释结果。
3. **验证绑定地址陷阱**：启动一个只绑回环的服务：
   ```bash
   docker run -d --name localonly -p 9000:9000 python:3.12-slim \
     python -m http.server 9000 --bind 127.0.0.1
   curl -v http://localhost:9000     # 失败
   ```
   然后改成 `--bind 0.0.0.0` 重新运行，再次测试。
4. **练习只绑本机**：用 `-p 127.0.0.1:8080:80` 启动 nginx，然后 `docker ps` 观察 PORTS 列的显示与 `-p 8080:80` 有何不同。
5. **解决端口冲突**：故意占用宿主 8080（用 `python -m http.server 8080`），然后尝试 `docker run -p 8080:80 nginx`，观察报错，用 `netstat`/`lsof` 找出占用者并解决。
6. **完整组合**：写出启动一个 PostgreSQL 容器的完整命令，要求：数据持久化、只允许本机访问、端口 5433、自动重启。给出每一段的解释。
