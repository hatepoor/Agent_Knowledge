# 数据卷与绑定挂载

## 学习目标

读完本篇，你应当能够：

1. 解释"容器中的可写层"与容器生命周期的关系，并说明为什么必须挂载数据
2. 准确区分**数据卷（volume）**、**绑定挂载（bind mount）**、**tmpfs** 三种方式，并为场景选对
3. 正确使用 `-v` 与 `--mount`，说出两者的差别
4. 处理挂载中最常见的两个坑：**权限问题**与**匿名卷堆积**
5. 备份与恢复一个数据卷

## 一、先看问题：容器里的数据存在哪

回忆容器的文件系统结构：

```
容器文件系统 = 镜像的所有只读层  +  一层可写层（Container Layer）
```

你把文件写进容器（比如让 PostgreSQL 写入数据），写的就是那个**可写层**。

### 可写层的问题

| 问题 | 后果 |
|------|------|
| **容器删除，可写层一并删除** | `docker rm` 后数据彻底消失 |
| **容器重建，可写层是新的** | 改名、改端口、改环境变量都需要重建容器，**数据全丢** |
| **不便于备份与迁移** | 数据藏在 Docker 的内部目录里，格式不直观 |
| **写性能较差** | 可写层基于联合文件系统的"写时复制"，比直接写磁盘慢 |
| **无法在多个容器间共享** | 每个容器有自己独立的可写层 |

> **一句话结论**：**任何需要保留的数据都必须挂载出来，绝不能只放在容器的可写层里。**

## 二、三种挂载方式

| | 数据卷（volume） | 绑定挂载（bind mount） | tmpfs |
|---|---|---|---|
| **数据存在宿主机哪里** | Docker 管理的目录（`/var/lib/docker/volumes/<卷名>/`） | **你指定的任意路径** | **内存**（不落盘） |
| **谁管理** | Docker | 你自己 | Docker |
| **写语法** | `-v 卷名:/容器路径` | `-v /宿主/路径:/容器路径` | `--tmpfs /容器路径` |
| **首次挂载时的行为** | 自动创建卷 | 宿主路径不存在会自动创建（**目录**），可能造成空目录覆盖 | —— |
| **可移植性** | ✅ 高（换个机器也能 `docker volume create`） | ❌ 依赖宿主的目录结构 | —— |
| **宿主机直接查看/编辑** | 需要进 Docker 目录（权限麻烦） | ✅ 直接看就是普通文件 | ❌ 看不到 |
| **性能** | 好 | 好（Windows/macOS 上可能较慢） | **最快** |
| **典型用途** | 数据库数据、日志、需长期保留的状态 | 开发时代码热重载、挂配置文件 | 临时缓存、敏感数据的临时处理 |

### 怎么选

```
这个数据需要保留吗？
├── 不需要（临时） → tmpfs 或容器的可写层
└── 需要
    ├── 生产环境（你要的是"可靠 + 可移植"） → ✅ 数据卷
    └── 开发环境（你要的是"能直接在宿主机改文件"） → ✅ 绑定挂载
```

> ⚠️ **一个常见误区**：绑定挂载**不是**"更方便所以更好"。它在生产环境有两个实际风险：① 依赖宿主机上某个具体路径存在且权限正确；② 容器里的进程可能改到宿主机的真实文件。**生产用数据卷，开发用绑定挂载**，这是通行做法。

## 三、数据卷（volume）详解

### 3.1 三种使用形式

```bash
# ① 匿名卷：只写容器路径，Docker 自动起一个随机名字
docker run -v /var/lib/postgresql/data postgres:18

# ② 具名卷（推荐）：卷名:容器路径
docker run -v pgdata:/var/lib/postgresql/data postgres:18

# ③ 先用命令创建（可以用参数精细控制）
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:18
```

| 形式 | 卷名 | 优缺点 |
|------|------|--------|
| 匿名卷 | 随机哈希（如 `a1b2c3...`） | ⚠️ **难以辨认，容易堆积且不敢删** |
| 具名卷 | 你指定（如 `pgdata`） | ✅ **推荐**，一眼看出用途 |
| 预创建 | 你指定 | ✅ 可用 `docker volume create --driver local --opt ...` 配置选项 |

### 3.2 卷的管理命令

```bash
docker volume ls                     # 列出所有卷
docker volume inspect pgdata         # 查看卷的详情（含宿主机真实路径）
docker volume rm pgdata              # 删除卷（⚠️ 数据一并销毁）
docker volume prune                  # ⚠️ 删除所有"无容器使用"的卷
```

`docker volume inspect pgdata` 的关键输出：

```json
[
    {
        "Name": "pgdata",
        "Driver": "local",
        "Mountpoint": "/var/lib/docker/volumes/pgdata/_data",   ← 数据在宿主机的真实位置
        "Labels": null,
        "Scope": "local"
    }
]
```

> ⚠️ **关于 `/var/lib/docker/volumes/...` 这个路径**：
> - Linux 上可以直接访问（需要 root 权限）
> - **Windows / macOS 上访问不到**——因为 Docker 实际跑在一个虚拟机里（回忆 [[docker/01-入门阶段-基础教程/第00章-学前准备/0.2-Docker的组成与运行架构]]）。想操作数据要用容器中转，见下面的"备份与恢复"。
> - ❌ **绝对不要手工去改这个目录下的文件**。Docker 不感知外部改动，可能造成状态不一致。要操作数据用容器或 `docker cp`。

### 3.3 卷的生命周期（关键认知）

> **卷的生命周期独立于容器。**

| 操作 | 容器 | 卷 |
|------|------|-----|
| `docker rm <容器>` | 销毁 | ✅ **保留** |
| `docker rm -v <容器>` | 销毁 | 同时删除它用的**匿名卷**（具名卷仍保留） |
| 重新 `docker run -v pgdata:...` | 新容器 | ✅ 挂载到**同一个卷**，数据还在 |

**这就是"容器删了数据不丢"的实现方式**：

```bash
docker run -d --name pg1 -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:18

# 写点数据…

docker rm -f pg1                                    # 删掉容器

docker run -d --name pg2 -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_PASSWORD=secret postgres:18           # 新容器
# → 数据还在！因为卷没变
```

### 3.4 匿名卷为什么会堆积

```bash
docker run -d postgres:18        # 没写 -v，但镜像的 VOLUME 指令创建了匿名卷
docker rm -f <容器>               # 容器删了，匿名卷还在！
```

**默认情况下 docker rm 不删除匿名卷**。所以反复重建容器会积累大量匿名卷：

```bash
docker volume ls
# DRIVER    VOLUME NAME
# local     3f2a1b8c...      ← 完全不知道是干什么的
# local     7d9e4f2a...
```

**处理方式**：

| 做法 | 说明 |
|------|------|
| 优先用**具名卷** | 能辨认、能判断该不该删 |
| 删除容器时加 `-v` | `docker rm -v <容器>` 连带删除匿名卷 |
| 用 Compose | `docker compose down` **默认保留卷**，`down -v` 才删；且 Compose 创建的卷有项目名前缀，可辨认 |
| 批量清理 | `docker volume prune`，但**先 `ls` 看清有什么** |

> ⚠️ **`docker volume prune` 是本知识库里风险最高的命令之一**。它的语义是"删除**所有**没有被容器使用的卷"——包括你手工创建的、准备给新容器用的具名卷。**执行前必须先 `docker volume ls` 确认。**

### 3.5 `-v` 与 `--mount` 的区别

| | `-v`（老写法） | `--mount`（推荐新写法） |
|---|---|---|
| 语法 | 冒号分隔的紧凑字符串 | 键值对，更明确 |
| 示例 | `-v pgdata:/data` | `--mount type=volume,src=pgdata,dst=/data` |
| **宿主路径不存在时** | **自动创建一个目录**（可能是 bug 来源） | ✅ **报错**，不静默创建 |
| 日志/报错可读性 | 较差 | ✅ 更好 |
| 便捷性 | ✅ 短 | 啰嗦 |

**推荐的判断**：

| 场景 | 用哪个 |
|------|--------|
| 手动敲命令、快速试验 | `-v` 够用 |
| 脚本、Compose、CI | ✅ `--mount`（出错时能立刻发现，而不是默默创建空目录） |

**`--mount` 的完整语法：**

```bash
# 数据卷
--mount type=volume,src=pgdata,dst=/var/lib/postgresql/data

# 绑定挂载
--mount type=bind,src=/home/me/app,dst=/app

# 只读绑定挂载
--mount type=bind,src=/home/me/config,dst=/etc/app,readonly

# 临时内存挂载
--mount type=tmpfs,dst=/tmp
```

### 3.6 只读挂载

```bash
docker run -v /home/me/config:/etc/app:ro nginx         # -v 形式加 :ro
docker run --mount type=bind,src=...,dst=...,readonly nginx   # --mount 形式
```

| 用途 | 说明 |
|------|------|
| 挂配置文件 | 容器只需要读，不该改 |
| 挂 `skills` 目录（沙箱场景） | **这是沙箱安全的关键手段之一**，见 [[docker/沙箱/00-沙箱专题导航]] |
| 防止容器写坏宿主数据 | 安全性提升 |

## 四、最常踩的两个坑

### 坑 1：挂载路径写错，容器启动失败或数据"丢失"

容器镜像里的数据目录是**固定的**，写错就挂到了别的地方。

| 镜像 | 正确的容器内路径 | 常见错误 |
|------|------------------|----------|
| `postgres` | `/var/lib/postgresql/data` | 写成 `/var/lib/postgres` 或 `/data` |
| `mysql` / `mariadb` | `/var/lib/mysql` | 写成 `/var/lib/mysql/data` |
| `redis` | `/data` | 写成 `/var/lib/redis` |
| `mongo` | `/data/db` | 写成 `/data` |
| `nginx`（静态文件） | `/usr/share/nginx/html` | —— |

**验证方法**：用 `docker exec` 进去 `ls` 确认目录内容：

```bash
docker exec my-app ls -la /var/lib/postgresql/data
```

**另一个相关陷阱**：把宿主机上一个**非空目录**绑定挂载到容器里的**非空目录**上，容器原目录的内容会被"遮住"（不是删除，但看不到）。这常发生在挂载 `/app` 时——它把镜像里的代码遮住了。

### 坑 2：权限问题（宿主机文件在容器里写不进去）

**现象**：容器报 `Permission denied`，或 PostgreSQL 报 `could not change permissions of directory`。

**根本原因**：容器内的进程以某个 UID 运行（如 `postgres` 用户是 UID 999，或你的 `appuser` 是 10001），而挂载进来的宿主目录属主是另一个 UID。**Docker 不做 UID 映射**（默认情况下），容器看到的文件权限就是宿主的真实权限。

**排查与解决：**

```bash
# 查宿主目录的属主
ls -ln /home/me/pgdata              # -n 显示数字 UID，而不是名字

# 查容器内进程的 UID
docker exec my-pg id

# 解法 1：修改宿主目录属主（开发环境常用）
sudo chown -R 999:999 /home/me/pgdata

# 解法 2：让容器以指定 UID 运行
docker run --user 1000:1000 -v /home/me/data:/data myapp

# 解法 3（推荐）：改用具名卷 —— Docker 会自动处理好属主
docker run -v pgdata:/var/lib/postgresql/data postgres:18
```

> **为什么解法 3 是推荐的**：**具名卷的属主由 Docker 在首次挂载时按镜像中的目录属主自动设置**。这正是"生产用卷、开发用绑定挂载"这条建议的一部分理由——**绕开了 UID 对齐问题**。

**Windows / macOS 用户注意**：在 Docker Desktop 上，绑定挂载的权限行为与 Linux 不同（因为中间隔着虚拟机与文件共享层）。你在 Windows 上挂载目录通常不会遇到 Linux 那样的 UID 报错，但这也意味着**你在 Windows 上验证通过，部署到 Linux 服务器可能因权限失败**。这类环境差异必须留意。

## 五、备份与恢复

### 5.1 备份一个数据卷

思路：**用临时容器挂载这个卷，把内容打包到宿主机**。

```bash
docker run --rm \
  -v pgdata:/data \
  -v "$PWD:/backup" \
  alpine \
  tar czf /backup/pgdata-backup.tar.gz -C /data .
```

**逐段解释：**

| 片段 | 作用 |
|------|------|
| `--rm` | 用完即删，不留垃圾容器 |
| `-v pgdata:/data` | 把要备份的卷挂到容器内的 `/data` |
| `-v "$PWD:/backup"` | 把宿主当前目录挂到 `/backup`，用于接收备份文件 |
| `alpine` | 用最小镜像（`tar` 是标准工具，alpine 自带） |
| `tar czf /backup/xxx.tar.gz -C /data .` | 打包 `/data` 的内容 |

> **为什么需要"容器中转"**：因为 Windows / macOS 上访问不到 `/var/lib/docker/volumes`；而且即使能访问，也**不该直接操作 Docker 的内部目录**。

### 5.2 恢复一个数据卷

```bash
# ① 建一个新卷（或复用已有的）
docker volume create pgdata-restored

# ② 解包回去
docker run --rm \
  -v pgdata-restored:/data \
  -v "$PWD:/backup" \
  alpine \
  sh -c "tar xzf /backup/pgdata-backup.tar.gz -C /data"
```

### 5.3 数据层备份 vs 应用层备份

| 方式 | 做法 | 优点 | 风险 |
|------|------|------|------|
| **文件层备份**（上面这种） | 直接打包卷目录 | 通用、简单 | ⚠️ **数据库运行中直接打包可能得到不一致的快照** |
| **应用层备份** | 用数据库自己的工具：`pg_dump`、`redis-cli SAVE` | ✅ **保证一致性**，可跨版本恢复 | 需要了解该数据库的工具 |

**对数据库容器的建议**（两条都要做）：

| 场景 | 做法 |
|------|------|
| 逻辑备份 | `docker exec my-pg pg_dump -U app appdb > backup.sql` |
| 物理备份 | 先 `docker stop my-pg`（或进入一致性状态），再打包卷目录 |

> 备份策略的完整讨论见 [[docker/02-中段阶段-专题精讲/数据持久化与备份/专题概览]]。

## 六、完整实战：给 PostgreSQL 挂数据卷

```bash
# ① 创建具名卷
docker volume create pgdata

# ② 启动数据库，数据目录挂到卷上
docker run -d \
  --name my-postgres \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=appdb \
  -p 5432:5432 \
  -v pgdata:/var/lib/postgresql/data \
  --restart unless-stopped \
  postgres:18

# ③ 验证数据目录确实挂上了
docker exec my-postgres df -h /var/lib/postgresql/data
#   输出里应该出现类似 overlay 或卷相关的挂载点

# ④ 写点数据
docker exec -it my-postgres psql -U app -d appdb -c \
  "CREATE TABLE t(id int); INSERT INTO t VALUES (1);"

# ⑤ 删掉容器，重新起一个挂同一卷的容器
docker rm -fv my-postgres
docker run -d --name my-postgres2 ... -v pgdata:/var/lib/postgresql/data postgres:18

# ⑥ 验证数据仍在
docker exec -it my-postgres2 psql -U app -d appdb -c "SELECT * FROM t;"
#   应该仍能查到那一行 → 数据持久化成功
```

> ⚠️ **`docker rm -fv` 里的 `-v`**：它会删除容器的**匿名卷**。因为这里用的是具名卷 `pgdata`，所以 `-v` **不会**删掉它。但如果当初用的是匿名卷，这一下数据就没了。**这就是必须用具名卷的另一个理由。**

## 七、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 数据只放容器可写层 | 容器重建数据全丢 | 必须挂卷 |
| 用匿名卷 | 无法辨认、容易堆积、清理时不敢删 | 用**具名卷** |
| `docker volume prune` 不加确认 | 删掉准备用的卷 | 先 `docker volume ls` |
| 手工改 `/var/lib/docker/volumes` | Docker 状态不一致 | 用容器或 `docker cp` 中转 |
| 挂载路径写错 | 数据写到别处，看起来"丢了" | 查镜像文档确认路径，`exec` 进去验证 |
| 绑定挂载遮住镜像原有内容 | 容器里看不到原文件 | 明确挂载点，或用具名卷 |
| 宿主目录 UID 与容器用户不匹配 | `Permission denied` | `chown`、`--user`，或改用具名卷 |
| Windows 上验证通过就直接上 Linux | 权限行为不同，部署失败 | 在目标平台验证 |
| 数据库运行中直接打包卷 | 备份不一致，恢复后可能损坏 | 用 `pg_dump` 等应用层工具 |

## 小结

| 要点 | 内容 |
|------|------|
| 为什么必须挂载 | 可写层随容器销毁、不便于备份、写性能差、无法共享 |
| 三种方式 | 数据卷（Docker 管理，推荐生产）、绑定挂载（你指定路径，适合开发）、tmpfs（内存） |
| 具名卷 vs 匿名卷 | 必须用**具名卷**：可辨认、好管理、`rm -v` 不会误删 |
| 卷的生命周期 | **独立于容器**。删容器不影响卷，这是数据持久化的原理 |
| `-v` vs `--mount` | `--mount` 报错更清晰、不自动建目录，推荐用于脚本与 CI |
| 两大坑 | ① 挂载路径写错 ② UID 权限不匹配 |
| 备份方式 | 用临时容器 `tar` 打包；数据库另需应用层工具保证一致性 |

## 练习

1. **验证持久化**：按第六节的完整实战走一遍，确认删除容器后数据仍在。
2. **对比三种挂载**：用同一个镜像分别做三次运行——(a) 不挂载 (b) 绑定挂载到宿主目录 (c) 具名卷。每次都在容器里写一个文件，然后删除容器，检查文件是否还在、在宿主机哪里能找到。
3. **触发并修复权限问题**（Linux）：
   ```bash
   mkdir -p /tmp/pgdata && chown root:root /tmp/pgdata
   docker run -d --name pgx -e POSTGRES_PASSWORD=x -v /tmp/pgdata:/var/lib/postgresql/data postgres:18
   docker logs pgx          # 观察权限报错
   ```
   然后分别用 `chown` 和改用具名卷两种方式修复。
4. **找出匿名卷**：
   ```bash
   docker run -d --name t3 -v /data alpine sleep 300
   docker rm -f t3
   docker volume ls          # 有没有多出一个匿名卷？
   ```
   解释为什么它还在，以及如何避免。
5. **备份与恢复**：为练习 1 中的 `pgdata` 卷做一次完整备份，然后删除卷、从备份恢复，并验证数据完整。
