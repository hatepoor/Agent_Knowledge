# 看懂报错信息

## 学习目标

读完本篇，你应当能够：

1. 在 10 秒内判断一条 Docker 报错**属于哪一层**问题
2. 按固定顺序执行排错，而不是盲目重试或百度
3. 独立解决最常见的 12 类报错，包括"容器启动后立刻退出"

## 一、核心方法：先定位层次，再查原因

Docker 的报错看着五花八门，但**来源层次是有限的**。判断出层次，搜索范围和解决路径就缩小了 90%。

```
① 客户端层        你敲的命令本身有问题（拼写、参数）
       ↓
② 连接层          CLI 连不上 daemon
       ↓
③ 服务端层        daemon 拒绝请求（镜像找不到、端口冲突、磁盘满）
       ↓
④ 运行时层        runc 创建容器失败（CMD 命令不存在、权限）
       ↓
⑤ 容器内部层      容器起来了，但里面的程序报错
```

### 快速定位口诀（看报错的前缀）

| 报错开头 | 层次 | 快速判断 |
|----------|------|----------|
| `docker: 'xxx' is not a docker command` | ① 客户端 | 命令拼错了 |
| `docker: command not found` | ① 客户端 | 没装或 PATH 不对 |
| `Cannot connect to the Docker daemon` | ② 连接层 | Docker 没启动 / 权限不足 |
| `Error response from daemon: ...` | ③ 服务端 | daemon 拒绝了，看冒号后面的具体原因 |
| `OCI runtime create failed` | ④ 运行时 | 容器的启动命令有问题 |
| 容器 `Exited (n)`，无明显报错 | ⑤ 容器内 | 进 `docker logs` 看程序自己报了什么 |

**记住这个信号词**：`Error response from daemon:` 意味着**你的命令成功送到了服务端，是服务端拒绝了**。所以问题不在命令语法，而在资源状态（名字重复、端口占用、磁盘满等）。

## 二、通用排查五步法

遇到任何 Docker 问题，按这个顺序走，不要跳：

```bash
# 第 1 步：容器到底在什么状态？
docker ps -a
```
> 看 `STATUS` 列。`Up` 是运行中，`Exited (n)` 是已退出（`n` 是退出码），`Created` 是创建了没启动。**这一步能区分"没起来"和"起来又挂了"，方向完全不同。**

```bash
# 第 2 步：看容器自己的输出
docker logs <容器名>
```
> 容器内程序的报错都在这里。**排错 80% 的时间花在这一步。**

```bash
# 第 3 步：看详细配置与状态
docker inspect <容器名>
```
> 输出很长，重点看 `State`（含 `ExitCode`、`Error`、`OOMKilled`）和 `Config`（环境变量、命令）。

```bash
# 第 4 步：确认环境本身正常
docker info
```
> 磁盘是否还有空间？存储驱动是否正常？

```bash
# 第 5 步：还是不行，就进去看
docker run -it --rm --entrypoint sh <镜像名>
```
> ⚠️ 这一步的前提是**容器能启动**。它用 `sh` 覆盖原有启动命令，进镜像内部检查文件是否存在、依赖装没装。这是"镜像构建问题"的终极手段。

## 三、12 类常见报错逐条详解

### 1. `docker: command not found`

| 项 | 内容 |
|----|------|
| **层次** | ① 客户端 |
| **原因** | Docker CLI 没安装，或装在 PATH 之外 |
| **验证** | `which docker`（Linux/macOS）或 `where docker`（Windows） |
| **解决** | 重新安装；Windows 上注意安装后需**重启终端**让 PATH 生效 |

### 2. `docker: 'docker run' is not a docker command`

| 项 | 内容 |
|----|------|
| **层次** | ① 客户端 |
| **原因** | 命令拼写错误，或把 `docker-compose up` 之类旧写法混进来了 |
| **验证** | `docker --help` 看子命令列表 |
| **解决** | 检查拼写。注意 **Compose 的命令是 `docker compose`，两个词之间有空格**，不是 `docker-compose` |

### 3. `Cannot connect to the Docker daemon at unix:///var/run/docker.sock`

| 项 | 内容 |
|----|------|
| **层次** | ② 连接层 |
| **原因** | daemon 没运行，或客户端连的目标不对 |
| **验证** | `docker version` 看是否有 `Server` 段 |
| **解决** | Windows/macOS：启动 Docker Desktop 并等状态变为 running；Linux：`sudo systemctl start docker`；检查 `docker context ls` 是否切换到了不可用的远程目标 |

### 4. `permission denied while trying to connect to the Docker daemon socket`

| 项 | 内容 |
|----|------|
| **层次** | ② 连接层 |
| **原因** | 当前用户不在 `docker` 组，无权访问 socket |
| **验证** | `groups` 看输出里有没有 `docker` |
| **解决** | `sudo usermod -aG docker $USER` → **必须重新登录**（或 `newgrp docker`） |
| **安全提醒** | 加入该组等于获得 root 等价权限，共享服务器上需评估 |

### 5. `Error response from daemon: No such image: ngix`

| 项 | 内容 |
|----|------|
| **层次** | ③ 服务端（其实是你的输入问题） |
| **原因** | 镜像名拼写错误 |
| **验证** | `docker images` 看本地有什么；`docker search <关键词>` 搜正确的名字 |
| **解决** | 修正镜像名。**常见错法**：`ngix`→`nginx`、`redis-server`→`redis`、`postgresql`→`postgres` |

### 6. `Error response from daemon: pull access denied for xxx, repository does not exist or may require 'docker login'`

| 项 | 内容 |
|----|------|
| **层次** | ③ 服务端 |
| **原因** | 镜像名不存在，或私有镜像未登录 |
| **验证** | 在 <https://hub.docker.com/> 搜该镜像确认名字与 tag |
| **解决** | 核对名字；私有镜像先 `docker login` |
| **注意** | 有些镜像需要带用户名空间，如 `bitnami/postgresql` 而不是 `postgresql` |

### 7. `Error response from daemon: Conflict. The container name "/my-web" is already in use`

| 项 | 内容 |
|----|------|
| **层次** | ③ 服务端 |
| **原因** | 已有同名容器（**包括已停止的**） |
| **验证** | `docker ps -a \| grep my-web` |
| **解决** | 三个选择：删掉旧的（`docker rm my-web`）、给新容器改名、或对旧容器用 `docker start` 而不是 `run` |
| **根因提醒** | 这个报错的高频来源是**忘了 `--rm`**，导致临时容器越积越多 |

### 8. `Error response from daemon: driver failed programming external connectivity ... bind: address already in use`

| 项 | 内容 |
|----|------|
| **层次** | ③ 服务端 |
| **原因** | `-p` 里指定的**宿主端口**已被别的程序占用 |
| **验证** | Linux/macOS：`lsof -i :8080`；Windows：`netstat -ano \| findstr :8080` |
| **解决** | 换一个宿主端口（`-p 8081:80`），或停掉占用者 |
| **注意** | 占用者可能是**另一个容器**，也可能是宿主上的普通程序 |

### 9. `Error response from daemon: no space left on device`

| 项 | 内容 |
|----|------|
| **层次** | ③ 服务端 |
| **原因** | 磁盘满。镜像、容器可写层、卷、日志都可能占满 |
| **验证** | `docker system df` 看各类占比；`df -h` 看分区剩余 |
| **解决** | 见 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.2-磁盘占用与日志清理]] |
| **注意** | ⚠️ **不要上来就 `docker system prune -a --volumes`**，那会连数据卷一起删 |

### 10. `OCI runtime create failed: ... exec: "xxx": executable file not found in $PATH`

| 项 | 内容 |
|----|------|
| **层次** | ④ 运行时 |
| **原因** | 镜像的 `CMD` / `ENTRYPOINT` 里写的命令，容器里**根本没有这个文件** |
| **验证** | `docker run -it --rm --entrypoint sh <镜像名>` 进去 `which <命令名>` |
| **解决** | 修正启动命令；或换一个装了该程序的基础镜像 |
| **典型场景** | 基于 `alpine` 的镜像里通常**没有 bash**，写了 `bash` 就会报这个（改用 `sh`）；基于 `python:slim` 的经常没装 `curl` |

### 11. 容器启动后**立刻退出**，`docker ps` 看不到（最高频问题）

这是最容易被误解的报错：**它本身不是报错，而是"容器的工作做完了"或"主进程崩溃了"。**

```bash
docker ps -a                    # 第 1 步：看到 Exited (n)
docker logs <容器名>             # 第 2 步：看它退出前说了什么
```

**按退出码判断：**

| 退出码 | 含义 | 常见原因 |
|--------|------|----------|
| `0` | 正常结束 | 命令执行完了（如 `docker run ubuntu echo hi`）；或**主进程是后台型程序**（见下） |
| `1` | 通用错误 | 程序启动失败，看日志 |
| `126` | 命令找到但不可执行 | 缺少执行权限 |
| `127` | 命令找不到 | `CMD` 写错 |
| `137` | **被强杀（SIGKILL）** | ⚠️ 最常见原因是**内存超限被 OOM Killer 干掉**，或手动 `docker kill` |
| `143` | 收到 SIGTERM | 正常 `docker stop` 的结果 |

**退出码 `0` 却"不该退出"——最常见的认知误区：**

> 容器只关心它的**主进程（PID 1）**。主进程一退出，容器就结束。
>
> 所以如果你这样启动：`docker run -d ubuntu`（ubuntu 镜像默认没有前台进程），它会**立刻以 0 退出**。
>
> 同样地，如果在 `CMD` 里写了 `service nginx start` 或 `nohup python app.py &`，主进程启动完子进程就结束了，容器跟着退出。

**验证方式**：

```bash
docker run -it ubuntu bash     # 给它一个前台进程（bash），它就会保持运行
docker run -d nginx            # nginx 镜像的 CMD 是前台运行的 nginx，所以能持续运行
```

**这个现象的完整原理**（含 `-d`、`-it`、前台/后台进程的区别）见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]]。

### 12. `exec format error`

| 项 | 内容 |
|----|------|
| **层次** | ④ 运行时 |
| **原因** | 镜像的 CPU 架构与当前机器不匹配 |
| **验证** | `docker inspect <镜像> \| grep Architecture` |
| **解决** | 拉对应架构的镜像（如 Apple 芯片用 `arm64` 变体），或用 `--platform` 指定 |
| **典型场景** | 在 Apple 芯片 Mac 上跑只发布了 amd64 的镜像；或在 Windows 上误用 Windows 容器镜像 |

## 四、一条重要的排错纪律

| 做法 | 为什么 |
|------|--------|
| ❌ **不要盲目重试同一命令** | 容器名冲突、端口占用这类报错，重试一百次结果都一样，只会浪费时间 |
| ❌ **不要一遇到问题就 clean 一切** | `docker system prune -a --volumes` 会删数据卷，可能把数据库数据一起清掉 |
| ❌ **不要直接搜报错全文** | 报错里的容器名、路径、端口是**你环境特有的**，搜到的答案常不匹配 |
| ✅ **搜索时删掉个性化部分** | 例如把 `bind: address already in use: 0.0.0.0:8080` 搜成 `docker bind address already in use` |
| ✅ **先读 `docker logs`** | 容器相关的疑难问题，答案通常就在日志里 |

## 小结

| 要点 | 内容 |
|------|------|
| 核心方法 | 先按报错前缀定位层次（客户端 / 连接 / 服务端 / 运行时 / 容器内），再查具体原因 |
| 信号词 | `Error response from daemon:` = 命令送到了，是服务端拒绝，问题在资源状态 |
| 五步法 | `ps -a` → `logs` → `inspect` → `info` → 进镜像内部查 |
| 最高频问题 | 容器立刻退出。用退出码判断：`0` 正常/主进程后台化，`137` 多为内存超限 |
| 关键认知 | 容器只关心**主进程**，主进程退出容器即结束 |
| 纪律 | 不盲目重试、不一上手就清理 |

## 练习

1. **分类训练**：判断下列报错属于哪一层，并说出第一步该敲什么命令。
   - `docker: Error response from daemon: Conflict. The container name "/web" is already in use`
   - `docker: permission denied while trying to connect to the Docker daemon socket`
   - `docker: Error response from daemon: OCI runtime create failed: exec: "pythonn": executable file not found`
2. **主动制造并修复**：故意跑三次下面的命令，观察并解释每次的结果差异。
   ```bash
   docker run --name t1 alpine echo hello      # 第 1 次
   docker run --name t1 alpine echo hello      # 第 2 次（会报错，为什么？）
   docker rm t1 && docker run --name t1 alpine echo hello   # 第 3 次
   ```
3. **诊断退出问题**：运行 `docker run -d --name test1 ubuntu`，然后 `docker ps -a` 看它的退出码。解释为什么它没有像 nginx 那样持续运行。
4. **诊断资源问题**：运行 `docker run --name test2 -m 20m alpine sh -c "dd if=/dev/zero of=/dev/null bs=1M count=500"`，观察退出码是否为 137，并解释原因。
