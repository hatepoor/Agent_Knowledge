# Docker 的组成与运行架构

## 学习目标

读完本篇，你应当能够：

1. 说出 Docker 由哪几个程序组成，各自负责什么
2. 完整描述"敲下 `docker run nginx` 之后发生了什么"
3. 解释为什么"命令执行成功"不等于"容器没问题"，并能据此定位故障层次
4. 说清 Windows / macOS 上 Docker 为什么需要一个 Linux 虚拟机

## 一、为什么要先学架构

初学者常有一个疑问："我只要会用命令就行了，为什么要了解内部结构？"

理由很实际：**排错时的定位能力完全取决于它。**

同样一个 `docker run` 失败，可能是四个不同层次的问题：

| 现象 | 出错层次 | 排查入口 |
|------|----------|----------|
| `docker: command not found` | 客户端没装 | 检查安装与 PATH |
| `Cannot connect to the Docker daemon` | 客户端连不上服务端 | 启动 Docker Desktop / 检查服务 |
| `docker: Error response from daemon: pull access denied` | 服务端拉镜像失败 | 检查镜像名／登录状态 |
| `OCI runtime create failed` | 底层运行时创建失败 | 检查 `CMD`／`ENTRYPOINT` 写的命令是否存在 |

看懂了架构，你就能**在第几层出错**开始查，而不是盲目重试。

## 二、Docker 的四个组成部分

Docker 不是"一个程序"，而是一组程序按分工协作。自外向内四层：

```
┌─────────────────────────────────────────────────────────────┐
│  ① Docker CLI（客户端）       你敲的 docker 命令             │
│     - 只做参数解析与格式输出，自己不干活                       │
│     - 通过 HTTP API（unix socket 或 TCP）把请求发出去          │
└────────────────────────┬────────────────────────────────────┘
                         │  HTTP（默认 /var/run/docker.sock）
┌────────────────────────▼────────────────────────────────────┐
│  ② Docker daemon（守护进程）  程序名 dockerd                 │
│     - 后台常驻服务，接收客户端请求                             │
│     - 负责镜像管理、网络、卷、构建调度                          │
└────────────────────────┬────────────────────────────────────┘
                         │  gRPC
┌────────────────────────▼────────────────────────────────────┐
│  ③ containerd（容器运行时）                                  │
│     - 真正管容器生命周期：创建、启动、停止、删除                │
│     - 也负责镜像的拉取与解包                                  │
└────────────────────────┬────────────────────────────────────┘
                         │  OCI 规范
┌────────────────────────▼────────────────────────────────────┐
│  ④ runc（低层运行时）                                        │
│     - 按 OCI 规范调用内核 API，创建 namespace / cgroup 并拉进程 │
│     - 干完就退出（它是"一次性"的）                             │
└────────────────────────┬────────────────────────────────────┘
                         │
                    Linux 内核（namespace / cgroup）
```

**另外还有一处不在你机器上：**

```
┌──────────────────────────────────────────────┐
│  ⑤ Registry（镜像仓库）                        │
│     例如 Docker Hub、私有 Harbor               │
│     - pull 时的数据来源，push 时的目的地        │
└──────────────────────────────────────────────┘
```

### 用类比理解这四层

| 层次 | 类比 | 说明 |
|------|------|------|
| CLI | 你去餐厅点菜的**服务员** | 只把需求传下去，不炒菜 |
| daemon | **餐厅经理** | 调度一切：有菜吗？要进货吗？安排给谁做？ |
| containerd | **后厨主管** | 管理做菜的流程与排期 |
| runc | **炒菜的厨师** | 真正动手，做完这一道就撤 |
| registry | **食材供应商** | 缺料时去这里进货 |

服务员的职责只有传递需求，所以他跑在任何地方都能工作——这正是下一节"客户端与服务端分离"的意思。

## 三、`docker run nginx` 的完整旅程

现在把上面这张图变成一条时间线。**这是本篇最值得记住的内容。**

```
你敲下：docker run -d -p 8080:80 nginx
```

| 步骤 | 谁在工作 | 做什么 |
|------|----------|--------|
| 1 | **CLI** | 解析参数：镜像 `nginx`、后台运行 `-d`、端口映射 `8080:80`。发现本地没有这个镜像 |
| 2 | **CLI → daemon** | 通过 unix socket 发 HTTP 请求：`POST /containers/create` |
| 3 | **daemon** | 检查本地是否有 `nginx` 镜像 → 没有 |
| 4 | **daemon → registry** | 向 Docker Hub 请求 `library/nginx:latest` 的 manifest |
| 5 | **daemon** | 按 manifest 逐层下载（已存在的层跳过，这就是"拉第二次很快"的原因） |
| 6 | **daemon → containerd** | 通知：镜像就绪，创建容器 |
| 7 | **containerd → runc** | 传递 OCI 运行时配置 |
| 8 | **runc** | 调用内核：创建 namespace（隔离）、设置 cgroup（限制）、挂载文件系统、在容器内启动进程 `nginx` |
| 9 | **runc** | 启动完成，**runc 进程退出**（它的任务已完成） |
| 10 | **containerd / daemon** | 记录容器状态；CLI 打印容器 ID 并退出（因为 `-d`） |

**几个容易被忽略但很关键的点：**

| 观察 | 含义 |
|------|------|
| 镜像**分层**下载 | 第 5 步中"已存在的层跳过"——这就是为什么基于 `python:3.12` 的镜像第二次拉取很快 |
| `runc` 会**退出** | 不要以为容器是 runc 在管。runc 只负责"创建"，创建完就结束 |
| 容器里的 `nginx` 是**内核里的普通进程** | 你可以在宿主机用 `docker top` 看到它，它的父进程其实在内核层面属于宿主机 |
| CLI 打印完 ID 就退出 | `-d` 的含义是"不等容器输出"。不带 `-d` 时 CLI 会一直挂着显示日志 |

## 四、客户端与服务端分离（这是特性，不是缺陷）

CLI 与 daemon 通过 **API** 通信，而不是"CLI 内部直接调用函数"。这带来一个重要能力：**你可以管理远程机器上的 Docker。**

```bash
# 默认：连本地 socket
docker ps

# 连远程主机（指定守护进程地址）
docker -H tcp://192.168.1.100:2376 ps
```

在较新版本中更推荐用 **context（上下文）** 管理多个目标：

```bash
docker context ls          # 看有哪些可用目标
docker context use remote  # 切换默认目标
```

| 概念 | 说明 |
|------|------|
| **`DOCKER_HOST`** | 环境变量，指定 daemon 地址。不设置则用默认本地 socket |
| **`/var/run/docker.sock`** | Linux 上 CLI 与 daemon 之间的 unix socket 文件（Windows 上是命名管道 `//./pipe/docker_engine`） |
| **`docker context`** | 把"连哪台机器"固化成配置项，避免每次敲 `-H` |

> ⚠️ **安全提示**：能访问 docker socket 等于**拥有宿主机 root 权限**（因为可以起特权容器）。所以 `docker` 组的成员实际上是特权用户——这一点在 [[docker/02-中段阶段-专题精讲/容器安全加固/专题概览]] 会展开。

## 五、Windows / macOS 上的特殊结构（重要）

回忆 0.1 节的结论：**容器共享宿主内核，所以 Linux 容器必须有 Linux 内核。**

但 Windows 和 macOS 的内核不是 Linux。那 Docker Desktop 是怎么让它们跑起 Linux 容器的？

答案是：**Docker Desktop 实际上在后台跑了一个轻量 Linux 虚拟机，真正的 daemon 和容器都在那台虚拟机里。**

```
Windows / macOS
└── Docker Desktop（桌面应用）
    └── 轻量 Linux VM  ← 真正的宿主环境在这里
        └── dockerd（daemon）
            └── containerd → runc
                └── 你运行的容器
```

| 平台 | 实现方式 | 注意点 |
|------|----------|--------|
| **Linux** | 无虚拟机，daemon 直接跑在本机 | 性能最接近原生 |
| **Windows** | 依赖 **WSL 2** 或 Hyper-V 提供 Linux 环境 | 必须开启硬件虚拟化；有 WSL 2 才能跑 Linux 容器 |
| **macOS** | 依赖轻量虚拟化框架（当前为 VirtioFS 文件共享） | 文件共享性能曾是痛点，现已显著改善 |

**这个结构解释了两个常见困惑：**

| 困惑 | 原因 |
|------|------|
| "为什么 Windows 上 `localhost` 能访问容器，但用宿主机 IP 不行？" | 实际涉及虚拟机内的端口转发，行为与纯 Linux 不同（见 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.3-端口映射与访问]]） |
| "为什么容器里访问宿主服务要用 `host.docker.internal`？" | 因为容器的"宿主"其实是那台 Linux VM，不是一个你可以直接写 IP 的普通机器 |

## 六、这张架构图在排错中的直接用法

| 症状 | 按架构定位 | 下一步动作 |
|------|-----------|-----------|
| `docker: command not found` | 第 ① 层没装好 | 检查安装、PATH |
| `Cannot connect to the Docker daemon` | 第 ①→② 之间断了 | 确认 Docker Desktop 已启动（Linux 上确认 `dockerd` 服务） |
| `permission denied ... docker.sock` | ①→② 权限不足 | Linux 上把用户加进 `docker` 组 |
| 拉镜像超时、`WARNING: retrying` | 第 ②→⑤ 网络问题 | 配置镜像加速器 |
| `pull access denied` / `manifest unknown` | 第 ④ 步镜像名/tag 写错 | 核对镜像名与 tag |
| `OCI runtime create failed` | 第 ⑧ 步 runc 失败 | 检查 `CMD`/`ENTRYPOINT` 命令是否存在 |
| 容器瞬间退出 | 第 ⑧ 步起来了但主进程结束 | 看 `docker logs`，见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]] |

## 小结

| 要点 | 内容 |
|------|------|
| 四层结构 | CLI（传话）→ daemon（调度）→ containerd（管生命周期）→ runc（真正创建进程） |
| 外部依赖 | Registry 提供镜像数据，不属于本机 |
| runc 的生命周期 | 创建完容器就退出，不负责后续管理 |
| 分离的意义 | CLI 与 daemon 通过 API 通信，所以可以远程管理（`-H` / `docker context`） |
| 平台差异 | Windows / macOS 上的 daemon 实际跑在一个轻量 Linux 虚拟机里 |
| 排错价值 | 知道每个报错属于哪一层，就不用盲目重试 |
