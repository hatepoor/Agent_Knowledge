# 容器与 Docker 是什么

## 学习目标

读完本篇，你应当能够：

1. 说清"**容器解决了什么问题**"，而不是只记住"容器很轻量"
2. 准确区分**容器**与**虚拟机**，知道两者最容易混淆的地方
3. 说清 **镜像**、**容器**、**仓库** 三者的关系
4. 判断一个场景该不该用容器

## 前置知识

**无。** 本篇不要求任何前置知识。你不需要知道 Linux、不需要知道服务器运维，只要会敲命令行即可。

---

## 一、先看没有容器时的痛苦

假设你写了一个 Python 程序，要交给同事运行。你的环境是 Python 3.12，同事的环境是 Python 3.9，程序里用了 3.10 才有的语法。结果是：**在你机器上能跑，在他机器上报错。**

这就是软件行业几十年的老问题。它的标准表述是"**在我机器上明明能跑啊**"。

问题出在哪？一个程序能否运行，取决于一整套**环境**：

| 依赖层级 | 例子 |
|----------|------|
| 语言版本 | Python 3.12 还是 3.9 |
| 第三方库 | `fastapi==0.115` 还是 `0.104` |
| 系统库 | 有没有 `libpq`、`glibc` 的哪个版本 |
| 操作系统 | Ubuntu 22.04 还是 CentOS 7 |
| 配置文件 | `/etc/` 下某个配置项的值 |
| 环境变量 | `PATH`、`LANG`、`TZ` |

任意一层不一致，程序行为就可能不同。手工对齐这些层非常费劲，而且**换一台机器就要重来一遍**。

于是出现了两种解决方案。

### 方案一：虚拟机

**虚拟机（Virtual Machine，简称 VM）** 的思路是：在物理机器上装一套软件（叫 **Hypervisor**，虚拟机管理程序），让它在物理机上模拟出完整的"假电脑"，每台假电脑里装一个完整的操作系统。

比如你的 Windows 电脑里装了 VMware，在 VMware 里装了 Ubuntu —— 那个 Ubuntu 就是一台虚拟机，它认为自己在独占一台电脑。

这样环境就打包好了。但代价很明显：

| 代价 | 说明 |
|------|------|
| **重** | 每台虚拟机都要跑一个完整操作系统，动辄几个 GB |
| **慢** | 启动要等操作系统引导，通常几十秒到几分钟 |
| **浪费** | 宿主机 16 GB 内存，开 3 台虚拟机可能就满了 |

**根本原因**：如果三台虚拟机装的都是 Linux，那么**三份 Linux 内核在同时运行**，而它们做的几乎是同一件事。这是重复。

### 方案二：容器

容器的思路完全不同：**操作系统内核只留一份，让多个程序共享它。**

具体做法是：内核本身提供了两种能力（这是 Linux 早已具备的，不是 Docker 发明的）：

| 内核能力 | 作用 | 用一句话理解 |
|----------|------|--------------|
| **命名空间（namespace）** | 隔离"看得见什么" | 让这个进程只看得见自己的进程列表、自己的网络、自己的文件系统 |
| **控制组（cgroup）** | 限制"能用多少" | 限制这个进程组最多用 1 个 CPU 核、512 MB 内存 |

把这两种能力组合起来作用在一组进程上，这组进程就**以为自己独占了一台机器**——但实际上它用的是宿主机那同一个内核。

这就是容器。所以：

> **容器 = 一组被内核隔离和限制的普通进程。**

请注意这句话的分量：容器里**没有**独立的操作系统内核，**没有**虚拟硬件。它就是进程，只是被"关"进了一个看不见外面、也出不去的小房间。

### 两种方案对比

| 维度 | 虚拟机 | 容器 |
|------|--------|------|
| 隔离单位 | 一整台机器（含内核） | 一组进程 |
| 是否含独立内核 | **含** | **不含**（共享宿主内核） |
| 体积 | GB 级 | MB 级（取决于镜像） |
| 启动耗时 | 几十秒到几分钟 | **通常在 1 秒以内** |
| 性能损耗 | 较大（虚拟化开销） | 极小（接近原生） |
| 隔离强度 | **更强**（内核都不同） | 较弱（共享内核，见下方陷阱） |
| 能否跑不同内核 | 能（Windows 宿主跑 Linux 虚拟机） | **不能**（Linux 宿主只能跑 Linux 容器） |

**一个重要推论**：正因为容器共享宿主内核，**Windows 上无法直接运行 Linux 容器**，除非先准备一个 Linux 环境。这就是 Docker Desktop 在 Windows 上必须依赖 **WSL 2**（Windows 上的 Linux 子系统）的原因——详见 [[docker/01-入门阶段-基础教程/第00章-学前准备/0.3-跑通第一个容器]]。

## 二、三个必须分清的概念

容器技术里有三个词反复出现，且关系紧密。**先把它们的关系理清，后面一切都顺。**

### 镜像（image）—— 菜谱

**镜像是一个只读的模板**，里面打包了：程序本身 + 它依赖的运行库 + 精简后的系统文件 + 启动配置。

"只读"是关键：你**不能**在镜像里改东西。它就像一张刻录好的光盘。

### 容器（container）—— 照菜谱做出的菜

**容器是镜像的运行实例**。Docker 以镜像为基础，在上面加一层**可写层**，然后启动它，这就成了一个容器。

这个"加一层"的设计很巧妙：

```
容器 = 镜像的只读层（共享，不复制）+ 一层可写层（这个容器独有）
```

后果是：**用同一个镜像起 10 个容器，镜像部分在磁盘上只有一份**，每个容器只额外占用自己改动的部分。这是容器能"轻"的另一个原因。

### 仓库（registry）—— 菜谱的图书馆

**仓库是集中存放镜像的服务**。默认的公共仓库是 **Docker Hub**（<https://hub.docker.com/>）。

你从仓库 `pull`（拉取）镜像，也可以把自建镜像 `push`（推送）上去。

### 三者关系

```
        ①  build（构建）
Dockerfile ──────────────→ 镜像（image）
                              │       ↑
                   ②  pull   │       │  ③  push
                              ↓       │
                        仓库（registry）
                              │
                   ④  run   ↓
                          容器（container）  ← 可以起很多个
```

一条命令串起来看：

```bash
docker pull nginx            # 从仓库把 nginx 镜像拉到本地
docker run -d -p 8080:80 nginx   # 用这个镜像启动一个容器
```

第一行是"从图书馆借菜谱"，第二行是"照菜谱做一份菜"。

## 三、容器带来的四个实际好处

| 好处 | 具体含义 | 实际收益 |
|------|----------|----------|
| **环境一致** | 开发、测试、生产跑的是同一个镜像 | 消灭"在我机器上能跑" |
| **秒级启停** | 不引导操作系统，直接起进程 | 快速部署、快速回滚 |
| **资源密度高** | 一台机器能跑几十上百个容器 | 省机器、省成本 |
| **交付物统一** | 交付的是镜像，不是"文档 + 一堆脚本" | 部署不再依赖人工步骤 |

## 四、容器不适合做什么

技术选型必须知道边界。以下场景**不适合**用容器：

| 场景 | 原因 |
|------|------|
| 需要不同内核（如在 Linux 上跑 Windows 程序） | 容器共享宿主内核，做不到 |
| 需要强安全隔离（多租户、执行不可信代码） | 容器共享内核，**隔离强度弱于虚拟机**。需要额外加固，见 [[docker/02-中段阶段-专题精讲/容器安全加固/专题概览]] |
| 有状态的重型数据库（大规模生产） | 技术上能跑，但存储与高可用需专门设计，不能只靠容器 |
| 需要持久化的图形界面程序 | 容器面向无界面服务，图形化很别扭 |
| 只跑一个本地脚本 | 直接跑脚本更简单，容器是多余的一层 |

> **关于"容器不适合跑数据库"这个说法**：这是一个被过度简化的结论。事实是**本地开发、测试、小型服务用容器跑数据库非常方便**（本知识库的姊妹库 [[postgresql/README]] 就全程用容器跑实例）。真正需要谨慎的是**大规模生产环境**，因为那里涉及存储性能、备份、主从切换等独立课题。

## 五、常见误区（务必看完）

| 误区 | 事实 |
|------|------|
| "容器是轻量级虚拟机" | ❌ 这是最常见的错误说法。虚拟机是**机器级虚拟化**，容器是**进程级隔离**。两者机制完全不同 |
| "容器里有一个精简的操作系统" | ❌ 容器里只有**文件**（系统库、程序），**没有内核**，也没有系统服务 |
| "容器比虚拟机安全" | ❌ 恰好相反。容器共享宿主内核，**内核漏洞可导致逃逸**。安全靠加固，不靠容器本身 |
| "容器启动快是因为优化得好" | ❌ 是因为**不需要引导操作系统**。容器启动本质上就是"启动一个进程" |
| "容器里应该跑多个服务" | ❌ 一个容器跑一个主进程是推荐做法。多服务应拆成多容器（见第 04 章 Compose） |
| "镜像就是一个压缩包" | ❌ 镜像是**分层**结构，层可被共享与复用。这是它比压缩包高效的原因 |

## 小结

| 要点 | 内容 |
|------|------|
| 容器解决什么 | 环境一致性问题："在我机器上能跑" |
| 容器的本质 | 一组被内核**命名空间隔离** + **控制组限制**的普通进程 |
| 与虚拟机的差别 | 虚拟机含独立内核（重、慢、隔离强）；容器共享宿主内核（轻、快、隔离弱） |
| 三件套 | 镜像（模板）→ 容器（实例）→ 仓库（存放处） |
| 关键推论 | 容器共享宿主内核，所以 Linux 宿主跑不了 Windows 容器，Windows 跑 Linux 容器需要 WSL 2 |

## 练习

1. **用自己的话回答**（不要查资料）：如果一个容器里没有操作系统内核，那么容器里的程序调用 `open()` 读文件时，是谁在处理这个请求？
2. **判断选型**：下面三个场景，该用虚拟机、容器，还是都不用？说明理由。
   - (a) 你需要在一台 Linux 服务器上同时跑 20 个互不干扰的小型 Web 服务
   - (b) 你要在 Linux 上运行一个只能跑在 Windows 的旧版财务软件
   - (c) 你要执行一段从网上复制来的、来源不明的 Python 代码
3. **预判下一个问题**：你说"容器共享宿主内核"，那么**容器里的 `/bin/ls` 这个程序文件是从哪来的**？如果 10 个容器都用 `ubuntu` 镜像，磁盘上存了几份 `/bin/ls`？
