# 用 Compose 编排多容器服务

3. 完成启动 → 验证 → 排错 → 清理的完整闭环
4. 说出 `docker compose up` / `restart` / `down` 各自对**数据**的影响

## 一、实战目标

把「一个 Python Web 应用 + PostgreSQL + Redis」编排成一套服务。学完这套，你能套用到绝大多数"应用 + 依赖中间件"的场景。

**项目结构：**

```
myproject/
├── compose.yaml
├── Dockerfile
├── requirements.txt
├── app.py
└── .env                ← 密钥（不进 Git）
```

**`app.py`（最小示例，能验证数据库与缓存连通性）**

```python
import os
import socket
import time

import psycopg
import redis
from fastapi import FastAPI

app = FastAPI()

DB_HOST = os.getenv("DB_HOST", "db")
DB_PORT = int(os.getenv("DB_PORT", "5432"))
DB_USER = os.getenv("DB_USER", "app")
DB_PASSWORD = os.getenv("DB_PASSWORD", "")
DB_NAME = os.getenv("DB_NAME", "appdb")
REDIS_HOST = os.getenv("REDIS_HOST", "cache")

@app.get("/health")
def health():
    """健康检查端点：数据库与缓存都通才算健康"""
    checks = {}
    # 检查数据库
    try:
        with psycopg.connect(
            host=DB_HOST, port=DB_PORT, user=DB_USER,
            password=DB_PASSWORD, dbname=DB_NAME, connect_timeout=2,
        ) as conn:
            conn.execute("SELECT 1")
        checks["db"] = "ok"
    except Exception as e:
        checks["db"] = f"fail: {e}"

    # 检查 Redis
    try:
        redis.Redis(host=REDIS_HOST, port=6379, socket_timeout=2).ping()
        checks["cache"] = "ok"
    except Exception as e:
        checks["cache"] = f"fail: {e}"

    ok = all(v == "ok" for v in checks.values())
    return {"status": "healthy" if ok else "degraded", "checks": checks}

@app.get("/")
def root():
    return {"msg": "hello from container"}
```

**`requirements.txt`**

```
fastapi==0.115.0
uvicorn[standard]==0.32.0
psycopg[binary]==3.2.3
redis==5.2.0
```

**`Dockerfile`**

```dockerfile
FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

# 依赖清单先复制，最大化利用缓存（见 2.2）
COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd -m -u 10001 appuser && chown -R appuser /app
USER appuser

EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

> **注意 `--host 0.0.0.0`**：这是 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.3-端口映射与访问]] 里讲过的关键点。绑 `127.0.0.1` 会导致容器外访问不到。

## 二、完整的 `compose.yaml`

```yaml
name: myproject

services:
  # ─────────── 数据库 ───────────
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: ${DB_NAME}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      # pg_isready 是 postgres 镜像自带的探测工具
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s        # 数据库首次初始化可能较慢，给宽限期
    restart: unless-stopped
    networks:
      - backend
    # ⚠️ 不映射端口到宿主机：应用和数据库在同一网络里，不需要暴露
    #    若你需要在宿主上用 psql 调试，再加 "127.0.0.1:5432:5432"

  # ─────────── 缓存 ───────────
  cache:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]   # 开启 AOF 持久化
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10
    restart: unless-stopped
    networks:
      - backend

  # ─────────── 应用 ───────────
  app:
    build:
      context: .
      dockerfile: Dockerfile
    image: myapp:1.0                 # 构建后打一个明确的名字
    ports:
      - "127.0.0.1:8000:8000"        # 只绑本机（本地开发推荐）
    environment:
      DB_HOST: db                    # ← 服务名即主机名（Compose 自动组网）
      DB_PORT: 5432
      DB_USER: ${DB_USER}
      DB_PASSWORD: ${DB_PASSWORD}
      DB_NAME: ${DB_NAME}
      REDIS_HOST: cache
    depends_on:
      db:
        condition: service_healthy   # ★ 关键：等数据库"就绪"而非仅"启动"
      cache:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "python", "-c",
             "import urllib.request;urllib.request.urlopen('http://127.0.0.1:8000/health')"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 15s
    restart: unless-stopped
    networks:
      - backend

volumes:
  pgdata:
  redisdata:

networks:
  backend:
    driver: bridge
```

**`.env`（与 compose.yaml 同目录，加入 `.gitignore`）**

```
DB_USER=app
DB_PASSWORD=change-me-in-production
DB_NAME=appdb
```

**`.gitignore`**

```
.env
__pycache__/
*.pyc
```

**`.dockerignore`**

```
.git
.env
.env.*
__pycache__
*.pyc
.venv
```

> ⚠️ **`.env` 必须同时出现在 `.gitignore` 与 `.dockerignore` 里**。前者防止密钥进 Git，后者防止 `COPY . .` 把密钥打进镜像（见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.2-构建过程与分层缓存]]）。

## 三、逐段拆解（关键设计）

### 3.1 `db` 服务：为什么把端口映射注释掉

| 考虑 | 说明 |
|------|------|
| **应用与数据库在同一自定义网络** | 应用可以直接用服务名 `db` 访问，**不需要经过宿主机端口** |
| **少暴露一个端口 = 少一个攻击面** | 数据库端口暴露到宿主，等于多一个入口 |
| **需要调试时才临时暴露** | 用 `127.0.0.1:5432:5432`（只本机） |
| **Compose 不允许"额外加参数"** | 若临时需要，可加一个 `compose.override.yaml`，见 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.3-环境变量与多环境配置]] |

**这就是"最小暴露原则"**：只有真正需要外部访问的服务才映射端口。API 需要，数据库和缓存不需要。

### 3.2 `healthcheck` 的写法要点

| 服务 | 检查命令 | 为什么这样写 |
|------|----------|--------------|
| `db` | `pg_isready -U app -d appdb` | PostgreSQL 官方镜像自带此工具，判断"能否接受连接"最准 |
| `cache` | `redis-cli ping` | Redis 自带，返回 `PONG` 即健康 |
| `app` | 请求自己的 `/health` | **检查的是"依赖都通了"，不只是"进程活着"** |

**`start_period` 为什么重要**：数据库首次启动要初始化数据目录、创建用户与库，可能耗时 10-30 秒。如果 `interval` 是 5 秒、`retries` 是 3，那么 15 秒后就被标记为 `unhealthy`，`app` 会一直等不到就绪而卡住。**`start_period` 让这段时间内的失败不计入 `retries`。**

### 3.3 `depends_on` 完整形式的必要性

```yaml
# ❌ 只保证"db 容器被启动了"，不保证"数据库能接受连接"
depends_on:
  - db

# ✅ 等健康检查通过
depends_on:
  db:
    condition: service_healthy
```

| 不加 `condition` 会发生什么 | 说明 |
|----------------------------|------|
| `db` 容器 `Up` 后立刻启动 `app` | 此时 PostgreSQL 还在初始化 |
| `app` 尝试连接 → **`Connection refused`** | 应用可能直接崩溃退出 |
| 若有 `restart`，会反复崩溃重启 | 日志里看到一串连接失败 |

> **实践结论**：**任何"应用依赖数据库/缓存"的场景，都必须写 `healthcheck` + `condition: service_healthy`。** 这是最容易漏、后果最明显的一步。

### 3.4 `command` 覆盖

```yaml
cache:
  image: redis:7-alpine
  command: ["redis-server", "--appendonly", "yes"]
```

| 要点 | 说明 |
|------|------|
| `command` 覆盖镜像的 `CMD` | 语义与 `docker run <镜像> <命令>` 相同 |
| **列表形式更安全** | 避免 shell 解析问题（对应 exec 形式） |
| 数据持久化 | `--appendonly yes` 开启 AOF；配合 `- redisdata:/data` 让数据落盘 |

> ⚠️ **Redis 默认 `save` 策略可能丢数据**：默认快照间隔下，异常宕机可能丢最后几分钟的写入。生产需按 RPO 要求配置 AOF 与 `appendfsync`。详见 [[docker/02-中段阶段-专题精讲/数据持久化与备份/专题概览]]。

## 四、完整操作闭环

### 4.1 启动

```bash
# ① 确认配置无误（排错利器，先跑这个）
docker compose config

# ② 构建并启动（-d 后台）
docker compose up -d --build
```

**`up -d` 的输出会显示每个容器的创建与状态**。注意四个阶段：`Creating`（创建）、`Created`、`Starting`、`Started`。

> **`depends_on` + `service_healthy` 的效果**：你会看到 `app` 的 `Starting` 明显晚于 `db`，且要等 `db` 显示健康后才进行。

### 4.2 验证状态

```bash
docker compose ps
```

输出示例：

```
NAME                IMAGE           STATUS                    PORTS
myproject-app-1     myapp:1.0       Up 30 seconds (healthy)   127.0.0.1:8000->8000/tcp
myproject-cache-1   redis:7-alpine  Up 1 minute (healthy)
myproject-db-1      postgres:18     Up 1 minute (healthy)
```

| STATUS 列 | 含义 |
|-----------|------|
| `Up (healthy)` | ✅ 健康检查通过 |
| `Up (health: starting)` | 正在检查中（看 `start_period`） |
| `Up (unhealthy)` | ⚠️ 检查失败，需要排查 |
| `Exited (n)` | 已退出，看日志 |

### 4.3 功能验证

```bash
# 从宿主机访问应用（端口映射只绑了本机，所以用 localhost）
curl http://localhost:8000/
curl http://localhost:8000/health
```

`/health` 应该返回：

```json
{"status":"healthy","checks":{"db":"ok","cache":"ok"}}
```

**这个输出同时验证了三件事**：应用在跑、数据库可连、缓存可连。

### 4.4 排错

```bash
# 看某个服务的日志（-f 实时跟踪）
docker compose logs -f app
docker compose logs --tail 50 db

# 看所有服务日志
docker compose logs

# 进容器排查
docker compose exec app sh
docker compose exec db psql -U app -d appdb

# 从 app 容器内部测试到 db 的连通性（验证"服务名解析"是否生效）
docker compose exec app python -c "
import socket; s=socket.socket(); s.settimeout(3)
s.connect(('db',5432)); print('db reachable')
"
```

> **`docker compose logs` 的 `-f` 与 `docker logs -f` 相同，且 `Ctrl+C` 不会停容器。**

### 4.5 日常运维

```bash
# 重启某个服务
docker compose restart app

# 只重建应用（改了代码之后）
docker compose up -d --build app

# 停止但不删除（保留容器，之后 start 能恢复）
docker compose stop
docker compose start

# 扩缩容（⚠️ 不能用 container_name，且不能映射固定端口）
docker compose up -d --scale app=3

# 完全清理（停容器 + 删容器 + 删网络，保留卷）
docker compose down

# ⚠️ 危险：连卷一起删
docker compose down -v
```

### 4.6 `up` 与 `restart` 的关键区别

| 命令 | 做什么 | 对配置变更的反应 |
|------|--------|------------------|
| `docker compose up -d` | 对比"期望状态"与"实际状态"，**创建/重建**有差异的容器 | ✅ **会应用配置变更** |
| `docker compose restart` | 只是重启现有容器 | ❌ **完全忽略配置变更** |

> **这是最实用的一条经验**：
> 你改了 compose.yaml（如加了环境变量），执行 `restart` **不会生效**。
> **必须用 `up -d`**——它会检测到配置差异并重建容器。
>
> 这正是 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]] 里"配置只在创建时确定"这条原理在 Compose 层面的体现。

### 4.7 数据的影响（必须记住）

| 命令 | 容器 | 网络 | **卷（数据）** |
|------|------|------|----------------|
| `docker compose stop` | 保留（停止） | 保留 | ✅ 保留 |
| `docker compose down` | 删除 | 删除 | ✅ **保留** |
| `docker compose down -v` | 删除 | 删除 | ❌ **删除** |
| `docker compose up -d --build` | 重建 app | 保留 | ✅ 保留 |

> **`down` 默认保留卷**，这是精心设计的——`up` → `down` → `up` 循环不会丢数据。**只有 `-v` 才会删。**

## 五、常见陷阱汇总

| 陷阱 | 现象 | 处理 |
|------|------|------|
| `depends_on` 只写服务名 | 应用启动时报 `Connection refused` | 加 `healthcheck` + `condition: service_healthy` |
| `start_period` 太短 | 数据库还没初始化完就被判 `unhealthy` | 调大（数据库给 30s+） |
| 改了配置用 `restart` | 配置不生效 | 用 `up -d` |
| `ports` 值不加引号 | 解析异常 | 写成 `"8000:8000"` |
| `.env` 没进 `.dockerignore` | 密钥被打进镜像 | 两处都要排除 |
| 端口映射冲突 | 起不来 | 改宿主端口；或检查是否有旧容器 |
| `container_name` + `--scale` | 扩缩容失败 | 不写 `container_name` |
| 应用绑 `127.0.0.1` | 宿主机访问不到 | 改 `--host 0.0.0.0` |
| 数据库端口暴露到家宽 IP | 安全风险 | 不映射，或只绑 `127.0.0.1` |
| `down -v` 随手敲 | 数据丢失 | 敲前确认 |
| 卷没在顶层声明 | `service "x" refers to undefined volume` | 顶层 `volumes:` 加一行 |

## 六、排错决策树

```
docker compose up -d 之后有问题？
│
├── 容器根本没出现（Invalid）
│   └── docker compose config 看配置错误
│
├── 容器 Exited
│   ├── docker compose logs <服务>      看退出原因
│   └── docker compose ps               看退出码，137 → 内存超限
│
├── 容器 Up 但 unhealthy
│   ├── docker inspect <容器> --format '{{json .State.Health}}'   看检查输出
│   └── 检查 healthcheck 的 test 命令是否写对
│
├── 容器都 Up，但访问不到
│   ├── docker compose ps               确认 PORTS 列有映射
│   ├── 应用是否绑了 0.0.0.0（不是 127.0.0.1）
│   └── 见 3.3 节的排查流程
│
└── 应用日志报"连不上数据库"
    ├── 是否写了 condition: service_healthy
    ├── DB_HOST 是否等于 db 的**服务名**
    └── docker compose exec app 内部测 socket 连通性
```

## 小结

| 要点 | 内容 |
|------|------|
| 编排三要素 | `healthcheck`（判断就绪）+ `depends_on: condition: service_healthy`（等就绪）+ 服务名当主机名（组网） |
| 最小暴露 | 只有需要外部访问的服务才 `ports`；数据库/缓存不映射 |
| 密钥链 | `.env` → 同时进 `.gitignore` 与 `.dockerignore` |
| 配置生效 | 改配置后用 **`up -d`**，不用 `restart` |
| 数据影响 | `stop` 保留；`down` 保留卷；**`down -v` 删卷** |
| 排错三件套 | `docker compose ps` → `docker compose logs <服务>` → `docker compose exec` 进容器测连通 |

## 练习

1. **完整跑通**：按本篇的项目结构搭建并启动，`curl /health` 看到两个 `ok`。
2. **复现并修复启动顺序问题**：删掉 `db` 的 `healthcheck` 与 `app` 的 `condition`，只保留 `depends_on: [db]`，重启后观察 `app` 日志是否出现连接失败。然后恢复正确写法。
3. **验证"restart 不应用配置"**：给 `app` 加一个新环境变量，分别用 `docker compose restart app` 和 `docker compose up -d app` 各试一次，进容器 `env` 检查该变量何时才出现。
4. **验证卷的持久化**：
   ```bash
   docker compose exec db psql -U app -d appdb -c "CREATE TABLE t(x int); INSERT INTO t VALUES (1);"
   docker compose down
   docker compose up -d
   docker compose exec db psql -U app -d appdb -c "SELECT * FROM t;"   # 数据还在吗？
   ```
   然后再执行一次带 `-v` 的 `down` 与 `up`，对比结果。
5. **扩缩容实践**：用 `docker compose up -d --scale app=3` 扩到 3 个副本。观察是否成功；若失败，说出原因（提示：`ports` 与 `container_name`）。
6. **排错演练**：故意把 `app` 的 `DB_HOST` 改成 `database`（不存在的服务名），启动后按第六节的决策树定位问题。
