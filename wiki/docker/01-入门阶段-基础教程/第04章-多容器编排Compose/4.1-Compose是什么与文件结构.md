# Compose 是什么与文件结构

## 学习目标

1. 说出 Compose 解决了 `docker run` 的哪些具体痛点

4. 解释"项目名"对容器名、网络名、卷名前缀的影响
5. 说出 Compose 自动为你做了哪些事（不必再手工创建网络）

## 一、先看 `docker run` 的痛点

假设你要起"应用 + 数据库"两个容器。用 `docker run` 要这么做：

```bash
# ① 手工建网络（否则两个容器不能用名字互访）
docker network create myapp-net

# ② 起数据库
docker run -d --name myapp-db \
  --network myapp-net \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_USER=app \
  -e POSTGRES_DB=appdb \
  -v myapp-pgdata:/var/lib/postgresql/data \
  --restart unless-stopped \
  postgres:18

# ③ 构建自己的应用镜像
docker build -t myapp:1.0 .

# ④ 起应用
docker run -d --name myapp-app \
  --network myapp-net \
  -p 8000:8000 \
  -e DB_HOST=myapp-db \
  -e DB_PASSWORD=secret \
  --restart unless-stopped \
  myapp:1.0
```

**问题一目了然：**

| 痛点 | 具体表现 |
|------|----------|
| **命令太长、易错** | 参数一多就写错、漏参数 |
| **无法版本化** | 这些命令只能存在文档或 shell 脚本里，改了什么没人知道 |
| **启动顺序不可控** | 应用可能比数据库先起来，连不上就崩 |
| **难以复现** | 同事要重建这套环境，得复制粘贴一堆命令 |
| **拆装麻烦** | 停止清理要逐条来，容易漏 |

**Compose 的解法：把这些命令写成一个声明式配置文件。**

```yaml
name: myapp

services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: appdb
    volumes:
      - pgdata:/var/lib/postgresql/data
    restart: unless-stopped

  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      DB_HOST: db
      DB_PASSWORD: secret
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

volumes:
  pgdata:
```

然后：

```bash
docker compose up -d      # 一条命令起全部
docker compose down       # 一条命令停并清理
```

## 二、命令形式：`docker compose`（有空格）

**这是必须先纠正的过时知识。**

| 形式 | 状态 | 说明 |
|------|------|------|
| `docker-compose up`（**连字符**） | ❌ **已废弃** | Compose v1，Python 编写，2014 年起。官方已停止支持 |
| `docker compose up`（**空格**） | ✅ **当前形式** | Compose v2（2020 起）与 v5（2025 起），Go 编写，作为 Docker CLI 的子命令 |

网上大量教程仍写 `docker-compose`。**照抄会出问题**——要么命令不存在，要么行为与文档不符。

### 关于 v2 与 v5

| 版本 | 发布 | 与前一版的关系 |
|------|------|----------------|
| v1 | 2014 | Python，`docker-compose` |
| v2 | 2020 | Go 重写，`docker compose`，依赖 **Compose Specification** 解释文件 |
| v5 | 2025 | **功能与 v2 等同**，区别是提供了官方 Go SDK（可在程序里直接调用 Compose） |

> **不必焦虑版本号**：v2 与 v5 在**配置文件格式与命令**上没有差异。你看到别人写 Compose v2，用的是同一套 `compose.yaml`。

### `version: '3'` 字段已废弃

```yaml
# ❌ 老教程的写法，不要再用
version: '3.8'
services:
  ...
```

**为什么废弃**：v1 时代 `version` 用来声明"用哪一版的文件格式"。Compose v2/v5 改为完全依赖 **Compose Specification**（一个滚动更新的规范），不再需要声明版本号。

**当前行为**：写 `version` 字段会被**忽略**，并在执行时打印一条警告（`the attribute 'version' is obsolete`）。**删掉它。**

## 三、文件命名与位置

| 文件名 | 优先级 | 说明 |
|--------|--------|------|
| `compose.yaml` | ✅ **官方推荐** | 新项目用这个 |
| `compose.yml` | ✅ | 等价 |
| `docker-compose.yaml` | 兼容 | 旧项目常用 |
| `docker-compose.yml` | 兼容 | 旧项目常用 |

**多个文件名同时存在时**，Compose 按固定优先级选择（`compose.yaml` 优先）。**建议只留一个，避免困惑。**

**位置**：默认在执行 `docker compose` 命令的**当前目录**查找。也可以用 `-f` 指定：

```bash
docker compose -f /path/to/compose.yaml up -d
docker compose -f base.yaml -f override.yaml up -d     # 多文件合并
```

## 四、文件结构：四个顶层字段

```yaml
name: myapp              # ① 项目名（可选，默认取目录名）

services:                # ② 必填：定义所有服务（每个服务 ≈ 一个容器）
  web:
    ...

volumes:                 # ③ 可选：声明具名卷
  pgdata:

networks:                # ④ 可选：声明自定义网络（不写则自动创建一个默认网络）
  backend:
```

| 顶层字段 | 作用 | 是否必填 |
|----------|------|----------|
| `name` | 项目名。影响所有资源的命名前缀 | 可选 |
| `services` | **核心**。定义每个容器怎么跑 | ✅ 必填 |
| `volumes` | 声明具名卷，供 `services` 引用 | 可选 |
| `networks` | 声明自定义网络 | 可选（不写则自动创建 `<项目名>_default`） |
| `include` | 引入其他 compose 文件（拆分大型配置） | 可选 |
| `x-*` | 自定义扩展字段（如用 YAML 锚点复用配置） | 可选 |
| ~~`version`~~ | ⚠️ **已废弃，不要写** | —— |

## 五、"项目名"的作用（重要，能解释很多现象）

Compose 会给它创建的**所有资源**加上项目名前缀。理解这一点，就能解释"为什么容器名和我的配置不一样"。

| 资源 | 命名规则 | 示例（项目名 `myapp`） |
|------|----------|------------------------|
| **容器名** | `<项目名>-<服务名>-<序号>` | `myapp-db-1`、`myapp-app-1` |
| **网络名** | `<项目名>_<网络名>` 或 `<项目名>_default` | `myapp_default` |
| **卷名** | `<项目名>_<卷名>` | `myapp_pgdata` |

**项目名的确定顺序：**

| 来源 | 优先级 |
|------|--------|
| `-p` / `--project-name` 命令行参数 | 最高 |
| `COMPOSE_PROJECT_NAME` 环境变量 | ↓ |
| `name:` 顶层字段 | ↓ |
| **所在目录名** | 最低 |

> **`container_name` 字段的陷阱**：Compose 允许用 `container_name: my-db` 固定容器名（不加项目名前缀）。但**这会带来两个问题**：
> ① **无法扩缩容**（`--scale` 会因为名字冲突失败）；
> ② 同一台机器上无法同时运行两个项目。
>
> **结论：一般不要写 `container_name`。** 需要知道容器名时，用 `docker compose ps` 查。

## 六、`services` 下的常用字段

### 6.1 镜像来源：`image` 或 `build`

| 字段 | 含义 |
|------|------|
| `image: postgres:18` | **直接用现成镜像** |
| `build: .` | 从当前目录的 Dockerfile 构建（简写形式） |
| `build: { context: ., dockerfile: Dockerfile.prod, args: {...}, target: prod }` | 完整形式 |
| **两者同时写** | 用 `build` 构建，并给它打上 `image` 指定的名字（**推荐**，便于识别） |

```yaml
services:
  app:
    build: .
    image: myapp:1.0        # 构建后打这个 tag。这样 `docker images` 里能看到明确的名字
```

### 6.2 `ports` —— 端口映射

```yaml
ports:
  - "8000:8000"                    # 宿主 8000 → 容器 8000
  - "127.0.0.1:5432:5432"          # 只绑本机（本地开发推荐）
  - "9090:80/udp"                  # 指定协议
  - "3000"                         # 随机宿主端口
```

> ⚠️ **必须加引号**！`- 8000:8000` 不加引号在 YAML 里有歧义（会被当作"六十进制数字"解析），**必须写成字符串 `"8000:8000"`**。这是 Compose 最经典的坑之一。

### 6.3 `volumes` —— 挂载

```yaml
volumes:
  - pgdata:/var/lib/postgresql/data          # 具名卷（需在顶层 volumes 声明）
  - ./src:/app/src                           # 绑定挂载（相对配置文件的路径）
  - ./nginx.conf:/etc/nginx/nginx.conf:ro     # 只读
```

| 写法 | 类型 |
|------|------|
| 以 `./` 或 `/` 开头 | 绑定挂载 |
| 其他（无路径分隔符） | 具名卷 |

> **相对路径的基准是配置文件所在目录**，不是当前工作目录。这与 `docker run -v` 的行为不同（`docker run` 里 `-v ./x` 也相对当前目录，但含义容易混淆）。

### 6.4 `environment` 与 `env_file`

```yaml
services:
  app:
    environment:                    # 映射写法（推荐，可读性好）
      DB_HOST: db
      DB_PORT: 5432
      DEBUG: "false"                # 注意：值是字符串
    # 或列表写法
    environment:
      - DB_HOST=db
      - DB_PORT=5432
    env_file:                       # 从文件批量读
      - .env
      - .env.local
```

> ⚠️ **不要把密钥直接写在 `compose.yaml` 里并提交到 Git**。用 `env_file` 指向一个被 `.gitignore` 忽略的文件，或使用 `secrets`。见 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.3-环境变量与多环境配置]]。

### 6.5 `depends_on` —— 启动顺序（**有重要陷阱**）

```yaml
depends_on:
  - db                    # 简单形式：只保证"db 先启动"

# 完整形式：能等"健康"
depends_on:
  db:
    condition: service_healthy       # 等 db 的健康检查通过
```

| 关键认知 | 说明 |
|----------|------|
| **简单形式只等"容器启动"，不等"服务就绪"** ⚠️ | 数据库容器 `Up` 了，但数据库进程可能还要几秒才接受连接。此时应用启动**依然会连不上** |
| **正解** | 给被依赖服务加 `healthcheck`，再用 `condition: service_healthy` |

**这是 Compose 里最容易踩的坑**，在下一节 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.2-用Compose编排多容器服务]] 会用完整示例解决。

### 6.6 `healthcheck` —— 健康检查

```yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
  interval: 10s          # 多久检查一次
  timeout: 5s            # 单次检查超时
  retries: 5             # 连续失败几次判定为 unhealthy
  start_period: 30s      # 启动宽限期，期间的失败不计入 retries
```

| 字段 | 含义 |
|------|------|
| `test` | 检查命令。`CMD` 形式（exec）/ `CMD-SHELL` 形式（走 shell） |
| `interval` | 检查间隔 |
| `timeout` | 单次超时 |
| `retries` | 失败多少次后标记为 `unhealthy` |
| `start_period` | **启动宽限期**。对慢启动服务（如数据库初始化）很关键，避免启动阶段就被判失败 |

**健康状态在 `docker compose ps` 的 STATUS 列可见**：`Up (healthy)` / `Up (unhealthy)` / `Up (health: starting)`。

### 6.7 其他常用字段

| 字段 | 作用 | 注意 |
|------|------|------|
| `restart` | 重启策略 | 与 `docker run --restart` 相同 |
| `networks` | 加入哪些网络 | 不写则加入默认网络 |
| `command` | 覆盖镜像的 `CMD` | 列表或字符串形式 |
| `entrypoint` | 覆盖镜像的 `ENTRYPOINT` | —— |
| `container_name` | 固定容器名 | ⚠️ 阻碍扩缩容，一般不用 |
| `profiles` | 按 profile 分组启动 | 实现"可选服务" |
| `deploy.resources.limits` | 资源限制 | 见 [[docker/02-中段阶段-专题精讲/资源限制与性能/专题概览]] |
| `ulimits` | 进程资源限制 | `nofile` / `nproc` 等 |
| `user` | 以哪个用户运行 | 安全加固用 |
| `read_only` | 根文件系统只读 | 安全加固用 |
| `logging` | 日志驱动与选项 | 生产必配 |

## 七、Compose 自动为你做的事

理解了这些，就不会重复劳动：

| Compose 自动做的事 | 说明 |
|--------------------|------|
| ✅ **创建自定义网络** | 默认创建 `<项目名>_default`，把所有服务接进去。**这就是能用服务名互访的原因** |
| ✅ **服务名即主机名** | 应用里写 `DB_HOST=db`，`db` 就是服务名 |
| ✅ **加项目名前缀** | 容器、网络、卷都带前缀，避免与别的项目冲突 |
| ✅ **统一标签** | 所有资源打上项目标签，便于 `down` 时精确清理 |
| ✅ **按依赖顺序启动** | 按 `depends_on` 决定顺序 |
| ✅ **合并多文件配置** | `-f a.yaml -f b.yaml`，后者覆盖前者 |

**所以你不需要**在 compose.yaml 里手工建网络、也不需要给容器起名——这些都由 Compose 处理。

## 八、常用命令速览

| 命令 | 作用 |
|------|------|
| `docker compose up -d` | 创建并启动全部服务（后台） |
| `docker compose up -d --build` | 先重建镜像再启动 |
| `docker compose down` | 停止并删除容器与网络（**保留卷**） |
| `docker compose down -v` | ⚠️ 连**卷一起删**（数据丢失） |
| `docker compose ps` | 查看本项目容器状态 |
| `docker compose logs -f <服务>` | 实时日志 |
| `docker compose exec <服务> <命令>` | 在服务容器内执行命令 |
| `docker compose run --rm <服务> <命令>` | 一次性执行（**不映射端口**） |
| `docker compose build` | 构建镜像 |
| `docker compose pull` | 拉取镜像 |
| `docker compose config` | **打印合并后的最终配置（排错利器）** |
| `docker compose restart` / `stop` / `start` | 重启 / 停止 / 启动 |
| `docker compose up -d --scale <服务>=3` | 扩缩副本数 |
| `docker compose watch` | 监听文件变化自动同步/重建 |

> **`docker compose config` 为什么重要**：它会把多文件合并、变量替换后的**最终结果**打印出来。当"我明明配了但没生效"时，用它确认 Compose 实际读到的是什么。

## 九、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 `docker-compose`（连字符） | 命令不存在或版本不符 | 用 `docker compose`（空格） |
| 写 `version: '3'` | 被忽略，打印警告 | 删掉 |
| `ports` 值不加引号 | YAML 解析异常 | 写成 `"8000:8000"` |
| 以为 `depends_on` 能等就绪 | 应用比数据库先就绪，启动失败 | 加 `healthcheck` + `condition: service_healthy` |
| 写 `container_name` | 无法扩缩容 | 一般不用 |
| 密钥写在 `compose.yaml` 里并提交 | 泄露 | 用 `env_file` + `.gitignore` |
| 卷没在顶层声明 | 报"未定义卷" | 顶层 `volumes:` 里声明 |
| `down -v` 随手敲 | 数据丢失 | 确认后再敲 |
| 绑定挂载用绝对路径 | 换机器就失效 | 用相对配置文件目录的路径 |
| 在错误的目录执行 compose | 找不到文件/项目名不对 | 在配置文件目录执行，或用 `-f` |

## 小结

| 要点 | 内容 |
|------|------|
| Compose 解决什么 | 把一长串 `docker run` 变成声明式配置，可版本化、可复现、可控顺序 |
| 命令形式 | **`docker compose`（空格）**；`docker-compose` 已废弃 |
| `version` 字段 | 已废弃，删掉 |
| 四个顶层字段 | `name`（可选）、`services`（必填）、`volumes`、`networks` |
| 项目名的作用 | 给所有资源加前缀：容器 `项目-服务-序号`、网络 `项目_default`、卷 `项目_卷名` |
| Compose 自动做 | 建自定义网络、服务名即主机名、打标签、按依赖启动 |
| 最大陷阱 | `depends_on` **只等启动不等就绪**，必须配 `healthcheck` |
| 排错利器 | `docker compose config` 看合并后的最终配置 |

## 练习

1. **改造练习**：把第 03 章练习里的那条 PostgreSQL `docker run` 命令改写成一个 `compose.yaml`，用 `docker compose up -d` 启动，验证功能等价。
2. **观察项目名前缀**：
   ```bash
   mkdir -p /tmp/demo && cd /tmp/demo
   # 写入一个最简单的 compose.yaml
   docker compose up -d
   docker compose ps           # 容器名是什么？
   docker network ls           # 网络名是什么？
   docker volume ls            # 卷名是什么？
   ```
   解释这些名字是怎么来的。
3. **验证引号陷阱**：把 `- "8000:8000"` 改成 `- 8000:8000`，执行 `docker compose config`，观察报错或警告。
4. **找出废弃字段**：写一个含 `version: '3.8'` 的 compose.yaml，执行 `docker compose config`，观察输出中对该字段的处理。
5. **验证 `depends_on` 的局限**（重要）：写一个只有 `depends_on: [db]`、没有 `healthcheck` 的配置，启动后立刻看应用日志，观察是否出现"连接被拒绝"。然后加上 `healthcheck` + `condition: service_healthy` 再试。
6. **对比命令**：分别执行 `docker compose config` 与直接阅读你的 `compose.yaml`，指出前者多出了什么（提示：相对路径被转成了什么？）。
