# 环境变量与多环境配置

## 学习目标

读完本篇，你应当能够：

1. **区分两个完全不同的概念**：`compose.yaml` 里的 `${VAR}` 替换 vs 传给容器的环境变量
2. 正确使用 `environment`、`env_file` 与 `.env` 三种机制，并说出各自解决什么问题
3. 排出环境变量的优先级顺序
4. 用多文件合并（`compose.override.yaml`）管理开发/测试/生产配置
5. 用 `profiles` 实现"可选服务按需启动"
6. 说清为什么密钥不该写在 `compose.yaml` 里

## 一、最容易混淆的一点：两个"环境变量"是不同的东西

这是 Compose 里最绕的概念，先看一个例子：

```yaml
services:
  app:
    image: ${APP_IMAGE}:${APP_TAG}          # ← ① 这里是"配置文件里的变量替换"
    environment:
      DB_HOST: db                            # ← ② 这里是"传给容器的环境变量"
      LOG_LEVEL: ${LOG_LEVEL}                # ← 两者在这里交汇
```

| | ① `${VAR}` 替换 | ② 容器环境变量 |
|---|---|---|
| **发生在什么时候** | `docker compose` **解析配置文件时** | 容器**启动时**注入 |
| **谁读取它** | Compose 程序自己 | 容器内的进程（`os.getenv`） |
| **数据来源** | shell 环境变量、`.env` 文件、`--env-file` | `environment` 字段、`env_file` 字段、镜像的 `ENV` |
| **容器里 `env` 能看到吗** | ❌ 看不到 | ✅ 看得到 |
| **失败表现** | 配置解析报 `variable is not set` | 程序里读出 `None` |

> **一句话区分**：
> - **`${VAR}` 是给 Compose 看的**，用来生成最终配置——就像模板填空。
> - **`environment`/`env_file` 是给容器里的程序看的**。

理解了这个区分，下面所有机制都会变得清晰。

## 二、机制一：`.env` 文件（给 Compose 做变量替换用）

**位置**：与 `compose.yaml` 同目录，文件名固定为 `.env`。

**Compose 会自动加载它**，用于替换配置文件里的 `${VAR}`。

```
# .env
APP_IMAGE=myapp
APP_TAG=1.0
DB_USER=app
DB_PASSWORD=change-me
DB_NAME=appdb
LOG_LEVEL=info
```

```yaml
# compose.yaml
services:
  app:
    image: ${APP_IMAGE}:${APP_TAG}        # → myapp:1.0
    environment:
      DB_HOST: db
      DB_USER: ${DB_USER}                 # → app
      DB_PASSWORD: ${DB_PASSWORD}
      LOG_LEVEL: ${LOG_LEVEL}
```

| 要点 | 说明 |
|------|------|
| 文件名**必须**是 `.env`（放在项目目录） | 用 `--env-file` 可指定其他文件 |
| **不会自动注入容器** ⚠️ | `.env` 只用于替换。**不写 `environment` 的话，容器里读不到 `DB_USER`** |
| 语法 | `KEY=value`，不要加 `export`，不要加引号（除非值里有空格） |
| 注释 | `#` 开头 |
| **必须加入 `.gitignore`** | 含密钥 |

**语法细节：**

| 写法 | 含义 |
|------|------|
| `KEY=value` | 基本 |
| `KEY=` | 空字符串 |
| `KEY=${OTHER}` | 引用另一个变量 |
| `KEY=${OTHER:-default}` | 若 `OTHER` 未设置，用 `default` |
| `KEY=${OTHER:?error msg}` | 若 `OTHER` 未设置，**报错退出**（推荐用于必填项） |

> **`${VAR:?err}` 是很有用的防御手段**：把关键变量写成 `${DB_PASSWORD:?必须设置 DB_PASSWORD}`，缺失时会立刻报错，而不是带着空密码启动。

## 三、机制二：`environment`（直接写在配置里）

```yaml
services:
  app:
    environment:
      DB_HOST: db
      DB_PORT: "5432"
      DEBUG: "false"
```

**两种写法等价：**

```yaml
# 映射写法（推荐，可读性好）
environment:
  DB_HOST: db
  DB_PORT: 5432

# 列表写法
environment:
  - DB_HOST=db
  - DB_PORT=5432
```

| 要点 | 说明 |
|------|------|
| ✅ **会注入容器** | 容器里 `env` 能看到 |
| ⚠️ **值类型需要注意** | YAML 会把 `5432` 解析为数字、`false` 解析为布尔。**保险做法是一律加引号** `"5432"` |
| ⚠️ **不要在这里写密钥** | 因为 `compose.yaml` 通常要进 Git |
| 常见用法 | 不该变的值（`DB_HOST: db`）、从 `.env` 转发的变量（`DB_PASSWORD: ${DB_PASSWORD}`） |

## 四、机制三：`env_file`（从文件批量注入容器）

```yaml
services:
  app:
    env_file:
      - .env              # 复用同一个文件
      - .env.local        # 后者覆盖前者
```

| 要点 | 说明 |
|------|------|
| ✅ **会注入容器** | 与 `.env` 的作用完全不同 |
| 可用于**非 `.env` 文件名** | 如 `app.env`、`secrets.env` |
| 多个文件**后者覆盖前者** | 便于分层 |
| 每个文件里也可以写 `KEY=${VAR}`？ | ⚠️ **不会**——`env_file` 里的内容**不做变量替换**（Compose v2 起支持有限形式，容易困惑，**建议避免**） |

**`env_file` 与 `environment` 同时用时：**

```yaml
env_file:
  - .env
environment:
  LOG_LEVEL: debug        # 优先于 env_file 里的 LOG_LEVEL
```

**优先级：`environment` > `env_file`**。

## 五、优先级总表

分两组看，**不要混在一起**。

### 组 1：容器最终拿到的环境变量（从高到低）

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | `docker compose run -e KEY=value` | 命令行临时覆盖 |
| 2 | `environment` 字段 | —— |
| 3 | `env_file` 字段（多个文件时后者优先） | —— |
| 4 | 镜像里的 `ENV`（Dockerfile） | 兜底默认值 |

### 组 2：`${VAR}` 替换的取值来源（从高到低）

| 优先级 | 来源 |
|--------|------|
| 1 | **shell 环境变量**（`export KEY=value` 后执行） |
| 2 | `.env` 文件 |
| 3 | `--env-file` 指定的文件 |

> **注意组 2 的第 1 条**：如果你在 shell 里 `export DB_PASSWORD=xxx`，它会**覆盖 `.env` 里的值**。这既是灵活性，也是"为什么我改了 `.env` 却不生效"的原因之一——**你的 shell 里可能已经有一个同名变量了**。
>
> 排查方式：`echo $DB_PASSWORD` 看 shell 里有没有。

## 六、多环境配置：多文件合并

### 6.1 机制

```bash
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

**规则**：从左到右依次应用，**后面的覆盖前面的**。

| 规则细节 | 说明 |
|----------|------|
| 标量（字符串/数字） | 后者覆盖前者 |
| **映射（映射写法）** | **合并**（键级合并，后者覆盖同名键） |
| **列表** | ⚠️ **替换**（不是追加）——这是最大的陷阱 |
| 服务 | 同名服务合并；新服务追加 |

### 6.2 `compose.override.yaml` 的自动加载

**约定**：`compose.yaml` 或 `docker-compose.yaml` 存在时，Compose 会**自动加载**同目录的 `compose.override.yaml`（若存在）。

**用途**：把"开发环境的特殊配置"放进去，**不用改主文件**：

```yaml
# compose.override.yaml —— 开发专用，被自动加载
services:
  app:
    build:
      target: dev                # 用 Dockerfile 里的 dev 阶段
    volumes:
      - ./src:/app/src           # 源码挂载，实现热重载
    environment:
      LOG_LEVEL: debug
    ports:
      - "127.0.0.1:8000:8000"
      - "127.0.0.1:5678:5678"    # 调试端口

  db:
    ports:
      - "127.0.0.1:5432:5432"    # 开发时暴露数据库便于调试
```

**生产环境则用显式文件组合**（因为生产不该自动加载开发配置）：

```yaml
# compose.prod.yaml —— 生产专用
services:
  app:
    image: registry.example.com/myapp:${APP_TAG:?必须指定版本}
    build: !reset null            # 生产不从本地构建
    environment:
      LOG_LEVEL: info
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

```bash
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

> **`!reset null` 是 Compose 提供的"清空"标签**：因为"列表是替换、映射是合并"，要**删掉**一个继承来的字段，需要用 `!reset`（或 `!override` 用于列表整体替换）。这是多文件合并进阶用法。

### 6.3 三种环境配置的组织方式

| 方式 | 结构 | 适用 |
|------|------|------|
| **overlay 覆盖** | `compose.yaml` + `compose.override.yaml`（开发）/ `compose.prod.yaml`（生产） | ✅ **推荐**。共享部分只写一次 |
| **完全独立的文件** | `compose.dev.yaml`、`compose.prod.yaml` 各自完整 | 差异极大、共享很少时 |
| **一个文件 + profiles** | 用 `profiles` 区分服务 | 差异在"服务是否启用"而非"配置值"时 |

## 七、`profiles`：让服务按需启动

**问题**：有些服务只在特定场景需要（如"管理界面"、"调试工具"、"监控栈"），不想每次 `up` 都起。

**解法**：

```yaml
services:
  app:
    image: myapp:1.0

  db:
    image: postgres:18

  # 只在启用 debug profile 时启动
  adminer:
    image: adminer:latest
    profiles: ["debug"]
    ports:
      - "127.0.0.1:8080:8080"

  # 只在启用 monitor profile 时启动
  grafana:
    image: grafana/grafana:latest
    profiles: ["monitor"]
    ports:
      - "127.0.0.1:3000:3000"
```

| 命令 | 效果 |
|------|------|
| `docker compose up -d` | 只启动**没有 profile** 的服务（`app`、`db`） |
| `docker compose --profile debug up -d` | 加上 `adminer` |
| `docker compose --profile debug --profile monitor up -d` | 全部 |
| `docker compose --profile "*" up -d` | 所有 profile 的服务 |

| 要点 | 说明 |
|------|------|
| 有 `profiles` 的服务**默认不启动** | 这正是目的 |
| **被其他服务 `depends_on` 时会被自动启用** | 即使它的 profile 没激活 |
| 未指定 profile 的命令（如 `ps`）**看不到** profile 服务 | 加 `--profile` 才能看到 |

## 八、密钥的正确处理

### 8.1 为什么不能写在 `compose.yaml` 里

| 风险 | 说明 |
|------|------|
| `compose.yaml` 通常进 Git | 密钥永久留在提交历史里 |
| 即使后来删掉 | Git 历史里仍在，需要重写历史才能清除 |
| 镜像构建时也可能带入 | 如在 `build.args` 里传 |

### 8.2 三种可行方案

| 方案 | 做法 | 适用 |
|------|------|------|
| **`env_file` + `.gitignore`** | 密钥写在 `.env`，`.env` 加入 `.gitignore` 与 `.dockerignore` | ✅ **本地开发、小型项目** |
| **环境变量注入** | 由部署环境（CI/CD、K8s、云平台）注入，配置文件里不出现 | ✅ **生产环境推荐** |
| **Compose `secrets`** | 用 Docker 的 secret 机制，密钥以文件形式挂在容器内 | ✅ 需要更严格隔离时 |

**`secrets` 用法：**

```yaml
services:
  app:
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password    # 程序读这个文件

secrets:
  db_password:
    file: ./secrets/db_password.txt        # 本地文件（须 .gitignore）
    # 或从环境变量取：
    # environment: DB_PASSWORD
```

程序端改为读文件：

```python
import os

def read_secret(name: str) -> str:
    path = f"/run/secrets/{name}"
    if os.path.exists(path):
        with open(path) as f:
            return f.read().strip()
    return os.getenv(name.upper(), "")
```

| 优势 | 说明 |
|------|------|
| 密钥**不出现在环境变量里** | 环境变量容易被 `docker inspect`、「进程环境」等方式看到 |
| 以文件形式挂载在 `/run/secrets/` | 通常用内存文件系统，不落盘 |
| 便于与 K8s 的 Secret 对齐 | 迁移成本低 |

> **关于环境变量 vs 文件传递密钥的权衡**：环境变量方便但**会出现在 `docker inspect` 输出、子进程环境、崩溃转储里**。文件方式更安全但需要改代码。**入门阶段用 `env_file` 即可；生产环境建议向 secrets 演进。**

## 九、一个可直接套用的多环境结构

```
myproject/
├── compose.yaml                 # 共享基础配置（不含密钥）
├── compose.override.yaml         # 开发：源码挂载、调试端口、暴露数据库（自动加载）
├── compose.prod.yaml             # 生产：资源限制、日志轮转、镜像 tag 必填
├── .env                          # 本地开发的值（.gitignore）
├── .env.example                  # ✅ 提交这个：列出所有需要的变量名（不含真实值）
├── .gitignore                    # 含 .env
└── .dockerignore                 # 含 .env
```

**`.env.example`（进 Git，给同事看"需要配哪些变量"）：**

```
# 复制为 .env 后填入真实值
DB_USER=app
DB_PASSWORD=          # 必填
DB_NAME=appdb
APP_TAG=1.0
LOG_LEVEL=info
```

| 命令 | 用途 |
|------|------|
| `docker compose up -d` | 开发（自动加载 override） |
| `docker compose -f compose.yaml -f compose.prod.yaml up -d` | 生产 |
| `docker compose config` | 检查最终配置（**每次改完都跑一遍**） |

## 十、常见陷阱汇总

| 陷阱 | 现象 | 处理 |
|------|------|------|
| 以为 `.env` 会自动注入容器 | 程序里 `getenv` 返回 `None` | `.env` 只用于替换；要注入必须写 `environment` 或 `env_file` |
| 以为 `env_file` 里能做 `${}` 替换 | 变量没被替换 | `env_file` 内容不做替换，改用 `environment` |
| shell 里已有同名变量 | 改了 `.env` 不生效 | `echo $VAR` 检查；或 `unset` |
| `environment` 的值没加引号 | `5432` 变数字、`false` 变布尔，行为异常 | 一律加引号 |
| 列表字段在多文件合并中 | 以为会追加，实际被替换 | 用 `!override`，或完整重写该列表 |
| `.env` 没进 `.gitignore` | 密钥泄露到 Git | 加入 |
| `.env` 没进 `.dockerignore` | 密钥被打进镜像 | 加入 |
| 密钥写在 `compose.yaml` | 提交后永久留在历史 | 改用 `env_file` / `secrets` |
| 用了 `profiles` 但没加 `--profile` | 服务没起来 | 加 `--profile xxx` |
| 生产误加载了 override | 开发配置（如调试端口）进了生产 | 生产显式用 `-f` 指定文件 |

## 小结

| 要点 | 内容 |
|------|------|
| 核心区分 | `${VAR}` 替换是**给 Compose 看的**；`environment`/`env_file` 是**给容器看的** |
| 三种机制 | `.env`（Compose 变量替换，不注入容器）、`environment`（写在配置里，注入）、`env_file`（从文件注入） |
| 容器侧优先级 | `run -e` > `environment` > `env_file` > 镜像 `ENV` |
| 替换侧优先级 | shell 环境变量 > `.env` > `--env-file` |
| 多环境 | `compose.yaml` + `compose.override.yaml`（开发自动加载）/ `compose.prod.yaml`（生产显式指定） |
| 合并规则 | 标量覆盖、**映射合并**、**列表替换**（用 `!reset` / `!override` 控制） |
| `profiles` | 让服务默认不启动，按需 `--profile` 启用 |
| 密钥 | 入门用 `env_file` + 双 `.gitignore`；生产向 `secrets` 或外部注入演进 |

## 练习

1. **验证 `.env` 不注入容器**：
   ```
   # .env
   MY_TEST_VAR=hello
   ```
   ```yaml
   services:
     t:
       image: alpine
       command: ["sh","-c","env | grep MY_TEST_VAR || echo NOT_FOUND; sleep 5"]
   ```
   `docker compose up` 后看日志。然后在 `environment` 里加上 `MY_TEST_VAR: ${MY_TEST_VAR}`，再试一次。
2. **验证优先级**：同一个变量分别放在 `.env`、`env_file`、`environment` 三处，各给不同值，用 `docker compose config` 与容器内 `env` 确认最终值。
3. **验证 shell 覆盖 `.env`**：
   ```bash
   export DB_USER=from_shell
   docker compose config | grep DB_USER
   unset DB_USER
   docker compose config | grep DB_USER
   ```
4. **搭多环境**：为 4.2 节的项目写 `compose.override.yaml`（开发：暴露数据库端口、挂载源码）与 `compose.prod.yaml`（生产：加资源限制、日志轮转）。用 `docker compose config` 分别验证两种组合的差异。
5. **验证列表替换陷阱**：在 `compose.yaml` 里给某服务写 `ports: ["8000:8000"]`，在 `compose.override.yaml` 里写 `ports: ["8001:8000"]`，用 `docker compose config` 看最终 ports 是一个还是两个。
6. **用 profiles**：给项目加一个 `adminer` 服务并使用 `profiles: ["debug"]`。验证：(a) 默认 `up` 不起它 (b) `--profile debug up` 起它。
7. **设计密钥方案**：把你的 `DB_PASSWORD` 从 `environment` 改为 `secrets`，程序改为读 `/run/secrets/db_password`，验证功能不变。
