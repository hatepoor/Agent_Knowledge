# Dockerfile 是什么与指令详解

1. 说出 Dockerfile 的作用，以及它与镜像、容器三者的关系

## 一、为什么需要 Dockerfile

到目前为止你用的是别人做好的镜像。但你的应用需要自己的镜像。

**Dockerfile 就是"如何构建这个镜像"的说明书**，是一份纯文本文件，默认名为 `Dockerfile`（无扩展名）。

| 问题 | Dockerfile 的答案 |
|------|-------------------|
| 基于什么系统 | `FROM` |
| 装了哪些依赖 | `RUN` |
| 代码怎么进去 | `COPY` |
| 怎么启动 | `CMD` / `ENTRYPOINT` |

**它带来的核心价值**：**镜像构建过程可版本化、可复现、可审查**。相比"手工敲一堆命令再 `commit`"，Dockerfile 是声明式的、进 Git 的、能被同事 review 的。

```
Dockerfile  ──docker build──→  镜像(image)  ──docker run──→  容器
（说明书）                      （产品）                     （运行中的服务）
```

---

## 二、一个可用的最小例子

先看完整的，再逐条拆解。

```dockerfile
FROM python:3.12-slim

LABEL maintainer="dev@example.com"

ENV PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd -m appuser && chown -R appuser /app
USER appuser

EXPOSE 8000

CMD ["python", "-m", "uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

构建并运行：

```bash
docker build -t myapp:1.0 .
docker run -d --name app -p 8000:8000 myapp:1.0
```

## 三、指令详解

### 3.1 `FROM` —— 一切的基础

```dockerfile
FROM python:3.12-slim
```

| 要点 | 说明 |
|------|------|
| **必须是第一条有效指令** | 只有 `ARG` 可以放在它前面 |
| **必须指定具体 tag** | 写 `FROM python` 等于 `python:latest`，不可复现 |
| `scratch` | 特殊值，表示"空镜像"，用于构建完全从零开始的镜像（如静态编译的 Go 程序）。见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.3-多阶段构建与最佳实践]] |
| `AS <阶段名>` | 多阶段构建的语法，给这个阶段命名供后续引用 |

**基础镜像怎么选**（这直接影响最终体积与可用工具）：

| 基础镜像 | 体积量级 | 有什么 | 没有什么 |
|----------|----------|--------|----------|
| `python:3.12` | ~1 GB | 完整 Debian + 编译器 + 文档 | —— |
| `python:3.12-slim` | ~150 MB | 精简 Debian + Python | 编译工具（装需要编译的包会缺头文件） |
| `python:3.12-alpine` | ~50 MB | Alpine + Python | **bash**、`curl`、glibc（用 musl） |
| `distroless` | ~20-50 MB | 只有运行时与依赖 | shell、包管理器、任何调试工具 |

> **选型口诀**：能用 slim 就用 slim；需要极致小且愿意承担兼容问题才用 alpine；`distroless` 用于安全要求极高的场景（但**没有 shell 会导致无法进容器排查**，这是重要权衡）。

### 3.2 `RUN` —— 构建时执行

```dockerfile
RUN pip install --no-cache-dir -r requirements.txt
```

这是**构建期**执行，结果**固化进镜像层**。

**两种写法：**

| 形式 | 写法 | shell 解析 | 适用 |
|------|------|-----------|------|
| **shell 形式** | `RUN pip install flask` | ✅ 会经 `/bin/sh -c` 处理 | 需要管道、重定向、变量展开时 |
| **exec 形式** | `RUN ["pip","install","flask"]` | ❌ 直接执行 | 不需要 shell 特性时**更可控** |

**为什么推荐合并 `RUN`：**

```dockerfile
# ❌ 三条 RUN = 三层，且第一层装的缓存留在镜像里
RUN apt-get update
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*

# ✅ 一条 RUN = 一层
RUN apt-get update && \
    apt-get install -y --no-install-recommends curl && \
    rm -rf /var/lib/apt/lists/*
```

原因在第 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.2-构建过程与分层缓存]] 会讲透：**每一层都是只读的，"删除"只是在新层里标记删除，底层数据仍然存在镜像里**。所以"装完再删"必须写在同一层内才有意义。

### 3.3 `COPY` 与 `ADD`

```dockerfile
COPY requirements.txt ./
COPY . .
```

| 指令 | 行为 | 推荐度 |
|------|------|--------|
| `COPY` | 从**构建上下文**复制文件到镜像 | ✅ **首选** |
| `ADD` | 同 `COPY`，但**额外支持自动解压 tar** 和 **从 URL 下载** | ⚠️ 只在需要自动解压 tar 时用 |

**为什么默认用 `COPY`（Docker 官方也这么建议）**：

| 原因 | 说明 |
|------|------|
| `ADD` 的隐式解压**难以预料** | 本意是复制一个 tar 备份文件，结果被解压了 |
| 从 URL 下载**无法校验、不利用缓存** | 应该用 `RUN curl -o xx && 校验` 或 `ADD` 之外的方式 |
| 语义单一 = 更少意外 | `COPY` 就是复制，没有隐藏行为 |

**路径规则（常踩坑）：**

| 写法 | 含义 |
|------|------|
| `COPY . .` | 上下文全部 → 当前 `WORKDIR`。**受 `.dockerignore` 影响** |
| `COPY requirements.txt ./` | **单个文件**复制到目录（推荐这种明确写法） |
| `COPY requirements.txt /app/req.txt` | 目标写完整文件名时，就是重命名 |
| `COPY . /app` | 绝对路径目标 |

> ⚠️ **`COPY . .` 的隐患**：它会把上下文目录里的**所有东西**都复制进去，包括 `.git`、`node_modules`、`.env`、测试数据、本地临时文件。**必须配合 `.dockerignore`**，见第 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.2-构建过程与分层缓存]]。

### 3.4 `WORKDIR` —— 设置工作目录

```dockerfile
WORKDIR /app
```

| 要点 | 说明 |
|------|------|
| 目录**不存在会自动创建** | 不需要先 `RUN mkdir` |
| 对后续**所有**指令生效 | `RUN` / `COPY` / `CMD` 都基于它 |
| 可以多次使用，**相对路径会叠加** | `WORKDIR /a` 后再 `WORKDIR b` → 结果是 `/a/b` |

**为什么不要用 `RUN cd /app`：**

```dockerfile
# ❌ 无效！cd 只在那一条 RUN 里生效，后面的指令还在原目录
RUN cd /app
COPY . .          # 复制到了根目录，不是 /app

# ✅ 正确
WORKDIR /app
COPY . .
```

`RUN cd` 的失效原因是：**每条 `RUN` 都是独立的 shell 会话**，`cd` 的影响不会跨越指令。Docker 官方为此提供了 `WORKDIR`。

### 3.5 `ENV` 与 `ARG` —— 最容易混淆的一对

```dockerfile
ARG APP_VERSION=1.0        # 仅构建期
ENV APP_HOME=/app          # 构建期 + 运行期
```

| | `ARG` | `ENV` |
|---|---|---|
| **生效时期** | ❌ **仅构建期** | ✅ **构建期 + 容器运行期** |
| **能否被 `docker run -e` 覆盖** | 不适用（运行期已消失） | ✅ 能（`-e` 优先级更高） |
| **能否在容器内 `env` 看到** | ❌ 看不到 | ✅ 看得到 |
| **如何传入** | `docker build --build-arg` | 构建时写入，运行时用 `-e` 覆盖 |
| **适用场景** | 构建参数（版本号、镜像源地址） | 运行配置（路径、默认端口） |

**为什么 `ARG` 不能用来传密钥（重要安全点）：**

```dockerfile
# ❌ 危险做法
ARG DB_PASSWORD
RUN echo "password=$DB_PASSWORD" > /app/config
```

原因：**`ARG` 的值会出现在镜像的构建历史里**，任何能拉到这个镜像的人都能查出来：

```bash
docker history --no-trunc myapp:1.0     # 会看到 ARG 的实际值
```

**正确做法**（按推荐度）：

| 方案 | 说明 |
|------|------|
| **运行时传环境变量** | `docker run -e DB_PASSWORD=...`，或 `--env-file` |
| **挂载/Secret** | Compose 的 `secrets`、K8s 的 Secret |
| **BuildKit 的 secret 挂载** | `RUN --mount=type=secret,id=pw ...`，**这是唯一能安全用于构建期的方案** |

### 3.6 `EXPOSE` —— 声明端口

```dockerfile
EXPOSE 8000
```

| 要点 | 说明 |
|------|------|
| **只是文档性质** | 它**不会**真的把端口发布到宿主机 |
| 作用一 | 告诉使用者"这个镜像打算提供哪个端口" |
| 作用二 | 配合 `docker run -P`（大写 P）时，用于选择要随机映射哪些端口 |
| **真正发布端口靠什么** | `docker run -p` 或 Compose 的 `ports` |

> **常见误解**：以为写了 `EXPOSE 8000` 就能从宿主访问。**不行**，必须 `docker run -p 8000:8000`（见 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.3-端口映射与访问]]）。

### 3.7 `VOLUME` —— 声明卷（慎用）

```dockerfile
VOLUME /var/lib/postgresql/data
```

| 要点 | 说明 |
|------|------|
| 作用 | 声明该路径应作为数据卷，Docker 会为其创建**匿名卷** |
| **主要风险** ⚠️ | 如果使用者忘了显式挂载，Docker 会为每次 `run` 创建**新的匿名卷**——**数据看似保存了，实际下次启动读不到** |
| 建议 | 在 Dockerfile 里声明后，**务必在文档与 Compose 里明确要求显式挂载** |

> **这个坑很隐蔽**：`docker run postgres:18` 不写 `-v` 时，PostgreSQL 会把数据写进一个匿名卷。你以为数据在容器里，其实在卷里；下次 `docker run` 又创建一个新卷，于是"数据丢了"。**永远显式挂载数据目录**。

### 3.8 `USER` —— 切换用户（安全关键）

```dockerfile
USER appuser
```

| 要点 | 说明 |
|------|------|
| **默认是 root** | 不写 `USER`，容器内进程就是 root。**这是生产环境的主要风险之一** |
| 影响范围 | 后续所有 `RUN`，以及容器启动时的主进程 |
| 一般写法 | 先 `RUN useradd ...` 创建用户，在**装完依赖之后**再 `USER` 切换 |
| 关于 `USER` 与 `WORKDIR` 的顺序 | 切换用户后如果 `WORKDIR` 目录权限不对会失败，注意 `chown` |

```dockerfile
RUN useradd -m -u 10001 appuser && chown -R appuser /app
USER appuser
```

> **关于 `USER 10001` 与 `USER appuser`**：用**数字 UID** 更稳妥——因为用户名在不同系统上可能映射到不同 UID，Kubernetes 的 `runAsNonRoot` 校验也要求能明确判断非零。安全加固细节见 [[docker/02-中段阶段-专题精讲/容器安全加固/专题概览]]。

### 3.9 `LABEL` —— 元数据

```dockerfile
LABEL maintainer="dev@example.com" \
      org.opencontainers.image.source="https://github.com/me/repo" \
      org.opencontainers.image.version="1.0.0"
```

| 要点 | 说明 |
|------|------|
| 纯元数据，不影响运行 | 但**对镜像治理很有用**（溯源、合规、自动化） |
| `MAINTAINER` 已废弃 ⚠️ | 用 `LABEL maintainer=` 替代 |
| 推荐的标准化键前缀 | `org.opencontainers.image.*`（OCI 标准） |

### 3.10 `CMD` 与 `ENTRYPOINT` —— 本篇最重要的一节

这两个指令都指定"容器启动时执行什么"，但行为差别大，是初学者最大的困惑源。

#### 各自动作

| 指令 | 作用 | 能否被 `docker run` 覆盖 |
|------|------|------------------------|
| `CMD` | 提供**默认命令**（或默认参数） | ✅ **能被完全覆盖** |
| `ENTRYPOINT` | 提供**固定入口** | ❌ 不易被覆盖（需 `--entrypoint` 显式指定） |

#### 两种写法（shell 形式 vs exec 形式）

这是**另一个必须掌握的区分**：

| 形式 | 写法 | 实际执行的命令 | 信号传递 |
|------|------|---------------|----------|
| **exec 形式** ✅ | `CMD ["python","app.py"]` | 直接执行 `python`，PID 1 = python | ✅ 信号直达应用 |
| **shell 形式** ⚠️ | `CMD python app.py` | `/bin/sh -c "python app.py"`，PID 1 = sh | ❌ 信号发给 sh，应用可能收不到 |

> ⚠️ **优先用 exec 形式（方括号 JSON 数组）**。shell 形式会让 `sh` 成为 PID 1，导致：
> - `docker stop` 发的 SIGTERM 被 `sh` 吃掉，**应用收不到优雅停止信号**（可能被 10 秒后 SIGKILL 强杀，丢数据）
> - 应用的退出码被 `sh` 包装，**退出码失真**

#### 两者组合的行为矩阵（务必理解）

| Dockerfile | `docker run <镜像>` | `docker run <镜像> arg1 arg2` |
|-----------|---------------------|------------------------------|
| 只有 `CMD ["c1","a"]` | 执行 `c1 a` | **替换为** `arg1 arg2` |
| 只有 `ENTRYPOINT ["e1"]` | 执行 `e1` | 执行 `e1 arg1 arg2`（**追加**） |
| `ENTRYPOINT ["e1"]` + `CMD ["a"]` | 执行 `e1 a`（CMD 作为默认参数） | 执行 `e1 arg1 arg2`（`CMD` 被替换，`ENTRYPOINT` 保留） |
| `ENTRYPOINT ["e1","a"]` + `CMD ["b"]` | 执行 `e1 a b` | 执行 `e1 a arg1 arg2` |

**记忆口诀：**

> - **`CMD` 是"可被替换的默认值"**
> - **`ENTRYPOINT` 是"不会被替换的主体"**
> - **`CMD` 的内容会作为 `ENTRYPOINT` 的默认参数**
> - **`docker run` 后面跟的东西，永远替换 `CMD`，永远追加给 `ENTRYPOINT`**

#### 该怎么选

| 场景 | 推荐 |
|------|------|
| 通用基础镜像（如 `python`、`nginx`） | 只写 `CMD`，让人可以自由覆盖（用 `python:3.12` 后跟任意脚本很自然） |
| 应用镜像（固定就要启动这个服务） | `ENTRYPOINT` + `CMD` 组合：`ENTRYPOINT ["python","-m","uvicorn"]`、`CMD ["app:app"]` |
| 命令行工具的镜像 | 只写 `ENTRYPOINT`，让参数直接透传 |

#### 覆盖方式

```bash
# 覆盖 CMD：直接在镜像名后追加
docker run myapp:1.0 python other.py

# 覆盖 ENTRYPOINT：用 --entrypoint
docker run --entrypoint sh -it myapp:1.0

# 覆盖 entrypoint 并给参数
docker run --entrypoint python myapp:1.0 -c "print('hi')"
```

### 3.11 其余指令简表

| 指令 | 作用 | 备注 |
|------|------|------|
| `HEALTHCHECK` | 定义健康检查命令 | Docker 据此判断容器"是否真的可用"，见 [[docker/01-入门阶段-基础教程/第04章-多容器编排Compose/4.2-用Compose编排多容器服务]] |
| `SHELL` | 指定后续 `RUN` 用哪个 shell | 默认 Linux 是 `/bin/sh -c`；Windows 镜像里需要改成 `cmd /S /C` |
| `STOPSIGNAL` | 指定 `docker stop` 发什么信号 | 默认 `SIGTERM`。某些程序需要 `SIGQUIT` 等 |
| `ONBUILD` | 延迟到别人以本镜像为基础时才执行 | 少用；会让下游构建行为不透明 |

## 四、指令顺序的推荐结构

```dockerfile
① FROM          基础镜像（固定版本）
② LABEL         元数据
③ ARG           构建期变量
④ ENV           环境变量
⑤ WORKDIR       工作目录
⑥ COPY 依赖清单 + RUN 装依赖      ← 变化频率低，放前面以利用缓存
⑦ COPY 源码                        ← 变化频率高，放后面
⑧ USER          切非 root 用户
⑨ EXPOSE        声明端口
⑩ HEALTHCHECK   健康检查
⑪ ENTRYPOINT / CMD   启动命令
```

**这个顺序的核心逻辑在第 ⑥⑦ 步**：**变化频率低的放前面，变化频率高的放后面**。因为一旦某一层变了，它**之后的所有层**缓存都会失效。

> 如果顺序写反（先 `COPY . .` 再装依赖），那么**你每改一行代码，都要重新装一遍依赖**。这是最影响开发体验的 Dockerfile 错误。

## 五、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 `FROM python`（省 tag） | 不可复现 | 固定版本：`python:3.12-slim` |
| `RUN cd /app` | 后续指令仍在原目录 | 用 `WORKDIR` |
| 用 `ADD` 复制普通文件 | 行为不透明 | 用 `COPY` |
| `COPY . .` 无 `.dockerignore` | 把 `.git`/`.env`/`node_modules` 打进镜像，巨大且**可能泄露密钥** | 配 `.dockerignore` |
| 多条 `RUN` 装完又删缓存 | 删除无效，镜像仍大 | 合并到同一条 `RUN` |
| 用 `ARG` 传密钥 | 密钥留在 `docker history` 里 | 运行时传环境变量，或 BuildKit secret |
| `CMD` 用 shell 形式 | 信号传递失效，退出码失真 | 用 exec 形式 `CMD ["a","b"]` |
| `CMD` 里写后台命令 | **容器立刻退出** | 前台运行 |
| 把依赖安装放到 `COPY . .` 之后 | 改代码就重装依赖，构建极慢 | 依赖清单先复制 |
| `VOLUME` 声明后不显式挂载 | 数据写进匿名卷，看似丢失 | 文档与 Compose 中强制显式挂载 |

## 小结

| 要点 | 内容 |
|------|------|
| 定位 | Dockerfile 是"构建镜像的说明书"，进 Git、可审查、可复现 |
| 必用 | `FROM`（固定版本）、`WORKDIR`（不用 `RUN cd`）、`COPY`（不用 `ADD`） |
| `ENV` vs `ARG` | `ENV` 构建+运行期都在；`ARG` 仅构建期，**会留在 history 里，不能传密钥** |
| `CMD` vs `ENTRYPOINT` | `CMD` 可被替换（且作为 `ENTRYPOINT` 的默认参数）；`ENTRYPOINT` 不易被替换 |
| 写法 | 一律用 **exec 形式**（`["a","b"]`），保证信号与退出码正确 |
| 顺序原则 | 变化频率低的指令放前面，让缓存最大化生效 |
| 安全 | 最后 `USER` 切非 root；不把密钥写进任何构建期变量 |

## 练习

1. **写第一个 Dockerfile**：在空目录里创建 `Dockerfile`，目标是运行一个打印 hello 并保持运行的程序。要求：基于 `python:3.12-slim`、设置 `WORKDIR /app`、使用 exec 形式的 `CMD`。构建并运行它。
2. **验证 `CMD` 可被覆盖**：
   ```bash
   docker build -t cmddemo .
   docker run --rm cmddemo                       # 默认行为
   docker run --rm cmddemo python -c "print('覆盖成功')"   # 覆盖 CMD
   ```
3. **验证 `ENTRYPOINT` 的行为**：把 `CMD` 改成 `ENTRYPOINT ["python"]`，重新构建。分别运行 `docker run --rm cmddemo` 和 `docker run --rm cmddemo -c "print('追加参数')"`，解释差异。
4. **实验 `ARG` 会泄露**：
   ```dockerfile
   FROM alpine:3.21
   ARG MY_SECRET=abc123
   RUN echo "use it"
   ```
   构建后执行 `docker history --no-trunc <镜像>`，观察能否看到 `abc123`。
5. **修复错误顺序**：下面这个 Dockerfile 为什么会让"改一行代码就重装依赖"？写出修正版本。
   ```dockerfile
   FROM python:3.12-slim
   WORKDIR /app
   COPY . .
   RUN pip install -r requirements.txt
   CMD ["python","app.py"]
   ```
