## 一、构建的第一步：把上下文发给守护进程

这条命令里的 `.` 常被当作"随便写的"，其实它**决定了哪些文件能进入镜像**。

```bash
docker build -t myapp:1.0 .
#                          ↑ 这就是"构建上下文"（build context）
```

### 发生了什么

回忆 [[docker/01-入门阶段-基础教程/第00章-学前准备/0.2-Docker的组成与运行架构]]：`docker build` 是 **CLI 把请求发给 daemon**。而 daemon 可能在同一台机器，也可能在**远程主机**。

所以：

> **`docker build` 会先把上下文目录的整个内容打包，发送给 daemon。Dockerfile 里的 `COPY` 只能从这个包里取文件——它读不到上下文之外的任何路径。**

```
宿主机                                    daemon（可能在远程）
  │                                            │
  ├── 上下文目录 (.)  ──打包传输──→  接收
  │     ├── Dockerfile                         │
  │     ├── app.py                             │
  │     └── ...                                │
  │                                            ↓
  └── /etc/passwd  ← COPY 读不到！        在这个包里执行 COPY
```

### 这直接导致两个重要后果

| 后果 | 说明 |
|------|------|
| **上下文越大，构建越慢** | 传输本身要时间。如果上下文里有几十 GB 的数据，每次构建都要先传 |
| **`COPY ../xxx` 一定失败** | Dockerfile 不能引用上下文之外的路径（绝对路径也不行） |

```dockerfile
COPY ../requirements.txt ./     # ❌ 报错：forbidden path outside the build context
COPY /home/me/app.py ./         # ❌ 同上
```

**正确做法**：把 `Dockerfile` 放在项目根目录，让需要的文件都在上下文中；或用 `-f` 指定 Dockerfile 位置但**上下文仍指向需要的目录**：

```bash
docker build -f docker/Dockerfile.prod -t app:prod .    # Dockerfile 在子目录，上下文仍是根目录
```

## 二、`.dockerignore`：不做会有什么具体后果

`.dockerignore` 放在**上下文目录**（通常与 Dockerfile 同级），语法类似 `.gitignore`。

```
.git
.gitignore
node_modules
__pycache__
*.pyc
.venv
.env
.env.*
*.log
data/
tests/
docs/
.DS_Store
Dockerfile
docker-compose*.yml
README.md
```

### 不做会发生的四件具体的事

| # | 后果 | 说明 |
|---|------|------|
| 1 | **构建变慢** | `.git` 可能有几百 MB 历史；`node_modules` 动辄上千个文件。每次构建都要打包传输 |
| 2 | **`.env` 密钥被打进镜像** ⚠️ | `COPY . .` 会把 `.env` 一起复制。**镜像可能被推到仓库，密钥直接泄露** |
| 3 | **宿主机的构建产物污染镜像** | 宿主上编译出的 `.pyc`、`node_modules` 可能是**别的平台**的，在容器里运行会出错 |
| 4 | **缓存频繁失效** | 日志、临时文件、`.git` 里的引用变化都会改变层内容，导致后面的缓存全部作废 |

> ⚠️ **第 2 条最严重**：很多人以为"`.env` 不在 Git 里就安全了"，但 `COPY . .` 会把**工作目录里实际存在的所有文件**复制进去——`.gitignore` 对 Docker 构建**完全没有作用**。**必须单独写 `.dockerignore`。**

### 关于 `Dockerfile` 是否要排除

把 `Dockerfile` 自己也写进 `.dockerignore` 是常见做法，但要注意：

| 场景 | 是否需要 |
|------|----------|
| 只有 `COPY . .`，不需要 Dockerfile 进镜像 | ✅ 排除它 |
| 用了多阶段构建、后续阶段需要引用它 | 通常不需要排除 |

**判断标准**：**这个文件进镜像有用吗？** 没用就排除。

## 三、镜像分层：一切缓存与瘦身问题的根源

### 层是怎么形成的

**Dockerfile 里几乎每条指令都会产生一层**。

```dockerfile
FROM python:3.12-slim        → 层 1（基础镜像的层，多个）
WORKDIR /app                 → 层 2（只是元数据，几乎不占空间）
COPY requirements.txt ./     → 层 3（文件内容进这一层）
RUN pip install -r requirements.txt   → 层 4（装出来的包全在这层）
COPY . .                     → 层 5（源码）
CMD [...]                    → 层 6（元数据）
```

### 层的三条性质

| 性质 | 含义 | 影响 |
|------|------|------|
| **层是只读的** | 构建完成后层不可修改 | 所以"修改"实际是"在新层里写新版本" |
| **层可共享** | 相同内容的层在多个镜像之间只存一份 | 所以 10 个基于 `python:3.12-slim` 的镜像不会重复占基础镜像的空间 |
| **层是累加的** | 容器的最终文件系统 = 所有层按顺序叠加 | 所以**后面的层"覆盖"前面的层，但前面的数据仍在** |

### 最关键的一条推论：删除不能让镜像变小

```dockerfile
# ❌ 这样写，镜像依然很大
FROM debian:12
RUN apt-get update && apt-get install -y build-essential    # 层 A：约 300 MB
RUN apt-get purge -y build-essential && apt-get autoremove  # 层 B：删除标记
```

为什么没用？因为：

```
层 A（只读）：/usr/bin/gcc 等文件存在      ← 300 MB 永远在
层 B（只读）：标记"/usr/bin/gcc 已删除"    ← 只是标记
最终视图：文件"看不见"，但层 A 的数据从未消失
```

**正确写法（装和删放在同一层内）：**

```dockerfile
RUN apt-get update && \
    apt-get install -y --no-install-recommends build-essential && \
    make && make install && \
    apt-get purge -y --auto-remove build-essential && \
    rm -rf /var/lib/apt/lists/*
```

**为什么同层内有效**：同一层里，"创建文件"与"删除文件"的净结果会被合并计算——文件从未被写入这一层，所以不占空间。

### 用 `docker history` 看每层多大

```bash
docker history myapp:1.0
```

```bash
docker history myapp:1.0 --no-trunc --format "table {{.Size}}\t{{.CreatedBy}}"
```

| 观察要点 | 说明 |
|----------|------|
| `SIZE` 是**这一层的大小** | 不是净增量。所以会出现"某层 `RUN rm -rf` 却仍然很大"的情况 |
| 显示 `<missing>` 或 `0B` | 纯元数据层（`CMD`、`ENV`、`LABEL`） |
| **用它定位"哪一层最大"** | 这是镜像瘦身的第一步诊断 |

## 四、缓存机制：为什么第二次构建很快

### 缓存如何命中

Docker 构建每一层时，会计算一个"缓存键"，包含：

| 输入项 | 说明 |
|--------|------|
| 父层的 ID | 上一层变了，本层缓存必然失效 |
| **指令本身** | 指令文本变了就失效（如 `RUN pip install flask` → `RUN pip install fastapi`） |
| **`COPY`/`ADD` 的文件内容校验和** | 文件内容变了就失效（**注意：是内容，包含 mtime 等元数据**） |
| `ARG` 的值（若该指令引用了它） | 如 `RUN echo $VERSION`，`VERSION` 变了就失效 |

**命中则复用缓存层，跳过执行；未命中则重新执行该层，并且之后的所有层缓存全部失效。**

### 关键推论：缓存失效是"连锁"的

```
层1 FROM          ✅ 命中
层2 WORKDIR       ✅ 命中
层3 COPY reqs     ❌ 改了 requirements.txt → 未命中
层4 RUN pip install   ⛔ 强制重建（因为父层变了）
层5 COPY . .          ⛔ 强制重建
层6 CMD               ⛔ 强制重建
```

> **这就是"指令顺序决定构建速度"的原因**：把易变的放前面，会导致后面所有层反复重建。

### 顺序对比

```dockerfile
# ❌ 慢：改一行代码就重装依赖
COPY . .                              # 源码一变，这层就变
RUN pip install -r requirements.txt   # 父层变了 → 依赖全部重装（可能几分钟）

# ✅ 快：改代码不影响依赖层
COPY requirements.txt ./               # 依赖清单很少变
RUN pip install -r requirements.txt    # 这层长期命中缓存
COPY . .                               # 只有这层及之后重建（秒级）
```

### 什么时候会"意外"失效

| 现象 | 原因 | 处理 |
|------|------|------|
| 什么都没改，缓存却失效了 | 文件 mtime 变化（Git 切换分支、复制文件等） | 换用 BuildKit；或对不常变的文件用 `COPY --link` |
| 网络下载的依赖每次都要重装 | `RUN curl` 这类指令本身不缓存网络结果 | 用 `RUN --mount=type=cache` 缓存包管理器目录 |
| `apt-get update` 之后 `apt-get install` 用了旧索引 | 缓存复用了旧的 update 层 | **永远把 `update` 和 `install` 写在同一条 `RUN` 里** |
| 加了 `--build-arg` 后缓存失效 | `ARG` 值参与缓存键 | 正常行为；把易变的 `ARG` 放到需要它的指令附近 |

> **最后一条的陷阱很经典**：把 `apt-get update` 单独写一条 `RUN`，之后用缓存复用它。几周后索引过期，`install` 找不到包或装到旧版本。**官方明确建议两者写在同一层。**

## 五、构建命令的常用控制

```bash
docker build -t myapp:1.0 .                  # 常规构建
docker build --no-cache -t myapp:1.0 .       # 完全不用缓存（排查缓存导致的诡异问题）
docker build --pull -t myapp:1.0 .           # 强制拉取最新的基础镜像
docker build -f Dockerfile.prod -t app:prod .
docker build --build-arg ENV=prod -t app:prod .
docker build --target builder -t app:debug . # 只构建到某阶段（多阶段构建用）
docker build --progress=plain -t myapp:1.0 . # 输出完整构建日志（排查构建失败的利器）
docker build --platform linux/amd64 -t app:amd64 .
```

| 参数 | 何时用 |
|------|--------|
| `--no-cache` | 怀疑缓存导致问题（如依赖明明改了却没生效） |
| `--pull` | 确保用到最新的基础镜像（**CI 环境建议加**） |
| `--progress=plain` | 构建失败但报错被进度条吃掉时 |
| `--target` | 只构建多阶段中的某一段 |

## 六、BuildKit：现代构建引擎

从 Docker 18.09 起引入了 **BuildKit**，现在已是默认构建后端。它带来的能力：

| 能力 | 说明 | 语法 |
|------|------|------|
| **并行构建** | 独立的分支可以并行执行 | 自动 |
| **构建缓存挂载** | 缓存包管理器目录（pip/npm/apt），跨构建复用 | `RUN --mount=type=cache,target=/root/.cache/pip` |
| **安全密钥挂载** | 构建期用密钥但不留在镜像里 | `RUN --mount=type=secret,id=npmrc,target=/root/.npmrc` |
| **不依赖文件校验和** | 只校验文件内容，减少 mtime 干扰 | 自动 |
| **SSH 转发** | 构建期访问私有 Git 仓库 | `RUN --mount=type=ssh` |

**缓存挂载示例（开发体验提升明显）：**

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

| 优势 | 说明 |
|------|------|
| 依赖不变时**跳过重新下载** | 即使 `requirements.txt` 变了，只是增量安装新包 |
| 缓存**不进入镜像** | 与"装完删"不同，缓存挂载的内容完全不在最终镜像层里 |

> ⚠️ **使用注意**：带 `RUN --mount` 的指令要求 Dockerfile 以 `# syntax=docker/dockerfile:1` 开头（或使用较新版 BuildKit，可省略）。另外，缓存挂载的内容**不会在层间共享**——如果同一层里缓存了 pip 却写到一个新层去用，会拿不到。这是它最常见的困惑点。

## 七、构建缓存的清理

```bash
docker builder prune            # 清理未使用的构建缓存
docker builder prune -a         # 全部清理
docker system df                # 看缓存占了多大（Build Cache 那一行）
```

> **构建缓存可以占掉几十 GB**。如果 `docker system df` 显示 Build Cache 很大，而你又不需要复用缓存，可以安全清理（代价是下次构建变慢）。

## 八、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 上下文选成 `/` 或家目录 | 构建极慢甚至卡死 | 上下文指向项目目录 |
| `COPY ../x` | 直接报错 | 把文件放进上下文 |
| 没有 `.dockerignore` | 构建慢 + **密钥泄露** + 跨平台污染 | 必写，且把 `.env`、`.git` 排除 |
| `RUN install` 与 `RUN remove` 分开 | 镜像不变小 | 合并到同一层 |
| `RUN apt-get update` 单独一层 | 缓存过期后装到旧包 | 与 `install` 同层 |
| 依赖安装写在 `COPY . .` 之后 | 改代码就重装依赖 | 拆开两步 |
| 什么都没改却重新构建 | 可能是 mtime 干扰 | 用 BuildKit；或 `--no-cache` 排查 |
| 构建缓存占满磁盘 | `no space left on device` | `docker builder prune` |

## 小结

| 要点 | 内容 |
|------|------|
| 构建上下文 | `docker build` 末尾那个 `.`；整个目录会被打包发送；`COPY` 只能读它 |
| `.dockerignore` | 必写。不写会导致构建慢、**密钥泄露**、跨平台污染、缓存频繁失效 |
| 分层本质 | 每层只读、可共享、累加。**删除只在新层标记，不减小镜像** |
| 缓存键 | 父层 ID + 指令文本 + 文件内容 + 相关 `ARG` 值 |
| 缓存连锁 | 某层失效 → 其后所有层重建 |
| 顺序原则 | 变化频率低的放前（依赖清单在前、源码在后） |
| 同层原则 | "装"与"删"必须写在同一 `RUN` 里才有效 |
| BuildKit | 支持缓存挂载（`--mount=type=cache`）与密钥挂载（`--mount=type=secret`） |

## 练习

1. **观察上下文大小**：在一个含有 `.git` 的项目里执行 `docker build -t t .`，注意第一行输出 `Sending build context to Docker daemon  XX.XMB`。然后添加 `.dockerignore`（先排除 `.git`、`node_modules`），再构建一次，比较这个数字。
2. **验证删除无效**：
   ```dockerfile
   FROM debian:12
   RUN dd if=/dev/zero of=/big.bin bs=1M count=200
   ```
   构建后看 `docker images` 的体积；再把 `RUN rm /big.bin` 加到**下一行**，重新构建，比较体积变化。然后改成同一条 `RUN` 内删除，再比较。
3. **验证缓存连锁失效**：用第 2.1 节练习里的 Dockerfile，依次改动 (a) `requirements.txt` (b) `app.py`，观察每次构建时哪几层显示 `CACHED`、哪几层重建。
4. **诊断"哪层最大"**：对任意一个镜像执行 `docker history <镜像>`，找出体积最大的三层，并说出它们分别对应什么操作。
5. **验证 apt 陷阱**：写出两种 apt 安装的写法（update 与 install 分开 / 同层），分别构建两次（第二次不做任何修改），观察缓存行为差异。
