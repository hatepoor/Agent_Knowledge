## 一、问题：构建需要的东西，运行不需要

考虑一个 Go 程序：**编译**需要完整的 Go 工具链（约 800 MB），但**运行**只需要一个静态二进制文件（约 10 MB）。

如果按单阶段写：

```dockerfile
FROM golang:1.23
WORKDIR /src
COPY . .
RUN go build -o /app/server .
CMD ["/app/server"]
```

**结果**：镜像约 900 MB，其中 890 MB 是**只在构建时用过、运行时完全不需要**的编译器、标准库源码、缓存。

其他语言的同类问题：

| 语言 | 构建期需要 | 运行期需要 | 浪费 |
|------|-----------|-----------|------|
| Go | Go 工具链 | 静态二进制 | ~800 MB |
| Java | JDK + Maven | JRE | ~500 MB |
| Node（前端） | node + 完整 `node_modules` | 静态文件（HTML/JS/CSS） | ~300 MB |
| Python（带 C 扩展） | gcc + 头文件 | 已编译的 `.so` | ~200 MB |
| Rust | rustc + cargo | 二进制 | ~1 GB |

> 而在构建后执行 `rm -rf /usr/local/go` 也**没用**——回忆上一节的结论：**删除只在新层标记，构建层的体积仍留在镜像里**。

## 二、多阶段构建：把"构建"和"运行"分成两个镜像

**核心思想**：在同一个 Dockerfile 里写多个 `FROM`，每个 `FROM` 开始一个新阶段。**只有最后一个阶段会成为最终镜像，前面阶段的层全部被丢弃。**

```dockerfile
# ---- 阶段 1：构建（这个阶段的一切都不会进最终镜像）----
FROM golang:1.23 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app/server .

# ---- 阶段 2：运行 ----
FROM alpine:3.21
RUN apk add --no-cache ca-certificates
COPY --from=builder /app/server /usr/local/bin/server    # ← 只带走这一个文件
CMD ["server"]
```

| 对比 | 单阶段 | 多阶段 |
|------|--------|--------|
| 最终镜像体积 | ~900 MB | ~15 MB |
| 镜像里有没有编译器 | 有 | **没有** |
| 攻击面 | 大（工具链可被利用） | 小 |
| 可读性 | 一般 | 更清楚地表达了"构建"与"运行"的边界 |

### 语法要点

| 语法 | 作用 |
|------|------|
| `FROM <镜像> AS <阶段名>` | 开始一个新阶段并命名 |
| `COPY --from=<阶段名> <源> <目标>` | 从**前面的阶段**复制产物 |
| `COPY --from=<外部镜像> <源> <目标>` | 也可以从任意**镜像**复制（不必是本 Dockerfile 的阶段） |
| `--target=<阶段名>`（构建参数） | 只构建到指定阶段（调试用） |

### 阶段名可以省略吗

可以。不命名的阶段可以用序号引用（第一段是 0）：

```dockerfile
COPY --from=0 /app/server /usr/local/bin/server
```

> ⚠️ **但强烈建议命名**：用序号时，一旦在中间插入一个新的 `FROM`，所有序号引用都会错位。

### 从外部镜像复制（很实用的一招）

不必在本 Dockerfile 里构建，直接从公开镜像里取现成的产物：

```dockerfile
# 直接从官方镜像取一个二进制
COPY --from=busybox:1.36 /bin/busybox /bin/busybox

# 从另一个项目已经构建好的镜像里取配置
COPY --from=nginx:1.27-alpine /etc/nginx/nginx.conf /etc/nginx/nginx.conf
```

### `--target`：只构建到某个阶段

构建时会停在指定阶段，**该阶段的产物可以运行**。用途：调试构建问题。

```bash
docker build --target builder -t app:debug .
docker run -it --rm app:debug sh     # 进到构建环境里看状态
```

## 三、三个完整实战示例

### 3.1 Python（带依赖编译的场景）

```dockerfile
# syntax=docker/dockerfile:1

# ---- 构建阶段：装依赖（可能需要编译 C 扩展）----
FROM python:3.12-slim AS builder
WORKDIR /app

# 编译 C 扩展需要这些；运行阶段不需要
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends \
        build-essential libpq-dev && \
    rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
# 装到独立目录，便于整体搬运
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --prefix=/install -r requirements.txt

# ---- 运行阶段：只带运行时依赖 ----
FROM python:3.12-slim
WORKDIR /app

# 运行期需要的系统库（不含编译工具）
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y --no-install-recommends \
        libpq5 && \
    rm -rf /var/lib/apt/lists/*

COPY --from=builder /install /usr/local
COPY . .

RUN useradd -m -u 10001 appuser && chown -R appuser /app
USER appuser

EXPOSE 8000
CMD ["python","-m","uvicorn","app:app","--host","0.0.0.0","--port","8000"]
```

| 关键点 | 说明 |
|--------|------|
| `pip install --prefix=/install` | 装到独立目录，便于 `COPY --from` 整体搬运 |
| `libpq-dev`（构建）vs `libpq5`（运行） | 前者含头文件供编译，后者只有运行时库 |
| 两阶段都要装 **apt 依赖** | 因为运行阶段是全新的镜像，不继承构建阶段的系统包 |

> ⚠️ **关于 `--mount=type=cache,target=/var/lib/apt,sharing=locked`**：apt 的缓存目录在多个并行构建间需要加锁，否则会冲突。这是 CI 环境里常见的坑。

### 3.2 Node（前端构建 → 静态文件）

```dockerfile
# ---- 构建阶段：编译前端 ----
FROM node:22-alpine AS builder
WORKDIR /src
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # 产物在 /src/dist

# ---- 运行阶段：用 nginx 托管静态文件 ----
FROM nginx:1.27-alpine
COPY --from=builder /src/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
```

| 效果 | 说明 |
|------|------|
| 最终镜像 | 约 50 MB（只有 nginx + 静态文件） |
| 省掉了什么 | `node_modules`（可能几百 MB）、源码、npm 缓存 |
| **顺带的安全收益** | 镜像里**没有 node 运行时**，前端源码也不在里面，攻击面大幅减小 |

### 3.3 Go（极致最小：`scratch`）

```dockerfile
FROM golang:1.23-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# CGO_ENABLED=0 生成静态链接二进制，不依赖 glibc
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app/server .

FROM scratch                     # 空镜像：没有任何文件、没有 shell
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /app/server /server
ENTRYPOINT ["/server"]
```

| 要点 | 说明 |
|------|------|
| `scratch` | 完全空的镜像。最终镜像 = 二进制 + CA 证书，约 10 MB |
| `CGO_ENABLED=0` | **必须**。否则二进制依赖 glibc，在 scratch 里跑不起来 |
| `-ldflags="-s -w"` | 去掉符号表与调试信息，二进制更小 |
| 复制 CA 证书 | 否则容器内发起 HTTPS 请求会失败 |
| ⚠️ **没有 shell** | `docker exec` 进不去（没有 `sh`），**排错会很难** |

> **`scratch` vs `distroless` 的选择**：两者都极小。`distroless`（Google 出品）会多带一些基础文件（CA 证书、时区、`/etc/nsswitch.conf`），**兼容性更好但仍无 shell**。安全要求高、且你能接受"无法进容器调试"时选它们；否则用 `alpine` 更实用。

## 四、20 条最佳实践清单

按重要程度分三级。**A 级是必须做的，B 级是强烈建议，C 级是锦上添花。**

### A 级：必须做

| # | 实践 | 理由 |
|---|------|------|
| A1 | **固定基础镜像版本**，不用 `latest` | 可复现；避免"今天构建成功明天失败" |
| A2 | **写 `.dockerignore`** | 构建速度 + 防止密钥泄露 |
| A3 | **`CMD`/`ENTRYPOINT` 用 exec 形式** | 保证信号传递与退出码正确 |
| A4 | **主进程前台运行** | 否则容器立刻退出 |
| A5 | **切换非 root 用户** | 降低容器逃逸后的影响范围 |
| A6 | **依赖清单先复制、源码后复制** | 让缓存有效，避免改代码就重装依赖 |
| A7 | **不把密钥写进任何构建期变量** | `ARG` 会留在 `docker history` 里 |

### B 级：强烈建议

| # | 实践 | 理由 |
|---|------|------|
| B1 | **用多阶段构建** | 体积与攻击面双降 |
| B2 | **合并 `RUN`，装完即删** | 层只读，删除必须在同层才有效 |
| B3 | **`apt-get update` 与 `install` 同层** | 避免缓存过期装到旧包 |
| B4 | **用 `COPY` 而非 `ADD`** | 语义单一，无隐式行为 |
| B5 | **`WORKDIR` 而非 `RUN cd`** | `cd` 不跨指令生效 |
| B6 | **加 `HEALTHCHECK`** | 让编排层能判断"真就绪" |
| B7 | **用 `LABEL org.opencontainers.image.*`** | 镜像治理、溯源、合规 |
| B8 | **显式 `--no-install-recommends`**（apt） | 少装无关包 |
| B9 | **构建时加 `--pull`**（CI） | 确保基础镜像的安全更新被带上 |

### C 级：进阶优化

| # | 实践 | 理由 |
|---|------|------|
| C1 | 用 BuildKit 缓存挂载 `--mount=type=cache` | 依赖增量安装，构建更快 |
| C2 | 用 `--mount=type=secret` 处理构建期密钥 | 唯一安全的构建期密钥方案 |
| C3 | 用 `dive` 工具分析层效率 | 逐层查看浪费 |
| C4 | 定期用 `docker scout` 扫漏洞 | 及时发现基础镜像的 CVE |

## 五、审查练习：一个"看起来没问题"的 Dockerfile

```dockerfile
FROM python:3.12
RUN apt-get update
RUN apt-get install -y gcc
COPY . .
RUN pip install -r requirements.txt
ENV SECRET_KEY=prod-secret-12345
EXPOSE 8000
CMD python app.py
```

<details>
<summary>点开看问题清单（建议先自己想一遍）</summary>

| 行 | 问题 | 违反 |
|----|------|------|
| `FROM python:3.12` | 用完整版，约 1 GB 且含编译工具 | A1 + B8 |
| `RUN apt-get update` | 与 `install` 分开，缓存会过期失效 | B3 |
| `RUN apt-get install -y gcc` | 未用 `--no-install-recommends`；且安装后未清理；gcc 进了运行镜像 | B2 + B8 |
| `COPY . .` | 在依赖安装之前，导致改代码就重装依赖 | A6 |
| `RUN pip install` | 未用 `--no-cache-dir`，pip 缓存进了镜像 | B2 |
| `ENV SECRET_KEY=...` | ⚠️ **密钥硬编码在镜像里**，任何人 `docker inspect` 就能看到 | A7 |
| `CMD python app.py` | shell 形式，信号与退出码失真 | A3 |
| 缺少 | 没切非 root 用户 | A5 |
| 缺少 | 没 `.dockerignore` | A2 |
| 缺少 | 没用多阶段构建 | B1 |

**修正版本：**

```dockerfile
FROM python:3.12-slim

ENV PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

WORKDIR /app

COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd -m -u 10001 appuser && chown -R appuser /app
USER appuser

EXPOSE 8000
CMD ["python","app.py"]
```

（`SECRET_KEY` 改为运行时通过环境变量或挂载传入。）

</details>

## 六、常见陷阱

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用序号引用阶段（`--from=0`） | 插入新阶段后错位 | 用 `AS` 命名 |
| 多阶段里忘了装**运行期**系统依赖 | 最终镜像启动报"缺少 xxx.so" | 两个阶段都要装各自需要的 apt 包 |
| `scratch` 里跑动态链接程序 | `no such file or directory` | 加 `CGO_ENABLED=0` 或改用 alpine |
| `scratch`/`distroless` 后无法调试 | `docker exec` 报"sh not found" | 保留一个用 `alpine` 的调试目标，用 `--target` 构建 |
| 只复制二进制不复制配置/证书 | 运行时报证书错误、找不到配置 | 一并 `COPY --from` |
| 构建阶段 `USER` 切换后 `COPY` 失败 | 权限不足 | 先 `chown` 再 `USER`，或把 `USER` 放到最后 |

## 小结

| 要点 | 内容 |
|------|------|
| 多阶段解决什么 | 构建工具只在构建时需要，不该进运行镜像 |
| 机制 | 每个 `FROM` 是一个阶段；**只有最后一个阶段成为最终镜像** |
| 核心语法 | `FROM x AS builder` + `COPY --from=builder /app/bin /bin` |
| 外部复制 | `COPY --from=<公开镜像> ...` 可直接取现成产物 |
| 调试 | `--target=<阶段名>` 只构建到某个阶段 |
| 极致最小 | `scratch` / `distroless`，但**无 shell**，需权衡可调试性 |
| A 级红线 | 固定版本、写 `.dockerignore`、exec 形式、前台运行、非 root、密钥不进构建变量 |

## 练习

1. **做出多阶段对比**：为同一个 Python 应用写两个 Dockerfile（单阶段 vs 多阶段），构建后用 `docker images` 比较体积，并说出差距主要来自什么。
2. **改造为 Go 多阶段**：假设你有一个 Go 程序，写出从 `golang:1.23-alpine` 构建、用 `scratch` 运行的 Dockefile，并说明为什么必须加 `CGO_ENABLED=0`。
3. **用 `--target` 调试**：给上面的多阶段 Dockerfile 加 `--target=builder` 构建，进容器确认编译产物是否存在。
4. **审查并修正**：把第五节那个"看起来没问题"的 Dockerfile 的 10 个问题**全部列出并逐条修正**（先遮住答案自己写）。
5. **验证外部复制**：写一个只用 `FROM alpine:3.21` + `COPY --from=nginx:1.27-alpine /usr/sbin/nginx /usr/sbin/nginx` 的 Dockerfile，构建后观察体积与运行结果，解释缺少了什么。
