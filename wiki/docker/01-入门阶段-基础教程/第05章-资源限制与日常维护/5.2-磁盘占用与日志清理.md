# 磁盘占用与日志清理

## 学习目标

读完本篇，你应当能够：

1. 说出 Docker 占用磁盘的**五个来源**，并用 `docker system df` 分辨各自占比
2. **解释为什么容器日志会无限增长**，并配置日志轮转
3. 按"安全 → 有风险 → 危险"三档选择清理命令，不再盲目 `prune -a --volumes`
4. 独立完成一次磁盘告急的完整处置流程

## 一、Docker 占用磁盘的五个来源

```
/var/lib/docker/   （Linux）/  Docker 虚拟磁盘    （Windows/macOS）
├── ① 镜像（Images）        每个镜像的全部层
├── ② 容器可写层（Containers）  每个容器相对镜像改动的部分
├── ③ 数据卷（Volumes）      业务数据。⚠️ 唯一"丢了就没了"的东西
├── ④ 构建缓存（Build Cache）  BuildKit 的中间层缓存
└── ⑤ 容器日志（Logs）       ⚠️ 默认无限增长，最容易被忽视
```

**用一条命令看清各项占比：**

```bash
docker system df
```

```
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          12        3         4.2GB     3.1GB (73%)
Containers      8         2         120MB     90MB (75%)
Local Volumes   5         1         1.8GB     0B (0%)
Build Cache     45        0         2.4GB     2.4GB
```

| 列 | 含义 |
|----|------|
| `TOTAL` | 数量 |
| `ACTIVE` | **正在被使用**的数量 |
| `SIZE` | 占用空间 |
| `RECLAIMABLE` | **可回收空间**（未被使用的部分） |

**加 `-v` 看细分到每个对象：**

```bash
docker system df -v
```

输出会列出**每个镜像、每个容器、每个卷**各自的大小。用它定位"到底是哪个东西占的"。

> **注意 `Local Volumes` 的 `RECLAIMABLE` 常显示 `0B (0%)`**：这不代表卷不占空间，而是表示"**Docker 不认为其中有可安全回收的部分**"。卷的清理需要你人工判断。

## 二、最容易被忽视的问题：日志无限增长

### 2.1 问题的由来

回忆 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.3-进入容器与查看日志]]：容器主进程写到 stdout/stderr 的内容，会被 Docker 以 `json-file` 格式追加到：

```
/var/lib/docker/containers/<容器ID>/<容器ID>-json.log
```

**关键点**：默认配置下，**这个文件没有任何大小上限，也不会轮转**。

| 场景 | 后果 |
|------|------|
| 一个报错循环的服务 | 每秒写几百行日志，几小时吃掉几十 GB |
| 一个访问量大的 Web 服务 | 访问日志迅速堆积 |
| 长期运行（几个月）的容器 | 即使日志量不大，也会累积到可观体积 |

**最典型的症状**：

```
Error response from daemon: no space left on device
```

此时**整个 Docker 都可能无法正常工作**——连删镜像都可能失败。

### 2.2 先定位：是日志占的吗

```bash
# 看 Docke 数据目录的总占用
sudo du -sh /var/lib/docker/

# 看哪个容器的日志最大（Linux）
sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head -10

# 或直接查某个容器的 LogPath
docker inspect <容器> --format '{{.LogPath}}'
```

> **Windows / macOS 用户**：Docker 跑在虚拟机里，宿主机上看不到这些路径。可以在 Docker Desktop 的设置里看到虚拟磁盘文件的大小，或用下面第五节的"清空日志"方式处理（不需要访问宿主路径）。

### 2.3 配置日志轮转（正确的根治方法）

**方法 A：全局配置（推荐）**

编辑 daemon 配置（Linux 是 `/etc/docker/daemon.json`；Windows/macOS 在 Docker Desktop 的 Settings → Docker Engine）：

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

| 参数 | 含义 |
|------|------|
| `max-size` | 单个日志文件上限。达到后**轮转**（重命名旧的，新建一个） |
| `max-file` | 保留的**文件个数**。超过后删最旧的 |

**上例的效果**：每个容器日志最多占 `10m × 3 = 30 MB`。

**然后重载配置并重建容器：**

```bash
sudo systemctl daemon-reload
sudo systemctl restart docker
# ⚠️ 已存在的容器不会自动获得新配置，需要重建
```

> ⚠️ **最重要的注意事项**：**日志配置是容器"创建时"确定的，已存在的容器不会因为改了 daemon.json 就生效。** 必须删除容器重建（`docker run` 或 `docker compose up -d --force-recreate`）。
>
> **验证方式**：
> ```bash
> docker inspect <容器> --format '{{json .HostConfig.LogConfig}}'
> # 应该看到 {"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
> ```

**方法 B：单个容器指定**

```bash
docker run --log-driver json-file --log-opt max-size=10m --log-opt max-file=3 myapp
```

**方法 C：Compose 中配置**

```yaml
services:
  app:
    image: myapp:1.0
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

> **注意 YAML 里要加引号**：`"10m"` 而不是 `10m`。

### 2.4 日志驱动选择（简述）

| 驱动 | 行为 | 适用 |
|------|------|------|
| `json-file` | 写本地 JSON 文件（**默认**） | 单机、需要 `docker logs` |
| `local` | 类似 json-file 但**默认带轮转**，二进制格式更省空间 | ✅ 单机推荐替代 |
| `journald` | 交给 systemd 的 journal | Linux + 已有 journal 体系 |
| `syslog` | 发到 syslog | 集中式日志 |
| `fluentd` / `gelf` / `awslogs` | 发到日志收集系统 | 生产环境集中日志 |
| `none` | 丢弃日志 | ⚠️ `docker logs` 将不可用 |

> **生产环境的正确做法不是"清理日志"，而是"把日志收集走"**：用 `fluentd`/`awslogs`/`syslog` 等驱动发到集中平台（如 Loki、ELK），本地只留少量缓冲。详见 [[docker/02-中段阶段-专题精讲/日志与监控/专题概览]]。

## 三、清理命令的三档分级

**把清理分档是避免误删的关键。** 下表按风险从低到高排列。

### 第 1 档：安全（可以随时执行）

| 命令 | 清理什么 | 风险 |
|------|----------|------|
| `docker container prune` | 所有**已停止**的容器 | ✅ 低。只删停止的，但**停止的容器里可能有你要排查的东西** |
| `docker image prune` | **悬空镜像**（无 tag、无引用的层） | ✅ 低 |
| `docker builder prune` | 未使用的**构建缓存** | ✅ 低（代价是下次构建变慢） |
| `docker network prune` | 未被使用的网络 | ✅ 低 |

### 第 2 档：有风险（执行前先看清对象）

| 命令 | 清理什么 | 风险点 |
|------|----------|--------|
| `docker image prune -a` | **所有无容器引用的镜像** | ⚠️ 会删掉你手动拉的基础镜像（下次要重新拉） |
| `docker container prune --filter "until=24h"` | 24 小时前停止的容器 | ✅ 比全删更可控，**推荐这种加过滤的用法** |
| `docker system prune` | 停止的容器 + 悬空镜像 + 未用网络 | ⚠️ 不含卷，但会删停止的容器 |

### 第 3 档：危险（必须先人工确认）

| 命令 | 清理什么 | 风险点 |
|------|----------|--------|
| `docker volume prune` | **所有无容器使用的卷** | ❌ **删数据**。包括你准备给新容器用的卷 |
| `docker system prune -a` | 上面全部 + 所有未用镜像 | ⚠️ 镜像需重新拉取 |
| `docker system prune -a --volumes` | **全部 + 卷** | ❌ **最危险**。可能删掉数据库数据 |
| `docker compose down -v` | 本项目的容器 + 网络 + **卷** | ❌ 删数据 |

> ⚠️ **执行第 3 档命令前的强制动作**：
> ```bash
> docker volume ls            # 先看清有哪些卷！
> docker ps -a                # 确认没有停止的容器是你要保留的
> ```
> **不要凭记忆判断"那些卷应该没用"。**

## 四、一次完整的磁盘告急处置流程

假设你看到 `no space left on device`：

```
第 1 步：定量 —— 到底什么占的？
  docker system df -v
  sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head

第 2 步：先处理最安全的（日志），因为它常常是元凶
  ├── 查最大日志：docker inspect <容器> --format '{{.LogPath}}'
  ├── 立即回收空间（不删容器）：见下方"清空日志"
  └── 配置日志轮转，根治问题
  
第 3 步：清理构建缓存
  docker builder prune

第 4 步：清理悬空镜像与停止的容器
  docker image prune
  docker container prune --filter "until=24h"

第 5 步：判断是否需要动镜像与卷（第 2、3 档）
  ├── 先 docker images / docker volume ls 看清对象
  └── 确认后再执行

第 6 步：根治 —— 配置日志轮转 + 规划数据目录位置
```

### 清空日志但保留容器（应急手段）

如果日志已经把磁盘写满，而你不能立刻删容器，可以**直接把日志文件截断为 0**：

```bash
# Linux：截断所有容器的日志文件（保留文件，清空内容）
sudo sh -c "truncate -s 0 /var/lib/docker/containers/*/*-json.log"
```

| 要点 | 说明 |
|------|------|
| `truncate -s 0` 只清空内容 | **不删除文件本身**，Docker 的写入句柄仍然有效 |
| ❌ **不要用 `rm`** | 删掉文件后 Docker 仍持有已删除文件的句柄，空间**不会释放**，直到重启 Docker |
| Windows / macOS | 访问不到该路径，改用 `docker compose up -d --force-recreate` 重建容器（但会丢现场） |

> **`rm` 与 `truncate` 的差别**是本篇最值得记住的实操细节：在 Linux 上，一个被进程打开的文件即使被 `rm`，其磁盘空间也不会释放（因为 inode 仍被引用）。**必须用 `truncate`。**

### 根治：把数据目录换到其他盘

磁盘被写满的深层原因常是"数据目录在系统盘"。根治方式：

| 平台 | 做法 |
|------|------|
| **Linux** | 编辑 `/etc/docker/daemon.json` 加 `"data-root": "/data/docker"`，迁移数据并重启 docker |
| **Windows / macOS** | Docker Desktop → Settings → Resources → Disk image location，改到其他盘 |

## 五、prune 命令语义对照表

容易混，单独列一张表：

| 命令 | 容器 | 镜像 | 网络 | **卷** | 构建缓存 |
|------|------|------|------|--------|----------|
| `docker container prune` | ✅ 停止的 | —— | —— | —— | —— |
| `docker image prune` | —— | ✅ 悬空 | —— | —— | —— |
| `docker image prune -a` | —— | ✅ 无引用 | —— | —— | —— |
| `docker network prune` | —— | —— | ✅ 未用 | —— | —— |
| `docker volume prune` | —— | —— | —— | ✅ 无容器用 | —— |
| `docker builder prune` | —— | —— | —— | —— | ✅ 未用 |
| `docker system prune` | ✅ 停止的 | ✅ 悬空 | ✅ 未用 | ❌ | ✅ |
| `docker system prune -a` | ✅ 停止的 | ✅ 无引用 | ✅ 未用 | ❌ | ✅ |
| `docker system prune -a --volumes` | ✅ | ✅ | ✅ | ❌→✅ **删** | ✅ |

> **注意一个反直觉的点**：**`docker system prune`（不带 `-a`）也会清理构建缓存**。所以它可能比你想的更"彻底"（代价是下次构建重来）。

## 六、磁盘问题的预防清单

| 措施 | 说明 |
|------|------|
| ✅ **配置日志轮转** | 最重要的一条。全局配 + Compose 里也配 |
| ✅ **用 `--rm` 跑临时容器** | 避免停止的容器堆积（见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]]） |
| ✅ **用 `.dockerignore`** | 避免上下文过大导致的构建缓存膨胀 |
| ✅ **定期 `docker system df`** | 及早发现增长趋势，而不是等磁盘满了 |
| ✅ **数据目录放数据盘** | 系统盘留给系统 |
| ✅ **生产用集中日志收集** | 本地不长期存日志 |
| ✅ **镜像固定版本并周期性清理旧版本** | 每次发布都产生新镜像 |

## 七、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 直接跑 `system prune -a --volumes` | 删掉数据库数据 | 分档执行，先看对象 |
| 没配日志轮转 | 磁盘被日志写满 | 全局 + Compose 双重配置 |
| 改了 daemon.json 但没重建容器 | 新配置不生效 | 重建容器并 `inspect` 验证 |
| 用 `rm` 删日志文件 | 空间不释放 | 用 `truncate -s 0` |
| 用 `prune -a` 后要重新拉基础镜像 | 浪费时间与流量 | 日常用不带 `-a` 的版本 |
| 以为卷有 `RECLAIMABLE` 就安全 | `0B` 不代表不占空间 | 人工判断卷的用途 |
| `container prune` 删掉待排查的停止容器 | 失去故障现场 | 用 `--filter until=24h`，或先 `logs` 备份 |

## 小结

| 要点 | 内容 |
|------|------|
| 五个来源 | 镜像、容器可写层、卷、构建缓存、**日志（最易忽视）** |
| 诊断入口 | `docker system df`（概览）、`docker system df -v`（细分） |
| 日志问题 | 默认**无上限、不轮转**。必须配 `max-size` + `max-file` |
| 日志配置生效条件 | 是**创建时**确定的，改配置后**必须重建容器** |
| 应急清空日志 | 用 `truncate -s 0`，**不要 `rm`** |
| 清理分档 | 安全（prune / builder prune）→ 有风险（`-a`）→ 危险（`volume prune`、`--volumes`） |
| 强制动作 | 执行危险命令前，先 `docker volume ls` 与 `docker ps -a` |
| 根治 | 日志轮转 + 数据目录迁移到数据盘 + 生产集中收集日志 |

## 练习

1. **看清占用**：执行 `docker system df` 与 `docker system df -v`，说出你机器上占用最大的是哪一类，具体是哪个对象。
2. **制造日志膨胀并观察**：
   ```bash
   docker run -d --name noisy alpine sh -c 'while true; do echo "log line $(date)"; done'
   sleep 20
   docker inspect noisy --format '{{.LogPath}}'
   sudo du -sh $(docker inspect noisy --format '{{.LogPath}}')     # Linux
   docker logs --tail 5 noisy
   ```
   然后用 `truncate` 清空它（Linux），验证空间被释放。
3. **验证日志配置需重建才生效**：给一个已存在的容器加日志限制配置（改 daemon.json 或 Compose），重启 Docker 后 `inspect` 它的 `LogConfig`，观察是否变化；然后重建容器再验证。
4. **给 4.2 节项目加日志配置**：在 `compose.yaml` 里为所有服务加 `logging` 配置，用 `docker compose up -d --force-recreate` 重建，再用 `inspect` 验证。
5. **演练分档清理**：先创建两个测试容器与一个测试卷（一个被容器使用、一个不被使用），然后：
   - 用 `docker volume prune` 看它删了哪一个
   - 解释为什么另一个没被删
   - 说明如果要保留那个未使用的卷，该怎么办
6. **设计预防方案**：为一个"跑 10 个容器、每天产生 5 GB 日志"的服务器设计一套磁盘管理方案（包含配置项与巡检动作）。
