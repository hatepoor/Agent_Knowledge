# 容器排错流程

## 学习目标

读完本篇，你应当能够：

1. 遇到 Docker 问题时按固定流程定位，而不是随机试错
2. 按**七类现象**分别执行对应的排查序列，并说出每步的判据
3. 收集完整的诊断信息（无论自助排查还是向他人求助）
4. 遵守排错纪律：不破坏故障现场、不在生产容器里改东西

## 一、排错的第一原则

> **先确定"在哪一层出错"，再确定"具体是什么错"。顺序不能颠倒。**

```
发生了什么？                 →  属于哪一类现象？
                                    ↓
                        ┌───────────┴───────────┐
                    起不来                   起来后又出问题
                        ↓                        ↓
                   看创建错误               看状态 / 日志 / 资源
```

**绝对不要做的事：**

| ❌ 行为 | 后果 |
|--------|------|
| 反复重试同一个命令 | 对"名字冲突""端口占用"这类问题完全无效 |
| 一上手就 `system prune -a --volumes` | 可能丢失数据 |
| 在生产容器里 `exec` 进去改配置"修好它" | ① 重建即失效 ② 现场被破坏 ③ 无人知道改了什么 |
| 搜索报错时带上自己的容器名/端口 | 搜不到匹配答案 |
| 不问自己"我改了什么" | 90% 的问题源于最近的一次变更 |

## 二、通用五步法

```bash
# 第 1 步：容器现在是什么状态？
docker ps -a
#   看 STATUS。Up / Exited (n) / Created / Restarting
#   ↑ 这一步决定后面走哪条分支

# 第 2 步：容器自己说了什么？
docker logs --tail 100 <容器>
#   80% 的答案在这里

# 第 3 步：运行时配置对不对？
docker inspect <容器> --format '
status={{.State.Status}}
exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}}
ports={{json .NetworkSettings.Ports}}
mounts={{json .Mounts}}
env={{json .Config.Env}}
'
#   一次拿到最关键的信息

# 第 4 步：环境本身健康吗？
docker info
docker system df
#   磁盘是否满？守护进程是否正常？

# 第 5 步：进容器内部看（容器能运行时）
docker exec -it <容器> sh
#   注意：slim/alpine 镜像用 sh，不是 bash
```

### 状态列的含义对照

| STATUS | 含义 | 下一步 |
|--------|------|--------|
| `Up X minutes` | 运行中 | 问题在服务层面（访问不到/变慢） |
| `Up X minutes (healthy)` | 运行且健康检查通过 | 查应用逻辑 |
| `Up X (unhealthy)` | 运行但健康检查失败 | 看 `.State.Health` 的输出 |
| `Up X (health: starting)` | 正在检查中 | 等，或调大 `start_period` |
| `Exited (0)` | 正常退出 | 主进程结束了（见第 3 类现象） |
| `Exited (1)` | 程序报错退出 | 看日志 |
| `Exited (137)` | 被 SIGKILL | **首查内存超限**（`.State.OOMKilled`） |
| `Exited (143)` | 收到 SIGTERM | 正常停止的结果 |
| `Created` | 创建了没启动 | `docker start` |
| `Restarting (n)` | 反复重启 | 看日志里的崩溃原因，检查重启策略 |
| `Paused` | 被 `docker pause` 冻结 | `docker unpause` |

## 三、按现象分类的排查序列

### 现象 1：容器创建/启动失败（`docker run` 直接报错）

**判据**：命令返回错误，`docker ps -a` 里可能都没有这个容器。

| 可能原因（按高频排序） | 判据命令 |
|------------------------|----------|
| ① 容器名重复 | `docker ps -a \| grep <名字>` |
| ② 宿主端口被占用 | `lsof -i :<端口>` / `netstat -ano \| findstr :<端口>` |
| ③ 镜像不存在 | `docker images \| grep <镜像名>` |
| ④ 挂载路径有问题 | 检查 `-v` 的宿主路径是否存在、权限是否对 |
| ⑤ 磁盘满 | `docker system df`、`df -h` |
| ⑥ 参数拼写错误 | 逐段核对命令，或 `docker run --help` |

```bash
# 排查序列
docker ps -a | grep <名字>                                  # ① 
lsof -i :<宿主端口>                                          # ②
docker images | grep <镜像>                                  # ③
df -h                                                        # ⑤
```

> **最常见的是 ① 和 ②**。而且 ① 的根因通常是**忘了 `--rm`**，导致临时容器堆积（见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]]）。

---

### 现象 2：容器立刻退出（`Exited (n)`）

**这是最高频的一类问题。** 核心原理：**容器只关心主进程（PID 1），主进程退出容器即结束**。

```bash
# 排查序列
docker ps -a                                  # 看退出码
docker logs <容器>                             # 看它退出前说了什么
docker inspect <容器> --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
```

| 退出码 | 判据 | 处置 |
|--------|------|------|
| `0` | 主进程正常结束 | ① 命令跑完了（正常）② **主进程是后台型程序**（`service`/`nohup`/`&`）→ 改为前台运行 |
| `1` | 程序自身报错 | 读 `docker logs`，通常是配置错、依赖缺失、连不上数据库 |
| `126` | 命令存在但不可执行 | 检查执行权限 |
| `127` | 命令不存在 | 检查 `CMD`/`ENTRYPOINT` 写的路径；用 `--entrypoint sh` 进镜像确认 |
| `137` | 被 SIGKILL | **查 `.State.OOMKilled`：`true` 就是内存超限**，调大 `-m` 或修内存泄漏 |
| `143` | 收到 SIGTERM | 正常（`docker stop` 的结果） |

**最经典的三种根因：**

| 根因 | 表现 | 修法 |
|------|------|------|
| **主进程后台化** | 退出码 0，日志显示"启动成功"但容器已退 | `CMD` 改为前台运行（如 `nginx -g 'daemon off;'`） |
| **依赖服务未就绪** | 退出码 1，日志有 `Connection refused` | Compose 加 `healthcheck` + `condition: service_healthy` |
| **内存超限** | 退出码 137，`OOMKilled: true` | 调大 `-m`，或排查内存泄漏 |

### 现象 3：容器在运行，但访问不到

**判据**：`docker ps` 显示 `Up`，但请求超时/拒绝。

```bash
# 排查序列（顺序很重要）
# ① 端口映射存在吗？
docker port <容器>
docker inspect <容器> --format '{{json .NetworkSettings.Ports}}'

# ② 宿主上那个端口真的在监听吗？
lsof -i :<宿主端口>                    # Linux/macOS
netstat -ano | findstr :<宿主端口>      # Windows

# ③ 从容器内部访问服务，确认服务是活的
docker exec <容器> sh -c "wget -qO- http://localhost:<容器端口> || echo FAIL"

# ④ 服务监听的地址是 0.0.0.0 还是 127.0.0.1？
docker exec <容器> sh -c "netstat -tlnp 2>/dev/null || ss -tlnp"

# ⑤ 看容器日志
docker logs --tail 100 <容器>
```

| 判据 | 结论 |
|------|------|
| ① 无输出（没有映射） | 忘了 `-p`，或以为 `EXPOSE` 会生效 |
| ② 宿主端口无监听 | 映射没建立（重启 Docker / 重建容器） |
| ③ 容器内自测就失败 | **问题在服务本身**，与端口映射无关 |
| ④ 监听 `127.0.0.1:<端口>` | ⚠️ **必须改成 `0.0.0.0`**（见 [[docker/01-入门阶段-基础教程/第03章-数据卷与容器网络/3.3-端口映射与访问]]） |
| ① 显示 `80/tcp`（无箭头） | 只有 `EXPOSE` 声明，没真正映射 |

**两大隐形原因回顾**：① `-p` 方向写反 ② 服务绑在 `127.0.0.1`。

---

### 现象 4：容器运行中变慢 / 无响应

```bash
# ① 看资源占用
docker stats --no-stream

# ② 看进程数与内存（判断 fork 炸弹/内存泄漏）
docker top <容器>
docker inspect <容器> --format 'restarts={{.RestartCount}} oom={{.State.OOMKilled}}'

# ③ 看是否被限流
docker inspect <容器> --format 'Mem={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}} Pids={{.HostConfig.PidsLimit}}'

# ④ 看磁盘 IO 与空间
docker system df
df -h

# ⑤ 看宿主整体负载
top / htop
```

| 判据 | 结论 |
|------|------|
| `MEM USAGE / LIMIT` 的分母很小 | 内存限制设太小，容器在挣扎 |
| `CPU %` 被压在上限附近且不再上升 | 被 `--cpus` 限流（正常行为，但可能设小了） |
| `PIDS` 数持续飙升 | fork 炸弹或线程泄漏，需 `--pids-limit` |
| `RestartCount` 很大 | 在反复崩溃重启，看日志里的原因 |
| 宿主 `df -h` 接近 100% | 磁盘满导致所有 IO 变慢（见 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.2-磁盘占用与日志清理]]） |

> ⚠️ **使用 swap 的容器会"变慢但不被杀"**：回忆 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.1-资源限制]]——不设 `--memory-swap` 时，swap 额度默认等于 `-m`。如果容器在 swap 上运行，CPU 会大量消耗在换页上。

### 现象 5：容器之间连不上（Compose 场景尤其常见）

```bash
# ① 确认是否在同一网络
docker network inspect <网络名> --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'

# ② 测试名称解析
docker exec <容器A> nslookup <容器B>       # 镜像里可能没有 nslookup

# ③ 测试端口连通性（不依赖额外工具）
docker exec <容器A> python -c "
import socket; s=socket.socket(); s.settimeout(3)
try:
    s.connect(('<容器B>', <端口>)); print('OK')
except Exception as e:
    print('FAIL:', e)
"

# ④ 确认目标服务在监听
docker exec <容器B> sh -c "netstat -tlnp 2>/dev/null || ss -tlnp"

# ⑤ 看双方日志
docker logs --tail 50 <容器A>
docker logs --tail 50 <容器B>
```

| 判据 | 结论 |
|------|------|
| ① 目标容器不在列表里 | 没接同一网络 |
| ② 解析失败 | 用了**默认 bridge**（不支持名称解析）→ 建自定义网络 |
| ③ 连接超时/拒绝 | 目标端口没监听，或服务绑在 `127.0.0.1` |
| 应用日志里有 `Connection refused` + 容器刚启动 | **`depends_on` 没配 `condition: service_healthy`** |

> **用 Python 而不是 `nc`/`curl` 测试的原因**：`slim`/`alpine` 镜像里通常没有这些工具。Python 在多数应用镜像里都有；或者临时起一个工具容器：
> ```bash
> docker run --rm -it --network <网络名> nicolaka/netshoot
> ```

### 现象 6：镜像构建失败

```bash
# ① 看完整构建日志（不被进度条吃掉）
docker build --progress=plain -t test .

# ② 怀疑缓存问题就不带缓存构建
docker build --no-cache -t test .

# ③ 失败在 COPY？确认文件在上下文里、且没被 .dockerignore 排除
docker build -t test . 2>&1 | head -20     # 看"Sending build context"的大小

# ④ 失败在 RUN？进到那一步的镜像里看
docker build --target <阶段名> -t debug-stage . && docker run -it --rm debug-stage sh
```

| 判据 | 结论 |
|------|------|
| `forbidden path outside the build context` | `COPY` 引用了上下文之外的文件 |
| 上下文大小异常大 | 缺 `.dockerignore` |
| `RUN` 里命令不存在 | 基础镜像太精简（如 alpine 无 bash/curl） |
| 明明改了代码但没生效 | 缓存问题 → `--no-cache`，或检查指令顺序 |
| 缺少头文件/编译错误 | `slim`/`alpine` 镜像缺编译工具，需在构建阶段装 |

见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.2-构建过程与分层缓存]]。

## 四、诊断信息收集清单

无论是自助排查还是向他人/AI 求助，**提供以下信息**能极大提高效率：

```bash
# 一次性收集脚本（Linux/macOS）
{
  echo "=== 版本 ===";        docker version
  echo "=== 环境 ===";        docker info
  echo "=== 容器列表 ===";     docker ps -a
  echo "=== 磁盘 ===";        docker system df
  echo "=== 目标容器详情 ==="; docker inspect <容器名>
  echo "=== 目标容器日志 ==="; docker logs --tail 200 <容器名>
} > docker-diag.txt 2>&1
```

| 必提供 | 为什么 |
|--------|--------|
| 完整命令（不是"我 run 了个容器"） | 参数问题占很大比例 |
| `docker ps -a` 输出 | 状态与退出码 |
| `docker logs` 输出 | 程序的真实报错 |
| `docker version` 两端版本 | 版本不匹配是隐形故障源 |
| 宿主 OS 与架构 | 平台差异（Windows/Linux、amd64/arm64） |
| **"我最近改了什么"** | 90% 的问题源于最近的一次变更 |

**提交问题时不要做的事**：不要只说"报错了"或粘贴半截截图。**完整的命令 + 完整报错文本**是最低要求。

## 五、常用诊断命令速查

| 想知道什么 | 命令 |
|-----------|------|
| 所有容器状态（含已停止） | `docker ps -a` |
| 容器日志 | `docker logs --tail 100 -f <容器>` |
| 退出码 / 是否 OOM | `docker inspect <容器> --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'` |
| 健康检查详情 | `docker inspect <容器> --format '{{json .State.Health}}'` |
| 端口映射 | `docker port <容器>` |
| 挂载清单 | `docker inspect <容器> --format '{{json .Mounts}}'` |
| 环境变量 | `docker inspect <容器> --format '{{json .Config.Env}}'` |
| 启动命令 | `docker inspect <容器> --format 'ENTRYPOINT={{json .Config.Entrypoint}} CMD={{json .Config.Cmd}}'` |
| 资源限制 | `docker inspect <容器> --format 'Mem={{.HostConfig.Memory}} Cpus={{.HostConfig.NanoCpus}}'` |
| 实时资源占用 | `docker stats` |
| 容器内进程 | `docker top <容器>` |
| 容器内文件改动 | `docker diff <容器>` |
| 网络内有哪些容器 | `docker network inspect <网络> --format '{{range .Containers}}{{.Name}}{{"\n"}}{{end}}'` |
| 磁盘占用概览 / 细分 | `docker system df` / `docker system df -v` |
| 容器日志文件路径 | `docker inspect <容器> --format '{{.LogPath}}'` |
| 宿主 Docker 事件流 | `docker events` |
| 宿主内存告警记录 | `dmesg \| grep -i oom`（Linux） |

## 六、排错纪律

| 纪律 | 理由 |
|------|------|
| ✅ **先备份现场**：`docker logs > 文件`，再动手 | 重建/删除后日志就没了 |
| ✅ **优先"重建"而不是"进容器改"** | 容器内的改动不可持续，也不可追溯 |
| ✅ **一次只改一个变量** | 同时改多处，出问题时无法归因 |
| ✅ **记录你做的每一步** | 便于回退，也便于他人协助 |
| ❌ **不要在故障时执行破坏性清理** | 磁盘满时更该谨慎，而不是急着 prune |
| ❌ **不要在生产环境直接试** | 先在本地/测试环境复现 |
| ❌ **不要跳过 `logs` 直接猜** | 日志里通常已经写明了原因 |

## 小结

| 要点 | 内容 |
|------|------|
| 第一原则 | 先定层次（哪一类现象），再定原因。不随机试错 |
| 通用五步 | `ps -a` → `logs` → `inspect` → `info`/`df` → `exec` 进容器 |
| 七类现象 | ① 创建失败 ② 立刻退出 ③ 访问不到 ④ 变慢 ⑤ 互连不通 ⑥ 构建失败 ⑦ 磁盘满 |
| 高频三根因 | 主进程后台化（退出码 0）、依赖未就绪（`Connection refused`）、内存超限（137） |
| 访问不到的隐形原因 | `-p` 方向写反、服务绑 `127.0.0.1` |
| 互连不通的隐形原因 | 用了默认 bridge、`depends_on` 没配 `condition` |
| 求助必给 | 完整命令 + `ps -a` + `logs` + `version` + 最近改了什么 |
| 纪律 | 保现场、优先重建、一次一变量、不动生产 |

## 练习

1. **按现象分类**：下面三个报错分别属于哪一类现象？各自的**第一条**排查命令是什么？
   - `docker: Error response from daemon: driver failed programming external connectivity: bind: address already in use`
   - 容器 `Exited (0)`，日志显示 "server started successfully"
   - `docker compose` 里 `app` 日志反复出现 `could not connect to server: Connection refused`
2. **完整排查演练**：用 4.2 节的项目，故意制造三个故障并各自修复：
   - (a) 把 `app` 的 `DB_HOST` 改成不存在的名字
   - (b) 删掉 `db` 的 `healthcheck` 与 `condition`
   - (c) 把 `-m` 限到 20m 让它 OOM
3. **收集诊断信息**：写一个 shell 脚本，输入容器名，自动输出本页第四节"必提供"的全部信息。
4. **验证"先备份现场"的价值**：启动一个会立刻退出的容器，先 `docker logs` 保存输出，再 `docker rm` 它，尝试再次 `docker logs`，体会差别。
