# 资源限制

## 学习目标

读完本篇，你应当能够：

1. 说清"不给容器设限制"会带来什么具体风险
2. 正确设置内存、CPU、进程数、文件句柄四类限制
3. **解释只设 `-m` 而不设 `--memory-swap` 会带来什么意外行为**
4. 用三条命令验证限制是否真的生效
5. 在 Compose 中正确表达资源限制

## 一、为什么不限制很危险

**Docker 默认不给容器任何资源上限。** 一个容器可以吃掉宿主机的全部 CPU 和内存。

| 风险 | 具体后果 |
|------|----------|
| **单个容器拖垮整机** | 内存泄漏的容器把宿主内存吃光，触发宿主的 OOM Killer，可能杀掉**其他**进程（甚至 sshd，导致你连不上服务器） |
| **互相干扰** | 一个容器的计算任务占满 CPU，其他服务响应变慢 |
| **fork 炸弹** | 容器里的程序递归创建进程，耗尽宿主 PID 资源，整机无法创建新进程 |
| **磁盘 IO 抢占** | 大量磁盘读写让其他服务的 IO 等待时间飙升 |
| **无法做容量规划** | 不知道每个服务实际能用多少，无法判断该买多大的机器 |

> **一条实践原则**：**只要容器不是"独占整台机器"，就应该设限制。** 特别是在一台机器上跑多个服务时，限制是"隔离"从"能用"走向"可靠"的关键一步。

## 二、内存限制

### 2.1 基本用法

```bash
docker run -m 512m nginx          # 硬限制 512 MB
docker run -m 1g --memory-swap 2g nginx
docker run --memory-reservation 256m nginx    # 软限制
```

| 参数 | 含义 |
|------|------|
| `-m` / `--memory` | **硬限制**。容器内存用量达到此值即被 OOM Killer 杀掉 |
| `--memory-swap` | 内存 + swap 的**总量**上限（注意：是总量，不是"swap 单独的量"） |
| `--memory-reservation` | **软限制**。语义上是"建议值"，压力大时才生效，不保证 |
| `--oom-kill-disable` | ⚠️ 禁止 OOM 杀容器。**极度危险**——会导致宿主内存耗尽 |

### 2.2 `--memory-swap` 的真实语义（重要）

这是最容易误解的参数。

| `-m` | `--memory-swap` | 效果 |
|------|-----------------|------|
| `512m` | 不设置 | 容器可用 **512 MB 内存 + 512 MB swap**（swap 默认等于 `-m` 的值） |
| `512m` | `1g` | 容器可用 **512 MB 内存 + 512 MB swap**（总量 1g） |
| `512m` | `512m` | **禁用 swap**（总量 = 内存量） |
| `512m` | `-1` | 无限 swap（**默认行为**，等价于不设 `-m` 时的 swap 待遇） |
| `512m` | `0` | 同 `512m`（禁用 swap） |

> **关键理解**：`--memory-swap` 是"内存 + swap 的总配额"，所以：
> **`--memory-swap = -m` 时代表禁用 swap**；**不设置 `--memory-swap` 时，swap 额度默认等于 `-m`**。
>
> **如果你希望"超过 512 MB 就直接被杀、不要去用 swap"**，必须显式写：
> ```bash
> docker run -m 512m --memory-swap 512m myapp
> ```
> 否则容器可能用 swap 撑到 1 GB 才被杀——**在 swap 上运行的服务性能会急剧下降**（这是"容器变慢但没被杀死"的常见原因）。

### 2.3 超限后的行为

```
内存用量 → 达到 -m
    ↓
内核尝试回收（释放缓存）
    ↓
仍不够 → 触发 OOM Killer
    ↓
杀掉容器内的进程 → 容器以退出码 137 结束
```

**验证是否被 OOM：**

```bash
docker inspect <容器> --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
# 137 true  → 确认是内存超限
```

**宿主侧的日志（排查依据）：**

```bash
dmesg | grep -i "oom\|killed process"
# 或
journalctl -k | grep -i oom
```

> ⚠️ **容器内的 `free` 命令会骗你**：容器内看到的"总内存"可能是宿主的总量（取决于 `lxcfs` 是否安装）。**不要用容器内 `free` 判断限制是否生效**，用 `docker stats` 或 `docker inspect`。

## 三、CPU 限制

CPU 限制的语义比内存复杂，因为 CPU 是"可分配的比例"而非"可独占的量"。

| 参数 | 含义 | 类比 |
|------|------|------|
| `--cpus=1.5` | **绝对上限**：最多用 1.5 个核的算力 | "最多给你 1.5 个人干活" |
| `--cpuset-cpus="0,1"` | **绑核**：只能跑在 0、1 号 CPU 上 | "只准在 1 号和 2 号工位工作" |
| `--cpu-shares=512` | **相对权重**（默认 1024） | "竞争时按权重分，没竞争时可以全占" |

### 3.1 `--cpus`：最常用的方式

```bash
docker run --cpus=1.5 myapp        # 最多 1.5 核
docker run --cpus=0.5 myapp        # 最多半核
docker run --cpus=4 myapp          # 最多 4 核
```

| 要点 | 说明 |
|------|------|
| 这是**硬上限** | 超过就会被限流（throttle） |
| 允许小数 | 所以能表达"半个核" |
| **限流会表现为延迟** | 容器不会被杀，但会变慢。`docker stats` 里能看到 CPU % 被压在 150% 附近（1.5 核 = 150%） |

### 3.2 `--cpuset-cpus`：绑核

```bash
docker run --cpuset-cpus="0,1" myapp      # 只能用 0、1 号核
docker run --cpuset-cpus="0-3" myapp      # 用 0 到 3 号核
```

| 用途 | 说明 |
|------|------|
| **减少上下文切换** | 绑核后进程不会被调度到其他核，缓存命中率更高 |
| **隔离干扰** | 把延迟敏感的服务固定在特定核上，与批处理任务分开 |
| ⚠️ **可能降低吞吐** | 核少了，并行度下降 |

### 3.3 `--cpu-shares`：相对权重（注意语义）

```bash
docker run --cpu-shares=512 myapp        # 默认 1024，这里是"一半的权重"
```

| 关键认知 | 说明 |
|----------|------|
| **它不是上限** ⚠️ | 只是"CPU 争抢时的分配比例" |
| 没有竞争时 | 容器可以占满所有 CPU |
| 有竞争时 | 按权重比例分配 |
| 实际用途 | 在"同一台机器上的多个服务"之间分配优先级，而不是限制单个服务的峰值 |

> **实践建议**：想"限制"就用 `--cpus`；想"调优先级"才用 `--cpu-shares`。初学者最常犯的错是拿 `--cpu-shares` 当限制用，结果发现"限制根本没生效"。

### 3.4 验证 CPU 限制

```bash
docker run -d --name cputest --cpus=1 progrium/stress --cpu 4
docker stats cputest
# 观察 CPU % 应被压在 100% 附近（1 核 = 100%），而不是 400%
```

## 四、进程数限制：防 fork 炸弹

```bash
docker run --pids-limit 100 myapp
```

| 要点 | 说明 |
|------|------|
| 限制容器内**最大进程/线程数** | 默认无限制 |
| **防御目标** | fork 炸弹（`:(){ :|:& };:`）与线程泄漏 |
| 达到上限的后果 | 新进程创建失败（`fork: retry: Resource temporarily unavailable`），容器本身不会被杀 |
| 合理值 | 按应用需要设。Web 服务通常几百够用；`-1` 表示不限 |

**`docker stats` 的 `PIDS` 列**可以直接观察当前进程数。这是判断"是不是 fork 炸弹"的第一入口。

## 五、文件句柄与其他限制：`--ulimit`

```bash
docker run --ulimit nofile=4096:8192 myapp
docker run --ulimit nproc=512 myapp
docker run --ulimit core=0 myapp
```

| 格式 | 含义 |
|------|------|
| `--ulimit <类型>=<软限制>:<硬限制>` | 同时设软硬限制 |
| `--ulimit <类型>=<值>` | 软硬设为同一个值 |

| 常见类型 | 含义 |
|----------|------|
| `nofile` | 打开文件描述符数（**高并发服务的常见瓶颈**） |
| `nproc` | 进程/线程数 |
| `core` | core dump 文件大小（设 0 关闭） |
| `nofile` 默认值 | 通常是 1024 或 1048576（视宿主配置） |

> **`nofile` 与"Too many open files"**：如果你的服务在高并发下报这个错，而宿主限制很宽，**先检查容器的 `nofile` 限制**（`docker exec <容器> ulimit -n`）。这是容器化服务的经典坑。

## 六、块设备 IO 限制

```bash
docker run --device-read-bps /dev/sda:10mb myapp
docker run --device-write-bps /dev/sda:10mb myapp
docker run --device-read-iops /dev/sda:1000 myapp
docker run --blkio-weight 500 myapp
```

| 参数 | 含义 |
|------|------|
| `--device-read-bps` / `-write-bps` | 每秒读写字节数上限 |
| `--device-read-iops` / `-write-iops` | 每秒 IO 次数上限 |
| `--blkio-weight` | 相对权重（类似 `--cpu-shares`） |

> **注意平台限制**：这些参数主要对**直连块设备**生效。在 Docker Desktop（Windows/macOS）上，由于存储走的是虚拟化层，**这些限制常常不生效**。生产环境的 Linux 上才有意义。

## 七、重启策略（补充）

在 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]] 已介绍，这里补充"与资源限制的配合"：

```bash
docker run -d -m 512m --restart on-failure:5 myapp
```

| 组合 | 效果 |
|------|------|
| `-m 512m` + `--restart always` | ⚠️ **危险组合**：若程序持续内存泄漏，会陷入"启动 → OOM 被杀 → 重启 → OOM"的循环，反复消耗 CPU |
| `-m 512m` + `--restart on-failure:5` | ✅ 更可控：最多重试 5 次后停下，让你能发现并处理 |

> **实践建议**：**给内存限制配上次数限制的重启策略**，或配合健康检查与告警。无限制的 `always` 在内存问题上会掩盖故障。

## 八、验证限制是否生效（三条命令）

### 8.1 `docker stats`：看实时占用与上限

```bash
docker stats --no-stream
# CONTAINER   CPU %   MEM USAGE / LIMIT     MEM %   PIDS
# myapp       12.5%   180MiB / 512MiB       35.2%   18
```

| 观察点 | 含义 |
|--------|------|
| `MEM USAGE / LIMIT` 的分母 | **就是 `-m` 的值**。显示 `512MiB` 说明限制生效了 |
| `CPU %` | 被 `--cpus` 限流后会稳定在上限附近 |
| `PIDS` | 接近 `--pids-limit` 说明要调大 |

### 8.2 `docker inspect`：看实际配置值

```bash
docker inspect myapp --format 'Memory={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}} PidsLimit={{.HostConfig.PidsLimit}}'
# Memory=536870912 NanoCpus=1500000000 PidsLimit=100
```

| 陷阱 | 说明 |
|------|------|
| `Memory` 单位是**字节** | `536870912` = 512 MB。看到大整数是正常的 |
| `NanoCpus` 单位是**纳核** | `1500000000` = 1.5 核（`1.5 × 10^9`） |
| `PidsLimit: -1` | 表示无限制 |

### 8.3 容器内部：看 cgroup 文件

```bash
docker exec myapp cat /sys/fs/cgroup/memory.max        # cgroup v2
docker exec myapp cat /sys/fs/cgroup/memory/memory.limit_in_bytes   # cgroup v1
```

> **这就是底层真相**：Docker 的资源限制最终是写在 **cgroup** 文件里的（见下方第十节）。读这个文件是"绕过所有抽象层"的确认方式。

## 九、在 Compose 中表达资源限制

**Compose 有两个地方可以写，但只有一个生效——这是必须知道的坑。**

```yaml
services:
  app:
    image: myapp:1.0
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 512M
        reservations:
          cpus: "0.25"
          memory: 128M
```

| 关键认知 | 说明 |
|----------|------|
| `deploy.resources.limits` 在 **Compose** 下是**生效的** | 不要被"`deploy` 是 Swarm 专用"的老文档误导 |
| 但 `deploy.replicas` 等**其他 deploy 字段**在非 Swarm 下大多无效 | 只有 `resources.limits/reservations` 被 Compose 支持 |
| 传统写法（旧版也支持） | `mem_limit`、`cpus`、`pids_limit` 等顶层服务字段 |

**两套写法的对应关系：**

| `docker run` 参数 | Compose 顶层字段（旧写法） | Compose `deploy` 字段 |
|-------------------|---------------------------|----------------------|
| `-m 512m` | `mem_limit: 512m` | `deploy.resources.limits.memory: 512M` |
| `--cpus=1.5` | `cpus: 1.5` | `deploy.resources.limits.cpus: "1.5"` |
| `--pids-limit 100` | `pids_limit: 100` | —— |
| `--ulimit nofile=4096:8192` | `ulimits: {nofile: {soft: 4096, hard: 8192}}` | —— |

```yaml
services:
  app:
    # 旧式顶层写法（更贴合 docker run 的语义，推荐入门使用）
    mem_limit: 512m
    cpus: 1.5
    pids_limit: 100
    ulimits:
      nofile:
        soft: 4096
        hard: 8192
    # 或使用 deploy 形式（推荐，与 K8s/Swarm 语义一致）
    deploy:
      resources:
        limits:
          cpus: "1.5"
          memory: 512M
```

> ⚠️ **`cpus` 的值要加引号**：`cpus: 1.5` 会被 YAML 解析为浮点数，某些版本的 Compose 会警告或行为异常；写成 `"1.5"` 更安全。

## 十、底层机制：cgroup（一句话）

Docker 的资源限制**不是 Docker 自己实现的**，而是把参数写进 Linux 内核的 **cgroup（控制组）**。

| 机制 | 作用 | 对应限制项 |
|------|------|-----------|
| `memory` cgroup | 限制内存用量 | `-m` / `--memory-swap` |
| `cpu` cgroup | 限制 CPU 带宽 | `--cpus` |
| `cpuset` cgroup | 绑定 CPU 核 | `--cpuset-cpus` |
| `pids` cgroup | 限制进程数 | `--pids-limit` |
| `blkio` cgroup | 限制块设备 IO | `--device-*-bps` |

**cgroup v1 与 v2 的差异：**

| 版本 | 特点 | 如何查看 |
|------|------|----------|
| cgroup v1 | 每种资源一个独立层级 | `/sys/fs/cgroup/memory/...` |
| **cgroup v2** | 统一层级（现代系统默认） | `/sys/fs/cgroup/memory.max` |

```bash
docker info | grep -i cgroup
# Cgroup Version: 2
```

> 完整原理（cgroup 层级结构、如何被的内核调度、与 namespace 的配合）属于中段内容，见 [[docker/02-中段阶段-专题精讲/资源限制与性能/专题概览]]。

## 十一、常见陷阱汇总

| 陷阱 | 现象 | 处理 |
|------|------|------|
| 不设任何限制 | 单容器拖垮整机 | 至少设 `-m` 与 `--cpus` |
| 只设 `-m` 不设 `--memory-swap` | 容器用 swap 撑到 2 倍限制，**性能暴跌但不被杀** | 显式设 `--memory-swap` 等于 `-m` 以禁用 swap |
| 用 `--cpu-shares` 当限制 | 限制"不生效"（无竞争时可占满） | 用 `--cpus` |
| 用容器内 `free` 验证内存限制 | 看到的是宿主总量 | 用 `docker stats` 或 cgroup 文件 |
| `docker inspect .HostConfig.Memory` 看到大整数 | 以为异常 | 单位是字节 |
| `-m` + `--restart always` | 内存泄漏导致无限重启循环 | 用 `on-failure:N` |
| 高并发报 "Too many open files" | 只查宿主限制 | 也要查 `docker exec <容器> ulimit -n` |
| Docker Desktop 上测 IO 限制 | 不生效 | 这些限制需在 Linux 上验证 |
| Compose 里以为 `deploy` 不生效 | 去用旧写法 | Compose 下 `deploy.resources.limits` 是生效的 |

## 小结

| 要点 | 内容 |
|------|------|
| 为什么限制 | 防单容器拖垮整机、防 fork 炸弹、便于容量规划 |
| 内存 | `-m` 硬限制；**`--memory-swap` 是"内存+swap 总量"，不设时 swap 额度默认等于 `-m`** |
| 超限行为 | 触发 OOM Killer → 退出码 137 + `OOMKilled: true` |
| CPU | `--cpus` 是硬上限；`--cpu-shares` 只是相对权重（**不是限制**）；`--cpuset-cpus` 绑核 |
| 进程数 | `--pids-limit` 防 fork 炸弹 |
| 文件句柄 | `--ulimit nofile`，高并发服务必查 |
| 验证三法 | `docker stats`、`docker inspect --format`、读 cgroup 文件 |
| Compose | `deploy.resources.limits` **在 Compose 下生效**；旧式 `mem_limit`/`cpus` 也可用 |
| 底层 | 全部落到 Linux 的 **cgroup** |

## 练习

1. **观察 OOM**：
   ```bash
   docker run --name mem1 -m 20m alpine sh -c "dd if=/dev/zero of=/dev/null bs=1M count=500"
   docker inspect mem1 --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
   ```
   然后去掉 `-m` 再跑一次（⚠️ 注意可能影响宿主，跑前想清楚）。
2. **验证 CPU 限制**：
   ```bash
   docker run -d --name cpu1 --cpus=0.5 progrium/stress --cpu 4
   docker stats --no-stream cpu1     # CPU % 应该被压在 50% 附近
   ```
   改成 `--cpus=2` 再对比。
3. **验证 swap 语义**：分别用 (a) `-m 100m` (b) `-m 100m --memory-swap 100m` 启动同一个吃内存的程序，观察被杀时的实际内存用量差异，解释原因。
4. **验证 `--cpu-shares` 不是限制**：启动一个 `--cpu-shares=100` 的 CPU 密集容器（宿主无其他负载），观察它能否占满 CPU。
5. **验证 fork 炸弹防护**：
   ```bash
   docker run --name bomb --pids-limit 50 alpine sh -c ':(){ :|:& };: ' 
   docker inspect bomb --format 'exit={{.State.ExitCode}}'
   docker stats bomb --no-stream      # 观察 PIDS 列
   ```
6. **找 nofile 瓶颈**：
   ```bash
   docker run --rm --ulimit nofile=64:64 alpine sh -c 'ulimit -n'
   docker run --rm alpine sh -c 'ulimit -n'      # 对比默认值
   ```
7. **Compose 资源限制**：给 4.2 节的 `app` 服务加上内存 512M、CPU 1.0 的限制，用 `docker compose config` 验证，再用 `docker stats` 确认生效。
