# 进入容器与查看日志

## 学习目标

读完本篇，你应当能够：

1. 说清 `docker exec` 与 `docker attach` 的本质差别，并在正确的场景选对命令
2. 在"容器里没有 bash"的情况下依然能进去排查
3. 熟练使用 `logs` 的过滤参数，快速定位日志中的关键行
4. 读懂 `docker inspect` 输出中的关键字段，用它解决网络与挂载问题
5. 在容器与宿主机之间安全地互传文件

## 一、为什么要"进入容器"

容器正常运行时是**不需要**你进去的。进入容器只为了解决三类问题：

| 场景 | 进入容器要做什么 |
|------|------------------|
| **排查配置** | 看配置文件到底是不是我以为的内容、环境变量有没有传进去 |
| **排查网络** | 从容器内部试着连数据库/外部接口，判断是网络问题还是应用问题 |
| **验证依赖** | 确认程序、库、目录是否存在 |

> ⚠️ **一条纪律**：**不要在运行的容器里改代码或改配置来解决生产问题。**
> 容器内的改动：① 容器重建就丢失；② 不会被记录在任何地方；③ 让镜像与实际运行状态不一致。
> **正确做法是改 Dockerfile 或挂载配置，然后重建容器。** 进容器只用于"看"，不用于"改"。

## 二、`exec` 与 `attach`：本质区别

这是初学者最容易搞混的一对命令。

| | `docker exec` | `docker attach` |
|---|---|---|
| **做什么** | 在容器里**启动一个新进程** | 连接到容器**已有的主进程**的输入输出 |
| **进程关系** | 新进程是主进程的"兄弟"（同在容器内） | 你直接对着 PID 1 说话 |
| **退出后果** | ✅ **容器继续运行** | ⚠️ 退出可能导致**容器停止** |
| **能否在容器未运行时用** | ❌ 不能（容器必须是 running） | ❌ 不能 |
| **典型用途** | 进 shell、执行单条命令 | 看主程序的标准输出（较少用） |

### 为什么 `exec` 退出不影响容器

回顾 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.2-容器的创建与运行]] 的核心原理：容器只关心主进程。`exec` 启动的是**额外的进程**，它退不退与主进程无关。

```
容器内：
  PID 1   ← 主进程（如 nginx），它退出容器才结束
  PID 47  ← 你 exec 出来的 sh，退出它毫无影响
```

### 结论

| 需求 | 用哪个 |
|------|--------|
| 进容器看文件/敲命令 | ✅ **`exec`**（99% 的情况） |
| 看主程序的实时输出 | ✅ 用 `docker logs -f`（比 `attach` 更好，见下节） |
| 需要给主进程喂输入 | `attach`（但极少见） |

> **实践建议**：几乎只需要 `exec`。`attach` 的场景基本可以被 `logs -f` 替代，而且 `logs -f` 更安全——**`Ctrl+C` 退出时不会影响容器**。

## 三、`docker exec` 的完整用法

### 3.1 进交互 shell

```bash
docker exec -it <容器名> bash
```

| 片段 | 含义 |
|------|------|
| `exec` | 在运行中的容器里执行命令 |
| `-i` | 保持标准输入打开（你的键盘输入能进去） |
| `-t` | 分配伪终端（有提示符、支持颜色、`Ctrl+C` 正常） |
| `bash` | 要执行的命令——这里是启动一个 bash |

### 3.2 容器里没有 bash 怎么办

**这是极高频问题**。基于 Alpine 的镜像通常**只有 `sh`，没有 `bash`**：

```bash
docker exec -it my-web bash
# OCI runtime exec failed: exec: "bash": executable file not found in $PATH
```

三种解决办法：

| 方法 | 命令 | 说明 |
|------|------|------|
| **改用 `sh`** | `docker exec -it my-web sh` | ✅ 最简单。Alpine、`distroless`、`slim` 都用 `sh` |
| 查有哪些 shell | `docker exec my-web sh -c "cat /etc/shells"` | 先看镜像里有什么 |
| 用 `--entrypoint` 起一个新容器 | `docker run -it --rm --entrypoint sh <镜像名>` | 当容器**起不来**时的终极手段 |

> **`sh` 与 `bash` 的关系**：`bash` 是 `sh` 的功能增强版。`sh` 语法更少但**几乎总是存在**（因为它是 POSIX 标准要求的）。所以"进去看看"用 `sh` 的兼容性最好。

### 3.3 不进入，只执行一条命令

排查时最常用的形式——**不交互，直接拿结果**：

```bash
docker exec my-web ls /etc/nginx/conf.d          # 看目录
docker exec my-web cat /etc/nginx/nginx.conf     # 看配置
docker exec my-web env                           # 看环境变量
docker exec my-web ps aux                        # 看进程
docker exec my-web nslookup db                    # 测 DNS 解析（镜像里要有该命令）
```

对数据库容器特别实用：

```bash
# 进入 psql 交互界面
docker exec -it my-postgres psql -U app -d appdb

# 只执行一条 SQL 并退出
docker exec my-postgres psql -U app -d appdb -c "SELECT version();"
```

### 3.4 `exec` 的其他有用参数

| 参数 | 作用 | 示例 |
|------|------|------|
| `-u` | 指定以哪个用户执行 | `docker exec -u root my-web sh`（容器默认用户不是 root 时提权排查） |
| `-w` | 指定工作目录 | `docker exec -w /app my-web ls` |
| `-e` | 传入环境变量 | `docker exec -e DEBUG=1 my-web ./check.sh` |
| `-d` | 后台执行 | 少用 |

> **`-u` 的实战价值**：如果镜像里用 `USER` 指令切换到了非 root 用户（这是安全上的好做法），你可能因权限不足无法查看某些文件。此时 `docker exec -u root` 可以临时提权排查。**但只用于排查，不要用它改东西。**

## 四、`docker logs`：查看容器输出

### 4.1 基础用法

```bash
docker logs my-web              # 全部输出
docker logs -f my-web           # 实时跟踪（Ctrl+C 退出查看，不影响容器）
docker logs --tail 50 my-web    # 只看最后 50 行
docker logs -t my-web           # 每行带时间戳
docker logs --since 10m my-web  # 最近 10 分钟
docker logs --since 2026-09-22T10:00:00 my-web
docker logs --until 10m my-web  # 10 分钟前为止
```

### 4.2 日志里到底有什么

`docker logs` 显示的是容器**主进程写到标准输出（stdout）和标准错误（stderr）的内容**。

| 关键认知 | 说明 |
|----------|------|
| **不是所有日志都在这里** | 如果程序把日志写进**文件**（如 `/var/log/app.log`），`docker logs` 看不到它 |
| **看文件里的日志要 `exec`** | `docker exec my-web tail -f /var/log/app.log` |
| **容器被删除，日志也一起消失** | 因为日志由容器持有。这就是生产环境必须做日志收集的原因 |

> **这是 Docker 日志机制的核心设计**：Docker 期望应用**把日志写到标准输出**，由 Docker 统一接管（"12-factor app"的日志原则）。写文件的旧习惯在容器里会造成"日志到底在哪"的困惑。

### 4.3 日志存在哪里

默认日志驱动是 `json-file`，每个容器的日志存在宿主机的：

```
/var/lib/docker/containers/<容器ID>/<容器ID>-json.log
```

（Windows / macOS 上在 Docker 的虚拟机内部，宿主机看不到该路径。）

**这里有个必须知道的坑：**

> ⚠️ **默认情况下，这个日志文件会无限增长**，长期运行的容器可能把宿主机磁盘写满。
>
> 解决办法是配置日志轮转——在 `daemon.json` 里设置全局 `max-size` / `max-file`，或在 `docker run` 时用 `--log-opt` 单独设置。详见 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.2-磁盘占用与日志清理]]。

### 4.4 组合排错示例

排查"应用连不上数据库"：

```bash
# 1) 先看应用日志里的报错
docker logs --tail 100 my-app

# 2) 看数据库容器是否正常
docker logs --tail 50 my-postgres

# 3) 从应用容器内部测试能否解析数据库名
docker exec my-app nslookup db

# 4) 从应用容器内部测试端口连通性
docker exec my-app sh -c "nc -zv db 5432 || echo 'connect failed'"
```

这个顺序在第 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.3-容器排错流程]] 中会有更系统的展开。

## 五、`docker inspect`：查看容器全部元数据

```bash
docker inspect my-web
```

输出很长，建议用 `--format` 提取关心的字段。

### 5.1 最常用的字段

```bash
# 运行状态、退出码、是否被 OOM 杀掉
docker inspect my-web --format '{{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'

# 容器 IP（在哪个网络里、地址是多少）
docker inspect my-web --format '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}'

# 挂载（这个容器挂了哪些卷/路径）
docker inspect my-web --format '{{json .Mounts}}'

# 端口映射
docker inspect my-web --format '{{json .NetworkSettings.Ports}}'

# 环境变量
docker inspect my-web --format '{{json .Config.Env}}'

# 启动命令与入口
docker inspect my-web --format 'ENTRYPOINT={{json .Config.Entrypoint}} CMD={{json .Config.Cmd}}'

# 重启策略
docker inspect my-web --format '{{json .HostConfig.RestartPolicy}}'
```

### 5.2 关键字段对照表

| 路径 | 含义 | 什么时候查它 |
|------|------|--------------|
| `.State.Status` | `running` / `exited` / `created` | 确认状态 |
| `.State.ExitCode` | 退出码 | 容器退出后排错 |
| `.State.OOMKilled` | 是否因内存超限被杀 | **退出码 137 时必查** |
| `.State.StartedAt` / `.FinishedAt` | 启停时间 | 判断是否反复重启 |
| `.Config.Env` | 环境变量（含默认值） | 确认 `-e` 有没有生效 |
| `.Config.Cmd` / `.Entrypoint` | 启动命令 | 排查 `OCI runtime create failed` |
| `.HostConfig.RestartPolicy` | 重启策略 | 确认 `--restart` 是否写对 |
| `.HostConfig.Memory` / `.NanoCpus` | 资源限制（字节 / 纳秒） | 确认限制是否真的设上了 |
| `.NetworkSettings.Ports` | 端口映射 | 端口访问不通时查 |
| `.Mounts` | 挂载清单 | 数据"没挂上"时查 |
| `.LogPath` | 日志文件在宿主机的路径 | 磁盘被日志占满时查 |

> **`.HostConfig.Memory` 的单位陷阱**：它输出的是**字节数**。`-m 512m` 会显示为 `536870912`。看到大整数不要以为是异常。

## 六、`docker cp`：容器与宿主机互传文件

```bash
# 从容器复制到宿主机
docker cp my-web:/etc/nginx/nginx.conf ./nginx.conf

# 从宿主机复制到容器
docker cp ./app.conf my-web:/etc/nginx/conf.d/app.conf

# 复制整个目录
docker cp my-web:/var/log/nginx ./nginx-logs
```

| 特性 | 说明 |
|------|------|
| 容器**不需要在运行** | 停止的容器也可以 `cp`（因为它操作的是文件系统） |
| 用于排查 | 把配置文件拷出来对比（如与宿主机上挂载的那份比对） |
| 用于修复 | ⚠️ **临时手段**。拷进去的修改在容器重建后消失，正式修复应改镜像或挂载 |

> ⚠️ **安全提示**：`docker cp` 历史上曾有安全漏洞（归档解压路径处理问题，已在 Engine 29.5.1 修复）。在不可信容器上使用前，建议把 Engine 升级到当前版本。

## 七、观察资源占用：`stats` 与 `top`

### 7.1 `docker stats`：实时资源监控

```bash
docker stats                   # 所有运行中容器的实时数据
docker stats my-web my-db      # 只看指定容器
docker stats --no-stream       # 只输出一次（适合脚本）
```

| 列 | 含义 |
|----|------|
| `CPU %` | CPU 使用率（可能超过 100%，表示多核） |
| `MEM USAGE / LIMIT` | 当前内存占用 / 限制。**这里能看到你设的限制有没有生效** |
| `MEM %` | 内存占比 |
| `NET I/O` | 累计网络收发字节数 |
| `BLOCK I/O` | 累计磁盘读写字节数 |
| `PIDS` | 进程数（**判断有没有 fork 炸弹**） |

### 7.2 `docker top`：看容器内的进程

```bash
docker top my-web
```

输出的是**宿主机视角**的进程列表（真实 PID），但只包含该容器内的进程。

**它的实战价值**：确认容器里到底跑了什么。比如你 `exec` 进去发现某个进程不见了，或者要核对 PID 1 是哪个程序：

```bash
docker top my-web
# UID   PID    PPID   CMD
# root  48231  48212  nginx: master process nginx -g daemon off;   ← PID 1，主进程
# nginx 48262  48231  nginx: worker process
```

### 7.3 `docker diff`：看容器改了哪些文件

```bash
docker diff my-web
```

| 前缀 | 含义 |
|------|------|
| `A` | Added，新增 |
| `C` | Changed，修改 |
| `D` | Deleted，删除 |

**用途**：判断"这个容器是否被人为改过"，以及"哪些改动会在容器重建后丢失"。**如果发现重要文件出现在这里，说明你正在用容器存不该存的东西。**

## 八、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 `attach` 后按 `Ctrl+C` | **容器被停掉** | 用 `logs -f` 看输出；或 `Ctrl+P` `Ctrl+Q` 脱离 |
| 在容器里改配置"修好了" | 容器重建后问题复现，且没人知道改过什么 | 改 Dockerfile 或挂载文件 |
| 用 `bash` 进 Alpine 容器 | `executable file not found` | 用 `sh` |
| 以为 `docker logs` 能看到所有日志 | 程序写文件的日志看不到 | 用 `exec` 看文件，或让程序改写到 stdout |
| 忽略日志无限增长 | 磁盘被写满（`no space left on device`） | 配置日志轮转 |
| 用 `cp` 往容器里塞文件当部署 | 重建即失效 | 用挂载或重建镜像 |

## 小结

| 要点 | 内容 |
|------|------|
| `exec` vs `attach` | `exec` 起新进程，退出不影响容器；`attach` 连主进程，退出可能停容器 |
| 进容器的常识 | 优先 `docker exec -it <容器> sh`；没 bash 就用 sh |
| 不提权排查 | `docker exec -u root`；不提权只用于看，不用于改 |
| `logs` 的本质 | 显示主进程的 stdout/stderr；**写文件的日志看不到** |
| 日志的位置与风险 | 默认在 `/var/lib/docker/containers/...`，**会无限增长**，必须配轮转 |
| `inspect` 的价值 | 端口、挂载、环境变量、重启策略、是否 OOM——全部排错入口在这里 |
| `stats` / `top` / `diff` | 分别用于看资源、看进程、看文件改动 |

## 练习

1. **对比 `exec` 与 `attach`**：
   ```bash
   docker run -d --name demo -p 8080:80 nginx:1.27-alpine
   docker exec -it demo sh          # 进去后敲 exit —— 容器还在吗？
   docker ps                        # 验证
   ```
   然后用 `docker attach demo`，按 `Ctrl+C`，再看看容器是否还在。
2. **无 bash 环境排查**：`docker exec -it demo bash` 观察报错，然后改用 `sh` 成功进入，查看 `/etc/nginx/conf.d/default.conf` 的内容。
3. **用 `inspect` 回答三个问题**：对上面的 `demo` 容器，分别用 `--format` 查出 (a) 它的 IP 地址 (b) 它的端口映射 (c) 它的挂载清单。
4. **制造 OOM 并诊断**：
   ```bash
   docker run --name oom-test -m 20m alpine sh -c "dd if=/dev/zero of=/dev/null bs=1M count=500"
   docker inspect oom-test --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
   ```
   解释输出，并说明该查哪个字段确认原因。
5. **日志实践**：启动 `my-postgres` 容器，用 `logs --tail 20` 看最后 20 行；再用 `exec` 进入并查看容器内的 PostgreSQL 日志目录（提示：`/var/lib/postgresql/data/log` 或 `/var/log`）。
