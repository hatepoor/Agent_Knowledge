# 容器的创建与运行

## 学习目标

读完本篇，你应当能够：

1. 准确区分 `docker run` / `create` / `start`，并解释为什么 `run` 不能重复执行同名容器
2. 完整说出容器的状态流转，以及每个状态由什么命令触发
3. **解释"容器启动后立刻退出"的根本原因**，并能在 1 分钟内定位
4. 正确使用 `-d` / `-it` / `--rm`，并说明三者各自适用什么场景
5. 配置重启策略，让服务在意外退出后自动恢复

## 一、先分清三个容易混的命令

| 命令 | 做什么 | 能不能重复执行 |
|------|--------|----------------|
| `docker run` | **创建**一个新容器 **并启动** | ❌ 名字会重复 |
| `docker create` | 只创建，**不启动** | ❌ 同上 |
| `docker start` | 启动一个**已存在**的容器 | ✅ 可以反复用到 |

**类比**：`docker run` 像"**新买一台设备并开机**"，`docker start` 像"**把已经买回来的设备重新开机**"。

```bash
# 第一次：使用 run（新建 + 启动）
docker run --name web -d nginx

# 停止后想再起来：用 start（不新建）
docker stop web
docker start web

# 如果这里又敲 docker run --name web -d nginx
# 会报错：Conflict. The container name "/web" is already in use
```

**关键认知**：容器的"配置"（端口映射、挂载、环境变量）是在**创建时**确定的。所以：
- `docker run` 带的 `-p` `-v` `-e` 只在那一次创建时生效
- `docker start` **不能**改这些配置
- 要改配置，只能删除容器后重新 `run`（或 `docker update` 改资源限制与重启策略）

> ⚠️ 这一条解释了初学者最常遇到的困惑："我明明加了 `-p`，为什么还是访问不到？"
> 答案常常是：**你改的是 `run` 命令，但容器是之前用旧参数创建的**，用 `docker start` 起来当然不带新参数。正确做法是 `docker rm` 旧的再 `run`。

## 二、容器的状态机

```
                        docker create
                             ↓
                    ┌─────────────┐
                    │   created   │  （已创建，未启动）
                    └──────┬──────┘
        docker run ────────┤
                           ↓
                    ┌─────────────┐   docker pause    ┌────────────┐
                    │   running   │────────────────→  │   paused   │
                    │             │←────────────────  │            │
                    └──────┬──────┘   docker unpause   └────────────┘
                           │
          ┌────────────────┼─────────────────┐
          │                │                 │
   docker stop      docker kill      主进程自行退出
   (SIGTERM→SIGKILL)  (SIGKILL)      (退出码 n)
          │                │                 │
          └────────────────┴─────────────────┘
                           ↓
                    ┌─────────────┐
                    │   exited    │  （已退出，容器与可写层仍在！）
                    └──────┬──────┘
                           │ docker start  ← 可以重新启动
                           │
                           │ docker rm
                           ↓
                        （销毁）
```

**三个最容易搞混的点：**

| 问题 | 答案 |
|------|------|
| `exited` 的容器还在吗？ | **在**。用 `docker ps -a` 能看到。只有 `docker rm` 才真正销毁 |
| `exited` 的容器占磁盘吗？ | **占**。可写层与日志都还在。这就是磁盘被慢慢吃满的原因之一 |
| `exited` 容器能重新起来吗？ | **能**，`docker start`。数据（可写层内容）还在 |

## 三、核心原理：容器只关心它的主进程（PID 1）

**这是本篇最重要的一节。理解了它，第 00 章里"容器立刻退出"的困惑就彻底解决了。**

### 什么是 PID 1

在 Linux 里，**PID** 是进程编号（Process ID）。系统启动的第一个进程编号是 1。

容器虽然共享宿主内核，但它有自己的**命名空间**，所以容器内也有一个"1 号进程"——就是你启动的那个主命令。

```
容器内的 PID 视图（隔离的）：            宿主机的真实视图：
  PID 1  ← 你 CMD 里写的那个程序           PID 48231  ← 其实是同一个进程
  PID 7                                     PID 48250
  PID 8                                     PID 48251
```

### 规则：主进程退出 → 容器结束

> **容器不是虚拟机。它没有 init 系统帮你"维持运行状态"。它只做一件事：运行你指定的主进程。主进程结束，容器立刻结束。**

这个规则推导出全部现象：

| 你敲的命令 | 结果 | 原因 |
|-----------|------|------|
| `docker run ubuntu` | **立刻退出（退出码 0）** | `ubuntu` 镜像默认没有前台进程可跑，"没事可做"就结束了 |
| `docker run ubuntu echo hi` | 打印 `hi` 后**立刻退出（0）** | `echo` 执行完就结束 |
| `docker run -d nginx` | **持续运行** | `nginx` 的官方镜像把 nginx 配置为**前台运行**（`nginx -g 'daemon off;'`） |
| `docker run -it ubuntu bash` | **保持运行** | `bash` 在等你的输入，属于前台阻塞进程 |
| `docker run -d ubuntu service nginx start` | **立刻退出** | `service start` 把 nginx 放到后台就返回了，主进程结束 |
| `docker run -d python app.py &` | **立刻退出** | `&` 让程序后台化，shell 立即返回 |

### 「前台」与「后台」的本质区别

| | 前台进程（foreground） | 后台进程（daemonize / background） |
|---|---|---|
| 行为 | 一直占着终端，不返回 | 把自己 fork 到后台，父进程立即返回 |
| 对容器 | ✅ **正确**，容器会持续运行 | ❌ **错误**，父进程返回 = 主进程结束 = 容器退出 |
| 典型写法 | `nginx -g 'daemon off;'`、`python app.py`、`gunicorn -c ...`、`nginx`（官方镜像已配好） | `service nginx start`、`systemctl start`、`nohup ... &` |

**所以容器里有一条铁律：**

> **让主进程在前台运行，不要用 `service`/`systemctl`/`nohup`/`&` 把它推到后台。**

这条规则在写 Dockerfile 的 `CMD` 时需要格外注意——见 [[docker/01-入门阶段-基础教程/第02章-镜像构建与Dockerfile/2.1-Dockerfile是什么与指令详解]]。

### 例外：为什么有些镜像看起来"用了后台命令也没事"

因为官方镜像的作者已经在镜像里处理好了。例如 `postgres:18` 镜像的启动脚本会以前台方式运行数据库进程。你不需要自己操心，但**自己写 Dockerfile 时必须管**。

## 四、三个关键参数：`-d` / `-it` / `--rm`

### `-d`（detached，后台运行）

```bash
docker run -d --name web -p 8080:80 nginx
```

**含义**：CLI 发完请求就返回，不占用你的终端，也不打印容器日志。

| 不加 `-d` 会怎样 | 说明 |
|------------------|------|
| 终端被容器输出占住 | 你看到的是实时日志 |
| `Ctrl+C` 会发送信号给容器 | **常常把容器一起停掉** |
| 关闭终端窗口 | 容器可能一并退出 |

**所以：长期服务一律加 `-d`。**

### `-it`（interactive + tty）

这是**两个参数合并**的写法，拆开是：

| 参数 | 全称 | 作用 |
|------|------|------|
| `-i` | `--interactive` | 保持标准输入（stdin）打开，让你的键盘输入能送进容器 |
| `-t` | `--tty` | 分配一个伪终端，让容器里的程序有"终端感"（有提示符、支持颜色、支持 `Ctrl+C`） |

**实践规则**：

| 场景 | 该加 `-i` 吗 | 该加 `-t` 吗 | 原因 |
|------|-------------|-------------|------|
| 进容器敲交互 shell | ✅ | ✅ | 需要输入 + 需要提示符 |
| 跑一次性脚本（不需要输入） | ❌ | ❌ | 加了反而可能干扰 |
| 从 stdin 管道输入 | ✅（只加 `-i`） | ❌ | `-t` 会污染数据流 |
| 只启动服务 | 都不加，用 `-d` | — | 不需要交互 |

典型正确用法：

```bash
docker run -it --rm ubuntu bash         # 进交互 shell
docker run -it --rm --entrypoint sh nginx:1.27-alpine    # 进 shell 排查镜像
echo "SELECT 1;" | docker exec -i mydb psql -U app       # 管道输入，只加 -i
```

> **`-i` 与 `-t` 分开记**：`-it` 是缩写，不是不可分割的整体。管道场景下加 `-t` 会出问题，这是有经验的工程师也常犯的错。

### `--rm`（退出即删除）

```bash
docker run --rm alpine echo "hello"
```

| 不加 `--rm` | 加了 `--rm` |
|-------------|-------------|
| 容器退出后仍以 `exited` 状态存在 | 退出后**自动删除** |
| 需要手动 `docker rm` | 自动清理 |
| 优点：能事后 `logs`/`inspect` 查看现场 | 缺点：现场没了，无法事后排查 |
| 缺点：积累垃圾容器，吃磁盘 | 适合：一次性任务、调试 |

**选择原则**：

| 场景 | 建议 |
|------|------|
| 临时任务、执行一次就跑 | **加 `--rm`** |
| 调试、可能需要事后看日志 | 先不加，看到结果后手动删 |
| 长期服务 | 不加（你要它一直存在），但要用 `--restart` |

## 五、停止、重启与信号

### `docker stop` 做了什么

```bash
docker stop web           # 默认等 10 秒
docker stop -t 30 web     # 给 30 秒优雅退出时间
```

内部是两步：

| 步骤 | 动作 | 目的 |
|------|------|------|
| 1 | 向主进程发送 **SIGTERM** | 让它有机会保存数据、关闭连接（"优雅退出"） |
| 2 | 等超时（默认 10 秒）后发 **SIGKILL** | 强杀，不给机会 |

| 命令 | 信号 | 后果 |
|------|------|------|
| `docker stop` | SIGTERM → （超时）SIGKILL | 尽量优雅 |
| `docker kill` | 直接 SIGKILL | 立即杀掉，程序无机会清理 |

**实践建议**：数据库、消息队列这类服务**优先用 `stop` 而不是 `kill`**，否则可能丢数据或留下损坏的文件。

### 退出码对照（这是排错的入口）

| 退出码 | 信号 | 常见原因 |
|--------|------|----------|
| `0` | — | 正常结束（命令执行完了） |
| `1` | — | 程序自身报错 |
| `126` | — | 命令找到但不可执行（缺执行权限） |
| `127` | — | 命令不存在（`CMD` 写错） |
| `137` | SIGKILL (9) | **被强杀**。最常见是**内存超限被 OOM 杀掉**，或 `docker kill` |
| `143` | SIGTERM (15) | 收到正常停止信号（`docker stop` 的结果） |

> **退出码 `137` 是排查重点**：如果你的容器跑着跑着就"莫名其妙"变成 `Exited (137)`，第一反应应该是**内存限制太小**。验证方式：
> ```bash
> docker inspect <容器> --format '{{.State.OOMKilled}}'   # 输出 true 就是被 OOM 了
> ```
> 内存限制的调整见 [[docker/01-入门阶段-基础教程/第05章-资源限制与日常维护/5.1-资源限制]]。

### 重启策略：`--restart`

长期服务应配置自动重启，否则宿主机重启后服务就没了。

| 策略 | 含义 | 适用 |
|------|------|------|
| `no` | 不自动重启（默认） | 一次性任务 |
| `on-failure[:N]` | 仅当**非 0 退出**时重启，最多 N 次 | 批处理任务 |
| `always` | 总是重启，**包括 `docker stop` 后手动重启 daemon 时也会拉起** | 谨慎使用 |
| `unless-stopped` | 总是重启，**除非你手动 stop 了它** | ✅ **长期服务的推荐值** |

```bash
docker run -d --name web --restart unless-stopped -p 8080:80 nginx
```

**`always` 与 `unless-stopped` 的实际差别**：

| 操作 | `always` | `unless-stopped` |
|------|----------|------------------|
| 容器崩溃 → 自动重启 | ✅ | ✅ |
| 宿主机重启 → 自动拉起 | ✅ | ✅ |
| 你手动 `docker stop` 后 → 宿主机重启 | ⚠️ **会被拉起** | ✅ **保持停止** |

所以 `unless-stopped` 更符合直觉：**你说停就停**。

### 修改已存在容器的配置

部分参数可以在运行中修改：

```bash
docker update --restart always web               # 改重启策略
docker update -m 512m --cpus 1.5 web            # 改资源限制（需先启动）
```

**但不能改的**：端口映射、卷挂载、环境变量、镜像。要改这些**只能删掉重建**。

## 六、交互式容器怎么正确退出（一个高频困惑）

进入交互容器后，两种退出方式后果完全不同：

| 退出方式 | 效果 | 容器状态 |
|----------|------|----------|
| 在 shell 里敲 `exit` | 结束 shell | ⚠️ shell 是主进程 → **容器退出** |
| 按 `Ctrl + P` 然后 `Ctrl + Q` | 从容器"脱离"（detach） | ✅ **容器继续运行**（仅适用于 `docker attach`） |
| 在 `docker exec -it` 里敲 `exit` | 只结束这个 exec 会话 | ✅ **容器继续运行** |

> **关键区别**：`docker exec` 启动的是一个**附加进程**，退出它不影响主进程；而如果主进程本身就是 shell（`docker run -it ubuntu bash`），退出 shell 就等于结束主进程。
>
> 所以：**日常调试用 `exec`（见 [[docker/01-入门阶段-基础教程/第01章-镜像与容器基础操作/1.3-进入容器与查看日志]]），它不会因你退出而停掉服务。**

## 七、其他常用操作

```bash
docker rename web web-old          # 重命名
docker pause web                   # 冻结所有进程（不释放资源）
docker unpause web                 # 解冻
docker wait web                    # 阻塞直到它退出，返回退出码
```

| 命令 | 何时用 |
|------|--------|
| `docker pause` | 临时冻结以让出 CPU（进程状态被挂起，内存仍占着） |
| `docker rename` | 名字起错了，不想重建容器 |
| `docker wait` | 在脚本里等一个一次性容器跑完 |

## 小结

| 要点 | 内容 |
|------|------|
| 三个命令 | `run` = 新建+启动；`create` = 只建；`start` = 启动已有的 |
| 配置时机 | 端口/卷/环境变量只在**创建时**确定，`start` 无法变更 |
| 状态机 | `created` → `running` ⇄ `paused` → `exited` →（`rm`）销毁 |
| 核心原理 | **容器只跑一个主进程（PID 1），主进程退出容器即结束** |
| 铁律 | 容器内的服务必须**前台运行**，不要 `service`/`nohup`/`&` |
| 三参数 | `-d` 长期服务；`-it` 交互；`--rm` 一次性任务 |
| `-it` 拆解 | `-i` 保持输入，`-t` 分配终端。管道场景只加 `-i` |
| 退出码 | `0` 正常；`137` 多为内存超限（查 `.State.OOMKilled`）；`143` 是 `stop` 的结果 |
| 重启策略 | 长期服务用 `--restart unless-stopped` |

## 练习

1. **对比三个命令**：依次执行并解释每步的输出差异。
   ```bash
   docker run --name t1 alpine echo hello     # 观察：容器是退出状态
   docker ps                                  # 看不到 t1
   docker ps -a                               # 看得到 t1，状态 Exited (0)
   docker start t1                            # 重新启动：还会再打印 hello 吗？
   docker logs t1                             # 能看到几条 hello？
   ```
2. **解释退出**：为什么 `docker run -d ubuntu` 会立刻退出，而 `docker run -d nginx` 不会？从"主进程"角度回答。
3. **修正错误写法**：下面的命令为什么会导致容器立刻退出？写出两种修正方式。
   ```bash
   docker run -d --name web nginx sh -c "nginx && sleep 1"
   ```
4. **验证参数不可改**：用 `-p 8080:80` 创建容器，停止后试着用 `docker start` 重新启动并访问 `8081`。解释为什么不行，并写出正确做法。
5. **配置重启策略**：启动一个 `--restart unless-stopped` 的容器，然后 `docker stop` 它，再重启 Docker Desktop。观察它是否被拉起。
