# 镜像的获取与管理

3. 说出 `latest` 标签的真实含义，并制定一套可用于生产的标签策略

## 一、先把"镜像名"读透

初学者 90% 的 `pull` 失败源于**没看懂镜像名的结构**。一个镜像名的完整形式是：

```
registry-host/namespace/repository:tag@digest
```

以 `docker pull docker.io/library/nginx:1.27-alpine@sha256:abc...` 为例：

| 片段 | 值 | 含义 | 可省略？ |
|------|-----|------|----------|
| **registry 主机** | `docker.io` | 哪个仓库服务 | ✅ 省略则默认 Docker Hub |
| **namespace（命名空间）** | `library` | 谁发布的。官方镜像都在 `library` 下 | ✅ 省略则默认 `library` |
| **repository（仓库名）** | `nginx` | 镜像叫什么 | ❌ 必须写 |
| **tag（标签）** | `1.27-alpine` | 版本标记 | ✅ 省略则默认 `latest` |
| **digest（摘要）** | `sha256:abc...` | 内容的哈希，唯一且不可变 | ✅ 省略则用 tag 解析 |

### 省略规则带来的实际后果

| 你写的 | 实际含义 | 说明 |
|--------|----------|------|
| `docker pull nginx` | `docker.io/library/nginx:latest` | 官方镜像可以省掉前缀 |
| `docker pull bitnami/postgresql` | `docker.io/bitnami/postgresql:latest` | 非官方需带命名空间 |
| `docker pull gcr.io/myproj/api` | 从 Google 的仓库拉 | 第三方仓库必须写主机名 |
| `docker pull localhost:5000/myapp` | 从本地仓库拉 | 自建仓库 |

> **一个高频踩坑**：`docker pull postgresql` 会失败，因为官方镜像名是 **`postgres`**（不是 `postgresql`）。同理官方名是 `redis` 而不是 `redis-server`。**不确定时去 <https://hub.docker.com/> 搜。**

## 二、`tag` 与 `latest` 的真实含义（必读）

**tag 只是一个人为约定的字符串**，你可以给它起任何名字。

```bash
docker tag nginx:1.27-alpine my-nginx:v1     # 给已有镜像再打一个名字
```

这条命令**没有复制任何数据**——它只是给同一个镜像 ID 增加了一个别名。所以：

```bash
docker images
# REPOSITORY    TAG            IMAGE ID       SIZE
# nginx         1.27-alpine    a8b1c2d3e4f5   48.2MB
# my-nginx      v1             a8b1c2d3e4f5   48.2MB   ← 同一个 ID，磁盘上只有一份
```

### `latest` 不是"最新版"

这是 Docker 文档中反复强调、但初学者最常误解的一点：

> **`latest` 只是一个默认标签名。它既不保证是最新版本，也不保证是稳定版本。**

| 常见误解 | 事实 |
|----------|------|
| `latest` = 最新版 | 它只是"没写 tag 时的默认值"。维护者可能把 `latest` 指向三年前的老版本 |
| 用了 `latest` 就会自动更新 | ❌ 本地已有 `nginx:latest` 时，`docker run nginx` **不会**去检查有没有新版 |
| `latest` 更方便 | 它是**不可复现**的。今天拉到的和半年后拉到的可能是两个不同的镜像 |

**`latest` 的真实作用**：它只是一个方便的默认值。仅此而已。

### 生产环境的标签策略

| 策略 | 示例 | 适用 | 评价 |
|------|------|------|------|
| 只用 `latest` | `nginx:latest` | 本地随便试试 | ❌ 不可复现，禁止上生产 |
| 固定版本号 | `nginx:1.27-alpine` | **绝大多数场景** | ✅ 推荐 |
| 版本 + 变体 | `python:3.12-slim`、`node:22-alpine` | 需要控制体积时 | ✅ 推荐 |
| 版本 + digest | `nginx@sha256:abc...` | 合规、强可复现要求的场景 | ✅ 最严格 |
| 固定版本 + 自建 tag | `myapp:1.4.2`、`myapp:git-a1b2c3d` | 自建镜像 | ✅ 见 [[docker/02-中段阶段-专题精讲/CI-CD与镜像分发/专题概览]] |

**常见后缀变体的含义**（同一个软件的"口味"）：

| 后缀 | 含义 | 特点 |
|------|------|------|
| 无后缀（如 `python:3.12`） | 完整版 | 功能全，体积大（约 1 GB 级） |
| `-slim` | Debian 精简版 | 去掉编译工具与文档，约缩到 1/4 |
| `-alpine` | 基于 Alpine Linux | **最小**（几 MB 到几十 MB），用 `musl` 而非 `glibc`，**可能缺 bash/curl** |
| `-bookworm` / `-bullseye` | 指定 Debian 版本 | 便于对齐系统库 |
| `-windowsservercore` | Windows 容器 | 只能在 Windows 容器模式下运行 |

## 三、镜像管理命令详解

### 3.1 拉取：`docker pull`

```bash
docker pull nginx:1.27-alpine

# 指定平台（Apple 芯片上跑 amd64 镜像）
docker pull --platform linux/amd64 nginx:1.27-alpine
```

**关于"拉取速度"的观察**：第一次拉 `python:3.12` 很慢，第二次拉 `python:3.12-slim` 却很快。原因是**镜像是分层的，且已存在的层会被跳过**——`slim` 变体复用了大量公共基础层。这个原理在第 02 章展开。

### 3.2 列出：`docker images`

```bash
docker images
```

| 列 | 含义 | 注意点 |
|----|------|--------|
| `REPOSITORY` | 镜像名 | 显示 `<none>` 的是"悬空镜像"（见下） |
| `TAG` | 标签 | 显示 `<none>` 同上 |
| `IMAGE ID` | 镜像 ID（截断的 digest） | 同一个 ID 可以对应多个 REPOSITORY:TAG |
| `CREATED` | 创建时间 | 指**镜像被构建**的时间，不是拉取时间 |
| `SIZE` | 体积 | **是这一套层的总大小**，多个镜像共享的层不重复计算 |

**过滤与格式化：**

```bash
docker images nginx                 # 只看 nginx 相关
docker images --filter "dangling=true"   # 只看悬空镜像
docker images --format "{{.Repository}}:{{.Tag}} {{.Size}}"   # 自定义输出
```

**什么是"悬空镜像"（dangling image）？**

指的是**没有 REPOSITORY 与 TAG 的镜像**（显示为 `<none>:<none>`）。产生原因：镜像被重新构建后，旧的层组合失去了名字引用。

```bash
docker image prune         # 只清悬空镜像（安全）
docker image prune -a      # ⚠️ 清掉所有"无容器引用"的镜像（含你手动拉的 nginx）
```

> ⚠️ `prune -a` 的语义是"**任何没有被容器引用的镜像都会被删**"。当前没有运行 nginx 容器，你的 `nginx:1.27-alpine` 就会一起被删掉，下次要重新拉。**这两个命令的区别务必记住。**

### 3.3 删除：`docker rmi`（以及为什么删不掉）

```bash
docker rmi nginx:1.27-alpine
docker rmi a8b1c2d3e4f5          # 也可以用 IMAGE ID
```

**删除失败的情形与原因：**

| 报错 | 原因 | 正确做法 |
|------|------|----------|
| `image is being used by running container xxx` | 有**运行中**容器在用 | 先 `docker stop` + `docker rm` 容器 |
| `image is referenced in multiple repositories` | 一个镜像 ID 有多个 tag | 先删所有 tag，或加 `-f` 强删单个 tag |
| `conflict: unable to delete xxx (must be forced)` | 有**已停止**的容器引用它 | 删掉那些停止的容器（`docker ps -a` 找） |

> **一个必须理解的点**：**已停止的容器仍然占用镜像**。这是"删不掉镜像"的第一大原因。初学者经常只清理了运行中的容器，忽略了 `docker ps -a` 里那一堆 `Exited`。

### 3.4 查看构建历史：`docker history`

```bash
docker history nginx:1.27-alpine
```

输出逐层显示：**每层由哪条指令产生、每层多大**。

| 列 | 含义 |
|----|------|
| `IMAGE` | 层 ID |
| `CREATED BY` | 产生这一层的构建指令 |
| `SIZE` | **这一层**的大小（不是你改动的净大小，见第 02 章陷阱） |

**用途**：分析一个镜像为什么这么大。**这是镜像瘦身的第一步诊断工具**（见 [[docker/02-中段阶段-专题精讲/镜像优化与瘦身/专题概览]]）。

### 3.5 查看元数据：`docker inspect`

```bash
docker inspect nginx:1.27-alpine
```

输出 JSON，重点字段：

| 字段 | 含义 |
|------|------|
| `.Architecture` / `.Os` | 架构与系统——**`exec format error` 时查这里** |
| `.Config.Cmd` / `.Config.Entrypoint` | 容器启动时执行的命令 |
| `.Config.Env` | 默认环境变量 |
| `.Config.ExposedPorts` | 声明的端口 |
| `.RootFS.Layers` | 全部层的 digest 列表 |

```bash
# 常用提取
docker inspect nginx:1.27-alpine --format '{{.Architecture}}'
docker inspect nginx:1.27-alpine --format '{{json .Config.Cmd}}'
```

### 3.6 离线搬运：`save` / `load`

在没有网络的环境中部署时用：

```bash
# 导出：镜像 → tar 文件
docker save -o nginx.tar nginx:1.27-alpine

# 导入：tar 文件 → 镜像
docker load -i nginx.tar
```

| 命令 | 方向 | 保留什么 |
|------|------|----------|
| `docker save` / `load` | 镜像 ↔ tar | **完整保留**所有层、tag、元数据 |
| `docker export` / `import` | 容器 ↔ tar | ⚠️ **只导出文件系统，丢失层结构与元数据** |

> **不要混用**：`save`/`load` 是"镜像搬家"，`export`/`import` 是"容器快照"。前者保留历史与层，后者会压成扁平的单一层且丢掉 `CMD`/`ENV` 等配置。**需要搬运镜像时永远用 `save`/`load`。**

## 四、常见陷阱汇总

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 用 `latest` | 不可复现；不同时间拉到不同版本 | 固定版本号 |
| `docker image prune -a` | 删掉所有未使用镜像 | 日常用不带 `-a` 的版本 |
| 忘了停止容器占着镜像 | `rmi` 一直失败 | 先 `docker ps -a` 检查 |
| `tag` 后以为占了两份磁盘 | 误判空间 | 同一个 IMAGE ID 只占一份 |
| `export`/`import` 搬镜像 | 丢元数据，容器起不来 | 用 `save`/`load` |
| 把私有镜像当公开的直接拉 | `pull access denied` | 先 `docker login` |
| 拉错架构 | `exec format error` | 用 `--platform` 或选对应架构 tag |

## 小结

| 要点 | 内容 |
|------|------|
| 镜像名结构 | `registry/namespace/name:tag@digest`，前三段可选，`name` 必须有 |
| `latest` 本质 | 只是默认标签名，不代表最新，也不自动更新。生产必须固定版本 |
| tag 的真实作用 | 只是别名，`docker tag` 不复制数据 |
| 层共享 | 相同 ID 的镜像只占一份磁盘；相同层在多个镜像间共享 |
| 删不掉的原因 | **已停止的容器仍然占用镜像** |
| 搬运方式 | `save`/`load`（保层与元数据）优于 `export`/`import`（会丢） |

## 练习

1. **拆解镜像名**：说出下面四个镜像名的完整含义，指出哪些片段被省略了。
   - `nginx:1.27-alpine`
   - `bitnami/postgresql:16`
   - `ghcr.io/owner/private-tool:v2`
   - `redis`
2. **验证 tag 不复制数据**：用 `docker images` 记下 `nginx` 的 IMAGE ID 与 SIZE，然后 `docker tag` 一个新名字，再看一次。解释你观察到的结果。
3. **制造并修复"删不掉"**：
   ```bash
   docker run -d --name keepme nginx:1.27-alpine
   docker rm keepme           # 第一步：先删容器（会失败吗？为什么？）
   docker stop keepme && docker rm keepme
   docker rmi nginx:1.27-alpine   # 现在能删掉了吗？
   ```
4. **判断风险**：你手动拉了 `postgres:18` 和 `redis:7-alpine`，当前没有容器在跑。执行 `docker image prune -a` 会删掉什么？
