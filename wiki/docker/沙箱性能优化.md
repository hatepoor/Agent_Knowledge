# 沙箱性能优化

生产环境中每次 Agent 调用 tool 都要启动容器，延迟直接影响用户体验。以下从镜像、预热、缓存、并发四个维度优化。

## 一、镜像优化

### 1.1 镜像大小对比

| 镜像 | 大小 | 冷启动 | 适用场景 |
|------|------|--------|----------|
| `python:3.11` | ~350MB | ~3s | 开发 |
| `python:3.11-slim` | ~50MB | ~1s | 生产推荐 |
| `python:3.11-alpine` | ~20MB | ~0.5s | 极致优化 |
| 自定义预装 | ~80MB | ~1s | 需要依赖时 |

### 1.2 分层优化 Dockerfile

```dockerfile
# ❌ 每行一层，层数多、缓存差
FROM python:3.11-slim
RUN apt-get update
RUN pip install pandas

# ✅ 合并 RUN，减少层数
FROM python:3.11-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential && \
    pip install --no-cache-dir pandas numpy && \
    apt-get remove -y build-essential && \
    apt-get autoremove -y && \
    rm -rf /var/lib/apt/lists/*
```

## 二、预热池

容器冷启动是最主要的延迟来源（~1s）。预热池预先创建容器，tool 调用时直接复用。

```python
import queue
import threading

class WarmPoolSandbox:
    """预热池：预创建 N 个容器，执行时直接取，用完归还"""

    def __init__(self, config: SandboxConfig, pool_size: int = 3):
        self.config = config
        self.pool_size = pool_size
        self.pool: queue.Queue[str] = queue.Queue(maxsize=pool_size)
        self.lock = threading.Lock()
        self._fill_pool()

    def _fill_pool(self):
        """后台线程持续填充容器池"""
        while self.pool.qsize() < self.pool_size:
            container = self.client.containers.create(
                image=self.config.image,
                command=["sleep", "infinity"],
                mem_limit=self.config.memory_limit,
            )
            container.start()
            self.pool.put(container.id)

    def execute(self, code: str, **kwargs) -> SandboxResult:
        """从池中取容器 → 执行 → 归还"""
        cid = self.pool.get(timeout=5)    # 取一个
        container = self.client.containers.get(cid)

        try:
            # 执行代码
            exec_result = container.exec_run(
                cmd=["python", "-c", code],
                timeout=kwargs.get("timeout", 30),
            )
            return SandboxResult(
                stdout=exec_result.output.decode("utf-8"),
                exit_code=exec_result.exit_code,
                container_id=cid[:12],
            )
        finally:
            self.pool.put(cid)            # 归还到池中
```

**预热池的取舍**：

| 优势 | 劣势 |
|------|------|
| 接近零延迟（复用容器） | 容器间可能状态污染（需 `exec_run` 隔离） |
| 资源利用率高 | 空闲容器消耗内存（~30MB/个） |
| 并发能力好 | 需要监控池中的容器健康状态 |

## 三、exec_run vs containers.run

| 方式 | 延迟 | 适用场景 |
|------|------|----------|
| `containers.run()` | 完整创建+启动+销毁 | 每次执行需完全隔离 |
| `exec_run()` + 长运行容器 | 毫秒级（无需创建） | 预热池/高频调用 |

生产建议：低风险工具用 `exec_run` + 预热池，高风险工具用 `containers.run` 每次新建。

## 四、并发控制

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor

# docker-py 是同步库，在 async FastAPI 中需放到线程池
executor = ThreadPoolExecutor(max_workers=10)

async def execute_async(code: str) -> SandboxResult:
    loop = asyncio.get_event_loop()
    return await loop.run_in_executor(executor, sandbox.execute, code)

# 并发限制：最多 5 个容器同时执行
semaphore = asyncio.Semaphore(5)

@app.post("/sandbox/execute")
async def execute(req: ExecuteRequest):
    async with semaphore:
        result = await execute_async(req.code)
    return {"stdout": result.stdout, "duration_ms": result.duration_ms}
```

## 六、延迟目标

| 指标 | 目标 | 当前方案 |
|------|------|----------|
| P50 执行延迟 | < 500ms | 预热池 `exec_run` |
| P95 执行延迟 | < 2s | `containers.run` + slim 镜像 |
| P99 执行延迟 | < 5s | slim 镜像 + 预拉取 |
| 冷启动（首次调用） | < 3s | 应用启动时预拉镜像 |
