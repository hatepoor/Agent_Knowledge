## 一、进程与线程：并发不是凭空来的

### 1.1 什么是进程

**进程（Process）** 是一个正在运行的程序实例，是操作系统进行**资源分配**的最小单位。
一个 JVM 启动就是一个进程，它向操作系统要一块内存（堆）、若干线程栈、以及文件句柄等资源。

### 1.2 什么是线程

**线程（Thread）** 是进程内部的一条执行路径，是 CPU 调度的最小单位。
一个进程里可以有多条线程，它们**共享**这个进程的内存空间，但各有自己的执行现场。

> 类比：进程像「一家工厂」，线程像「工厂里的工人」。工人共用厂房里的原料（堆），但每个人有自己的工位（栈）和手头的活儿（程序计数器）。

### 1.3 线程的内存模型：共享什么、私有什么

这是全篇最重要的一张图。Java 线程的私有/共享划分，和 JVM 运行时数据区一一对应（回顾 [[java/02-中段阶段-专题精讲/JVM/JVM内存区域与对象布局]]）：

```
┌──────────────────── 一个 JVM 进程 ─────────────────────┐
│                                                          │
│  【线程共享】              ┌──────────────────────────┐ │
│  ┌──────────────┐         │      堆（Heap）           │ │
│  │  方法区/元空间 │         │  所有 new 出来的对象      │ │
│  │ 类信息·静态变量│         │  ⭐ 多个线程同时读写它    │ │
│  └──────────────┘         └──────────────────────────┘ │
│  ┌──────────────────────────┐                          │
│  │      堆（Heap）          │  ⭐ 共享 = 会有数据竞争   │
│  └──────────────────────────┘                          │
│                                                          │
│  【线程私有】—— 每个线程各一份，互不可见                  │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐                │
│  │ 虚拟机栈  │ │本地方法栈│ │程序计数器│                │
│  │ 方法栈帧  │ │ native   │ │ 指令行号 │                │
│  │ 局部变量表│ │ 调用     │ │          │                │
│  └──────────┘ └──────────┘ └──────────┘                │
└──────────────────────────────────────────────────────────┘
```

| 区域 | 是否共享 | 线程安全含义 |
|------|---------|------------|
| 堆（对象、数组） | ✅ 共享 | ⭐ **所有共享可变状态都住在这里，竞态条件的重灾区** |
| 方法区 / 元空间（静态变量） | ✅ 共享 | `static` 字段同样需要同步保护 |
| 虚拟机栈（局部变量） | ❌ 私有 | 方法里的局部变量天然线程安全 |
| 程序计数器 | ❌ 私有 | 每个线程独立记录「执行到哪条指令」 |

⭐ **一句话结论**：**方法参数和局部变量天生线程安全；对象字段和静态字段天生线程不安全。**

⭐ **数据竞争（data race）**：两个线程同时读写同一份共享数据，且至少有一个在写，就可能出乱子。这正是「共享堆」带来并发风险的原因——下一章会专门讲怎么防它（见 [[java/02-中段阶段-专题精讲/并发编程/02-线程安全与Java内存模型]]）。

### 1.4 并发的两种目标

| 目标 | 含义 | 典型场景 |
|------|------|---------|
| **并发（concurrency）** | 多个任务**交替**推进，宏观上同时 | 大量 IO 等待：调接口、读数据库 |
| **并行（parallelism）** | 多个任务在**同一时刻**真的在跑 | CPU 密集计算：加密、图像处理 |

Java 的线程是「抢占式调度」——操作系统随时可能把 CPU 从一个线程抢走给另一个，所以**你无法假设两个线程的执行顺序**。这一条是后面所有并发 bug 的根源。

## 二、创建线程的三种方式

### 方式一：继承 `Thread` 类

**`Thread`** 是 Java 表示线程的核心类，`java.lang.Thread` 实现了 `Runnable` 接口。

```java
public class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("我在 " + Thread.currentThread().getName() + " 线程里跑");
    }

    public static void main(String[] args) {
        MyThread t = new MyThread();
        t.setName("工作线程-1");
        t.start();                 // ⭐ start 才会真正创建线程
    }
}
```

### 方式二：实现 `Runnable` 接口（⭐ 推荐）

**`Runnable`** 是一个函数式接口，只有一个方法 `run()`。

```java
public class MyRunnable implements Runnable {
    @Override
    public void run() {
        System.out.println("我在 " + Thread.currentThread().getName() + " 线程里跑");
    }

    public static void main(String[] args) {
        Thread t = new Thread(new MyRunnable(), "工作线程-2");
        t.start();
    }
}
```

⭐ **为什么推荐 `Runnable`**：

1. **避免继承带来的耦合**——Java **单继承**，一个类一旦 `extends Thread` 就不能再继承别的类；`implements Runnable` 不占用这个名额；
2. **任务与线程分离**——`Runnable` 是「要干什么」，`Thread` 是「谁去干」。同一个任务可以交给不同的执行器（线程池）；
3. **Lambda 友好**——`Runnable` 只有一个抽象方法，可以用 Lambda 表达式一行写完：`new Thread(() -> System.out.println("hi")).start();`

### 方式三：`Callable` + `FutureTask`

**`Callable<V>`** 是 `Runnable` 的加强版：① 可以**返回结果**；② 方法可以**抛受检异常**（`Runnable.run()` 不能抛 `throws` 的受检异常）。

**受检异常（checked exception）** 指 `Exception` 中除 `RuntimeException` 及其子类以外的那些异常（如 `IOException`），编译器强制要求 `try-catch` 或 `throws` 声明。

```java
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.FutureTask;

public class MyCallable {
    public static void main(String[] args) throws ExecutionException, InterruptedException {
        // Callable 可以返回值、可以抛受检异常
        Callable<Integer> task = () -> {
            Thread.sleep(100);
            return 42;
        };

        FutureTask<Integer> future = new FutureTask<>(task);  // 把 Callable 适配成 Runnable + 结果容器
        new Thread(future).start();

        Integer result = future.get();   // 阻塞等待结果，异常会包成 ExecutionException
        System.out.println("拿到结果：" + result);
    }
}
```

**`FutureTask`** 是 `Future`（结果容器）与 `Runnable`（可执行）的合体：它实现了 `RunnableFuture` 接口，既能被 `Thread` 执行，又能 `get()` 结果。

### 三种方式对比

| 维度 | 继承 `Thread` | 实现 `Runnable` | `Callable` + `FutureTask` |
|------|--------------|----------------|------------------------|
| 返回值 | ❌ | ❌ | ✅ |
| 抛受检异常 | ❌ | ❌ | ✅ |
| 复用 `Runnable` 任务 | ❌ | ✅ | ✅ |
| 占用唯一继承名额 | ⚠️ 是 | ✅ 否 | ✅ 否 |
| Lambda 写法 | ❌ | ✅ | ✅ |
| 推荐度 | 仅教学 | ⭐ **日常首选** | 需要返回值/异常时 |

### ⚠️ 实际项目不要手写 `new Thread`

`new Thread(...).start()` 在生产代码里是**反模式**：

| 问题 | 后果 |
|------|------|
| 线程数不可控 | 创建 1 万个请求 → 1 万个线程 → 内存耗尽 / `unable to create new native thread` |
| 无法复用 | 每个任务新建线程、结束后销毁，创建开销远大于任务本身 |
| 无法统一治理 | 没法统一命名、打日志、监控、捕获异常、优雅停机 |
| 异常会丢失 | 线程里的未捕获异常只打到 stderr，主线程感知不到 |

✅ **正确做法**：把任务提交给**线程池（ThreadPoolExecutor）**统一调度。它提供线程复用、队列缓冲、拒绝策略、优雅停机。

> 线程池的七个参数、任务提交流程、队列怎么选、拒绝策略怎么用，见 [[java/02-中段阶段-专题精讲/并发编程/04-线程池与任务调度]]；并发容器与虚拟线程见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]]。

## 三、线程的 6 种状态

`Thread.getState()` 返回 `Thread.State` 枚举，一共 6 个值。

```
   ┌────────┐
   │  NEW   │  线程对象已 new 出来，但还没调用 start()
   └────┬───┘
        │ start()
        ▼
   ┌──────────┐ ◄───────────────────────────────┐
   │ RUNNABLE │  正在执行代码，或就绪等着被调度        │
   └────┬─────┘                                 │
        │                                       │ 拿到锁 / 条件满足
        │ 抢 synchronized 锁失败                   │
        ▼                                       │
   ┌──────────┐                                 │
   │ BLOCKED  │  阻塞在 synchronized 入口          │
   └────┬─────┘                                 │
        └───────────────────────────────────────┘

        │ wait() / join() / park()
        ▼
   ┌──────────┐
   │  WAITING │  无期限等待某个条件（没有超时）
   └────┬─────┘
        │ notify() / join 的目标线程结束 / unpark()
        ▼
   ┌──────────┐
   │ RUNNABLE │
   └──────────┘

   ┌────────────────┐
   │ TIMED_WAITING  │  带超时的等待：sleep(n)/wait(n)/join(n)/await(n)
   └───────┬────────┘
           │ 超时到期或条件满足
           ▼
       RUNNABLE

   ┌────────────┐
   │ TERMINATED │  run() 执行完毕（正常结束或抛异常结束）
   └────────────┘  —— 不可复活，不能再 start()
```

### 状态速查表

| 状态 | 含义 | 怎么进入 | 怎么离开 |
|------|------|---------|---------|
| **NEW** | 已创建未启动 | `new Thread(...)` | 调用 `start()` |
| **RUNNABLE** | 运行中 **or** 就绪等 CPU | `start()`、等待结束、抢到锁 | 让出 CPU / 进入等待 |
| **BLOCKED** | 等 `synchronized` 锁 | 竞争锁失败 | 拿到锁 |
| **WAITING** | 无限期等条件 | `wait()`、`join()`、`park()` | `notify()`、目标线程结束、`unpark()` |
| **TIMED_WAITING** | 限时等条件 | `sleep(n)`、`wait(n)`、`join(n)`、`await(n)` | 超时或条件满足 |
| **TERMINATED** | 已结束 | `run()` 返回或抛异常 | 无（不可复活） |

⚠️ **两个高频误解**：

1. **`RUNNABLE` 不等于「正在占用 CPU」。** 它还包含「就绪但没被调度」的状态。在 `jstack` 里，等待网络 IO 的线程也显示 `RUNNABLE`（详见 [[java/02-中段阶段-专题精讲/JVM/排查工具与故障案例]]）。
2. **一个线程同一时刻只有一种状态。** `RUNNABLE` 和 `BLOCKED` 不会同时出现。

### ⭐ `BLOCKED` 与 `WAITING` 的区别

这是面试必问，也是最容易搞混的一对。

| | **BLOCKED** | **WAITING** |
|---|---|---|
| 在等什么 | ⭐ **等锁**（`synchronized` 监视器锁） | ⭐ **等条件**（某个协作信号 / 某个线程结束） |
| 典型 API | 竞争 `synchronized` 失败 | `Object.wait()`、`Thread.join()`、`LockSupport.park()` |
| 持锁吗 | ⚠️ **没拿到锁，自然没持锁** | ⭐ **可能正持有锁**——`wait()` 会**释放**锁 |
| 别人怎么唤醒它 | 持锁者 `synchronized` 块退出 | `notify()` / `notifyAll()` / 目标线程结束 / `unpark()` |
| 典型用途 | 线程安全代码的互斥保护 | 生产者-消费者、任务编排、线程池空闲等待 |

一句话记忆：

> **`BLOCKED` = 我在门口等钥匙；`WAITING` = 我在房间里等通知（还把钥匙交出去了）。**

⚠️ **进阶细节**：`BLOCKED` 是 `synchronized` **专有**的状态。用 `ReentrantLock` 时，等待锁的线程在 `jstack` 里显示为 **`WAITING`**（因为 `Lock` 内部用 `LockSupport.park()`），**不是** `BLOCKED`。所以「`jstack` 里全是 WAITING」往往意味着**锁竞争**，而不是「线程都没事干」。

## 四、`Thread` 的关键方法

### 4.1 `start()` vs `run()` ⭐

```java
public class StartVsRun {
    public static void main(String[] args) {
        Thread t = new Thread(() ->
                System.out.println("线程名：" + Thread.currentThread().getName()));

        t.run();        // ⚠️ 普通方法调用！只是当前线程（main）同步执行了一遍
        System.out.println("main 线程继续往下走");
        t.start();     // ✅ 申请创建新线程，由新线程去执行 run()
    }
}
```

输出：

```text
线程名：main        ← 这是 main 线程执行的
main 线程继续往下走
线程名：Thread-0    ← 这是新线程执行的
```

⚠️ **直接调 `run()` 不会创建新线程**。`run()` 就是一个普通方法，`t.run()` 等价于「在当前线程里同步调用这个方法」。必须调 `start()`。

⚠️ **`start()` 只能调一次**，第二次会抛 `IllegalThreadStateException`（线程状态机不允许 `TERMINATED → RUNNABLE`）。

### 4.2 `sleep(long millis)` —— ⭐ 释放 CPU，⚠️ 不释放锁

`Thread.sleep()` 是**静态方法**，作用是让**调用它的当前线程**暂停指定毫秒数。

| | `sleep()` | `wait()` |
|---|---|---|
| 释放 CPU | ✅ | ✅ |
| 释放 `synchronized` 锁 | ❌ **不释放** | ✅ 释放 |
| 所属 | `Thread`（静态） | `Object`（必须在持有锁时调用） |
| 等待对象 | 时间 | 别的线程的 `notify()` |
| 超时能力 | 必须有 | `wait()` 无限等 / `wait(ms)` 限时 |

⚠️ **经典陷阱**：在 `synchronized` 块里 `sleep` 会**继续占着锁**，其他线程全卡在 `BLOCKED`。

### 4.3 `join()` —— 等目标线程结束

`t.join()` 表示「当前线程等 `t` 结束再继续」。

```java
public class JoinDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            System.out.println("子线程干完了");
        });

        t.start();
        t.join();          // main 在这里等 t 结束（期间 main 状态是 WAITING）
        System.out.println("main 继续执行");
    }
}
```

⚠️ `join()` 必须**先 `start()` 再 `join()`**，否则目标线程根本没跑，`join()` 立刻返回。
⚠️ `join()` 没有超时参数时会**无限等待**——如果目标线程卡死，调用方也一起卡死。生产代码用 `join(timeout)`。

### 4.4 `yield()` —— 让出 CPU，⚠️ 不保证切换

`yield()` 是**静态方法**，提示调度器「我暂时不想跑了，可以换别的线程」。**只是提示**：

- 调度器**可以无视它**，当前线程可能立刻又被选中；
- 调用后线程状态**仍然是 `RUNNABLE`**（不是 `BLOCKED`）；
- 它**不会释放锁**。

⭐ 实际上，**绝大多数情况下不需要 `yield()`**——抢占式调度器本来就会在时间片用完或遇到阻塞点时切换线程。乱用 `yield()` 只会让代码更难推理。

### 4.5 `interrupt()` —— 中断协作机制

Java 的中断是**协作式（cooperative）**的：不能强行杀掉线程，而是**设置一个中断标记**，由被中断的线程自己决定怎么处理。

```java
public class InterruptDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                Thread.sleep(10_000);          // sleep 期间被 interrupt → 抛异常
            } catch (InterruptedException e) {
                System.out.println("收到中断，收拾东西退出");
                Thread.currentThread().interrupt();  // ⭐ 恢复中断标记，让上层也能看到
            }
        }, "worker");
        worker.start();

        Thread.sleep(200);
        worker.interrupt();                  // 设置中断标记
        worker.join();                       // 等它收完尾
        System.out.println("worker 是否还活着：" + worker.isAlive());
    }
}
```

规则一览：

| 情况 | `interrupt()` 的效果 |
|------|---------------------|
| 目标线程在 `sleep` / `wait` / `join` / `park` 中 | ⭐ 抛 `InterruptedException`，**并清除中断标记** |
| 目标线程在 `BLOCKED`（抢锁） | ⚠️ **不抛异常**，只是把中断标记记下来，等它抢到锁后下一次 sleep/wait 才抛 |
| 目标线程在跑纯计算 | ⚠️ **什么也不会发生**，必须自己 `isInterrupted()` 检查 |

两个查询方法：

| 方法 | 作用 | 是否清除标记 |
|------|------|------------|
| `Thread.interrupted()` | 查询**当前线程**是否被中断 | ✅ 清除 |
| `Thread.currentThread().isInterrupted()` | 查询当前线程是否被中断 | ❌ 不清除 |

⚠️ **`InterruptedException` 之后中断标记被清掉了**。如果异常被吞掉，上层就再也感知不到「有人让我停下来」。所以标准写法是 `catch` 之后**重新设置中断标记**（如上例），把信号继续往上层传。

### 4.6 六个方法速查

| 方法 | 静态/实例 | 释放 CPU | 释放锁 | 一句话 |
|------|----------|---------|--------|--------|
| `start()` | 实例 | — | — | 真正创建线程 |
| `run()` | 实例 | — | — | ⚠️ 普通方法，直接调不起线程 |
| `sleep(ms)` | 静态 | ✅ | ❌ | 当前线程睡一会儿 |
| `join()` | 实例 | ✅ | ❌ | 等目标线程结束 |
| `yield()` | 静态 | ✅（不保证） | ❌ | 提示调度器换人 |
| `interrupt()` | 实例 | — | — | 设置中断标记 / 唤醒等待者 |

## 五、守护线程（Daemon Thread）

**守护线程**是「为其他线程服务的线程」。规则很简单：

> **JVM 在只剩守护线程时直接退出**，不管守护线程干完没干完。

```java
public class DaemonDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread daemon = new Thread(() -> {
            try {
                Thread.sleep(5_000);
                System.out.println("守护线程干完了");   // ⚠️ 大概率打印不出来
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "守护线程");
        daemon.setDaemon(true);      // ⭐ 必须在 start() 之前设置
        daemon.start();

        Thread.sleep(1000);
        System.out.println("main 结束，JVM 即将退出（守护线程被直接干掉）");
    }
}
```

典型用途：GC 辅助线程、日志异步刷盘线程、Redis 的哨兵线程。

⚠️ **两个真实的坑**：

1. **清理工作可能来不及**。守护线程里的「写文件 / flush / 关连接」在 JVM 退出时会被**硬生生掐断**，数据可能丢。⚠️ **关键清理工作应该放在非守护线程里做**，或者用 JVM 关闭钩子（`Runtime.getRuntime().addShutdownHook(...)`）；
2. **`setDaemon()` 必须在 `start()` 之前调用**，否则抛 `IllegalThreadStateException`。

## 六、`ThreadLocal`：线程本地变量

### 6.1 它解决什么问题

**`ThreadLocal`**（线程本地变量）提供的变量，**每个线程读到的都是自己那份**，线程之间互不干扰。

```java
public class ThreadLocalDemo {
    // ⭐ 每个线程一份独立的副本
    private static final ThreadLocal<String> USER_NAME = new ThreadLocal<>();

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            USER_NAME.set("线程一的用户");
            sleep(200);
            System.out.println("t1 读到：" + USER_NAME.get());
        }, "t1");
        t1.start();

        Thread t2 = new Thread(() -> {
            USER_NAME.set("线程二的用户");
            System.out.println("t2 读到：" + USER_NAME.get());
        }, "t2");
        t2.start();

        t1.join();
        t2.join();
        System.out.println("main 读到：" + USER_NAME.get());   // null：main 线程从没 set 过
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

典型用途：**线程不安全对象的「每线程一份」包装**——数据库连接、SimpleDateFormat、Spring 的 `RequestContextHolder`、MDC 日志上下文。

### 6.2 底层结构：`ThreadLocalMap`

关键点：**`ThreadLocal` 自己不存值**，值存在**每个线程自己的 `ThreadLocalMap` 里**。

```
Thread（线程对象）
  └─ threadLocals : ThreadLocalMap      ← 强引用，线程活着就一直活着
       └─ Entry[] （数组，每个元素是一条记录）
            ├─ key   : WeakReference<ThreadLocal>   ← ⚠️ 弱引用，指向 ThreadLocal
            └─ value : 强引用 → 业务对象（Connection / SimpleDateFormat / ...）
```

`ThreadLocalMap` 内部用**哈希槽位**存放 entry，key 用 `ThreadLocal` 自己的 `hashCode` 定位（所以 `ThreadLocal` 实例最好**声明为 `static final`**，避免重复创建导致 hash 分布不均）。

### 6.3 ⭐ 内存泄漏风险（必须理解）

**泄漏链条**：

```
Thread（强引用 ThreadLocalMap）
   └─► ThreadLocalMap（强引用 Entry）
          └─► Entry.key  = WeakReference<ThreadLocal>   ← 弱引用，ThreadLocal 可被 GC
               Entry.value = 强引用 → 业务对象
```

- 当 `ThreadLocal` 实例本身不再被外部引用时，它的 key **会被 GC 回收**（弱引用的作用）；
- **但 entry 里的 value 是强引用**，而 `ThreadLocalMap` 被线程强引用着；
- ⭐ 所以只要**线程还活着**，这个 value 就**永远不会被回收** → **内存泄漏**。

⚠️ **线程池让这个问题从「偶尔」变成「必然」**：线程池里的工作线程**几乎永不死亡**，一旦某个任务用完 `ThreadLocal` 不清理，泄漏就永久存在。跑几天后表现为 `OutOfMemoryError` 或 GC 频繁。

⭐ **正确写法：永远 `remove()`**

```java
public class ThreadLocalCorrectUsage {
    private static final ThreadLocal<StringBuilder> BUFFER = ThreadLocal.withInitial(StringBuilder::new);

    public static void main(String[] args) {
        try {
            BUFFER.get().append("本次请求的数据");
            System.out.println(BUFFER.get());
        } finally {
            BUFFER.remove();     // ⭐ 必须放在 finally 里，异常路径也要清
        }
    }
}
```

| 写法 | 是否安全 |
|------|---------|
| `set()` 之后**从不** `remove()` | ❌ 线程池场景必然泄漏 |
| `try { set/使用 } finally { remove(); }` | ✅ 标准答案 |
| 用 `static final` 声明 `ThreadLocal` | ✅ 避免 key 被反复创建/哈希分散 |

### 6.4 `InheritableThreadLocal` 与线程池污染

**`InheritableThreadLocal`** 是 `ThreadLocal` 的子类：子线程创建时，会**自动拷贝**父线程的值。

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class InheritableLocalDemo {
    private static final InheritableThreadLocal<String> CTX = new InheritableThreadLocal<>();
    private static final ExecutorService pool = Executors.newFixedThreadPool(1);

    public static void main(String[] args) throws Exception {
        CTX.set("请求A 的上下文");

        // ⭐ 第一个提交的任务触发了工作线程的创建，它继承了此刻的值
        pool.submit(() -> System.out.println("任务1 看到：" + CTX.get())).get();

        CTX.set("请求B 的上下文");

        // ⚠️ 任务2 复用同一个工作线程，拿到的是「创建时继承的」旧值！
        pool.submit(() -> System.out.println("任务2 看到：" + CTX.get())).get();

        pool.shutdown();     // ⭐ 关闭线程池，否则 JVM 不会退出
    }
}
```

输出：

```text
任务1 看到：请求A 的上下文
任务2 看到：请求A 的上下文     ← ⚠️ 污染！应该是「请求B 的上下文」
```

原因：**线程池的工作线程是懒创建的**，第一次创建时把提交者线程的值继承了下来，之后**一直复用**这个线程，于是所有后续任务都看到那份「陈年旧值」。

**解法**：

| 方案 | 说明 |
|------|------|
| 手动在任务开始/结束时 `set` / `remove` | 最朴素，靠自觉，容易漏 |
| **`TransmittableThreadLocal`（TTL）** | 阿里开源的第三方库，在任务提交时把上下文**快照**给工作线程，结束时还原。⚠️ 需要额外依赖 |
| **`Scoped Values`** | ⭐ **Java 21 引入预览（JEP 446），Java 25 正式（JEP 506）**。JDK 自带的「不可继承、显式绑定」的上下文机制，是官方推荐答案（见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]]） |

⚠️ **还有一个更隐蔽的坑**：`InheritableThreadLocal` 拷贝的是**引用**，不是深拷贝。被继承的值如果是个可变对象，子线程改它，父线程也会看到。

## 七、线程上下文类加载器（点到为止）

**线程上下文类加载器**（TCCL, Thread Context Class Loader）就是 `Thread.currentThread().getContextClassLoader()` 返回的那个 `ClassLoader`。

**为什么需要它**：在 Tomcat、Spring Boot 这类**应用服务器**里，容器的类（如 `tomcat-catalina.jar`）由**容器类加载器**加载，而你的业务类由**应用类加载器**加载。当框架代码（也在容器 jar 里）需要去加载你的资源（`application.properties`、XML 配置、JDBC 驱动）时，它手里的 `ClassLoader` 根本看不到应用类，于是就需要通过 TCCL「借」一个应用类加载器来用。

**需要记住的两条**：

1. TCCL 默认**继承创建线程**的 TCCL——所以在主线程创建的线程池里，任务的 TCCL 是对的；但**线程池由框架容器创建**时，TCCL 可能指向容器而非你的应用；
2. 在**定时任务 / 线程池任务**里，如果遇到 `ClassNotFoundException` 但类明明在 classpath 上，**第一反应就该查 TCCL**，必要时在任务里重设：`Thread.currentThread().setContextClassLoader(MyClass.class.getClassLoader());`

类加载机制本身见 [[java/02-中段阶段-专题精讲/JVM/类加载机制]]。

## 八、可运行示例：亲眼观察线程状态

下面两个程序会依次把线程推到 6 种状态里，再逐个打印 `getState()`。⭐ **全部线程都设成守护线程**——这样 `main` 结束后 JVM 直接退出，不用写收尾代码。

### 示例一：NEW / RUNNABLE / TIMED_WAITING / WAITING / TERMINATED

```java
public class ThreadStateDemo {
    public static void main(String[] args) throws Exception {
        Thread tNew = new Thread(() -> { }, "A-NEW");              // ① NEW

        Thread tRunning = new Thread(() -> {
            while (true) { Math.sqrt(System.nanoTime()); }        // ② RUNNABLE：忙等占 CPU
        }, "B-RUNNABLE");

        Thread tSleep = new Thread(() -> sleepQuietly(60_000), "C-TIMED_WAITING");

        Thread tTarget = new Thread(() -> sleepQuietly(60_000), "D-被join方");
        Thread tWaiting = new Thread(() -> {
            try { tTarget.join(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "E-WAITING");                                           // ④ WAITING（join 无超时）

        for (Thread t : new Thread[]{ tRunning, tSleep, tTarget, tWaiting }) {
            t.setDaemon(true);                                    // ⭐ 守护线程：不用手动收尾
        }
        tRunning.start(); tSleep.start(); tTarget.start(); tWaiting.start();

        Thread tDone = new Thread(() -> { }, "F-TERMINATED");     // ⑥ TERMINATED
        tDone.start();
        tDone.join();                                             // 等它跑完

        Thread.sleep(200);                                        // 让各线程就位
        for (Thread t : new Thread[]{ tNew, tRunning, tSleep, tWaiting, tDone }) {
            System.out.printf("%-18s -> %s%n", t.getName(), t.getState());
        }
    }

    static void sleepQuietly(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

预期输出：

```text
A-NEW             -> NEW
B-RUNNABLE        -> RUNNABLE
C-TIMED_WAITING   -> TIMED_WAITING
E-WAITING         -> WAITING
F-TERMINATED      -> TERMINATED
```

### 示例二：制造 `BLOCKED`

```java
public class BlockedDemo {
    private static final Object LOCK = new Object();

    public static void main(String[] args) throws Exception {
        // 线程 1：拿到锁后睡 60 秒，全程持有 LOCK
        Thread holder = new Thread(() -> {
            synchronized (LOCK) { sleepQuietly(60_000); }
        }, "A-持锁者");
        holder.setDaemon(true);
        holder.start();
        Thread.sleep(100);                        // ⭐ 等持锁者先拿到锁

        // 线程 2：抢不到锁 → BLOCKED
        Thread blocked = new Thread(() -> {
            synchronized (LOCK) { sleepQuietly(60_000); }
        }, "B-BLOCKED");
        blocked.setDaemon(true);
        blocked.start();

        Thread.sleep(200);
        System.out.printf("%-12s -> %s%n", holder.getName(), holder.getState());
        System.out.printf("%-12s -> %s%n", blocked.getName(), blocked.getState());
    }

    static void sleepQuietly(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

预期输出：

```text
A-持锁者        -> TIMED_WAITING
B-BLOCKED       -> BLOCKED
```

⭐ **注意 `A-持锁者` 本身是 `TIMED_WAITING`**——它虽然**持有锁**，但因为在 `sleep` 里而不占 CPU。**「持有锁」和「处于什么状态」是两件事**。

## 九、陷阱

1. **⚠️ 直接调用 `run()` 以为起了线程**——`run()` 是普通方法，必须 `start()`；
2. **⚠️ 以为 `BLOCKED` 就是「线程在干活」**——`BLOCKED` 是**没拿到锁干不了活**；`jstack` 里大量 `BLOCKED` 说明锁竞争激烈（见 [[java/02-中段阶段-专题精讲/JVM/排查工具与故障案例]]）；
3. **⚠️ 在 `synchronized` 里 `sleep`**——不释放锁，把并发全卡死；想释放锁要用 `wait()`（用错 `wait`/`notify` 还会引发**死锁**，即两个线程互相等待、永久卡住，详见 [[java/02-中段阶段-专题精讲/并发编程/03-锁机制与原子操作]]）；
4. **⚠️ 以为 `yield()` 能让出 CPU**——它只是提示，调度器可以无视；而且不释放锁；
5. **⚠️ 以为 `interrupt()` 能强杀线程**——它只是设标记；纯计算中的线程必须自己检查 `isInterrupted()`；
6. **⚠️ 吞掉 `InterruptedException` 不恢复中断标记**——中断信号丢失，上层以为线程还在正常工作；标准写法是 `catch` 后 `Thread.currentThread().interrupt()`；
7. **⚠️ 生产代码 `new Thread().start()`**——线程数不可控、无法复用、异常丢失；要用线程池（见 [[java/02-中段阶段-专题精讲/并发编程/04-线程池与任务调度]]）；
8. **⚠️ 用守护线程做关键清理**——JVM 退出时会被硬生生掐断，数据可能丢；
9. **⚠️ `ThreadLocal` 用完不 `remove()`**——线程池场景必然内存泄漏；`InheritableThreadLocal` 还会造成跨任务**上下文污染**；
10. **⚠️ 以为 `Thread` 可以重复 `start()`**——第二次抛 `IllegalThreadStateException`，线程也不能复活。

## 小结

- **共享什么、私有什么**：堆和元空间共享（⭐ 竞态重灾区），虚拟机栈和程序计数器私有（局部变量天然安全）
- **三种创建方式**：`Thread` 子类（占继承名额）、⭐ `Runnable`（首选）、`Callable` + `FutureTask`（能返回值、能抛受检异常）
- **6 种状态**：`NEW` / `RUNNABLE` / `BLOCKED` / `WAITING` / `TIMED_WAITING` / `TERMINATED`
- ⭐ **`BLOCKED` = 等锁；`WAITING` = 等条件**（`ReentrantLock` 的等待线程在 `jstack` 里也是 `WAITING`）
- **方法语义**：`start` 起线程、`run` 是普通方法、`sleep` 不释放锁、`join` 等结束、`yield` 只是提示、`interrupt` 是协作式中断
- **守护线程**：JVM 只剩守护线程就退出，⚠️ 清理工作别放这儿
- **`ThreadLocal`**：值存在**线程自己的 `ThreadLocalMap`** 里；key 弱引用 + value 强引用 → ⚠️ 线程池里必然泄漏，**必须 `remove()`**
- **`InheritableThreadLocal`** 在线程池里会**污染**后续任务 → 用 TTL 或 `Scoped Values`（Java 21 预览 / Java 25 正式）
