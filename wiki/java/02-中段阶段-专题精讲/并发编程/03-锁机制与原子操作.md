## 一、`synchronized`：语法与语义

### 1.1 两种写法

**临界区（critical section）**：被锁保护起来的那段代码。**同一时刻只允许一个线程进入临界区**，这是所有锁机制存在的根本原因。

```java
public class SyncDemo {

    private final Object lock = new Object();     // ⭐ 私有 final 字段，专门当锁

    // 写法一：同步代码块 —— 锁的是 lock 这个对象
    public void methodA() {
        synchronized (lock) {
            // 临界区
        }
    }

    // 写法二：同步方法（实例方法）—— 锁的是 this
    public synchronized void methodB() {
        // 临界区
    }

    // 写法二变体：静态同步方法 —— 锁的是 XXX.class 这个 Class 对象
    public static synchronized void methodC() {
        // 临界区
    }
}
```

| 写法 | 锁的是谁 |
|------|---------|
| `synchronized (lockObj) { }` | `lockObj` 引用的那个**对象** |
| `public synchronized void m()` | **当前实例 `this`** |
| `public static synchronized void m()` | **该类对应的 `Class` 对象**（`SyncDemo.class`） |

### 1.2 ⭐ 锁的是「对象」，不是「代码」

这是 `synchronized` 最核心、也最容易被误解的一点。

> **`synchronized` 关键字的作用是：获取「某一个具体对象」的监视器锁（monitor）。**
> **代码本身没有锁。** 两个不同的 `synchronized` 代码块，只要锁的是**同一个对象**，就互斥。

```java
public class SameLock {
    private static final Object SHARED = new Object();

    public void methodA() {
        synchronized (SHARED) { doWork(); }    // 锁 SHARED
    }

    public void methodB() {
        synchronized (SHARED) { doWork(); }    // ⭐ 也是锁 SHARED → 与 methodA 互斥！
    }

    private static void doWork() {
        System.out.println("临界区里在干活");
    }
}
```

⚠️ 推论：**只要两个线程锁的是同一个对象，它们就是互斥的**——哪怕这两段代码在完全不同的类里、看起来毫不相干。

### 1.3 ⚠️ 锁对象该怎么选

| 选择 | 后果 |
|------|------|
| ⭐ **私有 `final` 字段**（`private final Object lock = new Object();`） | ✅ 正确：外部无法干扰，锁对象不会被替换 |
| **`this`** | ⚠️ 外部拿到实例引用就能 `synchronized(obj)` 干扰你；且 `this` 容易在构造期泄漏 |
| **`String` 字面量** | ⚠️⚠️ **大忌**：字符串在常量池里共享，两个应用用了同一个字符串字面量会**互相锁死** |
| **`Integer` / `Long` 缓存对象** | ⚠️ 大忌：`-128~127` 范围的包装类是共享缓存的 |
| **可变字段** | ⚠️ 字段被重新赋值后，锁对象就变了，锁失效 |

⭐ **标准写法**：

```java
public class OrderService {
    // ⭐ 私有、final、专门用来加锁，绝不暴露
    private final Object lock = new Object();

    private int stock = 10;

    public boolean reduceStock() {
        synchronized (lock) {
            if (stock <= 0) {
                return false;
            }
            stock--;
            return true;
        }
    }
}
```

⚠️ **`private final Object lock` 绝不能通过 getter 暴露出去**，否则外部代码能拿它去 `synchronized` 你，从而把你的锁变成一把「谁都能抢的大锁」。

### 1.4 ⚠️ 锁范围：保护什么，就锁什么

```java
// ❌ 锁范围过大：把不需要保护的慢操作也锁进去了
public synchronized void process(Order order) {
    validate(order);            // 慢
    saveToDb(order);            // 慢（网络 IO）
    sendEmail(order);           // 更慢（网络 IO）
}

// ✅ 锁范围合理：只保护真正共享可变状态的那几行
public void process(Order order) {
    validate(order);
    synchronized (lock) {
        counter++;
    }
    saveToDb(order);
    sendEmail(order);
}
```

⚠️ **在锁里做网络 IO 是线上卡顿的常见原因**：一个线程持锁等数据库，其他线程全卡在 `BLOCKED`。排查手法见 [[java/02-中段阶段-专题精讲/JVM/排查工具与故障案例]]。

## 二、字节码层：`monitorenter` / `monitorexit`

`synchronized` 在字节码层面有两种实现。

```java
public class BytecodeView {
    public void block() {
        synchronized (this) {      // ⭐ 编译成 monitorenter / monitorexit
            doWork();
        }
    }

    public synchronized void method() {   // ⭐ 编译成 ACC_SYNCHRONIZED 标志
        doWork();
    }

    private static void doWork() {
        System.out.println("干活");
    }
}
```

用 `javap -c`（反编译查看字节码）能看到：

```text
  public void block();
    Code:
       0: aload_0
       1: monitorenter      // ⭐ 获取锁
       ...
      10: monitorexit       // ⭐ 释放锁
      ...
      // 方法异常退出时，编译器会生成多个 monitorexit，保证异常路径也释放锁

  public synchronized void method();
    Code:
       0: aload_0
       1: invokevirtual doWork
       4: return
    // ⭐ 方法上没有 monitorenter！取而代之的是方法访问标志 ACC_SYNCHRONIZED
    //    JVM 执行时看到这个标志，自动在方法前后加锁/解锁
```

| 实现方式 | 字节码表现 | 特点 |
|---------|-----------|------|
| 同步代码块 | `monitorenter` / `monitorexit` 指令 | 锁范围可精确控制 |
| 同步方法 | 方法访问标志 `ACC_SYNCHRONIZED` | 整个方法都是临界区 |

⭐ **对面试和排查的意义**：
- 看到 `monitorenter` 就知道有锁竞争；
- `javap -c` 看到 `ACC_SYNCHRONIZED` 就知道整个方法被锁住，**如果方法里有慢 IO，就是一个潜在的卡顿点**。

## 三、锁升级：无锁 → 偏向锁 → 轻量级锁 → 重量级锁

### 3.1 为什么要「升级」

理想情况下，一把锁只有**一个线程**在争用。这时根本不需要操作系统介入——直接在用户态用一条 CPU 原子指令（CAS）就能搞定，何必惊动内核、挂起线程、切换上下文？

所以 JVM 的策略是：**从最轻的方案开始，冲突加剧时再往重的方案升**。这个过程叫**锁升级（lock coarsening / lock escalation）**。

### 3.2 四个阶段

```
   ┌─────────┐
   │  无锁    │  对象刚 new 出来，Mark Word 记 hashCode
   └────┬────┘
        │ 第一个线程进入 synchronized
        ▼
   ┌─────────┐
   │ 偏向锁   │  锁「偏向」某个线程：该线程再进来不用做任何事（历史方案）
   └────┬────┘
        │ 别的线程也要进来 → 偏向失效
        ▼
   ┌───────────────┐
   │  轻量级锁     │  CAS + 自旋：不挂起线程，失败就自旋重试
   └────┬──────────┘
        │ 自旋多次仍失败 / 竞争加剧（超出撤销阈值）
        ▼
   ┌───────────────┐
   │  重量级锁     │  Monitor（依赖操作系统互斥量），线程挂起、上下文切换
   └───────────────┘
```

| 阶段 | 实现原理 | 代价 |
|------|---------|------|
| **无锁** | 无 | 无竞争，但无法保护 |
| **偏向锁** | 把「锁的拥有者线程 ID」写进对象头的 Mark Word | 同线程进出零成本（**已废弃**） |
| **轻量级锁** | **CAS + 自旋**，用栈上的锁记录（Lock Record）占位 | 竞争时不挂起线程，**但会烧 CPU** |
| **重量级锁** | **Monitor** 对象，内部用操作系统的互斥量（mutex） | 线程被挂起、切换，**正确但慢** |

### 3.3 ⭐ 偏向锁的现状（版本敏感）

⚠️ **偏向锁（JEP 374）已在 JDK 15 起被默认禁用并标记为废弃，在后续 JDK 版本中实现被彻底移除。**

- **历史价值**：偏向锁解决的是「**几乎总是单线程访问**」的场景。早期大量代码是无竞争的，加偏向锁后，同一线程进出 `synchronized` 几乎零开销；
- **为什么被废弃**：
  1. 现代应用普遍是多线程的，偏向锁命中率低，**维护成本却很高**（撤销偏向要触发 safepoint，暂停所有线程）；
  2. JDK 15 之后，**卸载偏向锁路径**、偏向锁相关的 safepoint 都可以被移除，JVM 变得更简单；
  3. JDK 18 起，HotSpot 里**偏向锁的实现已被删除**；
- ⭐ **现状**：现在（Java 21 / 25 这类现代 LTS）**不要再按「无锁 → 偏向 → 轻量 → 重量」四步来讲**，正确的说法是「**无锁 → 轻量级锁 → 重量级锁**」，偏向锁只作为历史背景了解。

⭐ **面试怎么答**：可以说「历史上是四阶段，但**偏向锁从 JDK 15 起默认废弃（JEP 374）、后续版本移除**，所以现在实际只有三阶段」——这既懂历史，又知道现状。

### 3.4 轻量级锁：CAS + 自旋

**CAS**（Compare-And-Swap，比较并交换）是一种**原子指令**：比较内存中的值是否等于预期值，相等则改成新值并返回成功。

**自旋（spin）**：拿不到锁时，不把自己挂起，而是**原地循环反复尝试**（`while (!tryLock()) {}`）。

轻量级锁的流程简化版：

```
线程要加锁：
  ① 在当前线程的栈上分配一个「锁记录」（Lock Record）
  ② 用 CAS 把对象头里的指针从「无锁」改成「指向我的锁记录」
     ├─ CAS 成功 → 我拿到锁，轻量级锁完成
     └─ CAS 失败 → 说明别人抢先了
            ├─ 若失败原因是「重入」（同一线程重复加锁）→ 记录重入次数，OK
            └─ 否则 → 自旋重试 CAS；自旋超过阈值仍失败 → 膨胀为重量级锁
```

⭐ **轻量级锁的适用前提**：**锁竞争不激烈、临界区执行时间很短**。因为自旋是在**烧 CPU**——如果临界区要执行 100ms，别的线程自旋 100ms 纯浪费。

⚠️ **所以「临界区要短」是并发编程的第一准则**：临界区越长，自旋的线程浪费越多，越容易膨胀成重量级锁。

## 四、`Monitor`：重量级锁的本体

**Monitor（监视器）** 是 JVM 层面的对象，对应 `java.lang.Object` 的 `monitorenter`/`monitorexit` 所操作的锁结构。

它有三个核心部分：

```
┌─────────────────── Monitor（ObjectMonitor）───────────────────┐
│                                                                  │
│  ┌───────────────┐                                              │
│  │   EntryList   │  ← 正在竞争锁的线程队列（BLOCKED 的线程在这排队）│
│  │   入口队列      │                                              │
│  └───────────────┘                                              │
│                                                                  │
│  ┌───────────────┐    ┌──────────────┐                          │
│  │    Owner      │───►│  持有锁的线程  │  ← 当前持锁者，null = 空闲 │
│  │   锁的拥有者    │    └──────────────┘                          │
│  └───────────────┘                                              │
│                                                                  │
│  ┌───────────────┐                                              │
│  │   WaitSet     │  ← 调用了 wait() 后等待被唤醒的线程集合（WAITING）│
│  │   等待队列      │                                              │
│  └───────────────┘                                              │
│                                                                  │
│  reentrancy count  ← 重入计数：同一线程重复加锁会 +1             │
└──────────────────────────────────────────────────────────────────┘
```

### 4.1 三种线程与 Monitor 的关系

| 线程状态 | 在 Monitor 里的位置 |
|---------|------------------|
| `RUNNABLE`（正要加锁） | 在 **EntryList** 排队 |
| `BLOCKED` | 在 **EntryList** 排队（抢锁失败） |
| `WAITING`（调了 `wait()`） | 在 **WaitSet** |
| 持锁者 | 是 **Owner** |

⭐ **两个队列的切换逻辑**：

- 线程抢锁失败 → 进 **EntryList**（状态 `BLOCKED`）；
- 持锁者调 `wait()` → **释放锁**，线程从 Owner 挪到 **WaitSet**（状态 `WAITING`）；
- 别人调 `notify()` → WaitSet 里的线程被唤醒，回到 **EntryList** 重新抢锁；
- 持锁者释放锁 → EntryList 里的线程抢到 → 成为新的 Owner。

### 4.2 ⚠️ `wait()` / `notify()` 必须在持有锁时调用

```java
synchronized (lock) {
    lock.wait();      // ⭐ 必须持有 lock 的监视器
}
```

⚠️ 如果没持有锁就调 `wait()` 或 `notify()`，会抛 **`IllegalMonitorStateException`（非法监视器状态异常）**。

原因：`wait()` 的语义是「**释放锁 + 等待**」，没锁可释放，这个操作在逻辑上就不成立。

⭐ **标准写法**：

```java
public class BoundedBuffer {
    private final Object lock = new Object();
    private final int[] data = new int[10];
    private int count = 0;

    public void put(int v) throws InterruptedException {
        synchronized (lock) {
            while (count == data.length) {   // ⭐ 用 while 不用 if
                lock.wait();
            }
            data[count++] = v;
            lock.notifyAll();                // ⭐ 唤醒所有等待者
        }
    }

    public int take() throws InterruptedException {
        synchronized (lock) {
            while (count == 0) {
                lock.wait();
            }
            int v = data[--count];
            lock.notifyAll();
            return v;
        }
    }
}
```

⚠️ **两个经典细节**：

1. ⭐ **用 `while` 而不是 `if` 检查条件**——被唤醒后可能条件又变了（比如别人抢先消费了），`if` 会直接往下走导致越界；`while` 会重新检查；
2. ⭐ **用 `notifyAll()` 而不是 `notify()`**——`notify()` 只唤醒一个线程，如果唤醒的那个线程条件不满足（比如它要消费但队列已经被别人填满），它又 `wait()` 了，而其他等待者还在睡 → **信号丢失，程序卡死**。除非你非常确定只有一个等待者且条件对称，否则一律用 `notifyAll()`。

## 五、`ReentrantLock`：更灵活的锁

**`ReentrantLock`** 是 `java.util.concurrent.locks` 包里的**可重入锁**，行为上和 `synchronized` 一样（同一线程可重复加锁、退出时按重入次数逐层释放），但功能更多。

```java
import java.util.concurrent.locks.ReentrantLock;

public class ReentrantLockDemo {
    private final ReentrantLock lock = new ReentrantLock();
    private int count = 0;

    public void increment() {
        lock.lock();                       // ⭐ 获取锁
        try {
            count++;
        } finally {
            lock.unlock();                 // ⭐ 必须释放锁，放在 finally
        }
    }
}
```

⚠️ **`lock()` 和 `unlock()` 必须配对**，且**必须写在 `try-finally` 里**——否则中间抛异常，锁永远不释放，后面所有线程全部卡死。

（`synchronized` 由 JVM 保证异常时自动释放，这是它相对 `ReentrantLock` 唯一的便利优势。）

### 5.1 与 `synchronized` 对比表 ⭐

| 特性 | `synchronized` | `ReentrantLock` |
|------|---------------|-----------------|
| 获取锁 | `synchronized` 关键字 | `lock()` / `lockInterruptibly()` / `tryLock()` |
| 释放锁 | 编译器自动生成（异常也释放） | ⚠️ **必须手动 `unlock()`，写在 `finally`** |
| **可中断** | ❌ 等锁时无法响应中断 | ✅ `lockInterruptibly()`，拿不到锁就抛 `InterruptedException` |
| **可超时** | ❌ | ✅ `tryLock(timeout, unit)`，拿不到就返回 false |
| **公平锁** | ❌ 只有非公平（谁抢到谁拿） | ✅ `new ReentrantLock(true)` |
| **多个条件队列** | ❌ 只有一个 `wait` 队列 | ✅ 可创建多个 `Condition` |
| **锁状态可查询** | ❌ | ✅ `isLocked()` / `isHeldByCurrentThread()` / `getQueueLength()` |
| 只能作用于**代码块** | ❌ | ⚠️ **只能锁代码块**，不能修饰方法 |

⭐ **公平锁（fair lock）**：按「先来先服务」排队，谁等得久谁先拿。⚠️ **公平锁的吞吐量通常明显低于非公平锁**——非公平锁允许刚到的线程「插队」，减少了线程挂起/唤醒的开销。**除非有严格的 FIFO 要求（比如避免饥饿），否则用默认的非公平锁。**

⭐ **为什么 `ReentrantLock` 会出现**：`synchronized` 是语言关键字，JVM 必须支持，无法扩展；`ReentrantLock` 是普通类，可以在上面加功能。

## 六、`Condition`：多个条件队列

**`Condition`**（条件）是 `ReentrantLock` 配套的等待/通知机制，对应 `Object` 的 `wait()` / `notify()`。

| `Object` | `Condition` |
|----------|-------------|
| `wait()` | `await()` |
| `notify()` | `signal()` |
| `notifyAll()` | `signalAll()` |
| 一个 `wait` 队列 | ⭐ **可以创建多个队列** |

⭐ **多条件队列的价值**：生产者-消费者模型里，「队列满了要等消费者」和「队列空了要等生产者」是**两个不同的条件**，用一个 `wait` 队列 + `notifyAll` 会导致大量无效唤醒。用两个 `Condition` 就精准得多。

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class BlockingQueueDemo {
    private final ReentrantLock lock = new ReentrantLock();
    // ⭐ 两个独立的条件队列
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();
    private final int[] queue = new int[16];
    private int count = 0;

    public void put(int v) throws InterruptedException {
        lock.lock();
        try {
            while (count == queue.length) {
                notFull.await();          // ⭐ 队列满了，等「有空位」这个条件
            }
            queue[count++] = v;
            notEmpty.signal();            // ⭐ 只唤醒等待「非空」的线程
        } finally {
            lock.unlock();
        }
    }

    public int take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await();         // ⭐ 队列空了，等「有数据」这个条件
            }
            int v = queue[--count];
            notFull.signal();             // ⭐ 只唤醒等待「有空位」的线程
            return v;
        } finally {
            lock.unlock();
        }
    }
}
```

⚠️ **`await()` / `signal()` 必须在持有 `lock` 时调用**，否则抛 `IllegalMonitorStateException`——和 `wait()`/`notify()` 一模一样。

## 七、读写锁与 `StampedLock`

### 7.1 `ReadWriteLock`

**`ReadWriteLock`** 把「读」和「写」分成两种模式：

- **读锁（共享锁）**：多个线程可以**同时**持有；
- **写锁（排他锁）**：同一时刻只有一个线程能持有，且**与所有读锁互斥**。

典型场景：**读多写少的共享数据**（配置缓存、本地缓存、只读表）。

```java
import java.util.concurrent.locks.ReadWriteLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class Cache {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final java.util.Map<String, String> map = new java.util.HashMap<>();

    public String get(String key) {
        rw.readLock().lock();            // ⭐ 读锁
        try {
            return map.get(key);
        } finally {
            rw.readLock().unlock();
        }
    }

    public void put(String key, String value) {
        rw.writeLock().lock();           // ⭐ 写锁
        try {
            map.put(key, value);
        } finally {
            rw.writeLock().unlock();
        }
    }
}
```

⚠️ **锁升级（降级）是允许的**：`ReentrantReadWriteLock` 支持**持有读锁时获取写锁**（写锁会等读锁释放），但**不支持持有写锁时获取读锁**（会死锁）。

### 7.2 `StampedLock`（概览）

**`StampedLock`**（JDK 8+）是更激进的版本，除了读锁/写锁，还提供**乐观读（optimistic read）**。

```java
import java.util.concurrent.locks.StampedLock;

public class StampedCache {
    private final StampedLock sl = new StampedLock();
    private int value = 0;

    public int read() {
        long stamp = sl.tryOptimisticRead();     // ⭐ 拿到一个「版本戳」，不加任何锁
        int v = value;                            // 读数据
        if (!sl.validate(stamp)) {               // ⭐ 校验：期间有没有人写过？
            // 校验失败 → 有人写过了，重新走悲观读
            stamp = sl.readLock();
            try {
                v = value;
            } finally {
                sl.unlockRead(stamp);
            }
        }
        return v;
    }
}
```

⭐ **乐观读的思路**：先不上锁直接读，读完用「版本戳」验证一下「我读的期间有没有人修改过」。没修改过 → 读到的是一致的值，零锁开销；修改过 → 退化成普通读锁。

⚠️ **`StampedLock` 的代价**：**不可重入**，而且 `validate` 的逻辑要自己写对，写错了会读到不一致的数据。它属于「性能极致、正确性靠自己」的 API。

⚠️ **`StampedLock` 不支持 `Condition`**（`newCondition()` 会抛 `UnsupportedOperationException`）。

## 八、CAS 与 AQS

### 8.1 ⭐ CAS：Compare-And-Swap

**CAS** 是一条 CPU 级别的原子指令，语义是：

> **比较**内存位置 M 中的值与预期值 V；如果相等，就把 M 改成新值 A；如果不等，就什么都不做并返回失败。

关键点：**比较 + 交换是一个不可分割的整体**，不需要加锁。

```java
AtomicInteger atomic = new AtomicInteger(0);

// ⭐ 经典的 CAS 循环
boolean updated = atomic.compareAndSet(0, 1);   // 如果当前是 0，就改成 1
System.out.println(updated);   // true
System.out.println(atomic.get());   // 1

// ⭐ 原子自增：内部就是 CAS 循环
atomic.incrementAndGet();   // 读 → CAS 改 → 失败就重试
```

### 8.2 CAS 的自旋：ABA 问题

CAS 的典型用法是**自旋重试**：

```java
// ⭐ 标准 CAS 循环（AtomicInteger 内部就是这个结构）
int expected = 0;
do {
    expected = atomic.get();
    // 循环体里做点计算
} while (!atomic.compareAndSet(expected, expected + 1));
```

⚠️ **ABA 问题**：CAS 只比较**值**，不比较「这个值是不是同一个值」。假设变量先从 0 变成 1，又从 1 变回 0——CAS 看到的还是 0，认为「没人动过」，于是修改成功。但实际上中间已经发生过一次变化，基于「值没变」的假设（比如用它做版本号、做无锁栈的指针）就错了。

**解法**：给 CAS 加一个**版本号**，值和版本一起比较。

```java
AtomicStampedReference<String> ref =
        new AtomicStampedReference<>("A", 0);   // 值 + 版本戳
ref.compareAndSet("A", "B", 0, 1);            // 期望值 "A"，期望版本 0
```

⚠️ 实际业务里 **ABA 很少成为真正的 bug 源**，所以 `AtomicInteger` 系列都没做这个处理；只有**无锁数据结构**（如无锁栈）才需要 `AtomicStampedReference`。

### 8.3 ⭐ AQS：锁与同步器的实现基座

**AQS（AbstractQueuedSynchronizer，抽象队列同步器）** 是 `java.util.concurrent.locks` 包的**基础类**。JDK 里的很多东西都建立在它之上：

```
AQS（AbstractQueuedSynchronizer）
 ├── ReentrantLock（可重入锁）
 ├── ReentrantReadWriteLock（读写锁）
 ├── CountDownLatch（倒计时门闩）
 ├── Semaphore（信号量）
 └── 各种同步队列的阻塞插入

（并发容器的部分内部实现也基于 AQS，见第 05 篇）
```

⭐ **AQS 的三根支柱**：

| 支柱 | 说明 |
|------|------|
| **一个 `state`（状态量）** | `int` 字段，语义由子类自己定义：`ReentrantLock` 用它记**重入次数**（0 = 未加锁，>0 = 已加锁几次）；`CountDownLatch` 用它记**剩余计数**；`Semaphore` 用它记**剩余许可数** |
| **一个 CLH 变体的等待队列** | 一个**双向链表**（节点叫 `Node`），所有竞争失败的线程排成队列，先来先服务地唤醒 |
| **一组模板方法** | ⭐ `acquire` / `release` 是**模板方法**（final 的），子类只需实现 `tryAcquire` / `tryRelease` 这几个「尝试」方法 |

**AQS 的核心流程（以加锁为例）**：

```
线程调用 lock()
  └─► AQS.acquire()                      ← 模板方法，final，子类不能改
        ├─ tryAcquire()                  ← 子类实现：尝试改 state
        │    ├─ 成功 → 直接返回（无竞争，零开销）
        │    └─ 失败 ↓
        ├─ addWaiter() → 入队到等待队列尾部
        └─ acquireQueued() → 循环：
             ├─ 前驱是 head 且 tryAcquire() 成功 → 出队成为新 head
             └─ 否则 park() 挂起（等被唤醒）
```

⭐ **一句话理解 AQS**：

> **AQS = 一个状态量 + 一个等待队列 + 「模板方法 + 状态 + 队列」的组合。**
> 子类只负责定义「状态怎么变」（`tryAcquire`/`tryRelease`），**排队、阻塞、唤醒的复杂逻辑全部由 AQS 统一实现**。

⭐ **这也是面试最爱问的设计模式之一**：**模板方法模式（Template Method）** 的典型代表。

## 九、原子类

**原子类**是 `java.util.concurrent.atomic` 包里提供的一组线程安全计数器与引用容器，底层全部基于 **CAS**。

| 类 | 用途 | 关键方法 |
|---|------|---------|
| `AtomicInteger` | `int` 原子计数 | `incrementAndGet()`、`addAndGet(int)`、`compareAndSet(int,int)` |
| `AtomicLong` | `long` 原子计数 | 同上 |
| `AtomicBoolean` | `boolean` 原子值 | `compareAndSet(boolean,boolean)` |
| `AtomicReference<T>` | 对象**引用**的原子读写 | `get()` / `set()` / `compareAndSet()` |
| `AtomicIntegerArray` | 整型数组逐元素原子操作 | `getAndIncrement(int i)` |
| `LongAdder` | ⭐ 高并发累加（计数专用） | `increment()` / `sum()` |
| `DoubleAdder` | `LongAdder` 的浮点版 | `increment()` / `sum()` |

⚠️ **`AtomicReference` 只能保证「引用替换」是原子的**——它**不会**让被引用的对象内部状态变得线程安全。`AtomicReference<User> ref`，换引用是原子的，但 `ref.get().name = "x"` 依然不安全。

### 9.1 ⭐ `LongAdder` 为什么比 `AtomicInteger` 快

⭐ **这是高频面试题。**

**问题**：`AtomicInteger.incrementAndGet()` 在高并发下，所有线程都在**竞争同一个 `value` 字段的 CAS**。CAS 失败的线程要自旋重试，**重试次数随线程数增加而急剧上升**——这就是**CAS 竞争（contention）**。

**`LongAdder` 的解法**：**空间换时间，分段累加（striping）**。

```
AtomicInteger：
   [  0  ]  ← 所有线程都抢这一个格子（CAS 冲突严重）

LongAdder：
   [ 0 ][ 1 ][ 2 ][ 3 ] ... [N-1]   ← 分散到多个 Cell（分段）
     ↑    ↑    ↑
   线程A 线程B 线程C  各占一个格子，几乎不冲突
```

| 维度 | `AtomicInteger` | `LongAdder` |
|------|-----------------|-------------|
| 底层结构 | 单个 `value` 字段 + CAS | `Cell[]` 数组，每个 Cell 内部还是 CAS |
| 高并发表现 | CAS 冲突多，自旋重试 | ⭐ **冲突分散，吞吐量高得多** |
| **读取当前值** | ⭐ **直接读，精确** | ⚠️ `sum()` 是**把各 Cell 加起来**，**不保证瞬时一致**（求和期间可能有 Cell 在变） |
| 适用 | ⭐ **需要精确读**（比如发号器 `getAndIncrement`） | ⭐ **只管累加、偶尔读总量**（QPS 统计、监控计数） |

⚠️ **`LongAdder` 的代价：读出来的值不精确。** 需要「唯一递增 ID」这种场景必须用 `AtomicInteger`（靠 `getAndIncrement()` 拿到不重复的号）。

## 十、⭐ 死锁

### 10.1 什么是死锁

**死锁（deadlock）** 指两个或多个线程各自持有对方需要的资源，同时等待对方释放，导致**所有相关线程永久阻塞**。

### 10.2 产生的四个必要条件（缺一不可）

| # | 条件 | 含义 |
|---|------|------|
| 1 | **互斥** | 资源同一时刻只能被一个线程占用 |
| 2 | **持有并等待** | 线程持有资源 A 的同时，等待资源 B |
| 3 | **不可剥夺** | 资源只能由持有者主动释放，不能被强行抢走 |
| 4 | **循环等待** | 存在一个等待环：T1 等 T2 持有的，T2 等 T1 持有的 |

⭐ **破解思路**：破坏任意一个条件即可。最常用的是破坏**循环等待**（统一加锁顺序）。

### 10.3 经典例子

```java
public class DeadlockDemo {

    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        // 线程 1：先拿 A，再要 B
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(100);                       // ⭐ 放大时间窗口，让死锁稳定复现
                synchronized (LOCK_B) {
                    System.out.println("t1 拿到了两把锁");
                }
            }
        }, "t1");

        // 线程 2：先拿 B，再要 A  ← ⭐ 与 t1 的顺序相反
        Thread t2 = new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(100);
                synchronized (LOCK_A) {
                    System.out.println("t2 拿到了两把锁");
                }
            }
        }, "t2");

        t1.start();
        t2.start();
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

运行后程序**永远不结束**，两个线程的 `jstack` 都停在 `BLOCKED`。

### 10.4 如何避免死锁

| 手段 | 做法 | 说明 |
|------|------|------|
| ⭐ **固定加锁顺序** | 全局统一「先锁 A 再锁 B」 | ⭐ **最常用、最有效**。用 `hashCode` 或 `System.identityHashCode` 排序就是一个通用做法 |
| **`tryLock` 超时** | `if (!lock.tryLock(1, TimeUnit.SECONDS)) { ... }` | 拿不到就放弃/降级，**打破「无限等待」** |
| **减少锁范围** | 别把慢 IO 放在锁里 | 缩短临界区 → 交叉窗口变小 |
| **避免嵌套锁** | 一次只持有一把锁 | 破坏「持有并等待」 |
| **不持有锁时调用外部代码** | 别在锁里调第三方库 | 外部代码可能再加锁，直接制造死锁 |
| **用 `tryLock` + 回滚** | `ReentrantLock` 版 | 拿第二把锁失败就释放第一把 |

**统一加锁顺序**的实现：

```java
// ⭐ 两把锁按固定顺序获取：谁 id 小先拿谁
public void transfer(Account from, Account to, int amount) {
    int a = System.identityHashCode(from);
    int b = System.identityHashCode(to);

    if (a > b) {                       // ⭐ 保证全局顺序一致
        Account tmp = from; from = to; to = tmp;
    }

    synchronized (from) {
        synchronized (to) {
            from.balance -= amount;
            to.balance += amount;
        }
    }
}
```

## 十一、可运行示例：CAS 自旋与死锁检测

### 示例一：CAS 自旋累加

```java
import java.util.concurrent.atomic.AtomicInteger;

public class CasDemo {
    private static final AtomicInteger COUNTER = new AtomicInteger();

    public static void main(String[] args) throws InterruptedException {
        // ⭐ 10 个线程各累加 1000 次，结果一定精确等于 10000
        Thread[] workers = new Thread[10];
        for (int i = 0; i < workers.length; i++) {
            workers[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    // ⭐ CAS 循环：比较失败就重试，最终一定成功
                    int expected;
                    do {
                        expected = COUNTER.get();
                    } while (!COUNTER.compareAndSet(expected, expected + 1));
                }
            }, "cas-" + i);
            workers[i].start();
        }
        for (Thread w : workers) {
            w.join();                      // 等全部线程跑完
        }
        System.out.println("CAS 累加结果 = " + COUNTER.get() + "（期望 10000）");
    }
}
```

输出：

```text
CAS 累加结果 = 10000（期望 10000）
```

⭐ **注意结果是精确的 10000**——CAS 保证了原子性，即使 10 个线程同时抢。这也是 `AtomicInteger` 相对于 `volatile int` 的核心价值。

### 示例二：死锁复现与检测

```java
public class DeadlockDetectDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) throws InterruptedException {
        // 线程 1：先要 A，再要 B
        new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(100);
                synchronized (LOCK_B) { }      // 要 B
            }
        }, "deadlock-t1").start();

        // 线程 2：先要 B，再要 A  ← ⭐ 与 t1 顺序相反
        new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(100);
                synchronized (LOCK_A) { }      // 要 A
            }
        }, "deadlock-t2").start();

        Thread.sleep(500);
        System.out.println("两个线程的状态（都是 BLOCKED = 死锁了）：");
        for (Thread t : Thread.getAllStackTraces().keySet()) {
            if (t.getName().startsWith("deadlock")) {
                System.out.printf("  %-12s state=%s%n", t.getName(), t.getState());
            }
        }
        System.out.println("用 jstack <pid> 看末尾的 Found one Java-level deadlock 段");
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

输出：

```text
两个线程的状态（都是 BLOCKED = 死锁了）：
  deadlock-t1  state=BLOCKED
  deadlock-t2  state=BLOCKED
```

⚠️ **这个程序跑完不会退出**（死锁线程一直卡着）。测试时用 `Ctrl+C` 结束，或者把死锁部分注释掉。

## 十二、陷阱

1. **⚠️ 以为 `synchronized` 锁的是「代码块」**——锁的是**对象**；两段毫不相干的代码锁同一个对象照样互斥；
2. **⚠️ 用 `String` 字面量或 `Integer` 缓存对象当锁**——常量池/缓存共享，会造成**跨应用的意外互斥**；
3. **⚠️ 用 `this` 或可变的外部对象当锁**——外部能干扰你，字段被换掉锁就失效；要用私有 `final` 字段；
4. **⚠️ `ReentrantLock` 的 `lock()` 不写在 `try` 里、`unlock()` 不写在 `finally` 里**——异常时锁永不释放，全线程卡死；
5. **⚠️ 以为 `volatile` 能替代锁**——`count++` 这类复合操作依然错；「多个变量要一起改」必须用锁；
6. **⚠️ 在 `synchronized` 里做慢 IO**——锁被长时间持有，其他线程全卡 `BLOCKED`，接口整体超时；
7. **⚠️ `wait()` / `notify()` 没在锁内调用**——抛 `IllegalMonitorStateException`；
8. **⚠️ `wait()` 的条件判断用 `if` 而不是 `while`**——信号丢失 / 越界，**一律用 `while`**；
9. **⚠️ 用 `notify()` 而不是 `notifyAll()`**——可能唤醒错线程导致**永久卡死**；
10. **⚠️ 以为偏向锁还在**——⚠️ **JDK 15 起默认禁用并废弃（JEP 374），后续版本实现已移除**；现在只有「无锁 → 轻量级 → 重量级」三阶段；
11. **⚠️ 临界区写太长**——自旋线程白烧 CPU、容易膨胀为重量级锁；**临界区要短**；
12. **⚠️ 用 `LongAdder` 做发号器**——它的 `sum()` 不精确；唯一 ID 要用 `AtomicInteger.getAndIncrement()`；
13. **⚠️ 多线程加锁顺序不一致**——直接死锁；必须**全局固定顺序**；
14. **⚠️ 以为「死锁概率低就没事」**——死锁一旦触发就是**永久卡死**，必须从代码结构上杜绝。

## 小结

- ⭐ **`synchronized` 锁的是对象**：同步块锁指定对象，实例同步方法锁 `this`，静态同步方法锁 `Class` 对象；**锁对象要用私有 `final` 字段**
- **字节码**：同步块 → `monitorenter`/`monitorexit`；同步方法 → `ACC_SYNCHRONIZED` 标志
- **锁升级**：无锁 → 偏向锁 → 轻量级锁 → 重量级锁；⚠️ **偏向锁 JDK 15 起默认禁用废弃（JEP 374），后续版本移除，现在只有三阶段**
- **轻量级锁** = CAS + 自旋（适合竞争小、临界区短）；**重量级锁** = Monitor（挂起线程、上下文切换）
- **`Monitor` 三要素**：`EntryList`（抢锁排队）/ `Owner`（持锁者）/ `WaitSet`（`wait()` 等待队列）；⚠️ `wait`/`notify` 必须在锁内
- **`ReentrantLock` 优势**：可中断、可超时、可公平锁、多条件队列；⚠️ `lock()`/`unlock()` 必须 `try-finally` 配对
- **`Condition`**：多个条件队列（`notFull`/`notEmpty`），精准唤醒
- **`ReadWriteLock`** 读共享写排他；**`StampedLock`** 提供乐观读（`tryOptimisticRead` + `validate`）
- ⭐ **CAS** = 原子比较并交换，`AtomicInteger` 内部就是 CAS 循环；⚠️ 有 ABA 问题（用 `AtomicStampedReference` 解）
- ⭐ **AQS** = 状态量 + CLH 等待队列 + 模板方法（`tryAcquire`/`tryRelease`）；是 `ReentrantLock`/`CountDownLatch`/`Semaphore` 的基座
- **原子类**：`AtomicInteger`（CAS，精确）/ `LongAdder`（分段累加，高并发快但读不精确）
- ⭐ **死锁四条件**：互斥、持有并等待、不可剥夺、循环等待；**破解循环等待 = 固定加锁顺序**；排查看 `jstack` 的 `Found one Java-level deadlock`

## 练习

1. 写两个方法，一个用同步块、一个用静态同步方法，分别说明它们锁的是哪个对象。
2. 用 `javap -c` 反编译一个含同步块和同步方法的类，找到 `monitorenter`/`monitorexit` 和 `ACC_SYNCHRONIZED`。
3. 解释「自旋」为什么只在「临界区很短」时才划算；如果临界区是 100ms 会发生什么？
4. 说出偏向锁被废弃的原因（JEP 374），以及现在锁升级实际有几个阶段。
5. 画出 `Monitor` 的 `EntryList` / `Owner` / `WaitSet` 三者之间的关系，并说明线程从 `Owner` 调到 `WaitSet` 的条件。
6. `ReentrantLock` 相比 `synchronized` 多出哪四个能力？为什么 `synchronized` 做不到？
7. 为什么 `wait()` 的条件判断必须用 `while` 而不是 `if`？举一个 `notify()` 导致卡死的具体场景。
8. 用 `Condition` 实现一个生产者-消费者队列，说明为什么用两个 `Condition` 优于一个。
9. 解释「`LongAdder` 为什么比 `AtomicInteger` 快」，以及它的代价。
10. 什么是 AQS 的「模板方法」？用 `ReentrantLock` 举例说明 `state` 字段的语义。
11. 复现本文的死锁例子，用 `jstack` 找到 `Found one Java-level deadlock` 段，读出持锁关系。
12. 写一个「转账」方法，保证两个账户的加锁顺序全局一致，从结构上杜绝死锁。
