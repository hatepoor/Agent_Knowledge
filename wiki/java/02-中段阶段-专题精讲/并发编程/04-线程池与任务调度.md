## 一、为什么必须用线程池

最朴素的写法是每个任务 `new Thread(r).start()`。它有四个硬伤：

| 问题 | 具体后果 |
|------|---------|
| **创建销毁开销大** | 每创建一个 OS 线程都要分配独立的栈内存（默认约 1MB），创建/销毁是系统调用级别的开销。任务很轻时，这部分开销远大于业务本身 |
| **无限创建会 OOM** | 流量一涨线程数就线性涨，最终 `OutOfMemoryError: unable to create new native thread`，或者把进程内存吃光 |
| **无法控制并发数** | 数据库只有 20 个连接，你起了 1000 个线程并发去查，全部卡在等连接上——**下游被打垮，上游毫不知情** |
| **无统一治理** | 线程没有名字、没有指标、异常无处收敛、停机时无法等待任务完成 |

**线程池（Thread Pool）** 的定义：一组**可复用的工作线程 + 一个存放待执行任务的队列 + 一套过载时的拒绝规则**，把「每次创建线程」的成本摊薄成「反复复用线程」。

⭐ 线程池的三层价值，一句话一层：

1. **复用** —— 省掉创建销毁开销；
2. **限流** —— 用线程数与队列容量给下游兜底（这叫**背压**，backpressure）；
3. **治理** —— 有名字、有指标、能优雅停机。

> 对照 Python：`concurrent.futures.ThreadPoolExecutor` 是最接近的概念。
> ```python
> from concurrent.futures import ThreadPoolExecutor
>
> with ThreadPoolExecutor(max_workers=8) as pool:
>     fut = pool.submit(task, arg)   # 返回 Future
>     print(fut.result(timeout=5))   # 超时会抛 TimeoutError
> ```
> ⚠️ Python 的线程池队列**默认无界**，Java 这边的 `LinkedBlockingQueue` 默认也是无界——但 Java 生态对这件事踩坑更多、要求更严（见本文第六节）。

## 二、ThreadPoolExecutor：七个构造参数

Java 8+ 的 `ThreadPoolExecutor` 只有一个「全参」构造器，参数正好七个：

```java
public ThreadPoolExecutor(
        int corePoolSize,                 // ①
        int maximumPoolSize,              // ②
        long keepAliveTime,               // ③
        TimeUnit unit,                    // ④
        BlockingQueue<Runnable> workQueue,// ⑤
        ThreadFactory threadFactory,      // ⑥
        RejectedExecutionHandler handler) // ⑦
```

| # | 参数 | 作用 | 建议 / 默认 | ⚠️ 陷阱 |
|---|------|------|-------------|---------|
| ① | `corePoolSize`<br>**核心线程数** | 即使空闲也保留的常驻线程数。池启动后线程数从 0 开始，任务到来先补到这么多个 | IO 密集 2N~4N；CPU 密集 N+1 | 核心线程**不会**因为空闲而自动回收（除非设 `allowCoreThreadTimeOut(true)`） |
| ② | `maximumPoolSize`<br>**最大线程数** | 线程数上限。**只有队列满了之后**才会用到它 | 一般 = core 的 1.5~2 倍 | ⭐ **无界队列下它永远不生效**，因为任务永远进得去队列 |
| ③ | `keepAliveTime`<br>**非核心线程空闲存活时间** | 超出核心数的线程，在空闲多久后被回收 | 30~60 秒 | ⚠️ **这个时间只管非核心线程**，核心线程不看它 |
| ④ | `unit` | 上面那个时间单位（秒/毫秒/…） | `TimeUnit.SECONDS` | 与 ③ 必须配对使用，别传错单位 |
| ⑤ | `workQueue`<br>**任务队列** | 放不下的任务在这里排队等待。**必须是有界队列** | `new ArrayBlockingQueue<>(200)` | ⚠️ 无界队列 = 任务无限堆积 = OOM（见第四、六节） |
| ⑥ | `threadFactory`<br>**线程工厂** | 决定「线程叫什么名字、属于哪个线程组、优先级多少」 | 自定义命名 | 默认工厂生成 `pool-1-thread-1`，线上排查时根本认不出是哪个业务的池 |
| ⑦ | `handler`<br>**拒绝策略** | 线程数到顶 + 队列也满时，任务怎么办 | `CallerRunsPolicy` 或自定义 | 默认 `AbortPolicy` 会抛异常（见第五节） |

配套的 3 个构造器只是把 ④⑥⑦ 填上默认值：

```java
public ThreadPoolExecutor(int corePoolSize, int maximumPoolSize,
                          long keepAliveTime, TimeUnit unit,
                          BlockingQueue<Runnable> workQueue);          // ⑥⑦ 用默认值
public ThreadPoolExecutor(int corePoolSize, int maximumPoolSize,
                          long keepAliveTime, TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          ThreadFactory threadFactory);               // ⑦ 用默认值
public ThreadPoolExecutor(int corePoolSize, int maximumPoolSize,
                          long keepAliveTime, TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          RejectedExecutionHandler handler);           // ⑥ 用默认值
```

⭐ **生产规范：永远用全参构造器显式写出 ⑥ 和 ⑦**，不要依赖默认实现。

### 一个可直接用的写法

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadFactory;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class BizExecutorFactory {

    private static final AtomicInteger SEQ = new AtomicInteger(1);

    public static ThreadPoolExecutor create(String bizName, int core, int max, int queueSize) {
        ThreadFactory factory = r -> {
            Thread t = new Thread(r, bizName + "-" + SEQ.getAndIncrement());  // ⭐ 线程要能认得出业务
            t.setDaemon(false);   // ⚠️ 业务线程别设守护线程，否则进程可能提前退出
            return t;
        };

        return new ThreadPoolExecutor(
                core,
                max,
                60L, TimeUnit.SECONDS,                              // 非核心线程空闲 60 秒回收
                new ArrayBlockingQueue<>(queueSize),                // ⭐ 必须有界
                factory,
                new ThreadPoolExecutor.CallerRunsPolicy()           // 满了让调用方执行 = 天然限流
        );
    }
}
```

⚠️ **为什么推荐 `CallerRunsPolicy` 做默认**：队列和线程都满时，让**提交任务的线程自己干**。这个线程本来就要等结果，现在顺便干了活——等于把并发压力自动回压给了上游调用方，不需要额外的限流组件。

## 三、任务执行流程（⭐ 本篇最重要）

`execute(task)` 提交一个任务后，线程池内部按下面这张图走：

```
                          execute(task)  /  submit(task)
                                     │
                                     ▼
                  ┌──────────────────────────────────────┐
                  │  ① 当前工作线程数 < corePoolSize ?     │
                  └──────────────────────────────────────┘
                       是 │                    │ 否
                          ▼                    │
              ┌────────────────────┐           │
              │ 创建【核心线程】     │           │
              │ 立刻执行这个任务     │           │
              └────────────────────┘           │
                                               ▼
                  ┌──────────────────────────────────────┐
                  │  ② 尝试 workQueue.offer(task) 成功?    │
                  └──────────────────────────────────────┘
                       是 │                    │ 否
                          ▼                    ▼
        ┌───────────────────────────┐   ┌────────────────────────────────┐
        │ 任务在队列中排队等待        │   │  ③ 线程数 < maximumPoolSize ?  │
        │ 由空闲线程取走执行         │   └────────────────────────────────┘
        │ ⚠️ 此时还没扩容！          │        是 │              │ 否
        └───────────────────────────┘           ▼              ▼
                              ┌──────────────────────┐  ┌──────────────────────────┐
                              │ 创建【非核心线程】     │  │ ④ 触发 RejectedExecution │
                              │ 立刻执行这个任务      │  │    Handler 拒绝策略      │
                              └──────────────────────┘  └──────────────────────────┘
```

### ⭐ 关键点：先入队，再扩容

这个顺序**和大多数人的直觉相反**。直觉是「线程不够就多开一个」，但真实顺序是：

> **先试着把任务塞进队列；只有队列满了，才去创建非核心线程；线程数也到顶了，才拒绝。**

用一组具体数字走一遍（`core=2`、`max=4`、队列容量 `2`）：

| 任务 | 到达时线程数 | 队列长度 | 实际发生了什么 |
|------|-------------|---------|---------------|
| 1 | 0 | 0 | 0 < core → **创建核心线程 1**，直接执行 |
| 2 | 1 | 0 | 1 < core → **创建核心线程 2**，直接执行 |
| 3 | 2 | 0 | 2 ≥ core → **入队**（队列 1/2） |
| 4 | 2 | 1 | 2 ≥ core → **入队**（队列 2/2，已满） |
| 5 | 2 | 2 | 入队失败 → 2 < max → **创建非核心线程 3**，直接执行 |
| 6 | 3 | 2 | 入队失败 → 3 < max → **创建非核心线程 4**，直接执行 |
| 7 | 4 | 2 | 入队失败 → 4 = max → **触发拒绝策略** |

⭐ **由此推出两条重要结论**：

1. **队列越大，越不容易触发扩容。** 队列容量给到 1000 时，前面 1000 个任务全在排队，线程数始终停在 `corePoolSize`，`maximumPoolSize` 形同虚设；
2. **这就是 `Executors.newFixedThreadPool` 会 OOM 的根因**——它内部用无界队列，于是「扩容」这条路永远走不到，「拒绝」也永远触发不了，任务只会无限堆积在队列里直到堆内存爆掉。

⚠️ 另外两个容易忽略的细节：

- **Java 8 起，即使核心线程全空闲，只要队列没满，也不会创建新线程去执行新任务。** 这和早期「空闲核心线程优先接收任务」的策略不同；
- 队列里等待的任务，是**由空闲线程取走执行的**。所以队列是 FIFO 的，**提交顺序 ≠ 执行顺序**（多个线程并行取任务时，实际完成顺序不可控）。

## 四、阻塞队列（BlockingQueue）的选择

**阻塞队列**是线程池的蓄水池：放不下的任务先在这里排队等着，且 `put`/`take` 在满/空时**会阻塞等待**而不是直接失败。

| 实现 | 容量 | 特点 | 适合什么场景 |
|------|------|------|-------------|
| **`ArrayBlockingQueue`** | **必须有界**（构造时指定，如 `new ArrayBlockingQueue<>(200)`） | 底层是环形数组，固定大小 | ⭐ **生产默认选择**。容量明确，超量立刻触发拒绝，是天然的限流阀门 |
| **`LinkedBlockingQueue`** | ⚠️ **默认 `Integer.MAX_VALUE`（约 21 亿），等于无界** | 底层是链表，双锁读写分离，吞吐高 | ⭐ **必须显式写容量**：`new LinkedBlockingQueue<>(200)`。不写就是无界队列 → OOM |
| **`SynchronousQueue`** | **容量 0** | 不存储任何元素，`put` 必须等到有 `take` 接手才返回（直接交接） | 需要「生产者必须找到消费者」的严格背压场景；也是 `CachedThreadPool` 内部的队列 |
| **`PriorityBlockingQueue`** | ⚠️ **无界** | 元素按优先级出队，**不保证 FIFO**（同优先级内部顺序不定） | 任务有明确优先级（告警 > 普通报表） |

⚠️ **`LinkedBlockingQueue` 的默认值是最大的坑**：

```java
new LinkedBlockingQueue<>()             // ⚠️ 无界！容量 Integer.MAX_VALUE
new LinkedBlockingQueue<>(200)          // ✅ 有界
```

它不会报错、不会告警，只是让你在半年后看到 OOM 堆栈时想不起这件事。

### 怎么选

- **绝大多数业务场景 → `ArrayBlockingQueue`（有界）**：容量就是一个显式的「水位线」，能背得下来；
- **任务耗时极短、追求更高吞吐 → `LinkedBlockingQueue`（有界）**：链表在高并发下锁竞争更小，但**一定要写容量**；
- **必须「一个任务对应一个处理者」→ `SynchronousQueue`**：拿不到消费者就让提交方自己跑（配合 `CallerRunsPolicy` 效果好）；
- **有优先级需求 → `PriorityBlockingQueue`**：⚠️ 它无界，且「队头被取走但没成功入队」时会自旋重试，压力大时 CPU 会有毛刺。

## 五、四种拒绝策略（⭐）

当「线程数到 `maximumPoolSize`」且「队列也满了」，说明池子彻底扛不住了，此时由**拒绝处理器（`RejectedExecutionHandler`）** 决定任务的去向。

| 策略 | 行为 | 优点 | ⚠️ 风险 / 适用 |
|------|------|------|--------------|
| **`AbortPolicy`**（默认） | 抛 `RejectedExecutionException` | 失败显式，不丢任务 | ⚠️ 异常会一路抛回提交方。**如果提交方没处理，可能连业务主流程一起挂掉** |
| **`CallerRunsPolicy`** | 由**调用者线程**（提交任务的那个线程）直接执行 | ⭐ **天然限流**：提交方被迫参与干活，提交速度自动降下来 | 提交方线程被阻塞，接口 RT 变长；**非 Web 场景（如定时任务自己提交）会拖慢调度线程** |
| **`DiscardPolicy`** | 静默丢弃，不抛异常不记录 | 简单粗暴，永不阻塞提交方 | ⚠️ **任务凭空消失**，且没有任何痕迹——最危险的一种，除非任务本身可丢 |
| **`DiscardOldestPolicy`** | 丢弃队首最老的任务，再重试入队 | 保住「最新任务」 | ⚠️ 队列持续满时可能反复重试；老任务被丢，无日志 |

### ⭐ 生产建议：自定义「落库 / 入 MQ + 告警」

四种内置策略都不够用——它们要么丢任务没痕迹，要么抛异常打穿业务。生产上推荐自定义一个把失败任务**先存下来**的处理器：

```java
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.RejectedExecutionHandler;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.atomic.AtomicInteger;

public class SaveAndRejectHandler implements RejectedExecutionHandler {

    // ① 被拒任务的「补偿队列」：真实项目里换成落库 / 投递 MQ
    private final List<Runnable> backupQueue = new CopyOnWriteArrayList<>();
    private final AtomicInteger rejectCount = new AtomicInteger();
    private final RejectedExecutionHandler fallback;   // 兜底：真存不下来时的行为

    public SaveAndRejectHandler(RejectedExecutionHandler fallback) {
        this.fallback = fallback;
    }

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        rejectCount.incrementAndGet();      // ② 拒绝次数是最关键的池健康信号
        try {
            backupQueue.add(r);              // ③ 先把任务留住，之后再补偿重放
        } catch (RuntimeException e) {
            fallback.rejectedExecution(r, executor);   // ④ 连存都存不下，才交给兜底策略
        }
    }

    public int rejectCount() {
        return rejectCount.get();
    }
}
```

⭐ 有了它，「任务被拒」从**静默的线上事故**变成**一条可查的补偿队列**：被拒的 `Runnable` 还在 `backupQueue` 里，事后可以捞出来重放。

## 六、⚠️ Executors 工厂方法的坑

JDK 提供了 `Executors` 工具类，一步创建线程池。**它方便，但生产环境基本都不能用**——原因是它硬编码了不安全的队列或线程数策略。

| 工厂方法 | 内部实现 | ⚠️ 后果 |
|----------|---------|---------|
| `newFixedThreadPool(n)` | 无界 `LinkedBlockingQueue` | 任务无限堆积 → **OOM**。队列永远不满，`maximumPoolSize` 形同虚设 |
| `newSingleThreadExecutor()` | 无界 `LinkedBlockingQueue` | 同上；且一个任务卡住会堵死全部后续任务 |
| `newCachedThreadPool()` | **线程数无上限** + `SynchronousQueue` | 任务来得比消费快时无限创建线程 → **OOM**（`unable to create new native thread`） |
| `newScheduledThreadPool(n)` | 无界 `DelayedWorkQueue` | 定时任务堆积无上限 → **OOM** |
| `newWorkStealingPool()`（Java 21+） | `ForkJoinPool` | 语义与线程池差异大（见第五篇 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]] 的 `CompletableFuture` 部分） |

⭐ **生产铁律：显式 `new ThreadPoolExecutor(...)`，把队列容量、线程工厂、拒绝策略三样都写出来。**

《阿里巴巴 Java 开发手册》明确禁止使用 `Executors` 创建线程池，原因就是上面这些。

## 七、线程池大小怎么定

两个经典公式，先说清楚每个符号：

- **N** = CPU 核数（`Runtime.getRuntime().availableProcessors()`）；
- **W** = 单个任务等待时间（等 IO 的时间，如等数据库响应）；
- **T** = 单个任务的 CPU 计算时间。

### CPU 密集型：≈ N + 1

任务几乎不等待，全在算数。线程数超过核数只会加剧上下文切换。留 +1 是为了在某个线程因缺页/GC 被挂起时，仍有线程能接着跑。

### IO 密集型：≈ N × (1 + W/T)

等待时间远大于计算时间时，多开线程可以提高利用率。例：8 核，任务 90% 时间在等 IO（W/T = 9）→ 8 × 10 = 80 个线程。

### ⚠️ 但结论是「先给经验值，再压测调优」

不要迷信公式，原因有三：

1. **W/T 是最难测的量**——它随流量、下游负载、数据量实时变化；
2. **瓶颈往往不在 CPU**——真正卡住你的可能是数据库连接数（见 [[java/02-中段阶段-专题精讲/SpringBoot/Web开发与分层实践]] 里的 HikariCP 配置）；
3. **线程数不是唯一的旋钮**——队列容量、批量大小、超时时间都会影响吞吐。

⭐ 正确姿势：**先给一个保守的经验值**（IO 密集从 2N~4N 起步），上线后看指标（第 11 节）压测调优。

## 八、任务提交：execute / submit / schedule

| 方法 | 提交什么 | 返回值 | 异常去哪了 |
|------|---------|--------|-----------|
| `execute(Runnable)` | 任务 | `void` | ⭐ 交给线程的 `UncaughtExceptionHandler`，**调用方感知不到** |
| `submit(Runnable/Callable)` | 任务 | `Future<?>` | ⚠️ **异常被吞进 `Future`**，不调 `get()` 就永远看不到 |
| `schedule(Runnable, delay, unit)` | 延迟执行的任务 | `ScheduledFuture<?>` | 同 `submit` |

### `ScheduledThreadPoolExecutor`：定时与周期任务

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);

scheduler.schedule(() -> System.out.println("10 秒后执行一次"), 10, TimeUnit.SECONDS);
scheduler.scheduleAtFixedRate(() -> heartbeat(), 0, 30, TimeUnit.SECONDS);   // 固定频率
scheduler.scheduleWithFixedDelay(() -> report(), 0, 30, TimeUnit.SECONDS);   // 固定间隔
```

⚠️ **`scheduleAtFixedRate` 与 `scheduleWithFixedDelay` 的区别**：

- `scheduleAtFixedRate`：**按「开始时间」算间隔**。若某次执行耗时 40 秒而周期是 30 秒，下一次会立刻开始，任务**堆积**；
- `scheduleWithFixedDelay`：**按「上次结束时间」算间隔**。永远不会有任务堆积，但总耗时会被拉长。

⚠️ 另一个坑：**周期任务抛异常后，后续调度会直接停止**。所以周期任务内部必须自己 `try-catch` 兜住所有异常。

### `Future`：拿结果、超时、中断

```java
Future<String> future = executor.submit(() -> callRemoteApi());

try {
    String result = future.get(3, TimeUnit.SECONDS);   // ⭐ 最多等 3 秒
    System.out.println(result);
} catch (TimeoutException e) {
    future.cancel(true);          // ⭐ 取消，并尝试中断执行中的线程
    log.warn("远程调用超时", e);
} catch (InterruptedException e) {
    future.cancel(true);
    Thread.currentThread().interrupt();   // ⭐ 恢复中断标志，别吞掉
} catch (ExecutionException e) {
    // ⚠️ 只有这里能看到 submit 提交的任务抛出的异常
    log.error("任务执行失败", e.getCause());
}
```

三个要点：

1. **`get()` 会阻塞**，所以别在 `submit` 之后立刻在主线程 `get()`——那就等于没异步；
2. **`get(timeout, unit)` 超时抛 `TimeoutException`**，不会自动取消，**必须自己 `cancel(true)`**；
3. **`cancel(true)` 是「请求中断」**，任务代码必须自己响应 `InterruptedException`（捕获后要恢复中断标志）才会真的停下。

### `CompletableFuture`：组合式异步

`Future` 只能等一个结果、无法把多个结果串起来。`CompletableFuture` 提供了链式组合，**但它默认用的是 `ForkJoinPool.commonPool()`，不是你的线程池**——这是第五篇的重点（见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]] 的「CompletableFuture」小节）。这里先给一个最小用法：

```java
CompletableFuture<User> userF = CompletableFuture.supplyAsync(() -> loadUser(id));
CompletableFuture<List<Order>> orderF = CompletableFuture.supplyAsync(() -> loadOrders(id));

CompletableFuture.allOf(userF, orderF)
        .thenApply(v -> merge(userF.join(), orderF.join()))   // 组合
        .thenAccept(this::sendToUser)
        .exceptionally(e -> { log.error("聚合失败", e); return null; });
```

## 九、优雅停机（⭐）

进程收到 `SIGTERM`（容器编排、systemd 停服）时，如果线程池里的任务被硬生生打断，任务就丢了。**优雅停机**的语义是：不再接新活 → 把存量干完 → 再退出。

| 方法 | 行为 | ⚠️ 注意 |
|------|------|--------|
| `shutdown()` | **不再接受新任务**；已提交任务继续执行完 | 正在跑的任务**不会被打断** |
| `shutdownNow()` | 尝试**立即中断**所有正在执行的任务，返回未开始的任务列表 | ⚠️ **不保证任务能执行完**；正在跑的线程会收到中断信号 |
| `awaitTermination(timeout, unit)` | 等待池在超时时间内终止 | 返回 `true` 表示干净终止，`false` 表示超时 |

标准写法：

```java
executor.shutdown();                                  // ① 停止接单
try {
    if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
        executor.shutdownNow();                       // ② 超时还没完，硬停
        executor.awaitTermination(5, TimeUnit.SECONDS);
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}
```

### ⭐ Spring Boot 里的两种做法

**做法一：用 `ThreadPoolTaskExecutor`（推荐）**

Spring 自带的 `ThreadPoolTaskExecutor`（`org.springframework.scheduling.concurrent`）在容器关闭时会自动调用 `shutdown()`。

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(8);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(500);
    executor.setKeepAliveSeconds(60);
    executor.setThreadNamePrefix("biz-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    // ⚠️ 必须等它初始化完成，否则首次调用时线程池还没建好
    executor.initialize();
    return executor;
}
```

**做法二：自己注册销毁钩子**

```java
@Bean(destroyMethod = "shutdown")
public ThreadPoolExecutor bizExecutor() {
    return new ThreadPoolExecutor(8, 16, 60, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(500),
            new BizThreadFactory("biz"),
            new ThreadPoolExecutor.CallerRunsPolicy());
}
```

⚠️ `destroyMethod = "shutdown"` 只调用 `shutdown()`（不等待）。想要「等任务做完再退」，用 `destroyMethod = "close"`——`ExecutorService` 在 **Java 19+** 实现了 `AutoCloseable`，`close()` 会关闭并**等待终止**。

## 十、Spring 场景：@Async 的坑

`@Async` 让一个方法在**另一个线程**执行，是「异步任务」最省事的写法。但它有四个经典坑。

### 坑 1：默认执行器可能根本不池化

`@Async` 不指定执行器时，Spring 会去容器里找名为 `taskExecutor`（或唯一的 `TaskExecutor` 类型）的 Bean；**找不到就退回到 `SimpleAsyncTaskExecutor`**。

⚠️ **`SimpleAsyncTaskExecutor` 的行为是「每次调用都 new 一个新线程」，完全不复用**。在流量稍大时就会把线程数打到几百上千，最终 `unable to create new native thread`。

Spring Boot 通过 `TaskExecutionAutoConfiguration` 默认提供了一个池化的 `ThreadPoolTaskExecutor`（bean 名为 `applicationTaskExecutor`，别名 `taskExecutor`），所以普通 Boot 项目不会踩到这个坑。但只要满足下面任一条件，就会退回 `SimpleAsyncTaskExecutor`：

- 排除了 `TaskExecutionAutoConfiguration`；
- 在**非 Boot 的 Spring 环境**里用；
- 自己定义了多个 `Executor` Bean，导致 Spring 无法确定「唯一」的那个。

⭐ **稳妥做法：自己定义一个 `Executor` Bean，并在 `@Async` 上显式指定名字。**

```java
@Bean("taskExecutor")          // ⭐ 名字必须是 taskExecutor，或在 @Async 里指定
public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(8);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(200);
    executor.setThreadNamePrefix("async-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}

@Service
public class OrderService {
    @Async("taskExecutor")     // ⭐ 显式指定，别赌默认
    public void sendEmail(Long orderId) { ... }
}
```

### 坑 2：同类内部自调用不生效

```java
@Service
public class OrderService {
    @Async
    public void outer() { inner(); }   // ⚠️ 还是同步执行！

    @Async
    public void inner() { ... }        // 直接调用不走代理，异步注解形同虚设
}
```

原因：`@Async` 靠 **Spring AOP 代理**实现，而内部调用是 `this.inner()`，**不经过代理**，注解自然不会被拦截。

解法：把 `@Async` 方法拆到另一个 Bean 里用注入调用，或自己注入代理 `AopContext.currentProxy()`（需 `@EnableAspectJAutoProxy(exposeProxy = true)`）。代理机制详见 [[java/02-中段阶段-专题精讲/SpringBoot/IoC与Bean生命周期]]。

### 坑 3：返回值只能是 `void` 或 `Future` / `CompletableFuture`

`@Async` 方法返回 `void` 表示「fire-and-forget」（发出即忘），调用方拿不到任何执行结果。需要结果时，返回 `CompletableFuture<T>`（推荐）或 `Future<T>`。

### 坑 4：方法不能是 `private` / `final`，类不能是 `final`

AOP 代理依赖生成子类覆盖方法。`private` 方法无法被覆盖，`final` 方法/类无法被继承，注解都会**静默失效**——不报错，只是同步执行，非常难查。

### `@Async` 与事务的顺序

⚠️ **同一个类里，`@Async` 和 `@Transactional` 的执行顺序是不确定的**（取决于代理链顺序）。想要「先提交事务，再异步发消息」，**必须把 `@Async` 方法拆到另一个 Bean**。

## 十一、监控线程池

不看指标的线程池等于黑盒。`ThreadPoolExecutor` 自带这些观测点：

| 指标 | 取值方法 | 健康区间 / 含义 |
|------|---------|----------------|
| **活跃线程数** | `getActiveCount()` | 长期贴着 `maximumPoolSize` → 池太小，该扩容了 |
| **线程总数** | `getPoolSize()` | — |
| **队列长度** | `getQueue().size()` | ⭐ **持续逼近容量 → 下游已经扛不住了**，是最早的预警信号 |
| **完成任务数** | `getCompletedTaskCount()` | 吞吐趋势 |
| **已提交任务数** | `getTaskCount()` | 与完成数相减 ≈ 还在排队 + 被拒的 |
| **最大历史线程数** | `getLargestPoolSize()` | 用来验证「我设的 max 到底有没有被用到」 |
| **拒绝次数** | ⚠️ **没有公开 getter**，需要自定义 `RejectedExecutionHandler` 计数（见第五节） | ⭐ **只要这个数在涨，池就不够用** |

接进 Spring Boot 的 Micrometer（`/actuator/metrics` 可查）：

```java
@Bean
public MeterBinder bizExecutorMetrics(MeterRegistry registry,
                                      @Qualifier("bizExecutor") ThreadPoolTaskExecutor executor) {
    // 把线程池注册为可观测对象，指标名形如 executor.active / executor.queued / executor.completed
    return ExecutorServiceMetrics.monitor(registry, executor.getThreadPoolExecutor(),
                                          "bizExecutor", Tags.of("biz", "order"));
}
```

⚠️ 加上告警后至少要有这三条：

- **队列长度持续 > 80% 容量** → 容量不足；
- **拒绝次数 > 0** → 立即扩容或加降级；
- **活跃线程数 == 最大线程数** → 已到天花板。

指标导出与端点配置见 [[java/02-中段阶段-专题精讲/SpringBoot/Web开发与分层实践]] 的「可观测性（Actuator）」小节。

## 十二、完整可运行示例

把前面的知识点串起来：4 个核心线程 + 有界队列 + 统计拒绝次数 + 优雅停机。

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class ThreadPoolDemo {

    public static void main(String[] args) throws InterruptedException {
        AtomicInteger rejected = new AtomicInteger();
        AtomicInteger done = new AtomicInteger();
        AtomicInteger seq = new AtomicInteger(1);

        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                4, 4,                                   // 4 个核心线程，不扩到更多
                60L, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(2),            // ⚠️ 队列只放 2 个，很快就会触发拒绝
                (r) -> new Thread(r, "biz-" + seq.getAndIncrement()),  // 线程工厂
                (r, executor) -> {                      // 自定义拒绝策略：计数 + 抛异常
                    rejected.incrementAndGet();
                    throw new RejectedExecutionException("队列已满，任务被拒");
                });

        for (int i = 1; i <= 10; i++) {
            final int taskId = i;
            try {
                pool.execute(() -> {
                    System.out.println("任务 " + taskId + " 执行中 @ " + Thread.currentThread().getName());
                    try {
                        Thread.sleep(100);              // 模拟耗时任务
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                    done.incrementAndGet();
                });
            } catch (RejectedExecutionException e) {
                System.out.println("⚠️ " + e.getMessage());
            }
        }

        System.out.println("活跃线程数 = " + pool.getActiveCount());
        System.out.println("队列长度   = " + pool.getQueue().size());
        System.out.println("拒绝次数   = " + rejected.get());

        pool.shutdown();                                 // 优雅停机：不再接单
        pool.awaitTermination(10, TimeUnit.SECONDS);     // 等待存量任务做完
        System.out.println("完成任务数 = " + pool.getCompletedTaskCount());
    }
}
```

运行后可以看到：**前 6 个任务被正常执行（4 个线程 + 2 个排队），后 4 个被拒绝**，队列长度和拒绝次数都能被观测到。

## 十三、陷阱

1. **⚠️ 每次任务 `new Thread`**——开销、OOM、无法限流、无法治理，四个问题一次性全中；
2. **⚠️ 以为「线程不够会自动扩容」**——真实顺序是**先入队、再扩容**，队列够大时 `maximumPoolSize` 永远用不上；
3. **⚠️ 用 `new LinkedBlockingQueue<>()` 不写容量**——默认 `Integer.MAX_VALUE`，等于无界，任务无限堆积直到 OOM；
4. **⚠️ 用 `Executors.newFixedThreadPool` / `newCachedThreadPool`**——前者无界队列、后者线程数无上限，生产代码必须显式 `new ThreadPoolExecutor(...)`；
5. **⚠️ 用 `DiscardPolicy` 静默丢任务**——任务消失且无痕迹，线上无从追溯；宁可 `AbortPolicy` 抛异常；
6. **⚠️ `submit` 之后不 `get()`**——异常被吞进 `Future`，业务失败你完全不知道；
7. **⚠️ 不做优雅停机**——容器重启时任务被硬打断，数据写一半；
8. **⚠️ `@Async` 方法内部自调用**——不走代理，异步完全失效（且不报错）；
9. **⚠️ `@Async` 方法是 `private` 或 `final`**——AOP 无法织入，同样静默失效；
10. **⚠️ 只看应用日志，不看线程池指标**——队列堆积、拒绝次数这两个最关键的信号被漏掉，问题往往在崩溃前几小时就有征兆；
11. **⚠️ 把线程池大小当成唯一旋钮**——瓶颈常常在数据库连接数或下游服务，不在 CPU。

## 小结

- **线程池 = 复用 + 限流 + 治理**，替代每次 `new Thread`
- **七个参数**：core（常驻）、max（上限）、keepAliveTime+unit（非核心存活）、queue（蓄水池）、threadFactory（可识别）、handler（兜底）——**全参构造器显式写全**
- **执行流程：核心线程 → 入队 → 非核心线程 → 拒绝**——⭐ **先入队、再扩容**，与直觉相反
- **队列**：生产默认 `ArrayBlockingQueue`（有界）；⚠️ `LinkedBlockingQueue` 不写容量就是无界
- **拒绝策略**：`CallerRunsPolicy` 天然限流；生产建议自定义「落库 / 入 MQ + 告警」
- ⚠️ **`Executors` 工厂方法生产禁用**，显式 `new ThreadPoolExecutor(...)`
- **大小**：CPU 密集 ≈ N+1，IO 密集 ≈ N×(1+W/T)，但**以压测为准**
- **提交**：`execute` 无返回值无感知，`submit` 返回 `Future`（异常在 `get()` 里），`schedule` 定时周期
- **停机**：`shutdown` → `awaitTermination` → 必要时 `shutdownNow`；Spring 用 `ThreadPoolTaskExecutor` 或 `destroyMethod`
- **Spring**：`@Async` 四个坑——默认执行器可能不池化、内部自调用失效、返回值只能是 void/Future、方法不能 private/final
- **监控**：活跃线程数、队列长度、完成任务数、拒绝次数

## 练习

1. 用 `core=2`、`max=4`、队列容量 `2`，写出连续提交 8 个任务后的：线程数、队列长度、被拒绝的任务编号。
2. 解释为什么 `newFixedThreadPool` 里 `maximumPoolSize` 永远不会被触发。
3. 写一个自定义拒绝策略：把被拒任务投递到内存队列并打点。
4. `submit` 一个会抛 `RuntimeException` 的任务，不调用 `get()`。异常去哪了？在哪能看到？
5. 实现一个 `shutdown` + `awaitTermination` 的停机钩子，要求：最多等 30 秒，超时则 `shutdownNow`。
