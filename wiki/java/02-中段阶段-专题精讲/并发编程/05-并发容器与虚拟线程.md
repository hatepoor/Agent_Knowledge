## 一、ConcurrentHashMap（Java 8+）

### 1.1 它解决什么问题

`HashMap` **不是线程安全的**。并发写入时可能：数据丢失（后写覆盖先写）、`size()` 与实际不符；Java 7 时代甚至会出现链表成环导致 `get()` 死循环。

`ConcurrentHashMap`（**CHM**）是 JDK 提供的线程安全哈希表，也是并发编程里最常用的容器。

### 1.2 Java 8+ 的实现：CAS + synchronized（锁桶头节点）

**Java 7** 的 CHM 用 `Segment`（分段）把表切成 16 段，每段一把锁——这就是常说的「分段锁」。**Java 8 起彻底废弃了 `Segment` 结构**，改成：

- 表结构是一个 `Node[]`（数组），跟 `HashMap` 一样，元素按哈希散列到「桶（bucket）」里；
- 桶内结构依然是链表，链表长度 ≥ 8 且表长 ≥ 64 时转成红黑树；
- 写入时：**桶为空 → 用 `CAS` 直接把新节点放进去**；**桶非空 → 用 `synchronized` 锁住这个桶的头节点**，在桶内做插入或树化。

⭐ **关键点：锁的是桶头节点，不是「分段」。**

```
   线程 A                          线程 B
     │                                │
     ▼                                ▼
 ┌─────────┐                    ┌─────────┐
 │ 桶 0 空 │                    │ 桶 5 有节点│
 │ → CAS   │                    │ → synchronized(桶5头节点)
 │ 直接放入 │                    │   锁住后插入
 └─────────┘                    └─────────┘
     ✅ 不阻塞                     ❌ 和其他操作桶 5 的线程互斥
```

| 维度 | Java 7 | Java 8+ |
|------|--------|---------|
| 结构 | 数组 + 16 个 `Segment`（每段一把锁） | 单个 `Node[]` + 每桶独立加锁 |
| 并发度上限 | 16（锁段数） | ⭐ **接近桶数量**（小表时 ≈ 表长） |
| 扩容 | 段内扩容 | 全表扩容，多线程通过 `helpTransfer` 一起搬 |
| ⚠️ 常见误解 | 「CHM 就是分段锁」 | ⭐ **Java 8 起已无 Segment**，锁粒度是桶 |

⚠️ 记住这句就够了：**Java 8+ 的 `ConcurrentHashMap` 锁的是桶，不是段。**

### 1.3 `putVal` 流程要点

`put(key, value)` 的核心逻辑（`putVal` 方法）可以概括为：

1. **表为空** → 调用 `initTable()` 初始化数组（用 CAS 保证只有一个线程初始化）；
2. **算哈希** → `(h = key.hashCode()) ^ (h >>> 16)`（扰动，让高位也参与寻址）；
3. **定位桶** → `(n - 1) & hash`；
4. **桶为空** → `CAS` 放入新节点（⚠️ CAS 失败说明别人抢先了，**自旋重试**）；
5. **桶非空** → `synchronized (f)` 锁住桶头节点 `f`：
   - 哈希相同且 `equals` → 直接覆盖 value；
   - 哈希不同 → 挂到链表尾部（Java 7 是头插，**Java 8 改成尾插**，减少并发下的链表成环风险）；
   - 链表长度 ≥ 8 且表长 ≥ 64 → 树化为红黑树；
6. **表长超过阈值（负载因子 0.75）→ 扩容**。

⭐ 与 `HashMap` 的关键差异汇总：

| 对比项 | `HashMap` | `ConcurrentHashMap`（Java 8+） |
|--------|-----------|-------------------------------|
| 线程安全 | ❌ 无 | ✅ 有 |
| 空桶写入 | 直接赋值 | `CAS`（无锁） |
| 非空桶写入 | 无同步 | `synchronized` 锁桶头节点 |
| `null` 键 / 值 | ✅ 允许 | ⚠️ **不允许**（见下） |
| 迭代器 | 弱一致（fail-fast，会抛 `ConcurrentModificationException`） | 弱一致（**不抛**该异常，见下） |
| `size()` | 精确 | ⚠️ **估算值**（并发下不精确） |
| `get()` 复杂度 | 平均 O(1) | 平均 O(1) |

### 1.4 ⚠️ 为什么不允许 null 键和值

`ConcurrentHashMap.get(key)` 返回 `null` 时有**两种可能**：

1. 这个 key 根本不存在；
2. 这个 key 存在，但值就是 `null`。

对并发容器来说这个二义性是致命的——「值是 null」意味着「我看到了这个 key 的最新值，它就是 null」，而 `HashMap` 里 `get` 返回 null 只能说明「没有这个 key」（`HashMap` 允许存 null 值，所以 `HashMap` 其实也存在同样的二义性，但它没有并发语义压力）。

**`ConcurrentHashMap` 用「禁止 null」这个约束换来了确定性的语义**：返回 null 就是真的不存在。判断「有没有这个 key」必须用 `containsKey(key)`。

⚠️ 实践影响：从 `Map` 取值时不要写 `if (map.get(k) == null) { map.put(k, v); }` 这种「读-改-写」，并发下会丢数据。改用 `putIfAbsent(k, v)` 或 `computeIfAbsent(k, key -> v)`（原子的）。

### 1.5 弱一致性迭代器

CHM 的迭代器：

- ✅ **不会抛 `ConcurrentModificationException`**（不像 `HashMap` 那样 fail-fast）；
- ⚠️ **但它不保证是某一时刻的快照**。迭代过程中看到的元素**可能包含也可能不包含**迭代开始之后的修改。

⭐ **一句话**：CHM 的迭代器保证「**不会崩、不会读到脏数据**」，但不保证「**看到的是某一瞬间的全量**」。需要快照语义，就自己 `new ArrayList<>(map)` 拷贝一份再遍历。

### 1.6 `computeIfAbsent` 的原子性

`computeIfAbsent(key, mappingFunction)`：如果 key 不存在，就用 `mappingFunction` 计算一个值并放入 map。⭐ **保证整个「判断-计算-放入」过程是原子的**，同一个 key 的映射函数只会被执行一次。

```java
ConcurrentHashMap<String, List<String>> index = new ConcurrentHashMap<>();

// ⭐ 原子：多个线程同时 get 同一个 key，只有一个线程会真正执行 lambda
index.computeIfAbsent("tagA", k -> new ArrayList<>()).add("item1");
```

⚠️ 两个坑：

1. **lambda 里不要做耗时操作或再操作同一个 map**——它持有桶锁，耗时会阻塞同桶的其他线程，嵌套操作可能死锁；
2. Java 8 早期 `putIfAbsent` + `get` 的组合写法会导致映射函数被执行多次，**Java 8 起 `computeIfAbsent` 才修好这个问题**。

### 1.7 计数优化：`LongAdder`

CHM 内部维护计数用的就是 `LongAdder` 的思路。普通的 `AtomicLong` 用 `CAS` 自增，**高并发下所有线程都抢同一个变量，CAS 失败重试会互相干扰**，吞吐上不去。

`LongAdder`（`java.util.concurrent.atomic`）的做法：把计数**分散到多个 cell（格子）**上，各线程写各自的格子，求和时再加起来。

| | `AtomicLong` | `LongAdder` |
|---|---|---|
| 机制 | 单个变量 + CAS 自旋 | 多 cell 分散 + 求和汇总 |
| 低并发 | ✅ 更快 | 稍慢（要遍历 cell） |
| 高并发写多 | ⚠️ **CAS 竞争激烈，吞吐下降** | ✅ **显著更好** |
| 读 | 精确 | ⚠️ **求和期间不是精确快照** |
| 用途 | 需要精确读（如生成 ID） | ⭐ **纯统计计数**（QPS、访问量） |

⚠️ `LongAdder` 的 `sum()` **不保证是精确快照**——求和过程中别的线程还在加。**要精确值就用 `AtomicLong`**。

### 1.8 ⚠️ `size()` 是估算值

CHM 的 `size()` 会把各个 cell 的计数加起来，返回的是**估算值**。并发写入时，它既可能偏大也可能偏小。

要精确的元素个数，通常的做法是：

```java
// 方式一：自己维护一个 AtomicLong / LongAdder 计数器
private final LongAdder counter = new LongAdder();

// 方式二：需要强一致时，先 stop-the-world 再读（CHM 没有直接暴露这个 API）
```

⭐ **面试高频**：`size()` 为什么不精确 —— 因为它统计的是分段计数器的和，而遍历过程中计数还在变；这也是为什么 CHM **不提供 `clear()` 之外的批量原子操作**。

### 1.9 可运行示例：并发计数

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.LongAdder;

public class ChmDemo {

    public static void main(String[] args) throws InterruptedException {
        ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
        int threads = 20, perThread = 10_000;

        CountDownLatch start = new CountDownLatch(1);      // 让所有线程同时起跑
        CountDownLatch done = new CountDownLatch(threads);

        for (int t = 0; t < threads; t++) {
            new Thread(() -> {
                try {
                    start.await();                          // 等统一发令
                    for (int i = 0; i < perThread; i++) {
                        counters.computeIfAbsent("hit", k -> new LongAdder()).increment();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }

        start.countDown();                                  // 发令
        done.await();                                       // 等所有线程结束

        long total = counters.get("hit").sum();
        System.out.println("期望 " + (long) threads * perThread + "，实际 " + total);
        // ⚠️ 注意：换成普通 HashMap 就会丢数据；换成 AtomicLong 也能对，但高并发下 CAS 竞争更激烈
    }
}
```

## 二、CopyOnWriteArrayList / CopyOnWriteArraySet

**写时复制（Copy-On-Write，COW）**：读操作直接读一个不可变的快照；写操作时**复制出整个新容器**，把元素改完，再用一个原子操作把引用换过去。

`CopyOnWriteArrayList` 内部持有一个 `Object[]` 数组 + 一把写锁。

```java
CopyOnWriteArrayList<String> listeners = new CopyOnWriteArrayList<>();
listeners.add("listenerA");     // 复制数组 → 改 → 原子换引用
for (String s : listeners) {    // ⭐ 迭代器是当前数组的快照
    System.out.println(s);      // 迭代期间的 add 对本次遍历不可见
}
```

| 优点 | 代价 |
|------|------|
| 读操作**完全无锁**、不会抛 `ConcurrentModificationException` | ⚠️ **写放大**：一次 `add` 要复制整个数组，O(n) |
| 迭代器是快照，遍历期间容器变化不影响当前遍历 | ⚠️ **写多时极慢**：1000 个元素的列表，`add` 1000 次 = 复制 100 万次元素 |
| 内存可见性天然安全（换引用是 volatile 写） | ⚠️ 内存占用翻倍（新老两个数组共存） |

⭐ **适用场景（必须同时满足）**：

1. **读远多于写**（读 : 写 通常是 10:1 以上）；
2. **元素数量不大**（几百到几千）；
3. **遍历时不能看到中间状态**。

典型场景：**监听器列表、配置快照、路由表、白名单**。

⚠️ **不适合**：写频繁的场景。写频繁请用 `ConcurrentLinkedQueue`（无锁并发队列）或加锁的 `ArrayList`。

`CopyOnWriteArraySet` 是它的 Set 版本，内部基于 `CopyOnWriteArrayList` 实现——**元素天然去重，且不允许 null**。

## 三、BlockingQueue 家族

**阻塞队列**（`BlockingQueue`）是线程池的蓄水池，也是生产者-消费者的标准解法。它的四个核心方法：

| 方法 | 队列满时 | 队列空时 | 返回值 |
|------|---------|---------|--------|
| `put(e)` | ⭐ **阻塞等待** | — | 无 |
| `take()` | — | ⭐ **阻塞等待** | 取出的元素 |
| `offer(e)` | **立即返回 false** | — | `boolean` |
| `poll()` | — | **立即返回 null** | 元素或 `null` |
| `offer(e, timeout, unit)` | ⭐ **阻塞等待超时** | — | `boolean`（超时返回 false） |
| `poll(timeout, unit)` | — | ⭐ **阻塞等待超时** | 元素或 `null` |

⚠️ **`put` 和 `offer` 的区别就是「等不等」**——这是所有生产者-消费者代码里最关键的一个选择：调 `put` 会把生产者堵住（背压），调 `offer` 会直接失败（需要你自己处理失败）。

### 家族成员

| 实现 | 容量 | 内部机制 | 特点 / 适用 |
|------|------|---------|------------|
| **`ArrayBlockingQueue`** | **有界，必须指定** | 数组环形缓冲，**单把锁** | 容量明确 = 天然限流；读写都串行化，吞吐一般 |
| **`LinkedBlockingQueue`** | ⚠️ **默认 `Integer.MAX_VALUE`（无界）**，应显式指定 | 链表，**读锁 + 写锁分离** | 吞吐高于 ABQ；⚠️ **不写容量就是无界队列**，会 OOM |
| **`SynchronousQueue`** | **0（不存元素）** | 直接交接 | `put` 必须等到有 `take` 接手才返回；适合「一进一出严格配对」 |
| **`PriorityBlockingQueue`** | ⚠️ **无界** | 二叉堆 | 按优先级出队，**不保证 FIFO**；⚠️ 无界会堆积 |
| **`DelayQueue`** | ⚠️ **无界** | 内部 `PriorityQueue` | 元素**到期才能取出**，用于延迟任务、订单超时取消、缓存过期 |
| **`LinkedTransferQueue`** | ⚠️ **无界** | 双队列 | `transfer()` 方法能把元素「直接交给等待中的消费者」，性能最好，但生态上用得少 |

⚠️ **`ArrayBlockingQueue` 与 `LinkedBlockingQueue` 的锁差别**：

- `ArrayBlockingQueue`：**一把 `ReentrantLock`**，读和写互斥；
- `LinkedBlockingQueue`：**两把锁**（`putLock` 保护写、`takeLock` 保护读），读和写可以并发，吞吐更高。

### 可运行示例：生产者-消费者

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;

public class ProducerConsumerDemo {

    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<String> queue = new ArrayBlockingQueue<>(3);   // ⭐ 有界 = 有水位线
        String poison = "STOP";

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 5; i++) {
                    queue.put("task-" + i);   // ⭐ 队列满时阻塞，等消费者腾位置
                }
                queue.put(poison);           // 毒丸：通知消费者结束
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "producer");

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    String task = queue.take();       // ⭐ 队列空时阻塞
                    if (poison.equals(task)) break;
                    System.out.println("消费 " + task);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, "consumer");

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
    }
}
```

⭐ 这里 `put` / `take` 的阻塞特性**天然实现了背压**：生产者跑太快会自动停在队列满的那一行，不会把内存撑爆。

## 四、同步工具类

### 4.1 `CountDownLatch`（倒计数门闩）

**一次性**的同步闸门：计数减到 0 时，等待的线程全部放行，**且不能重置**。

```java
CountDownLatch latch = new CountDownLatch(3);   // 计数 3

new Thread(() -> { doWorkA(); latch.countDown(); }).start();
new Thread(() -> { doWorkB(); latch.countDown(); }).start();
new Thread(() -> { doWorkC(); latch.countDown(); }).start();

latch.await();     // ⭐ 主线程在这里等三个都完成
System.out.println("全部完成");
```

| 方法 | 作用 |
|------|------|
| `countDown()` | 计数减 1（减到 0 时释放所有等待者） |
| `await()` | 阻塞直到计数为 0 |
| `await(timeout, unit)` | 超时版本 |
| `getCount()` | 当前剩余计数 |

⭐ 典型用途：**并发初始化后再统一开始**、**等待 N 个并行任务全部完成**、**模拟「三道门都开了才放行」**。

### 4.2 `CyclicBarrier`（栅栏）

**可重复使用**的栅栏：所有参与线程都到达屏障时，一起放行，然后开始下一轮。

```java
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("--- 三人到齐，一起冲 ---"));

for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        barrier.await();    // ⭐ 到达栅栏，等其他人
        System.out.println(Thread.currentThread().getName() + " 出发");
    }).start();
}
```

| 对比 | `CountDownLatch` | `CyclicBarrier` |
|------|------------------|-----------------|
| 语义 | **一个**事件（等 N 件好事发生） | **多个**阶段（每轮等到齐再走） |
| 可重用 | ❌ 一次性 | ✅ 可重复（每轮自动重置） |
| 参与者 | 等待方与计数方可以不同 | 所有线程既是等待方也是参与方 |
| 额外能力 | — | 可传 `barrierAction`，放行时执行一次（打日志、汇总） |

⚠️ `CyclicBarrier` 的等待方数量一旦凑不齐就**永久阻塞**；某线程被中断会破坏屏障，让其他线程抛 `BrokenBarrierException`。

### 4.3 `Semaphore`（信号量）

允许**固定数量**的线程同时进入临界区——本质是一个**许可（permit）计数器**。

```java
Semaphore semaphore = new Semaphore(3);   // 3 个许可

semaphore.acquire();        // 拿许可（没有就阻塞）
try {
    callDownstreamApi();     // ⭐ 同时最多 3 个请求在飞
} finally {
    semaphore.release();     // ⭐ 必须在 finally 里还回去
}
```

| 方法 | 作用 |
|------|------|
| `acquire()` | 获取许可，无许可则阻塞 |
| `acquire(n)` / `tryAcquire(n, timeout, unit)` | 获取 n 个许可 |
| `release()` | 归还 1 个许可 |
| `tryAcquire()` | 尝试获取，拿不到立即返回 false |

⭐ 典型用途：**限流**（保护下游）、**资源池**（数据库连接、第三方配额）。

⚠️ ⚠️ **`release()` 必须在 `finally` 里**，否则业务抛异常会永久泄漏许可，信号量很快耗尽，整个系统卡死。这是最常见的 semaphore bug。

### 4.4 `Phaser`（阶段化同步）

`CountDownLatch` 和 `CyclicBarrier` 的「加强版」，支持**可变数量的参与者**、**多阶段**、每阶段结束可执行回调。

```java
Phaser phaser = new Phaser(1);      // 注册 1 个主线程

for (int i = 0; i < 3; i++) {
    phaser.register();               // 动态注册参与者
    new Thread(() -> {
        doWork();
        phaser.arriveAndAwaitAdvance();   // 到达并等待本阶段结束
    }).start();
}

phaser.arriveAndAwaitAdvance();      // 主线程也参与
```

⭐ 典型用途：**多阶段流水线**（如「并行算 A → 汇合 → 并行算 B → 汇合」），阶段间参与者数量可以变化。

| 场景 | 选谁 |
|------|------|
| 等 N 个任务完成，一次性 | `CountDownLatch` |
| 分阶段、每阶段都要凑齐 | `CyclicBarrier` |
| 限制同时进入的线程数 | `Semaphore` |
| 阶段数不定、参与者会增减 | `Phaser` |

## 五、CompletableFuture（⭐）

### 5.1 它解决什么问题

`Future`（见 [[java/02-中段阶段-专题精讲/并发编程/04-线程池与任务调度]]）只能「等一个结果」，而且只能阻塞地等。`CompletableFuture` 提供了**非阻塞的链式组合**：多个异步任务完成后，把结果组合起来继续往下走。

### 5.2 创建与执行器

```java
CompletableFuture<User> f = CompletableFuture.supplyAsync(() -> loadUser(id));  // 有返回值
CompletableFuture<Void>  g = CompletableFuture.runAsync(() -> sendEmail(id));  // 无返回值
```

⚠️⚠️ **默认执行器不是你的线程池！**

`supplyAsync` / `runAsync` 不传第二个参数时，用的是 **`ForkJoinPool.commonPool()`**——JVM 里的一个**全局共享**线程池。

| 问题 | 后果 |
|------|------|
| 你的业务线程池形同虚设 | 明明配了 `bizExecutor`，异步任务却跑在公共池里 |
| **公共池的并行度 = CPU 核数 - 1** | ⚠️ **IO 密集型任务在公共池里几乎无法并行**，全部串行等待——这是「异步了但没变快」的经典原因 |
| 公共池被其他库占满 | 第三方库（各种 SDK）的 `CompletableFuture` 也用公共池，会互相拖累 |

⭐ **生产必须显式传自己的线程池**：

```java
CompletableFuture<User> f =
        CompletableFuture.supplyAsync(() -> loadUser(id), bizExecutor);
```

### 5.3 常用方法

| 方法 | 作用 | 类型 |
|------|------|------|
| `thenApply(fn)` | 前一个完成后，用它的**结果**继续计算 | 转换（同步） |
| `thenApplyAsync(fn, executor)` | 同上，但在 executor 上异步执行 | 转换（异步） |
| `thenCompose(fn)` | 前一个完成后，用它的**结果**产生**另一个 `CompletableFuture`** | ⭐ **扁平化**（避免 `Future<Future<T>>`） |
| `thenCombine(other, fn)` | 两个 future **都完成**后合并 | 合并 |
| `thenAccept(consumer)` | 消费结果，无返回值 | 消费 |
| `thenRun(runnable)` | 前一个完成后执行动作，忽略结果 | 副作用 |
| `allOf(f1, f2, ...)` | **全部**完成才完成，返回 `CompletableFuture<Void>` | 聚合 |
| `anyOf(f1, f2, ...)` | **任意一个**完成就完成 | 竞速 |
| `exceptionally(fn)` | 只在**异常**时被调用 | 异常处理 |
| `handle(biFn)` | **无论成功失败**都被调用（拿到结果或异常） | 统一处理 |
| `whenComplete(action)` | 无论成功失败都执行，**但不影响结果**（不改变返回值） | 收尾/打日志 |
| `orTimeout(timeout, unit)` | 超时则以 `TimeoutException` 异常完成 | ⭐ 超时控制 |
| `completeOnTimeout(value, timeout, unit)` | 超时则以**默认值**正常完成 | ⭐ 超时控制 |
| `complete(value)` / `completeExceptionally(ex)` | 手动结束一个 future | 手工控制 |

⭐ **`thenApply` vs `thenCompose` 的区别**（面试常问）：

- `thenApply(fn)`：`fn` 返回普通值 → 结果是 `CompletableFuture<T>`；
- `thenCompose(fn)`：`fn` 返回 `CompletableFuture<U>` → 结果被**自动展平**为 `CompletableFuture<U>`。

如果用 `thenApply` 去接收一个返回 `CompletableFuture` 的函数，你会得到 `CompletableFuture<CompletableFuture<U>>`——多套了一层。`thenCompose` 就是来解决这个的。

### 5.4 ⚠️ 异步异常不会自动传播到主线程

```java
public static void main(String[] args) {
    CompletableFuture.supplyAsync(() -> {
        throw new RuntimeException("炸了");
    }).thenAccept(x -> System.out.println(x));

    System.out.println("主线程干完，正常退出");   // ⚠️ 「炸了」这个异常去哪了？
}
```

⚠️ **异常被吞掉了**，程序正常结束，没有任何报错。

原因：异步任务的异常被封装进 future 的结果里，**只有在该 future 上挂了异常处理或调用 `get()`/`join()` 时才会被观察到**。

⭐ **必须显式处理异常**，两种写法：

```java
// 写法一：exceptionally —— 只处理异常
CompletableFuture.supplyAsync(() -> loadUser(id), executor)
        .thenApply(this::toVO)
        .exceptionally(ex -> {
            log.error("加载用户失败", ex);      // ⭐ 必须记录日志
            return null;                       // 给个兜底值
        });

// 写法二：handle —— 成功失败都进，能拿到异常也能拿到值
CompletableFuture.supplyAsync(() -> loadUser(id), executor)
        .handle((user, ex) -> {
            if (ex != null) {
                log.error("加载失败", ex);
                return UserDTO.empty();
            }
            return toVO(user);
        });
```

⚠️ 另外注意 **`join()` vs `get()`**：`join()` 抛的是 `CompletionException`（非受检异常，不需要声明），`get()` 抛的是 `ExecutionException`（受检）。在 `CompletableFuture` 链上推荐用 `join()`。

### 5.5 可运行示例：组合两个调用

```java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class CfDemo {

    public static void main(String[] args) {
        ExecutorService executor = Executors.newFixedThreadPool(4);   // ⭐ 自己的池，不共用 commonPool

        CompletableFuture<String> userF =
                CompletableFuture.supplyAsync(() -> "user-张三", executor);
        CompletableFuture<String> orderF =
                CompletableFuture.supplyAsync(() -> "order-001", executor);

        CompletableFuture<String> merged = userF.thenCombine(orderF, (u, o) -> u + " / " + o);

        merged.orTimeout(2, TimeUnit.SECONDS)                 // ⭐ 2 秒没结果就异常结束
                .exceptionally(ex -> "降级默认值: " + ex.getClass().getSimpleName())
                .thenAccept(System.out::println);

        executor.shutdown();
    }
}
```

## 六、虚拟线程（Java 21+）

### 6.1 动机：平台线程太贵

**平台线程（platform thread）**：Java 里的普通 `Thread`。它与操作系统线程（OS thread）是 **1:1 映射**的——每创建一个 `Thread`，OS 就创建一个真实的内核线程。

代价：

| 代价 | 量级 |
|------|------|
| 栈内存 | 每个线程默认约 1MB 栈（`-Xss` 控制），1000 个线程 ≈ 1GB 虚拟内存 |
| 创建开销 | 内核对象创建 + 栈映射，是系统调用级别的成本 |
| 数量上限 | 受 OS 限制（Linux 通常几千到一万多） |

⭐ **核心矛盾**：IO 密集型服务里，线程 99% 的时间都在**等**（等数据库、等 HTTP），但每个都在占着 1MB 栈和一个 OS 线程名额。**线程成了最贵的等待容器。**

### 6.2 虚拟线程怎么解决

**虚拟线程（virtual thread）**，**Java 21 正式引入（JEP 444）**：

- 由 **JVM 调度**到数量很少的**载体线程（carrier thread）**上运行；
- **载体线程** = 真正对应 OS 线程的「工作线程」，数量通常 = CPU 核数；
- 虚拟线程**很轻**：栈在堆上、按需增长（不是 1MB 固定预留），创建成本约等于创建一个普通对象；
- 可以轻松创建**几十万、几百万**个。

```
   虚拟线程 V1 ─┐
   虚拟线程 V2 ─┼─► 载体线程 C1 (→ OS 线程 T1)   ← 调度由 JVM 负责
   虚拟线程 V3 ─┤
   虚拟线程 V4 ─┴─► 载体线程 C2 (→ OS 线程 T2)
        ↑ 阻塞时，虚拟线程让出载体线程，载体去跑别的虚拟线程
```

### 6.3 ⭐ 本质：阻塞式写法 + 高并发

⭐ **虚拟线程最大的价值是——你的业务代码几乎不用改。**

```java
// ⭐ 和平台线程完全一样的写法：Thread.sleep、JDBC 调用、synchronized，照写不误
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int id : orderIds) {
        executor.submit(() -> {
            try {
                Thread.sleep(500);            // 阻塞等待，虚拟线程会自动让出载体线程
                notifyUser(id);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

对比响应式（Reactor）写法：响应式要把 `Thread.sleep` 改成 `Mono.delay`，把 JDBC 改成 `R2DBC`，整条链路都要改写。**虚拟线程不需要**——它是「**用同步的写法，获得异步的并发能力**」。

### 6.4 ⚠️ 不适合 CPU 密集型任务

虚拟线程不会让计算变快。载体线程数 = CPU 核数，CPU 密集任务的并行度上限就是核数，多开虚拟线程只是徒增调度开销。

| 任务类型 | 虚拟线程是否合适 |
|---------|-----------------|
| IO 密集（等数据库、等 HTTP、等 MQ） | ⭐ **非常合适**，这正是它的主场 |
| CPU 密集（加密、图像处理、大量计算） | ❌ **不合适**，用平台线程池，线程数 = 核数 |

### 6.5 ⭐ pinning（钉住）问题

**pinning（钉住，也译作「固定/钉针」）**：虚拟线程在某些情况下**阻塞时会占住载体线程不放**，导致其他虚拟线程拿不到载体，载体线程被白白占住。

**历史原因**：Java 21 时代，虚拟线程在 `synchronized` 方法或 `synchronized` 块里阻塞时，会**钉住**它的载体线程。

```java
synchronized (lock) {              // ⚠️ Java 21/22/23：在这里阻塞会 pin 住载体线程
    Thread.sleep(1000);            //    整个载体线程被占住，不能跑别的虚拟线程
}
```

⭐ **版本时间线（务必记准）**：

| 版本 | 状态 |
|------|------|
| Java 21 | 虚拟线程正式引入（JEP 444）；**`synchronized` 内阻塞会 pin 住载体线程** |
| Java 22 / 23 | 仍存在 pinning 问题；官方一直在改底层实现 |
| **JDK 24（JEP 491）** | ⭐ **修复**：`synchronized` 内阻塞不再 pin 住载体线程（把锁改成「不阻塞载体」的形态） |
| **Java 25（LTS）** | ⭐ **第一个包含 JEP 491 修复的 LTS 版本**，虚拟线程可放心用于生产 |

⭐ **在旧版本（< 24）上的通用规避手段：用 `ReentrantLock` 代替 `synchronized`**。

```java
private final ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    Thread.sleep(1000);            // ⭐ Java 21~23：用 ReentrantLock 就不会 pin 住载体线程
} finally {
    lock.unlock();
}
```

原因：`ReentrantLock` 是**普通的 Java 实现**，阻塞时走的是「虚拟线程让出载体线程」的正常路径，不会触发 JVM 层面的特殊处理。

> 补充：`ReentrantLock` 的机制详见 [[java/02-中段阶段-专题精讲/并发编程/03-锁机制与原子操作]]。

⚠️ **但 pinning 不只由 `synchronized` 引起**：`Object.wait()`、类初始化（static 初始化块里加锁）、本地方法（native method）里阻塞也会 pin。在这些地方同样要小心。

### 6.6 ⭐ 虚拟线程不要池化

⚠️ **虚拟线程不需要、也不应该被池化。**

- 平台线程池化的理由是「创建线程贵」；虚拟线程创建极便宜，**池化反而毁掉了它的核心优势**；
- 池化会**限制并发数**，把「能创建 100 万个」打回原形；
- 官方明确建议：**每个任务一个虚拟线程**（`newVirtualThreadPerTaskExecutor`）。

```java
// ⭐ 正确：每个任务一个虚拟线程
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    tasks.forEach(executor::submit);
}

// ⚠️ 错误：把虚拟线程塞进固定大小的池
ExecutorService pool = Executors.newFixedThreadPool(200);   // 白白浪费了虚拟线程
```

### 6.7 ⚠️ ThreadLocal 与 Scoped Values

虚拟线程**不适合**用 `ThreadLocal` 在层级调用间传递上下文：

- `ThreadLocal` 的设计前提是「一个线程长期存在，可以反复 set/get」；
- 虚拟线程数量巨大（可能百万个），每个都持有 `ThreadLocal` 值 → **内存占用爆炸**；
- 虚拟线程会**复用载体线程**，载体线程上的 `ThreadLocal` 可能被下一个虚拟线程看到 → **数据串号**（这是最严重的风险）。

⭐ **Java 25 正式引入了 `Scoped Values`（JEP 506）** 作为替代方案：

```java
// Scoped Values 的思路：显式、有作用域、只读的上下文绑定
static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

ScopedValue.where(REQUEST_ID, "req-123").run(() -> {
    System.out.println(REQUEST_ID.get());   // 在作用域内可读
});
// 作用域结束，绑定自动解除
```

⭐ **对比**：`ThreadLocal` 是「**线程私有、可变、无作用域**」；`Scoped Values` 是「**不可变、有明确作用域、自动解绑**」——后者天生适合虚拟线程。

⚠️ 在 Java 25 之前，虚拟线程场景下的常见做法是用**显式参数传递**代替 `ThreadLocal`（虽然啰嗦但安全）。

### 6.8 Structured Concurrency（结构化并发）

**结构化并发**（Structured Concurrency，**Java 19 起为预览特性，到 Java 25 仍是预览状态，尚未正式发布**）是一种编程模型：把一组并发子任务限制在**一个明确的父任务作用域**内——父任务结束前所有子任务必须结束，异常也能正确向上传播。

⭐ **要理解它解决什么问题**：普通线程池里的任务彼此独立，父任务结束（甚至进程退出）时，子任务可能还在跑，异常也可能被吞。结构化并发让「并发任务的父子关系」显式化。

⚠️ **版本提醒**：截至 Java 25，它仍是**预览特性（preview）**，需要 `--enable-preview` 编译运行，**不要用于生产**。

### 6.9 Spring Boot 3.2+ 的虚拟线程开关

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

⭐ 一行配置即可让 Spring Boot 用虚拟线程执行请求处理。**Spring Boot 3.2+**（基于 Spring Framework 6.1）支持这个开关。

开启后的效果：

- Web 容器（Tomcat / Jetty）用虚拟线程处理每个请求；
- `@Async` 默认也走虚拟线程（不再有 `SimpleAsyncTaskExecutor` 无限开线程的问题）；
- ⭐ **但数据库驱动和连接池仍可能是瓶颈**——如果连接池只有 20 个连接，1000 个虚拟线程也只会排队等连接。**虚拟线程解决的是「线程不够」，不是「连接不够」**。

⚠️ 相关配置在 [[java/02-中段阶段-专题精讲/SpringBoot/Web开发与分层实践]] 的「线程池与虚拟线程」小节有概览。

### 6.10 可运行示例：1 万个虚拟线程

```java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class VirtualThreadDemo {

    public static void main(String[] args) throws InterruptedException {
        int taskCount = 10_000;
        AtomicInteger done = new AtomicInteger();
        CountDownLatch latch = new CountDownLatch(taskCount);

        long start = System.nanoTime();

        // ⭐ 每个任务一个虚拟线程，不池化
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < taskCount; i++) {
                executor.submit(() -> {
                    try {
                        Thread.sleep(100);            // 模拟 IO 等待
                        done.incrementAndGet();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    } finally {
                        latch.countDown();
                    }
                });
            }
            latch.await(30, TimeUnit.SECONDS);
        }

        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.println("完成 " + done.get() + " 个任务，耗时 " + ms + " ms");
        // ⭐ 1 万个任务每个睡 100ms：串行要 1000 秒，虚拟线程约 100~200ms 完成
    }
}
```

⚠️ **注意**：这个例子必须在 **Java 21+** 上运行。低版本会报 `UnsupportedClassVersionError` 或找不到 `newVirtualThreadPerTaskExecutor`。

⚠️ 另一点：**每个虚拟线程任务的栈在堆上**。创建 100 万个虚拟线程时，堆要承受得住——别在一个只有 256MB 堆的容器里玩这个。

## 七、选型对比：平台线程 / 虚拟线程 / 响应式

| 维度 | 平台线程池 | 虚拟线程（Java 21+） | 响应式（Reactor） |
|------|-----------|-------------------|------------------|
| 编程模型 | 阻塞式 + 线程池 | ⭐ **阻塞式写法** | ⭐ **非阻塞式回调/流** |
| 代码改动 | 基准 | ⭐ **几乎零改动** | ⚠️ **整条链路重写**（`Mono`/`Flux`、R2DBC） |
| 单机并发上限 | 几千 | ⭐ **几十万~几百万** | 几十万 |
| CPU 密集任务 | ✅ 合适 | ❌ 不合适（载体数=核数） | ❌ 不合适 |
| IO 密集任务 | ✅ 合适（但线程贵） | ⭐ **最合适** | ✅ 合适，但学习/调试成本高 |
| 背压（backpressure） | 靠队列+拒绝策略 | 靠队列+拒绝策略 | ⭐ **天然内建**（`request(n)`） |
| 调试与可读性 | ✅ 直观 | ✅ 直观（栈是同步栈） | ⚠️ 栈断裂、链式难读 |
| 生态成熟度（DB/中间件驱动） | ✅ 最全 | ✅ 主流已适配 | ⚠️ **部分驱动只支持阻塞**（JDBC 无 R2DBC 驱动时） |
| 学习成本 | 低 | 低 | ⚠️ **高** |
| 典型适用 | 通用、CPU 混合型 | ⭐ **IO 密集的请求处理** | 极高并发 + 已有响应式技术栈 |

⭐ **选型建议**：

1. **新项目、IO 密集、团队熟悉阻塞式** → ⭐ **虚拟线程**（Java 21+/25）+ 有界队列 + 明确的限流；
2. **需要严格背压、已有 WebFlux 技术栈、超高并发** → 响应式；
3. **CPU 密集或依赖大量阻塞式三方库** → 平台线程池；
4. **⚠️ 混用要注意**：响应式链路里**不要**调用阻塞 API（比如在 `Mono` 里调 JDBC），会占死事件循环线程。虚拟线程某种程度上缓解了这个问题——这也是「响应式 + 虚拟线程」组合不推荐的深层原因。

## 八、陷阱

1. **⚠️ 用 `HashMap` 承载并发写入**——丢数据，Java 7 时代还可能死循环；用 `ConcurrentHashMap`；
2. **⚠️ 以为 `ConcurrentHashMap` 是「分段锁」**——Java 8 起已废弃 `Segment`，锁的是**桶头节点**；
3. **⚠️ 往 `ConcurrentHashMap` 里放 `null`**——直接抛 `NullPointerException`，用 `containsKey` 判断存在性；
4. **⚠️ 用 CHM 的迭代器做「快照」**——它是弱一致的，看到的不是某一瞬间的全量；要快照自己拷贝；
5. **⚠️ 用 `computeIfAbsent` 的 lambda 做耗时操作或嵌套操作同一个 map**——持锁时间长，可能死锁；
6. **⚠️ 用 `LongAdder` 当精确计数器**——`sum()` 是弱一致的，要精确值用 `AtomicLong`；
7. **⚠️ 在写频繁的场景用 `CopyOnWriteArrayList`**——每次写都复制整个数组，写放大严重；
8. **⚠️ `LinkedBlockingQueue` 不写容量**——默认无界，任务无限堆积 → OOM；
9. **⚠️ `Semaphore.release()` 不写在 `finally` 里**——异常时许可泄漏，信号量耗尽，系统卡死；
10. **⚠️ `CompletableFuture` 不传自定义线程池**——默认用 `ForkJoinPool.commonPool()`，并行度 = CPU 核数 - 1，IO 密集场景「异步了却没变快」；
11. **⚠️ `CompletableFuture` 的异步异常没人处理**——异常被静默吞掉，必须挂 `exceptionally`/`handle` 或在末端 `join()`；
12. **⚠️ 用虚拟线程跑 CPU 密集任务**——载体线程数 = CPU 核数，不会更快，只增加开销；
13. **⚠️ 在 Java 21~23 的 `synchronized` 块里阻塞虚拟线程**——会 **pin 住**载体线程（JEP 491 在 JDK 24 修复，Java 25 才是第一个含修复的 LTS）；
14. **⚠️ 池化虚拟线程**——完全失去了虚拟线程的意义，会把并发数打回固定线程池的水平；
15. **⚠️ 在虚拟线程里用 `ThreadLocal` 传上下文**——载体线程复用会导致数据串号，虚拟线程数量大时还会撑爆堆；用 `Scoped Values`（Java 25 正式）或显式传参；
16. **⚠️ 以为开了虚拟线程就不会 OOM**——数据库连接池、MQ 客户端连接数依然有限，瓶颈会转移到那里；
17. **⚠️ 把 `Structured Concurrency` 当成已正式特性**——截至 Java 25 它仍是**预览特性**。

## 小结

- **`ConcurrentHashMap`（Java 8+）**：桶空用 `CAS`、桶非空 `synchronized` 锁**桶头节点**；⚠️ **Java 8 起已无分段锁**；**不允许 null**；弱一致迭代器；`size()` 是估算值
- **计数**：`LongAdder` 多 cell 分散 → 高并发写更好，但 `sum()` 是弱一致；要精确用 `AtomicLong`
- **`CopyOnWriteArrayList/Set`**：写时复制、无锁读、快照迭代器 → **只适合读远多于写且元素不多**
- **`BlockingQueue`**：家族成员 `ArrayBlockingQueue`（有界单锁）、`LinkedBlockingQueue`（双锁，⚠️ 默认无界）、`SynchronousQueue`（零容量直传）、`PriorityBlockingQueue`（无界）、`DelayQueue`（延迟任务）、`LinkedTransferQueue`
- **同步工具**：`CountDownLatch`（一次性）、`CyclicBarrier`（可重复）、`Semaphore`（限流，`release` 必须在 `finally`）、`Phaser`（可变阶段）
- **`CompletableFuture`**：⚠️ **默认用 `ForkJoinPool.commonPool()`，必须传自己的线程池**；`thenApply` vs `thenCompose`；`allOf`/`anyOf`/`orTimeout`/`completeOnTimeout`；⚠️ **异步异常不会自动传播**
- **虚拟线程（Java 21+）**：JVM 调度到少量**载体线程**上；⭐ **阻塞式写法 + 高并发**；❌ 不适合 CPU 密集；**不池化**；`Executors.newVirtualThreadPerTaskExecutor()`
- ⚠️ **pinning（钉住）**：Java 21~23 的 `synchronized` 内阻塞会占住载体线程；⭐ **JEP 491 在 JDK 24 修复，Java 25 是第一个含该修复的 LTS**；旧版本用 `ReentrantLock` 规避
- ⚠️ 虚拟线程里别用 `ThreadLocal` → 用 **`Scoped Values`（Java 25 正式）**；**`Structured Concurrency` 截至 Java 25 仍是预览特性**
- **Spring Boot 3.2+**：`spring.threads.virtual.enabled=true`
