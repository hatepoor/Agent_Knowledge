## 一、类的生命周期：7 个阶段

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
└──────────── 连接（Linking）────────────┘
```

### 前 5 个阶段各做什么

| 阶段 | 做什么 | 关键点 |
|------|--------|--------|
| **加载（Loading）** | 读 `.class` 二进制流 → 方法区生成类结构 → 堆中创建 `Class` 对象 | 来源可以是文件、jar、网络、动态生成 |
| **验证（Verification）** | 校验字节码合法性（魔数、版本、语义） | 防止恶意字节码破坏 JVM |
| **准备（Preparation）** | 为**静态变量**分配内存并设**零值** | ⚠️ 此时 `static int a = 10` 的 `a` 是 **0**，不是 10 |
| **解析（Resolution）** | 符号引用 → 直接引用 | 常量池里的符号替换成内存地址 |
| **初始化（Initialization）** | 执行 `<clinit>()`：静态变量赋真值 + 静态代码块 | ⚠️ 到这一步 `a` 才变成 10 |

⭐ **面试高频对比**：

```java
public class Demo {
    static int a = 10;
    static { a = 20; }
}
```

- **准备阶段**：`a = 0`（零值）；
- **初始化阶段**：先 `a = 10`，再执行静态块 `a = 20` → **最终 20**。

### 类初始化的 6 个触发时机（面试常问）

1. `new` 对象、访问静态字段、调用静态方法；
2. 反射调用（`Class.forName`）；
3. 初始化子类时，先初始化父类；
4. 虚拟机启动时的主类（含 `main`）；
5. `MethodHandle` 解析结果对应的类；
6. 接口的默认方法被实现类调用时（接口本身初始化）。

⚠️ **不会触发初始化**：通过子类访问父类的静态字段（只初始化父类）、定义数组（`User[] arr = new User[10]` 不初始化 `User`）、访问 `static final` 常量（编译期已内联到常量池）。

## 二、三层类加载器

| 加载器 | 加载什么 | 实现语言 |
|--------|---------|---------|
| **Bootstrap ClassLoader** | `java.base` 等核心类（`String`、`Object`） | C++（JVM 内部） |
| **Platform ClassLoader**（JDK 9+，旧名 Extension） | JDK 扩展模块（`java.sql`、`javax.xml` 等） | Java |
| **Application ClassLoader** | 应用的 classpath（你的代码 + 依赖 jar） | Java |

⚠️ **JDK 9 的模块化变化**：原来 `rt.jar` 拆成了多个模块（`java.base`、`java.sql`…），Extension ClassLoader 改名为 **Platform ClassLoader**——老资料里的「扩展类加载器」是 JDK 8 的说法。

### 自定义类加载器

继承 `ClassLoader`，重写 `findClass()`：

```java
public class MyLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadBytesFromAnywhere(name);   // 从网络/加密文件读
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

用途：热部署、加密类、从数据库/网络加载、插件隔离。

## 三、双亲委派模型（核心）

### 调用链

```
Application ClassLoader.loadClass("com.example.User")
   ↓ 自己不加载，先问父加载器
Platform ClassLoader.loadClass("com.example.User")
   ↓ 继续往上问
Bootstrap ClassLoader.loadClass("com.example.User")
   ↓ 找不到（它只认核心类）
   回溯：Platform 找不到 → Application 自己 findClass()
   ↓
加载成功
```

### 代码层面的实现

```java
protected Class<?> loadClass(String name, boolean resolve) {
    // ① 已加载过？直接返回
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        // ② 先委托父加载器
        if (parent != null) {
            c = parent.loadClass(name, false);
        } else {
            c = findBootstrapClassOrNull(name);
        }
        // ③ 父加载器都找不到，才自己加载
        if (c == null) {
            c = findClass(name);
        }
    }
    return c;
}
```

⭐ **记住三个动作的顺序：查缓存 → 委派父级 → 自己加载。**

### 为什么要有双亲委派（两个理由）

1. **安全**：防止核心类被篡改——你写一个 `java.lang.String`，永远会被 Bootstrap 抢先加载，你的版本根本没有机会生效；
2. **避免重复加载**：同一个类在 JVM 中只加载一次（同一个类加载器下），保证类的一致性。

⚠️ **判断「两个类是否相同」的标准**：**类加载器 + 全限定类名**都相同才算同一个类。所以「同一个类加载两次」会导致 `ClassCastException`——常见于插件/热部署场景。

## 四、三个打破双亲委派的真实场景

### 场景 1：Tomcat —— Web 应用互相隔离

Tomcat 里多个 webapp 可能依赖**不同版本**的同一个库（如 Spring 4 和 Spring 6）。按双亲委派，父加载器会先加载，导致所有应用共用一份 → 版本冲突。

**Tomcat 的解法**：自定义 `WebappClassLoader`，**先自己加载**（webapp 优先），加载不到再委派父级；同时每个 webapp 一个加载器，实现隔离。

### 场景 2：SPI —— 父加载器要用子加载器的类

问题：`java.sql.DriverManager`（Bootstrap 加载）要加载 MySQL 的 `com.mysql.cj.jdbc.Driver`（在应用 classpath，只有 Application 加载器认识）——父加载器**看不到**子加载器的类。

**解法：线程上下文类加载器（TCCL）**

```java
Thread.currentThread().setContextClassLoader(appLoader);
// DriverManager 内部：
ServiceLoader.load(Driver.class);   // 用 TCCL 去加载实现类
```

⭐ 这是「双亲委派的向下委派」——JDBC、JNDI、JAXP 都在用。

### 场景 3：OSGi / 热部署

OSGi 用网状依赖模型：每个 Bundle 有自己的类加载器，按依赖关系加载——比双亲委派灵活得多。热部署工具（Spring Boot DevTools、JRebel）同理会为每个版本创建新加载器，旧的被 GC 回收。

## 五、两个高频异常的区别

| 异常 | 时机 | 含义 |
|------|------|------|
| `ClassNotFoundException` | 加载阶段 | 显式加载时（`Class.forName`、`loadClass`）找不到 class 文件 |
| `NoClassDefFoundError` | 链接/初始化阶段 | class 之前加载过，但初始化失败（静态块抛异常）或运行时找不到 |

⚠️ **`NoClassDefFoundError` 经常是「静态初始化块抛了异常」**——真正的根因被隐藏在 `ExceptionInInitializerError` 里，去日志前面找。

## 六、陷阱

1. **⚠️ 以为「准备阶段就赋了初值」**——准备阶段只给零值，`static int a = 10` 在初始化阶段才变 10；
2. **⚠️ 用「类名相同」判断是同一个类**——必须「类加载器 + 类名」都相同；
3. **⚠️ 认为双亲委派是强制规范**——它是**推荐模型**，Tomcat/SPI/OSGi 都打破了它；
4. **⚠️ 在静态代码块里做耗时/可能失败的操作**——失败会变成 `NoClassDefFoundError`，且后续无法恢复；
5. **⚠️ JDK 9 后还按「扩展类加载器 / rt.jar」理解**——已改为 Platform ClassLoader + 模块化。

## 小结

- 生命周期：**加载 → 验证 → 准备 → 解析 → 初始化**（前五步是类加载）
- ⚠️ 准备阶段赋**零值**，初始化阶段（`<clinit>`）赋**真值**
- 三层加载器：Bootstrap（核心）→ Platform（扩展）→ Application（classpath）
- 双亲委派：**查缓存 → 委派父级 → 自己加载**；目的是安全 + 唯一
- 打破场景：Tomcat（应用隔离）、SPI（TCCL 向下委派）、OSGi（网状依赖）
- 类的唯一性 = **类加载器 + 全限定类名**
