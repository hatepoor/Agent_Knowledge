## 一、运行时数据区：5 个部分

JVM 在执行 Java 程序时，把内存划分成 5 块：

```
┌─────────────────────── JVM 运行时数据区 ───────────────────────┐
│                                                                │
│  【线程共享】                                                   │
│  ┌──────────────────────────────┐  ┌─────────────────────┐    │
│  │        堆（Heap）             │  │  方法区（元空间）     │    │
│  │   所有 new 出来的对象          │  │  类信息·静态变量·常量 │    │
│  │   GC 的主战场                  │  │   JDK 8+ 用元空间    │    │
│  └──────────────────────────────┘  └─────────────────────┘    │
│                                                                │
│  【线程私有】—— 每个线程一份，互不共享                          │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐          │
│  │  虚拟机栈      │ │ 本地方法栈    │ │ 程序计数器 PC │          │
│  │  方法调用栈帧  │ │ native 方法  │ │ 执行到哪条指令 │          │
│  └──────────────┘ └──────────────┘ └──────────────┘          │
└────────────────────────────────────────────────────────────────┘
```

| 区域 | 存什么 | 共享/私有 | 会抛什么错 |
|------|--------|----------|-----------|
| **堆** | 所有对象实例、数组 | 共享 | `OutOfMemoryError: Java heap space` |
| **方法区/元空间** | 类结构、静态变量、常量池、JIT 代码 | 共享 | `OutOfMemoryError: Metaspace` |
| **虚拟机栈** | 栈帧（局部变量表、操作数栈、动态链接、返回地址） | 私有 | `StackOverflowError` / OOM |
| **本地方法栈** | native 方法调用 | 私有 | 同上 |
| **程序计数器** | 当前字节码行号 | 私有 | 唯一不会 OOM 的区域 |

⭐ **面试标准问法**：「哪些区域线程共享？」→ 堆 + 方法区；其余私有。**唯一的反问陷阱是「程序计数器不会 OOM」**。

### 方法区的演进（重要版本变化）

| 版本 | 实现 | 位置 |
|------|------|------|
| JDK 7 及以前 | 永久代（PermGen） | JVM 堆内 |
| **JDK 8+** | **元空间（Metaspace）** | ⭐ **本地内存**（不在堆里） |

⚠️ 所以 JDK 8+ 的 `OutOfMemoryError: Metaspace` **不会**被 `-Xmx` 限制，要用 `-XX:MaxMetaspaceSize` 控制。

## 二、对象的一生：从 `new` 到可用

```java
User u = new User("张三", 25);
```

JVM 内部五步：

### ① 类加载检查

`new` 指令先检查 `User` 类是否已加载。没加载 → 先触发类加载（见 [[java/02-中段阶段-专题精讲/JVM/类加载机制]]）。

### ② 分配内存

对象大小在类加载时就确定了。分配方式取决于堆是否规整：

| 方式 | 适用 | 原理 |
|------|------|------|
| **指针碰撞（Bump the Pointer）** | 堆内存规整（无碎片） | 一个指针往空闲方向移动对象大小的距离 |
| **空闲列表（Free List）** | 堆内存有碎片 | 维护可用内存块列表，找一块够大的 |

⚠️ **并发分配的两种解法**：

1. **TLAB（Thread Local Allocation Buffer）** —— 每个线程在 Eden 区预分一小块私有空间，分配不用加锁。⭐ **默认开启**；
2. **CAS 重试**——TLAB 用完时在 Eden 上做原子分配。

### ③ 初始化零值

内存分配后，JVM 把这块内存**全部置零**——所以对象的字段即使你不赋值也有默认值（`int` → 0、引用 → null）。⭐ 这就是「对象字段**一定**有默认值」的原因。

### ④ 设置对象头

写入 Mark Word（哈希码、GC 年龄、锁状态）和类型指针（指向方法区的 Class 对象）。

### ⑤ 执行构造器 `<init>`

执行 `User(String, int)` 构造器，按你的代码给字段赋值。**到这一步对象才算真正可用**。

## 三、对象在内存里长什么样

```
┌──────────────────────────────────────────────┐
│ 对象头（Object Header）                       │
│  ① Mark Word（8 字节 / 64 位）               │
│     哈希码 · GC 年龄 · 锁状态 · 偏向线程 ID   │
│  ② 类型指针（Klass Pointer，4 或 8 字节）     │
│     指向方法区里的类元数据                     │
├──────────────────────────────────────────────┤
│ 实例数据（Instance Data）                     │
│   父类字段 + 本类字段（按类型宽度排列）        │
├──────────────────────────────────────────────┤
│ 对齐填充（Padding）                           │
│   补齐到 8 字节的整数倍                       │
└──────────────────────────────────────────────┘
```

### Mark Word 里有什么（重点）

64 位 JVM 上 8 字节，**内容随锁状态复用**：

| 锁状态 | 存什么 |
|--------|--------|
| 无锁 | hashCode（31 位）+ GC 年龄（4 位，最大 15）+ 偏向标志 |
| 偏向锁 | 偏向线程 ID + epoch + 偏向标志 |
| 轻量级锁 | 指向栈中锁记录的指针 |
| 重量级锁 | 指向 Monitor 对象的指针 |

⚠️ **GC 年龄最大 15**——因为只有 4 位。这就是「对象在 Survivor 里熬过 15 次 GC 必进老年代」的物理原因（`-XX:MaxTenuringThreshold` 默认 15）。

### 指针压缩（Compressed Oops）

- 64 位 JVM 上引用占 8 字节，**默认开启指针压缩后占 4 字节**（堆 ≤ 32GB 时有效）；
- 好处：对象更小、缓存更友好，堆 30GB 可能比 32GB 性能更好；
- ⚠️ 堆超过 32GB 后指针压缩失效，对象变大——**这不是「堆越大越好」的原因之一**。

## 四、JIT：为什么 Java 跑久了变快

```
字节码 → 解释器逐条执行（启动快，执行慢）
              ↓ 发现某方法被反复调用（热点代码）
         JIT 编译器（C1/C2）编译成机器码 → 缓存
              ↓ 后续调用直接执行机器码（执行快）
```

| 编译器 | 特点 | 适用 |
|--------|------|------|
| **C1（Client）** | 编译快、优化浅 | 启动阶段、短生命周期代码 |
| **C2（Server）** | 编译慢、优化深（内联、逃逸分析、循环展开） | 长期运行的热点代码 |

**热点探测**：方法调用计数器 + 回边计数器，超过阈值（`-XX:CompileThreshold`）就触发编译。

⭐ 这就是「Java 启动慢、跑久了接近 C」的机制——也是微服务冷启动问题的根源。

### 顺带一个优化：逃逸分析

JIT 会分析对象是否「逃出」方法：

- 不逃逸 → **栈上分配**（不占堆、不用 GC）；
- 不逃逸且字段可拆 → **标量替换**（把对象拆成几个局部变量）；
- 被多线程访问但无竞争 → **锁消除**。

⚠️ 这些是 JIT 自动做的，不能手动控制，但解释了「为什么有时候对象没那么占内存」。

## 五、每种 OOM 对应哪个区域

| 错误信息 | 区域 | 调什么参数 |
|---------|------|-----------|
| `Java heap space` | 堆 | `-Xmx`（或先查内存泄漏） |
| `Metaspace` | 元空间（本地内存） | `-XX:MaxMetaspaceSize` |
| `unable to create new native thread` | 线程栈（本地内存） | 减线程数 / 调 `-Xss` |
| `Direct buffer memory` | 直接内存（NIO） | `-XX:MaxDirectMemorySize` |
| `GC overhead limit exceeded` | 堆（GC 太频繁但回收不了多少） | 查泄漏 + 调堆 |
| `StackOverflowError`（不是 OOM） | 虚拟机栈 | 查无限递归 / `-Xss` |

⭐ **看到 OOM 第一件事是看错误信息**——不同后缀对应完全不同的排查方向。

## 六、陷阱

1. **⚠️ 以为「方法区就是永久代」**——JDK 8 起是元空间，在本地内存，`-Xmx` 管不到；
2. **⚠️ 以为「对象一 new 就在堆上」**——逃逸分析可能栈上分配；
3. **⚠️ 堆越大越好**——超过 32GB 指针压缩失效，对象反而变大；
4. **⚠️ 只调 `-Xmx` 不看 GC 日志**——不知道对象去了哪、GC 频率如何，调参就是蒙；
5. **⚠️ `-Xss` 调太大**——每个线程的栈独立占本地内存，线程多时会 native OOM。

## 小结

- 运行时数据区 5 块：**堆 + 方法区（元空间）共享**；栈、本地方法栈、PC 私有
- 对象创建 5 步：**类加载检查 → 分配（TLAB）→ 零值初始化 → 对象头 → 构造器**
- 对象布局三段：**对象头（Mark Word + 类型指针）+ 实例数据 + 对齐填充**
- GC 年龄最大 15（4 位）——决定晋升阈值
- JIT + 逃逸分析让 Java「跑久了变快」
- **OOM 的后缀决定排查方向**
