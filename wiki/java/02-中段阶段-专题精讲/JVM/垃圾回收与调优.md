# 垃圾回收与调优

> **什么时候该读**：准备面试（GC 是必问项）；或者线上服务出现 GC 频繁、响应变慢、Full GC 停顿。

## 学习目标

读完本篇，你应当能够：

1. 说清「怎么判断对象死了」与 GC Roots 有哪些
2. 解释分代模型与对象晋升规则
3. 说出 CMS 为什么被废弃、G1 为什么成为默认
4. 用 GC 日志判断问题类型，并按流程调参

## 一、GC 要解决的两个问题

1. **哪些对象该回收？**（怎么判断「死」）
2. **怎么回收？**（算法与回收器）

## 二、怎么判断对象死了

### 两种方案

| 方案 | 原理 | 谁在用 | 问题 |
|------|------|--------|------|
| **引用计数** | 每个对象记录被引用次数，为 0 即回收 | Python（CPython） | ⚠️ 无法处理循环引用 |
| **可达性分析** | 从 GC Roots 出发遍历，走不到的对象即回收 | ⭐ **Java** | 需要遍历，但能处理循环引用 |

### GC Roots 有哪些（必须记住）

1. 虚拟机栈中引用的对象（方法里的局部变量）；
2. 方法区中**静态变量**引用的对象；
3. 方法区中**常量**引用的对象（如字符串常量池）；
4. 本地方法栈中 JNI 引用的对象；
5. JVM 内部引用（基本类型的 Class 对象、常驻异常对象、系统类加载器）；
6. 被 `synchronized` 持有的对象。

⭐ **判断口诀**：**「栈上的局部变量、静态变量、常量」**——这三类能直接够得着的对象都算活的。

### 四种引用（面试常问）

| 引用类型 | 什么时候回收 | 典型用途 |
|---------|-------------|---------|
| **强引用**（`new`） | 永不主动回收，除非不可达 | 普通对象 |
| **软引用**（`SoftReference`） | 内存不足时才回收 | 本地缓存（图片缓存） |
| **弱引用**（`WeakReference`） | 下次 GC 必回收 | `ThreadLocalMap` 的 key、`WeakHashMap` |
| **虚引用**（`PhantomReference`） | 随时可回收，回收时收到通知 | 管理直接内存（NIO 的 Cleaner） |

### 对象「死」还要经过两次标记

1. 可达性分析发现不可达 → **第一次标记**；
2. 检查是否重写了 `finalize()` 且未执行过 → 有则放入 F-Queue 等待执行；
3. `finalize()` 里若重新引用自己（`this` 赋给某静态变量）→ **复活**；
4. 否则第二次标记 → 真正回收。

⚠️ `finalize()` 已废弃（JDK 9 起 deprecated，18 起标记为废弃待移除）——**生产代码永远不要依赖它**。

## 三、三种回收算法

| 算法 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **标记-清除** | 标记存活 → 清除未标记 | 简单 | ⚠️ **内存碎片** |
| **复制** | 存活对象复制到另一半空间 | 无碎片、快 | ⚠️ 浪费一半空间 |
| **标记-整理** | 标记存活 → 向一端移动 | 无碎片 | ⚠️ 移动成本高 |

⭐ **分代假说**：绝大多数对象「朝生夕死」——所以不同区域用不同算法：

- **新生代**（对象死亡率高）→ **复制算法**（只需复制少量存活对象）；
- **老年代**（对象存活率高）→ **标记-清除 / 标记-整理**。

## 四、分代模型

```
堆
├── 新生代（Young，默认占堆 1/3）
│   ├── Eden（8/10）          ← 新对象在这
│   ├── Survivor 0（1/10）    ← 存活对象轮换
│   └── Survivor 1（1/10）
└── 老年代（Old，默认占堆 2/3） ← 长期存活对象
```

### 对象晋升规则

| 规则 | 说明 |
|------|------|
| **熬过 N 次 Young GC** | GC 年龄达到阈值（默认 15，`-XX:MaxTenuringThreshold`）→ 进老年代 |
| **动态年龄判定** | Survivor 中**同龄对象总和 > 一半** → 直接晋升（不一定等到 15） |
| **大对象直接进老年代** | `-XX:PretenureSizeThreshold`（⚠️ 只对 Serial/ParNew 有效，G1 不按此规则） |
| **Survivor 放不下** | 直接晋升老年代 |

### 一次 Young GC 的过程

```
Eden 满 → 触发 Young GC（Minor GC）
  ↓
标记 Eden + 当前 Survivor 中的存活对象
  ↓
复制到另一个 Survivor（年龄 +1）
  ↓
清空 Eden + 原 Survivor
  ↓
年龄达阈值 → 复制到老年代
```

⚠️ **Young GC 会 STW**（Stop-The-World）——暂停所有业务线程。但新生代小、存活对象少，停顿通常只有几毫秒到几十毫秒。

### Full GC 什么时候触发

1. 老年代空间不足；
2. 元空间不足；
3. 调用 `System.gc()`（⚠️ 只是建议，可通过 `-XX:+DisableExplicitGC` 禁用）；
4. 晋升时老年代放不下（**晋升失败**）；
5. CMS 的并发模式失败（Concurrent Mode Failure）。

⭐ **Full GC 是性能事故**——通常几百毫秒到几秒，必须重点监控。

## 五、回收器演进

| 回收器 | 分代 | 算法 | 特点 | 状态 |
|--------|------|------|------|------|
| **Serial** | 新生代 | 复制 | 单线程，最简单 | 客户端/小内存 |
| **ParNew** | 新生代 | 复制 | Serial 的多线程版 | 曾与 CMS 搭配 |
| **Parallel Scavenge** | 新生代 | 复制 | 吞吐量优先 | JDK 8 默认新生代 |
| **CMS** | 老年代 | 标记-清除 | 并发回收，低停顿 | ⚠️ **JDK 14 移除** |
| ⭐ **G1** | 整堆 | 复制 + 标记-整理 | Region 化，可预测停顿 | ⭐ **JDK 9+ 默认** |
| **ZGC** | 整堆 | 染色指针 + 读屏障 | 亚毫秒停顿 | JDK 21+ 分代 ZGC |
| **Shenandoah** | 整堆 | 转发指针 | 低停顿（非 Oracle 主力） | OpenJDK 发行版提供 |

### CMS 为什么被废弃

1. **标记-清除产生碎片** → 碎片多到放不下对象时触发 **Concurrent Mode Failure** → 退化成 Serial Old 单线程 Full GC（停顿数秒）；
2. 并发阶段占用 CPU（默认占 25% 线程）；
3. 浮动垃圾需要预留空间（`-XX:CMSInitiatingOccupancyFraction` 一般设 70% 左右）。

### G1 为什么成为默认（重点）

**核心创新：把堆切成等大的 Region（1–32MB），不再物理分代。**

```
堆 = 多个 Region（每个 Region 逻辑上可能是 Eden / Survivor / Old / Humongous）
     ↓
Young GC：回收所有 Eden Region（复制存活对象到 Survivor）
     ↓
Mixed GC：按「回收收益」排序，优先回收垃圾最多的 Region（Garbage First 的由来）
```

四个关键点：

1. **可预测停顿**：`-XX:MaxGCPauseMillis=200`（默认 200ms）——G1 会选「在目标时间内能回收多少 Region」，而不是一次扫完整个老年代；
2. **无碎片**：Region 之间是复制算法，整体效果接近标记-整理；
3. **Humongous 区**：大于 Region 一半的大对象单独存放；
4. **SATB（Snapshot-At-The-Beginning）**：并发标记时用写前屏障记录引用变化，保证标记正确性。

### ZGC（了解即可）

- **染色指针**：把 GC 信息存在指针的 spare bits 里（64 位指针只用 42 位寻址）；
- **读屏障**：读对象时检查指针状态，需要时修正；
- **停顿 < 1ms**（与堆大小无关）；
- JDK 21 起支持**分代 ZGC**（`-XX:+ZGenerational`），JDK 23+ 分代成为默认模式。

## 六、常用参数与 GC 日志

### 参数速查

```bash
-Xms4g -Xmx4g                     # 堆初始/最大（⚠️ 生产设为相等，避免动态扩容抖动）
-Xmn1g                            # 新生代大小（G1 不建议手动设）
-XX:MetaspaceSize=256m            # 元空间初始阈值
-XX:MaxMetaspaceSize=512m         # 元空间上限（防 Metaspace OOM）
-XX:+UseG1GC                      # 指定 G1（JDK 9+ 默认）
-XX:MaxGCPauseMillis=200          # G1 目标停顿
-XX:MaxTenuringThreshold=15       # 晋升年龄
-Xlog:gc*:file=gc.log:time,uptime,level,tags   # JDK 9+ 统一日志
```

### GC 日志怎么读（JDK 9+）

```text
[2.345s][info][gc] GC(12) Pause Young (Normal) (G1 Evacuation Pause)
  2048M->512M(4096M) 12.345ms
```

| 字段 | 含义 |
|------|------|
| `Pause Young` | Young GC |
| `2048M->512M` | GC 前占用 → GC 后占用 |
| `(4096M)` | 堆总大小 |
| `12.345ms` | ⭐ **本次停顿时间**——核心指标 |

⭐ **判断标准**：Young GC 单次 < 50ms、频率 < 每秒 1 次；出现 `Pause Full` 就要立刻排查。

## 七、调优方法论（四步）

```
① 看现象：是延迟高、吞吐低，还是 OOM？
② 取数据：GC 日志（-Xlog:gc*）+ jstat -gcutil <pid> 1000
③ 定原因：
     频繁 Young GC      → 新生代太小 / 对象创建太快（先查代码）
     Full GC 频繁       → 老年代有泄漏 / 大对象太多 / 晋升过快
     单次停顿超目标      → 换回收器（G1/ZGC）或调 MaxGCPauseMillis
④ 改一个参数 → 压测验证 → 再改下一个（一次只变一个变量）
```

⚠️ **顺序不能反**：先看是不是**代码问题**（内存泄漏、无界缓存、一次查 100 万行），再谈调参。**大多数「GC 问题」的根因是代码里有个不该活那么久的对象。**

## 八、陷阱

1. **⚠️ 一上来就调 `-Xmx`**——不知道是泄漏还是不够用，调大只是延后崩溃；
2. **⚠️ 认为 Young GC 停顿是问题**——Young GC 本来就是高频短停顿，要看的是 Full GC 和单次停顿是否超目标；
3. **⚠️ 用 `System.gc()` 手动触发**——生产环境应禁用（`-XX:+DisableExplicitGC`）；
4. **⚠️ 依赖 `finalize()` 释放资源**——已废弃，用 try-with-resources；
5. **⚠️ 只看堆不看元空间**——动态生成类（CGLIB、反射、热部署）会让元空间持续增长。

## 小结

- 判活：**可达性分析 + GC Roots**（栈引用、静态变量、常量）；四种引用对应四种回收时机
- 三种算法：标记-清除（碎片）、复制（新生代）、标记-整理（老年代）
- 分代模型：Eden + 2×Survivor + Old；晋升靠**年龄（最大 15）或动态年龄判定**
- 回收器：**G1 是当前默认**（Region 化 + 可预测停顿）；CMS 因碎片与并发失败被移除；ZGC 追求亚毫秒
- 调优四步：**看现象 → 取日志 → 定原因 → 一次只改一个参数**
- ⚠️ 大多数 GC 问题根因在代码（泄漏/大对象），不在参数
