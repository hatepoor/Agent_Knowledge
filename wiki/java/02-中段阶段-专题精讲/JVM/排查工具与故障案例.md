# 排查工具与故障案例

> **什么时候该读**：线上服务出现 OOM、CPU 100%、接口变慢；或者面试被问「你怎么排查 Java 服务问题」。

## 学习目标

读完本篇，你应当能够：

1. 用 JDK 自带四件套（`jps`/`jstat`/`jmap`/`jstack`）拿到关键数据
2. 按「四类故障」的固定路径定位根因
3. 说清 Arthas 三个最常用命令的用途
4. 独立完成一次「CPU 100%」与「堆 OOM」的排查

## 一、JDK 自带四件套

| 工具 | 一句话 | 常用命令 |
|------|--------|---------|
| **`jps`** | 列出 Java 进程 | `jps -l` |
| **`jstat`** | 看 GC 统计（实时） | `jstat -gcutil <pid> 1000` |
| **`jmap`** | 看堆对象统计 / 导出堆快照 | `jmap -histo <pid> \| head -20`；`jmap -dump:live,format=b,file=a.hprof <pid>` |
| **`jstack`** | 导出线程栈 | `jstack <pid> > t.txt` |

### `jstat -gcutil` 读法（最常用）

```bash
jstat -gcutil 12345 1000
```

```text
  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00  45.23  78.11  62.30  95.12  93.40   1234    12.345    3     1.203   13.548
```

| 列 | 含义 | 关注点 |
|----|------|--------|
| `E` | Eden 使用率 | 增长快 = 对象创建多 |
| `O` | 老年代使用率 | ⭐ **持续上涨不回落 = 内存泄漏信号** |
| `M` | 元空间使用率 | 持续上涨 = 动态生成类 |
| `YGC/YGCT` | Young GC 次数/总耗时 | 频率 = YGC 次数 ÷ 运行秒数 |
| `FGC/FGCT` | **Full GC 次数/总耗时** | ⭐ **> 0 就要关注，频繁就是事故** |

### `jmap -histo`：谁占了内存

```bash
jmap -histo:live 12345 | head -20
```

```text
 #instances    bytes    class name
   1:  8234512  987400000  [B          ← byte[] 占 900MB，第一嫌疑
   2:  2102331  336373000  java.lang.String
   3:   981223  156995680  java.util.HashMap$Node
```

⭐ **看第一列 instances 与第二列 bytes**——`[B`（byte 数组）、`String`、`HashMap$Node` 通常是内存大头。`byte[]` 异常多时，八成是在「读大文件/大响应/图片」后没释放。

### `jstack`：线程在干什么

```bash
jstack 12345 | grep -A 20 "java.lang.Thread.State: BLOCKED"
```

常见线程状态的含义：

| 状态 | 含义 | 排查方向 |
|------|------|---------|
| `RUNNABLE` | 运行中 / 等 IO（⚠️ 等待网络也显示 RUNNABLE） | CPU 高的线程看这里 |
| `BLOCKED` | 等锁 | 找持锁线程（`locked <0x...>`） |
| `WAITING` | 无限等待（`wait()`、`park()`） | 线程池空闲、等通知 |
| `TIMED_WAITING` | 限时等待（`sleep`、`await(timeout)`） | 通常是正常的池内空闲 |

⚠️ **死锁检测**：`jstack` 输出末尾会直接给出 `Found one Java-level deadlock` 段，不用自己拼图。

## 二、Arthas（线上排查利器）

阿里开源，**无需重启、不改代码**，attach 到运行中的 JVM：

```bash
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar        # 选择要诊断的进程
```

| 命令 | 用途 | 场景 |
|------|------|------|
| `dashboard` | 实时面板：线程、内存、GC | 一眼看全局 |
| `thread -n 3` | CPU 最高的 3 个线程 + 堆栈 | ⭐ CPU 100% 首选 |
| `thread <id> -b` | 指定线程的栈，并打印阻塞源头 | 找锁持有者 |
| `watch 类 方法 "{params, returnObj}"` | 观察方法入参/返回值 | 不打日志也能看数据 |
| `trace 类 方法` | 方法内部调用耗时分布 | 定位慢在哪一层 |
| `heapdump` | 导出堆快照 | 等同于 `jmap -dump` |
| `jad 类` | 反编译已加载的类 | 确认线上跑的是哪个版本 |

## 三、四类故障的固定排查路径

### 故障 1：堆 OOM（`Java heap space`）

**现象**：日志出现 `java.lang.OutOfMemoryError: Java heap space`，服务假死或重启。

**排查五步**：

1. **确认现场**：`jps` 找进程；`jstat -gcutil` 看老年代是否接近 100%；
2. **导出快照**（⚠️ 生产加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump`，让 OOM 时自动 dump）；
3. **分析快照**：用 Eclipse MAT 或 `jvisualvm` 打开 `.hprof`，看 **Dominator Tree**（谁占了最大内存）；
4. **定位代码**：找「数量异常多」的对象，反查是谁创建、谁持有引用（MAT 的 Path to GC Roots）；
5. **修复**：无界缓存加容量上限、分页查询、及时关闭流。

**真实案例（脱敏）**：一个导出接口把 30 万行数据一次性查进 `List` 再序列化 JSON。

| 项 | 数据 |
|----|------|
| 现象 | 每天 10 点左右 OOM，服务重启 |
| 证据 | `jmap -histo` 中 `[B` 占 1.2GB、`ArrayList` 数量 30 万+ |
| 根因 | 一次性加载全量数据 + 序列化成大字符串 |
| 修复 | 改为分页查询 + 流式写出（`StreamingResponseBody`），单次内存 < 50MB |
| 效果 | OOM 消失，接口内存峰值从 1.2GB 降到 50MB |

### 故障 2：元空间 OOM（`Metaspace`）

**现象**：`OutOfMemoryError: Metaspace`，`jstat` 的 `M` 列持续 95%+。

**常见原因**：

1. **动态生成类**：CGLIB 代理（大量 `@Configuration` 类）、反射、Groovy 脚本；
2. **热部署/重复加载**：每次重新加载都生成新类，旧类无法卸载；
3. **`-XX:MaxMetaspaceSize` 设得太小**。

**排查**：`jmap -clstats <pid>` 看类加载器数量；`jcmd <pid> GC.class_stats` 看类分布。若类加载器数量持续增长 → 有泄漏（如自定义 ClassLoader 被静态引用）。

### 故障 3：CPU 100%

**排查三步**（固定套路）：

```bash
# ① 找最耗 CPU 的 Java 进程
top -c | grep java

# ② 找该进程内最耗 CPU 的线程（⚠️ 转成 16 进制）
top -Hp <pid>
printf "%x\n" <线程id>

# ③ 用 jstack 找该线程在干什么
jstack <pid> | grep -A 30 "nid=0x<16进制id>"
```

常见根因：

| 现象 | 根因 |
|------|------|
| 栈顶是 `GC task thread` | GC 太频繁（回去看 GC 日志） |
| 栈顶是业务方法的死循环 | 循环退出条件写错 / 正则回溯爆炸 |
| 多个线程 `RUNNABLE` 在同一方法 | 某段计算太重（加缓存/优化算法） |
| 大量线程 `BLOCKED` | 锁竞争（找持锁线程） |

⚠️ **注意「等网络 IO 也显示 RUNNABLE」**——很多「CPU 高」其实是「线程多但都在等下游」。要看 `%CPU` 是否真的高，再决定方向。

### 故障 4：接口变慢但 CPU/内存正常

**方向**：不是 JVM 问题，是**外部依赖**。

1. `jstack` 看线程是否大量卡在同一处（如数据库连接池 `getConnection`）；
2. `Arthas trace` 看方法耗时分布（哪一层慢）；
3. 检查连接池（HikariCP 的 `active`/`pending`）、下游 RT、慢 SQL（见 [[mysql/02-中段阶段-专题精讲/索引与查询优化/索引诊断与慢查询优化]]）。

## 四、必开的三个启动参数

```bash
-XX:+HeapDumpOnOutOfMemoryError          # OOM 时自动 dump（⚠️ 最重要）
-XX:HeapDumpPath=/data/dump              # dump 落盘位置
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags   # GC 日志
```

⚠️ 没有 dump 和 GC 日志的线上服务，出问题时基本等于**盲诊**——这两个参数必须在上线前配好。

## 五、陷阱

1. **⚠️ OOM 后直接重启**——现场没了，同一个问题两周后必然复发；
2. **⚠️ 只看 `-Xmx` 不看元空间/直接内存**——OOM 的类型决定方向；
3. **⚠️ `jmap -histo` 不加 `:live`**——会把待回收对象也算进去，数字虚高（加 `:live` 会触发一次 Full GC，生产慎用）；
4. **⚠️ `jstack` 只抓一次**——一次快照看不出趋势，间隔几秒抓 3 次对比才有价值；
5. **⚠️ 在生产直接 `jmap -dump` 大堆**——会 STW 数秒，优先用 OOM 自动 dump 或 Arthas 的 `heapdump`。

## 小结

- 四件套：`jps`（找进程）→ `jstat`（看 GC）→ `jmap`（看对象/导快照）→ `jstack`（看线程）
- Arthas 三个主力：`dashboard`（全局）、`thread -n`（CPU）、`trace`（耗时）
- 四类故障各有固定路径：堆 OOM（dump + MAT）、元空间（类加载器泄漏）、CPU 100%（top -Hp + 十六进制线程号 + jstack）、变慢（先怀疑下游）
- ⭐ **上线必配**：`HeapDumpOnOutOfMemoryError` + GC 日志
