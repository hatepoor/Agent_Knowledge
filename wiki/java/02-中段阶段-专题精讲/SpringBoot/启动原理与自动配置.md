# Spring Boot 启动原理与自动配置

> **什么时候该读**：第一次用 Spring Boot；或者被问「自动配置是怎么实现的」「启动时到底发生了什么」。

## 一、Spring 与 Spring Boot 的关系

| | Spring Framework | Spring Boot |
|---|---|---|
| 定位 | 基础框架（IoC + AOP + 数据访问 + Web） | 在 Spring 上做**约定优于配置**的封装 |
| 配置方式 | XML / Java Config，大量手工装配 | 自动配置 + Starter 依赖 |
| Web 容器 | 需要外置 Tomcat | ⭐ **内嵌 Tomcat**，`java -jar` 即运行 |
| 启动 | 部署到容器 | `SpringApplication.run()` |

⭐ 一句话：**Spring Boot = Spring Framework + 自动配置 + 内嵌容器 + Starter**。它不是新框架，是「让 Spring 能直接用」的工程化方案。

## 二、启动流程：从 main 到服务就绪

```java
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);
    }
}
```

### 内部发生了什么（7 步）

```
① SpringApplication 构造
   推断应用类型（Servlet / Reactive / None）
   加载 Initializer 与 Listener

② run() 开始
   启动计时器、发布 ApplicationStartingEvent

③ 准备 Environment
   读 application.yml / 环境变量 / 命令行参数

④ 创建 ApplicationContext
   Servlet 应用 → AnnotationConfigServletWebServerApplicationContext

⑤ refresh()  ← 核心，12 个子步骤
   ① prepareRefresh
   ② obtainFreshBeanFactory
   ③ prepareBeanFactory
   ④ postProcessBeanFactory
   ⑤ invokeBeanFactoryPostProcessors   ← ⭐ 自动配置在这里解析
   ⑥ registerBeanPostProcessors
   ⑦ initMessageSource
   ⑧ initApplicationEventMulticaster
   ⑨ onRefresh                          ← ⭐ 创建并启动内嵌 Tomcat
   ⑩ registerListeners
   ⑪ finishBeanFactoryInitialization    ← ⭐ 实例化所有单例 Bean
   ⑫ finishRefresh                      → 发布 ContextRefreshedEvent

⑥ 启动内嵌 Tomcat（第 ⑨ 步）
   默认端口 8080；⚠️ 此时还没接收请求

⑦ 发布 ApplicationReadyEvent
   ⭐ 到这里服务才真正可用
```

⭐ **面试重点**：`refresh()` 的第 ⑤ 步（自动配置解析）、第 ⑨ 步（创建 Tomcat）、第 ⑪ 步（实例化 Bean）——三步决定了「Bean 从哪来、端口什么时候开、对象什么时候创建」。

## 三、`@SpringBootApplication` 是三个注解的合体

```java
@SpringBootApplication
// 等价于：
@SpringBootConfiguration      // 标记为配置类（本质是 @Configuration）
@EnableAutoConfiguration      // ⭐ 开启自动配置
@ComponentScan                // 扫描当前包及子包的 @Component
```

⚠️ **扫描范围默认是「启动类所在包及其子包」**——启动类放在 `com.example` 根包下，才能扫到 `com.example.*` 的所有组件。放在深层子包里，上层 Bean 会扫不到。

## 四、自动配置的实现链路（核心）

### 四步链路

```
① @EnableAutoConfiguration
      ↓ @Import(AutoConfigurationImportSelector.class)
② AutoConfigurationImportSelector
      读取 classpath 下所有 jar 中的注册文件
      ⚠️ Boot 2.7+：META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
         旧机制（Boot 2.7 前）：META-INF/spring.factories
      ↓
③ 得到候选配置类列表（几百个）
      ↓ 用条件注解逐个筛选
④ @ConditionalOnClass / @ConditionalOnMissingBean / @ConditionalOnProperty
      ↓ 满足条件的才注册为 Bean 定义
   容器中真正创建这些 Bean
```

### 关键文件长什么样

`spring-boot-autoconfigure` 的 `AutoConfiguration.imports`（节选）：

```text
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
org.springframework.boot.autoconfigure.web.servlet.WebMvcAutoConfiguration
org.springframework.boot.autoconfigure.jackson.JacksonAutoConfiguration
```

每一行是一个「候选自动配置类」，最终装不装配由条件注解决定。

### 三个最重要的条件注解

| 注解 | 含义 | 典型场景 |
|------|------|---------|
| `@ConditionalOnClass` | classpath 里有某个类才生效 | 引入了 `spring-boot-starter-web` 才装配 Web 相关 |
| `@ConditionalOnMissingBean` | ⭐ 容器里**没有**这个 Bean 才生效 | 你自己定义了 `DataSource`，Boot 就不再自动创建 |
| `@ConditionalOnProperty` | 配置项满足条件才生效 | `spring.datasource.url` 存在才装配数据源 |

⭐ **`@ConditionalOnMissingBean` 是「可覆盖」的机制**：自动配置永远给「默认实现」，你一自定义，默认的就退让——所以 Boot 才能既开箱即用、又能完全接管。

### 为什么加个 starter 就「什么都有了」

```xml
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

这个 starter 把 `spring-webmvc`、`tomcat`、`jackson` 等依赖打包引入 → classpath 上出现这些类 → `@ConditionalOnClass` 条件满足 → `WebMvcAutoConfiguration`、`JacksonAutoConfiguration` 自动生效 → **不用写一行配置就有了 REST 能力和 JSON 序列化**。

## 五、怎么排查「为什么装配了 / 没装配」

### 方法 1：`--debug` 参数（最快）

```bash
java -jar app.jar --debug
```

输出 **Condition Evaluation Report**，分两块：

- **Positive matches**：条件成立、被装配的（含原因）；
- **Negative matches**：条件不成立、没装配的（含哪个条件没过）。

⭐ 这是排查自动配置问题的第一手段——不用读源码。

### 方法 2：Actuator 的 `/actuator/conditions`

```yaml
management:
  endpoints:
    web:
      exposure:
        include: conditions,beans,health,metrics
```

访问 `/actuator/conditions` 看同样的报告（JSON 版）；`/actuator/beans` 看容器里所有 Bean。

### 方法 3：排除自动配置

```java
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
```

或配置：

```yaml
spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
```

⚠️ 排除后如果还有别处依赖它，启动会报 `NoSuchBeanDefinitionException`——排除要成对处理依赖。

## 六、自定义 Starter（了解）

三步：

1. 建一个 `xxx-spring-boot-autoconfigure` 模块，写配置类；
2. 在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 里登记；
3. 用 `@ConditionalOnClass` + `@ConditionalOnMissingBean` 控制生效条件。

⭐ 这解释了一件事：**第三方框架（MyBatis、Redis 客户端）的 Boot 集成，本质就是各自提供了一个自动配置类**。

## 八、陷阱

1. **⚠️ 把自动配置当黑魔法**——它只是「读文件 + 条件判断 + 注册 Bean」，`--debug` 就能看全过程；
2. **⚠️ 启动类放太深的包里**——`@ComponentScan` 只扫启动类所在包及子包，上层组件会漏；
3. **⚠️ 到处 `exclude` 自动配置**——排错了会引发连锁的 `NoSuchBeanDefinitionException`；
4. **⚠️ 还在用 `spring.factories` 注册自动配置**——Boot 2.7 起有新机制，3.0 起 `spring.factories` 不再用于自动配置；
5. **⚠️ 以为「启动完成 = Bean 都创建好了」**——懒加载（`@Lazy`）的 Bean 用到才创建，启动日志里没有不代表不存在。

## 小结

- **Spring Boot = Spring + 自动配置 + 内嵌容器 + Starter**，不是新框架
- 启动七步，核心是 `refresh()`：**自动配置解析（⑤）→ 创建 Tomcat（⑨）→ 实例化 Bean（⑪）**
- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`
- 自动配置链路：**注解 → imports 注册文件 → 候选类 → 条件注解筛选**
- 三个关键条件：`OnClass`（有没有依赖）、`OnMissingBean`（你能不能覆盖）、`OnProperty`（配没配）
- 排查用 **`--debug` 的 Condition Report**，别读源码
