# 集合框架

> **什么时候该读**：Java 面试里最高频的技术追问——面试官问「HashMap 底层怎么实现的」，实际是在考察你的**数据结构和工程取舍**能力。
> **答题主线**：**「数据结构的选型 = 代价的取舍」**。List/Set/Map 各自解决什么语义、每种实现牺牲了什么性能、什么场景该换容器。记住这条主线，集合题就不会变成 API 背诵。

---

## Q1. List、Set、Map 三大集合接口分别解决什么需求？该怎么选？

**答：**

**一句话区分语义**：

| 接口 | 语义 | 关键特征 | 典型场景 |
|------|------|---------|---------|
| **List** | **有序、可重复、可按位置访问** | 有索引、有顺序 | 订单列表、购物车（允许重复项） |
| **Set** | **无重复、唯一性判定** | `equals`/`hashCode` 决定唯一 | 去重、去重后的标签集合 |
| **Map** | **键值对映射** | key 唯一、按 key 查找 | 字典、缓存、字段映射 |

**⚠️ 一个必须澄清的误解**：**Set 不是「无序」的**——`LinkedHashSet` 保持插入顺序，`TreeSet` 按排序规则。而 **`Map` 本身不是 Collection 的子接口**——它不继承 `Collection`，因为「键值对」不是「元素集合」，Java 8 之前 `HashMap` 没有 `add()` 方法就是这个原因。

**选型决策树**：

```
需要按 key 查找？
  → Map（HashMap / LinkedHashMap / TreeMap）
需要去重？
  → Set（HashSet / LinkedHashSet / TreeSet）
需要保持顺序 + 允许重复？
  → List（ArrayList / LinkedList / CopyOnWriteArrayList）
需要排队（先进先出）？
  → Queue / Deque（ArrayDeque / LinkedBlockingQueue）
```

**三大接口的实现选择**（这是真正拉开差距的部分）：

| 接口 | 实现 | 底层结构 | 查找 | 插入 | 选择依据 |
|------|------|---------|------|------|---------|
| List | **ArrayList** | 数组 | O(1)（按下标） | O(n) | **默认选它**：读多写少、尾部增删 |
| List | LinkedList | 双向链表 | O(n) | O(1)（已知位置） | ⚠️ 几乎不选——链表缓存不友好 |
| Set | **HashSet** | 哈希表 | O(1) 平均 | O(1) 平均 | **默认选它**：只看唯一性 |
| Set | LinkedHashSet | 哈希表 + 双向链表 | O(1) | O(1) | 需要保持插入顺序 |
| Set | TreeSet | 红黑树 | O(log n) | O(log n) | 需要**排序 + 范围查询** |
| Map | **HashMap** | 哈希表 | O(1) 平均 | O(1) 平均 | **默认选它** |
| Map | LinkedHashMap | 哈希表 + 链表 | O(1) | O(1) | 需要迭代顺序 = 插入顺序；LRU 缓存 |
| Map | TreeMap | 红黑树 | O(log n) | O(log n) | 需要 key 有序、范围查询 |

⭐ **面试官真正想听的一句话**：**`HashMap` 适合「查得快」，`TreeMap` 适合「排得顺 + 范围查」；其余绝大多数场景用 `ArrayList` + `HashMap` 就够了**。

**追问：为什么 `LinkedList` 很少用？**
→ ① **缓存不友好**：链表节点分散在堆内存，每次遍历都是缓存 miss，数组是连续内存，对 CPU 缓存友好得多；② **每个节点额外存两个指针**（prev/next），内存开销大；③ 现代 JVM 对数组的遍历有**边界检查消除**等优化。**结论：几乎总是选 `ArrayList`**，只有「需要在中间频繁插入删除且已持有迭代器」这种极端场景才考虑 `LinkedList`——而那种场景的正确解法通常是 `ArrayList` + 重建。

**追问：`HashMap` 和 `TreeMap` 底层结构差在哪？**
→ `HashMap` 是**哈希表**（数组 + 链表/红黑树），靠哈希值定位，**无序**，但平均 O(1)；`TreeMap` 是**红黑树**，靠比较器排序，**有序**，但 O(log n)。要「范围查询」（`tailMap`、`subMap`）必须用 `TreeMap`——`HashMap` 做不到。

**追问：为什么 JDK 8 要把 `HashMap` 的链表改成红黑树？**
→ 极端情况下哈希冲突严重（恶意构造相同 hashCode），链表会退化成 O(n)。**树化后最坏 O(log n)**，把最坏情况从「灾难」拉回「可接受」。详见 [[java/01-入门阶段-基础教程/第04章-集合框架/4.4-HashMap底层原理]]。

## Q2. `ArrayList` 的扩容机制是什么？`new ArrayList<>(n)` 会预分配多少？

**答：**

**结论：`ArrayList` 底层是数组，默认容量 10，满了就扩容到「原容量的 1.5 倍」，并按「新容量 = 旧容量 + 旧容量/2」计算。**

**完整流程**：

```java
public class ArrayListDemo {
    public static void main(String[] args) {
        ArrayList<String> list = new ArrayList<>();      // 初始容量 0，首次 add 时 → 10
        System.out.println(list.size());                 // 0

        for (int i = 0; i < 15; i++) {
            list.add("item" + i);
        }
        // 容量变化：10 → 15 → 22（10*1.5=15, 15*1.5=22）
    }
}
```

| 时机 | 容量变化 |
|------|---------|
| `new ArrayList<>()` | 初始 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA`（空数组） |
| 第一次 `add` | 扩容到 **10** |
| 第 11 次 `add` | 扩容到 **15**（10 + 10/2） |
| 第 16 次 `add` | 扩容到 **22**（15 + 15/2） |

**`new ArrayList<>(n)` 的真实行为**：
- 它**只是设定「初始数组长度」**——`n` 是**期望的最小容量**，不是「最多能放 n 个」；
- 后续 `add` 仍然会按 1.5 倍规则扩容，**并且扩容时直接跳到「能装下 size+1 个」的新容量**（`newCapacity = max(旧容量*1.5, 需要的最小容量)`）；
- ⚠️ `new ArrayList<>(n)` **不会预分配 n 个空间**——如果 n=0 或 n=1，行为特殊：n=0 时首次 add 扩容到 1 再到 10；n=1 时首次 add 扩容到 10。

⭐ **所以 `new ArrayList<>(10000)` 确实会预分配 10000 的数组**，但**如果你只 add 了 100 个元素，那 9900 个槽位就浪费了**。**正确做法：知道确切数量就 `new ArrayList<>(count)`；不知道就用默认，让它自然扩容。**

**追问：为什么扩容是 1.5 倍而不是 2 倍？**
→ **权衡「内存浪费」与「拷贝成本」**。2 倍扩容空间浪费更快（长期只用 25% 就浪费了一半），但拷贝次数少；1.5 倍在空间和拷贝之间取了个平衡。**这是 JDK 长期沿用的经验值**（`ArrayList` 用 1.5，`HashMap` 也是 1.5）。

**追问：扩容是怎么实现的？`System.arraycopy` 还是逐个赋值？**
→ **`System.arraycopy()`**（底层是 JVM 的 `System.arraycopy` intrinsic，批量内存拷贝，用了 SIMD 优化）。⚠️ **扩容是 O(n) 的操作**——所以在循环里反复 `add` 会触发多次拷贝。**频繁增删的场景，要么预估容量，要么用 `LinkedList`（虽然不推荐），要么用 `ArrayDeque`。**

**追问：`ArrayList` 支持并发吗？**
→ **不支持**。多线程同时 `add` 可能导致数据丢失、数组越界、或 `size` 不一致。**并发场景用 `CopyOnWriteArrayList`（读多写少）或 `Collections.synchronizedList`（一般用 `Vector` 或加锁），但首选是 `ConcurrentLinkedQueue` 等并发容器。**

## Q3. `HashMap` 的底层原理是什么？为什么要对 hashCode 做扰动？

**答：**

**结论：`HashMap` 是「数组 + 链表 + 红黑树」的三段式结构，靠 `hash(key)` 定位桶、靠 `equals` 在桶内确认。**

**三个步骤串起来**：

```
① 计算扰动后的 hash
   hash = (h = key.hashCode()) ^ (h >>> 16)     ← 高 16 位混入低 16 位

② 定位桶下标
   index = (n - 1) & hash                       ← 因为容量是 2 的幂

③ 桶内比较
   if (桶为空) 直接放
   else if (hash 相同 && (key == k || key.equals(k))) 命中，覆盖旧值
   else 挂到链表尾部（或插入红黑树）
```

```java
public class HashMapDemo {
    public static void main(String[] args) {
        Map<String, Integer> map = new HashMap<>();
        map.put("a", 1);
        map.put("b", 2);
        System.out.println(map.get("a"));     // 1
        System.out.println(map.get("z"));     // null
        System.out.println(map.size());       // 2

        // 扰动的意义：让 hash 的高位也参与桶定位
        // "Aa" 和 "BB" 的 hashCode 相同，但 (h ^ (h>>>16)) 后不同 → 落到不同桶
    }
}
```

**为什么要扰动 `h ^ (h >>> 16)`？**

`HashMap` 用 `(n - 1) & hash` 定位桶，**因为容量是 2 的幂，取低位等价于取模**——而**取低位意味着 hashCode 的高位完全被忽略**。

⚠️ 问题来了：如果两个 key 的 hashCode **只在高位不同**（例如 `"Aa"` 和 `"BB"` 的 hashCode 就是这样），低位相同 → **必然落到同一个桶** → 链表很长 → 性能退化。扰动把高 16 位**右移后异或**进低 16 位，**让高位的差异也能体现在低位上**，从而分散到不同的桶。

**⚠️ 但要清楚：扰动只是「减少冲突概率」，不是「消除冲突」**——hashCode 最终还是要靠 `equals` 确认。

**容量为什么是 2 的幂？**

`(n - 1) & hash` 只有在 n 是 2 的幂时才等价于 `hash % n`（因为 2 的幂减 1 全是 1，位与正好是取模）。**取模运算比位与慢得多**，而且扩容时可以直接用「**旧容量左移一位**」来计算新位置（见 Q4）。

**追问：`HashMap` 的初始容量怎么定？**
→ **别用默认值（16），要按预期大小算**：`new HashMap<>(expectedSize / 0.75 + 1)`。因为**加载因子（load factor）默认是 0.75**——当 `size > capacity * 0.75` 时就会扩容。**要装 1000 个元素，初始容量应该是 `1000/0.75+1 ≈ 1334`**，而不是 1000（否则中途要扩容一次，白白拷贝一遍）。JDK 8 之后这个公式被写进了 `HashMap` 的注释里。

**追问：`HashMap` 为什么线程不安全？会出什么问题？**
→ **会**。多线程并发 `put` 可能导致：
1. **数据丢失**：两个线程同时 `put` 到同一桶，链表的指针写入互相覆盖；
2. **扩容期间死循环**：JDK 7 的 `HashMap` 在并发扩容时，因为头插法导致链表形成环，**两个线程 `get` 会无限循环**——这是 JDK 7 的著名 bug，**JDK 8 改成尾插法后死循环问题消失，但数据丢失和覆盖依然存在**。

**结论：并发场景必须用 `ConcurrentHashMap`**（见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]]）。

## Q4. `HashMap` 什么时候会树化？扩容是怎么做的？

**答：**

**树化的三个条件必须同时满足**：

| 条件 | 值 |
|------|-----|
| 桶内链表长度 | **≥ 8** |
| 数组容量 | **≥ 64** |
| 结果 | 该桶的链表**转成红黑树** |

⚠️ **注意第二个条件容易答错**：如果数组容量 < 64，即使链表长到 8 也**不树化**，而是**扩容**——因为在容量小的时候，扩容带来的重新散列成本比树化低。

**退化回链表的条件**：红黑树节点数减少到 **6**（树化门槛 8、退化门槛 6，中间留 1 个缓冲，避免在临界点反复转换抖动）。

**扩容流程（`resize()`）**：

```
① 扩容：newCap = oldCap << 1（×2），newThr = newCap * 0.75
② 遍历旧数组每个桶：
   桶为空         → 跳过
   桶是单节点链表 → 直接算出新下标搬过去
   桶是红黑树     → 拆分树成两棵树（lo/hi 链表）
   桶是链表       → 拆成「lo 链」和「hi 链」
③ 把旧哈希桶拆成两个：索引不变（j）或索引 + oldCap（j + oldCap）
```

**⭐ 第 ③ 步是 HashMap 的精髓**——**扩容时不需要重新计算 hash**：

```java
// JDK 8 的核心优化：oldCap 是 2 的幂，所以新下标只可能是 j 或 j + oldCap
if ((e.hash & oldCap) == 0) {
    lo.add(e);          // 下标不变
} else {
    hi.add(e);          // 下标 = 原下标 + oldCap
}
```

**为什么只需要判断一位？** 因为 `oldCap` 是 2 的幂，翻倍时 hash 的那一位决定了新下标落在前半区还是后半区。**这让扩容的复杂度从 O(n) 重新散列变成了 O(n) 的链表拆分**（虽然还是 O(n)，但省掉了昂贵的 `hashCode()` 重算和取模）。

**追问：树化之后呢？红黑树怎么插入？**
→ 转成红黑树后，插入走红黑树的插入调整（旋转 + 变色）保持平衡，**最坏 O(log n)**。查询时先比较根节点，再按 BST 方向走，同时修正查找路径上的父子指针。

**追问：为什么 HashMap 不用跳表？**
→ 早期版本考虑过，但**红黑树在并发场景下的表现更好**（锁粒度更小、范围查询能力也更强），而 `ConcurrentSkipListMap` 那套更适合有序并发场景。**历史选择 + 性能实测的结果**，不是因为红黑树一定更优。

**追问：HashMap 的负载因子可以改吗？**
→ 可以，`new HashMap<>(16, 0.9f)`。⚠️ **调高会减少扩容次数但增加冲突概率**（链表变长）；**调低会减少冲突但更频繁扩容**。默认值 0.75 是空间和时间的平衡点，**除非有明确的压测数据，否则不要动它。**

## Q5. 什么是 fail-fast？为什么增强 for 循环里删除元素会抛异常？

**答：**

**结论：fail-fast 是一种「快速失败」的错误检测机制——集合在遍历过程中被结构性修改时，立刻抛 `ConcurrentModificationException`，而不是让你拿着一个不一致的视图继续跑。**

**原理：`modCount` 计数法**：

```java
public class FailFastDemo {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("a", "b", "c"));

        try {
            for (String s : list) {
                if ("b".equals(s)) {
                    list.remove(s);      // ⚠️ 抛 ConcurrentModificationException
                }
            }
        } catch (ConcurrentModificationException e) {
            System.out.println("检测到并发修改: " + e.getMessage());
        }
    }
}
```

**机制拆解**：

1. `ArrayList`（及 `HashMap` 等）内部维护一个 `modCount` 字段，**记录「结构被修改的次数」**——每次 `add`/`remove`/清空都会 `modCount++`；
2. 迭代器创建时**快照**了当时的 `modCount` 值（`expectedModCount`）；
3. 每次 `next()` 时，迭代器检查 `modCount != expectedModCount` → 说明集合被改过了 → **立即抛 `ConcurrentModificationException`**；
4. ⭐ **关键**：这**不是线程安全问题**——fail-fast 是**尽力而为的错误检测**，它**不保证一定检测到**（比如你在遍历结束后才修改，就检测不到）。

**正确的删除方式**：

```java
// ✅ 方式 1：迭代器的 remove()
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (condition(it.next())) it.remove();     // 迭代器自己改 modCount
}

// ✅ 方式 2：removeIf（Java 8+，最简洁）
list.removeIf(s -> "b".equals(s));

// ✅ 方式 3：普通 for + 索引倒序删除
for (int i = list.size() - 1; i >= 0; i--) {
    if (condition(list.get(i))) list.remove(i);
}
```

**追问：fail-fast 是线程安全的保证吗？**
→ **完全不是**。它是**单线程下的编程错误检测**。真正的并发安全要靠 `ConcurrentHashMap`、`CopyOnWriteArrayList` 等并发容器（它们用**弱一致迭代器**，遍历时不抛异常，但也不保证看到最新数据）。

**追问：为什么 `ConcurrentHashMap` 不抛 `ConcurrentModificationException`？**
→ 因为它的迭代器是**弱一致性（weakly consistent）**的：遍历基于一个「弱一致的快照」，**能看到遍历开始时存在的元素，也可能看到期间的修改，但保证不抛异常、不会死循环、不会重复访问同一元素**。**这是并发场景下更实用的契约**——宁可给一个弱一致的视图，也不要抛异常打断业务。

**追问：为什么 `CopyOnWriteArrayList` 的迭代器是「快照式」的？**
→ 因为它的写操作是**复制整个底层数组**再替换（写时复制）。迭代器持有的是创建时的数组引用，**遍历完全不受后续修改影响**。**代价是写放大严重**——所以它只适合「读极多、写极少」的场景。

**追问：fail-fast 和 `ConcurrentModificationException` 有什么区别？**
→ `ConcurrentModificationException` 是 **JUC 包里 `ConcurrentModificationException`**（运行时异常）。⚠️ **同名但不同包**：老集合框架（`java.util`）抛的是它自己的；JUC 的并发容器在**弱一致迭代**下不会抛它。

## Q6. `TreeMap` 和 `HashMap` 有什么区别？`TreeSet` 呢？

**答：**

**核心区别是底层结构：红黑树 vs 哈希表。**

| 维度 | **HashMap** | **TreeMap** |
|------|-----------|------------|
| 底层 | 数组 + 链表 + 红黑树 | **红黑树** |
| 排序 | **无序** | **按 key 自然序或自定义 Comparator 排序** |
| 查找/插入 | 平均 O(1)，最坏 O(log n)（树化后） | **O(log n)**，稳定 |
| 是否允许 null key | ✅ 允许 1 个 | ⚠️ **不允许**（自然序下会 NPE） |
| 是否允许 null value | ✅ 允许 | ✅ 允许 |
| 范围查询 | ❌ 不支持 | ✅ `headMap`/`tailMap`/`subMap`/`firstKey`/`lastKey` |
| 导航方法 | ❌ | ✅ `floorKey`/`ceilingKey`/`higherKey`/`lowerKey` |
| 遍历顺序 | 哈希顺序（不保证） | **有序** |

**`TreeSet` 对应 `TreeMap` 的 key 集合**——它的底层就是一个 `TreeMap`，比较器作用于元素本身。

```java
public class TreeMapDemo {
    public static void main(String[] args) {
        TreeMap<String, Integer> map = new TreeMap<>();
        map.put("b", 2);
        map.put("a", 1);
        map.put("c", 3);

        System.out.println(map.firstKey());              // a
        System.out.println(map.lastKey());               // c
        System.out.println(map.floorKey("bb"));          // b   ← 最大的 ≤ "bb"
        System.out.println(map.ceilingKey("bb"));        // c   ← 最小的 ≥ "bb"

        // 范围查询：HashMap 做不到
        System.out.println(map.subMap("a", "c"));        // {a=1, b=2}
        System.out.println(map.tailMap("b"));            // {b=2, c=3}
    }
}
```

**选择标准**：

```
只需要 O(1) 按 key 查找，不需要顺序？
  → HashMap
需要有序遍历 / 范围查询 / 最近邻查找（floor/ceiling）？
  → TreeMap
```

**典型场景**：排行榜（按分数倒序）、时间轴、IP 段查找、**数据库索引在内存中的等价物**（B+ 树也是有序结构）。

**追问：`TreeMap` 的排序规则是谁定的？**
→ 两种：① **自然序**——key 实现 `Comparable`（如 `String` 按字典序、`Integer` 按数值）；② **自定义**——构造时传 `Comparator`。⚠️ **两种规则混用会抛 `ClassCastException`**——建树时和查找时的比较器必须一致。

**追问：`TreeMap` 为什么不允许 null key？**
→ 因为 null 没有自然序，插入时需要和 null 比较 → NPE。**但允许 null value**（value 不参与排序）。`HashMap` 允许一个 null key。

**追问：`LinkedHashMap` 有什么特别？**
→ 它在 `HashMap` 基础上**多维护了一条双向链表**来记录插入顺序，所以**遍历顺序 = 插入顺序**。⭐ **两个高频用途**：① **LRU 缓存**（`LinkedHashMap` 的 `removeEldestEntry` 钩子改一下就是 LRU）；② **需要稳定输出顺序**的场景（避免 `HashMap` 遍历顺序不可控导致测试不稳定）。

**追问：怎么让 `HashMap` 保持插入顺序？**
→ 用 `LinkedHashMap`。⚠️ **`HashMap` 的遍历顺序是「由 hash 值和容量决定的」**——扩容后顺序可能变，所以**不要依赖 `HashMap` 的遍历顺序做业务逻辑，也不要用它做单元测试的断言基准。**

## Q7. `Collections.unmodifiableList` 和 `List.of` 有什么区别？不可变集合怎么选？

**答：**

**两者都返回不可变集合，但来源和语义不同：**

| | `Collections.unmodifiableList(list)` | `List.of("a", "b")` / `List.copyOf(list)` |
|---|-----------------------------------|----------------------------------|
| **底层** | **视图（view）**——包住原 list | **全新的不可变 list**（内部用 `ImmutableCollections`） |
| **原 list 改动会反映吗** | ✅ **会**——视图是活的 | ❌ 不会——已经拷成快照 |
| **能否传 null** | ✅ 能（原 list 里有 null 也不报错） | ⚠️ **不能**——`List.of` 传 null 抛 NPE |
| **能否有重复** | ✅ 能 | ✅ 能（`List.of` 不是 Set） |
| **set 操作** | 抛 `UnsupportedOperationException` | 抛 `UnsupportedOperationException` |
| **序列化** | 保留原类型 | 可序列化 |

**⚠️ 最关键的一条**：`unmodifiableList` **只是「不允许你通过这个引用修改」**，但**底层对象如果还被别处持有并修改，你看到的视图也会变**。

```java
public class UnmodifiableDemo {
    public static void main(String[] args) {
        List<String> raw = new ArrayList<>(List.of("a", "b"));
        List<String> view = Collections.unmodifiableList(raw);
        raw.add("c");                    // 从原引用改
        System.out.println(view);       // [a, b, c] ← ⚠️ 视图跟着变了！

        List<String> snapshot = List.copyOf(raw);
        raw.add("d");
        System.out.println(snapshot);   // [a, b, c] ← ✅ 快照不变
    }
}
```

**⭐ 结论**：**要「真正不可变」用 `List.of` / `List.copyOf`（Java 9+ 静态工厂）；`Collections.unmodifiableXxx` 只是「防御性视图」，用来防止别人通过你暴露的引用改动你的内部数据。**

**其他不可变集合**：

```java
List.of(1, 2, 3);                        // Java 9+
Set.of("a", "b");
Map.of("k", "v");                        // 最多 10 对
Map.ofEntries(Map.entry("k", "v"));       // 超过 10 对
List.copyOf(mutableList);                // Java 10+
Map.copyOf(mutableMap);
```

**追问：`List.of` 为什么不允许 null？**
→ 因为不可变集合内部用**紧凑的数组布局**（`Object[]` 直接存元素）来减少内存和对象开销，**null 没有明确的「不存在」表示**，所以直接拒绝。`Collections.unmodifiableList` 底层是普通 list，可以有 null。**这是设计取舍，不是 bug。**

**追问：不可变集合有什么性能优势？**
→ ① **可以共享**——多个调用方持有同一个实例，不用担心互相影响；② **JIT 能更好优化**——字段全是 `final` 且不可变，JVM 可以做**常量折叠**和**逃逸分析**；③ **天然线程安全**（不可变 = 无共享可变状态）。**所以能用不可变集合就别用可变集合 + 加锁。**

**追问：`unmodifiableMap` 能当「只读配置」用吗？**
→ **能防误改，防不了「原 map 被别人改了」**。如果传进去的 map 还被别处持有，用 `Map.copyOf` 更彻底。

## Q8. `HashSet` 是怎么实现的？`HashSet` 和 `HashMap` 是什么关系？

**答：**

**结论：`HashSet` 内部就是持有一个 `HashMap`，用它的 key 存元素、value 统一用一个哨兵对象 `PRESENT`。**

```java
public class HashSet<E> implements Set<E> {
    private static final Object PRESENT = new Object();   // ⭐ 哨兵
    private transient HashMap<E, Object> map;            // ⭐ 内部就是一个 HashMap

    public boolean add(E e)      { return map.put(e, PRESENT) == null; }
    public boolean contains(Object o) { return map.containsKey(o); }
    public Iterator<E> iterator() { return map.keySet().iterator(); }
    public int size()            { return map.size(); }
}
```

**这个设计带来三个直接结论**：

1. **`HashSet` 的元素唯一性 == `HashMap` 的 key 唯一性** → **完全依赖 `hashCode`/`equals` 契约**（见 Q5）；
2. **`HashSet` 的 `add` 返回值语义特殊**：底层 `map.put(e, PRESENT)` 只有在「原来没有这个 key」时才返回 `null` → 所以 `add` 返回 `true` 表示「新增成功」，返回 `false` 表示「已存在，未添加」；
3. **可以给 `HashSet` 加个 null**：底层是 `HashMap`，允许一个 null 元素。

**`LinkedHashSet` / `TreeSet` 的关系同理**：

| Set | 底层 | 顺序 |
|-----|------|------|
| `HashSet` | `HashMap` | 无序 |
| `LinkedHashSet` | `LinkedHashMap` | **插入顺序** |
| `TreeSet` | `TreeMap` | **排序顺序**（比较器作用于元素本身，不是 value） |

**追问：`HashSet` 和 `List` 怎么互相转换？去重怎么做？**
→ `new HashSet<>(list)` 去重（⚠️ **会丢失顺序**）；要保序去重用 `LinkedHashSet`，或 `list.stream().distinct().collect(toList())`（⚠️ `distinct()` 也是**保持首次出现顺序**，底层用 `LinkedHashSet`）。

**追问：`TreeSet` 的排序规则和 `TreeMap` 一样吗？**
→ **机制一样，比较对象不同**：`TreeMap` 的比较器作用于 **key**，`TreeSet` 的比较器作用于**元素本身**。所以 `TreeSet` 的元素必须可比较（或提供 `Comparator`）。

**追问：为什么 `HashSet` 的遍历顺序「看起来是乱的」？**
→ 因为它按 `hashCode` 散列到数组槽位上，**顺序由 hash 值和当前容量决定**。⚠️ **所以永远不要依赖 `HashSet` 的遍历顺序**——同样元素集合在不同 JDK 版本、不同容量下顺序可能不同。

**追问：Set 能存放重复元素吗？`add` 返回 false 时元素去哪了？**
→ 不能重复。`add` 返回 `false` 表示**已存在，新元素被丢弃，集合保持原样**（不会替换原有元素）。

## Q9. 集合的遍历方式有哪些？各自适合什么场景？

**答：**

**四种遍历方式，性能和适用场景差别很大**：

```java
public class IterateDemo {
    public static void main(String[] args) {
        List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));

        // ① 增强 for —— 最简洁，日常首选
        for (int i : list) { System.out.println(i); }

        // ② 普通 for + 下标 —— 需要下标或要在循环中删除时
        for (int i = 0; i < list.size(); i++) { System.out.println(list.get(i)); }

        // ③ Iterator —— 需要显式删除元素时
        Iterator<Integer> it = list.iterator();
        while (it.hasNext()) {
            if (it.next() % 2 == 0) it.remove();
        }

        // ④ Stream —— 需要过滤/映射/聚合时的声明式写法
        list.stream().filter(i -> i % 2 == 1).map(i -> i * 10).forEach(System.out::println);
    }
}
```

| 方式 | 适用场景 | 注意 |
|------|---------|------|
| **增强 for** | 日常遍历、只读 | ⚠️ **不能删除元素**（抛 CME）；本质是 Iterator |
| **普通 for + 下标** | 需要下标、倒序遍历 | ⚠️ 删除元素后下标会错位（要倒序删） |
| **Iterator** | 需要删除元素 | `it.remove()` 而不是 `list.remove()` |
| **Stream** | 过滤、映射、聚合 | **注意副作用**：Stream 里的 `forEach` 适合输出，不适合改集合 |

**Map 的遍历有三种**：

```java
Map<String, Integer> map = new HashMap<>();

// ① entrySet 遍历 —— 推荐，效率最高
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    entry.getKey();
    entry.getValue();
}

// ② keySet + get —— 语义清晰但多一次查找
for (String key : map.keySet()) {
    Integer v = map.get(key);
}

// ③ values —— 只关心 value 时
for (Integer v : map.values()) { }
```

⚠️ **不要在增强 for 里 `map.put()`**——`put` 不会改变 `modCount`（**「结构性修改」指的是增删，不是覆盖已有 key 的值**），所以不会抛 CME，但**并发下会出问题**。

**追问：`forEach` 和增强 for 有什么区别？**
→ `forEach` 是 `Iterable` 的默认方法，**可以传 Lambda**，适合链式调用；增强 for 更适合需要 `break`/`continue` 的场景。**性能上两者基本一致**（增强 for 编译后也是 Iterator 模式）。

**追问：Stream 遍历为什么不能修改集合？**
→ Stream 的操作是**惰性求值 + 可能并行执行**——在 `forEach` 里改集合会破坏 Stream 的遍历假设，**并发流下甚至会导致数据竞争**。需要改就用 `forEach` 之外的终止操作收集结果，再统一修改。

**追问：`HashMap` 的 key 可以是可变对象吗？**
→ **绝对不行**。`hashCode` 被缓存在节点里，key 变了 hash 就变了，**这个 key 就再也 get 不到了**（数据凭空消失）。**Map 的 key 必须是不可变对象**——`String`、包装类、`record` 都是好选择。

## Q10. 集合类该选哪个实现？给一张速查表

**答：**

**一张表解决 90% 的选型问题：**

| 需求 | 选谁 | 为什么 |
|------|------|--------|
| 列表，普通读写 | `ArrayList` | 缓存友好、默认首选 |
| 列表，头插尾删频繁 | `ArrayDeque` | 双端队列，均摊 O(1)，比 `LinkedList` 好 |
| 队列（生产者消费者） | `LinkedBlockingQueue` / `ArrayBlockingQueue` | 线程安全 + 阻塞 |
| 栈 | `ArrayDeque` | **不要用 `Stack`**（遗留类，且 `Vector` 同步开销） |
| 去重 | `HashSet` | O(1) |
| 去重且保序 | `LinkedHashSet` | 插入顺序 |
| 去重且排序 | `TreeSet` | O(log n) + 范围查询 |
| 字典/缓存 | `HashMap` | O(1) |
| 字典保序 | `LinkedHashMap` | 插入顺序 / LRU |
| 字典有序 + 范围查 | `TreeMap` | 红黑树 |
| 读多写少的并发列表 | `CopyOnWriteArrayList` | 写时复制 |
| 任意并发 map | `ConcurrentHashMap` | CAS + synchronized 分段 |
| 生产者消费者 | `LinkedBlockingQueue` | 有界可控 |
| 计数/去重统计 | `HashMap<K, Integer>` 或 `merge()` | — |
| 保持排序的并发结构 | `ConcurrentSkipListMap` | 无锁有序 |

**三个「不要」**：

| 不要用 | 改用 | 原因 |
|--------|------|------|
| ⚠️ `Vector` | `ArrayList` / `CopyOnWriteArrayList` | `Vector` 每个方法都 `synchronized`，性能差且过时 |
| ⚠️ `Stack` | `ArrayDeque` | 遗留类，继承自 `Vector`，API 落后 |
| ⚠️ `Executors.newFixedThreadPool()` | `new ThreadPoolExecutor(...)` | **无界队列会 OOM**（《阿里巴巴 Java 开发手册》明令禁止） |

**⚠️ 一个易错点**：`Arrays.asList()` 返回的是**固定大小的列表**——支持 `set()` 但**不支持 `add()`/`remove()`**（抛 `UnsupportedOperationException`），而且**它的元素还是原数组的引用**（改元素会改到原数组）。

```java
// ❌ 固定大小，不能增删
List<String> a = Arrays.asList("x", "y");
a.add("z");      // UnsupportedOperationException

// ✅ 可增删的列表
List<String> b = new ArrayList<>(Arrays.asList("x", "y"));
```

**追问：为什么 `Stack` 被废弃？**
→ 它继承 `Vector`，所有方法都带 `synchronized`；而且它的 API 设计有问题（`push/pop` 与 `push/pop` 语义和 `Deque` 不一致，多个栈混用时容易出错）。**`Deque`（`ArrayDeque` 实现）是现代 Java 的栈/队列标准**。

**追问：什么时候该用 `LinkedList`？**
→ **几乎从不用**。唯一站得住脚的理由：**已持有 `ListIterator` 且需要在迭代中频繁删除/插入**。其他情况都用 `ArrayList` 或 `ArrayDeque`。

**追问：集合初始化时的容量估算怎么算？**
→ **`HashMap`：`new HashMap<>(expectedSize / 0.75 + 1)`**（加载因子 0.75）；**`ArrayList`：`new ArrayList<>(expectedSize)`**（精确值即可）。**目的都是避免扩容时的数组拷贝**——这一条在实际项目里能实实在在省下 CPU。
