# 异常处理与泛型

> **什么时候该读**：面试里「异常体系 + 泛型擦除」是必问组合——前者考你会不会设计错误处理，后者考你对 Java 类型系统的理解深度。
> **答题主线**：**「异常是控制流的信号，泛型是编译期的类型契约」**。异常处理讲的是「错误该在哪一层被处理」，泛型讲的是「类型信息在运行时还能不能看到」。

---

## Q1. Java 的异常体系长什么样？`Error` 和 `Exception` 有什么区别？

**答：**

**结论：Java 异常体系的根是 `Throwable`，它分两支：`Error`（JVM 级严重问题）和 `Exception`（程序级可预期问题）。**

```
                    java.lang.Throwable
              （所有异常和错误的根类，都继承自 Object）
                            │
            ┌───────────────┴───────────────┐
            │                               │
      java.lang.Error                java.lang.Exception
      （JVM 层面的严重问题）            （程序可以捕获处理的）
            │                               │
      ┌─────┴─────┐              ┌─────────┴─────────┐
      │           │              │                   │
 VirtualMachineError  LinkageError   RuntimeException   其他 Exception
 StackOverflowError   NoClassDefFoundError  （非受检）    （受检）
 OutOfMemoryError     ClassCastException
```

| 维度 | **Error** | **Exception** |
|------|----------|--------------|
| 语义 | **JVM 或系统级的严重问题** | **程序可以预见并处理的错误** |
| 典型 | `OutOfMemoryError`、`StackOverflowError` | `NullPointerException`、`IOException` |
| 该不该 catch | ⚠️ **通常不该**（catch 后往往也跑不动） | ✅ 应该按类型 catch 并处理 |
| 是受检的吗 | ❌ **都是非受检** | 既有受检也有非受检 |

**三个必须记住的具体类**：

- `OutOfMemoryError`（OOM）：内存不够——分堆、元空间、栈、直接内存几种，排查方向完全不同（见 [[java/02-中段阶段-专题精讲/JVM/排查工具与故障案例]]）；
- `StackOverflowError`：**无限递归**（不是栈内存不够），JVM 自己的保护机制；
- `ExceptionInInitializerError`：静态初始化块抛异常——它会导致后续访问该类时抛 `NoClassDefFoundError`，**真正的根因藏在它里面**。

**⭐ 面试官最爱追问的一句**：`catch (Exception e)` 能接住 `Error` 吗？——**能**！`Error` 是 `Throwable` 的子类，而 `catch (Exception e)` 只捕获 `Exception` 及其子类，**不捕获 `Error`**。能接住 `Error` 的是 `catch (Throwable t)`。⚠️ **所以 `catch (Exception e)` 不会捕获 OOM**——这是好事。

**追问：`NoClassDefFoundError` 和 `ClassNotFoundException` 有什么区别？**
→ 前者是 `Error`（链接/初始化阶段，类之前加载过但初始化失败或运行时找不到），后者是 `Exception`（加载阶段，显式 `Class.forName` 找不到 class 文件）。**`NoClassDefFoundError` 经常是「静态块抛异常」的伪装**——去日志前面找 `ExceptionInInitializerError`。

**追问：为什么 `Error` 和 `Exception` 都继承 `Throwable` 而不是直接继承 `Exception`？**
→ 因为 `Throwable` 是「所有非 JVM 正常流程异常」的公共父类，它提供了 `getMessage()`、`printStackTrace()`、`getCause()`、`addSuppressed()` 这套 API。`Error` 和 `Exception` 是两种不同的**语义分类**——**这个设计本身不重要，重要的是你 catch 的时候知道自己在 catch 哪一类**。

## Q2. 受检异常和非受检异常有什么区别？为什么 Java 要这么设计？

**答：**

**结论：受检异常（Checked Exception）是「编译器强制你处理」的异常；非受检异常（Unchecked）包括 `RuntimeException` 及其子类 + `Error`，编译器不管。**

| | **受检异常** | **非受检异常** |
|---|-------------|-------------|
| 范围 | `Exception` 中**不是** `RuntimeException` 子类的那些 | `RuntimeException` 子类 + `Error` |
| 典型 | `IOException`、`SQLException`、`ClassNotFoundException` | `NullPointerException`、`IllegalArgumentException`、`ArithmeticException`、`ArrayIndexOutOfBoundsException` |
| 编译器 | **强制 catch 或 throws 声明** | 不强制 |
| 语义 | 「**外部世界**可能会失败，且调用方有合理手段应对」 | 「**程序逻辑有 bug**」 |

```java
// ⚠️ 受检异常：编译器逼你处理
public void readFile(String path) throws IOException {
    // IOException 是受检异常，不 catch 也不声明 throws 就编译不过
    new FileInputStream(path).read();
}

// ✅ 非受检异常：编译器不管，但运行时可能炸
public int divide(int a, int b) {
    return a / b;      // b=0 时抛 ArithmeticException
}
```

**⭐ 为什么 Java 要这么设计？——核心思想是「把「必须处理的错误」显式暴露出来」。**

Java 的设计者（C++ 的教训是相反的：没人 catch `int` 返回码，于是错误被一路忽略）认为：

1. **受检异常 = 「调用方确实应该关心」**：比如 `IOException`，调用方可以决定「重试」「换个路径」「记日志降级」——**这些决策只有调用方能做**；
2. **非受检异常 = 「这是 bug，调用方也修不了」**：`NullPointerException` 意味着你少写了一个判空，catch 它然后继续跑只会让 bug 藏得更深。

**⚠️ 但现实中，受检异常被广泛「滥用」**——很多框架的 API 会把受检异常包成非受检的运行时异常（`RuntimeException`），因为强制 catch 逼开发者写出 `catch (IOException e) { e.printStackTrace(); }` 这种假处理。

**决策标准（我实际会怎么选）**：

| 情况 | 选择 |
|------|------|
| **调用方有真实可行的处理策略**（重试、降级、提示用户） | 用**受检异常**，强制它面对 |
| **纯编程错误**（判空、越界、参数非法） | 用**非受检异常**（`IllegalArgumentException` 等） |
| **框架内部的底层异常** | 包成非受检（`RuntimeException`），在边界层统一转成业务异常 |

**追问：Spring 的 `DataAccessException` 是什么类型？**
→ **非受检**（继承 `RuntimeException`）。这是 Spring 有意的设计：**把 `SQLException` 这个受检异常包成非受检**，让业务代码不必层层 catch。⚠️ **代价是：忘记 catch 就直接 500 了**——所以 Spring Boot 提供了 `@RestControllerAdvice` 做全局兜底。

**追问：为什么 `RuntimeException` 不叫 `UncheckedException`？**
→ 历史原因——`RuntimeException` 强调的是「**运行期异常**」（不特指 unchecked），而 `Error` 同样是非受检的。**术语上不严谨，但已成事实**。

**追问：自定义异常该继承哪一类？**
→ **看语义**：
- **业务异常**（订单不存在、余额不足）→ 继承 `RuntimeException`，属于非受检，**不需要在每个调用点声明 throws**；
- **强制调用方处理**（如「必须走审批流程」的业务前置条件）→ 可以继承 `Exception`，但**代价是污染所有调用方的签名**，实践中很少这么干。

**结论：99% 的自定义业务异常继承 `RuntimeException`。**

## Q3. `try-catch-finally` 的执行顺序是什么？`finally` 里 `return` 有什么后果？

**答：**

**正常执行顺序**：`try` → （出异常则 `catch`）→ `finally` 一定执行。

```java
public class FinallyDemo {
    public static void main(String[] args) {
        System.out.println(test(1));   // try 正常返回
        System.out.println(test(0));   // catch 捕获
    }

    static String test(int mode) {
        try {
            if (mode == 0) throw new RuntimeException("boom");
            return "from try";
        } catch (RuntimeException e) {
            return "from catch";       // ⚠️ 这里 return 会等 finally 执行完再返回
        } finally {
            System.out.println("finally 一定会执行");
        }
    }
}
```

**⚠️ `finally` 里 `return` 的后果——这是最高频的陷阱**：

```java
public static int bad() {
    try {
        return 1;
    } finally {
        return 2;        // ⚠️ 覆盖了 try 的 return！实际返回 2
    }
}
```

**结果永远是 2**。原因：`try` 里的 `return 1` 并不是真的「立刻返回」，而是**先把返回值 1 存进一个临时变量，然后去执行 `finally`**；`finally` 里的 `return 2` 会**重新覆盖这个待返回值并直接完成返回**——`try` 里存的值 1 被丢弃了。

**同样危险的还有 `finally` 里抛异常**：

```java
public static int worse() {
    try {
        return 1;
    } finally {
        throw new RuntimeException("finally 炸了");   // ⚠️ try 的返回值直接丢失
    }
}
```

**⚠️ 所以规则很简单：`finally` 里绝对不要写 `return`、`break`、`continue` 或抛异常。** `finally` 块只应该做「**清理**」——关闭资源、恢复状态、还原标志位。

**另外两个 `finally` 的执行特性**：

| 情况 | `finally` 是否执行 |
|------|------------------|
| try 正常结束 | ✅ 执行 |
| try 抛异常且被 catch | ✅ 执行 |
| try 抛异常且未被 catch | ✅ **仍然执行**（然后异常继续向上抛） |
| try 里 `System.exit()` | ❌ **不执行**（JVM 直接退出） |
| JVM 被 kill（SIGKILL） | ❌ 不执行 |
| 死循环卡在 try 里 | ❌ **永远执行不到** |

**追问：`finally` 的作用到底是什么？为什么不直接写在 try 末尾？**
→ 因为**它保证「无论走哪条路都会执行」**——正常返回、异常返回、被 catch、没被 catch 四条路径都能覆盖。这是「资源清理」必需的语义。⚠️ **但如果清理动作本身可能抛异常，它会掩盖掉 try 里的原始异常**——所以资源清理应该用 try-with-resources（见 Q4），它会自动处理异常抑制。

**追问：`return` 和 `finally` 的执行顺序，编译后是什么代码？**
→ 编译器把方法重写成这样（**这就是为什么 `finally` 能覆盖返回值**）：

```java
static int bad() {
    int temp;              // 声明临时变量
    try {
        temp = 1;
        return temp;        // 实际是：把 1 存进 temp，跳到 finally
    } finally {
        temp = 2;
        return temp;        // ⚠️ 这里直接 return，try 的 temp=1 被跳过
    }
}
```

**追问：多个 `catch` 块的匹配顺序是什么？**
→ **从上到下匹配，命中第一个就停**——所以**子类异常必须写在父类异常前面**，否则子类异常永远走不到（编译器会直接报错 "already caught"，这算是 Java 的一个安全检查）。

**追问：`try-catch` 能只写 `try-finally` 吗？**
→ 能，语法合法（`finally` 单独存在）。但**几乎总是应该写成 try-with-resources**（见 Q4）。

## Q4. try-with-resources 是什么？它比 `finally` 里手动 `close()` 好在哪？

**答：**

**结论：try-with-resources 是 Java 7 引入的语法糖，让「声明并使用可自动关闭的资源」变得简洁且不会漏关。**

```java
public class ResourceDemo {
    public static void main(String[] args) {
        // ✅ try-with-resources：资源按声明的逆序自动关闭
        try (BufferedReader reader = new BufferedReader(new FileReader("a.txt"))) {
            System.out.println(reader.readLine());
        } catch (IOException e) {
            System.out.println("读取失败: " + e.getMessage());
        }
    }
}
```

**⚠️ 关键前提**：资源必须实现 `AutoCloseable`（Java 7+）或 `Closeable`（`Closeable extends AutoCloseable`，额外要求 `close()` 不抛 IOException）。`try-with-resources` **只对 `AutoCloseable` 生效**。

**它比手写 `finally` 好在哪（四点）**：

| 对比点 | 手写 `finally` | try-with-resources |
|--------|---------------|-------------------|
| **漏关风险** | ⚠️ 异常发生在 `resource = new X()` 之后、`try` 开始之前时，`close()` 不会被调用 | ✅ **只有资源声明成功后才进入 try**，声明失败则不注册，编译器保证正确 |
| **异常掩盖** | ⚠️ `close()` 抛异常会**覆盖掉 try 里的原始异常** | ✅ **原始异常为主**，关闭异常被「抑制」（suppressed）到原异常上，不会丢 |
| **代码量** | 4~6 行样板 | 1 行 |
| **多个资源** | 手写多个 finally，逆序难保证 | ✅ **自动按逆序关闭**（后声明的先关） |

**「异常抑制」机制是它最被低估的价值**：

```java
try (Buffer b = open()) {
    throw new RuntimeException("主异常");
}   // close() 此时也抛异常
```

结果：抛出的是 **「主异常」**，`close()` 的异常被挂到主异常的 `getSuppressed()` 数组上。⚠️ **手写 finally 的话，`close()` 的异常会把主异常顶掉——原始错误信息彻底丢失，这是线上排查最头疼的问题之一。**

**Java 9 增强**：资源变量可以是**已存在的 effectively final 变量**（之前必须是新声明的）：

```java
var writer = new FileWriter("out.txt");     // Java 9+
try (writer) {
    writer.write("hello");
}
```

**追问：多个资源的关闭顺序？**
→ **逆序**（后声明的先关），相当于栈结构。**这正是我们想要的**——`BufferedReader` 包着 `FileReader`，应该先关 `BufferedReader` 再关 `FileReader`。

**追问：JDK 21+ 的模式匹配 `switch` 能用来做资源管理吗？**
→ ⚠️ **不能自动关资源**。Java 21 正式支持**模式匹配的 `switch`**（JEP 441：类型模式、`case null`、`when` 守卫、record 解构），但**模式变量只是绑定，不会自动调用 `close()`**——JEP 441 里没有任何自动资源管理的语义。**资源释放仍然只有 try-with-resources 这一条正路。**

**追问：`finalize()` 能代替它吗？**
→ **绝对不能**。① `finalize()` **已废弃**（JDK 9 起 deprecated，18 起标记为待移除）；② **执行时机不确定**（GC 何时回收不确定）；③ **对象可达时永远不会被调用**（它依赖对象被回收）；④ **一次异常会终止后续所有 finalizer**。**结论：资源释放一律用 try-with-resources，不要碰 `finalize()`。**

**追问：怎么让自定义类支持 try-with-resources？**
→ 实现 `AutoCloseable`（或 `Closeable`），覆写 `close()`。**关键设计：`close()` 应该声明 `throws Exception` 而不是 `IOException`**——`Closeable` 的 `close()` 只允许抛 `IOException`，而 `AutoCloseable` 允许任意异常，更通用。

## Q5. 怎么设计一个好的自定义异常？异常信息该怎么写？

**答：**

**结论：自定义异常要「携带足够定位问题的上下文」，而不是只写一句「操作失败」。**

```java
// ✅ 好的自定义异常：继承 RuntimeException，携带结构化上下文
public class InsufficientBalanceException extends RuntimeException {

    private final Long userId;
    private final BigDecimal required;
    private final BigDecimal available;

    public InsufficientBalanceException(Long userId, BigDecimal required, BigDecimal available) {
        super(String.format("用户 %d 余额不足：需要 %s，实际可用 %s", userId, required, available));
        this.userId = userId;
        this.required = required;
        this.available = available;
    }

    // getter 省略
}
```

**四条设计原则**：

| 原则 | 说明 |
|------|------|
| **① 继承 `RuntimeException`** | 业务异常不应污染所有调用方的 `throws` 签名 |
| **② 区分「可恢复」与「不可恢复」** | 可恢复（如「余额不足，充值后重试」）→ 提供业务字段供上层判断；不可恢复 → 简单抛出即可 |
| **③ 带上定位信息** | 异常信息里要能看出「**谁的、哪个环节、什么值**」——ID、参数、上下限 |
| **④ 不要在异常信息里塞敏感数据** | 密码、身份证、完整卡号**绝对不能进异常信息**——异常会进日志，日志会被很多人看到 |

**异常信息该怎么写——一个可执行的模板**：

```
<什么操作> 失败：<原因>，<关键上下文：实体ID、参数值、期望 vs 实际>
```

```
❌ "操作失败"
❌ "SQLException"
✅ "扣减库存失败：productId=10086, 请求数量=5, 当前可用库存=3"
```

**⚠️ 异常信息本身也有性能成本**：`new Exception("...")` 会**填充整个调用栈**（`fillInStackTrace`），在高频抛异常的路径上开销明显。**极热路径上的异常要么避免抛出，要么用不带堆栈的异常子类**（覆写 `fillInStackTrace()` 置空，或用 `super(msg, null, false, writableStackTrace)` 构造）。

**追问：异常应该在哪里捕获？**
→ **在「能做决策」的边界捕获**。判断标准是三个问题：
1. 我能不能处理它（重试、降级、提示用户）？
2. 我能不能补充更有价值的信息？
3. 捕获之后，我能不能给上层一个更有意义的错误？

**三个都不能 → 不捕获，让它往上抛**，在最外层统一处理（Spring 的 `@RestControllerAdvice`）。

**追问：为什么很多框架把底层异常包装成业务异常？**
→ 为了**把技术细节和业务语义分离**。`SQLException` 是技术层的，Controller 直接返回 `数据库连接失败` 对用户无意义；包装成 `OrderCreateException("订单号 " + orderId + " 创建失败")` 后，上层既能给用户友好提示，又能记录完整的技术堆栈。

**追问：`throw` 和 `throws` 有什么区别？**
→ `throw` 是**抛出一个具体的异常对象**（执行动作，语法是 `throw new XxxException(...)`）；`throws` 是**在方法签名上声明「本方法可能抛出哪些异常」**（声明，语法是 `void f() throws IOException`）。**一个是动词，一个是声明。**

## Q6. Java 的泛型解决了什么问题？泛型方法和泛型类怎么写？

**答：**

**结论：泛型把「类型检查」从运行时提前到了编译期，同时避免了强制类型转换。**

**泛型解决的问题（对比泛型前）：**

```java
// ❌ 泛型前：类型不安全 + 到处强转
List list = new ArrayList();
list.add("hello");
String s = (String) list.get(0);      // 忘了强转 → ClassCastException，运行时才炸

// ✅ 泛型后：编译期就知道类型
List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);                // 不需要强转
list.add(123);                         // ⚠️ 编译期直接报错
```

**三个具体收益**：

| 收益 | 说明 |
|------|------|
| **类型安全** | 编译期拦下类型错误，不用等到线上 `ClassCastException` |
| **消除强转** | 取出来直接可用，代码更干净 |
| **代码复用** | 一个类适配多种类型（`List<String>` / `List<Integer>`），**不用为每种类型写一个类**（这是「泛型」相对「多态 + 适配器」方案的核心价值） |

**泛型类**：

```java
public class Box<T> {              // T 是类型参数
    private T content;

    public void set(T content) { this.content = content; }
    public T get() { return content; }
}

// 使用
Box<String> b = new Box<>();
b.set("hi");
String v = b.get();       // 无需强转
```

**泛型方法**：

```java
public class Utils {
    // <T> 是方法自己的类型参数，可以独立于类
    public static <T> T firstNonNull(T a, T b) {
        return a != null ? a : b;
    }

    public static <T extends Comparable<T>> T max(List<T> list) {
        // ⚠️ extends 保证 T 可比较，编译器才能写 list.get(0).compareTo(...)
        T best = list.get(0);
        for (T item : list) {
            if (item.compareTo(best) > 0) best = item;
        }
        return best;
    }
}
```

⚠️ **泛型方法 vs 泛型类的方法**：
- **泛型类**的类型参数属于**类**，`new Box<>()` 时指定，**一次指定，该类的所有实例共享**；
- **泛型方法**的类型参数属于**方法**，由编译器在调用时**根据实参推断**（如 `Collections.emptyList()`）。

**追问：泛型方法的类型参数怎么推断？**
→ **靠实参**：`Utils.firstNonNull("a", "b")` → 推断 `T = String`；`Collections.<String>emptyList()` 可以**显式指定**（当推断不出来或想强制时）。

**追问：为什么泛型不能用于基本类型？**
→ ⚠️ **泛型是类型擦除的**（见 Q7）——擦除后 `Box<int>` 和 `Box<Integer>` 都会变成 `Box`，JVM 层面无法区分。所以**泛型参数只能是引用类型，不能是基本类型**。`List<int> list = new ArrayList<>();` 编译报错。

**变通办法**：Java 8 起接口**可以有默认方法**，所以 JDK 提供了一组**针对基本类型的特化接口**：`IntStream`、`LongStream`、`DoubleStream`、`IntFunction`、`ToIntFunction` 等。**这些是独立接口，不是泛型的特化**——所以 `IntStream` 和 `Stream<Integer>` 是两个不同的类型，不能互换。

**追问：泛型有 checked exception 的对应版本吗？**
→ 没有。`Function<T, R>` 不抛受检异常，`Function` 的 `apply` 声明 `throws Throwable`——⚠️ **这是个坑**：`Function.apply` 声明的是 `throws Throwable`，但实现时不能抛受检异常（因为接口方法签名不允许），**所以 `Function` 无法表达「会抛 IOException 的转换」**。需要时自己定义带受检异常的函数接口。

## Q7. 什么是类型擦除？为什么 Java 要这么做？

**答：**

**结论：类型擦除是指「编译器把泛型类型信息擦掉，只保留原始类型（raw type）」——这是 Java 泛型实现的核心机制，也是它所有限制的根源。**

**擦除后的样子**：

```java
// 源码
public class Box<T> {
    private T content;
    public T get() { return content; }
    public void set(T t) { this.content = t; }
}

// 编译后的字节码（等价于）
public class Box {
    private Object content;          // ⚠️ T 被擦成 Object
    public Object get() { return content; }
    public void set(Object t) { this.content = t; }
}
```

**为什么 Java 要这么做？**

**最主要的原因是「二进制兼容性」**。Java 的类文件格式在泛型出现之前就定好了，**泛型不能改变字节码的结构**——否则所有旧的 class 文件、所有的 JDK 内部实现都会失效。所以：

| 动机 | 说明 |
|------|------|
| **① 保持二进制兼容** | 泛型是**编译期特性**，不进入字节码。`List<String>` 和 `List<Integer>` 在字节码里都是 `List` |
| **② 不需要改 JVM** | JVM 完全不需要理解泛型 |
| **③ 兼容旧代码** | Java 5 之前写的 `List`（raw type）代码在 Java 5+ 依然能编译（只是有警告） |

**类型擦除的三个必然后果（面试高频）**：

| 后果 | 例子 | 说明 |
|------|------|------|
| **① 不能 `new T[]`** | `new T[10]` 编译报错 | 运行时不知道 T 是什么，无法确定数组类型 |
| **② 不能 `instanceof T`** | `obj instanceof T` 编译报错 | 同上，只能 `instanceof Object` 或用通配符 `instanceof List<?>` |
| **③ 静态成员不能用类的类型参数** | `static T instance;` 编译报错 | 类型参数属于实例，静态成员是类级别的 |

**但 Java 为泛型加了「桥接方法」（bridge method）来保住多态**：

```java
// 接口
interface Comparator<T> {
    int compare(T a, T b);
}

// 实现类：T 被具体化为 String
class StringComparator implements Comparator<String> {
    @Override
    public int compare(String a, String b) { return a.compareTo(b); }
}
```

擦除后，`Comparator` 的方法签名变成 `compare(Object, Object)`，而实现类是 `compare(String, String)`——**签名不匹配，多态就断了**。编译器为此生成一个**桥接方法**：

```java
// 编译器自动生成的桥接方法
public int compare(Object a, Object b) {
    return compare((String) a, (String) b);   // 转发到上面的方法
}
```

**所以运行时多态依然成立**——这个细节能直接回答「为什么擦除后泛型还能多态」。

**追问：既然擦除了，那 `List<String>` 和 `List<Integer>` 在运行时能区分吗？**
→ **不能**。⚠️ 这就是 **`ClassCastException` 的经典场景**：

```java
List<String> list = new ArrayList<>();
list.add("a");
Object o = list.get(0);
// 在 unchecked 转换的场景下，编译器插入了 checkcast 指令
Integer i = (Integer) o;    // ⚠️ 运行时抛 ClassCastException
```

**关键机制**：编译器在需要时会插入 **`checkcast` 字节码指令**做运行时类型检查——这保证了「编译期允许的 unsafe cast 在运行期会被拦住」。

**追问：为什么 Java 不用「保留泛型信息」的方式（比如 C#）？**
→ **C# 的泛型是运行时泛型**（需要运行时类型元数据），C# 编译器为每个特化类型生成独立的机器码。这带来更好的性能，但**破坏了二进制兼容性**。Java 选了另一条路：**源码层面泛型安全（编译期检查 + checkcast），运行时放弃类型信息**。代价是基本类型不能泛型、性能有装箱开销。

**追问：Java 有没有绕过擦除的办法？**
→ 有，但都是「技巧」：
- **自己把 `Class` 对象当类型参数传进来**：`class Box<T> { Class<T> type; }`；
- **用反射读泛型签名**：`field.getGenericType()` 能拿到 `List<String>` 这样的信息（**这是 Spring 泛型注入、MyBatis 类型推断的基础**）；
- **`TypeToken` 模式**（Gson/Guava 用的）：用匿名子类把类型信息"捕获"下来，绕过擦除。

## Q8. 泛型通配符 `?`、`? extends T`、`? super T` 分别怎么用？

**答：**

**结论：记住 PECS 原则——Producer Extends, Consumer Super（生产者用 extends，消费者用 super）。**

| 通配符 | 语义 | 能读 | 能写 |
|--------|------|------|------|
| **`? extends T`** | 「T 或 T 的**子类型**」（协变） | ✅ 能读成 T | ❌ **不能写**（写进去的实际类型不确定） |
| **`? super T`** | 「T 或 T 的**父类型**」（逆变） | ⚠️ 只能读成 `Object` | ✅ **能写 T 及其子类型** |
| **`?`** | 任意类型（无界） | 只能读成 `Object` | ❌ 不能写 |

**用 `? extends T` 的场景：生产者（只往外读）**：

```java
public class Producer {
    // ✅ 返回 List<? extends Number>：调用方可以当 List<Number> 用
    public static List<? extends Number> produce() {
        return List.of(1, 2.5, 3L);
    }
}

public static void main(String[] args) {
    List<? extends Number> nums = Producer.produce();
    Number n = nums.get(0);      // ✅ 读出来可以当 Number
    // nums.add(4);              // ❌ 编译错误：不能往里写
}
```

**用 `? super T` 的场景：消费者（往里写）**：

```java
public class Consumer {
    // ✅ 参数 List<? super Integer>：可以接收 List<Integer>、List<Number>、List<Object>
    public static void consume(List<? super Integer> list) {
        list.add(1);             // ✅ 能写
        list.add(2);
        // Integer i = list.get(0);   // ⚠️ 只能读成 Object
    }
}
```

⭐ **PECS 的经典应用是 `Collections.copy` 的签名**：

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src)
```

- **src 是生产者**（把它的元素读出来）→ 用 `? extends T`；
- **dest 是消费者**（往里写）→ 用 `? super T`。

**⭐ 实战中最好记的例子：`List<? super Integer>` 用来接收任意「Integer 的父类型集合」**：

```java
List<Integer> ints = new ArrayList<>();
List<Number> nums = new ArrayList<>();
List<Object> objs = new ArrayList<>();

Consumer.consume(ints);   // ✅
Consumer.consume(nums);   // ✅
Consumer.consume(objs);   // ✅
```

**⚠️ 为什么 `? super T` 读出来只能是 `Object`？** 因为集合里的实际元素类型可能是 `T` 的任意父类型（甚至是 `Object`），**你无法安全地把它当成 `T` 读出来**。

**追问：无界通配符 `<?>` 和 `? extends Object` 一样吗？**
→ **基本等价**。`<?>` 就是 `? extends Object` 的简写。⚠️ **区别在于语义**：`List<?>` 表达「我不管里面是什么类型，只关心它的数量和迭代」，而 `List<Object>` 表达「这是一个装 Object 的列表，可以装任何东西进去」——**`List<Object>` 仍然可以 `add` 任何对象，`List<?>` 不行**。

**追问：`List<? extends Number>` 和 `List<Number>` 有什么区别？**
→ `List<Number>` **可以写**（可以 `add(1)`），`List<? extends Number>` **不能写**。但 `List<Number>` **不能接收 `List<Integer>`**（泛型不可变——`List<Integer>` 不是 `List<Number>` 的子类）。所以 `? extends` 通配符的价值就是**解决「协变」的问题**。

**追问：为什么泛型是不可变的（invariant）？**
→ **Java 为了类型安全，故意不允许 `List<Integer>` 赋值给 `List<Number>`**。因为如果允许：

```java
List<Number> list = new ArrayList<Integer>();
list.add(3.14);       // ⚠️ 编译能过，但运行时会 ClassCastException
```

**通配符就是 Java 提供的「安全的协变/逆变」方案**——只放开「读」或「写」其中一侧，另一侧保持类型安全。

## Q9. 什么是堆污染（heap pollution）？什么是原始类型（raw type）？

**答：**

**结论：堆污染是指「程序中出现一个参数化类型与原始类型混合，导致运行时可能抛 `ClassCastException` 的状态」。**

**典型的堆污染场景**：

```java
public class HeapPollution {
    // ⚠️ raw type：List 不带类型参数
    @SuppressWarnings("unchecked")
    static List<String> build() {
        List raw = new ArrayList();     // ⚠️ 原始类型
        raw.add("hello");
        raw.add(123);                   // ⚠️ 塞了个 Integer 进去，编译器不管
        return raw;                     // ⚠️ 隐式转成 List<String>，编译器只警告
    }
}
```

**问题的本质**：`build()` 返回的 `List<String>` 里**实际可能装着 `Integer`**。调用方写 `String s = list.get(0);` 时，编译器插入了 `checkcast String` → **运行时抛 `ClassCastException`**，而且错误现场在**调用方**，离真正的错误源头（`raw.add(123)`）很远。

**原始类型（raw type）**：使用泛型类时**不写类型参数**，比如 `List` 而不是 `List<String>`。Java 允许这么写（为了兼容 Java 5 之前的代码），但：

- 编译器给**警告**（unchecked warning），不是错误；
- ⚠️ **所有原始类型互不兼容**：`List` 和 `ArrayList` 是不同的类型，`List l = new ArrayList()` 可以（因为 `ArrayList` 实现了 `List`），但 `List l = new LinkedList` 之后不能赋值给 `ArrayList` 变量——**原始类型会丢失所有泛型信息**。

**⚠️ 更隐蔽的场景——方法参数传递时污染**：

```java
static void addToList(List list, Object o) {   // ⚠️ raw type 参数
    list.add(o);      // 任何类型都能塞进去
}
```

**如何在工程上避免堆污染**：

| 做法 | 说明 |
|------|------|
| **① 不用原始类型** | 所有集合、工具方法都写全类型参数 |
| **② 用 `List<?>` 代替 `List`** | 需要「只读任意类型」时，`List<?>` 比 raw type 安全得多——**禁止写入**，从根上杜绝污染 |
| **③ `@SafeVarargs`** | 泛型可变参数方法上标注（Java 9+ 允许私有实例方法用），消除 unchecked 警告 |
| **④ 局部变量用 `var`** | Java 10+ 的 `var` 会**推断出具体类型**（`var list = new ArrayList<String>()`），比 raw type 安全 |

**追问：怎么消除 unchecked 警告？**
→ **不要用 `@SuppressWarnings("unchecked")` 掩盖问题**——它只是让编译器闭嘴，堆污染还在。**正确做法是修好类型**：把 raw type 改成参数化类型，用 `<?>` 表达「只读未知类型」，或者在边界处做一次显式转换。

**追问：`@SuppressWarnings` 该怎么用？**
→ **在「无法避免 unchecked 操作」的最小范围上使用**——比如一个内部会做安全检查的工具方法，加在方法上并**写清原因注释**。⚠️ **不要在类级别加**（那等于关掉了整个类的类型检查）。

## Q10. 泛型在框架里是怎么被用起来的？为什么 Spring 能注入带泛型的参数？

**答：**

**结论：泛型信息虽然在运行时被擦除了，但被「反射保留」在了 class 文件的签名属性里，框架通过反射读出来就能实现类型推导。**

**Spring 的案例：泛型限定注入（Generic Type Resolution）**

```java
public interface UserRepository extends JpaRepository<User, Long> { }
//                        ^ 泛型参数：实体类型 = User，主键类型 = Long
```

Spring Data JPA 靠这个**推断出**：
- 实体类是 `User`（要扫描 `@Entity`、映射表）；
- 主键类型是 `Long`（决定 `findById` 的参数类型）。

**原理**：类文件里有一个 `Signature` 属性记录了泛型签名，**运行时可通过反射读到**：

```java
public class TypeUtils {
    public static void main(String[] args) throws Exception {
        // 读字段的泛型类型
        java.lang.reflect.Field f = Impl.class.getDeclaredField("list");
        System.out.println(f.getGenericType());   // java.util.List<java.lang.String>

        // 读方法参数的泛型类型
        java.lang.reflect.Method m = Impl.class.getDeclaredMethod("add", List.class);
        System.out.println(m.getGenericParameterTypes()[0]); // java.util.List<java.lang.String>
    }

    static class Impl {
        List<String> list;
        void add(List<String> items) {}
    }
}
```

⚠️ **注意区别**：
- `field.getType()` → 只拿到 `List`（**擦除后的原始类型**）；
- `field.getGenericType()` → 拿到 `List<String>`（**保留了泛型信息**，因为它在 class 文件的 `Signature` 属性里）。

**这就是「类型擦除」和「反射能读泛型」能同时成立的原因**——泛型参数**不出现在方法签名和运行时类型里**，但**作为一个独立的属性被保留下来**。

**其他框架里的用法**：

| 框架 | 怎么用泛型 | 效果 |
|------|-----------|------|
| **Spring Data JPA** | `Repository<User, Long>` | 推断实体类型和主键类型 |
| **Spring 的 `@RequestBody` 转换** | 方法参数泛型 `List<OrderVO>` | Jackson 按泛型决定反序列化成什么 |
| **MyBatis** | `Mapper<T>` | 生成代理时确定返回类型 |
| **Gson / Jackson** | `TypeToken<List<String>>()` | 正确反序列化嵌套泛型 |
| **Retrofit** | `Call<List<User>>` | 解析响应类型 |

**追问：为什么 `new ArrayList<String>()` 的类型信息读不出来，但字段/方法签名能读出来？**
→ 因为**局部变量的类型信息在编译后就完全消失了**（不进 class 文件），而**字段和方法的签名属性是 class 文件格式的一部分**，会被保留。⚠️ 这就是为什么 Spring 的泛型推导**只能从字段、方法参数、返回值、类签名这几个地方拿信息**，拿不到局部变量。

**追问：泛型 + 反射的局限？**
→ **无法区分「类型参数本身是泛型」的情况**。比如 `class A<T> { List<T> list; }`——反射能读到 `List<T>`，但 `T` 绑定到什么，取决于 `A` 被怎么实例化，这需要更复杂的 `TypeVariable` 解析逻辑。**Spring 自己实现了一套完整的泛型解析器（`GenericTypeResolver`、`ResolvableType`），就是这个原因。**

**追问：为什么泛型用起来「类型安全但运行时仍可能出错」？**
→ 因为**擦除**。编译期检查在「跨类型边界」的地方会失效——比如你从 `Object` 强转、或从 raw type 传入、或通过反射构造。**泛型保证的是「源码层面的类型安全」，不是「运行时的绝对安全」**——运行时的那道防线是 `checkcast` 指令。
