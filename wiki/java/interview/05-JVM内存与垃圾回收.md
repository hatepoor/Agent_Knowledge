# JVM 内存与垃圾回收

> **什么时候该读**：面试里 JVM 是**分值最高的模块**，也是最容易用「背名词」糊弄过去的模块。面试官问「讲讲 GC」，答「分代收集，G1 是默认」只能拿一半分。
> **答题主线**：**「内存分哪几块 → 对象怎么放进去 → 怎么判断该回收 → 怎么回收 → 出问题怎么查」**。这五段对应五组问题，答每一题都要能落回这条链上。机制详解见 [[java/02-中段阶段-专题精讲/JVM/JVM内存区域与对象布局]] 与 [[java/02-中段阶段-专题精讲/JVM/垃圾回收与调优]]。

## Q1. JVM 运行时数据区有哪些？哪些是线程共享的？

**答：**

**结论：5 个区域——堆、方法区、虚拟机栈、本地方法栈、程序计数器。前两个共享，后三个线程私有。**

| 区域 | 存什么 | 共享 | 异常 |
|------|-------|------|------|
| **堆（Heap）** | 所有对象实例、数组 | ✅ 共享 | `OutOfMemoryError: Java heap space` |
| **方法区 / 元空间** | 类结构、静态变量、运行时常量池、JIT 代码 | ✅ 共享 | `OutOfMemoryError: Metaspace` |
| **虚拟机栈** | 方法调用栈帧（局部变量表、操作数栈、动态链接、返回地址） | ❌ 私有 | `StackOverflowError` / OOM |
| **本地方法栈** | native 方法的调用 | ❌ 私有 | 同上 |
| **程序计数器（PC）** | 当前线程执行到的字节码行号 | ❌ 私有 | **唯一不会 OOM 的区域** |

**⭐ 三个必答的追问点**：

1. **「哪些是共享的？」** → 堆 + 方法区。其余三个每个线程一份。
2. **「哪个不会 OOM？」** → **程序计数器**。因为它是唯一一个**纯寄存器级别的、不涉及内存分配**的区域——它只记录行号。⚠️ 其他区域哪怕溢出也只是记录信息，不需要额外空间。
3. **「方法区在哪儿？」** → ⚠️ **JDK 8 起是元空间（Metaspace），在本地内存里，不在堆里**。所以 `-Xmx` 管不到它，要用 `-XX:MaxMetaspaceSize` 控制。

**⚠️ 三个容易说错的点**：

| 常见错误 | 正确说法 |
|---------|---------|
| 「方法区就是永久代」 | JDK 7 及以前是永久代（PermGen，在堆内），**JDK 8 起是元空间，在本地内存** |
| 「字符串常量池在方法区」 | **JDK 7 起常量池搬到了堆**，方法区（元空间）里存的是类的结构信息、静态变量等 |
| 「栈放的是基本类型」 | 栈放的是**局部变量表里的引用和基本类型值**；对象本体永远在堆上 |

**追问：为什么程序计数器必须是线程私有的？**
→ 因为它记录的是「**当前线程**执行到哪一行字节码」。如果共享，多线程切换时这个值会被别的线程改掉，恢复现场时就找错位置了。**每个线程有自己的执行轨迹，就必须有自己的行号记录。**

**追问：线程栈会 OOM 吗？什么情况？**
→ 会，两种：① **无限递归** → `StackOverflowError`（这是栈「溢出」，通常不叫 OOM）；② **线程太多，每个线程的栈独立占本地内存** → `OutOfMemoryError: unable to create new native thread`。⚠️ 调大 `-Xss` 会加剧第二种，所以**线程多时应该调小 `-Xss`**。

## Q2. 一个 Java 对象在内存里长什么样？Mark Word 里存了什么？

**答：**

**结论：对象分三段——对象头、实例数据、对齐填充。对象头里最重要的是 Mark Word。**

```
┌──────────────────────────────────────────────┐
│ 对象头（Object Header）                       │
│  ① Mark Word（8 字节 / 64 位）               │
│  ② 类型指针 Klass Pointer（4 或 8 字节）      │
├──────────────────────────────────────────────┤
│ 实例数据（Instance Data）                     │
│   父类字段 + 本类字段（按宽度排列，减少空洞）  │
├──────────────────────────────────────────────┤
│ 对齐填充（Padding）                           │
│   补齐到 8 字节整数倍                          │
└──────────────────────────────────────────────┘
```

**Mark Word 里存什么——随锁状态复用同一块空间**：

| 锁状态 | 存的内容 |
|--------|---------|
| **无锁** | 对象哈希码（31 位）+ GC 年龄（4 位）+ 偏向标志（1 位） |
| **轻量级锁** | 指向栈中锁记录（Lock Record）的指针 |
| **重量级锁** | 指向 `Monitor` 对象的指针 |

⚠️ **偏重级锁的内容要按版本说**：偏向锁在 **JDK 15 起默认禁用并标记废弃（JEP 374）**，JDK 18 起被移除。**面试时不要说「现在有四种锁状态」，应该说「历史上还有偏向锁，现已废弃」。**

**⭐ 面试官最爱的追问：为什么 GC 年龄最大是 15？**

**因为 GC 年龄只有 4 个二进制位**，能表示 0~15。所以对象在 Survivor 区熬过 15 次 GC 就会晋升老年代（`-XX:MaxTenuringThreshold` 默认也是 15）。**这不是随便定的数字，是硬件位宽的直接结果。**

**指针压缩（Compressed Oops）**：

- 64 位 JVM 上引用本该占 8 字节，**开启指针压缩后只占 4 字节**（堆 ≤ 32GB 时有效）；
- 好处：对象更小、对 CPU 缓存更友好——**堆 30GB 可能比 32GB 跑得更快**；
- ⚠️ **堆超过 32GB 后指针压缩失效，对象变大**——这是「堆不是越大越好」的技术原因之一。

**追问：对象的哈希码为什么存在 Mark Word 里？**
→ 因为 `Object.hashCode()` 的值**第一次计算后要缓存起来**（否则每次调用都重算，太慢），而对象上**没有专门存哈希码的字段**——Mark Word 是唯一可复用的 32/64 位空间。这也解释了为什么**「可变对象不适合当 HashMap 的 key」**：哈希码被缓存了，内容变了哈希就失效。

**追问：Java 25 的「紧凑对象头」是什么？**
→ **Java 25 起可选开启**（`-XX:+UseCompactObjectHeaders`），**Java 27 起默认开启**。它把 Mark Word 从 64 位压到更小，**直接减少所有对象的内存占用**（对海量小对象场景收益明显）。⚠️ **但它要求启用紧凑对象头时不能使用偏向锁**——而偏向锁本来就已废弃，所以不冲突。

## Q3. `new` 一个对象，JVM 内部做了什么？

**答：**

**结论：五步——类加载检查 → 分配内存 → 零值初始化 → 设置对象头 → 执行构造器。**

```java
User u = new User("张三", 25);
```

| 步骤 | 做什么 | 关键点 |
|------|-------|--------|
| **① 类加载检查** | 检查 `User` 类是否已加载 | 没加载 → 触发类加载（见 [[java/02-中段阶段-专题精讲/JVM/类加载机制]]） |
| **② 分配内存** | 在堆上划一块空间 | 方式取决于堆是否规整：**指针碰撞** vs **空闲列表** |
| **③ 零值初始化** | 把这块内存**全部置零** | ⚠️ **这就是「对象字段一定有默认值」的物理原因** |
| **④ 设置对象头** | 写 Mark Word + 类型指针 | 哈希码此时还是 0，要等首次调用 `hashCode()` 才生成 |
| **⑤ 执行 `<init>`** | 跑构造器，赋值真实值 | 到这一步对象才真正可用 |

**⭐ 面试官最爱追问第 ② 步：并发分配怎么办？**

两种解法：

| 方案 | 机制 |
|------|------|
| **TLAB**（Thread Local Allocation Buffer） | **每个线程在 Eden 区预分一小块私有空间，分配时不用加锁**。⭐ **默认开启**，是并发分配的**主力方案** |
| **CAS 重试** | TLAB 用完时，在 Eden 区上用 CAS 做原子分配，失败就重试 |

**追问：第 ③ 步的「零值初始化」和第 ⑤ 步的「构造器赋值」有什么区别？**
→ **零值初始化是 JVM 层面的、语言层面的默认值**（`int` → 0、引用 → null、boolean → false），**发生在内存分配后、构造器执行前**；构造器赋值是**你写的业务代码**。⚠️ **如果构造器里读了另一个还没赋值的字段，读到的是零值而不是「未初始化」**——这是 Java 字段初始化顺序的经典坑。

**追问：对象一定在堆上吗？**
→ **不一定**。JIT 的**逃逸分析**（escape analysis）会判断对象有没有逃出方法：没逃出 → **栈上分配**（不占堆、不用 GC）；没逃出且字段可拆 → **标量替换**（拆成几个局部变量）。所以「new 出来的东西都在堆上」是**不准确的**——但**这些优化是 JIT 自动做的，不能手动控制**。

**追问：大对象怎么分配？**
→ **优先在 Eden 区分配**；Eden 放不下时：① 对象很大（超过某个阈值）→ **直接进老年代**；② Eden 剩余空间不够但对象能放下 → 触发 Young GC 后再分配。⚠️ `-XX:PretenureSizeThreshold`（大对象直接进老年代）**只对 Serial/ParNew 有效，G1 不按这条规则**——G1 用 Humongous Region 单独存大对象。

## Q4. 怎么判断一个对象可以被回收？GC Roots 有哪些？

**答：**

**结论：Java 用「可达性分析」——从 GC Roots 出发遍历对象图，走不到的（不可达）就是垃圾。**

**为什么不用引用计数？**

| 方案 | 问题 |
|------|------|
| **引用计数**（Python CPython 用） | ⚠️ **无法处理循环引用**——两个对象互相引用、彼此都不再被外部引用，计数永远不为 0 |
| **可达性分析**（Java 用） | 需要从根遍历一遍，但**能正确处理循环引用** |

**GC Roots 有哪些（必须能背）**：

1. **虚拟机栈中引用的对象**（方法里的局部变量——最常见）；
2. **方法区中静态变量引用的对象**；
3. **方法区中常量引用的对象**（如字符串常量池里的字符串）；
4. **本地方法栈中 JNI 引用引用的对象**；
5. **JVM 内部引用**（基本类型的 Class 对象、常驻在内存中的异常对象、系统类加载器）；
6. **被 `synchronized` 持有的对象**（锁膨胀成重量级锁时，Monitor 记录了对象引用）。

⭐ **记忆口诀：「栈上的局部变量、静态变量、常量」**——这三类是最高频的 GC Roots 来源。

**四种引用强度（决定「什么时候被回收」）**：

| 引用类型 | 回收时机 | 典型用途 |
|---------|---------|---------|
| **强引用** | 永不主动回收 | 普通对象 |
| **软引用** `SoftReference` | **内存不足时**才回收 | 本地缓存、图片缓存 |
| **弱引用** `WeakReference` | **下次 GC 必回收** | `ThreadLocalMap` 的 key、`WeakHashMap` |
| **虚引用** `PhantomReference` | 随时可回收，回收时收到通知 | 管理直接内存（NIO 的 Cleaner） |

**追问：`ThreadLocalMap` 的 key 为什么用弱引用？**
→ `ThreadLocalMap` 是 `Thread` 持有的一份 Map，**key 是 `ThreadLocal` 实例，value 是要存的变量**。如果 `ThreadLocal` 本身长期存活（比如被线程池里的线程持有），key 永不消失 → value 也永不回收 → **内存泄漏**。用弱引用后，**`ThreadLocal` 没有其他强引用时，key 会被回收，Map 里对应的 value 变成 null**——这就是为什么用完 `ThreadLocal` 必须 `remove()`（否则 value 还占着内存，只是不再能通过 `get()` 访问到）。

**追问：对象「死」了为什么还要标记两次？**
→ 第一次标记：可达性分析判定不可达；此时检查对象是否重写了 `finalize()` 且未执行过 → 有则放入 **F-Queue** 等待执行；**如果 finalize() 里让对象重新可达（复活）**，则撤销标记；否则第二次标记 → 真正回收。⚠️ **`finalize()` 已废弃（JDK 9 起 deprecated，18 起标记待移除）**，生产代码绝不能依赖它。

**追问：软引用和弱引用怎么选？**
→ 看**「丢了会不会影响正确性」**：软引用（`SoftReference`）在**内存紧张时才回收**，适合当**内存缓存**（图片、字典数据）——JVM 还有富余内存时它就留着；弱引用（`WeakReference`）**下次 GC 必被回收**，适合表达「**只是顺带引用一下**」的弱关联（如 `ThreadLocalMap` 的 key、`WeakHashMap` 的键）。⚠️ **软引用的回收时机由 JVM 决定，不可控**——不要用它做关键数据的唯一持有者。

## Q5. GC 有哪些算法？分代模型是怎么来的？

**答：**

**结论：三种基础算法 + 一个分代假说。**

**三种基础算法**：

| 算法 | 做法 | 优点 | 缺点 |
|------|------|-------|------|
| **标记-清除** | 标记存活 → 清除未标记 | 简单、不移动对象 | ⚠️ **产生内存碎片** |
| **复制** | 存活对象复制到另一块空间 | 无碎片、分配快（指针碰撞） | ⚠️ **浪费一半空间** |
| **标记-整理** | 标记存活 → 向一端移动 | 无碎片 | ⚠️ **移动成本高** |

**⭐ 核心洞见——分代假说（Generational Hypothesis）**：

> **绝大多数对象「朝生夕死」，只有少数对象会长期存活。**

**所以不同区域用不同算法**：

| 区域 | 对象特征 | 使用的算法 |
|------|---------|-----------|
| **新生代** | 死亡率极高（90%+） | **复制算法**——只需要拷贝那 10% 的存活对象，极快 |
| **老年代** | 存活率高 | **标记-清除 / 标记-整理** |

**这就是「为什么新生代只占 1/3 堆空间」的来源**——它只需要装「马上就要死」的对象。

**分代模型的结构**：

```
堆
├── 新生代 Young（默认约占 1/3）
│   ├── Eden（8/10）        ← 新对象都在这分配
│   ├── Survivor 0（1/10）  ← 存活对象在这里轮换
│   └── Survivor 1（1/10）
└── 老年代 Old（默认约占 2/3）  ← 长期存活对象
```

**对象晋升老年代的四种方式**：

| 规则 | 说明 |
|------|------|
| **熬过 N 次 Young GC** | GC 年龄 ≥ `MaxTenuringThreshold`（默认 15）→ 晋升 |
| **动态年龄判定** | Survivor 中**同龄对象总和 > 一半** → 直接晋升（不用等到 15） |
| **大对象直接进老年代** | 受 `-XX:PretenureSizeThreshold` 控制（⚠️ 只对 Serial/ParNew 有效，G1 不按此规则） |
| **Survivor 放不下** | 直接晋升老年代 |

**追问：为什么 Survivor 要有两个？**
→ **为了避免内存碎片**。复制算法需要一块「干净的目标空间」——如果只有一个 Survivor，复制完就满了，没地方复制了。**两个 Survivor 轮换使用：A → B → A**，每次 GC 把存活对象从一块复制到另一块，然后清空原来那块。

**追问：Minor GC / Young GC / Full GC 分别是什么？**
→ **Minor GC（Young GC）**：只回收新生代（Eden + Survivor），**触发频繁、停顿短（通常几毫秒到几十毫秒）**。**Full GC**：回收整个堆 + 方法区，**停顿长（几百毫秒到几秒）**，是性能事故。

**Full GC 的触发条件**（面试常问）：① 老年代空间不足；② 元空间不足；③ 晋升失败（老年代放不下要晋升的对象）；④ CMS 的并发模式失败；⑤ 显式调用 `System.gc()`（⚠️ 只是建议，可用 `-XX:+DisableExplicitGC` 禁用）。

**追问：为什么 Full GC 这么慢？**
→ 因为它要**处理整个堆**——标记阶段要遍历所有存活对象（STW 期间），还要处理引用链、Remembered Set 等。**Full GC 通常意味着「已经攒了很久没回收干净」，是问题的信号而不是解决方案。**

## Q6. 常见 GC 收集器有哪些？G1 和 ZGC 分别适合什么场景？

**答：**

**结论：G1 是 JDK 9 起的默认收集器；ZGC 追求亚毫秒停顿。CMS 已被移除。**

| 收集器 | 分代 | 算法 | 特点 | 状态 |
|--------|------|------|------|------|
| **Serial** | 新生代 | 复制 | 单线程，最简单 | 小内存/客户端 |
| **ParNew** | 新生代 | 复制 | Serial 的多线程版 | 曾与 CMS 搭配 |
| **Parallel Scavenge** | 新生代 | 复制 | **吞吐量优先** | JDK 8 默认新生代 |
| **CMS** | 老年代 | 标记-清除 | 并发回收，低停顿 | ⚠️ **JDK 14 已移除** |
| ⭐ **G1** | 整堆 | 复制 + 标记-整理 | **Region 化，可预测停顿** | ⭐ **JDK 9+ 默认** |
| **ZGC** | 整堆 | 染色指针 + 读屏障 | **亚毫秒停顿** | JDK 21+ 分代 ZGC |
| **Shenandoah** | 整堆 | 转发指针 | 低停顿 | OpenJDK 发行版提供 |

**⭐ G1 为什么成为默认（重点）**：

**核心创新：把堆切成等大的 Region（1~32MB），不再物理分代。**

```
堆 = 多个 Region（每个 Region 逻辑上可以是 Eden / Survivor / Old / Humongous）
     ↓
Young GC：回收所有 Eden Region（复制存活对象到 Survivor）
     ↓
Mixed GC：按「回收收益」排序，优先回收垃圾最多的 Region
          （Garbage First 这个名字的由来）
```

**G1 的四个关键特性**：

1. **可预测停顿**：`-XX:MaxGCPauseMillis`（默认 200ms）——**G1 会挑选「在目标时间内能回收多少 Region」，而不是一次扫完整个老年代**；
2. **无碎片**：Region 之间用复制算法，整体效果接近标记-整理；
3. **Humongous 区**：**大于 Region 一半**的大对象单独存放；
4. **SATB（Snapshot-At-The-Beginning）**：并发标记时用**写前屏障**记录引用变化，保证标记正确性。

**⭐ ZGC 的关键机制**：

- **染色指针（Colored Pointer）**：把 GC 标记信息存在指针的「备用位」里（64 位指针实际只用 42 位寻址）——**不需要额外的对象头空间**；
- **读屏障**：读对象时检查指针颜色，需要时修正；
- **停顿 < 1ms，且与堆大小无关**——这是它相对 G1 的核心优势；
- **JDK 21 起支持分代 ZGC**（`-XX:+ZGenerational`），**JDK 23 起分代成为默认模式**。

**⭐ CMS 为什么被移除（JDK 14）**：

1. **标记-清除产生碎片** → 碎片多到放不下对象时触发 **Concurrent Mode Failure** → 退化成 Serial Old 单线程 Full GC（**停顿数秒**）；
2. **并发阶段占用 CPU**（默认占 25% 的 CPU 线程）；
3. **浮动垃圾**（并发期间新产生的垃圾）需要预留空间。

**追问：G1 和 ZGC 怎么选？**
→ **看堆大小和延迟要求**：
- **常规微服务（堆 4~16GB）** → **G1**，它是默认、生态最成熟、调优资料最多；
- **超大堆（几十上百 GB）+ 极端延迟要求** → **ZGC**；
- ⚠️ **别自己乱换**——ZGC 的调优经验和 G1 完全不同，很多 G1 的参数在 ZGC 上无效。

**追问：Parallel Scavenge 和 G1 怎么选？**
→ **吞吐量优先**（批处理、离线任务）用 **Parallel**；**延迟优先**（在线服务）用 **G1**。**Parallel 是「用更多 CPU 换更高吞吐」，G1 是「用更多 CPU 换更低停顿」。**

## Q7. 类加载过程是什么？双亲委派模型解决什么问题？

**答：**

**结论：类加载分 7 个阶段（加载、验证、准备、解析、初始化、使用、卸载），核心是「双亲委派」——先问父加载器，保证核心类不被篡改。**

**五个前置阶段**：

| 阶段 | 做什么 | 关键点 |
|------|-------|--------|
| **加载** | 读 `.class` 二进制流 → 方法区生成类结构 → 堆中创建 `Class` 对象 | 来源可以是文件、jar、网络、动态生成 |
| **验证** | 校验字节码合法性 | 防恶意字节码 |
| **准备** | 为静态变量分配内存并赋**零值** | ⚠️ `static int a = 10` 在准备阶段是 **0** |
| **解析** | 符号引用 → 直接引用 | 常量池里的符号替换成内存地址 |
| **初始化** | 执行 `<clinit>()`：静态变量赋真值 + 静态代码块 | ⚠️ 到这一步 `a` 才变成 10 |

**⭐ 面试标准对比题**：

```java
public class Demo {
    static int a = 10;      // 准备阶段：a = 0
    static { a = 20; }     // 初始化阶段：先 a = 10，再执行静态块 a = 20
}
```

- **准备阶段**：`a = 0`（零值）；
- **初始化阶段**：先赋真值 `a = 10`，再执行静态块 `a = 20` → **最终 20**。

**三层类加载器**：

| 加载器 | 加载什么 | 实现语言 |
|--------|---------|---------|
| **Bootstrap ClassLoader** | `java.base` 等核心类（`String`、`Object`） | C++（JVM 内部） |
| **Platform ClassLoader**（JDK 9+，旧名 Extension） | JDK 扩展模块 | Java |
| **Application ClassLoader** | 应用 classpath（你的代码 + 依赖 jar） | Java |

⚠️ **JDK 9 的模块化变化**：原来 `rt.jar` 拆成了 `java.base`、`java.sql` 等多个模块，**Extension ClassLoader 改名为 Platform ClassLoader**——老资料里的「扩展类加载器」是 JDK 8 的说法。

**双亲委派的三个动作（顺序不能错）**：

```
查缓存（findLoadedClass）→ 委派父加载器 → 自己 findClass 加载
```

**它解决两个问题**：

1. **安全**：你写一个 `java.lang.String`，永远会被 Bootstrap 抢先加载，**你的版本没有机会生效**；
2. **唯一性**：同一个类在一个类加载器下**只加载一次**，保证类的一致性。

**⭐ 关键结论**：**判断「两个类是否相同」的标准 = 类加载器 + 全限定类名，两者都相同**。同一个类被两个加载器各加载一次 → 是两个不同的类 → 强转时抛 `ClassCastException`（插件/热部署场景的经典坑）。

**三个打破双亲委派的真实场景**：

| 场景 | 怎么打破 | 为什么 |
|------|---------|--------|
| **Tomcat** | `WebappClassLoader` **先自己加载**，加载不到再委派父级 | 不同 webapp 依赖不同版本的同一个库，需要隔离 |
| **SPI**（JDBC/JNDI/JAXP） | **线程上下文类加载器（TCCL）向下委派** | `DriverManager`（Bootstrap 加载）要加载 MySQL 驱动（只有 Application 认识） |
| **OSGi / 热部署** | 网状依赖，每个 Bundle 一个加载器 | 需要更灵活的加载拓扑 |

**追问：类什么时候会被初始化？**
→ 六种主动使用会触发：① `new`、访问静态字段、调用静态方法；② 反射（`Class.forName`）；③ 初始化子类时**先初始化父类**；④ 虚拟机启动的主类；⑤ `MethodHandle` 解析结果对应的类；⑥ 接口默认方法被实现类调用时。

⚠️ **不触发初始化**：通过子类访问父类的静态字段（只初始化父类）；**定义数组**（`User[] arr = new User[10]` 不初始化 `User`）；访问 `static final` **编译期常量**（已内联进常量池）。

**追问：`ClassNotFoundException` 和 `NoClassDefFoundError` 的区别？**
→ 前者是**加载阶段**（显式 `Class.forName` 找不到 class 文件）；后者是**链接/初始化阶段**（类之前加载过，但初始化失败或运行时找不到）。⚠️ **`NoClassDefFoundError` 经常是「静态初始化块抛了异常」的伪装**——真正的根因在 `ExceptionInInitializerError` 里，要往日志前面找。

## Q8. 线上出现了 OOM，你的排查思路是什么？

**答：**

**结论：第一步永远不是重启，而是「先看 OOM 的后缀」——不同后缀对应完全不同的排查方向。**

| OOM 类型 | 区域 | 排查方向 | 关键参数 |
|---------|------|---------|---------|
| `Java heap space` | 堆 | **内存泄漏** or **单次分配过大** | `-Xmx` |
| `Metaspace` | 元空间（本地内存） | 动态生成类、类加载器泄漏 | `-XX:MaxMetaspaceSize` |
| `unable to create new native thread` | 线程栈（本地内存） | 线程数过多 | 减线程数 / 调小 `-Xss` |
| `Direct buffer memory` | 直接内存（NIO） | `ByteBuffer` 未释放 | `-XX:MaxDirectMemorySize` |
| `GC overhead limit exceeded` | 堆 | GC 太频繁但回收不了多少 → 基本是泄漏 | 查泄漏 |
| `StackOverflowError` | 虚拟机栈 | **无限递归**（不是 OOM） | 查递归 |

**堆 OOM 的固定五步**：

```
① 确认现场：jps 找进程；jstat -gcutil 看老年代是否接近 100%
② 导出快照：⚠️ 生产必须提前配 -XX:+HeapDumpOnOutOfMemoryError
            -XX:HeapDumpPath=/data/dump，让 OOM 时自动 dump
③ 分析快照：Eclipse MAT 打开 .hprof，看 Dominator Tree（谁占内存最多）
④ 定位代码：找「数量异常多」的对象，反查持有者（MAT 的 Path to GC Roots）
⑤ 修复：无界缓存加容量上限、分页查询、及时关闭流
```

**⭐ 三个工具的分工**：

| 工具 | 用途 | 典型命令 |
|------|------|---------|
| **`jstat`** | 看 GC 实时统计 | `jstat -gcutil <pid> 1000` |
| **`jmap`** | 看对象统计 / 导快照 | `jmap -histo:live <pid> \| head -20` |
| **`jstack`** | 看线程栈 | `jstack <pid> > t.txt` |

**读 `jstat -gcutil` 的关键列**：

- **`O`（老年代使用率）持续上涨不回落** → ⭐ **内存泄漏的信号**；
- **`M`（元空间使用率）持续上涨** → 动态生成类（CGLIB、反射、热部署）；
- **`FGC`（Full GC 次数）> 0** → 就要关注，频繁就是事故。

**元空间 OOM 的常见原因**：① **动态生成类**（大量 `@Configuration` 的 CGLIB 代理、反射、Groovy）；② **热部署/重复加载**（旧类无法卸载）；③ `MaxMetaspaceSize` 设太小。

**追问：为什么 OOM 后不能直接重启？**
→ **重启会销毁现场**——堆快照、日志线索全没了，同一个问题必然复发，而且你永远不知道根因。⚠️ **正确做法：重启前先把 dump 拿下来**（如果 dump 已经配置好，OOM 时会自动落盘）。

**追问：内存泄漏和「内存不够用」怎么区分？**
→ **看趋势，不看绝对值**：
- **泄漏**：老年代使用率**单调上涨不回落**，多次 Full GC 后也降不下来 → 一定有东西被意外持有；
- **不够用**：Full GC 后能降下去，只是峰值超了 → 调大堆或优化分配。

**追问：`jmap -histo` 为什么要加 `:live`？副作用是什么？**
→ 加 `:live` 只统计**可达对象**，数字更有意义；⚠️ **但它会触发一次 Full GC**，生产环境要慎用（会 STW）。

## Q9. GC 日志怎么读？线上调优的完整流程是什么？

**答：**

**结论：调优四步——看现象 → 取数据 → 定原因 → 一次只改一个参数。**

**⭐ 最重要的一条纪律**：**顺序不能反。先看是不是代码问题（内存泄漏、无界缓存、一次查 100 万行），再谈调参。大多数「GC 问题」的根因是代码里有个不该活那么久的对象。**

**第一步：必须开的三样东西**（上线前配好，出问题时才不至于盲诊）：

```bash
-XX:+HeapDumpOnOutOfMemoryError          # OOM 时自动 dump（最重要）
-XX:HeapDumpPath=/data/dump              # dump 落盘路径
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags   # GC 日志（JDK 9+ 统一日志）
```

⚠️ **JDK 9 之前是 `-XX:+PrintGCDetails` + `-XX:+PrintGCTimeStamps`，JDK 9+ 统一成 `-Xlog`**——面试时要说清版本。

**第二步：读懂一行 GC 日志**：

```text
[2.345s][info][gc] GC(12) Pause Young (Normal) (G1 Evacuation Pause)
  2048M->512M(4096M) 12.345ms
```

| 字段 | 含义 |
|------|------|
| `Pause Young` | Young GC；出现 `Pause Full` 才是事故 |
| `2048M->512M` | GC 前占用 → GC 后占用 |
| `(4096M)` | 堆总大小 |
| `12.345ms` | ⭐ **本次停顿时间——核心指标** |

**判断标准**（可作为经验值参考，具体要看业务）：
- **Young GC 单次 < 50ms、频率 < 每秒 1 次** → 正常；
- **出现 `Pause Full`** → 立刻排查；
- **GC 后老年代占用仍然很高** → 泄漏信号。

**第三步：按现象定方向**：

| 现象 | 方向 |
|------|------|
| **频繁 Young GC** | 新生代太小 / **对象创建太快（先查代码）** |
| **Full GC 频繁** | 老年代泄漏 / 大对象太多 / 晋升过快 |
| **单次停顿超目标** | 换收集器（G1/ZGC）或调 `MaxGCPauseMillis` |
| **老年代占用持续上涨** | 内存泄漏 → 导 dump 查 Dominator Tree |

**第四步：改一个参数 → 压测验证 → 再改下一个。**

**常用参数速查**：

```bash
-Xms4g -Xmx4g                     # 堆初始=最大（生产设相等，避免动态扩容抖动）
-XX:MaxGCPauseMillis=200          # G1 目标停顿
-XX:MaxTenuringThreshold=15       # 晋升年龄
-XX:MaxMetaspaceSize=512m         # 元空间上限
-XX:+UseG1GC                      # JDK 9+ 本来就是默认，写出来更明确
-Xss512k                          # 线程栈大小（线程多时调小）
```

**追问：为什么 `-Xms` 和 `-Xmx` 要设成一样？**
→ 因为**堆会动态扩容和收缩**。如果 `-Xms` 小、`-Xmx` 大，JVM 会在运行中反复扩缩容，**每次都伴随 Full GC**，造成不必要的停顿抖动。**生产上固定大小，避开这个抖动。**

**追问：容器里怎么配堆大小？**
→ **不要写死 `-Xmx`**——换规格就出事。用 **`-XX:MaxRAMPercentage=75`**（堆最多用容器内存的 75%）。JDK 10+ 默认开启容器感知（`-XX:+UseContainerSupport`），不配的话 JVM 可能按宿主机内存算堆，导致容器被 OOMKilled。

**追问：怎么看当前的 GC 器和参数？**
→ `java -XX:+PrintFlagsFinal -version | grep -i gc`；或 `jcmd <pid> VM.flags`；或用 Arthas 的 `dashboard`。

## Q10. JDK 的诊断工具有哪些？Arthas 好在哪？

**答：**

**结论：JDK 自带四件套（`jps`/`jstat`/`jmap`/`jstack`）解决「看得见」，Arthas 解决「看得清、能动手」。**

**四件套分工**：

| 工具 | 一句话 | 关键命令 | 解决什么问题 |
|------|-------|---------|-----------|
| **`jps`** | 列出 Java 进程 | `jps -l` | 找到目标进程 |
| **`jstat`** | GC 统计（实时） | `jstat -gcutil <pid> 1000` | 老年代是不是在涨、Full GC 几次 |
| **`jmap`** | 对象统计 / 导快照 | `jmap -histo:live <pid>`；`jmap -dump:live,format=b,file=a.hprof <pid>` | 谁占了内存 |
| **`jstack`** | 线程栈 | `jstack <pid> > t.txt` | 线程在干什么、卡在哪、谁持锁 |

**⭐ 三个高频场景的固定套路**：

**① CPU 100%**（三步，线程号要转十六进制）：

```bash
top -c | grep java                      # ① 找最耗 CPU 的 Java 进程
top -Hp <pid>                           # ② 找进程内最耗 CPU 的线程
printf "%x\n" <线程id>                  #    转成 16 进制
jstack <pid> | grep -A 30 "nid=0x<16进制id>"   # ③ 看这个线程在干什么
```

| 栈顶是什么 | 根因方向 |
|------------|---------|
| `GC task thread` | GC 太频繁 → 回去看 GC 日志 |
| 业务方法死循环 | 循环退出条件写错 / 正则回溯爆炸 |
| 多个线程在同一方法 | 某段计算太重 → 加缓存/优化算法 |
| 大量 `BLOCKED` | 锁竞争 → 找持锁线程 |

⚠️ **注意「等网络 IO 也显示 RUNNABLE」**——很多「CPU 高」其实是「线程多但都在等下游」，**要看 `%CPU` 是否真的高**。

**② 接口变慢但 CPU/内存正常** → **不是 JVM 问题，是外部依赖**。`jstack` 看线程是否卡在同一处（数据库连接池 `getConnection`）；用 Arthas `trace` 看方法耗时分布；查连接池活跃数、下游 RT、慢 SQL。

**③ 死锁** → `jstack` 输出末尾**直接会打印 `Found one Java-level deadlock` 段**，不用自己拼图。

**⭐ Arthas 为什么是排查利器**：

**不需要重启、不改代码**，attach 到运行中的 JVM：

| 命令 | 用途 | 场景 |
|------|------|------|
| `dashboard` | 实时面板：线程、内存、GC | 一眼看全局 |
| `thread -n 3` | CPU 最高的 3 个线程 + 堆栈 | ⭐ CPU 100% 首选 |
| `thread <id> -b` | 指定线程的栈 + 打印阻塞源头 | 找锁持有者 |
| `watch 类 方法 "{params, returnObj}"` | 观察方法入参/返回值 | **不打日志也能看数据** |
| `trace 类 方法` | 方法内部调用耗时分布 | 定位慢在哪一层 |
| `heapdump` | 导出堆快照 | 等同 `jmap -dump` |
| `jad 类` | 反编译已加载的类 | **确认线上跑的是哪个版本** |

**⭐ `watch` 和 `trace` 是两个最被低估的命令**：
- **`watch` 解决「参数是什么」**——不重启就看到方法收到的实际参数和返回值；
- **`trace` 解决「慢在哪一层」**——直接给出方法内部每一层的耗时分布。

**追问：`jstack` 抓一次够吗？**
→ **不够**。一次快照只能看到「此刻」的状态，**看不到趋势**。正确做法是**间隔几秒抓 3 次对比**——如果线程栈每次都不一样，说明它在轮转（可能是定时任务）；如果三次都卡在同一处，那就是真问题。

**追问：`jmap -dump` 在生产上有什么风险？**
→ **会 STW 数秒**——dump 大堆时 JVM 要冻结所有线程。**优先用「OOM 自动 dump」（已配置的话）或 Arthas 的 `heapdump`**（可指定只 dump 活对象）。**绝不要在大流量生产上随手 `jmap -dump`。**

**追问：除了这些，还有什么排查手段？**
→ **火焰图**（async-profiler，生产可用，采样低开销）、**JFR（Java Flight Recorder，JDK 11+ 内置，开销极低）**、**GC 日志 + GC Viewer/GCViewer**、**Arthas 的 profiler**。**现代做法首选 async-profiler 出火焰图 + JFR 做持续观测。**
