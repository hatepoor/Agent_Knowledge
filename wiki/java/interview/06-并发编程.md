# 并发编程

> **什么时候该读**：Java 面试里**最容易拉开差距**的一章——初级问「线程有哪些状态」，高级问「你的线程池参数怎么定的」「线上死锁怎么排查」。这七道题答不透，后面的系统设计题基本无从谈起。
> **答题主线**：**「线程安全 = 原子性 + 可见性 + 有序性」**。所有机制（volatile、synchronized、CAS、并发容器）都在这三个维度上做取舍。机制详解见 [[java/02-中段阶段-专题精讲/并发编程/02-线程安全与Java内存模型]] 与 [[java/02-中段阶段-专题精讲/并发编程/04-线程池与任务调度]]。

## Q1. Java 线程有哪几种状态？`BLOCKED` 和 `WAITING` 有什么区别？

**答：**

**结论：Java 线程在 `Thread.State` 里有 6 种状态（`BLOCKED`、`WAITING`、`TIMED_WAITING` 是三种等待的细分）。**

```
        ┌──────────────┐
        │    NEW       │ 线程创建了但还没 start()
        └──────┬───────┘
               │ start()
        ┌──────▼───────┐
   ┌───►│  RUNNABLE    │ 正在执行（⚠️ 也包括"等待 IO"和"等待获取锁"）
   │    └──────┬───────┘
   │           │ 等待锁 / 等待条件 / 限时等待
   │    ┌──────▼───────┐  ┌──────────────┐  ┌───────────────────┐
   │    │   BLOCKED    │  │   WAITING    │  │  TIMED_WAITING    │
   │    │ 等 monitor   │  │ 无限期等待   │  │ 限时等待          │
   │    └──────┬───────┘  └──────┬───────┘  └─────────┬─────────┘
   │           │                 │                    │
   │           └────────┬────────┴────────────────────┘
   │              ┌──────▼───────┐
   └──────────────│  TERMINATED  │ 线程执行完毕
                  └──────────────┘
```

| 状态 | 含义 | 怎么进入 |
|------|------|---------|
| **NEW** | 已创建未启动 | `new Thread(...)` |
| **RUNNABLE** | 正在 Java 层执行 | `start()` 后 |
| **BLOCKED** | **阻塞等待 monitor 锁** | 想要进入同步块但锁被别人持有 |
| **WAITING** | **无限期等待**（无超时） | `Object.wait()`、`Thread.join()`、`LockSupport.park()` |
| **TIMED_WAITING** | **限时等待** | `sleep()`、`wait(ms)`、`join(ms)`、`parkNanos()` |
| **TERMINATED** | 已结束 | `run()` 执行完或抛异常 |

**⭐ 最容易答错的是 `BLOCKED` vs `WAITING`**：

| | **BLOCKED** | **WAITING / TIMED_WAITING** |
|---|------------|--------------------------|
| **在等什么** | **等锁**（monitor 竞争） | **等条件**（其他线程的 notify/park 解除） |
| **怎么解除** | **拿到锁**就解除 | **必须有人显式唤醒**（`notify`/`unpark`） |
| **典型 API** | 进入 `synchronized` 块 | `wait()`/`join()`/`park()`/`sleep()` |
| **谁负责唤醒** | JVM（锁释放自动） | **别的线程**（`notify`/`unpark`） |

⚠️ **两个必须记住的纠正**：

1. **「等待 IO 的线程在 jstack 里也显示 RUNNABLE」**——这是很多人以为的 bug，其实是正常的：JDK 层面线程在 `SocketRead` 里等待，操作系统层面是 IO 等待，但 Java 状态模型里没有单独的 IO 状态，归入 RUNNABLE。
2. **`sleep()` 不释放锁，`wait()` 释放锁**——这是超高频追问。

**追问：`sleep()` 和 `wait()` 有什么区别？**
→ 三个差异：
| | `sleep()` | `wait()` |
|---|-----------|---------|
| **所属** | `Thread` 的静态方法 | `Object` 的实例方法（所以每个对象都能 `wait`） |
| **释放锁** | ❌ **不释放** | ✅ **释放**（释放当前对象的那把锁） |
| **调用前提** | 任何地方 | **必须在 `synchronized` 块/方法内**，否则抛 `IllegalMonitorStateException` |
| **唤醒方式** | 时间到自动醒 | 需要 `notify()`/`notifyAll()` 或超时 |

**追问：`wait()` 为什么必须在 synchronized 里？**
→ 因为 `wait()` 的语义是「**释放锁并进入等待队列**」——如果调用时根本没持有锁，就没有锁可释放，语义不成立。JVM 用 `IllegalMonitorStateException` 来保证这个契约。

**追问：`Thread.yield()` 是什么？**
→ **主动让出 CPU 时间片**，让同优先级的其他线程有机会运行。⚠️ **它不保证任何事**——只是给个暗示，调度器可能完全无视。**需要真正让出并且等待特定条件，用 `wait()`/`park()`。**

## Q2. 什么是 Java 内存模型（JMM）？三大并发问题是什么？

**答：**

**结论：JMM 是「Java 内存操作（JMM）的抽象」——它规定了一个线程的写入何时对另一个线程可见，以及指令重排的边界。它要解决三个问题。**

**三大并发问题**：

| 问题 | 含义 | 例子 |
|------|------|------|
| **原子性** | 操作不可被中途打断 | `count++` 是「读-改-写」三步，多线程下会丢更新 |
| **可见性** | 一个线程的写，其他线程能及时看到 | 线程 A 改普通变量，线程 B 可能一直读到缓存的旧值 |
| **有序性** | 指令执行顺序符合预期 | 编译器/JIT 重排后，`flag=true` 可能先于 `data=1` 可见 |

**⚠️ 必须先纠正一个常见误解**：「原子性问题」**不是 JMM 特有的**——单线程里 `count++` 当然是原子的。**原子性问题特指「多线程下复合操作被打断」**。

**JMM 的核心：happens-before 规则**

**「A happens-before B」= 「A 的写入对 B 可见，且 A 在 B 之前执行」**。只要有一条 hb 规则成立，**就不需要加同步**。

**8 条 happens-before 规则**（面试要能背出主要几条）：

| 规则 | 内容 |
|------|------|
| **程序顺序** | 同一线程内，前面的操作 hb 后面的操作 |
| **监视器锁** | `unlock(m)` hb 后续的 `lock(m)`（**同一把锁**） |
| **volatile** | 对 volatile 变量的写 hb 后续的读 |
| **线程启动** | `Thread.start()` hb 该线程内的所有操作 |
| **线程终止** | 线程内的所有操作 hb 其他线程 `join()` 返回 |
| **线程中断** | `interrupt()` hb 检测到中断 |
| **对象终结** | 构造器执行结束 hb `finalize()` 开始 |
| **传递性** | A hb B，B hb C ⟹ A hb C |

⭐ **传递性是理解「安全发布」的关键**：

```java
// 线程 A
data = 42;          // 普通变量
flag = true;        // volatile
// 线程 B
if (flag) {         // 读到 true
    use(data);      // ⭐ 保证读到 data == 42
}
```

**为什么？** `写data` hb `写flag`（程序顺序）→ `写flag` hb `读flag`（volatile 规则）→ `读flag` hb `if` 内部（控制依赖 + 传递性）→ 所以 `写data` hb `use(data)`。**这就是 volatile 的「变量重排序禁止」的实际意义**。

**追问：JMM 和 CPU 内存模型有什么关系？**
→ JMM 是**语言层的抽象**，屏蔽了不同 CPU 的缓存一致性协议差异。硬件上：
- **x86** 的内存模型较强（大多数操作天然有序），所以在 x86 上问题不明显；
- **ARM** 较弱（允许更多重排），**所以同一个 bug 在 x86 上不复现、在 ARM 机器上复现**——这是「测试环境没事、上线到 ARM 机器就出事」的典型原因。

**追问：什么是「指令重排」？编译器重排和 CPU 重排有什么区别？**
→ **编译器重排**：JIT 编译时调整指令顺序（比如把无依赖的写操作提前）；**CPU 重排**：CPU 的乱序执行单元（out-of-order execution）会提前执行后面的独立指令。**JMM 是通过「内存屏障（memory barrier / fence）」在两者之间插入限制**——`volatile` 写后会插入 StoreStore+StoreLoad 屏障等。**硬件重排是「乱序执行但保证结果可见性一致」，软件层的重排限制则是 JMM 规定的。**

**追问：为什么并发 Bug 难复现？**
→ 因为它**依赖线程交错的具体时序**——同样的代码换个 CPU 核心数、换个 JIT 编译时机，结果就可能不同。**所以并发 bug 必须靠「正确的同步原语」来预防，不能靠「反复测试没复现」来证明没问题。**

## Q3. `volatile` 保证了什么？为什么它不能保证原子性？

**答：**

**结论：`volatile` 保证「可见性」和「有序性」，但**不保证原子性**。**

**`volatile` 的两个保证**：

| 保证 | 机制 |
|------|------|
| **可见性** | 写线程写完后，其他线程读**立刻能看到最新值**（每次读都从主内存取，不缓存） |
| **有序性** | 禁止编译器/JIT **重排序越过 volatile 读写**（写前插入 StoreStore 屏障，写后插入 StoreLoad 屏障） |

**⚠️ 不保证原子性——经典反例**：

```java
public class VolatileDemo {
    private static volatile int count = 0;      // ⚠️ volatile 但仍然不安全

    public static void main(String[] args) throws InterruptedException {
        int threads = 10, loops = 1000;

        for (int t = 0; t < threads; t++) {
            new Thread(() -> {
                for (int i = 0; i < loops; i++) {
                    count++;                    // ⚠️ 读-改-写三步，会丢更新
                }
            }).start();
        }
        Thread.sleep(200);
        System.out.println(count);               // 期望 10000，实际小于 10000
    }
}
```

**为什么 `volatile` 救不了？** `count++` 编译成三步：

```
① 读 count        ← volatile 读，能拿到最新值
② 加 1            ← ⚠️ 这一步不原子
③ 写回 count      ← volatile 写，能立刻可见
```

**两个线程可能都读到 5，都写回 6——更新丢了**。⚠️ **`volatile` 保证的是「每一步读写本身是可见的、有序的」，不是「这三步作为一个整体不可被打断」。**

**正确做法**：

```java
private static final AtomicInteger count = new AtomicInteger();
count.incrementAndGet();        // ✅ 原子自增

// 或者
private static int count;       // 靠 synchronized 保证
public static synchronized void inc() { count++; }
```

**⭐ 什么时候用 `volatile`？三个典型场景**：

| 场景 | 说明 |
|------|------|
| **状态标志位** | `volatile boolean running = true;` 一个线程改、其他线程轮询退出 |
| **单写多读的独立变量** | 多个线程读同一个「一次性写入」的值（如配置快照、缓存的 volatile 引用） |
| **Double-Checked Locking** | 单例的懒加载（⚠️ **必须给 instance 加 volatile**，否则 DCL 会拿到半成品对象，见 [[java/interview/02-面向对象与设计模式]]） |

**追问：`volatile` 和 `synchronized` 怎么选？**
→ **判断标准只有一条：要保护的复合操作需要原子性吗？**
- 只需要「改了别人马上能看见」→ `volatile`（**无锁、极快**）；
- 需要「一连串操作不能被打断」→ `synchronized`（或 `Lock`）。

**追问：`volatile` 能保证「读-改-写」的原子性吗？**
→ **不能**。⚠️ 这是最经典的错误认知。`volatile` 的语义是**单个读/单个写**的可见性与有序性，**不是复合操作的原子性**。

**追问：`i++` 是不是原子操作？**
→ **不是**。它是「读 → 加 → 写」三步，任何一步都可能被线程切换打断。**在 Java 内存模型里，即使是单线程的 `i++` 也要经过三步，只是单线程下不会被打断而已。**

**追问：原子类为什么能保证原子性？**
→ 靠 **CAS（Compare-And-Swap）**——「比较并交换」是一条 CPU 级别的原子指令，读-改-写在硬件层是一步。⚠️ **但 CAS 只保证「单个变量」的原子性**，多个变量要一起改就得加锁（这就是 `AtomicInteger` 的 `updateAndGet` 要用 lambda 的原因）。

## Q4. `synchronized` 的原理是什么？锁是怎么升级的？

**答：**

**结论：`synchronized` 依赖 JVM 的 **monitor（管程）** 实现，有两种字节码指令：`monitorenter` / `monitorexit`。锁有升级过程，但偏向锁已废弃。**

**两个层面理解**：

| 层面 | 内容 |
|------|------|
| **字节码层** | `synchronized` 块编译成 `monitorenter` / `monitorexit` 指令；同步方法则通过方法的 `ACC_SYNCHRONIZED` 标志实现 |
| **JVM 层** | 每个对象都有一个 **monitor**（对象头里的 Mark Word 在竞争时会指向它） |

**⭐ 锁的升级过程（按获取成本从低到高）**：

```
① 无锁
   ↓ 只有一个线程访问 → 偏向（历史设计）
② 偏向锁 → 轻量级锁 → 重量级锁 → 重量级锁
   ↑         ↑              ↑
  CAS 自旋  CAS 自旋      操作系统互斥锁
            + 栈上锁记录    (park / unpark)
```

| 锁状态 | 机制 | 适用场景 |
|--------|------|---------|
| **无锁** | 只需 CAS 一次（写对象头） | 无竞争 |
| **偏向锁**（**已废弃**） | 记录「这个锁偏向哪个线程」，同一线程再进入只需比较线程 ID | 单线程访问 |
| **轻量级锁** | 在**当前线程栈上**建 Lock Record，用 **CAS** 把 Mark Word 指向它；有竞争就**自旋** | 低竞争、临界区短 |
| **重量级锁** | 生成 `Monitor` 对象（存储在对象头 Mark Word），线程**挂起（park）** | 高竞争、临界区长 |

**⭐ 必须按版本说清楚的两点**：

1. ⚠️ **偏向锁在 JDK 15 起默认禁用并标记废弃（JEP 374），JDK 18 起被移除**。所以**现在的实际路径是：无锁 → 轻量级锁 → 重量级锁**。**面试时不要说「现在有四种锁状态」。**
2. **偏向锁被废弃的原因是**：它对「几乎只有一个线程访问」的场景优化很好，但在「锁是共享的、但每个线程处理不同数据」的现代多核服务器上反而成了负担（JDK 的实测发现「偏向锁 rarely helpful, typically detrimental」）。

**为什么需要自旋（轻量级锁）？**

**因为「阻塞（park）」的代价远大于「自旋等待」**——线程挂起 → 内核态调度 → 唤醒 → 上下文切换，**这个成本是微秒级的**，而临界区可能只有几十纳秒。**所以先自旋一会儿（用 CPU 空转），万一锁马上就释放了呢。**

**自旋的代价**：**纯 CPU 空转，不释放 CPU**。所以：
- **临界区短** → 自旋划算；
- **临界区长**（比如里面做 IO）→ 自旋纯浪费，应该直接重量级锁挂起。

**⭐ 锁升级是「不可逆」的**：一旦升级到重量级锁，**不会降级回轻量级锁**（无锁→偏向/轻量→重量级）。

**追问：偏向锁被废弃后，「无锁」状态还剩什么？**
→ 剩的是**「没有并发竞争」的状态**：Mark Word 里存的是**对象哈希码 + GC 年龄**。当第一个线程要加锁时，JVM 用 **CAS** 把 Mark Word 里的哈希码替换成「锁记录指针」→ 进入轻量级锁。⚠️ **注意：这个 CAS 会把哈希码挪到栈上的 Lock Record 里**——所以「对象头里存哈希码」只在无竞争时成立。

**追问：为什么 `synchronized` 偏向锁废弃后性能反而变好了？**
→ 因为在现代服务器上，**无竞争的场景本来就不需要额外开销**（无锁状态的 CAS 就够），而偏向锁的「判断是否偏向当前线程」也是一次比较。**JEP 374 的实测数据表明：禁用偏向锁后，多线程应用的性能普遍提升，锁竞争场景提升尤其明显。**

**追问：`synchronized` 和 `ReentrantLock` 怎么选？**
→ **默认用 `synchronized`**（简单、自动释放、不会漏解锁）。用 `ReentrantLock` 的三个理由：① 需要**可中断**（`lockInterruptibly`）；② 需要**超时**（`tryLock(timeout)`）；③ 需要**公平锁**（`new ReentrantLock(true)`，⚠️ 公平锁吞吐低得多）；④ 需要**多个条件变量**（`new Condition()`）。详见 [[java/02-中段阶段-专题精讲/并发编程/03-锁机制与原子操作]]。

## Q5. CAS 是什么？ABA 问题怎么解决？

**答：**

**结论：CAS（Compare-And-Swap， 比较并交换）是一条 CPU 级的原子指令：「如果内存位置的值仍然是我预期的旧值，就改成新值；否则什么都不做并返回失败」。**

```java
public class AtomicIntegerDemo {
    public static void main(String[] args) {
        AtomicInteger count = new AtomicInteger(0);

        // ✅ 基于 CAS 的原子自增
        count.incrementAndGet();
        count.getAndIncrement();        // 返回旧值
        count.compareAndSet(1, 100);    // 期望是 1 才改成 100
        count.updateAndGet(x -> x * 2); // 基于 CAS 循环实现
    }
}
```

**⚠️ 关键实现细节**：`AtomicInteger.incrementAndGet()` **不是一条指令完成的**，它是**自旋 + CAS 循环**：

```java
// 简化版源码
int prev, next;
do {
    prev = get();          // 读当前值
    next = prev + 1;      // 计算新值
} while (!compareAndSet(prev, next));   // CAS 失败就重试
```

**这带来一个重要推论：⚠️ `incrementAndGet()` 在高竞争下可能自旋很多次。** 竞争极激烈时，CAS 的重试率会上升，性能不如 `synchronized`（因为 CAS 忙等会烧 CPU）。

**⭐ ABA 问题**：

```java
AtomicInteger a = new AtomicInteger(0);
// 线程1: 读到 0
// 线程2: 把 0 改成 1，再改回 0
// 线程1: CAS(0, 1) —— ⚠️ 成功了！它以为没人动过，但值其实已经"变过一轮"
```

**根因**：CAS 只比较**值**，不关心「这个值被谁改过、什么时候改的」。

**三种解法**：

| 解法 | 做法 | 评价 |
|------|------|------|
| **① 原子引用 + 版本号**（`AtomicStampedReference`） | 引用和版本号一起 CAS | ⭐ **标准解法** |
| **② 加版本号字段**（自己实现） | `AtomicLong` 打包成 `(version << 32) \| value` | 实用但有溢出边界 |
| **③ 单线程场景** | 用锁替代 CAS | ⭐ **最实用的答案：能用锁就用锁** |

```java
// ✅ AtomicStampedReference 的用法
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);
int[] stamp = new int[1];
String v = ref.get(stamp);        // 读值和版本号
ref.compareAndSet(v, "B", stamp[0], stamp[0] + 1);   // 值和版本号都要匹配
```

**追问：ABA 问题在实践中真的重要吗？**
→ **多数场景不重要**。它只在「**值相同但中间状态不同会影响正确性**」的场景才是 bug——典型例子是**无锁栈**：节点 A 被弹出又被压回，栈顶指针还是 A，但 A 的 `next` 变了 → CAS 成功但栈结构已损坏。**结论：优先用锁（简单正确），只在「无锁队列/无锁栈」这类明确场景才关心 ABA。**

**追问：CAS 的性能问题？**
→ ① **忙等烧 CPU**（自旋）；② **只能保证单变量原子性**（多变量要加锁或用 `updateAndGet` 的 lambda 一次性算）；③ **ABA**；④ **高竞争下重试率高**，可能不如 `synchronized`（因为 `synchronized` 会让线程挂起，不烧 CPU）。⚠️ **JVM 从 JDK 9 起在热点循环里会自适应自旋失败并直接挂起**（`-XX:OnStackReplacePercentage` 相关机制）。

## Q6. `ThreadPoolExecutor` 的七个参数是什么？任务提交后是怎么执行的？

**答：**

**结论：七个参数 + 一条核心链路：核心线程 → 队列 → 非核心线程 → 拒绝策略。**

```java
public class ThreadPoolDemo {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2,                                   // 1. corePoolSize：核心线程数
                8,                                   // 2. maximumPoolSize：最大线程数
                60, TimeUnit.SECONDS,                // 3. keepAliveTime：非核心线程空闲存活时间
                TimeUnit.SECONDS,                    // 4. unit：时间单位
                new ArrayBlockingQueue<>(200),        // 5. workQueue：任务队列（⭐ 必须有界）
                new NamedThreadFactory("biz"),        // 6. threadFactory：线程工厂（便于排查）
                new ThreadPoolExecutor.AbortPolicy()); // 7. handler：拒绝策略
    }
}
```

**⭐ 这就是「七参数」的来源**——构造器正好七个参数，面试里要能默写出来：

```java
public ThreadPoolExecutor(
        int corePoolSize,               // 1
        int maximumPoolSize,            // 2
        long keepAliveTime,             // 3
        TimeUnit unit,                  // 4
        BlockingQueue<Runnable> workQueue,        // 5
        ThreadFactory threadFactory,    // 6
        RejectedExecutionHandler handler)         // 7
```

⚠️ **`unit` 单独算一个参数**——很多人把 `keepAliveTime` 和 `unit` 合成一个算成「六参数」，然后被面试官追问时答不上来。**记住：七个数，一个都不能少。**

**⭐ 核心执行流程（面试必背，画出来）**：

```
提交任务 execute(task)
   ↓
① 当前线程数 < corePoolSize？
   → YES：创建核心线程执行任务 → 结束
   → NO：↓
② workQueue 没满？
   → YES：任务入队 → 结束
   → NO：↓
③ 当前线程数 < maximumPoolSize？
   → YES：创建非核心线程执行任务 → 结束
   → NO：↓
④ 触发拒绝策略 RejectedExecutionHandler
```

⭐ **最关键的一点**：**「先入队，后扩容」**。只有队列满了才会创建非核心线程到 `maximumPoolSize`——所以：

- **队列设得大 → 几乎用不到 `maximumPoolSize`**（这个参数形同虚设）；
- **队列无界 → `maximumPoolSize` 永远用不到，且任务无限堆积 → OOM**。

**`execute` vs `submit` vs `schedule` 的区别**：

| 方法 | 返回值 | 异常处理 |
|------|-------|---------|
| `execute(Runnable)` | void | ⚠️ **异常直接抛给线程的 uncaughtExceptionHandler**（工作线程会死掉！） |
| `submit(Runnable/Callable)` | `Future` | ⚠️ **异常被 Future 捕获**，不 `get()` 就永远看不到 |
| `schedule(...)` | `ScheduledFuture` | 定时/延迟任务 |

**⭐ 这是超高频的坑**：`submit` 提交的任务如果抛异常，**调用方不调 `future.get()` 就完全无感知**——日志里什么都没有。

```java
// ❌ 异常被吞，任务"静默失败"
pool.submit(() -> { throw new RuntimeException("boom"); });

// ✅ 至少在提交处捕获
pool.submit(() -> {
    try {
        doWork();
    } catch (Exception e) {
        log.error("任务执行失败", e);   // ⚠️ 必须自己兜住
    }
});
```

**追问：核心线程池的核心线程会被回收吗？**
→ **会。** `allowCoreThreadTimeOut` 默认是 `false`（核心线程不回收），但**当线程池缩到 0 个工作线程时，核心线程也会被回收**（JVM 保活判定看的是「工作线程数是否为 0」）。可以把 `allowCoreThreadTimeOut(true)` 打开，让核心线程也超时退出——**适合「流量波动大」的场景**，能省内存。

**追问：线程池的线程是「核心线程」还是「非核心线程」怎么区分？**
→ **身份是动态的**：先创建的算核心线程；核心线程数满了、队列也满了之后创建的，**即使后来核心线程空闲了，它们也只是「非核心线程」**（受 `keepAliveTime` 控制）。⚠️ **这是一个反直觉的点**：`corePoolSize` 不是「一批固定线程」，而是「扩容的起点」。

**追问：线程池应该设多大？**
→ **CPU 密集型**：`corePoolSize = CPU 核数 + 1`（多一个补偿线程切换时的空档）；**IO 密集型**：`corePoolSize = CPU 核数 × (1 + W/C)`，其中 W 是等待时间、C 是计算时间——**这个公式是通用估算，不是精确值，最终靠压测确定**。⚠️ **比「设多少」更重要的是「队列必须有界」和「拒绝策略要选对」。**

**追问：为什么 `Executors.newFixedThreadPool()` 被阿里规约禁止？**
→ 因为它用 **`LinkedBlockingQueue` 无界队列**——任务无限堆积，内存持续增长直到 OOM。⚠️ 同类问题还有 `newSingleThreadExecutor()` 和 `newCachedThreadPool()`（后者是**无界线程数**，会创建海量线程导致 OOM）。**结论：永远显式 `new ThreadPoolExecutor(...)`。**

## Q7. 四种拒绝策略分别是什么？线上该选哪个？

**答：**

**结论：四种策略，核心区别是「任务被拒绝时，谁来兜底」。**

| 策略 | 行为 | 后果 | 适用场景 |
|------|------|------|--------|
| **AbortPolicy**（默认） | **直接抛 `RejectedExecutionException`** | 调用方感知到失败 | ⭐ **默认选它**——失败要暴露，不能悄悄吞 |
| **CallerRunsPolicy** | **让调用线程自己执行这个任务** | ⚠️ 调用方被阻塞，但**形成天然的背压** | ⭐ **写接口场景**：宁可慢，不能丢 |
| **DiscardPolicy** | **静默丢弃** | 任务凭空消失 | ⚠️ **几乎不能用**——问题被完全掩盖 |
| **DiscardOldestPolicy** | **丢弃队列最老的任务，重试入队** | 老任务被丢 | 需要「保新弃旧」且队列足够大时 |

**⭐ 面试要讲清 `CallerRunsPolicy` 的双面性**：

**优点**：① **天然背压**——池满了，调用方自己干活，**提交速度自动降下来**，不会堆积内存；② **不丢任务**。

**⚠️ 危险**：
- **会阻塞调用线程**——如果调用方是 **Web 容器的请求线程**（Tomcat 的工作线程），那请求线程就去执行这个耗时任务了 → **Tomcat 线程被耗尽，整个服务不可用**；
- 如果调用方是 **MQ 消费线程**，消费线程被拖住 → 消费堆积。

**结论：`CallerRunsPolicy` 适合「非关键路径的后台任务」（如日志、埋点、通知），⚠️ 不适合直接在 Controller 里调用池的接口方法。**

**⚠️ 更安全的做法：用自定义拒绝策略把任务「持久化后重投」**：

```java
// 自定义策略：拒绝时把任务落到 DB/MQ 的"待重试"表，由另一个调度器慢慢消化
public class RetryAfterPersistPolicy implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        // ⚠️ 绝不要在这里做耗时操作（会进一步阻塞调用方）
        pendingTaskRepository.save(PendingTask.from(r));
        throw new RejectedExecutionException("任务已转入待重试队列");
    }
}
```

**⭐ 实战推荐组合**：

| 场景 | 推荐 |
|------|------|
| **核心业务接口**（不能丢） | `AbortPolicy` + 上层捕获 + **降级/返回失败**（让用户知道失败了） |
| **非关键异步任务**（日志、埋点） | `CallerRunsPolicy`（背压）或 `DiscardPolicy`（明确接受丢弃） |
| **重要异步任务** | 自定义策略（持久化 + 重投） |

**追问：任务被拒绝时，怎么知道线上已经「过载」了？**
→ **必须埋监控**：自定义拒绝策略里 **increment 一个计数器 + 打日志 + 上报告警**。**拒绝策略触发 = 容量不足的信号**，是扩容或降级的触发条件。⚠️ **用默认 `AbortPolicy` 时，异常会传到业务代码，很容易被 catch 掉就没人知道了**——这也是要自定义策略的重要理由。

**追问：队列该用什么类型？**
→ | 队列 | 特点 | 适用 |
|------|------|------|
| | `ArrayBlockingQueue` | **有界**、数组、单锁 | ⭐ **默认选它**——必须设容量 |
| | `LinkedBlockingQueue` | 默认容量 `Integer.MAX_VALUE`（**等于无界！**） | ⚠️ 用的话**必须显式设容量** |
| | `SynchronousQueue` | 容量 0，直接交给线程 | `newCachedThreadPool` 用 |
| | `PriorityBlockingQueue` | 无界、按优先级 | 优先级调度（⚠️ 无界） |
| | `DelayQueue` | 延时任务 | 延迟执行 |

**⭐ 核心原则：队列必须有界。** 无界队列 = 用 OOM 换「看起来不丢任务」。

## Q8. 死锁是怎么产生的？线上怎么发现和处理？

**答：**

**结论：死锁需要四个条件同时成立。排查靠 `jstack`（它能直接打印死锁段），处理靠「预防」而不是「事后」。**

**死锁的四个必要条件**（缺一不可）：

| 条件 | 含义 |
|------|------|
| **互斥** | 资源同一时刻只能被一个线程占用 |
| **占有并等待** | 持有资源 A 的同时，等待资源 B |
| **不可剥夺** | 资源只能由持有者主动释放 |
| **循环等待** | 存在一个「线程-资源」的循环等待链 |

**典型代码**：

```java
public class DeadlockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(100);
                synchronized (LOCK_B) { }    // 等待 B
            }
        }).start();

        new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(100);
                synchronized (LOCK_A) { }    // 等待 A → 死锁
            }
        }).start();
    }
}
```

**⭐ 预防手段（按有效性排序）**：

| 手段 | 说明 | 有效性 |
|------|------|--------|
| **① 固定加锁顺序** | 所有线程都按「资源 ID 从小到大」的顺序加锁 | ⭐ **最有效、最常用**——代码审查可查 |
| **② 尽量用 `tryLock` 带超时** | `if (lock.tryLock(1, TimeUnit.SECONDS)) { }` | 有效——打破「占有并等待」 |
| **③ 避免嵌套锁** | 一段代码里最多一把锁 | ⭐ **最简单**——设计上避免 |
| **④ 用 `ConcurrentHashMap` 替代「锁 + 查表」** | 减少锁的数量 | 有效 |
| **⑤ 减少锁的作用域** | 把 synchronized 块缩到最小 | 有效——降低交错概率 |
| **⑥ 用更高层的并发工具** | `ConcurrentHashMap`、`BlockingQueue`、`computeIfAbsent` | ⭐ **根治**——很多「需要锁」的场景根本不需要锁 |

**⭐ 最重要的建议**：`ConcurrentHashMap.computeIfAbsent()` / `merge()` 这类**「原子性的读-改-写」API**，能消灭掉大量「先 contains 再 put」的伪原子操作带来的死锁。

```java
// ❌ 危险：两个线程可能同时进入 if 分支
if (!map.containsKey(k)) {
    map.put(k, createValue(k));    // ⚠️ check-then-act 竞态
}

// ✅ 原子操作
map.computeIfAbsent(k, this::createValue);
```

**⭐ 线上发现死锁的三种方式**：

| 方式 | 做法 |
|------|------|
| **`jstack`** | ⭐ **最直接**——输出末尾会直接打印 `Found one Java-level deadlock` 段，含两个线程各自的持锁和等待 |
| **`jcmd <pid> Thread.print`** | 等价于 jstack，不用找 jstack 脚本 |
| **Arthas `thread -b`** | 找出阻塞源头 |

```bash
jstack <pid> | grep -A 30 "Found one Java-level deadlock"
```

**⭐ 处理策略**：

| 策略 | 说明 |
|------|------|
| **预防为主** | 上面六条——死锁一旦发生，**应用已经卡死了**，事后恢复不如事前预防 |
| **JVM 死锁检测** | `jstack` 能检测；但**检测本身有成本**（遍历锁关系图） |
| **超时中断** | `tryLock` 超时后回退或抛异常，让系统保持「部分可用」而不是「完全卡死」 |
| **`kill -3`** | 给 JVM 发 SIGQUIT，**触发线程 dump 但不终止进程**——这是线上安全抓取线程栈的正确方式 |

**追问：数据库也会死锁吗？**
→ **会**（MySQL/PostgreSQL 都有行级死锁检测）。但**数据库死锁会被自动检测并回滚其中一个事务**，不会永久卡住——代价是应用收到异常要重试。**「数据库死锁」和「Java 线程死锁」要分清**：前者表现为事务回滚异常，后者表现为请求全部卡住。

**追问：`synchronized` 死锁和 `Lock` 死锁有什么区别？**
→ **死锁本身没区别**。但 `Lock` 死锁时 **所有线程都卡在 `lock()` 里，jstack 能看到它们停在 `LockSupport.park`**；而 `synchronized` 死锁时线程状态是 **`BLOCKED`**。⚠️ **排查时两种都要看——只看 `BLOCKED` 会漏掉 `Lock` 的死锁。**

**追问：怎么避免「数据库死锁」？**
→ **固定访问顺序**（比如所有业务都按主键 ID 升序更新），缩短事务，减少锁范围，必要时用 `SELECT ... FOR UPDATE` 显式加锁并统一顺序。

## Q9. `ConcurrentHashMap` 是怎么实现的？为什么它比 `Hashtable` 好？

**答：**

**结论：JDK 8 起 `ConcurrentHashMap` 用「CAS + synchronized 锁单个桶头节点」实现并发控制，彻底放弃了 JDK 7 的 `Segment` 分段锁。**

**JDK 7 → JDK 8 的变化**：

| | JDK 7 | JDK 8 |
|---|--------|--------|
| **结构** | **Segment 分段锁**（默认 16 段，每段一把锁）+ HashEntry 数组 | **单个 Node 数组 + 链表/红黑树**，**取消了 Segment** |
| **并发粒度** | 段级（16 段） | **桶级（锁单个桶的头节点）** |
| **扩容** | 多个 Segment 各自扩容 | **协助扩容（help transfer）** |
| **size()** | `AtomicInteger` 累加 | **`baseCount` + `CounterCell` 分散计数** |

**JDK 8 的核心设计**：

```
① 桶为空（head == null）
   → 用 CAS 把新节点放入（无锁）
② 桶非空
   → synchronized (head 节点) 锁住桶头
     → 在桶内执行链表/红黑树的插入
     → 扩容时协助其他线程一起迁移
```

**⭐ 为什么比 `Hashtable` 好？**

| | `Hashtable` | `ConcurrentHashMap` |
|---|------------|-------------------|
| **锁粒度** | ⚠️ **整个 Map 一把 `synchronized` 锁** | **桶级锁**（几乎无竞争） |
| **空桶插入** | 也要加全局锁 | **CAS 无锁插入** |
| **迭代器** | 抛 `ConcurrentModificationException` | **弱一致迭代器**，不抛异常 |
| **不允许 null** | ❌ | ⚠️ **也不允许 null**（因为 `get` 返回 null 无法区分「不存在」和「值就是 null」） |

**⚠️ 最后一个是高频追问**：`ConcurrentHashMap` **不允许 key 和 value 为 null**。**原因：`get()` 返回 null 时，调用方无法区分「这个 key 不存在」还是「这个 key 存在但值是 null」**——在并发场景下这个歧义无法安全解决。`Hashtable` 也禁止 null，理由相同。

**⭐ JDK 8 的三个计数机制**：

- **`baseCount`**：普通计数；
- **`CounterCell[]`**：竞争激烈时，把计数分散到多个格子（类似 `LongAdder`），减少 CAS 冲突；
- **`size()` 的估算**：返回的是**估计值**（把 `baseCount + sum(counterCells)` 加起来），⚠️ **不保证精确**——但对 `size()` 来说，精确本身就没意义。

**⭐ 弱一致迭代器（Weakly Consistent Iterator）的语义**：

- 遍历基于一个「弱一致的快照」；
- **能看到迭代开始时存在的元素**；
- **可能看到遍历期间的修改**；
- **保证不抛 `ConcurrentModificationException`、不重复访问同一元素、不会死循环**。

**追问：JDK 7 的 `Segment` 分段锁为什么被废弃了？**
→ 三个原因：① **Segment 结构复杂**（每层都要判断当前在哪一段）；② **Segment 数量固定（默认 16）**，并发度被限制死——**线程超过 16 个时，后面的线程只能排队**；③ **扩容时各 Segment 独立进行，内存搬迁复杂**。**JDK 8 用桶级锁 + 协助扩容，同时解决了这三个问题。**

**追问：`ConcurrentHashMap` 的扩容是怎么避免死循环的？**
→ JDK 7 用**头插法**——并发扩容时链表顺序反转，**两个线程可能同时把 A 插到 B 前面，又把 B 插到 A 前面，形成环 → `get` 无限循环**（这是 JDK 7 的著名 bug）。**JDK 8 改成尾插法**，链表顺序不变，**不可能形成环**，死循环问题消失。⚠️ 但数据覆盖/丢失问题仍然存在（这也是为什么 JDK 8 的 `ConcurrentHashMap` 也必须用 `putIfAbsent` 这类原子 API）。

**追问：并发下正确地计数应该怎么做？**
→ **不要用 `map.size()` 判断「再放一个会不会超」**——`size()` 是估算值，且检查和放入不是原子的。**正确做法：用 `LongAdder` 单独计数，或者用 `AtomicLong`；或者用 `ConcurrentHashMap` 的 `mappingCount()`（比 `size()` 稍准）**。

**追问：其他并发容器有哪些？**
→ | 容器 | 用途 | 特点 |
|------|------|------|
| | `CopyOnWriteArrayList` | 读极多写极少的列表 | **写时复制**，读完全无锁 |
| | `ConcurrentLinkedQueue` | 无锁并发队列 | CAS 实现，不阻塞 |
| | `LinkedBlockingQueue` / `ArrayBlockingQueue` | 生产者消费者 | **有界可阻塞**，配线程池用 |
| | `ConcurrentSkipListMap` | 无锁有序 Map | 跳表实现，支持范围查询 |
| | `Collections.synchronizedMap` | 给 Map 加锁包装 | ⚠️ **整个 Map 一把锁**，不如 `ConcurrentHashMap` |
| | `AtomicInteger` / `LongAdder` | 原子计数 | `LongAdder` 高竞争下优于 `AtomicLong` |

---

## Q10. 虚拟线程是什么？什么时候该用，什么时候不该用？

**答：**

**结论：虚拟线程（Virtual Thread，Java 21 正式引入）是「由 JVM 调度的轻量级线程」——它把「昂贵的线程」和「廉价的任务」解耦，让 IO 密集型应用能开几万个并发请求。**

**版本状态（必须说准）**：

| 版本 | 状态 |
|------|------|
| **Java 19 / 20** | 预览（Preview） |
| **Java 21** | ⭐ **正式版**（JEP 444） |
| **Java 24** | **JEP 491 修复了「synchronized 钉住载体线程（pinning）」问题** |
| **Java 25（LTS）** | ⭐ **第一个包含该修复的 LTS，生产可用** |

**核心机制**：

```
虚拟线程（Virtual Thread）        ← 轻量，由 JVM 调度，不是 OS 线程
      │  挂载（mount）
      ▼
载体线程（Carrier Thread）        ← 真正的 OS 线程（平台线程）
```

- **虚拟线程由 JVM 用户态调度**，创建成本极低——**可以创建几十万甚至更多**；
- **一个载体线程可以承载成千上万个虚拟线程**，虚拟线程阻塞时，**载体线程被释放去跑别的虚拟线程**（不占 OS 线程）；
- **虚拟线程总是守护线程**（不能设 `setDaemon(false)`）；**没有线程池**——它就是廉价的，可以直接 `new`。

**⭐ 最大的架构变化：不用池化虚拟线程**。

```java
// ✅ 虚拟线程不需要池——它本身就是廉价的
Thread.ofVirtual().start(() -> handle(request));

// ❌ 传统思维：给虚拟线程也套个池（会白白吃掉虚拟线程的优势）
Executors.newFixedThreadPool(200).submit(() -> handle(request));
```

**Spring Boot 3.2+ 一行开启**：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

**⭐ 适用与不适用（这是必考判断题）**：

| | 场景 | 原因 |
|---|------|------|
| ✅ **适合** | **IO 密集**：大量等待数据库、HTTP、消息队列 | 等待时虚拟线程几乎不占资源，**并发上去了，CPU 也没浪费** |
| ❌ **不适合** | **CPU 密集**：大量计算、加密、编解码 | **虚拟线程不会让计算变快**——CPU 核数是硬上限，多开只是增加调度开销 |
| ⚠️ **注意** | **需要 ThreadLocal 的场景** | 每个虚拟线程一个 `ThreadLocal` → **内存开销会随并发数线性增长**。Java 25 提供了 **Scoped Values（JEP 506）** 作为替代方案 |

**⭐ 最关键的一条限制：数据库连接池变成了瓶颈**。

```java
// ❌ 10000 个虚拟线程 → 全部去抢 20 个数据库连接
//    虚拟线程的优势被下游的连接池抹平了
```

**结论：用了虚拟线程，连接池、HTTP 客户端池的大小都要重新评估——它们现在是真正的瓶颈。** 这也是为什么「虚拟线程 + 连接池大小不变」通常得不到预期收益。

**追问：虚拟线程会被 pinning（钉住）吗？**
→ **这是版本相关的关键点**：
- **Java 21~23**：⚠️ **会**。如果虚拟线程在 `synchronized` 块里阻塞，或者在 `Object.wait()` 里等待，**它会钉住载体线程**（载体无法被释放）——大量这种场景下虚拟线程的并发优势会大幅缩水。
- **Java 24+（含 25 LTS）**：⭐ **JEP 491 修复了 `synchronized` 的 pinning 问题**——JVM 重构了 `synchronized` 的实现，让阻塞时能释放载体线程。

**⚠️ 注意：Java 24+ 修复的是 `synchronized` 的 pinning；`Object.wait()` 在原生（foreign）函数调用中的 pinning 问题在后续版本继续改进。** 面试里说「Java 25 起 `synchronized` 不再钉住载体线程」是准确的。

**追问：虚拟线程和 `ThreadLocal` 怎么配合？**
→ **能用，但要注意成本**。每个虚拟线程都有自己的 `ThreadLocal` 值——**虚拟线程数量是百万级时，ThreadLocal 的内存开销会非常可观**。**Java 25 的 Scoped Values（JEP 506）** 是官方给的现代替代方案：它是「不可变、作用域受限」的上下文传递方式，**不会为每个线程分配存储**，而是把值放在结构化作用域的调用栈里。

**追问：虚拟线程能提升性能吗？**
→ ⚠️ **要分清提升的是什么**：
- **提升的是「并发吞吐」（同时处理多少请求）**，不是「单个请求的响应时间」；
- **提升的前提是 IO 等待占大头**。如果 99% 时间在算，虚拟线程**一点忙都帮不上**；
- **很多「虚拟线程提速」的案例，其实是「原来的固定线程池被 200 个线程卡住了」的伪命题**——换成虚拟线程只是把限制从线程数挪到了下游资源上。
