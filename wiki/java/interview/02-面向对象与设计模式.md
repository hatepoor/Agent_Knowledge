# 面向对象与设计模式

> **什么时候该读**：面试第二轮的常客——面试官想看你是不是只会「继承 extends」，还是真的理解多态、抽象与解耦。
> **答题主线**：**「多态 + 组合优于继承」**。Java 的三大特性、重载重写、抽象接口全都服务于一件事：让调用方依赖抽象而不是实现。设计模式就是这套解耦手法的工具箱，SOLID 是它的检查清单。

---

## Q1. 封装、继承、多态在 Java 里分别靠什么实现？多态的底层原理是什么？

**答：**

三大特性在 Java 里的实现手段：

| 特性 | Java 的实现机制 | 关键点 |
|------|----------------|-------|
| **封装** | `private` 修饰字段 + 访问器方法 | 隐藏实现细节，暴露稳定接口 |
| **继承** | `extends`（类）/ `implements`（接口） | 复用代码 + 表达「is-a」关系 |
| **多态** | **运行时动态绑定**（父类引用指向子类对象，调父类方法实际执行子类实现） | 编译期看声明类型，运行期看实际类型 |

**多态的底层原理 = 虚方法表（vtable）**：

```
编译期：  Animal a = new Dog();
          a.speak();   // 编译器查 Animal 的方法表 → 槽位 #3

运行期：  实际对象是 Dog → 查 Dog 的 vtable → 槽位 #3 指向 Dog.speak() → 执行
```

JVM 在类加载、链接阶段为每个类生成一张**方法表**（`vtable`），记录「每个方法签名 → 实际实现地址」。虚方法调用（`invokevirtual`）在运行期按**实际对象的类型**查表，而普通方法调用（`invokestatic`/`invokespecial`）在编译期就绑定了。

⚠️ **推论：只有「可被重写的方法」才有运行时多态。** 以下三类调用是**静态绑定**，不走 vtable：

| 调用形式 | 绑定时机 | 例子 |
|---------|---------|------|
| 静态方法 | 编译期 | `Animal.speak()` |
| `private` 方法 | 编译期 | 外部不可见，无法重写 |
| `final` 方法 | 编译期 | 禁止重写，编译期直接绑定 |

**追问：多态的「编译期多态」和「运行期多态」分别指什么？**
→ **编译期多态 = 重载（overload）**：编译器根据实参的**静态类型和数量**决定调哪个方法，编译期就定死了。**运行期多态 = 重写（override）**：编译器只确定「调哪个签名」，实际执行哪个实现由对象的**实际类型**决定。重载不叫多态是通俗说法，但面试里最好说清楚这个区分。

**追问：`final` 方法会破坏多态吗？**
→ 会，但这是**故意的**。`final` 方法承诺「子类不许改我的实现」，此时编译器可以安全地把调用点直接绑定到父类实现，省掉一次 vtable 查表。**这是性能优化，不是缺陷**。

## Q2. 重载和重写有什么区别？方法重载能只改返回值吗？

**答：**

| 维度 | **重载（Overload）** | **重写（Override）** |
|------|-------------------|-------------------|
| 发生范围 | **同一个类内**（或继承链中） | **父子类之间** |
| 判定依据 | 方法名相同 + **参数列表不同**（个数/类型/顺序） | 方法名相同 + **参数列表完全相同** + 返回类型协变 |
| 返回值 | 可以不同 | 相同或**协变**（子类返回父类型的子类型） |
| 访问修饰符 | 无要求 | **不能比父类更严格**（protected → public 可以，反之不行） |
| 异常 | 无要求 | 不能抛出比父类更宽的受检异常 |
| 绑定时机 | 编译期（静态多态） | 运行期（动态多态） |

**⚠️ 重载能不能只改返回值？不能。** 因为**参数列表才是重载的判定依据，返回值不参与签名判定**：

```java
public class OverloadDemo {
    void show(int x) { System.out.println("int"); }
    // ⚠️ 编译错误：已有 show(int)，返回值不同不构成重载
    // int show(int x) { return 1; }

    void show(long x) { System.out.println("long"); }   // ✅ 加宽后是另一个重载
    void show(Object o) { System.out.println("Object"); } // ✅ 另一个重载
    void show(String s) { System.out.println("String"); }

    public static void main(String[] args) {
        OverloadDemo d = new OverloadDemo();
        d.show(1);        // int    —— 精确匹配优先
        d.show(1L);       // long
        d.show("s");      // String
        d.show((Object) 1); // Object

        // ⚠️ 重载解析是「最具体优先」，不是「最近声明」
    }
}
```

**重载解析规则（面试常考顺序）**：

1. 编译器**先看实参的静态类型**，收集所有候选；
2. 按「**不擦除泛型后完全匹配 > 需要加宽 > 需要装箱/拆箱 > 需要变长参数**」逐级筛选；
3. 同级则选「**类型最具体**」的（`String` 比 `Object` 具体）；
4. 仍然无法唯一确定 → **编译歧义错误**。

**追问：为什么 `@Override` 注解是必须的？**
→ 不是必须，但**强烈建议写**。它让编译器帮你检查「真的是重写」——参数写错、漏写 `@Override` 导致变成重载，编译器会报错。⚠️ **子类方法少了 `@Override` 但签名写错了，编译器不会报错，运行时才炸**——这是 Spring 项目里非常隐蔽的 bug 来源（比如事务方法参数写错，事务直接不生效）。

**追问：构造器能重写吗？**
→ **不能**。构造器不是方法，不参与继承——`super()` 调的是父类构造器，不是「重写」。子类构造器一定先调用父类构造器（隐式 `super()`，父类无无参构造器时编译报错）。

## Q3. 抽象类和接口有什么区别？什么时候用哪个？

**答：**

**核心区别（Java 8 之后已经大幅收敛，但本质差异还在）**：

| 维度 | **抽象类**（`abstract class`） | **接口**（`interface`） |
|------|---------------------------|---------------------|
| 继承方式 | **单继承**（一个类只能 extends 一个） | **多实现**（可以 implements 多个） |
| 成员变量 | 可以有任意状态的字段 | 字段默认 `public static final`（常量） |
| 构造器 | ✅ 有（给子类初始化用） | ❌ 没有 |
| 方法 | 抽象方法 + **普通方法 + 静态方法 + 私有方法** | 抽象方法 + `default` + `static` + `private`（Java 9+） |
| 访问修饰符 | 任意 | 接口方法默认 `public`（不能改窄） |
| 设计意图 | **「是一个」**（is-a）的模板 + 共用实现 | **「能做什么」**（can-do）的能力契约 |

**⭐ 面试标准答法**：**接口是「能力契约」，抽象类是「类族模板」**。

```java
// ✅ 接口：表达「能做什么」，多个实现互不相关
public interface Flyable {
    void fly();
    default boolean canLand() { return true; }   // Java 8+ default 方法
}

// ✅ 抽象类：表达「是什么」，子类共享一部分实现和状态
public abstract class AbstractAnimal {
    protected String name;                        // 抽象类可以有实例字段
    protected abstract void makeSound();
    public void introduce() {                     // 共用实现，子类不用重复写
        System.out.println("我是 " + name);
    }
}
```

**Java 8 之后接口新增的 `default` 方法**，是接口和抽象类边界模糊化的原因：接口可以带默认实现，但**依然不能有实例字段、不能有构造器**——这是两条硬边界。

**选择决策树**：

```
需要多个不相关的类型共享同一套「能力」？
  → 接口
需要子类复用一份公共实现 + 共享状态？
  → 抽象类
只是想让调用方面向抽象编程，其实两者都行？
  → 优先接口（组合优于继承）
```

**追问：接口的 `default` 方法如果多个接口有同名方法怎么办？**
→ 两条规则：① **继承优先**——子接口/实现类可以重写来消歧；② **编译报错**——如果两个无关接口的 default 方法同名且实现类都没重写，必须在实现类里**显式重写并用 `接口名.super.方法名()` 指定调哪个**：

```java
public class Robot implements Flyable, Runnable {
    @Override
    public void run() {
        Flyable.super.fly();   // ⚠️ 必须显式指定，否则编译歧义
    }
}
```

**追问：接口可以有构造器吗？为什么？**
→ **不能**。接口描述的是「契约」，不是「实现」——接口的实例由实现类创建，构造过程属于实现细节。接口里要放共享状态，只能用 `static final` 常量（编译期常量，天然不可变）。

**追问：`sealed` 类和接口是什么？**
→ **Java 17 引入**（JEP 409）。`sealed interface Shape permits Circle, Square;` 表示「**这个类型层次是封闭的**」——只有 `permits` 里列出的子类能继承/实现它。价值在于：配合 `switch` 的模式匹配，**编译器能证明 switch 覆盖了所有情况**，漏一个分支直接编译报错，而不是运行时才发现。详见 [[java/01-入门阶段-基础教程/第02章-面向对象/2.3-抽象类与接口]]。

## Q4. Java 的多态在运行期是怎么实现的？`instanceof` 为什么被重写了？

**答：**

**多态的实现 = 动态绑定 + 虚方法表**，已在 Q1 讲过机制。这里说**「怎么用对」**。

**问题所在**：老的 `instanceof` 写法要写两次类型，一次判断一次强转：

```java
// ❌ 老写法：判断一次、强转一次
if (obj instanceof Dog) {
    Dog dog = (Dog) obj;
    dog.bark();
}
```

**Java 16 起（正式）支持模式匹配（pattern matching for instanceof）**：

```java
// ✅ 新写法：判断 + 绑定一步到位
if (obj instanceof Dog dog) {
    dog.bark();          // 编译器知道 dog 的类型，不用再强转
}
```

⚠️ **变量作用域**：模式变量在 `if` 为真的分支内有效（还支持 `&&` 短路组合：`obj instanceof Dog d && d.bark()`），出了分支就不能用了。

**Java 21 起 switch 也支持模式匹配**，配合 `sealed` 可以做「穷尽匹配」：

```java
sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}

static double area(Shape s) {
    return switch (s) {
        case Circle c   -> Math.PI * c.r() * c.r();
        case Square sq  -> sq.side() * sq.side();
        // ⚠️ 因为 Shape 是 sealed 且两个分支都覆盖，编译器知道穷尽了，不用写 default
    };
}
```

**追问：为什么 `instanceof` 的重写被推迟到 Java 16？**
→ 因为它是**语言特性的破坏性演进**：老代码里可能已经有同名局部变量叫 `dog`，新写法引入的模式变量会造成遮蔽（shadowing）冲突。Java 16 正式版明确「模式变量只在条件为真的分支内引入」，避免了大部分冲突。

**追问：`getClass()` 和 `instanceof` 有什么区别？**
→ `getClass() == X.class` 是**精确类型判断**（子类不算）；`instanceof` 是**包含判断**（子类算）。**写业务代码优先用 `instanceof`**——它对继承体系更友好。

**追问：Java 的多态在接口上表现和类上一样吗？**
→ 完全一样。接口方法的调用也是 `invokevirtual`（或 JDK 11+ 的 `invokeinterface`），运行期按实际对象类型查找实现。**接口只是把「方法签名集合」和「实现」解耦了，动态绑定的机制没变。**

## Q5. `equals` 和 `hashCode` 的契约是什么？只重写一个会出什么问题？

**答：**

**契约（两句话必须记牢）**：

1. **一致性**：在对象未被修改的前提下，多次调用 `equals` 必须返回相同结果；
2. **同值同哈希**：`a.equals(b) == true` ⟹ `a.hashCode() == b.hashCode()`；
3. **对称性**：`a.equals(b)` 与 `b.equals(a)` 结果相同；
4. **传递性**：若 `a.equals(b)` 且 `b.equals(c)`，则 `a.equals(c)`；
5. **非空**：`a.equals(null)` 必须是 `false`（不能抛 NPE）。

**⚠️ 只重写 `equals` 不重写 `hashCode` 会怎样？**

```java
public class User {
    private final String name;
    public User(String name) { this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        return name.equals(((User) o).name);
    }

    // ⚠️ 没有重写 hashCode —— 编译能过，运行出问题
}

public class HashMapDemo {
    public static void main(String[] args) {
        User u1 = new User("张三");
        User u2 = new User("张三");
        System.out.println(u1.equals(u2));       // true
        System.out.println(u1.hashCode());       // 1234
        System.out.println(u2.hashCode());       // 1234 —— 巧合相同（Object 用内存地址，不同对象本该不同）

        Map<User, String> map = new HashMap<>();
        map.put(u1, "A");
        System.out.println(map.get(u2));         // ⚠️ null！明明 equals 相等
    }
}
```

**机制**：`HashMap.put` 先用 `hashCode()` 定位桶，桶内再逐个用 `equals()` 比较。所以**两个 `equals` 相等的对象必须 `hashCode` 相等**，否则会被扔进不同的桶，`get` 时在另一个桶里找，永远找不到。

⚠️ 这里的 `u1.hashCode()` 和 `u2.hashCode()` 输出相同是**巧合**（取决于内存布局），实际生产中不重写就会不同。

**正确写法**：

```java
@Override
public int hashCode() {
    return Objects.hash(name);   // 字段必须和 equals 用的字段一致
}
```

⚠️ **铁律：`equals` 里比较了哪些字段，`hashCode` 就必须包含哪些字段**。多一个少一个都会破坏契约。

**追问：为什么用 HashMap 要重写 `hashCode`，用 `HashSet` 呢？**
→ `HashSet` 内部就是 `HashMap`，`add` 走的是 `hashCode` 定位 + `equals` 去重。所以 **`HashSet` 里放自定义对象，必须同时重写这两个方法**，否则重复元素加不进去。

**追问：为什么 HashMap 的 key 最好用不可变对象？**
→ 因为 `hashCode` 的结果被缓存进了 HashMap 的节点里。**如果 key 可变，put 之后改了内容，hash 变了，就再也 get 不到了**——数据「凭空消失」。`String` 之所以是最佳 key 类型，就是因为它不可变（见 [[java/01-入门阶段-基础教程/第01章-核心语法/1.4-字符串与包装类]]）。

**追问：对象的哈希值默认是怎么算的？**
→ `Object.hashCode()` 返回**对象身份哈希码**（通常由内存地址派生，在 JVM 内部生成后缓存在对象头 Mark Word 里），**同一个对象每次调用返回同一个值**（因为被缓存了），但不同对象大概率不同。注意它**不是真的内存地址**，也不保证跨 JVM 运行稳定。

## Q6. 单例模式有几种实现方式？为什么《Effective Java》推荐枚举？

**答：**

**四种实现 + 一票否决**：

| 方式 | 做法 | 是否线程安全 | 是否能被反射破坏 | 是否能被反序列化破坏 |
|------|------|------------|----------------|--------------------|
| **饿汉式** | 类加载时就 `new` 好单例 | ✅ | ⚠️ 反射能改 | ✅ 安全 |
| **懒汉式（加锁）** | `getInstance()` 里 `synchronized` | ✅ | ⚠️ 反射能改 | ✅ 安全 |
| **双重检查锁 DCL** | 两次判空 + `volatile` | ✅ | ⚠️ 反射能改 | ✅ 安全 |
| **静态内部类** | 懒加载 + JVM 保证初始化线程安全 | ✅ | ⚠️ 反射能改 | ✅ 安全 |
| ⭐ **枚举** | `enum Singleton { INSTANCE; }` | ✅ | ❌ **不能** | ❌ **不能** |

```java
// ⭐ 枚举实现：最简洁也最安全
public enum Singleton {
    INSTANCE;

    public void doWork() {
        System.out.println("do work");
    }
}

// 使用
Singleton.INSTANCE.doWork();
```

**为什么枚举最安全？三条理由**：

1. **序列化安全**：Java 规范规定，**枚举的序列化用 name 字段做标识**，反序列化时返回容器里已有的那个实例，不会造出第二个；
2. **反射安全**：JDK 明确禁止通过反射修改 `final` 枚举字段——`Constructor.newInstance()` 对枚举类型会抛 `IllegalArgumentException`；
3. **线程安全由 JVM 兜底**：枚举类的静态初始化由 JVM 保证「只执行一次且线程安全」（类初始化锁机制），不需要自己写 `synchronized`。

**DCL 的 `volatile` 为什么不能省？**

```java
public class DclSingleton {
    private static volatile DclSingleton instance;   // ⚠️ volatile 必须有

    private DclSingleton() {}

    public static DclSingleton getInstance() {
        if (instance == null) {                     // 第一次检查：无锁快速路径
            synchronized (DclSingleton.class) {
                if (instance == null) {             // 第二次检查：持锁复查
                    instance = new DclSingleton();
                }
            }
        }
        return instance;
    }
}
```

⚠️ 没有 `volatile` 时，`instance = new DclSingleton()` 这一行会被编译成三步（分配内存 → 初始化 → 引用赋值），**JIT 可能重排成「分配 → 引用赋值 → 初始化」**。别的线程看到非 null 的引用时，对象**还没初始化完** → 拿到半成品对象。`volatile` 禁止了这个重排。

**追问：单例什么时候该用？**
→ **谨慎使用**。单例=全局可访问 = 隐藏依赖 = 测试困难 + 并发风险。**现代 Java 优先用 Spring 的单例 Bean**（容器管理、有生命周期、可测试）。真正的单例适合「**进程内唯一且无状态**」的资源：线程池、配置加载器、ID 生成器。**有可变状态的单例是并发 Bug 温床**。

**追问：为什么说「枚举单例不会被序列化破坏」？**
→ 因为 Java 规范**专门为枚举定义了序列化机制**：写出去的是枚举的 `name`（字符串），读回来时用 `Enum.valueOf()` 查容器，返回**已有的那个实例**。普通单例类默认序列化会把整个对象写出去，反序列化时 `readResolve()` 之前会造出**新对象**，导致「两个单例」。

**追问：静态内部类为什么是懒加载的？**
→ 因为**静态嵌套类是一个独立的类**，它只在**首次被引用时**才被初始化（触发类加载）。外部类 `Outer` 的 `<clinit>` 只负责创建 `Outer` 的静态字段，不会触发 `Holder` 的初始化——所以实例在第一次 `getInstance()` 时才创建，且由 JVM 的类初始化锁保证线程安全。

## Q7. 工厂模式有哪几种？Spring 里的 Bean 创建算不算工厂模式？

**答：**

**三个层次，面试常被混着问**：

| 模式 | 结构 | 意图 | 什么时候用 |
|------|------|------|-----------|
| **简单工厂** | 一个静态方法 `create(type)` 用 `if/switch` 分发 | 隐藏创建细节，**但违反开闭原则**（加类型要改工厂） | 类型少且稳定 |
| **工厂方法** | 抽象父类 + 具体子类各实现一个工厂方法 | **每个产品一个工厂**，新增类型不用改老代码 | 产品类型会扩展 |
| **抽象工厂** | 工厂生产「产品族」 | 保证同一产品族风格一致 | 有「维度 × 型号」的矩阵场景 |

```java
// 工厂方法：新增类型不用改老代码
public interface Logger {
    void log(String msg);
}

public abstract class LoggerFactory {
    public abstract Logger createLogger();      // 工厂方法
}

public class FileLoggerFactory extends LoggerFactory {
    @Override
    public Logger createLogger() { return new FileLogger(); }
}
```

**Spring 里的 Bean 创建确实是工厂模式的极致应用**：

- `BeanFactory` 接口就是**工厂方法**的定义（`getBean(name)`）；
- `FactoryBean<T>` 接口更是**直接以工厂命名**的——它定义的 `getObject()` 返回真正要放进容器的对象，而 `FactoryBean` 本身是个工厂。`getBean("x")` 拿到的不是 `FactoryBean` 本身，而是它 `getObject()` 的产物；
- `AutoConfigurationImportSelector` 筛选候选配置类后注册 Bean 定义，**每个配置类本质上都是一个「配置工厂」**。

**追问：工厂方法和抽象工厂怎么选？**
→ 看**变化的方向**：如果新增的是「**同维度的新型号**」（比如日志器：文件/控制台/远程），用**工厂方法**；如果新增的是「**新的维度**」（比如「Windows 版文件日志器 / Linux 版文件日志器」，产品和平台两个维度交叉），用**抽象工厂**。

**追问：简单工厂违反开闭原则吗？**
→ 违反。**每加一个新类型都要改 `create()` 方法**。但它的优点是**简单、无需额外的类层次**——类型少且几乎不变时（内部工具类），简单工厂是更务实的选择。**不要为了模式而模式**。

**追问：`FactoryBean` 和 `@Bean` 方法有什么区别？**
→ `@Bean` 是**在配置类里声明一个方法**，Spring 调它来造对象；`FactoryBean` 是**实现一个接口**，Spring 调它的 `getObject()` 来造对象。区别在于 `FactoryBean` 能**完全控制对象的创建与获取过程**（还能暴露 `&beanName` 拿到工厂本身），但侵入性更强。**普通业务用 `@Bean`，需要精细控制（代理、延迟、定制查找逻辑）才用 `FactoryBean`。**

## Q8. 建造者模式解决了什么问题？为什么不能直接用构造器？

**答：**

**建造者模式（Builder）解决的是「构造参数太多 + 可选项太多」导致的「构造器重载地狱」**。

**问题演进**：

```java
// 第 1 步：只能全传
new HttpClient("https://api.example.com", 5000, 3, true, "application/json", null);

// 第 2 步：加可选参数 → 构造器爆炸
new HttpClient(url, timeout, retries, https, contentType, proxy, headers, followRedirects);
// ... 组合爆炸，构造器数量指数增长

// 第 3 步：JavaBean setter —— 能用，但对象「半初始化」状态暴露
HttpClient c = new HttpClient();
c.setUrl("...");
c.setTimeout(5000);   // ⚠️ 中途抛异常的话，c 是个不完整的对象
```

**建造者的解法**：分步构建，**构造过程完整后才交付对象**。

```java
public class HttpClient {
    private final String url;
    private final int timeout;
    private final int retries;
    private final boolean https;
    private final String contentType;

    private HttpClient(Builder b) {     // ⚠️ 构造器私有，只能通过 Builder 创建
        this.url = b.url;
        this.timeout = b.timeout;
        this.retries = b.retries;
        this.https = b.https;
        this.contentType = b.contentType;
    }

    public static class Builder {
        private String url;
        private int timeout = 3000;        // 带默认值
        private int retries = 1;
        private boolean https = true;
        private String contentType = "application/json";

        public Builder url(String url) { this.url = url; return this; }
        public Builder timeout(int ms) { this.timeout = ms; return this; }
        public Builder retries(int n) { this.retries = n; return this; }

        public HttpClient build() {
            if (url == null) throw new IllegalStateException("url 必填");
            return new HttpClient(this);
        }
    }

    public static Builder builder() { return new Builder(); }
}

// 使用：可读性极强，参数名一目了然
HttpClient c = HttpClient.builder()
        .url("https://api.example.com")
        .timeout(5000)
        .retries(3)
        .build();
```

**建造者的三个优势**：

1. **可读性**：`.timeout(5000)` 比第 3 个位置的 `5000` 清楚一百倍；
2. **可选参数自由**：默认值写在 Builder 里，不需要靠重载组合表达；
3. **对象不可变**：字段全 `final`，`build()` 之后对象状态固定——这也是它常被用来实现「不可变对象」的原因。

**追问：Java 标准库里有哪些建造者？**
→ `StringBuilder`、`Calendar`、`HttpClient`（Java 11+）、`Stream.Builder`、`Optional`（`Optional.of().orElse()` 风格）。**更常见的用法是 Lombok 的 `@Builder` 注解**，在编译期生成上面这套代码。

**追问：建造者和工厂方法怎么选？**
→ **建造者管「组装过程」，工厂方法管「创建哪个类型」**。如果创建逻辑简单（一个 `new` 就够），用工厂方法；**如果对象有很多可选属性、或者创建过程本身有分步逻辑，用建造者**。

**追问：建造者有什么缺点？**
→ **代码量大**（一个类要写两遍字段声明），而且**只能用于「同一类型」的对象组装**，不能像抽象工厂那样在不同类型间选择。要权衡——**参数少（≤3 个）就直接用构造器，别上建造者。**

## Q9. 策略模式、模板方法模式、观察者模式分别解决什么问题？

**答：**

三个都是**行为型模式**，核心区别是「变化的那个轴」在哪里：

| 模式 | 变化的轴 | 一句话 | 典型实现 |
|------|---------|-------|---------|
| **策略**（Strategy） | **「怎么做」变了** | 把一组可互换的算法封装成同接口的不同实现 | `Comparator`、Spring 的 `TransactionManager`、支付渠道 |
| **模板方法**（Template Method） | **「流程的步骤」变了** | 定义算法骨架，把可变步骤留给子类 | `AbstractList`、`JdbcTemplate`、Spring 的 `AbstractApplicationContext.refresh()` |
| **观察者**（Observer） | **「谁需要知道」变了** | 一对多依赖，状态一变就通知所有订阅者 | Spring 的 `ApplicationEvent`、MQ 生产者、`Observer`/`Observable` |

```java
// ✅ 策略：同一件事，不同算法，运行时可换
public interface DiscountStrategy {
    double apply(double amount);
}
public class VipDiscount implements DiscountStrategy {
    public double apply(double amount) { return amount * 0.8; }
}
// 调用方持有策略引用，切换算法只改这一行 —— 消除 if/else 分支
```

```java
// ✅ 模板方法：流程固定，个别步骤可覆盖
public abstract class DataImporter {
    public final void importData() {        // final 锁死骨架，子类不能改流程
        open();
        read();          // ← 可变步骤
        close();
    }
    protected abstract void read();
    protected void open() { }               // 有默认实现
    protected void close() { }
}
```

```java
// ✅ 观察者：多对多解耦
public interface OrderListener { void onOrderCreated(Order o); }
// 订单创建后，通知所有监听者（发短信、扣库存、推消息）
```

**面试怎么讲区别**：策略是「**换个算法**」，模板方法是「**换个步骤的实现**」，观察者是「**多一个订阅者**」。

**追问：Spring AOP 用的是哪种模式？**
→ **代理模式**（JDK 动态代理 / CGLIB），通知类型上属于**模板方法 + 环绕通知**的组合——切面定义「环绕目标方法的骨架」，但被通知的**目标对象**是动态代理，不是继承。

**追问：Spring 的事务管理器算策略吗？**
→ **算**。`PlatformTransactionManager` 是策略接口，`DataSourceTransactionManager` 和 `JpaTransactionManager` 是不同策略实现——**换数据库就换策略，调用方代码不变**。Spring 的 `DispatcherServlet` 的 `HandlerAdapter` 也是策略（适配不同请求处理方式）。

**追问：观察者模式在 Spring 里怎么体现？**
→ **事件机制**：`ApplicationEventPublisher.publishEvent()` 发布，监听方用 `@EventListener` 或实现 `ApplicationListener` 接收。**应用内事件**是进程内的观察者；**跨进程要可靠投递**就得换成消息队列（MQ 才是「分布式观察者」）。

**追问：策略模式怎么避免「类爆炸」？**
→ 用**函数式接口 + Lambda**：策略只有一个抽象方法时，直接写成 `(amount) -> amount * 0.8`，不用为每个策略建一个类。**策略模式在 Java 8 之后通常就是一个 `Function`/`BiFunction`。**

## Q10. SOLID 原则分别是什么？在实际项目里怎么落地？

**答：**

五条，面试要能**每条说出「它解决什么问题 + 一个例子」**：

| 原则 | 全称 | 一句话 | 落地例子 |
|------|------|-------|---------|
| **S** | 单一职责（Single Responsibility） | 一个类只因**一种原因**而变化 | 把「计算 + 存数据库 + 发消息」拆成三个类 |
| **O** | 开放封闭（Open/Closed） | 对扩展开放，对修改关闭 | 加新支付渠道时新增实现类，不动调用方 |
| **L** | 里氏替换（Liskov Substitution） | 子类必须能替换父类而不破坏正确性 | 子类不能收紧异常范围、不能加强前置条件 |
| **I** | 接口隔离（Interface Segregation） | 不要「胖接口」，小接口更优雅 | 拆分 `readAll()` 为大接口，不让实现类实现用不到的方法 |
| **D** | 依赖倒置（Dependency Inversion） | **高层模块不依赖低层模块，两者都依赖抽象** | Service 依赖 `UserRepository` 接口，而不是 `MySqlUserRepository` |

**依赖倒置是最被低估的一条**（也是 IoC 的理论基础）：

```
❌ 高层（Service）直接依赖低层（MySqlUserRepository）
      ↑ 换数据库 = 改 Service 代码

✅ 高层（Service）依赖抽象（UserRepository 接口）
      ↑ 容器注入具体实现，换库只改配置
```

**实际项目里最容易违反的两条**：

1. **SRP 违反的典型症状**：一个类里同时出现 `@Transactional`、HTTP 调用、JSON 序列化、字段计算——**这就是「一个类 500 行」的来源**；
2. **LSP 违反的典型症状**：父类方法声明 `throws IOException`（受检异常），子类实现却throws 一个更宽的（`Exception`）→ 编译报错；反过来子类偷偷加前置条件（参数不能为 null）→ 调用父类方法时炸。

**追问：SOLID 是不是用得越多越好？**
→ **不是**。SOLID 是**修改时的解耦指南**，不是**写新代码时的炫技清单**。实际项目里的取舍：

- **不要为了 SRP 把一个类拆成五个只有一个方法的类**——那叫「类贫血」，可读性反而下降；
- **YAGNI 原则**（You Aren't Gonna Need It）：预测不到的需求不要提前抽象；
- **判断标准**：**当你要加第 N 种情况时，改动是否只需要动一个地方**。如果加渠道要改 5 个文件，就是设计有问题。

**追问：SOLID 和设计模式是什么关系？**
→ **设计模式是 SOLID 的具体落地工具**。策略模式 = OCP 的实现；依赖倒置 = 抽象工厂/工厂方法的实现；接口隔离 = 接口拆分实践。**但 SOLID 是「目标」，模式是「手段」——先有 SOLID 的意识，用不用具体模式是次要的。**
