## 一、`ArrayList` 内部结构：数组

`ArrayList` 的全部秘密在一句话里：**它是用一个数组把元素连续存放起来**。

```text
elementData（底层数组，初始长度 10）
┌────────┬────────┬────────┬────────┬────────┐
│  "a"   │  "b"   │  "c"   │  null  │  null  │  ← 容量 capacity = 5
└────────┴────────┴────────┴────────┴────────┘
  0         1         2         3        4
                    ↑
              size = 3（有效元素个数）
```

三个概念必须分清：

| 概念 | 含义 | 代码里怎么看 |
|------|------|------------|
| **底层数组** `elementData` | 真正存放引用的数组 | 内部私有字段，外部看不到 |
| **容量（capacity）** | 数组的长度 | 内部私有字段 |
| **`size`** | **有效元素的个数** | `list.size()` 拿到的就是这个 |

⭐ **`size` 是「有效元素个数」，不是「数组容量」**。上面那个数组容量是 5，但里面只有 3 个元素，所以 `size()` 返回 3。剩下两格是 `null`，等着被后面的 `add` 填上。

（上面画的是「已经放了一些元素之后」的状态。真实的初始状态略有不同：`new ArrayList<>()` 底层数组长度是 **0**，第一次 `add` 才扩到 10。）

这个区分不是吹毛求疵，它直接决定了两件事：

1. **遍历时不能按数组容量来**——`for (int i = 0; i < 数组容量; i++)` 会读到 `null`；
2. **内存占用看容量，不看 size**——一个只有 3 个元素的 `ArrayList`，底层数组可能占着 10 个引用的空间（对象引用 4 或 8 字节，取决于 JVM 压缩指针）。

### 扩容规则

`ArrayList` 的默认初始容量是 **10**，扩容方式是 **1.5 倍**（`newCapacity = oldCapacity + (oldCapacity >> 1)`，即 `old * 1.5`）。

⚠️ 精确的触发时机是「**实际需要插入时，发现容量不够了**」——也就是在 `add` 之前才判断，而不是「每次 add 都检查」。另外注意：`new ArrayList<>()` 是**空构造**（底层数组长度为 0），第一次 `add` 才会扩到 10；`new ArrayList<>(100)` 才是直接开 100。

实测的容量变化（反射读 `elementData` 长度）：

```text
size= 1  capacity=10
size=11  capacity=15      ← 装不下第 11 个，10 → 15
size=16  capacity=22      ← 装不下第 16 个，15 → 22
size=23  capacity=33      ← 装不下第 23 个，22 → 33
```

**为什么是 1.5 倍而不是 2 倍**：2 倍扩容会让内存占用在两次扩容之间浪费太多（刚扩完用掉 50% 就又要扩）；1.5 倍是空间与复制成本的折中——扩容需要把旧数组元素全部复制到新数组，倍数越大复制越少，但内存峰值越高。

⚠️ **扩容的代价是 O(n) 的复制**。所以「已知要放 1000 个元素」时，应该 `new ArrayList<>(1000)` 一次性开好，避免中途几次扩容的反复拷贝。`ArrayList` 的每次 `add` **平均**仍是 O(1)（摊还分析：多数时候不用扩容，偶发一次 O(n) 被摊平），但**单次最坏**是 O(n)。

## 二、⭐ `remove` 的重载陷阱

这是 `List` 最高频的 bug，没有之一。

`List` 接口上有两个名字都叫 `remove` 的方法：

```java
E    remove(int index)      // 按【下标】删除，返回被删掉的元素
boolean remove(Object o)    // 按【值】删除，返回是否删成功
```

调用时传什么类型，决定走哪个重载版本。

```java
import java.util.*;

public class RemoveTrap {
    public static void main(String[] args) {
        List<Integer> nums = new ArrayList<>(List.of(10, 20, 30));

        // 情况一：remove(1) —— 1 是 int，精确匹配 remove(int index)
        //         删掉的是【下标 1】的元素，也就是 20
        Integer removed = nums.remove(1);
        System.out.println(removed + " → " + nums);   // 20 → [10, 30]

        // 情况二：remove(Integer.valueOf(1)) —— 传的是对象，匹配 remove(Object o)
        //         删掉的是【值为 1】的元素
        List<Integer> nums2 = new ArrayList<>(List.of(10, 20, 30, 1));
        boolean ok = nums2.remove(Integer.valueOf(1));
        System.out.println(ok + " → " + nums2);       // true → [10, 20, 30]
    }
}
```

⭐ **判断规则很简单**（Java 的重载解析规则：先找「不需要转换就能匹配」的那个）：

| 写法 | 匹配到哪个版本 | 实际效果 |
|------|--------------|---------|
| `remove(1)` | `remove(int index)` | ⚠️ **删下标 1** |
| `remove(Integer.valueOf(1))` | `remove(Object o)` | ✅ **删值为 1 的元素** |
| `remove((short) 1)` | `remove(int index)` | ⚠️ **删下标 1**（short 可隐式扩大为 int） |
| `remove('1')` | `remove(int index)` | ⚠️ **删下标 49**（char `'1'` 的值是 49！）→ 常抛 `IndexOutOfBoundsException` |
| `remove(1L)` | `remove(Object o)` | ⚠️ **什么都没删**（装箱成 `Long`，`Long(1)` 不等于 `Integer(1)`）——**静默失效** |

💡 **正确写法**：想删值就**显式装箱**成 `Integer`；想删下标就用 `int`。如果代码可读性重要，宁可改用 `list.removeIf(x -> x == 1)` 或按下标删除的清晰写法，不要赌重载。

⚠️ **`remove(1L)` 是最阴的一个**——它既不报错也不删东西，程序看起来「正常运行」但数据没删掉。

⚠️ **关于 `List<String>`**：`remove(0)` 在 `List<String>` 上**能正常编译**，而且**删的是下标 0**（因为 `remove(int)` 版本对任何 `List` 都存在，`String` 无关）。但 `remove("a")` 才是删值——`String` 没有对应的 `remove(int)` 可匹配，只能走 `remove(Object)`。

```java
List<String> names = new ArrayList<>(List.of("a", "b", "c"));
names.remove(0);         // ✅ 编译通过，删掉的是下标 0 的 "a" → 结果 ["b", "c"]
names.remove("a");       // ✅ 删值为 "a" 的元素（此处已无 a，等于没删）
```

## 三、常用 API 与 `subList` 的真相

| 方法 | 作用 | 时间复杂度 |
|------|------|-----------|
| `add(E e)` | 末尾追加 | 平均 O(1) |
| `add(int index, E e)` | 在指定位置插入 | O(n)（要搬移后续元素） |
| `get(int index)` | 按下标取元素 | **O(1)** |
| `set(int index, E e)` | 替换下标处的元素，返回旧值 | O(1) |
| `remove(int index)` | 按下标删除，返回被删元素 | O(n) |
| `remove(Object o)` | 按值删除，返回 boolean | O(n) |
| `indexOf(Object o)` | 找**首次**出现的下标，找不到返回 `-1` | O(n) |
| `lastIndexOf(Object o)` | 找最后一次出现的下标 | O(n) |
| `contains(Object o)` | 是否包含 | O(n) |
| `size()` / `isEmpty()` | 元素个数 / 是否为空 | O(1) |
| `clear()` | 清空所有元素 | O(n) |
| `toArray()` | 转成数组 | O(n) |

⚠️ **`indexOf` 找的是「首次出现」**。`List` 里可以有重复元素，所以想找最后一个要用 `lastIndexOf`。

### ⭐ `subList` 是视图，不是拷贝

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));
List<String> sub = list.subList(1, 3);   // 取出下标 1、2 两个元素，即 ["b", "c"]
```

⭐ **`subList` 返回的不是一份拷贝，而是原列表的一段「窗口」（视图 / view）**。两边共享同一份数据：

```java
System.out.println(sub);          // [b, c]
list.set(0, "B");                  // 改原列表
System.out.println(sub);          // [b, c] —— 这个位置本来就没变，看不出效果
list.set(1, "X");                  // 改的是 sub 覆盖范围内的位置
System.out.println(sub);          // [X, c] —— sub 跟着变了！
```

这带来两个实际风险：

1. **内存风险**：你本以为 `subList` 只是截取一段、不占额外内存，实际上它只是「一个引用 + 上下边界」，几乎不占空间——但反过来说，**原列表一直活着，subList 就一直有效**，两者互相牵连；
2. **结构性修改风险**：**在 `subList` 存在期间，如果对原列表做了结构性修改**（`add`/`remove`/`clear` 等），之后再对 `subList` 调用 `add`/`remove` 就会抛 `ConcurrentModificationException`（原列表的 `modCount` 变了，而 `subList` 记着自己那份旧版本号）。

   ⚠️ 但注意：只是 `set`（改元素值、不改结构）**不会**触发这个异常。

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));
List<String> sub = list.subList(1, 3);   // 窗口 = ["b", "c"]

list.set(1, "X");          // 非结构性修改
System.out.println(sub);   // [X, c] —— sub 跟着变了

list.remove(0);            // ⚠️ 结构性修改
sub.add("Z");              // ❌ ConcurrentModificationException
```

💡 **需要一份真正独立的子列表**，用 `new ArrayList<>(list.subList(1, 3))`——先视图后拷贝。

## 四、`LinkedList`：双向链表，以及它被高估的程度

`LinkedList` 的底层是**双向链表（Doubly Linked List）**：每个节点存「数据 + 前一个节点的引用 + 后一个节点的引用」。

```text
        head ← → [a] ← → [b] ← → [c] ← → null
         ↓                                  ↓
       first                              last
```

它有两个身份：

- 实现了 `List` —— 所以是列表；
- 实现了 `Deque` —— 所以**也能当队列和双端队列用**（`addFirst`/`addLast`/`removeFirst`/`removeLast`/`offer`/`poll`）。

### 它的真实性能画像

| 操作 | `ArrayList` | `LinkedList` | 说明 |
|------|-------------|-------------|------|
| `get(i)` 按下标取 | **O(1)** | **O(n)** | 链表必须从头一步步走过去 |
| `add(E)` 末尾追加 | 平均 O(1) | O(1) | 都快 |
| `add(i, e)` 中间插入 | O(n) | **O(n)** | ⚠️ 链表省的是「搬移」不是「定位」 |
| `remove(i)` 中间删 | O(n) | **O(n)** | 同上 |
| 已知节点位置后删除 | O(n)（要搬移） | O(1) | 链表的唯一主场 |

⚠️ **「中间插入链表是 O(1)」是被误传最广的误解**。链表的 O(1) 前提是「**你已经站在那个节点上**」。真实业务里，你手上的只有「第 3 个元素」这样的下标——找到它就已经 O(n) 了。所以中间插入的**总成本**是 O(n)，和 `ArrayList` 同一个量级，只是常数不同（链表省了搬移，多了指针跳转）。

### ⭐ 结论：多数场景 `ArrayList` 更好

`LinkedList` 真正占优的场景非常窄：

- **队列 / 栈 / 双端队列**：从头尾进出，不需要按下标定位。⚠️ 但即使这种情况，`ArrayDeque` 通常也更快（它是**环形数组**，内存连续、缓存友好）；
- **用 `ListIterator` 在迭代途中频繁插入删除**；
- **已有节点引用、需要 `O(1)` 摘除**（极少场景）。

而 `ArrayList` 胜出的场景覆盖了日常开发的绝大部分：按下标遍历、随机取值、绝大多数增删、遍历时顺序访问（数组内存连续，CPU 缓存命中率高）。

⚠️ **实践建议**：**默认用 `ArrayList`**。只有当你明确需要「队列/栈语义」时用 `ArrayDeque`（不是 `LinkedList`）；只有当你明确做「迭代中插入删除」时才考虑 `LinkedList`。

## 五、`Vector` 与 `CopyOnWriteArrayList`

### `Vector`：同步的遗留类

`Vector` 是 JDK 1.0 时代的老集合，与 `ArrayList` 功能几乎一样，区别是**它的每个方法都是 `synchronized`（加锁同步）**的。

⚠️ **今天不要用 `Vector`**，理由有三：

1. **性能差**：每次读写都加锁，即使单线程也付代价；
2. **锁粒度是「整个方法」**：方法返回后锁就释放，**「检查再添加」这种组合操作依然不安全**——加锁没加在正确的粒度上；
3. **遗留 API**：`elementCount()`、`capacity()` 这些老方法至今还在，`remove(int)`/`remove(Object)` 的重载陷阱也一模一样地存在。

### `CopyOnWriteArrayList`：写时复制

`CopyOnWriteArrayList`（Java 5 引入）的思路非常特别：**写的时候不原地改，而是复制出一份新数组，把新数组作为底层存储**。

```text
写操作（add/remove/set）：
  旧数组 [a, b, c]  ──复制──→  新数组 [a, b, c, d]  ← 之后读的都是新数组

读操作（get/size/迭代）：
  直接读当前数组，不需要任何锁
```

⭐ **因此它的读操作完全无锁、无阻塞，且迭代器是「快照式」的**——迭代开始时拿到一份数组引用，迭代过程中即使别人改了列表，迭代器看到的仍是旧内容，**不会抛 `ConcurrentModificationException`**。

代价是**写操作极贵**：每次写都要复制整个数组，O(n)。所以它只适合「**读极多、写极少**」的场景，比如一个监听器列表、几乎不变的黑名单。

```java
import java.util.*;
import java.util.concurrent.*;

public class ConcurrentListDemo {
    public static void main(String[] args) throws InterruptedException {
        CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
        list.add("a");

        // 迭代器是"快照式"的：迭代期间别人 add 也不会抛 ConcurrentModificationException
        Thread writer = new Thread(() -> list.add("b"));
        writer.start();
        writer.join();                 // 等写线程结束，确保 b 已写入

        for (String s : list) {
            System.out.println(s);      // a、b —— 正常遍历，没有异常
        }
    }
}
```

⭐ 注意这里**没有出现 `ConcurrentModificationException`**——这正是 `CopyOnWriteArrayList` 与普通 `ArrayList` 的关键差别：普通 `ArrayList` 遍历时修改会抛异常（见下一节），而它不会。

⚠️ 注意 `CopyOnWriteArrayList` **允许存 `null`，也允许存重复元素**——它和 `ArrayList` 一样宽松，唯一的区别在于「怎么改」：改的时候复制整个数组。

> 更完整的并发容器（`ConcurrentHashMap`、`BlockingQueue` 等）见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]]，那是中段阶段的内容。

## 六、⭐ fail-fast 机制

### 现象

```java
import java.util.*;

public class FailFastDemo {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>(List.of("a", "b", "c"));
        for (String s : list) {
            if (s.equals("a")) {
                list.remove(s);        // ⚠️ 遍历中修改集合
            }
        }
    }
}
```

运行结果：

```text
Exception in thread "main" java.util.ConcurrentModificationException
```

### 原理

`ArrayList` 内部维护一个字段 **`modCount`**：记录「这个集合的结构被改动过多少次」。

- 每次发生**结构性修改**（`add`/`remove`/`clear` 等改变元素个数或位置的操作），`modCount` 就 **+1**；
- 创建**迭代器（Iterator）**时，迭代器把当前的 `modCount` 存进自己的 **`expectedModCount`** 字段——这是「我预期看到的版本号」；
- 迭代器的 `next()` 方法在返回元素**之前**检查一次：

```java
if (modCount != expectedModCount) {
    throw new ConcurrentModificationException();
}
```

⭐ **一句话原理**：迭代器记下「我开始时这个集合是第几版」，每次 `next()` 都对一下版本号；**一旦发现版本号变了，说明有人在迭代过程中改了集合**，为了避免遍历到一个混乱的状态，迭代器立刻抛异常。

这就是 **fail-fast（快速失败）** 机制：它的目标是**尽早暴露错误**，而不是保证正确性。

⚠️ **三个必须澄清的点**：

1. **异常只在 `next()` 里检查**——这导致一个反直觉的现象：**删哪个元素决定抛不抛异常**。

   ```java
   List<String> list = new ArrayList<>(List.of("a", "b", "c"));
   for (String s : list) { if (s.equals("b")) list.remove(s); }   // ⚠️ 不抛异常！
   ```

   为什么？因为删掉 `"b"` 后集合变成 `["a", "c"]`，迭代器刚好走到了末尾，`hasNext()` 返回 `false`，循环直接结束，**再没有调用过 `next()`**，版本号根本没机会被检查。把列表改成 4 个元素、或者删首元素/末元素，就会正常抛出 `ConcurrentModificationException`。

   💡 **这说明「不抛异常」不等于「写法正确」**——它只是碰巧没被检测到。

2. **fail-fast 是「尽力而为」的检测，不是保证**。它只保证「**一旦检测到**就抛异常」，不保证「**一定**会检测到」；
3. ⚠️ **`ConcurrentModificationException` 不等于「并发」**。它跟多线程没有任何关系——**单线程里遍历时修改集合，照样抛**。名字里的 "Concurrent" 指的是「集合在你遍历它的时候又变了」，不是「多线程」。

### 三种正确写法

**写法 1：`Iterator.remove()`** —— 迭代器自己提供删除方法，会同步更新 `modCount`，是 fail-fast 的「官方解法」：

```java
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.equals("b")) {
        it.remove();          // ✅ 用迭代器删，不抛异常
    }
}
```

**写法 2：`removeIf`（推荐）** —— Java 8 起 `Collection` 提供的默认方法，底层就是安全的迭代删除：

```java
list.removeIf(s -> s.equals("b"));      // ✅ 最简洁
```

**写法 3：收集要删的元素，最后统一删** —— 适合「遍历时不想改，遍历完再改」：

```java
List<String> toRemove = new ArrayList<>();
for (String s : list) {
    if (s.equals("b")) toRemove.add(s);
}
list.removeAll(toRemove);
```

⚠️ **错误写法**：用**下标 for 循环**倒着删——虽然不会抛异常，但**会跳过元素**（因为删除后后续元素整体前移了一位，而下标在往前走）。

```java
// ⚠️ 逻辑错误，不抛异常但漏删
for (int i = 0; i < list.size(); i++) {
    if (list.get(i).equals("b")) {
        list.remove(i);        // 删完后下一个元素挪到 i 位置，却被 i++ 跳过了
    }
}
```

💡 **最佳实践：能不遍历修改就别遍历修改**——先把条件写清楚，先想好要删什么，再一次性 `removeAll` 或 `removeIf`。

## 七、Stream、`forEach`、排序与二分查找

### `forEach` 与 Stream

```java
import java.util.*;
import java.util.stream.*;

public class StreamDemo {
    public static void main(String[] args) {
        List<String> names = List.of("alice", "bob", "charlie");

        // forEach：逐个过一遍
        names.forEach(n -> System.out.println(n));

        // Stream：声明式的链式处理
        List<String> longNames = names.stream()
                .filter(n -> n.length() > 3)      // 筛选
                .map(String::toUpperCase)          // 转换
                .sorted()                          // 排序
                .collect(Collectors.toList());     // 收集成新列表
        System.out.println(longNames);            // [ALICE, CHARLIE]
    }
}
```

⚠️ `Stream` 的两种终止操作会修改原集合：`forEach` 只是逐个执行回调（不改），但 `sorted()`、`collect()` 产出新集合；而 `list.sort(...)` 和 `Collections.sort(list)` 是**原地排序**。

### 排序

```java
List<String> names = new ArrayList<>(List.of("bob", "alice", "charlie"));
names.sort(Comparator.naturalOrder());                    // 自然序（String 按字典序）
names.sort((a, b) -> b.compareTo(a));                     // 降序
names.sort(Comparator.comparingInt(String::length));      // 按长度
```

**比较器（`Comparator`）** 是一个函数式接口，只有一个方法 `compare(a, b)`：返回负数表示 a 在前，返回正数表示 b 在前，返回 0 表示相等。`Comparator.naturalOrder()` 是「按元素自身的 `Comparable` 顺序」。

⚠️ 排序要求元素**可比较**：要么元素类实现了 `Comparable`（如 `String`、`Integer` 都实现了），要么你传一个 `Comparator`。对不可比较的元素直接 `Collections.sort` 会抛 `ClassCastException`。

### ⚠️ 二分查找：必须先排序

`Collections.binarySearch(list, key)` 依赖「有序列表」——它每次取中间位置比较，只能在有序时才可能排除一半。

```java
List<Integer> nums = new ArrayList<>(List.of(1, 3, 5, 7, 9));
Collections.sort(nums);                                 // ✅ 先排序
int idx = Collections.binarySearch(nums, 7);
System.out.println(idx + " → " + nums.get(idx));       // 2 → 7
```

⚠️ **不排序就二分，结果是「未定义」的**——不会报错，但返回的下标可能指向错误的元素，或者返回 `-1`（表示没找到）而其实元素就在里面。这是**静默的错误**，比抛异常危险得多。

⚠️ **另一个坑：返回 `-1` 表示「没找到」，会和「找到下标 0」混淆吗**？不会——找到下标 0 时返回的是 `0`，不是 `-1`。但如果你想区分「没找到」和「值本身是 -1」的情况，得靠返回值判断，不能用返回值反推。

## 八、性能选型小结

| 场景 | 推荐 | 一句话理由 |
|------|------|-----------|
| 默认的列表 | **`ArrayList`** | 内存连续、缓存友好、随机访问 O(1) |
| 队列 / 栈 / 双端队列 | **`ArrayDeque`** | 环形数组，两端进出 O(1)，内存比链表省 |
| 迭代过程中频繁增删 | `LinkedList` | 少数场景真正占优 |
| 多线程「读多写少」的列表 | `CopyOnWriteArrayList` | 读无锁、写时复制 |
| 元素数量已知且很大 | `new ArrayList<>(预估容量)` | 避免中途多次扩容复制 |
| 只读、对外暴露 | `List.of(...)` | 彻底不可变，线程安全 |

### 一段综合示例

```java
import java.util.*;
import java.util.stream.*;

public class ListPractice {
    public static void main(String[] args) {
        List<String> raw = List.of("Tom", "Amy", "Tom", "Bob", "Cindy");

        // ① 去重 + 保持首次出现顺序
        List<String> distinct = raw.stream().distinct().toList();
        System.out.println(distinct);            // [Tom, Amy, Bob, Cindy]

        // ② 按长度倒序 + 取前 2
        List<String> top = raw.stream()
                .distinct()
                .sorted(Comparator.comparingInt(String::length).reversed())
                .limit(2)
                .toList();
        System.out.println(top);                 // [Cindy, Tom]

        // ③ 安全删除：removeIf
        List<String> mutable = new ArrayList<>(raw);
        mutable.removeIf(s -> s.startsWith("T"));
        System.out.println(mutable);             // [Amy, Bob, Cindy]

        // ④ 统计每个名字出现次数（Map 的用法，详见 4.3）
        Map<String, Integer> counts = new HashMap<>();
        for (String s : raw) {
            counts.merge(s, 1, Integer::sum);
        }
        System.out.println(counts);              // {Tom=2, Amy=1, Bob=1, Cindy=1}
    }
}
```

## 陷阱

1. **⚠️ 以为 `size()` 是数组容量**——它是**有效元素个数**；容量是内部字段，外部读不到，但直接影响内存占用；
2. **⚠️ `remove(1)` 删的是下标**——`List<Integer>` 上传 int 字面量就走 `remove(int index)`；想删值必须显式 `Integer.valueOf(1)` 或用 `removeIf`；
3. **⚠️ 遍历时增删会抛 `ConcurrentModificationException`**——它与多线程无关，单线程改集合照样抛；用 `removeIf` 或 `Iterator.remove()`；
4. **⚠️ 用下标 for 循环边遍历边删**——不抛异常，但会**漏删元素**（删除后元素前移，下标却继续前进）；
5. **⚠️ 以为 `subList` 是拷贝**——它是**视图**，原列表改了它跟着变；对它做结构性修改会抛异常；需要独立副本用 `new ArrayList<>(...)` 包一层；
6. **⚠️ 以为 `LinkedList` 比 `ArrayList` 快**——按下标访问是 O(n)，中间插入总成本也是 O(n)；**默认用 `ArrayList`**，要队列/栈用 `ArrayDeque`；
7. **⚠️ 二分查找前忘了排序**——不排序不报错，但结果**未定义**，属于静默错误；
8. **⚠️ 用 `Vector`**——遗留类，逐方法加锁且粒度不当，新代码一律用 `ArrayList`；
9. **⚠️ 以为 `CopyOnWriteArrayList` 适合频繁写**——每次写都复制整个数组，O(n)；它只适合读极多写极少。

## 小结

- `ArrayList` = 数组存储；⭐ **`size` 是有效元素个数，不是容量**；初始容量 10，扩容 1.5 倍，单次 `add` 平均 O(1)、最坏 O(n)
- ⭐ **`remove(int)` 删下标、`remove(Object)` 删值**——`remove(1)` 删的是下标
- ⭐ **`subList` 是视图不是拷贝**——原列表改动会反映到它
- `LinkedList` 是双向链表、按下标访问 O(n)；**多数场景 `ArrayList` 更好**，队列/栈用 `ArrayDeque`
- `Vector` 是遗留的同步类，别用；`CopyOnWriteArrayList` 写时复制、读无锁、迭代器是快照，只适合读多写少
- ⭐ **fail-fast**：`modCount`（实际版本号）≠ `expectedModCount`（迭代器预期版本号）就抛 `ConcurrentModificationException`；**与多线程无关**；正解是 `removeIf` / `Iterator.remove()`
- 二分查找**必须先排序**，否则结果未定义
