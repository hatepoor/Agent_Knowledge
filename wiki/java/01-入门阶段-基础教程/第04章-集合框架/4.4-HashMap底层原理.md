## 一、整体结构：数组 + 链表 + 红黑树

`HashMap` 的核心是一个**数组**，叫 `table`。数组的每个位置叫一个**桶（bucket）**——「桶」这个词的意思是「一个格位」，一个桶里可以装 0 个、1 个或多个元素。

⭐ **Java 8 之前的结构**：数组 + **单向链表**。
⭐ **Java 8 及以后的结构**：数组 + **链表**，但链表太长时会**变成红黑树**。

```text
table（数组，默认长度 16）
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│  0  │  1  │  2  │  3  │  4  │  5  │  6  │  7  │  ...  │
└──┬──┴──┬──┴──┬──┴──┬──┴─────┴─────┴─────┴─────┘
   │     │     │     │
   ▼     ▼     ▼     ▼
  空    [A]   空   [D]──→[F]──→[H]      ← 桶 3 里是链表
              │
              └── 链表太长时变成红黑树：
                     [D]
                    /   \
                  [F]   [H]
```

三个关键点：

1. **元素放在哪个桶，由 hash 值决定**，不是按插入顺序依次排；
2. **同一个桶里可以是多个元素**——它们的 hash 值算下来落在同一个下标；
3. **桶内先是链表，链表长度达到 8 会转成红黑树**（Java 8+）。

### 为什么是「哈希表」

**哈希（hash）** 就是「根据内容算出一个整数」。`HashMap` 用 key 的 `hashCode()`（一个 32 位整数）算出应该放在数组的哪个下标，理想情况下**每个桶各有一个元素**，查找就是「算下标 + 看一格」，两步搞定——这就是平均 O(1) 的来源。

但现实中多个 key 算出的下标可能相同（**哈希冲突 / collision**），所以每个桶才需要能装多个元素。

### 索引怎么算

```java
int index = (n - 1) & hash;    // n 是数组长度（容量）
```

这个式子里 `n` **永远是 2 的幂**（16、32、64……），所以 `n - 1` 的二进制形如 `0000...1111`。`&`（按位与）后，**结果就等于 `hash` 的低几位**——即 `hash & (n-1)` 等价于 `hash % n`，但位运算快得多。

⭐ **这就是「为什么容量总是 2 的幂」的第一个答案**：位运算取模比 `%` 更快，而且后面扩容时还有更妙的作用（见第四节）。

## 二、⭐ hash 扰动函数：`(h = key.hashCode()) ^ (h >>> 16)`

`HashMap` 里真正用来定位桶的 hash 值，不是 `key.hashCode()` 的原值，而是经过**扰动**后的值：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**扰动函数**就是「把哈希值再搅一搅，让它的低位更均匀」的小函数。

### 为什么需要它

`int` 是 32 位。但数组容量通常是 16 或 32，定位下标**只用得到低位几个比特**（`hash & 15` 只看低 4 位）。高位的信息在这一步被完全丢弃了。

问题在于：两个 key 的 `hashCode()` **只在高位不同、低位完全相同**是很常见的事（比如 `hashCode()` 返回以常量 `1234567` 结尾的数）。这时：

- `hashCode()` 不同 → 它们本该去不同的桶；
- 但 `hash & (n-1)` 只看低位 → 低位相同 → **全撞进同一个桶**。

结果就是「哈希冲突」集中爆发，查找退化成 O(n)。

### `>>> 16` 的作用

`h >>> 16` 是**无符号右移 16 位**，把 `h` 的高 16 位挪到低 16 位；再与原值 `h` 做**异或（`^`）**，效果是：**把高 16 位的特征「混入」低 16 位**。

```text
h          = 0xABCD1234
h >>> 16   = 0x0000ABCD
h ^ (h>>>16) = 0xABCD89D9
              ↑ 高 16 位的 ABCD 混进了低 16 位
```

于是定位下标时用的低位里，**已经包含了高位的信息**。原本「低位相同、高位不同」的一批 key，被打散到了不同的桶。

⭐ **一句话**：右移 16 位是为了让 `hashCode` 的高 16 位也参与桶定位，避免冲突过度集中；异或是为了把高低位混合、且**保留原值的高位特征**（异或是可逆的，不会丢信息）。

> 为什么是 16 而不是 8 或 24？因为 `hash` 在 `HashMap` 内部只保留 32 位，`>>> 16` 是**一次操作就能把高半部分整体搬到低半部分**的最直接方式；再左移回去需要额外一步，且会丢掉一部分原本就重要的低位信息。

## 三、⭐ `put` 流程：五步走

`map.put(key, value)` 的完整流程：

```text
① 计算 hash
   hash = (h = key.hashCode()) ^ (h >>> 16)      ← 扰动

② 定位桶
   index = (n - 1) & hash                        ← n = table.length

③ 桶为空？ —— 是 → 直接把新节点放进这个桶，结束

④ 桶里有元素？—— 比较两步：
   a) 第一个节点的 hash 是否 == 本次 hash？不同 → 走链表下一节
   b) 相同 → 比较 key.equals(key)
      equals 相同 → ⭐ 覆盖旧 value，返回旧 value
      equals 不同 → 继续往下走

⑤ 挂到链表尾部（Java 7 是头插，Java 8 是尾插）
   —— 过程中随时检查是否该树化：
      链表长度 ≥ 8  且  数组容量 ≥ 64  → 转红黑树
      链表长度 ≥ 8  但  数组容量 < 64  → ⭐ 先扩容（扩容会把链表拆散）
```

### 树化 vs 先扩容：为什么有 64 这个门槛

⭐ **关键规则**（Java 8 引入）：

| 条件 | 动作 |
|------|------|
| 链表长度 **< 8** | 什么都不做，继续用链表 |
| 链表长度 **≥ 8** 且 **数组容量 < 64** | **先扩容**（容量翻倍后链表被拆散，通常就不再需要树化） |
| 链表长度 **≥ 8** 且 **数组容量 ≥ 64** | **转成红黑树** |

⭐ **为什么容量不足时先扩容而不是树化**？

因为**链表长通常不是因为 key 分布差，而是因为桶太少**。容量只有 16 时，元素一多，链表自然就长。此时扩容（容量变 32、64……）能把链表拆散到更多桶里，冲突问题自然缓解——**比转红黑树更省内存、更简单**。

只有当**容量已经 ≥ 64（桶足够多）**，链表还长到 8，才说明「这个 key 的哈希分布确实很差」（比如所有 key 的 `hashCode` 都一样），这时候用红黑树把该桶的查找从 O(n) 降到 O(log n) 才划算。

### 树化的两个阈值

| 常量 | 值 | 含义 |
|------|-----|------|
| `TREEIFY_THRESHOLD` | 8 | 链表长度达到 8，触发树化 |
| `UNTREEIFY_THRESHOLD` | 6 | 红黑树节点数减少到 6，退化回链表 |

⚠️ **树化后如果元素被大量删除**，树节点数降到 6 以下会**退化（untreeify）回链表**——这是为了省内存：只剩几个元素时，红黑树的额外指针开销不划算。

> **红黑树**：一种**平衡二叉搜索树**，通过「节点染红/黑」和「旋转」规则保证树高为 O(log n)，因此查找、插入、删除都是 O(log n)。本篇只关心它的两个效果：**① 让树里的元素保持有序；② 把极端情况下的查找从 O(n) 拉回 O(log n)**。具体的旋转规则属于数据结构专题，此处不展开。

## 四、⭐ 扩容机制

### 触发条件：负载因子

**负载因子（load factor）** 是「**实际元素个数 ÷ 数组容量**」的比值，用来表示「这个哈希表装得有多满」。

`HashMap` 的默认负载因子是 **0.75**：

```java
static final float DEFAULT_LOAD_FACTOR = 0.75f;
```

扩容阈值（`threshold`）= 容量 × 负载因子。当 **`size > threshold`** 时触发扩容：

```text
容量 16，阈值 = 16 × 0.75 = 12
→ 放入第 13 个元素时，size(13) > threshold(12) → 扩容到 32，阈值变成 24
→ 放入第 25 个元素时，size(25) > threshold(24) → 扩容到 64，阈值变成 48
```

⭐ **为什么是 0.75 而不是 1.0**：容量刚好装满时，扩容会把所有元素重新搬一遍，代价最大；留 25% 的空位既能避免频繁扩容，又不会让空间浪费太多。**0.75 是「空间 vs 速度」的经典折中值**，绝大多数 Java 集合（`ArrayList` 之外的 `HashMap`、`HashSet` 等）都采用它。

⚠️ **注意扩容是 2 倍，不是 1.5 倍**——这和 `ArrayList` 的 1.5 倍增长不同，面试常对比问。

### ⭐ 扩容时为什么不用重新算 hash

扩容后容量从 `n` 变成 `2n`，桶下标公式从 `(n-1) & hash` 变成 `(2n-1) & hash`。看起来要重算，但实际可以**直接算出新位置**：

```text
旧容量 16，新容量 32：
  hash & 15   → 旧下标（0..15）
  hash & 31   → 新下标（0..31）

因为 31 = 16 + 15，所以：
  hash & 31 = (hash & 15) + (hash & 16)
             └─原下标─┘   └──要么 0，要么 16──┘
```

⭐ **结论：每个元素扩容后的新位置，只有两种可能——「原下标」或「原下标 + 旧容量」**。

所以扩容时只需遍历每个桶，把链表**拆成两条**：hash 的第 5 位（对应旧容量 16 那一档）为 0 的留在原位，为 1 的移到 `原位 + 16`。**整个过程一次 `hashCode()` 都不用调**——这比「全部重新计算 hash 再重新定位」快得多，也是 JDK 8 相对 JDK 7 的重要优化。

```text
扩容前（容量 16）                    扩容后（容量 32）
┌───┬───┬───┬───┐                 ┌───┬───┬───┬───┬───┬───┬───┬───┐
│ 0 │ 1 │ 2 │ 3 │  ...            │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │ 7 │ ...
└───┴───┴───┴───┘                 └───┴───┴───┴───┴───┴───┴───┴───┘
                                     ↑    ↑           ↑    ↑
                                   原位  原位      原位+16 原位+16
```

## 五、⭐ `equals` 与 `hashCode` 的契约

这是本篇最重要、也最实用的部分。

### 契约的两条

Java 要求任何重写 `equals` 的类**必须同时**重写 `hashCode`，并满足：

1. **相等对象必须哈希码相等**：`a.equals(b) == true` ⟹ `a.hashCode() == b.hashCode()`；
2. **哈希码相等不一定对象相等**（允许冲突）：`a.hashCode() == b.hashCode()` ⇏ `a.equals(b)`。

第一条是**强制的**，违反它 `HashMap`/`HashSet` 就会出乱子。

### ⚠️ 只重写 `equals` 不重写 `hashCode` 会怎样

```java
import java.util.*;

public class BadKeyDemo {
    // ⚠️ 只重写 equals，没有重写 hashCode
    static class BadKey {
        private final String id;
        BadKey(String id) { this.id = id; }

        @Override
        public boolean equals(Object o) {
            return o instanceof BadKey && this.id.equals(((BadKey) o).id);
        }
        // ⚠️ 没有重写 hashCode —— 用了 Object 默认实现（按内存地址算）
    }

    public static void main(String[] args) {
        Map<BadKey, String> map = new HashMap<>();
        BadKey k1 = new BadKey("A");
        BadKey k2 = new BadKey("A");

        System.out.println(k1.equals(k2));    // true —— equals 是对的
        map.put(k1, "value");
        System.out.println(map.get(k2));      // ⚠️ null —— 取不出来了！
    }
}
```

运行结果：

```text
true
null
```

**原理**：

- `put(k1, ...)` 时：用 `k1.hashCode()`（**默认实现按内存地址算**，`k1`、`k2` 地址不同 → 哈希不同）定位桶，`k1` 进了桶 A；
- `get(k2)` 时：用 `k2.hashCode()` 定位桶 → 哈希不同 → 定位到桶 B；
- 桶 B 里没有 `k2`（`k2` 根本没进去过）→ **返回 `null`**。

⭐ **一句话**：`equals` 决定「是不是同一个」，`hashCode` 决定「放哪个桶、查哪个桶」。**两者必须一致**，否则 `HashMap` 认为「它们相等却不在同一个桶里」，就会出现「放得进去、取不出来」的诡异现象。

⚠️ **注意**：JDK 的 `String`、`Integer` 这些内置类都**同时**正确重写了两个方法，所以用它们当 key 永远没问题。**出问题的永远是自定义类**。

### 正确写法

```java
import java.util.*;

public class GoodKeyDemo {
    static class GoodKey {
        private final String id;
        private final int version;

        GoodKey(String id, int version) {
            this.id = id;
            this.version = version;
        }

        @Override
        public boolean equals(Object o) {
            if (this == o) return true;
            if (!(o instanceof GoodKey)) return false;
            GoodKey other = (GoodKey) o;
            return version == other.version && id.equals(other.id);
        }

        @Override
        public int hashCode() {
            // 用与 equals 一致的字段，用 Objects.hash 自动组合
            return Objects.hash(id, version);
        }
    }

    public static void main(String[] args) {
        Map<GoodKey, String> map = new HashMap<>();
        map.put(new GoodKey("A", 1), "value");
        System.out.println(map.get(new GoodKey("A", 1)));   // ✅ "value"
    }
}
```

⭐ **铁律：`hashCode` 用的字段必须是 `equals` 用到的字段的子集。** 最简单的做法是：**两个方法用完全相同的一组字段**。

> `Objects.hash(a, b)` 是 JDK 提供的工具方法，自动把多个字段的哈希值组合起来。

### ⚠️ 用可变对象当 key 的后果

**对象放进 `HashMap` 之后，它的哈希值就不能再变**。因为 `HashMap` 是靠「按下标找桶」来定位元素的，而下标是**当初放进去时算出来的**——如果 key 的 `hashCode()` 变了（因为它的字段变了），`get` 时算出的下标就变了，**自然找不到**。

```java
class MutableKey {
    int code;
    MutableKey(int code) { this.code = code; }
    @Override public int hashCode() { return code; }
    @Override public boolean equals(Object o) {
        return o instanceof MutableKey && ((MutableKey) o).code == code;
    }
}

Map<MutableKey, String> map = new HashMap<>();
MutableKey k = new MutableKey(1);
map.put(k, "v");
k.code = 2;                  // ⚠️ key 被改了
System.out.println(map.get(k));   // null —— 找不到
```

💡 **实践建议**：**对象作为 `HashMap` 的 key 时，用不可变对象**——字段声明为 `final`，构造后不再修改。用 `String`、`Integer`、或者你自定义的 `final` 字段类。

## 六、线程安全

⚠️ **`HashMap` 不是线程安全的**。多线程同时 `put` 可能导致数据丢失、链表成环（Java 7 及更早版本会死循环）、或者读到不一致的中间状态。

**并发场景请用 `ConcurrentHashMap`**——它同样基于哈希表，但把锁粒度降到了「单个桶」，读操作几乎无锁（Java 8+ 用 `CAS` + `synchronized` 锁单个桶首节点，而不是像 `HashMap` 那样完全无保护）。

> `ConcurrentHashMap` 的完整机制（分段锁演进、CAS 插入、计数辅助类等）属于并发专题，见 [[java/02-中段阶段-专题精讲/并发编程/05-并发容器与虚拟线程]]。

⚠️ **但 `HashMap` 上的 `computeIfAbsent`/`merge` 等方法在 `HashMap` 上并不原子**——它们只有在 `ConcurrentHashMap` 上才具备 4.3 讲的原子性。

## 七、⭐ 面试追问预埋

### 追问 1：为什么容量总是 2 的幂？

三个理由，答全才算完整：

1. **位运算代替取模**：`(n-1) & hash` 等价于 `hash % n`，但快得多——前提是 `n` 是 2 的幂；
2. **扩容时定位简单**：容量翻倍后，新下标只可能是「原下标」或「原下标 + 旧容量」，一次判断即可，不需要重算 hash（见第四节）；
3. **哈希分布更均匀**：2 的幂配合扰动函数，能把 hash 的低位充分用满。

### 追问 2：为什么红黑树阈值是 8？

1. **性能考虑**：链表查找是 O(n)，红黑树是 O(log n)。链表长到 8 时，O(n) 已经明显变慢，转树能救回来；
2. **概率考虑**：正常情况下哈希冲突的分布是**泊松分布**——链表达到 8 个元素的概率极低（正常键值下几乎不可能出现）。所以一旦出现 8 连，说明要么数据量极大，要么遇到了**哈希碰撞攻击**（恶意构造大量同哈希值的 key）；
3. **空间考虑**：红黑树节点比链表节点多存两个指针（左右子节点引用），内存开销约为链表节点的 2–3 倍。链表只有 7、8 个元素时，这点开销换来的性能提升不划算。

### 追问 3：为什么先扩容再树化（64 这个门槛）？

因为**链表长多半是桶少造成的，不是哈希分布差造成的**。容量 < 64 时扩容（桶翻倍）就能把链表拆散，冲突自然缓解，比转红黑树更省内存。**只有容量 ≥ 64 仍然长到 8，才说明确实需要树来救**。

### 追问 4：`HashMap` 的 `get` 是 O(1) 吗？

**平均是，最坏不是**。最坏情况（所有 key 撞进同一个桶、且不树化）是 O(n)；树化后最坏是 O(log n)。所以准确表述是「**平均 O(1)，最坏 O(n)（树化后 O(log n)）**」。

### 追问 5：`ConcurrentHashMap` 和 `HashMap` 的区别？

| 维度 | `HashMap` | `ConcurrentHashMap` |
|------|-----------|-------------------|
| 线程安全 | ❌ | ✅ |
| 底层结构 | 数组 + 链表 + 红黑树 | 数组 + 链表 + 红黑树（结构类似） |
| 加锁方式 | 无 | Java 8+：`CAS` + `synchronized` 锁**单个桶**首节点 |
| 读操作 | 无保护 | 几乎无锁 |
| 允许 `null` | ✅ | ❌ **key 和 value 都不允许** |
| 迭代器 | fail-fast | **弱一致（weakly consistent）**，不抛 `ConcurrentModificationException` |

⚠️ **`ConcurrentHashMap` 不允许 `null` 键值**，原因是并发下「`null` 到底表示'不存在'还是'值就是 null'」无法区分，会造成歧义。

## 八、手工验证：把原理跑出来

### 1. 打印数组容量与扩容时机

```java
import java.util.*;
import java.lang.reflect.Field;

public class HashMapInternals {
    // 反射读取 HashMap 内部的 table 字段
    static Object[] tableOf(Map<?, ?> map) throws Exception {
        Field f = HashMap.class.getDeclaredField("table");
        f.setAccessible(true);
        return (Object[]) f.get(map);
    }

    public static void main(String[] args) throws Exception {
        Map<Integer, Integer> map = new HashMap<>();
        for (int i = 0; i < 20; i++) {
            map.put(i, i);
            Object[] table = tableOf(map);
            System.out.printf("size=%2d  table.length=%2d  阈值=%d%n",
                    map.size(), table.length, (int)(table.length * 0.75));
        }
    }
}
```

预期输出（关键行，实测 JDK 17）：

```text
size= 1  table.length=16   阈值=12
size=12  table.length=16   阈值=12
size=13  table.length=32   阈值=24     ← ⭐ 扩容了：16 → 32（2 倍）
size=20  table.length=32   阈值=24
```

⭐ **这段代码验证了三件事**：① 第一次 `put` 后容量就是 **16**（`new HashMap<>()` 本身是空表，第一次 `put` 才分配 16）；② 阈值 = 容量 × 0.75（16 × 0.75 = 12，32 × 0.75 = 24）；③ **扩容是 2 倍**（16 → 32）。

> ⚠️ `f.setAccessible(true)` 在 JDK 9+ 的模块系统下**默认被拒绝**——直接运行会抛 `InaccessibleObjectException`（实测 JDK 17 就是如此）。必须给运行命令加上：
> ```bash
> java --add-opens java.base/java.util=ALL-UNNAMED HashMapInternals
> ```

### 2. 制造哈希冲突，看桶内结构

```java
import java.util.*;

public class CollisionDemo {
    // 所有实例的 hashCode 相同 —— 制造极端冲突
    static class SameHash {
        final String name;
        SameHash(String name) { this.name = name; }
        @Override public int hashCode() { return 42; }        // 全部一样
        @Override public boolean equals(Object o) {
            return o instanceof SameHash && name.equals(((SameHash) o).name);
        }
    }

    public static void main(String[] args) {
        Map<SameHash, String> map = new HashMap<>();
        for (int i = 0; i < 20; i++) {
            map.put(new SameHash("k" + i), "v" + i);
        }
        // 20 个 key 全部 hashCode=42 → 全在同一个桶
        System.out.println("size = " + map.size());          // 20，元素都在
        System.out.println("取值正常吗？ " +
                map.get(new SameHash("k7")));                  // v7 —— 功能没坏
    }
}
```

### 3. 复现「放得进去取不出来」

```java
import java.util.*;

public class EqualsHashCodeDemo {
    static class User {
        final String name;
        User(String name) { this.name = name; }
        @Override public boolean equals(Object o) {
            return o instanceof User && name.equals(((User) o).name);
        }
        // ⚠️ 故意不重写 hashCode
    }

    public static void main(String[] args) {
        Map<User, Integer> map = new HashMap<>();
        User u1 = new User("张三");
        User u2 = new User("张三");

        System.out.println("equals 结果：" + u1.equals(u2));   // true
        map.put(u1, 1);
        System.out.println("取出结果：" + map.get(u2));          // null ⚠️ 取不到！
        System.out.println("hashCode 是否相等：" + (u1.hashCode() == u2.hashCode()));  // false
    }
}
```

⭐ 修掉它只需要补上：

```java
@Override public int hashCode() { return name.hashCode(); }
```

## 陷阱

1. **⚠️ 以为 `size()` 是数组容量**——`size()` 是有效元素个数；容量是内部字段（用反射才看得到），内存占用看容量；
2. **⚠️ 用自定义对象当 key 却只重写 `equals`**——放得进去取不出来，**必须同时重写 `hashCode`**；
3. **⚠️ `hashCode` 用了 `equals` 没用到的字段**——违反契约，同样会导致查找失败；
4. **⚠️ 用可变对象当 key**——key 的哈希值变了就再也找不回来；用**不可变对象**（`final` 字段）；
5. **⚠️ 以为 `HashMap` 是线程安全的**——多线程请用 `ConcurrentHashMap`；
6. **⚠️ 以为 `get` 一定是 O(1)**——平均是，最坏 O(n)（树化后 O(log n)）；
7. **⚠️ 以为 `ConcurrentHashMap` 允许 `null`**——它的 key 和 value 都不允许 `null`；
8. **⚠️ 以为 `HashMap` 扩容是 1.5 倍**——`HashMap` 是 **2 倍**，`ArrayList` 才是 1.5 倍；
9. **⚠️ 遍历 `HashMap` 时修改它**——触发 fail-fast，抛 `ConcurrentModificationException`（见 4.2）。

## 小结

- 结构：**数组 `table` + 桶（bucket）+ 桶内链表**，Java 8+ 链表长会转**红黑树**（平衡二叉搜索树，保证 O(log n) 查询）
- ⭐ **扰动函数** `(h = key.hashCode()) ^ (h >>> 16)`：把高 16 位混入低位，避免「高位不同低位相同」的 key 全部撞桶
- ⭐ **put 五步**：算 hash → 定位桶 → 桶空直接放 → 桶内有元素则比 hash 再比 `equals`（相同覆盖 value）→ 不同则挂链表尾部
- **树化门槛**：链表 ≥ 8 **且** 容量 ≥ 64；容量 < 64 时**先扩容**；树缩到 ≤ 6 退化回链表
- ⭐ **负载因子 0.75**：`size > 容量 × 0.75` 触发扩容，**扩容为 2 倍**；扩容后新下标 = 原下标 或 原下标 + 旧容量，**无需重算 hash**
- ⭐ **`equals`/`hashCode` 契约**：相等 ⟹ 哈希码相等；只重写 `equals` 会导致「放得进去取不出来」；key 必须不可变
- 面试三答：容量 2 的幂（位运算取模 + 扩容定位 + 分布均匀）；阈值 8（性能 + 低概率 + 内存开销）；先扩容再树化（桶少导致链表长）
