> **什么时候该读**：你发现「很多类有同样的方法，但每个类实现不一样」，想知道该抽一个父类还是抽一个接口；或者看到别人的代码里 `implements` 后面跟了一串接口、`default` 方法、`sealed` 关键字，不明白它们在解决什么问题。

## 一、抽象类：只定形状，不给实现

### 什么是抽象类

**抽象类**（abstract class）是**不能被实例化**（不能 `new`）的类。它存在的唯一目的是：**给子类规定「必须实现什么」**。

```java
// Shape.java —— 抽象类
public abstract class Shape {
    // 抽象方法：只有签名，没有方法体（没有大括号{})
    public abstract double area();

    // 普通方法：抽象类也可以有具体实现
    public void printInfo() {
        System.out.println("面积：" + area());
    }
}
```

```java
// Circle.java
public class Circle extends Shape {
    private final double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

### 抽象类的三条规则

| 规则 | 说明 |
|------|------|
| **不能实例化** | `new Shape()` 编译报错：抽象类不能被实例化 |
| **抽象方法没有方法体** | `public abstract double area();` —— 结尾**直接是分号**，不能有 `{ }` |
| **抽象方法必须被子类实现** | 除非子类本身也是抽象类 |

⚠️ **抽象类可以有构造器**——构造器用来初始化子类的公共状态，子类构造器会通过 `super()` 调用它。

⚠️ **抽象类里的抽象方法不能是 `private`**（private 方法不可见，子类无法实现）；**可以是 `static`**（但静态抽象方法没有意义——静态方法不参与多态，Java 也不允许 `abstract static` 组合）；**可以是 `final`**？——❌ 不行，`abstract` 和 `final` 语义冲突（一个要求实现，一个禁止重写），Java 编译报错。

### 抽象方法 vs 抽象类

| | 抽象方法 | 抽象类 |
|---|---------|--------|
| 写法 | `abstract void run();` | `abstract class Shape { }` |
| 必须在抽象类里吗 | ✅ 是 | —— |
| 能不能有方法体 | ❌ 绝对不能 | 类里的普通方法可以有 |
| 能不能被 `static` 修饰 | ❌ | ✅ |

## 二、接口（interface）：一份「能力契约」

**接口**（interface）是 Java 8 之后被彻底重新定义的东西。入门阶段先记住最核心的一点：

> **接口 = 一组「要做什么」的约定 + 一组「常量」。**

### 基本写法

```java
// Flyable.java —— 用 interface 声明接口
public interface Flyable {
    // 方法：隐式 public abstract
    void fly();

    // 字段：隐式 public static final
    int MAX_SPEED = 1000;
}
```

```java
// Bird.java —— 用 implements 实现接口
public class Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("扑棱棱棱");
    }
}
```

### 三个「隐式」

编译器会自动补上你不用写的东西：

| 你写的 | 编译器理解成 | 全称 |
|--------|------------|------|
| `void fly();`（在接口里） | `public abstract void fly();` | 抽象方法 |
| `int MAX_SPEED = 1000;`（在接口里） | `public static final int MAX_SPEED = 1000;` | 常量 |
| `void fly();`（在实现类里省略 `public`） | `public void fly()` | 实现方法必须是 `public` |

⭐ **为什么接口字段一定是常量？** 因为接口里的字段被**所有实现类共享**，如果允许修改，任何一个类改了都会影响所有人，「契约」就失效了。所以编译器强制 `static final`。

⚠️ **实现接口方法时不能缩小可见性**：接口方法隐式 `public`，你在实现类里写成 `void fly()`（默认权限）会编译报错，**必须写 `public`**。

### 一个类可以实现多个接口

这是接口相比抽象类最大的优势——**Java 的类只能继承一个父类，但可以实现任意多个接口**。

```java
import java.io.Serializable;      // Serializable 是 JDK 自带接口（可序列化标记接口）

public class Bird implements Flyable, Comparable<Bird>, Serializable {
    @Override
    public void fly() { }

    @Override
    public int compareTo(Bird o) { return 0; }
}
```

⚠️ `Comparable` 和 `Serializable` 是 JDK 自带的接口，完整 API 见 [[java/术语与关键字手册]]。

## 三、⭐ 抽象类 vs 接口对照表（核心）

| 维度 | 抽象类 `abstract class` | 接口 `interface` |
|------|------------------------|-----------------|
| **能否实例化** | ❌ 不能 `new` | ❌ 不能 `new` |
| **能否有字段** | ✅ 能，且可非 final、可有初始值 | ✅ 能，但**隐式 `public static final`**（只能是常量） |
| **能否有构造器** | ✅ 能（子类用 `super()` 调它） | ❌ **接口没有构造器** |
| **能否有实例状态** | ✅ 能——每个对象各存一份 | ❌ 不能——接口只能存**静态共享**的常量 |
| **方法默认可见性** | 自己定：`public` / `protected` / 默认 / `private` | 抽象方法隐式 `public`；Java 9+ 可有 `private` 方法 |
| **能否有具体实现的方法** | ✅ 能（普通方法） | ✅ 能——`default` 方法（Java 8+）、`static` 方法（Java 8+）、`private` 方法（Java 9+） |
| **能否被继承** | ✅ 子类 `extends` 抽象类 | ✅ 子类 `implements` 接口 |
| **多继承** | ❌ 一个类只能继承**一个**抽象类 | ✅ 一个类可以实现**多个**接口 |
| **耦合度** | 较高——子类必须依赖父类的实现细节 | 低——子类只需满足「做什么」，不管「怎么做」 |
| **典型场景** | 多个子类**共享一套实现**（模板） | 多个互不相关的类**共享一种能力**（能力标签） |

⭐ **一句话区分**：

> **抽象类用来「复用实现 + 规定模板」，接口用来「规定能力 + 允许多种实现」。**

### 一个能体现本质的对比

```java
// 抽象类：子类共享「实现」
public abstract class Vehicle {
    protected int wheels = 4;         // 实例状态：每个对象一份

    public abstract void start();     // 抽象方法

    public void honk() {              // 具体实现：子类直接继承
        System.out.println("哔——");
    }
}
```

```java
// 接口：只规定「能力」，没有共享实现
public interface Movable {
    void move();                      // 只有能力，没有实现、没有状态
}
```

⚠️ 常见错误：**把接口当抽象类用**。接口里不能放实例字段、不能有构造器，所以「接口 = 抽象类的轻量版」是错的，它们解决的是不同问题。

## 四、接口的 `default` 方法与钻石问题

### 为什么需要 `default` 方法（Java 8+）

**历史困境**：Java 8 之前，接口里**只能有抽象方法**。这带来一个致命问题——

> 你发布了接口 `List`，几年后想给它加一个 `stream()` 方法。**所有实现类都编译不过了**，因为它们都没实现新方法。

Java 8 引入 **`default` 方法**（默认方法）：接口方法**可以有默认实现**。实现类可以选择不重写，直接用接口给的实现。

```java
// Java 8+
public interface Greetable {
    String name();

    // default 方法：带方法体，实现类不重写也能用
    default String greet() {
        return "你好，我是" + name();
    }

    // 静态接口方法：属于接口自己，用接口名调用
    static Greetable of(String name) {
        return () -> name;            // Lambda，见 2.4
    }
}
```

```java
public class Chinese implements Greetable {
    @Override
    public String name() {
        return "张三";
    }
    // 没有重写 greet()，直接用接口的默认实现
}
```

⚠️ **规则**：
- `default` 方法**不是** `abstract`，**不能**加 `abstract` 修饰；
- `default` 方法**不能**是 `static` 的同时……——实际上 `default` 与 `static` 是**两种不同的方法类型**，一个接口里可以同时有 `default` 方法和 `static` 方法，但**不能**同时有 `abstract` 和 `default` 修饰同一个方法；
- **实现类可以重写 `default` 方法**，也可以选择不重写。

### 接口的 `private` 方法（Java 9+）

Java 9 起，接口可以有 **private 方法**（以及 `private static`），用来给多个 `default` 方法**提取公共实现**，避免重复代码。

```java
public interface Validator {
    // private 方法：接口外部完全看不见
    private boolean isBlank(String s) {
        return s == null || s.isBlank();
    }

    private static String normalize(String s) {
        return s == null ? "" : s.trim();
    }

    default boolean validate(String input) {
        return !isBlank(normalize(input));
    }
}
```

⚠️ Java 8 及以前**没有**接口私有方法——这就是为什么当时的接口 `default` 方法要么各自重复代码，要么只能调用 `public static` 工具方法。

### ⭐ 钻石问题与冲突解决规则

当一个类继承了/实现了**多个**来源的**同名 `default` 方法**时，就产生了「**钻石问题**」（diamond problem）——像继承链上的一个菱形结构。

```
        interface A { default void hi() { print("A"); } }
        interface B { default void hi() { print("B"); } }
                     ↓ implements        ↓ implements
                   class C implements A, B { }   // 冲突！
```

Java 给了三条规则来裁决：

| 规则 | 说明 | 例子 |
|------|------|------|
| **① 类优先（class wins）** | 如果类自己重写了这个 `default` 方法，**类里的赢**，接口的一个都不算 | `class C implements A, B { @Override public void hi() { ... } }` → 用 C 的 |
| **② 父接口优先（superinterface wins）** | 如果一个接口**继承**自另一个接口（不是直接两个并列），**更具体的那个赢** | `interface D extends A`、`class C implements A, D` → 用 D 的 |
| **③ 编译报错，必须显式覆盖** | 前两条都没法裁决时，**编译直接失败**，你必须在自己的类里写一个 `hi()` 明确选一个 | `class C implements A, B { }` 且不重写 → 编译错误 |

```java
// A.java
public interface A {
    default void hi() { System.out.println("A"); }
}

// B.java
public interface B {
    default void hi() { System.out.println("B"); }
}
```

```java
// Conflict.java —— 规则③：不重写就编译不过
public class Conflict implements A, B {
    @Override
    public void hi() {
        A.super.hi();   // ⭐ 显式指定「调 A 的」
        // B.super.hi(); // 也可以，两个都调
    }
}
```

⭐ `A.super.hi()` 这种写法叫**「限定超类调用」**（qualified super invocation），**只对接口的 `default` 方法有效**，是解决冲突的标准手段。

⚠️ 注意规则 ③ 是**编译期错误**，不是运行期——编译器会直接告诉你「类 C 继承了 A 和 B 中类型不一致的默认方法」，不给你「二选一」的默认行为。

## 五、接口的演进史：为什么走到今天

```
Java 7 及以前                 Java 8                     Java 9                Java 17 / 21
─────────────────────  ────────────────────────  ──────────────────  ─────────────────────
接口只能有抽象方法       →  + default 方法          →  + private 方法      →  + sealed 密封接口
接口字段全是常量           + static 方法               + 允许多个实现类继承     + 模式匹配 switch 穷尽检查
                            ↑ 解决「加方法破坏兼容」     ↑ 抽取 default 公共代码   ↑ 表达「有限且已知的实现集合」
```

⭐ **演进的驱动力只有一个：向后兼容。**

Java 有极强的向后兼容承诺：**已发布的 API 不能破坏任何已发布的实现类**。`default` 方法正是为此而生——它让接口能新增方法而不要求所有实现类立刻修改。

这个思路影响深远：**Java 8 之后，「接口」不再是纯粹的抽象契约，而成了「带默认实现的契约 + 能力集合」**。

## 六、`sealed` 密封类/接口（Java 17+）

### 问题背景

很多场景下，「一个父类**只允许**某几个子类」是明确的设计意图（比如支付方式只有这三种、状态机只有这几个状态）。但 Java 原本**没有**这个表达能力——任何人都能 `extends` 你的类，破坏你的假设。

**密封类**（sealed class）/ **密封接口**（sealed interface）就是为此设计的（Java 17 正式引入）。

### 写法：`sealed` + `permits`

```java
// SealedResult.java —— 密封接口
public sealed interface SealedResult
        permits Success, Failure {       // permits 列出「允许谁实现我」
}
```

```java
// Success.java
public final class Success implements SealedResult {   // final：到此为止，不再被继承
    private final String data;
    public Success(String data) { this.data = data; }
    public String data() { return data; }
}
```

```java
// Failure.java
public final class Failure implements SealedResult {
    private final String error;
    public Failure(String error) { this.error = error; }
    public String error() { return error; }
}
```

三个关键字的含义：

| 关键字 | 作用 |
|--------|------|
| `sealed` | 「我是一个密封的父类/接口，只有 `permits` 里列出的类型能继承我」 |
| `permits` | 列出允许的子类（**必须列出**，除非子类就在同一个文件里） |
| `final`（子类上） | 「继承到此为止」，保证密封链是**封闭的** |
| `non-sealed`（子类上） | 「我不封闭，允许别人继续继承我」——密封链上可以留一个口子 |

⚠️ **一个密封父类的子类必须三者择一**：标 `final`（封闭）、标 `non-sealed`（放开）、或者本身也是 `sealed`（继续密封下去）。

### ⭐ 与模式匹配 `switch`（Java 21+）配合：穷尽性检查

**穷尽性**（exhaustiveness）指「所有可能的情况都被覆盖了，一个都不漏」。

Java 21 之前，`switch` 需要 `default` 分支兜底，写漏了编译器不管：

Java 21 之前，`switch` 还不认识「类型模式」，只能老老实实一串 `if`：

```java
// Java 16+ 的 instanceof 模式匹配
public static String handle(SealedResult result) {
    if (result instanceof Success s) {
        return s.data();
    }
    if (result instanceof Failure f) {
        return f.error();
    }
    return "未知";      // ⚠️ 必须写兜底——编译器无法替你检查「有没有漏」
}
```

Java 21 起，`switch` 支持**模式匹配**，并且**对密封类型做穷尽性检查**：

```java
// Java 21+
public static String handle(SealedResult result) {
    return switch (result) {
        case Success s -> s.data();     // 模式匹配 + switch 表达式
        case Failure f -> f.error();
        // ⭐ 不需要 default！因为 SealedResult 是密封的，
        //    编译器知道只有这两种情况，全覆盖了
    };
}
```

⭐ **这就是 `sealed` 最大的价值**：把「这个类型只可能有这几种情况」这个**设计意图写进了代码**，编译器帮你检查有没有漏分支。

⚠️ **穷尽性检查的适用范围**：Java 21 的 `switch` **语句和表达式都要求穷尽**（对密封类型而言，漏一个 case 就编译报错 "the switch statement does not cover all possible input values"）。

⚠️ 但**传统的老式 `switch`（对 `int`、`String`、枚举做值匹配）不要求穷尽**——漏了 case 就走不到任何分支，静默跳过。所以「switch 会替你检查漏分支」这句话，**只在模式匹配 + 密封类型这个组合下成立**。

⚠️ **版本提醒**：`sealed` 是 **Java 17+**，模式匹配 `switch`（正式的、作为语句/表达式的 switch 模式）是 **Java 21+**。Java 17/19 里只有「预览特性」，需要 `--enable-preview` 编译。

## 七、设计视角：面向接口编程与依赖倒置

### 「面向接口编程」是什么意思

一句话：**写代码时依赖「能力」，而不是依赖「具体实现」**。

```java
// ❌ 依赖具体实现：换实现就要改代码
public class BadOrderService {
    private MySQLOrderRepository repo = new MySQLOrderRepository();
}
```

```java
// ✅ 依赖抽象：换实现只改一行（构造注入）
public class OrderService {
    private final OrderRepository repo;      // 字段类型是接口，不是实现

    public OrderService(OrderRepository repo) {
        this.repo = repo;      // 谁传进来就用谁
    }
}
```

对比效果：

```
   依赖具体类（旧）                    依赖接口（新）
┌──────────────────┐            ┌──────────────────┐
│   OrderService   │──直接 new──▶│ MySQLRepo        │
│  （写死了）      │            └──────────────────┘
└──────────────────┘                   ▲ 注入
                                       │
┌──────────────────┐            ┌──────────────────┐
│   OrderService   │◀──注入────│  OrderRepository  │ ← 接口
└──────────────────┘            │   （抽象）        │
                               └──────────────────┘
                                       ▲ 实现
                               ┌──────────────────┐
                               │ FakeOrderRepo     │ ← 测试用假实现
                               └──────────────────┘
```

⭐ **这就是「依赖倒置原则」**（Dependency Inversion Principle，属于 SOLID 里的 D）：**高层模块（业务）不应该依赖低层模块（存储细节），两者都应该依赖抽象（接口）**。接口由「谁在用它」的一方定义——所以接口放在业务侧。

⚠️ **别过度设计**：只有一个实现、又不会替换的简单场景，直接用具体类更清晰。接口不是为了「显得高级」，而是为了「**真的存在替换/扩展/测试隔离的需求**」。

## 陷阱

1. **⚠️ 以为接口的字段能修改**——接口字段隐式 `public static final`，**编译期就是常量**，任何赋值都编译报错；
2. **⚠️ 实现接口方法时省略 `public`**——接口方法隐式 `public`，实现时**必须**写 `public`，否则「试图降低可见性」编译报错；
3. **⚠️ 把接口当抽象类用**——接口**没有构造器**、**不能有实例字段**、实现类之间**不共享实现**（除了 `default`）；
4. **⚠️ 抽象方法写成了有方法体**——`public abstract void area() { }` 编译报错，抽象方法**只能有分号**；
5. **⚠️ 以为 `abstract` 和 `final` 能同时用**——语义冲突（要求实现 vs 禁止重写），编译报错；
6. **⚠️ 遇到钻石问题不加 `@Override` 就想蒙混过关**——规则 ③ 是**编译期错误**，必须在自己的类里显式覆盖，并用 `A.super.hi()` 指定调用哪个；
7. **⚠️ 以为 `default` 方法不能被重写**——实现类**可以**重写 `default` 方法；
8. **⚠️ 用 `sealed` 却忘了子类必须标 `final` / `non-sealed` / `sealed`**——三选一，否则编译报错；
9. **⚠️ 在 Java 21 以下的正式代码里用模式匹配 `switch`**——那是 Java 21+ 的正式特性；Java 17/19 只是预览；
10. **⚠️ 无脑给每个类都套接口**——接口的价值在于「真的存在替换需求」，否则是过度设计。

## 小结

- **抽象类**：不能实例化；可以有实例字段和构造器；有抽象方法（无方法体）+ 具体方法
- **接口**：不能实例化、无构造器、字段只能是 `public static final` 常量、抽象方法隐式 `public`
- ⭐ **本质区别**：抽象类能存**实例状态**（每个对象一份），接口不能
- 一个类只能继承**一个**抽象类，但可以实现**多个**接口
- **`default` 方法**（Java 8+）解决「给已发布接口加方法会破坏实现类」的兼容问题；**`private` 接口方法**（Java 9+）提取公共实现
- ⭐ **钻石问题三规则**：类优先 → 父接口优先 → 编译报错必须显式覆盖（`A.super.hi()`）
- **`sealed` + `permits`**（Java 17+）表达「有限的实现集合」；配合模式匹配 `switch`（Java 21+）做穷尽性检查，不用写 `default`
- **面向接口编程 = 依赖抽象而非实现**，这正是依赖倒置原则的直观形态

## 练习

1. 设计一个 `Shape` 抽象类（抽象方法 `area()`）和 `Comparable` 的组合，让 `Circle`、`Rectangle` 能按面积排序；写出你会放在抽象类里还是接口里的东西，并说明理由。
2. 写一个 `Flyable` 接口（含抽象方法 `fly()` 和一个 `default` 方法 `land()`），让 `Bird` 和 `Plane` 分别实现并各自覆盖 `land()`。
3. 构造钻石问题：`interface A { default void hi() {...} }`、`interface B { default void hi() {...} }`，然后写 `class C implements A, B`——先看编译错误，再用 `A.super.hi()` 解决。
4. 把「接口只能有抽象方法」的历史讲清楚：为什么 Java 8 之前接口加方法是「破坏性变更」？`default` 方法怎么解决的？
5. 用 `sealed interface Result permits Success, Failure` 建模一个「解析结果」，再用 Java 21 的模式匹配 `switch` 写一个处理函数，故意漏掉一个分支，观察编译器的报错。
6. 找出下面代码的三处问题并改正：
   ```java
   public interface Config {
       int VERSION = 1;
       void load();
   }
   public class FileConfig implements Config {
       void load() { System.out.println("loaded"); }
   }
   ```
7. 说出一个你最近写的类，说明「依赖具体实现」改成「依赖接口」之后，测试会变得多容易。
