## 一、异常是什么：为什么不能只用返回值

**异常（Exception）**指的是程序运行期间发生的、打断了正常执行流程的异常事件。

在没有异常机制的语言里，函数出错的常见做法是「返回一个魔法值」表示失败：

```java
// ❌ 方案 A：用魔法返回值表示失败
static int parseAge(String s) {
    if (s == null || s.isEmpty()) return -1;   // -1 是什么含义？只有作者知道
    try {
        return Integer.parseInt(s);
    } catch (NumberFormatException e) {
        return -1;                               // 调用方无法区分「空输入」和「格式错」
    }
}
```

这个方案有四个硬伤：

1. **返回值被污染** —— 函数本来该返回「年龄」，现在不得不兼职返回「错误码」，类型系统表达不了「要么年龄要么错误」。
2. **每个调用方都要记得检查** —— 漏掉一次 `if (age == -1)` 就是线上 bug。
3. **错误信息在跳转中丢失** —— 一旦转成 `-1`，「原始输入是 `"abc"`」这条线索彻底消失。
4. **层层调用要层层检查** —— 调用链有 10 层，就要写 10 次检查，且每层都可能忘。

Java 的解法是把「错误」从**数据流**移到**控制流**上：

```java
// ✅ 方案 B：正常路径只返回正常值，异常路径用 throw 单独表达
static int parseAgeViaException(String s) {
    if (s == null || s.isEmpty()) {
        throw new IllegalArgumentException("年龄不能为空");   // throw：主动抛出一个异常实例
    }
    return Integer.parseInt(s);   // 格式错会抛 NumberFormatException（它是 IllegalArgumentException 的子类）
}
```

> 首次出现的语法：`try { ... } catch (异常类型 e) { ... }` —— `try` 块里放可能出错的代码，一旦出错就跳到能匹配上的 `catch` 块处理。`catch` 后面圆括号里是异常类型，`e` 是装异常的变量，可以调 `e.getMessage()`（取一段人类可读的描述）和 `e.printStackTrace()`（把完整调用栈打印到控制台）。多个 `catch` 块、`finally` 块、精确的匹配规则都在下一篇 [[java/01-入门阶段-基础教程/第03章-异常处理/3.2-捕获处理与自定义异常]] 里讲，本篇只需要知道「有个 try 块套着一个 catch 块」。

⭐ **一句话总结设计意图**：返回值负责「成功时的数据」，异常负责「失败时的原因和补救信息」，两者互不污染。

## 二、⭐ Throwable 继承树

Java 里所有异常和错误的**根**是 `java.lang.Throwable`（继承自 `Object`）。它分出两大支：

```text
java.lang.Throwable  ── 所有异常与错误的根类
│
├── java.lang.Error ──────────── 严重问题，程序通常不处理（连 catch 都不该 catch）
│   ├── VirtualMachineError ──── 虚拟机层的严重错误
│   │   ├── OutOfMemoryError ────── 内存不足（堆 / 元空间 / 直接内存耗尽）
│   │   └── StackOverflowError ──── 栈溢出（递归太深，方法调用层数超限）
│   ├── LinkageError ─────────── 链接期错误：类找不到、类格式不对、初始化失败
│   │   ├── ClassFormatError
│   │   ├── NoClassDefFoundError
│   │   └── ExceptionInInitializerError
│   └── AssertionError ───────── assert 断言失败
│
└── java.lang.Exception ───────── 程序层面「预期之内、可处理」的错误
    │
    ├── java.lang.RuntimeException ── 非受检异常（unchecked）：都是编程错误
    │   ├── NullPointerException ───── 对 null 引用调用方法 / 访问字段
    │   ├── IllegalArgumentException ─ 参数不合法（非法参数值）
    │   │   └── NumberFormatException ── 数字格式错（它是 IllegalArgumentException 的子类）
    │   ├── IllegalStateException ──── 对象当前状态不允许做这件事
    │   ├── ArithmeticException ────── 算术错误（整数除以 0）
    │   ├── ClassCastException ─────── 强制类型转换失败
    │   ├── ConcurrentModificationException ─ 遍历集合时同时修改它
    │   ├── IndexOutOfBoundsException ─ 下标越界
    │   │   ├── ArrayIndexOutOfBoundsException
    │   │   └── StringIndexOutOfBoundsException
    │   └── UnsupportedOperationException ─ 对不可修改的操作（如 add 一个不可变集合）报错
    │
    └── 其他 Exception 子类 ───────── 受检异常（checked）：外部/环境导致的故障
        ├── IOException ────────────── IO 操作失败
        │   ├── FileNotFoundException ── 文件不存在
        │   └── SocketException ──────── 网络套接字错误
        ├── SQLException ───────────── 数据库操作失败
        ├── ClassNotFoundException ─── 反射加载类时找不到该类
        ├── CloneNotSupportedException ─ 该类不支持克隆
        └── InterruptedException ────── 线程被中断
```

⭐ **三个必须记住的层级事实**：

| 事实 | 说明 |
|------|------|
| `Error` 和 `Exception` 是**兄弟**，不是父子 | 两者都直接继承 `Throwable` |
| `RuntimeException` 是 `Exception` 的**子类** | ⚠️ 它**不是** `Error` 的子类——这是最高频误解，第七节专门拆 |
| 「受检 / 非受检」的切分线在 `RuntimeException` | `RuntimeException` 及其子类 = 非受检；`Exception` 的其他子类 = 受检 |

> `Error` 与 `Exception` 的划分是**语义**的：`Error` 表示「JVM 或系统级的严重问题，你的代码救不回来」；`Exception` 表示「程序可以预见、也可能处理的问题」。

### Throwable 上常用的几个方法

| 方法 | 作用 |
|------|------|
| `getMessage()` | 返回构造异常时传入的描述文字（可能为 `null`） |
| `getCause()` | 返回「原始异常」（cause，异常链的下一环），没有则为 `null` |
| `getStackTrace()` | 返回 `StackTraceElement[]`，即**堆栈轨迹**——异常创建时记录的调用栈快照 |
| `printStackTrace()` | 把类型、消息、堆栈轨迹打印到标准错误流（控制台） |
| `addSuppressed(Throwable)` | 追加「被抑制的异常」（try-with-resources 机制用） |

⭐ **堆栈轨迹（stack trace）**是排查问题的命根子：它记录了异常**被创建的那一刻**的完整调用链，从最内层一直排到最外层。`printStackTrace()` 打出来的就是它。

## 三、Error 与 Exception 的区别

| 维度 | `Error` | `Exception` |
|------|---------|------------|
| 语义 | JVM / 系统级严重问题 | 程序可预期、可处理的错误 |
| 典型 | `OutOfMemoryError`、`StackOverflowError`、`NoClassDefFoundError` | `IOException`、`NullPointerException`、`SQLException` |
| 程序该怎么做 | 基本不处理；通常让进程崩溃并由运维告警 | 要么就地处理，要么声明抛出 |
| 能否写业务代码补救 | 几乎不能 | 通常能 |
| 是受检还是非受检 | **非受检**（编译器不强制） | 两种都有 |

### OutOfMemoryError vs StackOverflowError

这两个最容易混，都属于 `VirtualMachineError`：

| | `OutOfMemoryError`（内存不足） | `StackOverflowError`（栈溢出） |
|---|---|---|
| 耗尽的是什么 | **堆**（对象）、**元空间**（类元数据）、**直接内存** | **虚拟机栈**（方法调用帧） |
| 典型成因 | 内存泄漏、一次加载超大集合/文件、缓存无上限 | 无限递归、递归层数太深、循环里死循环调用自身 |
| 排查方向 | 看堆占用与对象存活（见 [[java/02-中段阶段-专题精讲/JVM/JVM内存区域与对象布局]]） | 看递归终止条件与调用链深度 |
| 能靠加内存解决吗 | 有时能，但泄漏加内存只是推迟崩溃 | ❌ 不能，必须改代码 |

一段可运行的对比代码：

```java
public class ErrorDemo {
    static int depth = 0;

    // ⚠️ 无限递归 → 栈溢出
    static void recurse() {
        depth++;
        recurse();          // 没有终止条件
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("栈溢出，递归深度约 " + depth);
        }
        // OutOfMemoryError 无法在正常内存下安全演示：
        // 真正触发时会耗尽本机内存，通常直接让 JVM 崩溃
    }
}
```

> ⚠️ `StackOverflowError` 出现时 JVM 状态已经很不健康，`catch` 住它通常只能用于「记录现场后立刻退出」，不要试图在它上面继续跑业务逻辑。

## 四、⭐ 受检异常 vs 非受检异常

**受检异常（checked exception）**和**非受检异常（unchecked exception）**是 Java 独有的分类标准，编译器靠它决定放不放行。

### 判定规则

- `Exception` 的子类中，**除了 `RuntimeException` 及其所有子类**，剩下的都是**受检异常**。
- `RuntimeException` 及其所有子类 = **非受检异常**。
- `Error` 及其所有子类 = **非受检异常**（编译器同样不强制你处理）。

### 编译器是否强制

| | 受检异常 | 非受检异常 |
|---|---|---|
| 编译器强制吗 | ⚠️ **强制**。调用一个可能抛受检异常的方法时，必须 `catch` 住，或在自己的方法签名上用 `throws` 声明 | 不强制。想写就 `catch`，不写编译器不管 |
| 典型代表 | `IOException`、`SQLException`、`FileNotFoundException`、`ClassNotFoundException` | `NullPointerException`、`IllegalArgumentException`、`IllegalStateException`、`ArithmeticException`、`ClassCastException`、`IndexOutOfBoundsException` |
| 消息长什么样 | `unhandled exception: java.io.IOException`（编译错误） | 运行时才炸 |
| 设计意图 | **调用方有合理的恢复手段**：文件不存在可以换个路径、数据库超时可以重试、文件没找到可以问用户 | **编程错误**：代码写错了，应该改代码，而不是 catch 掉它 |

### 一个能跑的例子

```java
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class CheckedDemo {
    // ⚠️ 声明 throws：告诉调用者「我可能抛 IOException，你得处理」
    static String readConfig(String path) throws IOException {
        return Files.readString(Path.of(path));   // Java 11+；Files.readString 声明了 throws IOException
    }

    // 非受检异常不需要任何声明
    static int divide(int a, int b) {
        return a / b;      // 除以 0 会抛 ArithmeticException，但编译器不要求你写 throws
    }

    public static void main(String[] args) {
        // ❌ 如果直接写 readConfig("x.txt"); 编译就报错：
        //    unhandled exception: java.io.IOException
        try {
            System.out.println(readConfig("x.txt"));
        } catch (IOException e) {
            System.out.println("读取失败：" + e.getMessage());
        }

        try {
            divide(1, 0);
        } catch (ArithmeticException e) {   // 编译器不要求，但你想处理也可以
            System.out.println("除数不能为 0");
        }
    }
}
```

### 设计意图（这一段是本节的重点）

⚠️ **受检异常表达的是「责任」**：

- 「读文件」这件事，失败的原因是**外部世界**造成的（文件被删了、磁盘满了、权限不足）。调用方可能有恢复手段——换路径、重试、用缓存、问用户。编译器强制你想一下：**我真的处理了吗？**
- 非受检异常表达的是「**你的代码有 bug**」。`NullPointerException` 意味着你少写了一个判空，catch 掉它只会把 bug 藏起来，正确做法是**回去改代码**。

⭐ 这也是为什么 Spring 生态里受检异常很少见：现代 Java 更倾向于「内部用非受检异常一路向上抛，在最外层统一转成 HTTP 响应码」，而不是让 `throws` 签名层层传染。

## 五、常见异常速查表

| 异常名 | 类别 | 触发场景 | 典型处理 |
|--------|------|---------|---------|
| `NullPointerException` | 非受检 | 对 `null` 引用调用方法、取字段、数组长度 | **改代码**：提前判空；或用 `Optional` 表达「可能没有值」 |
| `IllegalArgumentException` | 非受检 | 传入的参数不合法（null、越界、格式错） | **改代码**：在调用前校验参数 |
| `NumberFormatException` | 非受检 | 字符串转数字失败（`"abc"` → `int`） | **改代码**：`Integer.parseInt` 前先校验 |
| `IllegalStateException` | 非受检 | 对象当前状态不允许做这件事（如未初始化就使用） | **改代码**：调用前检查状态 |
| `ArithmeticException` | 非受检 | 整数除以 0 | **改代码**：保证除数非 0 |
| `ClassCastException` | 非受检 | 强制类型转换失败 | **改代码**：先 `instanceof` 判断再转型 |
| `ConcurrentModificationException` | 非受检 | 用增强 for 遍历集合时同时修改集合 | **改代码**：用迭代器的 `remove()`，或改用 `CopyOnWriteArrayList` |
| `IndexOutOfBoundsException` | 非受检 | 下标越界（`ArrayIndexOutOfBoundsException` 是它的子类） | **改代码**：检查边界 |
| `IOException` | 受检 | 读写文件、网络、流操作失败 | 捕获后重试 / 降级 / 转为业务异常抛出 |
| `FileNotFoundException` | 受检 | 文件路径不存在（`IOException` 的子类） | 提示用户、换默认路径或用缓存 |
| `SQLException` | 受检 | SQL 执行失败（唯一键冲突、连接断开） | 捕获后记录并转成业务异常；注意事务回滚 |
| `ClassNotFoundException` | 受检 | 反射 `Class.forName` 加载不到类 | 捕获或修正类路径 |
| `OutOfMemoryError` | Error | 堆 / 元空间 / 直接内存耗尽 | 查泄漏、调大堆、改算法（见第 4 节的 JVM 内存页） |
| `StackOverflowError` | Error | 递归过深 | 改递归为循环或加终止条件 |

⭐ **记忆抓手**：`RuntimeException` 这一支基本都是「你写错了」，`IOException` / `SQLException` 这一支基本都是「环境出问题」。

## 六、异常在方法调用栈中的传播

异常一旦被抛出，会沿着**方法调用栈**（方法 A 调 B 调 C 的那条链）逐层往上走：

```text
main → level1 → level2 → level3
                          ↑ 在这里 throw
```

1. **抛出**：`level3` 执行 `throw new IllegalStateException(...)`。
2. **本层寻找处理器**：`level3` 自己的 `try/catch` 里没有能接住它的 `catch`，于是 `level3` 的栈帧被弹出，异常对象交给调用者 `level2`。
3. **逐层上抛**：`level2` 也没有匹配的 `catch`，继续交给 `level1`；`level1` 也没有，交给 `main`。
4. **找到处理器**：如果某一层有能匹配上的 `catch`，异常就在这一层被**消化**掉，栈不再往上传播，程序从 `catch` 块之后继续执行。
5. **找不到处理器**：异常一路冒到最外层线程（通常是 `main`），此时 JVM 会调用该线程的「未捕获异常处理器」，把堆栈轨迹打印到标准错误流，然后**线程终止**。`main` 线程终止 ⇒ 进程退出，退出码非 0。

```java
public class PropagationDemo {
    static void level3() {
        throw new IllegalStateException("数据库连接失败");   // 起点
    }
    static void level2() { level3(); }   // 没有 catch，异常自动向上抛
    static void level1() { level2(); }

    public static void main(String[] args) {
        try {
            level1();
        } catch (IllegalStateException e) {
            System.out.println("在 main 捕获：" + e.getMessage());
            System.out.println("异常来自第 " + e.getStackTrace().length + " 层调用：");
            for (StackTraceElement el : e.getStackTrace()) {
                System.out.println("   " + el);
            }
        }
    }
}
```

输出（栈轨迹从内到外）：

```text
在 main 捕获：数据库连接失败
异常来自第 4 层调用：
   PropagationDemo.level3(PropagationDemo.java:4)
   PropagationDemo.level2(PropagationDemo.java:6)
   PropagationDemo.level1(PropagationDemo.java:7)
   PropagationDemo.main(PropagationDemo.java:10)
```

⭐ **关键理解**：异常对象的堆栈轨迹是在**创建它的那一刻**就抓取的（`Throwable` 构造时自动调用 `fillInStackTrace()`），所以它记录的是「异常出生在哪里」，而不是「哪里接住了它」。

## 七、⚠️ 高频误解：RuntimeException 属于 Error 吗

**不。`RuntimeException` 是 `Exception` 的子类，与 `Error` 是「堂兄弟」关系，二者毫无继承关系。**

用代码验证：

```java
public class RuntimeIsNotError {
    public static void main(String[] args) {
        // ⚠️ 变量必须声明为 Throwable：若声明成 Exception，编译器会直接拒绝
        //    「npe instanceof Error」（Exception 与 Error 是互不兼容的兄弟类型，不可强转）
        Throwable npe = new NullPointerException("空指针");
        Throwable oom = new OutOfMemoryError("内存溢出");

        System.out.println(npe instanceof RuntimeException);  // true  ← 是 Exception 那一支
        System.out.println(npe instanceof Exception);         // true
        System.out.println(npe instanceof Error);             // false ← 不是 Error
        System.out.println(oom instanceof Error);             // true
        System.out.println(oom instanceof Exception);         // false ← Error 不是 Exception

        // 沿继承链向上打印（NumberFormatException 是链条最长、最好用的例子）
        Class<?> c = NumberFormatException.class;
        while (c != null) {
            System.out.println("   " + c.getName());
            c = c.getSuperclass();
        }
    }
}
```

输出：

```text
true
true
false
true
false
   java.lang.NumberFormatException
   java.lang.IllegalArgumentException
   java.lang.RuntimeException
   java.lang.Exception
   java.lang.Throwable
   java.lang.Object
```

⚠️ 由此推出两个实用结论：

1. **`catch (Exception e)` 抓不到 `Error`**——`OutOfMemoryError`、`StackOverflowError` 都不是 `Exception` 的后代。要连 `Error` 一起抓只能写 `catch (Throwable t)`，但这几乎总是错的（见下面的陷阱）。
2. **「非受检」不等于「属于 Error」**。`RuntimeException` 属于 `Exception` 那一支，只是编译器不管它。判断一个异常是否受检，看的是**它是不是 `RuntimeException` 的后代**，跟 `Error` 无关。

## 八、与 Python 异常的对比

| 维度 | Java | Python |
|------|------|--------|
| 根类 | `Throwable` | `BaseException` |
| 两大分支 | `Error` / `Exception` | `BaseException` 直系子类（`KeyboardInterrupt`、`SystemExit`）/ `Exception` |
| 是否有受检异常 | ⚠️ **有**，编译器强制处理 | ❌ **没有**，全部非受检，写不写 `try` 都能编译过 |
| `finally` 一定执行吗 | 是（除非 JVM 被强杀） | 是（除非解释器退出） |
| 有 `else` 子句吗 | ❌ 没有 | ✅ 有：`try` 块没抛异常时才执行 `else` |
| 声明「我可能抛什么」 | ✅ 方法签名上的 `throws` | ❌ 没有，靠约定和文档 |
| 主动抛出 | `throw new XxxException(...)` | `raise XxxError(...)` |
| 资源自动关闭 | `try-with-resources`（Java 7+） | `with open(...) as f:` |
| 原始异常保留 | `cause` 链：`getCause()` | `__cause__` / `raise ... from e` |

Python 的对应写法：

```python
# Python：不需要声明，读文件失败直接抛 FileNotFoundError
def read_config(path):
    with open(path) as f:     # Python 的 with ≈ Java 的 try-with-resources
        return f.read()

try:
    read_config("x.txt")
except FileNotFoundError as e:
    print("读取失败：", e)
```

⭐ **最大的迁移陷阱**：从 Python 转到 Java 后，你会习惯性地「不写 `try/catch` 也行」——但对 `IOException`、`SQLException` 这类**受检异常**，Java 编译器会直接拒绝编译。这不是 Java「更严格」，而是它在替你把「失败路径」写进接口契约里。

## 陷阱

1. **⚠️ 以为 `RuntimeException` 是 `Error` 的子类**——它是 `Exception` 的子类；`catch (Exception e)` 抓不到任何 `Error`；
2. **⚠️ 以为 `catch (Exception e)` 是万能兜底**——它既抓不到 `Error`，也会把真正的编程错误（如 NPE）当成可恢复故障吞掉，让 bug 变成「行为诡异」而不是「快速失败」；
3. **⚠️ 以为非受检异常「更严重」**——恰恰相反：非受检 = 编程错误（改代码），受检 = 外部故障（可恢复、可重试）；
4. **⚠️ 以为 `Error` 也要 try/catch 包住**——`OutOfMemoryError` 时 JVM 状态已不可信，捕获它继续跑业务只会让故障现场丢失；正确做法是让它崩、让监控告警；
5. **⚠️ 把 `OutOfMemoryError` 和 `StackOverflowError` 混为一谈**——一个缺内存、一个缺栈，加内存对后者无效；
6. **⚠️ 只看 `e.getMessage()` 不看堆栈**——`getMessage()` 只是一句话，排查靠的是 `getStackTrace()` 打出来的调用链；
7. **⚠️ 以为 `Exception` 能覆盖所有错误**——`Error` 和 `Exception` 是平级分支，`catch (Throwable)` 才能全覆盖，但那是最后手段；
8. **⚠️ 依赖「不 catch 就自动打印」的默认行为**——异常冒到线程最外层虽然会打印，但此时业务流程已经被打断，程序状态不可信；生产代码应该在能恢复的地方处理。

## 小结

- 异常机制把「错误」从**返回值数据流**移到**控制流**，避免魔法错误码污染返回值
- `Throwable` → `Error`（严重、通常不处理）/ `Exception`（可处理）；`Exception` → `RuntimeException`（非受检）/ 其他（受检）
- `RuntimeException` 是 `Exception` 的子类，**不是** `Error` 的子类
- 切分线是 `RuntimeException`：它及其后代 = 非受检；`Exception` 的其他后代 = 受检（`Error` 也属于非受检）
- 受检 = 编译器强制 + 「调用方有合理恢复手段」；非受检 = 「编程错误，该改代码」
- 传播路径：抛出 → 本层无匹配 `catch` → 弹栈上抛 → 逐层找处理器 → 找不到则线程终止（`main` 线程终止 = 进程退出）
- 堆栈轨迹在异常**创建时**抓取，记录的是出生地
- 相对 Python：Java 独有受检异常机制；Python 有 `else` 子句、Java 没有
