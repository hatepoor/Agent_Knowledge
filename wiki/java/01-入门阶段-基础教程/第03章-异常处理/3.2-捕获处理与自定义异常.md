## 一、try / catch / finally 基本语法

三个关键字构成 Java 异常处理的基本骨架：

```java
try {
    // 可能出错的代码
} catch (异常类型1 e1) {
    // 处理第一类异常
} catch (异常类型2 e2) {
    // 处理第二类异常
} finally {
    // 无论如何都会执行
}
```

各部分职责：

| 部分 | 作用 | 要点 |
|------|------|------|
| `try` 块 | 装「可能抛异常」的代码 | 只把**确实会出问题**的最小代码块放进来；别把整个方法体都塞进去 |
| `catch` 块 | 处理匹配到的异常 | 括号里是异常类型，`e` 是异常对象变量，可调 `getMessage()` / `getCause()` / `printStackTrace()` |
| `finally` 块 | 收尾：释放资源、还原状态、打日志 | ⭐ **几乎总会执行**，是「兜底清理区」 |

一个完整可运行的例子：

```java
public class BasicTryCatch {
    static int parse(String s) {
        try {
            return Integer.parseInt(s);      // 可能抛 NumberFormatException
        } catch (NumberFormatException e) {
            System.out.println("解析失败：" + e.getMessage());
            return 0;                         // 处理完给一个兜底值
        } finally {
            System.out.println("finally 一定会执行");
        }
    }

    public static void main(String[] args) {
        System.out.println(parse("123"));   // 输出 123
        System.out.println(parse("abc"));   // 输出 解析失败 + finally，然后 0
    }
}
```

⭐ **`catch` 的匹配规则**：编译器按**书写顺序**逐个检查 `catch`，第一个 `catch` 的异常类型是实际抛出异常类型的**父类或同类**时，就由它接手。所以 `catch` 的顺序直接决定行为——见下一节。

## 二、⭐ finally 一定执行（连 return 也不例外）

这是本篇必须背下来的规则：**`finally` 块在 `try` 块正常结束、抛出异常、被 `catch` 捕获、甚至 `try` 里执行了 `return` 的情况下，都会执行。**

```java
public class FinallyAlways {
    static void demo(String mode) {
        try {
            System.out.print("try; ");
            if (mode.equals("return")) { System.out.print("→ 执行 return; "); return; }
            if (mode.equals("throw")) throw new RuntimeException("炸了");
            System.out.print("→ 正常结束; ");
        } catch (RuntimeException e) {
            System.out.print("→ 被 catch 捕获; ");
        } finally {
            System.out.println("finally 执行");
        }
    }

    public static void main(String[] args) {
        demo("return");   // try; → 执行 return; finally 执行
        demo("throw");    // try; → 被 catch 捕获; finally 执行
        demo("normal");   // try; → 正常结束; finally 执行
    }
}
```

⚠️ **`finally` 唯一不执行的几种情况**（记住这一条就够了）：

1. JVM 被强制终止（`System.exit(...)`）；
2. 机器断电、进程被 `kill -9`；
3. 线程被强制杀死。

也就是说：**只要 JVM 还活着在正常跑，`finally` 就会执行。**

⭐ **为什么 `finally` 这么可靠**：`javac` 编译时会把它改写成「等价于 `finally` 的代码被插到所有出口之前」的形式（字节码层面的复制），所以不管从哪个出口离开 `try`，都会先跑 `finally`。这在 Python 里也一样（Python 用 `try/finally` 保证），但 Python 额外有 `else` 子句，Java 没有——Java 里「`try` 没抛异常」的情况就写在 `try` 块正常路径上。

## 三、多异常捕获与 catch 顺序

### 3.1 ⚠️ catch 顺序必须从具体到宽泛

```java
try {
    Integer.parseInt(s);
} catch (NumberFormatException e) {     // ✅ 子类在前：精确捕获
    // 只处理数字格式错
} catch (IllegalArgumentException e) {  // ✅ 父类在后：兜住同族的其他非法参数
    // 处理其他参数非法
} catch (Exception e) {                 // ✅ 最宽泛的放最后
    // 最后的兜底
}
```

⚠️ **如果把顺序写反会怎样**？`catch (Exception e)` 写在前面，它能接住一切，后面那个 `catch (NumberFormatException e)` **永远不可能被执行**——编译器会直接报错：

```text
error: exception NumberFormatException has already been caught
```

这叫「不可达 catch 块」，是**编译期**错误，不是运行时问题。记住规则：**子类在前、父类在后，`Exception` 兜底永远排最后。**

### 3.2 Java 7+ 多重捕获

Java 7 起支持一个 `catch` 同时接多个**互不相关**的异常，用 `|` 分隔：

```java
import java.io.IOException;
import java.sql.SQLException;

public class MultiCatch {
    static void run(String path, boolean useDb) {
        try {
            if (useDb) {
                throw new SQLException("数据库不可用");
            }
            throw new IOException("文件不可读");
        } catch (IOException | SQLException e) {
            // ✅ e 的类型是两者的公共父类 Exception
            System.out.println("外部资源故障：" + e.getMessage());
        }
    }

    public static void main(String[] args) {
        run("x", true);
        run("x", false);
    }
}
```

⚠️ 两个限制：

1. **`|` 连接的异常之间不能有继承关系**。写成 `catch (IOException | FileNotFoundException e)` 会编译失败：
   ```text
   error: Alternatives in a multi-catch statement cannot be related by subclassing
     Alternative FileNotFoundException is a subclass of alternative IOException
   ```
   原因很直白：`FileNotFoundException` 是 `IOException` 的子类，用多 catch 只会让子类失去单独处理的机会，编译器直接禁止。
2. **多 catch 里的变量 `e` 是隐式 final 的**，不能给它重新赋值——编译报错 `multi-catch parameter e may not be assigned`。
   > 另一个常见报错：`catch (IOException e)` 如果 `try` 块里根本不可能抛出 `IOException`，编译期就会报 `exception IOException is never thrown in body of corresponding try statement`。

⭐ **与 Python 对照**：

```python
# Python：except 后面接元组，也是从具体到宽泛
try:
    ...
except (ValueError, TypeError) as e:
    ...
except Exception as e:
    ...
```

结构上几乎一一对应，唯一差别是 Java 靠编译器强制你**不能写错顺序**，Python 写错顺序不报错、只是永远走不到后面那个分支。

## 四、⭐ throw vs throws

这是 Java 新手最常混的一对关键字，**它们完全不是一个层面的东西**：

| 维度 | `throw` | `throws` |
|------|---------|----------|
| 关键字后面跟什么 | **一个异常对象实例**：`throw new XxxException("msg")` | **一个或多个异常类型**：`throws IOException, SQLException` |
| 出现在哪 | **方法体内部**的一条语句 | **方法签名**上，紧跟参数列表 |
| 作用 | **主动抛出一个异常**——此刻这个异常就诞生了 | **声明「我这个方法可能抛出哪些异常」**——把处理责任交给调用者 |
| 数量 | 一次只能抛一个 | 可以多个，逗号分隔 |
| 谁处理 | 抛出点之后的调用链上 whoever | 由**调用者**决定：要么 `catch`，要么继续 `throws` 往上推 |
| 能不能省 | 受检异常必须被处理，所以该抛就抛 | 非受检异常可以不写 |

```java
import java.io.IOException;

public class ThrowVsThrows {
    // ✅ throws：声明在签名上，告诉调用者「我可能抛 IOException」
    static String readConfig(String path) throws IOException {
        if (path == null) {
            // ✅ throw：方法体里真正抛出一个异常实例
            throw new IllegalArgumentException("路径不能为 null");
        }
        return "config of " + path;
    }

    public static void main(String[] args) {
        try {
            System.out.println(readConfig(null));
        } catch (IllegalArgumentException e) {
            System.out.println("非法参数：" + e.getMessage());
        } catch (IOException e) {
            // 编译器强制你处理 readConfig 声明的 IOException
            System.out.println("读取失败：" + e.getMessage());
        }
    }
}
```

⭐ **一句话记法**：`throw` 是「扔出去」，`throws` 是「挂个牌子说我可能会扔」。

## 五、异常传播：向上声明 vs 就地捕获

方法遇到异常时有两条路可走，这是**接口设计**层面的取舍：

| 策略 | 做法 | 适用场景 | 代价 |
|------|------|---------|------|
| **向上声明** | 方法签名上写 `throws`，把处理责任推给调用者 | 调用方**真的**有不同处理策略：比如上层要重试、要降级、要把异常翻译成 HTTP 响应码 | `throws` 链一路往上传染，签名越来越长 |
| **就地捕获** | 在方法内部 `try/catch` 消化掉 | 本层**完全能决定**怎么处理：打日志、返回默认值、清理资源 | 异常信息在这一层被终结，上层看不到细节 |
| **就地捕获 + 包装** | `catch` 后 `throw new XxxException("...", e)` 换一种类型再抛 | 本层做不了主决策，但需要把「技术异常」翻译成「业务语义」 | 多一层包装，要小心别把原始 cause 丢了 |

```java
import java.io.IOException;

// ✅ 就地捕获 + 包装：把 IOException 翻译成业务能懂的话，同时保留原始 cause
class UserService {
    static class UserNotFoundException extends RuntimeException {
        UserNotFoundException(String message, Throwable cause) {
            super(message, cause);
        }
    }

    static String loadUser(long id) {
        try {
            if (id < 0) throw new IOException("id 非法：" + id);
            return "user-" + id;
        } catch (IOException e) {
            // ⚠️ 关键：把 e 作为 cause 传进去，原始信息不丢
            throw new UserNotFoundException("加载用户失败：" + id, e);
        }
    }

    public static void main(String[] args) {
        try {
            loadUser(-1);
        } catch (UserNotFoundException e) {
            System.out.println("业务层看到的：" + e.getMessage());
            System.out.println("原始原因：" + e.getCause().getMessage());   // ⭐ cause 链
        }
    }
}
```

⭐ **判断标准**：
- **调用方有多种合理反应** → 向上声明（`throws`）；
- **调用方只有一种反应（或根本不该关心）** → 就地捕获；
- **需要跨层转换语义**（技术错误 → 业务错误）→ 就地捕获后包装再抛。

⚠️ **最差的一种做法**：每一层都 `catch` 一下再原样 `throw e` 出去（既没处理也没加信息），纯粹是噪音，直接删掉。

## 六、try-with-resources（Java 7+）

手动管理资源（文件、连接、流）的经典写法是 `finally` 里 `close()`：

```java
// ⚠️ 老写法：啰嗦，且容易在 close 之前漏掉异常处理
BufferedReader br = null;
try {
    br = new BufferedReader(new FileReader("data.txt"));
    String line = br.readLine();
    System.out.println(line);
} catch (IOException e) {
    e.printStackTrace();
} finally {
    if (br != null) {
        try { br.close(); } catch (IOException e) { /* 吞掉 */ }
    }
}
```

Java 7 起提供 **`try-with-resources`**：把资源的创建写进 `try` 后面的括号里，离开 `try` 块时自动关闭。

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class TwrDemo {
    static void readFirstLine(String path) throws IOException {
        // ✅ 资源声明在 try 的括号里，离开 try 自动关闭（即使中途抛异常）
        try (BufferedReader br = Files.newBufferedReader(Path.of(path))) {
            System.out.println(br.readLine());
        }
        // 走到这里时 br 一定已经关闭了，不需要写 finally
    }

    public static void main(String[] args) {
        try {
            readFirstLine("data.txt");
        } catch (IOException e) {
            System.out.println("读取失败：" + e.getMessage());
        }
    }
}
```

### 6.1 前提：AutoCloseable / Closeable

`try-with-resources` 要求资源类型实现 **`AutoCloseable`**（Java 7+ 引入的接口，它只有一个方法 `close()`）。`java.io.Closeable` 是 `AutoCloseable` 的子接口，把 `close()` 的异常类型收窄成 `IOException`。

> **自动关闭**的本质：编译器在 `try` 块的所有出口处插入了 `close()` 调用，效果等价于手写的 `finally`，但绝不会漏写、也不会写错顺序。

### 6.2 可以声明多个资源，按「逆序」关闭

```java
try (BufferedReader br = Files.newBufferedReader(Path.of("in.txt"));
     BufferedWriter bw = Files.newBufferedWriter(Path.of("out.txt"))) {
    String line;
    while ((line = br.readLine()) != null) {
        bw.write(line);
        bw.newLine();
    }
}   // 关闭顺序：先 bw，再 br（与声明顺序相反，符合「栈」语义）
```

### 6.3 ⭐ 关闭时的异常会被「抑制」（suppressed）

如果 `try` 块里抛了异常 A，而 `close()` 又抛了异常 B，**A 才是主异常**，B 不会覆盖 A，而是被**挂到 A 的身上**——存放在 A 的「被抑制异常列表」里。

```java
import java.io.IOException;

public class SuppressedDemo {
    // 一个「关闭时必定失败」的资源
    static class BadResource implements AutoCloseable {
        @Override
        public void close() throws IOException {
            throw new IOException("关闭时出错");
        }
    }

    public static void main(String[] args) {
        try (BadResource r = new BadResource()) {
            throw new RuntimeException("主流程出错");   // 主异常
        } catch (Exception e) {
            System.out.println("主异常：" + e.getMessage());
            System.out.println("被抑制的异常数量：" + e.getSuppressed().length);
            for (Throwable t : e.getSuppressed()) {
                System.out.println("  被抑制：" + t.getMessage());
            }
        }
    }
}
```

输出：

```text
主异常：主流程出错
被抑制的异常数量：1
  被抑制：关闭时出错
```

⭐ **为什么要这个机制**：如果 `close()` 的异常直接抛出去，就会把 `try` 块里真正的错误盖掉——你看到的会是「关闭失败」，而不是「业务逻辑出错」。抑制机制保证**主异常永远优先**，同时把次要异常完整保留，通过 `getSuppressed()` 取回（`Throwable.getSuppressed()` 返回 `Throwable[]`，Java 7+）。

### 6.4 Java 9+：可以先声明变量再放进 try

```java
// Java 9+：变量在 try 之前声明（且必须是 effectively final 或 final）
BufferedReader br = Files.newBufferedReader(Path.of("data.txt"));
try (br) {
    System.out.println(br.readLine());
}
```

### 6.5 与 Python `with` 的对照

| | Java `try-with-resources` | Python `with` |
|---|---|---|
| 语法 | `try (资源声明) { }` | `with open(...) as f:` |
| 自动关闭 | ✅ | ✅ |
| 多资源 | 分号分隔，逆序关闭 | 逗号分隔，或嵌套 |
| 前提 | 资源必须实现 `AutoCloseable` | 资源必须有 `__enter__`/`__exit__`（即上下文管理器协议） |
| 关闭异常 | 挂为主异常的 suppressed | `__exit__` 异常会替换原异常（除非在 `__exit__` 里做处理） |
| 差异点 | Python 的 `with` 还能包**任意**上下文管理器（锁、计时器等），Java 只认 `AutoCloseable` | |

⭐ 结论：**Java 的 `try-with-resources` 正是 Python `with` 的对应物**，但 Java 把它做成了「必须实现接口」的强约定，因此不存在「忘记关闭」的可能。

## 七、⭐ 自定义异常

### 7.1 什么时候该自定义异常

当内置异常表达不了你的业务语义时，就该定义自己的异常类。典型场景：

- 「订单状态不对，不能退款」→ `OrderStateException`
- 「余额不足」→ `InsufficientBalanceException`
- 「用户不存在」→ `UserNotFoundException`

### 7.2 继承谁：受检还是非受检

| 父类 | 异常类别 | 什么时候选它 |
|------|---------|------------|
| `RuntimeException` | **非受检** | 业务异常（订单状态错、余额不足、参数非法）——调用方通常没法「恢复」，只是要知道「业务失败了」。**这是现代 Java 的主流做法** |
| `Exception` | **受检** | 调用方**确实有合理恢复手段**的外部故障（如文件读写、远程调用），且你想用编译器强制所有调用方都处理它 |

⭐ **默认选 `RuntimeException`**：让业务异常不污染每一层的方法签名。只有当「强制每个调用方都必须正面处理这个失败」本身就是你想要的契约时，才用受检。

### 7.3 命名规范

- 类名以 **`Exception`** 结尾（表示可预期错误）或 **`Error`** 结尾（表示严重错误，慎用）；
- 用**名词/业务概念**命名，不用动作：`OrderNotFoundException` ✅，`ThrowOrderException` ❌；
- 一个异常类只对应**一种**失败原因，别搞一个 `BizException` 装所有事（除非你确实需要「业务异常码」体系）。

### 7.4 构造器设计

一个规范的异常类通常提供这几个构造器：

```java
public class BizException extends RuntimeException {

    // ① 无参：给框架（Jackson / MyBatis / Spring）反射创建用
    public BizException() {
        super();
    }

    // ② 只带消息：最常用
    public BizException(String message) {
        super(message);
    }

    // ③ 消息 + 原始异常：⭐ 保留 cause 的关键构造器
    public BizException(String message, Throwable cause) {
        super(message, cause);
    }

    // ④ 带业务错误码：便于前端 / 上层按码处理
    private final String errorCode;

    public BizException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
    }

    public BizException(String errorCode, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
    }

    public String getErrorCode() {
        return errorCode;
    }
}
```

> `super(message)` / `super(message, cause)` 是调用父类 `Throwable` 的构造器——`Throwable` 提供了 `(String)`、`(String, Throwable)`、`(Throwable)`、`()` 这几个重载。

### 7.5 initCause 与 cause 链

**cause（原始异常）**就是「这个异常是由哪个异常引起的」。`Throwable` 有两套设置方式：

1. **构造器传入**（推荐）：`super(message, cause)`；
2. **事后用 `initCause(cause)` 补设**：适用于「对象先被创建，之后才拿到原因」的场景。

```java
public class InitCauseDemo {
    public static void main(String[] args) {
        // 事后补设 cause
        Exception e = new Exception("外层异常");
        e.initCause(new IllegalStateException("内层原因"));
        System.out.println(e.getCause().getMessage());   // 内层原因

        // ⚠️ 只能设置一次，再设会抛 IllegalStateException
        try {
            e.initCause(new RuntimeException("再来一次"));
        } catch (IllegalStateException ex) {
            System.out.println("重复设置 cause 失败：" + ex.getMessage());
        }
    }
}
```

⭐ **cause 链（异常链）**：`a.getCause().getCause()...` 可以一路挖到最初的根因。Java 打印堆栈时会自动带上 `Caused by:` 链：

```text
java.lang.RuntimeException: 外层异常
    at ...
Caused by: java.lang.IllegalStateException: 内层原因
    at ...
```

## 八、异常包装：不要吞掉原始异常

**这是本篇最重要的一条工程纪律。**

### 8.1 反模式：吞掉 cause

```java
// ❌ 错误：原始异常的信息彻底丢失
try {
    doSomething();
} catch (IOException e) {
    throw new BizException("操作失败");       // e 被丢掉了
}
```

此时 `bizException.getCause()` 返回 `null`，堆栈里也**没有** `Caused by:` 行。你只知道「操作失败」，但不知道是磁盘满了、网络断了还是 SQL 语法错了——排查成本极高。

### 8.2 正确做法：包装并保留 cause

```java
// ✅ 正确：把原始异常作为 cause 传进去
try {
    doSomething();
} catch (IOException e) {
    throw new BizException("查询用户失败：uid=" + uid, e);   // ⭐ 保留 e
}
```

效果：

- `e.getMessage()` → 你写的业务描述（带上下文，比原始信息更有价值）；
- `e.getCause()` → 原始异常对象，`getCause().getMessage()` 拿到根因；
- 堆栈打印自动出现 `Caused by:` 链。

⭐ **判断标准：包装异常时，问自己「如果只给我看一条信息，我该看到什么？」**——答案是**业务上下文**（哪个用户、哪笔订单），而**不是**原始的技术错误。原始错误用 cause 挂起来，排查时再挖。

### 8.3 什么时候可以真的丢掉 cause

极少数情况可以丢：

- 原始异常信息**已经完整包含**在新消息里（很少见）；
- 原始异常**包含敏感信息**（密码、token），不能往上暴露——但更好的做法是**脱敏后再包装**，而不是直接丢。

⚠️ **不允许的情况**：「我不知道怎么处理，先包一层总没错」——这只会把排查难度往后推。

## 九、陷阱

1. **⚠️ `catch` 里只 `printStackTrace()` 就完事**——`printStackTrace()` 打到的是**标准错误流**（不是标准输出），在容器化环境里通常被丢弃，而且没有时间戳、日志级别、上下文。生产代码应该用日志框架（SLF4J / Logback）记录：`log.error("加载用户失败，uid={}", uid, e)`——注意把 `e` 作为**最后一个参数**传，别拼进字符串里（那样会丢掉堆栈）；
2. **⚠️ `catch` 后 `return` 默认值，导致语义丢失**——`catch (IOException e) { return null; }` 让调用方分不清「本来就没有数据」和「读取失败了」。要么向上抛、要么返回 `Optional` / 明确的结果对象承载这个区分；
3. **⚠️ `finally` 里写 `return`**——这会**吞掉原本要抛出的异常**（异常在 `finally` 的 `return` 处被静默丢弃，栈轨迹也丢了）：
   ```java
   static String demo() {
       try {
           throw new RuntimeException("原始异常");
       } catch (RuntimeException e) {
           System.out.println("catch 执行了：" + e.getMessage());
           throw e;                        // 重新抛出：我就是要往上抛
       } finally {
           return "finally 的返回值";      // ⚠️ 上面那个异常在这里被彻底吞掉
       }
   }
   // 实际输出：catch 执行了：原始异常 → finally 的返回值
   // ⚠️ 异常消失了，程序装作什么都没发生
   ```
   顺带一个编译期细节：如果 `finally` 里是**无条件 `return`**，编译器会认为 `try` 块末尾的 `return` 不可达而报 `unreachable statement`；而 `catch` 里写了 `return` 时，`finally` 的 `return` 会**覆盖**掉它返回的值。
   `finally` 里只放**清理逻辑**，永远不要放 `return`；
4. **⚠️ 空的 `catch` 块**——`catch (Exception e) { }` 什么都不做，等于把故障信息全部销毁。至少要打一行日志；
5. **⚠️ 资源没关 / 关的方式不对**——手动 `close()` 容易漏（尤其 `try` 里抛异常时）。用 `try-with-resources`（Java 7+）；
6. **⚠️ `catch` 顺序写反**——子类 `catch` 写在父类后面 → 编译错误 `already been caught`；子类写在父类前面但只想要宽泛处理 → 子类那支永远不会执行；
7. **⚠️ 包装异常时忘记传 cause**——原始原因丢失，排查线索断掉（见第八节）；
8. **⚠️ 把 `catch (Throwable t)` 当万能兜底**——`Throwable` 包含 `Error`，连 `OutOfMemoryError` 都会被你「处理」掉，然后程序带着坏掉的 JVM 状态继续跑。**永远不要捕获 `Throwable`**；
9. **⚠️ 在循环里 `catch` 后 `continue`**——如果异常来自状态更新，会导致无限重试；捕获前先想清楚「重试有意义吗」。

---

## 小结

- `try`（可能出错的最小代码块）+ `catch`（按类型处理）+ `finally`（兜底清理）；`catch` 顺序必须**子类在前、父类在后**
- `finally` 几乎**一定执行**，连 `return` 也会先执行 `finally`；唯一例外是 JVM 被强杀
- Java 7+ 支持多重捕获 `catch (A | B e)`，但 `A` 和 `B` **不能有继承关系**
- `throw` = 在方法体里**扔出**一个异常实例；`throws` = 在方法签名上**声明**可能抛哪些异常；一个扔，一个挂牌子
- 传播取舍：调用方有多种反应 → 向上声明；只有一种反应 → 就地捕获；跨层换语义 → 捕获后包装再抛
- `try-with-resources`（Java 7+）自动关闭资源，前提是实现 `AutoCloseable`（`Closeable` 是其子接口）；关闭时的异常**被抑制**为主异常的 `getSuppressed()`
- 自定义异常默认继承 `RuntimeException`（非受检）；命名 `XxxException`；必须提供保留 cause 的构造器
- **不要吞掉原始异常**：`throw new BizException("上下文", e)`，让 `getCause()` 保留根因
- 九个高频坑：只 `printStackTrace`、catch 后返回默认值、`finally` 里 `return`、空 catch、资源没关、catch 顺序写反、包装丢 cause、`catch (Throwable)` 兜底、循环里 catch 后 continue
