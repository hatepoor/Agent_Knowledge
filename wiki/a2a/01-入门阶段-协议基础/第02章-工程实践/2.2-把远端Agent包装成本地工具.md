## 一、先纠正一个常见做法

很多教程会建议你把远端 Agent **包装成 MCP server** 再接入。这条路在实践中问题不少，先说清为什么。

### 做法：远端 Agent → MCP server → 我的 Agent

```
我的 Agent ──MCP── 本地 MCP server ──HTTP── 远端 A2A Agent
```

**这条链上会出问题的地方**：

| 问题 | 说明 |
|------|------|
| **语义丢失** | MCP 是「无状态的工具调用」，但远端 Agent 是**有状态的多轮任务**。中间这层 MCP 适配器必须自己维护 Task 状态，变成一个复杂的自研中间件 |
| **多轮对话无处安放** | 远端要反问（`input-required`）时，MCP 的工具调用模型没有位置放这个「等待补充」的状态 |
| **双倍延迟** | 一次调用变成 MCP 请求 + A2A 请求两跳网络 |
| **状态分裂** | Task 状态在远端，会话上下文在你的 Agent，中间层要对齐两套状态机 |
| **鉴权链路变长** | 你的 MCP server 要同时持有「对你的调用方的凭证」和「对远端的凭证」，两套都要管 |

**结论**：MCP 这条路要自己实现一层状态机同步，本质上是**把 A2A 的语义塞进 A2A 不设计的模型里**。能做，但没必要。

---

## 二、推荐做法：agent-as-tool

### 模式定义

**agent-as-tool（智能体即工具）**：把远端 A2A Agent 的能力，包装成你本地 Agent 的**一个工具**。调用这个工具时，内部走完整的 A2A 流程。

```
我的 Agent ──工具调用──> 本地包装函数 ──A2A──> 远端 Agent
                            ↑
                    拉 Agent Card、发 Task、
                    处理状态流转、拿 Artifact
```

### 和 MCP 包装的本质区别

| 维度 | MCP 包装 | agent-as-tool 包装 |
|------|---------|------------------|
| 中间层承担 | 无状态的请求转发 | **有状态的完整 A2A 交互** |
| 状态在哪 | 中间层要自己同步 | 远端持有 Task，你这边只持 Task ID |
| `input-required` | 无处安放 | 在包装函数内部循环处理 |
| 网络跳数 | 2 跳 | 1 跳 |

**关键洞察**：包装函数内部**就是一段完整的 A2A 客户端代码**，它不是「适配器」，它就是客户端本身。只是被包成了工具的样子，让你的 LangChain Agent 能无感调用。

### 最小实现

```python
from langchain_core.tools import tool
import httpx

from a2a.client import A2ACardResolver, ClientConfig, create_client
from a2a.helpers import new_text_message
from a2a.types import Role, SendMessageRequest, TaskState


class RemoteA2AAgent:
    """封装一个远端 A2A Agent 的客户端会话。"""

    def __init__(self, base_url: str, token: str | None = None):
        self.base_url = base_url
        self.token = token
        self.card = None
        self.client = None
        self.context_id: str | None = None   # 复用会话上下文

    async def connect(self):
        async with httpx.AsyncClient() as hc:
            resolver = A2ACardResolver(
                httpx_client=hc, base_url=self.base_url
            )
            self.card = await resolver.get_agent_card()

        self.client = await create_client(
            agent=self.card,
            client_config=ClientConfig(streaming=False),
        )
        return self.card

    async def send(self, text: str, timeout: float = 300.0) -> dict:
        # 发消息，自动处理 input-required 循环
        message = new_text_message(text, role=Role.ROLE_USER)
        request = SendMessageRequest(message=message)

        async for chunk in self.client.send_message(request):
            task = chunk

        # 远端反问了：拿到状态和反问内容，交回给调用方处理
        state = task.status.state
        if state == TaskState.TASK_STATE_INPUT_REQUIRED:
            question = task.status.message.parts[0].root.text
            return {
                "status": "need_input",
                "task_id": task.id,
                "question": question,
            }

        if state == TaskState.TASK_STATE_COMPLETED:
            artifact = task.artifacts[0] if task.artifacts else None
            text_out = artifact.parts[0].root.text if artifact else ""
            return {"status": "done", "output": text_out}

        return {"status": state}


# 包装成 LangChain 工具
@tool
async def query_legal_agent(question: str) -> str:
    """向法务 Agent 提问。只有合同审查、条款风险评估类问题才用这个工具。"""
    agent = _get_agent_singleton()          # 复用连接，别每次新建
    result = await agent.send(question)

    if result["status"] == "need_input":
        # 把反问抛给你的 Agent，让它决定是转发给用户还是自己补齐
        return f"法务 Agent 需要补充信息：{result['question']}"

    return result.get("output", str(result))
```

### 这段代码里值得注意的三点

| 设计 | 为什么 |
|------|--------|
| **复用客户端实例** | 每次调用新建连接 + 重新拉 Agent Card 是巨大浪费。Agent Card 应该缓存 |
| **保存 `context_id`** | 多次调用属于同一次业务会话，能复用上下文 |
| **`need_input` 不吞掉** | 远端反问是有效信息，应该转交给你自己的 Agent 或人类用户，而不是静默重试 |

⚠️ **最后一点最容易写错。** 很多实现在遇到 `input-required` 时直接重试或返回空——这会导致任务永远卡住，而且丢失了远端的提问信息。

## 三、在 LangGraph 系统里的位置

这一节回答一个具体问题：**这个包装应该放在图的哪一层？**

```
┌─────────────────────────────────────────────┐
│  LangGraph 图                                │
│                                              │
│  ┌────────────┐        ┌──────────────────┐ │
│  │ 编排节点    │───────>│  专家节点         │ │
│  │ 决定派给谁  │        │  （LangChain Agent）│ │
│  └────────────┘        └────────┬─────────┘ │
│                                  │           │
│                      工具调用：query_legal   │
│                                  │           │
└──────────────────────────────────┼──────────┘
                                   │ A2A
                                   ▼
                            远端专家 Agent
```

**放置原则：**

| 规则 | 说明 |
|------|------|
| **工具定义在专家节点里** | 让 LLM 只在「真的要查法务」时才调这个工具，不污染编排节点的决策 |
| **连接实例挂在图的状态外** | 别塞进 State——State 会被 checkpoint 序列化，连接对象序列化不了 |
| **编排逻辑留在编排节点** | 「什么时候该问法务」是你自己的业务决策，不要外包给远端 |
| **超时和降级在工具内** | 工具内部兜底，异常不要冒泡打断整个图 |

### 一个必须处理的结构问题：异步节点

A2A 调用是 `async` 的。LangGraph 的节点如果写成 `def`（同步），里面 `await` 会直接崩。

```python
from langgraph.graph import StateGraph, START, END

async def legal_node(state: dict) -> dict:
    """专家节点 —— 必须是 async def"""
    agent = get_or_create_legal_agent()
    result = await agent.send(state["question"])
    return {"answer": result.get("output", "")}

builder = StateGraph(dict)
builder.add_node("legal", legal_node)          # 异步节点
builder.add_edge(START, "legal")
builder.add_edge("legal", END)
graph = builder.compile()
```

⚠️ **同步节点里调异步工具是这个模式最常见的报错来源。** 如果你的工具是 async 的，节点就得是 `async def`，并且图的调用方也要相应处理（`ainvoke` / `astream` 而非 `invoke`）。

> 相关：[[fastapi/异步处理]] —— FastAPI 里同样要小心同步路由里跑 async 调用。

## 四、接入远端 Agent 必须处理的四件事

### 1. 鉴权

```python
# ❌ 错误：凭证写进代码
client = await create_client(agent=card, headers={"Authorization": "Bearer sk-hardcode"})

# ✅ 正确：从环境变量/密钥管理读，区分公开与扩展卡
import os
token = os.environ["LEGAL_AGENT_TOKEN"]
```

⚠️ **公开 Agent Card 是任何人可抓的。** 你的凭证只走 HTTP 头，**永远不要进卡片**。详见 [[a2a/02-中段阶段-生产实践/01-安全模型与鉴权]]。

### 2. 超时

跨公网调用必须设超时，且要**分阶段设**：

| 阶段 | 建议超时 |
|------|---------|
| 拉 Agent Card | 5~10 秒（就是个 GET） |
| 发消息（首次响应） | 30~60 秒 |
| 长任务等待 | 按业务实际，可能几分钟 |

⚠️ **别设一个统一的 300 秒然后祈祷。** 拉卡失败重试 300 秒是浪费。

### 3. 重试

```python
# ✅ 只对可重试的终态重试
if result["status"] in ("failed",):
    # failed 是处理中出错，可能是瞬时故障
    retry()
elif result["status"] == "rejected":
    # rejected 是策略性拒绝，重试无用
    raise UnsupportedSkillError(result.get("question"))
```

⚠️ **这个区分来自 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.4-Task生命周期与状态机]] 的状态机。** 对 `rejected` 重试是最常见的无用功。

### 4. 降级

远端挂了你的图不能跟着挂。工具内部要兜底：

```python
@tool
async def query_legal_agent(question: str) -> str:
    """向法务 Agent 提问。"""
    try:
        result = await agent.send(question, timeout=60)
    except Exception:
        logger.exception("legal agent 调用失败")
        return "法务 Agent 暂不可用，已记录并跳过该问题"
    return result.get("output", "")
```

⚠️ **降级不是可选的。** 外部依赖必须有降级路径，否则它会成为你整个系统的单点。

---

## 五、这个模式的适用边界

| 适合 | 不适合 |
|------|--------|
| 你的系统要调用**别人托管的** Agent | 对方 Agent 就在你本地（直接函数调用） |
| 需要对方**有状态、多轮、可能反问** | 对方只是个确定性的函数（用 MCP 更快） |
| 跨组织，需要标准鉴权边界 | 同一内网、同一团队、可以直连 |
| 你想在 LangGraph 图里复用现有工具机制 | 你愿意自己写一套异步编排 |

---

## 六、陷阱

1. **每次调用都新建客户端 / 重新拉 Agent Card。** 客户端实例和卡片都要复用。
2. **吞掉 `input-required`。** 远端的反问是有效信息，要转交出去。
3. **对 `rejected` 无脑重试。** 策略性拒绝重试永远被拒。
4. **同步节点里 `await`。** 节点必须 `async def`，调用方用 `ainvoke` / `astream`。
5. **凭证写进代码或 Agent Card。** 走环境变量，走 HTTP 头。
6. **统一超时不分阶段。** 拉卡和长任务的超时量级完全不同。
7. **把远端 Agent 包成 MCP server。** 要自己实现状态机同步，多一跳网络，语义还丢。
8. **没有降级路径。** 远端挂了整个图就挂了。

---

## 小结

- **agent-as-tool** 是接入远端 Agent 的推荐姿势：包装函数内部就是完整的 A2A 客户端
- 不要包成 MCP server——语义丢失、多跳延迟、状态分裂、鉴权链变长
- 在 LangGraph 里放在**专家节点作为工具**，连接实例放图状态外（别进 State）
- 异步节点必须 `async def`，调用方用 `ainvoke` / `astream`
- 四件必做事：**鉴权（走环境变量 + HTTP 头）/ 分阶段超时 / 按状态区分重试 / 降级兜底**
- 复用客户端实例和 `context_id`，别每次新建
