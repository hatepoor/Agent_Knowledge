## 一、三种结果获取机制

A2A 支持三种拿结果的方式。**它们不是三选一，可以同时用**——同一个 Task 可以同时有 5 个观察者。

### 机制 1：轮询（Polling）

客户端周期性调 `tasks/get` 查状态。

```
客户端                                服务端
  │── tasks/get(task_123) ──────────►│
  │◄─ {status: "working"} ───────────│   ← 1 秒后
  │── tasks/get(task_123) ──────────►│
  │◄─ {status: "working"} ───────────│   ← 3 秒后
  │── tasks/get(task_123) ──────────►│
  │◄─ {status: "completed", artifacts}│  ← 5 秒后
```

| 优点 | 缺点 |
|------|------|
| 最简单，任何 HTTP 客户端都能做 | 有延迟（取决于轮询间隔）；请求数多 |
| 无需保持连接 | 无法实时拿到中间进度 |

**适用**：短任务、简单集成、客户端不方便维持长连接的场景。官方把轮询定位为「简单集成」的选择。

### 机制 2：流式（SSE，Server-Sent Events）

客户端打开一个 HTTP 长连接，服务端持续推送增量结果和状态更新。

```
客户端                                服务端
  │◄═ SSE ══════════════════════════►│  长连接建立
  │◄─ {status: "working", ...} ──────│  增量 1
  │◄─ {artifact部分1} ───────────────│  增量 2
  │◄─ {artifact部分2} ───────────────│  增量 3
  │◄─ {status: "completed"} ─────────│  结束
```

**SSE 是什么**：一种服务端向客户端单向推流的 HTTP 机制。客户端发一个普通 HTTP GET，服务端保持响应不关闭，持续往里写数据。纯 HTTP，不需要额外协议。

> 对照你已有的知识：FastAPI 的 `StreamingResponse` + `text/event-stream`、LangGraph 的 `astream` 底层都是类似机制。

| 优点 | 缺点 |
|------|------|
| 实时性好；请求数少 | 长连接占用资源；客户端要能处理流式解析 |
| 支持增量结果，边收边用 | 需要对方 `capabilities.streaming: true` |

**适用**：**交互式 UI 的默认选择**。用户在等结果，能看到进度是体验关键。

### 机制 3：推送通知（Push Notification / Webhook）

客户端预先给服务端一个 webhook URL。服务端在任务有重要变化时，**主动 POST 到这个地址**。

```
客户端                                服务端
  │── 注册 webhook: https://me.com/hook ────────►│
  │◄─ {确认配置} ───────────────────────────────│
  │                                              │
  │        （客户端可以完全断开）                  │
  │                                              │
  │◄─ POST https://me.com/hook ─────────────────│  服务端主动来
  │   {taskId, status: "completed", artifacts}   │
```

| 优点 | 缺点 |
|------|------|
| 客户端无需保持任何连接；适合超长任务 | **必须校验 webhook URL 防 SSRF**；客户端必须校验通知真实性 |
| 客户端断连也不影响 | 有额外的公网可达性要求 |

**适用**：**长任务或客户端会断连的场景**——比如跑一小时的批处理，或者客户端是个手机 App。

### 三者对比

| 维度 | 轮询 | 流式（SSE） | 推送（Webhook） |
|------|------|-----------|--------------|
| 实时性 | 取决于轮询间隔 | 高 | 高（事件驱动） |
| 客户端状态 | 无要求 | 需维持连接 | 无要求 |
| 适合时长 | 短（秒级） | 中 | 长（分钟到小时） |
| 典型场景 | 简单集成 | **交互式 UI** | **长任务 / 断连** |
| 额外前置 | 无 | 对方 `streaming: true` | 对方 `pushNotifications: true` |
| 安全要求 | 无 | 无 | **校验 URL 防 SSRF** |

> 📐 **选择口诀**：**短的轮询、中的流式、长的推送。**

## 二、三层规范结构

A2A 规范明确分成三层。这个分层是它设计严谨的体现，也是它和「随便定个 JSON 格式」的根本区别。

### 第 1 层：规范数据模型（核心名词）

| 对象 | 说明 |
|------|------|
| `AgentCard` | 智能体名片 |
| `AgentSkill` | 能力声明 |
| `Task` | 工作单元 |
| `Message` | 通信轮次 |
| `Part` | 内容单元 |
| `Artifact` | 交付物 |
| `Extension` | 扩展声明 |

**格式**：用 **Protocol Buffers** 定义（权威来源），同时发布 **JSON Schema 2020-12**（文件 `a2a.json`，由 proto 自动生成）。

> **Protocol Buffers** 是 Google 的二进制序列化格式，一份 `.proto` 定义可以生成多语言代码。
> **JSON Schema 2020-12** 是描述 JSON 结构的元标准，定义了字段类型、必填项、取值范围等。

### 第 2 层：抽象操作（核心动词）

| 操作 | 作用 |
|------|------|
| `SendMessage` | 发消息（可同步可流式） |
| `GetTask` | 查任务 |
| `ListTasks` | 列任务 |
| `CancelTask` | 取消任务 |
| `SubscribeToTask` | 订阅任务更新 |
| 推送通知配置族 | 设置 / 读取 / 管理 webhook |
| Agent Card 读取操作 | 拉公开卡与扩展卡 |

**这一层不涉及任何传输细节**——它只说「有这些动作」，不说「用 HTTP 还是 gRPC 送」。

### 第 3 层：协议绑定（怎么落地）

v1.0 提供三套：

| 绑定 | 说明 | 适用 |
|------|------|------|
| **JSON-RPC 2.0 over HTTPS** | 默认，最通用 | 绝大多数场景 |
| **gRPC** | HTTP/2 + protobuf，强类型、流式原生 | 已有 gRPC 基础设施的团队 |
| **HTTP+JSON / REST** | 传统 REST 风格路径 | 走 API 网关、需要 WAF 审计的环境 |

### 为什么要分三层

**核心价值：换传输不用改核心逻辑。**

- 你的 Agent 内部逻辑、数据模型完全不变
- 只是换一层「怎么把这些对象送出去」的实现
- Agent Card 的 `supportedInterfaces` 可以同时列多套绑定，各取所需

### 三套绑定的实际差异

以「获取 Task」为例，同一个抽象操作 `GetTask` 在三套绑定下长这样：

| 绑定 | 形式 |
|------|------|
| JSON-RPC | `{"jsonrpc":"2.0","method":"tasks/get","params":{"id":"task_123"},"id":1}` |
| gRPC | `rpc GetTask(GetTaskRequest) returns (Task)` |
| REST | `GET /v1/tasks/task_123` |

**操作语义完全相同**，只是报文格式和命名风格不同（gRPC 用 `GetTask` 这样的方法名，REST 用路径）。

## 三、extensions：核心之外的扩展机制

**问题**：现实中总有一些需求是核心规范覆盖不到的。怎么扩展而不把协议撑爆？

**A2A 的答案**：`extensions` 字段 + 分层晋级机制（tiered promotion process）。

| 机制 | 说明 |
|------|------|
| Agent 在 Agent Card 里声明 `extensions[]` | 每条含 `uri`（扩展标识）和 `required`（是否必须支持） |
| 扩展治理走晋级流程 | 一个扩展成熟后可以被提议「晋级」进核心规范 |
| 核心保持稳定 | 未晋级前不污染核心 |

```json
"extensions": [
  { "uri": "https://x402.org/a2a/v1", "required": false }
]
```

`required: false` 意味着「你不支持这个扩展也能正常用我」。

## 四、陷阱

1. **不看 `capabilities` 就发流式请求。** 对方 `streaming: false` 会直接拒。同理 `pushNotifications`。
2. **长任务还在轮询。** 任务跑一小时你每 5 秒轮一次，那是 720 次请求。应该用流式或推送。
3. **忘了 Task 创建后要保存 ID。** 后续所有操作都靠它。
4. **把「三套绑定」理解成「要学三套 API」。** 不需要——抽象层是同一组操作，只是传输实现不同。实际用一套就够。
5. **JSON-RPC 的方法名记混。** v1.0 用 `message/send`、`tasks/get` 这类命名，速查见 [[a2a/速查索引]]。
6. **配 webhook 时不校验 URL。** 这是 SSRF 攻击的入口，必须做，见 [[a2a/02-中段阶段-生产实践/01-安全模型与鉴权]]。

## 小结

- 三种机制：轮询（短）/ SSE 流式（交互式 UI 默认）/ 推送（长任务与断连），可同时用
- SSE = 服务端单向推流的纯 HTTP 机制
- **三层规范**：数据模型（protobuf + JSON Schema）→ 抽象操作 → 协议绑定
- 分层的价值：换传输不改核心逻辑
- 三套绑定（JSON-RPC / gRPC / HTTP+JSON）暴露同一组抽象操作
- `extensions` 让扩展不污染核心规范
