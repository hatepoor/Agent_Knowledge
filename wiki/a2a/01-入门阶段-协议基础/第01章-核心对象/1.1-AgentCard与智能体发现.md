## 一、Agent Card 是什么

> **Agent Card 是一个 JSON 文档，说明这个 Agent 是谁、能干什么、怎么联系、怎么鉴权。**

它是 A2A 世界的**名片 + 合同 + 说明书**三合一。你把它理解成「机器可读的 OpenAPI 描述文件」就对了——程序员手写一个 `openapi.yaml` 是给人看的，Agent Card 是给程序看的。

放一张真实的（按 v1.0 规范裁剪过）：

```json
{
  "protocolVersion": "1.0",
  "name": "contract-review-agent",
  "description": "审查商业合同并标记异常条款",
  "version": "1.2.0",
  "provider": {
    "organization": "AcmeLegal",
    "url": "https://acmelegal.example.com"
  },
  "supportedInterfaces": [
    { "url": "https://agents.acmelegal.example.com/a2a", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" },
    { "url": "https://agents.acmelegal.example.com/grpc",   "protocolBinding": "GRPC",    "protocolVersion": "1.0" },
    { "url": "https://agents.acmelegal.example.com/json",   "protocolBinding": "HTTP+JSON","protocolVersion": "1.0" }
  ],
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "extendedAgentCard": true
  },
  "securitySchemes": {
    "oauth2": {
      "type": "oauth2",
      "flows": {
        "clientCredentials": {
          "tokenUrl": "https://auth.acmelegal.example.com/token",
          "scopes": { "contracts.read": "读取合同" }
        }
      }
    }
  },
  "security": [{ "oauth2": ["contracts.read"] }],
  "defaultInputModes": ["text/plain", "application/pdf"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "review-contract",
      "name": "审查商业合同",
      "tags": ["legal", "risk"],
      "description": "返回被标记的条款、严重级别与理由",
      "inputModes": ["text/plain", "application/pdf"],
      "outputModes": ["application/json"],
      "examples": ["审查这份 SaaS 采购合同并标出无限责任条款"]
    }
  ]
}
```

## 二、逐字段拆解

### 身份类

| 字段 | 说明 |
|------|------|
| `protocolVersion` | **协议**版本（这里 `"1.0"`）。别和下面的 `version` 搞混 |
| `name` | Agent 名称 |
| `description` | 一句话说明它是干什么的 |
| `version` | **Agent 自身**的版本。与协议版本无关，改了业务逻辑才动它 |
| `provider` | 背后的组织名与网址 |

⚠️ **`protocolVersion` vs `version` 是两个完全不同的东西。** 一个说「我讲哪一版协议」，一个说「我是第几版产品」。混用会导致版本协商失败。

### 接口类——`supportedInterfaces`（v1.0 的关键变化）

| 字段 | 说明 |
|------|------|
| `url` | 这个绑定的服务地址 |
| `protocolBinding` | 用哪套绑定：`JSONRPC` / `GRPC` / `HTTP+JSON` |
| `protocolVersion` | 该绑定上的协议版本 |

**为什么要按绑定分开列 URL？** 因为不同企业基础设施不同：有的内网只有 gRPC，有的只开放 REST 网关。列全之后，客户端可以挑一条自己能用的路，不必再问对方。

### 能力类——`capabilities`

| 字段 | 含义 | 你该怎么用 |
|------|------|---------------|
| `streaming` | 支持 SSE 流式 | 交互式 UI 必看这个，为 `false` 就只能轮询 |
| `pushNotifications` | 支持 webhook 推送 | 长任务必看，为 `false` 就得轮询 |
| `extendedAgentCard` | 提供认证后可拉的扩展卡 | 决定你能不能拿到完整信息 |

⚠️ **这三个字段是接口调用的直接依据。** 不看就发请求，会出现「发了流式请求对方不认」这类问题。

### 鉴权类

| 字段 | 说明 |
|------|------|
| `securitySchemes` | 本 Agent 接受哪些鉴权方式：`oauth2` / `openIdConnect` / `apiKey` / `http` / `mutualTLS` |
| `security` | 具体哪个方案对应哪些 scope，如 `[{ "oauth2": ["contracts.read"] }]` |

### 技能类——`skills`

| 字段 | 说明 |
|------|------|
| `id` | 技能唯一标识，调用时用它指明要哪个 |
| `name` / `description` | 人读的名字与说明，**编排 Agent 的 LLM 会读这些来做选择** |
| `tags` | 分类标签，便于检索匹配 |
| `examples` | 示例调用，**对 LLM 判断「该不该委派给它」很有帮助** |
| `inputModes` / `outputModes` | 该技能接受的输入 MIME 类型、产出的 MIME 类型 |

> **机制说明**：`description` 和 `examples` 不是给人看的装饰。当你的编排 Agent 用 LLM 决定「把任务交给谁」时，这些字段会进提示词。写得含糊，委派决策质量就下降。**这是 A2A 生态里一个实际的失败点**——很多人把 Agent Card 当成形式文书写，结果 LLM 判不准该派给谁。

### 签名类——`signatures`（v1.0 新增）

```json
"signatures": [
  { "alg": "ES256", "kid": "acmelegal-2026-04", "signature": "eyJhbGciOi..." }
]
```

## 三、Agent Card 放在哪里（发现的三条路径）

### 路径 1：well-known URI（最标准）

```
https://{对方域名}/.well-known/agent-card.json
```

`/.well-known/` 这个路径约定来自 **RFC 8615**（Well-Known URI）。它的好处是**不需要任何注册中心**——只要知道对方域名，按约定拼出 URL 就能拿到卡。

> **向后兼容**：为兼容 1.0 之前的服务端，`.well-known/agent.json` 也被接受作为回退路径。

### 路径 2：注册中心（Registry）

由第三方集中维护 Agent Card 目录，客户端去查询。Google Cloud 的 Agent Registry 就是这种。

- ✅ 适合「我要在一堆 Agent 里挑一个」的发现场景
- ❌ 引入了一个额外依赖：注册中心挂了发现就废了

### 路径 3：直接配置（静态配置）

在你的代码或配置里直接写死对方的 URL。

- ✅ 适合私有环境、强耦合、对方不对外暴露的场景
- ❌ 违背了「程序化发现」的初衷，但**这是最诚实的选择**——在可控环境里用它比硬套发现机制更简单

## 四、扩展卡：解决「公开 vs 保密」矛盾

这里有个真实的矛盾：

| 需求 | 冲突 |
|------|------|
| Agent Card 要公开可抓取（否则没法发现） | 但里面有些信息**不适合公开** |
| 客户端要看到完整能力 | 但内部端点、内部网络地址属于敏感信息 |

**A2A 的解法**：两段式获取。

| 阶段 | 怎么取 | 内容 |
|------|--------|------|
| 公开卡 | 无认证，直接 GET | 身份、公开技能、支持的能力、鉴权方式 |
| **扩展卡（extended Agent Card）** | **带认证**请求 | 更完整的端点、内部地址、详细描述 |

客户端判断 `capabilities.extendedAgentCard` 为 `true` 时，再发起带认证的请求拉完整版（方法是 `agent/getAuthenticatedExtendedCard`）。

## 五、签名卡：防的是什么攻击

**攻击场景**：一个恶意中间人（代理）拦截了你的发现请求，**返回一张伪造的 Agent Card**——把你的请求、你的合同、你的密钥全都转发到攻击者控制的服务器。卡片内容看起来完全合理，不做校验根本发现不了。

**A2A 的解法**：发卡方对整张卡做**加密签名**，写进 `signatures` 字段。客户端信任签发域的公钥，验证签名通过才继续。

- 算法目前主推 `ES256`（ECDSA + P-256）
- `kid` 标识用的是哪把公钥，方便密钥轮换
- 客户端必须**主动验证**，协议提供能力但不替你决定信任哪把钥匙

---

## 六、陷阱

1. **⚠️ 绝对不要把密钥写进 Agent Card。** 它是公开可抓取的 URL。官方明确建议：用认证扩展卡，或用 mTLS / HTTP Auth 保护，并把静态密钥排除在卡之外。
2. **别把 `version` 当成协议版本。** 版本协商看的是 `protocolVersion` / `supportedInterfaces[].protocolVersion`。
3. **别忽略 `capabilities`。** 对方 `streaming: false` 你还发流式请求，对方会拒。
4. **`skills.description` 不是形式文书。** 编排 Agent 的 LLM 靠它做委派决策，写得含糊会导致派错。
5. **别把内部端点直接写进公开卡。** 用扩展卡。
6. **拿到卡之后要验签。** v1.0 提供了能力，不用等于放弃了防冒名。

---

## 小结

- Agent Card = 机器可读的 OpenAPI 描述，公开在 `/.well-known/agent-card.json`
- `protocolVersion`（协议版本）≠ `version`（产品版本）
- `supportedInterfaces` 按绑定分别给 URL，客户端挑一条能用的
- `capabilities` 三个字段决定你用轮询/流式/推送
- `skills` 是编排 LLM 的决策依据，要认真写
- 扩展卡解决「公开但要保密」的矛盾；签名卡解决「代理冒名」
- **卡是公开的，绝不写密钥**
