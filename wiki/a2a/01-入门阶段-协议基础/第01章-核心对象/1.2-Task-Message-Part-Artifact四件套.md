# Task / Message / Part / Artifact 四件套

## 学习目标

读完本篇，你应当能够：

1. 说清 Task、Message、Part、Artifact 四个对象各自的职责边界
2. 解释 Part 为什么有四种形态，以及**结构化数据为什么必须是一等公民**
3. 区分 Message 和 Artifact——它们什么时候用哪个
4. 说出 `contextId` 解决什么问题
5. 判断什么时候该用 URL 引用文件、什么时候该内联

## 一、四个对象的职责边界

先用一张表把边界划清楚。这一节是本篇的骨架，后面都是细节。

| 对象 | 是什么 | 谁产生 | 生命周期 |
|------|--------|--------|---------|
| **Task** | 一个**有 ID 的工作单元**，有状态机 | 客户端发起，服务端推进 | 从创建到终态，可能几秒到几小时 |
| **Message** | 客户端与服务端之间的**一轮通信** | 双方都能产生 | 一轮，可往返多次 |
| **Part** | **最小内容单元**，内容实际载体 | 双方都能产生 | 依附于 Message 或 Artifact |
| **Artifact** | Task 的**实际交付物** | 服务端产生 | 挂在 Task 上，可以增量推送 |

**一句话区分 Message 和 Artifact：**

> **Message 是「对话」，Artifact 是「交付」。** 对方说「我正在查数据库」是 Message；对方把查出来的结构化数据给你，是 Artifact。

---

## 二、Task：工作的容器

Task 有唯一 ID 和一个状态（`status.state`），这是它和 MCP 工具调用最本质的差别——MCP 的一次工具调用基本是「请求进去、结果出来」，Task 是一个**持续存在的对象**。

关键字段：

| 字段 | 说明 |
|------|------|
| `id` | Task 唯一标识。**后续所有操作都靠它** |
| `contextId` | 归组标识，把相关 Task 和 Message 挂到同一次会话 |
| `status.state` | 8 个状态之一，详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.4-Task生命周期与状态机]] |
| `status.timestamp` | 最后一次状态变化的时间 |
| `artifacts[]` | 产出的交付物 |
| `history[]` | 完整的历史记录（Message 的集合） |
| `metadata` | 自定义键值对 |

```json
{
  "id": "task_123",
  "contextId": "ctx_456",
  "status": { "state": "working", "timestamp": "2026-10-13T10:30:00Z" },
  "artifacts": [],
  "history": [],
  "metadata": {}
}
```

**`history` 值得注意**：它保存了完整对话历史。这意味着**任务可以恢复**——客户端断连后重新连上，带着 Task ID 拉取，就能看到之前发生了什么。这一点和 LangGraph 的 Checkpointer 思路是相通的。

---

## 三、Message：一轮通信

Message 有两个关键属性：

| 属性 | 取值 | 含义 |
|------|------|------|
| `role` | `user` / `agent` | 谁说的 |
| `messageId` | 唯一 ID | 单条消息标识 |
| `parts[]` | 一个或多个 | 内容装在 Part 里 |

```json
{
  "messageId": "msg_789",
  "role": "user",
  "parts": [
    { "type": "text", "text": "请审查这份 SaaS 采购合同" },
    { "type": "file", "url": "https://example.com/contract.pdf", "mimeType": "application/pdf" }
  ],
  "taskId": "task_123",
  "contextId": "ctx_456"
}
```

⚠️ **注意 `role` 是双方对称的**——不只是客户端说话，服务端也会用 `role: "agent"` 发 Message。这是 A2A 能做到「远端中途反问你」的基础：服务端在 `input-required` 状态下发的就是一条 `role: "agent"` 的 Message。

**Message 与 Artifact 的分工**，看一个例子：

```
history 里（Message）：
  user:   "请审查这份合同，重点看责任条款"
  agent:  "好的，正在解析 200 页 PDF"
  agent:  "解析完成，发现 3 处异常，需要你确认第 47 页的赔偿上限"
  user:   "以 3 倍赔偿为准"
artifacts 里（Artifact）：
  完整的审查报告 JSON + 标记后的合同 PDF
```

前者是过程，后者是结论。

## 四、Part：四种形态

Part 是一个「容器」，用 `oneof` 语义——**一个 Part 里只能装其中一种**：

| 形态 | 字段 | 用途 |
|------|------|------|
| 纯文本 | `text` | 文本 / Markdown |
| 内联文件 | `bytes`（base64 编码的字节） | 小文件直接塞进报文 |
| 文件引用 | `url` + `mimeType` | 大文件给 URL |
| **结构化数据** | `data`（任意 JSON 值） | **机器可读的数据** |

每个 Part 还可以带：

| 附加字段 | 说明 |
|---------|------|
| `mediaType` | MIME 类型，如 `text/plain`、`image/png`、`application/json` |
| `filename` | 文件名或内容名 |
| `metadata` | 额外上下文的键值对 |

### 为什么「结构化数据」必须是一等公民

这一点是 A2A 设计和「普通聊天协议」拉开差距的关键。

假设你的编排 Agent 派了个任务给「数据分析 Agent」，对方查完库返回结果。两种可能：

| 返回方式 | 你的编排 Agent 收到后 |
|---------|---------------------|
| ❌ 一段自然语言 | 得再调一次 LLM 去解析这段话，提取出数字。慢、贵、有解析错误 |
| ✅ `data` 里的 JSON | 直接 `json.loads` 拿到结构化结果，接着往下编排 |

**这就是 `Part.data` 存在的意义：让 A2A 的返回值可以程序化消费，而不必经过 LLM 转一道手。**

> 📐 **记忆锚点**：这个设计与 LangChain 里的 `structured_output` / `with_structured_output` 是同一个诉求——把「让 LLM 输出可解析结构」这件事从提示词工程变成协议保证。A2A 是把它标准化到了协议层。

### 文件该内联还是给 URL

| 做法 | 何时用 |
|------|--------|
| `url` 引用 | ✅ **默认选这个**。文件可能较大、或本来就放在对象存储/网盘上 |
| `bytes` 内联 | 只在小文件（几十 KB 量级）、且不想额外搞存储时用 |

⚠️ 内联会把文件整个 base64 编码塞进 JSON 报文——**体积膨胀约 1/3**，而且大报文会让很多网关直接拒收。跨网络传文件一律优先 URL。

## 五、Artifact：交付物

Artifact 是 Task 的产出，结构上就是「带 ID 和名字的 Part 集合」：

```json
{
  "artifactId": "art_001",
  "name": "合同审查报告",
  "description": "含 3 处异常条款标记与风险评级",
  "parts": [
    { "type": "data", "data": { "riskLevel": "high", "findings": [ ... ] } },
    { "type": "file", "url": "https://example.com/reviewed.pdf", "mimeType": "application/pdf" }
  ]
}
```

| 字段 | 说明 |
|------|------|
| `artifactId` | 产物唯一 ID |
| `name` | 人读的名字 |
| `parts[]` | 产物内容，一个或多个 Part |
| `description` | 可选的详细说明 |

**Artifact 可以被流式增量推送**——服务端可以先推第一部分，改进了再推第二部分。客户端能边收边用。

## 六、contextId：把多次任务串成一次会话

```
ctx_789（一次业务会话）
  ├── task_a1b2  "查一下张三的年假余额"
  ├── task_c3d4  "顺便订下周的会议室"
  └── task_e5f6  "把结果汇总成周报"
```

**没有 contextId 会怎样？** 三个 Task 互相不知道是同一个人同一段时间的事。服务端就无法把「张三已经说过他的偏好是安静楼层」这条上下文带给第二个 Task。

`contextId` 是**服务端生成**的（不是客户端指定），这和 LangGraph 里 `thread_id` 通常由客户端持有不同——A2A 里客户端的作用是「拿到并复用它」。

## 七、四件套的完整关系图

```
Client                                          Remote Agent
  │                                                │
  │  ① 读 Agent Card（发现）                        │
  │  ───────────────────────────────────────────►  │
  │                                                │
  │  ② 发 Message（含 1..N 个 Part）创建 Task        │
  │  ───────────────────────────────────────────►  │
  │                            ③ 返回 Task{id,       │
  │                               status: submitted} │
  │  ◄───────────────────────────────────────────  │
  │                                                │
  │  ④ 轮询 / 订阅流 / 等推送                        │
  │  ◄───────────────────────────────────────────  │
  │                                                │
  │  ⑤ 拿 Task.artifacts[]（每个由 Part 组成）        │
  │  ◄───────────────────────────────────────────  │
  │                                                │
  │  ⑥（可选）补信息：发新 Message，同一个 taskId    │
  │  ───────────────────────────────────────────►  │
  │                                                │
    全程通过 contextId 归组
```

## 八、陷阱

1. **别把所有内容都塞进 text。** 结构化数据用 `data`，否则下游还得再过一道 LLM。
2. **别混淆 Message 和 Artifact。** 过程性内容进 Message（history），结论性交付进 Artifact。
3. **别用内联 `bytes` 传大文件。** base64 膨胀 + 网关拒收，用 `url`。
4. **`contextId` 是服务端生成的。** 客户端要保存并在后续交互中复用它，不要自己造一个。
5. **别以为 `role` 只有 `user`。** 服务端也会发 `role: "agent"` 的 Message，反问就是这么实现的。
6. **别忽略 `history`。** 它是任务恢复的依据，客户端断连重连后靠它补齐上下文。

---

## 小结

- Task = 有 ID 的工作单元（容器）；Message = 一轮对话；Part = 内容单元；Artifact = 交付物
- **Message 是过程，Artifact 是结论**
- Part 四形态：text / 内联 bytes / url 引用 / **data（结构化）**
- `data` 是一等公民，让返回值可程序化消费，不必过 LLM
- `contextId` 把多个 Task 归为一次会话，由服务端生成
- `history` 是任务恢复的依据
