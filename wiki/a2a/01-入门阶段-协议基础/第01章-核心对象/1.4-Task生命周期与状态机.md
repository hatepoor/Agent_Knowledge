## 一、状态清单（先背下来）

### 非终态（4 个）——还可以继续流转

| 状态 | 含义 | 客户端该做什么 |
|------|------|--------------|
| `submitted` | 服务端已接收任务，但还没开始处理 | 等待或开始观察 |
| `working` | 正在处理 | 等待 / 订阅流 / 等推送 |
| `input-required` | **缺少信息，需要调用方补充** | 发新 Message 补齐信息 |
| `auth-required` | **鉴权失效，需要重新认证** | 取新 token 后重试 |

### 终态（4 个）——不可再变

| 状态 | 含义 | 发生时机 |
|------|------|---------|
| `completed` | 成功完成，Artifact 已挂载 | 正常结束 |
| `failed` | **处理中途出错**终止 | 已经开始处理，途中失败 |
| `canceled` | 客户端主动取消 | 客户端调用取消 |
| `rejected` | **服务端在开始处理前就拒绝** | 策略不允许 / 不支持该技能 / 限流 |

⚠️ **终态不可再变，重试必须新建 Task。** 不存在「把 `failed` 改回 `working`」这种操作。

```
                        └────────┬─────────┘
                                 │
                                 ▼

        │                    │ working  │◄─────┐
        │                    └────┬─────┘      │
        │                         │            │

        │        ▼                ▼       │    │

   └─────────┘       └─────────┘       └──────────┘    │ rejected │
                                                       └──────────┘
```

## 三、逐状态详解

### `submitted`（非终态）

任务已创建，服务端已经收到，但**还没开始执行**。

**这个状态很短**，大多数实现里你几乎看不到它——但它的存在有实际意义：客户端能区分「对方收到了」和「对方还没收到」。网络抖动导致消息丢失时，这个状态能帮你判断。

### `working`（非终态）

正在处理。**这是长任务停留时间最长的状态。**

客户端在这一阶段能拿到：
- 中间进度（如果用了流式）
- 已产出的 Artifact 部分（如果支持增量推送）

### `input-required`（非终态）★

**这是 A2A 最有价值的状态之一，也是最容易被忽略的。**

它让远端 Agent 具备「执行到一半停下来反问」的能力——而这恰恰是 Agent 与普通函数调用的本质区别。普通函数要么能算出来，要么报错；Agent 会说「我需要更多信息才能继续」。

**真实场景**：

```
client → remote:  "帮我审查这份合同"
remote:  submitted → working
remote:  input-required + Message(role=agent):
          "合同第 47 页的赔偿上限被涂改了，我读到两个不同数字。
           请确认以哪个为准？"
          ← 客户端在这里补充信息，或转问人类用户
client → remote:  新 Message: "以 3 倍年费为准"
remote:  working → completed + Artifact
```

⚠️ **实现服务端时的关键点**：`input-required` 状态下必须能继续接收客户端的 Message，且这些 Message 要挂到**同一个 `taskId`** 上。如果你的实现里每个 Message 都新建一个 Task，这个状态就废了。

### `auth-required`（非终态）

需要客户端重新认证。典型触发：

- token 过期
- 权限范围不够，需要更大的 scope
- 客户端换了凭证，服务端要求重新绑定

**处理方式**：客户端取新凭证后在同一个 Task 上重试。

### `completed`（终态）

成功完成，`artifacts[]` 里挂满了产出。这是唯一「成功」的终态。

### `failed`（终态）

**处理中途出错。** 比如：
- 内部异常（数据库连不上）
- LLM 调用超时
- 处理到一半发现输入数据非法

### `canceled`（终态）

客户端主动取消，通常是调 `tasks/cancel` 的结果。

### `rejected`（终态）★

**服务端在开始处理之前就拒绝了。** 原因通常是：

| 原因 | 例子 |
|------|------|
| 策略不允许 | 该 Agent 不允许处理涉密合同 |
| 不支持该技能 | Agent Card 里声明的能力不覆盖这个需求 |
| 限流 | 超过 QPS 限制 |

## 四、`failed` 与 `rejected` 的关键区别

**这是本篇最值得单独拿出来的一节。**

| 维度 | `rejected` | `failed` |
|------|-----------|---------|
| 时机 | **开始处理之前** | 处理过程之中 |
| 原因 | 策略 / 不支持 / 限流 | 技术错误 / 执行异常 |
| 有没有副作用 | 无，一次都没跑 | 可能跑了一半，数据可能已被部分修改 |
| 重试价值 | **低**。同样的请求还会被拒 | **高**。可能是偶发故障 |

**对应的客户端策略**：

```
收到 rejected：
  → 别急着重试。先读懂原因（有的会带说明）
  → 如果是「不支持该技能」→ 换一个 Agent
  → 如果是「限流」→ 退避后重试
  → 如果是「策略不允许」→ 找人工，或走别的流程

收到 failed：
  → 检查是不是可重试的瞬时故障（超时、限流、5xx）
  → 是 → 退避重试（新建 Task）
  → 否 → 报错，排查
```

⚠️ **面试高频题**：「`rejected` 和 `failed` 有什么区别？」答不出来会显得只读了文档没想清楚。答案是：**一个是「我不接」，一个是「我接了但没办成」。**

## 五、观察状态变化的三种方式

同一个 Task 可以同时用三种方式观察：

| 方式 | 方法 | 说明 |
|------|------|------|
| 轮询 | `tasks/get` | 最简单 |
| 订阅流 | `tasks/subscribe` | 交互式 UI 的默认 |
| 推送 | 注册 webhook 后服务端主动 POST | 长任务 / 断连 |

⚠️ **一个 Task 可以有多个观察者同时在观察。** 你可以让一个监控组件轮询、同时 UI 在订阅流，两者互不干扰。

详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.3-三种交互机制与协议绑定]]。

## 六、终态不可复活的含义

**规则**：Task 一旦进入终态，**永不再次变化**。重试必须新建一个 Task。

**为什么这样设计？** 三个理由：

1. **审计清晰**：Task 状态历史就是一份不可篡改的执行记录。如果能复活，审计线索就断了。
2. **幂等性安全**：新建 Task 意味着「一次全新的尝试」，语义明确。如果复活旧 Task，你搞不清重试和恢复的区别。
3. **并发安全**：不会有客户端 A 正在改状态、客户端 B 也在改的竞争问题。

**对客户端的影响**：

```python
# ❌ 错误：试图复用终态 Task
if task.status.state == "failed":
    task.status.state = "submitted"   # 客户端改不了，这是服务端的领域

# ✅ 正确：新建 Task 重试
new_task = client.send_message(new_message)
```

⚠️ **注意「终态」是服务端的领域规则，不是客户端能改的字段。** 客户端只能读，不能写状态。

## 七、与 LangGraph 的对应关系

你已经学过 LangGraph，这里做个对照，能帮你更牢固地记住：

| A2A | LangGraph | 说明 |
|-----|-----------|------|
| Task | 一次 `invoke` / `astream` 调用产生的执行 | 都是一次工作的容器 |
| `status.state` | 图执行到哪个节点 / 是否 `interrupt` | 进度表示 |
| `input-required` | **`interrupt()` + `Command(resume=...)`** | **几乎完全对应**：执行中暂停等外部输入 |
| `auth-required` | 无直接对应 | LangGraph 不管鉴权 |
| `contextId` | `thread_id` | 会话标识 |
| `history` | Checkpointer 存的 checkpoint | 可恢复 |
| `completed` / `failed` | 正常结束 / 抛异常 | 终态 |
| `canceled` | 外部中止 | 取消 |
| `rejected` | **无对应** | LangGraph 是本地调用，不存在「拒绝受理」 |

> 📐 **这行对照是本篇最有价值的一张表。** `input-required` ≈ `interrupt()` 这个类比，能让你把 A2A 的设计意图和你已掌握的 LangGraph 机制焊在一起。

## 八、陷阱

1. **❌ 混淆 `failed` 和 `rejected`。** 前者是办砸了，后者是不接。
2. **❌ 在终态 Task 上继续发消息期待复活。** 必须新建 Task。
3. **❌ 实现服务端时把 `input-required` 做成死胡同。** 状态变了但收不到后续 Message，任务就卡死了。
4. **❌ 把 4 个中断态和非终态混为一谈。** 只有 `submitted`/`working`/`input-required`/`auth-required` 是非终态。
5. **❌ 客户端主动改 `status.state`。** 这是服务端领域，客户端只读。
6. **❌ 收到 `rejected` 立即无脑重试。** 策略性拒绝重试多少次都会被拒。

---

## 小结

- 8 个状态：4 个非终态（submitted / working / input-required / auth-required）+ 4 个终态（completed / failed / canceled / rejected）
- `input-required` ≈ LangGraph 的 `interrupt()`，让远端能反问
- `auth-required` 处理凭证过期
- **终态不可复活，重试必须新建 Task**
- **`rejected` = 开始前拒绝（策略/不支持/限流）；`failed` = 处理中出错。** 一个是「我不接」，一个是「我接了没办成」
- 观察方式三种：轮询 / 订阅流 / 推送，可同时用
