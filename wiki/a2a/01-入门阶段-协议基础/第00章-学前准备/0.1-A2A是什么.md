# A2A 是什么

## 学习目标

读完本篇，你应当能够：

1. 用一句话说清 A2A 是什么
2. 说出 A2A 和 MCP 的位置关系（谁管 agent→tool，谁管 agent→agent）
3. 复述官方明确列出的「A2A **不是**什么」四条
4. 判断自己手上的项目现在需不需要 A2A

## 前置知识

| 前置 | 为什么需要 |
|------|-----------|
| 无 | 本篇是零基础起点，**不要求任何前置知识** |

> 本篇只需知道「Agent」大致指一个会自己调用工具完成任务的 AI 程序。不了解也不影响往下读。

---

## 一、一句话定义

> **A2A（Agent2Agent Protocol，智能体对智能体协议）是一套让不同公司、不同框架、不同作者写的 AI 智能体互相「发现彼此、委派任务、交换结果」的开放通信标准。**

把这句拆成四段来理解：

| 词 | 含义 |
|----|------|
| **开放标准** | 公开的规范 + 公开的 SDK，任何人可以实现，不属于任何一家公司 |
| **发现彼此** | 一个 Agent 能读出另一个 Agent「我能干什么、怎么找我」 |
| **委派任务** | 我把一件完整的工作交给你去办，而不是调你一个函数 |
| **交换结果** | 办完之后，结果能以结构化的方式回到我这边 |

**「委派任务」和「调函数」的差别，就是 A2A 存在的全部理由。** 后面 [[a2a/01-入门阶段-协议基础/第00章-学前准备/0.2-为什么需要A2A|0.2 为什么需要 A2A]] 会把这个差别展开讲。

---

## 二、核心心智模型：纵向与横向

如果你只记一句话，记这句：

> **MCP 让智能体拿到工具（纵向变强），A2A 让智能体找到同行（横向变广）。**

用你熟悉的场景类比：

| | MCP | A2A |
|---|---|---|
| 类比 | **USB-C** | **HTTP** |
| 解决 | 设备怎么连上配件 | 不同厂商的电脑怎么互相通信 |
| 方向 | 纵向：Agent → 工具/数据 | 横向：Agent → Agent |
| 结果 | 这个 Agent 会做的事变多了 | 这个系统能触达的范围变广了 |

### 一个具体例子

假设你做了一个**差旅审批 Agent**（你自己写的，跑在你的服务器上）。现在你要接三家的订票能力：

```
只有 MCP 时（全部纵向）：
  差旅审批 Agent
      ├──MCP── 你的数据库（查员工信息）
      ├──MCP── 你的 HR 系统（查预算）
      └──MCP── 一个你自己封装的「订票工具」← 里面写死了对接哪一家

加上 A2A 后（纵向 + 横向）：
  差旅审批 Agent
      ├──MCP── 你的数据库
      ├──MCP── 你的 HR 系统
      ├──A2A── 供应商甲的订票 Agent（对方自己部署）
      ├──A2A── 供应商乙的订票 Agent（对方自己部署）
      └──A2A── 供应商丙的订票 Agent（对方自己部署）
```

关键在于：**供应商换了，你不用改代码。** 你只需要读对方公开的 Agent Card，就知道它提供哪些订票能力、需要什么格式的输入、怎么鉴权。

## 三、官方明确的「A2A **不是**什么」

这几条是最容易被误解的，逐条说清。

### 不是 Agent 开发框架

| | 说明 |
|---|---|
| **是框架的** | LangGraph、CrewAI、Google ADK——用它们**写** Agent |
| **是协议的** | A2A——让**已经写好的** Agent 之间通信 |

A2A 是通信层，不是开发工具。你依然要用 LangGraph 或 ADK 写你的 Agent，然后在出口处按 A2A 规范暴露接口。

### 不是子 Agent 调用协议

你的 Agent 内部有 3 个子 Agent，它们之间怎么传数据——**A2A 完全不管**。用 LangGraph 的 `Send`、用 `Command`、用 Python 函数调用，都行。

> 详见 [[a2a/02-中段阶段-生产实践/05-与LangGraph多智能体的关系]]。

### 不是 MCP 的替代品

这是最常见的误解。MCP 和 A2A 解决的是**两个不同的问题**：

| 问题 | 用什么 |
|------|-------|
| 我的 Agent 怎么查数据库、调搜索、调自己的内部 API？ | **MCP** |
| 我的 Agent 怎么把一整件事交给另一个公司的 Agent 办？ | **A2A** |

真实生产系统里**两个同时用**，各管一层。

### 不是聊天应用

不是 Slack、不是微信、不是 Discord。A2A 是**机器对机器**的协议——不给人发消息，不需要界面，双方都是程序。

## 四、A2A 侧重的四个能力

官方的目标是让 Agent 能够做到这四件事，缺一不可：

| 能力 | 含义 | 对应机制 |
|------|------|---------|
| **发现（Discovery）** | 知道对方是谁、能干什么、怎么联系 | Agent Card，详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.1-AgentCard与智能体发现]] |
| **协商（Negotiation）** | 双方对齐内容格式、交互方式 | `supportedInterfaces` 声明绑定，`skills` 声明输入输出模态 |
| **任务管理** | 长任务能跟踪、能取消、能知道进度 | Task 对象与状态机，详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.4-Task生命周期与状态机]] |
| **不透明协作** | 协作但不暴露内部状态、记忆、工具 | 协议只定义契约，不定义实现 |

**第四点值得单独强调**：A2A 的设计目标是「能看到对方的声明，看不到对方的内部」。这正是它能跨公司使用的原因——你不用把 Agent 的提示词、记忆、工具清单交出去。

## 五、你现在的项目需要 A2A 吗

⚠️ **大概率不需要。** 这句话必须放在最前面说，否则容易被协议的新鲜感带偏。

判断标准只有一条：**被调用的 Agent 在不在你的代码库里？**

| 情况 | 需要 A2A 吗 | 说明 |
|------|------------|------|
| 所有 Agent 都在你的进程里 / 你的仓库里 | **不需要** | 传任务就是一次 Python 函数调用，套协议是纯开销 |
| 你在用 LangGraph 扇出、DeepAgents 子 Agent | **不需要** | 同上，这是进程内编排 |
| 要调用**别人写的、别人托管的** Agent | **需要** | 这时你改不了对方，只能按契约对接 |
| 要把自己做的 Agent **暴露给**外部系统调用 | **需要** | 你需要一个标准入口，而不是让对方来读你的内部代码 |

**对于「终端交互多智能体 Agent」这类同一代码库内的系统，A2A 帮不上忙。** 你的 Sub Agent 同步函数调用比走一次 HTTP 快几个数量级，还不用管鉴权、重试、超时。

那为什么还要学它？

1. **面试与架构视野**：这是当前 Agent 领域最重要的两个协议之一，能讲清 A2A vs MCP 是有区分度的。
2. **未来的架构边界**：如果你的系统要从「单体多 Agent」演进到「多团队各建各的 Agent」，A2A 就是那道边界。
3. **成本极低的练手**：用 `a2a-sdk` 在本地起两个进程互相调用，半天就能跑通，不污染现有架构。详见 [[a2a/01-入门阶段-协议基础/第02章-工程实践/2.1-Python-SDK最小可用实现]]。

## 六、陷阱

1. **别把 A2A 当成「更高级的 MCP」而替换掉 MCP。** 两者层次不同，混用会导致工具层和协作层职责混乱。
2. **别在自己的代码库内部套 A2A。** 多一跳网络、多一套鉴权、多一层状态机，换来的是延迟和故障点，收益为零。
3. **别以为 A2A 规定了智能体「怎么思考」。** 它只管通信。对方的 Agent 用 ReAct 还是 Plan-and-Execute，A2A 不关心也不该关心。
4. **别在 Agent Card 里写密钥。** 它是公开可抓取的 URL，详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.1-AgentCard与智能体发现]]。
5. **别照着 v0.3 的教程写新代码。** v1.0 有破坏性变更，见 [[a2a/02-中段阶段-生产实践/02-版本演进与迁移陷阱]]。

---

## 小结

- A2A = 让独立智能体互相发现、委派、交换结果的开放标准
- 心智模型：MCP 是纵向的 USB-C，A2A 是横向的 HTTP
- 官方四条边界：不是框架、不是子 Agent 协议、不替代 MCP、不是聊天应用
- 四个能力：发现、协商、任务管理、不透明协作
- **你的多智能体项目大概率不需要它**——这是本文最重要的一句

3. 判断：你的终端多智能体 Agent 的 Sub Agent 之间要不要走 A2A？为什么？
