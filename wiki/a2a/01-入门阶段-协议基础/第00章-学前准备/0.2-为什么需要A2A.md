# 为什么需要 A2A

## 学习目标

读完本篇，你应当能够：

1. 说清 A2A 解决的四类具体困境，每类给出真实场景
2. 理解 N×(N-1)/2 这个集成爆炸公式的含义
3. 解释为什么 MCP **解不了**这四类困境
4. 理解 A2A 的 HTTP 类比在什么时候成立、什么时候不成立

## 一、起点：没有协议之前会发生什么

先看一个真实会遇到的场景。

你在做**企业采购系统**。业务流程里天然有几个专业角色：

| 角色 | 干什么 | 谁写的 |
|------|--------|--------|
| 采购编排 Agent | 决定询价几家、比价、下单 | **你** |
| 供应商 A 的报价 Agent | 报这个零件的价格和交期 | **供应商 A** |
| 财务 Agent | 审核预算够不够、走不走审批 | **公司财务部门** |
| 物流 Agent | 估算到货时间和运费 | **第三方服务商** |

现在问题来了：**这四个 Agent 分属四家，怎么通信？**

### 没有标准协议时的做法

只能一家一家对接，每家都可能不一样：

| 供应商 | 怎么调的 |
|--------|---------|
| 供应商 A | 提供 REST API，字段名叫 `unitPrice` |
| 供应商 B | 提供 SOAP 接口，字段名叫 `PricePerUnit`，还要带签名 |
| 财务 Agent | 是个内部服务，只监听消息队列，消息格式是自定义的 protobuf |
| 物流 Agent | 只提供 gRPC，方法名叫 `EstimateDelivery` |

于是你的代码里变成这样：

```python
def query_supplier_a(part_id):  # REST + JSON
    ...

def query_supplier_b(part_id):  # SOAP + XML + 签名校验
    ...

def query_finance(part_id):    # 消息队列 + protobuf
    ...

def query_logistics(part_id):  # gRPC
    ...
```

**问题不在于这四个函数能不能跑通，而在于规模。** 下文第二节会算这笔账。

## 二、四类困境

### 困境 1：集成爆炸（N×(N-1)/2）

**公式含义**：N 个 Agent 之间两两互通的连接数。N=2 时 1 条，N=5 时 10 条，N=10 时 45 条。

在你的采购系统里，如果每加一个新 Agent 都要跟已有的每个都写一遍对接：

| Agent 数量 | 需要维护的对接 |
|-----------|---------------|
| 2 | 1 |
| 5 | 10 |
| 10 | 45 |
| 20 | **190** |

而 MCP **完全不解决**这个问题——MCP 是「Agent→工具」，而这里需要的是「Agent→Agent」，方向就不对。

> 📐 **记忆锚点**：HTTP 出来之前，不同学校的计算机网络之间连数据很困难。A2A 官方的类比正是如此——**HTTP 给了 Web 一套共同语言，A2A 想给 Agent 协作层一套共同语言。**

### 困境 2：长任务无法跟踪

真实的 Agent 任务耗时经常不是「秒」，而是「分钟到小时」：

- 合同审查 Agent：扫描 200 页合同并交叉引用，20 分钟
- 供应链 Agent：等三个供应商回复，2 小时
- 报告生成 Agent：跑 30 次工具调用，15 分钟

用普通 HTTP 请求处理这类任务会遇到三个问题：

| 问题 | 表现 |
|------|------|
| 连接挂太久 | 网关超时断开，服务端还在跑，结果丢了 |
| 不知道进度 | 客户端只看到一个 pending 请求，不知道对方干到哪了 |
| 断连后无解 | 客户端崩了重连，之前那个任务的结果再也拿不到 |

**A2A 的解法**：任务不是「一个请求」，而是「一个有 ID 的对象」（Task）。

- 客户端拿到 Task ID，之后随时能查状态
- 状态是结构化的（`working` / `completed` / …），不是「还在转圈」
- 可以**流式**接收增量结果，也可以**注册 webhook** 让服务端主动推
- 客户端挂了也没关系，任务服务端继续跑，好了推给你

### 困境 3：能力无法程序化发现

你现在接供应商 A 时，接入文档是一份 40 页的 PDF。你读完知道它能做报价。

**问题来了**：
- 半年后供应商 A 升级，新增了 5 个能力，你**怎么知道**？文档不会主动通知你。
- 你想做个「自动挑选最合适供应商」的 Agent，**程序怎么判断谁更合适**？靠文档？
- 客服问「B 家支持退货吗」，系统**怎么自动回答**？人工查文档？

**A2A 的解法**：每个 Agent 暴露一张 **Agent Card**，一个放在固定 URL 上的 JSON 文件，写清楚：我叫什么、我提供哪些技能、每项技能接受什么格式、产出什么格式、怎么鉴权。

程序读 JSON 比读 PDF 可靠得多。详见 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.1-AgentCard与智能体发现]]。

### 困境 4：跨组织鉴权各不相同

供应商 A 用 API Key，供应商 B 用 OAuth 2.0 客户端凭证，财务部门用内部 SSO 令牌，物流服务商用双向 TLS。

**每家的鉴权方式都不一样，而且都会变。** 如果这些逻辑写死在你的编排 Agent 里，任何一家改方案你都得改代码。

**A2A 的解法**：Agent 在自己的 Agent Card 里**声明**它接受哪些鉴权方案（`securitySchemes` 字段），你的编排逻辑按声明适配，而不是按硬编码。

⚠️ 注意边界：**A2A 规定了凭证「怎么传」（走 HTTP 头，与 A2A 报文分离），但不规定「授权策略怎么定」**——后者由各 Agent 自己决定，协议不强制。详见 [[a2a/02-中段阶段-生产实践/01-安全模型与鉴权]]。

## 三、四类困境的对照总表

| 困境 | 没有协议时 | MCP 能解吗 | A2A 的机制 |
|------|-----------|-----------|-----------|
| 集成爆炸 | N×(N-1)/2 份定制代码 | ❌ 方向不对 | 统一的发现与调用契约 |
| 长任务跟踪 | HTTP 长连接，容易超时 | ❌ 工具调用基本无状态 | Task 对象 + 状态机 + 流式/推送 |
| 能力发现 | 读 PDF 文档，人工判断 | ❌ MCP 的 tool 列表只对自己生效 | Agent Card（JSON，含 skills） |
| 跨组织鉴权 | 各家一套，写死 | ⚠️ 部分缓解但无跨组织概念 | Agent Card 声明 `securitySchemes` |

**结论很清楚：MCP 和 A2A 不是重叠关系，是拼图的两块。**

## 四、A2A 的设计取舍

一个协议要在跨组织场景落地，必须做取舍。A2A 明确选了「不透明」这一侧：

| A2A 允许你看到的 | A2A 刻意不让你看到的 |
|----------------|------------------|
| Agent 的身份、声明的技能 | Agent 的提示词 |
| 接受的输入格式、产出的格式 | Agent 的内部记忆 |
| 服务端点、支持的绑定方式 | Agent 内部用了哪些工具 |
| 鉴权方式 | Agent 的推理过程 |

**为什么这样设计？** 因为跨公司协作时，暴露内部实现意味着泄露商业机密。

**代价是什么？** 你**无法验证**对方的行为是否符合你的预期，也无法直接把对方 Agent 的内部能力复用到自己的系统里。这是「安全」与「可控」之间的交换，A2A 选了安全。

> 这也是为什么 A2A 更像「打电话给一家外部服务商」——你能下单、能查进度，但看不到他们内部怎么干活。这和 MCP 完全不同：MCP 把工具的 schema 全部公开给你看，因为工具本来就是你自己的东西。

## 五、陷阱

1. **别用 A2A 解决「集成爆炸」却不检查规模。** N=3 时 3 条对接完全可控，硬套协议是浪费。
2. **别以为 A2A 能让长任务变快。** 它解决的是「能不能跟踪」，不是「执行效率」。
3. **别指望 A2A 帮你做鉴权策略。** 它只定义凭证怎么传、必须走加密传输，**授权模型由各 Agent 自定**。
4. **别把「不透明」误解为「不透明所以更安全，不用做授权检查」**。官方要求服务端在**每个操作**上检查授权，并把结果限制在调用方有权看到的范围内——这条在你的服务端实现时必须做。
5. **别用 MCP 去接「另一个 Agent」。** 如果对方是个会推理的 Agent 而不是确定性的函数，MCP 表达不了它的有状态、多轮、需要澄清的行为。

---

## 小结

- 四类困境：集成爆炸、长任务无法跟踪、能力无法程序化发现、跨组织鉴权各异
- 核心创新：**Task 是有 ID 的对象**，不是一次 HTTP 请求
- 核心契约：**Agent Card 是 JSON**，不是 PDF 文档
- 设计取舍：为了跨组织安全，选择「不透明」，代价是失去对对方的内部控制
- MCP 一类都解不了，因为它方向是纵向的
