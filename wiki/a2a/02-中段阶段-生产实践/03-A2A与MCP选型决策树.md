# A2A 与 MCP 选型决策树

> **什么时候该读**：要做技术选型——某个需求该用 MCP、A2A、还是普通 REST API。
> 本篇是决策工具，**不需要读完整个知识库**，但先读过 [[a2a/01-入门阶段-协议基础/第01章-核心对象/1.4-Task生命周期与状态机]] 会更好判断。

---

## 一、核心判定规则（记住这一条就够 80%）

> **如果被调用方是个「你完全可以写成 REST 端点的函数」，用 MCP。**
> **如果被调用方会自己推理、规划、并且可能再调别的工具或 Agent，用 A2A。**

展开成可判断的特征：

| 特征 | MCP 侧 | A2A 侧 |
|------|--------|---------|
| 输入输出 | 结构固定、可枚举 | 每次任务都可能不一样 |
| 执行方式 | 确定性、无状态 | 多步推理、有状态 |
| 需要澄清 | 不会问你 | 可能中途反问（`input-required`） |
| 会调别的工具吗 | 不会 | 可能自己就是一个编排器 |
| 跑多久 | 毫秒到秒 | 秒到小时 |
| 对方是谁 | 你自己的服务/工具 | 别人写的、别人托管的 |

**举例对照**：

| 被调用方 | 结论 |
|---------|------|
| PostgreSQL 查询执行器 | **MCP**（确定性函数） |
| 一个 REST 端点 | **MCP** |
| 天气查询 API | **MCP** |
| 合同审查 Agent | **A2A**（会推理，要读 200 页交叉比对，可能反问） |
| 差旅审批 Agent | **A2A** |
| 一个「帮我调研 X 主题并出报告」的 Agent | **A2A**（多步、调多个工具、耗时长） |

## 二、决策树

```
被调用方是什么？
│
├─ 是我自己代码里的一个函数/类
│  └→ ❌ 都不用，直接调用。加协议是纯开销
│
├─ 是一个确定性的服务（查数据库、算数值、调 API）
│  │
│  ├─ 我自己的服务    → ✅ MCP
│  └─ 别人的服务
│     ├─ 对方提供 MCP server → ✅ 用 MCP
│     ├─ 只有 REST/gRPC    → ⚠️ 直接调 REST。对方不提供 MCP 就别硬套 A2A
│     └─ 只有网页/人工     → ❌ 不适合做集成
│
└─ 是一个会自己推理的 Agent
   │
   ├─ 在我的代码库里 / 我能改它的代码
   │  └→ ❌ 都不用。进程内调用（LangGraph 的 Send / 子 Agent 工具）
   │
   └─ 别人写的、别人托管的
      ├─ 对方提供 A2A 端点        → ✅ 用 A2A
      ├─ 对方提供 MCP server       → ⚠️ 优先 MCP（更轻）。见第五节
      ├─ 对方只有私有 API          → ⚠️ 见第六节「折中方案」
      └─ 对方什么都没有           → ❌ 只能人工介入
```

## 三、官方文档的对照表

| 维度 | MCP | A2A |
|------|-----|-----|
| **连接方向** | 纵向：agent → tool | 横向：agent → agent |
| **工作单位** | Tool Call，基本无状态 | **Task，有状态、有生命周期** |
| **对方暴露什么** | tools / resources / prompts，**schema 全部公开** | 只有契约，**内部状态、记忆、工具不可见** |
| **典型范围** | 一个 Agent 或一个团队内部 | 跨团队、跨厂商、跨云 |
| **交互模型** | client → tool，方向固定 | client ↔ server，**角色对等** |
| **传输** | stdio（本地子进程）/ Streamable HTTP（远程） | JSON-RPC 2.0 / gRPC / HTTP+JSON |
| **能否反问** | 不能 | 能（`input-required`） |
| **能否流式** | 可以 | 可以（SSE） |
| **能否推送** | 取决于实现 | 原生（webhook） |
| **复杂度** | 较低 | 较高（状态机、鉴权、持久化） |

---

## 四、决策维度打分表

拿不准的时候，逐项打分。**分高的那一边。**

| 维度 | 倾向 MCP | 倾向 A2A |
|------|---------|---------|
| 被调用方是否会推理/规划 | 否 | ✅ 是 |
| 是否需要对方反问澄清 | 不需要 | ✅ 可能需要 |
| 任务是否可能跑超过 1 分钟 | 不会 | ✅ 可能会 |
| 是否需要跟踪任务状态 | 不需要 | ✅ 需要 |
| 对方是否在我代码库里 | — | 在 → 都不用 |
| 是否跨组织/跨厂商 | 同组织 | ✅ 跨组织 |
| 对方内部实现是否需要保密 | 无所谓 | ✅ 需要保密 |
| 我需要读懂对方的能力清单 | ✅ tool schema | skills |
| 接入成本敏感度 | 高（要轻） | 可以接受重 |
| 生态成熟度 | ✅ 压倒性成熟（92:1 下载量） | 较新 |

**经验规则**：只要有**任意一项**倾向 A2A 且打分 ≥ 2，就用 A2A；否则用 MCP 或直接调用。

## 五、混合架构：官方给的例子

真实系统里两个是并存的。官方用「汽车修理厂」举例：

```
用户（人或用户的助手 Agent）
  │  A2A
  ▼
车间经理 Agent（Shop Manager）
  │  A2A（派活）
  ▼
机械师 Agent（Mechanic）
  │  MCP（用工具）
  ├─▶ 车辆诊断扫描仪   scan_vehicle_for_error_codes(vehicle_id='XYZ123')
  ├─▶ 维修手册数据库   get_repair_procedure(error_code='P0300', ...)
  └─▶ 举升机           raise_platform(height_meters=2)
  │  A2A（订零件）
  ▼
零件供应商 Agent
```

**这个例子把分工讲得很清楚**：

| 交互 | 用什么 | 为什么 |
|------|--------|--------|
| 用户 ↔ 车间经理 | A2A | 跨信任边界，可能反问 |
| 车间经理 → 机械师 | A2A | 不同角色，各自内部状态独立 |
| 机械师 → 诊断仪 | **MCP** | 确定性工具调用 |
| 机械师 → 供应商 | A2A | 跨组织 |

> 📐 **记忆锚点**：**A2A 处理高层的、对话式的、面向任务的交互；MCP 让 Agent 使用它自己的、具体的、结构化的工具。**

## 六、折中方案：对方只有私有 API

现实里最常见的情况：**你想接的 Agent 没有提供 A2A 端点，只有一个私有 REST API。**

| 方案 | 做法 | 优劣 |
|------|------|------|
| **直接调 REST**（推荐） | 不套协议 | ✅ 最简单、最稳。缺点：对方改 API 你得跟着改 |
| **自己写 A2A 适配层** | 你这边起一个 A2A 服务端，内部调对方的 REST | ⚠️ 能对外提供 A2A 接口，但**你需要维护这层适配**，且对方 API 变了还得改 |
| **等对方支持** | 先用 REST，等 | 被动但省事 |

⚠️ **「自己写 A2A 适配层」是可行且常见的做法**——你在中间充当「协议翻译」，对外用 A2A，对内用 REST。但这带来一个问题：**你要同时维护两套契约**。对方 API 变了，适配层要改；A2A 版本升级了，适配层也要改。

**判断建议**：如果对方明确表达了「未来会支持 A2A」，先直接调 REST，别急着写适配层。如果对方永远不会支持，但你需要对外提供标准化接口（比如你要做平台），那适配层是值得的。

---

## 七、一个反模式

⚠️ **最常见的误用：为了「用上新协议」而用 A2A。**

具体表现：

| 症状 | 问题 |
|------|------|
| 同一代码库内的两个 Agent 之间走 A2A | 纯粹的开销：多序列化、多网络往返、多状态管理 |
| 把确定性的查询接口包成 A2A Task | 过度设计，MCP 或 REST 都更合适 |
| 为了「架构先进」引入 | 架构先进不等于适合你的规模 |

**代价是真实的**：一次本地函数调用（微秒级）变成走 HTTP + 序列化 + 状态机（毫秒到秒级）。还要处理鉴权、超时、重试、降级、监控。**这些工作量有实际收益才行。**

---

## 八、陷阱

1. **❌ 把自己代码库内的 Agent 之间套 A2A。** 最常见的误用。
2. **❌ 对方只有 MCP server 却硬上 A2A。** MCP 更轻，除非你需要 A2A 的有状态特性。
3. **❌ 对方只有私有 API 就自己写适配层。** 先评估对方会不会支持。
4. **❌ 把 A2A 当成 MCP 的升级版。** 方向不同，不是替代关系。
5. **❌ 忽略生态成熟度差距。** A2A SDK 周下载量约为 MCP 的 1/21，遇到问题时能搜到的资料也少得多。
6. **❌ 决策时只看「哪个协议更先进」。** 看的是「哪个适合这个被调用方的性质」。

---

## 小结

- 核心规则：确定性函数 → MCP；会推理的 Agent → A2A
- 同代码库内 → **都不用**
- 决策树：先判断「是我的函数吗」，再判断「确定性还是自主 Agent」，最后判断「在我代码库里吗」
- 混合架构是正常形态：A2A 管 Agent 之间，MCP 管 Agent 到工具
- 对方只有私有 API 时，直接调 REST 往往是最优解
- 生态成熟度：A2A 约为 MCP 的 1/21，决策时要考虑
