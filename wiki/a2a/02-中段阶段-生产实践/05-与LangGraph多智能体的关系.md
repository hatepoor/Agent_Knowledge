# 与 LangGraph 多智能体的关系

> **什么时候该读**：你在用 LangGraph 的多智能体（Supervisor / Network / Hierarchical 模式），想知道它和 A2A 是什么关系、什么时候该从进程内编排升级到跨边界协议。

## 学习目标

读完本篇，你应当能够：

1. 说清「进程内多 Agent」和「跨边界 A2A」的分界线在哪
2. 画出三层分工：工具层 / 编排层 / 边界层
3. 知道自己系统该停在哪一层
4. 识别「该迁移到 A2A」的五个信号
5. 说清 LangGraph 与 A2A 的状态管理各自负责什么

---

## 一、先讲结论

> **LangGraph 的多 Agent 和 A2A 不是替代关系，是不同层次的东西。**
> LangGraph 管**你的图里怎么传状态**，A2A 管**跨治理边界怎么通信**。它们可以共存，但在同一个层面对使用时是错的。

| | LangGraph 多智能体 | A2A |
|---|---|---|
| 解决的问题 | 图里的状态怎么流转、节点怎么协作 | 跨组织/跨服务的 Agent 怎么互相委派 |
| 边界 | **代码库内部** | **代码库外部** |
| 通信方式 | 状态写入 State，reducer 合并 | HTTP + Task 状态机 |
| 谁持有状态 | Checkpointer 持有 | 远端 Agent 持有 Task |
| 延迟 | 微秒到毫秒 | 毫秒到秒 |

**你的终端多智能体系统，全部属于「代码库内部」。所以答案是：现在不需要 A2A。**

---

## 二、分界线在哪

**分界线就是治理边界（governance boundary）。**

| 问题 | 在边界内 | 在边界外 |
|------|---------|---------|
| 你能改它的代码吗 | ✅ 能 | ❌ 不能 |
| 你能部署它吗 | ✅ 能 | ❌ 不能 |
| 它挂了你能修吗 | ✅ 立刻修 | ❌ 要提工单等对方 |
| 它的鉴权由谁定 | 你 | 对方 |

| 类型 | 归属 | 用什么 |
|------|------|--------|
| LangGraph 节点间 | 同一张图 | 状态 + reducer |
| 子 Agent / 子图 | 同一代码库 | LangGraph 原生机制（子图、Send、Command） |
| Supervisor → 专家 Agent | 同一代码库 | Supervisor 模式 |
| **你的 Agent → 别人的 Agent** | **跨边界** | **A2A** |
| **你的 Agent → 别人的工具** | **跨边界** | **MCP** |

> 📐 **判断动作很简单：问自己「如果它挂了，我能不能自己重启它」。能，就在边界内；不能，就在边界外。**

---

## 三、三层分工模型

把你的系统按层看，A2A 属于最上面那层：

```
┌──────────────────────────────────────────────────┐
│ ③ 边界层：A2A                                    │
│    跨组织/跨服务的 Agent 通信                       │
│    —— 只有这一层需要 A2A                         │
├──────────────────────────────────────────────────┤
│ ② 编排层：LangGraph / DeepAgents                 │
│    图、State、reducer、Send、Command、Checkpointer │
│    —— 你的多 Agent 系统在这一层                   │
├──────────────────────────────────────────────────┤
│ ① 工具层：MCP / 函数工具 / Skills                │
│    Agent 拿到哪些能力                             │
└──────────────────────────────────────────────────┘
```

**三层的职责与不该越界的部分**：

| 层 | 该做 | 不该做 |
|----|------|--------|
| **① 工具层** | 提供确定性的能力 | 决定调用顺序和策略 |
| **② 编排层** | 决定「先做什么后做什么、什么时候派给谁」 | 关心对面是 HTTP 还是函数 |
| **③ 边界层** | 跨边界的通信契约、鉴权、状态同步 | 决定业务流程 |

⚠️ **越界是常见架构错误**：在工具层里写业务判断，或者在边界层里写业务流程。正确的方向是「编排层决定编排，边界层只管通信」。

---

## 四、LangGraph 各机制与 A2A 的对照

这张表能帮你把两个体系焊在一起。

### 状态与恢复

| LangGraph | A2A | 说明 |
|-----------|-----|------|
| **State** | Task + Message | 都是「工作状态的容器」，但 State 是图内的、Task 是协议对象 |
| **Checkpointer** | Task Store | 都持久化状态。Checkpointer 按 `thread_id`，Task Store 按 `task_id` |
| **`thread_id`** | **`contextId`** | 都是会话标识。**区别**：`thread_id` 通常由客户端持有；`contextId` 由服务端生成 |
| **`interrupt()`** | **`input-required`** | ⭐ **几乎完全对应**：执行到一半暂停等外部输入 |
| **`Command(resume=...)`** | 补充新 Message | 都是恢复机制 |
| **`astream`** | SSE 流式 | 都支持流式产出 |

### 编排机制

| LangGraph | A2A |
|-----------|-----|
| **Send**（动态扇出） | ❌ 无对应。子 Agent 分发是框架内部的事，A2A 不管 |
| **Command**（跨节点跳转 + 状态更新） | ❌ 无对应 |
| **Supervisor 模式** | 近似于 A2A 场景里的「编排 Agent」，但一个在图内、一个在边界上 |
| **子图 / 子 Agent 工具** | 近似于「agent-as-tool」，但一个在进程内、一个跨网络 |
| — | **`Agent Card`** 能力发现：**LangGraph 无对应** |

### 差异中最重要的一条

> ⚠️ **LangGraph 没有「拒绝受理」的概念，A2A 有。**
>
> 图里的节点一定会被调度，不存在「这个 Agent 拒绝接这个任务」。而 A2A 里对方可以在开始前就返回 `rejected`（策略不允许、不支持该技能、限流）。
>
> 这条差异在你接入外部 Agent 时会真实遇到——你的编排逻辑必须处理「对方不接」这个分支。

## 五、迁移信号：什么时候该从进程内升级到 A2A

⚠️ **这五个信号出现任意一个，才考虑把进程内编排改成跨边界 A2A。**

| 信号 | 说明 |
|------|------|
| **1. 有人要求把 Agent 暴露给外部** | 另一个团队/公司要调你的 Agent |
| **2. 代码库开始分裂** | Agent 团队独立开发、独立部署、独立发布 |
| **3. 要接入外部的 Agent 能力** | 你要用别人做的专业 Agent |
| **4. 集成线条数爆炸** | 图里 Agent 之间的连线太多，维护不动 |
| **5. 合规/审计要求物理隔离** | 不同数据域的 Agent 不能在同一进程 |

### 典型迁移路径

```
阶段 1：单图多节点
  StateGraph + 节点间直接流转
  例：检索 → 生成

阶段 2：多 Agent 编排（同代码库）
  Supervisor 模式 / 子 Agent 工具 / Send
  例：检索 Agent + 生成 Agent + 校验 Agent

阶段 3：Agent 变成独立服务 ★ 分界点
  每个 Agent 独立部署、独立扩缩容
  例：检索 Agent 单独部署成服务

阶段 4：跨边界 A2A
  Agent 之间通过协议通信，可以跨团队/跨组织
  例：接入外部专业 Agent
```

⚠️ **阶段 2 → 3 是关键转折。** 从「同代码库」变成「独立服务」的那一刻，A2A 才有了意义。

**但注意**：阶段 3 不一定要用 A2A。内部服务之间用 REST/gRPC + 各自的鉴权也是合理选择。**A2A 的优势在于「对方可能不是你的团队」**。

## 六、A2A Agent 放在 LangGraph 图里的具体位置

如果你要接一个外部 A2A Agent，按之前说的 agent-as-tool 模式放置：

```
StateGraph
│
├─ [编排节点]  decide_route()      ← 决定「该不该问外部」
│
├─ [本地专家节点]  local_expert()   ← 你的 LangChain Agent
│
└─ [远程专家节点]  remote_expert()  ← 包了 A2A 客户端的 Agent
        │
        └─ 工具：query_remote_legal_agent()   ← 内部走 A2A
```

### 三条放置原则

| 原则 | 原因 |
|------|------|
| **工具定义在远程专家节点里** | 让编排节点的 LLM 只在「真的要问外部」时才用，不污染本地决策 |
| **编排决策留在编排节点** | 「什么时候该问外部」是你的业务决策，不要外包 |
| **连接实例放图状态外** | State 会被 checkpoint 序列化，HTTP 连接对象序列化不了 |

⚠️ **异步问题**：A2A 调用是 async 的，远程专家节点必须 `async def`，图的调用方要用 `ainvoke` / `astream`。这是这个模式最常见的报错来源。

实现细节见 [[a2a/01-入门阶段-协议基础/第02章-工程实践/2.2-把远端Agent包装成本地工具]]。

## 七、A2A 对 LangGraph Checkpointer 的影响

⚠️ **接了外部 Agent 之后，你的 Checkpointer 语义会变。** 这点容易忽略。

| 维度 | 只有本地 Agent | 接了外部 A2A Agent |
|------|--------------|-----------------|
| 一次 `ainvoke` 的含义 | 图从入口跑到出口 | 图跑到某个节点，**节点内部触发了外部任务** |
| 状态快照包含什么 | 完整的图状态 | 图状态 + 「外部 Task ID」的引用 |
| 恢复时的复杂度 | 从 checkpoint 继续跑图 | 还要处理「外部 Task 还在不在跑」 |
| 失败重试 | 从节点重跑 | ⚠️ 要判断能不能重试（终态不可复活） |

**具体建议**：

1. **在 State 里只存外部 Task 的 ID，不存外部数据。** 外部数据的权威在远端。
2. **恢复时要先查外部 Task 状态。** 它可能已经 `completed` 了 —— 这时候直接取 Artifact，别重新发起。
3. **`rejected` 不要重试。** `failed` 才考虑重试，且是新建 Task。

> 📐 **记忆锚点**：`input-required` ≈ `interrupt()`，`contextId` ≈ `thread_id`，外部 Task 状态 ≈ 你需要额外追踪的「外部世界状态」。最后一条是 LangGraph 原生没有的——因为原生所有状态都在图里。

## 八、陷阱

1. **❌ 在同一张 LangGraph 图里用 A2A 连两个节点。** 纯粹的开销。
2. **❌ 把 Agent Card 当成 LangGraph 的什么东西。** 没有对应物——能力发现是 A2A 独有的。
3. **❌ 忘了处理 `rejected`。** LangGraph 没有这个概念，外部 Agent 有。你的编排逻辑必须有这个分支。
4. **❌ 把外部 Task 的数据复制进 State。** 权威在远端，State 只存 ID。
5. **❌ 恢复时不查外部 Task 状态就重跑。** 可能重复执行一个已经完成的外部任务。
6. **❌ 把「Agent 独立部署」直接等同于「要用 A2A」。** 内部服务用 REST/gRPC 也可以，A2A 的优势在跨团队。

---

## 小结

- LangGraph 多 Agent 管**代码库内部**，A2A 管**跨治理边界**，不是替代关系
- 分界线判断法：**「它挂了，我能不能自己重启它」**
- 三层分工：工具层（MCP）→ 编排层（LangGraph）→ 边界层（A2A）。**边界层只管通信，不写业务**
- 关键对应：`interrupt()` ≈ `input-required`；`thread_id` ≈ `contextId`（但后者服务端生成）
- **LangGraph 没有「拒绝受理」概念，A2A 有 `rejected`** —— 编排逻辑必须有这个分支
- 迁移信号：有人要暴露你的 Agent / 代码库分裂 / 要接外部 Agent / 集成线爆炸 / 合规隔离
- 接外部 Agent 后 State 里**只存 Task ID**，恢复时先查远端状态
