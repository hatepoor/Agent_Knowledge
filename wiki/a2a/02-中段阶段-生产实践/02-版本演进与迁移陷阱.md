# 版本演进与迁移陷阱

> **什么时候该读**：你有基于 A2A v0.3 的存量实现，或者你手上有一份 2025 年的资料需要判断新旧。

## 学习目标

读完本篇，你应当能够：

1. 说出 v0.3 → v1.0 的**具体字段级差异**
2. 用几个信号快速判断一份资料是 0.x 还是 1.0
3. 走完一次迁移的步骤，知道每步验证什么
4. 明白为什么「注册中心还兼容 0.3」不等于「可以一直不迁移」

## 一、先回答一个具体问题

**「我现在该迁移吗？」**

| 你的情况 | 建议 |
|---------|------|
| 纯 v0.3 实现，**还在实验阶段**，没有外部调用方 | 迁移成本低，早迁早省事 |
| v0.3 实现，**已有外部集成方** | 需要协调双方一起升级，别单方面切 |
| 只是读了资料、写了 demo | 直接重写，别迁移 |
| 暂时没时间 | 可暂缓，但要接受：v1.0 的安全能力（签名卡）你用不上 |

⚠️ **关键认知**：v1.0 相对 v0.3 的价值主要在**多绑定、版本协商、多租户、签名卡**。如果你只用 JSON-RPC 单绑定、不需要签名卡、不做多租户，那 v0.3 的功能你其实都在用。迁移的动力主要来自**长期维护和生态对齐**，不是「不迁就不能用」。

## 二、字段级差异清单

### Agent Card

| 项 | v0.3 | v1.0 | 迁移动作 |
|----|------|------|---------|
| **服务地址** | 单个 `url` 字段 | `supportedInterfaces[]` 数组 | 改成数组；单接口也要包一层 |
| **绑定声明** | 隐含（默认 JSON-RPC） | 每条接口带 `protocol_binding` | 每个接口都要声明绑定 |
| **协议版本** | `protocolVersion: "0.3.0"` | `"1.0"` | 改值 |
| **签名** | 无 | `signatures[]` | 新增（可选，但建议） |
| **首选传输** | 无 | `preferred_transport` | 新增 |
| **多租户** | 无 | 相关支持 | 按需 |
| **扩展卡** | `extendedAgentCard` 能力位 | 同 | 已有则保留 |

### 数据模型

| 项 | 变化 |
|----|------|
| 规范化定义 | protobuf（权威）+ JSON Schema 2020-12 自动生成 |
| `Part` 类型 | v1.0 明确为 `oneof`：`text` / `raw`（内联字节）/ `url` / `data` |
| 附加字段 | `mediaType`、`filename`、`metadata` 规范化 |

### 操作与方法

| 项 | 说明 |
|----|------|
| 方法命名 | v1.0 统一为 `message/send`、`message/stream`、`tasks/*` 风格 |
| 新增操作 | `tasks/list`、`tasks/resubscribe`（订阅已有任务）等 |
| SDK 结构 | Python SDK 从「单文件 AgentExecutor + A2AStarletteApplication」演化到 **`AgentExecutor` + `DefaultRequestHandler` + `create_*_routes` 三件拼装** |
| 路由工厂 | `create_agent_card_routes` / `create_jsonrpc_routes` / `create_grpc_routes` / `create_rest_routes` |

⚠️ **SDK 结构变化是最容易踩坑的地方。** 网上大量 2025 年中旬的教程用的是旧结构（一个 `A2AStarletteApplication` 类直接包办），照抄跑不通。**识别信号：代码里出现 `A2AStarletteApplication`（带 `Starlette` 字样）→ 大概率是旧版。**

## 三、快速判断资料新旧

拿到一份 A2A 资料，用三个信号判断：

| 看什么 | 新（1.0） | 旧（0.x） |
|--------|---------|----------|
| Agent Card 的地址字段 | `supportedInterfaces: [...]` | `url: "..."` |
| SDK 服务端写法 | `create_jsonrpc_routes(request_handler, '/')` | `A2AStarletteApplication(...)` |
| `protocolVersion` 值 | `"1.0"` | `"0.3.0"` |

**三个都指向旧，就别抄了。** 唯一例外：v1.0.1 至今官方仍把 0.3 文档放在同一个站点里，搜索结果容易混。

## 四、迁移步骤

### 步骤 0：评估影响面

先列清单，别直接动手：

```markdown
## 迁移清单
- [ ] Agent Card 文件（含文档、示例、配置里的）
- [ ] 服务端代码（路由装配、handler）
- [ ] 客户端代码（拉卡、解析、请求）
- [ ] 文档与 README
- [ ] 依赖版本（a2a-sdk）
- [ ] 外部集成方（是否需要协调）
```

⚠️ **最容易漏的是文档和示例。** Agent Card 通常被复制粘贴到文档、示例代码、测试数据里。

### 步骤 1：升级 SDK

```bash
pip install -U a2a-sdk
```

⚠️ **SDK 主版本变更可能带来 API 破坏。** 升级后先跑通官方 `a2a-samples` 里的 helloworld 示例，确认基础环境正常，再动自己的代码。

### 步骤 2：改 Agent Card

```python
# ❌ 旧
AgentCard(
    name='My Agent',
    url='https://example.com/a2a',
    version='1.0.0',
    protocolVersion='0.3.0',
)

# ✅ 新
AgentCard(
    name='My Agent',
    version='1.0.0',
    protocolVersion='1.0',
    supported_interfaces=[
        AgentInterface(
            protocol_binding='JSONRPC',
            url='https://example.com/a2a',
            protocol_version='1.0',
        )
    ],
)
```

⚠️ **注意 Python SDK 里是 snake_case（`supported_interfaces`），JSON 里是 camelCase（`supportedInterfaces`）。** 这个差异本身也是文档混乱的来源之一。

### 步骤 3：改服务端装配

按新的三件拼装结构改：路由工厂 + RequestHandler + Executor。参考 [[a2a/01-入门阶段-协议基础/第02章-工程实践/2.1-Python-SDK最小可用实现]] 的完整代码。

### 步骤 4：改客户端

主要变化在「解析 Agent Card」和「方法名」。用 SDK 的高层接口（`A2ACardResolver` + `create_client`）时，这层变化 SDK 帮你吸收了；**如果你手写了原始 HTTP 请求，就都要自己改**。

### 步骤 5：验证

```bash
# 1. 拉卡验证
curl https://example.com/.well-known/agent-card.json

# 2. 确认关键字段
#    - protocolVersion 是 "1.0"
#    - 有 supportedInterfaces
#    - 每条接口有 protocol_binding 和 protocol_version

# 3. 完整跑一遍任务，确认状态流转正常
```

### 步骤 6：协调外部集成方 ⚠️ 不能跳

如果你的 Agent **已有外部调用方**，v1.0 的破坏性变更意味着：

- 你的服务端改成 v1.0 后，老客户端（按 0.3 实现的）可能**连不上**
- 反过来也一样

**A2A 的版本协商能力（Agent Card 里的 `protocolVersion`）在这里能帮上忙**，但你需要显式实现双版本支持，而不是简单切换。

**这一步必须提前通知所有调用方并约定时间窗口。** 单方面切换是迁移事故的头号原因。

## 五、为什么「注册中心还兼容」不是免死金牌

Google Cloud 的 Agent Registry 目前**同时接受 1.0 和 0.3 两套 schema**。这确实降低了迁移压力，但要理解它为什么不等于「可以一直不迁」：

| 理由 | 说明 |
|------|------|
| **注册中心的兼容是产品策略，不是承诺** | 商业产品可以调整策略。你无法基于它做长期架构承诺 |
| **生态在往 1.0 收敛** | 新 SDK、新示例、新文档都是 1.0。留在 0.3 会越来越难找到支持 |
| **安全能力在 1.0** | 签名卡、多租户、明确的安全流程都是 1.0 引入的。留在 0.3 等于放弃这些 |
| **协作方会先迁** | 你的合作方升级到 1.0 后，你的 0.3 服务端就成为兼容负担 |

**建议**：把迁移当成**技术债**来管理——列进 roadmap，定时间点，别让它一直挂着。

## 六、陷阱

1. **❌ 照抄带 `A2AStarletteApplication` 的代码。** 那是旧 SDK 结构。
2. **❌ 只改服务端不改客户端。** 破坏性变更是双向的。
3. **❌ 忘了 Python 用 snake_case、JSON 用 camelCase。**
4. **❌ 单方面切版本。** 有外部调用方时必须先协调。
5. **❌ 因为「注册中心还支持」就无限期拖延。** 生态在收敛。
6. **❌ 升级 SDK 后不先跑官方示例。** 基础环境没验证就改自己的代码，出问题难定位。
7. **❌ 漏改文档和示例里的 Agent Card 片段。** 这是最容易漏的地方。

---

## 小段

- v1.0 相对 v0.3 有**破坏性变更**：`url` → `supportedInterfaces[]`、SDK 三件拼装结构、方法命名统一
- 三个信号判断资料新旧：`supportedInterfaces` / `create_*_routes` / `protocolVersion: "1.0"`
- 迁移六步：评估 → 升 SDK → 改卡 → 改服务端 → 改客户端 → 验证 → **协调外部方**
- 最危险的一步是单方面切换版本
- 「注册中心兼容 0.3」是产品策略不是长期承诺
