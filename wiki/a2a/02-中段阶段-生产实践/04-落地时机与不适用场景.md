# 落地时机与不适用场景

> **什么时候该读**：接到一个「要不要上 A2A」的需求，需要判断；或者上线前做最后一次自检。
> **本篇是本知识库最实用的一篇**——协议好懂，判断该不该用才是真问题。

## 学习目标

读完本篇，你应当能够：

1. 用五个信号判断「现在该不该上 A2A」
2. 说出五种明确**不该**用 A2A 的情况
3. 评估一个团队的 A2A 成熟度
4. 用上线自检清单核对准备度

---

## 一、先给结论

**按现在的生态成熟度，A2A 对绝大多数团队来说不是「该用的技术」，而是「该理解的技术」。**

| 判断维度 | 现实情况 |
|---------|---------|
| 架构正确性 | ✅ 长期正确的边界选择 |
| 生态成熟度 | ⚠️ SDK 下载量约为 MCP 的 1/21，踩坑时能搜到的资料少 |
| 生产验证 | ⚠️ 有落地案例（华为、Azure、AWS、Google Cloud），但**不像 MCP 那样普及** |
| 厂商支持 | ⚠️ 23 家里 8 家支持，且**全部同时支持 MCP**；Anthropic、OpenAI、Mistral、xAI 无公开支持声明 |

**所以正确的姿态是**：

> **学它、懂它、在架构设计时把它考虑进去，但在真实的跨边界需求出现之前，不要为了「先进」而引入它。**

---

## 二、五个「该用」信号

⚠️ **五个信号里至少命中两个**，才值得认真考虑。

### 信号 1：被调用的 Agent 在你的治理边界之外

| 情况 | 判定 |
|------|------|
| 对方是**另一家公司**部署和维护的 Agent | ✅ 命中 |
| 对方是**另一个团队**部署，但你改不了它的代码 | ✅ 命中 |
| 对方在你的代码库里 | ❌ 不命中 |

**这是最核心的信号。** 治理边界决定了「能不能用函数调用」——出了边界就只能走协议。

### 信号 2：存在 N×(N-1)/2 的集成问题

```
2 个 Agent：1 条对接
5 个 Agent：10 条
10 个 Agent：45 条
```

如果你的架构图上「Agent 之间的连线」数量在增长，且每条连线都是定制对接，A2A 就在解决一个真实存在的问题。

### 信号 3：任务需要跨请求跟踪

| 情况 | 判定 |
|------|------|
| 任务可能跑超过几分钟 | ✅ 命中 |
| 客户端可能断连 | ✅ 命中 |
| 需要知道进度百分比 | ✅ 命中 |
| 需要能取消 | ✅ 命中 |

**判断标志**：你会问出「这个任务跑到哪了」「上次那个任务的结果呢」这类问题。普通 HTTP 处理不了。

### 信号 4：对方是会推理的 Agent，不是函数

| 情况 | 判定 |
|------|------|
| 对方可能中途反问你要补充信息 | ✅ 命中 |
| 对方自己会调多个工具做规划 | ✅ 命中 |
| 对方返回的结果形式每次都不同 | ✅ 命中 |

### 信号 5：外部方要求

对方明确说「我们提供 A2A 端点」或者「请用 A2A 接我们」。

⚠️ **这时候不是「该不该用」的问题，是「怎么用对」的问题。** 优先读 [[a2a/01-入门阶段-协议基础/第02章-工程实践/2.2-把远端Agent包装成本地工具]]。

## 三、五种「不该用」情况

### ❌ 情况 1：Agent 都在你的代码库里

**这是最重要的一条。**

你的 LangGraph 多智能体、DeepAgents 子 Agent、Supervisor 模式——**全都属于这一类**。

| 直接调用 | 走 A2A |
|---------|--------|
| 微秒级 | 毫秒到秒级 |
| 无鉴权 | 要处理鉴权 |
| 无状态管理 | 要处理 Task 状态机 |
| 调试直接断点 | 要看日志和报文 |
| 失败自动抛异常 | 要设计重试/降级 |

**收益为零，代价全在。**

### ❌ 情况 2：被调用方是个确定性函数

数据库查询、计算、文件转换——用 MCP 或直接 REST。套 A2A 是杀鸡用牛刀。

判定见 [[a2a/02-中段阶段-生产实践/03-A2A与MCP选型决策树]]。

### ❌ 情况 3：只是想「架构先进」

⚠️ **这是最需要警惕的一条。** 新协议发布时最容易出现的心态。

先问自己：如果没有人会知道你们用了 A2A，你还会引入它吗？如果答案是「不会」，那你引入它的唯一理由是展示性，不是工程需要。

### ❌ 情况 4：对方不提供 A2A，你也不需要对外标准化

对方只有私有 REST API，而你不需要把自己的服务暴露给外部——那就直接调 REST。

「自己写 A2A 适配层」是有成本的：你要同时维护两套契约。

### ❌ 情况 5：团队没人有空维护

A2A 的**隐藏工作量在授权模型**——规范只强制「每个操作都检查授权」，策略要你自己设计。

| 需要自己做的 | 工作量 |
|-------------|--------|
| 授权策略设计 | 不小 |
| 持久化 Task 存储 | 中 |
| webhook 校验防 SSRF | 中 |
| 多租户隔离（如果需要） | 大 |
| 监控、审计、降级 | 中 |

**如果没有人负责这些，A2A 会变成一个「能跑通 demo、上线就出漏洞」的东西。**

## 四、成熟度评估

按你团队的状态对照：

| 阶段 | 特征 | 建议 |
|------|------|------|
| **L0 观望** | 没听说过 A2A | 先补概念，见 [[a2a/README]] |
| **L1 理解** | 知道是什么、能讲清和 MCP 的区别 | ✅ **大多数团队该停在这里** |
| **L2 演练** | 用 SDK 在本地跑通过，理解了 Task 状态机 | 有跨边界需求时可以开始评估 |
| **L3 试点** | 有一个真实的跨组织场景在用 | ⚠️ 确保有人负责授权设计和运维 |
| **L4 生产** | 多方对接，有监控和降级 | 持续跟进版本和安全更新 |

⚠️ **L1 是「及格」状态。** 不是每个团队都需要走到 L4。**能在架构评审时说清「为什么这里用 A2A、为什么那里不用」，就已经是把 A2A 用对了。**

## 五、上线自检清单

真要上线的话，逐项确认。

### 架构合理性

- [ ] 被调用的 Agent **确实**在你的治理边界之外
- [ ] 被调用方**确实**是会推理的 Agent，不是确定性函数
- [ ] 已经确认过：不能用 MCP 或直接 REST 解决
- [ ] 已经在架构文档里写清「为什么用 A2A」

### 能力就绪

- [ ] 有真实的跨边界需求（不是演练）
- [ ] 团队有人负责协议集成（不是甩给某个人的额外任务）
- [ ] 有至少一个月的维护窗口（初期调试会占时间）
- [ ] 踩坑时能查的资料足够（官方文档 + SDK 源码 + a2a-samples）

### 安全 ★

- [ ] 完整核对过 [[a2a/02-中段阶段-生产实践/01-安全模型与鉴权]] 的检查清单
- [ ] Agent Card 里没有任何密钥
- [ ] 授权模型有人设计过（不是「协议应该处理了吧」）
- [ ] webhook 做了域名白名单 + IP 检查
- [ ] 通过了越权测试

### 运维

- [ ] Task 用持久化存储
- [ ] 有降级路径（远端挂了主流程不受影响）
- [ ] 超时分阶段设置
- [ ] 重试基于终态判断
- [ ] 有链路监控和审计日志

### 退出预案

- [ ] **有降级回退方案**：如果 A2A 的对方挂了或停止维护，我能切回什么
- [ ] 知道对方的 SDK 版本和升级节奏
- [ ] 没有把 A2A 变成不可替换的深度依赖

⚠️ **最后一条最容易被跳过。** A2A 目前是较新的标准，虽然已归 AAIF 治理，但相比 MCP 仍属年轻。把核心链路完全押在它上面之前，先想清楚退路。

## 六、给你当前技术栈的具体建议

基于你的情况（终端交互多智能体系统，LangChain/LangGraph + Skills + MCP + RAG）：

| 项 | 建议 |
|---|---|
| **Sub Agent 之间** | ❌ 不用 A2A。继续用 LangGraph 的 Send / 子 Agent 工具 |
| **工具接入** | ✅ 继续用 MCP，你的 `deepagents/tools/MCP集成` 已经跑通 |
| **Skills 系统** | ✅ 和 A2A 完全正交，不冲突 |
| **要不要现在引入 A2A** | ❌ 不。你的所有 Agent 都在一个代码库里 |
| **那要做什么** | ① 补概念到能讲清的程度；② 未来若要接外部 Agent，按 [[a2a/学习路线图]] 路径 B 准备 |

**性价比最高的动作**：用半天在本地跑通 [[a2a/01-入门阶段-协议基础/第02章-工程实践/2.1-Python-SDK最小可用实现]]，亲眼看一次 Task 状态机流转。**不是为了用它，是为了在架构讨论时你有底气说「我试过，知道它的代价在哪」。**

---

## 七、陷阱

1. **❌ 把「支持组织 150+」当成生产就绪。** 支持 ≠ 部署，看 SDK 下载量。
2. **❌ 在同一代码库里套 A2A。** 最常见的误用，零收益全代价。
3. **❌ 因为「架构先进」引入。** 展示性不是工程理由。
4. **❌ 以为协议帮你解决了授权。** 授权模型要自己设计。
5. **❌ 没有退出预案。** 新标准要有退路。
6. **❌ 把 A2A 当成必须立刻掌握的技能。** 理解它就够了，用它是另一回事。

---

## 小结

- **A2A 现在是「该理解的技术」，不是「该用的技术」**
- 五个该用信号：治理边界外 / N×(N-1)/2 集成 / 需跨请求跟踪 / 对方会推理 / 外部方要求。**命中 ≥2 才考虑**
- 五种不该用：同一代码库 / 确定性函数 / 只想先进 / 对方无 A2A 且无需标准化 / 团队没人维护
- **L1（能讲清）就是及格**，不是每个团队都要上生产
- 对你的技术栈：Sub Agent 之间不用 A2A，工具继续用 MCP，**性价比最高的动作是本地跑通一次看状态机**
