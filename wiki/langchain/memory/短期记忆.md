# 短期记忆（Short-term Memory）

## 概述

记忆是记住先前交互信息的系统。对于 AI Agent 而言，记忆至关重要——它让 Agent 能记住先前的交互、从反馈中学习并适应用户偏好。

**短期记忆**让应用程序能记住单个对话线程（thread）内的先前交互。

对话历史是最常见的短期记忆形式。长对话对 LLM 构成挑战：完整历史可能无法放入 LLM 的上下文窗口。即使模型支持完整上下文长度，大多数 LLM 在长上下文上仍表现不佳——它们会被陈旧或偏离主题的内容"分散注意力"。

## 使用方法

要为 Agent 添加短期记忆（线程级持久化），需要在创建 Agent 时指定 `checkpointer`：

```python
# 导入 Agent 创建函数和内存级检查点保存器
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

# 定义一个普通工具函数，Agent 可以在对话中调用它
# 这里模拟查询用户信息，实际场景中可能查询数据库或 API
def get_user_info() -> str:
    """Look up information about the current user."""
    return "No user profile on file."

# 创建 Agent 并注入 checkpointer —— 这是启用短期记忆的关键
# InMemorySaver 将对话状态保存在内存中，适合开发/测试环境
# checkpointer 的作用：每次 Agent 执行后，自动将完整的状态（包括消息历史）
# 序列化并持久化到存储后端，下次调用时自动恢复
agent = create_agent(
    model="google_genai:gemini-3.5-flash",
    tools=[get_user_info],
    checkpointer=InMemorySaver(),  # 启用短期记忆，使用内存存储
)

# thread_id 是短期记忆的核心概念：
# - 每个 thread_id 代表一条独立的对话线程
# - 同一 thread_id 下的多次调用共享同一段对话历史
# - 不同 thread_id 之间的记忆完全隔离，互不干扰
# - checkpointer 以 thread_id 为键存储和检索状态快照
thread_config = {"configurable": {"thread_id": "1"}}

# 第一次调用：用户告知 Agent 自己的名字
# Agent 处理消息后，checkpointer 自动保存当前状态（包含这条用户消息和 Agent 回复）
response = agent.invoke(
    {"messages": [{"role": "user", "content": "Hi! My name is Bob."}]},
    thread_config,
)["messages"][-1].content  # 取最后一条消息（即 Agent 的回复）的内容
print(response)  # "Hi Bob!"

# 第二次调用：使用相同的 thread_id，Agent 能"记住"之前的对话
# 工作原理：
# 1. checkpointer 根据 thread_id="1" 恢复之前保存的完整对话历史
# 2. 新消息追加到已恢复的历史中
# 3. LLM 看到完整上下文，因此能回答"你叫 Bob"
# 这就是短期记忆的本质 —— 通过 checkpointer 自动管理对话状态的保存与恢复
response = agent.invoke(
    {"messages": [{"role": "user", "content": "What's my name?"}]},
    thread_config,
)["messages"][-1].content
print(response)  # "You are Bob!"
```

### 生产环境

在生产环境中，使用数据库支持的 checkpointer：

```python
# pip install langgraph-checkpoint-postgres
# 生产环境必须使用数据库级 checkpointer，因为：
# 1. InMemorySaver 在进程重启后数据丢失
# 2. 多进程/多实例部署需要共享存储
# 3. 数据库提供持久化、可靠性和并发安全
from langgraph.checkpoint.postgres import PostgresSaver

# PostgreSQL 连接字符串，包含用户名、密码、主机、端口、数据库名和 SSL 模式
DB_URI = "postgresql://postgres:postgres@localhost:5432/postgres?sslmode=disable"

# 使用上下文管理器（with 语句）确保数据库连接正确释放
# from_conn_string：从连接字符串创建 PostgresSaver 实例，内部维护连接池
with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    # setup() 在数据库中创建 checkpointer 所需的表结构
    # 包括：checkpoints 表（存储状态快照）、writes 表（记录每次写入）等
    # 首次运行必须调用，后续运行如果表已存在则安全跳过
    checkpointer.setup()
    # 将数据库 checkpointer 注入 Agent，用法与 InMemorySaver 完全一致
    # 这体现了 checkpointer 的抽象设计 —— 上层代码无需关心底层存储
    agent = create_agent("gpt-5.5", tools=[get_user_info][[, checkpointer=checkpointer)
```

更多后端对比详见 [[langchain/memory/Checkpointer存储后端]]。

## 自定义 Agent 记忆

默认使用 `AgentState` 管理短期记忆。可以扩展 `AgentState` 添加自定义字段：

```python
# 导入 Agent 创建函数和默认状态类
# AgentState 是 LangChain Agent 的默认状态结构，包含 messages 等基础字段
from langchain.agents import create_agent, AgentState

# 通过继承 AgentState 扩展状态，添加业务所需的自定义字段
# 这些自定义字段会和 messages 一样被 checkpointer 持久化
# 即：每次 Agent 执行后，user_id 和 preferences 也会一并保存
class CustomAgentState(AgentState):
    user_id: str          # 当前用户标识，可用于个性化响应或权限控制
    preferences: dict     # 用户偏好设置，如主题、语言等，跨轮次保持

# 通过 state_schema 参数告诉 Agent 使用自定义状态结构
# Agent 运行时会自动将输入数据映射到 CustomAgentState 的对应字段
agent = create_agent(
    "gpt-5.5",
    tools=[get_user_info],
    state_schema=CustomAgentState,   # 使用扩展后的状态结构
    checkpointer=InMemorySaver(),    # checkpointer 会持久化所有状态字段
)

# 调用时传入自定义字段的值，这些值会：
# 1. 被写入 CustomAgentState 实例
# 2. 在 Agent 执行过程中可供工具通过 runtime.state 访问
# 3. 被 checkpointer 保存，下次同一 thread_id 调用时自动恢复
result = agent.invoke(
    {
        "messages": [{"role": "user", "content": "Hello"}],
        "user_id": "user_123",           # 自定义字段：用户 ID
        "preferences": {"theme": "dark"}  # 自定义字段：用户偏好
    },
    {"configurable": {"thread_id": "1"}})
```

## 常见策略

### 裁剪消息（Trim Messages）

```python
# 导入 before_model 装饰器 —— 用于注册"模型调用前"执行的中间件钩子
# middleware（中间件）是 LangChain Agent 的扩展机制，允许在 Agent 执行流程中
# 插入自定义逻辑，无需修改 Agent 核心代码
from langchain.agents.middleware import before_model

# @before_model 装饰器将此函数注册为"模型调用前"钩子
# 执行时机：每次 LLM 被调用之前，此函数都会先执行
# 参数说明：
#   - state: 当前 Agent 状态，包含 messages 列表等所有状态字段
#   - runtime: 运行时上下文，提供工具调用信息等元数据
# 返回值：返回 None 表示不修改状态；返回 dict 表示用其中的值更新状态
@before_model
def trim_messages(state, runtime):
    messages = state["messages"]
    # 如果消息数不超过 3 条，无需裁剪，直接放行
    # 返回 None 表示不对状态做任何修改
    if len(messages) <= 3:
        return None
    # 保留第一条消息（通常是系统提示 / system prompt）
    # 系统提示定义了 Agent 的角色和行为规则，不能丢弃
    first_msg = messages[0]
    # 保留最近 3 条消息 —— 这是裁剪策略的核心
    # 只保留最近的交互，丢弃中间的旧消息以节省上下文窗口空间
    recent_messages = messages[-3:]
    # 返回状态更新：
    # RemoveMessage(id=REMOVE_ALL_MESSAGES) 先清除所有现有消息
    # 然后重新放入 first_msg（系统提示）和最近 3 条消息
    # 这种"先清空再重建"的模式比逐条删除更高效
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), first_msg, *recent_messages]}

# 将中间件注入 Agent —— middleware 参数接受中间件列表，按顺序执行
# 执行流程：用户消息 -> [trim_messages 裁剪] -> LLM 调用 -> Agent 回复
# 这样 LLM 永远只看到最近 N 条消息，避免上下文过长导致性能下降
agent = create_agent(
    "gpt-5.5", tools=[...], middleware=[trim_messages], checkpointer=InMemorySaver()
)
```

### 删除消息

```python
# 导入 RemoveMessage —— LangChain 中用于从消息列表中删除消息的特殊对象
# 与直接操作列表不同，RemoveMessage 是一种声明式操作，
# checkpointer 能正确追踪它并更新持久化状态
from langchain.messages import RemoveMessage

# @after_model 装饰器注册"模型调用后"钩子
# 与 @before_model 的关键区别：
#   - @before_model：在 LLM 生成回复之前执行（适合预处理/裁剪输入）
#   - @after_model：在 LLM 生成回复之后执行（适合清理/后处理输出）
# 这个中间件在每次 Agent 回复后清理最早的两条消息，保持窗口精简
@after_model
def delete_old_messages(state, runtime):
    messages = state["messages"][[
    # 当消息超过 2 条时，删除最早的两条
    # 这是一种滑动窗口策略：始终只保留最近的少量消息
    if len(messages) > 2:
        # 为每条要删除的消息创建 RemoveMessage 对象
        # 通过消息的唯一 id 标识来定位要删除的消息
        # 返回 dict 格式与 before_model 一致，用于更新状态
        return {"messages": [RemoveMessage(id=m.id) for m in messages[:2]]}
    # 消息数在阈值内，不做任何操作
    return None
```

### 摘要化消息（SummarizationMiddleware）

```python
# 导入内置的摘要中间件 —— LangChain 提供的开箱即用的记忆管理方案
# 与手写 trim/delete 中间件不同，SummarizationMiddleware 会：
# 1. 检测到对话历史超过阈值时，自动调用 LLM 将旧消息压缩为一段摘要
# 2. 用摘要替换旧消息，既保留了上下文语义又大幅减少 token 数量
from langchain.agents.middleware import SummarizationMiddleware

agent = create_agent(
    model="gpt-5.5",
    tools=[...],
    middleware=[
        SummarizationMiddleware(
            # 用于生成摘要的模型 —— 通常选择更小/更便宜的模型
            # 原因：摘要任务是相对简单的文本压缩，不需要最强模型
            # 使用小模型可以显著降低成本和延迟
            model="gpt-5.4-mini",
            # trigger：触发摘要化的条件
            # ("tokens", 4000) 表示当消息总 token 数超过 4000 时触发
            # 也支持 ("messages", N) 按消息数量触发
            trigger=("tokens", 4000),
            # keep：摘要后保留多少条最近消息不压缩
            # ("messages", 20) 表示保留最近 20 条消息原样不动
            # 只有被保留消息之前的旧消息才会被压缩为摘要
            keep=("messages", 20)
        )
    ],
    checkpointer=checkpointer,
)
```

## 在工具中访问记忆

### 读取短期记忆

```python
# @tool 装饰器将普通函数转换为 LangChain 工具
# 工具可以被 Agent 自主决定何时调用，实现与外部系统的交互
@tool
# ToolRuntime 是关键 —— 它是 LangChain 注入的运行时上下文对象
# 当工具参数中包含 runtime: ToolRuntime 时，框架会自动注入当前运行时信息
# runtime 包含：
#   - runtime.state: 当前 Agent 的完整状态（包括 messages、自定义字段等）
#   - runtime.tool_call_id: 本次工具调用的唯一标识
#   - runtime.config: 可配置的运行时参数
# 这使得工具能"感知"对话上下文，而不仅仅是处理输入参数
def get_user_info(runtime: ToolRuntime) -> str:
    """Look up user info."""
    # 通过 runtime.state 读取 Agent 状态中的自定义字段
    # 这些字段来自 CustomAgentState（见上方示例）或对话过程中写入的值
    # 这就是工具"读取短期记忆"的机制 —— 直接访问被 checkpointer 持久化的状态
    user_id = runtime.state["user_id"]
    return "User is John Smith" if user_id == "user_123" else "Unknown user"
```

### 写入短期记忆

```python
@tool
# 当工具需要修改 Agent 状态（写入短期记忆）时，返回类型改为 Command
# Command 是 LangChain 提供的特殊返回类型，用于向 Agent 发出指令
# 与普通返回值不同，Command 可以同时：
#   1. 更新状态字段（写入记忆）
#   2. 向消息列表添加消息（工具执行结果）
#   3. 控制 Agent 后续行为（如跳转到特定节点）
def update_user_info(runtime: ToolRuntime) -> Command:
    """Look up and update user info."""
    # Command(update={...}) 中的 dict 指定要更新哪些状态字段
    # 这些更新会被 checkpointer 持久化，实现"写入短期记忆"
    return Command(update={
        # 更新自定义状态字段 user_name
        # 下次同一 thread 调用时，runtime.state["user_name"] 将返回 "John Smith"
        "user_name": "John Smith",
        # 必须手动添加 ToolMessage 来记录工具执行结果
        # 原因：使用 Command 返回时，框架不会自动生成工具结果消息
        # ToolMessage 需要指定 tool_call_id 以匹配对应的工具调用请求
        # 这样 Agent 才能知道是哪个工具调用产生了这个结果
        "messages": [
            ToolMessage("Successfully looked up user information", tool_call_id=runtime.tool_call_id)
        ][[
    })
```
