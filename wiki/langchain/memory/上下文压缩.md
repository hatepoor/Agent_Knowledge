# 上下文压缩（Context Compression）

LangChain 中有两种上下文压缩，解决不同场景的问题：

- **对话历史压缩**：防止 messages 列表无限增长撑爆上下文窗口
- **检索结果压缩**：精简 RAG 检索到的文档，只保留与查询最相关的片段

两者压缩的对象和执行位置不同，但都不需要主模型参与压缩决策。

---

## 场景一：对话历史压缩

### 方式 A：`SummarizationMiddleware`（智能摘要）

用一个小模型（如 GPT-5.4-mini）将历史对话摘要化：

```python
# 导入摘要中间件 —— 这是 LangChain 提供的内置对话历史压缩组件
# 它会在每次 LLM 调用前自动检查消息列表长度，超过阈值时用一个小模型生成摘要
from langchain.agents.middleware import SummarizationMiddleware

# 创建 Agent 时，通过 middleware 参数注入压缩逻辑
# middleware 是一个列表，支持多个中间件按顺序链式执行
agent = create_agent(
    model="gpt-5.5",           # 主模型：负责回答用户问题（能力强、价格高）
    tools=[...],               # Agent 可用的工具列表
    middleware=[
        # SummarizationMiddleware：在 before_model 阶段自动执行摘要压缩
        SummarizationMiddleware(
            # 摘要模型：专门用来生成对话摘要的轻量模型
            # 选择原则：足够快、足够便宜、摘要质量够用即可
            # gpt-5.4-mini 的成本约为主模型的 1/10，速度快 3-5 倍
            model="gpt-5.4-mini",

            # trigger: 触发摘要压缩的阈值条件
            # ("tokens", 4000) 表示当消息列表的总 token 数超过 4000 时触发
            # 也支持 ("messages", 50) 格式，即按消息条数触发
            # 阈值设置建议：略低于模型上下文窗口的安全线
            trigger=("tokens", 4000),

            # keep: 摘要后保留的原始消息数量
            # ("messages", 20) 表示保留最近的 20 条消息原文不动
            # 更早的消息会被替换为一段摘要文本
            # 保留越多 → 信息越完整但 token 越多；保留越少 → 压缩越激进但可能丢失细节
            keep=("messages", 20),
        )
    ],
    # checkpointer: 状态持久化后端，用于保存/恢复对话状态
    # 中间件的压缩只影响发送给 LLM 的消息列表，不影响 checkpointer 中存储的完整历史
    checkpointer=checkpointer,
)
```

**触发时机**：`before_model` 钩子。每次 LLM 调用前检查当前消息列表的 token 数，超过阈值才执行摘要。

```
触发前： [System][User_1][AI_1]...[User_50][AI_50]  ← 5000 tokens
                        ↓ SummarizationMiddleware
触发后： [System][历史摘要: "用户询问了天气和股票..."][User_48][AI_48][User_49][AI_49][User_50][AI_50]  ← <4000 tokens
```

| 参数 | 作用 | 推荐值 |
|------|------|--------|
| `model` | 用于摘要的轻量模型 | `gpt-5.4-mini`、`gemini-2.0-flash` |
| `trigger` | 触发摘要的阈值 | `("tokens", 4000)` 或 `("messages", 50)` |
| `keep` | 保留的原始消息数 | `("messages", 20)` |

### 方式 B：`@before_model` 手动裁剪（硬截断）

不调用 LLM，直接按条数截断 messages：

```python
# 导入 before_model 装饰器 —— 用于注册 Agent 的"模型调用前"钩子
# 被装饰的函数会在每次 LLM 调用前自动执行，可以检查和修改 state
from langchain.agents.middleware import before_model

# 使用 @before_model 装饰器注册中间件函数
# 函数签名固定：接收 state（当前状态字典）和 runtime（运行时上下文）两个参数
@before_model
def trim_messages(state, runtime):
    # 从 state 中获取当前的消息列表
    # state["messages"] 包含所有历史消息（由 checkpointer 恢复或新增）
    messages = state["messages"]

    # 阈值判断：消息条数未超过 20 条时，不需要裁剪
    # 返回 None 表示"不做任何修改"，Agent 继续正常执行
    if len(messages) <= 20:
        return None

    # ===== 硬裁剪逻辑 =====
    # 保留策略：messages[0]（系统提示词，通常是 System Message）+ 最近 10 条消息
    # messages[0] 必须保留：因为系统提示词定义了 Agent 的角色和行为规则
    # messages[-10:] 取最后 10 条：保留最近的对话上下文，丢弃更早的历史
    # 注意：这是一种"有损压缩"——被丢弃的消息信息完全丢失，不会像摘要那样保留概要
    return {"messages": [messages[0][[, *messages[-10:]]}
    # 返回的 dict 会更新 state，从而改变发送给 LLM 的消息列表
    # 重要：这不会修改 checkpointer 中的完整历史，只影响本次 LLM 调用的输入

# 创建 Agent，将自定义中间件注入
agent = create_agent(
    model="gpt-5.5",
    tools=[...],
    middleware=[trim_messages][[,      # 注册硬裁剪中间件
    checkpointer=InMemorySaver(),   # 使用内存存储（开发测试场景）
)
```

### 对比

| 方式 | 调用 LLM | 信息损失 | token 节省 | 实现复杂度 |
|------|---------|---------|-----------|-----------|
| `SummarizationMiddleware` | ✅ 小模型摘要 | 低 | 50-80% | 低（配置即用） |
| `@before_model` 硬裁剪 | ❌ | 高 | 80-95% | 低（几行代码） |

两种方式都在 Agent 的 `before_model` 钩子中执行，**不涉及主模型**。`SummarizationMiddleware` 虽调用小模型，但那是一个专门负责摘要的轻量模型，不是回答问题的主模型。

## 场景二：检索结果压缩

### `ContextualCompressionRetriever`

在 RAG 流程中，检索器返回的文档可能包含大量不相关内容。压缩检索器对每个文档用 LLM 提取与查询最相关的片段：

```python
# 导入上下文压缩检索器 —— LangChain 提供的检索结果压缩组件
# 它包装一个普通检索器，在返回结果前自动用 LLM 提取与查询最相关的片段
from langchain.retrievers import ContextualCompressionRetriever
# 导入 LLM 链式提取器 —— 用 LLM 对每个文档逐段分析，提取与查询相关的句子
# 原理：将 (查询, 文档) 组成 prompt 发给 LLM，让 LLM 只返回文档中与查询相关的部分
from langchain.retrievers.document_compressors import LLMChainExtractor

# ===== 第一步：创建压缩器 =====
# LLMChainExtractor：对检索到的每个文档，用 LLM 提取与查询最相关的文本片段
# from_llm(llm)：传入一个 LLM 实例（通常用主模型或专用小模型）
# 压缩器会对每个文档独立调用一次 LLM，所以文档数量直接影响延迟和成本
compressor = LLMChainExtractor.from_llm(llm)

# ===== 第二步：创建压缩检索器（装饰器模式）=====
# ContextualCompressionRetriever 是一个"包装器"，组合了两个组件：
compression_retriever = ContextualCompressionRetriever(
    # base_compressor: 压缩器，负责对检索结果进行精简
    # 每个文档会被 LLM 提取出与查询最相关的句子/段落
    base_compressor=compressor,

    # base_retriever: 底层检索器，负责从向量数据库中检索原始文档
    # search_kwargs={"k": 5}：先检索 top-5 个最相似的文档
    # 这 5 个文档随后会被 compressor 逐一压缩
    base_retriever=vectorstore.as_retriever(search_kwargs={"k": 5}),
)

# ===== 第三步：使用压缩检索器进行检索 =====
# invoke() 方法的调用流程：
#   1. base_retriever 从向量库中检索 top-5 文档（每个可能数千字）
#   2. base_compressor 对每个文档调用 LLM，提取与查询相关的片段
#   3. 返回压缩后的文档列表（每个只剩几百字的关键内容）
docs = compression_retriever.invoke("LangChain 的 Agent 架构")
# 返回的不是原始 5 个完整文档，而是每个文档中与查询最相关的句子
# 效果：大幅减少送入主模型的 context 长度，节省 token 并提升回答质量
```

**工作原理**：

```
检索到 5 个文档：每个 2000 字（合计 10000 字）
                    ↓ LLMChainExtractor 对每个文档提取与查询相关的片段
返回 5 个片段：每个 200 字（合计 1000 字） → token 节省约 90%
```

### 其他压缩器

| 压缩器 | 行为 | 节省 |
|--------|------|------|
| `LLMChainExtractor` | 用 LLM 提取相关片段 | 70-90% |
| `LLMChainFilter` | 仅过滤掉无关文档，不提取 | 50-70% |
| `EmbeddingsFilter` | 基于向量相似度过滤，无需 LLM | 50-70% |

## 两种压缩的定位

```
上下文压缩
    │
    ├── 对话历史压缩
    │   ├── SummarizationMiddleware（智能摘要）
    │   ├── @before_model 硬裁剪
    │   └── 压缩 messages，在 Agent before_model 钩子中执行
    │
    └── 检索结果压缩
        ├── ContextualCompressionRetriever + LLMChainExtractor
        ├── ContextualCompressionRetriever + LLMChainFilter
        └── 压缩检索文档，在检索管道中执行
```

| 维度 | 对话历史压缩 | 检索结果压缩 |
|------|-------------|-------------|
| 压缩对象 | messages 列表 | 检索到的文档 |
| 执行位置 | Agent 的 `before_model` 钩子 | 检索管道 |
| 关键类 | `SummarizationMiddleware` / `@before_model` | `ContextualCompressionRetriever` |
| 是否调 LLM | 可选（摘要模式调小模型） | 是（`LLMChainExtractor`）或可选（`EmbeddingsFilter`） |
| token 节省 | 50-95% | 50-90% |

两种压缩互不冲突，可以同时使用。压缩决策由中间件和检索器框架自动完成。
