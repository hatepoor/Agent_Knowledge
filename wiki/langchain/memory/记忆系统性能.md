# 记忆系统性能

---

## Checkpointer 内存占用分析

### InMemorySaver 存储结构

InMemorySaver 本质上是一个 Python 字典：

```python
# InMemorySaver 的底层数据结构：一个以 thread_id 为键的嵌套字典
# 所有线程的记忆都存储进程内存中，进程退出后数据全部丢失
store: dict[str, dict] = {
    # 键（key）：thread_id，唯一标识一个对话线程
    # 值（value）：该线程的完整状态快照，包含消息历史和元数据
    "thread-001": {"messages": [...], "user_id": "xxx", ...},
    # 每个 thread 的 messages 列表会随对话轮次不断增长
    # messages 中包含 HumanMessage、AIMessage、ToolMessage 等对象
    # 每个消息对象本身也是一个 Python 对象，占用 200-5000 字节不等
    "thread-002": {"messages": [...], "user_id": "yyy", ...},
    # 新增一个对话线程 = 字典新增一个键值对 = 占用更多堆内存
    # 注意：这些对象不会被 GC 回收，因为 store 字典始终持有它们的引用
}
```

键为 `thread_id`，值为 Agent 的完整运行状态（消息历史 + 自定义字段）。

### 单次对话的内存估算

| 组成 | 每条大小 | 20 轮对话（约 60 条消息） |
|------|---------|------------------------|
| HumanMessage | ~200-500 B | ~20 KB |
| AIMessage（含推理） | ~500-2000 B | ~60 KB |
| ToolMessage（结果） | ~500-5000 B | ~100 KB |
| 状态字段 | ~100-500 B | ~5 KB |
| **单线程合计** | | **~150-200 KB** |

### 不同并发规模的估算

| 并发线程数 | 每线程 20 轮 | 每线程 100 轮 |
|-----------|-------------|--------------|
| 10 | ~2 MB | ~10 MB |
| 100 | ~20 MB | ~100 MB |
| 1000 | ~200 MB | ~1 GB |

**结论**：对个人开发或中小规模应用，InMemorySaver 的内存占用几乎可以忽略。真正吃内存的是**模型推理**，而非记忆存储。

> **注意**：如果 `ToolMessage` 携带了超长工具返回结果（如 `include_raw_content=True` 的 Tavily 搜索或大文件读取），一条消息就可能达到数 MB。这种情况下的内存占用主要来自**具体工具返回的数据量**，而非 Checkpointer 本身的存储开销。

## Python 进程内存模型

### 线程间共享内存

Python 的 `threading.Thread` **不分配独立内存**，所有线程**共享同一个进程堆**：

```python
import threading

# shared_list 分配在主线程（即进程的全局堆区）
# 所有子线程都能直接访问这个列表，因为它们共享同一块内存
shared_list = []  # 主线程分配

def worker():
    # 子线程直接操作同一块内存，无需序列化或 IPC
    # 这意味着：子线程 append 的数据直接占用进程的堆内存
    # 如果 100 个子线程各自 append 大量数据，总内存 = 所有线程数据之和
    shared_list.append("hello")  # 子线程直接操作同一块内存

# 创建子线程：子线程不会复制内存，而是共享父进程的整个地址空间
# 这是 threading 模型的核心特征：共享内存，零拷贝
t = threading.Thread(target=worker)
t.start()
# 关键结论：一个线程 OOM → 整个进程的所有线程全部崩溃
# 这与 multiprocessing 不同——子进程 OOM 只影响自己
```

所以"一个 Python 线程的可用内存"等于**整个进程的可用内存**，没有"每线程 N MB"的限制。

### 实际的限制因素

| 层级 | 限制 | 典型值 |
|------|------|--------|
| **进程地址空间** | 64 位系统虚地址上限 | 128 TB（实际用不完） |
| **物理内存** | 机器可用 RAM | 8 GB ~ 512 GB |
| **OS 资源限制** | ulimit / rlimit | 默认无限制 |
| **容器限制** | Docker `--memory` / cgroup | 常见 512m ~ 8g |
| **Python 对象开销** | 每个对象额外 32-56 字节 | 100 万小对象约 50+ MB |
| **GIL** | 不影响内存，影响 CPU 并行 | — |

### 实际瓶颈

```python
import psutil
# 读取操作系统报告的"当前可用物理内存"（单位：字节）
# 这个值 = 总物理内存 - 已使用内存，反映进程还能申请多少内存
# 在容器环境中，这个值受 cgroup 限制，不等于宿主机总内存
available = psutil.virtual_memory().available
# 将字节转换为 MB 并打印，便于运维人员直观判断剩余空间
# 生产环境中建议设置阈值告警：当 available < 某值时触发预警
print(f"可用内存: {available / 1024 / 1024:.0f} MB")
```

实际运行中，比"内存够不够"更常见的瓶颈是：

1. **GC 停顿**——大量对象创建/回收时，所有线程暂停
2. **内存碎片**——长时间运行后，大对象分配失败
3. **OOM Kill**——容器内内存超限，进程被系统杀掉

### 线程 vs 进程内存对比

| | threading（共享内存） | multiprocessing（独立内存） |
|--|---------------------|---------------------------|
| 内存模型 | 所有线程共享一个堆 | 每个进程独立堆 |
| 单个可用内存 | 整个进程的内存 | 该进程分配的量 |
| 相互影响 | 一个线程 OOM，全进程挂 | 一个进程 OOM，不影响其他进程 |
| 数据共享 | 直接读写变量 | 需要序列化 / IPC |

## OOM 风险分析与预防

### 真实的内存消耗来源排序

| 来源 | 内存占用 | OOM 风险 |
|------|---------|---------|
| **模型推理**（加载 LLM 权重） | 几 GB ~ 几十 GB | ⚠️ 最高 |
| **ToolMessage 返回数据**（搜索结果、文件内容） | 单条可达数十 MB | ⚠️ 高 |
| **对话历史无限增长**（百万条消息级） | 累计可达几百 MB ~ GB | ⚠️ 中 |
| **InMemorySaver 字典本身** | 通常几十 MB | ✅ 很低 |

### 最容易触发 OOM 的三种场景

#### 场景 1：超长对话从不裁剪

```python
# 危险场景：创建了一个没有任何记忆裁剪机制的 Agent
agent = create_agent(
    model="gpt-5.5",
    tools=[search],
    # 没有加 trim_messages 或 SummarizationMiddleware
    # 这意味着 messages 列表会随对话轮次无限增长，永远不会被截断或压缩
    checkpointer=InMemorySaver(),
    # InMemorySaver 会把所有消息存在进程内存里
    # 每轮对话新增的消息（HumanMessage + AIMessage + 可能的 ToolMessage）
    # 都会永久驻留在内存中，直到进程退出
)

# 危险点：循环 1 万次，每次调用都在 messages 列表尾部追加新消息
# 1 轮对话 ≈ 3 条消息（Human + AI + Tool），1 万轮 ≈ 3 万条消息
# 每条消息平均 5-10 KB → 3 万条 ≈ 150-300 MB，全部驻留在进程堆中
# 如果循环 10 万次 → 1.5-3 GB，在 512MB 容器中必然触发 OOM Kill
for i in range(10000):  # 一万轮对话
    # 每次 invoke 都会：get 历史 → 拼接新消息 → 调 LLM → put 新状态
    # messages 列表只增不减，内存占用线性增长
    agent.invoke({"messages": [f"第{i}轮"]}, {"configurable": {"thread_id": "1"}})
```

- 1 万轮对话 ≈ 3 万条消息 ≈ **150-300 MB**
- 10 万轮 → **1.5-3 GB**，在小内存容器中就会 OOM

#### 场景 2：工具返回了超大数据

```python
# 危险场景：工具直接将整个文件内容作为字符串返回
# 返回的内容会被封装成一条 ToolMessage，存入 messages 列表
@tool
def read_large_file(path: str) -> str:
    """Read a file."""
    with open(path) as f:
        # 如果文件有 50 MB，这里就返回一个 50 MB 的字符串
        # 这个字符串会被包装成 ToolMessage 对象，占用额外的对象头开销
        # 更危险的是：这条 ToolMessage 会永久留在 messages 历史中
        # 每次 agent.invoke() 都会把这条 50 MB 的消息发给 LLM（浪费 token）
        # 同时它一直驻留在内存中，无法被 GC 回收
        return f.read()  # 如果文件 50 MB，这条 ToolMessage 就是 50 MB
    # 调用 20 次这样的工具 → 20 条 ToolMessage → 1 GB 内存消失
    # 而且这些大消息还会被 Checkpointer 持久化，进一步消耗磁盘/数据库空间
```

每调用一次这样的工具，`messages` 列表里就多一条**几 MB ~ 几十 MB** 的 ToolMessage。调用 20 次，几百 MB 就消失了。

#### 场景 3：大规模并发 + 容器限制

```python
# 危险场景：容器内存限制只有 512 MB，但同时启动了 100 个 Agent 线程
# Docker 只给了 512m，同时运行 100 个 Agent 实例
# 每个 Agent 实例都有自己的 InMemorySaver，各自在堆内存中维护一份 messages 字典
# 由于 threading 共享内存，这 100 个实例的内存占用全部叠加在同一个进程堆上
for i in range(100):
    # 每个线程运行一个独立的 Agent，拥有独立的 thread_id
    # 每个 Agent 的 InMemorySaver 会累积该线程的所有对话历史
    # 单线程 20 轮对话 ≈ 20 MB，100 个线程 = 2000 MB = 2 GB
    # 2 GB 远超容器的 512 MB 限制 → 触发 cgroup OOM Kill → 整个进程被杀
    thread = Thread(target=run_agent, args=(f"thread-{i}",))
    thread.start()
    # 关键风险：所有线程共享内存，一个线程导致 OOM = 全部 100 个线程一起崩溃
    # 这是 threading 模型在内存层面的最大劣势：故障不隔离
```

每个 Agent 实例持有自己的 InMemorySaver，每条线程累积 ~20 MB 记忆 → 100 条线程 = **2 GB**，远超 512m 限制。

### 危险信号速查

| 信号 | 含义 | 风险等级 |
|------|------|---------|
| **没有加 trim_messages 或 SummarizationMiddleware** | 记忆无限增长 | 🔴 高 |
| **工具返回了 include_raw_content=True 的搜索结果** | 单条消息可能数 MB | 🔴 高 |
| **工具直接返回了大文件内容** | 同上 | 🔴 高 |
| **单线程对话超过 1000 轮** | 记忆可能 >200 MB | 🟡 中 |
| **并发线程数 > 50，且都在持续对话** | 总记忆容易超 GB | 🟡 中 |
| **只用 InMemorySaver 做短期记忆** | 本身不是问题 | 🟢 低 |

### 预防措施

#### 1. 消息裁剪（必做）

```python
from langchain.agents.middleware import before_model

# 使用 @before_model 装饰器注册一个中间件：在每次调用 LLM 之前执行
# 这个中间件的作用：限制 messages 列表的最大长度，防止内存无限增长
@before_model
def trim_messages(state, runtime):
    messages = state["messages"]
    # 如果消息数量在安全范围内（≤20 条），不需要裁剪，直接放行
    if len(messages) <= 20:
        return None
    # 超过 20 条时执行裁剪：只保留第 0 条（通常是系统提示）+ 最近 10 条
    # 这样 messages 列表被截断为 11 条，释放了中间所有旧消息的内存
    # 被丢弃的消息会被 GC 回收（前提是 Checkpointer 不再持有旧版本的引用）
    # 效果：无论对话进行多少轮，内存中最多只保留 11 条消息 ≈ 几十 KB
    return {"messages": [messages[0][[, *messages[-10:]]}
    # 注意：这里返回的是新的 messages 列表，会覆盖 state 中的旧列表
    # Checkpointer 在下次 put() 时只保存裁剪后的 11 条消息
```

#### 2. 工具返回值限流（必做）

```python
@tool
def concise_search(query: str) -> str:
    # 先执行搜索，获取完整结果
    result = search(query)
    # 关键防护：对返回值做硬截断，最多保留 2000 个字符
    # 这样无论搜索结果有多大（原始网页可能几 MB），ToolMessage 最多只有 2 KB
    # 2000 字符 ≈ 2 KB，即使调用 100 次也只占 200 KB，完全可控
    # 对比场景 2 中不截断的情况：一次调用就可能引入 50 MB
    return result[:2000][[  # 硬截断 2000 字符
    # 注意：截断会丢失信息，但对于 LLM 上下文来说，
    # 搜索结果的前 2000 字符通常已包含最相关的内容（摘要、标题等）
```

#### 3. SummarizationMiddleware（推荐）

```python
from langchain.agents.middleware import SummarizationMiddleware

# SummarizationMiddleware 是一种"智能裁剪"策略
# 与简单的 trim_messages 不同，它不是直接丢弃旧消息，而是用 LLM 将旧消息压缩成摘要
# 这样既控制了内存占用，又保留了对话的关键上下文信息
SummarizationMiddleware(
    # 使用一个小模型（gpt-5.4-mini）来做摘要，成本低、速度快
    # 注意：摘要本身也需要调用 LLM，会产生少量额外开销
    model="gpt-5.4-mini",
    # 触发条件：当 messages 列表的总 token 数超过 4000 时，自动触发摘要
    # 4000 token ≈ 3000 个中文字 ≈ 约 16 KB 文本
    # 超过这个阈值时，中间件会把旧消息压缩成一条摘要消息
    trigger=("tokens", 4000),  # 超过 4000 token 时触发摘要
    # 保留最近 20 条原始消息不做处理，只摘要更早的消息
    # 这样 LLM 仍然能看到最近的对话细节，同时旧对话被压缩为摘要
    # 效果：messages 列表的总大小被控制在 (摘要 + 20 条原始消息) 的范围内
    keep=("messages", 20),     # 保留最近 20 条原始消息
)
# 与 trim_messages 的对比：
# - trim_messages：简单粗暴，直接丢弃旧消息 → 丢失上下文
# - SummarizationMiddleware：用 LLM 压缩旧消息 → 保留关键信息，但需要额外 LLM 调用
```

#### 4. 生产环境换用数据库后端

```python
# 终极方案：将记忆存储从进程内存迁移到外部数据库
# InMemorySaver → PostgresSaver，记忆不再占用进程内存
# 之前：messages 列表存在 Python 进程的堆里 → 占用进程内存
# 之后：messages 序列化后存入 PostgreSQL → 进程内存中只保留当前轮的状态
# 即使对话进行了 10 万轮，Agent 进程的内存占用也不会因此增长
# 内存压力从 Agent 进程转移到了 PostgreSQL 服务器（独立管理、可独立扩展）
checkpointer = PostgresSaver.from_conn_string(DB_URI)
# DB_URI 是 PostgreSQL 连接字符串，如 "postgresql://user:pass@host:5432/dbname"
# PostgresSaver 内部使用连接池复用数据库连接，避免每次调用都建立新连接
# 代价：每次 agent.invoke() 多了 3-13 ms 的数据库读写延迟（见上文时间开销分析）
# 但相比 LLM 推理的 1000-5000 ms，这点延迟几乎可以忽略
```

### 总结

> **InMemorySaver 本身不会导致 OOM。真正的 OOM 来源是：无限对话历史不裁剪 + 工具返回超大内容 + 高并发（或三者叠加）。** 做好消息裁剪、控制工具返回值大小、或在容器内限制严格时换用 PostgresSaver，OOM 风险基本可控。

## Checkpointer 工作流程与性能开销

### 每次 Agent 调用的完整流程

Checkpointer 的底层只有两个操作：**`get`（读取）** 和 **`put`（写入）**。以 PostgresSaver 为例，每次 `agent.invoke()` 的执行序列如下：

```
用户输入
    │
    ▼
Agent.invoke()
    │
    ├── 1. Checkpointer.get(thread_id)     ← 从数据库读取最新状态
    │       │  SELECT checkpoint FROM checkpoints
    │       │  WHERE thread_id = ? ORDER BY checkpoint_id DESC LIMIT 1
    │       ▼
    │   返回最新状态快照（messages + 自定义字段）
    │
    ├── 2. 拼接历史消息 + 新输入 → 发给 LLM
    │
    ├── 3. LLM 返回结果（含可能的工具调用）
    │
    ├── 4. 执行工具 → 得到 ToolMessage
    │
    └── 5. Checkpointer.put(thread_id, 新状态)  ← 写回数据库
            │  INSERT INTO checkpoints (...) VALUES (...)
            ▼
        数据库持久化
```

### Checkpointer 不涉及 LLM

**LLM 不参与数据库交互。** 数据库读写完全由 Checkpointer 在 Agent 框架内部完成，对 LLM 透明：

```
LLM 的视角：
    只看到 messages 列表 → 生成回复 → 得到新的 messages
    （它不知道也不关心数据存在哪里）

Checkpointer 的视角：
    在 LLM 看不见的地方，读写 PostgreSQL

Agent 框架的视角：
    get() → 拿到历史 → 调 LLM → 调 put()
```

LLM 收到的 messages 已经是 Checkpointer 从数据库取出来**反序列化后**的结果。

### 资源开销

#### 存储开销

| 项 | 值 |
|---|-----|
| 每条 checkpoint 记录 | ~1-50 KB（取决于消息长度和工具返回大小） |
| 每轮对话产生 | 1 条新记录 |
| 100 轮对话 | ~100 KB - 5 MB |
| 1000 个并发 thread × 100 轮 | ~100 MB - 5 GB |

#### 网络开销

| 操作 | 数据传输量 |
|------|-----------|
| get（读取最新状态） | ~1-50 KB |
| put（写入新状态） | ~1-50 KB |
| 每次 Agent 调用合计 | 2-100 KB |

#### 内存开销

| 组件 | 内存占用 |
|------|---------|
| Agent 进程 | 只保留当前轮状态（~1-50 KB），不累积历史 |
| PostgreSQL 进程 | 独立管理，与 Agent 进程隔离 |
| 连接池 | 通常 10-50 个连接，每个 ~几 MB |

### 时间开销

#### 数据库操作耗时

| 操作 | 耗时 | 说明 |
|------|------|------|
| get（读最新 checkpoint） | **1-5 ms** | 按 thread_id 主键查询，索引命中 |
| put（写入新 checkpoint） | **2-8 ms** | INSERT + 提交事务 |
| 合计每次 Agent 调用 | **3-13 ms** | get + put |

#### 与 LLM 调用对比

```
数据库操作     3-13 ms      ██
LLM 推理      1,000-5,000 ms ██████████████████████████████████████

比例：数据库耗时 ≈ LLM 耗时的 0.3% - 1.3%
```

| 模型 | 平均 LLM 响应时间 | 数据库 get+put 耗时 | 占比 |
|------|------------------|-------------------|------|
| GPT-5.5（简单问答） | ~1,000 ms | ~5 ms | **0.5%** |
| GPT-5.5（含工具调用） | ~3,000 ms | ~5 ms | **0.17%** |
| Claude 长上下文 | ~5,000 ms | ~5 ms | **0.1%** |

#### 关键结论

**数据库操作的耗时在 LLM 调用面前几乎可以忽略不计。** 一次 3 秒的 Agent 问答中，数据库只贡献约 5 毫秒（0.17%）。优化 LLM 的推理速度和 token 用量远比优化数据库读写更有意义。

### 为什么有时会感觉"慢"

| 伪慢原因 | 真实原因 | 解决 |
|---------|---------|------|
| 对话历史太长 | messages 列表过大，LLM 处理慢 | 加 SummarizationMiddleware |
| 首次查询慢 | 建立数据库连接（~50 ms） | 用连接池复用 |
| 老觉得"DB 慢了" | 实际是 LLM 生成了超长回复 | 检查 token 用量 |
| 高并发下变慢 | 连接池满，请求排队 | 增大连接池 / 使用 PgBouncer |
