# 工具来源与集成方式

Agent 所使用的工具来自三种渠道，各有优劣。理解它们的区别才能在项目中做出合理的技术选型。

---

## 三种工具来源

### 来源一：pip 集成包

LangChain 官方和社区以独立 pip 包的形式提供大量预置工具，覆盖搜索、数据库、文档处理等常见场景：

```bash
pip install langchain-tavily          # Tavily 搜索
pip install langchain-community       # 社区工具集（DuckDuckGo、Wikipedia、ArXiv 等）
pip install langchain-postgres        # PostgreSQL
```

使用方式是在代码中 import、实例化、配置 API Key：

```python
from langchain_tavily import TavilySearch

tool = TavilySearch(
    api_key="sk-xxx",  # 需要配置 API Key
    max_results=5,
)

agent = create_agent(model="gpt-5.5", tools=[tool])
```

**局限**：新增工具需要改代码（加 import、实例化、配 Key），然后重新部署。API Key 散落在代码或环境变量中。

### 来源二：MCP 服务器（运行时发现）

MCP（Model Context Protocol）允许 Agent 在**运行时自动发现工具**，无需在代码中 import 或实例化：

```python
from langchain-mcp import tools as mcp_tools

# 连接 MCP 服务器，自动发现其暴露的所有工具
search_tools = await mcp_tools("web-search")
fs_tools = await mcp_tools("filesystem")
db_tools = await mcp_tools("database")

# 无需 import、无需实例化、无需 API Key
agent = create_agent(model="gpt-5.5", tools=[*search_tools, *fs_tools, *db_tools])
```

新增工具时只需在配置文件中添加一个 MCP Server 条目：

```json
{
  "mcpServers": {
    "web-search": {
      "command": "npx",
      "args": ["@anthropic/mcp-web-search"][[,
      "env": { "TAVILY_API_KEY": "sk-xxx" }
    }
  }
}
```

**代码零改动**，重启即可发现新工具。MCP 的详细设计见 [[langchain/modules/langchain-mcp/MCP协议概述]]。

### 来源三：@tool 手写

项目特有的业务逻辑需要用 `@tool` 装饰器自行封装：

```python
@tool
def check_order_status(order_id: str) -> str:
    """查询内部订单状态。"""
    return internal_api.get(f"/orders/{order_id}")

@tool
def submit_approval(request_id: str) -> str:
    """提交审批到内部工作流。"""
    return workflow_engine.submit(request_id)
```

通常只占整体工具量的 **10-20%**——其余来自 pip 包或 MCP。

## pip 方式 vs MCP 方式

### 核心区别

```
pip 方式：
    import TavilySearch → 实例化 → 配 API Key → 写死 tools=[][[
    (新增工具 → 改代码 → 重新部署)

MCP 方式：
    启动 MCP Server（独立进程） ──→ Agent 运行时自动发现
    (新增工具 → 加一个 Server 配置 → 零代码改动)
```

### 逐项对比

| 维度 | pip 方式 | MCP 方式 |
|------|---------|---------|
| 安装 | `pip install langchain-xxx` | 不需要安装 Python 包 |
| 代码耦合 | import + 实例化 + 配 Key | 无需 import，自动发现 |
| API Key | 散落在代码 / .env 文件中 | 集中在 MCP Server 配置 |
| 新增工具 | 改代码 → CI/CD → 重新部署 | 加一行 mcp.json 配置 |
| 运行时变更 | 不可能 | 热插拔（重启 Server 即可） |
| 跨语言 | 仅限 Python | 服务端可用任意语言实现 |
| 调试 | 单进程，较简单 | 多进程，需额外工具 |

### 选型建议

| 场景 | 推荐方式 | 原因 |
|------|---------|------|
| 外部公开服务（搜索、翻译、地图） | **MCP** | 变动频繁，不想写死 |
| 内部业务 API（审批、CRM） | **@tool 手写** | 项目特有，逻辑自包含 |
| 稳定且长期的依赖 | **pip 包** 或 **MCP** | 视是否需要跨语言/热插拔而定 |
| 快速原型 | **pip 包** | import 即用，最简单 |

## Skills vs Tools

Skills（技能）和 Tools（工具）是两个不同的概念，解决的问题也不同。

### 核心区别

```
Tools（工具）                    Skills（技能）
─────────────────               ─────────────────
可调用的函数/API                 可读入的指令/SOP
调用 → 执行 → 返回结果            加载 → 指导行为
"手"：帮你做事                   "大脑的流程记忆"：教你做事
```

### 对比表

| 维度 | Tool | Skill |
|------|------|-------|
| 本质 | 可调用的函数 | Markdown 操作说明书 |
| 触发方式 | Agent 决策 → 框架执行 | Agent 读取 → 自行执行 |
| 实现手段 | Python 代码（`@tool`） | 纯 Markdown（SKILL.md） |
| token 消耗 | 调用时传参 + 返回结果 | 匹配时才加载完整内容 |
| 使用门槛 | 需编码 | 无需编码，写文档即可 |
| 灵活性 | 功能固定，不能超出代码定义 | Agent 可在指令范围内灵活发挥 |
| 典型场景 | 搜索、计算、API 调用 | 代码审查流程、部署规范、报告生成 |

### 实战配合

```
项目中有"写测试"的需求：

Tool 负责"能力":    run_pytest、generate_mock、check_coverage
Skill 负责"规范":   "本项目的单元测试覆盖率达 80%，
                    测试文件放在 tests/ 目录下，
                    先用 pytest fixture 再写测试用例..."
```

Agent 持有 Tool（能力）和 Skill（规范）后：
1. 读 Skill → 知道"怎么写才是符合规范的"
2. 调 Tool → 实际执行写测试、运行测试、检查覆盖率

### 一句话总结

> **Tool 是 Agent 的"肌肉"——能做什么；Skill 是"训练手册"——该怎么做得专业。** 两者互补：没有 Tool，Agent 只能看不能做；没有 Skill，Agent 能做但可能做得不规范。

详见 [[agent/skills/Skills]]。

## 实际项目中的组合策略

```
┌──────────────────────────────────────────────┐
│                  工具总来源                      │
│                                                │
│  外部公开服务（搜索、翻译、地图等）                  │
│    └→ MCP Server：零代码改动，API 集中管理          │
│                                                │
│  内部业务逻辑（审批、CRM 查询等）                    │
│    └→ @tool + ToolRegistry：统一注册，不散落       │
│                                                │
│  稳定的第三方依赖                                 │
│    └→ pip 包：或 MCP，视需要而定                   │
│                                                │
│  运行时动态筛选                                   │
│    └→ middleware：按角色/权限控制可见性              │
└──────────────────────────────────────────────┘
```

占比估算：pip 包 40-50%、MCP 30-40%、@tool 手写 10-20%。
