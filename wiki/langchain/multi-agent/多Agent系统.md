# 多 Agent 系统（Multi-agent）

多 Agent 系统协调专门的组件来处理复杂的工作流。然而，并非每个复杂任务都需要这种方式——单个 Agent 配合合适的工具和提示词通常也能达到类似效果。

## 为什么需要多 Agent？

当开发者说需要"多 Agent"时，他们通常寻求以下一项或多项能力：

- **上下文管理**：提供专业知识而不超出模型的上下文窗口
- **分布式开发**：允许不同团队独立开发和维护能力
- **并行化**：为子任务生成专门的 Worker 并并发执行

多 Agent 模式在以下场景中特别有价值：
- 单个 Agent 工具过多导致决策质量下降
- 任务需要专业知识和大量上下文
- 需要强制执行顺序约束

多 Agent 设计的核心是**上下文工程（Context Engineering）**——决定每个 Agent 看到什么信息。

## 模式（Patterns）

| 模式 | 工作原理 |
|------|----------|
| **子 Agent** | 主 Agent 将子 Agent 作为工具协调。所有路由通过主 Agent |
| **交接** | 行为基于状态动态变化。工具调用更新状态变量触发路由或配置更改 |
| **技能** | 专门的提示词和知识按需加载。单个 Agent 保持控制 |
| **路由器** | 路由步骤对输入进行分类并导向专门的 Agent |
| **自定义工作流** | 使用 LangGraph 构建定制执行流 |

### 选择模式

| 模式 | 分布式开发 | 并行化 | 多跳 | 直接用户交互 |
|------|-----------|--------|------|------------|
| 子 Agent | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |

可以混合使用模式！子 Agent 架构可以调用包含自定义工作流或路由器 Agent 的工具。

## 性能对比

### 单次请求："Buy coffee"

| 模式 | 模型调用次数 |
|------|-------------|
| 子 Agent | 4 |
| 交接 | 3 ✅ |
| 技能 | 3 ✅ |
| 路由器 | 3 ✅ |

### 重复请求（Turn 1 + Turn 2）

| 模式 | Turn 2 调用 | 总计 |
|------|-------------|------|
| 子 Agent | 4 | 8 |
| 交接 | 2 | 5 ✅ |
| 技能 | 2 | 5 ✅ |
| 路由器 | 3 | 6 |

**关键洞察：** 有状态模式（交接、技能）在重复请求上节省 40-50% 调用。

### 多领域："比较 Python、JavaScript、Rust"

| 模式 | 调用 | Token 总数 |
|------|------|-----------|
| 子 Agent | 5 | ~9K ✅ |
| 交接 | 7+ | ~14K+ |
| 技能 | 3 | ~15K |
| 路由器 | 5 | ~9K ✅ |

**关键洞察：** 对于多领域任务，支持并行执行的模式（子 Agent、路由器）最高效。

## 总结

| 优化目标 | 推荐模式 |
|----------|---------|
| 单次请求 | 交接 / 技能 / 路由器 |
| 重复请求 | 交接 / 技能 |
| 并行执行 | 子 Agent / 路由器 |
| 大上下文领域 | 子 Agent / 路由器 |
| 简单聚焦任务 | 全部适用 |
