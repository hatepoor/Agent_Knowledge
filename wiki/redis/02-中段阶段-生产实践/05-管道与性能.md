## 一、性能账本：Redis 的延迟去哪了

一次 `GET` 的总延迟 = 网络往返（RTT）+ 服务端处理。**服务端处理通常 < 0.1ms，大头永远在网络**：

| 部署形态 | 典型 RTT | 1000 次串行 GET 的纯网络耗时 |
|----------|----------|------------------------------|
| 同机 | ~0.05ms | ~50ms |
| 同机房 | ~0.5ms | ~500ms |
| 跨可用区 | ~2ms | ~2000ms |

结论：**应用"感觉 Redis 慢"，九成是 RTT 数量没控制住（串行小命令太多），而不是 Redis 本身慢。** 解法按优先级：

1. **减少命令数**：批量命令（`MGET`/`MSET`）> pipeline > 并发 > 单发串行
2. **减少往返体积**：别一次拉大对象（大 key 问题）
3. **拉近物理距离**：应用与 Redis 同机房部署（这条上线时决定，运行期改不了）

## 二、机制层：pipeline 为什么有效

复习 [[redis/01-入门阶段-基础教程/第03章-Python客户端redis-py/3.2-操作五种数据类型]]：pipeline 把 N 条命令攒在客户端、一次发出、一次收回全部响应。收益：

```
串行:  RTT + RTT + ... + RTT   = N × RTT
管道:  RTT + 服务端处理 N 条    ≈ 1 × RTT
```

两个本质限制：

1. **仍是逐条执行**：服务端还是排队逐条处理，单条命令的语义没变（这是它与事务/Lua 的分界，见 [[redis/02-中段阶段-生产实践/04-事务与Lua脚本]] 的选型表）。
2. **整批缓冲**：客户端与服务端都要为整批分配缓冲区。**一批发几万条**会撑爆缓冲（客户端内存 + 服务端 client-output-buffer），正确粒度是 **几百到一千条一批，多批循环**。

### 什么时候用 MGET/MSET，什么时候用 pipeline

| 场景 | 用 |
|------|-----|
| 批量读写**简单 String** | `MGET`/`MSET`（一条命令搞定，最省） |
| 批量操作**不同类型/不同命令**（`GET` + `HGETALL` + `ZREVRANGE` 混合） | pipeline |
| 需要每条命令的独立结果 | pipeline（结果按序返回） |

### redis-py 8.x 的默认值影响（复习 + 深化）

| 默认值 | 数值 | 性能含义 |
|--------|------|----------|
| `socket_timeout` | 5s | 慢命令 5 秒必抛超时——定位问题而不是调大它 |
| `max_connections` | 100 | 并发 > 100 且无空闲连接时排队/报错；Web 服务按"并发 × 2"估 |
| 重试 | 10 次指数退避 | 网络抖动自动吸收，但**写命令的重试要注意幂等**（`INCR` 重试会多加一次！） |

> redis-py 的默认重试策略只对**连接级错误**重试；理解你所用版本的重试边界，计数类命令务必幂等设计。

## 三、实操：性能排查四板斧

### 1. SLOWLOG：抓慢命令（服务端视角）

```bash
CONFIG SET slowlog-log-slower-than 10000   # 记录 >10ms 的命令（微秒单位）
CONFIG SET slowlog-max-len 256
SLOWLOG GET 10                             # 最近 10 条：命令、耗时、来源 IP
SLOWLOG RESET
```

服务端记录的是**命令执行耗时**（不含网络）。SLOWLOG 空 + 应用还是慢 → 问题在网络或客户端。

### 2. 大 key 扫描

```bash
redis-cli --bigkeys                        # 采样扫描各类型的最大 key（低影响）
MEMORY USAGE 某key                          # 精确查某个 key 占多少字节
redis-cli --memkeys                        # 按内存排序找大户
```

大 key 的三宗罪复习：读传输大、写阻塞、删除卡顿（`UNLINK` 缓解，见 [[redis/01-入门阶段-基础教程/第02章-过期机制与通用Key命令/2.2-通用Key命令与SCAN]]）。

### 3. LATENCY 监控

```bash
CONFIG SET latency-monitor-threshold 100   # 记录 >100ms 的事件
LATENCY HISTORY event                      # 某事件（如 fork）的历史
LATENCY LATEST
```

它专抓**服务端停摆事件**：fork（RDB/AOF 重写，见 [[redis/02-中段阶段-生产实践/01-持久化-RDB与AOF]]）、过期键集中清理、命令队列拥堵。

### 4. 基准压测

```bash
redis-benchmark -h 主机 -p 6379 -c 50 -n 100000 -d 64 get set
# -c 并发连接数，-n 总请求数，-d value 字节数；先测基线，容量规划与故障对比都有据可依
```

## 四、生产实践：三条性能守则

### 守则 1：热路径禁止 N+1 查询

典型反模式（页面要展示 50 个用户）：

```python
# ✗ N+1：50 次 RTT，同机房也要 ~25ms
users = [r.get(f"user:{i}") for i in ids]

# ✓ 一次 MGET
values = r.mget([f"user:{i}" for i in ids])

# ✓✓ 混合类型用 pipeline，一批 ≤ 500
with r.pipeline(transaction=False) as pipe:
    for i in ids:
        pipe.hgetall(f"profile:{i}")
    profiles = pipe.execute()
```

### 守则 2：给连接池设置正确的规模

```python
pool = redis.ConnectionPool(
    host="...", decode_responses=True,
    max_connections=并发数 × 2,     # 例：Web worker 50 并发 → 100
    socket_timeout=2,              # 明确表达"超过 2 秒就是故障"
)
```

池耗尽的表现：请求突然排队变慢、日志出现取连接超时。**先看应用日志再怪 Redis。**

### 守则 3：监控三个水位

| 指标 | 命令 | 报警线（参考） |
|------|------|----------------|
| 慢查询增速 | `SLOWLOG LEN` / 定期拉取 | 新增持续 > 0 |
| 内存水位 | `INFO memory` 的 `used_memory_human` / `maxmemory` | > 70% |
| 连接与拒绝 | `INFO stats` 的 `rejected_connections`、`evicted_keys` | > 0 |

## 五、陷阱

1. **pipeline 攒几万条**：缓冲区爆 + 失败整批重发代价巨大。分批 ≤ 1000。
2. **阻塞命令进 pipeline**：`BLPOP` 等 block 语义与打包不兼容，混用行为不可预测。
3. **跨 slot 的 pipeline 在集群上**：集群模式下 pipeline 按 slot 分发，redis-py 集群客户端会自动拆分，但收益打折；大批量按 hash tag 分组（见 [[redis/02-中段阶段-生产实践/08-高可用-主从哨兵集群]]）。
4. **用 `KEYS` 代替 SCAN 做"统计"** → 卡死服务（入门铁律复习）。生产统计一律 `SCAN` + pipeline 批量取值。
5. **benchmark 数字直接当容量承诺**：`redis-benchmark` 测的是极限，真实业务混有慢命令、大 value、过期清理，容量按实测峰值 × 2 留余量。
6. **把 `socket_timeout` 调到 30s "解决超时"**：超时是症状不是病根；调大只是让故障持续更久。先 SLOWLOG 定位。

---

## 小结

- 延迟大头在 RTT：命令数是第一杠杆（MGET > pipeline > 并发 > 串行）
- pipeline 一批 ≤ 1000；阻塞命令不进 pipeline
- 排查四板斧：SLOWLOG（慢命令）→ --bigkeys（大 key）→ LATENCY（停摆事件）→ redis-benchmark（基线）
- 监控三水位：慢查询、内存、连接

## 练习

1. 用 redis-py 分别以"串行 500 次 GET"与"pipeline 500 次"取数，测耗时差（同机也应差 10 倍以上）。
2. `CONFIG SET slowlog-log-slower-than 0`（全记录）后执行几条命令，用 `SLOWLOG GET` 解读每列含义，记得改回阈值。
3. 跑 `redis-cli --bigkeys`，检查你练习阶段造的数据里有没有大 key 苗子。
