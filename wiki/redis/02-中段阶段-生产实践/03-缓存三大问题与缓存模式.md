## 一、Cache-Aside：缓存的标准姿势

**旁路缓存（Cache-Aside）** 是最通用、默认该用的缓存模式——应用自己维护缓存与数据库的同步：

```
读：
  1. 查 Redis → 命中，直接返回
  2. 未命中 → 查 PostgreSQL → 写回 Redis（带 TTL）→ 返回

写：
  1. 更新 PostgreSQL
  2. 删除缓存（DEL），而不是更新缓存
```

### 为什么写时是"删"而不是"更新"

| 方案 | 问题 |
|------|------|
| 更新缓存 | ① 缓存的值可能是**计算/聚合结果**，每次写都重算浪费；② 两个写请求并发时，"更新缓存"的顺序可能与"更新数据库"的顺序**相反**，缓存永久停留旧值（无 TTL 救场时） |
| 删除缓存 | 下次读未命中自然回填最新值；并发写最多导致一次额外的回源读，**不会停留脏数据**（配合 TTL 兜底） |

**"先更新库，再删缓存"** 是标准顺序。它的残留风险窗口极小（读请求恰好在"库已更新、缓存未删"之间读旧缓存），一般业务可接受；要求更强的场景用**延迟双删**（见第五节）。

### redis-py 模板

```python
import json

def get_user(uid: int):
    key = f"user:{uid}"
    cached = r.get(key)
    if cached is not None:
        return json.loads(cached)                     # 命中
    user = db.query_user(uid)                         # 回源
    if user is None:
        r.set(key, "", ex=60)                         # ★ 空值缓存，防穿透（见下）
    else:
        r.set(key, json.dumps(user), ex=1800)         # TTL 兜底一致性
    return user

def update_user(uid: int, **fields):
    db.update_user(uid, **fields)                     # 先库
    r.delete(f"user:{uid}")                           # 后删缓存（UNLINK 更稳）
```

## 二、三大问题：穿透、击穿、雪崩

三者的记忆框架——**问的都是"缓存没拦住，流量打到数据库"**，但层次完全不同：

| 问题 | 成因 | 层次 | 典型解法 |
|------|------|------|----------|
| **穿透** | 查询的数据**在数据库里也不存在**，缓存永远无法回填 → 每次都穿透到库 | 恶意/异常请求 | ① 空值缓存 ② 布隆过滤器 ③ 参数校验 |
| **击穿** | **某个热点 key** 恰好过期，瞬时高并发同时回源 | 单点热 key | ① 互斥重建（只放一个请求去查库）② 逻辑过期 ③ 热点永不过期 |
| **雪崩** | **大批 key 同时过期**（或 Redis 整体不可用），数据库被洪峰冲垮 | 全局性 | ① TTL 加随机抖动 ② 多级缓存 ③ 熔断限流兜底 |

### 穿透：空值缓存 + 布隆过滤器

```python
if user is None:
    r.set(key, "", ex=60)     # 空值也缓存 60 秒：同样的恶意查询 60 秒内打不到库
```

- **空值缓存**简单有效，代价是可能缓存大量垃圾键（TTL 要短）。
- **布隆过滤器**（Bloom Filter，`Redis 8.x` 内置 BF 系列，旧版需 RedisBloom 模块）：把"存在哪些 ID"预放进一个概率结构，查询前先问它——**它说不存在就一定不存在**，直接拒绝，连库和 Redis 都不用碰。误判率可配置（存在误报"可能存在"，无漏报"说不存在必真不存在"）。适合 ID 空间大、恶意扫描明显的场景。

### 击穿：互斥重建

```python
def get_hot(key, rebuild_fn, ttl=3600):
    val = r.get(key)
    if val is not None:
        return json.loads(val)
    # 未命中：抢重建锁（SET NX EX = 只放一个请求回源）
    got = r.set(f"lock:rebuild:{key}", "1", nx=True, ex=10)
    if got:
        try:
            data = rebuild_fn()               # 只有我查库
            r.set(key, json.dumps(data), ex=ttl)
            return data
        finally:
            r.delete(f"lock:rebuild:{key}")
    else:
        time.sleep(0.05)                      # 没抢到的稍等再读缓存
        return json.loads(r.get(key) or "null")
```

- **互斥重建**：保证同一时刻只有一个请求回源，其余等它回填。
- **逻辑过期**：值里带过期时间字段，物理上不过期；读到"逻辑过期"的值先返回旧值，同时异步触发重建——**不阻塞读**，代价是短暂返回旧数据。热点数据（如首页榜单）优先用这个。

### 雪崩：TTL 抖动 + 分层兜底

```python
ttl = 3600 + random.randint(0, 600)    # 基础 1h + 0~10min 随机抖动
```

- **TTL 抖动**把"同一秒集体过期"打散成缓慢漏斗——一行代码解决一大类雪崩。
- **多级缓存**：本地进程缓存（如 Python dict / cachetools）→ Redis → 数据库，Redis 挂掉时本地层还能撑一段。
- **兜底**：数据库前加限流熔断（应用层职责）；Redis 本身的高可用见 [[redis/02-中段阶段-生产实践/08-高可用-主从哨兵集群]]。

## 三、一致性的残留问题与延迟双删

"先更新库再删缓存"在**读并发 + 写并发**同时发生时，有一个极小概率的脏窗口：

```
读 A：缓存未命中 → 查库得旧值
写 B：更新库（新值）→ 删缓存
读 A：把旧值写回缓存      ← 脏数据停留至 TTL
```

**延迟双删**：写操作在"更新库 + 删缓存"之后，**延迟一小段（数百 ms ~ 1s）再删一次**，把 A 这种"在途回填"的脏数据清掉：

```python
def update_user(uid, **fields):
    db.update_user(uid, **fields)
    r.delete(f"user:{uid}")
    schedule(delay=1.0, lambda: r.delete(f"user:{uid}"))   # 异步二次删（定时任务/队列）
```

**认知定位**：缓存与数据库是**两个存储**，没有分布式事务就没有绝对一致。工程目标是：① 脏窗口尽量小 ② TTL 保证最终一致（**缓存永远要有 TTL**）③ 强一致的数据根本不该进缓存。

## 四、落到你的 Agent 场景

| 缓存对象 | Key 设计 | TTL 策略 | 三大问题对应 |
|----------|----------|----------|--------------|
| **LLM 响应**（prompt 哈希 → 回复） | `llm:{sha256(模型+参数+prompt)}` | 长 TTL（小时级）+ 抖动 | 击穿：热门 prompt 互斥重建 |
| **embedding**（文本哈希 → 向量） | `emb:{模型}:{sha256(文本)}` | 永久或超长（向量不变可长存） | 天然免疫穿透（查过的才存） |
| **RAG 检索结果** | `rag:{query哈希}:{过滤器}` | 分钟级（知识库会更新） | 雪崩：批量预热时必须加抖动 |
| **会话对象** | `session:{id}`（Hash） | 滑动续期（`EXPIRE ... GT`） | —— |

两个 Agent 场景特有的提醒：

1. **LLM 缓存的 key 必须包含全部影响输出的参数**（模型名、温度、system prompt 版本），否则返回错配的旧回复——这类 bug 极难排查。
2. **embedding 缓存是收益最高的缓存**：embedding 计算贵且确定性（同文本同向量），命中即省一次模型调用；注意 value 是二进制向量，用独立 `decode_responses=False` 客户端（复习 [[redis/01-入门阶段-基础教程/第03章-Python客户端redis-py/3.2-操作五种数据类型]] 陷阱 6）。

## 五、陷阱

1. **缓存了"永远不查第二次"的数据** → 缓存命中率低还占内存。上线前明确缓存对象的读放大倍数（读远多于写才值得缓存）。
2. **TTL 忘记加抖动** → 定时任务批量预热的数据在同一秒集体过期（人为制造雪崩）。
3. **空值缓存没有 TTL** → 垃圾键永久占用，穿透变成了内存泄漏。
4. **删缓存用 `DEL` 遇到大 value** → 删除卡顿，用 `UNLINK`。
5. **"先删缓存再更新库"** → 删除后、库更新前的读请求把旧值回填，脏数据必现。顺序是铁律：**先库后删**。
6. **布隆过滤器当真理**：它说"可能存在"可能是误报，仍要走正常查询；只有"不存在"可直接拒绝。且过滤器**不支持删除**（计数布隆/ cuckoo 除外），集合变化大的场景慎用。

---

## 小结

- Cache-Aside：读 = 缓存→库→回填；写 = 先库后**删**缓存；TTL 是一致性的最后兜底
- 穿透（数据不存在）：空值缓存 + 布隆过滤器；击穿（热点过期）：互斥重建 / 逻辑过期；雪崩（集体失效）：TTL 抖动 + 多级 + 兜底
- 延迟双删处理在途回填；绝对一致不存在，强一致数据不进缓存
- Agent 场景：embedding 缓存收益最高；LLM 缓存 key 必须含全部影响参数
