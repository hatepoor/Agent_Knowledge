## 一、机制层：为什么必然存在不一致窗口

先建立一个**必须刻进脑子的认知**：缓存（Redis）和数据库（PostgreSQL）是**两个独立的存储系统**，写操作要改两个地方，而"改两个地方"这个动作**不是原子的**——中间任何时刻都可能被并发请求插入。

一切缓存一致性方案，都是在回答同一个问题：**这个非原子的"两次写入"，谁先谁后、失败了怎么办、被并发插队了怎么办。**

### 四种写序推演

把"写缓存（W-R）/ 删缓存（D-R）"与"更新库（W-DB）"的先后顺序穷举，用"并发读请求 R 插在哪里"来检验：

| 写序 | 并发场景 | 后果 | 结论 |
|------|----------|------|------|
| ① 先删缓存，再更新库 | R 在**两步之间**到达 | R 发现缓存没有 → 查库（旧值）→ 把**旧值回填**进缓存；写流程随后才更新库 → **脏数据停留到 TTL** | **必现脏数据**（只要写时有读），最差方案 |
| ② 先更新库，再删缓存 | R 在"库已更新、缓存未删"的间隙读到旧缓存 | R 返回**一次**旧值；缓存随即被删，下次读回填新值 | 残留窗口极小（毫秒级），且**不留存**脏数据 |
| ③ 先更新库，再更新缓存 | 两个写并发 A、B | A 先写库、B 后写库，但 B 先写缓存、A 后写缓存 → 缓存停留 **A 的旧值** | 写序在两边可能相反（复习 03 第一节），弃用 |
| ④ 更新库 + 更新缓存（同一事务里） | —— | Redis 不参与数据库事务；跨系统没有分布式事务 | 概念不成立 |

**结论（标准答案）**：② 先更新库、再删缓存。① 的脏数据是"必现 + 长期停留"，② 的旧值是"偶现 + 一次性的"——工程上无可争议。

### 标准写序的残留窗口

② 仍有两个残留问题，**形态不同，对策不同**：

```
形态一（在途回填）：
  读 R：缓存未命中 → 查库拿到旧值（还没来得及写回缓存）
  写 W：更新库 → 删缓存（此时缓存本来就没有，删了个寂寞）
  读 R：把旧值写回缓存            ← 脏数据停留到 TTL

形态二（删除失败）：
  写 W：更新库成功 → DEL 缓存时网络抖动/进程崩溃 → 缓存停留旧值到 TTL
```

形态一是**时序竞争**，概率极低（要求读请求"查库"和"回填"两步恰好横跨整个写流程）；形态二是**故障**，概率取决于网络质量。TTL 是两者共同的最后防线——这也是"**缓存必须永远有 TTL**"这条铁律的由来（复习 03 陷阱 3）。

## 二、形态一对策：延迟双删的正确打开方式

延迟双删在 03 第五节已给出骨架，本篇补生产细节。

### 延迟时间怎么定

**不要拍脑袋定 500ms。** 延迟的目的是等"在途读请求"结束，因此在途请求的最长耗时 = 它的查询链路耗时。生产上依据：

```
延迟时间 ≈ 业务读请求 P99 耗时（查库 + 回填整段）
         或 主从复制延迟 P99（读写分离场景，见第四节）
取两者较大值，再留 50% 余量。
```

典型量级：单库直查 P99 通常 < 100ms，取 500ms 已很保守；读写分离场景看复制延迟监控（第八节 `master-repl_offset` 差值）。

### 异步实现（不能阻塞写请求）

二次删必须**异步**，否则写接口平白多一次 RTT 等待：

```python
import threading

def update_user(uid: int, **fields):
    db.update_user(uid, **fields)          # 1. 先库
    r.delete(f"user:{uid}")                # 2. 删缓存
    threading.Timer(
        1.0, r.delete, args=(f"user:{uid}",)
    ).start()                              # 3. 1 秒后异步二删
```

进程内 `threading.Timer` 的局限：**进程重启则二次删丢失**。要求更高的场景把"延迟删"丢进消息队列（见第三节方案 A），或直接用 binlog 订阅（方案 B）。

## 三、形态二对策：删除失败的兜底体系

删缓存失败 = 数据库已新、缓存仍旧，若不处理，脏数据停留到 TTL。三个方案按复杂度递增：

### 方案 A：重试队列（应用层，推荐起步方案）

删除失败时把"待删的 key"写进 Stream，由独立消费者重试：

```python
def delete_cache_with_retry(r, key: str, retry_stream="cache:del:retry"):
    try:
        r.delete(key)
    except redis.RedisError:
        # Redis 都连不上时，这个重试本身也进不了队列——退化为依赖 TTL
        r.xadd(retry_stream, {"key": key})

# 重试消费者（独立进程/协程）
def retry_consumer(r, retry_stream="cache:del:retry", group="retrier", consumer="c1"):
    try:
        r.xgroup_create(retry_stream, group, id="0")
    except redis.ResponseError as e:
        if "BUSYGROUP" not in str(e):
            raise
    while True:
        msgs = r.xreadgroup(group, consumer, {retry_stream: ">"},
                            count=10, block=5000)
        for _, entries in msgs:
            for msg_id, fields in entries:
                r.delete(fields["key"])
                r.xack(retry_stream, group, msg_id)
```

注意一个诚实的边界：**如果 Redis 本身不可达，重试队列也用不了**——这时唯一兜底就是 TTL。重试队列解决的是"Redis 活着但那次 DEL 抖动"的概率问题。

### 方案 B：binlog 订阅（中间件层，多服务统一方案）

**binlog** 是数据库（MySQL 的 binlog、PostgreSQL 的 WAL 逻辑解码）记录每一行变更的日志流。用 **Canal**（MySQL 生态）或 **Debezium**（多库生态，支持 PostgreSQL）伪装成数据库的从库订阅变更，把"某行变了"翻译成"删哪个缓存 key"：

```
写请求 → 只更新数据库（不再管缓存）
                      │ binlog/WAL
                      ▼
              Canal / Debezium
                      │ 解析变更 → 规则映射出缓存 key
                      ▼
              统一删缓存服务 → Redis
```

| 维度 | 方案 A（重试队列） | 方案 B（binlog 订阅） |
|------|-------------------|----------------------|
| 一致性触发点 | 业务代码显式删，**实时** | 数据真正落库后订阅到，**准实时**（秒级延迟） |
| 业务侵入 | 每个写点都要写删缓存 | **业务代码零缓存逻辑**，只更新库 |
| 覆盖范围 | 只覆盖"记得写"的代码路径 | 库里任何变更（包括手工修数、其他服务写入）都会触发 |
| 复杂度 | 低（复用 Stream） | 高（要部署维护中间件 + key 映射规则） |
| 适用 | 单服务、写点少 | 多服务共享一库、要求"改数必失效" |

**选型口诀**：起步用 A，多服务/强失效诉求上 B；上了 B 就**删掉业务代码里的双删**，两套并存会出现"订阅删完、手写双删又回填"的时序互搏。

## 四、主从复制延迟带来的新窗口

读写分离架构下（复习 [[redis/02-中段阶段-生产实践/08-高可用-主从哨兵集群]]），一致性多出一个环节：

```
写：更新库 → 删 Redis 主库缓存 → 复制到从库（有延迟）
读：未命中 → 从"从库读数据"回填 —— 若复制/同步链路慢，回填的可能是旧值
```

注意这里读旧值的来源是**数据库从库的旧数据**（或 Redis 主从间删除指令的传播延迟），与第一节的在途回填叠加。对策：

1. **"读己之写"路由**：用户写完自己立刻读的请求（如改完昵称看主页），强制走主库（数据库与 Redis 都读主），避免读到从库旧值。按会话标记路由，不是全局切换。
2. **`WAIT` 的适用边界**：Redis 的 `WAIT n 毫秒`（复习 08）等 n 个从库确认才返回，可缩短 Redis 层的删除传播窗口；但它是同步等待，牺牲写延迟换一致性，只用于关键少数 key。
3. **TTL 缩短**：读写分离 + 强时效场景，把这类 key 的 TTL 从小时级降到分钟级，缩小暴露面。

## 五、一致性等级决策表：什么数据能进缓存

不是所有数据都值得为一致性折腾。按业务容忍度分级：

| 等级 | 业务例子 | 缓存策略 |
|------|----------|----------|
| 强一致（写后必须立刻读到） | 库存扣减、账户余额 | **不进缓存**，或只做只读视图缓存 |
| 准实时（秒级延迟可接受） | 用户资料、商品详情 | 先库后删 + 延迟双删；要求高上 binlog 订阅 |
| 最终一致（分钟级可接受） | 排行榜、统计聚合 | 先库后删 + 长 TTL 兜底即可 |
| 只读/近只读 | 历史订单、embedding 向量 | 长 TTL 甚至永久，几乎无一致性问题 |

**本篇的工程目标重申**（复习 03 认知定位）：脏窗口尽量小 + TTL 保证最终一致 + 强一致数据不进缓存。绝对一致不存在，方案选到业务够用即止。

## 六、陷阱

1. **双删延迟拍脑袋定值**：不看读链路 P99 / 复制延迟监控，"听说 500ms 就 500ms"。延迟的依据是"在途请求何时结束"，用监控定。
2. **上了 binlog 订阅还保留手写双删**：两套失效机制时序互搏——订阅服务刚删完，业务侧的延迟二删把"订阅间隙读到的旧值"又回填进去。**一套为准，另一套下线。**
3. **重试队列不设上限**：某 key 反复删除失败（如 key 模式写错），在 Stream 里无限堆积。重试 N 次（如 5 次）仍失败就进死信并告警（死信模式见 [[redis/02-中段阶段-生产实践/12-Agent场景实战-缓存会话与任务分发]]）。
4. **删缓存用了 `DEL` 遇到大 value**：删除本身卡顿，还拉长"库已新、缓存未删"窗口。一律 `UNLINK`（复习 [[redis/02-中段阶段-生产实践/10-大Key与热Key治理]]）。
5. **把 binlog 订阅延迟当零**：Canal/Debezium 是准实时（百 ms 到秒级）。刚更新完立刻读，仍可能读旧缓存——这是方案 B 的固有属性，业务要"读己之写"时按第四节路由。
6. **为"绝对一致"层层加码**：双删 + 重试 + binlog + WAIT 全上，一致性没多多少，复杂度和故障面翻倍。先明确业务一致性等级（第五节），只取对应档位的方案。

## 小结

- 先库后删是四种写序里唯一可用的标准序；残留问题只有两个形态：在途回填（时序）与删除失败（故障）
- 在途回填 → 延迟双删（延迟按读链路 P99 定，异步执行）；删除失败 → 重试队列或 binlog 订阅
- binlog 订阅（Canal/Debezium）实现"业务零缓存逻辑"，但准实时且复杂；上了一套就下掉另一套
- 读写分离下新增"从库旧值"窗口：读己之写走主库，`WAIT` 用于关键少数
- 一切方案的最终兜底是 TTL；强一致数据不进缓存

## 练习

1. 用两个终端复现形态一：一个终端跑"查库（sleep 2 秒模拟）→ 回填"，另一个在其间完成"更新库 + 删缓存"，观察旧值被回填；再接入延迟双删验证脏数据被清掉。
2. 把第二节 `threading.Timer` 版双删改造成方案 A 的 Stream 重试版，并手工 `iptables`/断网模拟一次 DEL 失败，验证重试消费者能补删。
3. 给你的项目写"一致性等级表"：列出所有缓存对象，标注等级与所采用的方案档位——写不出来的对象多半是"忘了它有缓存"。
