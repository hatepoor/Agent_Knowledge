## 一、三级架构：每级解决一个问题

| 架构 | 解决的问题 | 没解决的问题 |
|------|-----------|--------------|
| **主从复制**（replication） | 数据冗余：主挂了数据在从库还在；读多写少时分担读压力 | 主挂了要**人工**提升从库、改客户端配置 |
| **哨兵**（Sentinel） | 在主从之上加**自动故障转移**：探活、选举、提升、通知客户端 | **容量**仍受单机内存限制；写吞吐单点 |
| **集群**（Cluster） | 数据**分片**到多节点：容量与写吞吐水平扩展 | 架构复杂度大幅上升；多 key 操作受限 |

**选型铁律：按需升级，不要跳级。** 单机能放下、挂了能容忍几分钟人工恢复 → 单机 + 备份就够；要自动恢复 → 主从 + 哨兵；内存装不下 / 写入单机扛不住 → 才考虑集群。

## 二、主从复制（机制层）

### 建立复制

```
# 从库执行（5.0+ 用 REPLICAOF，旧 SLAVEOF 仍可用）
REPLICAOF 192.168.1.10 6379
# 或配置文件：replicaof 192.168.1.10 6379
# 只读保护（从库默认）：replica-read-only yes
```

### 复制怎么工作

1. **全量复制**（首次或断链过久）：从库发 `PSYNC` → 主库 `BGSAVE` 生成 RDB → 传给从库 → 从库载入 → 主库把期间的写命令缓冲**增量补发**。
2. **部分复制**（短暂断线重连）：主库用**复制积压缓冲区**（`repl-backlog-size`，默认 1MB）记住最近的写命令；从库带着自己的复制偏移量（offset）重连，只要偏移量还在缓冲区范围内，只补发缺的那段——**这是断线恢复的快路径**。
3. **命令传播**：稳态下主库把每条写命令实时发给从库（**异步**——这就是一切"从库旧值"问题的根源）。

关键配置：

```conf
repl-backlog-size 64mb          # 断线容忍窗口：写流量大就调大，减少全量重连
min-replicas-to-write 1         # ★ 至少 1 个从库在线才接受写（防脑裂，见下）
min-replicas-max-lag 10         # 从库延迟 ≤10s 才算"在线"
```

### 两个必须理解的推论

1. **异步复制 → 从库读到旧值**：主库写入成功即对客户端返回，传播是异步的。读从库做读写分离时，刚写完立刻读从库可能读到旧数据（最终一致）。**缓解**：一致性敏感的读回主库；或 `WAIT 1 100`（等至少 1 个从库确认，`Redis 3.0+`，牺牲延迟换保障）。
2. **脑裂（split-brain）窗口**：主库与从库/哨兵之间网络分区，但与**部分客户端**仍通。客户端继续写旧主 → 哨兵提升新主 → 旧主降级为从并**清空数据同步新主**——分区期间写进旧主的数据**全丢**。`min-replicas-to-write` 就是为此设计的：没有足够健康的从库确认，主库拒绝写入，把"丢数据窗口"压到最小（不能完全消除）。

## 三、哨兵（Sentinel）：自动故障转移

哨兵是**独立进程**（`redis-sentinel` / `redis-server --sentinel`），通常**至少 3 个实例**（奇数、跨机），职责：

1. **监控**：持续 PING 主库与从库
2. **判定**：一个哨兵 ping 不通 = 主观下线（SDOWN）；**quorum 个**哨兵都认定 = 客观下线（ODOWN）
3. **选举与提升**：哨兵们选出一个 leader，从从库里挑数据最全的提升为新主（`replica-priority` 低者优先、offset 最大者优先）
4. **通知**：把新主地址通知其余从库（改挂新主）与**客户端**

### 最小可用部署（1 主 2 从 + 3 哨兵）

```conf
# sentinel.conf（三个哨兵实例各一份，端口 26379）
sentinel monitor mymaster 192.168.1.10 6379 2     # 主库名、地址、quorum=2
sentinel down-after-milliseconds mymaster 5000    # 5s 无响应判主观下线
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1                # 转移后从库逐个同步，避免同时打满主库
```

```bash
redis-sentinel /path/sentinel.conf
```

### 客户端怎么连哨兵（redis-py）

**应用不直连主库地址**，而是先问哨兵"主库现在是谁"：

```python
from redis.sentinel import Sentinel

sentinel = Sentinel([("s1", 26379), ("s2", 26379), ("s3", 26379)],
                    socket_timeout=0.5)
master = sentinel.master_for("mymaster", decode_responses=True)   # 自动发现主库
replica = sentinel.replica_for("mymaster", decode_responses=True) # 从库（读写分离用）

master.set("k", "v")      # 故障转移后，下次连接自动指向新主
```

哨兵客户端在连接失效时会**重新询问哨兵**并重连新主——这就是"自动"对应用侧的呈现。注意：**普通 `redis.Redis(host=主库IP)` 的代码在故障转移后会全部失效**，用哨兵就必须用 `master_for`。

## 四、集群（Cluster）：分片扩容

### 机制

- 16384 个**哈希槽（slot）**，按 `CRC16(key) % 16384` 决定键归属哪个节点；节点间 gossip 协议互通。
- 客户端连任意节点，键不在这个节点 → 返回 `MOVED` 重定向（智能客户端如 redis-py 集群模式会缓存槽位表直接直连）。
- **只有 db0**（键分布在多台机器，"第几个 db"失去意义——复习入门 1.1 的伏笔）。

### 多 key 命令的限制与 hash tag

`MGET k1 k2`、事务、Lua 若涉及的键在不同 slot → 报错 `CROSSSLOT`。解法：**hash tag**——键里 `{...}` 内的内容参与哈希，其余忽略：

```
user:1000:profile  与  user:1000:session
→ 用 {user:1000}:profile  与  {user:1000}:session
→ 两者必落同一 slot，多 key 操作可用
```

（这正是 [[redis/02-中段阶段-生产实践/04-事务与Lua脚本]] 里"键要显式列在 KEYS"的集群背景。）

### redis-py 集群客户端

```python
from redis.cluster import RedisCluster

rc = RedisCluster(host="node1", port=6379, decode_responses=True)
rc.set("k", "v")          # API 与普通客户端一致，路由自动处理
```

### 什么时候真的需要集群

| 信号 | 阈值参考 |
|------|----------|
| 内存 | 单机放不下（>25~50GB 且增长明显） |
| 写吞吐 | 单机持久化已到瓶颈（fork 卡顿、AOF 落盘饱和） |
| 风险隔离 | 不同业务想物理隔离 |

三条都不满足 → **主从 + 哨兵就是终点**，不要为了"看起来高级"上集群。多数中小系统（包括绝大多数 Agent 后端）止步于哨兵。

## 五、生产实践清单

| 项 | 标准 |
|----|------|
| 拓扑 | 主从 + 哨兵至少：1 主 2 从 + 3 哨兵，主从与哨兵**跨机/跨可用区** |
| 从库用途 | 读多写少时可读从库；一致性敏感读走主库（或 `WAIT`） |
| 脑裂防护 | `min-replicas-to-write 1` + `min-replicas-max-lag 10` |
| 复制缓冲 | `repl-backlog-size` 按写流量 × 断线容忍时长估算（默认 1MB 偏小） |
| 持久化 | **主从都开** AOF（主库挂了从库顶上，从库没有 AOF = 转移后数据回退） |
| 演练 | 每季度杀主库一次，验证哨兵转移时长与客户端恢复 |
| 监控 | `INFO replication` 的 `master_link_status`（从库）、`master_repl_offset` 差值（延迟） |

故障转移演练步骤：

```bash
# 1. 观察当前拓扑
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

# 2. 杀主库
docker stop redis-master

# 3. 等待 down-after + 选举提升（约 10~30s），再次询问哨兵
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster   # 地址应变为原从库

# 4. 恢复原主库（它将以从库身份重新加入）
docker start redis-master
```

## 六、陷阱

1. **读写分离时读到旧值** → 异步复制固有。一致性敏感读回主库；不要"写后立刻读从库"做校验逻辑。
2. **哨兵只有 2 个 / 都在同一台机器** → quorum 机制失去意义（那台机器挂 = 全部哨兵挂）。至少 3 个跨机。
3. **从库不开持久化** → 主库崩溃 + 哨兵提升后，新主是"空脑子"，全量数据丢失。从库也要 AOF。
4. **客户端直连主库 IP** → 故障转移后全挂。哨兵架构必须用 `master_for`（或支持哨兵的驱动）。
5. **`min-replicas-to-write` 当成零丢失保险** → 它只缩小窗口：从库"确认"也只是收到命令，不等于落盘。持久化仍是另一条腿。
6. **集群上用了无 hash tag 的多 key 命令/事务** → `CROSSSLOT` 报错。设计 key 时就把 `{tag}` 规划进去（后改代价大）。
7. **repl-backlog 默认 1MB 不调整** → 写入稍多时断线秒变全量复制，主库 fork + 全量传输雪崩式拖垮。

---

## 小结

- 复制 = 数据冗余（异步，从库会旧）；哨兵 = 自动换主（3 奇数跨机，客户端用 master_for）；集群 = 分片扩容（16384 slot、只有 db0、hash tag 解决跨 slot）
- 脑裂窗口靠 `min-replicas-to-write` 缩小，不能归零
- 按需升级：单机 → 主从哨兵（多数系统到此为止）→ 集群
- 从库也要持久化；定期演练故障转移
