## 一、为什么需要分布式锁（生产视角）

单机程序用线程锁（`threading.Lock`）互斥；但你的服务**多进程/多实例部署**时，线程锁只锁得住本进程——两个 pod 同时执行"清理过期会话"、同时抢一个定时任务，就需要一把**所有实例都认的锁**。Redis 凭单命令原子性，是最常用的锁实现底座。

典型的三类用途：

| 场景 | 锁保护的资源 | 备注 |
|------|--------------|------|
| 定时任务防重 | 任务执行权 | 多实例都挂了 cron，同一时刻只有一个跑 |
| 并发回源/重建 | 数据库 / 昂贵计算 | 缓存击穿的互斥重建（[[redis/02-中段阶段-生产实践/03-缓存三大问题与缓存模式]]）就是它的简化版 |
| 资源互斥 | 外部资源（文件、API 配额） | 如"同一账号同时只允许一个流程改配置" |

## 二、机制层：基础锁的三个零件与它们防的竞态

### 零件 1：`SET NX PX`——原子的"抢占"

```
SET lock:job1 <唯一值> NX PX 30000
```

- `NX`：已有人持有 → 返回 nil，抢占失败。**获取与设置过期一次完成**，避免"SET 成功但还没来得及 EXPIRE 就崩溃"的死锁。
- `PX 30000`：**锁必须有 TTL**。持有者崩溃后锁能自动释放——这是防死锁的底线，没有 TTL 的锁等于埋雷。

### 零件 2：唯一值——防止"删别人的锁"

为什么值要唯一（如 `实例ID:线程ID:uuid`）？场景：

```
A 拿到锁（TTL 30s）→ A 卡顿超过 30s → 锁自动过期 → B 抢到锁
A 恢复，执行 DEL lock:job1      ← 删掉的是 B 的锁！C 又能抢进来 → 两个持有者
```

值唯一 + 释放前校验"值是我的"就能防住。但 **GET + 判断 + DEL 是三条命令**，中间仍会插队——所以需要零件 3。

### 零件 3：Lua 释放——把"校验 + 删除"闭合为原子

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

复习 [[redis/02-中段阶段-生产实践/04-事务与Lua脚本]]：检查与动作之间的竞态只有脚本能闭合。

### 三个零件 = 最小正确实现（redis-py）

```python
import uuid, redis

r = redis.Redis(decode_responses=True)

UNLOCK = r.register_script("""
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
""")

def acquire(key, ttl_ms=30000):
    token = f"{uuid.uuid4().hex}"
    if r.set(key, token, nx=True, px=ttl_ms):
        return token          # 拿到锁，记住 token（释放凭证）
    return None

def release(key, token):
    return UNLOCK(keys=[key], args=[token]) == 1
```

**忘掉 token 等于没实现零件 2**——token 必须随调用链传递到释放点。

## 三、还没完：TTL 与执行时长的赛跑

基础锁有一个**结构性缺陷**：锁的 TTL 是预估的。业务执行超过 TTL → 锁提前失效 → 并发进入。三档应对：

| 档位 | 做法 | 代价 |
|------|------|------|
| ① 预估充足 TTL + 释放兜底 | 简单任务够用 | 执行波动大时不可靠 |
| ② **看门狗续期（watchdog）** | 后台线程每 TTL/3 自动 `PEXPIRE` 续期，持有期间锁永不过期；进程崩溃后无续期 → 锁按最后 TTL 自然释放 | 要自己管理续期线程的生命周期 |
| ③ fencing token | 锁带单调递增编号，下游资源校验"编号是不是最新的" | 下游存储必须支持校验，改造大 |

看门狗的续期也要防竞态（"还是我的锁才续期"），同样用 Lua：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
    return 0
end
```

### redis-py 内置 Lock：生产首选

```python
# redis-py 自带 Lock：含唯一 token、Lua 释放、阻塞等待、超时
lock = r.lock("lock:job1", timeout=30, blocking_timeout=5)
if lock.acquire():
    try:
        do_job()
    finally:
        lock.release()     # 非 token 持有者释放会抛 LockError，安全
# 或上下文管理器：
with r.lock("lock:job1", timeout=30, blocking_timeout=5):
    do_job()
```

| 参数 | 含义 |
|------|------|
| `timeout` | 锁 TTL（秒） |
| `blocking_timeout` | 最多等多久抢锁（超时抛 `LockNotOwnedError`/返回 False） |
| `thread_local`（默认 True） | token 与线程绑定，防线程间误释放 |

> redis-py 的 Lock **没有内置看门狗续期**。长任务要么定期手动 `lock.extend(expiration)` 续期，要么按档位①留足 TTL。Java 的 Redisson 才内置看门狗——别被跨语言教程误导。

## 四、根本局限与 Redlock 争议（认知层）

**Redis 单实例锁不是严格正确的互斥**：主从复制是**异步**的——A 在主库拿到锁后主库崩溃，锁还没复制到从库，提升后的新主库里锁不存在，B 又拿到锁 → 双持有。这不是实现 bug，是异步复制的固有属性。

**Redlock**（红锁，antirez 提出）：向 N 个（通常 5 个）**独立** Redis 主库同时加锁，多数派成功才算持有。**Martin Kleppmann 的著名批评**：Redlock 依赖时钟假设，在进程暂停（GC 停顿）、时钟跳变下仍可能双持有；而 fencing token 才是完备解。**工程结论**：

1. 效率型锁（防重复劳动，偶尔双跑无损失）→ 单实例 Redis 锁**足够**，别上 Redlock 的复杂度。
2. 正确性锁（双持有 = 资损/数据损坏）→ **不要用 Redis 锁**兜底，用支持 fencing 的资源端校验（数据库乐观锁版本号、条件更新）或换 ZooKeeper/etcd。
3. 绝大多数业务锁是效率型的——这就是 Redis 锁流行的原因，但要**知道自己属于哪一类**。

## 五、生产实践清单

| 检查项 | 标准 |
|--------|------|
| 锁粒度 | 锁**业务键**（`lock:import:doc:123`），不要全局一把大锁 |
| TTL | 按任务 P99 耗时 × 3 起步；长任务配续期 |
| 抢锁超时 | 必须有 `blocking_timeout`，无限等待会拖垮线程池 |
| 重试与抖动 | 抢锁失败加随机退避重试，防惊群 |
| 持有者记录 | 值里带实例标识，排查"谁占着锁"（`GET lock:x` 一眼看出） |
| 释放路径 | `finally` 里释放；释放失败记日志（锁会自然过期，不要死循环重试释放） |
| 双持有容忍 | 明确"锁只保证效率不保证正确"，正确性靠下游幂等/版本号 |

定时任务防重的最小可用形态（最多人用的场景）：

```python
def run_daily_job():
    token = acquire("lock:cron:daily", ttl_ms=10 * 60 * 1000)
    if token is None:
        log.info("另一实例在执行，跳过")
        return
    try:
        do_daily_job()
    finally:
        release("lock:cron:daily", token)
```

## 六、陷阱

1. **SET 与 EXPIRE 分两步** → SET 后崩溃 = 死锁。必须 `SET ... NX PX` 一体。
2. **无 TTL 的锁** → 持有者崩溃后全系统永久等待。任何锁都必须有过期时间。
3. **DEL 不校验值** → 删别人的锁，并发窗口打开。Lua 校验释放。
4. **token 用固定值**（如全实例都写 `"locked"`）→ 唯一值机制失效。
5. **业务超过 TTL 无续期** → 提前失效双持有。加长 TTL 或实现看门狗。
6. **拿 Redis 锁保护"强一致"操作** → 超出能力范围。正确性靠数据库版本号/条件更新兜底。
7. **锁内再嵌套 Redis 调用却没考虑阻塞** → 持锁期间的慢操作放大锁持有时间，加剧 TTL 赛跑。锁内代码要短、要设超时。

## 小结

- 基础锁三零件：`SET NX PX`（原子抢占 + TTL 防死锁）、唯一 token（防删错锁）、Lua 释放（闭合竞态）
- TTL 与执行时长的赛跑：简单任务留足 TTL；长任务看门狗续期；正确性要求高靠 fencing
- redis-py 用 `r.lock()`；它没有看门狗，长任务要 `extend()`
- 红线：Redis 锁是**效率锁**，不保证严格互斥；正确性依赖下游幂等与版本号
