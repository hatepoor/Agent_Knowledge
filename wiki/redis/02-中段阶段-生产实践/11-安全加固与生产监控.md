## 一、机制层：Redis 为什么"生来危险"

三个默认设定叠加，构成它的默认攻击面：

| 默认设定 | 含义 | 风险 |
|----------|------|------|
| **无密码** | 装完即可连接操作 | 任何人扫到端口就是管理员 |
| **信任内网** | 设计假设是"部署在可信内网" | 一旦暴露公网，防线为零 |
| **`dir` 可写 + `CONFIG SET dir`** | 可运行时改工作目录 | 经典勒索手法：攻击者改 `dir` 到 `/var/spool/cron`、`SET` 一条定时任务内容、`BGSAVE` 写盘 → 宿主机被种计划任务 |

因此有第一条铁律：**Redis 永远不裸露公网**。历史上一批 6379 端口暴露的实例在数小时内被扫描、清库、写入勒索数据。加固的层次：**网络隔离 → 认证 → 权限收敛 → 命令治理**，每层都有独立价值，缺一层就少一道墙。

## 二、网络层：第一道防线

```conf
# redis.conf
bind 127.0.0.1 192.168.1.10      # 只监听回环 + 内网网卡（空格分隔多个地址）
protected-mode yes                # 默认开：无密码且未显式 bind 时，拒绝非回环连接
port 6379
```

- **`protected-mode` 的语义**（易误解）：它不是防火墙——**只要配了密码（或 ACL 生效）或显式 bind，它就放行**。它只是"忘了配置"时的最后提醒，不能当认证用。
- **云上部署**：安全组只放行业务网段；**绝不对 0.0.0.0/0 开 6379**。
- **Docker 部署的映射纪律**：

```bash
# ✗ 映射到所有网卡 —— 等于帮 Redis 绕过宿主机防火墙直接上公网
docker run -d -p 6379:6379 redis:8.2

# ✓ 只映射到本机回环，应用走宿主机内网访问
docker run -d -p 127.0.0.1:6379:6379 redis:8.2
```

## 三、认证与 ACL：最小权限

### 遗留方式 `requirepass`

```conf
requirepass 一个强密码
```

单密码全权限，所有业务共享一个口令，改密码要通知所有人——**只建议在单服务自用的小实例上用**。它等价于给内置的 `default` 用户设密码（`ACL` 视角，见下）。

### ACL：用户 - 密码 - 权限三元组（`6.0+`）

**ACL（Access Control List，访问控制列表）** 把"谁能连、连上能操作哪些 key、能执行哪些命令"三者绑定到**具名用户**上：

```bash
# 创建业务账号：启用 + 密码 + 只能动 cache:* 的 key + 读写类命令 + 禁危险类
ACL SETUSER appuser on >S3cure-Pass! ~cache:* ~session:* +@read +@write -@dangerous

# 创建只读账号（报表/运维排查用）
ACL SETUSER viewer on >Another-Pass! ~* +@read

# 查验
ACL LIST            # 所有用户规则
ACL GETUSER appuser # 单用户详情
ACL CAT             # 命令分类（@read @write @dangerous @admin ...）
ACL CAT dangerous   # 看看"危险类"里都有谁
ACL WHOAMI          # 当前连接是谁
ACL SAVE            # 持久化到 aclfile（否则重启丢失）
```

逐段拆解 `ACL SETUSER` 语法（**从左到右读**）：

| 片段 | 含义 |
|------|------|
| `appuser` | 用户名 |
| `on` | 启用（`off` 禁用） |
| `>密码` | 添加密码（`<密码` 移除；可多条，换密码时先 `>` 新后 `<` 旧实现平滑轮换） |
| `~cache:*` | **key 模式白名单**：只能操作匹配的 key（多模式用多个 `~`） |
| `+@read` / `+@write` | 授予命令**类别**（也可 `+GET` 精确到单命令） |
| `-@dangerous` | 拒绝危险类别（`FLUSHALL`/`KEYS`/`CONFIG`/`SHUTDOWN` 等都在其中） |

配套配置：

```conf
# redis.conf —— 用独立文件管理用户，便于版本化
aclfile /etc/redis/users.acl

# 客户端登录方式
redis-cli --user appuser --pass 'S3cure-Pass!'
```

### 主从 / 哨兵架构下的认证

```conf
# 从库配置：连主库用的账号（复习 08）
masteruser appuser
masterauth S3cure-Pass!
# 哨兵监控也要带认证（sentinel.conf）
sentinel auth-pass mymaster S3cure-Pass!
```

### 内置 `default` 用户必须处理

ACL 生效后，**`default`（即无用户名登录）仍是无密码全权限**——加固不完整等于没加固。二选一：

```bash
ACL SETUSER default on >强密码 ~* +@all     # ① 给 default 设密码（兼容旧客户端）
ACL SETUSER default off                     # ② 直接禁用 default（推荐，逼所有人用具名账号）
```

## 四、危险命令治理

| 命令 | 危害 | 治理 |
|------|------|------|
| `KEYS` | O(N) 阻塞（复习入门铁律） | ACL 禁用 |
| `FLUSHALL` / `FLUSHDB` | 清库 | ACL 禁用 |
| `CONFIG SET` | 运行时改配置（含 `dir`，勒索入口） | 仅运维账号可用 |
| `SHUTDOWN` | 停服 | ACL 禁用 |
| `MONITOR` | 实时输出全部命令流，拖垮性能且泄露数据 | ACL 禁用 |
| `DEBUG` | 暴露内部操作（`DEBUG SLEEP` 可挂起） | ACL 禁用 |

**治理路线二选一**：

1. **ACL 类别禁用（推荐）**：账号按需 `+@read +@write -@dangerous`，粒度可到单命令（`-CONFIG`），且 `ACL LOG` 能**审计**被拒的命令尝试（`ACL LOG` 最近 128 条违规记录）。
2. **`rename-command`（遗留方式）**：

```conf
rename-command FLUSHALL ""
rename-command KEYS ""
```

把命令改名成空串即"物理删除"。缺点：运维工具、监控脚本、教学文档里该命令全部失灵，且**无审计**。新项目一律走 ACL。

## 五、传输加密与运行环境

- **TLS（`6.0+`）**：跨不可信网络（公网、跨机房专线）必须开：

```conf
port 0                      # 关闭明文端口
tls-port 6379
tls-cert-file /etc/redis/tls/server.crt
tls-key-file  /etc/redis/tls/server.key
tls-ca-cert-file /etc/redis/tls/ca.crt
```

```python
r = redis.Redis(host="redis.example.com", port=6379,
                ssl_cert_reqs="required",
                ssl_ca_certs="/etc/redis/tls/ca.crt")
# redis-py 8.x 默认协议 RESP3，TLS 连接同样可用
```

内网同机房部署可不开 TLS（有毫秒级 CPU 开销），但要写进架构决策记录。

- **运行环境**：不用 root 跑 `redis-server`；宿主机关闭透明大页（THP，避免 fork 延迟抖动，复习 01）与 `vm.overcommit_memory=1`（RDB/COW 保护，复习 07 的内存余量纪律）。

## 六、监控体系：INFO 全景与告警

`INFO` 按段输出服务状态（05 已用 `memory`/`stats` 三水位，这里是全集关键项）：

### 各段关键指标表

| 段 | 字段 | 含义 | 告警参考 |
|----|------|------|----------|
| `clients` | `connected_clients` | 当前连接数 | 接近 `maxclients`（默认 10000） |
| | `blocked_clients` | 阻塞中的连接（`BLPOP` 等） | 持续增长需关注 |
| `memory` | `used_memory_human` / `mem_fragmentation_ratio` | 数据水位 / 片化（详解在 07） | > 70% / > 1.5 |
| `stats` | `keyspace_hits` / `keyspace_misses` | 命中 / 未命中次数 → **命中率 = hits / (hits+misses)** | 缓存实例 < 80% 查原因 |
| | `instantaneous_ops_per_sec` | 当前每秒操作数 | 突降 = 故障；持续新高 = 容量评审 |
| | `rejected_connections` | 因 `maxclients` 被拒的连接 | **> 0 即告警** |
| | `evicted_keys` | 淘汰键数（07 详解） | 存储场景 > 0 即事故 |
| | `latest_fork_us` | 最近一次 fork 耗时（微秒） | > 100000（100ms）关注实例体积 |
| `persistence` | `rdb_last_save_time` / `rdb_changes_since_last_save` | 上次快照 / 其后变更数 | 变更数持续巨大 = 快照没跟上 |
| | `aof_last_bgrewrite_status` / `aof_last_write_status` | AOF 重写 / 写入状态 | `ok` 之外即告警 |
| `replication` | `role` / `master_link_status` | 角色 / 从库连主状态 | `down` 即告警（08） |
| | `master_repl_offset` 与 `slave_repl_offset` 差值 | 复制延迟（字节） | 持续拉大关注 |

### redis-py 定时采集（Python 栈的自建监控起步）

```python
import time
import redis

def collect(r: redis.Redis) -> dict:
    info = r.info()                      # 不传段名 = 全部段落
    hits, misses = info["keyspace_hits"], info["keyspace_misses"]
    return {
        "ts": time.time(),
        "mem_pct": info["used_memory"] / max(info["maxmemory"], 1),
        "hit_rate": hits / max(hits + misses, 1),
        "ops_sec": info["instantaneous_ops_per_sec"],
        "rejected": info["rejected_connections"],
        "clients": info["connected_clients"],
        "fork_ms": info["latest_fork_us"] / 1000,
    }
# 定时采集 → 推到时序库/打日志/对接告警；生产标配是
# redis_exporter + Prometheus + Grafana（ exporters 免开发，指标同源 INFO ）
```

监控采集本身的成本注意：`INFO` 很轻（秒级轮询无压力），但**不要高频跑 `CLIENT LIST` / `SCAN` 类采集**——那是拿生产实例做压力测试。

### 上线前 checklist

| # | 检查项 | 依据 |
|---|--------|------|
| 1 | 未监听公网（bind / 安全组 / Docker `-p 127.0.0.1:`） | 第二节 |
| 2 | `default` 已设密码或禁用；业务用 ACL 具名账号 | 第三节 |
| 3 | 危险命令已对业务账号禁用（`ACL LOG` 审计开着） | 第四节 |
| 4 | `maxmemory` + 淘汰策略按角色配置（缓存 / 存储分实例） | 07 |
| 5 | 持久化已配且**做过恢复演练**（没演练的备份等于没备份） | 01 |
| 6 | 内网跨机部署是否需要 TLS（决策留痕） | 第五节 |
| 7 | 监控四件套已接：内存水位 / 命中率 / 拒绝连接 / 慢查询 | 第六节 |
| 8 | 非 root 运行；THP 关闭；`overcommit_memory=1` | 第五节 |

## 七、陷阱

1. **以为配了 `bind` 内网 IP 就安全**：同内网的任何主机仍可无密码连入。bind 是"少暴露"，认证才是"准入"——两层都要。
2. **ACL 启用了但 `default` 没处理**：老代码、`AUTH` 兼容逻辑仍走 default 无密码通道，加固形同虚设。上线后 `ACL LIST` 检查 default 状态。
3. **监控账号权限过大**：采集器用了 `+@all` 账号，采集器被攻破即实例沦陷。给监控单独的 `viewer` 只读账号（第三节）。
4. **TLS 裸用默认配置拖性能**：TLS 握手有成本，连接不复用的短连接场景被放大。配合连接池长连接使用（复习 05 守则 2）。
5. **`rename-command` 后忘了自己**：改了名，排障时照文档敲命令报 `unknown command`，白排查一轮。新项目一律 ACL，不用 rename。
6. **告警阈值照抄别人**：命中率 80% 的红线对纯缓存合理，但只读场景（embedding 缓存）命中率天然应 > 95%；阈值跟着业务基线走，先记录一周基线再定告警。

## 小结

- Redis 危险的根源：无密码 + 信任内网 + `dir` 可写；铁律：永不裸露公网
- 四层防线：网络（bind/安全组/Docker 回环映射）→ 认证（ACL 具名账号）→ 权限（key 模式 + 命令类别）→ 命令治理（禁 `@dangerous`，弃用 rename-command）
- `default` 用户是加固盲区：设密码或禁用，二选一
- 监控全集：连接数、命中率（hits/(hits+misses)）、拒绝连接、fork 耗时、持久化状态、复制延迟；采集用只读账号
- 上线 checklist 八项，每项都有对应的正文节

## 练习

1. 给本机实例创建 `appuser`（只能动 `cache:*`，禁危险类）并禁用 `default`，分别用两个账号验证：`appuser` 执行 `KEYS *` 被拒，`viewer` 只能读；`ACL LOG` 查看违规记录。
2. 写一个 `collect()` 采集循环跑 10 分钟，输出命中率与 ops 曲线；故意用脚本灌入大量未命中查询，观察命中率下降——这就是告警会触发的形态。
3. 用 `redis-cli --user` 体验密码轮换：`ACL SETUSER appuser >新密码` 后用新密码连入，`<旧密码` 移除，全程业务无感。
4. 对照第七节 checklist 逐项检查你自己的练习实例，列出不合格项并修复。
