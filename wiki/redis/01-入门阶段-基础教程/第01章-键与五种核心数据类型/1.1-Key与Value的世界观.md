# Key 与 Value 的世界观

## 学习目标

读完本篇，你应当能够：

1. 准确说出 key 是什么（包括"二进制安全"的真实含义）、key 的长度限制
2. 用一套命名约定组织你的键（`对象类型:ID:属性`）
3. 理解"键空间"与 16 个逻辑数据库（db0~db15）的关系
4. 知道为什么 `KEYS *` 在生产环境是禁用命令

## 一、Key 到底是什么

**Key 是一个最长 512MB 的字节序列，用来标识一个值。**

三个要点逐个拆：

### 1. "字节序列"——二进制安全（binary-safe）

日常你可以把 key 当字符串用，但 Redis 对它做唯一假设：**它是一串字节**。

- `"user:1000"` ✅
- `"\x89PNG\r\n..."`（图片开头几个字节）✅ 也能当 key
- 空 key `""` ❌ 不允许（等价于没有 key）

同理 value 也是字节序列。这个设计意味着 Redis **不关心编码**——存进去什么字节，取出来就是什么字节。'中文变成乱码'之类的问题从来都出在**客户端编码**，不在服务端。

### 2. 长度限制

- Key 最长 512MB，**但没有任何理由超过 ~1KB**。key 越长，每次命令传输与哈希计算的开销越大。
- Value 同样上限 512MB（String），同样不建议存大对象——大 key 是性能杀手（详见 [[redis/01-入门阶段-基础教程/第02章-过期机制与通用Key命令/2.2-通用Key命令与SCAN]] 的陷阱节）。

### 3. Key 没有"类型"

**类型属于 value，key 只是名字。** 同一个名字，先 `SET k "hello"`（String），再 `LPUSH k a b` 会直接把旧值覆盖成 List。Redis 不报警、不阻止。

---

## 二、命名约定：冒号分层

Redis 不强制 key 格式，但社区有事实标准——**用冒号 `:` 分层**，像路径一样：

```
user:1000:profile        → 用户 1000 的资料（通常存 Hash）
user:1000:last_login     → 用户 1000 的最后登录时间
session:abc123           → 会话 abc123
rate:api:192.168.1.5     → 某 IP 的 API 调用计数
rank:game:daily          → 每日游戏排行榜
```

| 命名原则 | 说明 |
|----------|------|
| 冒号分层 | `对象:ID:属性`，一层一个语义 |
| 全小写 | 惯例，避免大小写混乱 |
| 别用空格和特殊字符 | 给排查和脚本处理省麻烦 |

> 分层的好处不只是可读：一些工具（如 RedisInsight）会按 `:` 把键树状展示；删除"某类前缀的所有键"时模式匹配也好写（`MATCH user:1000:*`，见 [[redis/01-入门阶段-基础教程/第02章-过期机制与通用Key命令/2.2-通用Key命令与SCAN]]）。

## 三、键空间与 16 个逻辑数据库

**键空间（keyspace）** = 当前数据库里所有 key 的集合。

Redis 在**一个实例**里划分了 16 个**逻辑数据库**（编号 0~15，可配置数量），彼此键空间隔离：

```
127.0.0.1:6379> SELECT 0      # 默认就在 db0
OK
127.0.0.1:6379> SET a 1
OK
127.0.0.1:6379> SELECT 1
OK
127.0.0.1:6379[1]> GET a      # db1 里没有 db0 的键
(nil)
127.0.0.1:6379[1]> SELECT 0
OK
127.0.0.1:6379> GET a
"1"
```

注意切换后提示符变成 `6379[1]`——**中括号里的数字就是当前 db**，排查"键不见了"先看它。

三个必须知道的事实：

1. **db 之间不隔离内存、不隔离配置**——它只是命名空间的切分，不是物理隔离。
2. **集群模式（中段内容）只有 db0**——多 db 的设计在分布式场景无法延续，现代实践普遍倾向"一个应用一个实例"而不是"一个应用一个 db"。
3. `DBSIZE` 返回**当前 db** 的键数量；`FLUSHDB` 清空当前 db（危险命令，慎用），`FLUSHALL` 清空所有 db（**极危险**）。

## 四、为什么 `KEYS *` 是禁用命令

`KEYS pattern` 返回匹配的所有键。看起来人畜无害，但：

```
KEYS *        → 遍历当前 db 全部键，O(N)，N = 键总数
KEYS user:*   → 同样 O(N)：先全量遍历再逐个匹配
```

回顾 [[redis/01-入门阶段-基础教程/第00章-学前准备/0.1-Redis是什么]]：命令执行是**单线程**的。100 万个键时，一条 `KEYS *` 可能霸占线程几百毫秒到数秒，**期间所有其他命令全部排队**——对线上服务等于瞬间卡死。

正确姿势是 `SCAN`（增量迭代，分批返回，不阻塞），第 2.2 章专门讲。**规则：`KEYS` 只在本地开发、键数可控时用；生产环境一律 `SCAN`。**

---

## 五、陷阱

1. **`SELECT` 切库后忘了切回来** → 之后所有读写都发生在别的 db，"数据丢了"的假象。看提示符的 `[n]`。
2. **把类型当 key 语义**：`SET user:1000 "..."` 之后又 `HSET user:1000 name Bob`——后者直接把 String 覆盖成 Hash，旧值无声丢失。
3. **key 里直接拼用户输入** → `session:{用户输入}` 可能造成键名混乱甚至碰撞。用户输入应作为 **value** 或经校验后再拼入 key。
4. **大 key**：一个 String 塞几十 MB 的 JSON。每次读写都要传这么多字节，且删除大 key 可能卡顿（`UNLINK` 可缓解，见 [[redis/01-入门阶段-基础教程/第02章-过期机制与通用Key命令/2.2-通用Key命令与SCAN]]）。

---

## 小结

- Key = 最长 512MB 的字节序列（实践中 < 1KB），类型属于 value 不属于 key
- 命名用冒号分层：`对象:ID:属性`
- 一个实例 16 个逻辑 db，键空间隔离但内存不隔离；集群只有 db0
- `KEYS` O(N) 阻塞，生产禁用，改用 `SCAN`

## 练习

1. 在 db0 存 `t:a` 和 `t:b`，切到 db5 验证 `KEYS t:*` 为空，再切回 db0 找到它们。
2. 用同一个 key `x`：先 `SET x 1`，再 `DEL x`，然后 `LPUSH x a b`，最后 `TYPE x`——体会"key 无类型"。
3. （思考题）为什么"多 db"不能在集群模式下工作？提示：键分布在多台机器时，`db1` 意味着什么？
