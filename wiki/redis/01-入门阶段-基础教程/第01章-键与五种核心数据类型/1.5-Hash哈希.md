# Hash 哈希

## 学习目标

读完本篇，你应当能够：

1. 画出 Hash 的心智模型（key → {field: value}），说清它与"String 存 JSON"的分界
2. 熟练使用 `HSET` / `HGET` / `HGETALL` / `HDEL` / `HEXISTS` 家族
3. 用 `HINCRBY` 对**单个字段**做原子计数
4. 识别"大 key 上 `HGETALL`"这一性能陷阱

## 一、心智模型：键下面挂着一层小字典

```
key: user:1000          ← 外层的 key（String 世界观里的 key）
   ├── field: name    → value: "张飞航"
   ├── field: age     → value: "21"
   └── field: city    → value: "宝丰"
```

- **field（字段）**：Hash 内部的"小 key"，本身也是字节序列
- 每个字段的值是独立的 String（受同样的 512MB 上限约束）
- Hash 最多约 40 多亿个字段——实际把字段数控制在几百以内是健康状态

与"String 存整个 JSON"的核心差异：

| 操作 | String + JSON | Hash |
|------|---------------|------|
| 改一个字段 | `GET` 整个 JSON → 反序列化 → 改 → `SET` 回去（4 步，还有并发覆盖风险） | `HSET user:1000 name "新值"`（1 步，原子） |
| 读一个字段 | 取整个 JSON 再挑 | `HGET user:1000 age` |
| 整体读取 | `GET`（1 步） | `HGETALL`（字段很多时是负担） |

**分界线**：总是整存整取 → String；字段级读写 → Hash。

---

## 二、基础命令实操

```
127.0.0.1:6379> HSET user:1000 name "Bob" age "21" city "Beijing"   # 一次写多个字段
(integer) 3                       ← 返回新建字段的数量
127.0.0.1:6379> HGET user:1000 name
"Bob"
127.0.0.1:6379> HGETALL user:1000
1) "name"
2) "Bob"
3) "age"
4) "21"
5) "city"
6) "Beijing"
127.0.0.1:6379> HLEN user:1000
(integer) 3
```

| 命令 | 作用 |
|------|------|
| `HSET key f v [f v ...]` | 写一个或多个字段（覆盖旧值） |
| `HGET key f` | 读单个字段（不存在返回 `(nil)`） |
| `HMGET key f [f...]` | 批量读指定字段 |
| `HGETALL key` | 读全部字段+值（交替出现） |
| `HDEL key f [f...]` | 删除字段 |
| `HEXISTS key f` | 字段存在？`1`/`0` |
| `HLEN key` | 字段数量 |
| `HKEYS key` / `HVALS key` | 所有字段名 / 所有值 |
| `HSETNX key f v` | 字段不存在才写 |
| `HINCRBY key f n` | 字段原子 ±n |
| `HINCRBYFLOAT key f x` | 字段原子 ±小数 |
| `HRANDFIELD key [n]` | 随机取字段名 | `Redis 6.2+` |

### 字段级原子计数

```
127.0.0.1:6379> HINCRBY user:1000 login_count 1
(integer) 1
```

与 [[redis/01-入门阶段-基础教程/第01章-键与五种核心数据类型/1.3-String字符串|String 的 INCR]] 同理：单线程执行保证原子。**计数器和它所属对象放同一个 Hash 里**，正是 Hash 相对 String+JSON 的又一优势。

---

## 三、典型场景：Agent 会话存储

把一个 Agent 会话的状态放进一个 Hash，字段级更新互不干扰：

```
127.0.0.1:6379> HSET session:abc123 user "u1" model "deepseek-chat" turns 0 status "running"
127.0.0.1:6379> HINCRBY session:abc123 turns 1            # 每轮 +1，不影响其他字段
127.0.0.1:6379> HSET session:abc123 status "summarizing"   # 只改状态
127.0.0.1:6379> EXPIRE session:abc123 3600                 # 整个会话 1 小时后过期（过期以 key 为单位，不是字段）
```

注意最后一点：**TTL 属于整个 key，Hash 无法对单个字段设过期**（字段级 TTL 长期是社区呼声，官方至今未支持）。

---

## 四、机制层一瞥

小 Hash（字段少且值短）内部用 **listpack** 紧凑编码——一块连续内存，极其省空间；变大后转为标准的哈希表。这就是"Hash 存小对象比 String 存 JSON 更省内存"的底层原因之一。细节属中段内存优化专题。

---

## 五、陷阱

1. **大 key 上 `HGETALL`**：几十万字段的 Hash 一次 `HGETALL`，等于一次网络大传输 + 服务端 O(N) 遍历。字段多时用 `HMGET` 只取需要的，或 `HSCAN` 分批（见 [[redis/01-入门阶段-基础教程/第02章-过期机制与通用Key命令/2.2-通用Key命令与SCAN]]）。
2. **"字段不存在"和"字段值为空"是两回事**：`HEXISTS` 返回 0 但 `HGET` 也可能返回空字符串——判断存在性用 `HEXISTS`，不要拿 `HGET` 的返回值当真值（空串在条件判断里也是真）。
3. **字段删空后整个键消失**：与 List 弹空同理，最后一个字段被 `HDEL` 后 key 本身被删除。
4. **嵌套没有原生支持**：字段的值只能是"扁平的 String/数字"，想存嵌套对象得序列化成 JSON 字符串塞进字段里——一层手动、二层开始就该考虑直接用 Redis 的 JSON 类型（中段内容）。

---

## 小结

- Hash = key 下的"字段→值"小字典，字段级原子读写
- 整存整取选 String；字段级操作选 Hash
- `HINCRBY` 字段计数；TTL 只能属于整个 key
- 大 Hash 慎用 `HGETALL`，改 `HMGET` / `HSCAN`

## 练习

1. 用 Hash 建一个 `session:test`，含 4 个字段；只更新其中 1 个；`HGETALL` 验证其他字段未动。
2. `HINCRBY` 一个不存在的字段，观察从 0 开始。
3. 把所有字段 `HDEL` 光，再 `EXISTS session:test`，验证键消失。
