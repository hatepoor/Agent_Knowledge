# 通用 Key 命令与 SCAN

## 学习目标

读完本篇，你应当能够：

4. 理解 SCAN 的两条保证与一条不保证

## 一、通用命令：对任何类型的 key 都有效

| 命令 | 作用 | 说明 |
|------|------|------|
| `DEL key [key...]` | 同步删除 | 阻塞直到释放完成；大 key 会卡 |
| `UNLINK key [key...]` | **异步**删除 | 主线程只摘掉引用，内存由后台线程回收 |
| `EXISTS key [key...]` | 存在性 | 传多个时返回**存在的个数**（`3.0+`） |
| `TYPE key` | 查值类型 | 排错第一反应（见 [[redis/01-入门阶段-基础教程/第00章-学前准备/0.4-看懂报错信息]]） |
| `RENAME key 新名` | 改名 | 目标已存在则**直接覆盖** |
| `RENAMENX key 新名` | 改名 | 目标存在则放弃（返回 0） |
| `RANDOMKEY` | 随机取一个 key | |
| `DBSIZE` | 当前 db 键数量 | O(1) |
| `COPY 源 目标` | 复制键 | `Redis 6.2+` |
| `OBJECT ENCODING key` | 查内部编码 | 前几章反复提到的观察工具 |

### DEL vs UNLINK（`UNLINK` 为 `Redis 4.0+`）

删除一个百万元素的集合，`DEL` 要在主线程里逐个释放内存——期间所有命令排队。`UNLINK` 把释放工作交给后台线程，主线程只做"把这个名字从键空间摘掉"一件小事。

**规则：删可能很大的 key（集合类、长列表、大 Hash）一律用 `UNLINK`。** 小 key 用哪个都行。

## 二、`KEYS` 的问题与 `SCAN` 的解法（机制层）

### KEYS：一步到位，但会卡死服务

```
KEYS pattern          # 一次返回所有匹配的键，O(N) 全量遍历 + 全量返回
```

单线程模型下，百万键的 `KEYS *` 独占服务端数百毫秒到数秒——**生产禁用**（复习 [[redis/01-入门阶段-基础教程/第01章-键与五种核心数据类型/1.1-Key与Value的世界观]]）。

### SCAN：把"全量"切成"分批"

```
SCAN 游标 [MATCH 模式] [COUNT 每批提示量] [TYPE 类型]
```

工作方式像一个**接力**：

```
127.0.0.1:6379> SCAN 0 MATCH user:* COUNT 100
1) "17"                          ← 下一批的游标（接力棒）
2) 1) "user:1001"
   2) "user:3420"
127.0.0.1:6379> SCAN 17 MATCH user:* COUNT 100
1) "0"                           ← 游标回到 0：遍历完成
2) 1) "user:88"
   ...
```

- 起点**永远是 `SCAN 0`**；每次调用返回**新游标 + 一批键**
- **游标回到 `0` 表示遍历结束**（中途出现的其他数字都是中间站）
- 每次调用之间，**服务端完全空闲**，别的命令照常执行——这就是"不阻塞"的本质

Python 里的标准写法（伪码）：

```python
cursor = 0
while True:
    cursor, keys = r.scan(cursor, match="user:*", count=500)
    process(keys)          # 每批处理完再去要下一批
    if cursor == 0:
        break
```

### SCAN 的三条约定（记住才能正确使用）

| 条目 | 内容 |
|------|------|
| ✅ 保证 1 | 遍历**开始时已存在**的键，完整遍历期间**从头到尾都存在**的，**一定**会被返回 |
| ✅ 保证 2 | 遍历期间**从未存在**的键**一定不会**被返回 |
| ⚠️ 不保证 | 遍历**期间被修改**（新增/删除/改名）的键：可能返回，也可能漏掉；同一键可能**重复出现** |

推论：**SCAN 适用于"批处理可以容忍少量遗漏/重复"的场景**（清理、统计、迁移）；需要严格精确一致的操作不能依赖 SCAN，应走业务层的可靠方案。

### MATCH 与 COUNT 的真实含义

- `MATCH`：过滤模式（`*` 任意、`?` 单字符、`[abc]` 选一）。**过滤发生在返回之后**——不匹配的批次可能是空的，属正常现象，不代表遍历完了（结束判据只有一个：游标归 0）。
- `COUNT`：**提示值**不是承诺——"每批大约摸这么多个桶"，实际返回数量可多可少。想加大批量就调大 COUNT，但别指望精确。

> 同族命令：遍历 Hash 字段用 `HSCAN`、Set 成员用 `SSCAN`、ZSet 成员用 `ZSCAN`——大集合遍历全部用它 们，用法与 SCAN 完全同构（游标 + 批量）。

---

## 三、陷阱

1. **`SCAN` 返回空批 ≠ 结束**：只有游标为 `0` 才是结束。MATCH 命中率低时空批很常见。
2. **遍历中删元素是允许的**，但被删的可能已被返回（你的处理要幂等——处理两次不炸）。
3. **`RENAME` 静默覆盖**：目标名已有键时直接覆盖，无提示。要"目标必须不存在"用 `RENAMENIX`（`RENAMENX`）。
4. **`EXISTS` 多键返回的是计数**：`EXISTS a b c` 返回 0~3，不再是 0/1 布尔。
5. **大 key 三宗罪**：创建（一次写几十 MB）、读取（`HGETALL`/`SMEMBERS`/`LRANGE 0 -1`）、删除（`DEL`）。本篇解决了第三宗（`UNLINK`），前两宗靠设计避免——大对象拆分或外置（值放对象存储，Redis 只放引用）。

---

## 小结

- 通用命令对五种类型一视同仁；删大 key 用 `UNLINK`
- `SCAN` = 游标接力的增量遍历：起点 0、终点 0、COUNT 是提示、MATCH 后过滤
- 三条约定：全程存在的必返回、从未存在的必不返回、期间变化的随缘（可能重复）
- 大集合遍历用 `HSCAN` / `SSCAN` / `ZSCAN`

## 练习

1. 造 1000 个键（可用脚本或重复命令），用 `SCAN 0 COUNT 100` 起步，手动接力直到游标归 0，数一数总键数。
2. 对一个 Hash 用 `HSCAN` 分批遍历字段，对比 `HGETALL` 的一次性输出。
3. `RENAME` 到一个已存在的键名，验证静默覆盖；再用 `RENAMENX` 验证拒绝。
