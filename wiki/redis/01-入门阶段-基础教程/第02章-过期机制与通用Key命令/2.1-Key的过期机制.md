# Key 的过期机制

## 学习目标

读完本篇，你应当能够：

1. 熟练使用 `EXPIRE` / `TTL` / `PERSIST` 管理过期时间
2. 准确解读 `TTL` 的三种返回：正数 / `-1` / `-2`
3. 讲清 Redis 删除过期键的**两层机制**：惰性删除 + 定期删除
4. 避开"过期时间被意外清除"的三大经典 bug

## 一、过期是什么：给 key 挂一个"死亡时间"

**TTL（Time To Live，剩余存活时间）属于整个 key**，与 value 是什么类型无关。到期后这个 key **从键空间消失**，如同从未存在。

| 命令 | 作用 |
|------|------|
| `EXPIRE key 秒` | 设置存活秒数 |
| `PEXPIRE key 毫秒` | 毫秒精度 |
| `EXPIREAT key unix时间戳` | 定点到某个时刻死亡 |
| `TTL key` | 查剩余秒数 |
| `PTTL key` | 查剩余毫秒 |
| `PERSIST key` | 移除过期时间（变永久） |

实操：

```
127.0.0.1:6379> SET session:u1 "data" EX 60       # 写入时就带 60 秒寿命
OK
127.0.0.1:6379> TTL session:u1
(integer) 58
127.0.0.1:6379> EXPIRE session:u1 3600            # 重新设置（重置，不是叠加）
(integer) 1
127.0.0.1:6379> PERSIST session:u1
(integer) 1
127.0.0.1:6379> TTL session:u1
(integer) -1                                      ← 永不过期
```

### TTL 的三种返回（必背）

| 返回 | 含义 |
|------|------|
| `正数` | 还剩这么多秒 |
| `-1` | 键存在，**永不过期** |
| `-2` | 键**不存在**（可能是从未有，也可能是刚过期被删） |

配套的 `SET` 选项复习（[[redis/01-入门阶段-基础教程/第01章-键与五种核心数据类型/1.3-String字符串]]）：`EX 秒` 一体化写入；`KEEPTTL`（`Redis 6.0+`）覆盖值但保留寿命。

### EXPIRE 的条件选项（`Redis 7.0+`）

| 写法 | 只在以下条件成立时设置过期 |
|------|--------------------------|
| `EXPIRE key 60 NX` | 当前**没有**过期时间 |
| `EXPIRE key 60 XX` | 当前**有**过期时间 |
| `EXPIRE key 60 GT` | 新时间**大于**当前剩余 |
| `EXPIRE key 60 LT` | 新时间**小于**当前剩余 |

`GT` / `LT` 典型用途：续期时"只延长不缩短"。

## 二、机制层：过期键什么时候真的被删

设置过期并不会让 Redis 定一个精确的闹钟。实际的删除是**两层配合**：

| 层 | 触发时机 | 做法 | 后果 |
|----|----------|------|------|
| **惰性删除**（lazy expiration） | 某个客户端**访问**这个键时 | 访问前检查：过期了就当场删掉，返回 nil | 访问前，过期键**一直躺在内存里** |
| **定期删除**（active expiration） | 后台周期任务，默认每秒约 10 次（`hz 10` 配置） | 每次随机抽样一批带 TTL 的键，过期比例高就继续抽，限时进行 | 清理"永远没人访问"的过期键，防止内存泄漏 |

**为什么这样设计**：精确到期的唯一办法是给每个键建时间堆、到点触发——百万键的定时器管理本身就是负担。惰性 + 定期的组合用"删除可以晚一点"换"写入路径零成本"，符合 Redis 的性能哲学。

**两个推论**（对实践很重要）：

1. `TTL` 显示 `-2` 之前，`DBSIZE` 可能仍把该键算在内——内存不会在到期那一瞬间释放。
2. **没设 TTL 的键永远不删**——定期删除只扫描有 TTL 的键。缓存务必设 TTL，否则就是无限增长的内存泄漏。

> 过期键如何影响持久化（RDB / AOF）与主从复制，属于**中段**内容，此处不展开。

## 三、陷阱

1. **`SET` 无选项覆盖会把 TTL 清空**（第一大坑，复习 [[redis/01-入门阶段-基础教程/第01章-键与五种核心数据类型/1.3-String字符串]] 陷阱 1）：

```
EXPIRE cache:hot 300
SET cache:hot "new-value"      # ← TTL 没了，键变永久！
SET cache:hot "new-value" KEEPTTL   # ✅ Redis 6.0+ 正确写法
```

2. **改值类命令不清 TTL**：`INCR` / `HSET` / `LPUSH` 等只动内容、不动寿命——所以"计数器 + 首次设过期"要小心：`INCR` 之后再 `EXPIRE` 会**重置**倒计时。限流的经典模式（`SET k 0 EX 60 NX` 先占位再 `INCR`）正是为了绕开这点（见 [[redis/01-入门阶段-基础教程/第01章-键与五种核心数据类型/1.3-String字符串]] 练习 1）。
3. **过期精度不是承诺**：到期后一瞬到几秒内才真正消失都属正常（两层机制的直接后果）。不要写"依赖第 60.000 秒键已消失"的逻辑。
4. **`EXPIRE` 重置而非叠加**：`EXPIRE k 60` 执行两次，剩余仍是 ~60 秒，不是 120。
5. **`EXPIRE` 不存在的键返回 0**：不是报错，是"没有可设置的对象"。`GETEX`（`6.2+`，取值兼设过期）适合"存在才续期"的场景。

---

## 小结

- TTL 属于整个 key；`TTL` 三返回：正数 / `-1` 永久 / `-2` 不存在
- 删除 = 惰性（访问时）+ 定期（后台抽样），不保证准时
- `SET` 清 TTL → 用 `KEEPTTL`；`EXPIRE` 重置不叠加；续期用 `GT`（7.0+）
- 无 TTL 的键永不清理——缓存必须设寿命

## 练习

1. `SET k v EX 100` → `TTL` → `SET k v2` → `TTL`，亲眼确认 TTL 被清；再用 `KEEPTTL` 复现正确行为。
2. `SET k v` 后 `TTL` 得 `-1`；`EXPIRE k 2`，等 3 秒后 `TTL` 得 `-2`。
3. `EXPIRE` 同一键两次各 60 秒，中间隔 5 秒，观察第二次后 TTL ≈ 60 而非 55（重置语义）。
