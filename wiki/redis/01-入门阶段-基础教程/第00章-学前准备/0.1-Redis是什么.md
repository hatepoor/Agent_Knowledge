# Redis 是什么

## 学习目标

读完本篇，你应当能够：

1. 用一句话说清 Redis 是什么、它和 PostgreSQL 这类数据库的根本区别
2. 建立 Redis 的核心心智模型："一个住在服务器内存里的、值有结构的超级字典"
3. 说出 Redis 的 5 个典型用途，并对应到你自己的 Agent 开发场景
4. 明确 Redis **不擅长**什么，避免把它用错地方

## 前置知识

| 前置 | 为什么需要 |
|------|-----------|
| 无 | 本章是零基础起点，**不要求任何前置知识** |

## 一、一句话定义

> **Redis（REmote DIctionary Server，远程字典服务器）是一个把数据放在内存里的键值（key-value）数据库。**

把这句话拆成三个词来理解：

| 词 | 含义 |
|----|------|
| **Remote（远程）** | 它是一个独立运行的**服务端程序**，你的程序通过网络（默认端口 `6379`）连上去使用它——和 PostgreSQL 一样是"客户端-服务器"结构 |
| **DIctionary（字典）** | 它存数据的方式像 Python 的 `dict`：给一个键（key），取一个值（value）。没有表、没有 SQL、没有 JOIN |
| **Server（服务器）** | 它是被多个程序**共享**的：你的 FastAPI 后端、Celery worker、另一个脚本，可以同时连同一个 Redis |

**"端口 6379"**：每个网络服务都要占一个编号（端口），用于区分"这条消息是给哪个程序的"。Redis 约定使用 6379。类比：PostgreSQL 默认是 5432。

---

## 二、核心心智模型：一个"值有结构"的超级字典

如果你只会一句话，记住这句：

> **Redis ≈ 一个搬到独立服务器上、所有数据都在内存里、值不只是字符串而是五种数据结构的 Python 字典。**

和 Python 字典逐点对比，你就知道 Redis 多了什么：

| 对比点 | Python `dict` | Redis |
|--------|---------------|-------|
| 住在哪 | 你的 Python 进程里 | 独立的服务器进程里 |
| 谁能用 | 只有你这个进程 | 任何能连到它的程序（跨进程、跨机器共享） |
| 数据在哪 | 内存（进程死了就没了） | 内存（**也是**进程重启有丢失风险，持久化见下） |
| 值的类型 | 任意 Python 对象 | 五种固定结构：String / List / Hash / Set / Sorted Set |
| 值能"部分操作"吗 | 只能整体取出 | **能**：可以对 List 的某一端 push、对 Hash 的某一个字段单独赋值 |
| 一秒能操作多少次 | 进程内极快 | 单机轻松 10 万次/秒以上（受网络往返影响） |

"值有结构"是 Redis 与"普通缓存"的分水岭。正因为它知道 value 是个 List，它才能提供"只在左端插入""取第 3 到第 10 个元素"这种**服务器端**操作，而不必把整个值拉回客户端再改。

## 三、为什么 Redis 快

三个原因，按重要性排序：

1. **数据在内存**。内存的读写速度比磁盘快几个数量级，这是根本原因。
2. **命令执行是单线程的**。所有客户端发来的命令排队、逐条执行，因此每条命令天然是**原子**（atomic，不可分割，执行中不会被别的命令插队）的，不需要加锁。
3. **I/O 多路复用**（一句话了解即可，属于进阶内容）：一个线程同时监听成千上万个网络连接，谁就绪就处理谁。

> ⚠️ **纠正一个常见误解**："单线程 = 慢"。恰恰相反，因为数据在内存，瓶颈几乎从不在 CPU 计算，单线程换来的是无锁、无上下文切换，反而快。慢命令（如全库扫描 `KEYS *`）之所以危险，正是因为它们会**霸占这唯一的线程**——第 2.2 章会专门讲。

## 四、Redis 用来做什么

| 用途 | 一句话说明 | 在你的技术栈中的对应 |
|------|-----------|---------------------|
| **缓存** | 把慢的操作结果（数据库查询、LLM 响应、embedding 计算）存起来，下次直接取 | LangChain 的缓存层、RAG 检索结果缓存 |
| **会话 / 状态存储** | 存用户会话、Agent 对话状态，天然支持按时间过期 | Agent 的短期记忆、限流计数器 |
| **计数器 / 限流** | `INCR` 原子自增，统计访问量、控制 API 调用频率 | 控制 LLM API 调用速率 |
| **排行榜** | Sorted Set 按分数实时排序 | 热门内容、评分排序 |
| **消息队列** | List 的阻塞弹出、Pub/Sub、Stream | Agent 间异步任务分发 |

**与 PostgreSQL 的关系是互补，不是替代**：

| 方面 | PostgreSQL | Redis |
|------|-----------|-------|
| 数据位置 | 磁盘为主（内存做缓存） | **内存为主**（可持久化到磁盘） |
| 查询方式 | SQL、复杂查询、事务 | 按键存取、命令操作 |
| 数据规模 | 可远超内存 | 受内存大小限制 |
| 典型角色 | 事实的最终存储（source of truth） | 缓存、临时状态、加速层 |

实践中最常见的组合：**PostgreSQL 存正式数据，Redis 做它前面的缓存**。

## 六、陷阱

1. **Redis ≠ 永不丢数据。** 数据在内存里，默认配置下重启就可能丢最近的数据。把数据写回磁盘（持久化，RDB/AOF）是**中段阶段**的内容；在此之前，请把 Redis 当"可丢数据的加速层"而非唯一存储。
2. **不要用 Redis 存"放不进内存的大数据"。** 它的一切优势都以数据在内存为前提。
3. **不要因为"Redis 快"就用它替代正式数据库。** 它没有 SQL、没有复杂事务与约束，角色是缓存与状态层。

---

## 小结

- Redis = 远程的、内存中的、值有五种结构的键值数据库
- 快的根源：内存 + 单线程原子命令 + I/O 多路复用
- 角色定位：缓存、状态、计数、排行、队列——与 PostgreSQL 互补
- 最新版 8.10.2；8.0 起许可证含 AGPLv3 且开源版自带 JSON 等能力
