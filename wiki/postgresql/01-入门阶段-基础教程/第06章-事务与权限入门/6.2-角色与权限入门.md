# 6.2 角色与权限入门

## 学习目标

- 分清角色、用户、组的关系与登录属性
- 掌握 `GRANT`/`REVOKE` 的层次结构与默认权限
- 认识行级安全(RLS)与最小权限原则

## 前置知识

[[postgresql/01-入门阶段-基础教程/第06章-事务与权限入门/6.1-事务基础]]

## 正文

### 一、角色即一切

**PostgreSQL 中没有"用户"这个独立概念,只有"角色"(role)。** 能登录的角色习惯上叫"用户",不能登录的叫"组"。

```sql
-- 建一个可登录的用户
CREATE ROLE app_user WITH LOGIN PASSWORD 'strong-password';

-- 建一个组角色(不可登录)
CREATE ROLE app_readonly NOLOGIN;

-- 让 app_user 继承 app_readonly 的权限
GRANT app_readonly TO app_user;

-- 建超级用户
CREATE ROLE dba WITH LOGIN SUPERUSER PASSWORD '...';

-- 查看
\du
SELECT rolname, rolsuper, rolcanlogin, rolcreatedb, rolconnlimit
FROM pg_roles ORDER BY rolname;
```

**常用角色属性**

| 属性 | 作用 |
|------|------|
| `LOGIN` / `NOLOGIN` | 可否登录 |
| `SUPERUSER` / `NOSUPERUSER` | 超级用户(绕过所有权限检查) |
| `CREATEDB` / `NOCREATEDB` | 可建库 |
| `CREATEROLE` / `NOCREATEROLE` | 可建角色 |
| `INHERIT` | 是否自动继承所属组的权限(默认开) |
| `BYPASSRLS` | 绕过行级安全 |
| `CONNECTION LIMIT n` | 并发连接上限 |
| `VALID UNTIL '...'` | 密码有效期 |

```sql
-- 修改
ALTER ROLE app_user WITH CONNECTION LIMIT 20;
ALTER ROLE app_user SET search_path = app, public;      -- 角色级默认参数
ALTER ROLE app_user SET statement_timeout = '30s';

-- 密码有效期与过期(PG14+)
ALTER ROLE app_user VALID UNTIL '2027-01-01';
```

> **角色级 `SET` 是配置最佳实践**:把 `search_path`、`statement_timeout`、`idle_in_transaction_session_timeout` 绑到应用角色上,应用连接即自动生效,不依赖应用代码正确设置。

### 二、权限的层次

PostgreSQL 权限分几个层次,**上层对象的权限不自动带来下层权限**。

```
实例
 └── 数据库 DATABASE (CONNECT, CREATE, TEMPORARY)
      └── schema SCHEMA (USAGE, CREATE)
           └── 表 TABLE (SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER)
           └── 序列 SEQUENCE (USAGE, SELECT, UPDATE)
           └── 函数 FUNCTION (EXECUTE)
           └── 类型 TYPE (USAGE)
```

**关键:要访问 `app.users`,必须同时具备:**

1. `CONNECT` 到该数据库
2. 对 schema `app` 的 `USAGE`
3. 对表 `app.users` 的 `SELECT`

```sql
-- 完整授权链
GRANT CONNECT ON DATABASE learn TO app_user;
GRANT USAGE   ON SCHEMA  app   TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO app_user;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA app TO app_user;   -- 自增列/序列需要
```

**权限缩写**

```sql
GRANT ALL PRIVILEGES ON ...   -- 该对象类型的所有权限
-- 常用简写
GRANT SELECT (col1, col2) ON t TO r;   -- 列级权限
```

**列级权限**:可只授某几列。

```sql
GRANT SELECT (id, email) ON app.users TO app_ro;
-- 之后该角色 SELECT 其他列会报错(需显式列名)
```

**收回权限**

```sql
REVOKE INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app FROM app_user;
REVOKE ALL ON SCHEMA app FROM PUBLIC;                -- 关闭默认的 PUBLIC 权限
REVOKE CREATE ON SCHEMA public FROM PUBLIC;          -- ★安全加固必做
```

> **PG15 重要变更**:`public` schema 的默认 `CREATE` 权限不再授予 `PUBLIC`。此前任何用户都能在 `public` 建对象,是新版本的安全改进。

### 三、默认权限(新对象自动授权)

`GRANT ... ON ALL TABLES` 只对**已存在**的对象生效。**将来**创建的表需用 `ALTER DEFAULT PRIVILEGES`。

```sql
-- 让 app_user 自动获得 app schema 中未来新建表/序列的权限
ALTER DEFAULT PRIVILEGES IN SCHEMA app
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

ALTER DEFAULT PRIVILEGES IN SCHEMA app
    GRANT USAGE, SELECT ON SEQUENCES TO app_user;

-- 查看
\dDp
SELECT * FROM pg_default_acl;
```

> **注意**:`ALTER DEFAULT PRIVILEGES` 只对**执行该命令的角色**将来创建的对象有效。若建表由迁移工具的角色(如 `migrator`)执行,必须用 `FOR ROLE migrator` 指定。
>
> ```sql
> ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA app
>     GRANT SELECT ON TABLES TO app_ro;
> ```

### 四、角色成员与权限继承

```sql
-- 组角色
CREATE ROLE rw NOLOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA app TO rw;
GRANT rw TO app_user;              -- app_user 继承 rw 的权限

-- 不自动继承(INHERIT 关闭时)
SELECT set_config(...);
SET ROLE rw;                       -- 手工切换生效
RESET ROLE;
```

**`SET ROLE` 的用途**:迁移/运维脚本可在会话内切换身份,便于精确控制。

```sql
SET ROLE migrator;
CREATE TABLE app.new_table (...);
RESET ROLE;
```

**超级用户与特殊角色**

| 角色 | 作用 |
|------|------|
| `pg_read_all_data` (PG14+) | 只读所有数据 |
| `pg_write_all_data` (PG14+) | 可写所有数据 |
| `pg_monitor` | 查看监控视图 |
| `pg_read_server_files` | `COPY` 读服务端文件 |
| `pg_signal_backend` | 可终止其他会话 |

```sql
GRANT pg_monitor TO monitor_user;   -- 监控账号的最佳实践
```

### 五、行级安全(RLS)

在多租户或需要"用户只能看自己的数据"时,RLS 把过滤逻辑下沉到数据库。

```sql
ALTER TABLE app.orders ENABLE ROW LEVEL SECURITY;

-- 策略:用户只能看到自己的订单
CREATE POLICY orders_own ON app.orders
    FOR ALL
    USING (user_id = current_setting('app.current_user_id')::bigint)
    WITH CHECK (user_id = current_setting('app.current_user_id')::bigint);

-- 表属主默认绕过 RLS;如需强制
ALTER TABLE app.orders FORCE ROW LEVEL SECURITY;
```

**要点**

| 事项 | 说明 |
|------|------|
| 默认行为 | 无策略时,普通用户看不到任何行(默认拒绝) |
| `USING` vs `WITH CHECK` | `USING` 管"能读哪些行",`WITH CHECK` 管"能写哪些行" |
| 表属主 | 默认绕过 RLS(除非 `FORCE`) |
| `BYPASSRLS` | 该属性角色绕过 RLS(慎授) |
| 性能 | RLS 会把策略条件**注入查询**,需相应索引否则会变慢 |

> **陷阱**:RLS 策略里的条件必须能走索引。若策略是 `user_id = ...`,那么 `user_id` 上必须有索引(通过外键索引顺便覆盖)。否则每个查询都会退化为全表扫描。

**应用如何设置上下文**

```sql
-- 应用在事务开始时设置(用参数而非 SQL 拼接,避免注入)
SET LOCAL app.current_user_id = '12345';
```

### 六、认证方式与安全清单

`pg_hba.conf` 决定"谁从哪以何种方式连接":

```
# TYPE  DATABASE  USER      ADDRESS        METHOD
local   all       postgres                 peer
host    all       all       127.0.0.1/32   scram-sha-256
host    app       app_user  10.0.0.0/8     scram-sha-256
```

| 方法 | 说明 |
|------|------|
| `trust` | 不做认证(**绝不可用于生产**) |
| `peer` | 用 OS 用户名匹配(仅本地 Unix socket) |
| `md5` | ⚠️ **PG18 起弃用**,将移除 |
| `scram-sha-256` | ✅ **推荐**(PG10+) |
| `cert` | SSL 客户端证书 |
| `oauth` | PG18 新增,对接 SSO |

**生产安全清单**

- [ ] 使用 `scram-sha-256`,**不保留任何 md5 密码**(PG18 会对 md5 发弃用警告)
- [ ] `postgresql.conf` 中 `ssl = on`,连接串用 `sslmode=require` 或 `verify-full`
- [ ] 应用账号**不是超级用户**,只授予必要权限
- [ ] `REVOKE CREATE ON SCHEMA public FROM PUBLIC`(PG15 前需手工做)
- [ ] 用 `ALTER DEFAULT PRIVILEGES` 覆盖未来的新对象
- [ ] 监控账号用 `pg_monitor` 而非 `SUPERUSER`
- [ ] `pg_hba.conf` 按来源网段最小化开放
- [ ] 定期审计:`SELECT * FROM pg_roles WHERE rolsuper;` 应只有 DBA 账号
- [ ] 密码策略:`password_encryption = scram-sha-256`;必要时用 `VALID UNTIL` 定期轮换

```sql
-- 连接与认证排查
SELECT usename, client_addr, ssl, backend_type FROM pg_stat_ssl JOIN pg_stat_activity USING (pid);
SHOW password_encryption;
SELECT * FROM pg_hba_file_rules;   -- 解析后的生效规则
```

## 小结

- PostgreSQL 只有角色:可登录的是"用户",不可登录的是"组";用 `GRANT 角色 TO 角色` 组合权限。
- 访问一个表需要三处权限:数据库 `CONNECT`、schema `USAGE`、表上具体权限。
- `GRANT ON ALL TABLES` 不管未来对象,需 `ALTER DEFAULT PRIVILEGES`(注意用 `FOR ROLE` 指定建表角色)。
- RLS 把行级过滤下沉到数据库,但策略条件必须有索引。
- 认证用 `scram-sha-256`;`md5` 在 PG18 已弃用。生产必须关闭 `public` 的 `CREATE` 权限并遵循最小权限。

## 练习

1. 创建 `app_rw`(组)与 `app_user`(用户),让 `app_user` 只对 `app` schema 的表有读写权限,并验证它无法访问 `public`。
2. 用 `ALTER DEFAULT PRIVILEGES` 让未来新建的表自动授权,新建一张表验证权限生效。
3. 开启 RLS,写一条"用户只能看自己订单"的策略,用两个不同身份验证可见行数不同。
4. 用 `pg_hba_file_rules` 查看你实例的认证规则,指出哪一条最危险。
5. 审计当前实例:`SELECT rolname FROM pg_roles WHERE rolsuper;`
