# 6.1 事务基础

## 正文

### 一、事务是什么:ACID

`BEGIN` 到 `COMMIT` 之间的所有操作构成一个**事务**。事务保证四件事,合称 **ACID**(四个英文单词的首字母):

| 性质 | 大白话 | PostgreSQL 怎么做到的(**先了解,不必懂**) |
|------|--------|------------------------------------------|
| **A**tomicity 原子性 | 要么全做,要么全不做 | 记录事务日志,可以整体撤销 |
| **C**onsistency 一致性 | 不会把数据改成违反约束的样子 | 约束会被强制执行,违反就整条拒绝 |
| **I**solation 隔离性 | 多个事务同时跑,互相不干扰 | 多版本快照 + 加锁 |
| **D**urability 持久性 | 提交成功就不会丢 | 提交时强制把日志写入磁盘 |

> **为什么"原子性"最常用**:一次转账要"扣 A 的钱"和"加 B 的钱"两步。原子性保证这两步不会只成功一半。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- 或 ROLLBACK;
```

**PostgreSQL 默认是"自动提交"**:没有显式 `BEGIN` 时,每条语句自成事务。

```sql
UPDATE t SET x = 1;            -- 立即自动提交
BEGIN; UPDATE t SET x = 1; ... -- 需显式 COMMIT 或 ROLLBACK
```

**DDL 也能回滚**:建表、改表结构、删表这些"改结构"的操作,同样可以放进事务里,并且能撤销。

```sql
BEGIN;
DROP TABLE users;
ROLLBACK;      -- ✅ 表回来了 —— 注意不是所有数据库都支持这样回滚
```

> **这一点的实用价值**:线上改表结构时如果发现改错了,可以直接 `ROLLBACK` 撤销,而不用去做数据恢复。

### 二、保存点 SAVEPOINT

在事务内部设置"回滚点",支持部分回滚。

```sql
BEGIN;
INSERT INTO users (email, name) VALUES ('a@b.c', 'A');
SAVEPOINT sp1;

INSERT INTO users (email, name) VALUES ('a@b.c', 'B');   -- 违反唯一约束,报错
ROLLBACK TO SAVEPOINT sp1;                                -- 只撤销第二条

INSERT INTO users (email, name) VALUES ('c@b.c', 'C');    -- 继续
COMMIT;
```

**关键点**:PostgreSQL 中一条语句报错后,事务进入**"aborted"状态**,后续语句全部被拒绝,直到 `ROLLBACK` 或 `ROLLBACK TO SAVEPOINT`。

```sql
BEGIN;
SELECT 1/0;      -- ERROR: division by zero
SELECT 1;        -- ERROR: current transaction is aborted, commands ignored until end of transaction block
ROLLBACK;
```

**应用层的意义**:需要"逐条容错"的批量处理,必须为每条(或每批)包 `SAVEPOINT`。

```sql
BEGIN;
SAVEPOINT s;
-- 尝试插入
RELEASE SAVEPOINT s;      -- 成功则释放
-- 失败则 ROLLBACK TO SAVEPOINT s 后继续下一条
```

### 三、隔离级别:PostgreSQL 的实际语义

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
BEGIN ISOLATION LEVEL SERIALIZABLE;
```

| 声明的级别 | PostgreSQL 实际行为 | 是否默认 |
|-----------|---------------------|----------|
| `READ UNCOMMITTED` | **等价于 `READ COMMITTED`** | |
| `READ COMMITTED` | 每条**语句**取新快照 | ✅ **默认** |
| `REPEATABLE READ` | 每条**事务**取一个快照(即快照隔离) | |
| `SERIALIZABLE` | `REPEATABLE READ` + 串行化冲突检测(SSI) | |

> **重要事实**:PostgreSQL **不支持脏读**。`READ UNCOMMITTED` 被静默降级为 `READ COMMITTED`。因此 PostgreSQL 从不读到未提交数据。

**四种并发异常与隔离级别的关系**

| 异常 | READ COMMITTED | REPEATABLE READ | SERIALIZABLE |
|------|----------------|-----------------|--------------|
| 脏读 dirty read | ❌ 不可能 | ❌ 不可能 | ❌ 不可能 |
| 不可重复读 | ✅ 可能 | ❌ 不可能 | ❌ 不可能 |
| 幻读 | ✅ 可能 | ❌ 不可能(PG 快照隔离已阻止) | ❌ 不可能 |
| 写偏斜 write skew | ✅ 可能 | ✅ 可能 | ❌ 不可能 |
| 丢失更新 | 通过行锁避免 | 报错需重试 | 报错需重试 |

**各隔离级别的行为示例**

```sql
-- READ COMMITTED:同一事务内两次相同查询可能返回不同结果
BEGIN;
SELECT amount FROM orders WHERE id = 1;   -- 100
-- (另一事务把 amount 改成 200 并提交)
SELECT amount FROM orders WHERE id = 1;   -- 200 ← 变了!
COMMIT;

-- REPEATABLE READ:同一事务内快照固定
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT amount FROM orders WHERE id = 1;   -- 100
-- (另一事务改成 200 并提交)
SELECT amount FROM orders WHERE id = 1;   -- 100 ← 不变
COMMIT;
```

**REPEATABLE READ 下的更新冲突**

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT amount FROM orders WHERE id = 1;        -- 100
-- 另一事务已更新该行并提交
UPDATE orders SET amount = 150 WHERE id = 1;
-- ERROR: could not serialize access due to concurrent update
```

> 这是**保护而非故障**:`REPEATABLE READ`/`SERIALIZABLE` 下遇到并发更新会报错,应用必须**捕获 `40001` 并重试整个事务**。

```sql
-- 应用伪代码
for attempt in range(3):
    try:
        with conn.transaction(isolation='repeatable read'):
            ...    # 业务逻辑
        break
    except SerializationFailure:      # SQLSTATE 40001
        continue
```

**写偏斜与 SERIALIZABLE**

典型例子:两名医生同时查看"至少一人在岗"的约束,各自以为自己可以离岗,结果双双离岗。行级锁无法阻止(它们更新不同行),只有 `SERIALIZABLE`(SSI 检测读写依赖环)能阻止。

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call WHERE shift = 'A' AND on_duty;
-- 若另一并发事务也做了相同判断并提交
UPDATE on_call SET on_duty = false WHERE doctor = 'Dr.X';
-- ERROR: could not serialize access due to read/write dependencies among transactions
```

细节见 [[postgresql/03-进阶阶段-深度剖析/并发控制与锁内核/原理剖析-SSI可串行化隔离]]。

### 四、事务相关的会话设置

```sql
-- 语句超时(防止查询失控)
SET statement_timeout = '30s';
SET LOCAL statement_timeout = '5s';       -- 仅当前事务

-- 空闲事务超时(防止应用忘提交)  ★生产必配
SET idle_in_transaction_session_timeout = '60s';
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';

-- 锁等待超时
SET lock_timeout = '3s';
SET LOCAL lock_timeout = '3s';

-- 只读事务(可减少开销,防止误写)
BEGIN READ ONLY;
BEGIN READ WRITE;
SET TRANSACTION READ ONLY;

-- 可延迟(用于外键 DEFERRABLE 场景)
BEGIN; SET CONSTRAINTS ALL DEFERRED; ... COMMIT;
```

**超时配置的经验值**

| 参数 | 建议 | 理由 |
|------|------|------|
| `statement_timeout` | 应用侧设 5–30s | 防慢查询拖垮连接池 |
| `idle_in_transaction_session_timeout` | 30–120s | 防"忘提交"的长事务阻塞 VACUUM |
| `lock_timeout` | 1–5s | 防长时间等锁堆积 |
| `idle_session_timeout` | (PG14+) 5–30min | 防空闲连接占用 |

### 五、长事务为什么是万恶之源

长事务(包括"开着事务不提交"的空闲事务)会引发一系列连锁问题:

| 后果 | 机制 |
|------|------|
| **阻塞 VACUUM** | 死元组在被所有快照"看不见"之前不能被回收;长事务持有旧快照 → 死元组无法清理 → 表膨胀 |
| **xid 消耗** | 事务频繁创建子事务(SAVEPOINT)也会消耗 xid,推高风险 |
| **锁持有时间长** | 阻塞其他事务,甚至死锁 |
| **复制延迟** | 长事务在只读副本上需等整体提交才能应用,`pg_stat_replication` 会显示滞后 |
| **WAL 堆积** | 长事务阻止检查点推进,`pg_wal` 目录膨胀 |

```sql
-- 找出长事务与空闲事务 ★排障必会
SELECT pid, state, xact_start, now() - xact_start AS xact_age,
       query_start, now() - query_start AS query_age,
       state, wait_event_type, wait_event, left(query, 60) AS q
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 20;

-- 老快照(会阻止 VACUUM)
SELECT pid, backend_xmin, xact_start FROM pg_stat_activity WHERE backend_xmin IS NOT NULL;

-- 清理空闲事务
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
WHERE state = 'idle in transaction' AND now() - state_change > interval '5 min';
```

> **工程纪律**:事务只包裹**必需的数据库操作**,不要在事务里做 HTTP 请求、文件 IO、用户交互。把"计算/远程调用"移到事务外。

### 六、两阶段提交(了解即可)

跨多个数据库/实例的原子提交需 `PREPARE TRANSACTION`:

```sql
BEGIN;
UPDATE ...;
PREPARE TRANSACTION 'tx1';
-- 稍后在任一时刻
COMMIT PREPARED 'tx1';
-- 或
ROLLBACK PREPARED 'tx1';
```

代价:prepared transaction 会**长期占用资源、阻止 VACUUM**,需监控 `pg_prepared_xacts`。除非真正需要跨库原子性(且无法用其他方案),否则不要用。

## 小结

- PostgreSQL 默认自动提交;`BEGIN` 后可 `COMMIT`/`ROLLBACK`,**DDL 也可回滚**。
- 语句报错后事务进入 aborted 状态,需 `ROLLBACK TO SAVEPOINT` 或整体 `ROLLBACK`。
- 隔离级别:默认 `READ COMMITTED`;`READ UNCOMMITTED` 被降级为 `READ COMMITTED`(不支持脏读);`REPEATABLE READ` 是快照隔离;`SERIALIZABLE` 加 SSI 检测。
- `REPEATABLE READ`/`SERIALIZABLE` 遇并发更新会报 `40001`,**应用必须重试**。
- 长事务与空闲事务会阻塞 VACUUM、造成膨胀与复制延迟;务必配置 `idle_in_transaction_session_timeout` 与 `statement_timeout`。

## 练习

1. 在两个会话中复现"`READ COMMITTED` 下同一事务内两次查询结果不同",再把隔离级别改为 `REPEATABLE READ` 复现不变。
2. 在事务内制造一次报错,验证后续语句被拒绝,并用 `SAVEPOINT` 恢复继续执行。
3. 在事务内 `DROP TABLE` 后 `ROLLBACK`,验证表恢复。
4. 用 `pg_stat_activity` 找出一个 `idle in transaction` 会话,记录其 `xact_age`,然后终止它。
5. 故意制造一个 `REPEATABLE READ` 下的并发更新冲突,记录 SQLSTATE(应为 `40001`)。
