# 3.0 表、主键与外键:为什么要把数据分成多张表

## 学习目标

读完这一篇,你应该能:

- 说清"为什么不把所有信息塞进一张表"
- 解释主键是什么、为什么每张表都该有
- 解释外键是什么、它能拦住什么错误
- 分清三种表间关系(一对一 / 一对多 / 多对多),并知道各自怎么建表

**这一篇不讲怎么写 SQL,只讲概念。** 概念清楚之后,第 3.1 篇的 `CREATE TABLE` 才会读得懂。

## 一、先看"全塞一张表"会怎样

假设你把用户和他们的订单都记在一张表里:

```
表: everything
┌────┬──────────┬────────┬───────────┬───────────┬────────┬────────┐
│ 用户名 │ 手机号    │ 订单号  │ 下单时间   │ 商品      │ 数量   │ 单价   │
├────┼──────────┼────────┼───────────┼───────────┼────────┼────────┤
│ 安妮 │ 138xxxx  │ O-1001 │ 09-01     │ 键盘      │  1     │ 299    │
│ 安妮 │ 138xxxx  │ O-1002 │ 09-05     │ 鼠标      │  2     │  99    │
│ 安妮 │ 138xxxx  │ O-1003 │ 09-09     │ 显示器    │  1     │ 1299   │
│ 本   │ 139xxxx  │ O-1004 │ 09-03     │ 键盘      │  1     │ 299    │
└────┴──────────┴────────┴───────────┴───────────┴────────┴────────┘
```

看起来"一张表搞定",但立刻有三个问题:

| 问题 | 具体表现 |
|------|----------|
| **数据重复** | 安妮的手机号被写了 3 遍。她换号时要改 3 行,漏改一行就出不一致 |
| **想不出该怎么记** | 一张订单里有 2 个商品?只能再加一行,或者再加"商品2""商品3"列——列数无法预知 |
| **会连累删除** | 删掉安妮最后一条订单时,顺带把"安妮这个用户"的信息也删没了 |

**核心矛盾**:一张表只能表达**一种**事物的结构。而"用户"和"订单"是两种事物,字段完全不同。

## 二、拆表:一种事物一张表

把上面那张表拆成两张:

```
表: users(用户)                         表: orders(订单)
┌────┬──────────┬────────┐             ┌────────┬─────────┬───────────┬────────┐
│ id │ 手机号    │ 姓名   │             │ id     │ user_id │ 下单时间   │ 商品   │
├────┼──────────┼────────┤             ├────────┼─────────┼───────────┼────────┤
│  1 │ 138xxxx  │ 安妮   │             │ O-1001 │    1    │ 09-01     │ 键盘   │
│  2 │ 139xxxx  │ 本     │             │ O-1002 │    1    │ 09-05     │ 鼠标   │
└────┴──────────┴────────┘             │ O-1003 │    1    │ 09-09     │ 显示器 │
                                        │ O-1004 │    2    │ 09-03     │ 键盘   │
                                        └────────┴─────────┴───────────┴────────┘
```

**问题全解决了**:

- 手机号只存 1 遍,换号只改 1 行。
- 订单表里想加多少行都行,不需要预设列。
- 删掉订单不会碰到用户信息。

**代价**:想知道"安妮有哪些订单"时,得把两张表**对应起来查**。而"对应"是靠 `orders.user_id` 指向 `users.id` 实现的。

这就是**关系型数据库**的核心思路:**用多张表分别描述不同事物,再用"引用"把它们连起来。**

> **这就解释了本套文档第 5 章"多表连接(JOIN)"存在的意义**:拆表解决了重复,但代价是查询时要重新拼。JOIN 就是"拼"的手段。

## 三、主键:一行的身份

拆表之后立刻需要一个东西:**如何唯一地指认某一行?**

上面 `users` 表里的 `id` 就是这个作用。它叫 **主键(PRIMARY KEY)**。

### 主键的两条硬性要求

| 要求 | 含义 |
|------|------|
| **唯一** | 全表不能有两行是同一个主键值 |
| **非空** | 主键不能是 NULL |

**为什么必须唯一**:因为别的地方要用它来"指认"这一行。如果两行主键相同,引用就指不清了。

### 主键的三种常见做法

| 做法 | 例子 | 优点 | 缺点 |
|------|------|------|------|
| **自增整数**(最常用) | `1, 2, 3, ...` | 简单、存储小、有序插入快 | 会暴露业务量(第 100 单就是 100);多套系统合并会撞号 |
| **UUID** | `0198f0a1-8b2c-7def-...` | 全局唯一、不暴露业务量 | 占空间、可读性差。随机 UUID 还会拖慢插入 |
| **业务编号** | `O-20260901-0007` | 人看得懂、有业务含义 | 业务规则变了就麻烦;长度长 |

**本套文档的建议**:业务表用**自增整数**做主键(Date PostgreSQL 的写法是 `GENERATED ALWAYS AS IDENTITY`,第 3.1 篇讲),需要对外暴露编号时**另外加一列**业务编号(如 `order_no`)并加唯一约束。

### 复合主键

有些表天生需要**两列一起**才能确定一行。例如"订单里买了哪些商品":

```
表: order_items(订单明细)
┌──────────┬────────────┬──────┐
│ order_id │ product_id │ 数量  │
├──────────┼────────────┼──────┤
│ O-1001   │ P-键盘     │  1   │
│ O-1001   │ P-鼠标     │  2   │   ← 同一个订单里两行不同商品
│ O-1002   │ P-键盘     │  1   │
└──────────┴────────────┴──────┘
```

单个 `order_id` 会重复,单个 `product_id` 也会重复,但 **(order_id, product_id) 这一对**不会重复。所以主键可以写成:

```sql
PRIMARY KEY (order_id, product_id)   -- 两列合起来当主键
```

这叫**复合主键**。

## 四、外键:让引用不会悬空

有了主键,就能"指认"了。`orders.user_id` 存的是 `users.id` 的值——这种"指向另一张表某一行"的列,叫 **外键(FOREIGN KEY)**。

### 外键帮我们拦住什么

**如果没有外键**,你可能写出这样的数据:

```
orders.user_id = 99    ← 但 users 表里根本没有 id=99 的用户!
```

这条订单就成了"孤儿":它指向一个不存在的用户。以后查"这个用户的所有订单"永远查不到它,数据出现静默损坏。

**加上外键之后**,数据库会在写入时检查:

```sql
-- 假设 users 表只有 id = 1, 2
INSERT INTO orders (user_id, ...) VALUES (99, ...);
-- ERROR: insert or update on table "orders" violates foreign key constraint
-- DETAIL: Key (user_id)=(99) is not present in table "users".
```

**数据库直接拒绝了。** 这就是外键的价值:**把"引用必须有效"这条规则交给数据库强制执行**,而不是指望每个写入的地方都记得检查。

### 外键的声明方式

```sql
CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id)   -- ← 这一句就是外键
    -- ...
);
```

`REFERENCES users(id)` 的含义是:**`user_id` 的值必须出现在 `users` 表的 `id` 列里**。

> **一个必须记住的实践要点**:外键列上**不会自动建索引**。这会带来性能问题(见 3.2 篇),但**正确性不受影响**。入门阶段先用着,性能问题到中段再处理。

### 被引用的行被删除时怎么办

安妮注销了,她名下的订单怎么办?这就是 `ON DELETE` 动作要决定的:

| 动作 | 含义 | 适用 |
|------|------|------|
| `RESTRICT` / `NO ACTION`(默认) | **不允许删**,除非先处理掉引用的行 | 保守、安全 |
| `CASCADE` | **连带删除**她的所有订单 | 订单离开用户没有意义时 |
| `SET NULL` | 把订单的 `user_id` 置为 NULL(保留订单,但不知道属于谁) | 数据要留档时 |

写法:

```sql
user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE
```

**选哪个是业务判断,不是技术问题。** 完整对比见 [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.2-约束体系与数据完整性]]。

## 五、表间关系只有三种

拆表时你只需要判断"这两类事物是什么关系"。

### 关系一:一对多(最常见)

**一个用户有多个订单;一个订单只属于一个用户。**

```
users                          orders
┌────┐                    ┌────────┬─────────┐
│ id │◄───────────────────┤ user_id │ id      │
├────┤   一个 user           ├────────┼─────────┤
│  1 │   对应多个 order      │    1    │ O-1001  │
│  2 │   (箭头指向"一"那侧)  │    1    │ O-1002  │
└────┘                    │    2    │ O-1003  │
                          └────────┴─────────┘
```

**建法**:在**"多"的那一侧**加一列外键。

```sql
CREATE TABLE users  (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, ...);
CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id),   -- ← 外键加在"多"的一侧
    ...
);
```

### 关系二:一对一

**一个用户有一份资料;一份资料属于一个用户。**

**建法**:在从属的那一侧加外键,并加**唯一约束**(保证不会有两份资料指向同一个用户)。

```sql
CREATE TABLE user_profiles (
    user_id bigint PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,  -- 主键即外键,天然唯一
    bio     text,
    avatar  text
);
```

> **为什么常常要拆成一对一**:因为资料表可能字段大、更新频繁,或者需要单独控制访问权限。分开可以避免频繁更新拖累主表。

### 关系三:多对多

**一个订单有多个商品;一个商品出现在多个订单里。**

**关键**:多对多**无法**直接用外键表达,必须建一张**中间表**。

```
users        order_items           products
┌────┐       ┌──────────┬────────────┐       ┌────┐
│ id │◄──────┤ order_id │ product_id ├──────►│ id │
└────┘       │ 数量      │            │       └────┘
             └──────────┴────────────┘
                 中间表:每行表示"某订单含某商品若干"
```

```sql
CREATE TABLE order_items (
    order_id   bigint NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,
    product_id bigint NOT NULL REFERENCES products(id),
    qty        integer NOT NULL CHECK (qty > 0),
    PRIMARY KEY (order_id, product_id)     -- 复合主键:同一订单里同一商品只出现一行
);
```

**中间表的一般模式**:

- 两个外键分别指向两边。
- 通常用**(两个外键)作复合主键**,保证组合不重复。
- 中间表自己可以带属性(这里的 `qty` 是数量)。

> **同一套模式还能表达更多信息**:比如"用户收藏了哪些商品"(收藏表)、"学生选修了哪些课"(选课表)、"文章有哪些标签"(标签关联表)。**看到多对多,就想到中间表。**

## 六、约束:让数据库替你把关

上面出现的主键、外键就是**约束(constraint)** 的两种。约束是**数据库强制执行的规则**:

| 你想表达的规则 | 用哪个约束 |
|----------------|-----------|
| 这一列不能为空 | `NOT NULL` |
| 这一列的值不能重复 | `UNIQUE` |
| 这一行怎么被唯一标识 | `PRIMARY KEY` |
| 这一列必须指向另一张表存在的行 | `FOREIGN KEY` |
| 这一列必须满足某个条件 | `CHECK (...)` |

**为什么把规则写进数据库**:因为你的应用可能有多个入口(网页、后台脚本、运维手改 SQL)。**只在应用里检查,绕过应用的写入就没人管了。** 约束是数据完整性的最后一道墙。

细节见 [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.2-约束体系与数据完整性]]。

## 七、一个完整的例子(把上面串起来)

需求:用户可以下多个订单,每个订单可以含多个商品。

```sql
-- ① 用户表:一个用户一行
CREATE TABLE users (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- 主键
    email text NOT NULL UNIQUE,                              -- 唯一
    name  text NOT NULL
);

-- ② 商品表:一个商品一行
CREATE TABLE products (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku   text NOT NULL UNIQUE,
    name  text NOT NULL,
    price numeric(12,2) NOT NULL CHECK (price >= 0)           -- 规则:价格不能为负
);

-- ③ 订单表:一个订单一行;"多"的一侧放外键 → 这是"一对多"
CREATE TABLE orders (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    status     text NOT NULL DEFAULT 'pending',
    created_at timestamptz NOT NULL DEFAULT now()
);

-- ④ 订单明细表:中间表 → 这是"多对多"
CREATE TABLE order_items (
    order_id   bigint NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,
    product_id bigint NOT NULL REFERENCES products(id),
    qty        integer NOT NULL CHECK (qty > 0),
    unit_price numeric(12,2) NOT NULL,
    PRIMARY KEY (order_id, product_id)                        -- 复合主键
);
```

**★ 先不用管那些修饰词。** 你现在只要看懂这张"关系图":

```
users ──1:N──► orders ──1:N──► order_items ◄──N:1── products
                                    │
                        (orders 与 products 之间由它连成多对多)
```

**每一步的含义**:

1. 用户和订单:**一对多**,外键在 `orders`。
2. 订单和商品:**多对多**,靠中间表 `order_items`。
3. `order_items` 存了"数量"和"下单时的单价"——**为什么单价要单独存?** 因为商品价格以后会变,而订单必须保留"当时成交的价格"。这是很典型的建模判断。

> **上面这段 4 张表的建表语句,就是第 3.1 篇要逐个词讲清楚的内容。** 如果现在觉得 `GENERATED ALWAYS AS IDENTITY`、`NOT NULL UNIQUE`、`CHECK (...)` 看不懂,**完全正常**——先去 3.1。

## 小结

- 一张表只能描述**一种**事物。不同事物混在一张表里会导致**重复、列数无法预知、意外连带删除**。
- **主键**是一行的身份:唯一 + 非空。业务表推荐自增整数,并另加业务编号列。
- **外键**是"指向另一张表某一行"的列,由数据库保证引用有效,防止出现"孤儿数据"。
- **外键列不会自动建索引**(3.2 详述)。
- 表间关系只有三种:
  - **一对多** → 外键加在"多"的一侧(最常见)
  - **一对一** → 从属侧外键 + 唯一约束
  - **多对多** → 必须建中间表,通常用两个外键作复合主键
- **约束**是把业务规则写进数据库,让你不必依赖所有应用入口都写对。
