# 3.2 约束体系与数据完整性

## 学习目标

- 完整掌握五类约束及其底层实现
- 理解外键的引用动作与性能代价
- 知道约束与索引的关系,避开"外键没索引"的性能陷阱

## 前置知识

- [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.0-表主键与外键]] — 主键、外键、表间关系的概念基础
- [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.1-DDL建表与列定义]] — 建表语句的语法基础

## 正文

> **本篇怎么读**:五类约束里,`NOT NULL` / `PRIMARY KEY` / `UNIQUE` / `CHECK` / `FOREIGN KEY` 是入门必须掌握的;最后的 `EXCLUDE` 约束属于进阶用法,第一遍可以跳过。遇到不认识的关键字查 [[postgresql/术语与关键字手册]]。

### 一、五类约束总览

| 约束 | 保证 | 底层实现 |
|------|------|----------|
| `NOT NULL` | 列非空 | 列标志位,无索引 |
| `PRIMARY KEY` | 唯一 + 非空 | **隐含唯一 B-tree 索引** |
| `UNIQUE` | 值唯一(允许多 NULL,P**G15+** 可改) | **隐含唯一 B-tree 索引** |
| `FOREIGN KEY` | 引用存在性 | 引用侧需索引(否则有性能问题) |
| `CHECK` | 表达式为真或 NULL | 无索引,写入时求值 |
| `EXCLUDE` | 任意两行不满足指定关系 | 需 GiST/SP-GiST 索引 |

### 二、主键与唯一约束

```sql
-- 命名式(推荐)
CREATE TABLE t1 (
    id    bigint NOT NULL,
    email text NOT NULL,
    CONSTRAINT t1_pk PRIMARY KEY (id),
    CONSTRAINT t1_email_uk UNIQUE (email)
);

-- 复合主键
CREATE TABLE order_items (
    order_id   bigint NOT NULL,
    product_id bigint NOT NULL,
    qty        integer NOT NULL,
    PRIMARY KEY (order_id, product_id)
);
```

**主键 vs 唯一约束的差异**

| 维度 | PRIMARY KEY | UNIQUE |
|------|-------------|--------|
| NULL | ❌ 不允许 | ✅ 允许(默认允许多个) |
| 每表数量 | 1 个 | 多个 |
| 可作外键引用目标 | ✅ | ✅ |

**为唯一约束指定索引行为**

```sql
-- 已知数据本就唯一,跳过校验以加速创建
ALTER TABLE t1 ADD CONSTRAINT t1_email_uk UNIQUE (email);

-- 唯一索引(与唯一约束等价,但用索引语法)
CREATE UNIQUE INDEX t1_email_uk2 ON t1 (lower(email));   -- 大小写不敏感唯一
```

**部分唯一索引**——只对满足条件的行做唯一性保证:

```sql
-- 每个用户只能有一条"未删除"的记录
CREATE UNIQUE INDEX t1_active_uk ON t1 (user_id) WHERE deleted_at IS NULL;
```

### 三、外键:引用动作与性能代价

```sql
CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL,
    CONSTRAINT orders_user_fk FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE RESTRICT          -- 被引用则禁止删除(默认)
        ON UPDATE CASCADE,          -- 主键变更时级联更新
    ...
);
```

**引用动作一览**

| 动作 | `ON DELETE` 行为 | 何时用 |
|------|------------------|--------|
| `NO ACTION`(默认) | 拒绝,但可延迟到语句/事务末检查 | 默认行为 |
| `RESTRICT` | **立即**拒绝 | 严格保护,不留延迟余地 |
| `CASCADE` | 级联删除子行 | 明细依附主表(订单→订单行) |
| `SET NULL` | 子行外键置 NULL | 允许"孤立但仍存在" |
| `SET DEFAULT` | 子行外键置默认值 | 少用 |

`NO ACTION` 与 `RESTRICT` 的差别:**前者可被 `DEFERRABLE INITIALLY DEFERRED` 推迟到事务提交时检查**,可用于"先删后建"的循环引用场景。

```sql
CONSTRAINT fk_x FOREIGN KEY (a) REFERENCES t(b)
    DEFERRABLE INITIALLY DEFERRED
```

**关键性能事实:外键列上不会自动建索引。**

这是最常见的中级陷阱。原因:

- **父表**必须有唯一索引(`REFERENCES` 要求引用目标是主键或唯一列),这个索引是自动存在或被要求的。
- **子表**(外键列所在表)**不会**自动建索引。

后果有两个:

1. **`ON DELETE CASCADE` / `ON UPDATE CASCADE` 会非常慢**——父表删一行时,数据库需全表扫描子表找引用行。
2. 按外键列查询/连接(如"查某用户的所有订单")会走全表扫描。

```sql
CREATE INDEX orders_user_id_idx ON orders (user_id);   -- ✅ 必须手工加
```

> **PG18 起**外键检查有性能改进(更快的外键校验路径,PG19 进一步优化),但"子表需索引"这条规则不变。

**检查外键是否缺索引**

入门阶段用最直接的办法:用 `\d 表名` 看输出里的两个区块。

```
\d orders
```

```
Indexes:
    "orders_pkey" PRIMARY KEY, btree (id)                          ← 主键自带的索引
    "orders_user_id_idx" btree (user_id)                           ← 手工建的外键索引
Foreign-key constraints:
    "orders_user_fk" FOREIGN KEY (user_id) REFERENCES users(id)    ← 外键声明本身
```

**判断方法**:如果 `Foreign-key constraints` 里出现了某个外键列,而 `Indexes` 里**找不到以该列打头的索引**,那这个外键列就缺索引。

> **更系统的做法**:一条查询列出全库所有"缺索引的外键"。但那需要用到 `pg_constraint`、`pg_attribute`、`pg_index` 这几张系统目录表(它们的列名见 [[postgresql/术语与关键字手册]] 第十四节),属于进阶内容。
>
> **入门阶段只要记住这一条就够:外键列要手工建索引。**

### 四、CHECK 约束

```sql
CREATE TABLE accounts (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind    text NOT NULL,
    balance numeric(14,2) NOT NULL,
    CONSTRAINT acc_kind_ck CHECK (kind IN ('checking','savings')),
    CONSTRAINT acc_bal_ck  CHECK (balance >= 0)
);
```

**重要语义:CHECK 通过的条件是"表达式为 `true` 或 `NULL`"。**

```sql
-- 因此下面这条约束对 kind 为 NULL 的行不做限制
ALTER TABLE accounts ADD CONSTRAINT ck CHECK (kind <> 'x');
```

要严格约束,配合 `NOT NULL`。

**跨列 CHECK**

```sql
CONSTRAINT period_ck CHECK (end_date IS NULL OR end_date > start_date)
```

**表级 vs 列级**:涉及多列必须写表级;单列两者等价。

**`NO INHERIT`**:让 CHECK 不对继承子表生效(少用)。

### 五、EXCLUDE 约束(排他)

需要"任意两行不满足指定关系"时用,常见于时间/空间排期。

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 让等值也能进 GiST

CREATE TABLE bookings (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room      text NOT NULL,
    during    tstzrange NOT NULL,
    CONSTRAINT bookings_no_overlap
        EXCLUDE USING gist (room WITH =, during WITH &&)
);

-- 插入重叠区间会被拒绝
INSERT INTO bookings (room, during) VALUES ('A', '[2026-09-19 10:00, 2026-09-19 12:00)');
INSERT INTO bookings (room, during) VALUES ('A', '[2026-09-19 11:00, 2026-09-19 13:00)');  -- ERROR
```

`WITH` 后可用的操作符:任何 GiST/SP-GiST 索引支持的"冲突"操作符,如 `=` `&&` `<>`。

### 六、约束管理速查

```sql
-- 查看某表所有约束
\d t1
SELECT conname, contype, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 't1'::regclass;

-- 添加
ALTER TABLE t1 ADD CONSTRAINT name CHECK (...);
ALTER TABLE t1 ADD CONSTRAINT name CHECK (...) NOT VALID;   -- 只对新行生效,免全表扫描
ALTER TABLE t1 VALIDATE CONSTRAINT name;                    -- 后台补校验

-- 删除
ALTER TABLE t1 DROP CONSTRAINT name;
ALTER TABLE t1 ALTER CONSTRAINT name DEFERRABLE INITIALLY DEFERRED;   -- 仅外键可用

-- 临时禁用(不推荐,需超级用户)
ALTER TABLE t1 DISABLE TRIGGER ALL;   -- 外键由触发器实现
```

**约束与触发器**:`FOREIGN KEY` 在 PostgreSQL 内部由**系统触发器**实现,这也是 `DISABLE TRIGGER ALL` 能绕过外键的原因。CHECK 与 NOT NULL 是写入时即时求值,不是触发器。

### 七、约束放在哪一层?——架构取舍

| 位置 | 优点 | 缺点 |
|------|------|------|
| 数据库约束 | 唯一权威,所有写入路径都生效 | 变更需 DDL;复杂规则难表达 |
| 应用层校验 | 灵活、错误提示友好 | 多入口时易被绕过 |

**结论**:**能进数据库的规则就进数据库**。应用层做的应是"友好提示",不是"唯一防线"。约束是数据完整性的最后一道墙,挡住的是所有绕过应用的写入(脚本、运维手改、其他服务)。

## 小结

- 主键 = 唯一 + 非空;唯一约束允许多个 NULL(PG15+ 可加 `NULLS NOT DISTINCT`)。
- **外键列不会自动建索引** —— `ON DELETE CASCADE` 慢与按外键列查询慢都源于此。
- CHECK 通过的条件是"真或 NULL",要严格需配 `NOT NULL`。
- `EXCLUDE` 用于区间不重叠等排他规则,需 GiST 索引(配合 `btree_gist`)。
- 大表加约束用 `NOT VALID` + `VALIDATE` 两步,避免长时间持锁。
- 完整性规则应尽量下沉到数据库。

## 练习

1. 建两张表并给外键列**故意不加索引**,插入 10 万行子数据,执行父表 `DELETE` 并计时;然后加上索引重测,比较耗时。
2. 用给出的 SQL 找出你库中所有"外键列无索引"的表。
3. 用 `EXCLUDE USING gist` 建一张会议室排期表,验证重叠区间被拒绝、相邻不重叠区间被接受。
4. 给一张大表用 `NOT VALID` 方式加 CHECK 约束,再用 `VALIDATE` 完成校验,过程中观察 `pg_constraint.convalidated` 的变化。
5. 验证 `CHECK (x <> 1)` 对 `x IS NULL` 的行不生效,并给出修正写法。
