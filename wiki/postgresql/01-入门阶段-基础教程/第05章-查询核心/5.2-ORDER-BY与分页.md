# 5.2 ORDER BY 与分页

## 学习目标

- 掌握排序规则、NULL 位置、多列排序
- 分清 `LIMIT/OFFSET`、键集分页(keyset)的适用场景
- 理解排序与索引的关系,知道什么时候必须排、什么时候可以吃索引顺序

## 前置知识

[[postgresql/01-入门阶段-基础教程/第05章-查询核心/5.1-WHERE与运算符]]

## 正文

### 一、基础排序

```sql
SELECT * FROM orders ORDER BY created_at;              -- 升序(默认)
SELECT * FROM orders ORDER BY created_at DESC;         -- 降序
SELECT * FROM orders ORDER BY amount DESC, id ASC;     -- 多列,依次决胜
SELECT * FROM orders ORDER BY 1 DESC;                  -- 按第 1 列排(不推荐,可读性差)
SELECT * FROM orders ORDER BY created_at DESC NULLS LAST;
```

**排序规则(ORDER BY 的"规则")**

| 维度 | 可选项 |
|------|--------|
| 方向 | `ASC`(默认)/ `DESC` |
| NULL 位置 | `NULLS FIRST` / `NULLS LAST`(升序默认 `NULLS LAST`,降序默认 `NULLS FIRST`) |

```sql
-- 等价写法演示:DESC 时 NULL 默认在前
ORDER BY amount DESC              -- NULL 在前
ORDER BY amount DESC NULLS LAST   -- 强制 NULL 在后
```

**排序规则(collation)的影响**

```sql
SELECT name FROM users ORDER BY name;                    -- 按会话/列排序规则
SELECT name FROM users ORDER BY name COLLATE "C";         -- 强制字节序
SELECT name FROM users ORDER BY name COLLATE "zh-x-icu";  -- 中文拼音序(需 ICU)
```

> **高频坑**:`ORDER BY` 用了与**索引建立的排序规则不同**的 collation,索引的物理有序性就不再可用,规划器只能排序。要么查询与索引一致,要么为特定 collation 单独建索引。

### 二、表达式排序与自定义顺序

```sql
-- 表达式排序
SELECT * FROM products ORDER BY price * (1 - discount);

-- 自定义业务顺序(CASE)
SELECT * FROM orders
ORDER BY CASE status
           WHEN 'paid' THEN 1
           WHEN 'pending' THEN 2
           WHEN 'shipped' THEN 3
           ELSE 4
         END, created_at DESC;

-- 用数组位置定义顺序(简洁写法)
SELECT * FROM orders
ORDER BY array_position(ARRAY['paid','pending','shipped'], status), created_at DESC;

-- 用 VALUES 表连接排序
SELECT o.* FROM orders o
JOIN (VALUES ('paid',1),('pending',2),('shipped',3)) AS s(status, ord)
  ON o.status = s.status
ORDER BY s.ord;
```

若业务顺序稳定且高频使用,更好的做法是建一张**查找表**存 `sort_order` 列(见 [[postgresql/01-入门阶段-基础教程/第02章-数据类型/2.4-布尔枚举与UUID]])。

### 三、分页的三种方式

#### 方式一:`LIMIT / OFFSET`

```sql
SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET 400;
```

**问题**

| 问题 | 说明 |
|------|------|
| **深翻页慢** | `OFFSET 100000` 要求引擎先产生并丢弃前 10 万行 |
| **结果漂移** | 翻页期间有新数据插入/删除,会导致重复或漏行 |
| **必须有序** | 不排序则结果不确定 |

#### 方式二:键集分页(Keyset / Cursor Pagination)—— **推荐**

不用 `OFFSET`,而是用"上一页最后一行的排序键"作为游标。

```sql
-- 第 1 页
SELECT id, created_at, amount
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 后续页:把上一页最后一行的 (created_at, id) 传入
SELECT id, created_at, amount
FROM orders
WHERE (created_at, id) < ('2026-09-19 12:00:00+08', 998877)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

**行值比较 `(a, b) < (x, y)`** 是键集分页的关键语法,PostgreSQL 按字典序比较,等价于 `a < x OR (a = x AND b < y)`。

| 维度 | `OFFSET` | 键集分页 |
|------|----------|----------|
| 深翻页性能 | O(offset) 线性变慢 | 恒定,走索引区间 |
| 结果稳定性 | 易漂移 | 稳定 |
| 跳页 | ✅ 可跳到任意页 | ❌ 只能顺序前进(或需要缓存游标) |
| 适用 | 后台管理、总页数少 | 前台信息流、无限滚动、API |

> 键集分页要求排序键**唯一且可比较**。若排序键不唯一,务必在末尾补主键(如上例的 `id DESC`),否则会漏行。

#### 方式三:窗口函数取"第 N 页"(仅小数据集)

```sql
SELECT * FROM (
    SELECT *, row_number() OVER (ORDER BY created_at DESC, id DESC) AS rn
    FROM orders
) t WHERE rn BETWEEN 41 AND 60;
```

比 `OFFSET` 没有本质优势(仍需扫过前 40 行),但可与其他窗口计算合并。

### 四、排序与索引

**索引的物理顺序即排序顺序**。如果查询的 `ORDER BY` 与某个索引的顺序完全一致(方向也一致),规划器可以走索引扫描**免排序**。

```sql
CREATE INDEX orders_created_id_idx ON orders (created_at DESC, id DESC);

-- ✅ ORDER BY 与索引完全同向同序 → Index Scan,无 Sort 节点
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC, id DESC LIMIT 20;

-- ⚠️ 混合方向 → 需要 Sort 或反向扫描
EXPLAIN SELECT * FROM orders ORDER BY created_at ASC, id DESC LIMIT 20;

-- ⚠️ 不同 collation / 不同表达式 → 需要 Sort
EXPLAIN SELECT * FROM orders ORDER BY lower(status);
```

**B-tree 索引的方向支持**

- 单列索引可**双向扫描**,所以 `ASC` 与 `DESC` 都能用同一个索引。
- **多列索引的方向组合必须与 `ORDER BY` 匹配或完全相反**。例如索引 `(a ASC, b DESC)` 支持 `ORDER BY a, b DESC` 与 `ORDER BY a DESC, b`,但不支持 `ORDER BY a, b`(需排序)。
- PG13+ 起`,` 与默认排序规则下的 `ORDER BY` 更易匹配;PG 支持为多列索引指定不同方向。

**`ORDER BY` + `LIMIT` 的 Top-N 优化**

```sql
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
-- 有索引:Index Scan + Limit,只读 10 行
-- 无索引:Seq Scan + Sort + Limit,须读全表并排全表
```

这是 `LIMIT` 最有价值的优化场景:**用索引把"排全表"变成"读前 N 行"**。

### 五、`DISTINCT` 与排序的关系

```sql
-- DISTINCT 内部通常需要排序或哈希去重
SELECT DISTINCT status FROM orders;

-- 若已有按该列排序的索引,规划器可能省掉排序
EXPLAIN SELECT DISTINCT status FROM orders ORDER BY status;
```

## 小结

- 多列排序用逗号续写,前一列相同时才看后一列。
- NULL 位置可显式控制;排序规则(collation)不一致会让索引失效。
- 分页首选**键集分页**:恒定性能、结果稳定;`OFFSET` 只适合浅翻页的后台场景。
- 键集分页要求排序键唯一,末尾补主键。
- `ORDER BY` 与索引同向同序时可免排序;`ORDER BY ... LIMIT N` 是最典型的索引受益场景。
