# 5.4 多表连接 JOIN

## 学习目标

- 分清五类 JOIN 的语义与结果集差异
- 掌握 `LEFT JOIN` 的"过滤条件放哪"陷阱
- 会用 `LATERAL` 做"每组取前 N 条"

## 前置知识

[[postgresql/01-入门阶段-基础教程/第05章-查询核心/5.3-聚合函数与GROUP-BY]]

## 正文

### 一、五类 JOIN

```sql
-- 建演示数据
CREATE TABLE a (id int, v text);
CREATE TABLE b (id int, w text);
INSERT INTO a VALUES (1,'a1'), (2,'a2'), (3,'a3');
INSERT INTO b VALUES (2,'b2'), (3,'b3'), (4,'b4');
```

| 类型 | 含义 | 结果(id) |
|------|------|----------|
| `INNER JOIN` | 两侧都匹配 | 2, 3 |
| `LEFT JOIN` | 保留左表全部,右侧无匹配补 NULL | 1, 2, 3 |
| `RIGHT JOIN` | 保留右表全部 | 2, 3, 4 |
| `FULL JOIN` | 两侧都保留 | 1, 2, 3, 4 |
| `CROSS JOIN` | 笛卡尔积 | 9 行 |

```sql
SELECT a.id, a.v, b.w FROM a INNER JOIN b ON a.id = b.id;
SELECT a.id, a.v, b.w FROM a LEFT  JOIN b ON a.id = b.id;
SELECT a.id, a.v, b.w FROM a RIGHT JOIN b ON a.id = b.id;
SELECT a.id, a.v, b.w FROM a FULL  JOIN b ON a.id = b.id;
SELECT a.id, b.id FROM a CROSS JOIN b;
```

**`USING` 与自然连接**

```sql
-- USING:同名列只输出一次,简化结果
SELECT id, v, w FROM a JOIN b USING (id);

-- NATURAL JOIN:自动按所有同名列连接(⚠️ 危险,列一变语义就变)
SELECT * FROM a NATURAL JOIN b;   -- 不推荐
```

> **实践建议**:一律显式 `ON` 或 `USING`。`NATURAL JOIN` 在表结构演化后极易产生意外结果。

### 二、`INNER JOIN` 与"逗号连接"的区别

```sql
-- 内连接
SELECT * FROM a JOIN b ON a.id = b.id;

-- 逗号连接(隐式交叉连接 + WHERE 过滤)
SELECT * FROM a, b WHERE a.id = b.id;
```

两者在现代优化器下计划通常相同,但**语义有差别**:逗号连接若忘了写 `WHERE`,就是完整笛卡尔积(静默的巨大结果)。**永远用显式 `JOIN ... ON`。**

### 三、`LEFT JOIN` 的头号陷阱:过滤条件放哪

这是 SQL 中最常见的中级错误。

```sql
-- ❌ 错误写法:把右表条件放在 WHERE,LEFT JOIN 退化成 INNER JOIN
SELECT u.id, u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid';
-- 没有 paid 订单的用户被过滤掉了!LEFT JOIN 失去意义

-- ✅ 正确写法:右表条件放在 ON 里
SELECT u.id, u.name, o.amount
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 'paid';
-- 没有 paid 订单的用户保留,o.* 为 NULL
```

**记忆规则**

| 条件位置 | 效果 |
|----------|------|
| `ON` 中的右表条件 | 影响**匹配**(不减少左表行) |
| `WHERE` 中的右表条件 | 过滤**结果**行(会剔除左表行,退化为内连接) |
| `WHERE` 中的左表条件 | 正常过滤左表 |

若确实需要"取到结果后再过滤",用 `WHERE (o.status = 'paid' OR o.id IS NULL)` 显式保留未匹配行——但这说明你真正想要的可能是 `ON`。

**统计"没有订单的用户"**

```sql
-- 反连接(检测不匹配)
SELECT u.* FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- 更清晰的写法
SELECT u.* FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

### 四、连接类型与执行算法

概念上分三类,物理上由优化器选三种算法:

| 概念连接 | 物理算法 | 适用 |
|----------|----------|------|
| 嵌套循环 | Nested Loop | 小表驱动大表,且大表连接列有索引 |
| 哈希连接 | Hash Join | 等值连接,大表对中等表 |
| 归并连接 | Merge Join | 两侧都已按连接键有序 |

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, o.amount FROM users u JOIN orders o ON o.user_id = u.id WHERE u.vip;
-- 观察输出中是 Nested Loop / Hash Join / Merge Join
```

细节见 [[postgresql/02-中段阶段-专题精讲/执行计划与性能诊断/EXPLAIN与EXPLAIN-ANALYZE解读]]。

**连接列上有索引为何重要**

```sql
-- 没有索引:Nested Loop 的内侧需全表扫,或被迫用 Hash Join
-- 有索引:内侧可用 Index Scan,小驱动集时极快
CREATE INDEX orders_user_id_idx ON orders (user_id);   -- 外键列索引(同 3.2)
```

**多表连接的顺序**

优化器会重排连接顺序(基于代价),但连接**数量**很关键:

- `N` 个表的连接顺序组合是阶乘级。超过约 12 个表后,规划器会退化到**遗传算法**搜索(不保证最优)。
- 实践上:避免单条 SQL 连接超过 8~10 张表;超出时拆成中间结果(CTE 或临时表)。

```sql
SET geqo = on;                 -- 默认在表数超过 geqo_threshold(默认 12)时启用
SHOW geqo_threshold;
SET join_collapse_limit = 1;   -- 强制按书写顺序连接(排障时用)
```

### 五、半连接 / 反连接

| 概念 | 含义 | SQL 写法 |
|------|------|----------|
| 半连接 | 左表行"存在"匹配即保留(不重复) | `EXISTS` / `IN` / `INNER JOIN` + `DISTINCT` |
| 反连接 | 左表行"不存在"匹配 | `NOT EXISTS` / `NOT IN`(慎用) / `LEFT JOIN ... IS NULL` |

```sql
-- 半连接:有订单的用户(不重复)
SELECT u.* FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

-- 若用 INNER JOIN,一个用户多笔订单会产生重复行
SELECT DISTINCT u.* FROM users u JOIN orders o ON o.user_id = u.id;   -- 须 DISTINCT 修正

-- 反连接:没有订单的用户
SELECT u.* FROM users u WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

> **优先 `EXISTS` / `NOT EXISTS`**:语义精确(不产生重复行),天然规避 `NOT IN` 的 NULL 问题,且规划器可转为半连接/反连接并提前短路。

### 六、`LATERAL`:让子查询能引用左侧表

普通 `JOIN` 的子查询**不能**引用左侧表的列;`LATERAL` 可以,相当于"对左表每一行执行一次右侧查询"。

```sql
-- 取每个用户最近 3 笔订单
SELECT u.id, u.name, t.id AS order_id, t.created_at
FROM users u
LEFT JOIN LATERAL (
    SELECT o.id, o.created_at
    FROM orders o
    WHERE o.user_id = u.id
    ORDER BY o.created_at DESC
    LIMIT 3
) t ON true
ORDER BY u.id, t.created_at DESC;
```

`ON true` 是常见写法:`LATERAL` 子查询自身已完成相关性过滤,无需额外条件。

**`LATERAL` 与 `DISTINCT ON` / 窗口函数对比**

| 方案 | 优势 | 劣势 |
|------|------|------|
| `LATERAL` | 每组可分页(取前 N 条)、可用索引逐组查 | 组数多时执行次数多(但有索引时快) |
| `DISTINCT ON` | 一次扫描排序 | 只能取每组 1 条 |
| 窗口函数 | 一次扫描、可算排名 | 大表上排序开销大 |

> **性能要点**:`LATERAL` + 外层索引(如 `orders(user_id, created_at DESC)`)在"取每组少量行、组数多"的场景通常**最优**——因为它对每组只读几行,而非对全表排序。

**`LATERAL` 用于展开函数结果**

```sql
-- 把数组展开并与其他列连接
SELECT p.id, p.name, t.tag
FROM products p
CROSS JOIN LATERAL unnest(p.tags) AS t(tag);

-- 等价的新式写法
SELECT p.id, p.name, t.tag FROM products p, unnest(p.tags) AS t(tag);
```

## 小结

- 五类 JOIN 的语义差异体现在"哪一侧保留全部";一律显式 `ON`/`USING`,避免 `NATURAL JOIN`。
- **`LEFT JOIN` 的右表过滤条件必须写在 `ON` 里**,写在 `WHERE` 会退化成内连接。
- 物理算法由优化器在 Nested Loop / Hash Join / Merge Join 中选,连接列有索引才可能用小驱动集 + 索引扫描。
- 半连接/反连接优先 `EXISTS` / `NOT EXISTS`;避免 `NOT IN`。
- `LATERAL` 让子查询引用左侧表,是"每组取前 N 条"的最优解(配合合适的复合索引)。

## 练习

1. 写出同一需求的两个版本:把右表条件放在 `ON` 与放在 `WHERE` 的 `LEFT JOIN`,对比结果行数并解释。
2. 用 `LATERAL` 取每个用户最近 3 笔订单,建 `(user_id, created_at DESC)` 索引前后比较 `EXPLAIN ANALYZE` 的耗时。
3. 用 `EXISTS`、`INNER JOIN + DISTINCT`、`LEFT JOIN ... IS NULL` 三种方式分别实现"有订单的用户"与"无订单的用户",比较计划。
4. 造 8 张表做连接,观察 `EXPLAIN` 中的连接顺序,再尝试调低 `join_collapse_limit` 看计划变化。
