# 2.2 字符与二进制类型

## 学习目标

- 破除"`varchar(n)` 比 `text` 快"的误解,学会按**语义**而非性能选型
- 掌握字符集/排序规则(collation)对比较与索引的影响
- 会用 `bytea` 存二进制与转义格式

## 前置知识

[[postgresql/01-入门阶段-基础教程/第02章-数据类型/2.1-数值类型]]

## 正文

### 一、三种字符类型

| 类型 | 说明 | 推荐度 |
|------|------|--------|
| `character varying(n)` / `varchar(n)` | 变长,**超过 n 报错** | 需要长度约束时用 |
| `character(n)` / `char(n)` | 定长,**不足补空格**,比较时忽略尾部空格 | ❌ 极少用 |
| `text` | 变长,无长度限制 | ✅ **默认选它** |

**关键事实:在 PostgreSQL 中 `varchar(n)` 与 `text` 的性能没有实质差异。**

原因是 **PostgreSQL 内部对这三者的存储方式几乎一致**:它们都只是"一段变长的文本",数据库按实际长度存储,不会因为写了 `n` 就预留空间。`n` 在这里的实际作用只是**一条检查规则**——超过 n 个字符就报错,并不改变存储方式。因此:

- 若 `n` 来自业务规则(如"手机号 11 位"),用 `varchar(n)` —— 让数据库替你校验。
- 若只是"想不出长度"而随手写 `varchar(255)`,那就是**没有任何约束价值的噪音**,直接用 `text`。

```sql
CREATE TABLE t_char (
    a text,                  -- 推荐
    b varchar(50),           -- 业务上限 50 字符
    c char(10)               -- 定长,不推荐
);

INSERT INTO t_char VALUES ('x', 'x', 'x');
SELECT length(a), length(b), length(c) FROM t_char;  -- 1, 1, 1(尾部空格不计入 length)
SELECT c || '|' FROM t_char;                          -- 'x         |'(存储时补齐 10 位)
```

**`char(n)` 的陷阱**:存储时补齐空格、比较时忽略尾部空格,却占用完整空间。语义不清,现代 Schema 基本不用。

### 二、字符集与排序规则

PostgreSQL 支持两类**排序规则提供者**:

| 提供者 | 说明 |
|--------|------|
| `libc` | 依赖操作系统的 locale,行为随 OS 版本变化 |
| `icu` | ICU 库,跨平台一致,支持语言感知排序(**新项目推荐**) |
| `builtin` | PG17+ 新增,内置 C 与 Unicode 语义 |

初始化集群时指定:

```bash
initdb --encoding=UTF8 --locale-provider=icu --icu-locale=zh-CN
```

**排序规则影响什么**

1. `ORDER BY` 的顺序(`a` vs `A` vs `啊`)
2. `=`、`<`、`>` 比较结果
3. **索引的可用性** —— 这是最容易被忽略的一点

```sql
-- 列上定义了排序规则
CREATE TABLE t (name text COLLATE "zh-x-icu");

-- 查询时用了不同排序规则 → 该列的索引可能无法使用
SELECT * FROM t WHERE name = 'abc' COLLATE "C";
```

用 `COLLATE` 可显式指定:

```sql
SELECT 'a' < 'B';                          -- true(libc 默认)
SELECT 'a' < 'B' COLLATE "C";              -- false(C 排序按字节码)
SELECT * FROM t ORDER BY name COLLATE "C"; -- 强制字节序
```

查看可用排序规则:

```sql
SELECT * FROM pg_collation LIMIT 20;
\dOS                -- psql 列出排序规则
```

> **PG18 兼容性提示**:PG18 起,全文检索与 `pg_trgm` 读取配置文件/词典时使用**集群默认的排序规则提供者**,而非固定用 `libc`。若集群默认不是 libc,升级后应对全文检索与 `pg_trgm` 相关索引执行 `REINDEX`。

### 三、常用字符串函数

下面按用途分组。若某个函数想进一步细看,查 [[postgresql/函数手册]]。

**长度与截取**

```sql
SELECT length('你好');         -- 2  字符数
SELECT char_length('你好');    -- 2  同上(SQL 标准写法,两者等价)
SELECT octet_length('你好');   -- 6  字节数:UTF-8 下每个中文占 3 字节

SELECT left('abcdef', 3);                 -- 'abc'  取左侧 3 个字符
SELECT right('abcdef', 3);                -- 'def'  取右侧 3 个字符
SELECT substring('abcdef' from 2 for 3);  -- 'bcd'  从第 2 位起取 3 个(标准 SQL 语法)
SELECT substr('abcdef', 2, 3);            -- 'bcd'  同上,函数形式
SELECT split_part('a,b,c', ',', 2);       -- 'b'    按分隔符取第 2 段
```

> **`length` 与 `octet_length` 的区别**:前者数**字符**,后者数**字节**。判断"字符串是否超长"时,业务说的通常是字符数。

**拼接与填充**

```sql
SELECT 'a' || 'b';                     -- 'ab'   运算符拼接(遇 NULL 得 NULL,见第四节)
SELECT concat('a', NULL, 'b');         -- 'ab'   函数拼接(忽略 NULL)
SELECT concat_ws('-', 'a', NULL, 'b'); -- 'a-b'  ws = with separator,用分隔符拼接

SELECT lpad('7', 3, '0');              -- '007'  左侧用 '0' 填充到总长 3
SELECT rpad('x', 5, '.');              -- 'x....' 右侧填充
SELECT repeat('ab', 3);                -- 'ababab'
```

**大小写与清洗**

```sql
SELECT upper('abc');            -- 'ABC'
SELECT lower('ABC');            -- 'abc'
SELECT initcap('hello world');  -- 'Hello World'  每个单词首字母大写

SELECT trim('  x  ');           -- 'x'  去两端空格
SELECT ltrim(' x');             -- 'x'  只去左端
SELECT rtrim('x ');             -- 'x'  只去右端
SELECT btrim('xxaxx', 'x');     -- 'a'  去两端"指定字符集"(b = both)
```

**查找与替换**

```sql
SELECT position('b' in 'abc');   -- 2  子串首次出现的位置(下标从 1 开始)
SELECT strpos('abc', 'b');       -- 2  同上,函数形式
SELECT starts_with('abc', 'ab'); -- true
SELECT replace('abc', 'b', 'X'); -- 'aXc'  全量替换所有匹配
```

**正则表达式**

```sql
-- ① 匹配运算符:~ 区分大小写,~* 忽略大小写。返回布尔值
SELECT 'a1b2' ~  '^[a-z][0-9]';   -- true
SELECT 'a1b2' ~* 'A1B2';          -- true(忽略大小写)

-- ② 替换:第 4 个参数 'g' 表示全局替换,不加则只换第一处
SELECT regexp_replace('a1b2', '[0-9]', '#');       -- 'a#b2'
SELECT regexp_replace('a1b2', '[0-9]', '#', 'g');  -- 'a#b#'

-- ③ regexp_matches 是表函数:返回"匹配结果的集合",每行一个数组
SELECT * FROM regexp_matches('a1b2', '[0-9]', 'g');
-- 返回两行:{1} 和 {2}

-- ④ 切分:regexp_split_to_array 返回数组,regexp_split_to_table 返回多行
SELECT regexp_split_to_array('a,b;c', '[,;]');       -- {a,b,c}
SELECT * FROM regexp_split_to_table('a,b;c', '[,;]'); -- 三行:a / b / c
```

> **模式 `'[,;]'` 的含义**:方括号表示"字符集合",即"逗号或分号任一个"。这是正则语法,不是字面量。
>
> **四个正则函数怎么选**:

| 想做什么 | 用哪个 |
|----------|--------|
| 只判断是否匹配 | `~` / `~*`(运算符) |
| 取出匹配到的内容 | `regexp_matches` |
| 替换匹配到的内容 | `regexp_replace` |
| 按模式拆成数组 | `regexp_split_to_array` |
| 按模式拆成多行 | `regexp_split_to_table` |

**哈希与编码**

```sql
SELECT md5('abc');                      -- 32 位十六进制摘要字符串
SELECT sha256('abc'::bytea);            -- 需先 CREATE EXTENSION pgcrypto
SELECT encode('abc'::bytea, 'base64');  -- 'YWJj'   二进制 → 文本
SELECT decode('YWJj', 'base64');        -- 文本 → 二进制
```

**聚合(把多行合成一个字符串)**

```sql
SELECT string_agg(name, ', ' ORDER BY name) FROM products;
--      ↑ 忽略 NULL;ORDER BY 写在函数内部决定拼接顺序,不写则顺序不确定
```

### 四、`concat` 与 `||` 对 NULL 的差异(高频坑)

```sql
SELECT 'a' || NULL;                  -- NULL   || 运算符:任意一侧为 NULL,结果就是 NULL
SELECT concat('a', NULL);            -- 'a'    concat 函数:自动忽略 NULL 参数
SELECT concat_ws('-','a',NULL,'b');  -- 'a-b'  concat_ws:忽略 NULL,且不为被跳过的项插入分隔符
```

**后果**:用 `||` 拼地址、拼全名时,任一字段为 NULL 会导致**整串变 NULL**。要用就要配 `coalesce`:

```sql
SELECT coalesce(city,'') || coalesce(addr,'');
```

### 五、二进制类型 `bytea`

```sql
CREATE TABLE files (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, content bytea);

-- 十六进制字面量(推荐表示法,PG 默认 bytea_output = hex)
INSERT INTO files (content) VALUES ('\x48656c6c6f');   -- 'Hello'

-- 转义字面量
INSERT INTO files (content) VALUES (E'\\001\\002'::bytea);

SELECT encode(content, 'hex'), encode(content, 'base64'), octet_length(content)
FROM files;

-- 反转十六进制输出为转义格式(旧客户端兼容)
SET bytea_output = 'escape';
```

| 函数 | 作用 |
|------|------|
| `encode(bytea, 'hex'\|'base64'\|'escape')` | 编码为文本 |
| `decode(text, 'hex'\|'base64')` | 文本解码为 bytea |
| `octet_length(bytea)` | 字节数 |
| `get_byte(bytea, n)` / `set_byte(...)` | 按字节读写 |
| `md5(bytea)` / `sha256(bytea)` | 摘要(pgcrypto) |

**该不该把大文件存进数据库?**

| 方案 | 优点 | 缺点 |
|------|------|------|
| `bytea` | 事务一致、备份一体、权限统一 | 存大文件会让表体积暴涨,备份也变慢 |
| 大对象 `lo`(large object) | 支持流式读写 | API 复杂,需单独管理 `pg_largeobject` |
| 外部对象存储 + 存 URL | 数据库轻 | 失去事务一致性,需自己保证不悬挂 |

实践通例:**小文件(几 KB~几十 KB)可入库,大文件放对象存储,库里只存引用 + 校验和**。

## 小结

- `text` 是默认选择;`varchar(n)` 只在 n 是真实业务约束时用;`char(n)` 基本不用。
- `varchar(n)` 与 `text` 无性能差异,`n` 只是检查约束。
- 排序规则影响排序、比较和**索引可用性**;新集群推荐 ICU。
- `||` 遇 NULL 得 NULL,`concat` 忽略 NULL —— 拼接字段时要小心。
- `bytea` 存小二进制;大文件走对象存储。

## 练习

1. 建一张含 `text` / `varchar(10)` / `char(10)` 三列的表,分别插入 3 个字符,比较 `length()` 与 `octet_length()` 的结果并解释。
2. 验证 `'a' || NULL IS NULL` 为真,并用 `coalesce` 写一个不会因缺字段而整串为 NULL 的地址拼接。
3. 用 `string_agg` 把一个用户的所有订单状态拼成一行,按创建时间排序。
4. 用 `regexp_split_to_array` 把 `'a,b;c,d'` 按逗号或分号拆成数组。
