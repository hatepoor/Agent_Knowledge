# 2.4 布尔、枚举与 UUID

## 学习目标

## 正文

### 一、boolean

```sql
CREATE TABLE t_bool (flag boolean);
```

**接受的输入(不区分大小写)**

| 为真 | 为假 |
|------|------|
| `true` `t` `yes` `y` `on` `1` | `false` `f` `no` `n` `off` `0` |

**输出永远是** `t` / `f`(psql 中显示为 `t`/`f`,或按 `\pset null` 显示 NULL)。

> **注意**:`boolean` 的输入宽松但**输出规范**。应用解析时不要假设输出是 `true`/`false` 字符串,应按布尔类型处理。

**三值逻辑**:`boolean` 有 `true` / `false` / `NULL` 三个状态。NULL 参与的逻辑运算遵循 Kleene 逻辑:

```sql
SELECT true AND NULL;   -- NULL
SELECT false AND NULL;  -- false   ← 短路:false 与任何值都是 false
SELECT true OR NULL;    -- true    ← 短路
SELECT false OR NULL;   -- NULL
SELECT NOT NULL;        -- NULL
```

**实践建议**:可空布尔列是常见的语义陷阱("未知"与"否"混在一起)。若业务上不存在"未知",列定义加 `NOT NULL DEFAULT false`。

```sql
-- 统计为真的比例(注意 NULL 会被 count(*) 计入分母,导致比例偏低)
SELECT count(*) FILTER (WHERE flag)::numeric / nullif(count(*), 0) FROM t_bool;
SELECT avg(flag::int) FROM t_bool;   -- 布尔可直接转 int 求均值
```

### 二、枚举类型 enum

```sql
CREATE TYPE order_status AS ENUM ('pending','paid','shipped','done','canceled');

CREATE TABLE orders (
    id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status order_status NOT NULL DEFAULT 'pending'
);

INSERT INTO orders (status) VALUES ('paid');
INSERT INTO orders (status) VALUES ('bogus');   -- ERROR: invalid input value for enum
```

**枚举的优点**

- 类型安全:非法值在写入前就被拒绝。
- 存储紧凑:内部用 4 字节序号,不是字符串。
- 排序按**声明顺序**(不是字典序),符合业务直觉:

```sql
SELECT * FROM orders ORDER BY status;   -- pending → paid → shipped → done
```

**枚举的代价**

| 问题 | 说明 |
|------|------|
| 增删值需 `ALTER TYPE` | `ALTER TYPE order_status ADD VALUE 'refunded';` |
| 删除值几乎不可行 | 没有 `DROP VALUE`,要重建类型 |
| **`ADD VALUE` 在旧版本不能在事务内执行** | PG12+ 允许在事务内 `ADD VALUE`,但**同一事务内不能立即使用新值** |
| 调整顺序需重建 | 需新建类型并 `ALTER TABLE ... TYPE ... USING` |

```sql
ALTER TYPE order_status ADD VALUE IF NOT EXISTS 'refunded' BEFORE 'done';
-- 同一事务中不能立刻 INSERT 'refunded',需等事务提交
```

**三种建模方式对比**

| 方案 | 类型安全 | 扩展成本 | 可携带元数据 | 适用 |
|------|----------|----------|--------------|------|
| `enum` | 强 | 中(可加难删) | ❌ | 选项**稳定**、不常变 |
| `text + CHECK (x IN (...))` | 强 | **低**(改约束即可) | ❌ | 选项偶尔变动 |
| 查找表 + 外键 | 强 | 低 | ✅(可存显示名、排序、启用状态) | 选项需元数据、需多语言、需后台配置 |

```sql
-- 方案 2:CHECK 约束(最灵活,推荐用于会变的选项)
status text NOT NULL DEFAULT 'pending'
  CHECK (status IN ('pending','paid','shipped','done','canceled'))

-- 改选项只需重建约束
ALTER TABLE orders DROP CONSTRAINT orders_status_check;
ALTER TABLE orders ADD CONSTRAINT orders_status_check
  CHECK (status IN ('pending','paid','shipped','done','canceled','refunded'));
```

> **选型建议**:选项集合会随业务演进的(状态、渠道、标签),优先用 **`text + CHECK`** 或**查找表**;真正稳定不变的(性别、星期、货币代码)可用 `enum`。若需多语言显示名,直接上查找表。

枚举相关的系统信息:

```sql
SELECT enumlabel, enumsortorder FROM pg_enum WHERE enumtypid = 'order_status'::regtype ORDER BY enumsortorder;
\dT+ order_status
```

### 三、UUID

```sql
CREATE TABLE t_uuid (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),   -- pgcrypto 或 PG13+ 内置
    ...
);
```

**UUID 作为主键的取舍**

| 维度 | UUID | bigint 自增 |
|------|------|-------------|
| 全局唯一 | ✅ 可离线生成、多库合并无冲突 | ❌ 需中心序列 |
| 存储 | 16 字节 | 8 字节 |
| 索引局部性 | ❌ 随机 UUID **严重打散 B-tree**,页分裂多、缓存命中低 | ✅ 顺序写入,追加到最右页 |
| 信息泄露 | ✅ 不暴露业务量 | ❌ 自增 ID 会暴露订单量 |
| 调试友好度 | 差(长串) | 好 |

**PG18 新增 `uuidv7()` —— 这正是为解决"随机 UUID 的索引局部性"问题而生的。**

UUIDv7 的前 48 位是**毫秒级 Unix 时间戳**,因此生成值**近似单调递增**,写入时像自增 ID 一样集中在 B-tree 右端,兼顾"全局唯一/可离线生成"与"顺序写入"。

```sql
SELECT uuidv7();   -- PG18+,示例:0198f0a1-8b2c-7def-...
SELECT uuidv4();   -- 若装了 uuid-ossp 扩展
SELECT gen_random_uuid();   -- 等价于 v4 随机
```

> **迁移建议**:若现有系统用 UUIDv4 主键且写入量大,升级到 PG18 后可将新记录的默认值改为 `uuidv7()`,但**不要指望自动改善存量数据的局部性**——存量页的碎片依旧存在,需 `REINDEX` 或重建表来整固。

其他 UUID 相关函数(`uuid-ossp` 扩展):

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
SELECT uuid_generate_v1(), uuid_generate_v4();
SELECT uuid_nil(), uuid_ns_dns();
```

## 小结

- `boolean` 输入宽松、输出规范(`t`/`f`),存在三值逻辑;可空布尔列易混淆语义,建议 `NOT NULL DEFAULT false`。
- 枚举优点在类型安全与紧凑存储,缺点在"可加难删";选项会变时用 `text + CHECK` 或查找表。
- UUID 主键的代价是**索引局部性**;PG18 的 `uuidv7()` 通过时间前缀把随机写变成顺序写,是本次版本最实用的改进之一。

## 练习

1. 建一张 `boolean` 与 `boolean NOT NULL DEFAULT false` 的表,做一次 `GROUP BY` 统计,观察 NULL 对统计结果的影响。
2. 分别用 `enum`、`text + CHECK`、查找表三种方式建模"订单状态",写出各自的"新增一个 refunded 状态"所需的 SQL,比较成本。
3. 用 `pg_enum` 查出枚举的声明顺序,验证 `ORDER BY` 与声明顺序一致。
4. 若你使用 PG18,对比 `uuidv7()` 与 `gen_random_uuid()` 各生成 100 万个值写入表,比较表的物理大小与写入耗时。
