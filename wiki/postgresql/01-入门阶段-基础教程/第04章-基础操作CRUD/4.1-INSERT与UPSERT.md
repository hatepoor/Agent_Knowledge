# 4.1 INSERT 与 UPSERT

## 学习目标

- 掌握单行、多行、`INSERT ... SELECT` 三种插入
- 写出正确的 `ON CONFLICT` 幂等写入
- 会用 `COPY` 批量导入百万级数据

## 前置知识

[[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.2-约束体系与数据完整性]]

## 正文

### 一、基础插入

```sql
-- 单行
INSERT INTO users (email, name, vip) VALUES ('a@b.c', 'Ann', true);

-- 多行(一次往返,远快于多次单行)
INSERT INTO users (email, name) VALUES
    ('b@b.c', 'Ben'),
    ('c@b.c', 'Cara'),
    ('d@b.c', 'Dan');

-- 全列省略列名(不推荐,列顺序一变就出错)
INSERT INTO users VALUES (DEFAULT, 'e@b.c', 'Eve', false, NULL, now());

-- 指定 IDENTITY 列的显式值
INSERT INTO users (id, email, name) OVERRIDING SYSTEM VALUE
VALUES (1000, 'f@b.c', 'Fox');

-- 从查询插入
INSERT INTO users_archive (email, name)
SELECT email, name FROM users WHERE created_at < now() - interval '1 year';

-- 返回插入结果
INSERT INTO users (email, name) VALUES ('g@b.c', 'Gil')
RETURNING id, email, created_at;
```

**`DEFAULT` 关键字**:在 `VALUES` 中显式写 `DEFAULT` 表示"用列默认值",而不是 NULL。

```sql
INSERT INTO users (email, name, vip, created_at)
VALUES ('h@b.c', 'Hal', DEFAULT, DEFAULT);
```

### 二、UPSERT:`ON CONFLICT`

"如果冲突则更新,否则插入",这是**幂等写入**的标准手段。

**前提:必须有能判定冲突的唯一索引或唯一约束**(主键也算)。

```sql
-- 1) 冲突则忽略(幂等插入)
INSERT INTO users (email, name) VALUES ('a@b.c', 'Ann')
ON CONFLICT (email) DO NOTHING;

-- 2) 冲突则更新
INSERT INTO users (email, name, vip)
VALUES ('a@b.c', 'Ann New', true)
ON CONFLICT (email) DO UPDATE
SET name = EXCLUDED.name,
    vip  = EXCLUDED.vip,
    updated_at = now();
```

**`EXCLUDED` 的含义**:代表"本次试图插入但被拒绝的那一行"。因此 `EXCLUDED.name` 就是新值,`users.name` 则是库里的旧值。

```sql
-- 只在新值更大时更新
ON CONFLICT (id) DO UPDATE
SET amount = greatest(orders.amount, EXCLUDED.amount);

-- 带条件更新
ON CONFLICT (id) DO UPDATE
SET status = EXCLUDED.status
WHERE orders.status <> EXCLUDED.status;      -- 无变化则不写(减少 WAL)
```

**冲突目标的三种指定方式**

```sql
ON CONFLICT (email) DO ...                    -- 按列(需有对应唯一索引)
ON CONFLICT ON CONSTRAINT users_email_uk DO ...  -- 按约束名
ON CONFLICT DO NOTHING                        -- 不指定目标:任意冲突都忽略
```

> **重要限制**:`ON CONFLICT DO UPDATE` **必须**能确定一个冲突目标(列推断或约束名);`ON CONFLICT DO NOTHING` 才可以不指定。

**判断本次是插入还是更新(可选技巧)**

`RETURNING` 里可以写一个叫 `xmax` 的东西。它是**系统列**——每张表都自带的、不需要你在建表时定义的隐藏列(所有系统列见 [[postgresql/术语与关键字手册]] 第十三节)。

```sql
INSERT INTO users (email, name) VALUES ('a@b.c', 'Ann')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name
RETURNING id, (xmax = 0) AS is_insert;   -- true = 本次是新插入,false = 走了更新
```

判断依据很简单:

| `xmax` 的值 | 说明 |
|-------------|------|
| `0` | 这一行是**本次新插入**的 |
| 非 0 | 这一行**被更新**过(不是新插入) |

> **看不懂就跳过这一段。** `xmax` 为什么能有这个含义,属于进阶内容(见 [[postgresql/03-进阶阶段-深度剖析/事务与MVCC内核/原理剖析-可见性与事务状态]])。日常开发中:
> - 想知道"到底插入还是更新了",照上面这样写即可;
> - 如果觉得别扭,也可以先用 `SELECT` 查一下再决定插入还是更新——只是多一次往返,而且**并发下不如上面严谨**(两个请求可能同时查到"不存在",然后都去插入)。

**并发安全注意**:`ON CONFLICT` 在**高并发下可能抛序列化失败**或出现"UPDATE 影响 0 行"的情况。因为它不是完全无锁的,冲突检测依赖唯一索引。若业务要求严格,需配合重试逻辑。

```sql
-- 批量 UPSERT(同一语句内若有两行冲突同一个键会报错:
-- "ON CONFLICT DO UPDATE command cannot affect row a second time")
INSERT INTO t (k, v) VALUES (1,'a'), (1,'b')
ON CONFLICT (k) DO UPDATE SET v = EXCLUDED.v;
-- ERROR!

-- 解决:先在同批内去重
INSERT INTO t (k, v)
SELECT DISTINCT ON (k) k, v FROM (VALUES (1,'a'), (1,'b')) AS x(k, v)
ON CONFLICT (k) DO UPDATE SET v = EXCLUDED.v;
```

### 三、批量导入:COPY

**`COPY` 是 PostgreSQL 最快的批量装载方式**,比逐行 `INSERT` 快一到两个数量级。

```sql
-- 服务端读取(文件需在服务端,且需超级用户或 pg_read_server_files)
COPY users (email, name) FROM '/tmp/users.csv' WITH (FORMAT csv, HEADER true);

COPY users TO '/tmp/users_out.csv' WITH (FORMAT csv, HEADER true);

-- 从标准输入
COPY users FROM STDIN WITH (FORMAT csv);
```

```bash
# 客户端读取(推荐,权限要求低)
psql -c "\copy users FROM 'users.csv' WITH (FORMAT csv, HEADER)"
```

**`COPY` 常用选项**

| 选项 | 说明 |
|------|------|
| `FORMAT csv\|text\|binary` | 格式,默认 `text` |
| `HEADER true` | 首行为列名 |
| `DELIMITER ','` | 分隔符 |
| `NULL 'NULL'` | NULL 表示 |
| `QUOTE '"'` | 引号字符 |
| `ENCODING 'UTF8'` | 编码 |
| `FREEZE true` | 导入后直接冻结(仅新建/清空表可用,大幅加速) |

**导入性能建议**

1. 导入**新建表或已 TRUNCATE 的表**时用 `FREEZE`,可跳过后续 VACUUM 需求。
2. 导入时用 `UNLOGGED` 表(PG 18 起分区表不允许 UNLOGGED,但普通表可用),速度更快,代价是崩溃后数据丢失。
3. 先导入再建索引/外键,比边导入边维护索引快得多:

```sql
-- 快速装载流程
BEGIN;
CREATE UNLOGGED TABLE stage (LIKE app.orders INCLUDING ALL);
COMMIT;
COPY stage (...) FROM '...' WITH (FORMAT csv, HEADER, FREEZE);
-- 或直接 COPY 到无索引的正式表
-- 装载完成后再建索引与约束
CREATE INDEX CONCURRENTLY ...;
ALTER TABLE ... ADD CONSTRAINT ... NOT VALID;
ALTER TABLE ... VALIDATE CONSTRAINT ...;
```

**PG18 兼容性提示**:`COPY FROM` 在读取 CSV 时**不再把 `.` 当作文件结束标记**(此前行为);`psql` 从 STDIN 读 CSV 时仍保留该行为。若依赖该旧行为的脚本需调整。

### 四、其他写入形式

```sql
-- 从 VALUES 表表达式插入(可套用任意 SQL)
INSERT INTO t (a, b)
SELECT x, y * 2 FROM (VALUES (1,2), (3,4)) AS v(x, y);

-- MERGE(PG15+):一条语句覆盖 INSERT/UPDATE/DELETE 三种动作
MERGE INTO inventory AS inv
USING daily_sales AS s ON inv.sku = s.sku
WHEN MATCHED AND inv.qty + s.qty <= 0 THEN DELETE
WHEN MATCHED THEN UPDATE SET qty = inv.qty + s.qty
WHEN NOT MATCHED THEN INSERT (sku, qty) VALUES (s.sku, s.qty);
```

> **MERGE vs ON CONFLICT**:`MERGE` 能表达"不匹配则删"等复杂分支,但**并发下更易产生死锁**,且不能像 `ON CONFLICT` 那样依赖唯一索引做原子 UPSERT。简单 UPSERT 优先 `ON CONFLICT`;复杂多分支同步用 `MERGE`。

PG18 起 `MERGE` 的 `RETURNING` 支持 `OLD`/`NEW`,便于审计。

## 小结

- 多行 `VALUES` 优于多次单行插入;`INSERT ... SELECT` 做表间搬运。
- UPSERT 用 `ON CONFLICT ... DO UPDATE`,新值通过 `EXCLUDED` 取;需有唯一索引作冲突判定基础。
- 用 `(xmax = 0)` 可判断本次是插入还是更新。
- 同批 UPSERT 同一键会报错,需先 `DISTINCT ON` 去重。
- 大批量装载用 `COPY`,顺序是"先装载后建索引",必要时用 `UNLOGGED` + `FREEZE`。

## 练习

1. 写一条幂等写入语句:反复执行 3 次,结果行数始终为 1。
2. 用 `(xmax = 0)` 实现"返回本次是新插入还是更新"。
3. 构造同批两行同键的 UPSERT,观察报错,并用 `DISTINCT ON` 修复。
4. 生成 100 万行 CSV,分别用逐行 `INSERT`(可用 `generate_series` 模拟)与 `COPY` 导入,比较耗时。
