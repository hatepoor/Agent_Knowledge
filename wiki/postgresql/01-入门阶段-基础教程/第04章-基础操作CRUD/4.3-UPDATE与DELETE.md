# 4.3 UPDATE 与 DELETE

## 学习目标

- 掌握 `UPDATE ... FROM`、`DELETE ... USING` 的写法
- 建立"UPDATE 与删除在 PostgreSQL 中是追加写"的认知
- 知道 `TRUNCATE` 与 `DELETE`、`VACUUM` 与空间回收的关系

## 前置知识

[[postgresql/01-入门阶段-基础教程/第04章-基础操作CRUD/4.2-SELECT基础查询]]

## 正文

### 一、UPDATE 基础

```sql
-- 单列
UPDATE users SET name = 'Ann' WHERE id = 1;

-- 多列
UPDATE orders
SET status = 'done',
    updated_at = now()
WHERE id = 100;

-- 基于自身/其他列计算
UPDATE products SET price = round(price * 1.1, 2) WHERE tags @> ARRAY['热销'];

-- 返回被修改的行
UPDATE orders SET status = 'shipped', updated_at = now()
WHERE status = 'paid'
RETURNING id, status, updated_at;

-- PG18+:RETURNING 同时返回旧值与新值
UPDATE orders SET status = 'done'
WHERE id = 100
RETURNING old.status AS old_status, new.status AS new_status;
```

**致命习惯:`UPDATE` 不写 `WHERE`**

```sql
UPDATE users SET vip = true;   -- ⚠️ 全表生效!
```

防御措施:

```sql
-- 会话级:禁止无 WHERE 的 UPDATE/DELETE
SET session_replication_role = ...;  -- 不是这个
```

更实用的是**事务包裹 + 先 SELECT 确认行数**:

```sql
BEGIN;
UPDATE users SET vip = true WHERE id = 1;      -- 检查 "UPDATE 1" 的行数
ROLLBACK;   -- 确认后再换成 COMMIT
```

或使用 `psql` 的 `\set ON_ERROR_STOP` 配合脚本审阅。真正的工程解法是通过**数据库账号权限**限制批量更新能力。

### 二、`UPDATE ... FROM`:跨表更新

```sql
-- 用另一张表的数据更新本表
UPDATE orders o
SET total = s.total
FROM (
    SELECT order_id, sum(qty * unit_price) AS total
    FROM order_items GROUP BY order_id
) s
WHERE o.id = s.order_id;
```

**注意**:`FROM` 里若出现同名表,需别名区分,否则可能产生笛卡尔积式的意外全表更新。

```sql
-- ⚠️ 危险:FROM 中的 orders 与目标表同名,若不加别名会自连接
UPDATE orders
SET status = o2.status
FROM orders o2
WHERE orders.id = o2.parent_id;   -- 语义正确但极易写错
```

**`UPDATE ... FROM` 的行为特性**

| 特性 | 说明 |
|------|------|
| 匹配多行的后果 | `FROM` 侧若对同一目标行匹配多行,结果**不确定**(取任意一行) |
| 修复 | 在 `FROM` 子查询里先做聚合或 `DISTINCT ON`,保证一对一 |

### 三、DELETE 基础

```sql
DELETE FROM orders WHERE status = 'canceled' AND created_at < '2025-01-01';
DELETE FROM orders WHERE id = 1 RETURNING id, status;

-- 跨表删除
DELETE FROM order_items oi
USING orders o
WHERE oi.order_id = o.id AND o.status = 'canceled';
```

**`USING` 与 `FROM` 的区别**:`DELETE ... USING` 是 PostgreSQL/标准写法,语义等价于 `UPDATE ... FROM`。

### 四、`UPDATE` 与 `DELETE` 是"追加写"(重要)

这是 PostgreSQL 与直觉不同的一个地方,也是后面很多性能问题的根源。

**关键事实:PostgreSQL 修改数据时不是"就地改",而是"写一份新的"。**

```
UPDATE 的实际过程:
  ① 找到要改的那一行(旧版本)
  ② 在别的位置写出一份"改好了的"新版本
  ③ 把旧版本标记为"已作废",但不清除它

DELETE 的实际过程:
  ① 找到要删的那一行
  ② 把它标记为"已作废"
  ③ 同样不立即清除
```

**换句话说:改和删都只是"贴标签",数据本身还留在原地。**

> **为什么这样设计**:可能有别人正在读这一行。如果就地改掉,读的人就会在半路看到"改了一半"的数据。写一份新的、把旧的标记作废,就能做到"读的人看旧版、写的人写新版",互不干扰。
>
> 这个机制叫 **MVCC**(多版本并发控制),是 PostgreSQL 的核心设计之一。**入门阶段不需要懂它的原理,但需要知道它带来的后果**——就是下面三条。原理见 [[postgresql/03-进阶阶段-深度剖析/事务与MVCC内核/原理剖析-MVCC与快照隔离]]。

**三个直接后果**

1. **表会"膨胀"**。大量 `UPDATE` / `DELETE` 之后,表占用的磁盘空间**不会自动缩小**,里面堆着一大堆已作废的旧版本。
2. **需要 `VACUUM` 回收**。`VACUUM` 把这些作废版本占的空间标记为"可复用"(但表文件大小不变);`VACUUM FULL` 才会真正把空间还给操作系统——代价是会长时间锁住整张表,大表慎用。
3. **索引也会膨胀**。删掉一行不会立刻从索引里移除对应条目,同样要靠 `VACUUM` 清理。

```sql
-- 观察:哪些表堆积了较多已作废的行(n_dead_tup = 已作废行数)
SELECT relname, n_live_tup, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- 手工回收
VACUUM (VERBOSE, ANALYZE) orders;
VACUUM FULL orders;          -- ⚠️ 会锁住整张表,阻塞读写,大表慎用
```

> **好消息**:这件事 PostgreSQL 默认**自动**在做(叫 autovacuum),通常不需要你手动执行——上表里的 `last_autovacuum` 就是它上次工作的时间。手动执行只在"刚做完大批量删除、想立刻回收"时才有必要。

**入门阶段只需记住这三条**

1. `UPDATE` / `DELETE` 之后表不会自动变小,**这是正常现象,不是 bug**。
2. **不要用"频繁 UPDATE 同一行"来存状态**(例如每秒把某行计数加一),那会让表迅速膨胀。这类需求改用"插入新行 + 事后汇总"。
3. `VACUUM FULL` 会锁表,**不要在业务高峰期做**。

### 五、TRUNCATE vs DELETE

```sql
DELETE FROM logs;                             -- 逐行标记删除,要写事务日志,慢,可回滚
TRUNCATE logs;                                -- 直接重建文件,快,可回滚
TRUNCATE logs RESTART IDENTITY;               -- 顺便把自增序号重置回 1
TRUNCATE logs CASCADE;                        -- 连带清空"引用它的表"
TRUNCATE a, b, c;                             -- 一次清空多张表(整体生效)
```

| 维度 | `DELETE` | `TRUNCATE` |
|------|----------|-----------|
| 机制 | 逐行标记删除,之后靠 `VACUUM` 回收 | 直接重建整张表的数据文件 |
| 速度 | 慢(逐行处理,行越多越慢) | 极快(**与行数无关**) |
| 空间 | 需 `VACUUM` 才能回收 | 立即释放 |
| 能否加 `WHERE` | ✅ | ❌ 只能整表清空 |
| 触发器 | ✅ 会触发 | ❌ 不触发 |
| 可回滚 | ✅ | ✅ |
| 锁 | 行级 | **锁整张表**(阻塞所有读写) |

> **两条实践要点**
>
> 1. `TRUNCATE` **锁整张表**,会让所有读写请求排队等待。生产环境不要在业务高峰期执行。
> 2. `TRUNCATE` 虽然快,但**不能加条件**。想"只删老数据"必须用 `DELETE`(并配合下面的分批方式)。

### 六、批量更新/删除的正确姿势

大表上一次性更新/删除千万行会引发一连串问题:**事务持续很久、事务日志暴涨占满磁盘、别人被锁住排队等待、表严重膨胀**。所以必须分批做。

**分批处理模式**

```sql
-- 循环执行直到影响行数为 0
WITH target AS (
    SELECT id FROM orders
    WHERE status = 'canceled' AND created_at < '2025-01-01'
    ORDER BY id
    LIMIT 5000
)
DELETE FROM orders o USING target t WHERE o.id = t.id;
```

在脚本中循环:

```bash
while true; do
  affected=$(psql -At -c "WITH t AS (SELECT id FROM orders WHERE ... LIMIT 5000)
                          DELETE FROM orders o USING t WHERE o.id = t.id;
                          SELECT count(*) FROM ...")
  # 或用 RETURNING + 计数判断
  [ "$affected" = "0" ] && break
  sleep 0.1
done
```

**同一行的并发更新会"阻塞"而不是"丢失"**:PostgreSQL 在 `UPDATE` 时会对目标行加行级锁,并遵循 `READ COMMITTED` 的"重新评估"语义:后到的事务会等待,然后在新版本上**重新应用** `WHERE` 条件。这是 PostgreSQL 与"丢失更新"对抗的机制,细节见 [[postgresql/02-中段阶段-专题精讲/执行计划与性能诊断/专题概览]] 与进阶篇锁机制。

## 小结

- `UPDATE`/`DELETE` 一定要有 `WHERE`,并用事务 + 行数确认保护。
- 跨表更新用 `UPDATE ... FROM`,跨表删除用 `DELETE ... USING`;`FROM` 侧必须保证对目标行一对一。
- 两者都是**追加写**:产生死元组、表膨胀,需 `VACUUM` 回收;`VACUUM FULL` 才真正还给 OS。
- `TRUNCATE` 快且可回滚,但取排他锁且不触发行触发器。
- 大表批量变更必须分批,避免长事务与复制延迟。
