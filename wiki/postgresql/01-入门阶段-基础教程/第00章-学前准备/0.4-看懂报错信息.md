# 0.4 看懂报错信息

## 学习目标

读完这一篇,你应该能:

- 拆解任意一条 PostgreSQL 报错,知道它想告诉你什么
- 独立排查 12 类最常见的报错
- 不再因为一条红色提示就把整个环境删掉重来

## 前置知识

[[postgresql/01-入门阶段-基础教程/第00章-学前准备/0.3-跑通第一条语句]]

## 一、先建立一个态度:报错是帮助,不是失败

数据库报错时,它其实在做三件事:告诉你**哪里错了、为什么错、怎么改**。读懂它就等于有了一个一直在旁边指路的老师。

而且 PostgreSQL 的报错信息在开源数据库里是相当详细的——它常常直接圈出出错的那一行,还给出修改建议。**不要跳过报错信息,逐字读一遍。**

## 二、报错信息的三段结构

```sql
SELECT emial FROM users;
```

```
ERROR:  column "emial" does not exist
LINE 1: SELECT emial FROM users;
               ^
HINT:  Perhaps you meant to reference the column "users.email".
```

逐段拆解:

| 段 | 内容 | 说明 |
|----|------|------|
| **ERROR:** | 错误的**一句话结论** | 这里说:没有名为 `emial` 的列 |
| **LINE n:** | **出错位置** | `LINE 1:` 表示第 1 行;下面的 `^` 符号**精确指向**出错的那个词 |
| **HINT:** | **修复建议** | 这里直接猜到了你想写的是 `email` |

这三段里最有价值的是 **`^` 和 `HINT`**:

- **`^` 指向哪,错就在哪附近**。语法错误时,它常指向"发现不对劲"的那个词,而这个词**往往不是真正的错处,它前面的词才是**。
- **有 `HINT` 一定要先按它试**。数据库多数情况下猜得对。

> **最高效的排查动作**:把 `^` 指向的位置前后各看两个词,以及照着 `HINT` 改。

## 三、12 类常见报错逐条排查

### 1. `syntax error at or near "..."`

**完整示例**

```
ERROR:  syntax error at or near "FROM"
LINE 1: SELECT * FORM users;
                 ^
```

**含义**:语法错误。数据库在这个词附近看不懂了。

**真正原因往往在 `^` 指向位置的**前面**:上例中错的是 `FORM`(应为 `FROM`),但 `^` 指向的是 `FROM`,因为数据库是读到那里才发现前面拼错了。

**排查顺序**

1. 看 `^` 指向的词**以及它前一个词**,通常是拼写错。
2. 检查有没有漏写逗号、括号不配对。
3. 检查有没有漏写关键字:`SELECT mail FROM users` 少了逗号会变成别的含义。

---

### 2. `relation "xxx" does not exist`

```
ERROR:  relation "user" does not exist
LINE 1: SELECT * FROM user;
                      ^
```

**含义**:找不到这张表(或视图、序列)。`relation` 是"关系"的意思,在 PostgreSQL 里泛指**表、索引、视图**这类对象。

**四步排查**

1. **表名拼写对吗?** —— `user` 和 `users` 是两个名字。注意 PostgreSQL 里 `user` 是保留字,很容易踩。
2. **你在正确的库里吗?** —— 执行 `\c` 看当前库;用 `\l` 看有哪些库。表是建在库里的,切错库就找不到。
3. **表真的建了吗?** —— 执行 `\dt` 列出当前库所有表。
4. **是不是在别的模式(schema)里?** —— 见下文 `\dt *.*`。

```
\dt          -- 当前模式下(默认 public)的表
\dt *.*      -- 所有模式下的表,排查"表明明建了却找不到"必用
```

---

### 3. `column "xxx" does not exist`

```
ERROR:  column "emial" does not exist
```

**含义**:表里没有这个列。

**排查**:执行 `\d 表名` 打印真实的列名对照。**这是最有用的一招**——不要凭记忆猜列名。

---

### 4. `missing FROM-clause entry for table "xxx"`

```
ERROR:  missing FROM-clause entry for table "orders"
LINE 1: SELECT orders.id FROM users;
```

**含义**:你用了 `orders.id`(某张表的列),但 `FROM` 后面只写了 `users`,数据库不知道 `orders` 是哪来的。

**怎么办**:检查 `FROM` 里有没有写上那张表,或者列名前的表名是不是写错了。

---

### 5. `invalid input syntax for type ...`

```
ERROR:  invalid input syntax for type integer: "abc"
```

**含义**:你想把一个不是数字的东西塞进数字列。

**常见触发**

| 写法 | 问题 |
|------|------|
| `INSERT INTO t (n) VALUES ('abc')` 而 `n` 是整数列 | 文本不是数字 |
| `SELECT '1,234'::integer` | 千分位逗号不是数字的一部分 |
| `WHERE id = '1 '` | 尾部有空格 |

**排查**:确认值的类型与列的类型一致。查列类型用 `\d 表名`;查一个值的类型用 `SELECT pg_typeof(值);`。

---

### 6. `null value in column "xxx" violates not-null constraint`

```
ERROR:  null value in column "email" violates not-null constraint
DETAIL:  Failing row contains (4, null, 张三, f, 2026-09-20 ...).
```

**含义**:`email` 这一列定义时加了 `NOT NULL`(必填),但你的 `INSERT` 没有给它值。

**两种修正**

```sql
-- 修正一:补上这个值
INSERT INTO users (email, name) VALUES ('d@example.com', '丁');

-- 修正二:给这一列加默认值,让它将来可以省略
ALTER TABLE users ALTER COLUMN email SET DEFAULT '待补充';
```

> 注意 `DETAIL` 段非常有用——它打印出**整行实际要写入的内容**,`null` 出现在哪个位置,一眼就能看出是哪一列。

---

### 7. `duplicate key value violates unique constraint`

```
ERROR:  duplicate key value violates unique constraint "users_email_key"
DETAIL:  Key (email)=(ann@example.com) already exists.
```

**含义**:这一列(或这几列)要求**值不能重复**,而你插的值已经存在了。

**`DETAIL` 会直接告诉你重复的是哪个值**。

**三种修正**

```sql
-- 修正一:换成不重复的值
INSERT INTO users (email) VALUES ('new@example.com');

-- 修正二:如果本意是"存在就更新",用 UPSERT(见 4.1)
INSERT INTO users (email, name) VALUES ('ann@example.com', '安妮V2')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

-- 修正三:确实不需要唯一性 → 删掉该约束(谨慎)
ALTER TABLE users DROP CONSTRAINT users_email_key;
```

---

### 8. `permission denied for ...`

```
ERROR:  permission denied for table users
```

**含义**:当前登录的角色没有这张表的操作权限。

**排查**

```sql
SELECT current_user;   -- 我现在是谁?
SELECT current_database();  -- 我在哪个库?
```

学习阶段最常见的原因是:**用普通角色去访问别人建的表**。让表的属主给你授权即可:

```sql
GRANT SELECT ON users TO 你的角色名;
```

权限体系详见 [[postgresql/01-入门阶段-基础教程/第06章-事务与权限入门/6.2-角色与权限入门]]。

---

### 9. `function xxx does not exist`

```
ERROR:  function width_buket(integer, integer, integer, integer) does not exist
HINT:  No function matches the given name and argument types. You might need to add explicit type casts.
```

**含义**:没有这个函数,**或者**函数名对但参数类型/个数不对。

**排查三步**

1. **函数名拼写** —— 上例是 `width_bucket` 拼成了 `width_buket`。
2. **参数个数与类型** —— 同样的名字可能有多个版本(这叫**重载**),个数或类型对不上就找不到。
3. **确认函数是否存在**:

```
\df 函数名        -- psql 里查函数签名
```

```sql
-- SQL 里查:
SELECT proname, pg_get_function_arguments(oid)
FROM pg_proc WHERE proname = 'width_bucket';
```

> **本套文档出现的每个函数都在 [[postgresql/函数手册]] 里有签名和示例。** 报这个错时先去查它。

---

### 10. `column "xxx" must appear in the GROUP BY clause`

```
ERROR:  column "users.name" must appear in the GROUP BY clause or be used in an aggregate function
```

**含义**:你用了**分组聚合**(`GROUP BY`),但 `SELECT` 里带了一个既没参与分组、也不是聚合结果的列。

**为什么**:一组有多行,数据库无法决定该显示哪一行的这个列值。

**修正**

```sql
-- ❌ 错:name 没有参与分组
SELECT name, count(*) FROM users GROUP BY vip;

-- ✅ 对:把 name 也放进 GROUP BY
SELECT name, count(*) FROM users GROUP BY name;

-- ✅ 或者:用一个聚合函数把它"收"成单值
SELECT min(name), count(*) FROM users GROUP BY vip;
```

原理见 [[postgresql/01-入门阶段-基础教程/第05章-查询核心/5.3-聚合函数与GROUP-BY]]。

---

### 11. `database "xxx" already exists` / `does not exist`

```
ERROR:  database "learn" already exists
FATAL:  database "leanr" does not exist
```

**含义**:建库时重名,或连库时库名写错/不存在。

**排查**

```
\l            -- 看有哪些库
\c 正确的库名  -- 切换
```

**想干净重来**:删库再建。

```sql
DROP DATABASE learn;      -- ⚠️ 会连同库里的所有表一起删掉
CREATE DATABASE learn;
```

---

### 12. `unterminated quoted string` / `unterminated quoted identifier`

```
ERROR:  unterminated quoted string at or near "'Ann"
```

**含义**:引号没配对。`'Ann` 少了右边的单引号。

**常见的三个原因**

| 原因 | 例子 | 修正 |
|------|------|------|
| 忘了右引号 | `'Ann` | `'Ann'` |
| 用了中文引号 | `‘Ann’` | 换成英文 `'Ann'` |
| 字符串内部要写单引号 | `'it's'` | 连写两个:`'it''s'` |

> **中文标点是最隐蔽的坑**:`‘’`、`“”`、`；`、`（）` 看起来像但数据库不认识。**输入法记得切英文半角。** 尤其是分号写成中文 `;` 时,报错会指向很奇怪的位置。

## 四、提示符变了但不是报错

| 现象 | 含义 | 怎么办 |
|------|------|--------|
| `learn-#`(`#` 前的符号从 `=` 变成 `-`) | 语句还没结束,数据库在等你写完 | 补 `;` 回车;想放弃就敲 `\r` |
| `learn'#` 或 `learn"#` | 引号没闭合,数据库在等右引号 | 补上引号,或敲 `\r` 放弃 |
| `learn(#` | 圆括号没闭合 | 补 `)` |
| 输出在 `less` 里滚不动 | `\d` 的结果太长,进了分页器 | 按 `q` 退出 |

## 五、通用排查方法(遇到没见过的报错时)

按顺序做这五件事:

1. **读 `ERROR:` 那一句的英文**。它通常已经说清是什么类别的问题(`does not exist` / `syntax` / `permission` / `violates`)。
2. **看 `^` 指向哪里**,再看它前面的词。
3. **按 `HINT` 改一遍**,多数情况直接解决。
4. **核对"我写的东西"与"数据库里的东西"是否一致**:
   ```
   \dt          表存在吗
   \d 表名      列名、类型、约束对吗
   SELECT current_database();   库对吗
   SELECT current_user;         角色对吗
   ```
5. **把报错整段读一遍**。如果还不行,把报错信息连同你的 SQL 一起留档——它本身就是最好的线索。

> **一个必须避免的坏习惯**:遇到报错就删掉环境重来。那样你永远学不到东西。**报错是学习材料,不是障碍。**

## 小结

- 报错分三段:`ERROR`(结论)、`LINE` + `^`(位置)、`HINT`(建议)。**先看 `^` 和 `HINT`**。
- 语法错误的 `^` 常指向错处的**后一个词**。
- `does not exist` 类:先查**拼写**,再查**库 / 模式 / 表 / 列是否真的存在**(用 `\dt`、`\d 表名`)。
- `violates constraint` 类:看 `DETAIL` 段,它直接给出冲突的行或值。
- 引号规则:字符串用单引号,内部单引号连写两个;**输入法务必切英文半角**。
- 提示符变成 `-#`、`(#`、引号不闭合都不是报错,是在等你写完。

## 练习

1. 故意把 `SELECT * FROM users;` 里的 `users` 拼错,记录报错全文,指出 `^` 指向哪里。
2. 触发一次 `null value in column ... violates not-null constraint`,从 `DETAIL` 段指出是哪一列缺值。
3. 触发一次 `duplicate key value violates unique constraint`,并用 `ON CONFLICT DO UPDATE` 消除它。
4. 把分号写成中文 `;`,观察报错位置如何"跑偏",体会为什么中文标点难排查。
5. 故意写一条 `GROUP BY` 错误的语句,记录报错并改成两种不同的正确写法。
