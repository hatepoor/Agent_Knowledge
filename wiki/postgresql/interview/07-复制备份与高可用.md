# 复制、备份与高可用

> **适用场景**：社招/运维向岗位。开发岗至少要说清「同步 vs 异步」「PITR 怎么做的」。
> **主线**：**物理复制复制的是「页和 WAL」，逻辑复制复制的是「行变更」。**

---

## Q1. PostgreSQL 的流复制（物理复制）是怎么工作的？

**答：**

流复制是**基于 WAL 的物理复制**：把主库的 WAL 持续传给从库，从库重放出完全相同的物理副本。

```
主库                                  从库
┌─────────────┐                      ┌─────────────┐
│ 产生 WAL     │                      │ walreceiver │
│ walsender ───┼──── WAL 流 ─────────►│      ↓      │
│             │                      │ startup 进程 │
│             │                      │ 重放 WAL     │
└─────────────┘                      └─────────────┘
```

关键进程：

| 进程 | 位置 | 职责 |
|------|------|------|
| **walsender** | 主库 | 读取 WAL，通过网络发送 |
| **walreceiver** | 从库 | 接收 WAL，写入本地 WAL 文件 |
| **startup** | 从库 | 重放 WAL，应用数据页变更 |

特点：

| 特点 | 说明 |
|------|------|
| **物理级一致** | 从库是主库的块级副本，包括所有数据库、索引、系统表 |
| **从库只读** | 可以接读请求（Hot Standby），但不能写 |
| **版本必须一致** | 主从大版本必须相同（小版本可不同） |
| **不能按表复制** | 要复制整实例 |

**追问：从库重放会不会阻塞读查询？**
→ 会。重放需要拿锁，如果读查询持有冲突的锁，重放会等待，表现为**复制延迟**。`max_standby_streaming_delay` 控制「等多久后取消读查询」，需要权衡「读一致性」和「延迟」。

## Q2. 同步复制和异步复制的区别？`synchronous_commit` 起什么作用？

**答：**

| 模式 | 提交行为 | 数据安全 | 延迟 |
|------|---------|---------|------|
| **异步（默认）** | 主库 WAL 落盘即返回 | 主库崩溃可能丢最近事务 | 低 |
| **同步** | 等至少一个从库确认收到/写入/应用 | 更高 | **受从库网络和磁盘影响** |

配置：

```sql
-- 主库
synchronous_standby_names = 'standby1'
synchronous_commit = on            -- 等从库 flush 到磁盘
```

`synchronous_commit` 的档位：

| 值 | 等待到哪一步 | 安全性 |
|----|-------------|--------|
| `off` | 不等本地 WAL 刷盘 | 最低（崩溃可能丢） |
| `local` | 本地 WAL 刷盘 | 单机安全 |
| `remote_write` | 从库收到并写入 OS 缓冲 | 中（从库 OS 崩溃可能丢） |
| `on` | 从库 WAL 刷盘 | 高（默认同步档） |
| `remote_apply` | 从库**已重放**，读得到 | 最高（读一致性最强） |

**追问：同步复制会不会拖慢主库？**
→ 会，而且**受最慢从库影响**。从库网络抖动、磁盘慢，主库提交就跟着卡。所以生产常用「一主一同步 + 一异步」：同步保安全，异步保可用；同步从库挂了要能快速降级为异步，否则主库写入会停。

**追问：同步复制能保证「零丢失」吗？**
→ 能保证「已提交事务至少在两个节点有副本」，但**不能防脑裂**。网络分区时，如果主库降级为异步继续写，仍可能丢。零丢失需要配合 quorum 和 fencing 机制。

## Q3. 逻辑复制是什么？和物理复制有什么区别？

**答：**

逻辑复制是**基于逻辑解码的行级复制**：主库把 WAL 解析成「INSERT/UPDATE/DELETE 的逻辑变更」，订阅端按表重放。

```sql
-- 发布端
CREATE PUBLICATION pub_orders FOR TABLE orders;

-- 订阅端
CREATE SUBSCRIPTION sub_orders
CONNECTION 'host=publisher dbname=app'
PUBLICATION pub_orders;
```

| 维度 | 物理复制 | 逻辑复制 |
|------|---------|---------|
| **复制单位** | 整个实例（块级） | **表级**（可选行列） |
| **版本要求** | 主从大版本必须一致 | **可跨大版本** |
| **从库可写** | ❌ 只读 | ✅ 可写（适合双活/汇总） |
| **DDL** | 自动同步 | **不同步**，要手动执行 |
| **序列** | 同步 | **不同步**，要单独处理 |
| **冲突处理** | 无（物理一致） | 可能主键冲突，订阅会停 |
| **开销** | 低（传 WAL） | 较高（解码 + 重新执行） |

**追问：逻辑复制最适合什么场景？**
→ ① **跨版本升级**（老版本 → 新版本，停机时间短）；② **按表同步**到数据仓库/报表库；③ **多库汇总**；④ 异构系统对接。**不适合**做「高可用主从」——它不复制 DDL、序列，切换后容易出问题。

**追问：逻辑复制为什么容易卡住？**
→ 订阅端遇到主键冲突、约束失败、表结构不一致时，会**停止应用**并报错，直到人工跳过或修复。物理复制不会，因为它只是重放页。

## Q4. PITR 是什么？完整流程怎么做？

**答：**

PITR（Point-In-Time Recovery，时间点恢复）= **基础备份 + WAL 归档**，可以恢复到「任意一个时间点」。

流程：

```
① 开启归档
   archive_mode = on
   archive_command = 'cp %p /archive/%f'

② 做基础备份
   pg_basebackup -D /backup/base -Ft -z -P

③ 持续归档 WAL（后台自动）

④ 需要恢复时：
   - 恢复基础备份到数据目录
   - 配置 restore_command 从归档取 WAL
   - 设置 recovery_target_time / recovery_target_lsn / recovery_target_xid
   - 启动，PG 重放 WAL 到目标点

⑤ 确认后 promote，开始接受写入
```

关键参数：

| 参数 | 作用 |
|------|------|
| `recovery_target_time` | 恢复到某个时间点 |
| `recovery_target_lsn` | 恢复到某个 LSN |
| `recovery_target_action` | `promote` / `pause` / `shutdown` |

**追问：PITR 能恢复「误删表」吗？**
→ 能，但要恢复到**误删之前**的时间点，**整个实例一起回退**，不是只恢复一张表。如果要单表恢复：① 恢复到临时实例；② 从临时实例导出该表；③ 导入生产。**这就是为什么「逻辑备份 + 定期演练」仍然必要。**

**追问：基础备份期间主库能写吗？**
→ 能。`pg_basebackup` 用复制协议做一致性快照，不阻塞写入；但它需要读全部数据文件，会带来 I/O 压力，建议低峰期做。

## Q5. 怎么监控复制延迟？延迟大了怎么处理？

**答：**

主库看 `pg_stat_replication`：

```sql
SELECT client_addr, state, sent_lsn, write_lsn, flush_lsn, replay_lsn,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

四个 LSN 对应复制链路的不同阶段：

```
sent_lsn → write_lsn → flush_lsn → replay_lsn
  发送       写入OS      刷盘        重放完成
```

**延迟 = 主库当前 LSN 与 `replay_lsn` 的差距**，可以用 `pg_wal_lsn_diff()` 算字节数。

延迟大的原因：

| 原因 | 表现 | 处理 |
|------|------|------|
| **网络带宽不足** | `sent_lsn` 落后 | 升级带宽/压缩 WAL |
| **从库磁盘慢** | `flush_lsn` 落后 | 换 SSD、调 `wal_writer` |
| **从库 CPU 不足** | `replay_lsn` 落后 | 加资源 |
| **长事务/大事务** | 突然堆积 | 拆大事务、分批提交 |
| **从库有长查询** | 重放被锁阻塞 | 调 `max_standby_streaming_delay` |
| **写入突增** | WAL 生成速度超过传输 | 限流/扩容 |

**追问：延迟多少算危险？**
→ 没有绝对值。看**业务能容忍丢多少数据**：异步复制下，延迟 10 秒就意味着故障可能丢 10 秒的事务。**关键指标是「延迟时间 × 写入速率 = 潜在丢失量」。**

## Q6. 主从切换怎么做？切换时要注意什么？

**答：**

**手动切换（最基础）**：

```bash
# 在从库上提升为主库
pg_ctl promote -D /data

# 或
SELECT pg_promote();
```

自动切换需要外部工具：**Patroni**（最常用，基于 etcd/Consul 做选主）、pg_auto_failover、云厂商托管方案。

切换的六个注意点：

| 点 | 说明 |
|----|------|
| **确认延迟** | 切换前看 `replay_lsn`，延迟大意味着丢数据多 |
| **防止脑裂** | 旧主必须被 fence（关机/断网/降级），否则两个主同时写 |
| **VIP/连接串** | 应用要能切到新主，别写死 IP |
| **序列与逻辑复制** | 逻辑复制切换后要重建订阅 |
| **时间线（timeline）** | 切换会产生新 timeline，旧从库要按新时间线重新接入 |
| **回切方案** | 旧主恢复后作为从库重新加入，不能直接当主 |

**追问：为什么「自动切换」比想象中难？**
→ 难的不是 `promote`，是**判断「主库真的挂了」还是「网络抖了一下」**。误判会导致双主写入、数据分叉。所以需要 quorum（多数派确认）+ fencing（确保旧主不能再写）。

## Q7. 生产环境的备份策略怎么设计？

**答：**

核心原则：**备份不是「有就行」，要能恢复、要有演练。**

三层组合：

| 层 | 方式 | 频率 | 恢复粒度 |
|----|------|------|---------|
| **基础备份** | `pg_basebackup`（全量） | 每天/每周 | 整个实例 |
| **WAL 归档** | `archive_command` 持续归档 | 实时 | 任意时间点 |
| **逻辑备份** | `pg_dump` / `pg_dumpall` | 每周/每月 | 单库/单表 |

保留策略：

- 全量备份保留 N 天/N 周；
- WAL 归档保留时间 ≥ 最长恢复需求（要能恢复到「上周五」就至少留 7 天）；
- 异地/对象存储一份，防单点。

必须做的三件事：

1. **定期恢复演练**：真恢复到临时实例，验证备份可用；
2. **监控归档失败**：`archive_command` 失败会堆积 WAL，最终撑爆磁盘；
3. **记录 RPO/RTO**：能容忍丢多少数据、多久恢复，倒推备份频率。

**追问：`pg_dump` 和 `pg_basebackup` 怎么选？**
→ `pg_dump` 是**逻辑备份**：可跨版本、可单表、可编辑；但慢、恢复也慢，且不是时间点一致。`pg_basebackup` 是**物理备份**：快、可做 PITR；但版本绑定、只能整实例。**生产通常两者都要。**

## Q8. 复制槽是什么？有什么坑？

**答：**

复制槽（Replication Slot）是**主库对从库的承诺**：「你还没消费的 WAL，我不会删。」

```sql
SELECT * FROM pg_replication_slots;
```

作用：

- 防止主库在从库落后时把 WAL 删掉；
- 从库断线重连后，还能从断点继续；
- 逻辑复制也依赖复制槽做解码位置记录。

**最大的坑：WAL 堆积。**

```
从库长期离线 → 复制槽一直不推进 → 主库 WAL 无限堆积 → 磁盘满 → 主库宕机
```

防护：

| 手段 | 说明 |
|------|------|
| `max_slot_wal_keep_size` | 限制单个槽保留的 WAL 上限，超出后槽失效（从库需重建） |
| **监控** | 定期查 `pg_replication_slots` 的 `restart_lsn` 和当前 LSN 差距 |
| **清理废弃槽** | 下线从库/订阅时同步删槽 |
| **告警** | WAL 目录大小、槽落后字节数 |

**追问：槽失效后从库怎么办？**
→ 只能**重新做基础备份**（rebuild）。所以 `max_slot_wal_keep_size` 是「用重建换主库存活」的取舍，要配合监控提前处理，不要等它触发。
