# 架构与存储模型

> **适用场景**：PG 面试的开场题。答得好，后面会被当「真用过」；答得空，会被一直往 MySQL 常识上带。
> **主线**：**进程模型 → 内存 → 页 → WAL**，四层讲完就是一条完整的「一条 SQL 怎么落到磁盘」。

---

## Q1. PostgreSQL 的进程模型是什么？和 MySQL 的线程模型有什么区别？

**答：**

PostgreSQL 是**多进程**架构：

| 角色 | 职责 |
|------|------|
| **postmaster** | 主进程：监听端口、接受连接、fork 出后端进程、崩溃后重启整个集群 |
| **backend** | **每个客户端连接一个独立进程**，负责该连接的所有查询 |
| **checkpointer** | 定期执行 checkpoint，把脏页刷盘 |
| **background writer** | 平时渐进地把脏页写回磁盘，平滑 I/O |
| **walwriter** | 把 WAL 缓冲区刷到 WAL 文件 |
| **autovacuum launcher/worker** | 自动清理与统计信息收集 |
| **walsender / walreceiver** | 流复制的主从传输 |

MySQL（InnoDB）是**单进程多线程**：一个 mysqld 进程，连接是线程。

| 维度 | PostgreSQL | MySQL |
|------|-----------|-------|
| 并发单元 | 进程 | 线程 |
| 连接开销 | **大**（fork + 独立内存） | 小 |
| 隔离性 | 进程地址空间天然隔离，一个 backend 崩了通常不拖垮全局 | 线程共享地址空间，一个线程崩了可能整个实例挂 |
| 连接数 | 通常几百，**必须上连接池** | 可以上千 |
| 共享内存 | 显式 shared_buffers | Buffer Pool |

**追问：为什么 PG 一定要连接池？**
→ 每个连接是一个进程，有独立栈和内存，创建/销毁成本高；连接数上去后上下文切换和内存开销会压垮机器。生产上通常用 **PgBouncer** 做连接复用，应用侧再用小连接池。

## Q2. 一条 SQL 从进入 PostgreSQL 到返回结果，经过哪些阶段？

**答：**

五个阶段：

```
客户端
  ↓ ① 连接与认证（postmaster → fork backend）
  ↓ ② Parser：词法/语法分析 → 语法树
  ↓ ③ Analyzer：语义分析、权限检查、类型解析 → Query 树
  ↓ ④ Rewriter：展开视图、应用规则 → 改写后的 Query
  ↓ ⑤ Planner/Optimizer：生成候选执行计划，按代价选最优 → Plan
  ↓ ⑥ Executor：按 Plan 拉取数据（火山模型）
  ↓ ⑦ Buffer Manager / Storage：读页、写页、写 WAL
结果返回
```

**关键点**：

- **解析和执行是分离的**：简单查询协议（simple query）每次都要重新 parse/plan；预编译语句（extended query）可以复用计划。
- **优化器是基于代价的（CBO）**：依赖统计信息，统计信息过期会导致计划跑偏。
- **执行器是火山模型（Volcano）**：节点之间 `next()` 拉取一行，所以 `LIMIT` 能提前终止。

**追问：预编译语句的计划一定更好吗？**
→ 不一定。PG 对 prepared statement 有「通用计划 vs 定制计划」的选择：前几次用定制计划（按实际参数），执行足够多次后可能切到通用计划。参数倾斜严重时，通用计划会很差，可以强制 `plan_cache_mode = force_custom_plan`。

## Q3. `shared_buffers` 是什么？为什么不建议无限调大？

**答：**

`shared_buffers` 是 PG 的**共享缓冲池**：所有 backend 共享，按 8KB 页缓存表和索引数据。读先查缓冲池，命中直接返回；没命中从磁盘读入。

通常建议 **物理内存的 25% 左右**（不是绝对规则，要看负载和是否与 OS page cache 争用）。

不建议无限调大的原因：

| 原因 | 说明 |
|------|------|
| **双重缓存** | PG 读文件也走 OS page cache，shared_buffers 太大会让同一份数据在用户态和内核态各存一份 |
| **checkpoint 压力** | 缓冲池越大，一次 checkpoint 要刷的脏页越多，I/O 尖峰越明显 |
| **启动/恢复变慢** | 崩溃后需要重建更大的共享内存 |
| **收益递减** | 命中率到一定程度后，再加内存对延迟的改善很小 |

**追问：怎么判断 shared_buffers 够不够？**
→ 看 `pg_stat_database` 的 `blks_hit / (blks_hit + blks_read)` 命中率，结合 `EXPLAIN (ANALYZE, BUFFERS)` 看具体查询的读页数。**命中率低不一定是缓冲池小，也可能是索引缺失导致扫了太多页。**

**追问：那剩下的内存给谁？**
→ OS page cache（缓存数据文件）、`work_mem`（排序/哈希）、`maintenance_work_mem`（VACUUM/建索引）、连接进程的私有内存。**PG 的性能是「共享缓冲 + OS 缓存」协同的结果，不是单靠 shared_buffers。**

## Q4. `work_mem` 是什么？为什么它容易导致 OOM？

**答：**

`work_mem` 是**单个查询里「每个排序或哈希操作」可用的内存上限**，不是每个连接的总量。

```
一个连接
├── Sort 节点        → 最多 work_mem
├── Hash Join 节点   → 最多 work_mem
├── HashAggregate    → 最多 work_mem
└── ...              → 每个节点各算一份
```

所以实际内存 ≈ `work_mem × 并发连接数 × 单查询内的排序/哈希节点数`。

风险来源：

| 场景 | 后果 |
|------|------|
| 复杂查询有多个 Sort/Hash 节点 | 单查询就能吃掉几倍 work_mem |
| 高并发 | 乘上连接数后迅速超过物理内存 |
| 超大排序 | 超过 work_mem 会落临时文件，磁盘 I/O 暴涨（不是报错） |

**调优思路**：

- 全局 `work_mem` 设保守值（如几十 MB），**不要按最重的查询设**；
- 对个别重查询用 `SET LOCAL work_mem = '256MB'` 临时提高；
- 监控 `pg_stat_database.temp_bytes` / `temp_files`，临时文件暴涨说明 work_mem 太小或查询需要优化。

**追问：work_mem 调大一定更快吗？**
→ 不一定。它只影响「排序/哈希能否在内存完成」。如果瓶颈是索引缺失或返回行数太多，调大 work_mem 只是让错误计划跑得更快。

## Q5. 表在磁盘上是怎么存的？一个 8KB 页里有什么？

**答：**

PG 的存储层级：

```
数据库 → 表空间 → 数据文件（按 1GB 分段）→ 页（8KB）→ 行（tuple）
```

一个页的典型结构：

```
┌──────────────────────────────┐
│ 页头（24B）：LSN、校验和、空闲空间指针等 │
├──────────────────────────────┤
│ 行指针数组（ItemId）：offset + length + 标志 │
├──────────────────────────────┤
│ 空闲空间                       │
├──────────────────────────────┤
│ 行数据（tuple），从页尾向前增长    │
├──────────────────────────────┤
│ Special 区（索引页专用）         │
└──────────────────────────────┘
```

关键点：

- **行指针与行数据分离**：通过 `ctid`（页号, 行指针号）定位一行；行移动时只改指针，不用改所有索引。
- **行不能跨页**：单行太大就触发 TOAST。
- **更新产生新版本**：旧行标记 `xmax`，新行写入（可能同页也可能新页），索引指向新 `ctid`。

**追问：`ctid` 能当主键用吗？**
→ **不能**。`ctid` 会随 UPDATE/VACUUM FULL 变化，只能用于「当前时刻定位」，不能作为业务标识。

## Q6. TOAST 是什么？什么时候触发？对查询有什么影响？

**答：**

TOAST（The Oversized-Attribute Storage Technique）是 PG 处理**超大字段**的机制：当一行超过约 2KB 时，把大的变长字段**压缩后挪到行外**的 TOAST 表里，主表只留一个指针。

触发逻辑：

1. 行大小超过 `TOAST_TUPLE_THRESHOLD`（约 2KB）；
2. 优先压缩（`pglz` 或 `lz4`）；
3. 压缩后仍超限，就切片存到 TOAST 表；
4. 查询时按需读取、解压、拼接。

**影响**：

| 场景 | 影响 |
|------|------|
| `SELECT *` 查大文本/大 JSON | 强制读取 TOAST 表，I/O 和内存放大 |
| 只查其他列 | 不读 TOAST，影响小 |
| 大字段上做 LIKE/正则 | 无法走普通索引，通常要全文检索或表达式索引 |
| 更新大字段 | 可能重写 TOAST，产生额外 WAL |

**追问：怎么避免 TOAST 带来的性能问题？**
→ ① 查询**只选需要的列**，别 `SELECT *`；② 大字段拆到单独的扩展表（冷热分离）；③ 需要检索大文本时用 GIN 全文索引；④ 超大二进制放对象存储，表里只存路径。

## Q7. WAL 是什么？为什么必须「先写日志再写数据」？

**答：**

WAL（Write-Ahead Logging）是**预写日志**：任何数据页的修改，必须先把「改了什么」顺序写入 WAL 并刷盘，数据页本身可以延迟写。

规则：**日志落盘之前，对应的脏页不能落盘。**

为什么这样设计：

| 目的 | 说明 |
|------|------|
| **崩溃恢复** | 数据页可能只写了一半（partial write），但 WAL 是完整的，重启时按 LSN 重放即可 |
| **随机写变顺序写** | 事务提交只需顺序追加 WAL，不用等待多个随机数据页刷盘，提交延迟大幅降低 |
| **复制的基础** | 流复制就是把主库的 WAL 持续发给从库重放 |
| **PITR** | 基础备份 + 归档 WAL，可以恢复到任意时间点 |

关键概念：

- **LSN（Log Sequence Number）**：WAL 的位置指针，单调递增；
- **`synchronous_commit`**：控制提交是否等待 WAL 刷盘。关掉能提速，但崩溃会丢最近事务；
- **`full_page_writes`**：checkpoint 后第一次修改某页时，把整页写入 WAL，防止页断裂。

**追问：关掉 `synchronous_commit` 会丢多少数据？**
→ 最多丢失「最后一个未刷盘的事务」，通常是毫秒级窗口。但**不是零风险**：机器断电、OS 崩溃都可能触发。金融类业务不能关；可容忍少量丢失的日志/埋点类可以关。

## Q8. checkpoint 是什么？它和 WAL、崩溃恢复是什么关系？

**答：**

**checkpoint 是一次「把内存里的脏页统一刷到磁盘，并在 WAL 里记录一个恢复起点」的动作。**

它做三件事：

1. 把 shared_buffers 中的脏页写回数据文件；
2. 在 WAL 中写入 checkpoint 记录，标记「这个 LSN 之前的所有修改都已落盘」；
3. 更新控制文件，记录 redo 起点。

和 WAL 的关系：

```
WAL:  ... [checkpoint] ... 修改A ... 修改B ... 崩溃
                 ↑
           恢复从这里开始重放，不用从头
```

没有 checkpoint，崩溃恢复就要从 WAL 的开头重放，时间不可控。

| 参数 | 作用 |
|------|------|
| `checkpoint_timeout` | 两次 checkpoint 的最大间隔 |
| `max_wal_size` | WAL 增长到阈值会触发 checkpoint |
| `checkpoint_completion_target` | 把刷盘摊到多长时间内，避免 I/O 尖峰 |

**追问：checkpoint 太频繁/太稀疏分别有什么问题？**
→ **太频繁**：持续大量随机写，I/O 抖动，影响查询延迟；**太稀疏**：WAL 堆积占磁盘，崩溃恢复时间变长。生产上通常让 `checkpoint_completion_target` 接近 0.9，把刷盘摊平。

**追问：checkpoint 时会不会阻塞查询？**
→ 正常刷脏页不阻塞读；但 checkpoint 相关的锁和 I/O 竞争会影响延迟。**突发的大量脏页（如大批量导入后）是常见的延迟尖峰来源。**
