# 锁与并发控制

> **适用场景**：只要岗位涉及「高并发」「线上排查」，这一篇必问。
> **主线**：**MVCC 管读，锁管写。** 读不阻塞写，但写与写之间要靠锁排队。

---

## Q1. PostgreSQL 有哪些表级锁？

**答：**

八种模式，按强度从弱到强：

| 锁模式 | 典型触发 | 说明 |
|--------|---------|------|
| **ACCESS SHARE** | `SELECT` | 最弱，只阻止 `ACCESS EXCLUSIVE` |
| **ROW SHARE** | `SELECT FOR UPDATE/SHARE` | 阻止 `EXCLUSIVE` / `ACCESS EXCLUSIVE` |
| **ROW EXCLUSIVE** | `INSERT` / `UPDATE` / `DELETE` | 写操作的默认表锁，**相互不冲突** |
| **SHARE UPDATE EXCLUSIVE** | `VACUUM`（非 FULL）、`CREATE INDEX CONCURRENTLY`、`ANALYZE` | 阻止其他 DDL 和 VACUUM |
| **SHARE** | `CREATE INDEX`（非 CONCURRENTLY） | 阻止写，允许读 |
| **SHARE ROW EXCLUSIVE** | 部分 `ALTER TABLE` | 自冲突，阻止写 |
| **EXCLUSIVE** | 较少使用 | 阻止除 `ACCESS SHARE` 外所有 |
| **ACCESS EXCLUSIVE** | `DROP` / `TRUNCATE` / 多数 `ALTER TABLE` | **最强**，读写全阻塞 |

**关键点**：

- **`UPDATE` 只拿 ROW EXCLUSIVE**，所以多个事务可以同时写同一张表（行锁在行级竞争）；
- **`ACCESS EXCLUSIVE` 会阻塞所有查询**，这是 DDL 的危险所在；
- 锁冲突是**双向**的：后来的请求会排队，排队又会阻塞它后面的请求（锁队列堆积）。

**追问：为什么 `SELECT` 也要拿锁？**
→ 防止查询过程中表被 `DROP`/`ALTER`。ACCESS SHARE 很弱，几乎不冲突，但能挡住破坏性 DDL。

## Q2. 行级锁有哪几种？`FOR UPDATE` 和 `FOR NO KEY UPDATE` 有什么区别？

**答：**

四种行锁，强度递减：

| 锁模式 | 语句 | 作用 |
|--------|------|------|
| **FOR UPDATE** | `SELECT ... FOR UPDATE` | 最强：锁定行，阻止其他事务更新/删除/加锁 |
| **FOR NO KEY UPDATE** | `UPDATE` 非键列时自动加 | 不阻止 `FOR KEY SHARE`，允许外键引用继续 |
| **FOR SHARE** | `SELECT ... FOR SHARE` | 共享锁：多个事务可同时持有，阻止写 |
| **FOR KEY SHARE** | `SELECT ... FOR KEY SHARE` | 最弱：只锁「键」，不阻止非键列更新（外键检查用） |

**核心区别**：

- `FOR UPDATE` 会阻塞所有其他行锁请求；
- `FOR NO KEY UPDATE` 是普通 UPDATE 的默认行为，**不阻塞外键检查**（`FOR KEY SHARE`）；
- 这样设计是为了**避免「更新非键列」把外键引用方全部卡死**。

```sql
-- 悲观锁：锁住这一行，别人不能改
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
```

**追问：行锁存在哪里？**
→ 不是锁表里的独立记录，而是**写在行头的 `xmax` 上**（多事务共享时用 multixact）。所以行锁数量不会像「每行一个锁对象」那样爆炸——这是 PG 的设计优势。

## Q3. 行锁和 MVCC 是什么关系？为什么加了行锁，普通 `SELECT` 还是能读？

**答：**

**MVCC 负责「读哪个版本」，锁负责「谁能写」。**

| 操作 | 是否需要行锁 | 读什么 |
|------|-------------|--------|
| 普通 `SELECT` | ❌ 不加行锁 | 按快照读可见版本 |
| `SELECT ... FOR UPDATE` | ✅ 加行锁 | 读最新版本并锁定 |
| `UPDATE` / `DELETE` | ✅ 自动加行锁 | 找目标行，锁定后修改 |

所以：

```sql
-- 事务 A
BEGIN;
UPDATE accounts SET balance = 200 WHERE id = 1;   -- 持有行锁，未提交

-- 事务 B
SELECT balance FROM accounts WHERE id = 1;        -- ✅ 能读，读到旧版本 100
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;   -- ❌ 阻塞，等 A 提交
```

**一句话**：**普通读走快照，不看锁；加锁读才需要等。**

**追问：那 `SELECT` 会不会读到「正在被改」的中间状态？**
→ 不会。UPDATE 产生的是**新版本**，旧版本在事务提交前仍然完整；读快照只会看到旧版本。**这就是 MVCC 的核心价值。**

## Q4. 死锁是怎么产生的？PostgreSQL 怎么处理？

**答：**

死锁 = **两个或多个事务互相持有对方需要的锁，形成环**。

```
事务 A：锁住行 1 → 请求行 2
事务 B：锁住行 2 → 请求行 1
         ↑ 互相等待，成环
```

PG 的处理：

1. **死锁检测器**周期性检查等待图；
2. 发现环后，**选择一个事务作为牺牲者**，回滚它；
3. 被回滚的事务收到 `ERROR: deadlock detected`，SQLSTATE **40P01**；
4. 另一个事务继续执行。

**应用必须重试**，而且要重试**整个事务**，不是单条语句。

预防手段：

| 手段 | 说明 |
|------|------|
| **固定加锁顺序** | 多行更新按主键排序后再锁，避免交叉 |
| **缩短事务** | 锁持有时间越短，成环概率越低 |
| **一次锁定** | 用 `SELECT ... FOR UPDATE` 按顺序一次性锁住所有需要的行 |
| **降低隔离级别** | 减少间隙锁/谓词锁（PG 的 RR 不加间隙锁，但 MySQL 会） |
| **advisory lock 统一入口** | 用应用级锁串行化关键区 |

**追问：死锁和「锁等待超时」有什么区别？**
→ 死锁是**成环**，检测器主动杀一个；锁等待超时是**单方向等待太久**（`lock_timeout` / `deadlock_timeout`），没有环，只是慢。前者是逻辑问题，后者往往是长事务或 DDL 排队。

## Q5. 线上出现锁等待，怎么排查？

**答：**

三步定位：**谁在等 → 谁阻塞了它 → 在跑什么 SQL**。

```sql
-- ① 当前等待中的会话
SELECT pid, wait_event_type, wait_event, state, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';

-- ② 谁阻塞了它（PG 9.6+）
SELECT pid, pg_blocking_pids(pid) AS blocked_by, query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- ③ 锁的明细
SELECT locktype, relation::regclass, mode, granted, pid
FROM pg_locks
WHERE NOT granted;
```

常见根因：

| 现象 | 根因 | 处置 |
|------|------|------|
| 大量会话等 `relation` 锁 | DDL 拿了 ACCESS EXCLUSIVE，后面全排队 | 杀 DDL 或等窗口期；DDL 加 `lock_timeout` |
| 等 `transactionid` | 有长事务持有行锁不提交 | 找到长事务，确认后终止 |
| 等 `tuple` | 热点行更新冲突 | 拆热点（分片计数）、缩短事务 |
| 等 `advisory` | 应用级锁没释放 | 检查业务逻辑/连接是否泄漏 |

**追问：能直接 `pg_terminate_backend` 吗？**
→ 能，但要谨慎：① 先确认它是不是关键任务；② 终止会回滚整个事务，可能丢业务进度；③ 优先 `pg_cancel_backend`（取消当前查询）而不是杀连接。**生产上先通知业务方，再动手。**

## Q6. 咨询锁（advisory lock）是什么？什么场景用？

**答：**

咨询锁是**应用自定义语义的锁**：PG 不关心你锁的是什么，只保证「同一个 key 同时只有一个持有者」。

```sql
-- 会话级：连接断开才释放
SELECT pg_advisory_lock(42);
SELECT pg_advisory_unlock(42);

-- 事务级：事务结束自动释放
SELECT pg_advisory_xact_lock(42);

-- 非阻塞版本：拿不到立即返回 false
SELECT pg_try_advisory_lock(42);
```

适用场景：

| 场景 | 说明 |
|------|------|
| **定时任务互斥** | 多副本部署时，保证同一时刻只有一个实例跑批 |
| **同一资源的串行化** | 按业务 id 加锁，避免应用层分布式锁的额外依赖 |
| **迁移/初始化** | 防止多个实例同时执行 DDL |
| **同 thread 串行** | Agent 场景下按 `thread_id` 加锁，防止并发写同一会话 |

**追问：advisory lock 能替代 Redis 分布式锁吗？**
→ 在「单库」范围内可以，而且更简单（事务级锁随事务释放，不会因为进程崩溃留下死锁）。**跨库/跨系统就不行**，它只在当前数据库实例内有效。注意：会话级锁如果连接池复用连接而未释放，会「泄漏」到下一个请求。

## Q7. 为什么 DDL 会锁表？怎么降低影响？

**答：**

大多数 DDL（`ALTER TABLE`、`DROP`、`TRUNCATE`）需要 **ACCESS EXCLUSIVE** 锁，**阻塞该表上的所有读写**。

更危险的是**锁队列堆积**：

```
DDL 请求 ACCESS EXCLUSIVE → 排队
后续 SELECT 请求 ACCESS SHARE → 排在 DDL 后面（因为队列顺序）
→ 整个表的所有查询都被一个 DDL 卡住
```

降低影响的手段：

| 手段 | 说明 |
|------|------|
| **设置 `lock_timeout`** | DDL 等不到锁就失败，不进入无限排队 |
| **低峰期执行** | 业务低峰做变更 |
| **用 CONCURRENTLY** | `CREATE INDEX CONCURRENTLY` 不阻塞写（但不能在事务块里执行，失败会留 invalid 索引） |
| **分批变更** | 加列通常很快（PG 11+ 加带默认值的列不重写表），改类型可能重写全表 |
| **先加后删** | 改列名/类型用「新增列 → 双写 → 迁数据 → 删旧列」 |
| **gh-ost / pg_repack 类工具** | 大表结构变更用在线工具 |

**追问：`ALTER TABLE ADD COLUMN` 一定会锁很久吗？**
→ 不一定。PG 11+ 加「带常量默认值」的列是**元数据操作**，不重写表；但加「易变默认值」（如 `now()`）或改类型，可能触发全表重写，锁会持很久。**变更前先看执行计划/文档，不要想当然。**

## Q8. 乐观锁和悲观锁在 PostgreSQL 里怎么实现？

**答：**

**悲观锁**：先锁再改。

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- 锁住
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

适合**冲突频繁、重试成本高**的场景（如库存扣减）。

**乐观锁**：先改，提交时检查版本。

```sql
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 7;

-- 影响行数为 0 → 说明被别人改过，重试或报错
```

适合**读多写少、冲突少**的场景（如用户资料编辑）。

| 维度 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 加锁时机 | 读取时 | 提交时检查 |
| 阻塞 | 会阻塞其他写 | 不阻塞，冲突时失败 |
| 冲突高时 | 等待多，吞吐低 | 重试多，CPU 浪费 |
| 实现 | `FOR UPDATE` | version 列 / `xmin` |
| 风险 | 死锁、长事务 | ABA、重试风暴 |

**追问：能用 `xmin` 做乐观锁吗？**
→ 可以：`WHERE xmin = 123`。省一个 version 列，但 `xmin` 是系统列，类型和语义不够直观，且 VACUUM/特殊操作可能影响；**业务表建议显式 version 列**，可读性和可控性更好。
