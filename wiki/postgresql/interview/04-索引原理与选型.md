# 索引原理与选型

> **适用场景**：后端岗必问。PG 的索引类型比 MySQL 多，**能讲清「为什么选这个类型」就是区分度**。
> **主线**：索引不是「越多越好」，是**用写放大换读性能**的生意。

---

## Q1. PostgreSQL 的 B-tree 索引是怎么组织的？为什么适合范围查询？

**答：**

B-tree 是**平衡多路搜索树**，PG 的实现有几个关键点：

```
            [根页]
          /    |    \
      [中间页] [中间页] [中间页]
        /         |         \
   [叶子页] ←→ [叶子页] ←→ [叶子页]
      数据      数据        数据
```

| 特性 | 说明 |
|------|------|
| **多路** | 一个页（8KB）放几百个 key，树高很低（百万级表通常 3~4 层） |
| **有序** | 页内 key 有序，页间通过兄弟指针连成链表 |
| **平衡** | 所有叶子在同一层，查询复杂度稳定 O(log n) |
| **叶子存 TID** | 叶子项存 `(key, ctid)`，指向堆表中的行 |

为什么适合范围查询：

- 等值查询：从根走到叶子，命中后可能还要左右扫（重复 key）；
- 范围查询：定位到起点后，**沿叶子链表顺序扫描**，不用回到上层；
- 排序：索引本身有序，`ORDER BY` 可以直接利用，避免 Sort。

**追问：为什么 PG 的索引不存整行数据（不像 MySQL 聚簇索引）？**
→ PG 是**堆表 + 独立索引**：表数据按插入顺序存放，索引只存 `ctid`。优点是二级索引不用存主键、更新行时索引改动小；代价是**查非索引列要回表**（随机 I/O）。MySQL InnoDB 是聚簇索引，主键即数据，二级索引存主键值。

## Q2. PostgreSQL 有哪些索引类型？分别适合什么？

**答：**

| 类型 | 结构 | 适合 | 不适合 |
|------|------|------|--------|
| **B-tree** | 平衡多路树 | 等值、范围、排序、前缀匹配 | 多值字段、全文、几何 |
| **Hash** | 哈希表 | 纯等值查询 | 范围、排序（几乎不用） |
| **GIN** | 倒排索引 | 数组、JSONB、全文检索、多值包含 | 高频写入（写放大） |
| **GiST** | 通用搜索树 | 几何、范围类型、近邻搜索 | 精确等值（有损，需 recheck） |
| **SP-GiST** | 空间分区树 | 非平衡结构：四叉树、前缀树 | 通用场景 |
| **BRIN** | 块范围索引 | **物理有序的大表**（时间序列） | 随机分布的数据 |

**选型口诀**：

- 不知道选什么 → **B-tree**（90% 场景）；
- JSONB 的 `@>`、数组包含、全文 `@@` → **GIN**；
- 地理位置、范围重叠、`<->` 近邻 → **GiST**；
- 上亿行、按时间追加、按时间范围查 → **BRIN**（体积极小）；
- 纯 KV 等值且不在乎范围 → Hash（实际很少用）。

**追问：GIN 为什么写入慢？**
→ 它要为**每个元素**建索引项：一个 JSONB 文档有 50 个 key，插入时就要写 50 条索引记录。所以 GIN 适合「读多写少」；写入频繁时可以用 `fastupdate` 缓冲，但会增加查询时的合并成本。

## Q3. 复合索引的「最左前缀」在 PostgreSQL 里怎么理解？

**答：**

复合索引 `(a, b, c)` 按 **a → b → c** 的优先级排序，所以：

| 查询条件 | 能否用索引 | 说明 |
|---------|-----------|------|
| `WHERE a = ?` | ✅ | 用第一列 |
| `WHERE a = ? AND b = ?` | ✅ | 用前两列 |
| `WHERE a = ? AND b = ? AND c = ?` | ✅ | 全用 |
| `WHERE b = ?` | ❌（通常） | 跳过第一列，无法定位 |
| `WHERE a = ? AND c = ?` | ⚠️ 部分 | 只用 a，c 不能用于定位 |
| `WHERE a = ? AND b > ? AND c = ?` | ⚠️ 部分 | b 用了范围后，c 不能继续定位 |

**设计原则**：

1. **等值条件放前面，范围条件放后面**；
2. **选择性高的列不一定放最前**——要看查询模式，最左列必须是常用过滤条件；
3. 排序需求：`ORDER BY a, b` 可以直接用 `(a, b)` 索引避免排序。

**追问：能不能给所有列都建单列索引，让优化器自己组合？**
→ 可以（Bitmap Index Scan 能组合多个单列索引），但**组合索引通常更高效**：一次扫描定位、避免多索引交集、支持排序。单列索引多还会增加写放大和优化器决策成本。

## Q4. 什么是覆盖索引？为什么 `Index Only Scan` 有时候还是读了很多页？

**答：**

**覆盖索引** = 查询需要的所有列都在索引里，不用回表。

```sql
CREATE INDEX idx_users_email_name ON users (email) INCLUDE (name);

SELECT name FROM users WHERE email = 'a@b.com';   -- 可以 Index Only Scan
```

`INCLUDE` 是 PG 11+ 的语法：**key 列参与排序和定位，include 列只存数据**。

`Index Only Scan` 不总是「只读索引」：

| 条件 | 行为 |
|------|------|
| 索引项对应堆页**全可见**（visibility map 标记 all-visible） | 直接返回，不回表 |
| 堆页**不是全可见**（有未清理的死元组/未提交事务） | **要回表检查可见性**，退化成普通 Index Scan |

所以：

- 表刚大批量更新过、autovacuum 没跟上 → visibility map 不完整 → Index Only Scan 名不副实；
- `EXPLAIN (ANALYZE, BUFFERS)` 里看 `Heap Fetches`，数字大就说明回表了。

**追问：为什么 visibility map 能省回表？**
→ 它按页记录「这一页所有行对所有事务都可见」。如果整页都可见，索引里的 `ctid` 指向的行一定可见，不用再去堆表验证 MVCC。**VACUUM 负责维护这个位图。**

## Q5. 部分索引和表达式索引分别解决什么问题？

**答：**

**部分索引（Partial Index）**：只索引满足条件的行。

```sql
CREATE INDEX idx_orders_pending ON orders (created_at)
WHERE status = 'pending';
```

适用：**数据分布倾斜**，业务只查少数状态。

| 优点 | 说明 |
|------|------|
| 索引更小 | 只存部分行，缓存命中率更高 |
| 写入更快 | 不满足条件的行不写索引 |
| 更精准 | 查询必须带相同 `WHERE` 条件才能用 |

**表达式索引（Expression Index）**：索引「计算后的值」。

```sql
CREATE INDEX idx_users_lower_email ON users (lower(email));

SELECT * FROM users WHERE lower(email) = 'a@b.com';   -- 能用
SELECT * FROM users WHERE email = 'A@B.com';          -- 不能用（表达式不匹配）
```

适用：大小写不敏感查询、JSONB 字段提取、日期截断。

**追问：部分索引的 `WHERE` 条件和查询条件不一致会怎样？**
→ 优化器要求查询条件**蕴含**索引条件才使用。比如索引 `WHERE status='pending'`，查询 `WHERE status IN ('pending','paid')` 通常用不上；查询 `WHERE status='pending' AND ...` 才能用。**写之前先确认查询模式。**

## Q6. 哪些情况会导致索引「失效」？

**答：**

严格说不是索引失效，是**优化器选择不用**或**用不上**：

| 情况 | 原因 | 解法 |
|------|------|------|
| **列被函数包裹** | `WHERE lower(name) = 'x'`，普通索引用不了 | 建表达式索引 |
| **隐式类型转换** | `WHERE id = '123'`（id 是 int），可能转换后无法用索引 | 参数类型对齐 |
| **前导通配符** | `LIKE '%abc'` 无法定位 | 全文检索 / trigram（`pg_trgm`） |
| **`OR` 连接不同列** | 可能退化为全表扫描 | 改 `UNION ALL` 或建组合索引 |
| **选择性太差** | 返回 30% 的行，全表扫描更快 | 接受 Seq Scan，或建部分索引 |
| **统计信息过期** | 优化器估算错误 | `ANALYZE` |
| **排序规则/编码不匹配** | 索引排序规则与查询不一致 | 统一 collation |
| **表太小** | 全表扫描成本更低 | 正常现象，不用管 |

⚠️ **面试陷阱**：不要背「索引一定失效」的清单。**优化器是基于代价的**，有时不用索引是正确决策。判断标准是 `EXPLAIN (ANALYZE, BUFFERS)` 里的实际行数和耗时，不是「有没有走索引」。

**追问：怎么确认是「索引没被用」还是「索引用错了」？**
→ 先看 `EXPLAIN` 的 `rows` 估算 vs `actual rows`。差距大 → 统计信息问题；估算准但仍全表扫 → 选择性确实差，优化器没错。

## Q7. GIN、GiST、BRIN 三者到底怎么选？

**答：**

| 维度 | GIN | GiST | BRIN |
|------|-----|------|------|
| **索引对象** | 一个值内部的**多个元素** | 一个值整体的**空间/范围** | **一组连续页**的摘要 |
| **典型操作** | `@>`、`?`、`@@`（全文） | `&&`、`<->`、范围重叠 | 范围扫描（`BETWEEN`、`>`） |
| **写入成本** | 高（每元素一条） | 中 | **极低** |
| **索引体积** | 大 | 中 | **极小**（约为表的 1/1000 量级） |
| **精度** | 精确 | **有损**，需要 recheck | 粗粒度，可能多读页 |
| **典型场景** | JSONB 标签、数组、全文检索 | 地理位置、时间范围重叠 | 日志/时序表按时间查 |

**一句话选型**：

- 「值里面包含哪些元素」→ **GIN**；
- 「两个空间对象是否相交/谁离谁近」→ **GiST**；
- 「按物理顺序追加、按范围查」→ **BRIN**。

**追问：BRIN 为什么这么小还能用？**
→ 它不存每一行的位置，只存**每个数据块范围的 min/max**。查询时先排除不可能命中的块，只读剩下的块。前提是**数据物理顺序与查询列相关**（比如按时间追加的日志表）；如果数据乱序，每个块都可能命中，BRIN 就退化成全表扫描。

## Q8. HOT 更新是什么？它和索引维护有什么关系？

**答：**

HOT（Heap-Only Tuple）是 PG 减少索引更新的优化：

**如果 UPDATE 没有修改任何被索引的列，并且新版本能放进同一个页**，PG 就不新增索引项，而是用页内的指针链把新旧版本连起来。

```
普通更新：新行写新页 → 所有索引都要新增一条指向新 ctid
HOT 更新：新行写同页 → 索引仍指向旧 ctid，页内链跳转到新版本
```

| 收益 | 说明 |
|------|------|
| 少写索引 | 索引不膨胀，WAL 减少 |
| 少一次索引查找 | 更新更快 |
| 延迟清理 | 页内死元组由 VACUUM 清理 |

**前提条件**：

1. **更新的列不在任何索引里**（否则必须更新索引）；
2. **同页有足够空闲空间**（`fillfactor` 留白，默认 100 表示不留）。

**追问：`fillfactor` 怎么设？**
→ 对**频繁更新**的表，调低到 70~90，预留页内空间，提高 HOT 命中率；只读表保持默认 100。这是「用空间换更新性能」的典型取舍。

## Q9. 索引是不是越多越好？过多有什么代价？

**答：**

**不是。每个索引都是一份额外的写成本和存储成本。**

| 代价 | 说明 |
|------|------|
| **写放大** | 每次 INSERT/UPDATE/DELETE 都要维护所有相关索引 |
| **WAL 增加** | 索引变更也写 WAL，复制和备份压力变大 |
| **缓存占用** | 索引页挤占 shared_buffers，降低数据命中率 |
| **优化器成本** | 候选索引越多，planning time 越长（连接数高时明显） |
| **膨胀** | 频繁更新导致索引页分裂、碎片化 |
| **维护成本** | VACUUM、REINDEX、监控都要覆盖 |

**治理原则**：

1. **一个索引必须对应一个明确的查询模式**，没有查询用的索引删掉；
2. **优先组合索引**，覆盖多个查询的最左前缀；
3. 定期查未使用索引：

```sql
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

⚠️ 注意：`idx_scan = 0` 也可能是「统计周期内没跑到」，删除前要观察足够长的时间（覆盖完整业务周期）。

**追问：主键索引和唯一索引也要算成本吗？**
→ 要，但它们是**约束**，不能为了性能删。能做的是：主键尽量用窄类型（`bigint` 优于长字符串/UUID 文本），减少所有二级索引的存储和比较成本。
