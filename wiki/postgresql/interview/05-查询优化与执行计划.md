# 查询优化与执行计划

> **适用场景**：社招必问，也是「会不会调优」的分水岭。
> **主线**：优化不是「加索引」，是**让优化器的估算接近现实**。

---

## Q1. `EXPLAIN` 和 `EXPLAIN ANALYZE` 有什么区别？重点看哪些字段？

**答：**

| 命令 | 是否执行 | 输出 |
|------|---------|------|
| `EXPLAIN` | ❌ 只生成计划 | 优化器的**估算** |
| `EXPLAIN ANALYZE` | ✅ **真正执行** | 估算 + **实际**耗时/行数 |
| `EXPLAIN (ANALYZE, BUFFERS)` | ✅ | 再加页读写统计（**最常用**） |

⚠️ `EXPLAIN ANALYZE` 会真的执行 DML。测 `UPDATE/DELETE` 时放在事务里，看完 `ROLLBACK`。

重点字段：

| 字段 | 含义 | 怎么用 |
|------|------|--------|
| `cost=0.00..35.50` | 启动成本..总成本（相对单位） | 比较计划优劣，不是毫秒 |
| `rows=1000` | **估算**返回行数 | 和 `actual rows` 对比 |
| `width=64` | 每行平均字节数 | 判断是否读了太多列 |
| `actual time=0.05..1.20` | 实际首行/总耗时（**每个 loop**） | 找最慢节点 |
| `rows=... loops=N` | 实际行数 × 循环次数 | 注意 loops，别被单次数字骗了 |
| `Buffers: shared hit/read` | 缓存命中/磁盘读页数 | 判断 I/O 瓶颈 |
| `Heap Fetches` | Index Only Scan 回表次数 | 判断 visibility map 是否生效 |
| `Planning Time` / `Execution Time` |  planning 与执行耗时 | planning 过长说明索引太多或查询太复杂 |

**追问：`actual time` 为什么有两个数？**
→ `actual time=首行时间..全部返回时间`。首行时间影响 `LIMIT` 场景的响应速度，总时间影响整体吞吐。

**追问：`loops` 大说明什么？**
→ 说明该节点在 NestLoop 的内侧被反复执行。比如 `loops=10000`、单次 0.1ms，总耗时就是 1 秒。**看总耗时要把 `actual time × loops` 算进去。**

## Q2. PostgreSQL 的代价模型是怎样的？`cost` 的单位是什么？

**答：**

`cost` 是**相对单位**，不是毫秒。基准是「顺序读一个 8KB 页」的成本，默认 `seq_page_cost = 1.0`。

主要参数：

| 参数 | 默认 | 含义 |
|------|------|------|
| `seq_page_cost` | 1.0 | 顺序读一页 |
| `random_page_cost` | 4.0 | 随机读一页（HDD 假设） |
| `cpu_tuple_cost` | 0.01 | 处理一行的 CPU 成本 |
| `cpu_index_tuple_cost` | 0.005 | 处理一个索引项 |
| `cpu_operator_cost` | 0.0025 | 执行一个操作符 |

总成本 ≈ **I/O 成本 + CPU 成本**：

```
Seq Scan cost ≈ 页数 × seq_page_cost + 行数 × (cpu_tuple_cost + 过滤条件成本)
Index Scan cost ≈ 索引页成本 + 回表随机读成本 + CPU 成本
```

**关键点**：

- 如果库在 **SSD** 上，`random_page_cost = 4` 会**高估随机读的代价**，导致优化器偏爱 Seq Scan。常见调优是把它降到 1.1~2。
- `cost` 只用于**同一查询的不同计划之间比较**，不能跨查询比较。

**追问：为什么调低 `random_page_cost` 能让索引生效？**
→ 索引扫描是「随机回表」，代价被高估时优化器觉得不如全表顺序扫。SSD 的随机读和顺序读差距远小于 HDD，调低后估算更接近现实。

## Q3. 统计信息是怎么收集的？为什么会导致执行计划跑偏？

**答：**

统计信息由 `ANALYZE` 收集，存在 `pg_statistic`（用户视图 `pg_stats`）：

| 信息 | 用途 |
|------|------|
| **MCV（最常见值）** | 估算等值查询的选择性 |
| **直方图** | 估算范围查询的选择性 |
| **n_distinct** | 列的唯一值数量 |
| **correlation** | 物理顺序与逻辑顺序的相关性，影响索引扫描成本估算 |
| **null_frac** | NULL 占比 |

收集方式：**采样**，不是全表扫描。`default_statistics_target` 控制采样量（默认 100）。

计划跑偏的典型原因：

| 原因 | 现象 | 解法 |
|------|------|------|
| **统计信息过期** | 大批量导入/删除后没 ANALYZE | 手动 `ANALYZE table`，或调 autovacuum |
| **采样不足** | 数据倾斜严重，MCV 没覆盖 | 提高该列的 `statistics_target` |
| **列间相关性** | 多列条件相互独立假设不成立 | 建**扩展统计信息**：`CREATE STATISTICS ... (dependencies)` |
| **参数化查询** | 通用计划不适配具体参数 | `plan_cache_mode = force_custom_plan` |
| **表达式无统计** | `WHERE lower(x)=...` | 建表达式索引（会附带统计） |

**追问：怎么快速判断是统计信息问题？**
→ 看 `EXPLAIN ANALYZE` 的 `rows` 估算 vs `actual rows`。**差一个数量级以上**，基本就是统计信息或相关性假设的问题；差 2~3 倍属正常误差。

## Q4. Nested Loop、Hash Join、Merge Join 分别适合什么场景？

**答：**

| 算法 | 原理 | 适合 | 不适合 |
|------|------|------|--------|
| **Nested Loop** | 外表每行 → 内表查一次 | **外表很小**、内表连接列有索引 | 大表 × 大表（O(n×m)） |
| **Hash Join** | 小表建哈希表 → 扫大表探测 | **等值连接**、大表、无索引 | 非等值连接、内存不够（会落盘） |
| **Merge Join** | 两边按连接键排序 → 归并 | 两边**已有序**（索引/排序）、范围连接 | 无序且数据量大（排序成本高） |

选择逻辑（简化）：

```
外表很小 + 内表有索引        → Nested Loop
大表等值连接、无可用索引      → Hash Join
两边都有序 / 需要范围连接     → Merge Join
```

**追问：Hash Join 内存不够会怎样？**
→ 会分成多个批次落临时文件（`work_mem` 控制单批大小），性能急剧下降。`EXPLAIN (ANALYZE, BUFFERS)` 里能看到 `Batches > 1`，这时要么调大 `work_mem`，要么优化查询减少数据量。

**追问：为什么 Nested Loop 的 `loops` 会很大？**
→ 它对外表的每一行都执行一次内表扫描。外表 1 万行，内表就被查 1 万次。**外表估算错误（实际远大于估算）是 NestLoop 变慢的头号原因。**

## Q5. 明明建了索引，为什么还是走 Seq Scan？

**答：**

按概率排序，常见原因：

| 原因 | 判断方法 | 处理 |
|------|---------|------|
| **选择性差** | 返回行数占比高（如 30%） | 正常，全表扫更快，别硬加索引 |
| **表太小** | 几页的数据，索引反而多一次查找 | 不用管 |
| **统计信息过期** | `rows` 估算与实际差很多 | `ANALYZE` |
| **`random_page_cost` 过高** | 索引扫描成本被高估 | SSD 下调低 |
| **需要回表太多** | 索引命中多但都要回表 | 覆盖索引（`INCLUDE`） |
| **条件写法用不上索引** | 函数包裹、隐式转换、前导 `%` | 改写法/表达式索引 |
| **数据倾斜 + 参数化** | 某些参数走索引、某些不走 | 强制 custom plan 或拆分查询 |

⚠️ **不要用 `SET enable_seqscan = off` 来「验证索引」后就说优化好了**。那只是让优化器被迫选索引，生产上不能这么干。**正确做法是让估算变准，或改查询/索引结构。**

**追问：Seq Scan 一定慢吗？**
→ 不一定。顺序读整表在 SSD 上非常快，尤其是宽表只取少量列时。**判断标准是实际耗时，不是扫描方式的名字。**

## Q6. CTE 在 PostgreSQL 里会被优化吗？`MATERIALIZED` 有什么用？

**答：**

**PG 12 起，非递归、无副作用、且只被引用一次的 CTE 默认会被内联**（inline），也就是把 CTE 展开进主查询，让优化器一起做条件下推、连接重排。

```sql
WITH recent AS (
    SELECT * FROM orders WHERE created_at > now() - interval '7 days'
)
SELECT * FROM recent WHERE user_id = 42;
-- PG 12+：user_id 条件下推，可能用上 (user_id, created_at) 索引
```

控制手段：

| 写法 | 行为 |
|------|------|
| 默认（PG 12+） | 满足条件就内联 |
| `WITH x AS MATERIALIZED (...)` | **强制物化**，先算完再被引用（优化器不能下推） |
| `WITH x AS NOT MATERIALIZED (...)` | **强制内联** |
| 递归 CTE / 有副作用 / 被引用多次 | 默认物化 |

**什么时候要 `MATERIALIZED`**：

- CTE 被引用多次，物化避免重复计算；
- CTE 里有昂贵但结果集很小的计算，先算完再连接；
- 优化器内联后选了更差的计划（用 `MATERIALIZED` 做计划隔离）。

**追问：为什么 PG 12 之前 CTE 是「优化 fence」？**
→ 旧版所有 CTE 都强制物化，主查询的 `WHERE` 条件无法下推进 CTE，导致「先全量算 CTE 再过滤」，大表上非常慢。这是 PG 12 的重要改进。

## Q7. 分区表怎么做分区裁剪？什么情况下裁不掉？

**答：**

分区裁剪（Partition Pruning）= **根据 `WHERE` 条件排除不相关的分区**，只扫描命中的分区。

```sql
CREATE TABLE orders (id bigint, created_at date, ...) PARTITION BY RANGE (created_at);
CREATE TABLE orders_2026_09 PARTITION OF orders FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

SELECT * FROM orders WHERE created_at >= '2026-09-01';   -- 只扫 9 月及之后的分区
```

裁不掉的情况：

| 情况 | 原因 |
|------|------|
| **条件没直接引用分区键** | 如 `WHERE date_trunc('month', created_at) = ...`，表达式包住了分区键 |
| **条件里分区键被函数包裹** | 同上，无法在计划期比较 |
| **参数化查询 + 通用计划** | 计划期不知道参数值，只能运行时裁剪（`enable_partition_pruning`） |
| **分区键类型与常量不匹配** | 隐式转换导致无法比较 |
| **动态 SQL / 子查询** | 优化器无法在计划期推断 |

**追问：分区表能提升所有查询吗？**
→ 不能。**只有「按分区键过滤」的查询才受益**。如果查询不涉及分区键，分区表反而可能更慢（要扫所有分区 + Append 开销）。分区的核心价值是**裁剪 + 按分区维护（删旧数据用 DROP PARTITION）**。

## Q8. 线上一条 SQL 突然变慢，你的排查步骤是什么？

**答：**

按「先定位、再归因、后验证」走：

```
① 确认现象：从 pg_stat_statements 找 top 慢 SQL（按总耗时/平均耗时/调用次数）
② 看计划：EXPLAIN (ANALYZE, BUFFERS)，重点看 rows 估算 vs 实际、Buffers、loops
③ 分三类归因：
   ├─ 计划变了：统计信息过期 / 数据量变化 / 参数变化 → ANALYZE、扩展统计
   ├─ 计划没变但慢了：数据膨胀 / 缓存命中下降 / 锁等待 / I/O 抖动
   └─ 一直慢：缺索引 / 写法问题 / 返回数据太多
④ 对照环境：是否刚做过批量导入、VACUUM、DDL、版本升级、连接数暴涨
⑤ 修复并验证：改索引/改 SQL/调参数，再跑一次 EXPLAIN 对比
⑥ 防复发：加监控（慢查询日志、pg_stat_statements）、加回归测试
```

**关键工具**：

| 工具 | 用途 |
|------|------|
| `pg_stat_statements` | 聚合 SQL 的执行次数、总耗时、平均耗时 |
| `pg_stat_activity` | 当前正在跑的 SQL、等待事件 |
| `pg_locks` | 锁等待 |
| `EXPLAIN (ANALYZE, BUFFERS)` | 单条 SQL 的详细执行 |
| `pg_stat_user_tables` | 死元组、last_analyze/vacuum |

**追问：怎么区分「SQL 本身慢」和「数据库整体慢」？**
→ 看**其他 SQL 是否同时变慢**。只有一条慢 → SQL/计划问题；大面积慢 → 资源（CPU/IO/连接数/锁）或实例问题。**先看 `pg_stat_activity` 的等待事件分布，能快速分流。**
