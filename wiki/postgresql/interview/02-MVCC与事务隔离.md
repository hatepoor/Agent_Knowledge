# MVCC 与事务隔离

> **适用场景**：PG 面试**最高频**。这题答不深，基本会被归到「只会写 CRUD」。
> **主线**：**行版本 + 快照 + 可见性规则**。把这三件事讲清，隔离级别就是推论。

---

## Q1. 什么是 MVCC？PostgreSQL 是怎么实现的？

**答：**

MVCC（Multi-Version Concurrency Control，多版本并发控制）是**用「保留多个行版本」来避免读写互相阻塞**的并发控制机制。

核心思想：**读不阻塞写，写不阻塞读。**

- 读操作按自己的**快照**读取「对当前事务可见的那个版本」；
- 写操作**不覆盖旧行**，而是写入一个新版本，旧版本标记为已删除；
- 旧版本由 VACUUM 在确认没有事务需要后回收。

PostgreSQL 的实现特点：

| 特点 | 说明 |
|------|------|
| **旧版本留在堆表里** | 不像 MySQL 用 undo log 回滚段；PG 的新旧版本都在同一张表的数据文件里 |
| **靠隐藏列判断可见性** | `xmin` / `xmax` 记录创建和删除它的事务 |
| **没有回滚段** | 回滚靠「标记事务 abort」，读取时自动忽略 |
| **代价是膨胀** | 死元组堆积，必须靠 VACUUM 回收 |

**追问：PG 的 MVCC 和 MySQL 的 MVCC 最大区别？**
→ **旧版本的存放位置**。MySQL（InnoDB）把旧版本放 undo log，回滚段可复用；PG 把旧版本留在表里，所以 PG 的 UPDATE 多、VACUUM 不及时就会表膨胀。**这也是 PG 面试必问 VACUUM 的原因。**

## Q2. `xmin`、`xmax`、`ctid` 分别是什么？

**答：**

三个隐藏系统列，每行都有：

| 列 | 含义 | 用途 |
|----|------|------|
| **`xmin`** | **创建**这个行版本的事务 ID | 判断这行是不是「我这个事务能看见的」 |
| **`xmax`** | **删除/锁定**这个行版本的事务 ID；0 表示未被删除 | 判断这行是否已被删除或正被锁 |
| **`ctid`** | 行的物理位置：`(页号, 行指针号)` | 定位行、排查重复行、观察更新 |

```sql
SELECT xmin, xmax, ctid, id, name FROM users WHERE id = 1;
```

一次 UPDATE 的实际过程：

```
旧行：xmin=100, xmax=0      → 更新后 xmax=200（被事务 200 删除）
新行：xmin=200, xmax=0      → 事务 200 插入的新版本
```

**追问：`xmax` 不为 0 就一定表示行被删了吗？**
→ 不一定。`xmax` 还可能是**行锁**的持有者（`SELECT ... FOR UPDATE` 会给行打锁标记）。要区分「已删除」和「被锁」，需要结合事务状态和锁信息判断。

**追问：`ctid` 会变吗？**
→ 会。UPDATE 通常产生新版本、新位置；`VACUUM FULL` / `pg_repack` 会重写表，所有 `ctid` 都变。**所以 `ctid` 不能当业务主键。**

## Q3. 快照（snapshot）是怎么生成的？可见性怎么判断？

**答：**

快照本质是**一组事务 ID 的边界**，记录「哪些事务对我可见」：

| 字段 | 含义 |
|------|------|
| `xmin` | 生成快照时，**还在活跃的最小事务 ID** |
| `xmax` | 生成快照时，**下一个尚未分配的事务 ID** |
| `xip` | 生成快照时**正在活跃的事务 ID 列表** |

判断一行是否可见（简化版）：

```
1. 若 xmin 对应的 txid 未提交 / 已回滚        → 不可见
2. 若 xmin 在 xip（活跃列表）里                → 不可见
3. 若 xmax 为 0                              → 可见（未被删除）
4. 若 xmax 已提交，且不在 xip 里              → 不可见（已删除）
5. 若 xmax 未提交 / 已回滚                    → 可见（删除没生效）
```

一句话：**「创建我的事务已提交且不是我的活跃事务」+「删除我的事务没生效」= 我能看见。**

**追问：为什么快照要用「活跃事务列表」，不能只看 xmin/xmax？**
→ 因为事务 ID 的提交顺序和分配顺序**不一致**。事务 100 可能比事务 101 晚提交；只看边界会把「已提交的 101」误判为不可见。**必须用 xip 精确排除。**

## Q4. PostgreSQL 支持哪几种隔离级别？分别解决什么问题？

**答：**

SQL 标准四种，PG 全部支持，但行为有差异：

| 隔离级别 | PG 的实际行为 | 脏读 | 不可重复读 | 幻读 | 写偏斜 |
|---------|--------------|------|-----------|------|--------|
| **READ UNCOMMITTED** | **等同 READ COMMITTED** | ❌ 不会 | 可能 | 可能 | 可能 |
| **READ COMMITTED**（默认） | 每条语句开始生成新快照 | ❌ | **可能** | 可能 | 可能 |
| **REPEATABLE READ** | 整个事务一个快照（快照隔离） | ❌ | ❌ | **不会** | 可能 |
| **SERIALIZABLE** | SSI，检测危险依赖 | ❌ | ❌ | ❌ | **不会** |

**关键结论**：

1. PG **没有真正的脏读**：RU 被提升为 RC，因为 MVCC 下读不到未提交版本；
2. PG 的 **RR 比标准更强**：标准 RR 允许幻读，PG 的 RR 用事务级快照，幻读也不会出现；
3. **只有 SERIALIZABLE 能防写偏斜**，代价是可能报 `40001` 序列化失败，应用要重试。

**追问：默认用哪个？**
→ **READ COMMITTED**。绝大多数 OLTP 场景够用；需要「事务内多次读一致」时用 RR；只有涉及跨行不变式（如「两个账户余额之和不能为负」）才上 SERIALIZABLE。

## Q5. 为什么 PG 的 REPEATABLE READ 不会出现幻读？

**答：**

因为 PG 的 RR 实现的是**快照隔离（Snapshot Isolation）**：事务开始时生成一个快照，**整个事务内所有查询都用这一个快照**。

幻读的定义是「同一事务内两次查询，第二次看到了别人新插入的行」。在 PG 的 RR 下：

- 别人新插入的行，其 `xmin` 是快照之后的事务；
- 按可见性规则，这个 `xmin` 不在快照的可见范围内；
- 所以**第二次查询看不到新插入的行**。

对比 MySQL：

| 数据库 | RR 下防幻读的手段 |
|--------|------------------|
| MySQL InnoDB | 间隙锁（Next-Key Lock）**锁住区间**，阻止插入 |
| PostgreSQL | **快照**，让新插入的行对当前事务不可见（不阻塞写入） |

**追问：PG 的 RR 有什么代价？**
→ 如果事务尝试 UPDATE 一行「快照生成后被别人改过」的数据，会报 `could not serialize access due to concurrent update`（40001），需要重试。**快照隔离不是「无冲突」，而是「冲突时让你失败」。**

## Q6. READ COMMITTED 下同一事务两次查询结果不一样，正常吗？

**答：**

**正常，这是 RC 的定义行为。**

RC 下**每条语句开始时生成新快照**，所以：

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- 100
-- 另一个事务提交了 UPDATE，把余额改成 200
SELECT balance FROM accounts WHERE id = 1;  -- 200（同一事务内变了）
COMMIT;
```

这叫**不可重复读**，RC 明确允许。

如果业务要求「事务内读到的数据不变」，两个选择：

| 方案 | 做法 |
|------|------|
| **提高隔离级别** | `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` |
| **显式加锁** | `SELECT ... FOR SHARE` / `FOR UPDATE` 锁住行 |

**追问：RC 下 UPDATE 会看到别人刚提交的数据吗？**
→ 会。RC 的 UPDATE 在找目标行时用的是**语句开始时的快照**，但更新前会检查行的最新版本；如果被别人改过，会**重新评估 WHERE 条件**（EvalPlanQual）。这可能导致「同一语句更新了不同的行集」，是 RC 下容易忽略的语义。

## Q7. 长事务有什么危害？为什么 DBA 看到长事务会紧张？

**答：**

长事务是 PG 生产环境的**头号隐形杀手**：

| 危害 | 机制 |
|------|------|
| **阻止 VACUUM 回收** | VACUUM 只能清理「所有快照都不需要」的死元组；长事务持有的老快照会让死元组一直保留 |
| **表膨胀** | 死元组占着页，表和索引越来越大，扫描变慢 |
| **XID 老化** | 长事务让 `xmin` 一直不前进，加速接近回卷红线 |
| **锁持有时间长** | 持有的行锁/表锁不释放，阻塞其他会话，甚至引发死锁 |
| **复制延迟** | 长事务在从库上要等事务提交才能看到效果；逻辑复制还可能因超长事务卡住 |
| **DDL 无法执行** | 需要 `ACCESS EXCLUSIVE` 锁的 DDL 会排队，进而阻塞后续所有查询 |

**监控手段**：

```sql
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY duration DESC;
```

**追问：多长算长事务？**
→ 没有统一阈值。**超过几分钟的 OLTP 事务就该告警**；批处理要用「分批提交」而不是一个大事务。关键是看它是否阻碍了 VACUUM（`pg_stat_activity.backend_xmin`）。

## Q8. 什么是事务 ID 回卷（wraparound）？PG 怎么防止？

**答：**

PG 的事务 ID（XID）是 **32 位**，约 42 亿个。事务 ID 会循环复用，为了让「新事务」不被误判为「很老的事务」，PG 用**冻结（freeze）**标记「这行永远可见」。

如果不做 freeze：

```
XID 用到接近上限 → 新旧事务 ID 无法比较 → 数据可见性错乱
→ PG 为了保护数据，强制进入只读模式并停止服务
```

防护机制：

| 机制 | 说明 |
|------|------|
| **VACUUM FREEZE** | 把足够老的行标记为 frozen，视为「永久可见」 |
| **autovacuum** | 自动触发 freeze，正常情况不需要人工干预 |
| **`vacuum_freeze_min_age` / `vacuum_freeze_table_age`** | 控制 freeze 时机 |
| **监控** | `age(datfrozenxid)` 接近 `autovacuum_freeze_max_age` 要告警 |

```sql
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;
```

**追问：为什么「不做 VACUUM 会停库」？**
→ 因为 XID 用完后，PG 无法判断一行是「很久以前的事务写的」还是「刚回卷后的事务写的」。为了避免返回错误数据，它选择**拒绝写入**。这是保护机制，不是 bug。

## Q9. SERIALIZABLE 的 SSI 是什么？什么时候会报错？

**答：**

SSI（Serializable Snapshot Isolation，可串行化快照隔离）是 PG 实现 SERIALIZABLE 的机制：**在快照隔离的基础上，跟踪事务之间的读写依赖，发现「危险的执行结构」就中止其中一个事务。**

它主要防的是**写偏斜（write skew）**：

```
事务 A：查「值班医生有 2 人」→ 判断可以请假 → 把自己的值班取消
事务 B：查「值班医生有 2 人」→ 判断可以请假 → 把自己的值班取消
结果：两个人都请假，值班医生变成 0 人
```

RC/RR 都拦不住（两个事务改的是不同行），SERIALIZABLE 能。

报错形式：

```
ERROR: could not serialize access due to read/write dependencies among transactions
SQLSTATE: 40001
```

**处理方式**：**应用层重试整个事务**（不是重试单条语句），通常带指数退避。这是 SSI 的正常工作方式，不是异常。

**追问：SSI 会不会误杀？**
→ 会。它基于依赖图检测，可能中止「实际可串行化」的事务（假阳性）。所以 SERIALIZABLE 适合**冲突率低、正确性要求高**的场景；高冲突场景会频繁重试，反而拖垮吞吐。
