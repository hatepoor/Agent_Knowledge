# 原理剖析 · 可见性与事务状态

## ① 现象

- 同一行数据在 `xmin`/`xmax` 上看不懂
- `pg_stat_activity.backend_xmin` 非空,表却还在膨胀
- 出现过"database is not accepting commands to avoid wraparound"
- `VACUUM` 报告 "cannot remove N dead tuples"
- `xmax != 0` 的行仍能查到

## ② 机制

### 事务状态存放在哪里

| 结构 | 文件 | 内容 |
|------|------|------|
| `pg_xact`(旧称 CLOG) | `pg_xact/0000` 等 | 每个事务 2 bit:`IN_PROGRESS` / `COMMITTED` / `ABORTED` / `SUB_COMMITTED` |
| `pg_subtrans` | `pg_subtrans/` | 子事务 → 父事务映射 |
| `pg_multixact` | `pg_multixact/members`, `offsets` | 多事务(共享行锁) |
| `pg_commit_ts` | `pg_commit_ts/` | 提交时间戳(需 `track_commit_timestamp = on`) |

**关键点:元组头里只有 `xmin`/`xmax` 两个数字,并不包含"该事务是否提交"。** 可见性判定必须**查 `pg_xact`** 才能知道 `xmin` 是提交还是中止。

### hint bits:把结论写回元组头

每次判断可见性都去查 `pg_xact` 太慢。因此第一次查清后,把结论**写进元组头的 `t_infomask`**:

| 标志位 | 含义 |
|--------|------|
| `HEAP_XMIN_COMMITTED` | 插入事务已提交 |
| `HEAP_XMIN_INVALID` | 插入事务已中止 |
| `HEAP_XMAX_COMMITTED` | 删除事务已提交 |
| `HEAP_XMAX_INVALID` | 删除事务无效(即该版本仍有效) |
| `HEAP_XMAX_IS_MULTI` | xmax 是多事务 ID(共享锁) |

**三个必然推论**

1. **只读查询也会修改页**(设置 hint bits),产生脏页与 WAL(需保证崩溃后 hint bits 重放一致)。
2. **第一次扫描某表比后续慢** —— 需要查 `pg_xact` 并写回。
3. **`xmax != 0` 不代表行被删了**:`xmax` 可能指向一个**中止**的事务,或是一个"仅加锁"的事务。必须查状态才能判断。

### 可见性判定的完整逻辑

对某个元组 `t`,快照 `snapshot`:

**第一步:判断 `xmin`(插入是否可见)**

```
if xmin == my_xid:
    return (t.cid < snapshot.curcid)        # 本事务内,按命令顺序
elif XidInMVCCSnapshot(xmin, snapshot):
    return false                            # 快照时该事务未结束 → 不可见
elif TransactionIdDidCommit(xmin):
    return true                             # 已提交且早于快照 → 可见
else:
    return false                            # 中止 → 不可见
```

**第二步:判断 `xmax`(删除是否已生效)**

```
if xmax == InvalidTransactionId:
    return true                             # 没有删除者 → 该版本有效
if xmax == my_xid:
    # 自己也可能是"更新"或"加锁"
    if t.cid < snapshot.curcid: return false
    elif is_lock_only(xmax): return true    # 仅加锁,不是删除
    else: return false
if XidInMVCCSnapshot(xmax, snapshot):
    return true                             # 删除者未结束 → 该版本仍可见
if TransactionIdDidCommit(xmax):
    return false                            # 删除已生效
else:
    return true                             # 删除中止 → 该版本仍有效
```

> **这就是"为什么 `xmax` 非 0 的行还能看到"的答案**:`xmax` 指向的事务可能中止,或只是加了行锁(`SELECT FOR UPDATE`)。

### 四种可见性判定函数

PostgreSQL 有多个 `HeapTupleSatisfies*` 函数,对应不同场景:

| 函数 | 用途 |
|------|------|
| `HeapTupleSatisfiesMVCC` | 普通查询(最常用) |
| `HeapTupleSatisfiesNow` | 特例:`SnapshotNow` |
| `HeapTupleSatisfiesAny` | 不看可见性,只要是物理存在 |
| `HeapTupleSatisfiesDirty` | 用于索引扫描的早期过滤 |
| `HeapTupleSatisfiesVacuum` | **VACUUM 专用**,判断是否可回收/可冻结 |

`HeapTupleSatisfiesVacuum` 的四个返回值决定了 VACUUM 的动作:

| 返回值 | 含义 | VACUUM 动作 |
|--------|------|-------------|
| `HEAPTUPLE_DEAD` | 插入中止,或删除已提交且无人可见 | **回收** |
| `HEAPTUPLE_LIVE` | 有活跃快照可见 | 保留 |
| `HEAPTUPLE_RECENTLY_DEAD` | 无当前快照可见,但可能被更老的快照可见 | **保留**(这就是长事务阻塞 VACUUM 的机制) |
| `HEAPTUPLE_INSERT_IN_PROGRESS` / `DELETE_IN_PROGRESS` | 有事务正在进行 | 保留 |

> **`HEAPTUPLE_RECENTLY_DEAD` 是理解"长事务阻塞 VACUUM"的关键**:存在活跃快照,其 `xmin` 早于删除事务,所以旧版本仍可能被读到。

### 冻结与 xid 回绕

**问题**:事务 ID 是 32 位无符号整数,约 **42 亿**个后回绕。回绕后新事务的 xid 会"看起来比老事务还小",导致可见性判定彻底错乱。

**解法:冻结(freeze)**。把足够老的元组的 `xmin` 替换为特殊值 `FrozenTransactionId`(在元组头中用 `HEAP_XMIN_FROZEN` 标志表示),表示"这个版本永远可见,不需要再判断"。

| 参数 | 默认 | 作用 |
|------|------|------|
| `vacuum_freeze_min_age` | 50,000,000 | 超过此年龄的元组才考虑冻结 |
| `vacuum_freeze_table_age` | 150,000,000 | 超过此年龄触发全表扫描式 VACUUM |
| `autovacuum_freeze_max_age` | 200,000,000 | 强制 autovacuum(即使已禁用) |

```sql
-- 监控:年龄越接近 20 亿越危险
SELECT datname, age(datfrozenxid) AS xid_age,
       round(100.0 * age(datfrozenxid) / 2000000000, 2) AS pct_to_wraparound
FROM pg_database ORDER BY 2 DESC;

SELECT relname, age(relfrozenxid) AS age
FROM pg_class WHERE relkind = 'r'
ORDER BY age DESC LIMIT 10;
```

> **PG18 起**:`initdb` 默认启用数据校验和;`VACUUM`/`ANALYZE` 默认处理继承子分区。这些不影响冻结机制,但影响运维脚本的预期行为。

**回绕防护的极端后果**:若年龄逼近 20 亿,PostgreSQL 会**拒绝新事务**,并在日志中反复警告:

```
WARNING: database "x" must be vacuumed within 1000000 transactions
ERROR:   database is not accepting commands to avoid wraparound data loss in database "x"
HINT:    Stop the postmaster and vacuum that database in single-user mode.
```

这是**生产事故级**状态,唯一恢复手段是停机并以单用户模式 VACUUM。

### 子事务与 xid 消耗

- 每个 `SAVEPOINT` 会分配一个**子事务 xid**。
- PL/pgSQL 的 `EXCEPTION` 块**隐式创建子事务**。
- 子事务映射存于 `pg_subtrans`,过多会加速 xid 消耗。

```sql
-- 观察子事务与多事务
SELECT * FROM pg_stat_activity WHERE backend_xid IS NOT NULL;
SHOW max_locks_per_transaction;      -- PG19 默认由 64 改为 128
```

## ④ 实验验证

### 实验 1:看到 xmax 指向中止的事务

```sql
DROP TABLE IF EXISTS vis_demo;
CREATE TABLE vis_demo (id int, v text);
INSERT INTO vis_demo VALUES (1, 'a');

-- 会话 A:开始一个事务并更新但不提交
BEGIN;
UPDATE vis_demo SET v = 'A' WHERE id = 1;
SELECT txid_current();     -- 记下这个 xid,例如 2000

-- 会话 B
SELECT ctid, xmin, xmax, v FROM vis_demo;
-- 看到的是旧版本:v='a',xmax=2000
-- 说明:即使 xmax != 0,旧版本仍可见(因为 2000 未提交)

-- 会话 A:回滚
ROLLBACK;

-- 会话 B
SELECT ctid, xmin, xmax, v FROM vis_demo;
-- xmax 仍可能是 2000,但 v='a' 仍可见!
-- 因为 2000 已中止 → 删除无效
```

**这是"xmax 非 0 不代表被删除"最直接的证明。**

### 实验 2:验证 hint bits 导致只读查询写页

```sql
-- 先找出未设置 hint bits 的页
SELECT blkno, lp, t_infomask
FROM generate_series(0, 10) AS blkno,
     LATERAL heap_page_items(get_raw_page('vis_demo', blkno)) AS t(lp)
LIMIT 10;

-- 触发一次扫描
SELECT count(*) FROM vis_demo;

-- 再看 t_infomask,应已包含 HEAP_XMIN_COMMITTED 位
SELECT blkno, lp, t_infomask
FROM generate_series(0, 10) AS blkno,
     LATERAL heap_page_items(get_raw_page('vis_demo', blkno)) AS t(lp)
LIMIT 10;
```

### 实验 3:观察 RECENTLY_DEAD 与长事务

```sql
DROP TABLE IF EXISTS recent_demo;
CREATE TABLE recent_demo AS SELECT g AS id FROM generate_series(1, 10000) g;

-- 会话 A(保持长事务)
BEGIN;
SELECT count(*) FROM recent_demo;

-- 会话 B:新版 VACUUM 支持 VERBOSE 详细报告
UPDATE recent_demo SET id = id + 1;
VACUUM (VERBOSE) recent_demo;
-- 观察输出中关于 "cannot remove" 或可移除数量的信息

-- 会话 A:COMMIT 后,会话 B 再执行
VACUUM (VERBOSE) recent_demo;
-- 可移除数量应显著增加
```

### 实验 4:检查冻结状态

```sql
-- 查看表的冻结情况
SELECT relname,
       age(relfrozenxid) AS xid_age,
       pg_size_pretty(pg_relation_size(oid)) AS size
FROM pg_class WHERE relkind='r' AND relnamespace = 'public'::regnamespace
ORDER BY age(relfrozenxid) DESC;

-- 手工触发冻结式 VACUUM
VACUUM (FREEZE, VERBOSE) recent_demo;
```

### 实验 5:观察子事务消耗

```sql
-- 大量 SAVEPOINT 会消耗 xid
BEGIN;
DO $$
BEGIN
    FOR i IN 1..1000 LOOP
        BEGIN
            -- 每个 EXCEPTION 块创建一个子事务
            PERFORM 1/0;
        EXCEPTION WHEN division_by_zero THEN NULL;
        END;
    END LOOP;
END $$;
COMMIT;

-- 观察 xid 增长速度
SELECT txid_current();
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 元组头不含提交状态 | 可见性判定依赖 `pg_xact`;hint bits 是性能关键 |
| `xmax != 0` 不代表删除 | 排查时不要仅凭 `xmax` 判断行是否"过期" |
| `RECENTLY_DEAD` 保护旧版本 | **长事务与长快照阻塞 VACUUM**;必须治理 |
| 冻结是回绕防护 | 监控 `age(datfrozenxid)`,保持 autovacuum 正常 |
| 子事务消耗 xid | 避免在循环中使用 `EXCEPTION`(见 PL/pgSQL 篇) |
| 只读查询会写 WAL | 复制与 I/O 规划需考虑 |

```sql
-- 三个必配监控
-- 1) 长事务
SELECT pid, xact_start, now()-xact_start AS age, left(query,50)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 10;

-- 2) 回绕风险
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- 3) 膨胀与死元组
SELECT relname, n_dead_tup, n_live_tup,
       round(100.0*n_dead_tup/nullif(n_live_tup+n_dead_tup,0),1) AS dead_pct,
       last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
```

**VACUUM 受阻的排查路径**

```
表在膨胀 / VACUUM 清不掉死元组
   │
   ├─ 有长事务?→ pg_stat_activity 查 xact_start
   ├─ 有空闲事务?→ state = 'idle in transaction'
   ├─ 有活跃复制槽?→ pg_replication_slots.active = false 会 hold xmin
   ├─ 有备库反馈?→ hot_standby_feedback = on 让备库的 xmin 拖住主库
   ├─ 有并行 worker 未结束?→ 查 parallel workers
   └─ autovacuum 被禁用 / 被 `autovacuum_enabled=false` 关掉?
```
