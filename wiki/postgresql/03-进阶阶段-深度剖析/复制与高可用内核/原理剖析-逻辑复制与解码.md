# 原理剖析 · 逻辑复制与解码

## ① 现象

- 逻辑复制延迟很大,且与事务大小相关
- 订阅端出现主键冲突或 `could not serialize`
- 升级期间序列值不同步导致主键冲突
- 逻辑复制槽占用大量 WAL 且 `active = false`
- DDL 在订阅端不存在,导致复制中断

## ② 机制

### 与物理复制的本质区别

| 维度 | 物理复制 | 逻辑复制 |
|------|----------|----------|
| 复制内容 | **WAL 记录(页级物理变更)** | **行级逻辑变更**(INSERT/UPDATE/DELETE) |
| 解码时机 | 不需要,直接重放 | 需**逻辑解码**把 WAL 转成逻辑变更 |
| 粒度 | 实例级(全库) | 表级 / 行级 / 列级 |
| 大版本 | 必须相同 | **可跨大版本** |
| 架构 | 必须相同 | 可跨平台 |
| DDL | 自动跟随 | **不复制** |
| 备库可写 | ❌(只读) | ✅(但需处理冲突) |
| 用途 | 高可用、只读扩展 | 版本升级、数据分发、异构集成 |

### 逻辑解码的原理

**关键洞察**:WAL 中的物理变更记录里**包含了足够的信息**来重建逻辑变更(哪些行、哪些列变了)。逻辑解码就是"把 WAL 翻译回逻辑操作"。

```
主库产生 WAL(包含 Heap INSERT/UPDATE/DELETE 记录)
        ↓
逻辑解码插件读取 WAL
        ↓
输出逻辑变更(旧元组 / 新元组)
        ↓
通过复制槽 + walsender 发送给订阅端
        ↓
订阅端执行等价的行级 DML
```

**"旧元组"从哪来?**

UPDATE/DELETE 的记录里若只含新元组,订阅端就不知道要修改哪一行。因此需要**复制标识(REPLICA IDENTITY)**:

| 设置 | 提供的"旧值" |
|------|--------------|
| `DEFAULT` | 主键列(表必须有主键) |
| `USING INDEX idx` | 指定唯一索引的列 |
| `FULL` | 整行所有列(代价高,但无需主键) |
| `NOTHING` | 无旧值(仅支持 INSERT) |

```sql
ALTER TABLE t REPLICA IDENTITY FULL;
ALTER TABLE t REPLICA IDENTITY USING INDEX t_uk;
```

> **无主键表是逻辑复制的常见坑**:必须显式设置 `REPLICA IDENTITY`,否则 `UPDATE`/`DELETE` 会报错。

### 解码插件的输出格式

| 插件 | 用途 |
|------|------|
| `pgoutput` | **内置**,发布/订阅使用 |
| `test_decoding` | 调试用,输出人类可读文本 |
| `wal2json` | 输出 JSON(第三方,常用于 CDC 到 Kafka) |
| `decoderbufs` | Protobuf(第三方,Debezium 生态) |

```sql
-- 用 test_decoding 直接观察解码输出
SELECT * FROM pg_create_logical_replication_slot('demo_slot', 'test_decoding');

-- 做一些变更
CREATE TABLE dec_demo (id int PRIMARY KEY, v text);
INSERT INTO dec_demo VALUES (1, 'a');
UPDATE dec_demo SET v = 'b' WHERE id = 1;
DELETE FROM dec_demo WHERE id = 1;

-- 读取解码结果
SELECT * FROM pg_logical_slot_get_changes('demo_slot', NULL, NULL);
-- 输出形如:
-- BEGIN 1000
-- table public.dec_demo: INSERT: id[integer]:1 v[text]:'a'
-- table public.dec_demo: UPDATE: id[integer]:1 v[text]:'b'
-- table public.dec_demo: DELETE: id[integer]:1
-- COMMIT 1000

SELECT pg_drop_replication_slot('demo_slot');
```

> `pg_logical_slot_get_changes` **消费**(移除)变更;`pg_logical_slot_peek_changes` 只读不移除。

### 发布与订阅

**发布端(Publisher)**

```sql
-- wal_level 必须为 logical(需重启)
-- SHOW wal_level;

CREATE PUBLICATION pub_all FOR ALL TABLES;
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
CREATE PUBLICATION pub_filtered FOR TABLE orders WHERE (status <> 'canceled');   -- PG15+
CREATE PUBLICATION pub_cols FOR TABLE orders (id, user_id, total);               -- PG15+ 列列表

-- 后期增删表
ALTER PUBLICATION pub_orders ADD TABLE shipments;
ALTER PUBLICATION pub_orders SET TABLE orders, order_items;

-- 查看
SELECT * FROM pg_publication;
SELECT * FROM pg_publication_tables;
SELECT * FROM pg_publication_rel;
```

**订阅端(Subscriber)**

```sql
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=primary port=5432 dbname=app user=repl password=secret'
    PUBLICATION pub_orders
    WITH (copy_data = true);     -- 初始是否全量同步

-- 查看与监控
SELECT * FROM pg_subscription;
SELECT * FROM pg_stat_subscription;
SELECT * FROM pg_subscription_rel;   -- 每张表的同步状态

-- 暂停/恢复
ALTER SUBSCRIPTION sub_orders DISABLE;
ALTER SUBSCRIPTION sub_orders ENABLE;
ALTER SUBSCRIPTION sub_orders REFRESH PUBLICATION;   -- 重新拉取发布端表列表
ALTER SUBSCRIPTION sub_orders SET PUBLICATION pub_orders, pub_other;
```

**创建订阅会自动创建逻辑复制槽**(在发布端)。`DROP SUBSCRIPTION` 默认也会删槽(若发布端不可达会失败)。

### 初始数据同步(copy_data)

```
CREATE SUBSCRIPTION ... WITH (copy_data = true)
        ↓
① 创建复制槽(捕获此后的变更)
② 对每张表做快照并 COPY 到订阅端(初始同步)
③ 快照后开始应用增量变更
        ↓
期间所有变更都被槽捕获,不会丢失
```

| 场景 | `copy_data` |
|------|-------------|
| 新建订阅,订阅端为空 | `true`(默认) |
| 已有数据(如从 `pg_dump` 导入) | `false`(避免冲突) |
| 大表 | 考虑 `false` + 手工导入(更可控) |

### 延迟的来源

| 来源 | 说明 |
|------|------|
| **大事务** | 逻辑解码**不能在事务中间输出**(否则订阅端会看到不一致状态),必须等事务提交后整体发送 |
| 网络 | 跨地域传输 |
| 订阅端写入慢 | 索引多、触发器多 |
| 主键冲突 | 订阅端有独立写入 → 冲突处理耗时 |
| 解码 CPU | 高变更量下解码是 CPU 密集 |

> **大事务是逻辑复制的头号敌人**:一个更新 500 万行的事务,必须在主库提交后才开始传输 → 延迟可能达数分钟。**升级切换前必须避免大事务。**

### 冲突处理

订阅端若同时接受其他写入,可能产生冲突:

| 冲突 | 表现 | 处理 |
|------|------|------|
| 主键/唯一冲突 | `duplicate key value violates unique constraint` | 默认**报错并停止应用** → 需人工介入 |
| 唯一索引冲突 | 同上 | |
| 外键冲突 | 引用行不存在 | |
| 行已被删除 | `UPDATE`/`DELETE` 未命中 | 通常无害 |

```sql
-- PG15+ 可配置跳过某些错误
ALTER SUBSCRIPTION sub_orders SET (disable_on_error = false);

-- 查看冲突统计(PG16+ 在 pg_stat_subscription_stats 中)
SELECT * FROM pg_stat_subscription_stats;
-- 关注 conflict_count、apply_error_count
```

**冲突的根本规避**:让订阅端**只接受复制写入**(不做独立写入)。这也是升级场景的推荐做法。

### 版本演进要点

| 版本 | 逻辑复制改进 |
|------|--------------|
| PG10 | 逻辑复制引入 |
| PG11 | `TRUNCATE` 复制;初始同步增强 |
| PG14 | 大事务流式传输(减少内存) |
| PG15 | **行过滤**(`WHERE`)与**列列表**;冲突可跳过 |
| PG16 | 订阅端并行应用;`pg_stat_subscription_stats` |
| PG17 | `pg_createsubscriber`(从物理副本快速创建逻辑订阅) |
| **PG18** | **支持从物理备库作为发布源**;`pg_subscription_check` 校验数据一致性 |
| **PG19** | **支持复制序列值**;`wal_level = replica` 下可动态启用逻辑复制(无需重启) |

> **PG18 的重要实践价值**:可以从备库做逻辑复制源,减轻主库负载。**PG19 的"复制序列值"**解决了长期存在的"升级后序列不同步"痛点。

### 逻辑复制槽与 WAL 保留

逻辑复制槽会保留"尚未被消费的 WAL",且**比物理槽更危险**:

| 差异 | 物理槽 | 逻辑槽 |
|------|--------|--------|
| 是否需要解码 | 否 | **是**(需读 WAL 解码) |
| WAL 保留依据 | `restart_lsn` | `restart_lsn` + `catalog_xmin` |
| 权限 | — | 还需保留系统目录信息(`catalog_xmin`) |
| 最大保留量 | 无上限 | `max_slot_wal_keep_size` |

```sql
SHOW max_slot_wal_keep_size;   -- 默认 -1(无限制!)
-- 建议设为有限值,避免磁盘写满

SELECT slot_name, slot_type, active, restart_lsn, confirmed_flush_lsn,
       catalog_xmin, pg_size_pretty(
           pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots WHERE slot_type = 'logical';
```

> **`catalog_xmin` 的存在使逻辑槽更"阻塞"**:它会让主库保留必要的系统目录版本,因此**逻辑复制槽长期不活跃会比物理槽更快地造成膨胀与 WAL 堆积**。

## ④ 实验验证

### 实验 1:用 test_decoding 直接看解码输出

```sql
ALTER SYSTEM SET wal_level = 'logical';
-- 重启实例
-- docker restart pg18

SHOW wal_level;

SELECT * FROM pg_create_logical_replication_slot('s1', 'test_decoding');

CREATE TABLE ld_demo (id int PRIMARY KEY, v text);
INSERT INTO ld_demo VALUES (1, 'a'), (2, 'b');
UPDATE ld_demo SET v = 'c' WHERE id = 1;
DELETE FROM ld_demo WHERE id = 2;
ALTER TABLE ld_demo ADD COLUMN extra int;
UPDATE ld_demo SET extra = 9 WHERE id = 1;

SELECT * FROM pg_logical_slot_peek_changes('s1', NULL, NULL);
-- 观察输出:BEGIN / table ... INSERT|UPDATE|DELETE / COMMIT
-- 注意 UPDATE 会同时给出旧值与新值(依赖 REPLICA IDENTITY)

SELECT pg_drop_replication_slot('s1');
```

### 实验 2:验证 REPLICA IDENTITY 的作用

```sql
-- 无主键表
CREATE TABLE no_pk (a int, b text);
ALTER TABLE no_pk REPLICA IDENTITY DEFAULT;   -- 默认但无主键
-- 逻辑复制中对该表的 UPDATE/DELETE 会报错

-- 改为 FULL
ALTER TABLE no_pk REPLICA IDENTITY FULL;
-- 现在解码输出会包含整行的旧值
```

```sql
SELECT * FROM pg_create_logical_replication_slot('s2', 'test_decoding');
INSERT INTO no_pk VALUES (1,'x');
UPDATE no_pk SET b='y' WHERE a=1;
SELECT * FROM pg_logical_slot_peek_changes('s2', NULL, NULL);
-- FULL 模式下 UPDATE 会带出旧元组的所有列
SELECT pg_drop_replication_slot('s2');
```

### 实验 3:搭一个最简发布订阅

```bash
# 发布端(主库,5432):wal_level = logical 已设
docker exec pg18 psql -U postgres -c "
CREATE ROLE lrepl WITH REPLICATION LOGIN PASSWORD 'lrepl';
ALTER ROLE lrepl WITH SUPERUSER;   -- 实验用;生产按需
"
docker exec pg18 psql -U postgres -c "
CREATE TABLE IF NOT EXISTS pub_demo (id int PRIMARY KEY, v text);
INSERT INTO pub_demo SELECT g, 'v'||g FROM generate_series(1,100) g;
CREATE PUBLICATION pub_demo_pub FOR TABLE pub_demo;
"
docker exec pg18 bash -c 'echo "host replication lrepl 0.0.0.0/0 scram-sha-256" >> $PGDATA/pg_hba.conf'
docker exec pg18 psql -U postgres -c "SELECT pg_reload_conf();"

# 订阅端(备库实例,5433)
docker exec pg18 psql -U postgres -p 5433 -c "
CREATE TABLE pub_demo (id int PRIMARY KEY, v text);   -- 结构需已存在
CREATE SUBSCRIPTION sub_demo
  CONNECTION 'host=localhost port=5432 dbname=postgres user=lrepl password=lrepl'
  PUBLICATION pub_demo_pub;
"
```

```sql
-- 验证初始同步
-- 订阅端
SELECT count(*) FROM pub_demo;      -- 100

-- 发布端:增量变更
INSERT INTO pub_demo VALUES (101, 'new');
UPDATE pub_demo SET v='changed' WHERE id=1;
DELETE FROM pub_demo WHERE id=2;

-- 订阅端:应已同步
SELECT count(*) FROM pub_demo;      -- 100 (101 加、2 删)
SELECT * FROM pub_demo WHERE id=1;  -- changed

-- 监控
SELECT * FROM pg_stat_subscription;
```

### 实验 5:验证序列不复制(PG19 前的痛点)

```sql
-- 发布端
CREATE TABLE seq_demo (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, v text);
CREATE PUBLICATION pub_seq FOR TABLE seq_demo;

-- 订阅端
CREATE TABLE seq_demo (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, v text);
CREATE SUBSCRIPTION sub_seq CONNECTION '...' PUBLICATION pub_seq;

-- 发布端插入若干行
INSERT INTO seq_demo (v) SELECT 'x' FROM generate_series(1, 10);

-- 订阅端:数据同步了,但序列值仍是 1!
SELECT count(*) FROM seq_demo;                    -- 10
SELECT last_value FROM seq_demo_id_seq;           -- 1  ← 未同步

-- 订阅端若要写入会主键冲突
-- 手工修正(PG19 前必须做)
SELECT setval('seq_demo_id_seq', (SELECT max(id) FROM seq_demo));
```

> **PG19 起逻辑复制支持复制序列值**,这个手工步骤将不再必需。

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 逻辑复制不复制 DDL | **两端必须同步执行 DDL**(或用工具如 `pglogical`、自研分发) |
| 无主键表需 `REPLICA IDENTITY` | 否则 UPDATE/DELETE 无法复制;优先保证有主键 |
| 大事务造成长延迟 | 升级/迁移前避免大事务;必要时拆分 |
| 序列需手工同步(PG19 前) | **切换前必须 `setval`**,否则主键冲突 |
| 逻辑槽比物理槽更危险 | 设 `max_slot_wal_keep_size`;必须监控 `retained` + `catalog_xmin` |
| 订阅端应只接受复制写入 | 避免冲突;需要读写双活时用专业方案(如 `pglogical`/BDR) |
| 冲突默认会停止应用 | 关注 `pg_stat_subscription_stats`;评估是否 `disable_on_error = false` |
| PG18+ 可从备库做发布源 | 减轻主库负载,适合"主库已经很忙"的场景 |
| 升级场景是核心用途 | 近零停机跨大版本升级的标准方案 |

```sql
-- 逻辑复制健康监控(发布端)
SELECT slot_name, active, restart_lsn, catalog_xmin,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots WHERE slot_type = 'logical';

-- 订阅端监控
SELECT subname, pid, relid::regclass, received_lsn, latest_end_lsn,
       last_msg_receipt_time, latest_end_time
FROM pg_stat_subscription;

-- 每张表的同步状态
SELECT srsubid, srrelid::regclass, srsubstate, srsublsn FROM pg_subscription_rel;
-- srsubstate: i=initialize, d=data copy, f=finished copy, s=synchronized, r=ready

-- 冲突统计(PG16+)
SELECT * FROM pg_stat_subscription_stats;
```

> **`pg_subscription_rel.srsubstate = 'r'` 才表示该表已完全同步。** 升级切换前必须确认所有表都到了 `r`(ready)。
