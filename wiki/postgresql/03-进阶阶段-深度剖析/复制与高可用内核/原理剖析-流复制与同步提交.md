# 原理剖析 · 流复制与同步提交

## ① 现象

- `pg_stat_replication` 里 `replay_lag` 持续增长
- 主库磁盘被 `pg_wal` 撑满(复制槽未消费)
- 切换后发现丢了最近几秒的数据
- 备库长查询报 `canceling statement due to conflict with recovery`
- 主库写入变慢,原因是同步备库变慢

## ② 机制

### 流复制的本质:传输 WAL

流复制**不需要单独的数据同步协议**。它的全部内容就是:

```
主库(Primary)                              备库(Standby)
  写 WAL                                      walreceiver 接收
    ↓                                              ↓
  walsender 读取 WAL 并发送 ───网络───►     写入本地 WAL 文件
                                                   ↓
                                          startup 进程重放(replay)
                                                   ↓
                                          数据页被更新(备库只读可查)
```

| 进程 | 角色 |
|------|------|
| `walsender` | 主库侧,读 WAL 并发送(**每连接一个**) |
| `walreceiver` | 备库侧,接收并写入本地 WAL |
| `startup` | 备库侧,重放 WAL(PG15 起独立进程;此前由 startup 兼任恢复) |

**为什么这是"物理复制"**:

- 复制的是**页级别的物理变更**(WAL 记录),不是逻辑行变更
- 要求主备**架构、大版本、页大小、校验和设置一致**
- 备库是主库的**字节级副本**

### 三个 LSN:复制进度的度量

```
主库                                             备库
─────────────────────────────────────────────────────────
sent_lsn      ← 已发送到网络的 WAL 位置
write_lsn     ← 备库已写入本地 WAL 文件(接收确认)
flush_lsn     ← 备库已 fsync 到磁盘
replay_lsn    ← 备库已重放到数据页          ← 真正的"数据可见"位置

主库当前                  ────────────────────►
pg_current_wal_lsn()
```

```sql
-- 主库视角:每个备库的进度
SELECT
    pid, usename, application_name, client_addr, state, sync_state,
    sent_lsn, write_lsn, flush_lsn, replay_lsn,
    pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn))     AS total_lag,
    pg_size_pretty(pg_wal_lsn_diff(sent_lsn, write_lsn))      AS network_lag,
    write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- 备库视角
SELECT status, receive_start_lsn, received_lsn,
       last_msg_receipt_time, latest_end_lsn, latest_end_time
FROM pg_stat_wal_receiver;

SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

**延迟的分类与含义**

| 指标 | 含义 | 高值说明 |
|------|------|----------|
| `sent_lsn` 落后 | 主库来不及发(WAL 生成速率高/网络慢) | 网络带宽不足 |
| `write_lsn` / `flush_lsn` 落后 | 备库写入慢 | 备库磁盘慢 |
| `replay_lsn` 落后 | 备库重放慢 | 备库 CPU/磁盘瓶颈,或**长事务阻塞重放** |

### 复制槽(replication slot)

**问题**:`wal_keep_size` 只能粗放保留;若备库断连太久,主库会回收它所需的 WAL → 备库无法追上。

**解法**:复制槽让主库**精确知道**每个备库需要从哪里开始,从而不会回收那段 WAL。

```sql
-- 物理复制槽
SELECT pg_create_physical_replication_slot('standby1');
SELECT pg_create_physical_replication_slot('standby1', true);   -- immediate_reserve_wal

-- 查看与监控
SELECT slot_name, slot_type, active, restart_lsn, confirmed_flush_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;

-- 删除
SELECT pg_drop_replication_slot('standby1');
```

> **复制槽是高危对象**:若备库下线且槽未删除,主库会**永远保留**那段 WAL,直到磁盘写满。**必须监控 `pg_replication_slots` 的 `retained_wal` 与 `active`。**

```sql
-- 找出非活跃且占用大量 WAL 的槽
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots
WHERE NOT active
ORDER BY pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) DESC;
```

### 同步提交与仲裁

**同步复制**:主库提交时,必须等同步备库确认后才返回成功。

```ini
# postgresql.conf(主库)
synchronous_standby_names = 'standby1'              # 指定一个
synchronous_standby_names = 'FIRST 2 (s1, s2, s3)'  # 前 2 个
synchronous_standby_names = 'ANY 2 (s1, s2, s3)'    # 任意 2 个确认(PG10+ 仲裁提交)
synchronous_commit = 'on'
```

**`synchronous_standby_names` 语法**

| 形式 | 语义 |
|------|------|
| `'s1'` | 必须 s1 确认 |
| `'FIRST 2 (s1,s2,s3)'` | 按列表顺序取前 2 个可用的,它们必须确认 |
| `'ANY 2 (s1,s2,s3)'` | 三者中任意 2 个确认即可(**仲裁提交**) |
| `'*'` | 所有备库 |

**`ANY` 形式的意义**:避免"同步备库挂掉则主库不可写"的可用性问题。只要多数备份在线即可写入。

**同步粒度:由 `synchronous_commit` 决定**

```
主库提交 ───► WAL 写入本地 ───► 发送给同步备库
                                  │
                ┌─────────────────┼─────────────────┬──────────────┐
                │                 │                 │              │
      local:本地落盘即返回   on:备库写入WAL   remote_write:    remote_apply:
                                  (未fsync)     备库OS缓存      备库已重放
                │                 │                 │              │
             最宽松            默认             更弱于on        最强(可读一致)
```

| 值 | 主库返回条件 | 主库崩溃 | 备库 OS 崩溃 | 延迟 |
|----|-------------|----------|--------------|------|
| `off` | 不等本地刷盘 | 可丢 | 可丢 | 最低 |
| `local` | 本地刷盘 | 不丢 | 可丢 | 低 |
| `on`(默认) | 本地刷盘 + 同步备库写入 | 不丢 | 可能丢 | 中 |
| `remote_write` | 备库写入 OS 缓存 | 不丢 | 可丢 | 中 |
| `remote_apply` | 备库已重放 | 不丢 | 不丢 | **最高** |

> **`remote_apply` 的额外价值**:它保证"提交成功后,在备库上能立即读到该数据",即**读己之写(read-your-writes)** 语义。适合"写主库、读备库"的架构。

**可用性陷阱**:若设了 `synchronous_standby_names` 但同步备库全部下线,主库会**阻塞所有写操作**。**这是最常见的同步复制事故。**

```sql
-- 应急:临时取消同步要求
ALTER SYSTEM SET synchronous_standby_names = '';
SELECT pg_reload_conf();
```

### 备库的只读查询与冲突

备库上可以执行只读查询(`hot_standby = on`),但会与重放产生冲突:

| 冲突类型 | 说明 |
|----------|------|
| **锁冲突** | 备库查询持有锁,WAL 重放需升级锁(如 DDL)→ 备库取消查询 |
| **清理冲突** | 重放 VACUUM 记录要移除查询仍需要的行版本 → 冲突 |
| 缓冲区 pin | 重放需修改被查询 pin 住的页 → 冲突 |

**解决参数**

```ini
max_standby_streaming_delay = 30s    # 允许重放缓多久
max_standby_archive_delay = 30s
hot_standby_feedback = off           # 是否向主库反馈
```

| 参数 | 效果 | 代价 |
|------|------|------|
| 增大 `max_standby_*_delay` | 减少查询被取消的概率 | 复制延迟增大 |
| `hot_standby_feedback = on` | 主库知道备库的 `xmin`,不清理备库仍需的行版本 → 减少冲突 | **延迟主库 VACUUM,可能造成主库膨胀** |

> **这是一个真实的两难**:`hot_standby_feedback = on` 把备库的"长查询"变成了主库的"长事务",从而阻塞主库 VACUUM。决策依据是"备库长查询的价值"与"主库膨胀的容忍度"。

### 故障转移与提升

```bash
# 手工提升备库为主库
pg_ctl promote -D $PGDATA
# 或
SELECT pg_promote();

# 检查状态
SELECT pg_is_in_recovery();    -- false 表示已是主库
```

**提升后的关键问题**:原主库若恢复上线,会成为"有分歧的时间线" → 必须重建(`pg_rewind` 或重新做基础备份)。

```bash
# pg_rewind:把旧主库"回滚"到与新主库的分歧点,避免完整重建
pg_rewind --target-pgdata=/var/lib/postgresql/data \
          --source-server="host=newprimary ..."
```

**自动故障转移必须用仲裁工具**(Patroni / repmgr / pg_auto_failover),**不要自行编写脚本** —— 脑裂的代价远大于短暂停机。

### 级联复制

```
Primary
   ├──► Standby1  ──► Standby2   (Standby2 从 Standby1 拉 WAL)
   └──► Standby3
```

减轻主库的 walsender 与网络压力。配置:`Standby2` 的 `primary_conninfo` 指向 `Standby1`,且 `Standby1` 需 `hot_standby = on`。

## ④ 实验验证

### 实验 1:搭一个最简流复制(单机双实例)

```bash
# 1) 在主库创建复制用户
docker exec pg18 psql -U postgres -c "CREATE ROLE repl WITH REPLICATION LOGIN PASSWORD 'repl';"

# 2) 配置主库
docker exec pg18 psql -U postgres <<'SQL'
ALTER SYSTEM SET wal_level = 'replica';
ALTER SYSTEM SET max_wal_senders = 10;
ALTER SYSTEM SET hot_standby = on;
SQL
docker exec pg18 psql -U postgres -c "SELECT pg_reload_conf();"
# wal_level 改动需重启
docker restart pg18

# 3) pg_hba 允许复制连接
docker exec pg18 bash -c 'echo "host replication repl 0.0.0.0/0 scram-sha-256" >> $PGDATA/pg_hba.conf'
docker exec pg18 psql -U postgres -c "SELECT pg_reload_conf();"

# 4) 创建复制槽
docker exec pg18 psql -U postgres -c "SELECT pg_create_physical_replication_slot('standby1');"

# 5) 做基础备份到备库目录
docker exec pg18 bash -c "pg_basebackup -h localhost -U repl -D /tmp/standby -Fp -Xs -P -R -S standby1"

# 6) 启动备库(不同端口)
docker exec pg18 bash -c "echo 'port=5433' >> /tmp/standby/postgresql.conf"
docker exec pg18 bash -c "echo 'hot_standby=on' >> /tmp/standby/postgresql.conf"
docker exec pg18 bash -c "touch /tmp/standby/standby.signal"
docker exec -d pg18 bash -c "pg_ctl start -D /tmp/standby -l /tmp/standby.log"

# 7) 验证
docker exec pg18 psql -U postgres -p 5433 -c "SELECT pg_is_in_recovery();"   # t
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 流复制传的是 WAL | 主备必须同架大版本、页大小、校验和设置 |
| 复制槽防 WAL 被回收 | **必须监控残留量**;下线备库要删槽 |
| 同步复制有可用性风险 | 用 `ANY n (...)` 仲裁提交;准备应急预案(清空 `synchronous_standby_names`) |
| `remote_apply` 给读己之写 | "写主读备"架构需要它 |
| 备库长查询与复制冲突 | `max_standby_streaming_delay` 与 `hot_standby_feedback` 之间权衡(后者会拖慢主库 VACUUM) |
| 自动切换必须用仲裁 | Patroni / repmgr,不要自研脚本 |
| 提升后旧主库需 `pg_rewind` | 否则必须完整重建 |
| 复制延迟要端到端监控 | 同时看主库 `pg_stat_replication` 与备库 `pg_last_xact_replay_timestamp()` |

```sql
-- 复制健康监控(主库)
SELECT application_name, client_addr, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS lag_bytes,
       replay_lag
FROM pg_stat_replication;

-- 槽健康监控
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots ORDER BY 3 DESC;

-- 备库健康监控
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay,
       pg_is_in_recovery();
```
