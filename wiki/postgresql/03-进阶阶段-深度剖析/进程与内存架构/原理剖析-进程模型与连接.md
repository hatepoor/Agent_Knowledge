# 原理剖析 · 进程模型与连接

## ① 现象

- 连接数一高,数据库就卡,甚至拒绝新连接
- 空闲连接也占用内存,连接池之后内存明显下降
- `pg_stat_activity` 里看到大量 `idle` 或 `idle in transaction`
- 一个查询卡住,其他查询照常运行(而非全部阻塞)

这些现象的根源都在**多进程模型**。

## ② 机制

PostgreSQL 使用**多进程(pre-fork / fork-per-connection)架构**,而不是多线程。

```
                    ┌─────────────────────┐
                    │  postmaster(主进程)  │  监听端口、fork 子进程、崩溃重启
                    └──────────┬──────────┘
                               │ fork
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
   ┌────▼────┐            ┌────▼────┐            ┌────▼────┐
   │ backend │            │ backend │            │ backend │   每个客户端连接一个
   │ (会话1)  │            │ (会话2)  │            │ (会话3)  │   独立进程
   └────┬────┘            └────┬────┘            └────┬────┘
        │                      │                      │
        └──────────────────────┼──────────────────────┘
                               │
                    ┌──────────▼──────────┐
                    │   共享内存           │ shared_buffers / WAL buffer
                    │                     │ 锁表 / ProcArray / CLOG ...
                    └──────────┬──────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
   ┌────▼─────┐  ┌────▼──────┐  ┌────▼───────┐  ┌────▼──────────┐
   │bgwriter  │  │checkpointer│  │walwriter   │  │autovacuum     │
   │          │  │            │  │            │  │launcher +     │
   └──────────┘  └────────────┘  └────────────┘  │workers        │
                                                 └───────────────┘
   其他辅助进程:walwriter、stats 相关、walsender、walreceiver、
                logical replication launcher、archiver、startup(PG15+)
```

### 三类进程

| 类别 | 进程 | 职责 |
|------|------|------|
| **主进程** | `postmaster` | 监听、fork、异常时重启整个实例(崩溃恢复) |
| **后端进程** | `backend`(每连接一个) | 执行该会话的 SQL |
| **辅助进程** | `checkpointer` | 定期做检查点 |
| | `bgwriter` | 后台刷脏页,平滑 I/O |
| | `walwriter` | 定期把 WAL buffer 刷到 WAL 文件 |
| | `autovacuum launcher` + `worker` | 自动清理 |
| | `walsender` / `walreceiver` | 流复制发送/接收 |
| | `logical replication launcher` | 逻辑复制 |
| | `archiver` | WAL 归档 |
| | `startup`(PG15+) | 备库重放;主库崩溃恢复 |

> **PG15 重要变更**:统计收集器(stats collector)被移除,统计信息改存于**共享内存**,这使 `pg_stat_*` 视图的更新延迟显著降低。

### 必然结论

1. **每连接一个进程 → 每连接有固定内存开销**。即使空闲,也占用 `work_mem` 之外的基础内存(数 MB 级的进程开销)。
2. **切换上下文成本高**:进程切换比线程切换贵,跨进程通信要走共享内存。
3. **没有"共享的执行状态"**:各后端各自持有自己的快照、执行状态,通过共享内存协调(这正是 MVCC 的基础)。
4. **进程隔离带来健壮性**:一个后端崩溃不会直接拖垮其他后端(但 postmaster 会重启整个实例)。

### 连接成本量化

```sql
-- 查看后端进程的平均内存占用(近似)
SELECT
    count(*) AS backends,
    pg_size_pretty(sum(pg_backend_memory_contexts.total_bytes)) AS total_mem
FROM pg_stat_activity a, LATERAL pg_backend_memory_contexts() ;   -- 需 PG12+
```

实际经验值:每个后端即使空闲也约占 **5~15MB** 常驻内存(随配置与版本变化),加上 `work_mem` 等按需分配的部分。

**因此:1000 个连接可能占用数 GB 内存,而其中 99% 的时间在空闲。**

## ③ 数据结构与共享内存布局

| 共享内存区 | 作用 |
|-----------|------|
| `shared_buffers` | 数据页缓存(最大块) |
| WAL buffers | (`wal_buffers`)WAL 写入缓冲 |
| 锁表(lock table) | 重量级锁的哈希表,大小由 `max_locks_per_transaction` × `max_connections` 推算 |
| `ProcArray` | 所有活动后端的事务状态快照数组(**MVCC 快照的关键依赖**) |
| CLOG / `pg_xact` 缓冲 | 事务提交状态的 SLRU 缓存 |
| `pg_subtrans` / `pg_multixact` 缓冲 | 子事务、多事务 |
| 统计信息区(PG15+) | 取代统计收集器 |

```sql
SHOW shared_buffers;
SHOW max_connections;
SHOW max_locks_per_transaction;    -- PG19 默认由 64 改为 128
SHOW max_worker_processes;
SHOW max_parallel_workers;
SELECT * FROM pg_shmem_allocations ORDER BY size DESC LIMIT 15;   -- 共享内存分配明细
```

> **`ProcArray` 与 MVCC 的关系**:每个后端把自己的 `xmin`、正在执行的事务 ID、持有的快照登记到 `ProcArray`。计算新快照时需扫描该数组 —— 这解释了为什么**连接数极多时获取快照变慢**,也解释了 `backend_xmin` 为什么能用来发现"阻塞 VACUUM 的会话"。

## ④ 源码路径

| 内容 | 位置 |
|------|------|
| postmaster 主循环 | `src/backend/postmaster/postmaster.c` |

| 崩溃重启与恢复入口 | `src/backend/postmaster/postmaster.c`(`PostmasterStateMachine`) |

## ⑤ 实验验证

### 实验 1:观察进程

```bash
# 宿主机/容器内查看进程树
ps -ef | grep postgres
# 关注:
#   postgres: postmaster            ← 主进程
#   postgres: checkpointer
#   postgres: background writer
#   postgres: walwriter
#   postgres: autovacuum launcher
#   postgres: postgres learn [local] idle   ← 你的连接(backend)
```

```sql
-- 用 SQL 看后端类型
SELECT pid, backend_type, backend_start, state, application_name
FROM pg_stat_activity ORDER BY backend_type, pid;
-- backend_type: client backend / autovacuum worker / checkpointer / background writer /
--               walwriter / walsender / walreceiver / logical replication worker / archiver / startup
```

### 实验 2:验证"每连接一个进程"

```sql
-- 会话 A
SELECT pg_backend_pid();   -- 记下 pid,例如 12345
```

```bash
# 宿主机
ps -p 12345 -o pid,ppid,cmd
# 输出类似:12345  1000  postgres: postgres learn [local] idle
# 说明该连接对应一个独立进程,父进程是 postmaster
```

### 实验 3:观察进程内存与连接数关系

```sql
-- 当前会话的内存上下文明细(PG12+)
SELECT name, level, pg_size_pretty(total_bytes) AS total
FROM pg_backend_memory_contexts
ORDER BY total_bytes DESC LIMIT 15;
```

> `pg_backend_memory_contexts` 只显示**当前会话**。查看其他后端需用 `pg_log_backend_memory_contexts(pid)` 把其内存上下文写入服务端日志。

```sql
-- 把指定后端的内存上下文写入服务端日志
SELECT pg_log_backend_memory_contexts(pid) FROM pg_stat_activity WHERE pid = 12345;
-- 然后到日志文件里检索
```

### 实验 4:验证连接池的价值

```bash
# 不用连接池:开 200 个并发 psql(可脚本模拟),观察内存
for i in $(seq 1 200); do psql -c "SELECT pg_sleep(30)" & done

# 观察
ps -ef | grep -c "postgres: postgres"
free -m
```

## ⑥ 生产启示

| 结论 | 行动 |
|------|------|
| 连接是进程,开销高 | **必须用连接池**(PgBouncer / 应用侧池),`max_connections` 保持在 100–300 量级,而不是开到几千 |
| 连接池模式选择 | `transaction` 模式复用率最高但不支持会话级 `SET`/临时表/`LISTEN`;`session` 模式兼容好但复用低 |
| 空闲连接也要治理 | 配置 `idle_session_timeout`(PG14+)与 `idle_in_transaction_session_timeout` |
| 空闲事务危害最大 | `idle in transaction` 会阻塞 VACUUM(持有旧快照),必须超时终止 |
| `max_connections` 影响共享内存 | 它决定锁表等结构大小,调大需重启且增加内存占用 |
| 并行查询用 worker | `max_parallel_workers` 独立于连接数,不要让连接占满 worker 名额 |
| 进程隔离是好事 | 单个后端 OOM 或崩溃不会污染其他会话状态(但 postmaster 会整体重启) |
| 监控 `pg_stat_activity` | 按 `state`、`wait_event_type` 分组统计,是排障第一入口 |

```sql
-- 连接池配套监控:按状态与应用分组
SELECT application_name, state, count(*)
FROM pg_stat_activity
GROUP BY 1,2 ORDER BY 3 DESC;

-- 找出空闲事务(必须清理)
SELECT pid, usename, application_name, now() - xact_start AS xact_age, left(query,50)
FROM pg_stat_activity
WHERE state = 'idle in transaction' AND xact_start IS NOT NULL
ORDER BY xact_start;

-- 找出占用连接最多的应用
SELECT application_name, count(*) FROM pg_stat_activity GROUP BY 1 ORDER BY 2 DESC;
```

> **连接池的坑**:在 `transaction` 模式下,`SET` / `PREPARE` / 临时表 / `LISTEN` / 会话级 advisory lock 都会在事务结束后失效或被其他连接"继承"。应用必须避免依赖会话状态,或改用 `session` 模式。
