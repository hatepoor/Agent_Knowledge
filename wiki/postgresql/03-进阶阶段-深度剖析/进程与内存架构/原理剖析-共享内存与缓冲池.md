# 原理剖析 · 共享内存与缓冲池

## ① 现象

- 调整 `shared_buffers` 后性能变化不线性(有时反而变差)
- 查询报 `could not write to temporary file` 或排序落盘
- 明明有内存,却频繁读磁盘
- `EXPLAIN (ANALYZE, BUFFERS)` 的命中率计算与预期不符

## ② 机制

### 双层缓存

```
应用查询
   │
   ▼
shared_buffers(PostgreSQL 自己的缓存,共享内存)
   │  未命中
   ▼
OS page cache(操作系统缓存)
   │  未命中
   ▼
磁盘
```

**PostgreSQL 不直接用 OS 缓存绕过自己** —— 它必须把页读进 `shared_buffers` 才能访问。

这带来两个重要结论:

1. **存在"双重缓存"**:同一份数据可能同时存在于两者中。
2. **`shared_buffers` 不需要设得很大**:OS 缓存也在帮忙。这也是为什么 `shared_buffers = 物理内存的 25%` 是经验起点,而不是 80%。

### 内存参数分层

| 参数 | 作用域 | 分配方式 | 默认 |
|------|--------|----------|------|
| `shared_buffers` | 实例 | 启动时固定分配 | 128MB |
| `work_mem` | **每个排序/哈希操作** | 按需(每个操作可各占一份) | 4MB |
| `maintenance_work_mem` | 每个维护操作 | 按需 | 64MB |
| `wal_buffers` | 实例 | 启动时 | -1(自动,约 1/32 shared_buffers,上限 16MB) |
| `temp_buffers` | 每个会话 | 按需 | 8MB |
| `hash_mem_multiplier` | 哈希操作 | 放大 `work_mem` | 2.0(PG13+) |
| `effective_cache_size` | — | **只是规划器估算提示,不分配内存** | 4GB |

> **最危险的误解:`work_mem` 不是"每个连接"的配额,而是"每个排序/哈希节点"的配额。**
>
> 一个复杂查询可能同时有多个排序与哈希节点;每个都能用满 `work_mem`。因此实际峰值可能是 `work_mem × 节点数 × 并行 worker 数`,再乘以并发连接数。

**估算实例总内存占用**

```
粗算 = shared_buffers
     + max_connections × (基础进程开销 + temp_buffers + 若干 work_mem)
     + autovacuum_max_workers × maintenance_work_mem
     + 并行 worker × work_mem × hash_mem_multiplier
```

## ③ 数据结构与缓冲池结构

### Buffer Descriptor 与 Buffer Pool

`shared_buffers` 由两部分组成:

| 部分 | 说明 |
|------|------|
| **缓冲池数组** | N 个 8KB 的页槽(`NBuffers = shared_buffers / 8KB`) |
| **缓冲区描述符数组** | 每个页槽对应一个 `BufferDesc`(状态、引用计数、标签) |

```c
/* src/include/storage/buf_internals.h(结构示意) */
typedef struct BufferDesc
{
    BufferTag  tag;              /* 页标识:表空间 + 数据库 + 关系 + fork + 块号 */
    int        buf_id;
    pg_atomic_uint32 state;      /* 状态:脏、有效、IO 进行中、引用计数 */
    int        freeNext;
    Latch      ...;
    uint32     wait_backend_pid;
} BufferDesc;

typedef struct BufferTag
{
    Oid    rnode;       /* 关系的 file node */
    ForkNumber forkNum; /* main / fsm / vm / init */
    BlockNumber blockNum;
} BufferTag;
```

### 页替换与时钟扫描

PostgreSQL 使用**时钟扫描(clock sweep)** 近似 LRU,而非精确 LRU(避免链表维护开销):

- 每个缓冲区有一个**引用计数(usage count)**,被访问时递增(最大 5)。
- 需要空闲页时,从 `nextVictimBuffer` 开始扫描,递减引用计数;计数为 0 且非脏的页被选中。
- 脏页则触发刷盘(可能交给 bgwriter 完成)。

> **`pg_buffercache` 的 `usagecount` 就对应这个引用计数**。它反映了页的"热度",是理解时钟扫描的直接窗口。

### 后台写进程的作用

| 进程 | 行为 |
|------|------|
| `bgwriter` | 定期扫描缓冲池,把脏页提前刷出,保持可用空闲页 |
| `checkpointer` | 定期做检查点,保证崩溃恢复时间可控 |

**`bgwriter` 存在的意义**:避免"用户查询被迫同步刷脏页"而阻塞。相关参数:

```
bgwriter_delay = 200ms              # 每轮间隔
bgwriter_lru_maxpages = 100         # 每轮最多刷多少页
bgwriter_lru_multiplier = 2.0       # 按预测需求放大
```

## ⑤ 实验验证

### 实验 1:看缓冲池里有什么

```sql
CREATE EXTENSION IF NOT EXISTS pg_buffercache;

-- 汇总:缓存了哪些表、占用多少、热度分布
SELECT
    coalesce(c.relname, 'FREE/OTHER') AS relation,
    count(*)                                        AS buffers,
    pg_size_pretty(count(*)::bigint * 8192)         AS cached_size,
    round(avg(b.usagecount), 2)                     AS avg_usage,
    count(*) FILTER (WHERE b.isdirty)               AS dirty_buffers
FROM pg_buffercache b
LEFT JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
                   AND b.reldatabase = (SELECT oid FROM pg_database WHERE datname = current_database())
GROUP BY 1
ORDER BY buffers DESC
LIMIT 15;

-- 缓存命中率(从 pg_stat_database 看)
SELECT datname, blks_read, blks_hit,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
FROM pg_stat_database
WHERE datname = current_database();
```

### 实验 2:验证 work_mem 是"每操作"而非"每连接"

```sql
-- 造一个会排序的表
CREATE TABLE big AS SELECT g AS id, random() AS r FROM generate_series(1, 3000000) g;
ANALYZE big;

-- 小 work_mem:排序落盘
SET work_mem = '4MB';
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM big ORDER BY r;
-- 关注 "Sort Method: external merge  Disk: NNNNkB"

-- 大 work_mem:内存排序
SET work_mem = '256MB';
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM big ORDER BY r;
-- 关注 "Sort Method: quicksort  Memory: NNNNkB"
```

### 实验 3:验证多个排序节点会各自占用 work_mem

```sql
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS)
SELECT a.id, a.r
FROM big a
JOIN (SELECT id, r FROM big ORDER BY r LIMIT 1000) b ON b.id = a.id
ORDER BY a.r;
-- 计划中可能出现两个 Sort 节点,各自都有独立的 Memory 占用
-- 说明峰值内存 ≈ 2 × work_mem
```

### 实验 4:观察 shared_buffers 大小与页数

```sql
SHOW shared_buffers;
SHOW block_size;          -- 8192

SELECT setting::bigint * 8192 / 1024 / 1024 AS shared_buffers_mb
FROM pg_settings WHERE name = 'shared_buffers';

-- 实际可用的缓冲区数量
SELECT count(*) AS total_buffers FROM pg_buffercache;
-- 约等于 shared_buffers / 8192(会略少,因元数据占用)
```

### 实验 5:验证 OS 缓存也在贡献

```bash
# 清空 PostgreSQL 缓存(需重启)
docker restart pg18

# 清空 OS 缓存(macOS 不支持;Linux 需 root)
sync && echo 3 > /proc/sys/vm/drop_caches

# 对比两次相同查询的耗时
```

## ⑥ 生产启示

| 结论 | 行动 |
|------|------|
| `shared_buffers` 不必过大 | 起点 25% 物理内存;超过 8–16GB 后边际收益递减(OS 缓存已在帮忙) |
| `work_mem` 是**每操作** | 先按"单操作需求"设(如 32–64MB),再用 `hash_mem_multiplier` 单独放大哈希 |
| 警惕乘法放大 | 高并发 × 多排序节点 × 并行 worker,可能瞬间耗尽内存。可用 `work_mem` 保守 + 会话级上调 |
| 排序落盘要看 | `EXPLAIN (ANALYZE, BUFFERS)` 中 `Sort Method: external merge` 与 `temp written > 0` 都是内存不足的信号 |
| `effective_cache_size` 只是提示 | 应设为"shared_buffers + OS 预期可用缓存"(约物理内存 50–75%),它影响规划器是否偏好索引 |
| 关注命中率 | `pg_stat_database.blks_hit / (blks_hit + blks_read)` 长期 < 99%,说明工作集超出缓存,需优化访问模式或加内存 |
| `bgwriter` 调优 | 写密集时可增大 `bgwriter_lru_maxpages` 与 `bgwriter_delay`,把刷脏摊薄,减少查询被阻塞 |
| `pg_prewarm` 预热 | 重启后可用 `pg_prewarm` 提前把热表读进缓存,避免冷启动抖动 |

```sql
-- 会话级精细控制:报表查询临时放大 work_mem
BEGIN;
SET LOCAL work_mem = '512MB';
SET LOCAL statement_timeout = '5min';
-- 大报表查询
COMMIT;
```

```sql
-- 找出导致排序落盘的查询
SELECT left(query,80), temp_blks_written
FROM pg_stat_statements
WHERE temp_blks_written > 0
ORDER BY temp_blks_written DESC LIMIT 10;
```

> **`temp_blks_written` 是发现"内存不足"最直接的生产指标。** 它直接说明查询在落临时文件,通常意味着 `work_mem` 偏小或查询本身需要优化(如缺少合适的索引导致必须排序大量数据)。
