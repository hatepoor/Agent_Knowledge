# 原理剖析 · 优化阶段与代价模型

## ① 现象

- 同一条 SQL 换一个参数,计划完全不同
- 明明有索引,规划器却选 `Seq Scan`
- 加了索引反而变慢
- 表很小的时候计划"很蠢",数据多了反而变好
- 计划随执行次数变化(第一次慢,后面快,或反之)

## ② 机制

### 四个阶段

```
SQL 文本
   │
   ▼
① 解析(Parse)     → 语法树
   │
   ▼
② 分析/重写(Analyze/Rewrite) → 查询树;应用视图展开、规则
   │
   ▼
③ 规划(Plan)      → 枚举候选计划,按代价选最优
   │      ├─ 子查询提升(subquery pull-up)
   │      ├─ 连接顺序枚举
   │      ├─ 谓词下推(predicate pushdown)
   │      ├─ 连接算法选择(NL / Hash / Merge)
   │      └─ 扫描方式选择(Seq / Index / Bitmap / Index Only)
   ▼
④ 执行(Execute)   → 按计划树自底向上求值
```

**关键:规划是"基于估算的搜索"**,不是"基于事实的计算"。它:

1. 用**统计信息**估算每个步骤的**行数(cardinality)**;
2. 用**代价模型**把行数换算成"代价";
3. 在候选计划中选择**代价最小**的。

**所以估算错误 → 代价错误 → 选错计划。** 这是绝大多数"计划不合理"的根因。

### 代价模型

默认参数(可在 `postgresql.conf` 查看):

| 参数 | 默认 | 含义 |
|------|------|------|
| `seq_page_cost` | 1.0 | 顺序读一个页的代价(基准) |
| `random_page_cost` | 4.0 | 随机读一个页的代价 |
| `cpu_tuple_cost` | 0.01 | 处理一行元组的 CPU 代价 |
| `cpu_index_tuple_cost` | 0.005 | 处理一个索引项的 CPU 代价 |
| `cpu_operator_cost` | 0.0025 | 执行一个操作符/函数的代价 |
| `parallel_setup_cost` | 1000 | 启动并行的代价 |
| `parallel_tuple_cost` | 0.1 | 并行传递一行的代价 |
| `effective_cache_size` | 4GB | **不是内存分配**,是"规划器认为可缓存多少" |
| `min_parallel_table_scan_size` | 8MB | 小于此的表不考虑并行 |

**代价公式(概念化)**

```
Seq Scan 代价 ≈
    seq_page_cost × 表页数
  + cpu_tuple_cost × 行数
  + cpu_operator_cost × 每行的过滤条件数

Index Scan 代价 ≈
    random_page_cost × 预估索引页数
  + cpu_index_tuple_cost × 索引项数
  + random_page_cost × 预估回表页数      ← 随机 I/O,代价高
  + cpu_tuple_cost × 行数

Index Only Scan 代价 ≈
    random_page_cost × 索引页数
  + cpu_index_tuple_cost × 索引项数
  （无回表项 → 便宜得多）

Bitmap Heap Scan 代价 ≈
    索引扫描代价
  + 按块排序后的顺序读代价             ← 把随机 I/O 转成近似顺序
```

### 为什么有索引却选 Seq Scan

原因通常是**回表代价太高**:

```
假设:表 10000 页,查询命中 10% 的行(1000 页)
      random_page_cost = 4.0

Index Scan:
    索引页读 + 1000 页随机回表 × 4.0 ≈ 4000+ 代价

Seq Scan:
    10000 页顺序读 × 1.0 ≈ 10000 代价

如果命中 30%(3000 页):
Index Scan ≈ 12000  >  Seq Scan 10000  → 选 Seq Scan ✓ 合理
```

**结论**:选择性差(命中比例高)时,**Seq Scan 是正确的选择**,不是 bug。索引的收益来自"少量随机读替代大量顺序读"。

### SSD 上必须调 `random_page_cost`

默认 `4.0` 反映"机械盘随机读比顺序读贵 4 倍"。SSD 上随机读几乎和顺序读一样快,保持 4.0 会让规划器**过度偏好 Seq Scan**。

```sql
-- 验证:调低后是否改变计划
SET random_page_cost = 1.1;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
RESET random_page_cost;
```

| 存储 | 建议 `random_page_cost` |
|------|------------------------|
| 机械盘(HDD) | 4.0(默认) |
| 本地 SSD | 1.1 – 2.0 |
| 云块存储(网络盘) | 1.5 – 3.0(需实测) |
| 全内存数据集 | 1.0 |

### 连接算法与代价

| 算法 | 复杂度 | 代价特征 | 何时最优 |
|------|--------|----------|----------|
| **Nested Loop** | O(外 × 内) | 外行数少 + 内侧有索引 → 便宜 | 小驱动集 + 内侧索引 |
| **Hash Join** | O(外 + 内) | 需建哈希表,内存敏感 | 等值连接,两侧都不小 |
| **Merge Join** | O(外 + 内) 但需排序 | 两侧已有序时最便宜 | 两侧已按连接键有序 |

```
计划器选择的逻辑:
  若 外行数 很小 且 内侧可走索引 → Nested Loop
  否则若 等值连接 → Hash Join（通常）
  否则若 两侧已有序 → Merge Join
```

> **Nested Loop 的典型危险**:外层估算行数偏小(实际很大),规划器选 Nested Loop,于是内侧被反复扫描 N×M 次,导致灾难性性能。**"估算偏差 + Nested Loop"是最常见的计划事故组合。**

### 并行查询

```
Gather / Gather Merge   ← 汇总并行 worker 的结果
  → Parallel Seq Scan
  → Parallel Hash Join
```

| 参数 | 默认 |
|------|------|
| `max_parallel_workers_per_gather` | 2 |
| `max_parallel_workers` | 8 |
| `parallel_setup_cost` | 1000 |
| `min_parallel_table_scan_size` | 8MB |

**PG18 起**:`FULL OUTER JOIN` 与 `RIGHT OUTER JOIN` 也支持并行(此前仅部分类型)。

```sql
-- 对比并行开关的影响
SET max_parallel_workers_per_gather = 0;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
RESET max_parallel_workers_per_gather;
```

### 计划搜索的规模问题

| 表数 | 连接顺序组合 | 策略 |
|------|--------------|------|
| ≤ 5 | 几十 | 穷举 |
| 6–11 | 数万 | 穷举 + 剪枝(`join_collapse_limit`) |
| ≥ 12 | 阶乘级爆炸 | **遗传算法(GEQO)** 近似搜索 |

```sql
SHOW geqo;                  -- 默认 on
SHOW geqo_threshold;        -- 默认 12
SHOW join_collapse_limit;   -- 默认 8
SHOW from_collapse_limit;   -- 默认 8
```

> **实践含义**:连接超过 8–10 张表的单条 SQL,规划质量会下降且规划耗时上升。**拆成中间结果(CTE / 临时表)往往更稳定。**

### GEQO 与计划稳定性

GEQO 是**随机化**算法,同一 SQL 可能得到不同计划。若观察到计划漂移:

```sql
-- 提高穷举阈值(代价是规划变慢)
SET geqo_threshold = 20;
-- 或直接关闭 GEQO
SET geqo = off;
```

## ④ 实验验证

### 实验 1:验证"选择性差时 Seq Scan 是正确选择"

```sql
DROP TABLE IF EXISTS opt_demo;
CREATE TABLE opt_demo AS SELECT g AS id, (g % 1000) AS k, repeat('x', 50) AS pad
FROM generate_series(1, 1000000) g;
CREATE INDEX opt_demo_k ON opt_demo (k);
ANALYZE opt_demo;

-- 高选择性:k 只有 1000 个不同值,每个 1000 行 → 命中 0.1%
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM opt_demo WHERE k = 123;
-- 期望:Index Scan

-- 低选择性:命中 50%
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM opt_demo WHERE k < 500;
-- 期望:Seq Scan(Bitmap 也可能);这是正确的

-- 强制走索引对比
SET enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM opt_demo WHERE k < 500;
RESET enable_seqscan;
-- 对比耗时,通常 Seq Scan 更快
```

> `enable_seqscan = off` 不是"禁用",而是给 Seq Scan 加一个巨大的惩罚代价,**让规划器优先考虑别的方案**。它是排障工具,不是生产配置。

### 实验 2:验证 `random_page_cost` 对计划的影响

```sql
-- 找一个"临界"选择性:命中约 5%
EXPLAIN (SELECT * FROM opt_demo WHERE k < 50);

SET random_page_cost = 4.0;
EXPLAIN SELECT * FROM opt_demo WHERE k < 30;

SET random_page_cost = 1.1;
EXPLAIN SELECT * FROM opt_demo WHERE k < 30;
-- 观察计划在 Index Scan / Seq Scan 之间的切换
```

### 实验 3:验证估算偏差导致 Nested Loop 事故

```sql
DROP TABLE IF EXISTS nl_a, nl_b;
CREATE TABLE nl_a AS SELECT g AS id, (g%100) AS k FROM generate_series(1, 100) g;
CREATE TABLE nl_b AS SELECT g AS id, (g%100) AS k, repeat('y',100) AS pad
FROM generate_series(1, 1000000) g;
CREATE INDEX nl_b_k ON nl_b (k);
ANALYZE nl_a; ANALYZE nl_b;

-- 先看正确的计划(估算准)
EXPLAIN (ANALYZE, BUFFERS)
SELECT a.id, b.pad FROM nl_a a JOIN nl_b b ON a.k = b.k;
-- 期望:Hash Join(因为 b 侧要匹配大量行)

-- 人为制造估算偏差:使用不可估算的条件
EXPLAIN (ANALYZE, BUFFERS)
SELECT a.id, b.pad FROM nl_a a JOIN nl_b b ON a.k = b.k AND a.id < 100;
```

### 实验 4:观察并行查询

```sql
-- 大表 + 聚合,容易并行
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), avg(id) FROM opt_demo;

-- 关闭并行对比
SET max_parallel_workers_per_gather = 0;
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), avg(id) FROM opt_demo;
RESET max_parallel_workers_per_gather;
```

### 实验 5:观察计划缓存与参数敏感性

```sql
-- 同一 SQL 不同参数的估算行数差异
EXPLAIN SELECT * FROM opt_demo WHERE k = 1;      -- 每个值 1000 行
EXPLAIN SELECT * FROM opt_demo WHERE k < 1;      -- 极少
-- 估算 rows 差异巨大 → 说明参数值影响计划选择

-- 预处理语句的通用计划
PREPARE pq(int) AS SELECT * FROM opt_demo WHERE k = $1;
EXPLAIN EXECUTE pq(1);
SHOW plan_cache_mode;    -- auto
-- 若通用计划表现差:
SET plan_cache_mode = force_custom_plan;
```

### 实验 6:观察子查询提升

```sql
-- 子查询可能被"提升"并与外层合并,从而条件下推
EXPLAIN (VERBOSE)
SELECT * FROM (SELECT * FROM opt_demo WHERE k > 100) s WHERE id < 1000;
-- 关注计划里是否有 Subquery Scan 节点
-- 若被提升,则条件合并,索引可选
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 规划基于估算 | **统计信息质量决定计划质量**;见下一篇 |
| Seq Scan 常常是正确选择 | 不要把 `Seq Scan` 当作坏现象;要看 `Rows Removed by Filter` 与 Buffers |
| SSD 必调 `random_page_cost` | 1.1–2.0;不改则规划器系统性偏好全表扫描 |
| Nested Loop + 估算偏差 = 事故 | 看到 Nested Loop 且 `loops` 巨大,优先怀疑估算 |
| 连接不宜超过 8–10 张表 | 否则规划质量下降、可能启用 GEQO 导致计划漂移 |
| 并行不是越多越好 | 高并发下并行会抢 CPU;可用 `SET LOCAL` 按查询控制 |
| `enable_*` 参数只用于排障 | 不要写进生产配置 |

```sql
-- 排查计划选择是否受代价参数影响
EXPLAIN (ANALYZE, BUFFERS, SETTINGS) SELECT ...;
-- SETTINGS 会列出影响该计划的非默认配置

-- 手工验证"如果代价参数不同会怎样"
BEGIN;
SET LOCAL random_page_cost = 1.1;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
ROLLBACK;
```
