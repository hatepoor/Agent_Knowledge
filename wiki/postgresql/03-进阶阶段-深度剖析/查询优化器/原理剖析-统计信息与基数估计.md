# 原理剖析 · 统计信息与基数估计

## ① 现象

- `EXPLAIN` 的 `rows` 估算与实际相差几十上百倍
- 刚 `ANALYZE` 完计划变好,过几天又变差
- 加了索引但规划器"看不到"它的价值
- 两列相关性很强,但估算把行数乘在一起
- 分区表/继承表的估算尤其不准

## ② 机制

### 统计信息的存放位置

| 位置 | 内容 |
|------|------|
| `pg_statistic` | 系统目录,**普通用户通常无权限读** |
| `pg_stats` | `pg_statistic` 的可读视图(**日常查看用这个**) |
| `pg_statistic_ext` / `pg_statistic_ext_data` | 扩展统计(PG10+) |

```sql
\d pg_stats
SELECT attname, null_frac, n_distinct, most_common_vals, most_common_freqs,
       histogram_bounds, correlation
FROM pg_stats WHERE tablename = 'orders';
```

### 关键字段含义

| 字段 | 含义 | 用途 |
|------|------|------|
| `null_frac` | NULL 比例 | 估算 `IS NULL` 的选择性 |
| `n_distinct` | 不同值个数(**正数=绝对值,负数=占行数比例**) | 估算等值条件选择性 |
| `most_common_vals` (MCV) | 最常见值列表 | 处理**数据倾斜** |
| `most_common_freqs` | 对应频率 | 同上 |
| `histogram_bounds` | 等频直方图边界(默认 100 个桶) | 估算范围条件选择性 |
| `correlation` | 物理顺序与逻辑顺序的相关性(-1~1) | **BRIN 决策依据**;也影响索引代价估算 |
| `avg_width` | 平均字节宽度 | 估算行宽、I/O 量 |

### 估算的实际过程

```
查询:WHERE k = 123

估算逻辑:
  1. 若 123 在 MCV 中 → 用 most_common_freqs 对应值
  2. 否则 → 用 (1 - sum(mcv_freqs) - null_frac) / (n_distinct - mcv_count)
  3. 乘以总行数 → 得到估算行数
```

```
查询:WHERE k BETWEEN 100 AND 500

估算逻辑:
  1. 用 histogram_bounds 确定 100 与 500 落在哪个桶
  2. 按桶内插值计算比例
  3. 乘以总行数
```

**多条件组合的核心问题**

```
WHERE a = ? AND b = ?

朴素估算:rows = total × sel(a) × sel(b)
```

**当 a 与 b 相关时,这个乘积是错的。**

例:`city` 与 `province` 强相关。`WHERE city='杭州' AND province='浙江'`:

- `sel(city='杭州')` ≈ 0.01
- `sel(province='浙江')` ≈ 0.03
- 乘积 ≈ 0.0003
- 但实际:所有杭州行都满足浙江 → 实际选择性 ≈ 0.01
- **低估了 33 倍**

### 采样机制

`ANALYZE` 使用**随机页采样**(`random_page_cost` 之外的独立机制):

| 参数 | 默认 | 说明 |
|------|------|------|
| `default_statistics_target` | 100 | 每列的统计目标(MCV 数量与直方图桶数) |
| `statistics_target`(列级) | — | 可单列覆盖 |
| 采样比例 | 300 × target 行 | 自动计算 |

```sql
-- 列级覆盖(高倾斜列可调高)
ALTER TABLE orders ALTER COLUMN channel SET STATISTICS 1000;
ANALYZE orders;
```

> **权衡**:`STATISTICS` 越高 → 估算越准但 `ANALYZE` 越慢、`pg_statistic` 越大、规划时读取统计的开销也越大。**默认 100 对多数列足够;只为真正压测出偏差的列调高。**

### 扩展统计(多变量统计)

解决"列间相关性"问题的官方方案(PG10+)。

| 类型 | 作用 |
|------|------|
| `dependencies` | 函数依赖(如 city → province) |
| `ndistinct` | 组合的不同值个数 |
| `mcv` | 组合的 MCV 列表(PG12+) |
| `expressions` | 对表达式建统计(PG14+) |

```sql
-- 声明
CREATE STATISTICS s_city_prov (dependencies, ndistinct)
    ON city, province FROM addresses;

CREATE STATISTICS s_expr ON (date_trunc('day', created_at))
    FROM orders;      -- PG14+:表达式统计

ANALYZE addresses;

-- 查看
SELECT stxname, stxkind, stxkeys FROM pg_statistic_ext;
SELECT * FROM pg_statistic_ext_data WHERE stxname = 's_city_prov';
```

**效果验证**:

```sql
-- 未建扩展统计时
EXPLAIN SELECT * FROM addresses WHERE city='杭州' AND province='浙江';
-- 估算 rows 偏小

-- 建扩展统计后
CREATE STATISTICS s1 (dependencies) ON city, province FROM addresses;
ANALYZE addresses;
EXPLAIN SELECT * FROM addresses WHERE city='杭州' AND province='浙江';
-- 估算 rows 修正到接近实际
```

### 自动 ANALYZE 的触发

| 参数 | 默认 | 说明 |
|------|------|------|
| `autovacuum_analyze_threshold` | 50 | 基线变化行数 |
| `autovacuum_analyze_scale_factor` | 0.1 | 表大小的比例 |

```
触发条件:变更行数 > threshold + scale_factor × 表行数
```

> **大表的问题**:1000 万行的表,需变更 `50 + 100万 = 100万行` 才触发 autoanalyze。对"小批量高频变更"的表(**如只更新少量行但分布变化大**),统计会长期不刷新。对策:
>
> ```sql
> ALTER TABLE hot_table SET (autovacuum_analyze_scale_factor = 0.01);
> ```

### 备份与升级

- `pg_dump` / 逻辑备份**不含统计信息**,恢复后需 `ANALYZE`。
- **PG18 起 `pg_upgrade` 保留优化器统计信息**,升级后不必立即 `ANALYZE`。
- 物理备份(`pg_basebackup`)包含统计信息。

## ④ 实验验证

### 实验 1:看到估算与实际偏差

```sql
DROP TABLE IF EXISTS stat_demo;
-- 造一个强相关的表:city 与 province 一一对应
CREATE TABLE stat_demo AS
SELECT g AS id,
       (ARRAY['浙江','江苏','广东','四川'])[1 + (g % 4)] AS province,
       (CASE (g % 4)
            WHEN 0 THEN '杭州' WHEN 1 THEN '南京'
            WHEN 2 THEN '广州' ELSE '成都' END) AS city
FROM generate_series(1, 400000) g;
ANALYZE stat_demo;

-- 看单列统计
SELECT attname, null_frac, n_distinct, correlation
FROM pg_stats WHERE tablename='stat_demo';

-- 单条件估算(准)
EXPLAIN SELECT * FROM stat_demo WHERE province = '浙江';
EXPLAIN SELECT * FROM stat_demo WHERE city = '杭州';

-- 组合条件估算(不准:把两者相乘)
EXPLAIN SELECT * FROM stat_demo WHERE province='浙江' AND city='杭州';
-- 估算 rows 约为 100000/4/4 ≈ 6250,但实际是 100000 → 低估 16 倍
```

### 实验 2:扩展统计的修正效果

```sql
CREATE STATISTICS stat_demo_ext (dependencies, ndistinct, mcv)
    ON province, city FROM stat_demo;
ANALYZE stat_demo;

-- 再看组合条件
EXPLAIN SELECT * FROM stat_demo WHERE province='浙江' AND city='杭州';
-- 估算 rows 应接近实际 100000

-- 确认扩展统计已生效
SELECT stxname, stxkind FROM pg_statistic_ext WHERE stxrelid = 'stat_demo'::regclass;
```

### 实验 3:MCV 处理数据倾斜

```sql
DROP TABLE IF EXISTS skew_demo;
CREATE TABLE skew_demo AS
SELECT g AS id,
       CASE WHEN g % 1000 = 0 THEN 'HOT'
            ELSE 'v' || (g % 50) END AS k
FROM generate_series(1, 1000000) g;
ANALYZE skew_demo;

SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename='skew_demo' AND attname='k';
-- mcvs 里应有 'HOT',频率约 0.001(实际每 1000 行有 1 行)

-- 倾斜值:估算应准确(靠 MCV)
EXPLAIN SELECT * FROM skew_demo WHERE k = 'HOT';

-- 非倾斜值:靠 n_distinct 均分
EXPLAIN SELECT * FROM skew_demo WHERE k = 'v7';
```

### 实验 4:直方图与范围估算

```sql
DROP TABLE IF EXISTS hist_demo;
CREATE TABLE hist_demo AS SELECT g AS id, g AS val FROM generate_series(1, 1000000) g;
ANALYZE hist_demo;

SELECT histogram_bounds FROM pg_stats
WHERE tablename='hist_demo' AND attname='val';
-- 默认 100 个边界值

EXPLAIN SELECT * FROM hist_demo WHERE val BETWEEN 100 AND 500;
-- 估算应接近 401
```

### 实验 5:统计陈旧导致计划劣化

```sql
DROP TABLE IF EXISTS stale_demo;
CREATE TABLE stale_demo AS SELECT g AS id, 'a' AS k FROM generate_series(1, 1000) g;
ANALYZE stale_demo;

-- 大量变更数据分布
UPDATE stale_demo SET k = 'b';
INSERT INTO stale_demo SELECT g, 'c' FROM generate_series(1, 1000000) g;

-- 未 ANALYZE:估算严重偏低
EXPLAIN SELECT * FROM stale_demo WHERE k = 'c';

ANALYZE stale_demo;
-- ANALYZE 后:估算修正
EXPLAIN SELECT * FROM stale_demo WHERE k = 'c';
```

### 实验 6:验证 correlation 与 BRIN

```sql
DROP TABLE IF EXISTS corr_demo;
CREATE TABLE corr_demo AS
SELECT g AS id, (timestamp '2026-01-01' + (g||' s')::interval) AS ts
FROM generate_series(1, 1000000) g;
ANALYZE corr_demo;

SELECT attname, correlation FROM pg_stats
WHERE tablename='corr_demo' AND attname='ts';
-- 接近 1.0

-- 打乱后
DROP TABLE IF EXISTS corr_shuffled;
CREATE TABLE corr_shuffled AS SELECT * FROM corr_demo ORDER BY random();
ANALYZE corr_shuffled;
SELECT attname, correlation FROM pg_stats
WHERE tablename='corr_shuffled' AND attname='ts';
-- 接近 0
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 统计信息是计划的命门 | 升级/迁移/大批变更后**必须 `ANALYZE`** |
| 列间相关性需扩展统计 | 多条件查询且列相关时,建 `CREATE STATISTICS (dependencies, mcv)` |
| 大表的 autoanalyze 触发慢 | 对分布易变的表调低 `autovacuum_analyze_scale_factor` |
| 高倾斜列需更高 target | `ALTER COLUMN ... SET STATISTICS 1000` |
| `correlation` 是 BRIN 的开关 | 接近 0 就不要用 BRIN |
| PG18 升级后无需立即 ANALYZE | `pg_upgrade` 保留统计 |
| 逻辑恢复后必须 ANALYZE | `pg_dump` 不含统计 |
| 计划突变先查统计新鲜度 | `pg_stat_user_tables.last_analyze / last_autoanalyze` |

```sql
-- 统计新鲜度自查
SELECT relname, n_live_tup, n_mod_since_analyze,
       last_analyze, last_autoanalyze,
       now() - greatest(last_analyze, last_autoanalyze) AS staleness
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC NULLS LAST LIMIT 20;

-- 统计质量自查(偏差大的列)
SELECT schemaname, tablename, attname, n_distinct, correlation,
       array_length(most_common_vals, 1) AS mcv_count
FROM pg_stats
WHERE schemaname = 'public'
ORDER BY abs(coalesce(correlation,0)) DESC, tablename, attname;
```
