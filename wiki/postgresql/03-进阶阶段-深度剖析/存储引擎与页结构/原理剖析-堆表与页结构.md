# 原理剖析 · 堆表与页结构

## ① 现象

- 删除了大量数据,表文件大小却没减少
- 同样的行数,两个表占用空间差异很大
- `ctid` 在 `UPDATE` 之后变了
- `SELECT *` 比只取几列慢很多(即使行数相同)
- `pg_relation_size` 与实际"逻辑数据量"对不上

这些现象的根源都在**堆表(heap)的页结构与元组布局**。

## ② 机制

### 8KB 页是存储的基本单位

PostgreSQL 的存储单位是**页(page)**,默认 8192 字节(`block_size`,编译期固定)。

```
表文件(tablespace/db/relfilenode)
 ├── 块 0    ← 8KB 页
 ├── 块 1
 ├── 块 2
 └── ...
```

**页在文件内是"位置无关"的**:块号即偏移量。因此 `ctid = (块号, 页内槽位)` 能唯一定位一个元组版本。

### 页的内部布局

```
┌─────────────────────────────────────────────────────────────┐
│ PageHeaderData  (24 字节)                                    │
│  pd_lsn(8) pd_checksum(2) pd_flags(2) pd_lower(2)            │
│  pd_upper(2) pd_special(2) pd_pagesize_version(2)            │
├─────────────────────────────────────────────────────────────┤
│ ItemIdData[]  行指针数组(每个 4 字节,向 pd_lower 方向增长)    │
│  [0] lp_off, lp_len, lp_flags                                │
│  [1] ...                                                     │
├─────────────────────────────────────────────────────────────┤
│                        ← 空闲空间(free space)               │
├─────────────────────────────────────────────────────────────┤
│                        元组数据(向 pd_upper 反方向增长)      │
│  元组 N(通常从页尾开始往前放)                                │
│  ...                                                         │
│  元组 1                                                      │
├─────────────────────────────────────────────────────────────┤
│ Special space  (pd_special 起,普通表为空;索引页用来放元数据)  │
└─────────────────────────────────────────────────────────────┘
```

### 页头字段含义(必须记住)

```c
/* src/include/storage/bufpage.h */
typedef struct PageHeaderData
{
    XLogRecPtr  pd_lsn;                 /* 最后一次修改此页的 WAL 位置 */
    uint16      pd_checksum;            /* 页校验和(PG18 起默认启用) */
    uint16      pd_flags;               /* 标志位,如是否有空闲空间 */
    LocationIndex pd_lower;             /* 行指针数组末尾偏移 */
    LocationIndex pd_upper;             /* 元组数据起始偏移(向低地址增长) */
    LocationIndex pd_special;           /* special space 起始偏移 */
    uint16      pd_pagesize_version;    /* 页大小 + 版本 */
    TransactionId pd_prune_xid;         /* 可裁剪的最小 xid */
} PageHeaderData;
```

| 字段 | 意义 | 用途 |
|------|------|------|
| `pd_lsn` | 最后一次改页的 WAL 位置 | 恢复时判断页是否已应用某 WAL 记录(幂等) |
| `pd_checksum` | 页校验和 | 检测静默损坏(PG18 起 `initdb` 默认开启) |
| `pd_lower` | 行指针数组末端 | 空闲空间中界 |
| `pd_upper` | 元组区起点 | 空闲空间下界 |
| **空闲空间** | `pd_upper - pd_lower` | 决定能否插入新元组 |
| `pd_special` | special space 起点 | 索引页用于存放结构元数据 |

> **关键理解:`pd_lower` 向上增长(行指针数组),`pd_upper` 向下增长(元组数据),两者中间是空闲空间。** 清理后两者会重新靠拢,但**不会归还给操作系统** —— 这是"表膨胀"的几何解释。

### ItemIdData(行指针 / line pointer)

```c
typedef struct ItemIdData
{
    unsigned lp_off:15;     /* 元组在页内的偏移 */
    unsigned lp_flags:2;    /* 状态:UNUSED / NORMAL / REDIRECT / DEAD */
    unsigned lp_len:15;     /* 元组长度(含头部) */
} ItemIdData;
```

| `lp_flags` | 含义 |
|-----------|------|
| `LP_UNUSED` | 未使用(可复用) |
| `LP_NORMAL` | 正常指向一个元组 |
| `LP_REDIRECT` | 重定向(用于 HOT 更新的链头) |
| `LP_DEAD` | 已死(索引项可标记为 dead) |

**这是"元组被间接引用"的关键**:索引里存的是 `ctid = (块号, 槽号)`,即指向**行指针**,而不是直接指向元组数据。因此**元组在页内移动时,只要更新行指针,索引无需改动** —— 这就是 HOT 更新的基础(见 [[postgresql/03-进阶阶段-深度剖析/索引内核/原理剖析-HOT更新与索引维护]])。

### 元组头(HeapTupleHeader)

```c
/* src/include/access/htup_details.h */
typedef struct HeapTupleFields
{
    TransactionId t_xmin;      /* 插入该版本的事务 */
    TransactionId t_xmax;      /* 删除/更新该版本的事务 */
    union {
        CommandId t_cid;       /* 命令 ID */
        TransactionId t_xvac;
    } t_field3;
} HeapTupleFields;
```

从 `t_xmin` 开始(共 23 字节后对齐):

| 字段 | 含义 |
|------|------|
| `t_xmin` | 创建该行版本的事务 ID |
| `t_xmax` | 使其失效的事务 ID(0 表示仍有效) |
| `t_cid` | 同一事务内多个命令的顺序号 |
| `t_ctid` | 该版本在**最新版本链**中的位置(用于 HOT 链) |
| `t_infomask2` | 属性数、HOT 标志等 |
| `t_infomask` | 各种标志位(如 `HEAP_HASNULL`、`HEAP_XMIN_COMMITTED` 等 hint bits) |
| `t_hoff` | 数据起始偏移(有没有 NULL 位图) |

> **`t_infomask` 中的 hint bits** 是性能关键:事务提交状态本来存在 `pg_xact`(CLOG)里,每次判断可见性都去查会很慢。因此第一次查清后,就把结论**写回元组头**(设置 `XMIN_COMMITTED` 等标志)。这解释了:
> - 为什么"第一次读某张表"会写脏页(设置 hint bits 会修改页)
> - 为什么只读查询也可能产生 WAL 与脏页

### 行的物理布局

```
HeapTupleHeader (23 字节 + 对齐 + NULL 位图)
        ↓
数据区:按列顺序紧密排列
        ↓
        - 变长列(varlena):长度前缀 + 数据
        - 定长列(定长类型):直接排列
        - NULL:不占数据区,用 NULL 位图标记
```

**关键推论**

1. **NULL 值几乎不占空间**(只在位图占 1 位)—— 与固定长度字段的直觉相反。
2. **列顺序影响对齐填充**:把定长列(如 `bigint`)放前面,变长列放后面,可减少对齐空洞。
3. **`SELECT *` 的成本**:要读整行。若某列是 TOAST 的(如大 `text`),还会触发额外读取(见下一篇)。

### 表文件的分支(fork)

每个关系对应多个文件:

| Fork | 后缀 | 内容 |
|------|------|------|
| main | (无) | 数据页 |
| fsm | `_fsm` | Free Space Map:每页的可用空间量 |
| vm | `_vm` | Visibility Map:每页是否全可见/全冻结 |
| init | `_init` | 未初始化页(用于 `TRUNCATE` 后快速重建) |

```sql
SELECT pg_relation_filepath('orders');
-- 例如 base/16384/16400
SELECT size, pg_size_pretty(size) FROM pg_relation_size('orders', 'main') ...
-- 或用 pg_stat_file 查看各 fork 大小
SELECT pg_size_pretty(pg_relation_size('orders','main'))      AS main,
       pg_size_pretty(pg_relation_size('orders','fsm'))       AS fsm,
       pg_size_pretty(pg_relation_size('orders','vm'))        AS vm,
       pg_size_pretty(pg_relation_size('orders','init'))      AS init;
```

**FSM** 用于快速找到"能放下新元组的页",避免全表扫描找空位。**VM** 用于 Index Only Scan 与 VACUUM 的优化:标记"该页所有元组对所有事务可见",使 VACUUM 可跳过,使仅索引扫描可免回表。

### 段文件

单个文件不超过 **1GB**,超出后分成多个段:

```
16400        ← 第 1 个 1GB
16400.1      ← 第 2 个 1GB
16400.2      ← 第 3 个
```

## ④ 实验验证

### 实验 1:读页头

```sql
CREATE EXTENSION IF NOT EXISTS pageinspect;

INSERT INTO orders (user_id, total) VALUES (1, 100);

-- 读第 0 页的页头
SELECT * FROM page_header(get_raw_page('orders', 0));
-- 输出:lsn | checksum | flags | lower | upper | special | pagesize | version | prune_xid

-- 读行指针
SELECT * FROM heap_page_item_attrs(get_raw_page('orders', 0), 'orders'::regclass)
LIMIT 5;

-- 读元组头(更完整)
SELECT lp, lp_off, lp_flags, lp_len,
       t_xmin, t_xmax, t_ctid, t_infomask
FROM heap_page_items(get_raw_page('orders', 0))
LIMIT 10;
```

**验证空闲空间变化**:

```sql
-- 记录 lower / upper
SELECT lower, upper, upper - lower AS free_space
FROM page_header(get_raw_page('orders', 0));

-- 插入更多行
INSERT INTO orders (user_id, total) SELECT 1, g FROM generate_series(1,100) g;

-- 再看:lower 变大(行指针增多),upper 变小(元组增多),free_space 减小
SELECT lower, upper, upper - lower AS free_space
FROM page_header(get_raw_page('orders', 0));
```

### 实验 2:验证 UPDATE 产生新元组版本

```sql
CREATE TABLE t_demo (id int, v text);
INSERT INTO t_demo VALUES (1, 'a');

SELECT ctid, xmin, xmax, * FROM t_demo;
-- 例如 ctid=(0,1) xmin=1000 xmax=0

UPDATE t_demo SET v = 'b' WHERE id = 1;

SELECT ctid, xmin, xmax, * FROM t_demo;
-- ctid=(0,2) xmin=1001 xmax=0     ← 新版本,新 ctid,新 xmin

-- 看页里有两个元组版本
SELECT lp, lp_off, lp_len, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('t_demo', 0));
-- 会出现两个条目:旧版本(带 xmax)与新版本
```

> **这是 MVCC 最直观的证据**:`UPDATE` 不是原地修改,而是"标记旧版本 + 追加新版本"。

### 实验 3:验证 NULL 几乎不占空间

```sql
CREATE TABLE t_null1 (a int, b int, c int, d int, e int);
CREATE TABLE t_null2 (a int);
INSERT INTO t_null1 SELECT 1, NULL, NULL, NULL, NULL FROM generate_series(1,100000);
INSERT INTO t_null2 SELECT 1 FROM generate_series(1,100000);
VACUUM ANALYZE;
SELECT 't_null1' AS t, pg_size_pretty(pg_relation_size('t_null1'))
UNION ALL SELECT 't_null2', pg_size_pretty(pg_relation_size('t_null2'));
-- 两者大小接近(都只是 1 个 int + NULL 位图)
```

### 实验 4:验证表膨胀与空间不归还

```sql
CREATE TABLE t_expand AS SELECT g AS id, repeat('x', 100) AS pad FROM generate_series(1,200000) g;
SELECT pg_size_pretty(pg_relation_size('t_expand'));

DELETE FROM t_expand WHERE id % 2 = 0;
SELECT pg_size_pretty(pg_relation_size('t_expand'));    -- 大小几乎没变!

SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname='t_expand';

VACUUM t_expand;
SELECT pg_size_pretty(pg_relation_size('t_expand'));    -- 仍然没变(空间仅标记为可复用)

VACUUM FULL t_expand;
SELECT pg_size_pretty(pg_relation_size('t_expand'));    -- 这次变小了(重写文件)
```

### 实验 5:查看文件路径与 fork

```sql
SELECT pg_relation_filepath('t_demo');
-- 到容器里 ls -l 数据目录下该文件,并观察 _fsm / _vm 文件
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 页是 8KB,空间管理在页内 | 表膨胀的**第一层**是"页内空闲空间未归还";`VACUUM` 解决这一层 |
| 表膨胀的第二层是"页未归还 OS" | 只有 `VACUUM FULL` / `CLUSTER` / `pg_repack` 才缩小文件 |
| `ctid` 会变 | **不要持久化 `ctid`**,它只对当前事务/快照有效 |
| hint bits 会弄脏只读查询 | 监控 `pg_stat_user_tables.n_tup_hot_upd` 与脏页;查询也产生 WAL(逻辑上) |
| 列顺序有意义 | 定长列靠前、变长列靠后,减少对齐空洞;但收益通常很小,不必为此重构 |
| `SELECT *` 有真实成本 | 宽表会读整行;大字段触发 TOAST 读取。**代码里显式列名** |
| `fillfactor` 可减少页分裂 | 写密集表设 `fillfactor = 80`~`90`,为新版本预留页内空间 |
| 页校验和检测静默损坏 | PG18 起 `initdb` 默认开启;`--no-data-checksums` 可关闭 |

```sql
-- 观察表的死元组与 HOT 更新比例
SELECT relname, n_live_tup, n_dead_tup, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd,0), 1) AS hot_pct
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- 设置表的 fillfactor
ALTER TABLE orders SET (fillfactor = 85);
-- 注意:已有数据不会立刻重排,需 REINDEX/重建表才生效
```

```sql
-- 用 pgstattuple 量化膨胀
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstattuple('orders');
-- 关注 dead_tuple_percent / free_percent
```
