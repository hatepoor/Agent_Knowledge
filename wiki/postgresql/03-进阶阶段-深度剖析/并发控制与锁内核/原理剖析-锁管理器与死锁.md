# 原理剖析 · 锁管理器与死锁

## ① 现象

- 查询卡住不动,`pg_stat_activity` 里 `wait_event_type = 'Lock'`
- 偶发死锁报错:`deadlock detected`
- `SELECT FOR UPDATE` 之后其他写入全部排队
- 加列/建索引期间整表写入被阻塞
- 锁超时(`lock_timeout`)频繁触发

## ② 机制

### 四层锁体系

PostgreSQL 的"锁"是多个层次的概念,常被混为一谈:

| 层次 | 名称 | 粒度 | 存放位置 | 典型用途 |
|------|------|------|----------|----------|
| 最高层 | **重量级锁**(heavyweight lock) | 表/对象级 | 共享内存锁表 | `LOCK TABLE`、DDL、DML 的表级锁 |
| | **行级锁**(row lock) | 元组级(`xmax`) | **元组头里**(不是锁表!) | 行更新、`SELECT FOR UPDATE` |
| | **谓词锁**(predicate lock) | 索引范围 | 共享内存 | SSI 可串行化 |
| 最低层 | **轻量锁**(LWLock) | 内存结构 | 共享内存原子操作 | 保护缓冲池、WAL 缓冲等 |
| | **自旋锁**(spinlock) | 极短临界区 | 原子指令 | 保护 LWLock 自身等 |

### 行级锁的"非锁"实现

行级锁**不存在于锁表里**,而是利用元组的 `xmax`:

```
UPDATE t SET v='b' WHERE id=1:
  1. 把旧元组的 xmax 设为自己的 xid(表示"我持有该行的写锁")
  2. 写入新元组

另一个事务也想更新该行:
  1. 发现旧元组 xmax 指向一个未完成的事务
  2. 阻塞等待该事务结束(xact 锁等待)
```

**行锁模式(仅两个)**

| 模式 | 来源 | 语义 |
|------|------|------|
| `FOR UPDATE`(排他) | `UPDATE`/`DELETE`/`SELECT FOR UPDATE` | 独占,互斥 |
| `FOR NO KEY UPDATE` | 不涉及键列的 `UPDATE` | 与 `FOR SHARE` 兼容 |
| `FOR SHARE`(共享) | `SELECT FOR SHARE` | 多方共享,阻挡排他 |
| `FOR KEY SHARE` | 外键检查 | 最弱,只阻挡键列变更 |

```sql
SELECT * FROM t WHERE id = 1 FOR UPDATE;             -- 排他
SELECT * FROM t WHERE id = 1 FOR NO KEY UPDATE;       -- 不阻塞外键引用
SELECT * FROM t WHERE id = 1 FOR SHARE;               -- 共享
SELECT * FROM t WHERE id = 1 FOR KEY SHARE;           -- 最弱

-- 关键修饰符
SELECT ... FOR UPDATE NOWAIT;            -- 拿不到立刻报错,不等待
SELECT ... FOR UPDATE SKIP LOCKED;       -- 跳过被锁的行(★队列实现必备)
SELECT ... FOR UPDATE OF table_alias;    -- 只锁某张表(多表 JOIN 时)
```

> **`SKIP LOCKED` 是任务队列的标准实现**:多个 worker 并发取任务时,`SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` 让每个 worker 直接跳到未锁定的行,天然实现无冲突分发。
>
> **`NOWAIT` vs `SKIP LOCKED`**:前者报错,后者跳过。二者都不等待。

### 重量级锁与锁模式

表级锁有 8 种模式,冲突矩阵是理解"为什么 DDL 会阻塞一切"的关键:

| 模式 | 简称 | 获取场景 |
|------|------|----------|
| `ACCESS SHARE` | AS | `SELECT` |
| `ROW SHARE` | RS | `SELECT FOR UPDATE/SHARE` |
| `ROW EXCLUSIVE` | RX | `INSERT` / `UPDATE` / `DELETE` |
| `SHARE UPDATE EXCLUSIVE` | SUE | `VACUUM`、`ANALYZE`、`CREATE INDEX CONCURRENTLY` |
| `SHARE` | S | `CREATE INDEX`(非并发) |
| `SHARE ROW EXCLUSIVE` | SRE | `CREATE TRIGGER`、部分 `ALTER TABLE` |
| `EXCLUSIVE` | E | 阻止 RX 及以上 |
| `ACCESS EXCLUSIVE` | AX | `ALTER TABLE`(大部分)、`DROP`、`TRUNCATE`、`REINDEX`(非并发)、`VACUUM FULL`、`CLUSTER` |

**关键冲突对**

| 冲突 | 后果 |
|------|------|
| `ACCESS EXCLUSIVE` 与**一切**冲突 | **DDL 会阻塞所有读写** |
| `SHARE`(`CREATE INDEX`)与 `ROW EXCLUSIVE`(DML)冲突 | **建索引会阻塞写入** |
| `SUE` 与 `SUE` 冲突 | 两个 VACUUM 不能同时 |
| `ROW EXCLUSIVE` 与 `ROW EXCLUSIVE` **不冲突** | 不同行的 DML 可并发 |

**这就是"为什么必须用 `CREATE INDEX CONCURRENTLY` 和 `ADD CONSTRAINT NOT VALID + VALIDATE`"的根本原因**(见 [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.1-DDL建表与列定义]])。

**`ALTER TABLE` 加列为什么有时很快?**

| 操作 | 是否重写表 | 锁 |
|------|------------|-----|
| `ADD COLUMN`(有常量默认值,PG11+) | ❌ 不重写 | AX(但极短) |
| `ADD COLUMN`(有 volatile 默认值) | ✅ 重写 | AX(长时间) |
| `ALTER COLUMN TYPE`(二进制兼容) | ⚠️ 视情况 | AX |
| `SET NOT NULL`(PG12+ 有 CHECK 时可跳过扫描) | ❌ | AX(短) |
| `ADD CONSTRAINT CHECK` | ⚠️ 需全表扫描 | 可拆成 `NOT VALID` + `VALIDATE` |

### 锁管理器与等待队列

锁表位于共享内存,大小由 `max_locks_per_transaction × (max_connections + max_prepared_transactions + 若干)` 推算:

```sql
SHOW max_locks_per_transaction;   -- 默认 64;PG19 起默认改为 128
SHOW max_connections;
-- 若报错 "out of shared memory ... You might need to increase max_locks_per_transaction"
-- 说明锁表不够(常见于一次操作涉及大量分区的场景)
```

**等待机制**:

```
事务 T 请求锁 L
  → 若与已持有的锁兼容 → 立即授予
  → 否则 → 入等待队列,进入 "Lock" 等待(latch wait)
           → 被阻塞事务唤醒时,重新检查(可能再次等待)
```

**等待事件的分类**(`pg_stat_activity.wait_event_type`):

| 类型 | 含义 |
|------|------|
| `Lock` | 等重量级锁(行锁、表锁) |
| `LWLock` | 等轻量锁(缓冲池、WAL 等内部结构) |
| `IO` | 等 I/O |
| `Client` | 等客户端(如 `ClientRead`) |
| `IPC` | 进程间通信 |
| `BufferPin` | 等缓冲区 pin |
| `Timeout` | 等超时 |

### 死锁检测

**PostgreSQL 主动检测死锁**(不是靠超时):

```
事务 A 持锁 X,等锁 Y
事务 B 持锁 Y,等锁 X     ← 循环

检测机制:
  某事务等待锁超过 deadlock_timeout(默认 1s)时,
  触发死锁检测器,沿"等待图"搜索环。
  若发现环 → 选择代价最小的事务作为牺牲者,终止它:

  ERROR: deadlock detected
  DETAIL: Process 12345 waits for ShareLock on transaction 1000;
          blocked by process 67890.
          Process 67890 waits for ... blocked by process 12345.
  HINT: See server log for query details.
  SQLSTATE: 40P01
```

```sql
SHOW deadlock_timeout;    -- 默认 1s
```

> **`deadlock_timeout` 的意义**:它是"开始检测"的阈值,不是检测周期。设得太小会让普通锁等待也触发检测(浪费 CPU);设得太大则死锁发现慢。默认 1s 通常合适。

**死锁的典型成因与解法**

| 成因 | 解法 |
|------|------|
| 两事务按**不同顺序**更新同一批行 | **统一加锁顺序**(如总是按 id 升序) |
| 外键的隐式锁 + 显式锁交叉 | 明确加锁顺序,或先 `SELECT FOR KEY SHARE` |
| `UPDATE ... FROM` 涉及多表 | 改为固定顺序的单表更新 |
| 大批量更新与逐行更新交错 | 统一批次边界 |
| 触发器内的更新引入新锁 | 审视触发器逻辑 |

**死锁是应用设计问题,不是数据库问题。** 数据库只能检测并终止。

### 锁相关参数

| 参数 | 默认 | 作用 |
|------|------|------|
| `deadlock_timeout` | 1s | 开始死锁检测的等待阈值 |
| `lock_timeout` | 0(无限) | 单次等锁的超时 |
| `statement_timeout` | 0 | 单语句超时(包含等锁时间) |
| `idle_in_transaction_session_timeout` | 0 | 空闲事务超时 |
| `max_locks_per_transaction` | 64 | 锁表容量依据 |

```sql
-- 事务级锁超时(推荐模式:不为拿锁无限等待)
BEGIN;
SET LOCAL lock_timeout = '3s';
LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;
-- 拿不到 3s 后报错,而非无限等待
COMMIT;
```

### advisory lock(应用级锁)

用户自定义的锁,用于实现业务互斥。

```sql
-- 会话级(连接断开自动释放)
SELECT pg_advisory_lock(12345);              -- 阻塞获取
SELECT pg_try_advisory_lock(12345);          -- 非阻塞,返回 bool
SELECT pg_advisory_unlock(12345);

-- 事务级(事务结束自动释放)★推荐
SELECT pg_advisory_xact_lock(12345);         -- 阻塞
SELECT pg_try_advisory_xact_lock(12345);     -- 非阻塞

-- 两个 32 位参数形式
SELECT pg_advisory_xact_lock(1, 2);
```

| 类型 | 释放时机 | 风险 |
|------|----------|------|
| 会话级 | 显式 unlock 或断连 | 忘记 unlock 会长期持锁 |
| **事务级** | 事务结束 | **推荐**,无泄漏风险 |

> **advisory lock 的坑**:它是**应用自定义语义**,数据库不校验逻辑。且**事务级 advisory lock 与连接池的 `transaction` 模式兼容,会话级的不兼容**(会被其他连接"继承")。优先用事务级。

### 轻量锁(LWLock)

保护**内存结构**,粒度极细,持有时间以微秒计。

| 被保护对象 | 说明 |
|-----------|------|
| Buffer 相关 | 缓冲池的映射表、每个页的访问 |
| WAL 相关 | `WALInsertLock`、`WALWriteLock` |
| CLOG / SLRU | 各 SLRU 缓冲 |
| 锁管理器自身 | 保护锁表 |
| ProcArray | 保护进程数组 |

**LWLock 争用的典型症状**:`pg_stat_activity.wait_event_type = 'LWLock'`,且高并发下表现明显。常见于:
- 大量并发写 → `WALInsertLock` 争用
- 大量并发访问同一批页 → `buffer_content` 争用
- 高并发只读 + 频繁 hint bits 设置 → `buffer_content`

> **诊断 LWLock 争用可用 `pg_stat_activity` 聚合**:
> ```sql
> SELECT wait_event, count(*) FROM pg_stat_activity
> WHERE wait_event_type = 'LWLock' GROUP BY 1 ORDER BY 2 DESC;
> ```

## ④ 实验验证

### 实验 1:观察阻塞链

```sql
-- 会话 A
BEGIN;
UPDATE lock_demo SET v = 'A' WHERE id = 1;

-- 会话 B
UPDATE lock_demo SET v = 'B' WHERE id = 1;     -- 阻塞

-- 会话 C(监控)
SELECT
    a.pid, a.usename, a.state,
    a.wait_event_type, a.wait_event,
    now() - a.query_start AS wait_time,
    l.locktype, l.mode, l.granted,
    left(a.query, 50) AS query
FROM pg_stat_activity a
LEFT JOIN pg_locks l ON l.pid = a.pid
WHERE a.wait_event_type = 'Lock'
   OR (l.locktype = 'transactionid' AND NOT l.granted)
ORDER BY wait_time DESC;
```

> **`pg_locks` 里 `granted = false` 的行就是"等待中"的锁。** `locktype = 'transactionid'` 表示在等一个行锁持有者的事务结束。

### 实验 2:找出"谁阻塞了谁"

```sql
-- 找出被阻塞者与其阻塞源
SELECT
    blocked.pid            AS blocked_pid,
    blocked.query          AS blocked_query,
    blocking.pid           AS blocking_pid,
    blocking.query         AS blocking_query,
    blocked.wait_event
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS bp(pid) ON true
JOIN pg_stat_activity blocking ON blocking.pid = bp.pid
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;
```

> **`pg_blocking_pids(pid)`** 是一行解决阻塞链的官方函数(比手工 JOIN `pg_locks` 可靠得多)。

### 实验 3:复现死锁

```sql
-- 准备
DROP TABLE IF EXISTS d1, d2;
CREATE TABLE d1 (id int PRIMARY KEY, v text);
CREATE TABLE d2 (id int PRIMARY KEY, v text);
INSERT INTO d1 VALUES (1,'a'); INSERT INTO d2 VALUES (1,'b');

-- 会话 A
BEGIN;
UPDATE d1 SET v='A1' WHERE id=1;
-- 稍等
UPDATE d2 SET v='A2' WHERE id=1;

-- 会话 B(在 A 完成第一步后执行)
BEGIN;
UPDATE d2 SET v='B2' WHERE id=1;
-- 稍等
UPDATE d1 SET v='B1' WHERE id=1;

-- 约 1 秒后(A 或 B 其中之一)会收到:
-- ERROR: deadlock detected
```

### 实验 4:验证 `SKIP LOCKED` 做任务队列

```sql
DROP TABLE IF EXISTS job_queue;
CREATE TABLE job_queue (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    payload text,
    status  text DEFAULT 'pending'
);
INSERT INTO job_queue (payload) SELECT 'job'||g FROM generate_series(1, 100);

-- worker 取任务:
WITH picked AS (
    SELECT id FROM job_queue
    WHERE status = 'pending'
    ORDER BY id
    FOR UPDATE SKIP LOCKED
    LIMIT 5
)
UPDATE job_queue j SET status = 'processing'
FROM picked p WHERE j.id = p.id
RETURNING j.id;

-- 多个 worker 并发执行上面的语句,不会有任何锁等待,分配到不同的行
```

### 实验 5:验证 `NOWAIT` 报错

```sql
-- 会话 A
BEGIN;
SELECT * FROM lock_demo WHERE id = 1 FOR UPDATE;

-- 会话 B
SELECT * FROM lock_demo WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR: could not obtain lock on row in relation "lock_demo"
```

### 实验 6:验证 advisory lock

```sql
-- 会话 A
SELECT pg_advisory_lock(999);
-- 会话 B
SELECT pg_try_advisory_lock(999);   -- 返回 false
-- 会话 A
SELECT pg_advisory_unlock(999);
-- 会话 B
SELECT pg_try_advisory_lock(999);   -- 返回 true
```

### 实验 7:观察 DDL 的锁级别

```sql
-- 会话 A
BEGIN;
SELECT * FROM lock_demo LIMIT 1;    -- ACCESS SHARE

-- 会话 B
ALTER TABLE lock_demo ADD COLUMN x int;   -- 需要 ACCESS EXCLUSIVE → 阻塞!

-- 会话 C
SELECT pid, locktype, relation::regclass, mode, granted
FROM pg_locks WHERE relation = 'lock_demo'::regclass;
-- 会看到 ACCESS SHARE(granted=t)与 ACCESS EXCLUSIVE(granted=f)
```

## ⑤ 生产启示

| 结论 | 行动 |
|------|------|
| 行锁不在锁表里,靠 `xmax` | 行锁等待表现为"等一个 transactionid",不是表锁 |
| DDL 取 `ACCESS EXCLUSIVE` | **DDL 会阻塞一切**;生产必须用 `CONCURRENTLY` / `NOT VALID` + `VALIDATE`,并设 `lock_timeout` |
| `CREATE INDEX` 阻塞写入 | 一律用 `CREATE INDEX CONCURRENTLY` |
| 死锁靠应用规避 | **统一加锁顺序**;捕获 SQLSTATE `40P01` 并重试 |
| `SKIP LOCKED` 是队列利器 | 任务分发首选;注意它会返回"不完整视图",不适合做分页 |
| advisory lock 用事务级 | 避免会话级锁泄漏,且与连接池兼容 |
| LWLock 争用是高并发瓶颈 | 关注 `wait_event_type = 'LWLock'` 的分布 |
| 锁表容量需充足 | 分区多、一次操作涉及大量对象时,可能需要提高 `max_locks_per_transaction` |
| 排查工具:`pg_blocking_pids` | 比手工 JOIN `pg_locks` 可靠 |

```sql
-- 阻塞与锁等待监控 ★ 排障必备
SELECT
    pid, usename, application_name, state,
    wait_event_type, wait_event,
    now() - query_start AS running,
    pg_blocking_pids(pid) AS blockers,
    left(query, 60) AS q
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0
ORDER BY query_start;

-- 锁模式分布
SELECT relation::regclass AS obj, mode, granted, count(*)
FROM pg_locks
WHERE relation IS NOT NULL
GROUP BY 1,2,3
HAVING count(*) > 1
ORDER BY 4 DESC;

-- 死锁统计(需 log_lock_waits 与日志)
SHOW log_lock_waits;          -- 建议 on(记录超过 deadlock_timeout 的等待)
SELECT deadlocks, stats_reset FROM pg_stat_database WHERE datname = current_database();
```

> **建议开启 `log_lock_waits = on`**:它会把"等待锁超过 `deadlock_timeout` 的语句"写进日志,即使没形成死锁。这是发现"隐式长锁等待"的有效手段。
