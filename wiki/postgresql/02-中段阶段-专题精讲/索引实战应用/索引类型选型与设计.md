# 索引类型选型与设计

## 一、B-tree(默认)

### 适用与限制

| 支持 | 不支持 |
|------|--------|
| `=` `<` `>` `<=` `>=` | 后缀/中间匹配(`LIKE '%x'`) |
| `BETWEEN`、`IN` | 正则 |
| `IS NULL` / `IS NOT NULL` | 数组包含 |
| `LIKE 'prefix%'`(需 `text_pattern_ops` 或 `C` collation) | 函数结果(除非表达式索引) |
| `ORDER BY`(同序同向) | |

### 多列索引与最左前缀

```sql
CREATE INDEX idx ON t (a, b, c);
```

**这个索引能服务的查询**

| 查询条件 | 能否用 |
|----------|--------|
| `a = ?` | ✅ |
| `a = ? AND b = ?` | ✅ |
| `a = ? AND b = ? AND c = ?` | ✅ |
| `a = ? AND c = ?` | ⚠️ 只能用 `a`,c 退化为过滤 |
| `b = ?` | ❌ |
| `b = ? AND c = ?` | ❌ |
| `a > ? AND b = ?` | ⚠️ b 无法用于定位(范围后的列失去定位能力) |
| `a = ? AND b > ? AND c = ?` | ⚠️ c 无法定位 |
| `ORDER BY a, b, c` | ✅ 免排序 |
| `ORDER BY b` | ❌ 需排序 |
| `ORDER BY a, b DESC` | ⚠️ 取决于索引方向定义 |

**列顺序设计规则**

1. **等值条件列在前**,范围条件列在后。
2. **排序列**紧跟等值列之后,便于免排序。
3. **选择性高的列不一定放最前** —— 若有等值条件,列的具体顺序影响较小;但如果某列单独查询高频,它必须是最左列或单独建索引。
4. 优先复用已有索引的**最左前缀**,避免为每种组合都建索引。

```sql
-- 场景:WHERE tenant_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20
CREATE INDEX orders_tenant_status_created_idx
    ON orders (tenant_id, status, created_at DESC);   -- 等值 + 等值 + 排序,最优
```

### 索引方向

```sql
CREATE INDEX ON t (a ASC, b DESC);   -- 混合方向
```

**双向扫描规则**:单列索引可正反扫描;多列索引**整体反向**(全部取反)也可用。

| 索引 | `ORDER BY a, b DESC` | `ORDER BY a DESC, b` | `ORDER BY a, b` |
|------|----------------------|----------------------|-----------------|
| `(a, b DESC)` | ✅ | ✅(整体反向) | ❌ |

### 唯一索引

```sql
CREATE UNIQUE INDEX ON t (email);
CREATE UNIQUE INDEX ON t (lower(email));            -- 大小写不敏感
CREATE UNIQUE INDEX ON t (tenant_id, code) WHERE deleted_at IS NULL;   -- 部分唯一
```

PG15+ 支持 `NULLS NOT DISTINCT`:

```sql
CREATE UNIQUE INDEX ON t (code) NULLS NOT DISTINCT;   -- NULL 之间也判重
```

### 表达式索引

```sql
-- 列上加函数后,普通索引失效;表达式索引可救
CREATE INDEX ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.c';     -- ✅ 可用

CREATE INDEX ON orders ((date_trunc('day', created_at)));
SELECT * FROM orders WHERE date_trunc('day', created_at) = current_date;   -- ✅

CREATE INDEX ON orders (((ext->>'city')));
SELECT * FROM orders WHERE ext->>'city' = 'BJ';       -- ✅
```

**硬性要求:查询表达式必须与索引表达式"逐字一致"(语义等价)。**

```sql
CREATE INDEX ON t ((a + b));
SELECT * FROM t WHERE a + b = 10;      -- ✅
SELECT * FROM t WHERE b + a = 10;      -- ⚠️ 通常不能用(优化器未必等价化简)
```

表达式必须是 **IMMUTABLE**:

```sql
CREATE INDEX ON t (now());              -- ❌ 报错:函数不是 immutable
CREATE INDEX ON t ((created_at::date)); -- ✅ 类型转换通常 immutable
```

### 部分索引(Partial Index)

只索引满足条件的行,**体积更小、维护更轻**。

```sql
-- 只索引未完成订单(查询几乎都带这个条件)
CREATE INDEX orders_active_idx ON orders (created_at DESC)
    WHERE status IN ('pending','paid','shipped');

-- 查询必须包含同样的条件(或更强),索引才可用
SELECT * FROM orders WHERE status = 'paid' AND created_at > now() - interval '7 days';
```

**部分索引的适用判据**

| 判据 | 说明 |
|------|------|
| 条件选择性高 | 索引的行占比越小,收益越大 |
| 查询稳定带该条件 | 否则索引用不上 |
| 该列有"热区" | 如"未删除""未完成""活跃" |

```sql
-- 经典:软删除只索引未删除行
CREATE INDEX ON posts (created_at DESC) WHERE deleted_at IS NULL;

-- 经典:只索引非空
CREATE INDEX ON orders (shipped_at) WHERE shipped_at IS NOT NULL;
```

> **陷阱**:若部分索引的条件与查询条件**不匹配**(如索引 `WHERE status='paid'`,查询 `WHERE status <> 'canceled'`),规划器**无法**证明溢出关系,索引不会被用。条件必须能被逻辑推导包含。

### 覆盖索引(INCLUDE)

把"查询需要但不参与定位"的列放进索引的叶子层,使查询可走 **Index Only Scan**。

```sql
-- 索引键 (user_id),额外携带 amount、created_at
CREATE INDEX orders_user_cover_idx ON orders (user_id) INCLUDE (amount, created_at);

-- 若可见性映射干净,可走 Index Only Scan(不回表)
EXPLAIN SELECT user_id, amount, created_at FROM orders WHERE user_id = 5;
```

**要点**

| 要点 | 说明 |
|------|------|
| `INCLUDE` 列 | 不参与排序与定位,只作为附加载荷 |
| 收益 | 免回表,减少随机 I/O |
| 条件 | 需 Visibility Map 干净(近期 VACUUM 过),否则仍需回表取可见性 |
| 代价 | 索引变大;INCLUDE 列更新也要维护 |

> **与"把列放进键里"的区别**:`(user_id, amount)` 会让 `amount` 参与排序与定位,语义不同;`(user_id) INCLUDE (amount)` 只带数据不改语义。要免排序取列时用前者,要免回表时用后者。

## 二、GIN

**倒排索引**:从"元素"指向"包含它的行"。

```sql
-- 数组
CREATE INDEX ON posts USING gin (tags);
-- JSONB
CREATE INDEX ON events USING gin (payload);
CREATE INDEX ON events USING gin (payload jsonb_path_ops);   -- 更小更快,但不支持 ?
-- 全文检索
CREATE INDEX ON docs USING gin (to_tsvector('simple', body));
-- pg_trgm 模糊匹配
CREATE INDEX ON users USING gin (name gin_trgm_ops);
```

| 特性 | 说明 |
|------|------|
| 支持操作符 | `@>` `<@` `&&` `?` `?|` `?&` `@@` 等 |
| 写入成本 | 高(每个元素一条索引项) |
| 读取成本 | 需合并 posting list,可能产生较多候选行(需 recheck) |
| `fastupdate` | 默认 on,写入快但读可能需合并 pending list |
| 体积 | 通常显著大于 B-tree |

## 三、GiST

**通用平衡树**,适合"不精确匹配"的场景。

```sql
CREATE INDEX ON places USING gist (location);            -- PostGIS 几何
CREATE INDEX ON bookings USING gist (during);            -- 范围重叠
CREATE INDEX ON t USING gist (ip_range);                 -- 网络范围
```

| 特性 | 说明 |
|------|------|
| 支持操作符 | `&&` `@>` `<@` `<<` `>>` `~=` 等(按 opclass) |
| 特点 | 可能是**有损**的,查询需 recheck |
| 常用搭配 | `EXCLUDE` 约束、范围类型、几何类型 |
| `btree_gist` | 让普通类型(`text`、`int`)也能进 GiST,支持 `EXCLUDE` 的多列组合 |

## 四、SP-GiST

**空间分区树**,适合**非平衡**数据结构:四叉树、k-d 树、前缀树。

```sql
CREATE INDEX ON points USING spgist (p);                 -- 点
CREATE INDEX ON t USING spgist (ip);                     -- inet(前缀树)
CREATE INDEX ON t USING spgist (phone text_ops);         -- 前缀(类似 trie)
```

适合"点查询密集、数据分布不均"的场景;范围查询通常不如 GiST。

## 五、BRIN

**块范围索引**:记录每个"数据块区间"的摘要(min/max),体积极小。

```sql
-- 适用:超大表(亿级)+ 物理有序(如按时间追加写入)
CREATE INDEX ON logs USING brin (created_at) WITH (pages_per_range = 64);

-- 若数据物理顺序与索引列相关性强(高 correlation),效果最好
SELECT correlation FROM pg_stats WHERE tablename = 'logs' AND attname = 'created_at';
-- 接近 ±1 表示强相关 → BRIN 适合
```

| 维度 | BRIN | B-tree |
|------|------|--------|
| 体积 | 极小(约 1/1000) | 大 |
| 适用 | 物理有序的超大表 | 通用 |
| 选择性 | 低(需扫描整个 block range) | 高 |
| 典型 | 时间序列表、日志、IoT | 一切 |

**判据**:表很大 + 按某列顺序写入 + 查询总是范围过滤该列 → BRIN 用极小的代价换来可用的剪枝。

## 六、Hash

```sql
CREATE INDEX ON t USING hash (col);
```

仅支持 `=`,且**不参与排序**。B-tree 几乎总能替代它。唯一价值:键很长(如长 UUID、长文本)时,Hash 索引体积略小、等值查找略快。**实践中很少用。**

## 七、索引维护

```sql
-- 创建(阻塞写)
CREATE INDEX idx ON t (col);
-- 并发创建(不阻塞写,但更慢,且失败会留下 invalid 索引)
CREATE INDEX CONCURRENTLY idx ON t (col);

-- 检查是否有 invalid 索引(CONCURRENTLY 失败残留)
SELECT indexrelid::regclass, indrelid::regclass
FROM pg_index WHERE NOT indisvalid;

-- 重建(整表重建,阻塞)
REINDEX INDEX idx;
-- 并发重建(PG12+)
REINDEX INDEX CONCURRENTLY idx;
REINDEX TABLE CONCURRENTLY t;

-- 删除
DROP INDEX idx;
DROP INDEX CONCURRENTLY idx;

-- 重命名
ALTER INDEX idx RENAME TO idx2;
ALTER INDEX idx SET (fillfactor = 90);
```

**`CONCURRENTLY` 的注意事项**

| 事项 | 说明 |
|------|------|
| 不能在事务块内运行 | 会被拒绝 |
| 耗时为普通创建的 2–3 倍 | 需两次扫描 + 等待旧事务 |
| 失败会留下 `indisvalid = false` 的索引 | 必须手工 `DROP` |
| 建唯一索引失败 | 说明确实存在重复值 |

**索引膨胀与 `fillfactor`**

```sql
-- 写密集表留出填充空间,减少页分裂
CREATE INDEX ON t (col) WITH (fillfactor = 90);
```

## 八、决策流程

```
需要索引吗?
  ├─ 查询频率低 / 表很小 → 不建
  └─ 高频且选择性好 → 建
        │
        ├─ 等值 / 范围 / 排序 → B-tree
        │     ├─ 多列?→ 等值列在前,范围列在后,排序列紧随等值列
        │     ├─ 列上有函数?→ 表达式索引
        │     ├─ 只查子集?→ 部分索引
        │     └─ 要免回表?→ INCLUDE 覆盖索引
        │
        ├─ 多值(数组/JSONB/全文) → GIN
        ├─ 范围重叠 / 几何 / 排他约束 → GiST
        ├─ 点 / IP / 前缀 → SP-GiST
        ├─ 超大表 + 物理有序 → BRIN
        └─ 仅等值 + 键很长 → Hash(罕见)
```
