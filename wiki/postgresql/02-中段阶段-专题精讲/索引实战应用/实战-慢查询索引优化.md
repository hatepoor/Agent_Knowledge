# 实战:慢查询索引优化

## 优化流程总览

```
1. 定位慢查询(pg_stat_statements / log_min_duration_statement)
        ↓
2. 取到真实参数下的执行计划(EXPLAIN ANALYZE BUFFERS)
        ↓
3. 判断瓶颈类型(扫描量大 / 估算偏差 / 排序落盘 / 回表多 / 数据膨胀)
        ↓
4. 选择对策(索引 / 改写 SQL / 调参 / 结构改造)
        ↓
5. 验证(前后对比耗时与 buffers)
```

## 第一步:定位慢查询

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 按总耗时
SELECT
    round(total_exec_time::numeric, 1) AS total_ms,
    calls,
    round(mean_exec_time::numeric, 2)   AS mean_ms,
    round(100 * total_exec_time / sum(total_exec_time) OVER (), 1) AS pct,
    rows,
    left(query, 80) AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- Top 10 按单次最慢
SELECT calls, round(mean_exec_time::numeric,2) AS mean_ms,
       round(max_exec_time::numeric,2) AS max_ms, left(query,80)
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 10;

-- 关注"调用多但单次不快"的查询(总量大)
SELECT calls, round(total_exec_time::numeric,1) AS total_ms, left(query,80)
FROM pg_stat_statements WHERE calls > 1000 ORDER BY total_exec_time DESC LIMIT 10;
```

> **优化顺序很重要**:先优化"总耗时占比高"的查询。单次快但每秒调用上千次的查询,收益往往大于偶发的大查询。

```sql
-- 或直接用日志抓真慢查询
ALTER SYSTEM SET log_min_duration_statement = '500ms';
SELECT pg_reload_conf();
```

## 第二步:取真实计划

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)
SELECT ...;   -- 用真实参数,而不是占位符
```

**重点看四个信号**

| 信号 | 含义 |
|------|------|
| `rows=X (actual ... rows=Y)`,X 与 Y 差很多 | **估算错误** → 统计信息问题 |
| `Seq Scan` 且 `rows` 很大 | 缺索引,或索引未被用 |
| `Sort Method: external merge Disk: xxxkB` | 排序落盘 → `work_mem` 不足 |
| `Buffers: shared read=NNN` 很大 | 物理读多 → 缓存未命中 |
| `Rows Removed by Filter: NNNN` 很大 | 过滤发生在扫描之后 → 索引不匹配 |

## 案例一:缺索引导致 Seq Scan

```sql
-- 慢查询
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total FROM orders WHERE user_id = 12345;
```

```
Seq Scan on orders  (cost=0.00..38462.00 rows=12 width=16)
                    (actual time=0.015..198.443 rows=15 loops=1)
  Filter: (user_id = 12345)
  Rows Removed by Filter: 1999985
Buffers: shared hit=20123
```

**诊断**:读了两百万行只为找 15 行,`Rows Removed by Filter` 巨大 → 典型缺索引。

```sql
CREATE INDEX CONCURRENTLY orders_user_id_idx ON orders (user_id);
ANALYZE orders;
```

```
Index Scan using orders_user_id_idx on orders
  (actual time=0.028..0.041 rows=15 loops=1)
Buffers: shared hit=4
```

**收益**:从 ~200ms、2 万 buffer 降到 0.04ms、4 buffer。

> 这也是 [[postgresql/01-入门阶段-基础教程/第03章-建表与约束/3.2-约束体系与数据完整性]] 中"外键列必须建索引"的原因。

## 案例二:列上有函数导致索引失效

```sql
CREATE INDEX orders_created_idx ON orders (created_at);

-- ⚠️ 慢:对列做函数,普通索引不可用
EXPLAIN (ANALYZE)
SELECT * FROM orders WHERE date_trunc('day', created_at) = date '2026-09-19';
-- Seq Scan + Filter: (date_trunc('day'::text, created_at) = ...)

-- ✅ 改写一:半开区间(推荐)
EXPLAIN (ANALYZE)
SELECT * FROM orders
WHERE created_at >= date '2026-09-19'
  AND created_at <  date '2026-09-19' + 1;
-- Index Scan using orders_created_idx

-- ✅ 改写二:确需按表达式过滤 → 建表达式索引
CREATE INDEX orders_created_day_idx ON orders ((date_trunc('day', created_at)));
```

**结论**:优先改写 SQL;改写不了(如 ORM 生成)再建表达式索引。

## 案例三:隐式类型转换导致索引失效

```sql
CREATE TABLE p (id bigint PRIMARY KEY, code text);
CREATE INDEX ON p (code);

-- ⚠️ 字面量是整数,列是 text
EXPLAIN SELECT * FROM p WHERE code = 12345;
-- 可能 Seq Scan(取决于转换函数是否 immutable)

-- ✅ 类型一致
EXPLAIN SELECT * FROM p WHERE code = '12345';
```

**对策**:应用侧保证参数类型与列一致;或用显式转换;必要时为该转换建表达式索引。

## 案例四:估算错误(统计信息)

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE channel = 'web' AND status = 'paid';
```

```
Index Scan using ... (cost=... rows=100 width=...) (actual ... rows=45231 loops=1)
```

**估算 100,实际 4.5 万 → 差 450 倍**,规划器会因此选错连接算法(如误选 Nested Loop)。

**原因与对策**

| 原因 | 对策 |
|------|------|
| 统计信息过期 | `ANALYZE orders;` |
| 列间相关性(两列都低基数但有强相关) | `CREATE STATISTICS`(多变量统计) |
| 采样不足 | 提高该列 `default_statistics_target` |

```sql
-- 多变量统计(解决列间相关性)
CREATE STATISTICS orders_channel_status_stat (dependencies, ndistinct)
    ON channel, status FROM orders;
ANALYZE orders;

-- 提高单列采样精度
ALTER TABLE orders ALTER COLUMN channel SET STATISTICS 1000;
ANALYZE orders;

-- 验证
SELECT * FROM pg_stats WHERE tablename='orders' AND attname='channel';
SELECT * FROM pg_statistic_ext WHERE stxname LIKE 'orders%';
```

## 案例五:排序落盘

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20;
```

```
Sort  (cost=... rows=2000000) (actual time=3201.5..3201.5 rows=20)
  Sort Key: created_at DESC
  Sort Method: external merge  Disk: 245760kB     ← 落盘!
  ->  Seq Scan on orders  (cost=...)
```

**对策(按优先级)**

```sql
-- 1) 建索引,让"排全表"变成"读前 20 行"
CREATE INDEX CONCURRENTLY orders_created_desc_idx ON orders (created_at DESC);
-- 计划变为 Index Scan + Limit,buffers 从数万降到个位数

-- 2) 若无法建索引,临时增大 work_mem(会内存排序)
SET work_mem = '256MB';

-- 3) 缩小参与排序的行数
... WHERE created_at > now() - interval '7 days' ORDER BY created_at DESC LIMIT 20
```

> **`ORDER BY ... LIMIT N` + 同序索引**是性价比最高的一类优化。

## 案例六:多列索引顺序不当

```sql
-- 查询:WHERE status = 'paid' ORDER BY created_at DESC LIMIT 20
-- status 只有 5 个值,选择性极低

-- ⚠️ 索引顺序错了(低基数列在前,只能定位到 40% 的数据再排序)
CREATE INDEX ON orders (status, created_at DESC);
-- 计划:Bitmap Heap Scan + Sort(还是要排序,且扫描量大)

-- ✅ 正确:甚至单独用 created_at
CREATE INDEX ON orders (created_at DESC);
-- 计划:Index Scan + Limit(直接顺序读前 20 条满足条件的)

-- 若 status 选择性提高(如按 tenant 隔离):
CREATE INDEX ON orders (tenant_id, created_at DESC);
```

**结论**:低基数(值很少)的列单独放在最左列通常**没用**。应让**排序列**靠前,或把低基数列做成**部分索引**:

```sql
CREATE INDEX ON orders (created_at DESC) WHERE status = 'paid';
```

## 案例七:表膨胀导致扫描慢

```sql
SELECT relname, n_live_tup, n_dead_tup,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
       last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 100000
ORDER BY n_dead_tup DESC;
```

**若死元组占比高**:表与索引都膨胀,扫描同样的逻辑行数需读更多页。

```sql
VACUUM (VERBOSE, ANALYZE) orders;   -- 回收可复用空间
-- 若已严重膨胀且需真正缩小文件
VACUUM FULL orders;                 -- ⚠️ 排他锁,需停机窗口
-- 或
pg_repack                          -- 需扩展,可在线重建
```

## 案例八:无用索引拖慢写入

```sql
-- 找出从未使用且非约束的索引
SELECT s.relname, s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
LEFT JOIN pg_constraint c ON c.conindid = s.indexrelid
WHERE s.idx_scan = 0 AND c.oid IS NULL
ORDER BY pg_relation_size(s.indexrelid) DESC;
```

**评估后删除**:

```sql
DROP INDEX CONCURRENTLY idx_unused;
```

> **重要**:`idx_scan` 统计在实例重启后可能归零。删索引前应确认统计已积累足够时间(如观察一个月),并排除"仅在月末/季度末使用"的周期性索引。

## 优化检查清单

| 检查项 | 命令/方法 |
|--------|-----------|
| 是否缺索引 | 计划里 `Rows Removed by Filter` 大 |
| 索引是否被用 | `EXPLAIN` 是否出现 Index Scan |
| 列上是否有函数 | 检查 `WHERE` / `JOIN` 条件 |
| 类型是否一致 | 对比参数与列类型 |
| 估算是否准确 | 对比 `rows` 与 `actual rows` |
| 是否排序落盘 | `Sort Method: external merge` |
| 是否回表多 | `Heap Fetches` 高(Index Only Scan 未生效) |
| 统计是否新鲜 | `last_analyze` / `last_autoanalyze` |
| 表索引是否膨胀 | `pg_stat_user_tables.n_dead_tup` |
| 是否存在无用索引 | `pg_stat_user_indexes.idx_scan = 0` |

```sql
-- 一次性检查统计新鲜度
SELECT relname, n_live_tup, n_dead_tup, last_analyze, last_autoanalyze, last_vacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 20;
```
