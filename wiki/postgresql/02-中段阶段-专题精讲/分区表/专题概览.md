# 分区表 · 专题概览

## 专题定位

分区把一张逻辑大表拆成多个物理子表,使"按范围访问"的操作只碰相关子表。

**何时该翻这个专题**

- 单表上亿行,查询与维护都变慢
- 历史数据需要按时间归档/删除
- 按租户/区域隔离数据

**分区能解决什么 / 不能解决什么**

| 能 | 不能 |
|----|------|
| 分区裁剪(只扫相关分区) | 让单分区内的查询变快 |
| 按分区批量 `DETACH`/`DROP`(秒级归档) | 凭空提升并发能力 |
| 分区间并行扫描 | 替代索引(分区内仍需索引) |
| 分区级 VACUUM/REINDEX 更可控 | 解决"单点写入瓶颈" |

> **关键认知**:分区是**管理手段** + **裁剪优化**。若查询不带分区键,所有分区都会被扫,比不分区更慢(要扫 N 个表 + Append)。

## 一、声明式分区(PG10+)

```sql
-- 父表(分区根表):只定义结构,不存数据
CREATE TABLE measurements (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    device_id  bigint NOT NULL,
    ts         timestamptz NOT NULL,
    value      numeric(12,3),
    PRIMARY KEY (id, ts)          -- ★分区键必须包含在唯一约束中
) PARTITION BY RANGE (ts);

-- 子分区
CREATE TABLE measurements_2026_09 PARTITION OF measurements
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE TABLE measurements_2026_10 PARTITION OF measurements
    FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

**硬性约束:分区键必须包含在所有唯一索引/主键中。**

理由:唯一性只能在单个分区内保证,跨分区无法高效校验。因此 `PRIMARY KEY (id)` 单列不合法。

```sql
-- ❌ ERROR: unique constraint on partitioned table must include all partitioning columns
PRIMARY KEY (id)

-- ✅
PRIMARY KEY (id, ts)
```

## 二、三种分区策略

### RANGE(最常用)

```sql
PARTITION BY RANGE (ts)
-- 或按多列
PARTITION BY RANGE (tenant_id, ts)
```

适合:时间序列、按 ID 区间。

### LIST

```sql
CREATE TABLE orders (id bigint, region text NOT NULL, ...) PARTITION BY LIST (region);
CREATE TABLE orders_cn PARTITION OF orders FOR VALUES IN ('cn');
CREATE TABLE orders_us PARTITION OF orders FOR VALUES IN ('us');
```

适合:离散分类(区域、租户、状态)。

### HASH

```sql
CREATE TABLE users (id bigint NOT NULL, ...) PARTITION BY HASH (id);
CREATE TABLE users_p0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE users_p1 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 1);
```

适合:无明显范围特征、需要均匀打散。

**也可以组合(多级分区)**:

```sql
CREATE TABLE m (id bigint, ts timestamptz NOT NULL, region text NOT NULL)
    PARTITION BY RANGE (ts);
CREATE TABLE m_2026_09 PARTITION OF m FOR VALUES FROM ('2026-09-01') TO ('2026-10-01')
    PARTITION BY LIST (region);
CREATE TABLE m_2026_09_cn PARTITION OF m_2026_09 FOR VALUES IN ('cn');
```

多级分区会增加规划开销,慎用超过两级。

## 三、分区裁剪(Partition Pruning)

**分区裁剪是本专题的核心收益来源。**

```sql
-- ✅ 能裁剪:条件含分区键
EXPLAIN SELECT * FROM measurements WHERE ts >= '2026-09-15' AND ts < '2026-09-20';
-- 计划里只出现 measurements_2026_09(其他分区不进计划)

-- ❌ 不能裁剪:条件不含分区键
EXPLAIN SELECT * FROM measurements WHERE value > 100;
-- 计划里出现所有分区(Append)
```

**PG11+ 支持运行时裁剪**:参数化查询在**执行时**才知道参数值,也能裁剪。

```sql
PREPARE p(timestamptz) AS SELECT * FROM measurements WHERE ts >= $1;
-- PG11 之前:计划包含所有分区
-- PG11+ :执行时按参数值裁剪
```

**影响裁剪的写法**

| 写法 | 能否裁剪 |
|------|----------|
| `WHERE ts >= '2026-09-15'` | ✅ |
| `WHERE ts BETWEEN a AND b` | ✅ |
| `WHERE date_trunc('day', ts) = '2026-09-15'` | ❌ 对分区键做函数 |
| `WHERE ts::date = '2026-09-15'` | ❌ 转换后失去区间信息(部分情况可) |
| `WHERE ts + interval '1 day' > now()` | ❌ |
| `WHERE EXTRACT(month FROM ts) = 9` | ❌ |

**规则:分区键上的条件必须是"原值比较"或可静态化简的区间。**

```sql
-- 改写成可裁剪的写法
WHERE ts >= date_trunc('day', now()) AND ts < date_trunc('day', now()) + 1
```

## 四、分区管理

```sql
-- 查看分区树
\d+ measurements
SELECT * FROM pg_partition_tree('measurements');
SELECT relname, pg_get_expr(relpartbound, oid) AS bound
FROM pg_class WHERE relispartition AND relname LIKE 'measurements%';

-- 新增分区
CREATE TABLE measurements_2026_11 PARTITION OF measurements
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

-- 分离分区(DETACH):变成独立表,秒级完成
ALTER TABLE measurements DETACH PARTITION measurements_2026_08;
-- 并发分离(PG14+)
ALTER TABLE measurements DETACH PARTITION measurements_2026_08 CONCURRENTLY;

-- 挂载已有表为分区(数据不移动,只做元数据操作 + 校验)
ALTER TABLE measurements ATTACH PARTITION m_2026_08
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');
-- 若确定数据合规,可跳过扫描校验
ALTER TABLE measurements ATTACH PARTITION m_2026_08
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01') /* 需先加 CHECK 约束证明 */
```

> **归档模式**:`DETACH` 旧分区 → `pg_dump` 或直接搬到归档库 → `DROP TABLE`。**比 `DELETE FROM 大表 WHERE ts < ...` 快几个数量级**,这是分区最大的运维收益。

### DEFAULT 分区

```sql
CREATE TABLE measurements_default PARTITION OF measurements DEFAULT;
```

作用:接收不匹配任何分区的行,避免插入失败。**但要注意**:有 DEFAULT 分区时,新增普通分区需**扫描 DEFAULT 分区**确认无冲突行,可能很慢。PG 会因此对 `ATTACH` 加锁更重。

### 索引

```sql
-- 在父表上建索引,自动传播到现有与未来分区(PG11+)
CREATE INDEX ON measurements (device_id, ts);

-- 单独为某分区建索引
CREATE INDEX ON measurements_2026_09 (device_id);
```

> 每个分区都有自己的索引副本。分区多时索引总数 = 分区数 × 索引数,维护开销与磁盘占用都成倍增长。

## 五、分区 vs 手工分表 + UNION

| 维度 | 声明式分区 | 手工分表 + UNION ALL 视图 | 触发器分表 |
|------|-----------|--------------------------|-----------|
| 裁剪 | ✅ 自动 | ❌ 需手工改视图 | ❌ |
| 插入路由 | ✅ 自动 | ❌ 应用决定 | ✅ 触发器 |
| 全局唯一约束 | ⚠️ 需含分区键 | ❌ | ❌ |
| 维护复杂度 | 低 | 中 | 高 |
| 跨分区查询 | 原生 | UNION 拼接 | UNION 拼接 |

**结论**:新项目一律用声明式分区。手工分表只存在于存量系统。

## 六、分区键选择

| 业务 | 分区键 | 策略 |
|------|--------|------|
| 订单/日志/指标 | `created_at` / `ts` | RANGE(按月/日) |
| 多租户 SaaS | `tenant_id` | LIST 或 HASH |
| 区域隔离 | `region` | LIST |
| 无明显特征的大表 | 主键 | HASH |

**选择原则**

1. **查询几乎总是带该条件** —— 否则裁剪无效。
2. **分区数量适中**:几十到几百。过多(如按小时分年)会导致规划开销与元数据管理压力。
3. **分区大小均匀**:避免"一个分区特别大"的倾斜。

**检查分区大小**:

```sql
SELECT child.relname AS partition,
       pg_size_pretty(pg_total_relation_size(child.oid)) AS size,
       pg_stat_get_live_tuples(child.oid) AS live_rows
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child  ON pg_inherits.inhrelid  = child.oid
JOIN pg_class p ON p.oid = parent.oid
WHERE parent.relname = 'measurements'
ORDER BY child.relname;
```

## 七、版本演进要点

| 版本 | 分区相关改进 |
|------|-------------|
| PG10 | 声明式分区引入 |
| PG11 | 父表索引传播;运行时裁剪;默认分区 |
| PG12 | 大量性能改进(不逐分区加锁);`ATTACH` 更高效 |
| PG13 | 分区裁剪增强;跨分区聚合优化;`DETACH CONCURRENTLY` 前置 |
| PG14 | `DETACH PARTITION CONCURRENTLY` |
| PG15 | 更多裁剪场景(如 `IS NULL`、`NOT IN` 的多值) |
| PG16 | 分区表上更多操作支持 |
| PG17 | 分区表身份/继承行为改进 |
| **PG18** | VACUUM/ANALYZE **默认处理继承子分区**(此前需 `ONLY` 反向操作);分区表 VACUUM 进度上报;分区表**不允许 UNLOGGED** |

> **PG18 兼容性提示**:两处行为变化需要留意。
> 1. `VACUUM` / `ANALYZE` 现在默认会处理继承子表;要保持旧行为需显式加 `ONLY`。
> 2. **不允许创建 UNLOGGED 分区表**。此前 `ALTER TABLE ... SET UNLOGGED` 对分区表静默无效果,现在明确禁止。

## 八、常见陷阱

| 陷阱 | 后果 | 修正 |
|------|------|------|
| 查询不带分区键 | 扫全部分区,更慢 | 保证查询带分区键,或重新选键 |
| 分区键上做函数 | 无法裁剪 | 改写为区间比较 |
| 唯一约束不含分区键 | 无法创建 | 把分区键加入唯一约束 |
| 分区过多(成千) | 规划慢、元数据膨胀 | 提高分区粒度 |
| 忘记建新分区 | 插入报错(或进 DEFAULT) | 用 `pg_partman` 自动管理 |
| 各分区索引不统一 | 计划不一致 | 在父表统一建索引 |
| 用分区替代索引 | 分区内仍全扫 | 分区内仍需合适索引 |

**自动分区管理**:生产上通常用 `pg_partman` 扩展自动创建未来分区、归档旧分区。
