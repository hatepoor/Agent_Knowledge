# CTE 与递归查询 · 专题概览

## 专题定位

CTE(Common Table Expression,公用表表达式)用 `WITH` 定义**命名中间结果**,解决两个问题:

1. **可读性**:把深层嵌套的子查询拉平成顺序化的步骤。
2. **递归**:表达树形 / 图结构的遍历(这是 CTE 不可替代的能力)。

**何时该翻这个专题**

- 子查询嵌套超过 2 层,读不下去
- 需要同一个中间结果被多次引用
- 数据有父子关系(组织架构、分类树、评论回复、BOM 物料清单)
- 需要图遍历(最短路径、可达性)

## 一、基本语法

```sql
WITH
  a AS (SELECT ...),
  b AS (SELECT ... FROM a JOIN x ON ...)
SELECT * FROM b;
```

**与子查询对比**

```sql
-- 子查询:同一计算结果写两遍
SELECT * FROM users u
WHERE (SELECT count(*) FROM orders o WHERE o.user_id = u.id) > 3
  AND (SELECT count(*) FROM orders o WHERE o.user_id = u.id) < 10;

-- CTE:写一遍,引用两次
WITH oc AS (SELECT user_id, count(*) AS cnt FROM orders GROUP BY user_id)
SELECT u.* FROM users u JOIN oc ON oc.user_id = u.id
WHERE oc.cnt > 3 AND oc.cnt < 10;
```

## 二、CTE 的物化行为(重点)

这是 CTE 性能上最关键的知识点。

| 版本 | 默认行为 |
|------|----------|
| PG11 及更早 | CTE **总是物化**(生成临时结果集),且**优化器不能下推条件** —— 常被称为"优化栅栏(optimization fence)" |
| **PG12+** | 若不满足"多次引用"等条件,CTE **可能被内联(inline)** 到主查询,条件可下推 |

**显式控制(PG12+)**

```sql
-- 强制物化:适合"计算昂贵且被引用多次"
WITH c AS MATERIALIZED (SELECT expensive_agg() FROM big_table)
SELECT ... FROM c;   -- 被引用多次时避免重复计算

-- 强制内联:适合"CTE 是简单过滤,希望条件能下推到基表"
WITH c AS NOT MATERIALIZED (SELECT * FROM big_table WHERE flag)
SELECT * FROM c WHERE created_at > '2026-01-01';
-- 内联后,created_at 条件可下推到 big_table,可能用上索引
```

**实战判据**

| 场景 | 选择 | 原因 |
|------|------|------|
| CTE 被引用 1 次且条件选择性高 | `NOT MATERIALIZED` | 允许条件下推,可能吃到索引 |
| CTE 被引用多次 | `MATERIALIZED` | 避免重复计算 |
| CTE 含聚合/排序等昂贵操作 | `MATERIALIZED` | 只算一次 |
| CTE 含 `LIMIT` 且被外层过滤 | `MATERIALIZED` | 内联可能改变语义 |

> **典型症状**:同一个查询改成 CTE 后突然变慢 10 倍(或变快 10 倍),八成就是物化与内联差异。用 `EXPLAIN` 看计划里是否出现 `CTE Scan` 节点 —— 有则是物化,无则是内联。

## 三、`WITH ... SELECT ... ` 的几种用法

```sql
-- 1) 在 INSERT / UPDATE / DELETE 前定义
WITH target AS (SELECT id FROM orders WHERE status = 'canceled' LIMIT 1000)
DELETE FROM orders o USING target t WHERE o.id = t.id;

-- 2) 数据修改型 CTE(DML CTE):CTE 内可以做 INSERT/UPDATE/DELETE
WITH moved AS (
    DELETE FROM orders WHERE status = 'canceled' RETURNING *
)
INSERT INTO orders_archive SELECT * FROM moved;

-- 3) 为多个顶层语句共享(少见)
WITH a AS (...), b AS (...)
INSERT INTO t1 SELECT * FROM a
;
-- 注意:WITH 只作用于紧跟的一个语句
```

**DML CTE 的注意事项**

- DML CTE 互不可见:同一 `WITH` 里的多个 DML CTE **不能互相看到对方的效果**,执行顺序不确定。
- 顶层语句若也是 DML,可引用 DML CTE 的 `RETURNING` 结果。
- 同一个 CTE 在 `WITH` 中引用两次,DML 不会执行两次(但 `SELECT` CTE 可能被重复计算)。

```sql
-- 移动数据并统计(一处删除、一处插入)
WITH del AS (DELETE FROM orders WHERE created_at < '2025-01-01' RETURNING *)
INSERT INTO orders_archive SELECT * FROM del
RETURNING id;
```

## 四、性能要点

| 关注点 | 说明 |
|--------|------|
| `CTE Scan` 节点 | 出现即物化;若无必要且慢,考虑 `NOT MATERIALIZED` |
| 多次引用 | 引用 N 次且物化时只算一次;内联时可能算 N 次(甚至被规划器 CSE 优化) |
| 递归 CTE | 每轮迭代一次,轮数多则代价高;需注意死循环 |
| `work_mem` | 物化结果超出 `work_mem` 会落盘 |

```sql
-- 检查是否物化
EXPLAIN (COSTS OFF)
WITH c AS (SELECT * FROM orders WHERE status = 'paid')
SELECT * FROM c WHERE total > 100;
-- 计划中出现 "CTE Scan on c" → 已物化
-- 计划中出现 "Seq Scan on orders" + Filter → 已内联
```

## 五、`SEARCH` 与 `CYCLE`(PG14+)

递归 CTE 遍历时,可以用标准语法自动生成"路径"与"检测环":

```sql
WITH RECURSIVE tree AS (
    SELECT id, parent_id, name FROM nodes WHERE parent_id IS NULL
    UNION ALL
    SELECT n.id, n.parent_id, n.name FROM nodes n JOIN tree t ON n.parent_id = t.id
)
SEARCH DEPTH FIRST BY id SET ordercol        -- 生成深度优先顺序列
SELECT * FROM tree ORDER BY ordercol;
```

```sql
WITH RECURSIVE tree AS (...)
CYCLE id SET is_cycle USING path             -- 自动检测环
SELECT * FROM tree WHERE NOT is_cycle;
```

这替代了以往手工"维护 path 数组 + 判断 `any(path)`"的写法。
