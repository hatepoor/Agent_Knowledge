# 递归查询与树形结构

## 一、`WITH RECURSIVE` 语法

```sql
WITH RECURSIVE cte_name (col1, col2, ...) AS (
    -- ① 基准项(anchor):非递归,只执行一次
    SELECT ...
    UNION ALL                     -- 或 UNION(去重,隐式需要唯一性检查)
    -- ② 递归项:引用 cte_name 自身,反复执行到无新行产出
    SELECT ... FROM cte_name JOIN ...
)
SELECT * FROM cte_name;
```

**执行模型**:反复迭代,每一轮用"上一轮新产生的行"去执行递归项。当某一轮产出 0 行时停止。

> **性能要点**:必须让递归终止。数据中有环且用 `UNION ALL` 时会**无限循环**(直到 OOM 或超时)。用 `UNION` 去重或在递归项里做深度限制。

**安全护栏**

```sql
-- 方式一:深度限制
WITH RECURSIVE tree AS (
    SELECT id, parent_id, 1 AS depth FROM nodes WHERE parent_id IS NULL
    UNION ALL
    SELECT n.id, n.parent_id, t.depth + 1
    FROM nodes n JOIN tree t ON n.parent_id = t.id
    WHERE t.depth < 10            -- ★护栏
)
SELECT * FROM tree;

-- 方式二:路径数组防环
WITH RECURSIVE tree AS (
    SELECT id, parent_id, ARRAY[id] AS path FROM nodes WHERE parent_id IS NULL
    UNION ALL
    SELECT n.id, n.parent_id, t.path || n.id
    FROM nodes n JOIN tree t ON n.parent_id = t.id
    WHERE NOT n.id = ANY(t.path)  -- ★护栏:不回头
)
SELECT * FROM tree;
```

## 二、基础示例:组织架构

```sql
CREATE TABLE employees (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name      text NOT NULL,
    manager_id bigint REFERENCES employees(id),
    salary    numeric(12,2)
);

-- 自顶向下:某人的全部下属(含层级)
WITH RECURSIVE subs AS (
    SELECT id, name, manager_id, 1 AS depth, name::text AS path
    FROM employees WHERE id = 1                       -- 起点:某个老板
    UNION ALL
    SELECT e.id, e.name, e.manager_id, s.depth + 1, s.path || ' > ' || e.name
    FROM employees e JOIN subs s ON e.manager_id = s.id
)
SELECT id, name, depth, path FROM subs ORDER BY path;

-- 自底向上:某人的完整汇报链(到 CEO)
WITH RECURSIVE chain AS (
    SELECT id, name, manager_id, 1 AS lvl FROM employees WHERE id = 42
    UNION ALL
    SELECT e.id, e.name, e.manager_id, c.lvl + 1
    FROM employees e JOIN chain c ON e.id = c.manager_id
)
SELECT * FROM chain ORDER BY lvl;
```

**方向由"连接方向"决定**:

| 目标 | 连接条件 | 起点 |
|------|----------|------|
| 向下(求下属) | `child.manager_id = cte.id` | 父节点 |
| 向上(求祖先) | `parent.id = cte.manager_id` | 子节点 |

## 三、计算层级指标

```sql
WITH RECURSIVE tree AS (
    SELECT id, parent_id, salary, 1 AS depth, salary AS accumulated
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.parent_id, e.salary, t.depth + 1, t.accumulated + e.salary
    FROM employees e JOIN tree t ON e.parent_id = t.id
)
SELECT * FROM tree;
```

**注意**:`accumulated`(沿路径累加)与"子树总和"是两件事。子树总和需要用**后序聚合**,更简单的做法是先把层级关系展开成表,再用窗口/聚合:

```sql
-- 先求每个节点到根的路径,再按路径统计
WITH RECURSIVE tree AS (
    SELECT id, parent_id, ARRAY[id] AS path FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.parent_id, t.path || e.id
    FROM employees e JOIN tree t ON e.parent_id = t.id
)
SELECT t.id, count(*) AS subtree_size
FROM tree t
JOIN tree d ON d.id = ANY(t.path)        -- d 在 t 的路径上 ⇒ d 是 t 的后代
GROUP BY t.id;
```

这种方式在树很深时会比较重,生产上常改为**闭包表(closure table)** 或 **物化路径(materialized path)** 存储。

## 四、树形的三种主流存储方案

| 方案 | 结构 | 优点 | 缺点 |
|------|------|------|------|
| **邻接表**(`parent_id`) | 只存父指针 | 写入最简单,增删节点 O(1) | 查子树需递归 |
| **物化路径**(`path text` 如 `/1/3/7/`) | 存完整路径 | 查子树用 `LIKE '/1/3/%'` 一次搞定,可建索引 | 移动节点需重写整个子树 |
| **闭包表**(`ancestor, descendant, depth`) | 单独表存所有祖先-后代对 | 任意方向查询都快,可带深度 | 存储量大(O(n²) 级),写入需维护 |

**邻接表 + 递归 CTE** 在现代 PostgreSQL 中通常是好选择,因为它兼顾写简单与查灵活。只有在"读极多、写极少且层级很深"时才考虑闭包表。

```sql
-- 物化路径示例
CREATE TABLE categories (
    id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name text NOT NULL,
    path text NOT NULL DEFAULT ''          -- 形如 /1/5/12/
);
CREATE INDEX ON categories (path text_pattern_ops);

-- 查某节点及其所有后代(无需递归!)
SELECT * FROM categories WHERE path LIKE '/1/5/%' OR id = 5;
```

## 五、图遍历:最短路径

递归 CTE 可做 BFS(广度优先)求最短跳数。

```sql
CREATE TABLE edges (src int, dst int, cost numeric);
INSERT INTO edges VALUES (1,2,1),(2,3,1),(1,3,5),(3,4,1),(2,4,10);

-- 从 1 到 4 的最短跳数路径(按跳数)
WITH RECURSIVE reach AS (
    SELECT src, dst, ARRAY[src, dst] AS path, 1 AS hops, cost
    FROM edges WHERE src = 1
    UNION ALL
    SELECT r.src, e.dst, r.path || e.dst, r.hops + 1, r.cost + e.cost
    FROM edges e JOIN reach r ON e.src = r.dst
    WHERE NOT e.dst = ANY(r.path)               -- 不重复访问
      AND r.hops < 6                            -- 护栏
)
SELECT * FROM reach WHERE dst = 4 ORDER BY hops, cost LIMIT 5;
```

> **重要限制**:递归 CTE **无法在递归过程中做"最优剪枝"**。上面的写法会枚举所有路径,只适合小图。真正的加权最短路径(如 Dijkstra)在纯 SQL 里代价很高,生产上应使用:
>
> - `pgRouting` 扩展(专为图算法设计)
> - 应用层计算(把图拉到内存跑算法)
> - PG19 的 SQL/PGQ 属性图查询(仍在 Beta)

## 六、`SEARCH` 与 `CYCLE`(PG14+)实战

```sql
-- 深度优先顺序:自动产出可用于 ORDER BY 的序列
WITH RECURSIVE tree AS (
    SELECT id, parent_id, name FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.parent_id, c.name FROM categories c JOIN tree t ON c.parent_id = t.id
)
SEARCH DEPTH FIRST BY id SET seq
SELECT repeat('  ', (length(seq::text) - 1)) || name AS indented
FROM tree ORDER BY seq;
```

```sql
-- 环检测:自动标记是否成环并给出路径
WITH RECURSIVE walk AS (
    SELECT id, next_id, name FROM graph WHERE id = 1
    UNION ALL
    SELECT g.id, g.next_id, g.name FROM graph g JOIN walk w ON g.id = w.next_id
)
CYCLE id SET is_cycle USING path
SELECT * FROM walk WHERE NOT is_cycle;
```

`SEARCH DEPTH FIRST BY id SET seq` 生成的 `seq` 是一个数组,可直接 `ORDER BY` 得到深度优先顺序 —— 这等价于"把树按层级展开成带缩进的列表",是报表/文件树展示的标准实现。

## 七、性能与陷阱

| 陷阱 | 现象 | 解决 |
|------|------|------|
| 无限递归 | 查询不返回 / 内存爆 | 加深度护栏或 `UNION` 去重 |
| 无索引 | 每轮递归全表扫描 | 在连接列上建索引(邻接表就是 `parent_id`) |
| `UNION ALL` 重复行 | 结果含大量重复 | 改用 `UNION`,或在路径上做去重 |
| 图遍历无剪枝 | 路径数指数增长 | 限制深度;改用专门工具 |
| 递归中引用窗口函数 | 报错/语义不符 | 递归项内不能用窗口函数,需先在 CTE 外算 |

**必须有索引**:

```sql
CREATE INDEX ON employees (manager_id);   -- 向下遍历
-- 向上遍历用的是主键索引,已存在
```

没有这个索引,每一轮递归都会对整表做 Seq Scan,层级越深代价越大。
