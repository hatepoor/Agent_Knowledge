# 视图 / 函数 / 触发器 · 专题概览

## 专题定位

这三种对象都是为了**把逻辑收敛到数据库**,让多个入口(应用、脚本、运维手改)共享同一套规则。

**何时该翻这个专题**

- 同一段复杂 SQL 在多个地方重复
- 想让"原表"对外不可见,只暴露受控视图
- 需要"写入时自动校验/记录/派生"
- 需要数据库内定时任务

**先记住一句取舍**:数据库能做的逻辑,放数据库;**但不要把它变成业务应用服务器**。判断标准是:

| 放数据库 | 放应用 |
|----------|--------|
| 数据完整性、审计、派生列 | 业务编排、外部调用 |
| 复杂集合运算(避免拉数据到应用) | 需要频繁改动的逻辑 |
| 多入口共享的强制规则 | 与外部系统交互的逻辑 |

## 一、视图(VIEW)

视图是**保存的查询**,不存数据,每次访问重新执行。

```sql
CREATE VIEW v_active_orders AS
SELECT o.id, o.user_id, o.total, o.created_at, u.email
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status IN ('paid','shipped');

SELECT * FROM v_active_orders WHERE total > 100;
```

**视图的用途**

| 用途 | 说明 |
|------|------|
| 简化复杂查询 | 把 JOIN 封装,使用者只看一层 |
| 权限隔离 | 只暴露部分列/行(`GRANT SELECT ON v TO r`) |
| 稳定接口 | 底层表结构变了,视图定义保持对外接口不变 |
| 逻辑复用 | 多入口共享同一口径 |

**可更新视图**

简单视图(单表、无聚合、无 `DISTINCT` 等)可自动支持 `INSERT`/`UPDATE`/`DELETE`。

```sql
CREATE VIEW v_users_public AS
SELECT id, email, name FROM users;      -- 不含敏感列

UPDATE v_users_public SET name = 'X' WHERE id = 1;   -- ✅ 自动映射到 users
```

**复杂视图不可更新 → 用触发器或 `INSTEAD OF` 规则**

```sql
CREATE VIEW v_order_summary AS
SELECT user_id, count(*) AS cnt, sum(total) AS amt
FROM orders GROUP BY user_id;           -- ❌ 不可直接更新

-- 若确实需要,用 INSTEAD OF 触发器(见下)
```

**视图的安全性:`security_invoker`(PG15+)**

默认视图以**属主权限**执行(可能绕过 RLS)。PG15+ 可改为"以调用者权限执行":

```sql
CREATE VIEW v_orders WITH (security_invoker = true) AS
SELECT * FROM orders;      -- 尊重调用者的 RLS 与权限
```

> **安全提示**:若视图属主是高权限角色,普通用户通过视图可能读到本不该看到的数据。**涉及 RLS 或多租户时,务必用 `security_invoker` 或确保视图属主权限受限。**

## 二、物化视图(MATERIALIZED VIEW)

**会存数据**,需手工刷新。适合"计算昂贵 + 可容忍延迟"的报表场景。

```sql
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT date_trunc('day', created_at)::date AS d,
       channel,
       count(*) AS cnt,
       sum(total) AS amt
FROM orders
GROUP BY 1, 2;

-- 刷新(阻塞读)
REFRESH MATERIALIZED VIEW mv_daily_sales;

-- 并发刷新(不阻塞读,需唯一索引)★
CREATE UNIQUE INDEX ON mv_daily_sales (d, channel);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales;

-- 只建结构不填数据(便于后续并发刷新)
CREATE MATERIALIZED VIEW mv_x WITH NO DATA AS SELECT ...;
```

| 维度 | 视图 | 物化视图 |
|------|------|----------|
| 存数据 | ❌ | ✅ |
| 实时性 | 实时 | 刷新间隔 |
| 查询速度 | 依赖底层 | 快 |
| 可建索引 | ❌(可在底层建) | ✅ |
| 支持 RLS | 继承自基表 | 需自行处理 |
| 适合 | 逻辑封装 | 仪表盘、报表、复杂聚合 |

**`REFRESH CONCURRENTLY` 的代价**

| 事项 | 说明 |
|------|------|
| 需要唯一索引 | 否则报错 |
| 需额外一次扫描 | 比普通刷新慢 |
| 需保留旧数据 | 因此更占空间 |
| 不能在事务块内 | 与 `CREATE INDEX CONCURRENTLY` 类似 |

**增量刷新**:PostgreSQL **不支持**物化视图的增量刷新。每次 `REFRESH` 都是全量重算。若数据量大且刷新频繁,需:
- 用 `pg_ivm` 扩展(增量物化视图)
- 或自行维护增量汇总表(在写入时更新汇总)

```sql
-- 自行维护增量汇总的常用模式
CREATE TABLE daily_sales_summary (
    d date, channel text, cnt bigint DEFAULT 0, amt numeric(14,2) DEFAULT 0,
    PRIMARY KEY (d, channel)
);

-- 写入订单时用 UPSERT 累加
INSERT INTO daily_sales_summary (d, channel, cnt, amt)
VALUES (current_date, 'web', 1, 100)
ON CONFLICT (d, channel) DO UPDATE
SET cnt = daily_sales_summary.cnt + 1,
    amt = daily_sales_summary.amt + EXCLUDED.amt;
```

## 三、函数与存储过程

### 函数与过程的差异

| 维度 | FUNCTION | PROCEDURE(PG11+) |
|------|----------|------------------|
| 调用 | `SELECT f()` | `CALL p()` |
| 返回值 | 必须声明返回类型(可 `void`) | 无返回值(或用 `INOUT`) |
| 事务控制 | ❌ 不能在函数内 `COMMIT` | ✅ 可以 `COMMIT`/`ROLLBACK` |
| 可用于 SQL | ✅ 可出现在 `SELECT`/`WHERE` | ❌ |
| 适合 | 计算、查询封装 | 批处理、多步事务流程 |

```sql
-- 函数
CREATE FUNCTION total_of_user(p_user bigint) RETURNS numeric
LANGUAGE sql STABLE AS $$
    SELECT coalesce(sum(total), 0) FROM orders WHERE user_id = p_user;
$$;

SELECT total_of_user(1);

-- 过程(可控制事务)
CREATE PROCEDURE archive_old_orders(p_before date)
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO orders_archive SELECT * FROM orders WHERE created_at < p_before;
    COMMIT;                                     -- 过程内可提交
    DELETE FROM orders WHERE created_at < p_before;
    COMMIT;
END;
$$;

CALL archive_old_orders('2025-01-01');
```

### 语言选择

| 语言 | 特点 |
|------|------|
| `sql` | 简单、可内联、规划器可优化(`STABLE`/`IMMUTABLE`) |
| `plpgsql` | 默认,支持流程控制、异常处理 |
| `plpython3u` / `plperl` / `plv8` | 需要额外语言,慎用于生产(权限风险) |
| `C` | 性能最高,需编译,可访问内部结构 |

**优先 `sql` 语言**:它能被规划器内联优化,性能常优于 `plpgsql`。

### 易变性与优化

```sql
-- IMMUTABLE:同输入必同输出,可索引、可常量折叠
CREATE FUNCTION f_immutable(x int) RETURNS int LANGUAGE sql IMMUTABLE AS $$ SELECT x + 1 $$;

-- STABLE:同一事务内同输入同输出(如读表)
CREATE FUNCTION f_stable() RETURNS timestamptz LANGUAGE sql STABLE AS $$ SELECT now() $$;

-- VOLATILE:每次可能不同(默认)
CREATE FUNCTION f_volatile() RETURNS double precision LANGUAGE sql VOLATILE AS $$ SELECT random() $$;
```

> **声明错了会出事**:
> - 把读表函数声明为 `IMMUTABLE` → 可能被索引引用,导致数据不一致。
> - 把 `now()` 类声明为 `IMMUTABLE` → 索引会"冻结"时间。
>
> **规则**:不读表、不用时间/随机/序列 → `IMMUTABLE`;只读表 → `STABLE`;其他 → `VOLATILE`。

**函数内联**:`sql` 语言且是简单表达式时,规划器会**把函数体展开到查询里**。

```sql
-- 检查是否内联
EXPLAIN (ANALYZE, VERBOSE) SELECT * FROM orders WHERE user_id = total_of_user(1);
SET LOCAL enable_...;   -- 或直接看计划里是否出现 Function Scan
```

可用 `SET LOCAL` 关闭内联以对比:

```sql
-- plpgsql 函数不支持内联,常因此比 sql 函数慢
```

## 四、触发器(TRIGGER)

### 类型

| 维度 | 选项 |
|------|------|
| 时机 | `BEFORE` / `AFTER` / `INSTEAD OF` |
| 粒度 | `FOR EACH ROW` / `FOR EACH STATEMENT` |
| 事件 | `INSERT` / `UPDATE` / `DELETE` / `TRUNCATE` |

```sql
CREATE OR REPLACE FUNCTION trg_set_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;                 -- BEFORE ROW 触发器必须返回 NEW(或 NULL 取消操作)
END;
$$;

CREATE TRIGGER set_updated_at
    BEFORE UPDATE ON orders
    FOR EACH ROW
    EXECUTE FUNCTION trg_set_updated_at();
```

**BEFORE ROW 触发器返回值的语义**

| 返回 | 效果 |
|------|------|
| `NEW` | 使用(可能已修改的)新行 |
| `NULL` | **取消该行操作** |
| `OLD`(仅 UPDATE) | 使用旧值(相当于撤销修改) |

**AFTER 触发器的返回值被忽略。**

### 审计日志示例

```sql
CREATE TABLE audit_log (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tbl      text, op text, row_id bigint,
    before   jsonb, after jsonb,
    at       timestamptz DEFAULT now(),
    by_user  text DEFAULT current_user
);

CREATE OR REPLACE FUNCTION trg_audit() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    INSERT INTO audit_log (tbl, op, row_id, before, after)
    VALUES (TG_TABLE_NAME, TG_OP,
            coalesce(NEW.id, OLD.id),
            CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,
            CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END);
    RETURN NULL;
END;
$$;

CREATE TRIGGER audit_orders
    AFTER INSERT OR UPDATE OR DELETE ON orders
    FOR EACH ROW EXECUTE FUNCTION trg_audit();
```

`TG_*` 变量:`TG_TABLE_NAME`、`TG_OP`、`TG_WHEN`、`TG_LEVEL`、`TG_NARGS` 等。

### 事件触发器(PG9.3+)

监听 DDL 事件(建表、删表等)。

```sql
CREATE EVENT TRIGGER log_ddl ON ddl_command_end
    EXECUTE FUNCTION log_ddl_fn();
```

### 触发器的代价与陷阱

| 陷阱 | 说明 |
|------|------|
| 性能 | `FOR EACH ROW` 触发器逐行执行,批量写入时开销显著 |
| 隐形逻辑 | 应用看不到,排查困难 |
| 递归 | 触发器内改同一张表可能再触发自身 |
| 顺序 | 同事件多触发器的执行顺序**按名称字母序**(可 `SET ... FOLLOWS`) |
| 禁用 | `ALTER TABLE ... DISABLE TRIGGER ALL` 会连带禁用外键(外键由系统触发器实现) |
| 与逻辑复制 | 默认**不复制**触发器产生的效果(除非专门配置) |

**顺序控制**:

```sql
CREATE TRIGGER t1 BEFORE UPDATE ON x FOR EACH ROW EXECUTE FUNCTION f1();
CREATE TRIGGER t2 BEFORE UPDATE ON x FOR EACH ROW EXECUTE FUNCTION f2();
-- 按名称: t1 先于 t2

-- 显式指定
CREATE TRIGGER t2 BEFORE UPDATE ON x FOR EACH ROW
    EXECUTE FUNCTION f2();    -- 默认
-- 或用 ALTER TRIGGER ... RENAME 调整名称
```

**触发器的合理使用边界**

| 适合 | 不适合 |
|------|--------|
| 审计日志 | 复杂业务编排 |
| `updated_at` 自动维护 | 调用外部接口 |
| 派生列同步(如 `tsvector`) | 大规模数据变形 |
| 跨表一致性(谨慎) | 替代应用事务 |

> **实践建议**:能用 `DEFAULT`、生成列、约束解决的,不要用触发器。触发器是"最后手段",主要用于审计与派生。

## 五、权限与安全

```sql
-- 函数执行权限
GRANT EXECUTE ON FUNCTION total_of_user(bigint) TO app_ro;
REVOKE ALL ON FUNCTION f FROM PUBLIC;      -- 关闭默认的 PUBLIC 执行权限

-- 视图权限
GRANT SELECT ON v_active_orders TO app_ro;
```

> **`SECURITY DEFINER` 函数是高风险点**:它以**定义者权限**执行,若逻辑存在 SQL 注入或未校验 `search_path`,可被提权。使用时必须:
>
> ```sql
> CREATE FUNCTION f() RETURNS int
> LANGUAGE sql SECURITY DEFINER
> SET search_path = pg_catalog, app     -- ★必须固定 search_path
> AS $$ ... $$;
> ```
