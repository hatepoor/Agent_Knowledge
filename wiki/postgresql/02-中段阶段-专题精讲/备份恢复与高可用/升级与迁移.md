# 版本升级与数据迁移

## 一、次版本升级(小版本)

**次版本(如 18.5 → 18.6)不含不兼容变更**,只需替换二进制并重启。

```bash
# 停机窗口内
systemctl stop postgresql
# 替换安装包(包管理器)
apt install postgresql-18=18.6-1        # 或用官方仓库
systemctl start postgresql
# 验证
psql -c "SELECT version();"
```

**注意事项**

- 数据目录**无需重建**。
- 遵循官方建议:更新后检查 `RELEASE` 说明中"是否需要 REINDEX"(某些安全修复后需 `REINDEX`,例如涉及排序规则或索引类型的修复)。
- 例如 PG18.6 之后提到:并行 GIN 索引构建、`btree_gist`、`ltree` 有额外处理要求,需按发布说明执行。

> **重要**:不要跨大版本用二进制替换。`18.x` 与 `19.x` 的数据目录格式不兼容。

## 二、大版本升级的三种方式

| 方式 | 停机时间 | 风险 | 跨平台 | 适用 |
|------|----------|------|--------|------|
| **`pg_upgrade`**(原地/克隆) | 分钟级 | 中(需做兼容性检查) | ❌ 同架构 | 大多数场景,**推荐** |
| **`pg_dump` / `pg_restore`** | 小时级 | 低(逻辑一致) | ✅ | 数据量小、需跨平台/跨架构、需要清洗数据 |
| **逻辑复制**(滚动升级) | 秒级 | 中(需处理 DDL 与序列) | ✅ | 要求极低停机、跨大版本 |

### 方式一:pg_upgrade

**原理**:不搬数据,只把系统目录(元数据)从旧格式转换为新格式,数据文件原地复用。

```bash
# 1) 安装新版(旧版保留)
# 2) 停旧实例
systemctl stop postgresql-17

# 3) 兼容性检查(不实际升级)
/usr/lib/postgresql/18/bin/pg_upgrade \
    --old-datadir=/var/lib/postgresql/17/main \
    --new-datadir=/var/lib/postgresql/18/main \
    --old-bindir=/usr/lib/postgresql/17/bin \
    --new-bindir=/usr/lib/postgresql/18/bin \
    --check

# 4) 执行升级
... --link          # 用硬链接(快,但升级后旧实例不可再启动)
# 或 --copy          # 复制(慢,但保留旧实例)
```

**`pg_upgrade` 的关键收益与要求**

| 事项 | 说明 |
|------|------|
| **统计信息保留(PG18+)** | 升级后规划器立即有统计,**不必等 `ANALYZE` 跑完**才能恢复计划质量 |
| 并行检查(PG18+) | 用 `--jobs` 并行;`--swap` 可缩短停机 |
| 检查和数据校验和 | PG18 起 `initdb` 默认开启校验和,`pg_upgrade` 要求**新旧集群校验和设置一致**(旧集群无校验和时用 `initdb --no-data-checksums`) |
| `--link` 的代价 | 升级后**无法回退**到旧版本(数据文件已被新版接管) |
| 扩展 | 需在新版中安装相同扩展;`shared_preload_libraries` 需确认兼容 |
| 大对象/表空间 | `--link` 对表空间有额外约束 |

**升级后必做**

```bash
# 重建统计信息(若 --link 且旧版本升级,PG17 及以前需要)
/usr/lib/postgresql/18/bin/vacuumdb --all --analyze-only

# 检查是否有失效对象
psql -c "\dx"
psql -c "SELECT * FROM pg_stat_user_tables WHERE last_analyze IS NULL LIMIT 10;"

# 若涉及全文检索/排序规则相关(见下),执行 REINDEX
```

### 方式二:pg_dump / pg_restore

```bash
# 旧版导出
pg_dumpall -h old -U postgres -f all.sql
# 或
pg_dump -Fd -j 8 -h old -U postgres -d learn -f learn_dir

# 新版导入
psql -h new -U postgres -d postgres -v ON_ERROR_STOP=1 -f all.sql
pg_restore -j 8 -h new -U postgres -d learn_new learn_dir
```

**优点**:可跨平台/跨架构;可在中间修改数据。
**缺点**:停机时间长(导出+导入);大库不现实。

### 方式三:逻辑复制滚动升级(近零停机)

```
1) 新版实例建库,用 pg_dump --schema-only 建结构(或用 pg_upgrade --check 生成的脚本)
2) 建立逻辑复制:新版为订阅端,旧版为发布端(wal_level = logical)
3) 等追平,观察延迟
4) 切换(小停机窗口):
   - 停应用写入
   - 确认延迟为 0
   - 同步序列值(PG19 前需手工!)
   - 应用切到新实例
5) 撤销订阅,下线旧实例
```

**必须处理的细节**

| 细节 | 说明 |
|------|------|
| **序列值** | 逻辑复制**不复制序列**。切换前必须在新实例上 `setval` 到正确值,否则会主键冲突 |
| DDL 变更 | 升级期间的 DDL 不会自动同步,须在两端都执行(或冻结 DDL) |
| 大事务 | 会拉长延迟,切换前避免大事务 |
| 无主键表 | 需 `REPLICA IDENTITY FULL` 或唯一索引 |
| 触发器 | 订阅端触发器默认会执行,可能导致重复副作用,需评估 |

```sql
-- 序列同步(在新实例执行)
SELECT 'SELECT setval(''' || pg_get_serial_sequence(schemaname||'.'||tablename, column_name)
       || ''', ' || last_value || ');'
FROM ... ;
-- 更简单:用 pg_dump 只导出序列相关语句
```

## 三、跨实例/跨平台迁移

| 场景 | 方案 |
|------|------|
| 同版本迁移 | 逻辑备份 + 恢复;或流复制 + 提升 |
| 跨大版本 | `pg_upgrade`(同架构) / 逻辑复制 / dump |
| 跨操作系统 | 逻辑备份;或逻辑复制 |
| 跨架构(如 x86 → ARM) | 逻辑备份(物理不兼容) |
| 上云(自建 → RDS) | 逻辑复制 / `pg_dump`;云厂商常用 DMS 工具 |
| 下云 / 换厂商 | 逻辑复制(近零停机) |

**大库迁移的实用技巧**

```bash
# 1) 并行导出/导入(dir 格式)
pg_dump -Fd -j 8 ...
pg_restore -Fd -j 8 ...

# 2) 先建结构、再导数据、最后建索引与约束
pg_dump -s ...            # 只要结构,但可手工去掉索引/外键
# 导数据
# 再 CREATE INDEX CONCURRENTLY / ADD CONSTRAINT NOT VALID + VALIDATE

# 3) 关闭 synchronous_commit 加速导入
psql -c "SET synchronous_commit = off;"   # 导入期间(仅对可容忍丢失的场景)
# 或 ALTER SYSTEM 临时设置

# 4) 临时关闭 autovacuum(导入期间减少干扰)
ALTER TABLE t SET (autovacuum_enabled = false);

# 5) 加大 maintenance_work_mem 加速建索引
SET maintenance_work_mem = '1GB';

# 6) 用 unlogged 表导入再转 logged(仅当可容忍崩溃丢失)
ALTER TABLE t SET UNLOGGED;  -- 注意:PG18 起分区表不允许 UNLOGGED
-- 导入
ALTER TABLE t SET LOGGED;
```

## 四、升级前的检查清单

**兼容性检查**

- [ ] 阅读目标版本 Release Notes 的 "Migration to Version N" 章节(不兼容变更清单)
- [ ] 检查弃用功能:`recovery.conf`(PG12 废弃)、`md5` 密码(PG18 弃用)、`pg_standby`(PG18 移除)、`RADIUS`(PG19 移除)
- [ ] 检查扩展是否有对应版本(`SELECT * FROM pg_available_extensions`)
- [ ] 检查 `shared_preload_libraries` 中的扩展兼容性
- [ ] 检查客户端驱动版本(如 JDBC/psycopg 是否支持新版本)

**数据检查**

- [ ] PG18 起 `initdb` **默认开启数据校验和**;升级时新旧集群校验和设置必须一致
- [ ] PG18 起生成列**默认 VIRTUAL**;若依赖生成列落盘(如建了索引),必须改为显式 `STORED`
- [ ] PG18 起分区表**不允许 UNLOGGED**;存量 UNLOGGED 分区表需先转 LOGGED
- [ ] PG18 起 `VACUUM`/`ANALYZE` **默认处理继承子分区**;要保持旧行为需加 `ONLY`
- [ ] PG19 起 `standard_conforming_strings` 强制为 `on`;旧 dump 若含 `off` 设置将无法正确载入
- [ ] PG19 起禁止库名/角色名/表空间名含回车与换行;`--check` 会发现
- [ ] PG19 起 `inet`/`cidr` 的默认 GiST opclass 从 `btree_gist` 改为 `GiST`;含此类索引的集群 `pg_upgrade` 会拒绝升级
- [ ] PG19 起 `max_locks_per_transaction` 默认由 64 变为 128(锁分配方式变化,等价容量需翻倍)

**全文检索与排序规则**

- [ ] PG18 起全文检索与 `pg_trgm` 读取配置/词典使用**集群默认排序规则提供者**而非固定 `libc`。若集群默认不是 libc,升级后应对全文检索与 `pg_trgm` 相关索引执行 `REINDEX`

**操作准备**

- [ ] 备份(逻辑 + 物理)
- [ ] 准备回退方案(若用 `--link`,回退只能靠备份)
- [ ] 在测试环境演练一遍
- [ ] 确认停机窗口与业务沟通

## 五、升级后验证

```sql
-- 版本
SELECT version();

-- 对象完整性
SELECT count(*) FROM pg_class WHERE relkind IN ('r','i','v','m');

-- 是否有失效索引
SELECT indexrelid::regclass, indrelid::regclass FROM pg_index WHERE NOT indisvalid;

-- 扩展
SELECT extname, extversion FROM pg_extension;

-- 统计信息是否齐备(PG18 起 pg_upgrade 会保留,旧版本需手工 VACUUM ANALYZE)
SELECT relname, last_analyze, last_autoanalyze
FROM pg_stat_user_tables ORDER BY last_analyze NULLS FIRST LIMIT 20;

-- 关键查询的执行计划是否异常
EXPLAIN (ANALYZE, BUFFERS) <核心 SQL>;
```

```bash
# pg_upgrade 生成的脚本
./analyze_new_cluster.sh      # 重建统计(PG18 起通常不必)
./delete_old_cluster.sh       # 清理旧集群(--link 时删除前务必确认)
```
