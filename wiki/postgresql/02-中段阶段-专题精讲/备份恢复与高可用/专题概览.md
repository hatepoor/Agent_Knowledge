# 备份恢复与高可用 · 专题概览

## 专题定位

**备份是"能回到过去",高可用是"不中断服务"。** 两者目标不同,不能互相替代。

| 目标 | 手段 | RPO / RTO |
|------|------|-----------|
| 防止误删/误改 | 逻辑备份 + PITR | 可到秒级(PITR) |
| 防硬件故障 | 物理备份 + 流复制 | 秒级 |
| 防机房故障 | 异地副本 | 分钟级 |
| 不停机升级 | 逻辑复制 / `pg_upgrade` | 分钟级 |

## 一、逻辑备份:pg_dump 系列

**导出为 SQL 或自定义格式,可跨版本、跨平台、可选择性恢复。**

```bash
# 单库导出(自定义格式,推荐)
pg_dump -Fc -h localhost -U postgres -d learn -f learn.dump

# 纯 SQL 文本
pg_dump -h localhost -U postgres -d learn -f learn.sql

# 目录格式(支持并行)
pg_dump -Fd -j 4 -h localhost -U postgres -d learn -f learn_dir

# 全实例导出(含角色、表空间)
pg_dumpall -h localhost -U postgres -f all.sql

# 只导出 schema
pg_dump -s -d learn -f schema.sql

# 只导出特定表
pg_dump -t 'app.orders*' -d learn -f orders.sql

# 只导出数据
pg_dump -a -d learn -f data.sql
```

| 格式 | 参数 | 特点 |
|------|------|------|
| `plain` | `-Fp`(默认) | SQL 文本,可编辑,`psql` 恢复 |
| `custom` | `-Fc` | 压缩,支持并行恢复与选择性恢复,**推荐** |
| `directory` | `-Fd` | 支持并行导出/恢复,适合大数据量 |
| `tar` | `-Ft` | 较少用 |

**恢复**

```bash
# 自定义/目录格式用 pg_restore
pg_restore -h localhost -U postgres -d learn_new learn.dump
pg_restore -j 4 -d learn_new learn_dir            # 并行

# 只恢复某张表
pg_restore -t orders -d learn_new learn.dump

# 只重建结构
pg_restore -s -d learn_new learn.dump

# 文本格式用 psql(注意 ON_ERROR_STOP)
psql -h localhost -U postgres -d learn_new -v ON_ERROR_STOP=1 -f learn.sql
```

**`pg_dump` 的关键特性**

| 特性 | 说明 |
|------|------|
| 一致性 | 通过 `REPEATABLE READ` 快照保证导出期间数据一致,不阻塞写入 |
| 大对象 | 包含 `pg_largeobject` |
| 序列值 | 包含 `setval` |
| **不包含** | 角色(需 `pg_dumpall --roles-only`)、复制槽、统计信息、部分扩展配置 |
| 跨版本 | 可把高版本导出的 SQL 恢复到低版本(有限制,用 `--no-*` 选项) |

> **常见遗漏**:`pg_dump` **不导出数据库级设置**(如 `ALTER DATABASE ... SET`)。迁移后需单独处理。也不导出复制槽(logical replication slot),逻辑复制的迁移需手工重建订阅。

## 二、物理备份:pg_basebackup

**复制数据目录,是搭建流复制与 PITR 的基础。**

```bash
# 基础用法(含 WAL,可直接启动为备库)
pg_basebackup -h primary -D /var/lib/postgresql/standby -U replicator -Fp -Xs -P -R

# 打包为 tar
pg_basebackup -h primary -D /backup -Ft -z -Xs -P

# 只用于备份(不启动)
pg_basebackup -h primary -D /backup/base -Fp -Xs -P
```

| 参数 | 含义 |
|------|------|
| `-D` | 目标目录 |
| `-Fp`/`-Ft` | 输出为普通文件 / tar |
| `-Xs` | 用复制协议流式传输 WAL(推荐) |
| `-Xf` | 备份结束后再拉 WAL |
| `-R` | 自动生成 `standby.signal` 与 `primary_conninfo` |
| `-P` | 显示进度 |
| `-z` | 压缩 |
| `--checkpoint=fast` | 立即做检查点 |

**前置要求**:`postgresql.conf` 中 `wal_level` 至少为 `replica`,并有可用的复制用户与 `pg_hba.conf` 规则。

## 三、PITR(时间点恢复)

**核心原理:物理基础备份 + 重放 WAL 到指定时间点。**

```ini
# postgresql.conf(主库)
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'   # 或用 pgBackRest / WAL-G
```

**恢复流程**

```bash
# 1) 恢复基础备份
# 2) 配置 recovery
#    PG12+ :编辑 postgresql.conf + 创建 recovery.signal
```

```ini
restore_command = 'cp /archive/%f %p'
recovery_target_time = '2026-09-19 12:30:00+08'
recovery_target_action = 'promote'     # 到达目标后提升为可写
```

```bash
touch /var/lib/postgresql/data/recovery.signal
# 启动实例
pg_ctl start
```

**恢复目标选项**

| 参数 | 说明 |
|------|------|
| `recovery_target_time` | 恢复到某个时间点 |
| `recovery_target_xid` | 恢复到某个事务 ID |
| `recovery_target_lsn` | 恢复到某个 WAL 位置 |
| `recovery_target_name` | 恢复到命名的恢复点(`pg_create_restore_point()` 创建) |
| `recovery_target_inclusive` | 是否包含目标点 |
| `recovery_target_action` | `pause` / `promote` / `shutdown` |

> **PG12+ 变更**:`recovery.conf` 被废弃。改用数据目录中的 `recovery.signal` / `standby.signal` 文件触发,参数写入 `postgresql.conf`。PG18 明确弃用 `recovery.conf` 文件。

**建议的恢复演练节奏**:每季度做一次完整 PITR 演练。**没演练过的备份等于没有备份。**

## 四、流复制(Streaming Replication)

**主库把 WAL 实时推给备库,备库持续重放。**

```
Primary                          Standby
  walwriter  ──WAL──►  walsender ──网络──► walreceiver ──► 重放(recovery)
```

**主库配置**

```ini
wal_level = replica
max_wal_senders = 10
wal_keep_size = 1GB                # 或使用复制槽(推荐)
hot_standby = on
```

```sql
-- 复制用户
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '...';

-- 复制槽(防止主库过早回收 WAL)
SELECT pg_create_physical_replication_slot('standby1');
```

**备库配置**

```ini
primary_conninfo = 'host=primary port=5432 user=replicator password=... application_name=standby1'
primary_slot_name = 'standby1'
hot_standby = on
```

```bash
touch standby.signal     # 标记为备库
pg_ctl start
```

**监控复制状态**

```sql
-- 主库看备库进度
SELECT client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;

-- 备库看接收与重放
SELECT status, receive_start_lsn, received_lsn, last_msg_receipt_time,
       latest_end_lsn, latest_end_time FROM pg_stat_wal_receiver;

-- 备库看重放延迟
SELECT now() - pg_last_xact_replay_timestamp() AS replay_delay;
```

**同步提交与仲裁**

```ini
# 主库
synchronous_standby_names = 'standby1'          # 指定一个备库同步
synchronous_standby_names = 'ANY 1 (s1, s2)'    # 任一确认即可(PG10+ 仲裁提交)
synchronous_commit = on                         # on / remote_apply / remote_write / local / off
```

| `synchronous_commit` | 语义 | 丢失数据的边界 |
|----------------------|------|----------------|
| `off` | 不等本地 WAL 落盘就返回 | 崩溃可丢最近若干事务 |
| `local` | 本地落盘即返回 | 不丢本地,可丢同步副本 |
| `on`(默认) | 本地 + 同步备库写入(未重放) | 主库故障不丢 |
| `remote_write` | 备库写入 OS 缓存 | 备库 OS 崩溃可丢 |
| `remote_apply` | 备库已重放(可读一致性) | 最强,延迟最高 |

> **`synchronous_commit = off` 的风险边界**:丢失的是"最近几百毫秒内已提交但未刷盘的事务"。不丢已刷盘数据,数据库不会损坏。适合"可容忍少量数据丢失"的场景(如日志、指标)。

**级联复制**:备库再作为其他备库的上游(`cascading standby`),减轻主库压力。

## 五、逻辑复制

**基于逻辑解码,复制的是"行变更",可跨版本、可选择性复制。**

```sql
-- 发布端
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
-- PG15+ :行过滤与列列表
CREATE PUBLICATION pub_orders_filtered FOR TABLE orders
    WHERE (status <> 'canceled');

ALTER PUBLICATION pub_orders ADD TABLE orders (id, user_id, total);   -- 只复制部分列

-- 订阅端
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=primary dbname=learn user=repl password=...'
    PUBLICATION pub_orders;
```

**前置条件**:发布端 `wal_level = logical`。

| 维度 | 物理复制(流复制) | 逻辑复制 |
|------|-------------------|----------|
| 粒度 | 整个实例 | 表级 / 行级 / 列级 |
| 版本 | 必须相同大版本 | 可跨大版本 |
| 平台 | 必须相同架构(某些情况) | 可跨平台 |
| 只读副本 | ✅ 备库可读(热备) | 订阅端可写(但需注意冲突) |
| DDL | 自动复制 | ❌ **不复制 DDL** |
| 序列 | 不复制(但仍随 WAL) | **PG19 起支持复制序列值** |
| 冲突处理 | 无冲突(物理一致) | 可能出现冲突,需处理 |
| 用途 | 高可用、只读扩展 | 版本升级、数据分发、多主 |

**逻辑复制的关键限制**

| 限制 | 说明 |
|------|------|
| 不复制 DDL | 需在两端分别执行(或用 `pglogical`/手工) |
| 不复制序列 | PG19 之前需手工同步序列;PG19 起支持 |
| 大事务 | 需整体提交后才应用,大事务造成明显延迟 |
| 主键 | 表必须有主键或 REPLICA IDENTITY,否则 `UPDATE`/`DELETE` 无法定位行 |
| 冲突 | 订阅端若有独立写入,可能主键冲突/丢失更新,需 `pg_subscription` 相关配置与手工干预 |

```sql
-- 复制标识(无主键表)
ALTER TABLE t REPLICA IDENTITY FULL;      -- 用整行标识(代价高)
ALTER TABLE t REPLICA IDENTITY USING INDEX idx;  -- 用唯一索引

-- 监控逻辑复制延迟
SELECT subname, received_lsn, latest_end_lsn, last_msg_receipt_time
FROM pg_stat_subscription;

-- 查看复制槽(防止 WAL 被回收!必须监控)
SELECT slot_name, slot_type, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
```

> **复制槽是危险对象**:若订阅端长期离线,发布端的 WAL 会**持续堆积直到磁盘写满**。必须监控 `pg_replication_slots` 的残留量与磁盘空间。

**PG18 新增**:支持从**物理备库**作为逻辑发布的源(减轻主库负载),以及 `pg_subscription_check` 模块用于校验订阅端与发布端的数据一致性。

## 六、备份策略设计

**3-2-1 原则**:3 份副本、2 种介质、1 份异地。

| 层次 | 手段 | 频率 | 恢复目标 |
|------|------|------|----------|
| 逻辑备份 | `pg_dump -Fc` | 每日 | 误删单表/单库 |
| 物理全备 | `pg_basebackup` / `pgBackRest` | 每日/每周 | 整实例恢复 |
| WAL 归档 | `archive_command` | 持续 | PITR 到任意秒 |
| 流复制 | 同步/异步备库 | 实时 | 硬件故障切换 |

**推荐工具**

| 工具 | 特点 |
|------|------|
| `pgBackRest` | 增量/差分备份、并行、压缩、加密、保留策略,**生产首选** |
| `WAL-G` | 云对象存储、支持 PITR |
| `Barman` | 集中式备份管理 |
| 原生 `pg_dump` + `archive_command` | 简单场景可用 |

**保留策略示例**

```
每日全备     保留 7 天
每周全备     保留 4 周
每月全备     保留 12 月
WAL 归档     保留至最老全备之后
```

## 七、高可用架构

| 架构 | 说明 | 自动切换 |
|------|------|----------|
| 主备 + 手工切换 | `pg_ctl promote` | ❌ |
| **Patroni** | 基于 etcd/Consul/ZooKeeper 的自动故障转移,**最主流** | ✅ |
| repmgr | 社区方案,管理复制与切换 | ✅ |
| pg_auto_failover | Citus 出品,简单场景 | ✅ |
| 云托管 | RDS / Cloud SQL 等自带 | ✅ |

**切换与脑裂防护**:必须有仲裁机制(etcd/Consul)避免双主。**不要用脚本自行实现自动切换** —— 脑裂的代价远高于短暂停机。

**只读扩展**

```ini
hot_standby_feedback = on      # 备库向主库反馈,避免主库 VACUUM 删掉备库还需要的行
max_standby_streaming_delay = 30s
```

> `hot_standby_feedback = on` 能减少备库查询被取消的概率,但代价是**延迟主库的 VACUUM**(与长事务的影响相同)。这是一个真实的两难,需按业务权衡。

## 八、常见陷阱

| 陷阱 | 后果 | 对策 |
|------|------|------|
| 备份从未演练恢复 | 真出事时恢复失败 | 定期演练,记录 RTO |
| 只做逻辑备份 | 无法 PITR,丢失窗口大 | 加物理备份 + WAL 归档 |
| 只做物理备份 | 无法恢复单表 | 加逻辑备份 |
| 复制槽未监控 | WAL 堆积撑满磁盘 | 监控 `pg_replication_slots` |
| `pg_dump` 未用一致性快照参数 | 跨表不一致 | 单库内 `pg_dump` 本身是一致快照;跨库需 `--` 协调 |
| 异步复制当同步用 | 切换时丢数据 | 关键业务用 `synchronous_commit = remote_apply` 或仲裁提交 |
| 备份未加密 | 合规风险 | 用 `pgBackRest` 加密或存储侧加密 |
| 恢复后忘 `ANALYZE` | 计划变差 | 恢复后执行 `ANALYZE` / `VACUUM ANALYZE` |

> **PG18 的重要收益**:`pg_upgrade` 现在**保留优化器统计信息**,因此升级后不必等 `ANALYZE` 跑完才能恢复计划质量;升级过程也支持并行检查与 `--swap` 以缩短停机。
