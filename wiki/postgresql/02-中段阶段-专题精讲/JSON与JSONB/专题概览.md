# JSON 与 JSONB · 专题概览

## 专题定位

PostgreSQL 让"关系表"与"文档存储"共存于同一数据库:**结构化字段继续用列,变化频繁/嵌套深的字段用 JSONB**。

这让很多场景不再需要额外引入 MongoDB 之类的文档库。

**何时该翻这个专题**

- 第三方接口回调的 payload 需要原样落库
- 业务字段频繁变化(不同品类商品的属性不同)
- 需要存嵌套结构(购物车行、配置树、事件属性)
- 需要"字段级"查询与索引,而不是把整块 JSON 当黑盒

## 一、`json` vs `jsonb`

| 维度 | `json` | `jsonb` |
|------|--------|---------|
| 存储 | 原始文本 | 解析后的二进制 |
| 写入速度 | 快(不解析) | 慢(需解析 + 去重 + 排序键) |
| 读取/查询速度 | 慢(每次解析) | 快 |
| 保留空白/键顺序/重复键 | ✅ | ❌(去重、键排序、去空格) |
| 支持索引 | ❌ | ✅(GIN / 表达式 / 部分) |
| 支持操作符 | 仅 `->` `->>` `#>` `#>>` | 完整 |

**结论:默认用 `jsonb`。** 只有"必须原样保留文本"时用 `json`:

- 审计/合规要求保留原文(如签名验签、原文比对)
- 仅作为不透明载荷存储,永不查询

```sql
INSERT INTO t (raw) VALUES ('{"b":1,"a":2,"a":3}');
-- json 输出: {"b":1,"a":2,"a":3}
-- jsonb 输出:{a: 3, b: 1}   ← 键排序、重复键后者胜、空白去除
```

## 二、取值操作符

| 操作符 | 返回 | 说明 |
|--------|------|------|
| `->` | jsonb | 按键/下标取值 |
| `->>` | text | 取值并转为文本 |
| `#>` | jsonb | 按路径取值,路径用 `'{a,b}'` |
| `#>>` | text | 按路径取值转文本 |
| `@>` | boolean | 左是否包含右 |
| `<@` | boolean | 左是否被右包含 |
| `?` | boolean | 键/元素是否存在(仅 jsonb) |
| `?|` | boolean | 是否存在任一 |
| `?&` | boolean | 是否全部存在 |
| `-` | jsonb | 删除键/元素 |
| `#-` | jsonb | 按路径删除 |
| `||` | jsonb | 合并(浅合并) |

```sql
SELECT
  payload -> 'a'            AS a_json,      -- jsonb
  payload ->> 'a'           AS a_text,      -- text
  payload #> '{x,y}'        AS xy_json,
  payload #>> '{x,y}'       AS xy_text,
  payload ? 'a'             AS has_a,
  payload @> '{"vip": true}' AS is_vip
FROM events;
```

> **记住区别:`->` 得到 JSONB,`->>` 得到文本。** 这是 JSON 查询中最常见的错误来源。数值比较必须用 `->>` 再转型:
>
> ```sql
> WHERE (payload->>'qty')::int > 2        -- ✅
> WHERE payload->'qty' > '2'              -- ⚠️ JSONB 比较语义不同,通常不是你想要的
> ```

## 三、下标写法(PG14+)

PG14 起支持 `[...]` 下标,可读性显著优于 `->` 链:

```sql
SELECT payload['a'],          -- 等价 payload->'a'
       payload['items'][0]['qty']
FROM events;

-- 也可用于 UPDATE
UPDATE events SET payload['a'] = '1'::jsonb WHERE id = 1;
UPDATE events SET payload['items'][0]['qty'] = '5'::jsonb WHERE id = 1;
```

## 四、SQL/JSON 路径(PG12+)

功能最强、语法最标准的查询方式,支持过滤、通配、递归。

```sql
SELECT jsonb_path_query(payload, '$.items[*].qty');
SELECT jsonb_path_query(payload, '$.items[*] ? (@.qty > 2)');
SELECT jsonb_path_query(payload, '$.items[*] ? (@.name like_regex "^A")');
SELECT jsonb_path_exists(payload, '$.items[*] ? (@.qty > 10)');
SELECT jsonb_path_query_first(payload, '$.items[0]');
SELECT jsonb_path_query_array(payload, '$.items[*].name');

-- 传入变量(避免拼接)
SELECT jsonb_path_query(payload, '$.items[*] ? (@.qty > $min)',
                        jsonb_build_object('min', 2));

-- 严格/宽松模式
SELECT jsonb_path_query(payload, 'strict $.missing');   -- 报错
SELECT jsonb_path_query(payload, 'lax $.missing');      -- 返回空
```

**常用路径表达式**

| 表达式 | 含义 |
|--------|------|
| `$` | 根 |
| `$.a.b` | 成员访问 |
| `$[*]` | 数组所有元素 |
| `$.*` | 对象所有值 |
| `$..name` | 递归查找所有 `name` |
| `? (条件)` | 过滤 |
| `@.x > 1` | 当前元素的 `x` 大于 1 |
| `like_regex` / `starts with` | 字符串匹配 |
| `**` | 任意层级 |

## 五、构造函数与修改函数

```sql
-- 构造
SELECT jsonb_build_object('a', 1, 'b', 'x');
SELECT jsonb_build_array(1, 2, 3);
SELECT jsonb_object_agg(user_id, cnt) FROM ...;
SELECT jsonb_agg(t) FROM ...;
SELECT to_jsonb(row) FROM t row;
SELECT row_to_json(t) FROM t;

-- 设置(不存在则创建)
SELECT jsonb_set(payload, '{a,b}', '1'::jsonb);
SELECT jsonb_set(payload, '{a,b}', '1'::jsonb, false);   -- create_if_missing=false

-- 插入(仅数组:在指定位置插入)
SELECT jsonb_insert(payload, '{items,0}', '{"n":1}'::jsonb);
SELECT jsonb_insert(payload, '{items,0}', '{"n":1}'::jsonb, true);  -- 插到元素后

-- 删除
SELECT payload - 'a';
SELECT payload #- '{a,b}';

-- 合并:浅合并(顶层键覆盖)
SELECT payload || '{"new": 1}'::jsonb;
-- 深合并:PostgreSQL 没有内置函数,需要自己写一个(示例见《操作符与函数速查》,或应用层处理)
-- ⚠️ 注意:jsonb_deep_merge 不是官方函数,也不是任何扩展提供的,它是下面示例里自己创建的函数

-- 拼接数组
SELECT payload->'items' || '[{"n": 9}]'::jsonb;

-- 类型与判断
SELECT jsonb_typeof(payload), jsonb_typeof(payload->'items');
SELECT jsonb_array_length(payload->'items');
SELECT jsonb_object_keys(payload);
SELECT jsonb_strip_nulls(payload);

-- 展开为行
SELECT id, e.value FROM events, jsonb_array_elements(payload->'items') AS e(value);
SELECT id, k, v FROM events, jsonb_each(payload) AS x(k, v);
SELECT id, k, v FROM events, jsonb_each_text(payload) AS x(k, v);
```

**`jsonb_set` 与 `||` 的选择**

| 需求 | 用法 |
|------|------|
| 修改深层某个键 | `jsonb_set` / 下标赋值 |
| 顶层合并多个键 | `||` |
| 合并需要保留两边嵌套结构 | ⚠️ `||` 只做浅合并,需自行实现深合并 |

## 六、索引策略

JSONB 本身**不直接建索引**,需指定操作类(opclass)。

| 索引 | 支持的操作符 | 适用 |
|------|-------------|------|
| `GIN (col)` 默认 `jsonb_ops` | `@>` `<@` `?` `?|` `?&` | 通用,支持键存在性 |
| `GIN (col jsonb_path_ops)` | 仅 `@>` | 体积更小、`@>` 更快 |
| `BTREE (col)` | `=` `<` 等 | 整体相等/排序 |
| `BTREE ((col->>'x'))` | 表达式比较 | 单键高频查询 |
| 部分索引 | 配合 `WHERE` | 只索引子集 |

```sql
-- 通用:支持 @> ? ?| ?&
CREATE INDEX events_payload_gin ON events USING gin (payload);

-- 只做包含查询时更优(索引更小、@> 更快)
CREATE INDEX events_payload_gp ON events USING gin (payload jsonb_path_ops);

-- 高频单键:表达式索引
CREATE INDEX events_city_idx ON events ((payload->>'city'));

-- 数值字段:表达式 + 部分索引
CREATE INDEX events_vip_amount_idx ON events (((payload->>'amount')::numeric))
    WHERE payload @> '{"vip": true}';

-- 唯一性:JSONB 里的业务键也能做唯一索引
CREATE UNIQUE INDEX events_ext_id ON events ((payload->>'ext_id'));
```

**`jsonb_ops` vs `jsonb_path_ops` 取舍**

| 维度 | `jsonb_ops` | `jsonb_path_ops` |
|------|-------------|------------------|
| 支持 `?` `?|` `?&` | ✅ | ❌ |
| 支持 `@>` | ✅ | ✅(更快) |
| 索引大小 | 较大(每个键与值都建条目) | 较小(只为路径建哈希) |
| 选择 | 需要键存在性查询时 | 只做包含查询时 |

> **注意**:`jsonb_path_ops` 的索引**不能**用于 `?`(键存在性)。若你同时需要 `@>` 和 `?`,老实用 `jsonb_ops`。

**表达式索引与改写查询**

```sql
-- `payload->>'city'` 上建了 BTREE 索引,查询必须写成同一表达式
SELECT * FROM events WHERE payload->>'city' = '北京';   -- ✅ 可用索引

-- ⚠️ 换写法会失效
SELECT * FROM events WHERE payload @> '{"city":"北京"}';  -- 需要 GIN 索引
```

## 七、JSONB vs 规范化列的决策

| 维度 | JSONB | 规范化列 |
|------|-------|----------|
| 字段变动成本 | `ALTER TABLE` 不需要 | 需 DDL |
| 类型约束 | 弱(可加 CHECK 做部分约束) | 强 |
| 查询性能 | GIN 索引,但函数/转型成本高 | B-tree 最优 |
| 存储开销 | 键名重复存储,冗余大 | 紧凑 |
| 统计信息 | 差(规划器难估选择率) | 好 |
| 约束(外键、NOT NULL) | 基本不可用 | 完整 |
| 更新时间 | 需整块重写(整行更新) | 单列更新 |

**实践边界(重要)**

> **把"经常被查询和约束"的字段升级为正式列**;把"读少写少、结构多变"的字段放 JSONB。

```sql
-- ✅ 好:核心业务字段用列,扩展属性用 jsonb
CREATE TABLE products (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku     text NOT NULL UNIQUE,
    price   numeric(12,2) NOT NULL,          -- 常查、需精确 → 列
    attrs   jsonb NOT NULL DEFAULT '{}'      -- 品类差异属性 → jsonb
);

-- ⚠️ 反模式:所有字段都在 jsonb 里
CREATE TABLE bad (id bigint PRIMARY KEY, data jsonb);
-- 后果:无法外键、无法统计、查询都要转型、GIN 索引体积巨大
```

**对 JSONB 加约束**

```sql
ALTER TABLE products ADD CONSTRAINT attrs_is_obj CHECK (jsonb_typeof(attrs) = 'object');
ALTER TABLE products ADD CONSTRAINT attrs_color_type
    CHECK (attrs @> '{}' AND (attrs->>'color') IS NOT NULL);
```

## 八、常见陷阱

| 陷阱 | 说明 | 修正 |
|------|------|------|
| 用 `->` 做数值比较 | 得到 JSONB,比较语义是按类型 | 用 `->>` 再转型 |
| `@>` 与 `?` 混用但只建了 `jsonb_path_ops` | `?` 走不了索引 | 建 `jsonb_ops` |
| 更新的代价被低估 | 改任一键要重写整行与所有索引 | 高频改动的键升为列 |
| 依赖键顺序 | jsonb 不保留键序 | 不要依赖 |
| 用 JSONB 做唯一业务键但没加唯一索引 | 数据可重复 | 建唯一表达式索引 |
| 大 JSONB 撑爆 TOAST | 单个值 > 2KB 会进 TOAST 表 | 拆表或拆列 |
| 中文键名 | 可用但索引与可读性差 | 统一用英文键名 |

## 九、实战要点速查

```sql
-- 1) 幂等写入 + 局部更新
INSERT INTO events (id, payload) VALUES (1, '{"n":1}')
ON CONFLICT (id) DO UPDATE SET payload = events.payload || EXCLUDED.payload;

-- 2) 从关系数据生成 JSONB 文档
SELECT jsonb_build_object(
    'order_id', o.id,
    'items', (SELECT jsonb_agg(jsonb_build_object('sku', p.sku, 'qty', i.qty))
              FROM order_items i JOIN products p ON p.id = i.product_id
              WHERE i.order_id = o.id))
FROM orders o WHERE o.id = 100;

-- 3) 把 JSONB 拆回关系表
INSERT INTO flat (id, k, v)
SELECT e.id, x.k, x.v FROM events e, jsonb_each_text(e.payload) AS x(k, v);

-- 4) 数组元素聚合查询
SELECT id FROM events WHERE payload @> '{"tags": ["urgent"]}';
```
