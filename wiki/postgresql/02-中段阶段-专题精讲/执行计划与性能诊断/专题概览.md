# 执行计划与性能诊断 · 专题概览

## 专题定位

**读懂执行计划是从"会写 SQL"到"会调优 SQL"的分水岭。** 本专题建立一套"看到计划 → 定位瓶颈 → 给出对策"的方法论。

**何时该翻这个专题**

- 查询慢,不知道慢在哪
- 想知道为什么没走索引
- 需要判断优化是否真的有效

## 一、诊断工具箱

| 工具 | 用途 |
|------|------|
| `EXPLAIN` | 看计划(不执行) |
| `EXPLAIN ANALYZE` | 看计划 + 实际执行统计 |
| `EXPLAIN (ANALYZE, BUFFERS)` | **加看 I/O 与缓存命中** ← 最有用 |
| `EXPLAIN (ANALYZE, VERBOSE, SETTINGS, WAL)` | 更多细节(配置、WAL 量) |
| `pg_stat_statements` | 聚合统计:谁最耗资源 |
| `auto_explain` | 自动记录慢查询的计划 |
| `log_min_duration_statement` | 记录慢 SQL |
| `pg_stat_activity` | 实时看正在跑什么 |
| `pg_stat_user_tables` / `pg_stat_user_indexes` | 表/索引级访问统计 |
| `track_io_timing = on` | 让 BUFFERS 显示真实 I/O 耗时 |
| `pg_stat_progress_*` | 长操作(VACUUM、建索引)进度 |

## 二、计划的结构:一棵树

执行计划是**自底向上**的树,数据从叶子流向根。

```
Limit                          ← 根:最后执行
  ->  Sort                     ← 中间节点
        Sort Key: created_at DESC
        ->  Seq Scan on orders ← 叶子:最先执行
              Filter: ...
```

**读法**:缩进层数表示父子关系;同一层的多个节点按**从上到下**顺序执行。

## 三、`EXPLAIN` 输出的三段信息

```
Seq Scan on orders  (cost=0.00..38462.00 rows=12 width=16) (actual time=0.015..198.443 rows=15 loops=1)
   ↑节点类型    ↑对象   ↑估算段                      ↑实际段(仅 ANALYZE)
```

| 字段 | 含义 |
|------|------|
| `cost=启动..总` | 估算代价(任意单位),启动代价是"出第一行前的成本" |
| `rows` | **估算**输出行数 |
| `width` | 估算每行字节数 |
| `actual time=启动..总` | 实际耗时(毫秒,含子节点) |
| `actual rows` | **实际**输出行数 |
| `loops` | 该节点被执行次数 |

> **关键技巧:比较估算 `rows` 与实际 `rows`。** 差一个数量级以上,说明规划器的估算出了问题,它很可能因此选了错误的算法。

**`loops` 的陷阱**:`actual rows` 是**每次循环**的行数,总行数 = `rows × loops`;`actual time` 也是**每次**的时间(括号内的总时间已含子节点)。

## 四、常见节点类型

### 扫描节点

| 节点 | 含义 | 何时出现 |
|------|------|----------|
| `Seq Scan` | 全表顺序扫描 | 无可用索引,或索引选择性差(要读大部分行) |
| `Index Scan` | 走索引,再回表取其他列 | 选择性好,需回表 |
| `Index Only Scan` | 只读索引,**不回表** | 索引覆盖所需列 + 可见性映射干净 |
| `Bitmap Index Scan` | 先扫索引构造位图 | 需要读较多行但不够多到全表扫 |
| `Bitmap Heap Scan` | 按位图顺序读表页 | 上面 + 回表;可把随机 I/O 变为近似顺序 |
| `Tid Scan` / `CTE Scan` / `Subquery Scan` / `Values Scan` / `Function Scan` | 特定来源 | |

> **Index Only Scan 与 `Heap Fetches`**:即使走了 Index Only Scan,若可见性映射(VM)不干净,仍要回表检查可见性。看 `Heap Fetches` 是否很大 —— 大则说明需要 `VACUUM`。

### 连接节点

| 节点 | 算法 | 适用 |
|------|------|------|
| `Nested Loop` | 双层循环,内侧可走索引 | 驱动集小,内侧有索引 |
| `Hash Join` | 建哈希表 + 探测 | 等值连接,中等/大数据集 |
| `Merge Join` | 两侧有序归并 | 两侧已按连接键有序 |

### 其他节点

| 节点 | 说明 |
|------|------|
| `Sort` | 排序;看 `Sort Method` 是否落盘 |
| `Hash` / `HashAggregate` / `GroupAggregate` | 哈希聚合 / 排序聚合 |
| `Limit` | 限制行数 |
| `Materialize` | 物化子结果(供多次复用) |
| `Memoize` | 缓存内侧结果(避免重复扫描) |
| `Gather` / `Gather Merge` | 并行执行的结果汇总 |
| `WindowAgg` | 窗口函数 |
| `Append` / `Merge Append` | 分区/UNION 的多个子计划 |
| `SetOp` | 交/并/差 |
| `LockRows` | `FOR UPDATE/SHARE` |
| `Result` | 无表来源或仅做表达式计算 |

## 五、诊断决策树

```
EXPLAIN (ANALYZE, BUFFERS) 输出
│
├─ 有 Sort 且 "Method: external merge Disk" ──→ 排序落盘
│     对策:建同序索引 / 调大 work_mem / 缩小排序行数
│
├─ Seq Scan + "Rows Removed by Filter" 很大 ──→ 缺索引或索引不可用
│     对策:建索引 / 检查函数与类型转换 / 检查部分索引条件
│
├─ rows 估算与 actual 差 10 倍以上 ──→ 统计信息问题
│     对策:ANALYZE / CREATE STATISTICS / 提高 statistics target
│
├─ Nested Loop 且 loops 很大 ──→ 内侧被反复执行
│     对策:给内侧连接列建索引;或让规划器改选 Hash Join(修估算)
│
├─ Buffers: shared read 很大而 hit 很小 ──→ 缓存未命中,物理读
│     对策:增大 shared_buffers / 优化访问模式 / 减少扫描量
│
├─ Heap Fetches 很大 ──→ 可见性映射不干净
│     对策:VACUUM
│
└─ 计划本身合理但仍慢 ──→ 数据量或结构问题
      对策:分区 / 归档 / 物化视图 / 结构重构
```

## 六、并行查询

```sql
SHOW max_parallel_workers_per_gather;   -- 每个 Gather 节点最多几个 worker
SHOW parallel_setup_cost;               -- 启动并行开销
SHOW min_parallel_table_scan_size;      -- 表多小就不并行

-- 强制关闭并行(对比用)
SET max_parallel_workers_per_gather = 0;
```

计划中出现 `Gather` / `Gather Merge` 即为并行。

**PG18 起**:`FULL OUTER JOIN` 与 `RIGHT OUTER JOIN` 也支持并行执行(此前只有部分连接类型可并行)。
