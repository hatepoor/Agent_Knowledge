# 数组 / 范围 / 枚举 · 专题概览

## 专题定位

这三类类型解决共同的问题:**一个单元格里表达"多个值"或"一段区间"**,避免过早拆表。

**何时该翻这个专题**

- 一篇文章有多个标签,查询"含某标签"的文章
- 商品预订、房间排期,要判断时间是否冲突
- 价格区间、年龄段匹配
- 状态字段需要类型安全且排序符合业务直觉

## 一、数组(回顾与补充)

基础语法见 [[postgresql/01-入门阶段-基础教程/第02章-数据类型/2.5-数组与JSON初步]]。此处补充实战要点。

### 运算符语义澄清(高频误区)

| 运算符 | 语义 | 例子 |
|--------|------|------|
| `@>` | 左数组**包含**右数组的**所有**元素 | `'{a,b,c}' @> '{a,b}'` → `t` |
| `<@` | 左数组是右数组的子集 | `'{a}' <@ '{a,b}'` → `t` |
| `&&` | 两数组**有交集** | `'{a,x}' && '{x,b}'` → `t` |
| `= ANY(arr)` | 某值等于数组中**任一**元素 | `'a' = ANY('{a,b}')` → `t` |
| `<> ALL(arr)` | 某值不等于数组中**所有**元素 | `'z' <> ALL('{a,b}')` → `t` |
| `\|\|` | 拼接 | `'{a}' \|\| '{b}'` → `{a,b}` |

> **`@>` 与 `= ANY` 的差异是重点**:
> - `tags @> ARRAY['a']` = "tags 里含 a"
> - `'a' = ANY(tags)` = "数组里存在等于 a 的元素"
>
> 单元素时两者等价,但语义方向相反,且 `@>` 对多元素是"全部包含",`= ANY` 只匹配单值。**以为它们可以互换是最常见的错误。**

```sql
-- 含 a 且含 b
SELECT * FROM posts WHERE tags @> ARRAY['a','b'];

-- 含 a 或含 b
SELECT * FROM posts WHERE tags && ARRAY['a','b'];

-- 恰好为 {a,b}(顺序与元素都相同)
SELECT * FROM posts WHERE tags = ARRAY['a','b'];
```

### 数组索引

```sql
-- GIN:支持 @> && <@ =(需 array_ops)
CREATE INDEX posts_tags_gin ON posts USING gin (tags);

-- GIN + array_ops:同时也支持部分高级操作
CREATE INDEX posts_tags_gin2 ON posts USING gin (tags array_ops);

-- 单元素查询也能用 GIN
SELECT * FROM posts WHERE tags @> ARRAY['a'];
```

### 数组展开与聚合的实用模式

```sql
-- 标签统计(最常用)
SELECT tag, count(*) AS cnt
FROM posts, unnest(tags) AS tag
GROUP BY tag ORDER BY cnt DESC;

-- 标签共现(同一文章里同时出现的标签对)
SELECT a.tag AS tag_a, b.tag AS tag_b, count(*)
FROM posts, unnest(tags) AS a(tag), unnest(tags) AS b(tag)
WHERE a.tag < b.tag
GROUP BY 1,2 ORDER BY 3 DESC;

-- 数组去重
SELECT ARRAY(SELECT DISTINCT unnest(tags) FROM posts WHERE id = 1);

-- 数组排序
SELECT ARRAY(SELECT unnest(tags) ORDER BY 1) FROM posts;

-- 数组合并(聚合多行)
SELECT user_id, array_agg(DISTINCT tag) FROM user_tags GROUP BY user_id;
```

### 数组 vs 关联表

| 判据 | 数组 | 关联表 |
|------|------|--------|
| 元素数量 | 少且固定(标签、权限位) | 多或不定 |
| 元素需要属性 | ❌ 不行 | ✅ |
| 需要外键约束 | ❌ | ✅ |
| 需要频繁增删单个元素 | ⚠️ 整列重写 | ✅ |
| 查询模式 | "含某元素"、交集 | 复杂 JOIN、聚合 |
| 典型 | 标签、角色位、经纬度 | 订单行、评论、关注关系 |

**结论**:元素是"轻量、无序、只做包含判断"时用数组;元素有属性、需约束、需统计时用关联表。

## 二、范围类型(range)

### 内置范围类型

| 类型 | 说明 |
|------|------|
| `int4range` / `int8range` | 整数区间 |
| `numrange` | numeric 区间 |
| `tsrange` / `tstzrange` | 时间戳区间(带/不带时区) |
| `daterange` | 日期区间 |

**PG14+ 新增 multirange**:`int4multirange`、`tsmultirange` 等,可存**多段不连续区间**。

### 区间边界语义(核心)

范围类型用**方括号/圆括号**表示边界开闭:

```
[1, 5]   包含 1 和 5      (闭区间)
[1, 5)   包含 1,不含 5    (左闭右开)  ← PostgreSQL 规范化后优先用这个
(1, 5]   不含 1,包含 5
(1, 5)   都不含
```

> **规范化**:PostgreSQL 会把离散类型的范围**规范化**为左闭右开。所以 `[1,5]::int4range` 实际存储为 `[1,6)`。

```sql
SELECT '[1,5]'::int4range;    -- [1,6)
SELECT '[1,5)'::int4range;    -- [1,5)
SELECT '(1,5]'::int4range;    -- [2,6)
```

### 运算符

| 运算符 | 语义 |
|--------|------|
| `@>` | 包含元素或子区间 |
| `<@` | 被包含 |
| `&&` | 重叠(有交集) |
| `<<` | 完全在左 |
| `>>` | 完全在右 |
| `&<` | 不延伸到右侧之外 |
| `&>` | 不延伸到左侧之外 |
| `-|-` | 相邻(相接) |
| `+` `-` `*` | 并集 / 差集 / 交集 |
| `@>` `&&` 等 | |

```sql
SELECT '[1,5)'::int4range && '[4,9)'::int4range;    -- t(重叠)
SELECT '[1,5)'::int4range @> 3;                     -- t(包含元素)
SELECT date '2026-09-19' <@ daterange('2026-01-01','2026-12-31');  -- t
SELECT '[1,5)'::int4range * '[3,9)'::int4range;     -- [3,5)(交集)
SELECT '[1,5)'::int4range + '[5,9)'::int4range;     -- [1,9)(并集,相接时合并)
```

### 构造与检查函数

```sql
SELECT int4range(1, 5);                              -- [1,5)
SELECT int4range(1, 5, '[]');                        -- 显式指定边界
SELECT daterange('2026-01-01', '2026-02-01');
SELECT tstzrange(now(), now() + interval '1 day');

SELECT lower('[1,5)'::int4range), upper('[1,5)'::int4range);       -- 1, 5
SELECT lower_inc('[1,5)'::int4range), upper_inc('[1,5)'::int4range);-- t, f
SELECT isempty('empty'::int4range);                                 -- t
SELECT range_merge(...);
SELECT unnest(r) FROM (SELECT int4multirange(int4range(1,3), int4range(7,9)) AS r) t;
```

### 实战:排期防重叠

**这是范围类型最经典的应用**。

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 让等值也可用于 GiST

CREATE TABLE room_bookings (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room    text NOT NULL,
    during  tstzrange NOT NULL,
    who     text,
    CONSTRAINT no_overlap EXCLUDE USING gist (room WITH =, during WITH &&)
);

INSERT INTO room_bookings (room, during, who)
VALUES ('A', '[2026-09-19 09:00+08, 2026-09-19 11:00+08)', 'Ann');

-- 重叠 → 被拒绝
INSERT INTO room_bookings (room, during, who)
VALUES ('A', '[2026-09-19 10:00+08, 2026-09-19 12:00+08)', 'Ben');
-- ERROR: conflicting key value violates exclusion constraint "no_overlap"

-- 相接不重叠 → 允许
INSERT INTO room_bookings (room, during, who)
VALUES ('A', '[2026-09-19 11:00+08, 2026-09-19 12:00+08)', 'Ben');
```

**实战:查找空闲时段**

思路分四步:① 把所有"已占用区间"聚合成一个多段区间 → ② 构造"全天区间" → ③ 两者做差集 → ④ 把结果展开成一行行空闲段。

```sql
-- ① range_agg      :聚合函数,把多行区间收集成一个 multirange(多段区间)
-- ② tstzmultirange :类型构造器,把单个区间包装成 multirange(这样才能参与下面的差集运算)
-- ③  -             :运算符,两个 multirange 相减 = 差集,即"全天减去已占用"
-- ④ unnest         :表函数,把多段区间展开成多行,每行一个空闲时段
WITH taken AS (
    SELECT range_agg(during) AS busy
    FROM room_bookings WHERE room = 'A'
)
SELECT unnest(
           tstzmultirange(tstzrange('2026-09-19 08:00+08','2026-09-19 18:00+08'))
           - busy
       ) AS free_slot
FROM taken;
```

**逐个认识这里出现的名字**

| 名称 | 属于哪一类 | 作用 | 引入版本 |
|------|-----------|------|----------|
| `range_agg(区间列)` | 聚合函数 | 把多行的区间收集成**一个 multirange** | PG14+ |
| `tstzmultirange(区间)` | 类型构造器 | 把**单个**区间包装成 multirange,以便与另一个 multirange 做运算 | PG14+ |
| `A - B` | 运算符 | multirange **差集**:从 A 中减去 B 覆盖的部分 | PG14+ |
| `unnest(multirange)` | 表函数 | 把多段区间**拆成多行**,一行一段 | PG14+ |

> **为什么必须先 `range_agg`**:差集运算符 `-` 只接受"multirange 减 multirange"。而 `room_bookings` 里是**多行单区间**,不能直接与一个区间做差,所以要先聚合成一整个 multirange。这是 range 类型里最容易卡住的一步。
>
> 想先理解 multirange 与单区间的差别,见本页「二、范围类型」中的类型表。

### 实战:价格/年龄区间匹配

```sql
CREATE TABLE price_tiers (
    tier     text,
    price_r  numrange,
    EXCLUDE USING gist (price_r WITH &&)      -- 档位之间不得重叠
);
INSERT INTO price_tiers VALUES
  ('low',  '[0,100)'),
  ('mid',  '[100,1000)'),
  ('high', '[1000,)');

-- 某金额落在哪一档
SELECT tier FROM price_tiers WHERE price_r @> 5999::numeric;      -- high
```

## 三、枚举与替代方案

基础见 [[postgresql/01-入门阶段-基础教程/第02章-数据类型/2.4-布尔枚举与UUID]]。此处补充**决策框架**。

### 三方案完整对比

| 维度 | `enum` | `text + CHECK` | 查找表 + FK |
|------|--------|----------------|-------------|
| 类型安全 | ✅ | ✅ | ✅ |
| 新增值 | `ALTER TYPE ... ADD VALUE` | 重建约束 | `INSERT` |
| 删除值 | ❌ 几乎不可行 | 重建约束 | `DELETE`(需处理引用) |
| 调整顺序 | ❌ 需重建类型 | 天然按值排序 | 用 `sort_order` 列 |
| 携带元数据 | ❌ | ❌ | ✅(显示名、颜色、是否启用) |
| 多语言显示名 | ❌ | ❌ | ✅ |
| 排序可定制 | 声明顺序 | 需 CASE/数组 | `sort_order` 列 |
| 存储 | 4 字节序号 | 变长文本 | 4/8 字节外键 |
| 迁移(多库同步) | 困难(需同步类型) | 容易 | 容易 |
| 适合 | 稳定的技术枚举 | 会演进的状态 | 需要元数据的业务字典 |

### 决策树

```
该选项集合会被业务后台维护吗?
  ├─ 是 → 查找表
  └─ 否 → 会频繁增删吗?
           ├─ 是 → text + CHECK
           └─ 否 → 需要按业务顺序排序吗?
                    ├─ 是 → enum(声明顺序即排序) 或 查找表(带 sort_order)
                    └─ 否 → enum 或 text + CHECK 均可,优先 text + CHECK(更易演进)
```

> **个人偏好建议**:默认选 **`text + CHECK`**。它兼具类型安全与演进灵活,且不引入类型系统耦合。只有"选项绝对稳定 + 需要按语义顺序排序"时才用 `enum`。

### 枚举的迁移与演进操作

```sql
-- 新增值(可在事务内,但同事务不能使用新值)
ALTER TYPE order_status ADD VALUE IF NOT EXISTS 'refunded';

-- 新增值并指定位置
ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'done';

-- 重命名值(PG10+)
ALTER TYPE order_status RENAME VALUE 'canceled' TO 'cancelled';

-- 删除值:无原生支持,需重建类型
BEGIN;
ALTER TYPE order_status RENAME TO order_status_old;
CREATE TYPE order_status AS ENUM ('pending','paid','shipped','done');
ALTER TABLE orders ALTER COLUMN status TYPE order_status
    USING status::text::order_status;      -- 需确保无 'canceled' 数据
DROP TYPE order_status_old;
COMMIT;
```

**从 enum 迁移到 text**(减少耦合):

```sql
ALTER TABLE orders ALTER COLUMN status TYPE text USING status::text;
-- 然后加 CHECK 约束
ALTER TABLE orders ADD CONSTRAINT orders_status_ck
    CHECK (status IN ('pending','paid','shipped','done'));
DROP TYPE order_status;
```

**从 text 迁移到 enum**(收紧约束):

```sql
CREATE TYPE order_status AS ENUM ('pending','paid','shipped','done');
ALTER TABLE orders ALTER COLUMN status TYPE order_status
    USING status::order_status;   -- 若有不合法值会报错,先清洗数据
```

### 枚举的排序陷阱

```sql
-- enum 按声明顺序排
ORDER BY status;                         -- 声明顺序

-- text 按排序规则排(字典序),通常不是业务想要的
ORDER BY status;                         -- 'canceled','done','paid','pending','shipped'

-- text 想按业务顺序 → 显式映射
ORDER BY array_position(ARRAY['pending','paid','shipped','done','canceled'], status);
-- 或查找表的 sort_order 列
```

## 四、常见陷阱汇总

| 陷阱 | 说明 | 修正 |
|------|------|------|
| 混淆 `@>` 与 `= ANY` | 语义方向不同 | 明确"全部包含"还是"存在匹配" |
| 数组元素顺序被当作有意义 | `={a,b}` 与 `={b,a}` 不等 | 存前排序,或改用关联表 |
| 用数组存可变长的重要数据 | 无法约束、无法 JOIN | 用关联表 |
| 忽略范围规范化 | `[1,5]` 实际是 `[1,6)` | 用 `lower_inc`/`upper_inc` 判断,别硬编码 |
| 连续型范围(时间)用整数写法 | `tsrange(1,5)` 是时间戳 | 传 timestamp |
| 用 `EXCLUDE` 但没装 `btree_gist` | 报错 | `CREATE EXTENSION btree_gist` |
| enum 删值 | 无原生支持 | 重建类型 |
| 大范围表无 GiST 索引 | `EXCLUDE` 会自动建,但手写 `&&` 查询需索引 | 建 GiST |
